5.3

Two gates: where a person approves兩道門：人在哪裡批准哪些事必须由人来批？

This chapter assumes you have read Ask or refuse and Guardrails: why "ask me first" is not a limit, and why the agent must not be able to edit the rules.

讀這一章之前，你需要先讀過 詢問不是限制 和 保護規則本身的檔案：為什麼「先問我」不是限制，以及為什麼 agent 不能改規則。

读这一章之前，你要读过“先问我”为什么挡不住 Agent？和别让 Agent 改自己的规则：为什么“先问我”不是限制，以及为什么 agent 不能有权编辑规则。

The Knowledge經驗分享经验分享

In one sentence

Put a person at the points that cost money, grant power or cannot be undone. Make the approval come through a channel the agent cannot reach, and bind it to exactly the plan that was approved.

一句話

在花錢、授權、不能反悔的地方放一個人。讓批准從 agent 碰不到的管道進來，而且只綁定到被批准的那一份計畫。

一句话

在花钱、授权、无法撤销的地方放一个人。让审批走 agent 够不着的渠道，并把它绑定到被批准的那份计划上，一字不差。

For leaders

  • The decision: where a person must approve. Put them at the points that cost money, grant power or cannot be undone, and nowhere else. The approval must come through a channel the agent cannot reach, and it must belong to exactly the plan or change the person read.
  • The risk: a confirmation box can be switched off for the session without anyone noticing, and an approval the agent can give itself is not an approval. Even a real approval has a weak spot, because a tired person can still approve without reading. Binding the approval to the content stops a swap, not a careless yes.
  • The cost of doing it right: each gate costs a person one read and one command, and with too many gates people stop reading. In my setup, snapshots at the gates are kept for 14 days by default.
  • Ask the team: "Which approvals in our flow could the agent give itself or switch off, and does an approval still count if the plan changes afterwards?"

給主管

  • 要做的決定：人必須在哪裡批准。只放在花錢、授權、不能反悔的地方，其他地方都不放。批准必須走 agent 碰不到的管道，而且只屬於人讀過的那份計畫或那次改動。
  • 風險：確認框可以在整個會話裡被關掉，沒有人會發現；agent 能自己給的批准，也算不上批准。就算批准是真的，也有弱點，因為人累了還是可能不讀就批准。把批准綁到內容上，擋得住掉包，擋不住隨手按的「同意」。
  • 做對的成本：每道門要人讀一次、輸入一個指令，門一多，人就不讀了。在我的設定裡，門上的快照預設保留 14 天。
  • 可以問團隊：「我們的流程裡，哪些批准是 agent 能自己給或自己關掉的？計畫事後改了，批准還算數嗎？」

写给管理者

  • 要拍板的事：哪些地方必须由人审批。只放在花钱、授权、无法撤销的地方，别处都不放。审批必须走 agent 够不着的渠道，而且只属于人读过的那份计划或那次改动。
  • 风险：确认框可以在整个会话里被关掉，没有人会注意到；agent 自己能给的审批，也算不上审批。就算审批是真的，也有软肋，因为人累了照样可能不读就批。把审批绑定到内容上，能防住调包，防不住随手点的“同意”。
  • 做对的代价：每道关卡要人读一遍、敲一条命令，关卡一多，人就不读了。在我的配置里，关卡处的快照默认保留 14 天。
  • 可以问团队：“我们的流程里，哪些审批是 agent 能自己给、或者能关掉的？计划事后改了，审批还算数吗？”

Why a confirmation box is not an approval

You want a person to approve the important steps, and the obvious tool is already in front of you: the confirmation box that the agent tool shows, asking "Allow this?" It does not work well, for two reasons. The first is that people click Allow. By the hundredth box they are no longer reading it (Ask or refuse). The second is that many tools let you tick "allow for this session", after which the box never appears again. The approval you relied on is gone, and nothing tells you.

A third problem is subtler. Suppose that instead of a box, the approval is a command the person types. If the agent can run commands, it can type that command too. An approval that the agent can give is not an approval.

Where, then, should the person stand? And how can their yes become something the agent can neither produce nor reuse?

確認框為什麼算不上批准

你希望重要的步驟由人來批准，而最直接的工具就在眼前：agent 工具跳出來的確認框，問你「允許這個嗎？」可是它效果不好，原因有兩個。一是人會按允許，到了第一百個框，早就沒在讀了（詢問不是限制）。二是很多工具可以勾「這個會話都允許」，勾了之後，框就再也不會出現。你倚靠的批准就這樣不見了，也沒有任何東西告訴你。

還有第三個問題，比較不容易察覺。假設批准不是一個框，而是一個由人輸入的指令。可是如果 agent 能執行指令，它也能輸入同一個指令。一個 agent 自己就能給的批准，算不上批准。

那麼，人要放在哪裡？他的「同意」又怎樣才能成為 agent 既造不出來、也沒辦法重複使用的東西？

确认框为什么算不上审批

你希望重要的步骤由人来批准，而最顺手的工具就摆在眼前：agent 工具弹出来的确认框，问你“允许吗？”可它不太管用，原因有两个。一是人会点“允许”，到了第一百个框，早就不读了（见“先问我”为什么挡不住 Agent？）。二是很多工具可以勾选“本次会话都允许”，勾了之后这个框再也不会出现。你指望的审批就这样没了，也没有任何东西提醒你。

还有第三个问题，更不容易察觉。假设审批不是一个框，而是人敲的一条命令。可如果 agent 能运行命令，它也能敲这条命令。一个 agent 自己就能给出的审批，算不上审批。

那么，人该放在哪里？他的“同意”又怎样才能成为 agent 既造不出来、也没法重复使用的东西？

Where to put the person, and how to make the yes count

Where to put the person

The first question has a short answer. A person's attention is the scarcest thing in the system, so spend it on three kinds of point and nowhere else. Some points cost money, such as starting an expensive run. Some grant power, such as letting the agent write to a shared repository. And some cannot be undone: once the step is done, nothing takes it back.

Most of the agent's work is none of these, since everything inside a task folder is cheap to redo and the agent can work there freely (Manage tasks, not chats). A task that changes a real repository, though, has two points of this kind. I call each of them a gate, because the task cannot pass it until a person approves.

Gate 1: approve the plan

The first gate comes before any work file changes. The agent writes the requirement and a plan and then stops, and until the person has read the plan and approved it, the agent may draft and read but may not start on the changes.

The reason for stopping here is cost, since a wrong plan is cheap to fix while it is still a paragraph but expensive to fix once it has become a finished change. In my setup the plan also stands on a confirmed requirement (The agent writes the requirement), so one approval can confirm both.

Gate 2: approve the write-back

By the second gate, the agent has made its changes in the task folder and the checks have run. What is left is to copy the result to the real repository, a step called the write-back. Before that happens, the person reads the exact diff, which is the list of lines that would change, and then approves it.

Even an approved write-back does not go straight to the main branch. It goes to a new branch of the repository and is left uncommitted. And before anything is written, code checks that:

  • the working tree is clean,
  • the branch name is free,
  • none of the files to change has moved on the main branch since it was copied.

If any repository fails a check, nothing is written. This is also where two people, or two tasks, changing the same file are found, by the program here rather than later in a review.

Why the approval is typed in a terminal

Now the second question. How do you make a yes the agent cannot produce? A confirmation box in the chat can be switched off by "allow for this session", but a code that the person types in a terminal cannot. That is why the approval is a command that needs a real terminal. The design stands on two legs, though, and the terminal is only the first.

On its own, the terminal is not a wall. A check that "this is a terminal" is not a security boundary, because a determined program can imitate one. So what stops a program that pretends?

That is the second leg, a hook. When an agent tries to run the approval command, this piece of code refuses the attempt outright. It must sit outside the agent's reach, as Guardrails explains: if the hook is gone, or the agent can edit it, the approval is only a polite request. Neither leg is enough alone.

The hook, in turn, has to keep refusing when something goes wrong. The enforcement layer lets a call through when it breaks itself (Build the enforcement layer like software), so the refusal of the approval command belongs on the short list of rules that must block even when the hook errors. Otherwise this leg breaks exactly when it is needed.

None of this means the person reads the plan in the terminal. Plans and diffs are hard to read there, so the person reads them in an editor, while the terminal shows only the file path and the code to type. Reading and approving are separate acts on purpose.

Tie the approval to what was read

That leaves reuse. Suppose the person approves a plan, and then the agent edits the plan. Is the approval still good? It should not be. That is why the code the person types is derived from the plan's content. It is a hash, a fingerprint that changes if a single character changes, so when the plan changes after approval, the approval no longer matches and the gate closes again.

The same goes for the write-back, where the approval belongs to the exact diff that was shown. This is what "bind it to exactly the plan that was approved" means. Without it, a person approves one thing and the agent delivers another.

Snapshots at the gates

Besides deciding what may go forward, the gates are where the work is saved. When the plan is approved, before each check, and before the dry run of a write-back, a copy of the work (a snapshot) is saved automatically, so that when something breaks, the state of that moment can be found again. In my setup they are kept for 14 days by default.

Finding a state again is not the same as going back to it, though. A failure in the middle of a write to several repositories is not rolled back by itself. Instead the task goes to a "partly written" state, and a person runs a recovery. I chose not to guess at an automatic undo.

Several rounds

A task does not always end at the write-back. The same goal can come back, because a reviewer finds a defect or someone asks for a change. In that case a new round starts, in which the old work moves aside, a new plan is written and both gates apply again. A different goal, by contrast, is a new task.

Testing in other environments looks like another round, but it is not. The agent cannot run anything there, so the person does the running, and the work becomes its own task of kind testing, in which the agent writes the instructions, waits for the person's results and judges them. If a test fails, it goes back to the development task as a new round.

Without any of this machinery

The habit behind the gates works by hand too. Read the plan before you tell the agent to go, read the diff before you commit, and do not tick "allow for this session" on a tool that writes. The machinery above only makes sure these things happen when you are tired or not there.

人要放在哪裡，又怎樣讓他的「同意」算數

人要放在哪裡

第一個問題的答案很簡單。人的注意力是整個系統裡最稀少的東西，所以只把它花在三種地方，其他地方一概不花。有些地方要花錢，例如開始一次昂貴的執行；有些地方會授權，例如讓 agent 寫入共用的倉庫；還有些地方不能反悔，一旦做了，就再也收不回來。

agent 大部分的工作都不屬於這三種，因為任務資料夾裡的一切重做都很便宜，agent 在那裡可以自由工作（管任務，不管對話）。不過，一個會改動真實倉庫的任務，會遇到兩個這樣的地方。我把每一個都叫做一道門，因為人批准之前，任務過不去。

第一道門：批准計畫

第一道門設在任何工作檔案被改動之前。agent 寫出需求和計畫之後就停下來，在人讀完計畫、批准之前，它可以起草、可以讀，但還不能動手改。

之所以停在這裡，是為了成本。計畫錯了，還只是一段文字的時候改起來很便宜，等它變成做完的改動再改，就很貴了。在我的設定裡，計畫也建立在已確認的需求上（需求由 agent 寫，人確認），所以一次批准可以把兩者一起確認。

第二道門：批准寫回

到了第二道門，agent 已經在任務資料夾裡做完改動，檢查也跑過了，剩下的就是把結果複製到真實的倉庫，這一步叫寫回。寫回之前，人要讀那份確切的 diff，也就是會被改動的那些行的清單，然後才批准。

就算批准了，寫回也不會直接進主分支。結果會進到倉庫的一個新分支，而且不提交。而且在真正寫入之前，程式會先檢查：

  • 工作樹是乾淨的，
  • 分支名稱沒被用掉，
  • 要改的檔案，自從被複製之後，在主分支上都沒有動過。

只要有一個倉庫沒通過檢查，就什麼都不寫。兩個人、或兩個任務改了同一個檔案，也是在這裡被發現的，而且是由這裡的程式發現，不是之後在審查裡才發現。

為什麼批准要在終端機裡輸入

再看第二個問題的前一半：怎麼讓一個「同意」成為 agent 造不出來的東西？聊天裡的確認框可以被「這個會話都允許」關掉，人在終端機裡輸入的一串碼卻關不掉，所以批准被做成一個需要真正終端機的指令。不過，這個設計是站在兩條腿上的，終端機只是其中一條。

可是光靠終端機，算不上一道牆。檢查「這是不是終端機」並不是安全邊界，因為有心的程式可以假裝成終端機。那要是真有程式假裝，靠什麼擋住它？

靠的是第二條腿，也就是 hook。agent 只要想執行批准指令，這段程式碼就會直接拒絕。它必須放在 agent 碰不到的地方，就像保護規則本身的檔案說的：如果這個 hook 不見了，或 agent 能編輯它，批准就只剩一個客氣的請求。兩條腿，單靠任何一條都不夠。

而 hook 本身出錯的時候，也必須照樣拒絕。執行層在自己壞掉時會放行呼叫（把執行層當軟體來設計），所以拒絕批准指令這一條，要放進那份「即使 hook 出錯也必須擋住」的短清單。不然的話，這條腿剛好會在最需要它的時候斷掉。

這不表示人要在終端機裡讀計畫。計畫和 diff 在終端機裡很難讀，所以人是在編輯器裡讀，終端機只顯示檔案路徑和要輸入的碼。讀和批准是兩個動作，這是故意分開的。

把批准綁到讀過的內容

剩下的是後一半：重複使用。假設人批准了一份計畫，之後 agent 又改了這份計畫，那批准還有效嗎？不應該有效。正因為這樣，人要輸入的碼是從計畫的內容算出來的。它是一個 hash，像一枚指紋，只要改一個字就會變；所以批准之後計畫一變，批准就對不上，門也就重新關上了。

同樣地，寫回的批准只屬於當時顯示的那份確切的 diff。「綁定到被批准的那一份計畫」就是這個意思。沒有這一步，人批准的是一樣東西，agent 交出的卻可能是另一樣。

門上的快照

門除了決定什麼可以往下走，也負責把工作存下來。計畫被批准時、每次檢查之前、寫回的試跑之前，都會自動存一份工作的副本（快照），這樣哪裡壞了，那個時刻的狀態就找得回來。在我的設定裡，快照預設保留 14 天。

不過，找得回某個狀態，不等於能自動退回去。寫入多個倉庫的途中失敗了，不會自動回復，任務會進入「寫了一部分」的狀態，由人執行恢復。自動還原只能靠猜，我寧可不做。

多輪

任務不一定在寫回之後就結束。同一個目標可能再回來，例如 reviewer 找到缺陷，或有人要求改動，這時就開始新的一輪：舊的工作移到一旁，重新寫計畫，兩道門都再走一次。如果是不同的目標，那就是新任務。

在其他環境測試，看起來像是又一輪，其實不是。agent 在那裡什麼都不能執行，只能由人來跑，所以這件事另外開成一個測試類的任務：agent 寫好說明，等人給結果，再判斷結果。測試失敗的話，就回到開發任務，成為新的一輪。

沒有這些機制

門背後的習慣，用手也做得到：叫 agent 動手之前先讀計畫，提交之前先讀 diff，對會寫入的工具不要勾「這個會話都允許」。上面這些機制，只是確保你累了、或不在的時候，這些事也照樣會發生。

把人放在哪里，又怎样让他的“同意”算数

把人放在哪里

第一个问题的答案很简单。人的注意力是整个系统里最稀缺的东西，所以只把它花在三类点上，别处一概不花。有的点要花钱，比如启动一次昂贵的运行；有的点会授权，比如让 agent 往共享仓库里写东西；还有的点无法撤销，一旦做了，就再也收不回来。

agent 的大部分工作都不属于这三类，因为任务文件夹里的一切重做起来都很便宜，agent 在那里可以放手去干（见一个任务一个文件夹）。但一个要改真实仓库的任务，会碰上两个这样的点。我把每一个都叫作一道关卡，因为人批准之前，任务过不去。

关卡 1：批准计划

第一道关卡设在任何工作文件被改动之前。agent 写出需求和计划后就停下来，在人读完计划、批准之前，它可以起草、可以读，但还不能动手改。

之所以停在这里，是为了成本。一份错的计划，还停留在一段文字的时候改起来很便宜，等它变成一个做完的改动再改就贵了。在我的配置里，计划还建立在已经确认的需求之上（见需求说不清？让 Agent 先写一页给你确认），所以一次审批可以把两者一起确认。

关卡 2：批准写回

到了第二道关卡，agent 已经在任务文件夹里做完改动，检查也跑过了，剩下的就是把结果复制到真实的仓库里，这一步叫写回。在写回之前，人要读那份确切的 diff，也就是将要改动的那些行的清单，然后再批准。

就算批准了，写回也不会直接进主分支。结果会进入仓库的一个新分支，并且不提交。而且在真正写之前，代码会先检查：

  • 工作树是干净的，
  • 分支名没被占用，
  • 要改的文件在复制之后，没有在主分支上变动过。

只要有一个仓库没通过检查，就什么都不写。两个人或者两个任务改了同一个文件，也是在这里被发现的，发现它的是这里的程序，而不是后来的评审。

为什么审批要在终端里敲

再看第二个问题的前一半：怎样让一声“同意”成为 agent 造不出来的东西？聊天里的确认框可以被“本次会话都允许”关掉，人在终端里敲的一个码却关不掉，所以审批被做成一条需要真正终端的命令。不过，这个设计是靠两条腿站着的，终端只是其中一条。

可光靠终端，算不上一堵墙。检查“这是不是终端”并不是安全边界，因为有心的程序完全可以假冒一个终端。那要是真有程序假冒，靠什么拦住它？

靠的是第二条腿，也就是 hook。agent 只要试图运行审批命令，这段代码就会直接拒绝。它必须放在 agent 够不着的地方，正如别让 Agent 改自己的规则所讲的那样：如果这个 hook 没了，或者 agent 能编辑它，审批就只剩一个客客气气的请求。两条腿，单靠哪一条都不够。

而 hook 本身出了错的时候，也得照样拒绝。执行层在自己出故障时会放行调用（见hook 自己出故障了怎么办？），所以对审批命令的拒绝，应该列进那份即使 hook 出错也必须拦下的短清单。不然的话，这条腿恰恰会在最需要它的时候断掉。

这并不是说人要在终端里读计划。计划和 diff 在终端里很难读，所以人是在编辑器里读的，终端只显示文件路径和要敲的码。读和批准是两个有意分开的动作。

把审批绑在读过的内容上

剩下的是后一半：重复使用。假设人批准了一份计划，之后 agent 又改了这份计划，那这个批准还有效吗？不应该有效。正因为这样，人要敲的那个码是从计划的内容算出来的。它是一个哈希，相当于一枚指纹，哪怕只改一个字符它也会变；所以批准之后计划一变，批准就对不上了，关卡也随之重新关上。

同样，写回的批准只属于当时展示的那份确切的 diff。所谓“绑定到被批准的那份计划上，一字不差”，说的就是这个。没有这一步，人批准的是一样东西，agent 交出来的可能是另一样。

关卡处的快照

关卡除了决定什么能往下走，还负责把工作存下来。计划被批准时、每次检查之前、写回试运行（dry run）之前，系统都会自动保存一份工作的副本（快照），这样出了问题，就能把那一刻的状态找回来。在我的配置里，快照默认保留 14 天。

不过，能找回某个状态，不等于能自动退回去。往多个仓库写到一半失败了，并不会自动回滚，任务会进入“部分写入”的状态，由人来做恢复。自动撤销只能靠猜，我宁可不做。

好几轮

任务不一定在写回之后就结束。同一个目标可能再回来，比如 reviewer 发现了缺陷，或者有人要求改动，这时就开始新的一轮：旧的工作挪到一边，重新写计划，两道关卡再走一遍。如果是不同的目标，那就是一个新任务。

在其他环境里测试，看起来像是又一轮，其实不是。agent 在那里什么都运行不了，只能由人来跑，所以这件事另外开成一个测试类的任务：agent 写好说明，等人给出结果，再判断结果。测试失败的话，就作为新的一轮回到开发任务。

没有这套机制也行

关卡背后的习惯，手工也做得到：叫 agent 动手之前先读计划，提交之前先读 diff，对会写东西的工具别勾“本次会话都允许”。上面这套机制，只是保证你累了或者不在的时候，这些事也照样会发生。

What the gates cost, and where they can still fail

The plainest cost is time. Each gate holds the agent until a person has done one read and typed one command, and that is the price of the design. If you put gates everywhere, people stop reading, which brings you back to the hundredth box.

The gates also hold only while the refusing hook is there. If the hook that refuses the approval command is removed, edited or fails, an agent that can run commands could approve for itself. So protect that hook as the rules in Guardrails say, and test it. A test is cheap: ask the agent to run the approval and check that it is refused.

Even with the hook in place, a person can approve without reading. Binding the approval to the plan stops a swap, but it does not stop a tired yes. Making the diff short and the gates few helps, yet nothing here removes the problem. One idea I have not tried is to record how long each approval took and how big the diff was, because a very fast yes on a big diff is a signal worth looking at.

The last two limits came up above. The terminal check protects against accidents, not against an attack (Least privilege), and a partial failure across repositories still needs a person.

這兩道門要付出什麼，還會在哪裡失守

最直接的代價是時間。每道門都要讓 agent 停下來，等人讀一次、輸入一個指令，這是這套設計要付的代價。可是門要是放得到處都是，人就不讀了，又回到第一百個框。

這兩道門也只有在負責拒絕的 hook 還在的時候才成立。拒絕批准指令的 hook 如果被移除、被編輯或失敗，能執行指令的 agent 就可能自己批准自己。所以要照保護規則本身的檔案的規則保護好這個 hook，並且測試它。測試很便宜，叫 agent 去執行批准，確認它被拒絕就行。

就算 hook 好好的，人還是可能不讀就批准。把批准綁到計畫上，擋得住掉包，卻擋不住累了的「同意」。讓 diff 短一點、門少一點會有幫助，但這裡沒有任何東西能消除這個問題。一個我還沒試過的想法，是記下每次批准花了多久、diff 有多大，因為大 diff 卻很快就批准，是值得看一眼的訊號。

剩下兩條限制前面已經說過：終端機檢查只防意外，防不了攻擊（有些東西根本不給）；跨倉庫的部分失敗，還是要人來處理。

关卡要付出什么，还会在哪里失守

最直接的代价是时间。每道关卡都要让 agent 停下来，等人读一遍、敲一条命令，这是这套设计要付的价。可要是到处都设关卡，人就不读了，你又回到了第一百个框。

这套关卡也只有在负责拒绝的 hook 还在时才成立。如果拒绝审批命令的 hook 被删了、被改了，或者出了故障，能运行命令的 agent 就可能自己批准自己。所以要按别让 Agent 改自己的规则里的规则保护好这个 hook，并且测试它。测试很便宜，让 agent 去运行审批，看它是不是被拒绝就行。

就算 hook 好好的，人也可能不读就批。把审批绑到计划上，能防住调包，却防不住一句疲惫的“同意”。让 diff 短一点、关卡少一点会有帮助，但这里没有任何东西能消除这个问题。有一个我还没试过的想法，是记下每次审批用了多久、diff 有多大，因为对一个很大的 diff 飞快地批下来，是值得留意的信号。

剩下两条限制前面已经说过：终端检查只防意外，防不了攻击（见不要开放全部的权限或使用沙箱）；跨仓库的部分失败，仍然要人来处理。

When to delete the typed approval

Of all this, the typed approval is the part that depends on the platform. It exists because a platform's own confirmation can be switched off for a session and cannot be tied to a plan's hash. If a platform offers an approval that the agent cannot dismiss, that records what was shown, and that stops being valid when the content changes, use that and drop mine.

The idea stays either way: a person at the three kinds of point, and an approval that belongs to exactly what they read.

什麼時候可以刪掉在終端機輸入的批准

整套設計裡，在終端機輸入的批准是跟平台綁在一起的那一部分。它之所以存在，是因為平台自己的確認可以在一個會話裡被關掉，也沒辦法綁到計畫的 hash。如果哪天平台提供的批准，agent 無法關掉、會記錄當時顯示的內容、內容一變就失效，那就用平台的，把我的拿掉。

不管怎樣，想法會留下：在三種地方放一個人，而且批准只屬於他讀過的那份內容。

什么时候可以删掉敲码审批

整套设计里，敲码审批是跟平台绑在一起的那一部分。它之所以存在，是因为平台自己的确认可以在一个会话里被关掉，也没法绑到计划的哈希上。如果哪天平台提供的审批 agent 关不掉、会记录展示过什么、内容一变就失效，那就用平台的，把我的这套去掉。

不管怎样，想法会留下来：在三类点上放一个人，而审批只属于他读过的那份确切内容。
