4.5

Some things you never hand over有些東西根本不給不要开放全部的权限或使用沙箱

This chapter assumes you have read Hooks and Enforcement design, or know that a hook can refuse a tool call but can itself fail.

這一章假設你讀過Hooks：每次呼叫都會經過的執行點和把執行層當軟體來設計，或者知道 hook 能拒絕工具呼叫，但它自己也會出錯。

读这一章之前，你要读过硬性规则放在哪？用 hook和hook 自己出故障了怎么办？，或者至少知道：hook 能拒绝一次工具调用，但它自己也会出故障。

The Knowledge經驗分享经验分享

In one sentence

A hook only blocks what it can see. For things that must never be touched (production, credentials, other people's repositories), the best defence is never giving them to the agent.

一句話

hook 只擋得住它看得到的東西。對絕對不能碰的東西（正式環境、憑證、別人的倉庫），最好的防禦是根本不交給 agent。

一句话

hook 只能拦下它看得见的东西。对绝不能碰的东西（生产环境、凭证、别人的仓库），最好的防御是压根不交给 agent。

For leaders

  • The decision: for production systems, credentials and other teams' repositories, decide that the agent is never given access at all, rather than given access with a hook to guard it.
  • The risk: a hook sees the text of a call, not its effect, and it can fail. A guard that holds most of the time is the wrong tool for something that cannot be undone or is not yours. I have no count of incidents prevented.
  • The cost of doing it right: people's time. A person runs the query and pastes the answer back, which is slower than a connection. A real sandbox is a bigger step, and I have not built one. So use this where harm is large or cannot be undone, not everywhere.
  • Ask the team: "Make a list of everything this agent can open, run or connect to. Which of those must never be touched, and why can the agent reach them?"

給主管

  • 要做的決定：對正式環境、憑證和其他團隊的倉庫，決定完全不給 agent 存取權，而不是給了存取權再用 hook 守著。
  • 風險：hook 看到的是一次呼叫的文字，看不到它的效果，而且它自己也會出錯。「大多數時候守得住」的守衛，拿來管無法撤銷、或不屬於你的東西，是用錯了工具。擋掉了幾次事故，我沒有數字。
  • 做對的成本：人的時間。由人去執行查詢、再把答案貼回來，比直接連線慢。真正的沙箱是更大的一步，我還沒有做。所以只在傷害大、或無法撤銷的地方這樣做，不必到處都用。
  • 可以問團隊：「列出這個 agent 能打開、能執行、能連上的所有東西。其中哪些絕對不能碰，為什麼 agent 碰得到它們？」

写给管理者

  • 要拍板的事：对生产系统、凭证和其他团队的仓库，决定根本不给 agent 访问权限，而不是给了权限再用 hook 守着。
  • 风险：hook 看到的是一次调用的文本，看不到它的效果，而且它自己也会出故障。“大多数时候守得住”的守卫，拿来管撤销不了、或者不属于你的东西，是选错了工具。防住了多少起事故，我没有统计过。
  • 做对的代价：人的时间。由人来跑查询、再把答案贴回来，比直接连接慢。真正的沙箱是更大的一步，我还没有搭过。所以只在危害大或者无法撤销的地方这样做，不必到处都用。
  • 可以问团队：“把这个 agent 能打开、能运行、能连接的东西列一张清单。其中哪些是绝不能碰的？为什么 agent 够得着它们？”

Why some things should not be guarded at all

A good guard on a door is still only a guard. It can be tricked, it can fall asleep, and it can be handed the wrong list. A wall with no door has none of these problems.

Yet everything so far in this part has been a guard. A hook reads the text of a call but cannot see what the call will do (Hooks). And the hook itself is software that can fail (Enforcement design). The VS Code docs say as much: hooks and instructions are "not substitutes for enforced permissions, sandboxing, or enterprise controls".

For most of what an agent does, though, an imperfect guard is enough. If a hook misses a file edit in a code project, the change shows up in the diff and you can revert it. But some things cannot be undone, and some are not yours. A production system is one, because a single wrong command there changes real data. Credentials are another: a leak cannot be taken back. And another team's repository is a place where you have no right to make a mistake.

For these, a guard that holds "most of the time" is the wrong tool. What they need is an idea older than agents, least privilege: give a program only what it needs for the job, and nothing else. The security guidance on prompt injection lists the same idea first among its defences, as "Enforce privilege control and least privilege access" (OWASP). If the agent cannot reach a thing, it cannot be talked, tricked or confused into touching it, so no hook has to catch anything.

For high-risk work, then, least privilege is the first choice, and the hooks of the earlier chapters come second. That leaves a practical question: the agent still has to do the work, so how do you take things away from it without taking away the job?

為什麼有些東西根本不該靠守

門口的守衛再好，也只是個守衛。他會被騙，會打瞌睡，也可能拿到一份錯的名單。一堵沒有門的牆，就沒有這些問題。

可到目前為止，這一部分講的都是守衛。hook 讀的是一次呼叫的文字，卻看不到這次呼叫會做什麼（見Hooks：每次呼叫都會經過的執行點）。而且 hook 本身也是會出錯的軟體（見把執行層當軟體來設計）。VS Code 的文件也說，hooks 和指令「不能代替強制的權限、沙箱或企業管控」。

話說回來，對 agent 做的大部分事，不完美的守衛也夠用了。比如在程式碼專案裡，hook 漏攔了一次檔案編輯，改動會出現在 diff 裡，撤回來就好。可是有些事無法撤銷，有些東西也不是你的。正式環境算一個，因為在那裡一個錯的指令就會改到真實的資料。憑證也是一個：洩漏一次就收不回來。至於另一個團隊的倉庫，你根本沒有權利在那裡犯錯。

而對這些東西，「大多數時候守得住」的守衛是用錯了工具。它們需要的是一個比 agent 還老的想法，叫最小權限：只給程式做這份工作所需要的，別的都不給。關於 prompt injection 的安全指引，也把同一個想法列為防禦的第一條，「落實權限控制和最小權限存取」（OWASP）。agent 碰不到的東西，誰也沒辦法說服它、騙它或把它搞糊塗，讓它去碰，自然也不需要 hook 去攔。

所以對高風險的工作，最小權限是第一選擇，前面幾章的 hook 排第二。這就留下一個實際的問題：工作還是得讓 agent 做，怎麼才能把東西拿走，又不把工作一起拿走？

为什么有些东西压根不该靠守

门口的守卫再好，也只是个守卫。他可能被骗，可能打瞌睡，也可能拿到一份错的名单。一堵没有门的墙，就没有这些问题。

可到目前为止，这一部分讲的都是守卫。hook 读的是一次调用的文本，却看不到这次调用会做什么（见硬性规则放在哪？用 hook）。而且 hook 本身也是会出故障的软件（见hook 自己出故障了怎么办？）。VS Code 的文档也说，hook 和指令“不能替代强制执行的权限、沙箱或企业管控”。

话说回来，对 agent 做的大部分事，不完美的守卫也够用了。比如在代码项目里，hook 漏拦了一次文件编辑，改动会出现在 diff 里，撤销就是了。可有些事撤销不了，有些东西也不是你的。生产系统算一个，因为在那里一条错的命令就会改动真实数据。凭证也是一个：泄露一次就收不回来。至于别的团队的仓库，你根本没有资格在那里犯错。

而对这些东西，“大多数时候守得住”的守卫是选错了工具。它们需要的是一个比 agent 还老的想法，叫最小权限：只给程序完成工作所需要的，别的一概不给。讲 prompt 注入的安全指南，也把同一个想法列为防御措施的第一条，“落实权限控制和最小权限访问”（OWASP）。agent 够不着的东西，谁也没法说服它、骗它或者把它搞糊涂，让它去碰，自然也用不着 hook 去拦。

所以对高风险的工作，最小权限是首选，前面几章讲的 hook 排第二。这就留下一个实际的问题：活还得让 agent 干，怎么才能把东西拿走，又不把活一起拿走？

Taking things out of the agent's reach

The method is a question you ask once for each dangerous thing: can I arrange the work so the agent never needs it? Often you can, in one of four ways.

1. Give it a copy of the files to change, not the whole workspace

Suppose the agent works on code that lives in a large shared repository. The easy way is to open that repository and let the agent roam, but then every file is in reach, the ones it should change and a thousand it should not.

The other way is to decide first what the work will touch and hand over only that. In my setup, when the work is in a target repository, the agent works from a plan that names the files to change. Only those files are fetched, as copies, into the task's own folder (see Manage tasks, not chats), and the agent edits the copies. Your working tree, your current branch and your existing commits are not changed.

Writing back to the real repository is a separate step that a person approves (the second gate in Two gates). It puts the files on a new branch and does not commit, so if anything is wrong, you delete the branch. The agent's mistakes are thus limited to a folder that exists only for this task. A hook still guards that folder, but if the hook fails, the worst case is a bad copy, not a bad repository.

The same goes for commands. Those that push, open a pull request, reset hard or clean are never run by the agent, only by a person. If a guard is wrong about a push, the leak cannot be fetched back. A command that is not available cannot be wrong.

2. Never connect to the environment; ask a person to run the query

What does the agent actually need from production? Usually not a connection, but a fact: "what is in this table", "which version is deployed", "does this job exist". And a fact is something a person can fetch.

My setup gives the agent no credentials and no tools to connect to an environment. That is a rule of use, not a sandbox guarantee, and I come back to the difference below. When the agent needs something only an environment can tell it, it writes the question in one fixed place. With it goes a command or a query that only reads, ready for the person to run as it is. The person runs it and pastes the answer back. The agent asks at its next stop, not in the middle of work.

This costs time, and I will not pretend otherwise: a person is slower than a connection. In return, you get three things. The agent has no path to production, so no injected text, no bad guess and no failing hook can reach it. Every fact that came from an environment is written down, along with who ran it. And the person sees the query before it runs, which is the review you wanted anyway. (The answer the person pastes back is itself untrusted text, though, as Text the agent reads can give it orders explains.)

3. Keep credentials and keys out of the context

Taking away the connection still leaves the keys themselves. Anything in the agent's context can be sent somewhere else, whether written to a file, put in a command or repeated in a summary. A secret the agent has seen is therefore a secret that can leak, even when the agent is not malicious. A model that copies a token into a log line while debugging has already done the damage.

Four habits follow from this, and I offer them as a design, not as something I measured.

  • Do not put secrets in files the agent reads. Rules, notes and knowledge files hold no values, only where a value lives and who owns it.
  • Let the program that needs a secret get it at the moment of use, from the place meant for it, instead of passing it through the agent. The agent writes "run the deploy script", and the script holds the key.
  • For the agent's own access, use a limited key: read-only, one project, and expiring soon. Then a leak is small.
  • Keep secrets out of what the agent can read by accident, such as the environment variables of the shell it runs in and config files in the home folder. These are easy to forget.

4. Close the way out

Keeping secrets out of sight is one part. The way out is the other, because a secret that cannot be sent anywhere is much less dangerous. If the agent's commands can reach any address on the internet, anything it can read can be sent out. If they can reach only a short list, the damage is limited. This is the third circle in Untrusted input, and I treat it there. The point here is only that network access is a privilege like any other: ask what the agent needs, and give that.

When it is time for a real sandbox

Everything above works by giving the agent less. As I said under the second way, that is a rule of use, not a guarantee. A sandbox or container is different. It is a boundary set by the operating system around everything the agent runs, so inside it the agent can do what it likes, and the walls hold even if a command is cleverly written. A hook cannot offer that, because it only reads the text.

My harness has no sandbox. Terminal commands can write any path the user can, while the hook stops only the common spellings. The harness's own design notes say plainly that for strong isolation you use the operating system or a container. Look at one sooner than I did if any of these is true:

  • the agent runs commands without a person watching (Use subagents sparingly and the later chapters on unattended work);
  • the project handles production, credentials or another team's repository;
  • the agent can run code that came from somewhere you do not control.

Anthropic's write-up on sandboxing Claude Code makes a point worth copying: effective sandboxing needs both file system and network isolation. Without network isolation, a hijacked agent can send out your files. Without file system isolation, it can escape the sandbox to the network (Claude Code sandboxing). One without the other is not enough. In practice that means a container or a virtual machine with its own network rules, not just a folder.

Nor is a sandbox magic. The VS Code docs call theirs "an added layer", and "not a virtual machine or user-account boundary", so read what yours does and does not cover (I have not tested VS Code's).

Test your own setup

For each thing that must never be touched, three questions are worth asking.

  1. Is it in the agent's reach at all? List what the agent can open, run and connect to, and cross out what it does not need.
  2. If your hook and your instructions both failed today, what is the worst thing the agent could do with it?
  3. Is there a person-run step that could replace a connection or a key?

There is also a one-minute test you can run today. In a terminal opened the way your agent opens it, run env and look at the names of the variables. Then list the files in your home folder that hold keys or tokens, and ask whether the agent could read them. If you do not like the answer, that is your first fix, and it does not need a hook.

把東西移出 agent 碰得到的範圍

辦法是對每一樣危險的東西都問一次：我能不能把工作安排成 agent 根本不需要它？很多時候是可以的，辦法有四種。

1. 給它要改的檔案的副本，不給整個工作區

假設 agent 要改的程式碼放在一個很大的共用倉庫裡。最省事的辦法是打開那個倉庫，讓 agent 隨便逛，可是這樣一來，每個檔案都在它碰得到的範圍裡，有它該改的，也有上千個它不該碰的。

另一種辦法是先想好這份工作會碰到什麼，只把那些交出去。在我的設定裡，如果工作是在一個目標倉庫上，agent 會照一份計劃工作，計劃裡點名了要改哪些檔案。只有那些檔案會被取出來，作為副本放進任務自己的資料夾（見管任務，不管對話），agent 編輯的就是這些副本。你的工作樹、目前的分支和已有的提交，都不會被改動。

寫回真正的倉庫是另一個步驟，要由人批准（見兩道門：人在哪裡批准的第二道門）。這一步把檔案寫在一個新分支上，而且不提交，所以有哪裡不對，刪掉那個分支就好。這樣一來，agent 犯的錯就只限於一個只為這個任務存在的資料夾。hook 仍然守著那個資料夾，但就算 hook 失靈，最壞也只是一份壞掉的副本，而不是一個壞掉的倉庫。

指令也照這個思路處理。push、開 pull request、reset --hard、clean 這類指令，agent 永遠不執行，只由人來執行。守衛要是在 push 上判斷錯了，洩漏就收不回來。而一個用不了的指令，不可能出錯。

2. 絕不連到環境；請人去跑查詢

agent 到底要從正式環境得到什麼？通常不是一條連線，而是一個事實：「這張表裡有什麼」、「部署的是哪個版本」、「這個作業存不存在」。而事實，是可以由人去取的。

我的設定不給 agent 憑證，也不給它連到環境的工具。這是使用上的規則，不是沙箱的保證，兩者的差別後面還會講到。agent 需要只有環境才答得出來的東西時，會把問題寫在一個固定的地方。問題後面附著一條唯讀的指令或查詢，人拿來就能原樣執行。人執行完，把答案貼回來。agent 會等到下一次停下來時才提問，不會在工作做到一半時問。

這要花時間，我不假裝沒有：人就是比連線慢。換來的是三件事。agent 沒有通往正式環境的路，所以被注入的文字、錯誤的猜測、失靈的 hook，都碰不到正式環境。每一個來自環境的事實都寫了下來，連同是誰執行的。而且查詢執行之前，人就已經看過它了，這本來就是你想要的審查。（不過，人貼回來的答案本身也是不可信的文字，見agent 讀到的文字可能在指揮它。）

3. 讓憑證和金鑰不進上下文

連線拿掉了，金鑰本身卻還在。問題是，agent 上下文裡的任何東西都可能被送到別的地方，像是寫進檔案、放進指令、在摘要裡重複一遍。所以 agent 看過的祕密，就是可能洩漏的祕密，就算 agent 沒有惡意也一樣。模型在除錯時把一個 token 複製進一行日誌，傷害就已經造成了。

下面四個習慣就是由此來的。它們是一種設計，效果我沒有量過。

  • 不要把祕密放在 agent 會讀的檔案裡。規則、筆記和知識檔裡不放值，只寫值放在哪裡、誰負責。
  • 讓需要祕密的程式在用的那一刻，自己從專門放它的地方去拿，而不是經過 agent 傳遞。agent 寫「執行部署腳本」，金鑰在腳本手上。
  • agent 自己的存取，用一把受限的金鑰：唯讀、只限一個專案、很快過期。這樣就算洩漏，影響也很小。
  • 管住 agent 可能意外讀到的地方，例如它所在的 shell 的環境變數、家目錄裡的設定檔。這些很容易忘。

4. 把出路關上

讓祕密不被看見只是一部分。另一部分是出路：一個祕密要是送不出去，危險就小得多。如果 agent 的指令能連到網路上的任何位址，它讀得到的任何東西就都能送出去。如果它只能連一張短清單上的位址，傷害就有限。這是agent 讀到的文字可能在指揮它裡的第三個圈，我在那一章再詳細處理。這裡只想說一點：網路存取也是一種權限，和其他權限一樣，agent 需要什麼就給什麼。

什麼時候該用真正的沙箱

前面這些辦法都是讓 agent 少拿一點。可我在第二種辦法裡說過，這只是使用上的規則，不是保證。沙箱或容器不一樣，它是作業系統設下的一道邊界，圍住 agent 執行的一切。在邊界裡面，agent 想做什麼都行，而且即使指令寫得再巧妙，牆還是守得住。hook 做不到這一點，因為它只讀文字。

我的 harness 沒有沙箱。終端機指令可以寫使用者能寫的任何路徑，而 hook 只攔得住常見的寫法。harness 自己的設計筆記說得很直接，要強的隔離，就用作業系統或容器。如果你遇到下面任何一種情況，就該比我更早考慮沙箱：

  • agent 在沒有人看著時執行指令（見慎用子 agent，以及後面講無人值守工作的幾章）；
  • 專案涉及正式環境、憑證或另一個團隊的倉庫；
  • agent 能執行來源你控制不了的程式碼。

Anthropic 那篇講 Claude Code 沙箱的文章，有一點值得照抄：有效的沙箱需要同時有檔案系統和網路的隔離。沒有網路隔離，被劫持的 agent 能把你的檔案送出去；沒有檔案系統隔離，它能逃出沙箱連到網路（Claude Code sandboxing）。只有一邊是不夠的。實際做起來，就是一個有自己網路規則的容器或虛擬機器，而不只是一個資料夾。

不過，沙箱也不是魔法。VS Code 文件說自己的沙箱是「額外的一層」，而且「不是虛擬機器或使用者帳號的邊界」，所以要讀清楚你的沙箱涵蓋什麼、不涵蓋什麼。VS Code 的沙箱我沒有測過。

測一下你自己的設定

對每一樣絕對不能碰的東西，都值得問三個問題。

  1. 它到底在不在 agent 碰得到的範圍內？列出 agent 能打開、能執行、能連上的東西，把它不需要的劃掉。
  2. 如果你的 hook 和你的指令今天都失靈，agent 拿它最糟能做什麼？
  3. 有沒有一個由人執行的步驟，可以取代一條連線或一把金鑰？

還有一個今天就能跑、一分鐘就夠的測試。用你的 agent 打開終端機的方式打開一個終端機，執行 env，看看變數的名稱。再列出你家目錄裡存放金鑰或 token 的檔案，問問自己 agent 讀不讀得到它們。如果你不喜歡這個答案，那就是你要做的第一個修正，而且不需要 hook。

把东西挪出 agent 够得着的范围

办法是对每样危险的东西都问一次：我能不能把工作安排成 agent 根本用不着它？很多时候是可以的，做法有四种。

1. 给它要改的文件的副本，不给整个工作区

假设 agent 要改的代码放在一个很大的共享仓库里。省事的做法是打开这个仓库，让 agent 随便逛，可这样一来，每个文件都在它够得着的范围里，既有它该改的，也有上千个它不该碰的。

另一种做法是先想好这项工作会碰到什么，只把这些交出去。在我的配置里，如果工作落在一个目标仓库上，agent 会照一份计划干活，计划里写明了要改哪些文件。只有这些文件会被取出来，作为副本放进任务自己的文件夹（见一个任务一个文件夹），agent 改的就是这些副本。你的工作树、当前分支和已有的提交，都不会被改动。

写回真实仓库是单独的一步，要由人审批（见哪些事必须由人来批？里的第二道门）。这一步把文件写到一个新分支上，而且不提交，所以哪里不对，把分支删掉就行。这样一来，agent 犯的错就被限制在一个只为这个任务存在的文件夹里。这个文件夹仍然有 hook 守着，但就算 hook 出了故障，最坏也不过是一份坏的副本，而不是一个坏的仓库。

命令也照这个思路处理。推送、开 pull request、硬重置（reset hard）、清理（clean）这类命令，agent 从不运行，只由人来运行。守卫要是在推送上判断错了，泄露就收不回来。而一条用不了的命令，不可能出错。

2. 从不连接环境，让人去跑查询

agent 到底要从生产环境得到什么？通常不是一个连接，而是一条事实：“这张表里有什么”“部署的是哪个版本”“这个作业存不存在”。而事实，是可以由人去取的。

我的配置不给 agent 凭证，也不给它连接任何环境的工具。这是使用上的规则，不是沙箱的保证，两者的差别后面还会讲到。agent 需要只有环境才能告诉它的信息时，会把问题写在一个固定的位置。问题后面附着一条只读的命令或查询，人拿来就能原样运行。人跑完，把答案贴回来。agent 会等到下一次停下来时再问，不会在干活干到一半时问。

这要花时间，我不假装不是：人就是比连接慢。换来的是三件事。agent 没有通往生产环境的路，所以注入的文本、一次错误的猜测、一个出故障的 hook，都够不着生产环境。每一条来自环境的事实都记了下来，连同是谁跑的。而且查询运行之前，人就已经看过它了，这正是你本来就想要的审查。（不过，人贴回来的答案本身也是不可信的文本，见Agent 读到的网页和文件，可能在给它下命令。）

3. 凭证和密钥不进上下文

连接拿掉了，密钥本身却还在。问题是，agent 上下文里的任何东西都可能被送到别处，比如写进文件、放进命令、在摘要里复述一遍。所以 agent 见过的秘密，就是可能泄露的秘密，哪怕 agent 并没有恶意。一个模型在调试时把 token 抄进一行日志，损害就已经造成了。

下面四条习惯就是由此来的。它们是一种设计，效果我没有量过。

  • 不要把秘密放进 agent 会读的文件。规则、笔记和知识库文件里不放值，只写值存在哪里、归谁管。
  • 让需要秘密的程序在用的那一刻，自己从专门存放它的地方去拿，而不是经过 agent 转手。agent 写“运行部署脚本”，密钥由脚本持有。
  • agent 自己用的访问权限，配一把受限的密钥：只读、只限一个项目、很快过期。这样就算泄露了，影响也不大。
  • 管住 agent 可能不经意读到的地方，比如它所在 shell 的环境变量、home 目录里的配置文件。这些很容易忘。

4. 堵上出路

让秘密不被看见只是一部分。另一部分是出路：一个秘密要是送不出去，危险就小得多。如果 agent 的命令能连到互联网上的任何地址，它能读到的任何东西就都能被送出去。如果它只能连一份简短的清单里的地址，损害就有限。这是Agent 读到的网页和文件，可能在给它下命令里的第三个圆，我在那一章细讲。这里只想说一点：网络访问也是一种权限，和别的权限一样，agent 需要什么就给什么。

什么时候该上真正的沙箱

前面这些办法都是让 agent 少拿一些。可我在第二种做法里说过，这只是使用上的规则，不是保证。沙箱或容器不一样，它是操作系统设下的一道边界，围住 agent 运行的一切。在边界里面，agent 想怎么干都行，就算命令写得再巧妙，围墙也不会倒。hook 做不到这一点，因为它只读文本。

我的 harness 没有沙箱。终端命令能写用户能写的任何路径，而 hook 只拦得住常见的写法。harness 自己的设计笔记里说得很明白，要强隔离，就得用操作系统或者容器。如果你遇到下面任何一种情况，就该比我更早去看看沙箱：

  • agent 在没人盯着的情况下运行命令（见别跟风瞎用子 Agent和后面讲无人值守的各章）；
  • 项目涉及生产环境、凭证或者别的团队的仓库；
  • agent 能运行来路你控制不了的代码。

Anthropic 那篇讲给 Claude Code 做沙箱的文章，有一点值得照抄：有效的沙箱需要文件系统隔离和网络隔离同时具备。没有网络隔离，被劫持的 agent 能把你的文件送出去；没有文件系统隔离，它能逃出沙箱连上网络（Claude Code sandboxing）。只有一样是不够的。落到实际做法上，就是一个有自己网络规则的容器或虚拟机，而不只是一个文件夹。

不过，沙箱也不是魔法。VS Code 文档说自己的沙箱是“额外的一层”，“不是虚拟机或用户账户的边界”，所以要读清楚你用的那个管什么、不管什么。VS Code 的沙箱我没有测过。

测试你自己的配置

对每样绝不能碰的东西，都值得问三个问题。

  1. 它到底在不在 agent 够得着的范围内？列出 agent 能打开、能运行、能连接的东西，把用不着的划掉。
  2. 如果今天你的 hook 和指令都失灵了，agent 拿它能做的最坏的事是什么？
  3. 有没有一个由人来做的步骤，可以代替一个连接或一把密钥？

还有一个今天就能做、一分钟就够的测试。按你的 agent 打开终端的方式打开一个终端，运行 env，看看变量的名字。再列出你 home 目录里存着密钥或 token 的文件，问问自己 agent 能不能读到它们。如果你不喜欢这个答案，这就是你要修的第一件事，而且用不着 hook。

What giving less costs, and where it falls short

Giving less has a price. Part of it is paid by the work, because an agent that cannot reach something it needs will stop or do a worse job. I have no numbers on how many tasks that costs, so watch for it when you remove access. Part of it is paid by people, because the ask-a-person step is slower than a connection. For production that is worth it. For a read of a public file it is not. Use the method where the harm is large or cannot be undone, not everywhere.

The copies bring a trap of their own. The agent works on copies of the files, so if the real repository moves while the work is going on, the write-back has to cope with that. Keep tasks short, and check the diff before the write-back.

Least privilege is also only as good as your list. If you forgot a key in a config file, the agent has it. Finding such things is what the test above is for.

None of this makes the hook unimportant. Not giving the thing is the best defence for what must never be touched, but for everything else the hook is the cheap, always-on check, and the next-best defence. I use both. The chapter's claim is about order: first remove, then guard.

I have not measured any of this or counted the incidents it prevented. What I can say is that the design is simpler to reason about: a thing that is not there cannot be misused.

少給要付出什麼，又在哪裡不夠

少給是有代價的。一部分代價落在工作上，因為碰不到所需東西的 agent，會停下來，或做得更差。這樣會讓多少任務失敗，我沒有數字，所以去掉存取時要留意。另一部分落在人身上，因為請人去問比連線慢。這對正式環境來說值得，對讀一個公開檔案來說就不值得了。這個辦法用在傷害大、或無法撤銷的地方就好，不必到處都用。

副本還帶來一個自己的陷阱。agent 在檔案的副本上工作，如果工作進行時真正的倉庫動了，寫回時就得應付這個變化。任務要盡量短，寫回之前先檢查 diff。

最小權限也只和你的清單一樣好。你要是忘了某個設定檔裡還有一把金鑰，agent 就拿到了。上面那個測試，就是用來找這種東西的。

這些都不代表 hook 不重要。對絕對不能碰的東西，不給是最好的防禦，但對其他所有東西，hook 是便宜的、一直開著的檢查，是次好的防禦。我兩個都用。這一章的主張說的是順序：先拿掉，再守著。

這些我都沒有量過，也沒有統計過它擋掉了幾次事故。我能說的是，這樣的設計比較好推理：不在那裡的東西，不可能被誤用。

少给要付出什么，又在哪里不够

少给是有代价的。一部分代价落在工作上，因为 agent 够不着它需要的东西，就会停下来，或者做得更差。这会让多少任务失败，我没有数字，所以撤掉权限时要留意。另一部分落在人身上，因为让人去问比直接连接慢。这对生产环境来说值得，对读一个公开文件来说就不值得了。这个办法用在危害大或者无法撤销的地方就好，不必到处都用。

副本还带来一个自己的坑。agent 改的是文件的副本，如果工作进行期间真实仓库动了，写回时就得应付这种变化。任务要尽量短，写回之前先检查 diff。

最小权限也只和你的清单一样好。要是你忘了某个配置文件里还有一把密钥，agent 就拿到了它。上面那个测试，就是用来找出这类东西的。

这些都不等于 hook 不重要。对绝不能碰的东西，不给是最好的防御，但对其他一切，hook 是便宜的、一直开着的检查，是次好的防御。我两样都用。这一章的主张说的是顺序：先拿掉，再守卫。

这些我都没有测量过，也没有统计过它防住了多少起事故。我能说的是，这样的设计更容易推理：不存在的东西，没法被滥用。

Do OWASP and VS Code agree? Industry practice

Both sources have come up already in this chapter, and put side by side they point the same way. The OWASP list of defences against prompt injection includes "Enforce privilege control and least privilege access" and "Require human approval for high-risk actions" (OWASP LLM01). The VS Code docs say hooks and instructions "are not substitutes for enforced permissions, sandboxing, or enterprise controls", and describe their sandbox as "an added layer", not "a virtual machine or user-account boundary" (Hooks, Security). Neither says that a hook is useless, only that it is not enough alone.

OWASP 和 VS Code 也這麼看嗎？ 業界做法

這兩個來源前面都出現過，放在一起看，指的是同一個方向。OWASP 對 prompt injection 的防禦清單包括「落實權限控制和最小權限存取」和「高風險動作要求人批准」（OWASP LLM01）。VS Code 文件說 hooks 和指令「不能代替強制的權限、沙箱或企業管控」，並把自己的沙箱描述成「額外的一層」，而不是「虛擬機器或使用者帳號的邊界」（Hooks、Security）。兩邊都沒有說 hook 沒用，只是說只靠它不夠。

OWASP 和 VS Code 也这么看吗？ 业界做法

这两个来源前面都出现过，放在一起看，指的是同一个方向。OWASP 的 prompt 注入防御清单里有“落实权限控制和最小权限访问”和“高风险操作要求人工审批”（OWASP LLM01）。VS Code 文档说 hook 和指令“不能替代强制执行的权限、沙箱或企业管控”，并把自己的沙箱描述为“额外的一层”，而不是“虚拟机或用户账户的边界”（Hooks、Security）。两边都没说 hook 没用，只是说光靠它不够。

When to delete the ask-a-person step Industry practice

The step in which a person runs a query exists because I do not trust an agent with a live connection. If one day a platform offers a connection that is enforced read-only, scoped to one table, logged, and cannot be changed by the agent, the ask-a-person step can go for that data. The other part, not handing over what is not needed, does not retire. It is the principle, not a workaround.

什麼時候可以刪掉「請人去問」這一步 業界做法

由人執行查詢的這個步驟之所以存在，是因為我不信任讓 agent 拿著即時的連線。如果有一天平台提供這樣一種連線：強制唯讀、限定在一張表、有紀錄、agent 又改不了它，那麼這份資料的「請人去問」就可以去掉。另一部分，也就是不交出不需要的東西，不會退場。它是原則，不是繞路的辦法。

什么时候可以删掉“让人去问”这一步 业界做法

让人去跑查询这一步之所以存在，是因为我不信任一个拿着实时连接的 agent。如果有一天平台提供了这样一种连接：强制只读、限定在一张表、有日志、agent 改不了，那么对那份数据，让人去问这一步就可以去掉。另一部分，也就是不交出用不着的东西，不会退役。它是原则，不是权宜之计。
