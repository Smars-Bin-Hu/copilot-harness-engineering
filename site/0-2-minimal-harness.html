The Knowledge經驗分享经验分享

In one sentence

Write one page of rules, add one skill, then write one hook that blocks dangerous commands, and leave everything else until a real pain calls for it.

一句話

先寫一頁規則，加一個 skill，再寫一個擋危險指令的 hook，其他功能等遇到真實的痛點再加。

一句话

先写一页规则，加一个 skill，再写一个拦截危险命令的 hook，别的功能等遇到真实的痛点再加。

For leaders

  • The decision: build the smallest set first (one page of rules, one skill, one hook that blocks dangerous commands), and for each thing you add later, be able to name the real pain it solves.
  • The risk: a big harness built in one go is expensive to maintain, and nobody can say which part helped. The small set is not foolproof either: rules and skills are only requests, so the model may not follow them, and although the model cannot get around a hook, a hook stops only the spellings of a command it recognizes.
  • The cost of doing it right: if the project is already open in VS Code, about half an hour for one person. After that, the team reviews the rule and hook files the way it reviews code.
  • Ask the team: "Which parts of our setup came from real failures, and which did we copy from a template?"

給主管

  • 要做的決定：先搭最小的一組（一頁規則、一個 skill、一個擋危險指令的 hook），之後每加一樣功能，都要說得出它解決的是哪個真實的痛點。
  • 風險：一口氣搭出來的大 harness 維護成本高，也說不清哪一部分起了作用。最小的這一組也不是萬無一失：規則和 skill 只是請求，模型可以不照做；hook 模型繞不過去，但它只擋得住它認得的指令寫法。
  • 做對的成本：如果已經在 VS Code 裡打開了專案，一個人大約半小時能搭完。之後團隊要像審程式碼一樣審規則檔和 hook 檔。
  • 可以問團隊：「我們的設定裡，哪些部分來自真實的失敗，哪些是從範本抄來的？」

写给管理者

  • 要拍板的事：先搭最小的一套（一页规则、一个 skill、一个拦截危险命令的 hook），以后每加一样功能，都要说得出它解决的是哪个真实的痛点。
  • 风险：一口气搭出来的大 harness 维护成本高，也说不清哪一部分起了作用。最小的这一套也不是万无一失：规则和 skill 只是请求，模型可以不照做；hook 模型绕不过去，但它只拦得住它认得的命令写法。
  • 做对的代价：如果已经在 VS Code 里打开了项目，一个人大约半小时能搭完。之后团队要像审代码一样审规则文件和 hook 文件。
  • 可以问团队：“我们的配置里，哪些部分来自真实的失败，哪些是从模板抄来的？”

Don't try to get it perfect at the start

After reading about the seven layers in the last chapter, it's tempting to build everything at once: a task board, a knowledge base, human in the loop (review and approve), subagents, guardrails, permission management, a sandbox... You don't have to do all of that in one go. In my experience it's better to start with the smallest piece that works and iterate, and to think about adding something only when you run into a problem or a pain, and I've been caught by false needs too: some things I added early on turned out to be the wrong idea, so I deleted them later.

Anthropic's advice to teams building agents is the same: "we recommend finding the simplest solution possible, and only increasing complexity when needed", and "consider adding complexity only when it demonstrably improves outcomes". (Building effective agents)

So follow along with this chapter, build a minimal demo first, and then you'll see what a harness really is. I want to teach you to write a one-page rules .md file, then add a skill, and finally write a hook, so you get a feel for these three layers. If your project is already open in VS Code, the whole thing takes about half an hour.

Three steps to the smallest set

Why rules, then a skill, then a hook

Each of the three holds the agent harder than the one before and costs more to build, so start with the cheapest.

A rules file is usually AGENTS.md (Codex, Copilot), CLAUDE.md (Claude Code) or .github/copilot-instructions.md (Copilot). You can just create the first two at the root of your repository, and the third goes in the .github/ folder. Rules take a few minutes and no code, and they tell the agent what it can't guess for itself: how the project is built, how to run the tests, what not to touch. At the start of every session, the agent looks for this file automatically and, if it finds one, loads it into context. A rule is only a request, and the model can ignore it. In my experience it follows what's written most of the time, but when the context gets long it sometimes ignores some of the rules, so a rules file can't give you a 100% guarantee.

A skill is a folder: .github/skills/ for Copilot, .claude/skills/ for Claude Code, .agents/skills/ for Codex. Inside is a SKILL.md file with a name and a description at the top and, below them, the steps for one kind of job, such as cutting a release or adding a database table. Long procedures like these don't belong in the rules file, because that file is loaded in full every time, and the more steps you put there, the more tokens you pay every time (Instructions and skills, load only what you need). With a skill, the agent normally sees only the name and the description, and it reads the full text when a request matches. A skill's weakness is one more layer of uncertainty than a rule has: it's only a request too, and on top of that the agent decides for itself whether to use it, so with a poor description it won't think of it.

A hook is a small program of your own that the platform calls at fixed moments. Before each tool runs, for example, the platform hands it the details of the call (which tool, with what arguments), and the program decides whether to let the call through or refuse it. Rules and skills are written for the model, which may not follow them. A hook is different, because the decision is made by a program outside the model: when it says no, the model cannot get around it, so the few things that must never happen belong there. It comes last because it's code you have to write, test and maintain, and because it sees only this one call, not what the command does once it runs (Hooks, the point every call passes through). That means it stops only the spellings it recognizes, and the same command written another way may slip through.

Step 1: write one page of rules (about 10 minutes)

Create an AGENTS.md at the root of your project. If you're not sure which file to use, use this one, because Copilot and Codex both read it, and Claude Code reads it when there's no CLAUDE.md. Write in it only what the model would get wrong or miss, meaning your project's own commands, limits and traps, and leave out what it already knows, such as how to write a loop in your language. Shorter is better. Five to ten lines is plenty for a first version, and the Claude Code docs suggest keeping each file under 200 lines, because a longer file takes up more context and the model follows it less well (How Claude remembers your project).

One line is worth adding early: the command to run after a change (the tests, the linter), with "do not say done until it passes". It's the cheapest check there is (Let the agent check its own work).

The real file in my setup is longer, and its two core limits look like this:

Two core limits from the shipped rules file: look before you act, and keep the user's own changes.
- Look at the real files before you act. Do not guess a path, a command, a setting or how to test.
- Keep the changes the user already made. Do not touch unrelated files.

Once it's written, check that it works. Open a new chat and ask something only your rules can answer, such as "How do I run the tests in this project?" If the answer follows your rules, the file is loaded, and if the agent is guessing, check the file name and location. In VS Code you can also expand References under the response, or run Chat: Open Customizations from the Command Palette and look for the file in the list.

Step 2: add a skill (about 10 minutes)

Pick a job you've explained to the agent more than once, create a folder for it under .github/skills/, and put a SKILL.md in it with a name and a description at the top. The name can use only lowercase letters, numbers and hyphens and must match the folder name, and the description can be up to 1024 characters.

The description matters most, because it's what the agent normally sees, so whether the agent thinks of this skill at the right moment depends on how well you wrote it. VS Code's advice is to be specific about both what the skill does and when to use it, and I also include the words a user might say.

The top of a real skill: the name and the description are what the agent sees first.
---
name: generic-code-standards
description: 'Check the code of a task against the company''s code standards and fix what does not comply. The standards are written by the company in .harness/standards/code-standards.md; this skill only reads them. Use before the promote dry-run of a task that changed code, or when the user asks to check or fix code style, naming or conventions. Keywords: code standards, coding conventions, style check, lint, naming rules, comply with the rules.'
type: workflow
specificTo: generic
---

Below the top, write the steps, then a short list of traps, the places where the agent usually goes wrong. From then on, add one every time you see it fail, which is the most useful habit I know for writing skills (Turn your way of working into skills).

Check this one too. Type / in the chat box and the skill should appear in the list, then make a request that fits the description without naming the skill, and see whether the agent uses it. If it never picks the skill, the problem is usually the description.

Step 3: write a hook that blocks dangerous commands (about 10 minutes)

The terminal is the most powerful tool an agent has, so the first hook starts there, blocking commands whose damage can't be undone, such as recursively deleting a folder, or downloading a script and running it in one line.

A hook has two parts: a configuration file that tells the platform which program to call on which event, and the program, which makes the decision. VS Code reads the configuration from .github/hooks/*.json in the repository, and in my setup every event points at the same program:

The configuration for the moment before a tool runs: it just names the program to call.
    "PreToolUse": [
      {
        "type": "command",
        "command": "python3 .harness/engine/hook.py",
        "windows": "python .harness/engine/hook.py",
        "bash": "python3 .harness/engine/hook.py",
        "powershell": "python .harness/engine/hook.py",
        "cwd": ".",
        "timeout": 30,
        "timeoutSec": 30
      }
    ],

Don't test a hook with a command that's really dangerous. Add a harmless rule first, for example one that refuses the command echo hook-test, and ask the agent to run it. You should see a refusal with the reason you wrote, and then you remove the rule.

Hooks have three traps, and I've fallen into all of them:

  • If the hook program can't start (the interpreter isn't found, for example), the call counts as refused, which is also what GitHub's docs say: when a preToolUse command errors, the tool call is denied. The agent then can't use any tool at all, while the screen shows only that the hook errored, so test it once before you rely on it.
  • If the hook times out (30 seconds in my setup), the platform treats it as having no opinion and handles the call under the normal permission rules. If that command is normally auto-approved, it just runs, as if there were no hook, so keep the program fast.
  • In my setup, the hook configuration is read when the window starts, so after changing it, reload the VS Code window.

How much harness do you need?

Whether these three parts are enough depends on who is affected when the agent gets it wrong.

You are Probably enough Why
One person on your own project The three parts above You see every change, and mistakes cost only you
A small team on a shared repository The three parts, with the rules and hook files reviewed like code, plus a place to record what the agent did Others inherit the agent's mistakes, and "who changed the rules" becomes a question (Roll out and govern a harness)
A large team, or code with compliance duties The above, plus approval points, counted checks and reports, as your risks require A mistake costs others, and you must be able to show what happened

Most readers are in the first row, and things like two approvals and a task board can wait.

Once all three are in place, you don't need to read this book front to back. When something hurts, go and read the chapter that matches.

How do you know it got better?

Each time you add something, you'll want to know whether it helped, but a feeling isn't reliable. What works is to pick a few tasks you know the right answer to, run them before and after each change, and score them the same way (the method is in Part 6). Even a rough version beats guessing: five tasks, plus a list of what "right" means written before you run them, with each task run a few times, because the result of one run may be luck (One run proves nothing).

三步搭出最小的一組

為什麼先規則，再 skill，最後 hook

這三樣約束 agent 的力度一樣比一樣緊，搭起來的成本也一樣比一樣高，所以從最便宜的開始。

常見的規則檔就是 AGENTS.md（比如 Codex、Copilot）、CLAUDE.md（Claude Code）或者 .github/copilot-instructions.md（Copilot），前兩個一般在你的專案倉庫根目錄下建立就好了，第三個放在 .github/ 資料夾裡。規則只要寫幾分鐘，不用寫程式，就能告訴 agent 它自己猜不到的事：專案怎麼建置、測試怎麼跑、什麼東西不能碰。每次會話開始，agent 都會自動尋找有沒有這個檔案，如果有的話，就會載入到上下文裡。它只是請求，模型可以不理；依我的經驗，寫下來的東西它大多數時候會照做，但是如果上下文過長，有時候模型就會忽略一些規則，所以規則檔不能 100% 保證。

skill 是一個資料夾，Copilot 放在 .github/skills/ 下面，Claude Code 放在 .claude/skills/ 下面，Codex 放在 .agents/skills/ 下面，裡面有一個 SKILL.md，開頭寫名字和描述，下面寫某一類工作的具體步驟，比如怎麼發布版本、怎麼新增一張資料表。這些長的操作步驟不適合放進規則檔，因為規則檔每次都要整份載入，步驟一多，每次都要為它付 token（指令與 skill：只載入需要的），放進 skill 以後，agent 平時只看到每個 skill 的名字和描述，需求對得上了才去讀全文。它的短板是比規則多了一層不確定：除了同樣只是請求，用不用這個 skill 也是 agent 自己判斷的，描述寫得不好，它就想不起來用。

hook 是平台在固定時機呼叫的一個你自己寫的小程式，比如每次執行工具之前，平台會把這次呼叫的內容（用哪個工具、參數是什麼）交給它，由它決定放行還是拒絕。規則和 skill 都是寫給模型看的，模型可以不照做，hook 不一樣，做判斷的是模型外面的程式，它說不，模型繞不過去，所以那幾件絕對不能發生的事要交給它。它放在最後，是因為它是程式碼，要寫、要測、要維護，而且它只看得到這一次呼叫，看不到指令執行起來之後做了什麼（Hooks：每次呼叫都會經過的執行點），所以只擋得住它認得的寫法，同一個指令換一種寫法就可能漏過去。

第 1 步：寫一頁規則（約 10 分鐘）

在專案根目錄建一個 AGENTS.md，如果你不確定用哪個檔案，就用它，因為 Copilot 和 Codex 都讀，Claude Code 在沒有 CLAUDE.md 的時候也讀。檔案裡只寫模型會搞錯或者會漏掉的東西，也就是你專案自己的指令、限制和陷阱，它本來就懂的不用寫，比如在你用的語言裡怎麼寫迴圈。規則越短越好，第一版寫五到十行就夠了，Claude Code 的文件也建議每個檔案控制在 200 行以內，因為檔案越長，占的上下文越多，模型照做得也越差（How Claude remembers your project）。

有一行值得早點加上：改完之後要跑的指令（測試、lint），再加一句「通過之前不准說做完了」，這是最便宜的檢查（讓 agent 能檢查自己的活）。

我設定裡的真實檔案要長一些，核心的兩條限制是這樣的：

隨附的規則檔裡的兩條核心限制：動手之前先看，保留使用者自己的改動。
- Look at the real files before you act. Do not guess a path, a command, a setting or how to test.
- Keep the changes the user already made. Do not touch unrelated files.

寫完要確認它生效了。開一個新對話，問一個只有你的規則才答得出的問題，比如「這個專案怎麼跑測試？」，它照著規則回答，說明檔案載入了，如果它在猜，就檢查檔名和位置。在 VS Code 裡也可以展開回答下面的 References，或者在命令選擇區裡執行 Chat: Open Customizations，看這個檔案在不在清單裡。

第 2 步：加一個 skill（約 10 分鐘）

挑一件你跟 agent 解釋過不只一次的工作，在 .github/skills/ 下面給它建一個資料夾，裡面放一個 SKILL.md，開頭寫名字和描述。名字只能用小寫字母、數字和連字號，並且要和資料夾同名，描述最多 1024 個字元。

三步搭出最小的一套

为什么先规则，再 skill，最后 hook

这三样约束 agent 的力度一样比一样紧，搭起来的成本也一样比一样高，所以从最便宜的开始。

常见的规则文件就是 AGENTS.md（比如 Codex、Copilot）、CLAUDE.md（Claude Code）或者 .github/copilot-instructions.md（Copilot），前两个一般在你的项目仓库根目录下创建就好了，第三个放在 .github/ 文件夹里。规则只要写几分钟，不用写代码，就能告诉 agent 它自己猜不到的事：项目怎么搭、测试怎么跑、什么东西不能碰。每次会话开始，agent 都会自动查找有没有这个文件，如果有的话，就会加载到上下文里。它只是请求，模型可以不理；按我的经验，写下来的东西它大多数时候会照做，但是如果上下文过长，有的时候模型就会忽略一些规则，所以规则文件不能 100% 保证。

skill 是一个文件夹，Copilot 放在 .github/skills/ 下面，Claude Code 放在 .claude/skills/ 下面，Codex 放在 .agents/skills/ 下面，里面有一个 SKILL.md，开头写名字和描述，下面写某一类活的具体步骤，比如怎么发版、怎么加一张数据库表。这些长的操作步骤不适合放进规则文件，因为规则文件每次都要整份加载，步骤一多，每次都要为它付 token（规则写太多，Agent 反而记不住），放进 skill 以后，agent 平时只看到每个 skill 的名字和描述，需求对得上了才去读全文。它的短板是比规则多了一层不确定：除了同样只是请求，用不用这个 skill 也是 agent 自己判断的，描述写得不好，它就想不起来用。

hook 是平台在固定时机调用的一个你自己写的小程序，比如每次运行工具之前，平台会把这次调用的内容（用哪个工具、参数是什么）交给它，由它决定放行还是拒绝。规则和 skill 都是写给模型看的，模型可以不照做，hook 不一样，做判断的是模型外面的程序，它说不，模型绕不过去，所以那几件绝对不能发生的事要交给它。它放在最后，是因为它是代码，要写、要测、要维护，而且它只看得到这一次调用，看不到命令运行起来之后做了什么（硬性规则放在哪？用 hook），所以只拦得住它认得的写法，同一条命令换一种写法就可能漏过去。

第 1 步：写一页规则（约 10 分钟）

Rules files keep growing, and hooks make people too comfortable

The rules file goes wrong first. A line gets added after every incident, so after a while the file is long, some entries contradict each other, and the model stops following it, so cut it back regularly and keep each rule in one place.

The hook's problem is quieter: it makes people too comfortable. Because it stops only the spellings it recognizes, don't say "the agent can't delete things". Say "the agent can't run these specific commands".

規則檔會越寫越長，hook 會讓人太放心

規則檔最先出問題。每出一次事故就加一行，過一陣子它就很長了，有些條目還互相矛盾，模型也就不再照做了，所以要定期刪減，讓每條規則只出現在一個地方。

When to delete each part Industry practice

Every part of this starter set is something platforms are slowly building in. When the platform's own permission system refuses the same dangerous commands out of the box, delete your hook. When it learns your project's commands by itself, shorten your rules file. And re-read your rules after every major model upgrade (When the model is upgraded, delete), because lines written for an older model may have become dead weight.

什麼時候可以把每一樣刪掉 業界做法

這套入門設定裡的每一樣，平台都在慢慢內建。等平台自己的權限系統開箱就能拒絕同樣的危險指令，就刪掉你的 hook；等它自己學會了你專案的指令，就縮短你的規則檔。每次大的模型升級之後，都重讀一遍規則（模型升級了，就要刪），因為為舊模型寫的那些行，可能已經成了累贅。

Explore it in the harness

My own setup is the grown-up version of this chapter, with one page of rules, many skills and a hook that guards every tool call. The harness can show you each one from the inside, and help you set up your own.

Once you have set it up as described above, type:

/harness-rookie-wondering I have read the chapter "A minimal harness in 30 minutes". Teach me how this harness does its rules page, its skills and its hook. Open the real files with me, show me how the hook refuses a command, and help me see what I could copy into my own project.

It teaches one small piece at a time, stops to check that you are following, and opens the files with you.
