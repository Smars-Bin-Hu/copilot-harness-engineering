3.3

Instructions and skills指令與 skill：只載入需要的规则写太多，Agent 反而记不住

This chapter assumes you have used an AI coding agent and read the context budget (everything the agent reads shares one window of limited size).

這一章假設你用過 AI 寫程式的 agent，也讀過上下文是一份預算（agent 讀的所有東西共用一個大小有限的視窗）。

这一章假定你用过 AI 编程 agent，也读过为什么不能把所有规则都塞给 Agent？（agent 读到的所有东西共用一个大小有限的窗口）。

The Knowledge經驗分享经验分享

In one sentence

Load the fewest rules by default and read the rest only when they are needed. A skill is a manual read on demand. Like any written rule, it is not enforced.

一句話

預設只載入最少的規則，其餘的等需要時才讀。skill 是一本按需要才讀的手冊，和任何寫下來的規則一樣，它不會被強制執行。

一句话

默认只加载最少的规则，其余的等需要时再读。skill 是一本按需阅读的手册，和任何写下来的规则一样，它不是强制执行的。

For leaders

  • The decision: keep the always-loaded rules few, and decide who owns the rule files and cuts what is no longer needed.
  • The risk: a long rule file is followed less well than a short one, and when two files disagree, the model picks one. Even a rule in a file is only a request that the model may not follow, so anything that must hold goes into code. I have no measured case of an ignored rule to quote.
  • The cost of doing it right: an owner and a regular trim of the rule files. Cutting lines the agent would get right anyway costs little; in my own files I usually saw nothing get worse, though I have not tested this systematically.
  • Ask the team: "Which lines in our always-loaded file would the agent get wrong without them, and who owns that file?"

給主管

  • 要做的決定：讓一直載入的規則保持很少，並決定誰負責規則檔、誰去剪掉不再需要的內容。
  • 風險：長的規則檔比短的更不容易被遵守，兩個檔案說法不一致時，模型會挑其中一個。就算寫進了檔案，規則也只是一個請求，模型可能不照做，所以一定要成立的事，要放進程式碼。我手上沒有可以引用的、規則被無視的實測案例。
  • 做對的成本：一個負責人，加上定期修剪規則檔。剪掉 agent 本來就會做對的那些行，成本很低；在我自己的檔案裡，這樣剪過之後通常沒看到什麼變差，不過我沒有系統地測過。
  • 可以問團隊：「我們一直載入的檔案裡，哪幾行是 agent 沒有它們就會做錯的？誰負責那個檔案？」

写给管理者

  • 要拍板的事：始终加载的规则要少，并且定下谁负责规则文件、谁来删掉不再需要的内容。
  • 风险：长的规则文件不如短的被遵守得好，两个文件说法不一致时，模型会挑其中一个。就算写进了文件，规则也只是一个请求，模型可能不照做，所以必须成立的事要写进代码。我手上没有实测过的“规则被无视”的案例可以引用。
  • 做对的代价：一个负责人，加上定期精简规则文件。删掉 agent 本来就会做对的那些行，花不了多少；在我自己的文件里，这样删过之后一般没看到什么变差，不过我没有系统地测过。
  • 可以问团队：“我们始终加载的文件里，哪些行是去掉之后 agent 就会做错的？这个文件归谁管？”

Why does a longer rule file work worse?

The natural way to teach an agent your project is to write everything down in one file: the rules, the conventions, the warnings, the how-to for every job. Each time the agent makes a mistake, you add a line. After a few weeks the file is long, yet the agent follows it less well than it did when the file was short.

Why would more rules leave the agent following them worse? Two things go wrong as the file grows, and only the second is about obedience.

The first is that everything in the file is paid for on every turn. The file sits in the window all the time, whether or not the job in hand needs it, so a rule about database migrations takes room while you fix a typo. That room comes out of the same budget that the context budget is about. What it costs per turn is in Models and cost.

The second is that the more rules there are, the less well each one is followed. In a long file the rules compete with each other. Two lines may disagree, or an important line may be lost among small ones. The platforms' own docs point the same way. Both Claude Code's and VS Code's advise keeping instruction files short, and Claude Code's also warns that when two instructions contradict each other, the model may pick one arbitrarily.

The way out is to stop putting everything in front of the agent at once. Show it a little, then let it read more only when it needs more. This idea is called progressive disclosure. It works like a shop that keeps a menu at the door and the full recipe in the kitchen. Anthropic names it "the core design principle that makes Agent Skills flexible and scalable" (Equipping agents for the real world with Agent Skills).

Two kinds of file put the idea to work. Instructions are rule files written for the agent to read. Some are loaded in every conversation, while others are loaded only when the agent works on certain files. A skill is a folder holding a manual for one kind of job. The agent reads that manual when the job comes up, not before.

With both kinds of file in hand, the first choice about any rule is where to put it. (What follows is reasoning and checks, since I have no measured case of an ignored rule to quote.)

規則檔為什麼越長越不管用？

想讓 agent 認識你的專案，最自然的辦法是把一切都寫進一個檔案，規則、慣例、警告，還有每種工作的做法。agent 每犯一次錯，你就加一行。幾個星期下來，檔案已經很長了，agent 卻反而不如檔案還短的時候守得好。

規則多了，怎麼反倒守得更差？檔案變長以後，有兩件事會出問題，而只有第二件和「守不守」有關。

第一，檔案裡的所有東西，每一輪都要付錢。這個檔案一直待在視窗裡，不管手上這份工作用不用得到，所以你在改一個錯字的時候，一條講資料庫遷移的規則也照樣佔著位子。它佔的就是上下文是一份預算講的那份預算，至於每一輪要花多少，在選模型：算的是每次成功的成本。

第二，規則越多，每一條被遵守的程度就越低。在一個長檔案裡，規則會互相競爭，兩行之間可能互相矛盾，要緊的一行也可能淹沒在一堆小事裡。平台自己的文件也是這個意思。Claude Code 和 VS Code 的文件都建議讓指令檔保持簡短，Claude Code 的文件還提醒，兩條指令互相矛盾時，模型可能隨意挑一條。

那麼出路在哪裡？就是別把所有東西一下子都擺到 agent 面前，先給它看一點，等它需要更多時再讓它去讀。這個想法叫漸進式揭露（progressive disclosure），就像一家店把菜單放在門口，完整的食譜留在廚房裡。Anthropic 稱它是「讓 Agent Skills 靈活、可擴展的核心設計原則」（Equipping agents for the real world with Agent Skills）。

把這個想法落實的，是兩種檔案。指令是寫給 agent 讀的規則檔，有些在每個對話裡都載入，有些只在 agent 處理特定檔案時才載入。skill 是一個資料夾，裡面放著某一類工作的手冊，agent 要等這份工作真的來了才去讀，不會事先讀。

有了這兩種檔案，對每條規則要做的第一個選擇，就是把它放在哪裡。（下面給的是推理和檢查的辦法，因為我手上沒有可以引用的、規則被無視的實測案例。）

规则文件为什么越长越不好使？

想让 agent 了解你的项目，最自然的办法是把所有东西都写进一个文件，规则、约定、警告，还有每种活儿的做法。agent 每犯一次错，你就加上一行。几周下来，文件已经很长了，agent 却反而不如文件短的时候守得好。

规则多了，怎么反倒守得更差？文件变长以后，有两件事会出问题，而只有第二件和“守不守”有关。

第一，文件里的所有内容，每一轮都要付费。这个文件一直待在窗口里，不管手头这项工作用不用得上，所以你在改一个错别字的时候，一条讲数据库迁移的规则也照样占着地方。它占的就是为什么不能把所有规则都塞给 Agent？讲的那份预算，至于每一轮要花多少，在选模型，别只看 token 单价里。

第二，规则越多，每一条被遵守得就越差。在一个长文件里，规则会互相竞争，两行之间可能说法矛盾，重要的一行也可能淹没在一堆细枝末节里。平台自己的文档也是这个意思。Claude Code 和 VS Code 的文档都建议把指令文件写短，Claude Code 的文档还提醒，两条指令互相矛盾时，模型可能随便挑一条。

那么出路在哪？就是别把所有东西一下子都摆到 agent 面前，先给它看一点，等它需要更多时再让它去读。这个思路叫渐进式披露，就像一家店把菜单放在门口，完整的菜谱留在厨房里。Anthropic 称它是“让 Agent Skills 灵活、可扩展的核心设计原则”（Equipping agents for the real world with Agent Skills）。

把这个思路落到实处的，是两种文件。指令是写给 agent 读的规则文件，有的在每次对话里都加载，有的只在 agent 处理某些文件时才加载。skill 是一个文件夹，里面放着针对某一类工作的手册，agent 要等这项工作真的来了才去读，不会提前读。

有了这两种文件，对每条规则要做的第一个选择，就是把它放在哪里。（下面讲的是推理和检查的办法，因为我手上没有实测过的“规则被无视”的案例可以引用。）

Where each rule goes, and why it can still be ignored

1. Three places for a rule

Where you put a rule decides when it costs room and when the agent sees it.

The first place is always loaded. It is a short file in the root of the repository, read in every conversation, so only the rules that every job needs belong there: the safety limits, how to start, what to do when something is refused. In my setup this is one short page. If a rule is needed for one job in ten, it does not belong here.

Rules that apply to only one kind of file go in the second place, where they are loaded by file. In VS Code an instruction file has a header line, applyTo, with a pattern like "all files under this folder". Its rules load only when the agent opens a file that matches. The rules for how to write a skill, for instance, are loaded when the agent opens a skill file and cost nothing while it edits a pipeline. Here is the top of one such file:

An instruction file that loads only for skill files: the applyTo line is the pattern.
---
description: 'Guidelines for creating high-quality Agent Skills for GitHub Copilot'
applyTo: '.github/skills/**/SKILL.md'
---

.github/instructions/skills.instructions.md L1–L4 @ 1.5.50

Everything else is read on demand: long how-tos and details that are rarely needed. This is where skills and reference notes go, to be read only when the job calls for them.

There is also a fourth way to bring a rule in. A hook (a small program the platform runs at fixed moments, covered in Hooks) can put a few lines at the top of every message you send, so that a rule is repeated near the point where it is used. Keep it to a few lines, though, or you will have rebuilt the long file.

With these places in view, the question to ask of every rule is: how often is this needed, and what happens if the agent misses it? A rule that is needed every time and costly to miss is always loaded. A rule needed for one kind of file is loaded by file, while one needed for a single job goes in a skill.

That last place deserves a closer look, because a skill is not read all at once.

2. A skill loads in three levels

A skill is a folder whose main file, SKILL.md, has a header (a name and a description) and a body (the manual). Next to it there can be longer notes, scripts and templates.

The agent does not see all of it at once.

  1. It always sees the name and description of every skill. This is the menu. It is small, but it is paid for on every turn, once for every skill you have installed.
  2. When a request fits a description, it reads the whole manual. The agent decides this itself, or you type the skill's name.
  3. It reads the extra files only when the manual points to them, so a long reference or a script is read at the step that needs it.

That is why you can install many skills without filling the window.

It also means that at level 1, the description is all the agent has to go on, so the description decides whether the skill is ever found. A vague one, such as "helps with code quality", never matches anything. A good one says three things: what the skill does, when to use it ("use when..."), and the words a person would actually say when they need it. Length matters too, since the platform limits it and a wordy description costs room for every other skill as well.

Even a good description does not guarantee that the skill is used. VS Code's documentation says plainly that discovery makes skills available but does not guarantee the model uses one, so it is worth testing (the tests are at the end of this section).

The menu itself can also grow too long. With a few dozen skills it becomes a real cost, and many of those skills are never chosen. One answer is to keep the skills of a single business area out of the menu until the task is about that area.

3. One rule, one source

Once rules live in several places, it is easy for the same rule to be written in three files. A change then misses one of them, leaving the agent to read three versions that slowly drift apart. So write each rule in one place. The other places hold a link and one sentence. If you find you have to restate a rule everywhere, that is a sign the structure is wrong. Rule files are shared code, too, so give them an owner who cuts the lines that are no longer needed.

4. Why a written rule is ignored

If a rule is loaded, why would the agent still ignore it? Getting a rule loaded is not the same as getting it followed, and there are five usual causes. The first four are about the text and where it sits:

  1. The file is too long. Ask of each line whether the agent would get it wrong without it, and if not, delete the line.
  2. Rules conflict. When two files say different things, the model picks one, and not always the one you want. VS Code's docs say instruction sources are additive and that you should not depend on file order to settle a conflict, so removing conflicts is your job. Search for them and fix the wording until only one version remains.
  3. The rule is far from where it applies. It was in the first message and is now thousands of lines up. A rule loaded by file, or a hook reminder, puts it nearer.
  4. It gives no reason. "Never do X" is easy to rationalise away, but "Never do X, because Y breaks" lets the model apply the idea to cases you did not list.

The fifth cause is the deepest, and no change to the text or its place will fix it: the rule is a request. Whatever you write in a file is read by the model, and the model can do otherwise. The Claude Code docs put it plainly: the memory files are "context, not enforced configuration". To block an action regardless of what the model decides, the same docs point to a hook. The text of a skill is no different. It makes the work go smoothly, but it does not make the wrong thing impossible.

So a rule that must hold goes into code, and that choice is the subject of A rule in a prompt is a request. The text then only has to explain why, so that the agent does not try again to get around the refusal. In my setup a rule that matters has both layers: the text teaches and the code stops.

Does a skill's header change any of this? On some platforms the header can carry stronger settings, so check what they actually do. In Claude Code, for example, allowed-tools only pre-approves tools and does not restrict them. A skill can also register hooks, which are code (Skills).

5. One more choice: language

The idea of one source also settles a question that comes up if you work in more than one language. I keep one copy of the rules and skills in English and tell the model which language to answer in, because a second copy of prose slowly drifts from the first. That is my own choice, but the principle is only to have one copy.

Three questions and three tests

Before you add a rule, ask three questions of it:

  1. How often is it needed? If rarely, it does not go in the always-loaded file.
  2. Is it already written somewhere? If so, link to it.
  3. If the agent ignores it, what happens? If the answer is "something bad that cannot be undone", it is not a job for text.

One test you can run today needs no extra setup. Go through your always-loaded file and ask of every line whether the agent would get it wrong without it. Cut every line that fails, then run the same task as before and see whether anything got worse. When I have cut lines from my own rules file, I usually saw nothing get worse, although I have not tested this systematically.

To check that a skill is found, start by writing the requests, in the words a person would use rather than the words of the description: three ways of asking for the job, and two neighbouring requests that should not trigger it. Open a new chat for each one, since an old chat may already hold the skill. Do not type the skill's name, either. Then look at which skills were loaded. Use the platform's log if it has one, because what the agent says is not evidence. If the skill did not load, the description lacks the user's words; if it loaded when it should not have, the description is too wide.

Whether a skill changes anything is a separate test. Run the same task twice in new chats, once with the skill and once without. If you cannot see a difference, cut the lines that make none. The agent already knew them.

每條規則該放在哪裡，為什麼還是會被無視

1. 規則的三個位置

規則放在哪裡，決定了它什麼時候佔位子，也決定了 agent 什麼時候看得到它。

第一個位置上的規則一直載入。它們寫在倉庫根目錄一個簡短的檔案裡，每個對話都會讀，所以只有每份工作都需要的規則才放這裡，例如安全限制、怎麼開始、被拒絕時該怎麼辦。在我的設定裡，這個檔案只有短短一頁。如果一條規則十份工作裡只有一份需要，它就不該放在這裡。

只適用於某一類檔案的規則，放在第二個位置，依檔案載入。在 VS Code 裡，指令檔有一行檔頭 applyTo，寫著像「這個資料夾底下所有檔案」這樣的模式。只有 agent 打開了符合的檔案，這些規則才會載入。例如怎麼寫 skill 的規則，要等 agent 打開 skill 檔案時才載入，它去編輯 pipeline 時，這些規則一點位子也不佔。下面是這樣一個檔案的開頭：

只在處理 skill 檔案時載入的指令檔：applyTo 那一行就是模式。
---
description: 'Guidelines for creating high-quality Agent Skills for GitHub Copilot'
applyTo: '.github/skills/**/SKILL.md'
---

.github/instructions/skills.instructions.md L1–L4 @ 1.5.50

其餘的一切都按需要才讀，包括很長的做法說明和很少用到的細節。skill 和參考筆記就放在這裡，工作需要時，agent 才去讀。

還有第四種方式。hook（平台在固定時刻執行的小程式，見 Hooks：每次呼叫都會經過的執行點）可以在你送出的每則訊息最前面加上幾行，讓一條規則在用得到它的地方附近再出現一次。不過只能放幾行，不然你又把那個長檔案蓋回來了。

有了這幾個位置，對每一條規則要問的就是同一個問題：這條多常需要？agent 漏掉了會怎樣？每次都需要、漏掉代價又高的，一直載入；只有某一類檔案需要的，依檔案載入；只有某一份工作需要的，放進 skill。

最後這個位置值得多看幾眼，因為 skill 並不是一次讀完的。

2. skill 分三層載入

skill 是一個資料夾，主檔案 SKILL.md 有一段檔頭（名稱和描述）和一段正文（手冊），旁邊還可以放更長的筆記、腳本和範本。

agent 不會一次看到全部。

  1. 每個 skill 的名稱和描述，它一直都看得到。這就是菜單。菜單很小，但每一輪都要付錢，你裝了多少個 skill，就要付多少份。
  2. 請求符合某個描述時，它才讀整本手冊。這是 agent 自己決定的，或者由你直接輸入 skill 的名稱。
  3. 只有手冊指向時，它才去讀額外的檔案，所以很長的參考資料或腳本，要等到需要它的那一步才讀。

這樣一來，你可以裝很多 skill，而不會塞滿視窗。

這也表示，在第 1 層，agent 手上只有描述可以依據，所以描述決定了 skill 到底找不找得到。含糊的描述（例如「幫助提升程式碼品質」）永遠對不上任何東西。好的描述要說清三件事：這個 skill 做什麼、什麼時候用（「use when……」），以及人真的需要它時會用的那些說法。長度也要留意，平台對它有限制，而囉嗦的描述還會佔掉其他每個 skill 的位子。

不過，就算描述寫得很好，也不保證 skill 會被用上。VS Code 的文件說得很明白，發現機制只是讓 skill 可以被用到，並不保證模型會用某一個，所以值得測一測（測試的辦法在這一節最後）。

還有一點，菜單本身也可能變得太長。有了幾十個 skill，菜單就成了一筆實實在在的成本，而其中很多 skill 從來不會被選到。一個辦法是，任務還沒碰到某個業務領域時，先別把這個領域的 skill 放進菜單。

3. 一條規則，一個來源

規則一旦分散到幾個地方，同一條規則就很容易寫進三個檔案。這樣一來，改的時候總會漏掉一個，agent 讀到的就是三個慢慢分歧的版本。所以一條規則只寫在一個地方，其他地方只放一個連結和一句話。要是發現一條規則得到處重述，那就說明結構錯了。規則檔也是共用的程式碼，所以要給它們一個負責人，由他剪掉不再需要的行。

4. 寫下來的規則為什麼會被無視

規則明明載入了，agent 為什麼還是不理它？載入了不等於就會被遵守，常見的原因有五種。前四種出在文字本身和它放的位置上：

  1. 檔案太長。對每一行都問一句，沒有它，agent 會做錯嗎？不會，就刪掉這一行。
  2. 規則互相衝突。兩個檔案說的不同，模型會挑一個，而且不一定是你要的那個。VS Code 的文件說，指令的來源是疊加的，不要靠檔案的順序來解決衝突，所以消除衝突是你自己的工作。把它們搜尋出來，改好措辭，直到只留下一個版本。
  3. 規則離適用的地方很遠。它在第一則訊息裡，現在已經是幾千行以前的事了。依檔案載入的規則，或者 hook 的提醒，可以讓它離得近一點。
  4. 它沒有理由。「絕對不要做 X」很容易被找個理由繞過去，「絕對不要做 X，因為 Y 會壞掉」，卻能讓模型把這個想法用在你沒列出來的情況上。

第五種原因最根本，改文字、換位置都解決不了：規則只是請求。你寫在檔案裡的任何東西，都只是給模型讀的，而模型可以不照做。Claude Code 的文件說得很直白，memory 檔是「上下文，不是強制執行的設定」，不管模型怎麼決定，想擋掉某個動作，文件給的辦法是 hook。skill 的文字也一樣，它能讓工作進行得順利，卻不能讓錯事無從發生。

所以一條必須成立的規則，要放進程式碼。怎麼做這個選擇，是提示裡的規則只是請求的主題。有了程式碼，文字只需要解釋為什麼，免得 agent 再試著繞過那個拒絕。在我的設定裡，要緊的規則有兩層，文字負責教，程式碼負責擋。

那 skill 的檔頭能不能改變這一點？有些平台允許檔頭帶上更強的設定，這時要去查清楚它們到底做什麼。例如在 Claude Code 裡，allowed-tools 只是預先批准工具，並不限制工具。skill 還可以註冊 hook，而 hook 是程式碼（Skills）。

5. 還有一個選擇：語言

「一個來源」的道理，也能回答一個只有在你用不止一種語言工作時才會遇到的問題。我的做法是只留一份規則和 skill，用英文寫，再告訴模型用哪種語言回答，因為第二份文字會慢慢和第一份對不上。這是我自己的選擇，原則只有一條：只留一份。

三個問題，三個測試

加一條規則之前，先問它三個問題：

  1. 這條多常需要？很少的話，就不放進一直載入的檔案。
  2. 別處已經寫過了嗎？有的話，連過去。
  3. agent 無視它會怎樣？答案如果是「很糟、而且無法挽回的事」，那就不是靠文字能解決的事。

有一個測試今天就能做，不用額外設定。把你一直載入的檔案從頭看一遍，每一行都問，沒有它，agent 會做錯嗎？把不通過的行都剪掉，再跑一次和之前一樣的任務，看有沒有什麼變差。我從自己的規則檔剪掉一些行時，通常沒看到什麼變差，不過我沒有系統地測過。

要測 skill 找不找得到，先把請求寫好。請求要用人平常會說的話，而不是描述裡的用語：三種要求這份工作的說法，再加兩個相鄰、不該觸發它的請求。

寫好以後，每一個請求都開一個新的對話，因為舊的對話可能已經載入了這個 skill，也不要輸入 skill 的名稱。然後看哪些 skill 被載入了。平台有紀錄的話就看紀錄，因為 agent 自己說的不算證據。沒載入，說明描述裡缺少使用者的用語；不該載入時卻載入了，說明描述太寬。

skill 有沒有改變什麼，是另一個測試。同一個任務在新的對話裡跑兩次，有 skill 和沒有 skill 各一次。看不出差別的話，就剪掉那些沒有差別的行。agent 本來就知道它們。

每条规则该放在哪里，为什么还是会被无视

1. 规则的三个存放位置

规则放在哪里，决定了它什么时候占地方，也决定了 agent 什么时候看得到它。

第一个位置上的规则始终加载。它们写在仓库根目录的一个简短文件里，每次对话都会读，所以只有每项工作都需要的规则才放这里，比如安全底线、怎么开始、被拒绝时该怎么办。在我的配置里，这个文件只有短短一页。如果一条规则十项工作里只有一项要用，它就不该放在这里。

只适用于某一类文件的规则，放在第二个位置，按文件加载。在 VS Code 里，指令文件的头部有一行 applyTo，写着一个匹配模式，比如“这个文件夹下的所有文件”。只有 agent 打开了匹配的文件，这些规则才会加载。比如怎么写 skill 的规则，要等 agent 打开 skill 文件时才加载，它去改 pipeline 时，这些规则一点地方也不占。下面是这样一个文件的开头：

一个只对 skill 文件加载的指令文件：applyTo 那一行就是匹配模式。
---
description: 'Guidelines for creating high-quality Agent Skills for GitHub Copilot'
applyTo: '.github/skills/**/SKILL.md'
---

.github/instructions/skills.instructions.md L1–L4 @ 1.5.50

其余的一切都按需阅读，包括长篇的操作指南和很少用到的细节。skill 和参考笔记就放在这里，工作需要时，agent 才去读。

还有第四种办法。hook（平台在固定时刻运行的小程序，见 硬性规则放在哪？用 hook）可以在你发的每条消息开头加上几行，让一条规则在用得着它的地方附近再出现一次。不过只能加几行，不然你又把那个长文件搭回来了。

有了这几个位置，对每条规则要问的就是同一个问题：这条规则多久用一次？agent 漏掉它会怎样？ 每次都要用、漏掉代价又大的，始终加载；只有某一类文件要用的，按文件加载；只有某项工作要用的，放进 skill。

最后这个位置值得多看几眼，因为 skill 并不是一次读完的。

2. skill 分三级加载

skill 是一个文件夹，主文件 SKILL.md 有头部（名字和描述）和正文（手册），旁边还可以放更长的笔记、脚本和模板。

agent 不会一次看到全部内容。

  1. 每个 skill 的名字和描述，它始终都看得到。这就是菜单。菜单不大，但每一轮都要付费，你装了多少个 skill，就付多少份。
  2. 需求对得上某个描述时，它才读整份手册。这由 agent 自己决定，或者由你直接输入 skill 的名字。
  3. 只有手册指到时，它才去读额外的文件，所以长的参考资料或脚本，要等到用得上的那一步才读。

这样一来，你可以装很多 skill，而不会把窗口填满。

这也意味着，在第 1 级，agent 手上只有描述可以依据，所以描述决定了这个 skill 能不能被找到。含糊的描述（比如“帮助提升代码质量”）什么也匹配不上。好的描述要说清三件事：这个 skill 做什么，什么时候用（“use when……”），以及人真正需要它时会说的那些话。长度也要留意，平台对它有限制，而啰嗦的描述还会占掉其他所有 skill 的地方。

不过，即使描述写得好，也不保证 skill 会被用上。VS Code 的文档说得很明白，发现机制只是让 skill 可用，并不保证模型会用，所以值得测一测（测试办法在这一节最后）。

还有一点，菜单本身也会变得太长。有了几十个 skill，菜单就成了一笔实实在在的开销，而其中很多 skill 从来不会被选中。一种办法是，任务不涉及某个业务领域时，就不把这个领域的 skill 放进菜单。

3. 一条规则，一个来源

规则一旦分散到几个地方，同一条规则就很容易写进三个文件。这样一来，改的时候总会漏掉一个，agent 读到的就是三个慢慢走样的版本。所以一条规则只写在一个地方，别处只放一个链接和一句话。要是发现一条规则得到处重复，那说明结构出了问题。规则文件也是共用的代码，所以要有人负责，把不再需要的行删掉。

4. 写下来的规则为什么会被无视

规则明明加载了，agent 为什么还是不理它？加载了不等于就会被遵守，常见的原因有五种。前四种出在文本本身和它放的位置上：

  1. 文件太长。对每一行都问一句，没有它，agent 会做错吗？不会，就删掉这一行。
  2. 规则冲突。两个文件说法不一样，模型会挑一个，而且不一定是你想要的那个。VS Code 的文档说，各个指令来源是叠加的，不要指望靠文件顺序来解决冲突，所以消除冲突是你自己的活儿。去把它们搜出来，改好措辞，直到只剩一个版本。
  3. 规则离用到它的地方太远。它在第一条消息里，现在已经在几千行之前了。按文件加载的规则，或者 hook 的提醒，能让它离得近一点。
  4. 没写理由。“绝对不要做 X”很容易被找个理由绕过去，“绝对不要做 X，因为 Y 会坏掉”，却能让模型把这个道理用到你没列出的情况上。

第五种原因最根本，改文本、挪位置都解决不了：规则只是请求。你写在文件里的任何东西，都只是给模型读的，而模型可以不照做。Claude Code 的文档说得很直白，记忆文件是“上下文，不是强制执行的配置”，想不管模型怎么决定都拦住某个动作，文档给的办法是 hook。skill 的正文也一样，它能让工作进行得顺畅，却不能让错事无法发生。

所以必须成立的规则，要写进代码。怎么做这个选择，是为什么 Agent 不听 prompt 里的规则？的主题。有了代码，文本只需要解释为什么，这样 agent 就不会再想办法绕过拒绝。在我的配置里，重要的规则两层都有，文本负责教，代码负责拦。

那 skill 的头部能不能改变这一点？有的平台允许头部带上更强的设置，这时要查清楚它们到底做什么。比如在 Claude Code 里，allowed-tools 只是预先批准工具，并不限制工具。skill 还可以注册 hook，而 hook 是代码（Skills）。

5. 再说一个选择：语言

“一个来源”的道理，也能回答一个只有在你用不止一种语言工作时才会碰到的问题。我的做法是，规则和 skill 只留一份，用英文写，再告诉模型用哪种语言回答，因为散文的第二份副本会慢慢和第一份对不上。这是我自己的选择，原则只有一条：只留一份。

三个问题，三个测试

添加一条规则之前，先问它三个问题：

  1. 这条多久用一次？如果很少，它就不放进始终加载的文件。
  2. 别处已经写过了吗？如果写过，就链接过去。
  3. 如果 agent 无视它，会怎样？如果答案是“发生了无法撤销的坏事”，那就不是文本能解决的事。

有一个测试今天就能做，不需要额外配置。把你那份始终加载的文件过一遍，对每一行都问，没有它，agent 会做错吗？把通不过的行都删掉，再跑一遍和之前一样的任务，看有没有什么变差。我从自己的规则文件里删过行，一般没看到什么变差，不过我没有系统地测过。

要测 skill 能不能被找到，先把请求写好。请求要用人真正会说的话，而不是描述里的话：三种提出这项工作的说法，再加两个相邻的、不该触发它的请求。

写好以后，每个请求都开一个新对话，因为旧对话里可能已经带着这个 skill，也不要输入 skill 的名字。然后看加载了哪些 skill。平台有日志的话就看日志，因为 agent 自己怎么说不算证据。没加载，说明描述里缺了用户会说的词；不该加载时却加载了，说明描述太宽。

skill 有没有改变什么，是另一个测试。同一个任务在新对话里跑两次，一次带 skill，一次不带。如果看不出区别，就把那些不起作用的行删掉。agent 本来就知道它们。

What loading less costs

If splitting rules up saves room, what does it cost? A rule in a skill is read only if the skill is found, so a rule that matters but sits in a skill with a weak description may never be read at all. That is the price of saving room. So when missing a rule is costly, the rule belongs in a place that loads.

Nor is being found something you settle once. A skill is not a setting but a choice the model makes each time, so the same request can load it once and not the next. The more skills you have, the harder the choice between them becomes, because even a good description may be confused with its neighbour. Keep each skill narrow, and say what it is not for.

The fourth way, a hook that injects text, has a trap of its own. Its lines add up, because each one is repeated on every message. The always-loaded file has a similar limit: the Claude Code docs suggest under about 200 lines. That is a rule of thumb rather than a measured limit, so measure your own.

少載入要付出什麼

把規則拆開能省位子，那要付出什麼？skill 裡的規則，只有 skill 被找到時才會被讀，所以一條要緊的規則，要是放進了一個描述很弱的 skill，可能永遠不會被讀到。這就是省位子的代價。所以，漏掉一條規則的代價要是很高，它就該留在會載入的地方。

而且找不找得到，也不是一次就定下來的。skill 不是一項設定，而是模型每次都要重新做的選擇，所以同一個請求，這次可能載入它，下次就未必。skill 越多，在它們之間挑就越難，因為就算描述寫得好，也可能和相鄰的 skill 搞混。所以每一個 skill 的範圍都要窄，並寫明它不是做什麼的。

用 hook 往訊息裡注入文字，也就是第四種方式，同樣有自己的陷阱：這些行會越積越多，因為每一行都會在每則訊息裡重複一次。一直載入的那個檔案也有類似的上限：Claude Code 的文件建議它低於約 200 行，不過那只是經驗法則，不是量出來的限制，你得量量自己的。

少加载要付出什么

把规则拆开能省地方，那要付出什么？skill 里的规则，只有 skill 被找到才会被读到，所以一条重要的规则，要是放进了一个描述很弱的 skill，可能永远都不会被读到。这就是省地方的代价。所以，漏掉一条规则的代价要是很高，它就该放在会加载的地方。

而且能不能被找到，也不是一次就定下来的。skill 不是一项设置，而是模型每次都要重新做的选择，所以同一个请求，这次可能加载它，下次就未必。skill 越多，在它们之间挑就越难，因为即使描述写得好，也可能和相邻的 skill 混淆。所以每个 skill 都要写得窄一点，并说清它不是干什么的。

第四种办法，也就是往消息里注入文本的 hook，也有自己的坑。这些行会越积越多，因为每一行在每条消息里都会重复一次。始终加载的那个文件也有类似的上限：Claude Code 的文档建议它不超过 200 行左右，不过这只是经验法则，不是量出来的上限，你得量量自己的。

Do the platforms agree? Industry practice

VS Code loads skills in the same three levels. It reads the name and description first, loads the body "once the skill is relevant", and reads other files "only when it references them". It also says that discovery "does not guarantee that it invokes a skill for every relevant prompt". For instruction files, its advice is to "keep your instructions short and self-contained" and to "include the reasoning behind rules", and it calls the sources "additive". (Agent skills, Custom instructions)

Anthropic describes the same three levels for Agent Skills: the name and description first, the body when the skill applies, and linked files only as needed (Equipping agents for the real world with Agent Skills). Claude Code suggests keeping each memory file under 200 lines, moving rules for one part of the code into files that load only for matching paths, and removing contradictions. It treats these files as "context, not enforced configuration" (How Claude remembers your project).

So the two platforms use the same shape: an always-on file, path-scoped rules and on-demand skills. Because the idea is the same across tools, what you build here moves with you.

平台也這麼看嗎？ 業界做法

VS Code 對 skill 也是三層載入。它先讀名稱和描述，「skill 相關時」才載入正文，其他檔案「只有在被引用時」才讀。它還說，發現機制「不保證每個相關的 prompt 都會呼叫某個 skill」。對於指令檔，它建議「讓你的指令簡短而獨立」「附上規則背後的理由」，並說來源是「疊加的」。（Agent skills、Custom instructions）

Anthropic 為 Agent Skills 描述的也是這三層，先是名稱和描述，skill 適用時載入正文，連結的檔案只在需要時才載入（Equipping agents for the real world with Agent Skills）。Claude Code 建議每個 memory 檔保持在 200 行以下，把屬於程式碼某一部分的規則移到只在路徑符合時才載入的檔案，並移除矛盾。它把這些檔案當成「上下文，不是強制執行的設定」（How Claude remembers your project）。

可見兩個平台用的是同一種結構，一直載入的檔案、依路徑載入的規則、按需要才讀的 skill。既然各個工具的想法都一樣，你在這裡做的東西也就可以帶著走。

平台也这么看吗？ 业界做法

VS Code 对 skill 也是三级加载。它先读名字和描述，“一旦这个 skill 相关”才加载正文，其他文件“只有被引用时”才读。它还说，发现机制“不保证对每个相关的 prompt 都调用 skill”。对指令文件，它建议“让你的指令保持简短、自成一体”，“写明规则背后的理由”，并说各个来源是“叠加”的。（Agent skills、Custom instructions）

Anthropic 对 Agent Skills 描述的也是这三级，先是名字和描述，skill 适用时再读正文，链接的文件只在需要时才读（Equipping agents for the real world with Agent Skills）。Claude Code 建议每个记忆文件控制在 200 行以内，把只关系到部分代码的规则移到只对匹配路径加载的文件里，并去掉互相矛盾的地方。它把这些文件视为“上下文，不是强制执行的配置”（How Claude remembers your project）。

可见两个平台用的是同一种结构，始终开启的文件、按路径划分的规则、按需的 skill。既然各个工具的思路都一样，你在这里搭的东西也就可以带着走。

Which by-hand parts to delete, and what stays Industry practice

Two things in this chapter are done by hand: listing only the skills of the current area, and cutting a menu that has grown too long. Both are the kind of work the platform may take over. If the platform learns to load skills by relevance better, the area trick can go.

The reasoning does not retire, though. A bigger window does not make a long rule file better. It only lets you hold more before the problem shows up. And no loading scheme makes a written rule enforced. I would look again if a platform could show, on my own tasks, that long rule files are followed as well as short ones.

哪些手動的部分可以刪，哪些會留下 業界做法

這一章裡有兩件事是靠手動做的：只列出目前領域的 skill，以及剪短過長的菜單。這兩件都是平台以後可能接手的工作。如果平台學會更好地按相關性載入 skill，按領域篩選的辦法就可以不用了。

不過這套道理不會過時。視窗變大，並不會讓長的規則檔變好，它只是讓你在問題出現之前能多放一些。何況沒有任何載入方式，能讓寫下來的規則變成強制執行。如果有平台能在我自己的任務上證明，長的規則檔和短的守得一樣好，我會重新檢視一次。

哪些手工活可以删，哪些会留下 业界做法

这一章里有两件事是靠手工做的：只列出当前领域的 skill，以及削减过长的菜单。这两件都是平台以后可能接手的活儿。如果平台学会了更好地按相关性加载 skill，按领域取舍的办法就可以去掉。

不过这套道理不会过时。窗口变大，并不会让长的规则文件变好，它只是让你在问题冒出来之前能多装一些。何况没有哪种加载方案能让写下来的规则变成强制执行的。如果有平台能在我自己的任务上证明，长的规则文件和短的一样被遵守，我会重新考虑。
