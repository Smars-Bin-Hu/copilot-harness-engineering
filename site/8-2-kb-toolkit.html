In one sentence

Which objects exist and who uses whom is a question with one right answer, so a script computes it, the same way every time and at no token cost. Those scripts are called a toolkit, and the toolkit is code the team owns, written for your own technology stack.

一句話

有哪些物件、誰用誰，這個問題只有一個正確答案，所以交給腳本來算：每次都用同樣的方式算，也不花 token。這些腳本叫 toolkit，是團隊自己擁有的程式碼，為你自己的技術堆疊而寫。

一句话

有哪些对象、谁用谁，这个问题只有一个正确答案，所以交给脚本来算：每次都按同样的方式算，也不花 token。这些脚本叫 toolkit，是团队自己拥有的代码，针对你自己的技术栈来写。

For leaders

  • The decision: have the team own a small set of scripts that list which objects exist and who uses whom, instead of asking a model to work it out each time.
  • The risk: a model asked for the map reads by judgment. It can skip an object, and if you ask twice you get two different maps. A script gives the same map every time and says what it could not read. On a small open-source project my sample found 58 objects in 35 files and all 6 known uses, which shows that it runs, not that it works on your code.
  • The cost of doing it right: the model writes the scripts and a person approves the design, after which the scripts cost no tokens. They are still code, and they have to be maintained when the stack changes. I have not tested a very large code base.
  • Ask the team: "Who owns the scripts that map our code, and which uses do we already know they must find?"

給主管

  • 要做的決定：讓團隊擁有一小組腳本，列出有哪些物件、誰用誰，不要每次都請模型去推算。
  • 風險：請模型畫地圖，它是憑判斷在讀，可能漏掉一個物件，問兩次還會給出兩張不同的地圖。腳本每次給的都是同一張地圖，也會說出自己讀不到的部分。在一個小的開源專案上，我的範例在 35 個檔案裡找到 58 個物件，6 處已知的使用也全都找到了；這只證明它跑得起來，不證明它在你的程式碼上行得通。
  • 做對的成本：模型寫腳本，人批准設計，之後腳本就不花 token 了。不過它們終究是程式碼，堆疊一改變就得跟著維護。我沒有測過很大的程式碼庫。
  • 可以問團隊：「畫我們程式碼地圖的腳本誰負責？我們已經知道它們必須找到的使用有哪些？」

写给管理者

  • 要拍板的事：让团队拥有一小组脚本，列出有哪些对象、谁用谁，而不是每次都让模型去推算。
  • 风险：让模型出地图，它是凭判断在读，可能漏掉对象，问两次还会给出两张不同的地图。脚本每次给的都是同一张地图，还会说明哪些地方它没读懂。在一个小的开源项目上，我的样例在 35 个文件里找到了 58 个对象，已知的 6 处使用也全部找到；这只说明它能跑，不说明它在你的代码上管用。
  • 做对的代价：脚本由模型来写，设计由人审批，之后脚本就不花 token 了。不过它们终归是代码，技术栈一变就得跟着维护。我没有在非常大的代码库上测过。
  • 可以问团队：“谁负责给我们的代码画地图的那些脚本？我们已经知道哪些使用是它必须找到的？”

Why not let the model draw the map?

Before an agent can write a card about an object, someone has to answer two plain questions. Which objects are there? And for each one, what does it use? Here an object is a named thing in the code that other things can use (see A knowledge base: an honest index of the code), and a use is one object depending on another, as when a procedure calls another procedure, a class reads a table or a job runs a package. Put all the objects and all the uses together and you have the map of the code, the name the previous chapter gave it. If you know the term dependency graph, it is the same thing.

The obvious way to get a map is to ask a model to read the code and produce one, and it would do something reasonable. But it decides what to read next from what it just read, and along that path it can skip an object, follow a name that means two things, or stop early. It cannot say how much it missed either, and if you ask it twice, the two maps differ.

A script that parses every file has none of these problems. It gives the same map every time, for no tokens, and it can say what it could not read. That is the whole case for scripts. But where does the script itself come from?

為什麼不讓模型來畫地圖？

在 agent 能為一個物件寫卡片之前，得有人回答兩個簡單的問題：有哪些物件？每一個物件又用了什麼？這裡的物件，是程式碼裡一個有名字、別的東西可以使用的東西（見 知識庫：程式碼的誠實索引）。物件之間的關係叫使用：一個物件依賴另一個物件，例如一個預存程序呼叫另一個預存程序，一個類別讀一張資料表，一個工作執行一個套件。所有物件加上所有使用，合起來就是程式碼的地圖，這是上一章取的名字。如果你聽過依賴圖這個詞，它們是同一回事。

最直接的做法，是請模型讀程式碼、把地圖畫出來，它也會做出合理的東西。問題是，它靠剛讀到的內容決定下一步讀什麼，一路讀下去，可能漏掉一個物件，可能順著一個有兩種意思的名字追下去，也可能太早停下來。它自己也說不出漏了多少。再問它一次，兩張地圖還會不一樣。

而解析每個檔案的腳本，沒有這些問題。它每次給同一張地圖，不花 token，還能說出自己讀不到的部分。用腳本的理由，說到底就是這幾條。可是腳本本身又從哪裡來呢？

为什么不让模型来画地图？

agent 要给一个对象写卡片，得先有人回答两个朴素的问题：有哪些对象？每个对象又用到了什么？这里的对象，是代码里有名字、别的东西可以使用的东西（见知识库：代码的诚实索引）。对象之间的关系叫使用：一个对象依赖另一个对象，比如一个存储过程调用另一个存储过程，一个类读一张表，一个任务运行一个包。把所有的对象和所有的使用合在一起，就是代码的地图，这是上一章起的名字。如果你听说过依赖图，它们是一回事。

最顺手的办法，是让模型去读代码，把地图交出来，它也会做出一份像样的东西。问题是，它根据刚读到的内容决定下一步读什么，一路读下去，可能漏掉一个对象，可能顺着一个有两种意思的名字追下去，也可能太早停下来。它自己也说不出漏了多少。再问它一次，两张地图还会不一样。

而一个逐个解析文件的脚本，没有这些毛病。它每次给出同样的地图，不花 token，还能说出哪些东西它没读懂。用脚本的理由，说到底就是这几条。可脚本本身又从哪里来呢？

How scripts draw the map

What the toolkit is

That depends on your stack, since each stack writes a procedure, a job or a class into a file in its own way. A call is CALL name in one stack and a method on an injected object in another, so there is no ready-made parser that covers every convention of your code. Where a language server or a code-search service already gives you objects and uses, use it first (see When to delete your extractors). Only what it does not cover needs scripts of your own.

What you write is the toolkit, a small set of programs plus one config file, all kept inside the knowledge base. Each program is an extractor, which reads one kind of file and prints the objects it defines and the uses it finds. The config file says what an object is in your code and what kinds of use count. It also names the types of object that are entry points (the places the outside world calls in, such as a screen, an API or a scheduled job), the folders that are retired, and the words to ignore in names.

A runner applies the extractors to each repository's main branch and saves the map in a cache. That way, on the next run, only the files that changed since the last run are read again.

Who writes it: the model designs, a person approves, scripts run

You might expect to write the extractors yourself. In my setup the model writes them, in four moves. The first is a survey, in which a script counts the kinds of file in each repository and the model reads a few samples of each kind. With those samples read, the model writes a design that sets down what objects and uses look like in this stack, with examples from the code. A person reads the design and approves it, and this is the moment to catch "that is not a use, that is a comment". Then the model builds the extractors. The last move, the subject of the next section, is to run them until the known uses are found.

The model is good at writing a parser once, but it should not be the parser every time. After the build, only scripts touch the code.

A test that stays: the uses a person knew

When the map is first made, how do you know it is not nonsense? A person writes down 5 to 10 uses they know are there, for example "procedure A calls procedure B", and these go into a file in the toolkit. It is better to write them before the extractor exists, and not to show them to the model while it writes, so that the extractor is not tuned to just these. Every run of the map must find all of them. If a later change to an extractor loses one, the run fails.

This file of known uses is a regression test, a test that guards what already worked. It is small, and I do not pretend it measures the whole map. What it can do is grow: whenever you meet a use the map missed, add it. Measuring how complete the map is comes later, in Chapter 8.3.

The known uses are not the only check. On every run the runner reports two more things. One is the files it could not read, or read without finding anything, and either kind is suspicious. The other is the names that are used but defined nowhere. They may be other systems, deleted code, or a form the extractor misreads, so look at a few.

Two samples, only as examples

The harness ships no toolkit of its own (why, comes after the samples), only two samples that show the shape. One is for SQL Server, with stored procedures, scheduled agent jobs and integration packages. The other is for Spring, covering a Spring Boot service with controllers, repositories, entities and tables.

I built the Spring sample on the open-source spring-petclinic project. On that code it found 58 objects in 35 files and all 6 of the known uses, and no file failed to read or came back empty. That is a smoke test: it shows that the toolkit runs on one small, tidy project, not that it works on yours. The hard cases (SQL built at run time, calls driven by configuration) are not in that project. Your stack, your conventions and your odd cases are what you write.

Then the function that reads one Java file and prints its objects and uses:

The extractor for a Java file: find the class, its role, and the types it uses.
def java(text: str, context: Dict[str, Any]) -> List[Dict[str, Any]]:
    clean = blank_comments(text)
    match = TYPE.search(clean)
    if not match:
        return []
    name, head = match.group(2), clean[:match.start()]
    role = next((role for mark, role in ROLE if mark in head), "class")
    repository = REPOSITORY.search(match.group(3))
    if repository:
        role = "repository"
    refs: List[Dict[str, Any]] = []
    if repository:
        refs.append({"kind": "reads", "name": repository.group(1), "as": "entity", "line": line_at(clean, match.start(3))})
    parent = EXTENDS.search(match.group(3))
    if parent and not repository:
        refs.append({"kind": "extends", "name": parent.group(1), "line": line_at(clean, match.start(3))})
    table = TABLE.search(head)
    if table:
        refs.append({"kind": "maps", "name": table.group(1), "as": "table", "line": line_at(clean, table.start(1))})
    body = clean[match.end():]
    offset = line_at(clean, match.end()) - 1
    for used in used_types(body):
        if used != name:
            refs.append({"kind": "uses", "name": used, "line": offset + 1})
    found = [{"id": f"{role}:{name}", "type": role, "name": name, "line": line_at(clean, match.start(2)), "dynamic": False, "refs": refs}]
    if role == "controller":
        found += endpoints(clean, head, body, offset, name)
    return found

Why a general harness does not include a toolkit

I did not ship parsers for the common stacks. A parser that is almost right fails silently, and each team writes code a little differently. A toolkit the team owns and audits (next chapter) can instead be fixed when it misses. It also lives in the knowledge base, so upgrading the harness never overwrites it.

Draw and check a map of one repository

  1. Pick one repository and write down 5 to 10 uses you know are there, each with a file and line.
  2. Ask an agent to draft what objects and uses look like in your stack, with examples from your code. Read the draft and correct it.
  3. Have the agent write the extractors. Run them, and check that all your known uses appear.
  4. Run them twice. The two outputs must be identical.

腳本怎麼畫出地圖

toolkit 是什麼

腳本從哪裡來，要看你用的是什麼技術堆疊。一個預存程序、一個工作或一個類別在檔案裡長什麼樣，每種堆疊都不一樣。同樣是呼叫，在一種堆疊裡寫成 CALL name，在另一種堆疊裡是注入物件上的一個方法。寫法這麼多，沒有哪個現成的解析器能涵蓋你程式碼的每一種慣例。如果語言伺服器或程式碼搜尋服務已經給得出物件和使用，就先用它們（見 什麼時候可以刪掉自己的抽取器）。它們沒涵蓋的部分，才需要你自己寫腳本。

這些要你來寫的東西，就是 toolkit：一小組程式加上一個設定檔，全都放在知識庫裡面。每支程式是一個抽取器，讀一種檔案，印出這種檔案定義的物件和它找到的使用。設定檔說明在你的程式碼裡什麼是物件、哪些種類的使用算數，也說明哪些類型的物件是入口（從外部呼叫進來的地方，例如畫面、API、排程工作）、哪些資料夾已經退役，以及名字裡哪些詞要忽略。

執行器把抽取器用在每個倉庫的主分支上，並把地圖存進快取。這樣一來，下一次執行時，只要重讀上次之後改過的檔案。

誰寫：模型設計，人批准，腳本執行

你可能以為抽取器得自己寫。在我的設定裡，是模型來寫，一共分四步。第一步是調查：一個腳本數出每個倉庫裡各種檔案的數量，模型每一種讀幾個樣本。樣本讀過之後，模型寫出一份設計，說明在這個堆疊裡物件和使用長什麼樣，並附上程式碼裡的例子。人讀這份設計並批准它，這時正好可以抓出「那不是使用，那是註解」這類問題。接著，模型寫抽取器。最後一步留給下一節講：反覆執行，直到已知的使用都找到為止。

模型擅長把解析器寫一次，但它不該每一次都親自當解析器。建好之後，碰程式碼的就只有腳本了。

一個一直留著的測試：人知道的那些使用

地圖第一次做出來時，你怎麼知道它不是胡說？辦法是由人寫下 5 到 10 處自己確定存在的使用，例如「預存程序 A 呼叫預存程序 B」，放進 toolkit 裡的一個檔案。這些最好在抽取器出現之前就寫好，模型寫的時候也別給它看，免得抽取器只是對著這幾處調校出來的。之後每次執行都必須找到所有這些使用，所以哪天改抽取器時弄丟了一處，那次執行就會失敗。

這份已知使用的清單，就是一個迴歸測試，也就是確保原本好的東西不會壞掉的測試。它很小，我也不假裝它量得出整張地圖。它能做的是慢慢長大：每次你遇到地圖漏掉的使用，就把它加進去。地圖到底有多完整，要到 第 8.3 章 再去量。

不過，已知的使用並不是唯一的檢查。執行器每次還會回報兩類可疑的情況。一類是檔案出了問題：要麼讀不了，要麼讀了什麼都沒找到。另一類是被使用、卻沒在任何地方定義的名字。這些名字可能是別的系統，可能是被刪掉的程式碼，也可能是抽取器讀錯的寫法，值得挑幾個看看。

兩個範例，只當例子

harness 沒有附帶自己的 toolkit（為什麼不附，看完範例再說），只有兩個範例，讓你看看它長什麼樣。一個是 SQL Server 的，涵蓋預存程序、排程的 agent 工作和整合套件；另一個是 Spring 的，針對一個 Spring Boot 服務，裡面有 controller、repository、entity 和資料表。

Spring 範例是我在開源專案 spring-petclinic 上建的。在那份程式碼上，它在 35 個檔案裡找到 58 個物件，6 處已知的使用也全都找到了，沒有檔案讀取失敗，也沒有檔案是空的。這算是冒煙測試：它證明 toolkit 在一個小而整齊的專案上跑得起來，不證明在你的專案上也行得通。難的情況（執行時才組出來的 SQL、由設定驅動的呼叫）不在那個專案裡。你的堆疊、你的慣例和你那些奇怪的情況，要由你來寫。

為什麼通用的 harness 不附 toolkit

我沒有為常見的堆疊附上解析器。差不多對的解析器會悄悄出錯，而且每個團隊寫程式碼的方式都有點不同。團隊自己擁有、自己抽查的 toolkit（下一章）就不一樣，漏掉東西時可以修。它又放在知識庫裡，所以升級 harness 不會覆蓋它。

動手幫一個倉庫畫地圖並驗證

脚本怎么画出地图

toolkit 是什么

脚本从哪里来，要看你用的是什么技术栈。一个存储过程、一个任务或者一个类在文件里长什么样，每种栈都不一样。同样是一次调用，在一种栈里写作 CALL name，在另一种栈里是注入对象上的一个方法。写法这么多，没有哪个现成的解析器能覆盖你代码里的所有写法。如果语言服务器或代码搜索服务已经能给你对象和使用，就先用它们（见什么时候可以删掉自己的抽取器）。它们覆盖不到的部分，才需要你自己写脚本。

这些要你来写的东西，就是 toolkit：一小组程序加一个配置文件，都放在知识库里。每个程序是一个抽取器，读一种文件，打印出这种文件定义的对象和它找到的使用。配置文件写明在你的代码里什么算对象、哪几种使用算数，还写明哪几类对象是入口（外部调用进来的地方，比如一个页面、一个 API、一个定时任务），哪些文件夹已经停用，以及名字里要忽略哪些词。

一个运行器把抽取器用到每个仓库的主分支上，把地图存进缓存。这样一来，下一次运行时，只需要重新读上次以来改过的文件。

谁来写：模型设计，人审批，脚本运行

你可能以为抽取器得自己写。在我的配置里是模型来写，一共分四步。第一步是调研：一个脚本统计每个仓库里各种文件的数量，模型每种读几个样本。样本读过以后，模型写出一份设计，说明在这个技术栈里对象和使用长什么样，并附上代码里的例子。人来读这份设计并审批，这时正好可以抓出“那不是使用，那是注释”这类问题。接着，模型写抽取器。最后一步留给下一节讲：反复运行，直到已知的使用都找到为止。

模型擅长把一个解析器写一次，但它不该每次都亲自充当解析器。构建完成之后，碰代码的就只有脚本了。

一个一直留着的测试：人知道的那些使用

地图刚做出来时，你怎么知道它不是在胡说？办法是由人写下 5 到 10 处他们知道确实存在的使用，比如“存储过程 A 调用存储过程 B”，放进 toolkit 里的一个文件。这些最好在抽取器出现之前就写好，模型写抽取器时也别给它看，免得抽取器只是为这几处调出来的。之后每次运行都必须找到全部这些使用，所以哪天改抽取器时丢了一处，那次运行就会失败。

这份已知使用的清单，就是一个回归测试，也就是保护已经管用的东西的测试。它很小，我也不假装它衡量了整张地图。它能做的是慢慢长大：每当你发现地图漏掉了一处使用，就把它加进去。地图到底有多完整，要到第 8.3 章再去衡量。

不过，已知的使用并不是唯一的检查。运行器每次还会报告两类可疑情况。一类是文件出了问题：要么读不了，要么读了什么都没找到。另一类是被用到、却哪里都没定义的名字。这些名字可能指向别的系统，可能是已经删除的代码，也可能是抽取器读错的写法，值得挑几个看看。

Spring 样例是我在开源项目 spring-petclinic 上做的。在那份代码上，它在 35 个文件里找到了 58 个对象，已知的 6 处使用也全部找到，没有文件读失败，也没有文件读出来是空的。这算一次冒烟测试：它说明 toolkit 能在一个小而整洁的项目上跑起来，不说明它在你的项目上也管用。难的情况（运行时拼出来的 SQL、由配置驱动的调用）不在那个项目里。你的技术栈、你的约定、你那些古怪的情况，要你自己来写。

为什么通用的 harness 不带 toolkit

我没有为常见的技术栈提供解析器。差不多对的解析器会悄悄出错，而且每个团队写代码的方式都略有不同。团队自己拥有、自己审计的 toolkit（下一章）就不一样了，漏了能修。它又放在知识库里，所以升级 harness 永远不会把它覆盖掉。

What owning a toolkit costs, and what it cannot see

If scripts give the same map every time for no tokens, where is the cost? The plainest one is that the toolkit is code to maintain. When your stack changes, so does it, and that is the price of owning it.

Maintenance keeps the toolkit in step with the stack, but it does not make it read every form correctly. An extractor that handles three ways of writing a call and misses a fourth still looks fine on the known uses. That gap is what the audit is for (8.3).

And some things are beyond any reading of forms. A query built as a string at run time, or a call driven by a config table, is invisible to any parser. These are marked, not guessed (8.3). All of this comes from a small project. I have not tested the toolkit on a very large code base.

自己擁有 toolkit 要付出什麼，它又看不到什麼

如果腳本每次給同一張地圖，又不花 token，那代價在哪？最直接的一筆是，toolkit 是要維護的程式碼。你的堆疊改變，它也得跟著改。

維護能讓 toolkit 跟上堆疊，卻不能保證它把每種寫法都讀對。假如一次呼叫有四種寫法，抽取器只認得三種，已知的使用照樣一處不少，看不出有什麼問題。這個缺口，正是抽查要管的（8.3）。

還有些東西，抽取器認得再多寫法也看不到。執行時組成字串的查詢，或由設定表驅動的呼叫，任何解析器都看不見。這些要標出來，不要猜（8.3）。這些都來自一個小專案，我沒有在很大的程式碼庫上測過 toolkit。

如果脚本每次给同一张地图，又不花 token，那代价在哪？最直接的一笔是，toolkit 是要维护的代码。你的技术栈变了，它也得跟着变。

维护能让 toolkit 跟上技术栈，却不能保证它把每种写法都读对。假如一次调用有四种写法，抽取器只认得三种，已知的使用照样一处不少，看不出有什么问题。这个缺口，正是审计要管的（8.3）。

还有些东西，抽取器认得再多写法也看不到。运行时拼成字符串的查询，或者由配置表驱动的调用，对任何解析器都不可见。这些会被标出来，不去猜（8.3）。这些都来自一个小项目，我没有在非常大的代码库上测过 toolkit。

When to delete your extractors

Your own extractors are only one way to get the map. If a tool you trust, such as your language server or a code-search service, already gives you objects and uses with a measured accuracy, feed its output into the map and drop your extractors. The rest of the road does not care where the map came from.

什麼時候可以刪掉自己的抽取器

自己寫的抽取器，只是得到地圖的一種辦法。如果一個你信任的工具，例如你的語言伺服器或程式碼搜尋服務，已經給得出物件和使用，準確度也量過，就把它的輸出餵進地圖，丟掉自己的抽取器。路線的其餘部分不在乎地圖從哪裡來。

什么时候可以删掉自己的抽取器

自己写的抽取器，只是得到地图的一种办法。如果你信任的某个工具，比如你的语言服务器或代码搜索服务，已经能给出对象和使用，而且准确度测量过，就把它的输出喂给地图，丢掉你自己的抽取器。路线上的其余部分不关心地图是从哪来的。
