Problem. The agent guesses paths and commands, or tidies files you changed.

Pattern. Keep a short always-loaded page. Put in it only what the model would get wrong without it, and put it first. Two limits are enough to begin.

One hook entry for every moment

Problem. Several hook scripts, each with its own timeout and shell, are hard to keep in step.

Pattern. Make the configuration file only say which moments to call, and point every moment to one program. The program decides what to do. Set a time limit, and remember the file is read when the window starts.

The entry for the moment before a tool runs: it only names the program and its time limit.
    "PreToolUse": [
      {
        "type": "command",
        "command": "python3 .harness/engine/hook.py",
        "windows": "python .harness/engine/hook.py",
        "bash": "python3 .harness/engine/hook.py",
        "powershell": "python .harness/engine/hook.py",
        "cwd": ".",
        "timeout": 30,
        "timeoutSec": 30
      }
    ],

Refuse a dangerous command, with a reason

Problem. A command whose damage cannot be undone, such as recursive deletion of a root or home folder, should never run.

Pattern. Write a pattern and a why sentence for each. The agent reads the reason, so say what the command would do. Keep the pattern narrow, because a false refusal is a stuck task. It stops common spellings, not every spelling.

One real refusal rule: recursive force-delete of the root, home or current folder, with a reason the agent can read.
      {
        "why": {"en": "it recursively deletes the root, the home folder or the current folder", "zh": "递归删除根目录、家目录或当前目录"},
        "pattern": "{cmd}rm\\s+(?:-[a-z]+\\s+)*-[a-z]*(?:r[a-z]*f|f[a-z]*r)[a-z]*\\s+(?:/|~|\\$home|\\*|\\.|\\.\\.)/?\\*?(?:\\s|$|[;&|])"
      },

Pattern. Set disable-model-invocation: true, and say in the description that the agent must not call it. This limits who starts the skill. It does not limit what the skill does once started.

Make a stop explain itself

Problem. An unattended run that stops with "ran into a problem" leaves the person to work out what happened.

Pattern. Tell the agent when to stop and when not to, and what the reason must contain: which step is stuck, why, and what the person must decide. The hook still judges the stops that facts can show.

When to stop by yourself, when not to, and how to write the reason for the person who comes back.
## Stop

| Case | Example |
| --- | --- |
| A trade-off the plan does not cover and that changes the result | Both tables have the field, defined differently, and the plan does not say which to use |
| Information is missing, and a guess may be wrong | The knowledge base has no definition of this metric |
| A step cannot be done | The file to change does not exist in the target repository; a needed permission is missing |
| Something out of scope has to be touched | A file outside the task folder, a git write command, a change to the plan |
| The plan itself turns out wrong | Following the plan would contradict the requirement |
| The reviewer names the same problem twice and you cannot fix it | Your understanding is off; more fixing just spins in place |

## Do not stop

| Case | What to do |
| --- | --- |
| A small implementation choice | Decide it and add a line to `LOG.md`: what you decided, and why |
| One tool call fails | Try once more another way |
| The reviewer did not pass it, and the problem is clear | Fix as it says and check again |
| The gate refuses once, and the reason has a next step | Do the next step. On a second refusal autorun stops by itself |

## How to write the reason

Write it for the user who comes back. One sentence that says: which step is stuck, why, and what they have to decide.

- Good: `Step 3: orders and orders_v2 both have updated_at, defined differently, and the plan does not say which to use. Yours to decide.`
- Bad: `Ran into a problem`
