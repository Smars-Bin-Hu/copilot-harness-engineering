7.2

Ten things at once: parallel tasks同時管十件事：並行的是任務同时管十件事：并行的是任务

This chapter assumes you have read Use subagents sparingly and Manage tasks, not chats.

讀這一章，你需要讀過 慎用子 agent 和 管任務，不管對話。

读这一章之前，需要先读过慎用子 agent和管任务，不管对话。

The Knowledge經驗分享经验分享

In one sentence

To run ten things at once, run ten separate tasks with one agent each, and call the person only at the gates. Split by task, not by file, although read-only work inside a task can still go to subagents.

一句話

要同時管十件事，就跑十個獨立的任務，每個任務一個 agent，只在門口叫人。按任務拆，不按檔案拆；不過任務裡唯讀的工作，仍然可以交給子 agent。

一句话

想同时管十件事，就开十个独立的任务，每个任务一个 agent，只在关卡处叫人。按任务拆，不按文件拆；不过任务内部只读的活，仍然可以交给子 agent。

For leaders

  • The decision: decide whether people may run several tasks at once, how many they start with, and where a person is called.
  • The risk: the limit is a person's attention, not the number of agents, and a gate that is always approved without reading is decoration. I have no evidence of a net speed-up, because I have not measured ten tasks in parallel against ten in a row.
  • The cost of doing it right: usage grows with the number of tasks (ten tasks, ten times the usage), and you need a board or a simple list of what waits. Start with two or three.
  • Ask the team: "Which tasks are waiting for a person right now and since when, and what happens if two of them change the same files?"

給主管

  • 要做的決定：決定可不可以讓大家同時跑好幾個任務、一開始跑幾個，以及在哪些地方叫人。
  • 風險：限制在人的注意力，不在 agent 的數量；一道永遠不讀就批准的門，只是裝飾。我沒有淨加速的證據，因為十個任務並行和十個一個接一個跑，我沒有量過、比過。
  • 做對的成本：用量隨任務數成長（十個任務，十倍的用量），還需要一個看板，或一份簡單的等待清單。從兩三個開始。
  • 可以問團隊：「現在有哪些任務在等人，等多久了？如果其中兩個改了同樣的檔案，會怎樣？」

写给管理者

  • 要拍板的事：定下是否允许大家同时跑几个任务，一开始跑几个，以及在哪些地方叫人。
  • 风险：瓶颈是人的注意力，不是 agent 的数量；一个永远不看就批准的关卡，只是摆设。我没有整体提速的证据，因为十个任务并行和十个任务串行，我没有对比测过。
  • 做对的代价：用量随任务数增长（十个任务，十倍用量），还得有一块看板，或者一份简单的等待清单。先从两三个开始。
  • 可以问团队：“现在有哪些任务在等人、等了多久？如果其中两个改了同样的文件，会怎样？”

If one agent is good, why not run ten?

An agent can get a lot done while you are away, so the next thought comes naturally: if one agent is good, why not run many at once? There are two ways to read that thought, and only one of them works.

The first reading is one big job with many agents. When you hand over a large task, a coordinator splits it among a team of agents, each with a role such as plan, implement or check. The whole thing looks like a company org chart. That is the setup Use subagents sparingly tested, and what it found was that handovers lose understanding and that every agent reads the same files again. That chapter does not argue against a fresh worker for each step of one task. What it argues against is several agents changing the same files at the same time, because then someone has to merge their work.

The second reading is many jobs with one agent each: ten requests from ten people, say, or ten different problems of your own. Each one is a separate piece of work with its own folder, its own agent and its own finish line. Since nothing is shared between them, nothing needs to be merged. This is the reading the rest of the chapter follows. It is not clever, but it is what lets one person keep ten things moving.

Run work that way and the thing in short supply is not agents. It is you. An agent can wait for a person for hours without using any compute, but what it waits with goes stale: the conversation's cache expires, and by the time you answer, the repository may have moved on. The waiting is costly on your side too, because a person who keeps ten agents in mind soon loses the thread. So the design question becomes how to spend one person's attention across ten tasks.

一個 agent 好用，為什麼不跑十個？

你不在的時候，agent 也能做很多事。於是很自然會冒出下一個念頭：既然一個 agent 好用，為什麼不同時跑很多個？這個念頭有兩種讀法，只有一種行得通。

第一種讀法，是一個大工作配很多個 agent。你交出一個大任務，由協調者把它分給一組 agent，每個 agent 有自己的角色，像是計畫、實作、檢查。整個看起來就像公司的組織圖。慎用子 agent 測的正是這種設定，結果是交接會丟掉理解，每個 agent 又得把同樣的檔案再讀一遍。那一章並不反對為一個任務的每一步換一個新的工人，它反對的是好幾個 agent 同時改同樣的檔案，因為那樣就得有人去合併它們的工作。

第二種讀法，是很多個工作，每個一個 agent，例如十個人提的十個要求，或你自己手上十個不同的問題。每一個都是獨立的一件工作，有自己的資料夾、自己的 agent、自己的終點線。它們之間不共用任何東西，所以也不需要合併。這一章接下來走的就是這一種。它不花俏，但一個人能讓十件事同時往前走，靠的就是它。

這樣分工作，缺的就不再是 agent，而是你。agent 可以等人等上好幾個小時，不用任何運算，可是它等的時候帶著的東西會過期：對話的快取會失效，等你回答時，倉庫可能也已經變了。等待在你這邊也有代價：心裡同時掛著十個 agent，人很快就會弄丟線索。所以設計上要回答的問題就成了：一個人的注意力，要怎麼分配給十個任務？

一个 agent 好用，为什么不开十个？

你不在的时候，agent 也能干很多活。于是很自然会冒出下一个念头：既然一个 agent 好用，为什么不同时开很多个？这个念头可以有两种理解，只有一种行得通。

第一种理解，是一件大活配很多 agent。你交出一个大任务，由一个协调者把它分给一队 agent，每个 agent 有自己的角色，比如计划、实现、检查。整个看起来就像公司的组织架构图。慎用子 agent测的正是这种做法，结果是交接会丢掉理解，每个 agent 又要把同样的文件重读一遍。那一章并不反对一个任务的每一步都换一个新的帮手，它反对的是好几个 agent 同时改同样的文件，因为那样就得有人来合并它们的成果。

第二种理解，是很多件活，每件一个 agent，比如十个人提的十个需求，或者你自己手头十个不同的问题。每一件都是独立的一份工作，有自己的文件夹、自己的 agent、自己的终点。它们之间什么都不共享，所以什么都不用合并。这一章接下来讲的就是这一种。它不花哨，但一个人能同时推进十件事，靠的就是它。

这样分活，稀缺的就不再是 agent，而是你。agent 可以等人等上好几个小时，不消耗任何算力，可是它等的时候带着的东西会过期：对话的缓存会失效，等你回复时，仓库可能也已经变了。等待在你这边也有代价：心里同时挂着十个 agent，人很快就会丢了线索。所以设计上要回答的问题就成了：一个人的注意力，怎么分给十个任务？

Split by task, and call the person only at the gates

Parallel across tasks, not inside one

The first half of the answer is in how the work is split. Each task is a folder, as in Manage tasks, not chats, so the requirement, the plan, the to-do list and the handover file all live in files. Since one agent session holds one task at a time, ten tasks are ten folders and ten sessions.

Why does this split cleanly when splitting one big job does not? The first reason is that nothing is shared. Each task has its own folder and only one writer, so two agents never edit the same file at the same moment, and there is nothing to merge inside a task. The second is that each task is whole. The agent that does the work holds the plan and the context as well, so nothing has to pass from an agent that understood to an agent that must act. That handover was the cost of the three-role setup described above. When a task does change hands, the hand-off is a file rather than a message: if it stops for a day, whoever picks it up reads the folder.

The agents do not talk to each other. The only thing that crosses between tasks is you.

When does a task need you?

You are what crosses between tasks, so the other half of the answer is when a task needs you. Were the answer "often and unpredictably", ten tasks would eat your day. So the design pushes every need for a person into a few fixed points, the gates, where the agent stops and waits for a person's yes (the details are in Two gates: where a person approves).

A task waits for you only for reasons like these:

  • the first gate: the requirement is written and the plan is ready, and both wait for you to confirm and approve;
  • the second gate: the write-back (copying the finished changes into the repository) waits for your approval;
  • a write failed halfway;
  • it needs the results of a run that only you can do;
  • its independent checks are used up and you decide what next;
  • the agent stopped, or an unattended run ended.

Between those points the agent works and you are not needed. That is the whole idea: call the person only at the gates. The worst case is a task that needs you "now and then, when it has a question", because you cannot plan around it. A task that asks only at named points, by contrast, can be scheduled.

This also tells you what to build. Anything that makes the agent stop for a reason that is not a gate, such as a vague request, a missing permission or a confirmation box for a harmless action, is a leak in your attention and worth removing (Ask or refuse).

Tasks that touch the same code

The agents never talk, but their work can still collide, and that is the common case. Separate task folders do not make separate repositories, so two tasks that change the same files will meet when they are written back. Start by giving each task its own branch or working copy (git worktree is one way). Then, when a task is written back, check whether the files it touches changed since it began. If they did, stop and ask a person. Either way, write back one task at a time.

Attention is the expensive part

Even when the write-backs are in order, running ten tasks does not make you ten times faster. What it does is move your time to the gates, and a gate is only worth something if you read it.

That raises the question of what makes reading cheap. A plan you approve should fit on a page and sit in an editor, not scroll through a terminal. A requirement you confirm should be one page too (The agent writes the requirement, the person confirms it). If reading takes twenty minutes, you will skim, and a skimmed approval is the "click Allow" problem again. One number worth watching is how often you reject or change a plan. If it is never, you may be skimming.

How fast you can read plans and diffs, not how many sessions fit on the screen, is also what sets how many tasks you should hold. Start with two or three. How many you can hold well depends on the tasks.

The same reasoning says to group similar gates. If three plans are waiting, read them in one sitting, because switching between a plan, a diff and a requirement costs more than reading three plans.

Attention is not the only thing ten tasks multiply. Ten tasks are also ten times the usage, so put a stop rule on each one (Unattended: when it must stop). A task that waits for you for longer than the prompt cache lives (five minutes or an hour on Anthropic's API, see Models and cost) pays full price to read its context again when you return. I have not checked how Copilot behaves here.

One list of what waits for you

With ten sessions open, how do you know which one is waiting? Going through the windows one by one is exactly the cost you want to avoid.

The answer is a board: one page that lists every open task, what it is waiting for and for how long. Two design points make it worth looking at.

One is that the state is written by code, not by the agent. A hook runs when the agent stops and notes "waiting for you". The board reads that state from a file made for machines. It does not read the progress notes the agent wrote in prose, because an agent forgets to tick things or ticks too many. The other is that waiting is a number, the time since a task started waiting, so the board can also tell you which one to open first.

The same page has a switch that I use at the end of the day. It pauses every open task the agent is not working on and takes them back in the morning. Because the waiting time while paused is not counted, the numbers stay honest.

If you have no board, a list will do. The idea works just as well by hand: one terminal tab per task, titled with the task, and a short list you keep of which tab is waiting and since when.

Read-only helpers inside a task

The one-agent-per-task rule is about work that writes. Inside one task, helpers that only read can still run in parallel and hand in short summaries, because no helper changes a file (Use subagents sparingly). The shape, then, is one writer per task, and as many readers as the reading is worth.

按任務拆，只在門口叫人

並行在任務之間，不在一個任務裡面

答案的前一半，在於工作怎麼拆。就像 管任務，不管對話 講的，每個任務是一個資料夾，需求、計畫、待辦清單和交接檔全都放在檔案裡。一個 agent 會話一次只拿一個任務，所以十個任務就是十個資料夾、十個會話。

為什麼這樣拆得乾淨，一個大工作的拆法卻拆不乾淨？頭一個原因，是沒有共用的東西。因為每個任務有自己的資料夾，又只有一個寫入者，兩個 agent 絕不會在同一刻編輯同一個檔案，任務裡面也沒什麼要合併的。再一個原因，在於每個任務都完整。做事的 agent 同時拿著計畫和上下文，所以用不著從「理解了的 agent」交給「必須動手的 agent」。上面說的那種三個角色的分工，成本就花在這一步交接上。真的要換人接手，交接也是一個檔案，不是一則訊息：任務停了一天，接手的人讀一遍資料夾就行。

agent 之間不互相說話。唯一在任務之間來往的，是你。

任務什麼時候需要你？

在任務之間來往的只有你，所以答案的另一半，是任務什麼時候需要你。如果它們「常常來找你，而且說不準什麼時候」，十個任務會吃掉你一整天。所以設計上把每個需要人的時刻，都推到少數幾個固定的點上，也就是門：agent 在這裡停下來，等人點頭（細節在 兩道門：人在哪裡批准）。

任務只因為這類理由等你：

  • 第一道門：需求寫好了，計畫也準備好了，兩者都在等你確認和批准；
  • 第二道門：寫回（把做完的改動複製進倉庫）在等你的批准；
  • 寫入做到一半失敗了；
  • 它需要一次只有你能做的運行的結果；
  • 它的獨立檢查用完了，由你決定下一步；
  • agent 停了，或一次無人值守的執行結束了。

這些點之間的時間，agent 自己工作，用不著你。整個想法就是這一句：只在門口叫人。最糟的是那種「偶爾，有問題的時候」就需要你的任務，因為你沒辦法圍繞它安排時間。相較之下，只在固定的點上提問的任務，就排得進行程。

這也告訴你要建什麼。任何讓 agent 因為門以外的理由停下來的東西，像是模糊的要求、缺少的權限、為無害動作跳出來的確認框，都是你注意力上的漏洞，都值得移除（詢問不是限制）。

碰同一份程式碼的任務

這些 agent 之間從不說話，但它們的工作還是可能撞車，而且這種情況很常見：任務資料夾分開了，不等於倉庫也分開了，所以兩個改同樣檔案的任務，在寫回的時候會撞上。辦法是先讓每個任務有自己的分支或工作副本（git worktree 是一種辦法）。等到寫回時，再檢查它改過的檔案從任務開始後有沒有變。變了，就停下來問人。不管變沒變，都一次只寫回一個任務。

注意力才是貴的

就算寫回都理順了，跑十個任務也不會讓你快十倍。它做的，是把你的時間移到門上，而門只有在你讀了它的時候才有價值。

那麼，怎樣才能讓門好讀？你批准的計畫，應該放得進一頁，在編輯器裡看，而不是在終端機裡捲動；你確認的需求，也應該是一頁（需求由 agent 寫，人確認）。如果讀一次要二十分鐘，你就會略讀，而略讀之後的批准，又回到了「點允許」的老問題。有個數字值得看：你多常拒絕或修改計畫。如果從來沒有，你可能就是在略讀。

讀計畫和 diff 的速度，而不是螢幕上放得下幾個會話，也決定了你手上該拿幾個任務。從兩三個開始。能好好拿住幾個，要看任務本身。

照同樣的道理，類似的門最好放在一起處理。如果有三份計畫在等，就一次坐下來全讀完，因為在計畫、diff 和需求之間切換，比讀三份計畫更花力氣。

十個任務放大的不只是注意力，用量也成了十倍，所以每個任務都要有一條停止規則（無人值守：什麼時候必須停）。一個任務等你的時間如果超過了 prompt 快取的存活時間（在 Anthropic 的 API 上是五分鐘或一小時，見 選模型：算的是每次成功的成本），你回來時，它就得付全額價格把上下文再讀一次。Copilot 在這方面怎麼表現，我沒查過。

一份等你的清單

開著十個會話，你怎麼知道哪一個在等？一個一個視窗去翻，正是你想省掉的那筆成本。

答案是看板：一頁，列出每一個還開著的任務、它在等什麼、等了多久。有兩個設計重點讓它值得一看。

其一，狀態由程式寫，不是由 agent 寫。agent 停下來時，會有一個 hook 執行，記下「在等你」，看板讀的就是這個給機器讀的檔案裡的狀態。agent 用文字寫的進度筆記，看板是不讀的，因為 agent 會忘了打勾，或打太多勾。其二，等待是一個數字，也就是一個任務開始等待之後經過了多久，所以看板還能告訴你該先打開哪一個。

這一頁上還有一個開關，我在一天結束時會用。它把 agent 沒在做的那些開著的任務全部暫停，隔天早上再接回來。暫停期間的等待時間不計，所以數字一直是準的。

沒有看板，用一份清單也行。這個想法手動做也一樣行得通：每個任務一個終端機分頁，用任務命名，再自己記一張短清單，寫明哪個分頁在等、從什麼時候開始等。

任務裡的唯讀幫手

一個任務一個 agent 的規則，講的是會寫入的工作。在一個任務裡，唯讀的幫手仍然可以並行，各自交回簡短的摘要，因為沒有哪個幫手會改檔案（慎用子 agent）。說到底就是：每個任務只有一個寫入者，讀的人可以要多少有多少，前提是這些讀的工作值得做。

按任务拆，只在关卡处叫人

并行在任务之间，不在任务内部

答案的前一半，在于活怎么拆。和管任务，不管对话里一样，每个任务是一个文件夹，需求、计划、待办清单和交接文件都放在文件里。一个 agent 会话一次只管一个任务，所以十个任务就是十个文件夹、十个会话。

为什么这样拆很干净，“一件大活”的拆法却不行？头一个原因是什么都不共享。因为每个任务有自己的文件夹，又只有一个写入者，两个 agent 不会在同一时刻改同一个文件，任务内部也没什么可合并的。再一个原因是任务是完整的。干活的 agent 同时拿着计划和上下文，所以用不着从“理解了的 agent”交给“要动手的 agent”。上面说的那种三个角色的分工，成本就花在这一步交接上。真要换人接手，交接也靠文件，不靠消息：任务停了一天，接手的人读一遍文件夹就行。

这些 agent 之间不交谈。在任务之间穿梭的，只有你。

任务什么时候需要你？

在任务之间穿梭的只有你，所以答案的另一半，是任务什么时候需要你。要是它们“经常来找你，而且说不准什么时候”，十个任务会吃掉你一整天。所以设计上把所有需要人的时刻，都推到几个固定的点上，也就是关卡：agent 在这里停下来，等人点头（细节见两道门：人在哪里审批）。

任务只会因为下面这些原因等你：

  • 第一道关卡：需求写好了，计划也备好了，两者都在等你确认和批准；
  • 第二道关卡：写回（把做完的改动复制进仓库）在等你批准；
  • 一次写入中途失败；
  • 它需要一次只有你能做的运行的结果；
  • 它的独立检查次数用完了，由你决定下一步；
  • agent 停了，或者一次无人值守的运行结束了。

这些点之间的时间，agent 自己干活，用不着你。整个思路就是这一句：只在关卡处叫人。最糟的是那种“时不时有问题就来问你”的任务，因为你没法围绕它做安排。相比之下，只在明确的点上提问的任务，就能排进日程。

这也告诉了你该建设什么。凡是让 agent 因为关卡以外的原因停下来的东西，比如含糊的需求、缺少的权限、对无害操作弹出的确认框，都是你注意力上的漏洞，都值得去掉（询问不是限制）。

改同一份代码的任务

这些 agent 之间从不交谈，但它们的活还是可能撞车，而且这种情况很常见：任务文件夹分开了，仓库并没有分开，所以两个改同样文件的任务，会在写回的时候撞上。办法是先给每个任务一个自己的分支或工作副本（git worktree 是一种办法）。等到写回时，再检查它碰过的文件在任务开始之后有没有变。变了，就停下来问人。不管变没变，都一次只写回一个任务。

注意力才是贵的

就算写回都理顺了，跑十个任务也不会让你快十倍。它做的，是把你的时间挪到关卡上，而关卡只有在你真的看了的时候才有价值。

那么，怎样才能让关卡好读？你要批准的计划应该一页放得下，在编辑器里看，而不是在终端里翻滚动条；你要确认的需求也应该是一页（需求由 agent 写，人确认）。要是读一遍得花二十分钟，你就会扫一眼了事，而扫一眼就批准，又回到了“点允许”的老问题。有个数字值得盯着：你驳回或修改计划的频率。要是从来没有过，你可能就是在扫一眼。

读计划和 diff 有多快，而不是屏幕上放得下几个会话，也决定了你手里该拿几个任务。先从两三个开始。能稳稳拿住几个，要看任务本身。

按同样的道理，相似的关卡最好放在一起处理。有三份计划在等，就一口气读完，因为在计划、diff 和需求之间来回切换，比连读三份计划更费力。

十个任务放大的不只是注意力，用量也成了十倍，所以每个任务都要配一条停止规则（无人值守：什么时候必须停）。一个任务等你的时间如果超过了 prompt 缓存的存活时间（Anthropic 的 API 上是五分钟或一小时，见选模型：看每次成功的成本），你回来时它就得按全价把上下文重读一遍。Copilot 在这方面怎么处理，我没有查过。

一份等你的清单

开着十个会话，你怎么知道哪一个在等你？一个窗口一个窗口地翻，恰恰就是你想省掉的那笔成本。

答案是看板：一个页面，列出每个还没结束的任务、它在等什么、等了多久。有两个设计点让它值得一看。

其一，状态由代码写，不由 agent 写。agent 停下来时，会有一个 hook 运行，记下“等你”，看板读的就是这份给机器看的状态文件。agent 用文字写的进度笔记，看板是不读的，因为 agent 会忘了打勾，或者勾多了。其二，等待是一个数字，也就是一个任务从开始等待到现在过了多久，所以看板还能告诉你该先打开哪一个。

这个页面上还有个开关，我在一天结束时会用。它把 agent 没在干活的未结束任务全部暂停，第二天早上再接回来。暂停期间的等待时间不计，所以数字一直是真实的。

没有看板，用一份清单也行。这个思路手工做也一样行得通：每个任务开一个终端标签页，标题写上任务名，再自己记一份短清单，写明哪个标签页在等、从什么时候开始等。

任务内部只读的帮手

“一个任务一个 agent”这条规矩，管的是会写入的活。在一个任务内部，只读的帮手仍然可以并行，各自交回简短的摘要，因为没有哪个帮手会改文件（慎用子 agent）。说到底就是：每个任务一个写入者，读的人可以要多少有多少，前提是这些读的活值得做。

What still lands on you, and what I have not measured

Context switching costs the agents nothing. It lands on you. Each gate needs different knowledge, so ten tasks in ten different domains cost more attention than ten in the same domain.

Skimming has an extreme form, too: a gate that is always yes is a gate you do not read. Approve ten plans in a row without opening one, and the gates are decoration. The remedy is fewer, smaller gates, not more.

The board, for its part, is only as good as its state. If the state came from the agent's own words, the board would lie. That is why, as described above, it comes from hooks and files.

Beyond these costs, I have not compared this with other ways of working. I have no evidence of a net speed-up, because I have not measured ten parallel tasks against ten in a row, or against a team. Nor have I measured how many tasks one person can hold well, or tested ten tasks changing one repository at once to see how often they collide. The argument rests on the structure: nothing is shared, and a person's attention is the limit. The number ten in the title is an illustration, not a result.

落在你身上的代價，和我沒量過的事

這套辦法也有代價。切換上下文對 agent 來說不花什麼，成本落在你身上。每道門需要的知識不一樣，所以十個任務分在十個不同的領域，比十個都在同一個領域更花注意力。

略讀也有一種極端的樣子：永遠會過的門，就是你不會去讀的門。連續批准十份計畫，一份都沒打開過，那些門就成了裝飾。解法是更少、更小的門，而不是更多。

至於看板，它好不好，全看它的狀態。如果狀態來自 agent 自己的話，看板就會說謊。這正是前面說狀態要來自 hook 和檔案的原因。

除了這些代價，我也沒有拿它和其他辦法比較過。我沒有淨加速的證據，因為十個並行任務和十個一個接一個跑的任務，或和一個團隊，我都沒有量過、比過。一個人能好好拿住幾個任務，我沒有量過；十個任務同時改一個倉庫、多常會撞在一起，我也沒有測過。論點在結構上：沒有共用的東西，而人的注意力是極限。標題裡的「十」只是一個例子，不是結果。

落在你身上的代价，和我没测过的事

这套办法也有代价。上下文切换对 agent 来说不花什么，成本落在你身上。每个关卡需要的知识不一样，所以十个任务分布在十个不同的领域，比十个都在同一个领域更费注意力。

扫一眼也有一种极端的样子：一个永远通过的关卡，就是你不会去读的关卡。连着批准十份计划，一份都没打开过，这些关卡就成了摆设。补救的办法是更少、更小的关卡，而不是更多。

至于看板，它的好坏取决于它的状态。如果状态来自 agent 自己说的话，看板就会说谎。这正是前面说状态要来自 hook 和文件的原因。

除了这些代价，我也没有拿它和别的办法比过。我没有整体提速的证据，因为十个并行任务和十个串行任务，或者和一个团队，我都没有对比测过。一个人能稳稳拿住几个任务，我没有测过；十个任务同时改一个仓库、多久会撞一次，我也没有测过。论据在结构上：什么都不共享，而人的注意力是上限。标题里的“十”只是个例子，不是结果。

When to delete the board

The board exists because a session does not tell you that it is waiting. Once the platform shows, in one place, every running agent session and what each is waiting for, the board can go. I have not checked how far Copilot has got with that.

The idea does not go with it. Even when the platform does the listing, the split stays: one writer per task, and the person called at the gates.

什麼時候可以刪掉看板

之所以要有看板，是因為會話不會告訴你它在等。等哪天平台能在一個地方，顯示每個執行中的 agent 會話、以及各自在等什麼，看板就可以拿掉。Copilot 在這件事上做到哪裡，我沒查過。

想法並不會跟著拿掉。就算由平台來列出，這個拆法依然成立：每個任務只有一個寫入者，人只在門口被叫來。

什么时候可以删掉看板

之所以要有看板，是因为会话不会告诉你它在等。等哪天平台能在一个地方显示所有正在运行的 agent 会话、以及它们各自在等什么，看板就可以删了。Copilot 在这方面做到哪一步了，我没有查过。

思路并不会跟着消失。即使列表由平台来做，这个划分依然成立：每个任务一个写入者，只在关卡处叫人。
