5.4

Let the agent check its own work讓 agent 能檢查自己的活让 Agent 自己跑测试

This chapter assumes you have used an AI coding agent. It builds on The agent loop: the agent asks the model, runs a tool, and feeds the result back.

讀這一章，你需要用過 AI 寫程式的 agent。它建立在 agent 循環，和你能插手的地方 上：agent 問模型、執行工具、把結果餵回去。

读这一章，你要用过 AI 编程 agent。它建立在 Agent 到底是怎么干活的？之上：agent 问模型、运行一个工具、把结果送回去。

The Knowledge經驗分享经验分享

In one sentence

Give the agent a way to check its own work, such as running the tests, the linter or the program. A check it can run and read gives it feedback inside the loop, while a reviewer only finds problems afterwards.

一句話

讓 agent 有辦法檢查自己的活，例如跑測試、跑 linter、跑程式。它自己能跑、也能讀的檢查，在循環裡就給它回饋；reviewer 卻只能在事後找問題。

一句话

给 agent 一个检查自己活儿的办法，比如跑测试、跑 linter、跑程序。agent 自己能运行、能读懂的检查，在循环里就给了它反馈；reviewer 却只能等事后才发现问题。

For leaders

  • The decision: require every task to come with a check the agent can run and read itself, such as tests, a build or a linter, and decide which of those checks the agent may not edit.
  • The risk: an agent stops when its work looks done, and in my own use models often lean towards reporting success, though I have not recorded how often. Anthropic describes a later agent that would "declare the job done" after seeing progress. An agent can also pass by weakening the test. I have not recorded such a case, so treat it as a risk to design for.
  • The cost of doing it right: often one line in the instruction file, the command that runs the project's check. Slow suites need a fast subset that can run often. I have not measured how much a self-check improves results.
  • Ask the team: "What can the agent run to know that its work is done, and can it change that check?"

給主管

  • 要做的決定：要求每個任務都附一個 agent 自己能跑、能讀的檢查，例如測試、建置或 linter，並決定其中哪些檢查 agent 不能改。
  • 風險：agent 在活「看起來」做完時就會停下，而就我自己的使用經驗，模型常常傾向於回報成功，只是我沒有記錄過頻率。Anthropic 描述過，後來的 agent 看到已有進展，就會「宣布工作完成」。agent 也可能靠削弱測試來通過。這樣的案例我沒有記錄過，所以要把它當成設計時就得防著的風險。
  • 做對的成本：常常只是指令檔裡的一行，也就是執行專案檢查的那個指令。測試套件很慢的話，需要一個快的子集讓它常常跑。自我檢查能把結果改善多少，我沒有量過。
  • 可以問團隊：「agent 能跑什麼來知道它的活做完了？它能改這個檢查嗎？」

写给管理者

  • 要拍板的事：要求每个任务都带一个 agent 自己能运行、能读懂的检查，比如测试、构建或 linter，并决定其中哪些检查 agent 不许改。
  • 风险：agent 在活儿看起来做完时就会停下，而在我自己的使用中，模型常常倾向于报告成功，只是我没有记录过多久发生一次。Anthropic 描述过，后来的 agent 看到已经有进展，就会“宣布工作完成”。agent 还可能靠削弱测试来通过。这样的案例我没有记录过，所以要把它当作一个在设计里防着的风险。
  • 做对的代价：往往只是指令文件里的一行，也就是运行项目检查的那条命令。测试套件慢的话，需要一个能经常跑的快速子集。自查能把结果提高多少，我没有测过。
  • 可以问团队：“agent 能运行什么来知道它的活儿做完了？它能改这个检查吗？”

Why "looks done" is not done

An agent stops when its work looks done. But looking done is only a feeling the model has about its own code, and nothing has been run to back it up. So the agent says "I have made the change", you read it, and you find the bug.

If the agent has nothing to run that tells it whether the work is done, then you are the test suite. Every mistake waits until you notice it. That is slow, and it needs you in front of the screen.

In my own use I have often seen models lean towards reporting success, although I have not recorded how often. Anthropic describes the same pull in long runs, where a later agent instance would "declare the job done" after seeing that progress had been made (Effective harnesses for long-running agents). You might think the fix is to have the agent read its work over. That does not work either, because an agent that reads its own work shares its own blind spots: the same reasoning that wrote the mistake is now reading it (Use subagents sparingly).

So the way out is not a smarter agent but a check that does not depend on the agent's feeling. What changes once the agent has one?

「看起來做完」為什麼不算做完

agent 在活「看起來」做完時就會停下。可是「看起來做完」只是模型對自己程式碼的一種感覺，背後並沒有跑過任何東西。於是它說「我已經做了這個改動」，你一讀，就找到了 bug。

如果 agent 手上沒有東西可以跑、能告訴它活有沒有做完，那麼你就是那個測試套件。每個錯誤都得等你發現，這不但慢，還需要有人坐在螢幕前。

就我自己的使用經驗，我常看到模型傾向於回報成功，不過我沒有記錄過頻率。Anthropic 在長時間運行裡也描述過同樣的拉力：後來的 agent 實例看到已經有了進展，就會「宣布工作完成」（Effective harnesses for long-running agents）。你也許會想，那讓 agent 回頭把自己的活再讀一遍呢？這也沒用。自己讀自己的活，盲點還是原來那些，因為寫出錯誤的那套推理，現在又在讀這個錯誤（慎用子 agent）。

所以出路不在於換一個更聰明的 agent，而在於一個不靠 agent 的感覺的檢查。有了這樣的檢查，會有什麼不同？

“看起来做完了”为什么不算做完

agent 在活儿看起来做完时就会停下。可“看起来做完了”只是模型对自己代码的一种感觉，背后并没有运行过任何东西。于是它说“我做了这个改动”，你一读，发现了 bug。

如果 agent 手里没有什么可以运行、能告诉它活儿做完没有，那么你就是那个测试套件。每个错误都得等你发现，这既慢，又得有人守在屏幕前。

在我自己的使用中，常常看到模型倾向于报告成功，不过我没有记录过多久发生一次。Anthropic 在长时间运行里也描述过同样的倾向：后来的 agent 实例看到已经有了进展，就会“宣布工作完成”（Effective harnesses for long-running agents）。你也许会想，那让 agent 回头把自己的活儿再读一遍呢？这也不管用。自己读自己的活儿，盲区还是原来那些，因为写出错误的那套思路，现在又在读这个错误（别跟风瞎用子 Agent）。

所以出路不在于换一个更聪明的 agent，而在于一个不依赖 agent 感觉的检查。有了这样的检查，会有什么不同？

A check inside the loop, and where it falls short

One of the most useful things you can add

The clearest way to see it is to compare two runs of the same task. In the first, the agent changes the code and says "done". You run the tests and two fail, so you tell the agent. It fixes one, and you run them again.

In the second, the agent changes the code and runs the tests itself. When two fail, it reads the output and fixes both, then runs the tests again. This time they pass, and only then does it say "done", with the output attached.

The model is the same in both. What differs is that in the second run the result of the check came back inside the loop, before the agent finished. The loop in The agent loop already has a place for this, because a tool result goes back to the model and the model decides the next step. A test run is just a tool whose result says, plainly, pass or fail.

Anthropic's guide for Claude Code says the same thing in its own words. Give the agent something it can run that comes back pass or fail, and it can keep going on its own, so that you do not have to watch (Best practices for Claude Code). Of all the things you can add around an agent, I put this near the top. A reviewer is also valuable, but it can only work afterwards, on finished work, whereas a self-check changes what the agent does while it works.

What can be run

So what can the agent run? Almost anything, as long as its result is something it can read:

  • Tests: the project's own tests, or a new test written for this change.
  • A build or typecheck: the exit code alone says whether it works.
  • A linter or formatter: quick, and it catches a class of mistakes.
  • A script that compares output with a known-good file: good for data work, where the right answer is a table.
  • Running the program: for a pipeline, run it on a small input and look at the output.
  • A screenshot next to a mockup: for user interfaces.

If a repository already has one of these, the most useful single line in the agent's instruction file is the command that runs it, since the agent cannot guess which command the project trusts.

Knowing what to run still leaves the question of how firmly you ask for it. The answer is a scale from soft to hard, the same ladder as in A rule in a prompt is a request:

  1. The softest is a line in the prompt, such as "run the tests after, and keep going until they pass". The agent then decides for itself when it is satisfied.
  2. Firmer is a stop condition. A hook (Hooks) runs at the moment the agent tries to stop, and if the check fails, the hook sends the agent back to work. Because the platform enforces this, the agent cannot end its turn with a failing check. Claude Code's documentation describes this with a Stop hook (Best practices for Claude Code), although I have not tested the same in Copilot for this chapter.
  3. Firmest is to have a program count the passes, so that the number is not something the agent reports (Counted checks).

Make the result short and readable

Whatever the check is, the agent reads its output, and that output goes into its context (Context is a budget). It can go wrong by saying too much or by saying too little. A test run that prints thousands of lines fills the context, and the one failure the agent needs gets lost among them. So print only the failures, each with its file and line, plus a count. The passing noise can stay hidden. At the other extreme, "Error" alone gives the agent nothing to act on. A good failure says what was expected, what happened, and where.

This is the same advice as for tool messages in When an Agent misuses a tool, check its description and errors first: the agent is an unreliable user, and what it reads decides what it does next. A check whose output is cheap and clear is worth more than a thorough check that nobody can read.

The output has one more use, as evidence. "All tests pass" is only a claim, while the command that was run and its output are evidence, so ask for them. When you were not watching, they are the only evidence you have.

What a self-check cannot catch

Even a short, clear check that passes says less than it seems to. It says "this does what the check tests", not "this is what you wanted", and between those two statements two gaps open up.

One gap is in the requirement. If the page the agent works from is not what the person meant (The agent writes the requirement), then perfect code that passes every test is perfect code for the wrong thing. No test the agent writes from a wrong requirement will find that. Only a person reading the requirement can.

The other gap is in the test, which may check too little and pass with the bug still in. A test the agent wrote in the same session was written with the same understanding as the code, so it shares the same blind spot. If the agent misread the rule, its code and its test will agree with each other, and both will be wrong.

There is also a limit that is neither a gap in the requirement nor in the test. Some mistakes only show when the program runs in the real setting, with real data, and the agent cannot run it there. Those need a person's check, or a test environment's.

In all of these, the check simply misses something. The next problem is different: it comes from the check itself.

When the agent weakens the test instead

Giving the agent a check also opens a new way to fail. The agent wants the loop to end with a pass, and the easy way to get one is to change the check, not the code. It can loosen an assertion until it passes, delete or skip the test that fails, change the expected value to whatever the code now gives, or catch an error and swallow it.

None of this needs bad intent. The agent is only doing what the loop rewards: finishing with a pass. I have not recorded a case of this in my own runs, so I describe it as a risk to design for, not as something I measured.

The defences run from cheapest to hardest. The cheapest is to say it in words: "Fix the code, not the tests. If a test seems wrong, say so and stop." That helps, but it is a request (A rule in a prompt is a request).

When a request is not enough, keep the tests out of the agent's reach. If the tests are part of what must not be edited, a hook refuses the change. Guardrails explains why files that check the agent should be outside what the agent can write. That does not fit work where adding new tests is part of the job, so there you protect the existing tests and let the agent add new ones.

The hardest defence is to stop trusting the report and count instead. Look at the diff of the tests (the list of changed lines), where a change to a test that was failing is a flag. Better still, let code, not the agent, count the passes, with a record that the check ran (Counted checks).

How it divides work with an independent check

If a self-check misses so much, is an independent reviewer the better tool? The two are not rivals, because they catch different things.

Self-check Independent reviewer
When While the agent works After it finishes
Catches Things a program can judge: it runs, it passes, it matches a file Things a program cannot judge: does it match the request, is the logic sound
Misses Wrong requirement, weak test Blind spots the reviewer shares with the author
Cost Cheap, runs again and again One more agent, several times the usage (Use subagents sparingly)

So self-checks come first. Put them inside the loop, as many and as cheap as you can make them. Then, where it is worth the cost, add an independent check on the result. A reviewer who sees a green test run can spend its attention on the question tests cannot answer: is this the right thing?

放進循環裡的檢查，和它碰不到的地方

你能加的最有用的東西之一

要看出差別，最直接的辦法，是把同一個任務的兩次運行擺在一起看。第一次，agent 改完程式碼就說「做完了」。你去跑測試，兩個失敗，於是你告訴 agent。它修好一個，你再跑一次。

第二次，agent 改完程式碼，自己去跑測試。看到兩個失敗，它讀了輸出，把兩個都修好，再跑一次測試。這次通過了，它才說「做完了」，並附上輸出。

這兩次用的是同一個模型。差別在於，第二次裡檢查的結果在 agent 結束之前，就在循環裡回來了。agent 循環，和你能插手的地方 裡的那個循環，本來就留著這個位置，因為工具的結果會回到模型，由模型決定下一步。跑一次測試，說穿了就是一個結果直白地說「通過」或「失敗」的工具。

這一點，Anthropic 給 Claude Code 的指南用自己的話說過：給 agent 一個能跑、結果是通過或失敗的東西，它就能自己繼續做下去，你也就不用盯著（Best practices for Claude Code）。在能加給 agent 的各種東西裡，我把自我檢查放在靠前的位置。reviewer 當然也有價值，但它只能在事後看做完的活，而自我檢查改變的是 agent 工作時的行為。

能跑什麼

那 agent 能跑什麼？幾乎什麼都可以，只要它給出的結果 agent 讀得懂：

  • 測試：專案自己的測試，或為這次改動新寫的測試。
  • 建置或型別檢查：光是結束碼，就說明行不行。
  • linter 或格式化工具：很快，能抓到一類錯誤。
  • 把輸出和已知正確的檔案比對的腳本：適合資料工作，因為那裡正確的答案是一張表。
  • 執行程式：對 pipeline，用小的輸入跑一次，看輸出。
  • 截圖和設計稿並排：用於使用者介面。

如果倉庫裡已經有其中一個，那麼 agent 指令檔裡最有用的一行，就是執行它的那個指令。專案信任的是哪個指令，agent 自己猜不出來。

不過，知道了要跑什麼，還剩一個問題：要它跑，要求得多硬？這裡從軟到硬分成幾級，用的還是 提示裡的規則只是請求 裡那道階梯：

  1. 最軟的，是在 prompt 裡寫一句，例如「做完之後跑測試，一直做到通過」。什麼時候算滿意，由 agent 自己決定。
  2. 硬一點的，是把它當成停止條件。agent 想停下來的那一刻，會有一個 hook（Hooks：每次呼叫都會經過的執行點）執行；檢查要是失敗，hook 就把 agent 送回去繼續工作。因為這由平台強制，agent 沒辦法帶著失敗的檢查結束這一輪。Claude Code 的文件用 Stop hook 描述了這個做法（Best practices for Claude Code），不過這一章我沒有在 Copilot 測過同樣的做法。
  3. 最硬的，是讓程式來計算通過的次數，這個數字就不再由 agent 回報（讓「通過」可信）。

讓結果短而好讀

不管檢查是什麼，agent 都要讀它的輸出，而這些輸出會進到它的上下文（上下文是一份預算）。這裡可能出兩種錯，一種是說得太多，一種是說得太少。印出幾千行的測試運行，會把上下文塞滿，agent 需要的那一個失敗就埋在裡面。所以只印出失敗的項目，每一項附上檔案和行號，再加一個數量；通過的那些雜訊，藏起來就好。另一頭，只有一個「Error」，agent 根本無從下手。好的失敗訊息要說清楚預期什麼、實際發生什麼、出在哪裡。

這和 Agent 用不好工具，先看工具的描述和錯誤訊息 裡講工具訊息的建議是同一回事：agent 是個不可靠的使用者，它讀到什麼，就決定它下一步做什麼。輸出便宜又清楚的檢查，比沒人讀得懂的徹底檢查更有價值。

輸出還有一個用處：它是證據。「所有測試都通過」只是一個說法，執行過的指令和它的輸出才是證據，所以要向 agent 索取。你沒在看的時候，它們就是你唯一的證據。

自我檢查抓不到什麼

不過，就算檢查又短又清楚，而且通過了，它說明的事也比看起來少。它說的是「這做到了檢查所測的東西」，而不是「這是你要的」，兩者之間有兩個要緊的缺口。

一個缺口在需求上。如果 agent 工作所依據的那一頁，不是人的本意（需求由 agent 寫，人確認），那麼通過所有測試的完美程式碼，也只是為錯的東西寫的完美程式碼。agent 照著錯誤的需求寫出來的測試，沒有一個找得到這一點，只有人去讀需求才找得到。

另一個缺口在測試本身：它可能檢查得太少，bug 還在也照樣通過。agent 在同一個會話裡寫的測試，和程式碼出自同一份理解，所以有同樣的盲點。要是 agent 把規則讀錯了，它的程式碼和測試會彼此一致，而且都是錯的。

還有一個限制，既不是需求的缺口，也不是測試的缺口：有些錯誤只有在真實的環境、用真實的資料執行程式時才會出現，而 agent 沒辦法在那裡執行。這類錯誤要靠人來檢查，或靠測試環境。

前面這些，是檢查本來就碰不到的地方。下一個問題不一樣，它是檢查本身帶來的。

當 agent 轉而削弱測試

給了 agent 一個檢查，它也就多了一種失敗的方式。agent 想讓循環以通過收尾，而拿到通過最容易的辦法，是改檢查，不改程式碼。它可以把斷言放寬到能通過，可以刪掉或跳過失敗的測試，可以把預期值改成程式碼現在給的值，也可以抓住錯誤再把它吞掉。

這些都不需要什麼惡意，agent 只是在做循環獎勵的事：以通過收尾。我在自己的運行裡沒有記錄過這樣的案例，所以我把它描述成要為之設計的風險，而不是我量過的東西。

那該怎麼防？辦法有好幾道，從最便宜到最硬。最便宜的，是用話說清楚：「修程式碼，不要修測試。如果測試看起來是錯的，說出來然後停下。」這有幫助，但它是請求（提示裡的規則只是請求）。

光靠請求不夠的時候，就讓測試待在 agent 碰不到的地方。如果測試屬於不能編輯的東西，hook 會拒絕這個改動。保護規則本身的檔案 解釋了為什麼檢查 agent 的檔案，應該放在 agent 寫不到的地方。不過，要是新增測試本來就是工作的一部分，這個辦法就不適合；那種情況下，保護現有的測試，讓 agent 新增測試。

最硬的辦法，是不再信報告，改成去數。看測試的 diff（改動的行的清單），一個原本失敗的測試要是在裡面被改過，就是個警訊。更好的是讓程式而不是 agent 來計算通過的次數，並留下檢查有執行的紀錄（讓「通過」可信）。

它和獨立檢查怎麼分工

既然自我檢查漏掉的東西這麼多，獨立的 reviewer 是不是更好用？其實兩者不是對手，因為它們抓的東西不同。

自我檢查 獨立的 reviewer
什麼時候 agent 工作的時候 它做完之後
抓得到 程式能判斷的事：能跑、能通過、和檔案相符 程式不能判斷的事：是否符合要求、邏輯站不站得住
抓不到 錯的需求、弱的測試 reviewer 和作者共有的盲點
成本 便宜，可以一再執行 多一個 agent，用量是好幾倍（慎用子 agent）

所以自我檢查放在前面。把它放進循環裡，盡量多、盡量便宜。然後在值得付出成本的地方，再對結果做一次獨立檢查。reviewer 看到測試已經是綠的，就能把注意力花在測試回答不了的那個問題上：這是對的東西嗎？

放进循环里的检查，和它够不着的地方

你能加的最有用的东西之一

要看出有什么不同，最直观的办法，是把同一个任务的两次运行放在一起看。第一次，agent 改完代码就说“做完了”。你去跑测试，两个失败了，于是你告诉 agent。它修好一个，你再跑一遍。

第二次，agent 改完代码，自己去跑测试。看到两个失败，它读了输出，把两个都修好，再跑一遍测试。这回通过了，它才说“做完了”，并附上输出。

这两次用的是同一个模型。差别在于，第二次里检查的结果在 agent 收工之前，就在循环里回来了。Agent 到底是怎么干活的？里的那个循环本来就留着这个位置，因为工具的结果会送回模型，由模型决定下一步。跑一次测试，说到底就是一个结果直截了当地说“通过”或“失败”的工具。

这一点，Anthropic 的 Claude Code 指南用自己的话说过：给 agent 一个能运行、结果是通过或失败的东西，它就能自己接着干下去，你也就不用盯着（Best practices for Claude Code）。在能加给 agent 的各种东西里，我把自查放在靠前的位置。reviewer 当然也有价值，但它只能在事后看做完的工作，而自查改变的是 agent 干活时做的事。

能运行什么

那 agent 能跑什么？几乎什么都行，只要它给出的结果 agent 读得懂：

  • 测试：项目自己的测试，或者为这次改动新写的测试。
  • 构建或类型检查：光看退出码，就知道行不行。
  • linter 或格式化工具：快，能抓住一类错误。
  • 把输出和已知正确的文件做对比的脚本：适合数据工作，因为那里正确答案就是一张表。
  • 运行程序：对 pipeline，用一小份输入跑一遍，看输出。
  • 截图和设计稿并排放：用于用户界面。

如果仓库里已经有其中一样，那么 agent 的指令文件里最有用的一行，就是运行它的那条命令。项目信任的是哪条命令，agent 自己猜不出来。

不过，知道了跑什么，还剩一个问题：要它跑，要求得有多硬？这里从软到硬分几级，用的还是为什么 Agent 不听 prompt 里的规则？里那架梯子：

  1. 最软的，是在 prompt 里写一句，比如“之后运行测试，直到通过为止”。什么时候算满意，由 agent 自己决定。
  2. 硬一点的，是把它当作停止条件。agent 想停下的那一刻，会有一个 hook（硬性规则放在哪？用 hook）运行；检查要是失败，hook 就把 agent 送回去接着干。因为这是平台强制执行的，agent 没法带着一个失败的检查结束这一轮。Claude Code 的文档用 Stop hook 描述了这个做法（Best practices for Claude Code），不过写这一章时，我没有在 Copilot 里测过同样的做法。
  3. 最硬的，是让程序来数通过的次数，这个数就不再由 agent 报告（Agent 说“测过了”，能信吗？）。

让结果简短、可读

不管检查是什么，agent 都要读它的输出，而这些输出会进入它的上下文（为什么不能把所有规则都塞给 Agent？）。这里可能出两种问题，一种是说得太多，一种是说得太少。一次测试运行打印几千行，会把上下文塞满，agent 需要的那一个失败就淹没在里面。所以只打印失败的项，每一项带上文件和行号，再加一个计数；通过的那些噪音，藏起来就好。另一头，光一个“Error”，agent 根本无从下手。好的失败信息要说清楚期望什么、实际发生了什么、出在哪里。

这和Agent 用不好工具，先看工具的描述和报错里关于工具消息的建议是一回事：agent 是个不可靠的用户，它读到什么，就决定了它下一步做什么。一个输出便宜又清楚的检查，比一个全面却没人读得懂的检查更有价值。

输出还有一个用处：它是证据。“所有测试都通过了”只是一个说法，运行过的那条命令和它的输出才是证据，所以要向 agent 索取。你没在旁边看着的时候，它们就是你手里唯一的证据。

自查抓不住什么

不过，就算检查又短又清楚，而且通过了，它说明的东西也比看上去少。它说的是“这个做到了检查所测的东西”，而不是“这就是你想要的”，两者之间有两个要紧的缺口。

一个缺口在需求上。如果 agent 依据的那一页不是人的本意（需求说不清？让 Agent 先写一页给你确认），那么通过每一个测试的完美代码，也只是为错的东西写的完美代码。agent 照着错的需求写出来的测试，哪一个都发现不了这一点，只有人去读需求才能发现。

另一个缺口在测试本身：它可能检查得太少，带着 bug 也能通过。agent 在同一个会话里写的测试，和代码出自同一份理解，所以有同样的盲区。要是 agent 把规则理解错了，它的代码和它的测试会彼此一致，而且都是错的。

还有一个限制，既不是需求的缺口，也不是测试的缺口：有些错误只有在真实环境里、用真实数据运行程序时才会显现，而 agent 在那里运行不了。这类错误要靠人来检查，或者靠测试环境。

前面这些，是检查本来就够不着的地方。下一个问题不一样，它是检查本身带来的。

当 agent 转而削弱测试

给了 agent 一个检查，它也就多了一种失败的方式。agent 想让循环以通过收尾，而拿到通过最容易的办法，是改检查，不是改代码。它可以把断言放松到能通过为止，可以删掉或跳过失败的测试，可以把期望值改成代码现在给出的值，也可以捕获一个错误再把它吞掉。

这些都不需要什么恶意，agent 只是在做循环奖励的事：以通过收尾。我自己的运行里没有记录过这样的案例，所以我把它写成一个要在设计里防着的风险，而不是我测量过的东西。

那该怎么防？办法有好几种，从最便宜到最硬。最便宜的，是用话说清楚：“修代码，不要修测试。如果测试看起来不对，说出来，然后停下。”这有帮助，但它是一个请求（为什么 Agent 不听 prompt 里的规则？）。

光靠请求不够的时候，就让测试待在 agent 够不着的地方。如果测试属于不许编辑的东西，hook 会拒绝这个改动。别让 Agent 改自己的规则讲了为什么检查 agent 的文件应该放在 agent 能写的范围之外。不过，要是新增测试本身就是工作的一部分，这个办法就不合适；那种情况下，保护已有的测试，让 agent 新增测试。

最硬的办法，是不再信报告，改成去数。看测试的 diff（改动行的清单），一个本来失败的测试要是在里面被改过，就是个信号。更好的是让代码而不是 agent 来数通过的次数，同时留下检查运行过的记录（Agent 说“测过了”，能信吗？）。

它和独立检查怎么分工

既然自查漏掉的东西这么多，独立的 reviewer 是不是更好用？其实两者不是对手，因为它们抓的东西不同。

自查 独立 reviewer
什么时候 agent 干活的时候 它做完之后
抓什么 程序能判断的东西：能运行、能通过、和某个文件一致 程序没法判断的东西：符不符合需求、逻辑站不站得住
漏什么 错的需求、弱的测试 reviewer 和作者共有的盲区
成本 便宜，可以反复运行 多一个 agent，用量是好几倍（别跟风瞎用子 Agent）

所以自查放在前面。把它放进循环里，能多就多，能便宜就便宜。然后在值得花这笔成本的地方，再对结果做一次独立检查。reviewer 看到测试已经全绿，就可以把注意力花在测试回答不了的那个问题上：这是对的东西吗？

What a self-check costs, and how it can mislead

A self-check is cheap, but it is not free, and used badly it can mislead you. The worst case is a check that can pass wrongly. It is worse than having none, because it gives false comfort. A test that never fails is the extreme case: it passes, and it tells you nothing.

Other costs come from how a check behaves inside the loop. Speed is one. If the full suite takes twenty minutes, the agent runs it rarely, and the loop slows down. So give it a fast subset to run often, and the full suite at the end. A flaky check does a different kind of harm, because it teaches the agent the wrong thing. A test that fails at random sends the agent hunting for a bug that is not there, or teaches it to rerun until green.

Two more limits came up earlier. One is output that fills the context, covered under short, readable results. The other is code the agent cannot run at all. Where the real data, the real environment or the permission is not available to it, a self-check can only cover part of the work, so say which part and leave the rest to a person.

A cheap test of your own checks

How much does a self-check actually improve results? I have not measured that in my own setup. The direction is clear from the vendor's guidance and from the loop itself, but I do not know the size of the effect. What you can measure cheaply is how much your own checks cover.

Put a bug into working code on purpose, then run the checks the agent would run. If they stay green, the check does not cover that part of the code, whatever the agent reports. It is a cheap way to see how much a passing check is worth.

自我檢查的代價，和它會怎樣誤導你

自我檢查很便宜，但不是白送的，用錯了還會誤導你。最糟的情況，是一個可能錯誤通過的檢查。它比沒有檢查更糟，因為它給人虛假的安心。永遠不會失敗的測試是最極端的例子：它每次都通過，卻什麼都沒告訴你。

其他的代價，來自檢查在循環裡的表現。速度是其中之一。檢查太慢，agent 就不愛跑：完整的測試套件要是得跑二十分鐘，它就很少去跑，循環也跟著慢下來。所以給它一個快的子集常常跑，完整的測試套件留到最後。不穩定的檢查造成的是另一種傷害：它會把 agent 教錯。隨機失敗的測試，會讓 agent 去找一個根本不存在的 bug，或教它一直重跑，跑到變綠為止。

另外兩個限制，前面已經碰過。一個是輸出會把上下文塞滿，講結果要短而好讀時說過；另一個是，有些程式碼 agent 根本沒辦法執行。真實的資料、真實的環境或權限它拿不到的地方，自我檢查只能涵蓋一部分，所以要說清楚是哪一部分，其餘留給人。

一個便宜的辦法，測測你自己的檢查

自我檢查到底能把結果改善多少？我在自己的設定裡沒有量過。從廠商的指南和循環本身來看，方向很清楚，但效果有多大，我不知道。能便宜地量出來的，是你自己的檢查涵蓋了多少。

故意在能運作的程式碼裡放進一個 bug，然後執行 agent 會執行的檢查。如果它們還是綠的，那麼不管 agent 怎麼回報，這個檢查都沒涵蓋程式碼的那一部分。用這個便宜的辦法，就能看出一個通過的檢查值多少。

自查的代价，和它会怎样误导你

自查便宜，但它不是白送的，用错了还会误导你。最糟的情况，是一个可能错误地通过的检查。它比没有检查还糟，因为它给人虚假的安慰。一个永远不会失败的测试是最极端的例子：它每次都通过，却什么也没告诉你。

别的代价，来自检查在循环里的表现。速度是其中之一。检查太慢，agent 就不爱跑：整个套件要是得跑二十分钟，它就很少去跑，循环也跟着慢下来。所以给它一个能经常跑的快速子集，最后再跑整个套件。不稳定的检查造成的是另一种伤害：它会把 agent 教坏。一个随机失败的测试，会让 agent 去找一个根本不存在的 bug，或者教会它一直重跑，跑到变绿为止。

另外两个限制，前面已经碰到过。一个是输出会把上下文塞满，讲结果要简短、可读时说过；另一个是，有些代码 agent 根本运行不了。真实数据、真实环境或者权限它拿不到的地方，自查只能覆盖一部分，所以要说清楚是哪一部分，其余的留给人。

一个便宜的办法，测测你自己的检查

自查到底能把结果提高多少？我在自己的配置里没有测过。从厂商的指南和循环本身来看，方向是清楚的，但效果有多大，我不知道。能便宜地量出来的，是你自己的检查覆盖了多少。

故意往能正常运行的代码里放一个 bug，然后运行 agent 会运行的那些检查。如果它们还是绿的，那么不管 agent 怎么报告，这个检查都没有覆盖代码的这一部分。用这个便宜的办法，就能看出一次通过的检查值多少。

What Anthropic's guide says Industry practice

Anthropic's Claude Code guide puts "give it a check to run" next to telling the agent what it cannot see. Its examples are a test file, a build exit code, a linter, a script that compares output with a fixture, and a browser screenshot. It also says to ask for the evidence, not only for "all tests pass", and mentions a command that builds and runs the app to catch what tests and typechecks miss (Best practices for Claude Code).

Anthropic 的指南怎麼說 業界做法

Anthropic 的 Claude Code 指南，把「給它一個能跑的檢查」和告訴 agent 它看不到的東西放在一起，舉的例子有測試檔、建置的結束碼、linter、把輸出和預先備好的範例檔案（fixture）比對的腳本，還有瀏覽器截圖。它也說要索取證據，不是只有一句「所有測試都通過」，並提到一個會建置並執行應用程式的指令，用來抓測試和型別檢查漏掉的東西（Best practices for Claude Code）。

Anthropic 的指南怎么说 业界做法

Anthropic 的 Claude Code 指南，把“给它一个可以运行的检查”和告诉 agent 它看不到的东西放在一起，举的例子有测试文件、构建的退出码、linter、把输出和预先备好的样例文件（fixture）对比的脚本，还有浏览器截图。它还说，要索取证据，而不只是一句“所有测试都通过了”，并提到一条构建并运行应用的命令，用来抓住测试和类型检查漏掉的东西（Best practices for Claude Code）。

When to delete the reminders and the hook

Does all of this have to stay? The checks themselves do, for as long as there is code to check. What can retire is the scaffolding I put around the agent's use of them, meaning the repeated reminders to run the tests and the hook that sends it back. Those can go once the platform runs the project's checks as a normal step before the agent can finish, and the agent does not weaken them. I have not seen that yet.

什麼時候可以刪掉那些提醒和 hook

這些東西都得一直留著嗎？檢查本身是要留的，只要還有程式碼要檢查。可以退役的，是我為 agent 使用這些檢查而加的鷹架，也就是一再提醒它執行測試的話，以及把它送回去的那個 hook。等到平台在 agent 結束之前，就把專案的檢查當成一般的步驟來執行，而且 agent 也不會去削弱它們，這些就可以拿掉了。這樣的情況我還沒看到。

什么时候可以删掉那些提醒和 hook

这些东西都得一直留着吗？检查本身是要留的，只要还有代码要检查。可以退役的，是我围绕 agent 使用这些检查而搭的脚手架，也就是反复提醒它运行测试的话，以及把它送回去的那个 hook。等到平台在 agent 收工之前，就把项目的检查当作正常的一步来运行，而且 agent 也不会去削弱它们，这些就可以去掉了。这样的平台我还没见过。

You don't need the harness for this. Open your agent in your own repository and paste:

Find out what a coding agent could run in this repository to check its own work: tests, build, typecheck, linter, formatter, example runs. 在你自己的環境試試

找出在這個倉庫裡，寫程式的 agent 能執行什麼來檢查自己的活：測試、建置、型別檢查、linter、格式化工具、範例執行。對每一個，給出確切的指令、如果看得出來的話它要跑多久，以及它的輸出夠不夠短、夠不夠清楚，讓你能據以行動。說明指令檔有沒有告訴 agent 這些指令。然後指出程式碼裡最大的一塊：這些檢查沒有一個能在那裡抓到 bug。不要改任何檔案，也不要執行任何超過一分鐘的東西。
