5.2

The agent writes the requirement, the person confirms it需求由 agent 寫，人確認需求由 agent 写，人确认

This chapter assumes you have used an AI coding agent. It builds on Manage tasks, not chats: a task is one job with one folder of files.

這一章假設你用過 AI 程式 agent。它建立在管任務，不管對話上：任務是一份工作，配一個放檔案的資料夾。

读这一章，你要用过 AI 编程 agent。它建立在管任务，不管对话之上：一个任务就是一件事，加一个放文件的文件夹。

The Knowledge經驗分享经验分享

In one sentence

People's requests are vague and they shift. So have the agent write the requirement on one page, have the person confirm it, and from then on let everyone work from that page.

一句話

人的請求含糊，而且會變，所以要讓 agent 把需求寫成一頁，由人確認，從此大家都照著這一頁做。

一句话

人提的需求含糊，还会变，所以要让 agent 把需求写成一页，由人来确认，从此大家都照着这一页干活。

For leaders

  • The decision: for anything bigger than a small change, require a one-page requirement that the agent writes and the requester confirms before work starts.
  • The risk: requests are vague, leave things out and shift over time. If the agent starts from the first message, every guess it makes is built into the result, and you only find out at the end. I have no numbers on how often this happens.
  • The cost of doing it right: a few minutes of reading from the requester for each task. That is too much for a one-line change, so small tasks can skip it. Too many questions also wear people out, though I have not measured how many is too many.
  • Ask the team: "Where is the page the requester confirmed, and what does its 'not clear yet' list say?"

給主管

  • 要做的決定：比小修改大的事，都要求在開工之前先有一頁需求，由 agent 寫，由提出需求的人確認。
  • 風險：請求含糊、會漏東西，還會隨時間改變。agent 從第一則訊息就開工的話，它的每個猜測都會被做進結果，你要到最後才發現。這有多常發生，我沒有數字。
  • 做對的成本：每個任務都要請提出需求的人花幾分鐘讀。一行的修改，這就太多了，所以小任務可以跳過。問題太多也會讓人累，不過多少才算太多，我沒有量過。
  • 可以問團隊：「提出需求的人確認過的那一頁在哪裡？它的『還不清楚』清單寫了什麼？」

写给管理者

  • 要拍板的事：凡是比小改动大的事，都要求在开工之前先有一页需求，由 agent 来写，提需求的人来确认。
  • 风险：需求含糊，会漏东西，还会随时间变。如果 agent 从第一条消息就开工，它的每一个猜测都会做进结果里，你要到最后才发现。这种事有多常见，我没有数字。
  • 做对的代价：每个任务要占用提需求的人几分钟来读。对一行的改动来说这就太多了，所以小任务可以跳过。问题太多也会让人厌烦，不过多少才算太多，我没有测过。
  • 可以问团队：“提需求的人确认过的那一页在哪里？它的‘还不清楚’清单上写了什么？”

Why the words are not enough

You write "add the customer region to the daily report", and the agent does it, yet the result is not what you meant. You meant the region of the shipping address, while the agent used the billing one. Neither of you was wrong about the words. The words were not enough.

This is the normal case, not the odd one. A request leaves things out, because you know the context and skip it, while the agent does not know it and fills the gap with a guess. Even what you do write can be read in more than one way, since "region" can mean several things. And the request does not hold still, because over a few turns you add a condition, drop another and change your mind. Which version, by then, is the request?

This is where the trap lies: if you let the agent start work from the first message, every guess is built into the result, and you find out only at the end. So before work starts, there has to be one thing everyone can point to.

What should that be? The tempting answer is the person's words, kept exactly as they said them. I tried to design that, and gave it up.

為什麼光靠字面不夠

你寫了一句「在每日報表加上客戶的地區」，agent 也照做了，結果卻不是你的意思。你指的是收貨地址的地區，agent 用的卻是帳單地址的。你們誰也沒有搞錯字面，只是光有字面不夠用。

這不是特例，而是常態。請求會漏東西，因為背景你很清楚，順手就略過了，agent 卻不知道，只好用猜測把空缺填上。就算是寫出來的部分，也可能有不止一種讀法，「地區」就可以指好幾種東西。而且請求不會停在原地，幾輪下來，你加一個條件、拿掉另一個，又改變了主意。到了這時候，哪一版才是請求？

陷阱就在這裡：讓 agent 從第一則訊息就開工，每個猜測都會被做進結果，而你要到最後才發現。所以開工之前，得先有一樣東西讓大家都指著看。

那麼，這樣東西該是什麼？最誘人的答案是人說的原話，原封不動地留著。我試著這樣設計過，後來放棄了。

为什么光靠字面不够

你写了一句“在日报里加上客户所在地区”，agent 也照做了，可结果不是你要的。你指的是收货地址的地区，agent 用的却是账单地址的。你们俩对字面的理解都没错，只是光有字面不够。

这不是个别情况，而是常态。需求会漏东西，因为背景你很熟，随手就略过了，agent 却不知道，只好用猜测把缺口补上。就算是写出来的部分，也可能有不止一种读法，“地区”就可以指好几样东西。而且需求不会停在原地，几轮下来，你加一个条件、去掉一个，又改了主意。到了这时候，哪一版才算需求？

陷阱就在这里：如果让 agent 从第一条消息就开工，每一个猜测都会做进结果里，而你要到最后才发现。所以开工之前，得先有一样东西让大家都指着看。

那么，这样东西该是什么？最诱人的答案是人说的原话，一字不改地留着。我试着这样设计过，后来放弃了。

From what was said to what was meant

Why I do not keep the person's exact words

My first idea was to record every prompt, so that "what the person asked" would always be on disk. It fails for the reasons above: the words leave things out and are unclear. And because the requirement shifts over turns, neither the first prompt nor the last one on its own is the requirement. Keeping them all also fills the context (Context is a budget) with chatter that the agent then has to sort out again.

So the exact words are not the requirement. The requirement is what the person means, written down so that they can check it.

The agent writes it; the person confirms it

Someone has to do that writing, and here it is the agent. From the conversation, it writes the requirement as one page, and the person reads that page and confirms it. This is the requirement file, the one file every later step goes by.

Why this order, and not "the person writes it"? Because people do not like writing specifications, and the page is much easier to check than to write. Reading "you will use the shipping address" and answering "yes" or "no, billing" is cheap, while producing the whole page from nothing is not. In this order each side does what it is good at. The agent turns a mess into a structure, and the person knows what they meant.

It also gives the confirmation a clear meaning. The person is not confirming "I understood you" but "this page is what I want".

What goes on the page

Keep it to what the later steps need:

  • The goal: what should be true when this is done.
  • What to do, and what not to do: the scope and its limits.
  • Done when: the checks that show it is finished, each one something a person or a program can verify.
  • Where each point came from: the file and place in the sources, or the person's answer.
  • Not clear yet: the open questions, kept as an honest list rather than a hidden guess.

Of these, "done when" matters most. The independent check (Use subagents sparingly) goes by this page alone, and so do the self-checks in Let the agent check its own work.

How the agent asks

Where the conversation leaves gaps, the agent has to ask, but an agent that asks too much is as bad as one that guesses. The rules I give it come from my own use, and I have not tested them against other ways of asking.

  1. Stop before work. While things are unclear, it only reads and changes nothing.
  2. Look up what can be looked up. Which test framework the project uses is in the repository, so asking about it wastes the person's time.
  3. Ask only what cannot be looked up: intent, preference, trade-offs, what counts as done.
  4. Give options and a recommendation. "A, B or C; I suggest B because..." is easier to answer than "what do you want?". A recommendation is only advice, though. It does not count until the person confirms.
  5. Do not take a shrug as a yes. "Whatever" is not a confirmation. Ask back once ("I will do X. Is that all right?") and write down that the person agreed to leave it to the agent.
  6. Ask in batches that follow dependencies: upstream questions first, a few at a time.

The method is plain, but its point is the first rule: the agent must not fill in with its own guess what the person did not say. A default that looks obvious is where a guess goes wrong most easily.

When the requirement is a pile of documents

Sometimes the request does not arrive as a message at all, but as a business paper, a spreadsheet of mappings and some emails. This section is only about that case. Giving such files to the agent as they are costs context and invites mistakes, because a Word file carries a cover page, a revision history and comments, while a spreadsheet has hidden sheets and colours that mean something. A binary file is not text at all.

So a program, not a model, turns them into plain text first. Word becomes Markdown and each sheet becomes a table in a text file, while the original is kept untouched. A short report lists what the program left out, such as hidden sheets or pictures. The conversion costs no tokens and should change no number. It can still lose meaning that sits in layout or colour, and we come back to that loss among the costs below. The person then trims the text and adds a short note on what the job is, and only then does the agent read it and write the one page.

Two rules keep the agent honest here. A number that looks wrong is quoted and asked about, never corrected. Two sources that disagree are a finding to report, not something for the agent to settle by itself. This is the same split as in Who decides, with a program for the fixed conversion and a model for the reading.

Reviewing the page before work starts

Whichever way the page was written, it can be checked before any work starts. In my setup the agent compares it with what is known about the system, such as the knowledge base, an index of the code kept for the agent (A knowledge base: an honest index of the code). If you have no knowledge base, skip this step. Each problem it finds goes into the "not clear yet" list with the question, why it matters and the source. The agent then asks the person the few most blocking questions, puts each answer into the page, and repeats until the list is empty and the person confirms.

Two things guard against a bad review. The agent asks only where the documents contradict each other, are wrong, or do not match the system. It never asks the person to confirm what the documents clearly say. And the page has a confirmation line that is left to the person: only they fill it in.

When the request changes

The request will change even after the page is confirmed, and when it does, the page changes first. The agent edits the requirement and adds a line to the change record, and only then touches the work. If the person's latest instruction conflicts with the page, a hook reminds the agent to bring the two in line before doing anything else.

Changing the page first matters because the plan stands on the confirmed requirement. In my setup, approving a plan is refused while the requirement is unconfirmed or has changed since it was confirmed (Two gates). So if the requirement changes after work has begun, the person confirms it again and approves the plan again. The work already done is checked again, not thrown away.

Test it with a request that contradicts itself

To see how your own setup behaves, give the agent a short request with two sentences in conflict, for example one saying the report is daily and another saying it is weekly. Does the page it writes list the conflict under "not clear yet", or does it quietly pick one? If it picks one, the page is sounding sure about a guess.

從說了什麼，到想要什麼

為什麼我不留人的原話

我的第一個想法是記錄每個 prompt，讓「人要求了什麼」永遠在磁碟上。可是正是上面那些理由讓它行不通：原話會漏東西，也說不清楚。需求又會在幾輪之間變來變去，所以第一個 prompt 不是需求，只看最後一個也不是。全部留著，還會用閒聊塞滿上下文（上下文是一份預算），agent 之後還得再整理一遍。

所以原話不是需求，需求是人想表達的意思，而且要寫下來，讓他自己能檢查。

agent 寫，人確認

總得有人把它寫下來，這個人就是 agent。它根據對話把需求寫成一頁，人讀完這一頁，再確認它。這就是需求檔，之後每一步都以這一個檔案為準。

為什麼是這個順序，而不是「人來寫」？因為人不喜歡寫規格，而這一頁檢查起來比寫起來容易得多。讀到「你會用收貨地址」，回一句「對」或「不，用帳單的」，成本很低。可是要從零寫出整整一頁，就是另一回事了。照這個順序，雙方做的都是自己擅長的事：agent 把一團亂理出頭緒，人知道自己到底是什麼意思。

這樣一來，確認也有了清楚的意義。人確認的不是「我懂你了」，而是「這一頁就是我要的」。

這一頁寫什麼

只寫後面幾步用得上的：

  • 目標：做完時什麼應該成立。
  • 要做什麼、不做什麼：範圍和它的邊界。
  • 做完的條件：能證明工作已經做完的檢查，每一項都是人或程式能驗證的。
  • 每一點的來源：來源資料裡的檔案和位置，或人的回答。
  • 還不清楚：未解決的問題，老老實實列成清單，而不是藏成一個猜測。

其中最重要的是「做完的條件」。獨立檢查（慎用子 agent）只看這一頁，讓 agent 能檢查自己的活裡的自我檢查也是。

agent 怎麼問

對話裡留下空白的地方，agent 就得問。可是問太多的 agent，和亂猜的一樣糟。我給它的規則來自我自己的使用，沒有拿它們和別的問法比較過。

  1. 開工之前先停。還不清楚的時候，它只讀，什麼也不改。
  2. 查得到的先查。專案用哪個測試框架，在倉庫裡看得到，問這個是浪費人的時間。
  3. 只問查不到的：意圖、偏好、取捨、什麼算做完。
  4. 給選項，也給建議。「A、B 或 C；我建議 B，因為……」比「你要什麼？」好回答。不過建議只是建議，人確認之前不算數。
  5. 不把聳肩當成同意。「隨便」不是確認。反問一次（「我打算做 X。可以嗎？」），並寫下人同意交給 agent 決定。
  6. 按相依關係分批問：上游的問題先問，一次幾個。

方法很平淡，重點卻在第一條：agent 不可以用自己的猜測，填補人沒說的東西。看起來理所當然的預設，正是猜測最容易出錯的地方。

需求是一堆文件的時候

有時候，請求根本不是一則訊息，而是一份業務文件、一份當對應表用的試算表，再加幾封信，下面說的就是這種情況。這些材料要是原樣交給 agent，既花上下文，也容易出錯，因為 Word 檔帶著封面、修訂歷史和註解，試算表有隱藏的工作表，還有帶意義的顏色。至於二進位檔案，根本就不是文字。

所以先由程式，而不是模型，把它們轉成純文字。Word 變成 Markdown，每張工作表變成文字檔裡的一個表，而原件原封不動地保留。另有一份簡短的報告，列出程式漏掉的東西，例如隱藏的工作表或圖片。這一步不花 token，也不該改動任何數字。但藏在版面或顏色裡的意義還是可能會丟，後面講代價時我們再回到這一點。接著由人修剪這份文字，加一小段說明這份工作是什麼，然後 agent 才讀它，寫出那一頁。

有兩條規則讓 agent 在這裡保持誠實。看起來不對的數字要原樣引用出來，向人提問，絕不修正。兩份互相矛盾的來源是要回報的發現，不該由它自己去裁決。這和誰來判斷：程式、便宜模型、主模型、人是同一種分工，固定的轉換交給程式，閱讀交給模型。

開工之前，先審這一頁

不管這一頁是怎麼寫出來的，在任何工作開始之前都可以先檢查它。在我的設定裡，agent 會拿它和已知的系統資訊對照，例如知識庫，也就是為 agent 保存的一份程式碼索引（見知識庫：程式碼的誠實索引）。如果你沒有知識庫，就跳過這一步。找到的每個問題都寫進「還不清楚」清單，寫明問題是什麼、為什麼重要、來源在哪裡。然後 agent 挑最卡的幾個問題去問人，把每個答案寫回這一頁，一直重複，直到清單清空、人確認為止。

有兩件事防止審查走樣。agent 只在文件互相矛盾、有錯，或和系統對不上的地方問。文件寫得清楚的，它從不請人再確認一遍。而且需求檔裡留著「已確認」這一行，只有人能填。

請求改變的時候

就算這一頁已經確認過，請求還是會變。變的時候，先改這一頁：agent 先編輯需求，在變更紀錄裡加一行，然後才碰工作。如果人最新的指示和這一頁衝突，hook 會提醒 agent 先把兩者對齊，再做別的事。

先改這一頁，是因為計劃就建立在已確認的需求上。在我的設定裡，需求還沒確認，或確認後又改了，批准計劃就會被拒絕（兩道門：人在哪裡批准）。所以開工之後需求才改的話，人要重新確認需求、重新批准計劃，已經做完的工作則要重新檢查，而不是丟掉。

拿一個自相矛盾的請求試試

想看看你自己的設定表現如何，可以給 agent 一個簡短的請求，裡面放兩句互相矛盾的話，例如一句說報表是每天的，另一句說是每週的。它寫出來的那一頁，是把衝突列在「還不清楚」下面，還是悄悄選了一個？選了一個的話，這一頁就是把一個猜測說得斬釘截鐵。

从说了什么，到想要什么

为什么我不保留人的原话

我最初的想法是把每一条 prompt 都记下来，这样“人要求了什么”就始终在磁盘上。可正是上面那些原因让它行不通：原话会漏东西，也说不清楚。需求又会在几轮之间变来变去，所以第一条 prompt 不是需求，单看最后一条也不是。全部留着，还会用一堆闲聊填满上下文（见上下文是一份预算），agent 之后还得重新把它们理一遍。

所以原话不是需求，需求是人想表达的意思，而且要写下来，让他自己能检查。

agent 来写，人来确认

总得有人把它写下来，这个人就是 agent。它根据对话把需求写成一页，人读完这一页，再确认它。这就是需求文件，之后的每一步都以这一个文件为准。

为什么是这个顺序，而不是“人来写”？因为人不喜欢写规格说明，而这一页检查起来比写起来容易得多。读到“你会用收货地址”，回一句“对”或者“不对，用账单地址”，成本很低。可要从零写出整整一页，就是另一回事了。按这个顺序，双方做的都是自己擅长的事：agent 把一团乱麻理出头绪，人知道自己到底是什么意思。

这样一来，确认也有了清楚的含义。人确认的不是“我听懂你了”，而是“这一页就是我要的”。

这一页上放什么

只放后面几步用得上的：

  • 目标：做完之后，什么应该成立。
  • 要做什么，不做什么：范围和它的边界。
  • 做完的标准：能证明活已经干完的检查，每一条都是人或程序可以验证的。
  • 每一点的来源：来源文档里的文件和位置，或者人的回答。
  • 还不清楚：悬而未决的问题，老老实实列成清单，而不是藏成一个猜测。

其中最要紧的是“做完的标准”。独立检查（见慎用子 agent）只以这一页为准，让 agent 能检查自己的活里的自查也是。

agent 怎么提问

对话里留下空白的地方，agent 就得问。可问得太多的 agent，和乱猜的 agent 一样糟。我给它定的规则来自我自己的使用，没有拿它们和别的提问方式比较过。

  1. 开工之前先停。还不清楚的时候，它只读，什么都不改。
  2. 能查到的先查。项目用哪个测试框架，仓库里就有，去问这个是浪费人的时间。
  3. 只问查不到的：意图、偏好、取舍、怎样才算做完。
  4. 给出选项和推荐。“A、B 或 C；我建议 B，因为……”比“你想要什么？”好回答。不过推荐只是建议，人确认之前不算数。
  5. 不把耸肩当成同意。“随便”不是确认。再问一次（“我打算做 X，可以吗？”），并写下人同意交给 agent 决定。
  6. 按依赖关系分批问：上游的问题先问，一次问几个。

方法很朴素，要点却在第一条：agent 不能用自己的猜测，去填人没有说的东西。看起来理所当然的默认值，正是猜测最容易出错的地方。

需求是一堆文档的时候

有时候，需求根本不是一条消息，而是一份业务文件、一张映射表格，再加几封邮件，下面说的就是这种情况。这些材料要是原样交给 agent，既费上下文，又容易出错，因为 Word 文件带着封面、修订历史和批注，表格里有隐藏的工作表，还有带含义的颜色。至于二进制文件，根本就不是文本。

所以先由程序，而不是模型，把它们转成纯文本。Word 变成 Markdown，每张工作表变成文本文件里的一张表，而原件原样保留。另有一份简短的报告，列出程序丢掉了什么，比如隐藏的工作表或图片。这一步不花 token，也不该改变任何数字。但藏在排版或颜色里的含义还是可能会丢，后面讲代价时我们再回到这一点。接下来由人修剪文本，再加一段简短的说明，讲这件事是什么，然后 agent 才读这些内容，写出那一页。

有两条规则让 agent 在这里老实。看起来不对的数字，要原样引出来，向人提问，绝不擅自更正。两个来源互相矛盾，是要报告的发现，不该由它自己去裁决。这和谁来判断：代码、便宜模型、主模型、人是同样的分工，固定的转换交给程序，阅读交给模型。

开工之前，先审这一页

不管这一页是怎么写出来的，开工之前都可以先检查它。在我的配置里，agent 会把它和系统里已知的东西对照，比如知识库，也就是为 agent 维护的一份代码索引（见知识库：代码的诚实索引）。如果你没有知识库，就跳过这一步。发现的每个问题都写进“还不清楚”清单，写明问题是什么、为什么要紧、来源在哪。然后 agent 挑最卡进度的几个问题去问人，把每个答案写回这一页，如此反复，直到清单清空、人确认为止。

有两件事防着审查走样。agent 只在文档互相矛盾、有错，或者和系统对不上的地方提问。文档说得清楚的东西，它从不让人再确认一遍。而且需求文件里留着“已确认”这一行，只有人能填。

需求变了的时候

就算这一页已经确认过，需求还是会变。变的时候，先改那一页：agent 先编辑需求，在变更记录里加一行，然后才去动工作。如果人最新的指示和这一页冲突，hook 会提醒 agent 先把两者对齐，再做别的。

先改这一页，是因为计划就建立在已确认的需求之上。在我的配置里，需求还没确认，或者确认之后又变了，批准计划就会被拒绝（见两道门：人在哪里审批）。所以开工之后需求变了的话，人要重新确认需求、重新批准计划，已经做完的工作则要重新检查，而不是扔掉。

拿一条自相矛盾的需求试试

想看看你自己的配置表现如何，可以给 agent 一段简短的需求，里面放两句互相矛盾的话，比如一句说报告是每天的，另一句说是每周的。它写出来的那一页，是把这个冲突列在“还不清楚”下面，还是悄悄选了一个？如果选了一个，这一页就是把一个猜测写得言之凿凿。

What the page costs, and where it can still go wrong

Is the page worth it? It costs the person a few minutes of reading. For a one-line change that is too much, so a small task can skip the page (the sizes are in Manage tasks, not chats).

You might think that once the person has confirmed the page, it must be right. It need not be: people confirm pages they only skimmed, so a page can be wrong and confirmed at once. A confirmation is not a proof. What the page does is make a misunderstanding visible earlier, nothing more.

The agent can also write a page that sounds sure, as in the test above. A good page has an honest "not clear yet" list, so on a complex request an empty list is a warning sign, not a good sign.

Questions, too, can become a chore if there are too many of them, or if they are about what could have been looked up, until the person starts answering "whatever". I have not measured how many questions is too many.

Finally, if the requirement came as documents, remember that colours, comments and pictures do not survive the conversion. The program's report says what was left out, so read it.

這一頁要付出什麼，又可能在哪裡出錯

這一頁值不值得？它要花人幾分鐘來讀。對一行的修改來說，這就太多了，所以小任務可以跳過這一頁（大小怎麼分，見管任務，不管對話）。

你也許會想，人都確認過了，總該沒問題了吧？其實不然：人會確認只掃過一眼的頁面，所以一頁需求完全可能既是錯的，又被確認了。確認不是證明。這一頁能做的，只是讓誤解更早被看見，僅此而已。

agent 也可能寫出聽起來很有把握的一頁，就像上面那個測試裡那樣。好的一頁有一張誠實的「還不清楚」清單，所以複雜的請求配上一張空清單，是警訊，不是好事。

問題也可能變成苦差事：問得太多，或者問的是本來查得到的事，問到最後，人就開始回答「隨便」了。多少個問題算太多，我沒有量過。

最後，如果需求是一堆文件，要記得，顏色、註解和圖片在轉換中都留不下來。程式的報告會寫明漏掉了什麼，所以要去讀它。

这一页要付出什么，又可能在哪里出错

这一页值不值得？它要花人几分钟来读。对一行的改动来说，这就太多了，所以小任务可以跳过这一页（规模怎么分，见管任务，不管对话）。

你也许会想，人都确认过了，总该没问题了吧？其实不然：人会确认自己只扫了一眼的页面，所以一页需求完全可能既是错的，又被确认了。确认不是证明。这一页能做的，只是让误解更早地显现出来，仅此而已。

agent 也可能写出一页听起来很笃定的东西，就像上面那个测试里那样。好的一页有一份诚实的“还不清楚”清单，所以复杂的需求配上一份空清单，是警示信号，不是好兆头。

提问也可能变成负担：问得太多，或者问的是本来查得到的东西，问到最后，人就开始回答“随便”了。多少个问题算太多，我没有测过。

最后，如果需求是一堆文档，要记住，颜色、批注和图片在转换中都留不下来。程序的报告会写明丢掉了什么，所以要去读它。

What can shrink or go, and what stays

Two parts of this can shrink or go as agents get better. One is the asking method, whose rules you can shorten as models ask better questions on their own. The other is the conversion program, which can go if agents come to read Word and Excel reliably, with the noise left out. I have not tested this.

What stays is the one page and the confirmation, because they are about the person, not the model.

哪些可以縮短或刪掉，哪些留下

隨著 agent 越來越強，這裡有兩部分可以縮短，甚至拿掉。一是提問的方法，模型自己越來越會問出好問題，提問的規則就可以跟著縮短。二是轉換程式：如果 agent 能可靠地讀 Word 和 Excel，把雜訊去掉，這個程式就可以丟，不過這一點我沒有測過。

留下來的是一頁需求和確認，因為它們是為了人，不是為了模型。

哪些可以缩短或删掉，哪些留下

随着 agent 越来越强，这里有两部分可以缩短，甚至去掉。一是提问的方法，模型自己越来越会提好问题，提问的规则就可以跟着缩短。二是转换程序：如果 agent 能可靠地读 Word 和 Excel，并且把噪音去掉，这个程序就可以去掉，不过这一点我没有测过。

留下来的是那一页和确认，因为它们关乎的是人，不是模型。
