7.4

Roll out and govern a harness落地與治理落地与治理

This chapter assumes you have read Guard the files that hold the rules, Instructions and skills and Record what happened, not what the agent said.

讀這一章，你需要讀過 保護規則本身的檔案、指令與 skill：只載入需要的 和 記下發生了什麼，不是 agent 說了什麼。

读这一章之前，需要先读过保护规则本身的文件、指令与 skill：只加载需要的和记下发生了什么，而不是 agent 说了什么。

The Knowledge經驗分享经验分享

In one sentence

Rolling an agent setup out to a team is mostly a question of who owns the rules and who reviews changes to them. Widen the rollout only when the logs show that the rules hold.

一句話

把 agent 設定推給一個團隊，主要是兩個問題：誰擁有規則，誰審查對規則的改動。等日誌顯示規則撐得住了，再擴大範圍。

一句话

把一套 agent 配置推广到团队，主要是两个问题：规则归谁管，谁来审查对规则的改动。等日志显示规则站得住了，再往外放开。

For leaders

  • The decision: name an owner for each layer of rules, require a second reviewer for any change to them, and agree on what has to be true before the setup goes to the next team.
  • The risk: without owners, the rules drift into one copy per person and stale rules stay. Because I have no team data, I cannot put a number on that, so what this chapter gives is the design I would use, not a measured result.
  • The cost of doing it right: mostly people's time, both for the owners of the core and of each area and for a reviewer on every rule change. The setup itself adds little.
  • Ask the team: "Who owns this rule, who reviewed the last change to it, and what would the logs show if it were wrong?"

給主管

  • 要做的決定：為每一層規則指定一個負責人，要求任何改動都有第二位審查者，並先講好設定要符合什麼條件，才能交給下一個團隊。
  • 風險：沒有負責人，規則會漂成每人一份，過期的規則也一直留著。我沒有團隊的數據，給不出數字，所以這一章給的是我會用的設計，不是量過的結果。
  • 做對的成本：主要是人的時間，包括核心和每個領域負責人的時間，以及審查者在每次改規則時花的時間。設定本身加的很少。
  • 可以問團隊：「這條規則誰負責，上一次改它是誰審查的？如果它是錯的，日誌會顯示什麼？」

写给管理者

  • 要拍板的事：给每一层规则指定负责人，对规则的任何改动都要有第二个人审查，并事先约定好配置推给下一个团队之前必须满足什么条件。
  • 风险：没有负责人，规则会漂移成每人一份，过期的规则也一直留着。我没有团队的数据，给不出数字，所以这一章讲的是我会采用的设计，不是量出来的结果。
  • 做对的代价：主要是人的时间，既有核心层和各个领域负责人的时间，也有审查者在每次规则改动上花的时间。配置本身增加的很少。
  • 可以问团队：“这条规则归谁管？上一次改动是谁审查的？如果它是错的，日志会显示什么？”

What goes wrong when a team shares one person's setup?

A setup that suits one person has one owner by accident. That person writes the rules, notices when one is wrong, and knows why each one is there. Hand the same files to ten colleagues, though, and three things go wrong, none of them about the tools.

The first is that copies drift. Everyone fixes the rules for their own task in their own copy, so that after a month there are ten versions and no one can say which of them is "the rules". The second is that no single rule has an owner. A rule that was right last year is wrong now, but everyone has learned to ignore it. Rules go stale like that unless someone is paid in attention to prune them. The third is that a change made for one place breaks another. Tightening a rule for one project blocks another team's normal work, while the person who made the change never sees the damage.

A leader has a fourth worry on top of these: after the rollout, how do you know what the agents did? Answering it needs a record that someone looks at.

I should be honest about where I stand. I built my setup for one person and have not run a team rollout with measurements. What follows is the design I would use, built from what the setup already does (the parts I can point to) and from the questions I ask before adding anything. Where something is only a proposal, I say so.

一個人的設定交給整個團隊，會出什麼問題？

適合一個人的設定，碰巧只有一個負責人，就是那個人自己。規則是他寫的，哪一條錯了他會發現，每一條為什麼在那裡他也清楚。可是把同樣的檔案交給十個同事，就會出三個問題，而且沒有一個和工具有關。

第一個問題是副本會漂移。每個人都為自己的任務，在自己的副本裡修規則，一個月後就有了十個版本，沒有人說得清哪一個才是「規則」。第二個問題是沒有哪一條規則有人負責。去年還對的規則，現在已經錯了，大家卻只是學會了不理它。除非有人肯花心力去修剪，規則就是這樣過期的。第三個是，為一個地方做的改動，會弄壞另一個地方。為一個專案收緊一條規則，會擋住另一個團隊的正常工作，而做改動的人永遠看不到這份傷害。

還有第四個擔心，是主管的：推出去之後，你怎麼知道 agent 做了什麼？要回答這個問題，就需要一份有人在看的紀錄。

我該先老實說明自己的位置。我的設定是為一個人建的，也沒有帶著量測做過團隊推行。下面是我會用的設計，它建在兩樣東西上：設定現在已經做到的事（我能指出來的部分），以及我加任何東西之前都會問的問題。只是提議的地方，我會說明。

一个人的配置交给整个团队，会出什么问题？

适合一个人的配置，碰巧只有一个负责人，就是这个人自己。规则是他写的，哪条错了他会发现，每条为什么在那里他也清楚。可一旦把同样的文件交给十个同事，就会出三个问题，而且都和工具无关。

第一个问题是副本会漂移。每个人都为自己的任务，在自己的副本里改规则，一个月后就有了十个版本，谁也说不清哪一个才是“规则”。第二个问题是没有哪条规则有人负责。去年还对的规则，现在已经错了，可大家只是学会了无视它。除非有人专门花精力去修剪，规则就是这样过期的。第三个是，为一处做的改动会弄坏另一处。为一个项目收紧一条规则，会挡住另一个团队的正常工作，而做改动的人永远看不到这些破坏。

还有第四个担心，是管理者的：推广之后，你怎么知道 agent 做了什么？要回答这个问题，得有一份有人会去看的记录。

我得先说清楚自己的位置。我的配置是为一个人搭的，也没有带着测量去做过团队落地。下面讲的是我会采用的设计，依据是这套配置现在已经能做的事（我能指出来的那些部分），以及我在加任何东西之前都会问的那些问题。只是建议的地方，我会说明。

Owners, reviews, records, and a rollout in stages

Who owns the rules

Drifting copies and rules nobody owns both lead back to the question of who owns the rules. It has no single answer, because not all rules are alike, so I split them into three layers by who is hurt when one of them is wrong.

The core is the short set of rules every task must follow, together with the files that enforce them (the fence from Guard the files that hold the rules). A mistake here reaches everyone. It has one or two named owners, and nobody else edits it.

Below it sits the team layer: domain skills, the team's knowledge base (an index of the code, see A knowledge base: an honest index of the code), and settings that are the same for everyone, such as which paths no agent may touch. Here each area has one owner, the person who knows that part of the code. A skill about deployment, for example, belongs to whoever deploys.

Last comes the personal layer: a user name, a language, the folder where your repositories sit on your machine. It belongs to the individual and is not committed, because it holds paths that exist on one computer only.

Two mechanisms make this workable in my setup, though a team can copy the idea without the tool.

One is the override, a small config that sits next to the default instead of copying it and lists only what you change. Someone who wants to add one forbidden path writes one line rather than forking the whole rule file. So the team's customisation stays a few lines that anyone can read, and an upgrade of the core does not collide with it. In my implementation an override cannot remove the core's guardrails: if one drops them, the engine puts them back and reports an error. The setup's health check also lists what every override changes, which gives a reviewer one place to look.

The other is that one rule has one main source. The same rule written in three files is how copies drift (Instructions and skills), so when you assign owners, assign them to sources. A rule with two homes has two owners, so in effect it has none.

Who reviews a change to a rule

Once a layer has an owner, the next question is who checks a change to it. The answer starts from what a rule file is. It is not documentation. It is what the agent obeys, so changing it changes what the team's agents do tomorrow. I treat it like code, with four habits.

The first habit is that the agent does not edit the rules. Because the files are fenced, a person opens the fence for one session, makes the change, closes it, and reads the diff in git afterwards (Guard the files that hold the rules). What that leaves behind is a diff that someone else can review.

The second is that the author is not the only reviewer. The owner of the layer reads the change, as does someone who was not in the discussion. Treat a rule change like a change to code that an attacker would love to make, because a careless or hostile pull request is a way in, as is a shared skill or knowledge-base file that carries instructions the agent will read as its own (Text the agent reads can give it orders).

Two readers settle this change, but not the ones that come after it. For those, agree on who may approve exceptions and who takes over a layer when its owner leaves. Clarity matters too: a rule that makes sense only to its author is a poor rule for an agent, because the agent reads it cold.

The third habit is a fixed set of questions. The review asks six, the ones I ask before adding anything to my own setup.

  • What failure does this prevent? Is there a real example, log or measurement?
  • Does the platform already do it? Did anyone read its current docs?
  • What does it cost, in context, tokens and time?
  • Is it a request in words, or a rule in code (A rule in a prompt is a request)? Is that the right one for the harm?
  • When can it be deleted? What would have to change?
  • If we moved to another tool, would what we learned still be useful?

One more rule helps the review: write down only what the model gets wrong. A line the model would follow anyway costs context and gives the reviewer more to read. If you cannot name an error it prevents, leave it out.

The last habit is that a claim of "this helps" needs the same tasks before and after. If a change is meant to improve results, the review should ask for a before-and-after on fixed tasks (Fixed tasks, scored by a script), not for an opinion.

Audit: what the setup leaves behind

Review happens before a change goes in, but afterwards a leader who was not there needs to answer "what did the agents do, and who let them?" Answering that is an audit. It works only if the setup writes records that the agent does not control, so here is what mine writes. Five kinds of record are built.

  • Each tool call gets one log line: the kind of call, whether it was let through or refused, which rule refused it, and how long it took. The line holds no arguments and no prompt text, except that a refused call keeps its path and command (Record what happened, not what the agent said).
  • Refusals are also counted. A statistics command sums the prompts, the calls and the refusals, and which part of the setup refused.
  • Each task's approvals are kept as records that only a person can create, and the task's report shows the time of both.
  • The task report is written by code when a task closes. It says what was asked, what changed, how many checks there were and the verdict of each, and what was refused (A report a person can read in five minutes).
  • Changes to the rules leave their own trace. The agent cannot edit the rule files, so a person does it, in a session where every logged call is marked as admin, and the change is a diff in git.

Two more are ideas I have not built. The approval records carry a time, but I have not checked whether they carry a person's name. My setup has one user, so I never needed that. A team does. Nor is there one place for the logs: in my setup they stay on each computer, out of git, and I have not built any way to gather them across a team.

Records still need a reader. So who looks, and how often? In my own setup I read the log when a run fails and when I change a rule, not every day (Record what happened, not what the agent said). For a team I would propose a short routine, in which the owner of each layer looks at the refusal counts now and then and reads the diff of every rule change. A log that nobody owns is not an audit trail.

A rollout in stages

That leaves the order in which to hand all this out. Going wide first and adding review later is how you get the ten copies this chapter started with, so I would widen in stages and write down, for each stage, what has to be true before entering it.

  1. One team, core only. Pick a team that wants the setup and owns its own code, and give the core to one or two owners from day one. Enter when: the team asks for it. Nothing needs to be proven yet.
  2. Add the team layer. Domain skills, shared settings and the knowledge base come after the team has used the core long enough to know what it needs. Enter when: the core has named owners, and the owner can say what happened in a recent task from the records, not from the agent's summary.
  3. Open it to the next team. Enter when: the review habit works in the first team, meaning that every rule change had a second reviewer, the diff was read, and any change meant to improve results came with a before-and-after on fixed tasks.
  4. Everyone, including the colleague who did not ask for it. Enter when: the logs show the rules hold. What that looks like is the subject of the next section.

Like the rest of this design, these conditions have not been run on a team, and the thresholds (how long is "long enough") are for you to set.

How you would know it is working

Stage 4 rests on the phrase "the logs show the rules hold", so it has to mean something you can look at. Without team numbers, I can only say what I would watch, not what I measured.

  • Do people open tasks, or go around the setup? Count the tasks opened, against work done in plain chats.
  • What do the rules refuse, and is it the same thing every week? A rule that refuses the same normal work is a rule to fix (Ask or refuse).
  • How often does work come back after approval? Rework after a yes means the gate was read too fast.
  • How many local overrides exist, and do they match? See the trap about overrides, below.

Stage 4 asks that these have stopped moving: the refusals are steady and mostly the ones you meant, rework is low, and the overrides are few. That, and nothing grander, is what "the logs show the rules hold" means.

How strong the evidence in this book is

If this chapter rests on a design rather than data, so, to a degree, does the whole book. Its limits are worth keeping in mind as you read the rest. Everything was built and tried on one platform, VS Code Copilot. Other tools have counterparts, but I have not tested them. It is also one person's harness: I built it and I use it. Nobody else has tested it, and as its builder I am not a neutral judge of it. I also have no team data or incidents to go on: I have not measured adoption, and I have no record of a rule failing in a team. My one measured comparison is four tasks, one run each (Use subagents sparingly). Where a chapter does give a figure, it gives the run count and the setup next to it, so that you can see how far to trust the number.

So use the book for its questions and its design, not as proof. Take a design from it, state what you expect it to do, and check that on your own tasks (Fixed tasks, scored by a script, One run proves nothing). Your numbers should replace mine.

負責人、審查、紀錄，再分階段推行

規則歸誰管

副本漂移也好，規則沒人負責也好，最後都會回到同一個問題：規則歸誰？這個問題沒有單一的答案，因為規則不都一樣。我看「一條規則錯了會傷到誰」，把它們分成三層。

核心層是每個任務都必須遵守的那幾條短規則，加上執行它們的檔案（保護規則本身的檔案 裡的圍欄）。這裡錯了，影響的是所有人。它有一、兩位指名的負責人，其他人不去改它。

往下是團隊層，包括領域的 skill、團隊的知識庫（程式碼的索引，見 知識庫：程式碼的誠實索引），以及對所有人都一樣的設定，例如哪些路徑任何 agent 都不能碰。這一層每個領域有一位負責人，就是懂那一塊程式碼的人。比如部署的 skill，就屬於負責部署的人。

最後是個人層，例如使用者名稱、語言、你的倉庫放在你機器上的哪個資料夾。它屬於個人，也不提交，因為裡面是只存在於一台電腦的路徑。

這套分法要做得起來，在我的設定裡靠的是兩個機制，不過團隊就算不用那個工具，也可以借用這個做法。

一個是 override。它是放在預設旁邊的一個小設定，而不是預設的副本，只列出你要改的東西。想多加一個禁止路徑的人，寫一行就好，不用分叉整份規則檔。這樣一來，團隊的客製化始終只有幾行，誰都讀得懂，核心升級時也不會和它衝突。在我的實作裡，override 移除不了核心的護欄：哪個 override 要是把它們拿掉，引擎會放回去並回報錯誤。設定的健康檢查也會列出每個 override 改了什麼，審查者就有一個可以集中查看的地方。

另一個是一條規則只有一個主要來源。同一條規則寫在三個檔案裡，就是副本漂移的起點（指令與 skill：只載入需要的），所以指定負責人的時候，要指定給來源。一條規則有兩個家，就有兩個負責人，其實等於沒有。

誰審查對規則的改動

每一層有了負責人，接下來的問題是：對它的改動由誰把關？這要從規則檔是什麼說起。它不是文件，而是 agent 服從的東西，所以改它，就是改團隊的 agent 明天會做什麼。我把它當程式碼看待，具體有四個習慣。

第一個習慣是 agent 不改規則。這些檔案被圍欄圍著，要改，得由人為一個會話打開圍欄，改完再關上，之後在 git 裡讀 diff（保護規則本身的檔案）。這樣留下來的，就是一份別人可以審查的 diff。

第二個習慣是，作者不是唯一的審查者。那一層的負責人要讀這個改動，另一位沒參與討論的人也要讀。看待規則的改動，要像看待攻擊者很想做的程式碼改動那樣，因為一個草率或惡意的 pull request 是入口，一個共用的 skill 或知識庫檔案也是入口，只要裡面帶著 agent 會當成自己的指令讀進去的內容（agent 讀到的文字可能在指揮它）。

兩個人讀過，管得了這一次改動，管不了以後的。以後的事，要講好誰可以批准例外，以及負責人離開時誰接手那一層。寫規則的人還要記得，agent 是從零開始讀的，所以只有作者看得懂的規則，對它來說就是差的規則。

第三個習慣是一組固定的問題。審查要問六個，也就是我在為自己的設定加任何東西之前會問的那些。

  • 這防止什麼失敗？有真實的例子、日誌或量測嗎？
  • 平台已經做了嗎？有人讀過它現在的文件嗎？
  • 它花多少，在上下文、token 和時間上？
  • 它是用文字寫的請求，還是程式碼裡的規則（提示裡的規則只是請求）？對這個傷害來說，選對了嗎？
  • 什麼時候可以刪掉？要變成什麼樣？
  • 如果我們換到別的工具，學到的東西還有用嗎？

還有一條規則能幫上審查：只寫模型會做錯的。模型本來就會照做的一行，既花上下文，又讓審查者多讀一行。說不出它防止哪個錯誤，就不要寫。

最後一個習慣，是不接受空口的「這有幫助」。如果一個改動是為了改善結果，審查就該要求一份在同樣的固定任務上做的前後比較（固定的任務，用腳本打分），而不是一個意見。

稽核：設定留下什麼

審查發生在改動生效之前，可是事後，沒在場的主管還要能回答「agent 做了什麼，誰讓它做的？」回答這個問題，就是稽核。稽核要行得通，前提是紀錄不歸 agent 控制。那我的設定到底寫下了什麼？已經做好的有五類。

  • 每次工具呼叫記一行日誌：呼叫的種類、放行還是拒絕、哪條規則拒絕的，以及花了多久。這一行沒有參數，也沒有 prompt 的文字，只有被拒絕的呼叫會保留路徑和指令（記下發生了什麼，不是 agent 說了什麼）。
  • 拒絕也會被計數。一個統計指令會加總 prompt、呼叫和拒絕，以及是設定的哪個部分拒絕的。
  • 每個任務的批准，都存成只有人能建立的紀錄，任務的報告會顯示兩道批准的時間。
  • 任務報告在任務結束時由程式碼寫出，寫的是問了什麼、改了什麼、有多少檢查和每個檢查的結論，以及什麼被拒絕了（一份五分鐘讀得完的報告）。
  • 規則的改動也有自己的痕跡。agent 不能改規則檔，所以由人來改，而且是在一個會話裡改，這個會話裡記下的每個呼叫都標成 admin，改動本身就是 git 裡的一份 diff。

還有兩類只是想法，沒有做。批准的紀錄帶有時間，但有沒有帶人名，我沒有確認。我的設定只有一位使用者，所以我從沒需要過，團隊卻需要。日誌也沒有放在同一個地方：在我的設定裡，它們留在每台電腦上，不放進 git，我也沒有做任何跨團隊收集它們的辦法。

這些紀錄還得有人讀。那麼，誰來看，多久看一次？在我自己的設定裡，我在一次運行失敗和我改規則的時候讀日誌，不是每天讀（記下發生了什麼，不是 agent 說了什麼）。對團隊，我會提議加一個簡短的例行檢查，由每一層的負責人每隔一陣子看一下拒絕的計數，並讀每次規則改動的 diff。沒有人負責的日誌，算不上稽核的軌跡。

分階段推行

還有一件事，是按什麼順序推出去。先鋪開、之後再補審查，得到的就是這一章開頭那十份副本。所以我會分階段擴大，並為每個階段寫下要符合什麼條件才能進入。

  1. 一個團隊，只有核心。挑一個想要這套設定、自己擁有程式碼的團隊，從第一天就把核心交給一、兩位負責人。進入條件：團隊要它。現在還不需要證明什麼。
  2. 加上團隊層。領域的 skill、共用設定和知識庫，要等團隊用核心用得夠久、知道自己需要什麼之後再加。進入條件：核心有指名的負責人，而且負責人能靠紀錄，不是靠 agent 的摘要，說出最近一個任務發生了什麼。
  3. 開放給下一個團隊。進入條件：審查的習慣在第一個團隊行得通，也就是每次規則改動都有第二位審查者，diff 有人讀，任何要改善結果的改動，都附有固定任務上的前後比較。
  4. 所有人，包括沒有要求的同事。進入條件：日誌顯示規則撐得住。這句話具體指什麼，見下一節。

和這套設計的其他部分一樣，這些條件沒有在團隊上跑過，門檻（多久才算「夠久」）也要你自己定。

你怎麼知道它有效

第 4 階段靠的是「日誌顯示規則撐得住」這句話，所以它得指向看得到的東西。沒有團隊的數字，我只能說會看什麼，說不出量到了什麼。

  • 大家是開任務，還是繞過設定？數一數開了多少任務，對比在一般對話裡做的工作。
  • 規則拒絕什麼，每週都是同樣的東西嗎？一條一直拒絕同樣正常工作的規則，是該修的規則（詢問不是限制）。
  • 批准之後，多常需要返工？批准後返工，表示批准時看得太快。
  • 本機的 override 有多少，它們一致嗎？見後面關於 override 的那個陷阱。

第 4 階段要求這些都不再變動：拒絕的數量穩定，而且多半是你想要它拒絕的，返工少，override 也少。「日誌顯示規則撐得住」指的就是這些，沒有更多。

這本書的證據有多強

這一章靠的是設計而不是數據，整本書在某種程度上也是這樣。讀其餘的部分時，這些限制值得記在心裡。一切都是在一個平台上建立和試的，就是 VS Code Copilot。別的工具也有對應的東西，但我沒有測過。而且這是一個人的 harness：是我建的，我在用。沒有別人測過，而我身為建它的人，也不是它的中立評審。我也沒有團隊數據或事故可以依據：我沒有量過採用情況，也沒有團隊裡規則失敗的紀錄。我唯一量過的比較，是四個任務、各跑一次（慎用子 agent）。一章給出數字時，旁邊都會寫明運行次數和設定，讓你看出該信多少。

所以請把這本書當作問題和設計來用，不要當成證明。從裡面拿一個設計，說出你預期它做到什麼，再在你自己的任務上檢查（固定的任務，用腳本打分、一次運行證明不了什麼）。你的數字應該取代我的。

负责人、审查、记录，再分阶段落地

规则归谁管

副本漂移也好，规则没人负责也好，最后都会回到同一个问题：规则归谁管？这个问题没有唯一的答案，因为规则不都一样。我按“一条规则错了，谁会受伤”，把它们分成三层。

核心层是每个任务都必须遵守的那几条简短规则，加上执行它们的文件（保护规则本身的文件里的围栏）。这里出错，影响的是所有人。它有一两个指定的负责人，别人不去改它。

往下是团队层，包括领域 skill、团队的知识库（代码的索引，见知识库：代码的诚实索引），以及对所有人都一样的设置，比如哪些路径任何 agent 都不许碰。这一层每个领域有一位负责人，就是最了解那部分代码的人。比如关于部署的 skill，就归负责部署的人。

最后是个人层，比如用户名、语言、你的仓库在你机器上所在的文件夹。它归个人，也不提交，因为里面的路径只在一台电脑上有效。

这套分法要行得通，在我的配置里靠的是两个机制，不过团队就算不用这个工具，也可以照搬思路。

一个是 override。它是放在默认配置旁边的一小份配置，而不是默认配置的副本，只列出你改动的东西。想多禁止一个路径的人，写一行就行，用不着把整个规则文件 fork 出去。这样一来，团队的定制始终只有几行，谁都读得懂，核心层升级时也不会和它冲突。在我的实现里，override 删不掉核心层的护栏：哪个 override 要是把它们去掉了，引擎会把它们放回去，并报告一个错误。配置的健康检查还会列出每个 override 改了什么，这样审查者就有了一个集中查看的地方。

另一个是一条规则只有一个主来源。同一条规则写在三个文件里，副本就是这么漂移起来的（指令与 skill：只加载需要的），所以分派负责人时，要分派给来源。一条规则有两个家，就有两个负责人，实际上等于没有。

谁来审查对规则的改动

每一层有了负责人，接下来的问题是：对它的改动由谁来把关？这要从规则文件是什么说起。它不是文档，而是 agent 要服从的东西，所以改它，就是改团队的 agent 明天会做什么。我像对待代码那样对待它，具体有四个习惯。

第一个习惯是 agent 不改规则。这些文件被围栏围着，要改，得由人为一次会话打开围栏，改完再关上，之后在 git 里读 diff（保护规则本身的文件）。这样留下来的，就是一份别人可以审查的 diff。

第二个习惯是，作者不是唯一的审查者。这一层的负责人要读这个改动，另一个没参与讨论的人也要读。对待规则改动，要像对待攻击者很想做的代码改动那样，因为一个草率或怀有恶意的 pull request 是入口，一个共享的 skill 或知识库文件也是入口，只要里面带着 agent 会当成自己的指令来读的话（agent 读到的文字可能在指挥它）。

两个人读过，管得了这一次改动，管不了以后的。以后的事，要约定好谁可以批准例外、负责人离开时谁接手这一层。写规则的人还要记得，agent 是从零开始读的，所以只有作者看得懂的规则，对它来说就是差的规则。

第三个习惯是一组固定的问题。审查要问六个，也就是我往自己的配置里加任何东西之前会问的那些。

  • 它防止什么故障？有真实的例子、日志或测量吗？
  • 平台已经做了吗？有人读过它现在的文档吗？
  • 它花多少，在上下文、token 和时间上？
  • 它是文字里的请求，还是代码里的规则（提示里的规则只是请求）？对这个危害，选这个对吗？
  • 什么时候可以删？要变成什么样？
  • 如果我们换了别的工具，学到的东西还有用吗？

还有一条规矩能帮上审查：只写模型会弄错的东西。模型本来就会照做的一行，既占上下文，又让审查者多读一行。说不出它防止了什么错误，就别写。

最后一个习惯，是不接受空口的“这有帮助”。如果一个改动是为了改善结果，审查就该要一份在同样的固定任务上做的前后对比（固定的任务，用脚本打分），而不是一个意见。

审计：配置留下了什么

审查发生在改动生效之前，可事后，没在场的管理者还要能回答“agent 做了什么，是谁让它们做的”。回答这个问题，就是审计。审计要行得通，前提是记录不归 agent 控制。那我的配置到底写下了什么？已经做了的有五类。

  • 每次工具调用记一行日志：调用的类型、是放行还是拒绝、哪条规则拒绝的、花了多长时间。这一行不记参数，也不记 prompt 文本，只有被拒绝的调用会保留它的路径和命令（记下发生了什么，而不是 agent 说了什么）。
  • 拒绝还会被计数。一条统计命令会汇总 prompt、调用和拒绝的数量，以及是配置的哪个部分拒绝的。
  • 每个任务的审批，都保存成只有人才能创建的记录，任务报告会显示两道审批的时间。
  • 任务报告在任务关闭时由代码写出，写的是要求是什么，改了什么，做了多少次检查、每次的结论，以及拒绝了什么（一份五分钟读得完的报告）。
  • 对规则的改动也有自己的痕迹。agent 不能改规则文件，所以由人来改，而且是在一次会话里改，这次会话里每个记录下来的调用都标成 admin，改动本身就是 git 里的一份 diff。

还有两类只是想法，没有做。审批记录带有时间，但带不带人名，我没查过。我的配置只有一个用户，所以从来不需要，团队却需要。日志也没有集中放在一处：在我的配置里，它们留在每台电脑上，不放进 git，我也没有做过在团队范围内把它们收集起来的办法。

这些记录还得有人读。那么，谁来看，多久看一次？在我自己的配置里，我在一次运行失败时和改规则时读日志，不是每天读（记下发生了什么，而不是 agent 说了什么）。对团队，我会建议加一个简短的例行动作，由每一层的负责人时不时看看拒绝的次数，并读每一次规则改动的 diff。没人负责的日志，算不上审计线索。

分阶段落地

还有一件事，是按什么顺序推开。先铺开、后补审查，得到的就是这一章开头那十个副本。所以我会分阶段放开，并为每个阶段写下进入之前必须满足什么。

  1. 一个团队，只用核心层。挑一个想要这套配置、并且拥有自己代码的团队，从第一天起就把核心层交给一两个负责人。*进入条件：*这个团队来要。现在还不需要证明什么。
  2. 加上团队层。领域 skill、共享设置和知识库，要等这个团队用核心层用得足够久、知道自己需要什么之后再加。*进入条件：*核心层有了指定的负责人，而且负责人能根据记录，而不是 agent 的摘要，说出最近一个任务里发生了什么。
  3. 放给下一个团队。*进入条件：*审查的习惯在第一个团队里行得通，也就是每次规则改动都有第二个审查者，diff 被读过，凡是要改善结果的改动，都附了固定任务上的前后对比。
  4. 所有人，包括没要求过的那位同事。*进入条件：*日志显示规则站得住。这句话具体指什么，见下一节。

和这套设计的其他部分一样，这些条件没有在团队里跑过，阈值（多久才算“足够久”）也由你来定。

怎么知道它在起作用

第 4 阶段靠的是“日志显示规则站得住”这句话，所以它得指向看得见的东西。没有团队的数字，我只能说会盯什么，说不出量到了什么。

  • 大家是在开任务，还是绕开这套配置？数一数开了多少任务，对比在普通对话里完成的活。
  • 规则拒绝了什么？每周都是同样的东西吗？一条总是拒绝同样的正常工作的规则，是要修的规则（询问不是限制）。
  • 批准之后有多少活被打回来？点头之后又返工，说明审批时看得太快。
  • 本地 override 有多少，它们一样吗？见后面关于 override 的那个坑。

第 4 阶段要求这些都不再变动：拒绝的次数稳定，而且多半是你想拒绝的那些，返工很少，override 也很少。“日志显示规则站得住”指的就是这个，没有更大的含义。

这本书里的证据有多强

这一章靠的是设计而不是数据，整本书在一定程度上也是这样。读其余部分时，这些局限值得记在心里。所有东西都是在一个平台上搭建和试验的，就是 VS Code Copilot。别的工具也有对应的东西，但我没有测过。而且这是一个人的 harness：是我搭的，我在用。没有别人测过，而我作为搭建者，也不是它的中立评判者。我也没有团队数据或事故可以依据：我没测过采用情况，也没有规则在团队里失效的记录。我唯一量过的对比，是四个任务、各跑一次（慎用子 agent）。章节里给出数字的地方，都会在旁边写明运行次数和配置，好让你看出该信到什么程度。

所以，请把这本书当作问题和设计来用，不要当作证明。从中取一个设计，说清你预期它做什么，再在你自己的任务上检验（固定的任务，用脚本打分、一次运行证明不了什么）。你的数字应该取代我的。

Where governance can go wrong

Governance has costs of its own, and most of them fall on people. The first is that the owner can become a bottleneck. If every rule change goes through two people, people stop proposing changes and start keeping private copies, which is the problem you were solving. Keep the core small, so that few changes need the strict path, and let the team layer move fast.

Review of rules is also unglamorous, because no one is thanked for a rule that was not added. Put the owner's time in someone's plan, or the review turns into a rubber stamp. And the reviewer has to be able to judge the rule. A rule about a deployment path, reviewed by someone who has never deployed, gets only a spelling check.

Overrides need watching too, since too many local overrides amount to a fork. If most users carry the same override, it belongs in the team layer, so look at the overrides now and then and promote the common ones.

The logs bring a cost of a different kind, because they hold things about people. A log of every call says when someone worked and what they asked the agent to touch. Decide who may read it and how long it is kept before you collect it centrally.

The logs matter in one more way, as the evidence for a stage gate, and a gate is only as good as the record behind it. A hole in the logs (Record what happened, not what the agent said) makes "the rules hold" look true when it is not known.

All of this rests on the limit I admitted at the start. The three layers, the review habits, the audit routine and the stages are built on one person's use. I have not measured adoption or tracked who edits what in a team, so treat them as a starting point to check, not as results.

治理本身會在哪裡出問題

治理本身也有代價，多半落在人身上。首先，負責人可能變成瓶頸。如果每次改規則都要經過兩個人，大家就不再提改動，轉而留私人副本，而這正是你本來要解決的問題。讓核心保持小，需要走嚴格流程的改動就少，團隊層則讓它走得快。

審查規則也不風光，沒有人會因為一條沒加的規則被感謝。要把負責人的時間排進某個人的計劃，不然審查就會變成蓋章。而且審查者必須能判斷這條規則。一條關於部署路徑的規則，讓從沒部署過的人審查，就只剩拼字檢查。

override 也要盯著，因為本機 override 太多，就等於分叉。如果多數使用者都帶著同一個 override，它就屬於團隊層，所以要時不時看一下 override，把常見的升上去。

日誌帶來的則是另一種代價，因為裡面有關於人的事。一份記下每個呼叫的日誌，會說出某人什麼時候工作，以及他要 agent 碰什麼。在集中收集之前，先決定誰可以讀它，以及保留多久。

日誌還有一層作用：它是階段的門的證據，而門可不可靠，全看背後的紀錄。日誌裡的一個洞（記下發生了什麼，不是 agent 說了什麼），會讓「規則撐得住」看起來是真的，其實卻無從知道。

這一切都建立在我一開始承認的那個限制上。三層、審查的習慣、稽核的例行檢查和各個階段，都是照一個人的用法設計出來的。我沒有量過採用情況，也沒有追蹤團隊裡誰改了什麼，所以請把它們當成要檢查的起點，不要當成結果。

治理本身会在哪里出问题

治理本身也有代价，多半落在人身上。首先，负责人可能变成瓶颈。如果每次规则改动都要经过两个人，大家就不再提改动，转而留私人副本，而这正是你要解决的问题。让核心层保持小，这样走严格流程的改动就少，团队层则让它改得快。

审查规则也没什么光彩，没人会因为一条没加的规则而被感谢。要把负责人的时间排进某个人的计划里，否则审查就会变成走过场。而且审查者得有能力判断这条规则。一条关于部署路径的规则，让一个从没部署过的人来审，就只剩一次拼写检查。

override 也要盯着，因为本地 override 太多，就等于 fork。如果大多数用户都带着同样的 override，它就该放进团队层，所以要时不时看看 override，把常见的提升上去。

日志带来的则是另一种代价，因为里面有关于人的东西。一份记录每次调用的日志，会显示某人什么时候工作、让 agent 去碰了什么。在集中收集之前，先定好谁可以读，保存多久。

日志还有一层作用：它是阶段关卡的证据，而关卡的好坏，取决于背后的记录。日志里的漏洞（记下发生了什么，而不是 agent 说了什么）会让“规则站得住”看起来是真的，实际上却无从知道。

这一切都建立在我开头承认的那个局限上。三层划分、审查习惯、审计例行动作和各个阶段，都是根据一个人的使用设计出来的。我没有测过团队里的采用情况，也没有跟踪过谁改了什么，所以请把它们当作要验证的起点，不要当成结果。

When to delete the layers, and what stays

The three-layer split exists because the platform gives you files but no way to own them. If your platform lets an organisation publish rules centrally, with its own review, audit and roll-out, use that for the core layer and keep only the team layer yourself. I have not checked what Copilot offers here today, so look at its current docs before building your own.

The review questions, though, do not retire. They are how you decide whether any rule, skill or agent deserves to exist.

什麼時候可以刪掉這三層，什麼會留下來

三層的劃分之所以存在，是因為平台給了你檔案，卻沒給你管理它們的辦法。如果你的平台讓組織集中發布規則，並附帶自己的審查、稽核和推行，核心層就用它，自己只留團隊層。Copilot 今天在這方面提供什麼，我沒有確認，所以在自己動手之前，先看看它目前的文件。

不過，審查的那些問題不會退役。任何規則、skill 或 agent 值不值得存在，你都要靠它們來決定。

什么时候可以删掉这三层，什么会留下来

三层划分之所以存在，是因为平台给了你文件，却没给你管理这些文件的办法。如果你的平台允许组织集中发布规则，并自带审查、审计和推广，核心层就用它的，自己只留团队层。Copilot 现在在这方面提供什么，我没查过，所以自己动手建之前，先看看它当前的文档。

不过，审查的那些问题不会退役。任何规则、skill 或 agent 值不值得存在，你都要靠它们来决定。
