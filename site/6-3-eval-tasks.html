6.3

Fixed tasks, scored by a script固定的任務，用腳本打分固定的任务，用脚本打分

This chapter assumes you have used an AI coding agent, and that you have changed its rules or setup at least once. Nothing else.

讀這一章，你需要用過 AI 寫程式的 agent，而且至少改過一次它的規則或設定。不需要別的。

读这一章，你需要用过一个写代码的 AI agent，并且至少改过一次它的规则或配置。别的都不需要。

The Knowledge經驗分享经验分享

In one sentence

To know whether a change helped, run the same fixed tasks before and after the change and score them with a script. Then read the runs that failed.

一句話

要知道一個改動有沒有幫助，就在改動前後跑同樣的固定任務，用腳本打分，然後讀失敗的那幾次運行。

一句话

想知道一个改动有没有用，就在改动前后，对同样的固定任务各跑一遍，用脚本打分，然后去读失败的那几次运行。

For leaders

  • The decision: require that any change to the agent's rules or setup comes with a before-and-after run on the same fixed tasks, scored by a script.
  • The risk: one good result cannot tell you whether a change helped. My own set has four tasks, which is enough to show a gap of four to six times but not a gap of ten percent.
  • The cost of doing it right: an afternoon to build the scorer and test it on a good answer and a broken one, and after that the cost of every run. In my lab, the three-role team took about 16 minutes and about 456 AI credits to do the four tasks once.
  • Ask the team: "Which fixed tasks did you run before and after this change, and how do you know the script that scores them catches a wrong answer?"

給主管

  • 要做的決定：對 agent 的規則或設定做的任何改動，都要附上改動前後在同樣固定任務上的運行，並用腳本打分。
  • 風險：光看一個好結果，你分辨不出改動有沒有幫助。我自己的這組只有四個任務，足以顯示四到六倍的差距，卻顯示不出百分之十的差距。
  • 做對的成本：花一個下午建評分腳本，並用一個好答案和一個壞答案測試它，之後就是每一次運行的成本。在我的實驗裡，三角色團隊把四個任務做一遍，大約 16 分鐘、大約 456 個 AI credits。
  • 可以問團隊：「這個改動前後，你們跑了哪些固定任務？你們怎麼知道給它們打分的腳本，抓得到錯的答案？」

写给管理者

  • 要拍板的事：对 agent 规则或配置的任何改动，都要附上在同一组固定任务上改动前后各跑一遍的结果，由脚本打分。
  • 风险：光凭一次好结果，分不出改动有没有用。我自己这套只有四个任务，够看出四到六倍的差距，却看不出一成的差距。
  • 做对的代价：花一个下午写打分脚本，并用一个好答案和一个故意弄坏的答案测它，之后就是每次运行的开销。在我的实验里，三角色团队把四个任务做一遍，约 16 分钟、约 456 AI credits。
  • 可以问团队：“这个改动前后，你们跑了哪些固定任务？你们怎么知道给它们打分的脚本能抓出错误答案？”

How do you know a change helped?

After you add a rule, change a prompt or switch on a check, the next task goes well. Did the change help?

You cannot tell from that. The next task may simply have been easy, or the agent may have done well by luck (the next chapter is about that). Nor are you a neutral judge, because you made the change and you want it to work. Looking at a result and feeling that it is better is not evidence.

When I wrote Use subagents sparingly, I wanted to know whether three job-title agents did better than one agent. Rather than take one task and look, I took four fixed tasks, ran both setups on each of them (once each) and let the same script score all of the results. What came out changed my design: the team cost far more and got nothing more right (the numbers are in that chapter, with their limits). Looking at a few results, I would not have believed it.

What I did there is called an eval (short for evaluation), a test for an agent setup. It has three parts: a set of tasks, a way to run them and a way to score the results. My tasks were fixed tasks: their request, starting files and right answer did not change between runs. Whatever scored them, here mostly a script, is the grader. How, then, do you build an eval whose answer you can believe?

怎麼知道一個改動有沒有幫助？

你加了一條規則、改了一個 prompt，或開啟了一個檢查，接下來那個任務做得很順利。是改動有幫助嗎？

光憑這一次，你分辨不出來。那個任務可能本來就簡單，agent 也可能只是運氣好（下一章 就講這個）。再說，你也不是中立的評審：改動是你做的，你當然希望它有用。看著一個結果，覺得變好了，這不是證據。

寫 慎用子 agent 的時候，我想知道三個分工不同的 agent，是不是比一個 agent 好。我沒有拿一個任務來看看就算了，而是拿了四個固定任務，兩種設定各跑一次，再讓同一個腳本替所有結果打分。結果改變了我的設計：團隊花的錢多得多，卻沒有多做對任何一件事（數字在那一章，連同它們的限制）。要是只看幾個結果，我不會相信這一點。

我在那裡用的辦法，叫做評測（eval，evaluation 的縮寫）。它是對 agent 設定的測試，分三部分：一組任務、一種執行它們的方法、一種為結果打分的方法。我用的是固定任務：要求、起始檔案和正確答案在每次運行之間都不變；替它們打分的東西，這裡主要是一個腳本，叫評分器（grader）。那麼，要怎麼建一個答案信得過的評測？

怎么知道一个改动有没有用？

你加了一条规则，改了一个 prompt，或者打开了一项检查，接下来的那个任务做得挺顺。是改动起了作用吗？

光凭这一次，你分不出来。那个任务也许本来就简单，agent 也许只是运气好（下一章讲的就是这个）。再说，你也不是中立的裁判：改动是你做的，你自然希望它有用。看着一个结果，觉得它变好了，这算不上证据。

写慎用子 agent的时候，我想知道三个岗位的 agent 是不是比一个 agent 强。我没有拿一个任务看一眼就下结论，而是拿了四个固定任务，每个任务两种配置各跑一次，所有结果交给同一个脚本打分。结果改变了我的设计：团队贵了好多，做对的却一个也没多（数字和它们的局限在那一章里）。要是只看几个结果，我是不会信的。

我在那里用的办法，叫评测（eval，evaluation 的简称）。它是对 agent 配置的测试，分三部分：一组任务、一种运行它们的方式、一种给结果打分的方式。我用的是固定任务：需求、起始文件和正确答案在多次运行之间都不变；给它们打分的东西，这里主要是一个脚本，叫打分器（grader）。那么，怎样才能搭出一个结论信得过的评测？

Building an eval you can believe

The picture shows the method: fixed tasks, a run before and after the change, a script that scores both, and a person who reads what failed.

What a good task looks like

The method starts with the tasks, but not every task makes a good eval. I look for three things.

  1. It is real. It should look like the work the agent does for you, not like an exam question, so if you only ever add pipelines and fix formulas, do not test poetry. A change that helps on made-up work but not on yours teaches you nothing.
  2. It has one right answer you can check. "Add a pipeline" is checkable: five files exist, in the right places, and agree with each other. "Make the code nicer" is not. If two reasonable people would disagree on whether the result is right, a script cannot score it.
  3. It covers the mistakes people actually make. A good set has an easy case, but it also has the traps. In my lab, one task asks the agent to change a file that the rules forbid it to change, and the good result is to refuse. That task is there because a real request can ask for exactly that, and an agent that obeys it has done wrong.

The four tasks of my lab run from small to medium. They add a pipeline, pass a column downstream through three pipelines (one column is renamed on the way), rename a pipeline across areas and delete its old files, and fix a formula that lives in two places, where the request also asks to change a protected file. Four is few, and I come back below to what that means for the results.

These tasks also come in two sorts, and a failure means something different in each. A capability task checks something the setup cannot do yet, so you expect it to fail often at first. A regression task checks something that already works, so you expect it to pass every time, and a failure means a change broke it. Mix the two on purpose, but read a pass rate differently for each.

The repository under all of this is made up (93 files, 5 areas) and cannot be run. That is a choice. Because the right answers are known in advance, the script can say which result is right without anyone running code to find out.

Outcome or process?

With the tasks in place, what should the grader look at? It can look at the outcome, meaning the files the agent left behind, such as whether it added the five files, whether the registry lists the new pipeline and whether the protected file is untouched. Or it can look at the process, meaning what the agent did to get there, such as whether it got refused or wrote to a place before the plan was approved.

For most tasks, grade the outcome. Because there are usually many valid ways to reach a right answer, a grader that insists on one path marks good work as wrong. Grade the process only when the process is the thing you care about, such as "the rules refuse a write before the plan is approved". In my harness, such a scenario looks at two things, and it passes only if the log shows the refusal and the file is unchanged. Without a log there is nothing to check, which is why recording every call comes first.

In my lab's scoring, the outcome is a checklist. Some items are the same for every task and check that the repository is still consistent (valid files, every pipeline has its five files, columns agree, the protected area is untouched). Others belong to one task and check that the request itself is done. One more checks the scope: only the files that should change were changed. A task passes only when every item passes.

That makes the score all-or-nothing. If you want to see progress on a long task, score it in parts (partial credit) and report the parts. I do not split, because for a short task like these, one wrong item usually means a wrong result.

A script or a model as the grader

Then there is the question of who, or what, does the scoring. A script reads the files and answers pass or fail. A model can read the result and give a judgment. Each has a weak side.

A script is cheap and quick and gives the same answer every time. Its weakness is brittleness. Because it looks for one particular form, it can mark a valid result wrong, and you only find those cases by reading the failures. A model grader can accept valid variations and judge things a script cannot, such as whether an explanation is clear. But its answer can change from run to run. It can also share blind spots with the agent it grades (Can a model check a model?).

Anthropic's advice agrees: "We recommend choosing deterministic graders where possible, LLM graders where necessary or for additional flexibility." (Demystifying evals for AI agents) That is also how I work. I use a script wherever the answer can be checked in files and keep a model grader for the few things a script cannot see. The lab here has no model grader.

Prove the grader first

Either way, a grader is a program, and programs have bugs. A grader that passes everything makes every change look harmless. A grader that fails everything makes every change look harmful. So before I trust any score, I test the grader. My lab has a self-test with three parts:

  • The untouched repository must fail every task, since nothing was done.
  • The right answers, written by hand, must pass every task.
  • Broken versions of the right answers must all be caught. There are 23, each with one mistake such as a missing registry line or a wrong column. If the grader lets one pass, the grader is wrong.

The smallest version is one good answer and one answer you broke by hand: the grader must pass the first and catch the second. For my lab it took an afternoon. It is the part people skip, and also the reason I can say that a failed item means something.

Read the failed runs

Even a grader you have tested only tells you that something failed, not why. So I keep one habit even with a script: when a run fails, I open it and read what happened. The reason can be one of three very different things. The agent may have made a real mistake, which is what the eval is for. The grader may be wrong, because the result was right but came in a form the script did not expect. Or the task may be unclear, with two reasonable answers and a request that did not say which.

Only the first of these tells you about the agent. If you take every failure for that kind, you will throw away good changes and keep bad ones. Anthropic puts it this way: "Reading transcripts is how you verify that your eval is measuring what actually matters." (the same article)

So the script does not replace looking. What it replaces is reading every run. The script picks the runs that failed, as its guess at where to look, and a person then reads those.

Your tasks and public benchmarks

You might ask why I build my own tasks at all, when public ones exist. A benchmark is a public set of tasks, scored the same way for everyone, so that models can be compared. It is useful for one question: how does this model do on someone else's tasks? It cannot answer a different one: did my change to my setup help on my work? For that you need tasks from your repository, with your rules in them, such as the protected file in my lab. That is why I build my own.

That choice has a price. A set I build is small, and it is mine alone. It also goes stale: whenever the repository changes, the tasks must change with it.

What my harness does today

Everything so far has been about the lab. My harness itself does less. In my setup there are a few fixed scenarios, each one a prompt plus what is expected: a few calls that must appear in the log (such as a refusal) and a few files that must or must not change. I run a scenario by hand once, in Copilot, after which a check reads the log and the files and says whether it went right.

What it cannot do yet is run them in a batch. At the time of writing (October 2026), I see in my own setup that the non-interactive mode of Copilot does not run hooks, so I cannot run the scenarios in a batch. A before-and-after comparison on real tasks is not done yet either. In daily use, then, I have one scenario run by hand and a look at the log it leaves. What I have done with numbers, the scored and repeated comparison of this chapter, is the lab in this repository.

Run it yourself

If you want to see all of this working before you build your own, start with the lab. It is the test behind the numbers in Use subagents sparingly: the made-up repository, the four tasks and the scoring script. All of them work with any agent tool. labs/subagents/ says how to run the self-test first and then your own comparison. Once you see how it works, replace the tasks with tasks of your own.

Test your own setup

Whether or not you run the lab, three questions are worth asking before any change you are about to make to an agent setup:

  1. What would I see if this change helped, and what if it did not?
  2. Can a script tell the two apart?
  3. Does the script itself pass the untouched, right and broken test?

You can also make a small start with no tools at all. Pick three tasks you have done with your agent. For each one, write down the files you would expect in the end and one mistake you have seen, then write a short script that checks the files. (If your work is not code, check the output instead: the columns of a table, the row count, a total.) Run it on a good result and on a result you break by hand. If it catches the broken one and passes the good one, you have an eval. It is small. Use it the next time you change a rule.

怎麼建一個信得過的評測

圖裡畫的就是這個方法：固定任務，改動前後各跑一次，腳本替兩邊打分，再由人讀失敗的運行。

好的任務長什麼樣

方法從任務開始，但並不是每個任務都適合做評測。我找三樣東西。

  1. 它是真的。它應該像 agent 平常替你做的工作，不是像考試題，所以如果你只加 pipeline、修公式，就不要測寫詩。只在虛構的工作上有用、在你的工作上沒用的改動，教不了你什麼。
  2. 它有一個你能檢查的正確答案。「加一個 pipeline」可以檢查：五個檔案存在、位置對、彼此一致。「讓程式碼更漂亮」就不行。如果兩個講理的人會對結果對不對有不同意見，腳本就沒辦法打分。
  3. 它涵蓋人真的會犯的錯。好的一組有簡單的案例，也要有陷阱。在我的實驗裡，有一個任務要求 agent 改一個規則禁止它改的檔案，好的結果是拒絕。這個任務放在這裡，是因為真實的要求本來就可能這樣提，而照做的 agent 就是做錯了。

我的實驗的四個任務，從小到中等：加一個 pipeline；把一個欄位經過三個 pipeline 往下游傳（其中一個欄位途中改了名）；跨區域重新命名一個 pipeline 並刪掉舊檔案；修一個存在兩個地方的公式，而要求裡也要求改一個受保護的檔案。四個任務確實很少，這對結果代表什麼，後面再說。

這類任務還分兩種，失敗代表的意思也不同。能力任務檢查設定還做不到的事，所以一開始預期它常常失敗。回歸任務檢查已經做得到的事，所以預期它每次都通過，一旦失敗，就表示有改動把它弄壞了。兩種要有意地混在一起，但兩種的通過率要分開看。

這些任務底下的倉庫是虛構的（93 個檔案、5 個區域），而且不能執行。這是刻意的。正因為正確答案事先就知道，腳本才能判斷哪個結果是對的，不需要有人執行程式碼去查。

看結果，還是看過程？

任務有了，評分器該看什麼？它可以看結果，也就是 agent 留下來的檔案，例如五個檔案加了沒有、登記表有沒有列出新的 pipeline、受保護的檔案是不是沒動。它也可以看過程，也就是 agent 怎麼做到的，例如它有沒有被拒絕，有沒有在計畫批准之前就寫到某個地方。

大多數任務，給結果打分。到達正確答案通常有很多有效的路，所以堅持只走一條路的評分器，會把好的工作判成錯的。只有過程本身就是你在乎的東西時，才給過程打分，例如「規則在計畫批准之前，拒絕寫入」。在我的 harness 裡，這類情境要同時看兩件事：日誌顯示了那次拒絕，檔案也沒有變，兩樣都對上才算通過。沒有日誌就沒東西可查，這就是 記錄每一次呼叫 要排在最前面的原因。

在我的實驗的評分裡，結果是一張檢查清單。有些項目每個任務都一樣，檢查倉庫是不是仍然一致（檔案有效、每個 pipeline 有它的五個檔案、欄位一致、受保護的區域沒動）。有些項目只屬於一個任務，檢查要求本身做完了沒有。還有一項檢查範圍，看是不是只有該改的檔案被改了。每一項都通過，一個任務才算通過。

這樣的分數是全有或全無。如果你想在長任務上看到進度，就分段打分（部分給分），並報告各段。我沒有拆，因為對這些短任務來說，一項錯通常就表示結果是錯的。

用腳本還是用模型當評分器

接著的問題是，由誰、或由什麼來打分。腳本讀檔案，回答通過或失敗；模型可以讀結果，給出判斷。兩者各有弱點。

腳本便宜、快，每次給同樣的答案。它的弱點是脆。因為它只找某一種特定的形式，有效的結果也可能被它判成錯的，而這種情況要靠讀失敗的結果才找得出來。模型評分器可以接受有效的變化，也能判斷腳本做不到的事，例如一段解釋清不清楚。但它的答案每次運行可能不同，還可能和被它評分的 agent 有同樣的盲點（模型能檢查模型嗎）。

Anthropic 的建議也一致：「我們建議盡量選確定性的評分器，必要時，或需要額外彈性時，才用 LLM 評分器。」（Demystifying evals for AI agents）我自己也是這樣做的。答案能在檔案裡檢查的地方，我就用腳本，模型評分器只留給腳本看不到的少數東西。這裡的實驗沒有模型評分器。

先證明評分器是對的

不管用哪一種，評分器都是程式，而程式會有 bug。什麼都放行的評分器，會讓每個改動看起來都無害；什麼都擋的評分器，會讓每個改動看起來都有害。所以在相信任何分數之前，我先測評分器。我的實驗有一個自我測試，分三部分：

  • 沒動過的倉庫，必須每個任務都失敗（什麼都沒做）。
  • 手寫的正確答案，必須每個任務都通過。
  • 正確答案的壞版本，必須全部被抓到。有 23 個，每個有一個錯誤，例如少了一行登記，或欄位錯了。評分器放過一個，評分器就是錯的。

最小的版本是一個好答案，加上一個你手動弄壞的答案：評分器必須放行第一個、抓到第二個。我的實驗做這一步花了一個下午。這正是大家會跳過的部分，可我能說「一項失敗是有意義的」，靠的也是它。

讀失敗的運行

就算評分器測過了，它也只能告訴你有東西失敗了，說不出為什麼。所以就算有腳本，我也一直守著一個習慣：一次運行失敗，我會打開它，讀發生了什麼。失敗的原因可能是三種很不一樣的事。可能是 agent 真的犯了錯，這正是評測要找的；可能是評分器錯了，結果其實是對的，只是形式不是腳本預期的；也可能是任務不清楚，兩個答案都講得通，要求卻沒有說是哪一個。

三種裡只有第一種，才告訴你 agent 的事。如果你把每個失敗都當成這一種，你會丟掉好的改動、留下壞的。Anthropic 是這麼說的：「讀對話紀錄，是你驗證評測量的是不是真正重要的東西的辦法。」（同一篇文章）

所以腳本不取代親自去看。它省掉的，是把每次運行都看一遍的功夫。該細看哪幾次，交給腳本來挑。它挑出失敗的運行，這就是它對該看哪裡的猜測，人再去讀這幾次。

你的任務和公開的基準測試

你也許會問，既然有公開的任務，為什麼還要自己建一套？基準測試（benchmark）是一組公開的任務，對每個人用同樣的方式打分，讓模型可以互相比較。它只對一個問題有用：這個模型在別人的任務上表現如何？另一個問題它回答不了：我對我的設定做的改動，在我的工作上有沒有幫助？要回答這個，需要來自你的倉庫、帶著你的規則的任務，例如我的實驗裡那個受保護的檔案。這就是我自己建的原因。

這個選擇也有代價。自己建的一組任務很小，又只屬於我自己。它還會過期：倉庫一變，任務也得跟著變。

我的 harness 今天怎麼做

前面講的都是實驗。我的 harness 本身做得比較少。在我的設定裡有幾個固定情境，每一個是一個 prompt 加上預期的結果，也就是日誌裡必須出現的幾個呼叫（例如一次拒絕），和必須變或不能變的幾個檔案。我在 Copilot 裡手動把一個情境跑一遍，再由一個檢查讀日誌和檔案，說有沒有做對。

它現在還做不到的，是批次執行。寫這段的時候（2026 年 10 月），在我自己的設定裡，我看到 Copilot 的非互動模式不會執行 hook，所以我沒辦法批次跑這些情境，在真實任務上做前後比較也還沒做。這一章講的有打分、可重複的比較，我只在這個倉庫的實驗裡用數字做過。日常用的時候，就是手動跑一個情境，再看它留下的日誌。

自己跑

想在自己動手之前，先看看這一切怎麼運作，可以從這個實驗開始。它就是 慎用子 agent 裡那些數字背後的測試，包括虛構的倉庫、四個任務和評分腳本。它們都適用於任何 agent 工具。labs/subagents/ 說了怎麼先跑自我測試，再跑你自己的比較。看懂怎麼運作之後，把任務換成你自己的。

測你自己的設定

不管跑不跑這個實驗，在 agent 設定上做任何改動之前，都值得先問三個問題：

  1. 如果這個改動有幫助，我會看到什麼？如果沒有，又會看到什麼？
  2. 腳本分得出這兩種嗎？
  3. 腳本自己有沒有通過「沒動過、正確、壞掉」的測試？

不用任何工具，也能先小小地開始。挑三個你和 agent 做過的任務，為每一個寫下你預期最後會有的檔案，和一個你見過的錯誤，再寫一個短腳本檢查這些檔案。（如果你的工作不是程式碼，就檢查輸出：表格的欄位、列數、總和。）在一個好結果和一個你手動弄壞的結果上各跑一次。它抓到壞的、放行好的，你就有一個評測了。它很小，但下次你改規則時，就可以用它。

怎样搭一个信得过的评测

图里画的就是这个方法：固定任务，改动前后各跑一遍，脚本给两边打分，再由人去读失败的运行。

好任务长什么样

方法从任务开始，但并不是每个任务都适合做评测。我看三点。

  1. 它是真的。它该像 agent 平时替你干的活，而不是考试题，所以如果你只加 pipeline、修公式，就别去测写诗。一个改动只在编出来的活上有用，在你的活上没用，什么也教不了你。
  2. 它有一个能检查的正确答案。“加一条 pipeline”可以检查：五个文件存在，位置对，彼此一致。“把代码写得更好看”就不行。如果两个讲道理的人对结果对不对会有分歧，脚本就没法打分。
  3. 它覆盖人真正会犯的错。好的一组任务里有简单的，也得有陷阱。在我的实验里，有一个任务要 agent 去改一个规则禁止它改的文件，好结果是拒绝。放这个任务，是因为真实的需求就可能这么要求，而听话照做的 agent 就是做错了。

我实验里的四个任务从小到中等：加一条 pipeline；把一个字段沿三条 pipeline 往下游传（其中一个字段中途改了名）；跨领域给一条 pipeline 改名并删掉旧文件；修一个在两处都有的公式，而需求同时要求改一个受保护的文件。四个任务确实很少，这对结果意味着什么，后面再说。

这类任务还分两种，失败的含义也不一样。能力任务检查配置还做不到的事，所以一开始你预期它常常失败。回归任务检查已经能做的事，所以你预期它每次都通过，一旦失败，就说明某个改动把它弄坏了。两种要有意混在一起，但通过率得分开解读。

这些任务底下的仓库是编出来的（93 个文件，5 个领域），也跑不起来。这是有意的选择。正因为正确答案事先就知道，脚本才能判断哪个结果对，用不着谁去运行代码来确认。

看结果，还是看过程？

任务有了，打分器该看什么？它可以看结果，也就是 agent 留下的文件，比如那五个文件加了没有、注册表里有没有新的 pipeline、受保护的文件是不是没动。它也可以看过程，也就是 agent 是怎么做到的，比如它有没有被拒绝过，计划还没审批时它有没有往某个地方写过东西。

大多数任务，给结果打分。通向正确答案的有效路径通常有很多条，所以死咬一条路径的打分器，会把好的活判成错的。只有当过程本身就是你在意的东西时，才给过程打分，比如“计划审批之前，规则会拒绝写入”。在我的 harness 里，这类场景要同时看两样东西：日志里有那次拒绝，文件也没变，两样都对上才算通过。没有日志就无从检查，这就是为什么要先记录每一次调用。

在我实验的打分里，结果是一张清单。有些项对每个任务都一样，检查仓库是不是仍然自洽（文件有效、每条 pipeline 都有它的五个文件、字段一致、受保护的区域没动）。有些项只属于某一个任务，检查需求本身做完了没有。还有一项检查范围，看是不是只有该改的文件被改了。每一项都通过，任务才算通过。

这样打出来的分是全有或全无。如果你想在长任务里看到进展，就分部分打分（给部分分），并分别报告各部分。我没有拆，因为对这样的短任务来说，错一项通常就意味着结果是错的。

用脚本还是用模型打分

还有一个问题：由谁、或者由什么来打分？脚本读文件，回答通过或不通过；模型可以读结果，给出判断。两者各有弱点。

脚本便宜、快，每次答案都一样。它的弱点是脆。因为它只认一种特定的写法，有效的结果也可能被它判错，而这类情况只有读失败的运行才能发现。模型打分器能接受有效的变体，也能判断脚本判断不了的东西，比如一段解释清不清楚。但它的答案可能每次运行都不一样，还可能和被它打分的 agent 有同样的盲点（模型能检查模型吗）。

Anthropic 的建议也是这样：“能用确定性的打分器就用，必要时，或者为了更灵活，再用 LLM 打分器。”（Demystifying evals for AI agents）我自己也是这么做的。凡是答案能在文件里查出来的，我就用脚本，模型打分器只留给脚本看不到的少数事情。这里的实验没有用模型打分器。

先证明打分器靠谱

不管用哪一种，打分器都是程序，而程序会有 bug。什么都放过的打分器，会让每个改动看起来都无害；什么都判失败的打分器，会让每个改动看起来都有害。所以在信任任何分数之前，我先测打分器。我的实验有一个自测，分三部分：

  • 没动过的仓库，必须每个任务都不通过（什么都没做）。
  • 手写的正确答案，必须每个任务都通过。
  • 正确答案的破坏版本，必须全部被抓出来。一共 23 个，每个带一处错误，比如少了一行注册表，或者字段写错了。只要打分器放过一个，打分器就是错的。

最小的版本是一个好答案，加一个你亲手弄坏的答案：打分器必须放过前者、抓住后者。我的实验做这一步花了一个下午。这是人最爱跳过的一步，可我能说“失败的一项是有意义的”，靠的也正是它。

去读失败的运行

就算打分器测过了，它也只能告诉你有东西失败了，说不出为什么。所以哪怕有了脚本，我也一直守着一个习惯：一次运行失败了，我就打开它，读发生了什么。失败的原因，可能是三种很不一样的情况。可能是 agent 真的犯了错，评测本来就是为这个设的；可能是打分器错了，结果其实是对的，只是形式不是脚本预期的；也可能是任务不清楚，两种答案都说得通，需求却没说要哪一种。

三种里只有第一种，才能告诉你 agent 的情况。如果你把每次失败都当成这一种，就会丢掉好的改动、留下坏的改动。Anthropic 是这么说的：“读 transcript，才能确认你的评测衡量的是真正重要的东西。”（同一篇文章）

所以脚本并不能取代亲自去看。它省掉的，是把每次运行都看一遍的功夫。该细看哪几次，交给脚本来挑。它挑出失败的运行，这就是它对该看哪里的猜测，人再去读这几次。

你自己的任务和公开的基准

你也许会问，既然有公开的任务，为什么还要自己搭一套？基准（benchmark）是一组公开的任务，对所有人用同样的方式打分，好让模型之间可以比较。它只适合回答一个问题：这个模型在别人的任务上表现如何？另一个问题它回答不了：我对自己配置做的改动，在我的活上有没有用？要回答这个，你需要来自你仓库的任务，里面带着你自己的规则，比如我实验里那个受保护的文件。这就是我自己搭一套的原因。

这个选择也有代价。自己搭的一套任务很小，又只属于我自己。它还会过期：仓库一变，任务也得跟着变。

我的 harness 现在做到哪一步

前面说的都是实验。我的 harness 本身做得要少一些。在我的配置里，有几个固定的场景。每个场景是一个 prompt 加上预期结果，也就是日志里必须出现的几次调用（比如一次拒绝），和必须改或不能改的几个文件。我在 Copilot 里手动跑一次场景，再由一个检查读日志和文件，告诉我做得对不对。

它现在还做不到的，是批量运行。写作时（2026 年 10 月），我在自己的配置里看到，Copilot 的非交互模式不运行 hook，所以我没法批量跑这些场景，在真实任务上做改动前后的对比也还没做。本章讲的这种带打分、可重复的对比，我只在这个仓库的实验里用数字做过。日常用的时候，就是手动跑一个场景，再看它留下的日志。

自己跑一遍

想在自己动手之前先看看这一切怎么运转，可以从这个实验开始。它就是慎用子 agent里那些数字背后的测试，包括编出来的仓库、四个任务和打分脚本。它们都适用于任何 agent 工具。labs/subagents/讲了怎么先跑自测，再跑你自己的对比。看明白怎么用之后，把任务换成你自己的任务。

测你自己的配置

不管跑不跑这个实验，对 agent 配置做任何改动之前，都值得先问三个问题：

  1. 如果这个改动有用，我会看到什么？如果没用，又会看到什么？
  2. 脚本能把这两种情况区分开吗？
  3. 脚本本身通过了“没动过的、正确的、被弄坏的”这三项测试吗？

不用任何工具，也能先小小地起个步。挑三个你用 agent 做过的任务，给每一个写下你预期最后会有的文件，和一个你见过的错误，再写一个短脚本检查这些文件。（如果你的工作不是代码，就检查输出：表的列、行数、合计。）用它跑一个好结果，再跑一个你手动弄坏的结果。如果它抓住了坏的、放过了好的，你就有了一个评测。它很小，但下次改规则的时候，就可以用上它。

What a small eval cannot tell you, and what it costs

How far can an eval this small take you? Most of its limits come from the tasks. Four tasks are a thin base. Mine suggested a gap of four to six times, but they would not show a gap of ten percent. Nor can they cover what you did not think of, so add a task each time a real failure surprises you. The tasks can also mislead you in two quieter ways. If you tune the setup until they pass, you have measured how well you fit those four tasks, so keep some tasks aside that you do not tune against. And once every setup passes every task, the tasks have saturated. In Anthropic's words, "Eval saturation occurs when an agent passes all of the solvable tasks, leaving no room for improvement." An eval in that state can no longer tell the setups apart, so add harder tasks.

Other limits sit in the score. The first is that a static score does not run the code. My grader reads files, so it cannot say that the code works. For work where running matters, the grader has to run the tests (Let the agent check its own work). The second is that a score is only as fair as the runs behind it, so tasks must not share state. Start every run from the same clean copy. If one run leaves files, caches or a changed setting behind, the next run is not a fair test, because the score measures the leftovers.

Then there is the bill: running costs money and time. In my lab, the team took about 16 minutes and about 456 AI credits to do the four tasks once. Prompt caching changes the sum, since on Anthropic's API a cached read costs about a tenth of the base price (Models and cost), but I have not checked how Copilot bills it. A set of ten tasks, run several times on two setups, is a real bill. Decide before you start what you will do with the answer. (As "What my harness does today" explains, in my setup real work cannot be run in a batch for this.)

Last, one run is thin. My results are one run per task, and the next chapter says how to run more and how to report what you find.

小評測看不出的東西，和它的成本

這麼小的評測，能靠它走多遠？它的限制大多出在任務上。四個任務的底子很薄。我這四個提示了四到六倍的差距，可要是只差百分之十，就看不出來了。你沒想到的情況，它們也涵蓋不了，所以每次有真實的失敗讓你意外，就加一個任務。任務還會用兩種不那麼顯眼的方式誤導你。一種是你一直改設定，直到任務通過，這時量到的其實是設定和這四個任務貼合得多緊，所以要留一些不拿來調的任務。另一種是問題反過來，任務太容易了：每種設定都通過每個任務，任務就飽和了。用 Anthropic 的話說：「當 agent 通過所有可解的任務，沒有留下任何進步空間，就是評測飽和。」到了這一步，評測就分不出各種設定了，這時該加更難的任務。

另一些限制出在分數上。其一，靜態的分數不執行程式碼。我的評分器讀檔案，所以沒辦法說程式碼能不能用。對執行很重要的工作，評分器得去跑測試（讓 agent 能檢查自己的活）。其二，分數公不公平，還要看背後的運行公不公平，所以任務之間不能共用狀態。每次運行都要從同一份乾淨的副本開始。如果一次運行留下了檔案、快取或改過的設定，下一次運行就不是公平的測試，因為分數量到的是殘留的東西。

然後是帳單：運行要花錢，也要花時間。在我的實驗裡，團隊把四個任務做一遍，大約 16 分鐘、大約 456 個 AI credits。prompt 快取會改變總額，在 Anthropic 的 API 上，快取讀取大約是基本價格的十分之一（選模型：算的是每次成功的成本），但 Copilot 怎麼計費，我沒查過。十個任務，在兩種設定上各跑幾次，就是一筆實實在在的開銷。開始之前，先決定你拿到答案要做什麼。（前面「我的 harness 今天怎麼做」說過，在我的設定裡，真實的工作沒辦法為此批次跑。）

最後，一次運行很薄。我的結果是每個任務只有一次運行，下一章 說怎麼跑更多次、怎麼報告你發現的東西。

小评测看不出的东西，和它的开销

这么小的评测，能靠它走多远？它的局限大多出在任务上。四个任务的底子很薄。我这四个提示了四到六倍的差距，可要是只差一成，就看不出来了。你没想到的情况，它们也覆盖不了，所以每次遇到出乎意料的真实失败，就加一个任务。任务还会用两种不那么显眼的方式误导你。一种是你不停改配置，直到任务通过，这时量到的其实是配置对这四个任务拟合得有多好，所以要留一些不拿来调优的任务。另一种是问题反过来，任务太容易了：每种配置都通过每个任务，任务就饱和了。用 Anthropic 的话说：“评测饱和，是指 agent 通过了所有可解的任务，再没有改进的余地。”到了这一步，评测就分不出各种配置了，这时该加更难的任务。

另一些局限出在分数上。其一，静态打分不运行代码。我的打分器读文件，所以没法说代码能不能跑。对运行结果要紧的活，打分器得去跑测试（让 agent 能检查自己的活）。其二，分数公不公平，还要看背后的运行公不公平，所以任务之间不能共享状态。每次运行都要从同一份干净的副本开始。如果某次运行留下了文件、缓存或改过的设置，下一次运行就不是公平的测试，因为分数量到的是残留物。

然后是账单：运行要花钱，也要花时间。在我的实验里，团队把四个任务做一遍，约 16 分钟、约 456 AI credits。prompt 缓存会改变这笔账，在 Anthropic 的 API 上，命中缓存的读取约是基础价格的十分之一（选模型：看每次成功的成本），但我没有查过 Copilot 怎么计费。十个任务，在两种配置上各跑好几次，就是一笔实在的账单。动手之前，先想好答案出来后你打算拿它做什么。（前面“我的 harness 现在做到哪一步”说过，在我的配置里，真实的工作没法为此批量运行。）

最后，一次运行很单薄。我的结果是每个任务只跑了一次，下一章讲怎么多跑几次，以及怎么汇报你发现的东西。

When to delete the scripts, and why the tasks stay Industry practice

The scripts and the habit of running by hand exist because I have no built-in way to run a setup through a fixed set of tasks and compare. If a platform adds that, with logs and scoring, I would use it and drop my glue.

The fixed tasks do not retire with the scripts. Whenever a model is upgraded, a rule is added or a prompt is rewritten, that is a change, and it raises the same question again: did the change help? The fixed tasks are there to answer it (When the model is upgraded). A task retires when every setup passes it. I would look again at the lab's four tasks if they stopped telling the setups apart.

什麼時候刪掉腳本，任務為什麼要留著 業界做法

這些腳本和手動跑的習慣之所以存在，是因為我沒有內建的辦法，讓一種設定跑一組固定任務並比較。如果平台加了這個功能，有日誌也有打分，我會用它，把自己拼湊的膠水程式丟掉。

固定任務卻不會跟著腳本一起退役。模型升級、加一條規則、重寫一個 prompt，都是改動，每一次都會把同一個問題再問一遍：這個改動有沒有幫助？固定任務就是用來回答它的（模型升級了，就要刪）。一個任務在每種設定都通過它的時候才退役。如果實驗裡的四個任務不再分得出各種設定，我會重新檢視它們。

什么时候删掉脚本，任务为什么要留着 业界做法

这些脚本和手动运行的习惯之所以存在，是因为我没有内置的办法，把一套配置放到一组固定任务上跑一遍再比较。如果哪个平台加了这个功能，带日志和打分，我会用它，把自己的胶水代码丢掉。

固定任务却不会跟着脚本一起退休。模型升级、加一条规则、重写一个 prompt，都是改动，每一次都会把同一个问题再提一遍：这个改动有没有用？固定任务就是用来回答它的（模型升级了，就要删）。一个任务只有在每种配置都能通过时才退休。如果实验里这四个任务不再能区分各种配置，我会重新审视它们。
