The Knowledge經驗分享经验分享

In one sentence

A hook is code the platform runs at fixed points in every turn, including inside subagents. It is where hard rules live, though it sees calls, not what a command does once it runs.

一句話

hook 是平台在每一輪的固定位置執行的程式碼，子 agent 裡面也一樣。硬規則就放在這裡，不過它看到的是呼叫，不是指令執行起來會做什麼。

一句话

hook 是平台在每一轮的固定位置运行的代码，子 agent 里也一样。硬性规则就放在这里，不过它看得到的是调用，看不到命令运行起来之后做了什么。

For leaders

  • The decision: decide which rules must hold every time, and put those in a hook (code the platform runs on every tool call) rather than in a prompt.
  • The risk: a hook sees the text of a call, not what a command does once it runs, and it can fail quietly. In Copilot as I saw it in October 2026, a hook that times out counts as a pass, while one that cannot start blocks every tool. In one small batch on one machine, about a third of prompts reached the model without the rules a hook was meant to add. Read that as "a lot", not as a rate.
  • The cost of doing it right: one small program and one configuration file, kept under code review. Mine normally runs in a few dozen milliseconds.
  • Ask the team: "What happens to our rules when the hook is slow or broken, and how do we know the model actually received them?"

給主管

  • 要做的決定：決定哪些規則必須每次都成立，把它們放進 hook（平台在每次工具呼叫時執行的程式碼），而不是寫在 prompt 裡。
  • 風險：hook 看到的是呼叫的文字，不是指令執行起來會做什麼，它也可能悄悄失效。依我 2026 年 10 月看到的 Copilot，逾時的 hook 算通過，啟動不了的 hook 則會擋掉所有工具。在一台機器上的一小批樣本裡，大約三分之一的 prompt 到達模型時，沒有帶著 hook 本來要加上的規則。這個數字讀成「很多」就好，不要當成比率。
  • 做對的成本：一個小程式和一個設定檔，放在程式碼審查之下。我的通常在幾十毫秒內執行完。
  • 可以問團隊：「hook 很慢或壞掉的時候，我們的規則會怎樣？我們怎麼知道模型真的收到了它們？」

写给管理者

  • 要拍板的事：决定哪些规则必须每次都成立，把它们放进 hook（平台在每次工具调用时运行的代码），而不是写在 prompt 里。
  • 风险：hook 看到的是调用的文本，看不到命令运行起来之后做了什么，它也可能悄悄失效。按我在 2026 年 10 月看到的 Copilot，超时的 hook 算通过，启动不了的 hook 则会挡住所有工具。在一台机器上的一小批 prompt 里，约三分之一送到模型时没有带上 hook 本该加进去的规则。这个数理解为“不少”就好，别当成比率。
  • 做对的代价：一个小程序，加一个配置文件，放在代码审查之下。我的通常几十毫秒就跑完。
  • 可以问团队：“hook 慢了或者坏了，我们的规则会怎么样？我们怎么知道模型真的收到了它们？”

What makes a rule hold every time?

You write a rule: "never edit files in the config folder". The agent follows it nine times. On the tenth it is deep in a task, the context is long and the rule is far away, so it edits the file. It can do that because the rule was only a sentence, one the model could weigh against all the other sentences. This time it weighed it lower.

What you need, then, is something that does not depend on the model's memory or mood: a piece of code that every tool call must pass and that says yes or no. That is a hook.

More exactly, a hook is a small program that you write and the platform runs for you at fixed moments. Each time, the platform hands it a piece of JSON (a plain text format for data) that says what is happening, such as "the agent wants to run this command". The hook answers, also in JSON, which the platform then acts on. It is the platform that runs the hook, not the model, so the model cannot skip it.

My first lesson about hooks, though, came from one that did not work. I used a hook to put the harness's rules in front of the model at the start of each prompt. On the surface it worked, since it ran every time and its output looked right. Yet when I looked at what the model had actually received, in a small batch of prompts on one machine in October 2026, about a third had no rules in them (I did not keep the exact count, so read "a third" as "a lot", not as a rate). The hook had returned the right answer, and still nothing had happened. The cause turned out to be VS Code itself, which adds its own reminders to a prompt. Those reminders took the one slot the hook used. I fixed it by adding a second check at the last point before the text goes to the model. The whole text is visible there, so the check can put the rules back if they are missing.

That lesson holds for every hook: check what the model really received, not what the hook returned. And if a hook that ran every time could still fail like this, it is worth knowing exactly what a hook can do, how else it fails, and what it cannot see at all.

怎樣讓一條規則每次都成立？

你寫了一條規則：「絕不要改設定資料夾裡的檔案」。agent 遵守了九次。到了第十次，它正埋頭做一個任務，上下文已經很長，那條規則離得很遠，於是它改了那個檔案。會這樣，是因為規則只是一句話，模型可以把它和其他句子放在一起權衡。這一次，它把這句話看得比較輕。

所以你需要的，是一樣不靠模型的記憶、也不看模型心情的東西：一段每次工具呼叫都必須經過、而且會說「可以」或「不行」的程式碼。這就是 hook。

hook 是你寫的小程式，由平台在固定的時刻替你執行。每到一個時刻，平台就交給它一段 JSON（一種表示資料的純文字格式），說明正在發生什麼事，例如「agent 想執行這個指令」。hook 也用 JSON 回答，平台再依照這個答案行動。執行 hook 的是平台，不是模型，所以模型沒辦法跳過它。

不過，我在 hook 上學到的第一課，正好來自一個沒有作用的 hook。我用它在每個 prompt 開頭，把 harness 的規則放到模型面前。表面上看它好好的，每次都執行了，輸出看起來也對。可是等我去看模型實際收到什麼，2026 年 10 月在一台機器上的一小批 prompt 裡，大約三分之一根本沒有規則（確切的數字我沒有留，所以「三分之一」讀成「很多」就好，不要當成比率）。hook 回傳的答案沒錯，卻什麼也沒發生。後來查清楚，問題出在 VS Code 自己：它會在 prompt 裡加上自己的提醒，這些提醒占掉了 hook 用的那個位置。我的修法，是在文字送給模型之前的最後一關，再檢查一次。那裡看得到整段文字，規則如果不在，就把它們補回去。

這一課適用於每個 hook：要檢查模型真正收到什麼，而不是 hook 回傳什麼。既然一個每次都執行的 hook 也會這樣失效，就值得弄清楚 hook 到底能做什麼、還會怎樣失效，以及有哪些東西它根本看不到。

怎样让一条规则每次都成立？

你写了一条规则：“永远不要改配置文件夹里的文件”。agent 遵守了九次。到了第十次，它正埋头在一个任务里，上下文已经很长，那条规则离得很远，于是它改了那个文件。之所以会这样，是因为规则只是一句话，模型会把它和别的话放在一起掂量。这一次，它掂量得轻了。

所以你需要的，是一样不靠模型记性、也不看模型心情的东西：一段每次工具调用都必须经过、并且会说行或不行的代码。这就是 hook。

hook 是你写的一个小程序，由平台在固定的时机替你运行。每到一个时机，平台交给它一段 JSON（一种表示数据的纯文本格式），说明正在发生什么，比如“agent 想运行这条命令”。hook 同样用 JSON 回答，平台再按这个回答行事。运行 hook 的是平台，不是模型，所以模型跳不过它。

不过，我在 hook 上学到的第一课，恰恰来自一个没起作用的 hook。我用它在每个 prompt 开头把 harness 的规则放到模型面前。表面上看它好好的，每次都运行了，输出看着也对。可是等我去看模型实际收到了什么，2026 年 10 月在一台机器上的一小批 prompt 里，约有三分之一根本没有规则（确切的数我没有记下来，所以“三分之一”理解为“不少”就好，别当成比率）。hook 返回的答案没错，却什么也没发生。后来查明，问题出在 VS Code 自己：它会往 prompt 里加自己的提醒，这些提醒占掉了 hook 用的那个位置。我的修法是在文本送到模型之前的最后一道关口，再检查一次。那里能看到全部文本，规则要是不在，就把它们补回去。

这个教训对每个 hook 都适用：要检查模型实际收到了什么，而不是 hook 返回了什么。既然一个每次都运行的 hook 也会这样失效，那就值得弄清楚，hook 到底能做什么，还会怎样失效，又有哪些东西它根本看不到。

What can a hook do, and what can it not?

When a hook runs

A hook runs only at the moments the platform offers. The ones I use are below, with the names VS Code gives them in its docs.

Moment What happens What I use it for
A session starts A new chat begins Give the model the session's basic facts
A prompt is sent You press Enter Add the rules; note which task this is
Before a tool call The model asked; nothing has run Refuse a call. Every hard rule is here
After a tool call The tool ran Keep a record; add a note
A subagent starts or stops A helper agent begins or ends Hand it its package; record the end
The agent is about to stop The model wrote an answer Say "not yet", once, if work is open

Of these, only the moment before a tool call can refuse one specific action. A rule needs a call that exists but has not happened yet, and this is the only moment that has one. The other moments can watch, record and add words. (The stop moment can also say "not yet", as described below, but that is not a refusal of an action.) If you want to see these moments for yourself, the small test at the end of this section shows them.

What goes in and what comes out

What does the hook actually get at one of these moments? It receives JSON that says which event this is and which session, plus, for a tool call, the tool name and its arguments. Here is a real sample, recorded from VS Code, of what a hook is given after a command has run:

The hook answers in JSON too, and there are really only three useful answers:

  • Let it through. An empty answer counts as no opinion, and the platform's normal permission checks still apply.
  • Refuse, with a reason. The call does not run, and the reason is shown to the model and to you.
  • Add a few words for the model to read, such as a reminder or a status line.

At the stop moment there is a fourth, which is to block the stop with a reason that is fed back to the model as if it were a new prompt. I allow this once per stop, because a hook that blocked every stop would keep the agent running for ever, with you paying for every turn.

The reason is part of the design. A refusal should say why the call was refused and what to do instead, or the agent tries the same thing again, or something worse (Asking is not a limit).

Three ways a hook goes wrong

All of this assumes the hook works. A hook is software, though, so it will fail, and what the platform does then decides whether your rule is a fence or a decoration.

What happens What Copilot does (as I observed it in October 2026, and as the VS Code docs say)
The hook runs and refuses The call is stopped, the reason is shown. This works in the default mode and in the modes that skip permission prompts.
The hook cannot start (for example, the language it is written in is not installed) Treated as a refusal: no tool can run, and the screen says little more than "hook errored".
The hook takes too long Treated as a pass, silently. The VS Code docs describe it as falling through to normal permissions.

So the same failure can lock you out or leave the door open, depending on how it fails. Which of the two you would rather have is a design choice. Enforcement design is about how to make it. It also describes the choice I made: let the call through and log the error, and warn when the slowest recent call nears the time limit.

Inside subagents

A subagent is a second agent started for a piece of the work (Use subagents sparingly). Because it runs in its own session, you might expect it to be out of reach of the hooks. In Copilot today it is not, since its tool calls go through the hooks as well, with the event carrying the id of the parent session. So a rule set for the main agent also holds for the helpers it starts. I have not tested other platforms, so I would not assume it there.

What a hook cannot see

So far this has been about what a hook does. What it cannot see is the part I most want you to remember.

It sees calls, not effects. For a terminal command, the hook reads the text of the command, so it can see "write to this path". It cannot see a path built from variables, or a script that was written a minute ago and is only run now. Once the command is let through, the hook is out of the picture. A hook on terminal commands therefore stops the common spellings, but not an agent set on getting around it. The VS Code docs say the same: hooks are executable code and not a substitute for enforced permissions or sandboxing. For things that must never be touched, then, do not rely on the hook alone (Least privilege).

Even for the calls it does see, a hook does not know which agent is making them. In Copilot today the event does not carry the name of the main agent, so "this agent is allowed to" cannot be a rule, because any agent could pass for it. If rights must differ, they have to come from something the agent cannot set, such as a switch the person turns on in a terminal.

Some calls it never sees at all, because a hook does not run everywhere. In my measurements, the repository's hooks did not run when I used the command-line mode of Copilot (no window), and a setting that looks like an off switch did not stop them in the newer sessions. A company policy can also turn hooks off for a workspace, and even a change to the hook file takes effect only after a reload, because the file is read when the window starts. These are the facts as I found them in October 2026, and they will change, so look at the platform's current docs.

Finally, even when a hook runs and answers, its message can be lost. That is the story at the top of this chapter, where output from a hook may never reach the model. So test the delivery, not only the hook.

Other things that stand in the loop

Is a hook, then, the only thing that stands between the model and the world? It is not. A wrapper (a small program you call instead of the raw command), an MCP server (MCP) and a proxy between the platform and the model all stand there too. But each of them sees only what is routed through it, and the agent can route around them. What sets the hook apart is that the platform promises to call it. For the built-in tools and for subagents I saw every call pass through it, although I have not tested MCP tools.

Three questions and a small test

To put this to work on your own setup, ask three questions about any rule you care about.

  1. Is it written in a prompt, or in a hook? If it is in a prompt, it is a request.
  2. What does the hook see when the rule is broken? The call text, or the effect?
  3. What happens when the hook itself breaks or is slow?

There is also a test you can run today. Write the smallest hook your platform allows, one that only appends the event name and the tool name to a file. Use your agent for a small task, then read the file. You will see every moment in the table above, in order, and how many there are, which makes it the quickest way to understand the loop. Follow the VS Code hooks docs for the file format.

hook 能做什麼，做不到什麼？

hook 在什麼時候執行

hook 只在平台提供的時刻執行。下面是我用的那幾個，名字是 VS Code 在它的文件裡給的。

時刻 發生什麼 我拿它做什麼
會話開始 新的對話開始 把這個會話的基本事實給模型
送出 prompt 你按了 Enter 加上規則；記下這是哪個任務
工具呼叫之前 模型提出了要求；什麼都還沒執行 拒絕一次呼叫。每條硬規則都在這裡
工具呼叫之後 工具已經執行了 留下紀錄；加一則備註
子 agent 開始或結束 幫手 agent 開始或結束 把它要的那一包材料交給它；記下結束
agent 快要停下來 模型寫出了回答 還有工作沒做完，就說一次「還沒」

這些時刻裡，只有工具呼叫之前這一個能拒絕某個具體的動作。一條規則需要的，是一個已經存在、卻還沒發生的呼叫，只有這個時刻才有。其他時刻能看、能記錄，也能加一些文字。（停止的時刻也可以說「還沒」，下面會講，但那不是在拒絕一個動作。）想親眼看到這些時刻，可以做這一節結尾的那個小測試。

hook 也用 JSON 回答。真正有用的答案其實只有三種：

  • 放行。空的答案算沒意見，平台正常的權限檢查照樣適用。
  • 拒絕，附上原因。這次呼叫不會執行，原因會顯示給模型，也顯示給你看。
  • 加幾句話給模型讀，例如一則提醒、一行狀態。

到了停止的時刻，還有第四種：擋下這次停止，附上一個原因，這個原因會像新的 prompt 一樣餵回給模型。我每次停止只允許這樣做一次，因為每次停止都擋的 hook，會讓 agent 永遠跑下去，每一輪還都要你付錢。

原因是設計的一部分。拒絕的時候要寫清楚為什麼不行、該改做什麼，不然 agent 會再試同一件事，甚至做出更糟的事（詢問不是限制）。

hook 出錯的三種方式

上面說的這些，前提都是 hook 本身沒問題。可是 hook 也是軟體，總會出錯。出錯的時候平台怎麼處理，決定了你的規則是圍欄，還是裝飾。

發生什麼 Copilot 怎麼做（我在 2026 年 10 月觀察到的，也是 VS Code 文件說的）
hook 執行了並拒絕 呼叫被擋下，原因顯示出來。在預設模式，以及跳過權限提示的模式下都有效。
hook 啟動不了（例如寫它用的語言沒裝） 當成拒絕：沒有任何工具能執行，畫面上也只說「hook 出錯」之類的話。
hook 花太久 當成通過，而且沒有任何通知。VS Code 文件說，它會退回到正常的權限檢查。

所以同一種失敗，可能把你鎖在外面，也可能讓門開著，就看它是怎麼失敗的。你寧可要哪一種，是設計上的選擇。這個選擇該怎麼做，把執行層當軟體來設計 裡有講。那裡也寫了我的選擇：放行這次呼叫並記錄錯誤，最近最慢的一次呼叫接近時間上限時發出警告。

在子 agent 裡面

子 agent 是為了一部分工作而啟動的第二個 agent（慎用子 agent）。它在自己的會話裡執行，你也許會以為 hook 就管不到它了。其實在今天的 Copilot 裡，它的工具呼叫一樣會經過 hook，事件裡還帶著父會話的 id。所以為主 agent 設的規則，對它啟動的幫手也成立。別的平台我還沒測過，所以換了平台，我不會這樣假設。

hook 看不到什麼

hook 看不到什麼，是這一章裡我最希望你記住的部分。

它看到的是呼叫，不是效果。對終端機指令，hook 讀的是指令的文字，看得到「寫入這個路徑」。可是它看不到用變數拼出來的路徑，也看不到一分鐘前才寫好、現在才執行的腳本。指令一旦被放行，hook 就不在畫面裡了。因此終端機指令上的 hook，擋得住常見的寫法，卻擋不住一個一心要繞過它的 agent。VS Code 文件也這麼說：hook 是可執行的程式碼，不能代替強制的權限或沙箱。那些絕不能被碰的東西，就不要只靠 hook（有些東西根本不給）。

就算是它看得到的呼叫，hook 也不知道是哪個 agent 發出的。在今天的 Copilot 裡，事件不帶主 agent 的名字，所以「這個 agent 被允許」不能成為規則，因為任何 agent 都可以冒充它。如果權限必須有所不同，就得來自 agent 自己設不了的東西，例如由人在終端機裡打開的開關。

還有一些呼叫，hook 根本看不到，因為它並不是到處都會執行。在我的測量裡，用 Copilot 的命令列模式（沒有視窗）時，倉庫的 hook 沒有執行；一個看起來像關閉開關的設定，在較新的會話裡也沒能擋住它們。公司的政策也可以為一個工作區關掉 hook，就連改了 hook 檔，也要重新載入才會生效，因為這個檔案是在視窗啟動時讀的。這些是我 2026 年 10 月找到的事實，它們會變，所以請看平台目前的文件。

最後，就算 hook 執行了、也給了回答，它的訊息還是可能丟掉。這就是開頭那個故事：hook 的輸出可能永遠到不了模型。所以要測的是訊息有沒有送達，而不只是 hook 本身。

迴圈裡其他站著的東西

那麼，站在模型和外面世界之間的，只有 hook 嗎？並不是。包裝器（你呼叫來代替原始指令的小程式）、MCP server（MCP server：插工具的標準接口），以及平台和模型之間的代理，也都站在那裡。但它們每一個都只看得到經過自己的東西，agent 可以繞過它們。hook 的不同在於，平台保證會呼叫它。內建工具和子 agent，我看過每次呼叫都經過它，不過 MCP 工具我沒有測過。

三個問題和一個小測試

想把這些用在你自己的設定上，可以對任何一條你在乎的規則問三個問題。

  1. 它是寫在 prompt 裡，還是 hook 裡？如果在 prompt 裡，它就是請求。
  2. 規則被破壞時，hook 看到什麼？呼叫的文字，還是效果？
  3. hook 自己壞掉或很慢的時候，會怎樣？

另外還有一個今天就能跑的測試。寫出你的平台允許的最小 hook，它只做一件事，把事件名稱和工具名稱附加到一個檔案裡。然後用你的 agent 做一件小任務，再去讀這個檔案。你會依序看到上面表格裡的每個時刻，也數得出一共有幾個，這是理解迴圈最快的辦法。檔案格式請照 VS Code hooks 文件。

hook 能做什么，做不到什么？

hook 在什么时候运行

hook 只在平台提供的时机运行。下面是我用到的几个，名字是 VS Code 在它文档里起的。

时机 发生了什么 我拿它做什么
会话开始 一个新对话开始 把这次会话的基本情况告诉模型
发出 prompt 你按下回车 加上规则；记下这是哪个任务
工具调用之前 模型提出了请求；还没有运行任何东西 拒绝一次调用。所有硬性规则都在这里
工具调用之后 工具已经运行 留一份记录；加一条备注
子 agent 启动或停止 一个帮手 agent 开始或结束 把它的材料交给它；记下结束
agent 即将停止 模型写完了一个回答 如果还有活没干完，说一次“还没完”

这些时机里，只有工具调用之前这一个能拒绝某个具体的动作。一条规则需要的，是一个已经存在、却还没有发生的调用，只有这个时机才有。其他时机能观察、能记录，也能添几句话。（停止的时机也能说“还没完”，下面会讲，但那不是在拒绝某个动作。）想亲眼看看这些时机，可以做这一节末尾的那个小测试。

进去什么，出来什么

那么在这样一个时机，hook 实际拿到的是什么？是一段 JSON，里面写着这是什么事件、哪个会话；如果是工具调用，还有工具名和它的参数。下面是从 VS Code 录下来的一个真实样本，是一条命令运行完之后 hook 收到的内容：

hook 也用 JSON 回答。真正有用的回答其实只有三种：

  • 放行。空的回答算没有意见，平台正常的权限检查照样生效。
  • 拒绝，并附上原因。这次调用不会运行，原因会显示给模型，也显示给你。
  • 加几句话给模型读，比如一条提醒、一行状态。

到了停止的时机，还有第四种：挡住这次停止，并附上一个原因，这个原因会像一个新的 prompt 一样喂回给模型。我每次停止只允许挡一次，因为每次停止都挡的 hook 会让 agent 永远跑下去，每一轮还都得你付钱。

原因是设计的一部分。拒绝的时候要说清楚为什么不行、应该改做什么，否则 agent 会再试同样的事，甚至做出更糟的事（询问不是限制）。

hook 出问题的三种方式

上面说的这些，前提都是 hook 本身好好的。可 hook 也是软件，它总会出问题。出问题时平台怎么处理，决定了你的规则是围栏，还是摆设。

发生了什么 Copilot 怎么处理（我在 2026 年 10 月观察到的，也是 VS Code 文档里说的）
hook 运行了，并且拒绝 调用被拦住，原因会显示出来。这在默认模式下有效，在跳过权限提示的模式下也有效。
hook 启动不了（比如它所用的语言没有安装） 当作拒绝：没有任何工具能运行，屏幕上除了“hook 出错”，几乎没有别的说明。
hook 花的时间太长 当作通过，不吭声。VS Code 文档的说法是，回落到正常的权限检查。

所以同一种故障，可能把你锁在门外，也可能让大门敞开，就看它是怎么失败的。你更愿意要哪一种，是一个设计选择。这个选择该怎么做，把执行层当软件来设计里有讲。那里也写了我的选择：放行这次调用并记下错误，最近最慢的一次调用接近时间上限时发出警告。

在子 agent 里

子 agent 是为了某一部分工作而开的第二个 agent（慎用子 agent）。它在自己的会话里运行，你也许会以为 hook 就管不到它了。其实在今天的 Copilot 里，它的工具调用同样会经过 hook，事件里还带着父会话的 id。所以给主 agent 定的规则，对它开的帮手也成立。别的平台我还没测过，所以换了平台，我不会这样假设。

hook 看不到什么

hook 看不到什么，是这一章里我最想让你记住的部分。

它看到的是调用，不是效果。对终端命令，hook 读的是命令的文本，它能看到“写入这个路径”。可它看不到用变量拼出来的路径，也看不到一个一分钟前才写好、现在才运行的脚本。命令一旦被放行，hook 就出局了。所以针对终端命令的 hook，拦得住常见的写法，却拦不住铁了心要绕过它的 agent。VS Code 文档说的也是这一点：hook 是可执行的代码，不能替代强制执行的权限或沙箱。那些绝对不能碰的东西，就别只靠 hook（有些东西根本不给）。

就算是它看得到的调用，hook 也不知道是哪个 agent 发出的。在今天的 Copilot 里，事件里没有主 agent 的名字，所以“这个 agent 被允许”做不成规则，因为任何 agent 都可以冒充它。如果权限必须有所不同，就得来自 agent 自己设置不了的东西，比如由人在终端里打开的开关。

还有一些调用，hook 根本看不到，因为它并不是到处都会运行。在我的测量里，用 Copilot 的命令行模式（没有窗口）时，仓库里的 hook 没有运行；有一个看起来像关闭开关的设置，在较新的会话里也并没有让它们停下来。公司策略也可以为某个工作区关掉 hook，就连改了 hook 文件，也得重新加载才生效，因为这个文件是在窗口启动时读的。这些是我在 2026 年 10 月发现的情况，它们会变，所以请看平台当前的文档。

最后，就算 hook 运行了、也给出了回答，它的消息还是可能丢掉。这就是开头那个故事：hook 的输出可能根本没到达模型。所以要测的是消息有没有送到，而不只是 hook 本身。

循环里其他站岗的东西

那么，站在模型和外部世界之间的，只有 hook 吗？并不是。包装器（一个你调用它、而不是调用原始命令的小程序）、MCP server（MCP server：接工具的标准接口），以及平台和模型之间的代理，也都站在那里。但它们每一个都只看得到经过自己的东西，agent 可以绕开它们。hook 的不同之处在于，平台承诺会调用它。对内置工具和子 agent，我见过每次调用都经过它，不过 MCP 工具我没有测过。

三个问题和一个小测试

想把这些用到你自己的配置上，可以对任何一条你在乎的规则问三个问题。

  1. 它是写在 prompt 里，还是写在 hook 里？如果在 prompt 里，它就是请求。
  2. 规则被违反时，hook 看到的是什么？调用的文本，还是效果？
  3. hook 自己坏了或者慢了，会怎么样？

另外还有一个今天就能做的测试。写一个你的平台允许的最小的 hook，它只做一件事，把事件名和工具名追加到一个文件里。然后用你的 agent 做一个小任务，再去读那个文件。你会按顺序看到上面表格里的每个时机，也能数出一共有多少个，这是理解循环最快的办法。文件格式请看 VS Code hooks 文档。

What a hook costs, and what to watch for

Of the three failures above, the one that matters most in a team is the timeout, because a timeout is a silent pass. The rule is not enforced, and nobody is told. So watch the time your hook takes and read Enforcement design before you choose what happens on failure.

Time matters for a second reason, too. A hook runs on every call, so if it is slow, everything is slow. Mine normally takes a few dozen milliseconds. Keep yours cheap, and put a limit on what it may do.

A hook is also code you must trust. It runs on your machine and reads whatever the agent sends, so never put the agent's text straight into a shell command inside a hook. In a team, treat the hook file like any other code that guards something, which means changing it through review. Hooks are also still in Preview in VS Code, so their behavior may change with the platform. What I wrote in the failure table is only what I saw, so check it again after each update.

One last trap is in the reason itself, which can be too good. A refusal that explains exactly how to get around the rule teaches the model to do that. Say what to do instead, not how to dodge.

hook 要付出什麼，要提防什麼

上面三種失敗裡，對團隊最重要的是逾時，因為逾時就是無聲的通過。規則沒有被執行，卻沒有人被告知。所以要留意你的 hook 花多少時間；在決定失敗時怎麼辦之前，也請先讀 把執行層當軟體來設計。

時間重要，還有另一個原因。hook 每次呼叫都會執行，它慢，一切都慢。我的通常幾十毫秒。要讓它便宜，並且限制它能做的事。

hook 也是你必須信任的程式碼。它在你的機器上執行，agent 送來什麼它都讀，所以絕不要在 hook 裡把 agent 的文字直接放進 shell 指令。在團隊裡，hook 檔要像任何其他守著東西的程式碼一樣對待，改動都要經過審查。另外，hook 在 VS Code 裡還是 Preview，平台一變，它的行為也可能跟著變。失敗表裡寫的只是我看到的，每次更新後都該再確認一次。

最後一個陷阱在原因本身：它也可能寫得太好。一個把怎麼繞過規則說得清清楚楚的拒絕，等於在教模型去那樣做。要說該改做什麼，而不是說怎麼閃躲。

hook 要付出什么，要提防什么

上面三种故障里，在团队里最要紧的是超时，因为超时就是悄悄放行。规则没有被强制执行，却没有人知道。所以要盯着你的 hook 花多长时间；在决定失败时怎么处理之前，也请先读把执行层当软件来设计。

时间要紧，还有另一个原因。hook 在每次调用上都运行，它要是慢，一切都慢。我的通常几十毫秒。让它保持廉价，并且限制它能做的事。

hook 还是你必须信任的代码。它在你的机器上运行，agent 发来什么它都读，所以永远不要把 agent 的文本直接放进 hook 里的 shell 命令。在团队里，hook 文件要像任何其他守着东西的代码一样对待，改动都要经过审查。另外，hook 在 VS Code 里还是 Preview，平台一变，它的行为也可能跟着变。故障表里写的只是我看到的，每次更新之后都该再查一遍。

最后一个坑在原因本身：它可能写得太好。一个把怎么绕过规则解释得清清楚楚的拒绝，等于在教模型这么做。要说该改做什么，而不是说怎么躲。

Which parts to delete, and when Industry practice

A hook for a rule stays as long as the platform lets rules in prompts be ignored, because the reasoning behind it does not retire. The parts I would delete first are the workarounds. The second check that puts back rules lost on the way goes when the platform delivers hook output reliably, and the timing watch goes when a timeout is reported instead of silently passing. If the platform one day offers a native, enforced policy (a rule file it checks itself), I would move the hard rules there and keep hooks for records and reminders.

哪些可以刪，什麼時候刪 業界做法

只要平台還允許 prompt 裡的規則被忽略，規則用的 hook 就會留著，因為背後的道理不會退役。我最先會刪的，是各種繞路的做法。等平台能可靠地送達 hook 的輸出，那道把遺失的規則補回去的檢查就可以拿掉；等逾時改成會被回報，不再無聲通過，計時的監看也可以拿掉。如果有一天平台提供原生的、強制執行的政策（一個它自己檢查的規則檔），我會把硬規則搬到那裡，hook 留給紀錄和提醒。

哪些可以删，什么时候删 业界做法

只要平台还允许 prompt 里的规则被忽略，针对规则的 hook 就要留着，因为背后的道理不会退役。我最先会删的，是那些绕弯的补丁。等平台能可靠地送达 hook 的输出，那道把丢掉的规则补回去的检查就可以去掉；等超时会被报告出来，而不是悄悄放行，对耗时的监控也可以去掉。如果哪天平台提供了原生的、强制执行的策略（一个它自己会检查的规则文件），我会把硬性规则搬到那里，hook 留给记录和提醒。
