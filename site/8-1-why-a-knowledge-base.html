This chapter is the first of a case study and builds on the general ideas in Context budget and What an agent should remember. It is written for a team with a large, old code base. If yours is small, read it to decide that you do not need this. Either way, the most useful part is the small experiment in Find out first whether you need one, because you can run it before you build anything.

The Knowledge經驗分享经验分享

In one sentence

The code is the truth, and a knowledge base is only an index and summary of it that should be cheaper to read. Rather than trying to be complete on day one, it tries to be honest: each card says which version of the source file it read, and each gap is written down where the next reader will see it.

一句話

程式碼才是真相，知識庫只是它的索引和摘要，讀起來應該比程式碼便宜。它不求第一天就完整，只求誠實：每張卡片都寫明它讀的是哪個版本的原始檔案，每個缺口都寫在下一個讀者看得到的地方。

一句话

代码才是真相，知识库只是它的索引和摘要，读起来应该比代码便宜。它不求第一天就完整，只求诚实：每张卡片都写明它读的是源文件的哪个版本，每个缺口都写在下一个读者看得到的地方。

For leaders

  • The decision: whether to fund a knowledge base (a folder of short notes about the code, written for agents), and who will own it. Before that, test whether searching the code is already enough.
  • The risk: searching starts to hurt when the code base is large, when the same exploration is paid for in every session, or when a wrong answer is expensive. I have not measured a knowledge base against plain search, so this is a bet, not a proven win. And a base nobody refreshes becomes confidently wrong.
  • The cost of doing it right: the model reads each object's code once. For a large domain that is real money, and I have not priced it. Someone must also own the refresh, and the notes need the same access rules as the code.
  • Ask the team: "On ten questions we know the answers to, how often does an agent with plain search get it right?"

給主管

  • 要做的決定：要不要出錢做知識庫（一個資料夾，裡面是寫給 agent 看的程式碼短筆記），以及由誰負責。決定之前，先測一下只搜尋程式碼是不是已經夠用。
  • 風險：程式碼庫很大、同樣的探索每個會話都要再付一次，或者答錯的代價很高，這些時候搜尋就開始吃力了。我沒有拿知識庫和單純的搜尋比較過，所以這是一場賭注，不是已經證實的好處。而沒有人更新的知識庫，會很有把握地答錯。
  • 做對的成本：模型要把每個物件的程式碼讀一遍。對大的領域來說，這是真金白銀，我也沒有算過要花多少。另外得有人負責更新，筆記也需要和程式碼一樣的存取規則。
  • 可以問團隊：「十個我們知道答案的問題，只用單純搜尋的 agent 答對幾個？」

写给管理者

  • 要拍板的事：要不要出钱做知识库（一个文件夹，里面是写给 agent 看的代码短笔记），以及由谁负责。拍板之前，先测一下只搜索代码是不是已经够用。
  • 风险：代码库很大、同样的探索每个会话都要再付一次，或者答错的代价很高，这些时候搜索就开始吃力了。我没有拿知识库和单纯的搜索比过，所以这是一次押注，不是已经证明的收益。而没人更新的知识库，会变得自信满满地答错。
  • 做对的代价：模型要把每个对象的代码读一遍。对大的领域来说，这是真金白银，我也没有算过要花多少。另外得有人负责更新，笔记也需要和代码一样的访问规则。
  • 可以问团队：“十个我们知道答案的问题，只用单纯搜索的 agent 能答对几个？”

What does an agent need to know before it changes one object?

Say a team owns a code base with a few thousand objects, where an object is a named thing in the code that other things use: a stored procedure, a scheduled job, a class, a table. You ask an agent to change one of them. To do it safely, the agent has to know what the object does, who uses it and what breaks if it changes, yet a new agent session starts knowing none of this. The obvious way to fill that gap is to let it search.

Why not just let the agent search the code?

An agent can search. It can run grep (find every line that contains a word), open files and follow names. For many jobs that is the right answer, and it costs nothing to set up. That is why I want to say clearly when it is enough. Searching does not have to mean bare grep, either. A language server (the editor service that answers "where is this defined, who uses it") or a code-search service can help, as can a short, good rules page. The knowledge base has to beat that combination, not bare grep.

Searching is enough when the code base is small or the part you need fits in one context, when you know the name of what you are looking for, or when the task is a one-off, so nobody pays for the same exploration twice.

Outside those cases, searching starts to hurt, and the first reason lies in how an agent searches. It decides what to read next from what it just read, so it can miss an object, follow a name that means something else, or stop too early. It cannot tell you how much it missed. Ask it twice and you may get two different answers.

A search that goes well still has to be repeated. Every new session starts with an empty context (context budget), so the agent finds the same things again and pays for the same exploration in every session.

Some things, though, are not in the code at all: which environment runs a job, why a rule exists, what failed last year. No search finds them, because they are not written there.

And some answers are expensive to get wrong. If the object touches shared data, a guess from a partial search is not good enough.

A knowledge base works the other way round. It is a folder of plain text files about the code, written for agents to read. The idea is to pay once for the exploration, keep the result, and read the result first, because it should be cheaper than the code.

I say "should" because I have not run the same questions once with plain search and once with a knowledge base, so I do not know by how much the second one wins, if it does. What I have is the reasoning above, plus a way for you to test it on your own code (see Find out first whether you need one). Treat the knowledge base as a bet that pays off under the conditions above, not as a proven win.

agent 改一個物件之前，得先知道什麼？

假設一個團隊管著一份有幾千個物件的程式碼庫。這裡說的物件，是程式碼裡有名字、被別的東西用到的東西：預存程序、排程工作、類別、資料表。你請 agent 改其中一個。要改得安全，它得知道這個物件是做什麼的、誰在用它、改了會壞掉什麼，可是新開的 agent 會話對這些一無所知。要補上這個缺口，最直接的辦法就是讓它自己去搜。

為什麼不乾脆讓 agent 搜尋程式碼？

agent 當然會搜尋。它能執行 grep（找出每一行含有某個詞的地方）、打開檔案、順著名字往下追。很多工作這樣做就是對的，而且不用任何設定。正因為這樣，我想先說清楚它什麼時候就夠了。再說，搜尋也不一定是光禿禿的 grep：語言伺服器（回答「這個在哪裡定義、誰在用」的編輯器服務）或程式碼搜尋服務都幫得上忙，一頁簡短而好的規則也有幫助。知識庫要贏的是這一整套，不是單純的 grep。

如果程式碼庫很小，或者你要的那一塊放得進一個上下文；如果你知道要找的東西叫什麼；又或者任務只做一次，沒有人會為同樣的探索付兩次錢，那搜尋就夠了。

在這些情況之外，搜尋就開始吃力了，頭一個原因出在 agent 搜尋的方式上。它根據剛讀到的東西決定下一步讀什麼，所以可能漏掉一個物件，追到一個名字相同、意思不同的東西，或者太早停下來。漏了多少，它自己說不出來。同一個問題問它兩次，可能得到兩個不同的答案。

這樣的搜尋就算很順利，下次也得重來。每個新會話都從空的上下文開始（上下文是一份預算），agent 只好把同樣的東西再找一遍，同樣的探索每個會話都要付一次錢。

還有些事，搜尋再順利也幫不上忙，因為它們根本不在程式碼裡，例如哪個環境執行某個工作、某條規則為什麼存在、去年出過什麼問題。程式碼裡沒有寫，自然搜不到。

最後一種情況和代價有關：有些答案錯不起。如果物件碰到共用的資料，靠不完整的搜尋猜出來的答案就不夠用。

而知識庫走的是反過來的路。它是一個資料夾，裡面是關於程式碼的純文字檔案，寫給 agent 讀。想法是探索只付一次錢，把結果留下來，之後先讀結果，因為它應該比讀程式碼便宜。

我說「應該」，是因為我沒有把同樣的問題一次用單純搜尋、一次用知識庫跑過，所以不知道後者能贏多少，甚至贏不贏。我手上有的，是上面這番推理，再加上一個讓你在自己的程式碼上測試的辦法（見先弄清楚你需不需要它）。所以請把知識庫看成一場賭注：滿足上面那些條件才會有回報，而不是已經證實的好處。

agent 改一个对象之前，得先知道什么？

假设一个团队管着一份有几千个对象的代码库。这里说的对象，是代码里有名字、被别的东西用到的东西：存储过程、定时任务、类、表。你让 agent 改其中一个。要改得安全，它得知道这个对象是干什么的、谁在用它、改了会弄坏什么，可新开的 agent 会话对这些一概不知。要补上这个缺口，最直接的办法就是让它自己去搜。

为什么不直接让 agent 搜索代码？

agent 当然会搜索。它能运行 grep（找出每一行含有某个词的地方）、打开文件、顺着名字往下追。很多活这样做就是对的，而且不用任何配置。正因为这样，我想先说清楚它什么时候就够了。再说，搜索也不一定是光秃秃的 grep：语言服务器（回答“这个在哪里定义、谁在用”的编辑器服务）或者代码搜索服务都能帮上忙，一页简短而好的规则也有用。知识库要赢的是这一整套，不是单纯的 grep。

如果代码库很小，或者你要的那一块装得进一个上下文；如果你知道要找的东西叫什么；又或者任务只做一次，没人会为同样的探索付两次钱，那搜索就够了。

在这些情况之外，搜索就开始吃力了，头一个原因出在 agent 搜索的方式上。它根据刚读到的东西决定下一步读什么，所以可能漏掉一个对象，追到一个重名但意思不同的东西，或者太早停下来。漏了多少，它自己说不出来。同一个问题问它两次，可能得到两个不同的答案。

这样的搜索就算很顺利，下次也得重来。每个新会话都从空的上下文开始（为什么不能把所有规则都塞给 Agent？），agent 只好把同样的东西再找一遍，同样的探索每个会话都要付一次钱。

还有些事，搜索再顺利也帮不上忙，因为它们根本不在代码里，比如哪个环境运行某个任务、某条规则为什么存在、去年出过什么故障。代码里没写，自然搜不到。

最后一种情况和代价有关：有些答案错不起。如果对象碰到共用的数据，靠不完整的搜索猜出来的答案就不够用。

而知识库走的是反过来的路子。它是一个文件夹，里面是关于代码的纯文本文件，写给 agent 读。思路是探索只付一次钱，把结果留下来，以后先读结果，因为它应该比读代码便宜。

我说“应该”，是因为我没有把同样的问题一次用单纯搜索、一次用知识库跑过，所以不知道后者能赢多少，甚至赢不赢。我手里有的，是上面这番推理，外加一个让你在自己的代码上测试的办法（见先弄清楚你需不需要它）。所以请把知识库看成一次押注：满足上面那些条件才会有回报，而不是已经证明的收益。

How a knowledge base is built to be honest

The shape of a knowledge base

If you do place the bet, what are you building? A knowledge base has layers, and a reader goes down them only as far as the task needs.

At the top, the overview lists the domains and has a glossary. A domain is a group of objects that serve one job, such as "orders" or "payroll". Each domain has an architecture page that says what the domain is for, its main flows, where to start reading, its traps and its limits.

One layer down, a card is a short entry about one object: what it is for, its rules, who it uses, its traps. Each rule cites the lines of code it comes from. Cards are grouped by type, one file per type. To find one, an agent walks down: the overview, then the domain's page, then the card by its id.

At the bottom is the code, the source of truth, so if a card and the code disagree, the code wins. That makes a card a promise with a date rather than a replacement for the code. When an agent needs more, it reads the code.

Scripts do the structure, the model does the meaning

Who writes the cards, then? Two kinds of work go into a card, and they are different.

Structure has one right answer: which objects exist, who uses whom (together, the map of the code), in what order to learn them, whether a card lists the right relations. A script can compute this, giving the same answer every time at no token cost. A model asked to do it walks the code by judgment and may miss things.

Meaning is the opposite. It has no single answer: what an object is for, what its rule is, which trap catches people. Only a model, reading the code, can write it.

The rest of this part follows from that split. The toolkit is how scripts draw the map that the audit then measures. Learning in batches is where the model writes the meaning, with scripts checking what they can. Keeping it true is about what happens after the code changes.

Honest, not complete

How much of a base can come from the code? My guess is most of it, though that is a guess, not a measurement. The rest cannot: what runs in which environment, what failed and why, what someone decided. That part comes over time, from finished tasks, from root-cause reports and from what people export. So the base is never finished on day one, and pretending it is would make it worse, because a base that looks complete gets believed.

Two habits keep it honest. One is that every card says which version of its source file it read. It records a commit (a saved version of the code, named by a short id called a sha). To check that later, the scripts keep an object index: a list of every object, the source file it lives in, and that file's sha. That is how you can list the cards the code has moved past.

The other habit is that every gap is written down. What the code cannot tell goes into a requests list, with one row per thing a person must give, the kind of thing it is, and a read-only way to get it. The agent asks for these at its next stop, never in the middle of work. The details of both habits are in Chapter 8.5.

Every step is a task a person approves

Building the base is not one big prompt. Each step is a task (see Manage tasks, not chats) with a plan the person approves and a write-back the person approves, where the write-back copies the finished work into the base (see Two gates: where a person approves). Scripts check what can be checked: the form of the files, the relations, the cited lines.

I keep one more limit on every step: the agent never connects to a live environment. When something only an environment can tell is needed, a person runs it and hands the result over.

The road

Put in order, the steps make a road:

  1. Build a toolkit, once per code base (8.2).
  2. Compute the map, before each use (8.2).
  3. Audit the map (8.3).
  4. Split the code into domains, once (8.4).
  5. Learn each domain in batches (8.4).
  6. Write the architecture page (8.4).
  7. Keep it true: refresh, capture, requests (8.5).

Find out first whether you need one {#test}

Before you set off on that road, a small test can tell you whether you need it.

  1. Write 10 questions about your code whose right answers you know. Mix kinds: "what calls X?", "what happens if Y changes?", "why does Z skip this case?".
  2. Ask an agent each question in a fresh chat, with plain search only. Score each answer right or wrong against what you know.
  3. Write cards for one small domain, by hand or with the agent. Then ask the same questions again in fresh chats, with the cards available.
  4. Compare right answers, usage (the token numbers your tool shows for a run) and time.

A few cautions make the test worth trusting. Ask the questions in a form that cannot be answered from one file, such as "what breaks if Y changes?", and let someone who has not read the cards choose them. Because an agent does not do the same thing twice, run each condition several times rather than once (see Variance). Ten questions can only show a large difference anyway. If search alone scores about the same, do not build the base.

一個誠實的知識庫是怎麼建起來的

知識庫的形狀

如果你決定下這個注，要建的究竟是什麼？知識庫分好幾層，讀的人只往下走到任務需要的那一層。

最上面是總覽，列出所有領域，還附一份詞彙表。領域是為了同一件工作而存在的一組物件，例如「訂單」或「薪資」。每個領域有一份架構頁，說明這個領域是做什麼的、有哪些主要流程、從哪裡開始讀、有哪些陷阱、有哪些限制。

再往下一層是卡片，一張卡片是關於一個物件的短條目：它做什麼、它的規則、它用到誰、它的陷阱。每條規則都註明它來自哪幾行程式碼。卡片按類型分組，一種類型放一個檔案。要找一張卡片，agent 就一層層往下走：先看總覽，再到領域的頁面，最後用 id 找到卡片。

最底下是程式碼，它是真相的來源，所以卡片和程式碼不一致時，以程式碼為準。這樣看來，卡片是一份附日期的承諾，而不是程式碼的替代品。agent 需要更多資訊時，就去讀程式碼。

腳本管結構，模型管意義

那卡片由誰來寫？寫一張卡片其實要做兩種不一樣的工作。

結構只有一個正確答案：有哪些物件、誰用誰（合起來就是程式碼的地圖）、照什麼順序去學、一張卡片列出的關係對不對。這些腳本算得出來，每次給出同樣的答案，也不花 token。換成模型來做，它會憑判斷在程式碼裡走，可能漏掉東西。

意義正好相反。它沒有單一的答案：一個物件是做什麼的、它的規則是什麼、哪個陷阱會絆住人。這只有讀了程式碼的模型才寫得出來。

這一部分後面的內容，都是從這個分工推出來的。Toolkit：用腳本畫出程式碼的地圖講腳本怎麼畫地圖，地圖對不對：盲抽查再來量一量它畫得對不對。分批學一個領域是模型寫下意義的地方，腳本在旁邊檢查它能檢查的部分。讓知識庫一直是對的講的是程式碼改了之後怎麼辦。

求誠實，不求完整

知識庫有多少內容能從程式碼裡得到？我猜是大部分，不過這只是猜測，不是量測。剩下的得不到：什麼在哪個環境執行、出過什麼問題、原因是什麼、誰做了什麼決定。這一部分要靠時間慢慢累積，來自做完的任務、根因報告和人們匯出的東西。所以知識庫第一天不可能完成；假裝它已經完成只會更糟，因為一個看起來完整的知識庫會被人相信。

讓它保持誠實的，是兩個習慣。一個是每張卡片都寫明它讀的是哪個版本的原始檔案。卡片會記下一個 commit（程式碼的一個存下來的版本，用一個叫 sha 的短 id 來命名）。為了之後能核對，腳本還維護一份物件索引，列出每個物件、它所在的原始檔案，以及那個檔案的 sha。靠著這些，你才能列出程式碼已經改過、卡片卻還沒跟上的那些卡片。

另一個習慣是每個缺口都寫下來。程式碼說不清楚的事，記進一份請求清單：每件必須由人提供的東西占一列，寫明它屬於哪一類，以及一個唯讀的取得辦法。agent 會在下一個停下來的地方提出這些請求，絕不在工作做到一半時提。這兩個習慣的細節，都在第 8.5 章。

每一步都是一個由人批准的任務

建知識庫不是靠一個大 prompt。每一步都是一個任務（見管任務，不管對話），計劃要人批准，寫回也要人批准；寫回，就是把做完的工作複製進知識庫（見兩道門：人在哪裡批准）。能檢查的部分交給腳本：檔案的格式、關係、被引用的程式碼行。

還有一條限制，每一步都適用：agent 從不連上正在執行的環境。只有環境才說得出的事，由人去執行，再把結果交過來。

路線

照先後排起來，這些步驟就是一條路線：

  1. 建一個 toolkit，每個程式碼庫一次（8.2）。
  2. 計算地圖，每次使用之前（8.2）。
  3. 盲抽查地圖（8.3）。
  4. 把程式碼分成領域，一次（8.4）。
  5. 分批學每個領域（8.4）。
  6. 寫架構頁（8.4）。
  7. 讓它一直是對的：更新、擷取、請求（8.5）。

先弄清楚你需不需要它 {#test}

走這條路之前，一個小測試就能告訴你需不需要它。

  1. 寫 10 個關於你程式碼的問題，正確答案是你知道的。種類要混著來：「什麼呼叫了 X？」「Y 改了會怎樣？」「為什麼 Z 跳過這個情況？」
  2. 每個問題都在全新的對話裡問 agent，只用單純搜尋。照你知道的答案，每個回答判對或錯。
  3. 自己寫或讓 agent 幫忙，為一個小領域寫卡片。然後在全新的對話裡再問同樣的問題，這次有卡片可用。
  4. 比較答對的數量、用量（你的工具為一次運行顯示的 token 數）和時間。

這個測試要靠得住，有幾點得注意。問題的形式要讓人無法只靠一個檔案回答，例如「Y 改了會壞掉什麼？」，而且要讓沒讀過卡片的人來選題。agent 不會把同一件事做得兩次一樣，所以每種條件都要做好幾次，而不是只做一次（見一次運行證明不了什麼）。再說，十個問題本來就只看得出很大的差別。如果單靠搜尋得分也差不多，就不要建知識庫。

一个诚实的知识库是怎么搭起来的

知识库的形状

如果你决定押这一注，要搭的究竟是个什么东西？知识库分好几层，读的人只往下走到任务需要的那一层。

最上面是总览，列出所有领域，还附一份词汇表。领域是为同一项工作服务的一组对象，比如“订单”或者“薪资”。每个领域有一份架构页，写明这个领域是干什么的、有哪些主要流程、从哪里开始读、有哪些坑、有哪些限制。

再往下一层是卡片，一张卡片是关于一个对象的简短条目：它的用途、它的规则、它用到谁、它的坑。每条规则都引用它所依据的代码行。卡片按类型分组，一种类型放一个文件。要找一张卡片，agent 就一层层往下走：先看总览，再到领域的页面，最后按 id 找到卡片。

最底下是代码，它是真相的来源，所以卡片和代码对不上时，以代码为准。这样看，卡片是一份带日期的承诺，而不是代码的替代品。agent 需要更多信息时，就去读代码。

脚本管结构，模型管含义

那卡片由谁来写？写一张卡片其实要干两种不一样的活。

结构只有一个正确答案：有哪些对象、谁用谁（合起来就是代码的地图）、按什么顺序去学、一张卡片列出的关系对不对。这些脚本算得出来，每次给出同样的答案，也不花 token。换成模型来做，它会凭判断在代码里走，可能漏掉东西。

含义正好相反。它没有唯一的答案：一个对象是干什么的、它的规则是什么、哪个坑会绊倒人。这只有模型读了代码才写得出来。

这一部分后面的内容，都是从这个分工推出来的。代码里谁调用谁，交给脚本来算讲脚本怎么画地图，知识库写得对不对？抽查一遍再来量一量它画得对不对。让 Agent 学一个大系统：从底层往上，分批读是模型写下含义的地方，脚本在旁边检查它能检查的部分。代码变了，知识库怎么跟着变？讲的是代码改了以后怎么办。

求诚实，不求完整

知识库有多少内容能从代码里得到？我猜是大部分，不过这只是猜测，不是测量。剩下的得不到：什么在哪个环境里运行、出过什么故障、原因是什么、谁做了什么决定。这部分要靠时间慢慢积累，来自做完的任务、根因报告和人导出的东西。所以知识库第一天不可能完成；假装它已经完成只会更糟，因为一个看起来完整的知识库会被人相信。

让它保持诚实的，是两个习惯。一个是每张卡片都写明它读的是源文件的哪个版本。卡片会记下一个 commit（代码的一个已保存版本，用一个叫 sha 的短 id 来命名）。为了以后能核对，脚本还维护一份对象索引，列出每个对象、它所在的源文件，以及那个文件的 sha。靠着这些，你才能列出代码已经改过、卡片却还没跟上的那些卡片。

另一个习惯是每个缺口都写下来。代码说不清的事，记进一张请求清单：每件需要人提供的东西占一行，写明它属于哪一类，以及一种只读的获取办法。agent 会在下一个停靠点提出这些请求，绝不在干活干到一半时提。这两个习惯的细节，都在第 8.5 章。

每一步都是一个由人审批的任务

建知识库不是靠一个大 prompt。每一步都是一个任务（见一个任务一个文件夹），计划要人审批，写回也要人审批；写回，就是把做完的工作复制进知识库（见哪些事必须由人来批？）。能检查的部分交给脚本：文件的格式、关系、引用的代码行。

还有一条限制，每一步都适用：agent 从不连接线上环境。只有环境才知道的事，由人去运行，再把结果交给它。

路线

按先后排起来，这些步骤就是一条路线：

  1. 搭一个 toolkit，每个代码库一次（8.2）。
  2. 计算地图，每次使用之前（8.2）。
  3. 盲抽查地图（8.3）。
  4. 把代码切成领域，一次（8.4）。
  5. 分批学每个领域（8.4）。
  6. 写架构页（8.4）。
  7. 让它一直是对的：更新、捕获、请求（8.5）。

先弄清楚你需不需要它 {#test}

走这条路之前，一个小测试就能告诉你需不需要它。

  1. 写 10 个关于你的代码的问题，正确答案你是知道的。种类要混着来：“什么调用了 X？”“如果 Y 改了会怎样？”“为什么 Z 跳过了这种情况？”
  2. 每个问题都在新对话里问 agent，只用单纯搜索。对照你已知的答案，每个回答判对或错。
  3. 手工或者让 agent 帮忙，给一个小领域写卡片。然后在新对话里再问同样的问题，这次卡片可以用。
  4. 比较答对的个数、用量（你的工具为一次运行显示的 token 数）和时间。

这个测试要靠得住，有几点得注意。提问的形式要让一个文件回答不了，比如“如果 Y 改了，什么会坏？”，而且要让没读过卡片的人来选题。agent 不会把同一件事做得两次一样，所以每种条件都要做几次，而不是只做一次（见同一个任务跑两次，结果不一样）。再说，十个问题本来就只能显示出很大的差别。如果只靠搜索得分也差不多，就不要建知识库。

What it costs, and how it can go wrong

Even when the test says build, the base does not stay right by itself. It needs upkeep, because a base nobody refreshes becomes confidently wrong. If your code changes daily and nobody will own the refresh, search is the better choice.

A card that is up to date can still be wrong, since it is a model's reading of the code. The checks catch the structure, not whether a rule is understood right, so a person's review, or an independent reviewer (a model checking a model), has to cover that. And because the agent reads the card first, a card can anchor it: the agent may look at less code and keep a wrong card's view. For work where a mistake is expensive, have it re-read the lines a card cites.

Every card the agent reads costs tokens, so a base that is too long only moves the cost. Cards should be short, and the agent should open the lower layers only when it needs them.

Those are the costs of keeping and using a base. Building one is a separate cost: the model reads each object's code once, so for a large domain that is real money, spent on a bet that the reading will be reused. A rough size is every object read once, plus the files that change each month, though I have not priced it. Prompt caching may lower both the building and the reading. Anthropic's docs say a cached read costs about a tenth of the base price (see Choosing a model), though I have not checked this on Copilot. So test with it on, as you would really run.

Ownership is the last thing to settle. Someone must own the base, and because a card is a summary of internal code, the cards need the same access rules as the code. Decide who refreshes them and who may read them.

要付出什麼，又會在哪裡出錯

就算測試說值得建，知識庫也不會自己一直保持正確。它需要維護，因為沒有人更新的知識庫會很有把握地答錯。如果你的程式碼每天都在變，又沒有人願意負責更新，搜尋是比較好的選擇。

就算卡片是最新的，它也可能是錯的，畢竟它是模型對程式碼的解讀。檢查抓得到結構，抓不到一條規則是不是理解對了，這部分要靠人的審查，或獨立的 reviewer（模型能檢查模型嗎）。而且 agent 是先讀卡片的，所以卡片可能讓它被錨定：它可能少看一些程式碼，沿用一張錯誤卡片的看法。對出錯代價高的工作，讓它重讀卡片引用的那幾行。

agent 每讀一張卡片都要花 token，所以太長的知識庫只是把成本搬到別處。卡片要短，agent 只在需要時才往下打開更低的層。

前面說的都是維護和使用的成本，建的那一次還要另算：模型要把每個物件的程式碼讀一遍，所以對大的領域來說，建一次就是真金白銀，賭的是這些讀過的東西會被重複使用。粗略的規模是每個物件讀一遍，再加上每個月會變的檔案，不過我沒有算過價。prompt 快取也許能同時降低建和讀的成本。Anthropic 的文件說，快取讀取大約是基本價格的十分之一（見選模型：算的是每次成功的成本），不過我沒有在 Copilot 上確認過。所以測的時候要把它開著，就像你真正執行時那樣。

最後要定的是誰來負責。知識庫得有人管。卡片又是內部程式碼的摘要，所以也需要和程式碼一樣的存取規則。誰來更新、誰可以讀，要決定下來。

要花什么，又会在哪里出错

就算测试说值得建，知识库也不会自己一直保持正确。它需要维护，因为没人更新的知识库会变得自信满满地答错。如果你的代码天天在变，又没人愿意负责更新，搜索是更好的选择。

就算卡片是最新的，它也可能是错的，毕竟它是模型对代码的理解。检查只能抓住结构，抓不住一条规则理解得对不对，这部分要靠人审查，或者靠独立的 reviewer（让另一个模型来审，靠得住吗？）。而且 agent 是先读卡片的，所以卡片可能把它锚住：它可能少看一些代码，沿用一张错卡片的看法。对出错代价高的工作，让它重读卡片引用的那几行。

agent 每读一张卡片都要花 token，所以太长的知识库只是把成本挪了个地方。卡片要短，agent 只在需要时才往下打开更低的层。

前面说的都是维护和使用的成本，建的那一次还要另算：模型要把每个对象的代码读一遍，所以对大的领域来说，建一次就是真金白银，押的是这些读过的东西会被反复用到。粗略的规模是每个对象读一遍，再加上每月变动的文件，不过我没有算过价。prompt 缓存也许能同时降低建库和读取的成本。Anthropic 的文档说缓存读取约为基础价格的十分之一（见选模型，别只看 token 单价），不过我没有在 Copilot 上核实过。所以测试时要把它打开，就像你真正运行时那样。

最后要定的是谁来负责。知识库得有人管。卡片又是对内部代码的摘要，所以也需要和代码一样的访问规则。谁来更新、谁能读，要定下来。

When to delete the cards, and what to keep

If your own test shows that search alone gives the same answers at the same cost, delete the cards and keep only the requests list, because that is the part search can never give. And if the platform one day builds and refreshes a code index that you can measure as accurate, use it instead of keeping your own.

什麼時候刪掉卡片，留下什麼

如果你自己的測試顯示，單靠搜尋就能用同樣的成本給出同樣的答案，那就把卡片刪掉，只留下請求清單，因為那是搜尋永遠給不了的部分。如果有一天平台能建立並更新一份程式碼索引，而且你量得出它是準確的，就改用它，不要再自己維護一份。

什么时候删掉卡片，留下什么

如果你自己的测试表明，只靠搜索就能以同样的成本给出同样的答案，那就把卡片删掉，只留下请求清单，因为这是搜索永远给不了的部分。如果哪天平台能构建并更新一份代码索引，而且你测得出它是准确的，就改用它，别再自己维护一份。
