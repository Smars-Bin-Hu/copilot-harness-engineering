Asking is not a limit詢問不是限制询问不是限制

This chapter assumes you have read A rule in a prompt is a request: a rule that must hold has to be code, not words.

這一章假設你讀過提示裡的規則只是請求：一定要守住的規則，必須是程式碼，不能只是文字。

这一章默认你已经读过提示里的规则只是请求：必须成立的规则要写成代码，不能只靠文字。

The Knowledge經驗分享经验分享

In one sentence

"Ask me first" is not a limit, because people click Allow the hundredth time. A limit is a refusal the agent cannot argue with, graded by what the action can break.

一句話

「先問我」不是限制，因為問到第一百次，人就會直接點允許。真正的限制是 agent 吵不贏的拒絕，並且按這個動作可能弄壞多少來分級。

一句话

“先问我”不是限制，因为问到第一百次，人就会直接点“允许”。真正的限制是 agent 辩不过的拒绝，并且按这个动作可能弄坏多少来分级。

For leaders

  • The decision: decide that "ask me first" is not a safety limit. Actions that must not happen get a refusal, graded by what a mistake costs. A question to a person is kept for the rare cases that need judgment.
  • The risk: people click Allow the hundredth time, and the platform even offers ways to remove the box altogether. VS Code says global auto-approval "bypasses all user approvals, potentially leading to destructive actions". I did not measure how often people click without reading.
  • The cost of doing it right: a short set of refusal rules, each with a written reason the agent can act on, plus someone who reads the logs for rules that fire too often. Isolation in a sandbox cuts the number of boxes as well. Anthropic reports 84% fewer permission prompts in its own internal use, though that is its number for its own tool.
  • Ask the team: "Which actions can our agent take with no person in the loop, and are any of them impossible to undo?"

給主管

  • 要做的決定：決定「先問我」不算安全限制。一定不能發生的動作，要用拒絕，並按出錯的代價分級。問人，只留給少見的、需要判斷的情況。
  • 風險：問到第一百次，人就會直接點允許，平台甚至還提供了把詢問框整個拿掉的辦法。VS Code 說，全域自動批准會「繞過所有使用者批准，可能導致破壞性的動作」。我沒有量過人有多常不看就點。
  • 做對的成本：一小組拒絕規則，每條都附一句 agent 能照著做的原因，再加一個人去看日誌，找出觸發太頻繁的規則。把 agent 關進沙箱隔離，詢問框的數量也會減少：Anthropic 說它自己內部使用時，權限提示少了 84%，不過這是它對自己工具的數字。
  • 可以問團隊：「我們的 agent 有哪些動作，不用任何人在場就能做？其中有沒有無法撤銷的？」

写给管理者

  • 要拍板的事：认定“先问我”不算安全限制。不许发生的动作要拒绝，并按出错的代价分级。向人提问，只留给少数需要判断的情况。
  • 风险：问到第一百次，人就会直接点“允许”，平台甚至还提供了把弹框彻底去掉的办法。VS Code 说，全局自动审批会“绕过所有用户审批，可能导致破坏性操作”。我没量过人们有多常不看就点。
  • 做对的代价：一小组拒绝规则，每条都附一句 agent 能照着做的理由，再加一个人去读日志，找出触发得太频繁的规则。把 agent 放进沙箱隔离，弹框的数量也会减少：Anthropic 报告说，它自己内部使用时权限提示少了 84%，不过这是它对自己工具的数字。
  • 可以问团队：“我们的 agent 有哪些动作，可以在没人把关的情况下执行？其中有没有无法撤销的？”

Why does asking wear out?

The obvious way to keep an agent safe is to make it ask. Before it runs a command, a box pops up with Allow and Deny, so you stay in charge and nothing happens without your click.

On the first day, it does its job. You read the first command and glance at the tenth, but by the hundredth you click Allow before the box has finished drawing, because ninety-nine of the last ones were fine (that is what I and many others see, and what the platform docs warn about, though I have not measured how often). This is not laziness. It is what anyone does when almost every question has the same right answer. By then the box is a delay, not a check.

A delay is annoying, so when the platform offers ways to remove it, you use them, and each goes further than the last. With Allow in this session, one click on a single box is enough to stop the same kind of action being asked about again in that chat. Allow all removes the box altogether. It is a single setting, and after it the action just runs. Autopilot goes further still: the agent keeps working with no one at the keyboard, so even when a box does appear, no one is there to read it.

The platform itself is plain about where this leads. VS Code warns that global auto-approval "bypasses all user approvals, potentially leading to destructive actions". It also admits that its own parsing of commands is only "best-effort" (security). Its hooks page adds that ask "requires an interactive approval flow", so do not assume it pauses an unattended session (hooks).

So what still holds once the box is gone? In the three modes I tried (default, Allow all and Autopilot), one thing held in all of them: a refusal from a hook. A box can be switched off, whereas a refusal cannot be clicked away in a pop-up. A person can still change the rule itself, and doing that safely is what Guard the files that hold the rules is about. Before deciding what to refuse, though, it helps to be exact about how refusing differs from asking.

詢問為什麼會慢慢失效？

要讓 agent 保持安全，最直覺的辦法就是讓它先問。它每次執行指令之前，都會彈出一個框，讓你選允許還是拒絕。你說了算，沒有你點頭，什麼都不會發生。

頭一天，這招確實有用。第一個指令你會認真讀，到第十個就只掃一眼了。等到第一百個，框還沒畫完你就點了允許，因為前面九十九個都沒出過事（這是我和很多人都看過的情況，平台文件也提醒過，只是有多頻繁，我沒有量過）。這不是偷懶。幾乎每個問題的正確答案都一樣的時候，誰都會這樣做。到了這一步，這個框只是在拖時間，已經起不了檢查的作用。

拖時間總是很煩，所以平台一給出拿掉它的辦法，你就會用，而且這些辦法一個比一個徹底。「這個會話內允許」只要在某一個框上點一下，同一類動作在這次對話裡就不會再問。「全部允許」乾脆把框整個拿掉。它是一項設定，打開之後，動作就直接執行。Autopilot 走得更遠：agent 在沒人守著鍵盤的時候也照樣工作，就算框彈了出來，也沒有人看。

平台自己也把後果說得很直接。VS Code 提醒，全域自動批准會「繞過所有使用者批准，可能導致破壞性的動作」。它也承認，自己對指令的解析只是「盡力而為」（security）。它的 hooks 頁面還補了一句：ask「需要互動式的批准流程」，所以別以為它能讓無人值守的會話停下來（hooks）。

那麼，框沒了以後，還有什麼守得住？我試了三種模式（預設、全部允許、Autopilot），每一種都守住的只有一樣東西，就是 hook 發出的拒絕。詢問框可以被關掉，拒絕卻不能像詢問框那樣一點就過去。人仍然可以改規則本身，怎麼安全地改，是保護規則本身的檔案要講的。不過在決定拒絕什麼之前，得先把拒絕和詢問到底差在哪裡說清楚。

询问为什么会慢慢失效？

要让 agent 安全，最顺手的办法就是让它先问。它每次运行命令之前，都会弹出一个框，让你选“允许”还是“拒绝”。由你说了算，你不点，什么都不会发生。

头一天，这招确实管用。第一条命令你会认真读，到第十条就只扫一眼了。等到第一百条，框还没画完你就点了“允许”，因为前面九十九条都没出过问题（这是我和很多人都见过的情况，平台文档也警告过，只是有多频繁，我没量过）。这不是懒。几乎每个问题的正确答案都一样的时候，谁都会这么做。到了这一步，这个框只是在拖时间，已经起不到检查的作用了。

拖时间总是烦人的，所以平台一给出去掉它的办法，你就会用，而且这些办法一个比一个彻底。“本次会话内允许”只要在某一个框上点一下，同一类动作在这个对话里就不会再问。“全部允许”干脆把框整个去掉。它是一项设置，打开以后，动作就直接运行。Autopilot 走得更远：agent 在没人守着键盘的时候也照样干活，就算框弹了出来，也没有人去读。

平台自己也把后果说得很直白。VS Code 警告说，全局自动审批会“绕过所有用户审批，可能导致破坏性操作”。它也承认，自己对命令的解析只是“尽力而为”（security）。它的 hooks 页面还补充说，ask “需要交互式的审批流程”，所以别以为它能让一个无人值守的会话停下来（hooks）。

那么，框没了以后，还有什么守得住？在我试过的三种模式（默认、全部允许、Autopilot）里，始终有效的只有一样东西，就是 hook 做出的拒绝。弹框可以被关掉，拒绝却没法在弹框里一点就过去。人仍然可以改规则本身，怎么安全地改，是保护规则本身的文件要讲的。不过在决定拒绝什么之前，得先把拒绝和询问到底差在哪里说清楚。

What to refuse, and how

Asking and refusing

To ask is to stop and wait for a person to say yes. To refuse is to say no without waiting, and to say it the same way every time. The difference lies in what can be argued with. The agent can talk a person into a yes (or the person can talk themselves into one), but as long as the program is running, the agent cannot talk it out of a no.

That is why the two belong to different jobs. Refusing is for what must not happen, meaning the things you would never approve or cannot undo. Nobody should have to say no to those a hundred times when a program can say it once and keep saying it. Asking is for what depends on a person's judgment and comes up rarely, because a box only works when it is rare enough to be read. Spend it where it is worth a person's attention.

An ask that matters also has to reach the person through a channel the agent cannot press itself, since a box in the chat can be switched off by "allow for this session" (I come back to this in Two gates).

The terminal is the hard case

How hard a refusal is to write depends on the tool. Edit tools are easy to guard, because the path is a field in the call and the rule can simply be "refuse this path".

The terminal is another matter. It is the strongest tool an agent has, because it can run anything you can run. It is also the hardest to guard, because one effect can be spelled in many ways, such as a redirect, rm, sed -i, or a script that runs another script. Can a hook not simply read the command? It can, and reading the text catches the common spellings. What it misses is a path built from variables, or a script written first and run later (Hooks). So rules on the terminal never reach "complete". That is no reason to skip them, but it is a reason to be honest about what they are: a guard against mistakes, not against an agent set on getting round them.

Grade by consequence

If you cannot stop everything, stop things by how much a mistake costs, not by how hard the task is. Hard tasks can be harmless, while an easy command can ruin a day. Grading by consequence has another advantage: code can judge it from the path and the command, so you do not have to choose a level for each task by hand. The catch is that the code sees the words of a command, not its effect. The grade is a guess from text, and I come back to that among the costs below.

Consequence Example What I do
Reads only Looking things up, reading files Not stopped
Writes that can be undone Editing in a work folder, writing a plan Allowed, inside a defined area only
Writes to a real repository Code that people will use The agent writes in a work area first. A person approves before it is written back (Two gates)
Cannot be undone Pushing, deleting a branch, resetting hard Refused. The agent never gets a yes. A person does it

Read down the table and the pattern shows. The more a mistake costs, the less the agent decides alone, until at the top grade there is no asking at all.

git as an example

git makes a good case, because it has both ends. In my setup, with a repository connected, git commands fall into three groups.

  • Reads pass. status, diff, log and the like are never stopped.
  • Writes such as add, commit and switching branches are refused, but with a way forward. The refusal message holds the full command and a code, so the person can read it and approve by typing one command in their own terminal, within a time limit. The approval is for that command, not for git in general.
  • Some commands can never be approved by the agent. These are push, opening a pull request, reset --hard, clean, and force options, and the person runs them themselves.

Why not simply ask for all of them? Because the three groups deserve different treatment. Reads are free, while writes are normal but must be seen. A push or a hard reset, though, is the kind of thing a hundredth click would let through, so for those only a refusal will do.

Write the reason for the agent

A refusal has two readers, you and the agent. Of the two, the agent matters more, because it is the one that reads the message and decides what to do next.

If the message says only "denied", one of two things happens: the agent tries the same thing again, or it tries something worse. A good message avoids that by doing two jobs, saying in one sentence why the call was refused and what to do instead.

Say the agent writes to the code folder before the plan is approved. A good reason tells it that the plan is not approved yet (plan approval is the first gate in Two gates), and that it should write the plan, stop, and ask the person to approve it in their terminal. Now the agent knows the next step, so it goes that way instead of looking for a side door.

I write every refusal as if it were the only help the agent will get. It is the same split as in the last chapter, where the code stops and the words teach.

該拒絕什麼，怎麼拒絕

詢問和拒絕

詢問是停下來，等人說好。拒絕是不等任何人，直接說不，而且每次都用同樣的方式說。兩者的差別在於能不能被說動。agent 可以說服一個人點頭（人也可能自己說服自己），可是只要程式還在跑，agent 就說服不了它收回那個不。

正因為這樣，兩者各管不同的事。拒絕管的是不能發生的事，也就是你永遠不會批准、或者無法撤銷的那些。這類事不該讓人說一百次不，程式說一次，以後每次都這樣說就好。詢問管的是要靠人判斷、而且很少出現的事，因為詢問框只有少到有人肯讀，才會管用。所以要把它用在值得人花注意力的地方。

真正重要的詢問，還得經過一個 agent 自己按不到的管道傳到人那裡，因為對話裡的框可以被「這個會話內允許」關掉。這一點我會在兩道門：人在哪裡批准再講。

終端機最難管

一條拒絕好不好寫，要看是什麼工具。編輯工具很好管，因為路徑就是呼叫裡的一個欄位，規則寫成「拒絕這個路徑」就行。

終端機就是另一回事了。它是 agent 手上最強的工具，因為你能執行的它都能執行。它也是最難管的，因為同一個效果有很多種寫法，比如重新導向、rm、sed -i，或者一個執行另一個腳本的腳本。hook 難道不能直接讀指令嗎？能，讀文字就攔得住常見的寫法。它漏掉的，是用變數拼出來的路徑，或者先寫好、之後再執行的腳本（Hooks：每次呼叫都會經過的執行點）。這樣一來，終端機上的規則永遠不會「完整」。但這不等於可以不寫，只是得老實承認它們能做什麼：防的是失誤，防不了一個鐵了心要繞過去的 agent。

按後果分級

既然攔不住所有的事，就按出錯的代價來攔，而不是按任務難不難。難的任務可能完全無害，簡單的指令卻可能毀掉一整天。按後果分級還有一個好處：程式可以從路徑和指令判斷後果，所以你不必替每個任務手動選等級。問題是，程式看到的是指令的文字，不是它的效果。等級其實是從文字猜出來的，後面講代價的時候我會再回到這一點。

後果 例子 我怎麼做

寫進真正的倉庫 別人會用到的程式碼 agent 先寫在工作區。寫回去之前由人批准（兩道門：人在哪裡批准）

把這張表從上往下讀，規律就出來了。出錯的代價越大，agent 能自己決定的就越少，到了最高一級，就完全不問了。

以 git 為例

git 的指令在這張表的兩頭都有，所以是個好例子。在我的設定裡，連上倉庫之後，git 指令分成三組。

  • 讀的放行。status、diff、log 這類永遠不攔。
  • add、commit、切換分支這類寫入會被拒絕，但拒絕時會附一條出路。拒絕訊息裡有完整的指令和一個代碼，人讀完之後，可以在自己的終端機裡打一條指令來批准，有時間限制。批准只針對那一條指令，不是針對整個 git。
  • 有些指令 agent 永遠批不到，包括 push、開 pull request、reset --hard、clean，還有強制選項。這些由人自己執行。

為什麼不乾脆全都用詢問？因為這三組值得不同的對待。讀是免費的，寫是正常的，但必須被人看到。可是 push 或 hard reset 這種事，正是第一百次點擊會放過去的，所以對它們只能拒絕。

把原因寫給 agent 看

一條拒絕有兩個讀者：你，和 agent。其中更要緊的是 agent，因為讀這則訊息、決定下一步怎麼做的是它。

如果訊息只寫「已拒絕」，結果不外乎兩種：agent 再試一次同樣的事，或者換一個更糟的辦法。好的訊息能避開這種情況：它會用一句話說清楚為什麼被拒絕，再告訴 agent 該改做什麼。

舉例來說，agent 在計劃還沒批准時就去寫程式碼資料夾。好的原因會告訴它，計劃還沒批准（計劃批准是兩道門：人在哪裡批准的第一道門），它應該先寫計劃，然後停下來，請人在自己的終端機批准。這樣一來，agent 知道下一步該做什麼，就會照著走，不去找旁門。

我把每一條拒絕都當成 agent 唯一能得到的幫助來寫。這和上一章是同一個分工：程式負責擋，文字負責教。

该拒绝什么，怎么拒绝

询问和拒绝

询问是停下来，等人说“行”。拒绝是不等任何人，直接说“不行”，而且每次都用同样的方式说。两者的差别在于能不能被说动。agent 可以说服一个人点头（人也可能自己说服自己），可只要程序还在运行，agent 就没法说服它收回那个“不”。

正因为这样，两者各管不同的事。拒绝管的是不许发生的事，也就是你绝不会批准、或者无法撤销的那些。这类事不该让人一百次地说“不”，程序说一次，以后每次都这么说就行了。询问管的是要靠人判断、而且很少出现的事，因为弹框只有少到有人肯读，才管用。所以要把它花在值得人去关注的地方。

真正要紧的询问，还得经过一个 agent 自己按不到的渠道送到人面前，因为对话里的弹框可以被“本次会话内允许”关掉。这一点我在两道门：人在哪里审批里再讲。

终端最难守

一条拒绝好不好写，要看是什么工具。编辑工具很容易守，因为路径就是调用里的一个字段，规则写成“拒绝这个路径”就行。

终端就是另一回事了。它是 agent 手里最强的工具，因为你能运行的东西它都能运行。它也是最难守的，因为同一个效果可以有很多种写法，比如重定向、rm、sed -i，或者一个运行另一个脚本的脚本。hook 难道不能直接读命令吗？能，读文本就能抓到常见的写法。它漏掉的，是用变量拼出来的路径，或者先写好、之后再运行的脚本（Hook：每次调用都会经过的执行点）。这样一来，终端上的规则永远到不了“完整”。但这不等于可以不写，只是得老实承认它们能做什么：防的是失误，防不住一个铁了心要绕过去的 agent。

按后果分级

既然没法拦住一切，就按出错的代价来拦，而不是按任务有多难。难的任务可能毫无害处，简单的命令却可能毁掉一整天。按后果分级还有一个好处：代码可以根据路径和命令判断后果，所以你不用手动给每个任务选一个级别。问题是，代码看到的是命令的字面，不是它的效果。分级其实是根据文本做的猜测，后面讲代价的时候我还会回到这一点。

后果 例子 我怎么做
只读 查东西、读文件 不拦
可以撤销的写入 在工作文件夹里编辑、写一份计划 允许，只限在划定的区域内
写进真正的仓库 别人会用到的代码 agent 先在工作区里写。由人审批后，才写回去（两道门：人在哪里审批）

把这张表从上往下读，规律就出来了。出错的代价越大，agent 能自己决定的就越少，到了最高一级，就根本不问了。

以 git 为例

git 的命令在这张表的两头都有，所以是个好例子。在我的配置里，连着一个仓库的时候，git 命令分成三组。

  • 读的放行。status、diff、log 之类永远不拦。
  • add、commit、切换分支这类写操作会被拒绝，但拒绝时会指一条路。拒绝消息里有完整的命令和一个代码，人读完之后，可以在自己的终端里输入一条命令来批准，有时间限制。批准的只是那一条命令，不是笼统的 git。
  • 有些命令 agent 永远批不到，包括 push、开 pull request、reset --hard、clean，以及各种强制选项。这些由人自己来运行。

为什么不干脆全都询问？因为这三组值得不同的对待。读是免费的，写是正常的，但必须被人看到。可 push 或 hard reset 这类事，正是第一百次点击会放过去的，所以对它们只能拒绝。

把理由写给 agent 看

一条拒绝有两个读者：你，和 agent。其中更要紧的是 agent，因为读这条消息、决定下一步怎么办的是它。

如果消息只说“拒绝”，结果无非两种：agent 再试一遍同样的事，或者换一个更糟的办法。好的消息能避免这种情况：它会用一句话说清为什么被拒绝，再告诉 agent 该改做什么。

比如，agent 在计划还没获批的时候就往代码文件夹里写东西。好的理由会告诉它，计划还没获批（计划审批是两道门：人在哪里审批里的第一道关卡），它应该先写计划，然后停下来，请人在自己的终端里审批。这下 agent 知道下一步该做什么了，就会照着走，而不是去找旁门。

我写每一条拒绝，都当它是 agent 能得到的唯一帮助。这和上一章是同一个划分：代码负责拦，文字负责教。

What refusing costs, and where it falls short

Refusing has a price of its own. A refusal that is too wide stops real work, and the agent cannot argue its way past it. So keep the patterns narrow, keep a way for a person to approve what is wrong to refuse, and read the logs to see which rule fires.

Does that leave the box with no use at all? Not quite. I keep some "needs a person" steps as a reminder, but I never count them as protection, because anything that must hold gets a refusal.

The terminal patterns judge a command by its words, not by what it does. So they are always behind, and a new spelling will get through. The grade I said I would come back to has the same weakness, so a command that looks harmless can still do harm once its grade has let it through. For the things that must never be touched, then, do not rely on a pattern at all. Do not give the agent the thing (Least privilege).

One limit is in my own evidence. I have no numbers on approval fatigue, only what I and many others see and what the platform docs warn about.

拒絕要付出什麼，又在哪裡不夠

拒絕本身也有代價。拒絕得太寬，連正常的工作也會擋下來，而 agent 吵不贏它。所以規則要寫窄，要留一條路，讓人能批准那些本來不該拒絕的事，還要看日誌，知道是哪條規則在觸發。

那詢問框是不是就完全沒用了？也不是。有些「需要人」的步驟我留著當提醒，但從不把它們算作保護，因為一定要守住的事，都用拒絕來守。

還有一個限度出在字面上。終端機上的拒絕規則按指令的字面判斷，不是按它實際做了什麼，這就表示它們永遠慢一步：新的寫法總會漏過去。前面說要回來講的分級，也有同樣的弱點，所以一個看起來無害的指令，分級放行之後照樣可能造成傷害。對那些絕對不能碰的東西，就完全不要靠規則，乾脆別把它交給 agent（有些東西根本不給）。

還有一個限度在我自己的證據上。批准疲勞我沒有數字，只有我和很多人看過的情況，以及平台文件的提醒。

拒绝要付出什么，又在哪里不够

拒绝本身也有代价。拒绝得太宽，就会挡住正常的工作，而 agent 没法靠争辩绕过去。所以拒绝规则要写窄，要留一条路，让人能批准那些本不该被拒绝的事，还要读日志，看是哪条规则触发了。

那弹框是不是就一点用都没有了？也不是。我保留了一些“需要人”的步骤，当作提醒，但从不把它们算作保护，因为凡是必须成立的事，都用拒绝来守。

还有一个限度出在字面上。终端上的拒绝规则按字面判断一条命令，而不是看它实际做了什么，这就意味着它们总是落在后面：新的写法总能漏过去。前面说要回来讲的分级，也有同样的弱点，所以一条看起来无害的命令，分级放行之后照样可能造成伤害。对那些绝不能碰的东西，就根本不要依赖拒绝规则，干脆别把它交给 agent（有些东西根本不给）。

还有一个限度在我自己的证据上。审批疲劳我没有数字，只有我和很多人见过的情况，以及平台文档的警告。

Why the docs point to a sandbox Industry practice

If asking wears out and refusal patterns fall behind, where else can you turn? VS Code's security page answers with sandboxing, and recommends it over relying on approval rules alone. It is just as cautious about approvals themselves. It suggests scoping auto-approval to the session rather than the workspace or the user, and it calls model-assisted permissions "not a security boundary" (security). That fits this chapter's split: asking is a convenience, refusing is a rule, and isolation is stronger than both.

Isolation also attacks approval fatigue at the root. Inside a sandbox the agent may be allowed far more without asking, so there are fewer boxes to click. Anthropic reports that in its internal use of Claude Code, sandboxing "safely reduces permission prompts by 84%", and that it needs both file system and network isolation to work (Claude Code sandboxing). That is Anthropic's own number for its own tool. I have not tested the sandbox VS Code offers.

文件為什麼指向沙箱 業界做法

既然詢問會慢慢失效，拒絕的規則又永遠慢一步，還能靠什麼？VS Code 的 security 頁面給出的答案是沙箱，並且建議優先用它，不要只靠批准規則。對批准本身，它也一樣謹慎，建議把自動批准限定在會話範圍，不要開到工作區或使用者層級，並且說模型輔助的權限「不是安全邊界」（security）。這和本章的分工是一致的：詢問是方便，拒絕才是規則，而隔離比兩者都強。

隔離還能從根上解決批准疲勞。在沙箱裡，agent 可以不問就被允許做更多事，要點的詢問框自然就少了。Anthropic 說，它內部使用 Claude Code 時，沙箱「安全地減少了 84% 的權限提示」，而且要同時有檔案系統和網路的隔離才行（Claude Code sandboxing）。這是 Anthropic 對自己工具的數字。VS Code 提供的沙箱，我沒有測過。

文档为什么指向沙箱 业界做法

既然询问会慢慢失效，拒绝规则又总落在后面，还能靠什么？VS Code 的安全页面给出的答案是沙箱，并且建议优先用它，而不是单靠审批规则。对审批本身，它也一样谨慎，建议把自动审批限制在会话范围，而不是工作区或用户范围，并且说模型辅助的权限“不是安全边界”（security）。这和本章的划分是吻合的：询问是图方便，拒绝才是规则，而隔离比两者都强。

隔离还能从根上解决审批疲劳。在沙箱里，可以允许 agent 不经询问做得多得多，要点的弹框自然就少了。Anthropic 报告说，在它内部使用 Claude Code 时，沙箱“安全地把权限提示减少了 84%”，而且需要文件系统和网络两方面的隔离才能起作用（Claude Code sandboxing）。这是 Anthropic 对它自己工具的数字。VS Code 提供的沙箱，我没有测过。

When the refusal patterns can go Industry practice

A sandbox is also what decides when my own patterns can go. My refusal patterns for the terminal exist because I do not have a real sandbox. If your agent runs inside a container or a locked-down environment where it can reach only what you chose, most of them can go, because the boundary does the work. The grading by consequence stays either way, since it is a way of thinking, not a feature.

The other way out runs through the platform. If it lets you write refusals in its own permission settings, so that they hold in every mode, move your hook rules there and keep the reasons.

這些拒絕規則什麼時候可以刪掉 業界做法

我自己的這些規則什麼時候能刪，也要看沙箱。我在終端機上寫的拒絕規則之所以存在，是因為我沒有真正的沙箱。如果你的 agent 跑在容器或鎖死的環境裡，只能碰到你選好的東西，大部分規則就可以刪，因為邊界已經在做這份工作了。按後果分級則無論如何都會留著，因為它是一種想法，不是一個功能。

另一條出路在平台那邊。如果平台讓你在它自己的權限設定裡寫拒絕，使它在每種模式下都有效，就把你的 hook 規則搬過去，原因保留。

这些拒绝规则什么时候可以删掉 业界做法

我自己的这些拒绝规则什么时候能删，也要看沙箱。我为终端写的拒绝规则之所以存在，是因为我没有真正的沙箱。如果你的 agent 运行在容器或者锁得很死的环境里，只能碰到你选定的东西，那这些规则大多可以去掉，因为边界已经在起作用了。按后果分级则无论如何都会留下，因为它是一种思路，不是一项功能。

另一条出路在平台那边。如果平台允许你在它自己的权限设置里写拒绝规则，让它在每种模式下都有效，就把你 hook 里的规则挪过去，并保留那些理由。
