Troubleshooting排錯Agent 出问题了，先查哪里？

This appendix is for the day something goes wrong. Find your symptom, do the first check, then read the chapter it points to. Everything here comes from the chapters and the harness docs, so each piece is advice I can point to. It is not a complete list of causes.

這個附錄是給出事的那一天用的。先找到你的症狀，做第一個檢查，再去讀它指向的那一章。這裡的內容都來自各章和 harness 的文件，所以每條建議我都指得出出處，但這份附錄不是一份完整的原因清單。

这个附录是给出问题那天用的。先找到你的症状，做第一项检查，再去读它指向的那一章。这里的内容都来自各章和 harness 的文档，所以每条建议我都能指出出处，但这份附录不是一份完整的原因清单。

How to use it

Two rules apply to almost every symptom.

  • Look at what happened, not at what the agent said. The agent's account of its own work can be wrong, but a log can be checked (Record what happened).
  • Change one thing, then run the same task again. Otherwise you cannot tell which change helped (Fixed tasks, scored by a script).

Find your symptom by what you see:

  • A rule is not followed: ignored, dropped in a long chat.
  • A skill is not used: never used.
  • A hook is silent or too strict: did not fire, refuses real work.
  • The agent will not stop, or stops badly: goes in circles, says done too early.
  • The bill is high: the bill.
  • You cannot tell what happened: no record.

怎麼用

有兩條規則，幾乎每個症狀都用得上。

  • 看發生了什麼，不要看 agent 說了什麼。agent 對自己工作的說法可能是錯的，紀錄卻可以檢查（記下發生了什麼，不是 agent 說了什麼）。
  • 一次只改一樣，然後再跑同一個任務。不然你分不出是哪個改動有幫助（固定的任務，用腳本打分）。

照你看到的現象找症狀：

  • 規則沒被遵守：被無視、在長對話裡被丟掉。
  • skill 沒被用到：從沒用到。
  • hook 沒有反應或太嚴：沒有觸發、拒絕了真正的工作。
  • agent 停不下來，或停得很糟：一直繞圈、太早說做完了。
  • 帳單很高：帳單。
  • 你說不出發生了什麼：沒有紀錄。

怎么用

有两条规则，几乎每个症状都用得上。

  • 看实际发生了什么，不要看 agent 说了什么。agent 讲自己做了什么，可能讲错，日志却是可以核对的（别信 Agent 的总结，看日志）。
  • 一次只改一样，然后把同一个任务再跑一遍。不然你分不清是哪个改动起了作用（改了配置，怎么知道是不是变好了？）。

按你看到的现象找症状：

  • 规则没被遵守：被无视、长对话里被丢掉。
  • skill 没被用上：从来没用过。
  • hook 不吭声，或者太严：没触发、拒绝了正常的工作。
  • agent 停不下来，或者停得不对：原地打转、太早说做完了。
  • 账单太高：账单。
  • 你分不清发生了什么：没有记录。

Rules and instructions

The agent ignores a rule {#rule-ignored}

Check first. Is the rule actually loaded? To find out, open a new chat and ask a question only your rules can answer (A minimal harness). If it is loaded, go through the usual causes in order: the file is too long, two rules conflict, the rule sits far from where it applies, it gives no reason, or it is only a request. If the rule must hold, move it into code.

Chapter. Instructions and skills, section "Why a written rule is ignored", then A rule in a prompt is a request.

The rules file is long and getting worse {#rules-rot}

Check first. Ask of every line whether the agent would get it wrong without it. Cut the lines that fail, then run the same task and see whether anything got worse. Keep each rule in one place, too.

Chapter. A minimal harness, "How the starter set goes wrong", and Instructions and skills.

A rule is followed in a short chat and dropped in a long one {#rule-drift}

Check first. Look at how far the rule now sits from the work. A rule written in the first message is far away after hours of work, so put it nearer by loading it from a file or having a hook repeat a few lines. A cheap test is to ask the agent, after an hour, to state the rule.

Chapter. Long chats get worse and Instructions and skills.

規則和指令

agent 無視一條規則 {#rule-ignored}

先檢查。這條規則真的載入了嗎？要弄清楚，就打開新的對話，問一個只有你的規則才答得出的問題（30 分鐘搭一個最小 harness）。如果載入了，就依序把常見的原因過一遍：檔案太長、兩條規則衝突、規則離它適用的地方太遠、沒有給理由，或者它只是一個請求。這條規則要是必須成立，就把它搬進程式碼。

章節。指令與 skill：只載入需要的，「寫下來的規則為什麼會被無視」一節，然後是 提示裡的規則只是請求。

規則檔很長，而且越來越糟 {#rules-rot}

先檢查。對每一行都問一句：沒有它，agent 會做錯嗎？答案是『不會』的那幾行就刪掉，然後跑同一個任務，看有沒有變差。另外，每條規則只放在一個地方。

章節。30 分鐘搭一個最小 harness 的「這組入門設定會在哪裡出問題」，以及 指令與 skill：只載入需要的。

規則在短對話裡被遵守，在長對話裡被丟掉 {#rule-drift}

先檢查。看看這條規則現在離手上的工作有多遠。寫在第一則訊息裡的規則，工作好幾個小時之後就離得很遠了，所以要把它放近一點：依檔案載入，或者讓 hook 重複其中幾行。還有一個便宜的測試：過了一個小時，請 agent 說出這條規則。

章節。長對話會變差 和 指令與 skill：只載入需要的。

规则和指令

agent 无视一条规则 {#rule-ignored}

先查什么。这条规则真的加载了吗？要弄清楚，就开一个新对话，问一个只有你的规则才答得出的问题（30 分钟搭一个最小 harness）。如果加载了，就按顺序把常见原因过一遍：文件太长，两条规则冲突，规则离它适用的地方太远，没有给理由，或者它只是个请求。这条规则要是必须成立，就把它挪进代码里。

章节。规则写太多，Agent 反而记不住，“4. 写下来的规则为什么会被无视”一节，然后是为什么 Agent 不听 prompt 里的规则？。

规则文件很长，而且越来越差 {#rules-rot}

先查什么。对每一行都问一句：没有它，agent 会不会做错？通不过的行删掉，再跑同一个任务，看有没有变差。另外，每条规则只放在一个地方。

章节。30 分钟搭一个最小 harness的“这套入门配置会在哪里出问题”，以及规则写太多，Agent 反而记不住。

规则在短对话里遵守，在长对话里被丢掉 {#rule-drift}

先查什么。看看这条规则现在离手头的活有多远。写在第一条消息里的规则，干了几个小时之后就离得很远了，所以要让它离得近一些：按文件加载，或者让 hook 重复其中几行。还有个便宜的测试：干了一个小时以后，让 agent 把这条规则复述一遍。

章节。对话越久，Agent 越笨和规则写太多，Agent 反而记不住。

Skills

A skill is never used {#skill-not-loaded}

Check first. Open a new chat, since an old one may already hold the skill, and ask in the words a person would use rather than typing the skill's name. Then look at which skills were loaded, using the platform's log if it has one. If the skill did not load, the description lacks the user's words. And if you have many skills, a neighbour may be taking the request, so keep each skill narrow and say what it is not for.

Chapter. Instructions and skills, "Three questions and three tests", and A minimal harness (step 2).

A skill loads when it should not {#skill-too-wide}

Check first. The description is too wide. Narrow it, then turn the neighbouring requests that must not trigger it into test cases.

Chapter. Instructions and skills.

A skill loads but nothing changes {#skill-no-effect}

Check first. Run the same task twice in new chats, once with the skill and once without. If you see no difference, cut the lines that make none, since the agent already knew them. After that, check that the skill is not out of date.

Chapter. Instructions and skills and Skills as workflows.

Skills

一個 skill 從沒被用到 {#skill-not-loaded}

先檢查。打開新的對話，因為舊的對話可能已經載入了這個 skill，然後用一般人會說的話來問，不要輸入 skill 的名稱。接著看載入了哪些 skill，平台有紀錄的話就看紀錄。沒載入，表示描述裡缺了使用者的說法。如果你的 skill 很多，也可能是鄰近的某一個搶走了請求，所以每個 skill 都要保持窄，並寫明它不是做什麼的。

章節。指令與 skill：只載入需要的 的「三個問題，三個測試」，以及 30 分鐘搭一個最小 harness（第 2 步）。

一個 skill 不該載入時載入了 {#skill-too-wide}

先檢查。描述太寬了。把它收窄，再把鄰近、不該觸發它的請求寫成測試案例。

章節。指令與 skill：只載入需要的。

一個 skill 載入了，卻什麼都沒變 {#skill-no-effect}

先檢查。在新的對話裡，把同一個任務跑兩次，一次有 skill，一次沒有。如果看不出差別，就刪掉沒有差別的那幾行，因為 agent 本來就知道。之後再檢查這個 skill 有沒有過時。

章節。指令與 skill：只載入需要的 和 把團隊的做法寫成 skill。

Skill

skill 从来没被用上 {#skill-not-loaded}

先查什么。开一个新对话，因为旧对话里可能已经装着这个 skill，然后用一个人平常会说的话去问，不要输入 skill 的名字。接着看加载了哪些 skill，平台有日志的话就看日志。没加载，说明描述里缺了用户的说法。如果你的 skill 很多，也可能是旁边的某一个抢走了请求，所以每个 skill 都要保持狭窄，并写明它不管什么。

章节。规则写太多，Agent 反而记不住的“三个问题，三个测试”，以及30 分钟搭一个最小 harness（第 2 步）。

skill 不该加载的时候加载了 {#skill-too-wide}

先查什么。描述太宽了。把它收窄，再把那些不该触发它的相邻请求写成测试用例。

章节。规则写太多，Agent 反而记不住。

skill 加载了，但什么都没变 {#skill-no-effect}

先查什么。在新对话里把同一个任务跑两遍，一遍带 skill，一遍不带。看不出差别的话，就删掉那些没起作用的行，因为 agent 本来就知道它们。然后再看看这个 skill 是不是已经过时了。

章节。规则写太多，Agent 反而记不住和怎么写一个真正好用的 skill？。

Hooks and refusals

The hook did not fire {#hook-silent}

Check first. Four things can keep a hook silent. They are what I found in October 2026, and they will change.

  • The hook file is read when the window starts, so reload the window after a change.
  • The hooks did not run when I used the command-line mode of Copilot.
  • An organization policy can turn hooks off for a workspace.
  • A setting that looks like an off switch may not stop them in newer sessions.

Then test with the smallest hook your platform allows, one that only appends the event name to a file.

Chapter. Hooks, "What a hook cannot see" and "Three questions and a small test".

The hook fired but the model did not get the message {#hook-lost-message}

Check first. Look at what the model really received, not at what the hook returned. In my case some prompts arrived without the rules, because the platform's own reminders took the slot the hook used (the numbers are in the chapter below).

Chapter. Hooks, the story at the top.

Every tool is refused after I changed the hook {#hook-wont-start}

Check first. If the hook program cannot start (for example, the interpreter is not found), Copilot treats that as a refusal, so no tool can run. All the screen says is that the hook errored. Run the hook command by hand in a terminal to see the real error.

Chapter. A minimal harness and Hooks, "Three ways a hook goes wrong".

A hook that should have blocked a call let it through, with no notice {#hook-timeout}

Check first. Look at how long the hook takes. A hook that runs past its limit is treated as a pass, and nothing tells you so. Measure it and keep the hook cheap.

Chapter. Hooks and Build the enforcement layer like software, which is about deciding in advance whether a failure blocks or lets through.

The agent keeps trying the same refused thing {#refusal-loop}

Check first. Read the refusal reason. A reason that only says "denied" makes the agent retry or try something worse, so rewrite it to say why and what to do instead. But do not explain how to dodge the rule.

Chapter. Hooks (the reason is part of the design) and Asking is not a limit.

A refusal blocks real work {#false-refusal}

Check first. The pattern is too wide. Because the agent cannot argue with a refusal, a false refusal is a stuck task. Narrow the pattern, keep a way for a person to approve what is wrong to refuse, and read the logs to see which rule fired.

Chapter. A rule in a prompt is a request and Asking is not a limit.

The agent got around a rule, or changed the rule files {#rule-bypassed}

Check first. Is the rule in a prompt or in a hook? If it is in a hook, does the hook see the text of the call, or its effect? A hook stops the common spellings, not an agent set on getting around it. Also check that the files holding the rules and the hook are on the guarded list. For things that must never be touched, do not give them to the agent at all.

Chapter. Guard the files that hold the rules and Some things you never hand over.

The agent approved something for itself {#self-approval}

Check first. Test it by asking the agent to run the approval command, and check that it is refused. If the hook that refuses it was removed, edited or failed, an agent that can run commands could approve for itself.

Chapter. Two gates: where a person approves.

Hook 和拒絕

hook 沒有觸發 {#hook-silent}

先檢查。有四件事會讓 hook 沒有反應，都是我 2026 年 10 月的發現，以後會變。

  • hook 檔是在視窗啟動時讀的，所以改了之後要重新載入視窗。
  • 我用 Copilot 的命令列模式時，hook 沒有執行。
  • 組織的政策可以為一個工作區關掉 hook。
  • 一個看起來像關閉開關的設定，在較新的會話裡可能擋不住它們。

這幾點排除之後，再用你的平台允許的最小 hook 測試，例如只把事件名稱附加到一個檔案的那種。

章節。Hooks：每次呼叫都會經過的執行點 的「hook 看不到什麼」和「三個問題和一個小測試」。

hook 觸發了，但模型沒收到訊息 {#hook-lost-message}

先檢查。要看模型真正收到了什麼，而不是 hook 回傳了什麼。我就碰過：有些 prompt 到達時沒有規則，因為平台自己的提醒占掉了 hook 用的位置（數字在下面那一章）。

章節。Hooks：每次呼叫都會經過的執行點，開頭的故事。

我改了 hook 之後，每個工具都被拒絕 {#hook-wont-start}

先檢查。hook 程式要是啟動不了（例如找不到直譯器），Copilot 會當成拒絕，所以沒有任何工具能執行。畫面上只會說 hook 出錯了。想看到真正的錯誤，就在終端機裡手動執行一次 hook 的指令。

章節。30 分鐘搭一個最小 harness 和 Hooks：每次呼叫都會經過的執行點 的「hook 出錯的三種方式」。

一個本來該擋下呼叫的 hook 放行了，而且沒有任何通知 {#hook-timeout}

先檢查。看 hook 跑了多久。執行超過時限的 hook，會被當成通過，而且不會有任何提示。量一量你的 hook 花多久，讓它保持輕量。

章節。Hooks：每次呼叫都會經過的執行點 和 把執行層當軟體來設計，後者講的是事先決定失敗時是擋下還是放行。

agent 一直試同一件被拒絕的事 {#refusal-loop}

先檢查。讀拒絕的原因。原因裡只寫「denied」，agent 就會重試，或去試更糟的事，所以要改寫成說明為什麼，以及該改做什麼。但不要解釋怎麼閃躲這條規則。

章節。Hooks：每次呼叫都會經過的執行點（原因是設計的一部分）和 詢問不是限制。

拒絕擋住了真正的工作 {#false-refusal}

先檢查。樣式太寬了。agent 沒辦法跟拒絕爭辯，所以一次錯誤的拒絕就是一個卡住的任務。把樣式收窄，保留一個讓人批准那些不該被拒絕的事的辦法，再讀紀錄，看是哪條規則觸發的。

章節。提示裡的規則只是請求 和 詢問不是限制。

agent 繞過了一條規則，或改了規則檔 {#rule-bypassed}

先檢查。這條規則在 prompt 裡，還是在 hook 裡？如果在 hook 裡，hook 看到的是呼叫的文字，還是它的效果？hook 擋得住常見的寫法，擋不住一心要繞過它的 agent。也要檢查放規則的檔案和 hook 是不是在受保護的清單上。至於絕不能被碰的東西，根本不要給 agent。

章節。保護規則本身的檔案 和 有些東西根本不給。

agent 自己批准了某件事 {#self-approval}

先檢查。測試一下：請 agent 執行批准的指令，確認它會被拒絕。拒絕它的 hook 一旦被移除、被編輯或失敗了，能執行指令的 agent 就可能為自己批准。

章節。兩道門：人在哪裡批准。

Hook 和拒绝

hook 没触发 {#hook-silent}

先查什么。有四件事会让 hook 不吭声，都是我在 2026 年 10 月发现的，以后会变。

  • hook 文件在窗口启动时读取，所以改完之后要重新加载窗口。
  • 我用 Copilot 的命令行模式时，hook 没有运行。
  • 组织的策略可以对某个工作区关闭 hook。
  • 一个看起来像关闭开关的设置，在较新的会话里可能拦不住它们。

这几点排除之后，再用你的平台允许的最小的 hook 来测，比如只把事件名追加到一个文件里的那种。

章节。硬性规则放在哪？用 hook的“hook 看不到什么”和“三个问题和一个小测试”。

hook 触发了，但模型没收到消息 {#hook-lost-message}

先查什么。要看模型实际收到了什么，而不是 hook 返回了什么。我就遇到过：有些 prompt 到达时没带上规则，因为平台自己的提醒占了 hook 用的那个位置（数字在下面那一章里）。

章节。硬性规则放在哪？用 hook，开头的那个故事。

我改了 hook 之后，所有工具都被拒绝 {#hook-wont-start}

先查什么。hook 程序要是启动不了（比如找不到解释器），Copilot 会把它当作拒绝，于是任何工具都跑不了。屏幕上只会说 hook 出错了。想看到真正的错误，就在终端里手动运行一遍 hook 的命令。

章节。30 分钟搭一个最小 harness和硬性规则放在哪？用 hook的“hook 出问题的三种方式”。

本该拦住一次调用的 hook，悄悄放它过去了 {#hook-timeout}

先查什么。看 hook 跑了多久。超出时限的 hook 会被当作通过，而且没有任何提示。量一量你的 hook 要跑多久，让它保持轻量。

章节。硬性规则放在哪？用 hook和hook 自己出故障了怎么办？，后者讲的是事先决定一次失败是拦截还是放行。

agent 一直重试同一件被拒绝的事 {#refusal-loop}

先查什么。读一读拒绝的理由。理由里只写“已拒绝”，agent 就会重试，或者去试更糟的办法，所以要把理由改成说明为什么、该改做什么。但不要解释怎么绕开这条规则。

章节。硬性规则放在哪？用 hook（理由是设计的一部分）和“先问我”为什么挡不住 Agent？。

一次拒绝挡住了正常的工作 {#false-refusal}

先查什么。匹配模式太宽了。agent 没法和拒绝争辩，所以一次误拒就是一个卡住的任务。把匹配模式收窄，留一条路让人批准那些不该拒绝的事，再读日志，看是哪条规则触发的。

章节。为什么 Agent 不听 prompt 里的规则？和“先问我”为什么挡不住 Agent？。

agent 绕过了一条规则，或者改了规则文件 {#rule-bypassed}

先查什么。这条规则是在 prompt 里，还是在 hook 里？如果在 hook 里，hook 看到的是调用的文字，还是调用的效果？hook 拦得住常见的写法，拦不住一心要绕开它的 agent。还要检查存放规则的文件和 hook 是否在受保护的名单上。至于那些绝不能碰的东西，干脆不要交给 agent。

章节。别让 Agent 改自己的规则和不要开放全部的权限或使用沙箱。

agent 替自己批准了某件事 {#self-approval}

先查什么。测一下：让 agent 去运行审批命令，确认它会被拒绝。拒绝这条命令的 hook 一旦被删、被改或者出错，一个能运行命令的 agent 就可能替自己批准。

章节。哪些事必须由人来批？。

Loops, stops and cost

The agent goes in circles {#agent-loops}

Check first. Does anything outside the agent judge that it is stuck? Something should, because the agent itself is the worst judge of that. Put stop rules in code and have them judge from facts: a limit on turns and time, a limit on refusals, no progress over several rounds, a changed plan, checks used up. Also see whether it keeps trying something the guardrails block.

Chapter. Unattended: when it must stop.

A stopped run left the person with a puzzle {#stop-vague}

Check first. Does the stop hand back, in one sentence, why it stopped, where it is, and what a person has to decide? "Ran into a problem" is not enough.

Chapter. Unattended: when it must stop, "What the person coming back should find".

The agent says "done" and the tests fail {#done-too-early}

Check first. Did it run a check and show the command and its output? A claim of "all tests pass" tells you very little by itself. So give it a way to run the checks inside its loop, and let the run end on facts (steps ticked, a counted check passed) rather than on the agent's word.

Chapter. Let the agent check its own work and Unattended: when it must stop, "When 'done' comes too early".

Subagent usage does not add up {#subagent-usage}

Check first. A tool often shows the usage of the main conversation only. Check whether yours counts subagents too. Remember also that each subagent starts with an empty context and reads from zero, so several of them cost several times one agent. A limit on how many start is not a budget.

Chapter. Use subagents sparingly, "What the extra cost bought, and what else it costs", and Unattended: when it must stop, section "A budget is a total, not a count".

The bill is higher than expected {#bill}

Check first. Start with what the agent reads. Every turn rereads the whole context, so what is read matters more than how clever the model is. Look at tool results and loaded rules first, then at how often a task is redone. When you cut, stop short of the point where tasks fail and are thrown away. Check the usage numbers of one whole run, not one message. Cached context is billed at a lower rate (Anthropic's docs: about a tenth of the base price), though I have not verified that on Copilot, so look at what your own plan shows.

Chapter. Don't pick a model by token price alone, How does an Agent actually work? and Context is a budget.

循環、停止和成本

agent 一直繞圈 {#agent-loops}

先檢查。在 agent 之外，有沒有東西在判斷它是不是卡住了？應該要有，因為卡住的 agent 恰恰最不適合自己下這個判斷。把停止規則放進程式碼，讓它從事實來判斷：輪數和時間的上限、拒絕次數的上限、好幾輪都沒有進展、計劃改了、檢查次數用完。也看看它是不是一直在試護欄擋住的事。

章節。無人值守：什麼時候必須停。

執行停下來了，人卻不知道為什麼 {#stop-vague}

先檢查。這次停止有沒有用一句話交回為什麼停、停在哪裡，以及人要決定什麼？只說一句「遇到問題」是不夠的。

章節。無人值守：什麼時候必須停 的「回來的人該看到什麼」。

agent 說「做完了」，測試卻失敗 {#done-too-early}

先檢查。它有沒有執行檢查，並給出指令和輸出？一句「所有測試都通過」，本身說明不了什麼。所以要給它一個在自己循環裡執行檢查的辦法，並讓運行以事實收尾（步驟打勾、算數的檢查通過），而不是以 agent 的一句話收尾。

章節。讓 agent 能檢查自己的活 和 無人值守：什麼時候必須停 的「『做完了』說得太早」。

子 agent 的用量加不起來 {#subagent-usage}

先檢查。工具通常只顯示主對話的用量。確認一下你的工具有沒有把子 agent 也算進去。也要記得，每個子 agent 都從空的上下文開始、從零讀起，所以好幾個子 agent 的花費就是一個的好幾倍。也正因為這樣，光限制能啟動幾個，並不等於有了預算。

章節。慎用子 agent 的「多花的錢換到了什麼，拆分還有哪些代價」，以及 無人值守：什麼時候必須停 的「預算是總量，不是次數」一節。

帳單比預期高 {#bill}

先檢查。先看 agent 讀了什麼。每一輪都會重讀整個上下文，所以讀了什麼，比模型多聰明更重要。先看工具結果和載入的規則，再看任務被重做的頻率。砍的時候要停在任務開始失敗、被整個丟掉之前。看用量要看一整次運行，不是一則訊息。快取的上下文用較低的費率計費（Anthropic 的文件：約基本價格的十分之一），不過這一點我沒有在 Copilot 上驗證過，所以請看你自己的方案顯示什麼。

章節。選模型，別只看 token 單價、Agent 到底是怎麼做事的？ 和 上下文是一份預算。

循环、停止和成本

agent 原地打转 {#agent-loops}

先查什么。agent 之外，有没有东西在判断它是不是卡住了？应该有，因为卡住的 agent 自己恰恰最不适合做这个判断。把停止规则放进代码，让它根据事实来判断：轮数和时间的上限，拒绝次数的上限，几轮下来没有进展，计划变了，检查次数用完。还要看看它是不是一直在试护栏拦着的事。

章节。让 Agent 自己跑一晚上，怎么让它该停就停？。

运行停下了，人却不知道为什么 {#stop-vague}

先查什么。停下的时候，有没有用一句话交回为什么停、停在哪、人要决定什么？光说一句“遇到了问题”是不够的。

章节。让 Agent 自己跑一晚上，怎么让它该停就停？的“回来的人该看到什么”。

agent 说“做完了”，测试却失败 {#done-too-early}

先查什么。它跑过检查吗，给出命令和输出了吗？一句“所有测试都通过”，本身说明不了什么。所以要让它能在自己的循环里运行检查，并让这次运行以事实结束（步骤打了勾，一次计数的检查通过了），而不是以 agent 的话结束。

章节。让 Agent 自己跑测试和让 Agent 自己跑一晚上，怎么让它该停就停？的“‘做完了’说得太早”。

子 agent 的用量对不上 {#subagent-usage}

先查什么。工具往往只显示主对话的用量。看看你的工具有没有把子 agent 也算进去。还要记住，每个子 agent 都从空白的上下文开始、从零读起，所以几个子 agent 的成本就是单个的好几倍。也正因为这样，光限制能开几个，并不等于有了预算。

章节。别跟风瞎用子 Agent的“多花的钱换来了什么，拆分还有哪些代价”，以及让 Agent 自己跑一晚上，怎么让它该停就停？的“预算是总量，不是次数”一节。

账单比预想的高 {#bill}

先查什么。先看 agent 读了什么。每一轮都会把整个上下文重读一遍，所以读了什么，比模型多聪明更要紧。先看工具返回的结果和加载的规则，再看任务被重做的频率。削减的时候要停在任务开始失败、被整个扔掉之前。看用量要看一整次运行，不要只看一条消息。缓存的上下文按较低的价格计费（Anthropic 文档：约为基础价格的十分之一），不过这一点我没有在 Copilot 上验证过，所以请看你自己的套餐显示什么。

章节。选模型，别只看 token 单价、Agent 到底是怎么干活的？和为什么不能把所有规则都塞给 Agent？。

Checks

The checks never pass {#checks-never-pass}

Check first. Read the findings. If each round brings new findings, the loop is open-ended, so use a limit and let the person extend or waive it. Findings that do not point to a real file and line are noise. If the verdict is wrong, a false FAIL sends the author to fix a problem that is not there. And if edits keep cancelling earlier passes, the fingerprint of the work may include too much, such as progress notes.

Chapter. Make a pass count and Can a model check a model?.

Checks are on, but nothing was checked {#checks-silent}

Check first. The agent may simply never have called the checker, and then no FAIL is ever recorded. A rule in a prompt will not catch this. Put the check at a point the agent must pass, such as the moment it tries to stop.

Chapter. Make a pass count, "Checks on, but nothing checked".

A test passes sometimes and fails sometimes {#flaky}

Check first. A test that fails at random sends the agent hunting for a bug that is not there, or teaches it to rerun until green. Fix it or drop it. If the full suite is slow, give the agent a fast subset to run often.

Chapter. Let the agent check its own work.

Two runs of the same task give different results {#variance}

Check first. That is normal. Run the task several times, look at the spread, and read the runs that failed. One run proves nothing. What is not normal is a spread so wide that no result can be trusted. When you see that, the task is too loose or the check is too weak, and that is what to fix first.

Chapter. One run proves nothing.

檢查

檢查一直過不了 {#checks-never-pass}

先檢查。讀一讀發現的問題，可能是下面幾種情況。一種是每一輪都帶來新的發現，表示這個循環沒有終點，這時要設一個上限，讓人決定延長還是豁免。也可能發現沒有指向真實的檔案和行號，那就是雜訊。還可能結論本身是錯的，錯誤的 FAIL 會讓作者去修一個不存在的問題。最後，如果編輯一直抵銷先前的通過，可能是這份工作的指紋包含了太多東西，例如進度筆記。

章節。讓「通過」可信 和 模型能檢查模型嗎。

檢查開著，卻什麼都沒檢查 {#checks-silent}

先檢查。agent 可能根本從沒呼叫過檢查者，那就永遠不會有 FAIL 被記下。prompt 裡的規則抓不到這個。要把檢查放在 agent 必須經過的地方，例如它想停下來的那一刻。

章節。讓「通過」可信 的「檢查開著，卻什麼都沒檢查」。

一個測試有時通過、有時失敗 {#flaky}

先檢查。隨機失敗的測試，會讓 agent 去找一個不存在的 bug，或教會它一直重跑到變綠為止。要嘛修好它，要嘛丟掉它。如果完整的測試很慢，就給 agent 一個快的子集，讓它常常執行。

章節。讓 agent 能檢查自己的活。

同一個任務跑兩次，結果不同 {#variance}

先檢查。這是正常的。把任務跑好幾次，看看結果差了多少，再讀失敗的那幾次運行。一次運行證明不了什麼。不正常的，是差距大到沒有哪個結果可以信。遇到這種情況，就表示任務太鬆，或檢查太弱，應該先修這個。

章節。一次運行證明不了什麼。

检查

检查一直通不过 {#checks-never-pass}

先查什么。读一读发现的问题，可能是下面几种情况。一种是每一轮都冒出新问题，说明这个循环没有尽头，这时要设一个上限，让人来决定延长还是豁免。也可能发现的问题没有指向真实的文件和行号，那就是噪音。还可能结论本身是错的，一次误报的 FAIL 会让作者去修一个不存在的问题。最后，如果改动不断抵消之前的通过，可能是这份工作的指纹包含的东西太多，比如进度笔记。

章节。Agent 说“测过了”，能信吗？和让另一个模型来审，靠得住吗？。

检查开着，却什么都没检查 {#checks-silent}

先查什么。agent 可能压根没调用过检查者，那样就永远不会记下 FAIL。prompt 里的规则抓不住这种情况。要把检查放在 agent 必须经过的地方，比如它想停下的那一刻。

章节。Agent 说“测过了”，能信吗？的“检查开着，却什么都没检查”。

一个测试有时过、有时不过 {#flaky}

先查什么。随机失败的测试，会让 agent 去找一个不存在的 bug，或者教会它反复重跑，直到变绿为止。要么修好它，要么去掉它。如果完整的测试集太慢，就给 agent 一个能经常跑的快速子集。

章节。让 Agent 自己跑测试。

同一个任务跑两次，结果不同 {#variance}

先查什么。这很正常。把任务多跑几次，看看波动有多大，再读那些失败的运行。一次运行证明不了什么。不正常的，是波动大到没有哪个结果可信。遇到这种情况，说明任务太松，或者检查太弱，应该先把这个修好。

章节。同一个任务跑两次，结果不一样。

Context and memory

A long chat got worse {#long-chat}

Check first. Do not rely on the model to remember. Write what matters into a file, then start a fresh chat from that file. To test whether you did, ask what you would lose if this chat disappeared now. If chats get long because the task is too big, the fix is a smaller task.

Chapter. Long chats get worse.

The notes or memory file says something false {#notes-wrong}

Check first. Treat notes as the agent's report and check the ones that matter against the source. Keep the notes short and cut what is done, because a growing notes file fills the window. Memory that an agent writes should carry a source and a date, and a person should review it.

Chapter. Long chats get worse and What an agent should remember.

The agent obeyed text it read in a file or a web page {#injection}

Check first. Count the three circles of risk: can it read private data, does it read untrusted text, and can it send data out? Remove any one of them. Keep in mind that a summary of untrusted text is untrusted too. Re-check whenever you add a tool.

Chapter. Text the agent reads can give it orders and What should you think through before connecting an MCP server?.

上下文和記憶

長對話變差了 {#long-chat}

先檢查。不要靠模型記住。把重要的寫進檔案，再從那個檔案開一個新的對話。想知道寫夠了沒有，就問自己：如果這個對話現在消失，你會失去什麼？如果對話變長是因為任務太大，解法是更小的任務。

章節。長對話會變差。

筆記或記憶檔說了假的東西 {#notes-wrong}

先檢查。把筆記當成 agent 的報告，重要的幾條對照來源檢查一遍。筆記要短，做完的就刪掉，因為越長越大的筆記檔會塞滿視窗。agent 寫的記憶，應該帶有來源和日期，並由人審查。

章節。長對話會變差 和 agent 該記住什麼。

agent 服從了它在檔案或網頁裡讀到的文字 {#injection}

先檢查。數一數風險的那三個圈，也就是下面三個問題：它能不能讀私人資料？它有沒有讀不可信的文字？它能不能把資料送出去？三個裡去掉任何一個。要記得，不可信文字的摘要也是不可信的。每加一個工具，就要重新檢查一遍。

章節。agent 讀到的文字可能在指揮它 和 接 MCP server 之前，要想清楚什麼？。

上下文和记忆

长对话变差了 {#long-chat}

先查什么。别指望模型记得住。把要紧的写进文件，再从这个文件开一个新对话。想知道写够了没有，就问问自己：如果这个对话现在消失，会丢掉什么？如果对话变长是因为任务太大，解法是把任务变小。

章节。对话越久，Agent 越笨。

笔记或记忆文件里写了不实的内容 {#notes-wrong}

先查什么。把笔记当作 agent 的报告，要紧的几条对照源头核对一遍。笔记要短，做完的就删掉，因为不断变长的笔记文件会把窗口填满。agent 写的记忆应当带上来源和日期，并由人来审查。

章节。对话越久，Agent 越笨和让 Agent 记住经验，怎么防它记错？。

agent 听从了它在文件或网页里读到的文字 {#injection}

先查什么。数一数风险的那三个圈，也就是下面三个问题：它能读私有数据吗？它读不可信的文本吗？它能把数据发出去吗？三个里去掉任意一个。要记住，不可信文本的摘要也是不可信的。每加一个工具，都要重新检查一遍。

章节。Agent 读到的网页和文件，可能在给它下命令和接 MCP server 之前，要想清楚什么？。

Seeing what happened

I cannot tell what the agent did {#cannot-tell}

Check first. Is there a record, written by code, of every call and every refusal? If there is, read the trace of a failed run, not the agent's summary. Even then, a hook sees only what the platform shows it, so a clean log can still have a hole.

Chapter. Record what happened, not what the agent said and A report a person can read in five minutes.

A new model made things worse {#model-upgrade}

Check first. An upgrade is not better at every task, so rerun your fixed tasks. Then remove old rules and steps one at a time, running the evals after each.

Chapter. When the model is upgraded, delete.

看見發生了什麼

我說不出 agent 做了什麼 {#cannot-tell}

先檢查。有沒有一份由程式碼寫的紀錄，記下每個呼叫和每個拒絕？有的話，就讀失敗那次運行的軌跡，不要讀 agent 的摘要。即使這樣，hook 也只看得到平台給它看的東西，所以乾淨的紀錄仍然可能有洞。

章節。記下發生了什麼，不是 agent 說了什麼 和 一份五分鐘讀得完的報告。

新模型讓事情變糟 {#model-upgrade}

先檢查。升級不是在每個任務上都更好，所以先重跑你的固定任務。然後一次刪掉一條舊的規則或步驟，每刪一次都執行一次評測。

章節。模型升級了，就要刪。

看清发生了什么

我分不清 agent 做了什么 {#cannot-tell}

先查什么。有没有一份由代码写下的记录，涵盖每次调用和每次拒绝？有的话，就去读失败那次运行的轨迹，不要读 agent 的总结。即便如此，hook 也只能看到平台给它看的东西，所以干净的日志里仍然可能有个洞。

章节。别信 Agent 的总结，看日志和Agent 干完活，你该看什么？。

换了新模型，反而更糟 {#model-upgrade}

先查什么。升级并不是在每个任务上都更好，所以先把你的固定任务重跑一遍。然后一次删一条旧规则或旧步骤，每删一次都跑一遍评测。

章节。换了新模型，旧规则该删了。
