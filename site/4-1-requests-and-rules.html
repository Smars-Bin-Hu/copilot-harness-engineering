This chapter assumes you have read Hooks, so you know that a hook is code that tool calls pass through and that it can refuse the call.

這一章假設你已經讀過 Hooks：每次呼叫都會經過的執行點，知道 hook 是工具呼叫都要經過的程式碼，可以拒絕這次呼叫。

这一章默认你已经读过 硬性规则放在哪？用 hook，知道 hook 是工具调用必经的一段代码，可以拒绝这次调用。

The Knowledge經驗分享经验分享

In one sentence

A rule in a prompt is only a request; a rule in code is a rule. Start with words, then move a rule into code when it keeps being broken or the harm cannot be undone.

The concern here is how firmly a rule is held, a matter of safety. A different question is who, or what, can make a judgment most cheaply, which is the subject of Who decides.

一句話

寫在提示裡的規則只是請求；寫在程式碼裡的規則才是規則。先從文字開始，等一條規則一直被違反，或違反的後果無法挽回，再把它搬進程式碼。

這裡關心的是規則守得多牢，說到底是安全的問題。至於一個判斷交給誰、交給什麼來做最便宜，那是另一個問題，誰來判斷：程式、便宜模型、主模型、人會談。

一句话

写在 prompt 里的规则只是请求；写在代码里的规则才是规则。先从文字开始，等一条规则老被违反，或者违反的后果无法挽回，再把它挪进代码。

这里关心的是规则守得有多牢，说到底是安全问题。至于一个判断交给谁、交给什么来做最便宜，那是另一个问题，这个判断该交给谁：代码、便宜模型、主模型，还是人？会讲。

For leaders

  • The decision: which rules may stay as written words, and which must be enforced by code. A rule moves to code when it keeps being broken, when breaking it would do harm that cannot be undone, or when other steps rely on it.
  • The risk: a rule written in a prompt is only a request, which may not even reach the model. In October 2026 I counted a batch of prompts in my own setup. A hook that put my rules at the start of each prompt ran every time, yet many prompts still arrived without them. That is one setup and one batch, not a general rate. I also have no numbers on how often written rules are broken.
  • The cost of doing it right: code has a price, because it must be written, tested and kept up as the platform changes. Most rules do not need it, so you pay that price for a few rules, not for all of them.
  • Ask the team: "Which of our rules would do damage we cannot undo if the agent broke it once, and is each of those held by code, or only written in a prompt?"

給主管

  • 要做的決定：哪些規則可以只留在文字裡，哪些必須由程式碼強制執行。一條規則一直被違反、一旦違反就會造成無法挽回的傷害，或其他步驟依賴它時，就該搬進程式碼。
  • 風險：寫在提示裡的規則只是請求，甚至可能根本送不到模型面前。2026 年 10 月，我數過自己設定裡的一批 prompt：有個 hook 會把我的規則放在每個 prompt 的開頭，它每次都執行了，但還是有很多 prompt 到達時沒有帶著規則。這只是我這一套設定、一批資料，不是一般的比率。寫下來的規則多常被違反，我也沒有數字。
  • 做對的成本：程式碼有成本，因為它要寫、要測，平台變動時還要跟著維護。大多數規則不需要它，所以這筆成本只花在少數幾條規則上，不是全部。
  • 可以問團隊：「我們的規則裡，哪些只要 agent 違反一次，就會造成無法挽回的傷害？其中每一條，是由程式碼守著，還是只寫在提示裡？」

写给管理者

  • 要拍板的事：哪些规则可以只用文字写着，哪些必须由代码强制执行。一条规则老被违反、一旦违反就会造成无法挽回的伤害，或者有别的步骤依赖它，就该挪进代码。
  • 风险：写在 prompt 里的规则只是请求，甚至可能根本到不了模型面前。2026 年 10 月，我数过自己配置里的一批 prompt：有个 hook 会把我的规则放到每条 prompt 的开头，它每次都运行了，可还是有很多 prompt 到达时没带上这些规则。这只是一套配置、一批数据，不是普遍的比率。写下来的规则多久被违反一次，我也没有数字。
  • 做对的代价：代码是有成本的，因为它要写、要测，平台一变还得跟着维护。大多数规则用不着它，所以这笔成本只花在少数几条规则上，不是全部。
  • 可以问团队：“我们的规则里，哪些只要 agent 违反一次，就会造成无法挽回的损害？这些规则每一条，是由代码守着，还是只写在 prompt 里？”

Why does a clear rule still get broken?

You write a rule in the instruction file that says "never touch the generated files". For a week the agent follows it, but then one day it does not. When you go back to the rule, it is still there and still clear. Nothing in the file has changed. What changed is that the agent had other things to think about.

To see how that can happen, look at the rule the way the model sees it. Everything the model reads, from your request to the instruction files and the skills it has loaded, is called the prompt. Inside the prompt your rule is just one sentence among many, which the model weighs against all the others. Sometimes the others win. And the longer the chat, the more of them there are (Long chats get worse).

All of this assumes the rule reaches the model at all, which is not certain either. In Hooks I counted a batch of prompts from my own setup in October 2026. A hook put my rules at the start of each prompt and ran every time, yet many prompts still arrived without them. That is only one setup and one batch, not a general rate, but if even delivering a rule can fail, obeying it can fail more.

So what we call a rule is really two different things that are easy to mix up. The first is a request: you ask the model to behave, and it usually does, though no one can promise it always will. The second is a rule in the strict sense, where code stands in the way. As long as that code runs and sees the call, the call is refused, whatever the model thinks.

Anything that must hold has to be the second kind. But code is not free, and most rules do not need it. So which rule goes where?

寫清楚的規則，為什麼還是會被違反？

你在指令檔裡寫了一條規則，要 agent「絕對不要碰產生出來的檔案」。頭一個星期，agent 都乖乖照做，後來有一天，它還是碰了。你回頭去看那條規則，它還在原處，和當初一樣清楚，因為檔案裡一個字也沒改。不是規則變了，而是 agent 那一刻有別的事要考慮。

這是怎麼發生的？得先從模型的角度看這條規則。模型讀到的所有文字，從你的需求到指令檔，再到它載入的 skill，合起來叫做 prompt。在 prompt 裡，你的規則只是眾多句子中的一句，模型會把它和其他所有句子放在一起權衡。有時候其他句子的分量更重，規則就輸了。而對話拖得越長，跟它搶分量的句子就越多（長對話會變差）。

這一切都還假設規則送得到模型面前，而這一點其實也說不準。在 Hooks：每次呼叫都會經過的執行點裡，我數過 2026 年 10 月自己設定裡的一批 prompt。有個 hook 會把我的規則放在每個 prompt 的開頭，它也每次都執行了，結果還是有很多 prompt 到達時沒有帶著規則。這只是我這一套設定、一批資料，稱不上一般的比率，但既然連傳達規則都可能失敗，遵守規則就更可能失敗。

所以我們平常說的「規則」，其實是兩種很容易搞混的東西。第一種是請求：你請模型照規矩來，它通常會照做，但沒有人能保證它永遠照做。第二種才是嚴格意義上的規則，靠的是擋在路上的程式碼。只要這段程式碼在執行、看得到這次呼叫，不管模型怎麼想，呼叫都會被拒絕。

任何一定要成立的事，都必須是第二種。可是程式碼不是免費的，大多數規則也用不著它。那麼，哪條規則該放在哪裡？

写清楚的规则，为什么还是会被违反？

你在指令文件里写了一条规则，要 agent “绝不要碰生成的文件”。头一个星期，agent 守得好好的，可后来有一天，它还是碰了。你回头去翻那条规则，它还在原处，和当初一样清楚，因为文件里一个字都没变。不是规则变了，而是 agent 那一刻有别的事要考虑。

这是怎么发生的？得先从模型的角度看这条规则。模型读到的全部文本，从你的需求到指令文件，再到它加载的 skill，合起来叫 prompt。在 prompt 里，你的规则只是众多句子中的一句，模型会把它和其他所有句子放在一起掂量。有时候别的句子分量更重，规则就输了。而对话拖得越长，跟它抢分量的句子就越多（对话越久，Agent 越笨）。

这一切还都假设规则能送到模型面前，可这一点同样没准。在 硬性规则放在哪？用 hook里，我数过 2026 年 10 月自己配置里的一批 prompt。有个 hook 会把我的规则放到每条 prompt 的开头，它也确实每次都运行了，可还是有很多 prompt 到达时没带上这些规则。这只是一套配置、一批数据，算不上普遍的比率，但既然连送达都可能失败，遵守就更可能失败。

所以我们平时说的“规则”，其实是两种容易混为一谈的东西。第一种是请求：你请模型守规矩，它多半会守，但谁也不能保证它永远守。第二种才是严格意义上的规则，靠的是挡在路上的代码。只要这段代码在运行、看得到这次调用，不管模型怎么想，调用都会被拒绝。

凡是必须成立的事，都得是第二种。可代码不是免费的，大多数规则也用不着它。那么，哪条规则该放在哪里？

Which rule goes where?

Four levels of firmness

The short answer is that each rule goes on the lowest level that is enough for it. Of the four levels at which a rule can be held, three hold it more firmly the higher you go, which is why they form a ladder. Each level promises something different and has its own limit.

Level What it is What it promises Its limit
Words The rule is written in an instruction file, a skill, or the body of an agent The agent knows the rule and why it exists It may not comply
A command that checks itself The agent does the operation through a small program of yours, which checks the conditions before it acts The same result every time, on any platform It guards only what goes through it. If the agent edits the file by hand, the command is never called
A hook that refuses Code the platform runs before tool calls, which can say no The call is stopped, in the modes I tried, even when no one is watching It depends on the platform, and it sees the call, not the effect (Hooks)
Found afterwards A health check (a command that tests whether the setup is sound), a test run, a read of the logs A breach can be found and counted It cannot prevent anything. It is detection, not prevention

The last level is different in kind, because it does not hold the rule at all but only tells you whether the others held. You need it whatever level a rule sits at, since a rule you cannot see being broken is a rule you are only guessing about.

The two levels in the middle work in opposite ways. A command here is a program you give the agent alongside its built-in tools. Instead of creating the folder, copying the files and writing the state one at a time, the agent runs a single command that does all three. If a precondition is false, the command refuses to start. The rule lives inside the command. A hook works the other way round: the agent does what it likes, while the hook looks at each call before it runs.

When to move a rule up, and how far

Every new rule starts at the bottom, in words, because a sentence is cheap to write and cheap to change, and for most rules the model will follow it. Move a rule up when one of three things is true.

  1. It keeps being broken. You have seen it happen more than once, and a better sentence did not fix it. When a rule is ignored because it sits far back in a long chat, rewording will not help, but code will.
  2. The harm cannot be undone, as with a deleted branch, a pushed commit or an overwritten file nobody backed up. Then one breach is already one too many, so do not wait for the second.
  3. Other parts rely on it. If a later step trusts that the rule held (a "check passed" record, an approval), a broken rule breaks that later step too.

Once a rule has to move, pick the lowest level that is enough. If a command can hold the rule, do not build a hook. Besides being written and tested, a hook has to be kept alive as the platform changes (Enforcement design). Save the hook for when the agent can get to the thing in many ways and you cannot route them all through your command.

Stop with code, teach with text

When a rule moves into code, you might think its sentence has done its job and can go. Keep one, because the two do different jobs. The code does the stopping, without depending on what the model remembers. The text does the teaching, telling the agent why the rule exists and what to do instead before it runs into the wall. Without the text, the agent runs into the refusal again and again and tries other ways round it. Without the code, the text is a request again.

The bridge between the two is the refusal message, which is code that carries a sentence. A good one says why the call was refused and what to do next (Asking is not a limit is about writing these).

It also works the other way. Questions that only a judgment can decide, such as "is this the right requirement?" or "is this change good?", have no pattern to match, so they do not belong in code. They stay as words, checked from outside by an independent reviewer (Use subagents sparingly).

How one rule climbs the ladder

To see what moving a rule up looks like, take a made-up rule of the same kind as the one this chapter opened with. Say the rule is "generated files are never edited by hand". At first it is only words, one line in the instructions that also gives the reason: the files are rebuilt, so hand edits are lost.

Then the rule is broken twice, so you move it up by adding a check at the hook level. Now a call to the edit tool on those paths is refused, with the reason and the command that regenerates the files. That holds for a while, until the agent finds a new gap and writes the file through the terminal instead. So you also add the common spellings of that to the hook, meaning the different ways a terminal command can write the same file. You know the hook will still not catch a script written first and run later. That is why you keep the one sentence of words and add a test that finds changed generated files after the fact.

Notice that on the way up, the rule only gained levels, without losing any of the earlier ones.

A three-minute exercise

Before going on, try this with your own rules. Write down three rules you give your agent today, then ask three questions of each. Is it words, a command, a hook or a check afterwards? Could one breach be undone? Has it been broken twice? The rule to move up first is one held only by words, whose breach could not be undone and which has already been broken twice.

哪條規則該放在哪裡？

牢固程度分四級

簡單地說，每條規則都放在對它來說夠用的最低一級。一條規則可以守在四個層級上，其中三級越往上守得越牢，所以合起來像一道階梯。每一級保證的東西不同，也各有各的限制。

層級 它是什麼 它保證什麼 它的限制
文字 規則寫在指令檔、skill 或 agent 的正文裡 agent 知道這條規則，也知道它存在的理由 它可能不遵守
自己檢查的指令 agent 透過你寫的一個小程式來做這個操作，程式動手之前先檢查條件 在任何平台上，每次都是同樣的結果 它只守經過它的東西。agent 如果手動編輯檔案，這個指令根本不會被呼叫
會拒絕的 hook 平台在工具呼叫之前執行的程式碼，可以說不 呼叫會被擋下；在我試過的模式裡，即使沒有人看著也一樣 它依賴平台，而且它看到的是呼叫，不是效果（Hooks：每次呼叫都會經過的執行點）
事後發現 健康檢查（一個測試設定是否健全的指令）、跑一次測試、讀一遍紀錄 違反可以被發現、被計數 它什麼也預防不了。它是偵測，不是預防

最後一級的性質不一樣，它根本不守規則，只告訴你前面幾級有沒有守住。不管一條規則放在哪一級，你都需要它，因為規則有沒有被違反，你要是看不到，就只能用猜的。

中間兩級的運作方式正好相反。這裡說的指令，是你在 agent 內建工具之外另外給它的一個程式。agent 不必一步步地建資料夾、複製檔案、寫狀態，而是執行一個指令，三件事一次做完。只要有一個前提條件不成立，這個指令就拒絕開始。規則就藏在指令裡面。hook 則反過來：agent 想做什麼就做什麼，hook 在每次呼叫執行之前先看一眼。

什麼時候往上搬，搬到哪一級

每條新規則都從最底層的文字開始，因為一句話寫起來便宜、改起來也便宜，而且對大多數規則，模型都會照做。以下三種情況只要有一種成立，就該把它往上搬。

  1. 它一直被違反。你不只一次看到它被違反，換一句更好的寫法也沒有解決。如果一條規則被無視，是因為它在長對話裡離得太遠，那重新措辭沒有用，得靠程式碼。
  2. 傷害無法挽回，例如被刪掉的分支、推上去的 commit、沒人備份就被覆寫的檔案。這時候違反一次就已經太多，不要等第二次。
  3. 其他部分依賴它。如果後面的步驟相信這條規則守住了（例如一筆「檢查通過」的紀錄、一個批准），那麼規則一破，後面那一步也跟著破。

確定要搬了，就選夠用的最低一級：指令能守住的規則，就不要做 hook。除了要寫、要測，hook 還得跟著平台的變化一直維護下去（把執行層當軟體來設計）。只有當 agent 有很多方式可以碰到那樣東西，而你又無法把它們全部導到你的指令上時，才輪到 hook。

用程式碼擋，用文字教

規則搬進程式碼以後，你也許會覺得那句文字已經完成任務，可以刪了。其實應該留一句，因為兩者做的是不同的事。程式碼負責擋，而且不依賴模型記得什麼。文字負責教，在 agent 撞牆之前，就告訴它這條規則為什麼存在、該改做什麼。沒有文字，agent 會一次又一次撞上拒絕，還會試著繞過去；沒有程式碼，文字又變回請求。

這兩者之間的橋樑，是拒絕時給的訊息。它本身是程式碼，卻帶著一句話。好的拒絕訊息會說明為什麼被拒絕、接下來該做什麼（怎麼寫這類訊息，見詢問不是限制）。

反過來，有些事也不該放進程式碼：只有判斷才能決定的問題，例如這是不是對的需求、這個改動好不好，沒有可以比對的模式。它們仍然留在文字裡，再由獨立的 reviewer 從外面檢查（慎用子 agent）。

一條規則是怎麼一級級往上搬的

往上搬一條規則是什麼樣子？拿一條和本章開頭那條同類的規則來看，假設它是「產生出來的檔案絕不手動編輯」（例子是我編的）。一開始，它只是指令檔裡的一行文字，後面附著理由：這些檔案會被重新產生，手動改的內容會丟掉。

後來這條規則被違反了兩次，你就把它往上搬，在 hook 這一級加一個檢查。從此對這些路徑呼叫編輯工具就會被拒絕，拒絕時附上理由，以及重新產生這些檔案的指令。這樣守了一陣子，直到 agent 找到新的缺口，改用終端機去寫那個檔案，於是你把用終端機寫檔案的幾種常見寫法也加進 hook。你也知道，hook 還是抓不到先寫好一支腳本、之後再執行的情況，所以你留著那一句文字，再加一個測試，事後找出被改過的產生檔案。

回頭看，這條規則一路往上，只多了層級，沒有拿掉哪一層。

三分鐘的小練習

往下讀之前，先拿你自己的規則試試看。寫下你今天給 agent 的三條規則，每一條問三個問題。它是文字、指令、hook，還是事後檢查？違反一次，還能挽回嗎？它被違反過兩次了嗎？最該先往上搬的，是那條只靠文字守著、一旦違反就無法挽回、而且已經被違反過兩次的規則。

哪条规则该放在哪里？

牢固程度分四级

简单地说，每条规则都放在对它来说够用的最低一级。一条规则可以守在四个级别上，其中三级越往上守得越牢，所以合起来像一架梯子。每一级承诺的东西不同，也各有各的限度。

级别 它是什么 它承诺什么 它的限度
文字 规则写在指令文件、skill，或者 agent 的正文里 agent 知道这条规则，也知道它为什么存在 它可能不遵守
自带检查的命令 agent 通过你写的一个小程序来做这个操作，程序动手之前先检查条件 在任何平台上，每次结果都一样 它只守经过它的东西。如果 agent 手动改文件，这个命令根本不会被调用
会拒绝的 hook 平台在工具调用之前运行的代码，可以说不 调用会被拦下；在我试过的模式里，即使没人盯着也是如此 它依赖平台，而且它看到的是调用，不是效果（硬性规则放在哪？用 hook）
事后发现 健康检查（一条用来测试配置是否健全的命令）、一次测试运行、翻一遍日志 违规可以被发现、被计数 它什么也阻止不了。这是检测，不是预防

最后一级的性质不一样，它根本不守规则，只告诉你前面几级守住了没有。不管一条规则放在哪一级，都离不开它，因为规则有没有被违反，你要是看不见，就只能靠猜。

中间两级的路数正好相反。这里说的命令，是你在 agent 的内置工具之外另给它的一个程序。agent 不用一步步地创建文件夹、复制文件、写入状态，而是运行一条命令，把三件事一次做完。只要有一个前提不成立，命令就拒绝开始。规则就藏在命令里面。hook 则反过来：agent 想做什么就做什么，hook 在每次调用运行之前先看一眼。

什么时候往上挪，挪到哪一级

每条新规则都从最底下的文字开始，因为一句话写起来成本低，改起来也容易，而且对大多数规则来说，模型都会遵守。下面三种情况只要有一种成立，就该把它往上挪。

  1. 它老被违反。你不止一次看到它被违反，换一句更好的写法也没解决。如果一条规则被无视，是因为它在长对话里离得太远，那改措辞没用，得靠代码。
  2. 伤害无法挽回，比如删掉的分支、推送出去的提交、没人备份就被覆盖的文件。这种时候违反一次就已经太多，别等第二次。
  3. 别的部分依赖它。如果后面的某一步相信这条规则守住了（比如一条“检查通过”的记录、一次审批），那规则一破，后面那一步也跟着破。

确定要挪了，就选刚好够用的最低一级：一条命令就能守住的规则，就别去造 hook。除了要写、要测，hook 还得跟着平台的变化一直维护下去（hook 自己出故障了怎么办？）。只有当 agent 能从很多条路碰到那个东西，你又没法把这些路都引到你的命令上时，才轮到 hook。

用代码拦，用文字教

规则挪进代码以后，你也许会觉得那句文字已经完成了任务，可以删掉了。其实应该留一句，因为两者干的是不同的活。代码负责拦，而且不依赖模型记得什么。文字负责教，在 agent 撞墙之前，就告诉它这条规则为什么存在、该改做什么。没有文字，agent 会一次又一次撞上拒绝，还会试着绕过去；没有代码，文字又变回了请求。

这两者之间的桥，是拒绝时给出的消息。它本身是代码，却带着一句话。好的拒绝消息会说明为什么被拒绝、接下来该做什么（“先问我”为什么挡不住 Agent？讲的就是怎么写这类消息）。

反过来，有些事也不该放进代码：只能靠判断来决定的问题，比如这是不是对的需求、这个改动好不好，没有可以匹配的模式。它们还是留在文字里，再由独立的 reviewer 从外面检查（别跟风瞎用子 Agent）。

一条规则是怎么一级级往上挪的

往上挪一条规则是什么样子？拿一条和本章开头那条同类的规则来看，假设它是“生成的文件绝不手动编辑”（例子是我编的）。一开始，它只是指令里的一行文字，后面附着理由：这些文件会被重新生成，手动改的内容会丢。

后来这条规则被违反了两次，你就把它往上挪，在 hook 这一级加一条检查。从此对这些路径调用编辑工具就会被拒绝，拒绝时附上理由，以及重新生成这些文件的命令。这样守了一阵子，直到 agent 找到一个新缺口，改用终端去写这个文件，于是你把用终端写文件的几种常见写法也加进 hook。你也知道，hook 还是拦不住先写好一个脚本、之后再运行的做法，所以你留着那一句文字，再加一个测试，事后找出被改动过的生成文件。

回头看，这条规则一路往上，只添了层级，没有去掉哪一层。

三分钟的小练习

往下读之前，先拿你自己的规则试一试。写下你今天给 agent 的三条规则，每一条问三个问题。它是文字、命令、hook，还是事后检查？违反一次，还能挽回吗？它被违反过两次了吗？最该先往上挪的，是那条只靠文字守着、一旦违反就无法挽回、而且已经被违反过两次的规则。

What code costs, and what can still go wrong

Whichever rule you move, the code that holds it has a price. Like any software, it has to be written, tested and updated whenever the platform changes its tool names or events, so the more rules you move into code, the more of that you carry. It can also break. Depending on how a hook breaks, the platform may refuse every call or let every call through (Enforcement design).

Even when it works, a code rule can go wrong in two opposite ways. If its pattern is too wide, it blocks real work, and because the agent cannot argue with a refusal, a false refusal leaves the task stuck. So every code rule needs a reason in its message and a way to see which rule fired. The opposite mistake is letting things through. A hook only sees calls, so it stops the spellings it knows and misses the rest. It will not hold against an agent set on getting around it, so for things that must never be touched, see Least privilege.

There is also a trap that has nothing to do with refusing. If only the agent knows whether it kept a rule, you have no record, so do not let the agent be the only witness. For anything you will rely on later, have code write the record (Counted checks).

One last limit is the ladder itself. It comes from experience with one harness and from the docs, not from counting how often each level fails. I have no numbers for how often words alone are broken, nor would I trust anyone who gave you one without saying what model and what task.

程式碼要付出什麼，還可能在哪裡出錯

不管你搬的是哪條規則，守著它的程式碼都有成本。程式碼也是軟體：要寫、要測，平台改了工具名稱或事件時還要更新，所以你搬進程式碼的規則越多，要背的就越多。軟體也會壞。hook 一壞，平台可能拒絕每一次呼叫，也可能放行每一次呼叫，看它是怎麼壞的（把執行層當軟體來設計）。

就算沒壞，程式碼規則也會從兩個相反的方向出錯。一個方向是模式寫得太寬，連正常的工作也擋下來。因為 agent 沒辦法跟拒絕爭辯，誤拒一次，任務就卡住了。這就是為什麼每條程式碼規則的訊息裡都要寫明理由，還要有辦法看出是哪條規則觸發的。另一個方向是放過東西。hook 只看得到呼叫，所以只擋得住它認得的那幾種寫法，其餘的都會漏掉。一個一心想繞過它的 agent，它是擋不住的。絕不能碰的東西該怎麼辦，見有些東西根本不給。

還有一個陷阱和拒絕無關。規則守沒守，要是只有 agent 自己知道，就沒有紀錄可言，所以別讓它當唯一的證人。凡是之後你要依賴的，都讓程式碼來寫紀錄（讓「通過」可信）。

最後一個限制在階梯本身。它來自我對一個 harness 的經驗和文件，每一級多常失敗，我並沒有數過。光靠文字的規則多常被違反，我也沒有數字。誰要是給你一個數字，卻不說是什麼模型、什麼任務，我是不會信的。

代码要付出什么，还可能在哪里出错

不管你挪的是哪条规则，守着它的代码都有成本。代码也是软件：要写、要测，平台改了工具名或事件，还得跟着更新，所以挪进代码的规则越多，你要扛的就越多。软件也会坏。hook 一坏，平台可能拒绝每一次调用，也可能放过每一次调用，取决于它是怎么坏的（hook 自己出故障了怎么办？）。

就算不坏，代码规则也会从两个相反的方向出错。一个方向是模式写得太宽，挡住了正常的工作。因为 agent 没法跟拒绝争辩，误拒一次，任务就卡住了。这就是为什么每条代码规则的消息里都要写明理由，还要有办法看出是哪条规则触发的。另一个方向是放过东西。hook 只看得到调用，所以只拦得住它认识的那几种写法，其余的都会漏掉。一个铁了心要绕过它的 agent，它是挡不住的。绝不能碰的东西该怎么办，见不要开放全部的权限或使用沙箱。

还有一个坑和拒绝无关。规则守没守，要是只有 agent 自己知道，就没有记录可言，所以别让它当唯一的证人。凡是你以后要依赖的东西，都让代码来写记录（Agent 说“测过了”，能信吗？）。

最后一个限制在梯子本身。它来自我对一个 harness 的经验和文档，每一级多久失败一次，我并没有数过。光靠文字的规则多久会被违反一次，我也没有数字。要是有人给你一个数字，却不说是什么模型、什么任务，我不会信。

Does the platform agree? Industry practice

The platform docs agree on the split, though they put it in their own words. The VS Code hooks page says hooks and instructions are not substitutes for enforced permissions, sandboxing or enterprise controls (hooks). That sentence is worth reading in both directions: instructions are the weakest level, but a hook is not the strongest level either. The ladder goes on above it, and the next chapters climb it.

平台也這麼看嗎？ 業界做法

平台文件在這種劃分上是一致的，只是各有各的說法。VS Code 的 hooks 頁面說，hook 和寫在指令檔裡的指示，都不能取代強制執行的權限、沙箱或企業管控（hooks）。這句話值得正反兩面讀：指令檔裡的文字是最弱的一級，但 hook 也不是最強的一級，它上面還有更牢的。接下來的幾章，就沿著這道階梯往上走。

平台也这么看吗？ 业界做法

平台文档在这个划分上是一致的，只是各用各的说法。VS Code 的 hooks 页面说，hook 和指令都不能替代强制执行的权限、沙箱或企业级管控（hooks）。这句话值得正反两面读：指令是最弱的一级，但 hook 也不是最强的一级，它上面还有更牢的。接下来的几章，就沿着这架梯子往上走。

When to delete a code rule Industry practice

Of the two things that shrink the ladder over time, the first is a model that gets better at following words. Some rules you moved to code because the model ignored them may now be followed. The way to find out, though I have not run this myself, is to run the same tasks with the rule switched off and count the breaches (When the model is upgraded). Switch it off only where a breach can be undone. Choose tasks that used to trip the rule and run each a few times. Even then, a handful of runs will show only a large change.

The second is the platform taking over. When the platform itself can refuse a path or a command in every mode, your own hook for it can go, though the sentence of text stays.

What does not go away is the question of how firmly each rule is held and why.

什麼時候可以刪掉程式碼規則 業界做法

隨著時間過去，有兩件事會讓這道階梯變短，第一件是模型越來越能照著文字做事。有些規則，你當初是因為模型不理會才搬進程式碼的，現在它可能已經會照做了。這可以驗證，雖然這個測試我自己還沒跑過：選過去曾經觸發這條規則的任務，只在違反了也能挽回的地方關掉程式碼規則，每個任務跑幾次，數一數違反的次數（模型升級了，就要刪）。跑這麼幾次，也只看得出很大的變化。

第二件是平台接手。當平台自己就能在每種模式下拒絕某個路徑或指令時，你為它做的 hook 就可以刪掉，那一句文字則留著。

不會消失的，是這個問題本身：哪條規則該守得多牢，為什麼。

什么时候可以删掉代码规则 业界做法

随着时间推移，有两件事会让这架梯子变短，第一件是模型越来越能照着文字做事。有些规则，你当初是因为模型不理会才挪进代码的，现在它可能已经会照做了。这可以验证，虽然这个测试我自己还没跑过：挑那些过去会触发这条规则的任务，只在违反了也能挽回的地方关掉代码规则，每个任务跑几次，数一数违反了几次（换了新模型，旧规则该删了）。跑这么几次，也只看得出很大的变化。

第二件是平台接管。当平台自己就能在每种模式下拒绝某个路径或命令时，你为它写的 hook 就可以删掉，那一句文字则留着。

不会消失的，是这个问题本身：哪条规则该守得多牢，为什么。
