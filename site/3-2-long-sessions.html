Long chats get worse長對話會變差长对话会变差

This chapter assumes you have used an AI coding agent in a long chat, and read the context budget (the window has a size limit, and everything in it competes for room).

讀這一章，需要你已經和寫程式的 AI agent 開過很長的對話，也讀過上下文是一份預算（視窗有大小上限，裡面所有東西都在搶位子）。

读这一章，需要你用 AI 编程 agent 开过很长的对话，并且读过上下文是一份预算（窗口有大小上限，里面的东西互相争地方）。

The Knowledge經驗分享经验分享

In one sentence

Long chats get worse. Do not trust the model to remember: write what matters into files, clear old tool results, or start a fresh chat.

一句話

長對話會變差。別指望模型記得：把要緊的寫進檔案、清掉舊的工具結果，或開一個新的對話。

一句话

对话越长，表现越差。别指望模型自己记住：把重要的写进文件，清掉旧的工具结果，或者开一个新对话。

For leaders

  • The decision: require that anything that matters lives in a file, not only in the chat, and agree on when to start a fresh chat.
  • The risk: long chats get worse, and when a platform summarises a chat, the summary drops details such as your exact words and the reason for a choice. I have not measured how fast quality falls in my own setup, so I give no rate.
  • The cost of doing it right: a short notes file for each piece of work, updated after each finished step. If you cannot write the handover in half a page, the work is not yet clear enough.
  • Ask the team: "If this chat disappeared now, what would we lose?"

給主管

  • 要做的決定：要求凡是要緊的東西都放在檔案裡，不能只留在對話裡，並且約好什麼時候開新的對話。
  • 風險：長對話會變差；平台替對話做摘要時，還會丟掉細節，例如你原話的措辭、做某個選擇的理由。在我自己的設定裡，品質掉得多快我沒量過，所以不給比率。
  • 做對的成本：每件工作一份簡短的筆記檔，每做完一步就更新一次。如果交接寫不進半頁，說明這件工作還不夠清楚。
  • 可以問團隊：「如果這個對話現在消失了，我們會丟掉什麼？」

写给管理者

  • 要拍板的事：要求凡是重要的东西都放在文件里，不能只留在对话中，并且约定好什么时候开新对话。
  • 风险：对话变长会变差；平台给对话做摘要时，还会丢掉细节，比如你的原话、做某个选择的原因。在我自己的配置里，质量掉得多快我没量过，所以不给速率。
  • 做对的代价：每项工作一个简短的笔记文件，每做完一步就更新一次。如果交接内容半页纸写不下，说明这件事还没想清楚。
  • 可以问团队：“如果这个对话现在没了，我们会丢什么？”

Why does an agent get worse as the chat goes on?

You have been working with an agent for two hours. It started out sharp, but now it asks about something you settled at the start, repeats a mistake it had already fixed, or edits the wrong file. Nothing broke. The chat just got long.

Why should length alone make a difference? Because everything the agent works with sits in its context window, the text the model can see at one time, and that window has a size limit. The biggest things in it are usually tool results, what comes back each time the agent uses a tool (both terms are defined in Context is a budget). When the window is nearly full, the platform falls back on compaction: it asks a model to summarise the chat so far and then carries on from the summary.

I have not measured how fast quality falls in my own setup, so I will not give you a number. But the shape of the problem is clear enough to act on, and the people who build the models describe it the same way (more under Do the model makers see it the same way?).

What happens to the window as the chat grows

It is easiest to see as a picture of the same chat at three moments.

Four things happen together. The first is that the useful part does not grow, while the rest does. What the task needs right now (the request, the rule you gave, the file being edited) stays about the same size, but around it pile up the files read an hour ago, a test output that was long and is now irrelevant, and three wrong attempts.

That would matter less if the model could put old things away in a filing cabinet, but it has none: on every turn it reads the whole window again. The more old text there is, the more the one line that matters has to compete with it. (A cache can make the rereading cheaper in money, as Models and cost explains, but it does not make the window less crowded.) The name for this is context rot: as the window fills, the model's recall of what is in it gets less reliable.

Things said early also end up far from where they are needed. A rule from your first message is still there, but it is now thousands of lines back from the step where it applies. This point is my own reading of what I see, with no source behind it.

And when the window is nearly full, compaction loses detail. A summary keeps what its writer judged important. Your exact words, the reason for a choice and the one odd constraint are the first things a summary drops, without telling you which ones it dropped.

None of this is a bug in one product. It comes from how the window works, so it applies to every agent. What, then, can you do about it?

對話越長，agent 為什麼越差？

你和 agent 已經一起工作了兩小時。一開始它很敏銳，現在卻會問起你一開始就定好的事，會重犯一個已經修掉的錯誤，或是乾脆改錯檔案。什麼都沒壞，只是對話變長了。

那麼，光是對話變長，為什麼就會出問題？因為 agent 手上的一切，都放在它的上下文視窗裡，也就是模型一次能看到的全部文字，而這個視窗有大小上限。視窗裡最大的項目，通常是工具結果，也就是 agent 每次使用工具後回來的內容（這兩個詞在上下文是一份預算裡都定義過）。視窗快滿的時候，平台還會做一件事，叫壓縮（compaction）：請一個模型把到目前為止的對話摘要一遍，再從這份摘要繼續下去。

在我自己的設定裡，品質掉得多快，我沒量過，所以不會給你一個數字。但問題的樣子已經清楚到可以據此行動，做模型的人也是這樣描述的（詳見做模型的人也這麼看嗎？）。

對話變長時，視窗裡發生了什麼

這幾個時刻裡，有四件事同時在發生。頭一件是，有用的部分不會變大，其餘的卻越來越多。任務眼下需要的東西（需求、你給的規則、正在編輯的檔案）大小差不多不變，圍著它堆起來的，卻是一小時前讀過的檔案、一份很長而現在早已無關的測試輸出，還有三次錯誤的嘗試。

要是模型能把舊東西收進檔案櫃，這還不算太要緊，可它沒有檔案櫃：每一輪，它都要把整個視窗從頭重讀一遍。舊的文字越多，真正要緊的那一行要競爭的對手就越多。（快取可以讓重讀少花一點錢，見選模型：算的是每次成功的成本，但視窗並不會因此變得不擠。）這個現象叫上下文腐化：視窗越滿，模型對裡面內容的回想就越不可靠。

還有，早先說過的話，會離用到它的地方越來越遠。你在第一則訊息裡給的規則還在，只是和它該適用的那一步之間，已經隔了幾千行。這一點是我自己對所見的解讀，沒有來源。

等到視窗快滿，壓縮又會丟掉細節。摘要留下的，是寫摘要的那一方認為重要的東西。你原話的措辭、做某個選擇的理由、那一條古怪的限制，都是摘要最先丟掉的，而丟了哪些，你根本無從知道。

這些都不是某一個產品的 bug。它們來自視窗的運作方式，所以每一個 agent 都一樣。既然如此，我們能做些什麼？

对话越长，agent 为什么越差？

你和 agent 已经一起干了两个小时。一开始它很利落，可现在它会来问你开头就定下的事，会重犯一个已经修掉的错，或者干脆改错了文件。什么都没坏，只是对话变长了。

那么，光是对话变长，为什么就会出问题？因为 agent 手上的一切，都放在它的上下文窗口里，也就是模型一次能看到的全部文本，而这个窗口有大小上限。窗口里最大的几项，通常是工具结果，也就是 agent 每次用工具后返回的内容（这两个词在上下文是一份预算里都定义过）。窗口快满的时候，平台还会做一件事，叫压缩：让一个模型把到目前为止的对话总结一遍，再从这份摘要接着往下走。

在我自己的配置里，质量下降得有多快，我没量过，所以不会给你一个数字。但问题的样子已经清楚到可以据此行动了，做模型的人也是这么描述的（详见做模型的人也这么看吗？）。

这几个时刻里，有四件事在同时发生。头一件是，有用的部分不会变大，其余的却越来越多。任务眼下需要的东西（需求、你给的规则、正在改的文件）大小基本不变，围着它堆起来的，却是一小时前读过的文件、一份又长又早已无关的测试输出，还有三次失败的尝试。

要是模型能把旧东西收进文件柜，这还不算太要紧，可它没有文件柜：每一轮，它都要把整个窗口从头再读一遍。旧文本越多，真正要紧的那一行要争的对手就越多。（缓存能让重复读取少花点钱，见选模型：看每次成功的成本，可窗口并不会因此变得不挤。）这种现象叫上下文腐化：窗口越满，模型对里面内容的回忆就越靠不住。

还有，早先说过的话，会离用到它的地方越来越远。你在第一条消息里给的规则还在，只是和它该起作用的那一步之间，已经隔了几千行。这一条是我自己对所见现象的理解，没有出处。

等到窗口快满，压缩又会丢掉细节。摘要留下的，是写摘要的一方认为重要的东西。你的原话、做某个选择的原因、那条古怪的约束，都是摘要最先丢掉的，而丢了哪些，你根本没法知道。

这些都不是某个产品的 bug。它们来自窗口本身的工作方式，所以对每个 agent 都一样。既然如此，我们能做些什么？

Keep what matters out of the chat

The answer is not "a bigger window" or "a smarter summary". It is to stop depending on the chat as the place where important things live. There are four moves for that. The first is a habit to keep all the time, while the other three are for when the chat grows, going from lightest to heaviest.

1. Write down what matters, in a file

Start with a question: if this chat disappeared now, what would I lose? Whatever the answer is should not live only in the chat. That means what was decided and why, what is done and what comes next, and where things are (which files, which commands).

All of this goes in a file the agent can read again, such as a short notes file in the task's folder, or its to-do list (both are explained in Manage tasks, not chats). A file does not get compacted, and a new chat can read it in a second. When it is read again, its text also lands near the end of the window, close to where it is needed.

In my setup, every piece of work has a folder holding a handover file that records how far the work has got, the next step and what is decided. A new chat reads that file first and carries on from there. Because of this, losing a chat costs me a few minutes, not the work.

Keep the note short. One page is better than ten, because the new chat has to read it and the note takes room too. Write what is true now rather than the story of how you got there, and put the next step at the top.

Make the agent do it. Ask it to update the notes after each finished step, not at the end, because the end is when you are tired and the chat is longest. One sentence is enough to set this up: "After each finished step, update the notes file: what is decided, what is done, the next step."

Anthropic describes the same habit for long-running agents, built on a progress file and the git history that the agent reads first when a new session starts (Effective harnesses for long-running agents). Here is the template for the handover file in my setup:

2. Clear old tool results

Most of the window is usually old tool output. The agent read a file to find one function, but the whole file is still there. A test run printed pages of output, of which only the one failing line mattered.

Dropping that output is the lightest form of compaction and also the safest, because the decisions and the conclusions stay and only the raw material goes. If the agent needs the file again, it can read it again. On Anthropic's API this is a feature called context editing, in which a strategy named clear_tool_uses removes the oldest tool results once the input passes a size you set. The feature is in beta, and clearing has a price, because it invalidates the cached beginning (Context editing). Whether your own tool does anything like it, and when, is something to check rather than assume; I have not tested what Copilot does today (see Where these moves can let you down).

You can also get the same effect by hand. When a long read is done, ask the agent to write down only what it found, then carry on in a new chat that has the finding but not the reading.

3. Send a big read to a subagent

If the next step is to read a lot, do not do the reading in your main chat. Hand it to a subagent, a second agent that starts with an empty window and sends back only a short report. The reading stays in its window while your main chat gets the conclusion. This is the "parallel reading" case in Use subagents sparingly, with the same two limits: it only works when a short report is enough, and it costs more in total.

Some platforms make this a setting. In VS Code, a skill can declare context: fork in its header to run in a subagent of its own instead of in your chat (Agent skills; the docs mark it experimental). That suits a skill that reads a lot and reports a little. I have not tried it, though, so I do not know how it counts usage or how hooks see it.

4. Start a fresh chat

Sometimes the right move is to stop. These are the signs that it is time:

  • The agent repeats something you already settled.
  • It undoes a fix from an hour ago.
  • You catch yourself re-explaining.
  • The task changed (a new task is a new chat).

A fresh chat starts with an empty window and the rules. Give it only what it needs to carry on: point it at the notes file. In my experience (I have not measured it), it often does better than the old chat was doing at the end, because it is reading a clean page.

Starting fresh can feel like losing progress, so it is worth comparing what you actually lose. The progress is in the files and in the code. The chat only held the memory of it, a memory that was already worn.

For long work that I split into steps, I start fresh at planned points instead of waiting for the chat to degrade. Learning a large code base, for example, goes in batches, and I begin a new chat every two or three batches. Since the state is in the task and not in the chat, nothing is lost at the boundary.

What to hand over

If you do start a fresh chat, the next question is what to give it. It needs a small, fixed set of things:

  1. The request, in a few lines.
  2. What is decided, and what is not.
  3. What is done, and the next step.
  4. Where the files are.

If you cannot write these four in half a page, that is the real finding. The work is not yet clear enough to hand over to anyone, including yourself tomorrow.

A one-hour test of your own setup

How can you tell whether your chat is already doing worse than your files? There is a cheap test for it. It needs no extra setup, and one person can do it in an hour. Pick a rule with two or three parts that you gave early in a long chat. After an hour of work, ask the agent to state it without looking back. Then start a new chat, give it only your notes file, and ask the same question. Score each answer by how many of the parts it got right. If the second one is more accurate, your chat is doing worse than your files.

While you are at it, check where your instructions live. A rule given only in the conversation is lost when the chat is compacted, but a rule in a file that the platform reads again is not. Claude Code's documentation says exactly this about its project instruction file. So if you want a rule to survive, put it in a file.

把要緊的東西放到對話外面

答案不是「更大的視窗」，也不是「更聰明的摘要」，而是不再把對話當成存放要緊東西的地方。為此有四個動作。第一個是要一直保持的習慣；另外三個，等對話變長再用，由輕到重。

1. 把要緊的寫進檔案

先問自己一個問題：如果這個對話現在消失了，我會丟掉什麼？不管答案是什麼，那些東西都不該只存在於對話裡。具體來說，就是決定了什麼、為什麼這樣決定，做完了什麼、接下來做什麼，以及東西在哪裡（哪些檔案、哪些指令）。

這些都要寫進 agent 能再讀的檔案，例如任務資料夾裡一份簡短的筆記檔，或是它的待辦清單（兩者都在管任務，不管對話裡說明）。檔案不會被壓縮，新的對話一秒鐘就能讀完。而且再讀進來的時候，它的文字會落在視窗的末端，正好靠近用到它的地方。

在我的設定裡，每件工作都有一個資料夾，裡面放著一份交接檔，記著做到哪了、下一步是什麼、已經決定了什麼。新的對話先讀這份檔案，再接著做下去。所以就算丟掉一個對話，我也只損失幾分鐘，而不是整件工作。

筆記要寫得短。一頁比十頁好，因為新的對話得把它讀一遍，它本身也佔位子。寫現在是什麼樣子，不寫是怎麼走到這一步的，下一步放在最上面。

這件事交給 agent。請它每做完一步就更新筆記，不要等到最後，因為最後正是你累了、對話也最長的時候。設定起來一句話就夠：「每做完一步，就更新筆記檔：已決定的事、已完成的事、下一步。」

Anthropic 為長時間運行的 agent 描述了同樣的習慣，靠的是一份進度檔加上 git 歷史，新的會話一開始，agent 先讀這些（Effective harnesses for long-running agents）。下面是我的設定裡交接檔的範本：

2. 清掉舊的工具結果

視窗的大部分，通常是舊的工具輸出。agent 為了找一個函式讀了一個檔案，整個檔案卻還留在那裡；一次測試跑出好幾頁輸出，要緊的只有失敗的那一行。

把這些丟掉，是最輕的一種壓縮，也是最安全的一種，因為決定和結論都留著，拿掉的只是原始材料。agent 如果又需要那個檔案，再讀一次就好。在 Anthropic 的 API 上，這是一個叫 context editing 的功能：一個叫 clear_tool_uses 的策略，會在輸入超過你設定的大小之後，移除最舊的工具結果。不過這個功能還在 beta，清除也不是沒有代價，因為它會讓被快取的開頭失效（Context editing）。你自己的工具有沒有做類似的事、什麼時候做，要去查，不要假設。至於 Copilot 現在怎麼做，我沒有測過（見這幾招在哪裡會出問題）。

你也可以手動得到同樣的效果。一次很長的閱讀做完後，請 agent 只寫下它發現了什麼，然後換一個新的對話繼續。新的對話有這份發現，卻沒有那些閱讀。

3. 把大量閱讀交給子 agent

如果下一步要讀很多東西，就別在主對話裡讀，交給一個子 agent。它是第二個 agent，從空的視窗開始，最後只交回一份簡短的報告。讀過的內容都留在它的視窗裡，你的主對話拿到的是結論。這就是慎用子 agent裡說的「並行閱讀」，兩個限制也一樣：只有一份簡短的報告就夠的時候才行得通，而且總共花得更多。

有些平台把這件事做成了一個設定。在 VS Code 裡，skill 可以在檔頭寫 context: fork，它就會在自己的子 agent 裡執行，而不是在你的對話裡（Agent skills；文件標明是實驗性的）。讀得多、回報得少的 skill，正適合這樣做。不過我沒試過，所以不知道它的用量怎麼算，hook 又怎麼看到它。

4. 開一個新的對話

有時候，對的做法是停下來。出現下面這些跡象，就該停了：

  • agent 重複你已經定好的事。
  • 它推翻一小時前的一個修正。
  • 你發現自己在重新解釋。
  • 任務變了（新的任務就是新的對話）。

新的對話從空的視窗加上規則開始。只給它繼續所需要的東西就好，也就是讓它去讀筆記檔。依我的經驗（這一點我沒有量過），它常常比舊的對話在結尾時做得更好，因為它讀的是一張乾淨的紙。

重新開始，難免讓人覺得進度丟了，所以值得算一算到底丟了什麼。進度其實在檔案裡、在程式碼裡，對話裡留著的，只是對進度的記憶，而這份記憶早就磨損了。

對於我拆成幾步的長工作，我不會等對話變差，而是在事先排好的時間點重新開始。例如學習一個大的程式碼庫是分批做的，每兩三批我就開一個新的對話。狀態在任務裡，不在對話裡，所以在交界處什麼都不會丟。

交接什麼

既然要開新的對話，接下來的問題就是給它什麼。它需要一小組固定的東西：

  1. 需求，幾行就好。
  2. 決定了什麼，沒決定什麼。
  3. 做完了什麼，和下一步。
  4. 檔案在哪裡。

這四樣如果半頁寫不下，那才是真正的發現：這件工作還不夠清楚，沒法交給任何人，包括明天的你自己。

用一小時測一測你自己的設定

那麼，怎麼知道你的對話是不是已經不如你的檔案了？有一個便宜的測試，不用額外設定，一個人一小時就能做完。挑一條你在長對話早期給的、有兩三個部分的規則。工作一小時之後，請 agent 不回頭看，把它說出來。然後開一個新的對話，只給它你的筆記檔，問同樣的問題。每個答案按它答對了幾個部分打分。如果第二個更準，就表示你的對話還不如你的檔案。

順便也檢查一下你的指令放在哪裡。只在對話裡給的規則，對話一被壓縮就丟了；放在平台會再讀的檔案裡的規則，則不會。Claude Code 的文件談到它的專案指令檔時，說的正是這一點。所以，要讓一條規則留下來，就把它放進檔案。

把要紧的东西放到对话外面

答案不是“更大的窗口”，也不是“更聪明的摘要”，而是别再把对话当成存放重要东西的地方。为此有四招。第一招是要一直保持的习惯；另外三招在对话变长时才用，从最轻到最重。

1. 把要紧的写进文件

先问自己一个问题：如果这个对话现在没了，我会丢什么？不管答案是什么，那些东西都不该只存在于对话里。具体说，就是定了什么、为什么这么定，做完了什么、下一步做什么，以及东西在哪（哪些文件，哪些命令）。

这些都要写进 agent 能重新读到的文件里，比如任务文件夹里的一份简短笔记，或者它的待办清单（两者都在管任务，不管对话里讲）。文件不会被压缩，新对话一秒钟就能读完。而且重新读进来时，它的文本落在窗口的靠后位置，正好离用到它的地方很近。

在我的配置里，每项工作都有一个文件夹，里面放着一份交接文件，记着做到哪了、下一步是什么、定了什么。新对话先读这份文件，再接着往下干。所以就算丢了一个对话，我损失的也只是几分钟，而不是整份工作。

笔记要写得短。一页比十页好，因为新对话得把它读一遍，它本身也占地方。写现在是什么情况，不讲是怎么走到这一步的，下一步放在最上面。

这件事交给 agent。让它每做完一步就更新笔记，别等到最后，因为到了最后你已经累了，对话也最长。设置起来一句话就够：“每做完一步，更新笔记文件：定了什么、做完了什么、下一步。”

Anthropic 为长时间运行的 agent 描述过同样的习惯，靠的是一份进度文件加上 git 历史，新会话一开始，agent 先读它们（Effective harnesses for long-running agents）。下面是我配置里交接文件的模板：

交接文件模板：状态、现在在做什么、下一步、要读的文件、已经定下的事，以及待解决的问题。
# TASK: {name}

> The handover file. A new session reads this file first, then what it points to. Keep it within one screen. Update it every time before you stop.

- **Kind**: {kind}
- **Tier**: {tier}
- **Created**: {created}
- **Updated**: <yyyy-mm-dd>
- **Status**: <in progress / waiting for the user to approve the plan / waiting for the user to accept / done>
- **Doing now**: <one sentence>
- **Next step**: <the one thing to do next>

## Files to read

<The files a new session should read, in order, with links. Write "none" if there is nothing>

## Decided

<What the user has decided, one per line, with the date. Write "none" if there is nothing>

## Open questions

<Five at most. Delete each one once it is solved. Write "none" if there is nothing>

2. 清掉旧的工具结果

窗口里的大部分，通常是旧的工具输出。agent 为了找一个函数读了一个文件，可整个文件都还留在那里；一次测试跑出好几页输出，真正有用的只有失败的那一行。

把这些扔掉，是最轻的一种压缩，也是最安全的一种，因为决定和结论都留着，去掉的只是原始材料。agent 要是还需要那个文件，再读一遍就是了。在 Anthropic 的 API 上，这是一个叫上下文编辑（context editing）的功能：名为 clear_tool_uses 的策略，会在输入超过你设定的大小之后，把最旧的工具结果清掉。不过这个功能还在 beta，清除也不是没有代价，因为它会让缓存的开头失效（Context editing）。你自己的工具有没有类似的功能、什么时候触发，得去查，不能想当然。至于 Copilot 现在怎么做，我没测过（见这几招在哪里会出问题）。

你也可以手动做到同样的效果。一段长长的阅读结束后，让 agent 只写下它发现了什么，然后换一个新对话接着干。新对话里有那份发现，却没有读的过程。

3. 把大块的阅读交给子 agent

如果下一步要读很多东西，就别在主对话里读，交给一个子 agent。它是第二个 agent，从空窗口开始，最后只送回一份简短的报告。读过的内容都留在它的窗口里，你的主对话拿到的是结论。这就是慎用子 agent里说的“并行阅读”，两条限制也一样：只有一份简短的报告就够用时才行得通，而且总的花费会更多。

有的平台把这件事做成了一个设置。在 VS Code 里，skill 可以在头部声明 context: fork，这样它就在自己的子 agent 里运行，而不是在你的对话里（Agent skills；文档标明它是实验性的）。读得多、报告得少的 skill 正适合这么做。不过我没试过，所以不知道它怎么计用量，也不知道 hook 怎么看到它。

4. 开一个新对话

有时候，正确的做法是停下来。出现下面这些信号，就该停了：

  • agent 重复你已经定下的事。
  • 它撤销了一小时前的修复。
  • 你发现自己在重新解释。
  • 任务变了（新任务就开新对话）。

新对话从一个空窗口加上规则开始。只给它继续干活所需的东西就行，也就是让它去读笔记文件。按我的经验（这一点我没量过），它常常比旧对话到最后时做得更好，因为它读的是一张干净的纸。

重新开始，难免让人觉得进度丢了，所以值得算一算到底丢了什么。进度其实在文件里、在代码里，对话里留着的只是对进度的记忆，而这份记忆早就磨损了。

对我拆成多步的长任务，我不会等对话变差，而是在事先定好的节点重新开始。比如学一个大代码库是分批做的，每两三批我就开一个新对话。状态在任务里，不在对话里，所以在交界处什么也不会丢。

交接什么

既然要开新对话，接下来的问题就是给它什么。它需要一小套固定的内容：

  1. 需求，几行就行。
  2. 哪些定了，哪些没定。
  3. 做完了什么，下一步是什么。
  4. 文件在哪。

这四样要是半页纸写不下，那才是真正的发现：这件事还没想清楚，没法交给任何人，包括明天的你自己。

用一小时检验你自己的配置

那么，怎么知道你的对话是不是已经不如你的文件了？有一个便宜的测试，不需要额外配置，一个人一小时就能做完。挑一条你在长对话早期给的、包含两三个部分的规则。干了一小时之后，让 agent 不回头看，直接复述这条规则。然后开一个新对话，只给它你的笔记文件，再问同样的问题。按每个回答答对了几个部分来打分。如果第二个更准，就说明你的对话还不如你的文件。

顺便也查一下你的指令放在哪。只在对话里给的规则，对话一压缩就丢了；放在平台会重新读取的文件里的规则则不会。Claude Code 的文档说到它的项目指令文件时，讲的正是这一点。所以，想让一条规则留下来，就把它放进文件。

Where these moves can let you down

Before reaching for any of these moves, ask why the chat got long. If it is because the task is too big, the fix is a smaller task. Better note-taking would only hide a bad habit.

Even when the task is the right size, the notes themselves can be wrong. If the agent writes "tests pass" in the notes when they did not pass, the next chat starts from a false fact. Notes are the agent's report, so check the ones that matter. Memory is about this problem at length.

And a correct note still has a cost of its own: it takes room. A notes file that grows without trimming becomes the very thing that fills the window, so keep it short and cut what is done.

A notes file can also hold things you would not want shared, so think before it goes into a shared repository.

And a fresh chat, however good the notes, loses the feel of the old one. The old chat knew how you phrase things and what you meant by "the usual way". If that matters, write it down, because it is likely a rule.

Then there is what I did not test. I have not measured how my platform compacts: what it keeps, what it drops, and whether it clears old tool results by itself. Until you have checked this for your own tool, treat compaction as lossy.

這幾招在哪裡會出問題

用這幾招之前，先想想對話為什麼會變長。如果是因為任務太大，該做的是把任務拆小。筆記做得再好，也只是掩蓋了壞習慣。

就算任務大小合適，筆記本身也可能是錯的。agent 在筆記裡寫了「測試通過」，實際卻沒有通過，下一個對話就會從一個錯誤的事實開始。筆記是 agent 的報告，要緊的那些要檢查。agent 該記住什麼用較長的篇幅談這個問題。

寫對了的筆記也有自己的代價：它佔位子。一份一直長大、又沒人修剪的筆記檔，最後會變成填滿視窗的那個東西，所以要保持簡短，把做完的剪掉。另外，筆記檔裡可能有你不想分享的東西，放進共用的倉庫之前要想一想。

筆記寫得再好，新的對話也還是會失去舊對話的那份手感。舊的對話知道你怎麼說話，也知道你說「照平常的做法」是什麼意思。如果這很重要，就把它寫下來，因為這很可能就是一條規則。

最後是我沒測過的部分。我沒有量過我的平台怎麼壓縮：留下什麼、丟掉什麼，以及它會不會自己清掉舊的工具結果。在你為自己的工具查清楚之前，就把壓縮當成有損的。

这几招在哪里会出问题

用这几招之前，先想想对话为什么会变长。如果是因为任务太大，办法是把任务拆小。笔记记得再好，也只是掩盖了坏习惯。

就算任务大小合适，笔记本身也可能是错的。agent 在笔记里写了“测试通过”，实际却没通过，下一个对话就是从一个假的事实出发的。笔记是 agent 的报告，重要的那些要核对。agent 该记住什么详细讲的就是这个问题。

写对了的笔记也有自己的代价：它占地方。一份不断变长、又没人修剪的笔记文件，最后会变成填满窗口的那个东西，所以要保持简短，把已经做完的删掉。另外，笔记文件里可能有你不想共享的内容，放进共享仓库之前要想一想。

笔记记得再好，新对话也还是会丢掉旧对话的那份“默契”。旧对话知道你习惯怎么措辞，也知道你说的“老办法”是什么意思。如果这很重要，就把它写下来，因为它多半就是一条规则。

最后是我没测过的部分。我没量过我用的平台是怎么压缩的：留下什么，丢掉什么，会不会自己清理旧的工具结果。在你为自己的工具查清楚之前，就把压缩当作有损的。

Do the model makers see it the same way? Industry practice

Anthropic's engineering team describes this problem and the same fixes. They use the term context rot, meaning that as the window fills, "the model's ability to accurately recall information from that context decreases". They name compaction ("taking a conversation nearing the context window limit, summarizing its contents"), call tool result clearing "one of the safest lightest touch forms of compaction", and describe note-taking, where "the agent regularly writes notes persisted to memory outside of the context window". (Effective context engineering for AI agents)

Claude Code's documentation adds a practical detail, the one behind the check on where your instructions live. The project instruction file at the root is read again from disk after compaction, while an instruction given only in the conversation is gone. (How Claude remembers your project)

For long tasks that need many sessions, Anthropic describes a progress file plus git history that each new session reads first. (Effective harnesses for long-running agents) And on the API, tool result clearing is available as context editing, in beta. (Context editing)

These sources agree with each other and with this chapter. None of them gives a rule for when a chat is too long. I do not give one either, so judge by the signs above.

做模型的人也這麼看嗎？ 業界做法

Anthropic 的工程團隊描述過這個問題，也給過同樣的補救。他們用上下文腐化這個詞，意思是視窗越滿，「模型準確回想那段上下文中資訊的能力就越低」。他們談到壓縮，也就是「拿一段接近上下文視窗上限的對話，把它的內容摘要出來」，把清除工具結果稱為「最安全、最輕的壓縮方式之一」，也描述了做筆記，即「agent 定期把筆記寫到上下文視窗之外、持久保存的記憶裡」。（Effective context engineering for AI agents）

Claude Code 的文件補充了一個實用的細節，前面檢查指令放在哪裡，根據的就是它：根目錄的專案指令檔在壓縮後會從磁碟重新讀取，而只在對話裡給的指令就沒了。（How Claude remembers your project）

對於需要很多個會話的長任務，Anthropic 描述了一份進度檔加上 git 歷史，每個新的會話先讀它們。（Effective harnesses for long-running agents）而在 API 上，清除工具結果以 context editing 的形式提供，還在 beta。（Context editing）

這些說法彼此一致，也和這一章一致。對話多長才算太長，沒有一家給出規則，我也不給，還是看上面那些跡象來判斷。

做模型的人也这么看吗？ 业界做法

Anthropic 的工程团队描述过这个问题，也给过同样的办法。他们用的术语是上下文腐化（context rot），意思是窗口越满，“模型准确回忆那段上下文里信息的能力就越下降”。他们提出了压缩（“把一段接近上下文窗口上限的对话，总结其内容”），称清除工具结果是“最安全、最轻量的压缩方式之一”，还描述了记笔记，即“agent 定期写下笔记，保存在上下文窗口之外的内存里”。（Effective context engineering for AI agents）

Claude Code 的文档补充了一个实用的细节，前面查指令放在哪，依据的就是它：根目录的项目指令文件在压缩之后会从磁盘重新读取，而只在对话里给的指令就没了。（How Claude remembers your project）

对需要很多个会话才能完成的长任务，Anthropic 描述了一份进度文件加 git 历史，每个新会话先读它们。（Effective harnesses for long-running agents）而在 API 上，清除工具结果以上下文编辑的形式提供，处于 beta 阶段。（Context editing）

这些说法彼此一致，也和这一章一致。对话多长算太长，没有一家给出规则，我也不给，还是凭上面那些信号来判断。

Which parts you can delete, and which stay Industry practice

Some of what these moves do is the platform's job and will be done better by it: clearing old tool results, compacting, and carrying key facts across. When your tool does those well and you have checked what it keeps, stop doing them by hand.

The core stays, though. If the work matters, its state belongs in a file you can read, not in a chat. A bigger window and better compaction make chats last longer, but they do not make a summary as good as the original, nor do they give a new chat your last two hours. I would look at this again if a platform showed, measured on my own tasks, that its compacted chats lose nothing I care about.

哪些可以刪掉，哪些要留下 業界做法

上面這幾招裡，有一部分本來就是平台的工作，平台也會做得更好：清掉舊的工具結果、壓縮，以及把關鍵事實帶過去。等你的工具把這些做好了，而且你查過它留下了什麼，就不用再手動做。

哪些可以删掉，哪些要留下 业界做法

上面这几招里，有一部分本来就是平台的活，平台也会做得更好：清掉旧的工具结果、压缩、把关键事实带过去。等你的工具把这些做好了，而且你查过它留下了什么，就不用再手动做了。

不过核心不变：如果这项工作重要，它的状态就该放在你能读到的文件里，而不是对话里。窗口更大、压缩更好，能让对话撑得更久，但它们不会让摘要和原文一样好，也不会让新对话拥有你最近这两个小时。如果有平台能证明，它压缩后的对话没有丢掉我在意的任何东西，而且是在我自己的任务上量出来的，我会重新考虑。

Explore it in the harness

Copilot Harness keeps the state of every task in files, so a chat can end at any time. The harness can show you where those files are and how a new chat picks up from them.

Once you have set it up as described above, type:

/harness-rookie-wondering I have read the chapter "Long chats get worse". Teach me how this harness keeps the state of a task in files: what the handover file holds, how a new session reads it to carry on, and what it does about a window that fills up (topics 1 and 9). Open the real files with me.

It teaches one small piece at a time, stops to check that you are following, and opens the files with you.
