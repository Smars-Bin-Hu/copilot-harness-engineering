5.8

Long work across sessions跨會話的長任務跨会话的长任务

This chapter assumes you know the task folder from Manage tasks, not chats, and that a chat gets shortened or ends (Long chats get worse).

讀這一章，你需要知道管任務，不管對話裡的任務資料夾，也要知道對話會被縮短或結束（長對話會變差）。

读这一章，你需要知道管任务，不管对话里的任务文件夹，也需要知道一段对话会被压短或者结束（见长对话会变差）。

The Knowledge經驗分享经验分享

In one sentence

Long work survives across sessions only if its memory is in files: the requirement, the plan, the to-do list, the handover file. Split big work into tasks small enough to accept one by one.

一句話

長時間的工作要能跨會話撐下去，它的記憶就必須放在檔案裡：需求、計畫、待辦清單、交接檔。大工作要拆成小到能一個一個驗收的任務。

一句话

长任务要跨会话延续下去，它的记忆就得放在文件里：需求、计划、待办清单、交接文件。大任务要拆成一个个小任务，小到可以逐个验收。

For leaders

  • The decision: for work that spans days, decide that its memory lives in files, and that big work is split into tasks small enough to accept one by one.
  • The risk: a new session knows nothing unless a file tells it. A big job handed over in one go gets started all at once and left half done, and a later session can see progress and call the job done too early. In my setup a person's "passed" on a step is only text, with nothing in code behind it. That is the weakest link.
  • The cost of doing it right: the files cost effort, because every step writes a little and every new session reads a little. For a job that fits in one session, that is waste. I have not measured what a goal saves over starting a new chat.
  • Ask the team: "For our longest-running job, which file tells a new session what step it is on, and who accepted the steps so far?"

給主管

  • 要做的決定：對跨好幾天的工作，決定它的記憶放在檔案裡，並把大工作拆成小到能一個一個驗收的任務。
  • 風險：除非有檔案告訴它，新的會話什麼都不知道。大工作一次交出去，agent 往往會一口氣全部開工，做到一半就丟著；之後的會話看到有進展，還可能太早說工作做完了。在我的設定裡，人對一步說的「通過」只是文字，程式裡沒有任何東西撐著。這是最弱的一環。
  • 做對的成本：檔案要花力氣，因為每一步都要寫一點，每個新的會話都要讀一點。如果一次會話就做得完，這就是浪費。一個目標比起開新對話能省多少，我沒有量過。
  • 可以問團隊：「對我們跑得最久的那項工作，哪個檔案告訴新的會話它在哪一步？到目前為止的步驟，是誰驗收的？」

写给管理者

  • 要拍板的事：对要跨好几天的工作，定下它的记忆放在文件里，并且大任务要拆成能逐个验收的小任务。
  • 风险：除非有文件告诉它，新会话什么都不知道。一个大任务一股脑交出去，往往会被一下子全开工，最后做到一半就撂下；后来的会话看到有了进展，还可能过早宣布任务完成。在我的配置里，人对某一步说的“通过”只是一段文字，代码里没有任何东西撑着它。这是最薄弱的一环。
  • 做对的代价：文件要花功夫，因为每一步都要写一点，每个新会话都要读一点。如果一个会话就能做完，这就是浪费。一个 goal 比重新开个对话能省多少，我没有测过。
  • 可以问团队：“我们跑得最久的那个任务，哪个文件告诉新会话现在做到哪一步了？到目前为止的各步，是谁验收的？”

What tells a new session where the work stands?

A job that takes three days will not fit in one chat. At some point the first session ends, or the tool shortens it to make room and the details go. Whichever session picks the work up next then knows nothing, unless something tells it.

So what can tell it? Not the agent's memory, because it has none between sessions. Not yours either, if that means explaining the background again every morning, slightly differently each time. The only thing that is the same every morning is a file.

There is also a second problem, one that comes from the size of the job. Handed a big job in one go, an agent tends to start everything at once, run out of room halfway, and leave things half done. Anthropic saw the same on a long coding project: "the agent tended to try to do too much at once" (Effective harnesses for long-running agents). The same article describes the opposite failure too, a later instance that would "declare the job done" too early. That failure is the subject of Unattended: when it must stop.

The files, then, have to do more than carry the memory from one session to the next. They also have to keep a big job in pieces small enough to finish and accept.

新的會話怎麼知道工作做到哪裡？

要花三天的工作，一次對話是裝不下的。總有一刻，第一個會話結束了，或者工具為了騰出空間把它縮短，細節也就跟著沒了。接手的下一個會話什麼都不知道，除非有東西告訴它。

那什麼能告訴它？不是 agent 的記憶，因為它在會話之間根本沒有記憶。也不能靠你記著，那樣的話，你每天早上都得把背景重新解釋一次，而且每次說得都不太一樣。每天早上唯一一樣的東西，是檔案。

還有第二個問題，它出在工作的大小上。一次拿到大工作的 agent，往往想一口氣全部開工，做到一半空間用完，留下一堆做到一半的東西。Anthropic 在一個長時間的寫程式專案上也看到同樣的事：「agent 傾向一次做太多」（Effective harnesses for long-running agents）。同一篇文章也描述了相反的失敗，也就是後來的實例太早「宣布工作完成」，那是無人值守：什麼時候必須停的主題。

這樣看來，檔案要做的不只是把記憶從一個會話帶到下一個會話，還得把大工作切成一塊一塊，每塊小到能做完、能驗收。

新会话怎么知道工作做到哪了？

一个要做三天的任务，一次对话是装不下的。总有一刻，第一个会话结束了，或者工具为了腾地方把它压短，细节也就跟着丢了。接手的下一个会话什么都不知道，除非有东西告诉它。

那什么能告诉它？不是 agent 的记忆，因为它在会话之间根本没有记忆。也不能靠你记着，那样的话，你每天早上都得把背景重讲一遍，而且每次讲得都不太一样。每天早上唯一一模一样的东西，是文件。

还有第二个问题，它出在任务的大小上。一个大任务一股脑交给 agent，它往往想一下子全开工，做到一半空间用完了，留下一堆做了一半的东西。Anthropic 在一个长期的编程项目上也看到了同样的情况：“agent 倾向于一次想做太多”（Effective harnesses for long-running agents）。同一篇文章还描述了相反的失败，也就是后来的实例过早“宣布任务完成”，那是无人值守：什么时候必须停的主题。

这样看来，文件要做的不只是把记忆从一个会话带到下一个会话，还得把大任务切成一块块，每块小到能做完、能验收。

Memory in files, work in small steps

What a conversation loses

If a file is the only thing that stays the same, the first question is what it has to carry. A conversation holds four things that a later session needs: what was asked, what was decided and why, how far the work has got, and what comes next. When the conversation is shortened or ended, all four are at risk, and the agent does not know which ones it lost.

What goes in the folder

Those four things belong where nothing can shorten them.

  • The requirement records what was asked, in a form a person confirmed (The requirement on one page).
  • The plan covers how the work will be done, and what is out of scope.
  • The to-do list breaks the work into steps, each small, each with a status and a way to tell it is done.
  • The handover file is one short file saying which step the work is at and what comes next. It is the same file as in the chapter on tasks (Anthropic calls its version a progress file). It has to stay short, within one screen, or a new session spends its room reading it.

A fifth item helps too: a change log with one entry per finished step, saying what changed. When someone asks "why is it like this?", the answer is there.

What a new session reads

A new session does not read the whole folder. It reads the short handover file first, then the to-do list, and only then whatever the current step needs. After that it checks what the files say against the disk: does the file really exist, did the step really happen? When the record and the disk disagree, the disk wins. (Manage tasks, not chats explains why.) A handover file that says "step 4 done" does not make step 4 done.

Anthropic's team did three things here that I do not do the same way. The agent committed to git after each step, so every step left a clean state to return to. Each new session ran a basic end-to-end test before starting new work, so the old state was checked and not only read about in a file. And the feature list was kept in JSON, because the model was less likely to change a JSON file by mistake than a Markdown one. I keep my files in Markdown and have not compared the two.

Build the frame first, then step by step

That deals with memory. The other problem, starting everything at once, is settled before any work begins by starting with the frame, not the work. Only then do you go one step at a time:

  1. Settle the central idea: the goal, what is in scope and what is not, and how the whole will be accepted.
  2. Break it into small steps.
  3. Have a person read both and confirm them.
  4. Then do one step: do it, check it, and hand it to the person.
  5. Count the step as done only when the person says it passed. Then write the log entry, update the handover file, and move to the next.

The person's "passed" is a gate (Two gates). How far that gate can be trusted comes up again under what the files cost.

What is too big, and how to split it

Most jobs fit in one task. A job is too big for one task when one of these is true (these three are my rules of thumb, not tested):

  • It cannot finish in one session, and nobody can say how far along it is.
  • You cannot say how you would accept the whole of it at once.
  • The plan keeps changing as you learn more.

Those are the jobs a goal is for. A goal keeps the big thing as one set of files, with a few tasks under it. A task is one delivery, as in Manage tasks, not chats, with one folder, its own checks and its own acceptance. The goal holds the idea and the list, while each task does one piece.

A good task is small enough that you can say, in a sentence, how you will accept it. While you work on task 2, the goal does not need to know the details of task 3. That is the point: the plan can then change one task at a time without redoing what has already been accepted. Steps that were accepted are not rewritten: if one needs doing again, the redo is a new step.

Common traps

Two of the traps are the failures this chapter started with. If the agent tries to finish the whole goal in one session, the fix is the list, where only one step is active at a time. If a new session sees progress and decides the job is finished, the fix is the same as for unattended work (when to stop): done is a state that the files and the person confirm, not a thing the agent says.

The other two are about size. One is a handover file that grows past a screen: it stops being read, so the detail moves to the change log and the handover file stays short. The other is making a goal for a small job. Most jobs need one task, and a goal is for work that spans sessions and changes shape.

None of this comes free, and one link in it is weak.

記憶放進檔案，工作拆成小步

對話會丟掉什麼

既然只有檔案每天都一樣，那就得先弄清楚它要裝下什麼。一段對話裝著後來的會話需要的四樣東西：被要求做什麼、決定了什麼和為什麼、工作做到哪裡、接下來是什麼。對話一旦被縮短或結束，這四樣都有風險，而且 agent 並不知道自己丟了哪些。

資料夾裡放什麼

這四樣東西應該放在不會被縮短的地方。

  • 需求記下被要求做什麼，而且是人確認過的形式（需求由 agent 寫，人確認）。
  • 計畫裡寫工作要怎麼做，以及什麼不在範圍內。
  • 待辦清單把工作拆成一步一步，每步都小，每步都有狀態，也有辦法判斷它做完了沒。
  • 交接靠一份簡短的交接檔，說明目前在哪一步、接下來是什麼。它和講任務那一章說的是同一份（Anthropic 把它的版本叫做 progress file）。它必須保持簡短，一個畫面以內，不然新的會話會把空間都花在讀它上面。

還有第五樣東西也有幫助：變更紀錄，每完成一步寫一條，說明改了什麼。以後有人問「為什麼是這樣？」，答案就在那裡。

新的會話讀什麼

那新的會話一來，先讀什麼？不是整個資料夾。它先讀簡短的交接檔，再讀待辦清單，然後才讀目前這一步需要的東西。讀完之後，它要拿檔案裡寫的去對照磁碟：檔案真的存在嗎？這一步真的發生過嗎？紀錄和磁碟不一致時，以磁碟為準（為什麼，見管任務，不管對話）。寫著「第 4 步完成」的交接檔，不會讓第 4 步真的完成。

同樣是新的會話接手，Anthropic 的團隊有三件事做得和我不一樣。他們的 agent 每做完一步就 commit 到 git，所以每一步都留下一個乾淨、可以回去的狀態。每個新的會話在開始新工作之前，會先跑一個基本的端到端測試，這樣舊狀態是真的檢查過，而不只是在檔案裡讀到。功能清單他們放在 JSON 裡，因為比起 Markdown，模型誤改 JSON 檔案的機會比較小。我的檔案用的是 Markdown，兩者我也沒有比較過。

先搭框架，再一步一步來

記憶的問題有了著落。另一個問題是一口氣全部開工，這得在動手之前就防住：先搭框架，不先動手。然後再一步一步往下做：

  1. 定下核心想法：要達成什麼、範圍內有什麼、沒有什麼、整體怎麼驗收。
  2. 拆成小步驟。
  3. 讓人讀這兩樣並確認。
  4. 然後做一步：做、檢查、交給人。
  5. 一步要等人說通過才算做完。然後寫變更紀錄、更新交接檔，再進入下一步。

這裡人的「通過」是一道門（兩道門：人在哪裡批准）。這道門有多可靠，後面講代價時再說。

什麼算太大，怎麼拆

大多數工作一個任務就裝得下。一件工作只要符合下面任何一條，對一個任務來說就太大了（這三條是我的經驗法則，沒有測過）：

  • 一次會話做不完，而且沒人說得出做到多少了。
  • 你說不出要怎麼一次驗收整件事。
  • 隨著你學到更多，計畫一直在變。

目標就是為這種工作準備的：它把大事情做成一組檔案，底下有幾個任務。一個任務是一次交付，就像管任務，不管對話裡那樣：一個資料夾、自己的檢查、自己的驗收。目標放想法和清單，每個任務各做其中一塊。

好的任務小到你能用一句話說出怎麼驗收它。你在做任務 2 的時候，目標不需要知道任務 3 的細節。拆開的重點就在這裡：計畫可以一次改一個任務，不必重做已經驗收的東西。已經驗收的步驟不會被改寫，要重做，就算新的一步。

常見的陷阱

這裡面有兩個陷阱，就是這一章開頭說的那兩種失敗。第一個是 agent 想在一次會話裡完成整個目標，對付它靠清單：同一時間只有一步在進行。第二個是新的會話看到進展，就判定做完了。對付它的辦法和無人值守的工作一樣（什麼時候停）：做完是檔案和人確認的一個狀態，不是 agent 說的一句話。

另外兩個陷阱都和大小有關。一個是交接檔寫得太長。它本來只是用來指路的，一旦長過一個畫面就沒人讀了，所以細節要移到變更紀錄，交接檔保持簡短。另一個是為小工作建立目標，可是大多數工作一個任務就夠了，目標是留給跨會話、而且會改變形狀的工作。

這些都不是免費的，其中還有一環很弱。

记忆放进文件，工作拆成小步

一段对话会丢掉什么

既然只有文件每天都一样，那先要弄清楚它得装下什么。一段对话里装着后来的会话需要的四样东西：要求是什么，定了什么、为什么这么定，工作做到哪了，接下来做什么。对话一旦被压短或者结束，这四样都有风险，而且 agent 并不知道自己丢了哪几样。

文件夹里放什么

这四样应该放到压不短的地方。

  • 需求记下要求是什么，而且是人确认过的样子（见需求由 agent 写，人确认）。
  • 计划里写工作打算怎么做，什么不在范围内。
  • 待办清单把工作拆成一步步，每一步都小，每一步都有状态，也有判断它做完没有的办法。
  • 交接靠一份简短的交接文件，写明现在做到哪一步、接下来做什么。它和讲任务那一章说的是同一份（Anthropic 把自己的版本叫 progress file）。它得保持简短，不超过一屏，不然新会话的空间都花在读它上面了。

还有第五样东西也有帮助：变更日志，每完成一步记一条，写清楚改了什么。以后有人问“为什么是这样”，答案就在那里。

新会话读什么

那新会话来了先读什么？不是整个文件夹。它先读简短的交接文件，再读待办清单，最后才读当前这一步需要的东西。读完之后，它要拿文件里写的去对照磁盘：文件真的存在吗，这一步真的做过吗？记录和磁盘对不上时，以磁盘为准（为什么，见管任务，不管对话）。交接文件写着“第 4 步做完了”，并不会让第 4 步真的做完。

同样是新会话接手，Anthropic 的团队有三件事做得和我不一样。他们的 agent 每做完一步就提交到 git，这样每一步都留下一个干净的状态，随时可以退回去。每个新会话在开始新工作之前，先跑一遍基本的端到端测试，所以旧状态是真的检查过的，而不只是在文件里读到。功能清单他们放在 JSON 里，因为比起 Markdown 文件，模型误改 JSON 文件的可能性更小。我的文件用的是 Markdown，两者我也没有比较过。

先搭框架，再一步一步来

记忆的问题有了着落。另一个问题是一下子全开工，这得在动手之前就防住：先搭框架，不先干活。然后再一步一步往下做：

  1. 定下核心想法：目标是什么，范围里有什么、没有什么，整体怎么验收。
  2. 拆成小步骤。
  3. 让人把两样都读一遍并确认。
  4. 然后做一步：做完，检查，交给人。
  5. 人说“通过”，这一步才算完成。然后写日志，更新交接文件，进入下一步。

这里人说的“通过”是一道关卡（见两道门：人在哪里审批）。这道关卡有多可靠，后面讲代价时再说。

多大算太大，怎么拆

大多数事一个任务就装得下。一件事要是符合下面任何一条，就不适合只当作一个任务（这三条是我的经验法则，没有测过）：

  • 一个会话做不完，而且没人说得清它做到了哪里。
  • 你说不出怎么一次性验收它的整体。
  • 随着你了解得越来越多，计划总在变。

goal 就是给这类事准备的：它把这件大事放进一套文件里，下面挂几个任务。一个任务就是一次交付，和管任务，不管对话里一样：一个文件夹，有自己的检查，有自己的验收。goal 放想法和清单，每个任务各做其中一块。

一个好的任务，小到你能用一句话说出怎么验收它。你在做任务 2 的时候，goal 不需要知道任务 3 的细节。拆开的意义正在这里：计划可以一个任务一个任务地改，不用把已经验收的东西重做一遍。已经验收的步骤不改写，要重做，就算新的一步。

常见的坑

这里面有两个坑，就是这一章开头说的那两种失败。第一个是 agent 想在一个会话里做完整个 goal，对付它靠清单：同一时间只有一步在进行。第二个是新会话看到有进展，就认定已经做完了。对付它的办法和无人值守的活一样（见无人值守：什么时候必须停）：做完是由文件和人确认的一种状态，不是 agent 嘴里说的一句话。

另外两个坑都和大小有关。一个是交接文件写得太长。它本来只是指个路，一旦超过一屏就没人读了，所以细节要挪到变更日志里，交接文件保持简短。另一个是小任务也建 goal，可大多数事一个任务就够了，goal 是留给跨会话、而且形状会变的工作的。

这些都不是免费的，其中还有一环很薄弱。

What the files cost, and where they are weak

The plainest cost is effort. Every step writes a little and every new session reads a little. For a job that fits in one session, the files are waste.

The person's "passed" is the weakest link in this chapter. Two gates binds an approval to the exact plan, and code checks it. The "passed" of a step here is not bound to anything. In my setup it is text, not code, and nothing in code stops an agent from writing "passed" for itself. What I rely on is the agent following the instruction and the person reading. That is a gap I know about.

Files can also lie. The agent writes them, so they can be wrong or stale. That is why the disk wins and why the person accepts the work step by step.

Then there is the risk of too many goals. To guard against it, only the person can start one in my setup. An agent may suggest a goal when a job looks long, but if it could begin one, every job would become a project.

What I have not measured is how much a goal saves over just starting a new chat and explaining. I think it saves the most when the job changes shape, but I have no numbers.

檔案要付出什麼，弱在哪裡

最直接的代價是力氣：每一步都要寫一點，每個新的會話都要讀一點，對一次會話就做得完的工作來說，這些檔案就是浪費。

人的「通過」是這一章最弱的一環。兩道門：人在哪裡批准把批准綁到確切的計畫，由程式檢查。這裡一步的「通過」卻沒有綁定到任何東西。在我的設定裡，那只是文字而不是程式，程式裡沒有任何東西阻止 agent 替自己寫下「通過」。這是我知道的一個缺口，我靠的是 agent 遵守指令，再靠人去讀。

而且檔案會說謊。檔案是 agent 寫的，所以可能是錯的，也可能過期了。正因為這樣，才要以磁碟為準，也才要人一步一步驗收。

還有一個風險是目標開得太多。為了防住它，在我的設定裡只有人能開目標。agent 看到工作很長時可以建議開一個，可是如果它自己就能開，每個工作都會變成專案。

我沒量過的，是一個目標比起直接開新對話再重新解釋，到底能省多少。我認為當工作會改變形狀時省得最多，但我沒有數字。

文件要付出什么，弱在哪里

最直接的代价是功夫：每一步都要写一点，每个新会话都要读一点，对一个会话就能做完的任务来说，这些文件就是浪费。

人的“通过”是本章最薄弱的一环。两道门：人在哪里审批把一次审批绑定到确切的那份计划上，由代码来检查。这里一步的“通过”却没有绑定任何东西。在我的配置里，它只是文字而不是代码，代码里没有任何东西能阻止 agent 自己给自己写“通过”。这是我知道的一个缺口，我靠的是 agent 照着指令办，再靠人去读。

而且文件可能说谎。文件是 agent 写的，所以可能写错，也可能过期。正因为这样，才要以磁盘为准，也才要人一步一步地验收。

还有一个风险是 goal 开得太多。为了防住它，在我的配置里只有人才能开 goal。任务看起来很长时，agent 可以建议开一个，可要是它自己就能开，每个任务都会变成一个项目。

我没有测过的，是一个 goal 比起直接开个新对话再解释一遍，到底能省多少。我认为在任务形状会变的时候省得最多，但我没有数字。

When to delete the handover file, and what stays

If the platform keeps a trustworthy memory of a long job across sessions, so that a new session can resume without reading files, the handover file can go. I would keep the requirement and the plan as files anyway, because a person can read them too, and that is how you accept the work.

什麼時候可以刪掉交接檔，什麼會留下

如果平台能跨會話，為長工作保有可信的記憶，讓新的會話不必讀檔案就能接著做，交接檔就可以拿掉。不過需求和計畫我還是會留成檔案，因為人也讀得了它們，而驗收工作靠的就是這個。

什么时候可以删掉交接文件，什么会留下

如果平台能在跨会话时对长任务保有可靠的记忆，新会话不读文件就能接着干，交接文件就可以去掉。不过需求和计划我还是会留成文件，因为人也能读它们，验收工作靠的就是这个。

/harness-rookie-wondering I have read the chapter "Long work across sessions". Teach me how this harness keeps long work in files (topic 9): the task folder, the handover file a new session reads, and the goal that groups several tasks. Open real files with me and draw how the pieces fit together.
