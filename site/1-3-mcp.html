The Knowledge經驗分享经验分享

In one sentence

MCP is not a new power. It is a standard plug for tools, and it brings other people's code, permissions and text into your agent.

一句話

MCP 不是新的能力，而是工具的標準插頭；插上它，別人的程式碼、權限和文字也跟著進了你的 agent。

一句话

MCP 不是什么新的能力，而是工具的一个标准插头；插上它，别人的代码、权限和文本也跟着进了你的 agent。

For leaders

  • The decision: treat every MCP server as a dependency you approve, like a library you did not write, and prefer a plain command when one does the job.
  • The risk: a server brings in other people's code, their permissions, and text the model will read and obey, and its tool list can change after you approved it. I have not tested whether a hook guards MCP tools the way it guards built-in ones.
  • The cost of doing it right: a short review per server (who wrote it, what it can touch, where the credentials live), and a re-read of the tool list every so often.
  • Ask the team: "Which servers are connected, who approved each, and what can each one touch?"

給主管

  • 要做的決定：把每個 MCP server 當成一個要你批准的依賴，就像一個不是你寫的函式庫；一個普通的指令就能完成的工作，優先用指令。
  • 風險：server 會帶進別人的程式碼、別人的權限，以及模型會讀、也會照做的文字，而且在你批准之後，它的工具清單還可能改變。hook 能不能像守內建工具那樣守住 MCP 工具，我沒有測過。
  • 做對的成本：每個 server 做一次簡短的審查（誰寫的、能碰什麼、憑證放在哪裡），再隔一段時間重讀一次工具清單。
  • 可以問團隊：「接了哪些 server？每個是誰批准的？每個能碰什麼？」

写给管理者

  • 要拍板的事：把每个 MCP server 都当成一个要你批准的依赖，就像一个不是你写的库；一条普通命令就能完成的事，优先用命令。
  • 风险：server 会带进来别人的代码、别人的权限，以及模型会读、会照做的文本，而且你批准之后，它的工具清单还可能变。hook 能不能像管内置工具那样管住 MCP 工具，我没有测过。
  • 做对的代价：每个 server 做一次简短的审查（谁写的、能碰什么、凭据放在哪），再隔一段时间重读一遍工具清单。
  • 可以问团队：“现在连着哪些 server？每个是谁批准的？每个能碰什么？”

Why would tools need a standard plug?

An agent is only as useful as the tools it has. Sooner or later you will want yours to read your issue tracker, query a database or drive a browser, and someone has to write each of those tools. The trouble is that each platform (VS Code Copilot, Claude Code, Codex) has its own way to accept a tool.

So without a shared standard, the work multiplies. Three platforms and three tools could need nine separate connectors, each of them code that someone must write and then keep up to date. Every new platform adds a row, and every new tool adds a column.

The Model Context Protocol (MCP) is the standard that fixes this. It gives both sides one protocol, an agreed way of sending messages, so that two programs written by different people can work together. A tool is then written once, as an MCP server, and a platform learns the protocol once. After that, any server works with any platform that speaks MCP. Think of a USB socket: the plug is the standard, and it says nothing about what you plug in.

On the tool's side, an MCP server is a program that offers capabilities to an agent in the standard way, and it can run on your machine or somewhere else. On the other side is the MCP host, the AI application, such as VS Code. It makes one client for each server it connects to, and that client holds the connection.

Does a standard plug give the agent new powers, then? Usually not. MCP rarely gives an agent a power it could not have otherwise (a remote service with its own sign-in is the exception, since it can offer access you have no other way to get). What it changes is how tools are plugged in. If that is all it changes, the question that matters is what comes through the plug along with the tool.

工具為什麼需要一個標準插頭？

agent 有多少用處，取決於它手上有哪些工具。遲早你會想讓它讀你的問題追蹤系統、查資料庫，或操作瀏覽器，而這些工具都得有人寫。麻煩的是，每個平台（VS Code Copilot、Claude Code、Codex）接收工具的方式都不一樣。

所以，沒有共同的標準，工作量就會成倍增加。三個平台加三個工具，可能需要九個各自獨立的連接器，每一個都是有人要寫、寫完還要持續更新的程式碼。每多一個平台，就多一列；每多一個工具，就多一欄。

Model Context Protocol（MCP）就是解決這個問題的標準。它給兩頭定了同一套協定，也就是一種約定好的傳訊息的方式。有了它，不同人寫的兩個程式也能一起工作。這樣一來，一個工具只要寫一次，寫成一個 MCP server；一個平台也只要學一次這個協定。之後，任何 server 都能配合任何支援 MCP 的平台。想想 USB 插座就懂了：插頭是標準，至於你插上去的是什麼，它一概不管。

在工具這一頭，MCP server 是用標準方式向 agent 提供能力的程式，可以跑在你的機器上，也可以跑在別處。另一頭是 MCP host，也就是 AI 應用程式，例如 VS Code。它對連上的每個 server 各建一個 client，由這個 client 負責維持連線。

那麼，一個標準插頭會不會讓 agent 多出新的本事？一般不會（有自己登入機制的遠端服務是例外，它能提供你用別的辦法拿不到的存取）。MCP 改變的是工具怎麼接上去。既然改的只是接法，真正該問的就是：跟著工具一起，還有什麼從這個插頭進來了。

工具为什么需要一个标准插头？

agent 有多大用处，取决于它手里有哪些工具。早晚有一天，你会想让它读你的问题跟踪系统、查数据库，或者操作浏览器，而这些工具都得有人来写。麻烦在于，每个平台（VS Code Copilot、Claude Code、Codex）接收工具的方式都不一样。

所以，没有一个共同的标准，工作量就会成倍增加。三个平台、三个工具，可能就要九个单独的连接器，每一个都是有人要写、写完还要持续更新的代码。每多一个平台，就多一行；每多一个工具，就多一列。

Model Context Protocol（MCP）就是解决这个问题的标准。它给两头定了同一套协议，也就是一种约定好的发消息的方式。有了它，不同人写的两个程序也能配合工作。这样一来，一个工具只要写一次，写成一个 MCP server；一个平台也只要学一次这个协议。之后，任何 server 都能和任何支持 MCP 的平台配合。可以想想 USB 接口：插头是标准，至于你插的是什么，它一概不管。

在工具这一头，MCP server 是一个以标准方式向 agent 提供能力的程序，可以运行在你的机器上，也可以在别处。另一头是 MCP host，也就是 AI 应用，比如 VS Code。它为每个连上的 server 建一个 client，由这个 client 保持连接。

那么，一个标准插头会不会让 agent 多出新的本事？一般不会（自带登录的远程服务是个例外，它能提供你没有别的办法获得的访问）。MCP 改变的是工具怎么接上去。既然只改了接法，真正要问的就是：随着工具一起，还有什么从这个插头进来了。

What you actually plug in

What a server can offer

To see what comes through, start with what a server can send across. The protocol defines three things a server can expose. (Architecture overview) The one most people mean when they say MCP is tools: functions the agent can call to do something, such as file operations, API calls and database queries. They are the same kind of tool as in chapter 1.2. A server can also offer resources, which are data the agent can read for context, such as file contents or database records, and prompts, which are reusable templates that help structure a conversation, such as a system prompt or few-shot examples.

Before any of these is used, the agent's side asks the server what it has. For tools that is a tools/list request, and what comes back is each tool's name, its description and the parameters it accepts. Later, when the model asks for a call, the host sends a tools/call to the right server and puts the answer back into the conversation as text. So from the model's point of view, an MCP tool looks like any other tool.

Local and remote

A server can run in one of two ways, and the protocol is the same on both. A local (stdio) server is one the host starts as a program on your machine. The host talks to it through its standard input and output, the plain text pipes every command line program has. Typically only that one host uses it. A remote (Streamable HTTP) server runs somewhere else, and the host talks to it over ordinary web requests (HTTP), usually with sign-in. One remote server can serve many users.

The difference matters for safety. A local server is code that runs on your computer with your rights, while a remote one is someone else's service that you send data to.

What you take in when you plug one in

Local or remote, though, a server is not a feature you switch on. It is a dependency, like a library you did not write, and four things come in with it.

  1. It brings other people's code, because a local server runs on your machine. VS Code's own documentation says: "Local MCP servers can run code on your machine, and tools can access external services using your permissions." (MCP servers in VS Code)
  2. It brings other people's permissions. The server acts with whatever access you gave it, such as your database login or your token for the issue tracker, so through the server the agent has that access too.
  3. It brings other people's words, and the model treats them as instructions. A server's tool descriptions are text the model reads and takes seriously, and what a tool returns (an issue body, a web page) is text from whoever wrote it. Text the model reads can contain commands for it. Chapter 4.6 is about this.
  4. It brings a standing cost. Each tool's name, description and parameters are sent to the model on every call, so a server with many tools you rarely use still costs tokens on every turn, and many tools make it harder for the model to choose (chapter 1.2). There are ways around it, and I only point to them here. The protocol's own docs mention that clients with many servers can use progressive tool discovery instead of loading every tool up front (Architecture overview). Anthropic's post Code execution with MCP names tool definitions overloading the context window as a problem, and describes loading only the tools needed, or having the agent call servers through code. How big the cost is depends on how many tools you connect, so count yours.

What to check before you add one

If a server is a dependency, it deserves the questions you would ask of any dependency. Here are four, in the order I would ask them.

  • Who wrote it, and who keeps it up to date? VS Code's advice is to review "the publisher, command or endpoint, and requested access" before you install or start a server.
  • What can it touch? Prefer a server limited to what the job needs. A server for reading issues should not hold a token that can delete repositories.
  • Where do the credentials live? Keep them out of the chat and out of your project's commits, as VS Code's docs also warn.
  • Can what it returns be trusted? If the text comes from outside, such as the public web or tickets that anyone can file, treat it as untrusted.

MCP, or just a command?

There is also a question to ask before any of these four: does this tool need a server at all? Many things your agent needs already exist as command-line programs, such as git, a test runner or a cloud CLI, and an agent that can run a terminal can use them with no server.

Reach for When
A command line program It already exists, runs locally, and its output is short and clear. Fewer moving parts
An MCP server You want the same tool across several platforms, or it needs structured inputs, a discoverable list of capabilities, or sign-in to a remote service

I lean towards the command first, because it adds less code and fewer permissions to your setup. Moving to MCP is worth it once the shared plug starts to pay for the extra dependency.

Will a hook guard an MCP tool?

You might hope that a hook would catch a bad MCP call the way it catches a bad built-in one. I cannot tell you that it will, because I have not tested it. My own harness builds no MCP server, since a company sets them up for its own environment, and some company environments forbid unofficial ones. So I do not know whether MCP tool calls pass through a hook the way built-in tool calls do, nor whether the hook sees their arguments in full. Until you have tested it yourself, with a harmless server, do not count on a hook to guard an MCP tool.

How to check your own setup

The servers you have already connected deserve a look too. For each one, ask three questions:

  1. Do I know who wrote it and what it can touch?
  2. Could a command-line program do the same job?
  3. How many of its tools do I really use?

The third one you can answer without installing anything. List the tools your agent currently has (most editors show them in the chat's tools picker, though where exactly depends on the editor, so check its docs) and count them. Then ask which of them you used in the last week. The rest are cost and risk without benefit.

你接進來的到底是什麼

server 能提供什麼

要看清進來了什麼，得先知道 server 能往這邊送些什麼。協定定義了 server 可以公開的三樣東西。（Architecture overview）大多數人說 MCP，指的是其中的 Tools（工具），也就是 agent 可以呼叫來做事的函式，例如檔案操作、API 呼叫、資料庫查詢，它和 Tool calling，和給 agent 設計工具 裡的工具是同一類。除了工具，server 還可以提供 Resources（資源），也就是 agent 可以讀來當上下文的資料，例如檔案內容或資料庫紀錄；以及 Prompts（提示），也就是可重複使用的範本，用來幫忙組織對話，例如 system prompt 或 few-shot 範例。

在用到這些之前，agent 這一邊會先問 server 有什麼。對工具來說，這是一個 tools/list 請求，拿回來的是每個工具的名字、描述和它接受的參數。之後模型要求呼叫某個工具，host 就向對的 server 送出一個 tools/call，再把答案當文字放回對話。所以從模型的角度看，MCP 工具和其他任何工具沒有兩樣。

本地和遠端

server 有兩種跑法，兩種用的是同一個協定。本地（stdio） server 由 host 在你的機器上當成程式啟動，host 透過它的標準輸入和輸出（每個命令列程式都有的純文字管道）跟它說話。通常也只有這一個 host 在用它。遠端（Streamable HTTP） server 跑在別處，host 透過普通的網路請求（HTTP）跟它說話，通常要登入。一個遠端 server 可以服務很多使用者。

這個差別在安全上很重要，因為本地 server 是在你的電腦上、以你的權限執行的程式碼；遠端的則是別人的服務，你得把資料送過去。

接上一個，就帶進來什麼

不過，不管本地還是遠端，server 都不是打開就好的功能，而是一個依賴，像一個不是你寫的函式庫。接上它，會帶進來四樣東西。

  1. 它帶進別人的程式碼，因為本地 server 就在你的機器上執行。VS Code 自己的文件說：「本地 MCP server 可以在你的機器上執行程式碼，而工具可以用你的權限存取外部服務。」（MCP servers in VS Code）
  2. 它帶進別人的權限。server 以你給它的存取權行動，例如你的資料庫登入、你在問題追蹤系統的 token，於是 agent 透過 server，也擁有了那些存取權。
  3. 它帶進別人的話，而模型會把這些話當成指令。server 的工具描述，是模型會讀、也會當真的文字；工具回傳的內容（issue 的內文、網頁），也是寫它的人寫的文字。模型讀到的文字，可能含有給它的命令，agent 讀到的文字可能在指揮它 講的就是這個。
  4. 它帶進一筆固定的成本。每個工具的名字、描述和參數，每次呼叫都會送給模型，所以一個工具很多、你卻很少用的 server，每一輪還是要花 token；而且工具一多，模型就更難選（Tool calling，和給 agent 設計工具）。繞開的辦法是有的，這裡只點到為止。協定自己的文件提到，連了很多 server 的 client，可以用漸進式的工具探索，不必一開始就載入所有工具（Architecture overview）。Anthropic 的文章 Code execution with MCP 則把工具定義塞滿上下文視窗當成一個問題，並描述了只載入需要的工具，或讓 agent 透過程式碼呼叫 server 的做法。成本有多大，取決於你接了多少工具，所以數一數你自己的。

加一個之前要檢查什麼

既然 server 是一個依賴，任何依賴該問的問題，它都該問。下面是四個，照我會問的順序排。

  • 誰寫的？誰持續更新它？VS Code 的建議是，安裝或啟動 server 之前，先檢視「發布者、指令或端點，以及要求的存取權」。
  • 它能碰什麼？盡量用只限於工作所需的 server，例如讀 issue 的 server，就不該握有能刪除倉庫的 token。
  • 憑證放在哪裡？別放在對話裡，也別提交進專案，VS Code 的文件也是這樣提醒的。
  • 它回傳的能信嗎？如果文字來自外面，例如公開的網路、任何人都能開的工單，就當成不可信的輸入。

用 MCP，還是只用一個指令？

在這四個問題之前，其實還有一個問題：這個工具真的需要 server 嗎？你的 agent 需要的很多東西，早就以命令列程式的形式存在了，例如 git、測試執行器、雲端 CLI。只要 agent 能用終端機，完全不需要 server 就能用它們。

選 什麼時候
命令列程式 它已經存在、在本地執行，輸出又短又清楚。牽涉的環節更少
MCP server 你想在好幾個平台上用同一個工具，或者它需要結構化的輸入、可探索的能力清單，或登入遠端服務

我傾向先用指令，因為它在你的設定裡加的程式碼和權限比較少。等共用插頭的好處開始值得多出來的那個依賴，再換成 MCP。

hook 守得住 MCP 工具嗎？

你也許希望，hook 能像擋下一次糟糕的內建工具呼叫那樣，擋下一次糟糕的 MCP 呼叫。這一點我沒辦法向你保證。我自己的 harness 沒有建任何 MCP server（這類 server 是公司照自己的環境設定的，有些公司環境還禁止非官方的），所以 MCP 工具呼叫會不會像內建工具呼叫那樣經過 hook、hook 看不看得到完整的參數，我沒有測過。在你自己用一個無害的 server 測試過之前，不要指望 hook 能替你守住 MCP 工具。

怎麼檢查你自己的設定

已經接上的 server，也值得回頭看一看。對每一個，問三個問題：

  1. 我知道是誰寫的、它能碰什麼嗎？
  2. 一個命令列程式能做同樣的工作嗎？
  3. 它的工具，我真正用到幾個？

第三個問題，不用安裝任何東西就能回答。列出你的 agent 目前有的工具（大多數編輯器在對話的工具選擇器裡顯示，確切在哪要看編輯器，查一下它的文件），數一數，再問自己過去一週用過其中哪些。其餘的，就是有成本、有風險，卻沒有好處。

你接进来的到底是什么

server 能提供什么

要看清进来了什么，先得知道 server 能往这边送些什么。协议定义了 server 可以对外提供的三样东西。（Architecture overview）多数人说 MCP，指的是其中的工具（Tools），也就是 agent 可以调用来做事的函数，比如文件操作、API 调用、数据库查询，它和Tool calling，以及怎么给 agent 设计工具里的工具是同一种。除了工具，server 还可以提供资源（Resources），即 agent 可以读来当上下文的数据，比如文件内容或数据库记录；以及提示（Prompts），即可复用的模板，用来帮着组织一次对话，比如系统 prompt 或少样本示例。

用到这些之前，agent 这一侧会先问 server 有什么。对工具来说，这是一个 tools/list 请求，拿回来的是每个工具的名字、描述和它接受的参数。之后模型要求调用某个工具，host 就向对应的 server 发一个 tools/call，再把答案作为文本放回对话。所以在模型看来，MCP 工具和别的工具没什么两样。

本地和远程

server 有两种运行方式，两种用的是同一个协议。本地（stdio） server 由 host 在你的机器上作为一个程序启动，host 通过它的标准输入和输出（每个命令行程序都有的纯文本管道）和它通信。通常也只有这一个 host 在用它。远程（Streamable HTTP） server 运行在别的地方，host 通过普通的网络请求（HTTP）和它通信，通常要登录。一个远程 server 可以服务很多用户。

这个区别对安全很要紧，因为本地 server 是以你的权限、在你电脑上运行的代码；远程 server 则是别人的服务，你得把数据发给它。

接上一个，就带进来什么

不过，不管本地还是远程，server 都不是打开就行的功能，而是一个依赖，就像一个不是你写的库。接上它，会带进来四样东西。

  1. 它带进来别人的代码，因为本地 server 就运行在你的机器上。VS Code 自己的文档说：“本地 MCP server 可以在你的机器上运行代码，工具可以用你的权限访问外部服务。”（MCP servers in VS Code）
  2. 它带进来别人的权限。server 以你给它的访问权限行事，比如你的数据库登录、你在问题跟踪系统里的 token，于是 agent 通过这个 server，也拿到了这些权限。
  3. 它带进来别人的话，而模型会把这些话当成指令。server 的工具描述，是模型会读、会当真的文本；工具返回的内容（一个 issue 的正文、一个网页），也是写它的人写的文本。模型读到的文本里，可能藏着给它的命令，agent 读到的文字可能在指挥它讲的就是这件事。
  4. 它带进来一笔固定的开销。每个工具的名字、描述和参数，每次调用都要发给模型，所以一个工具很多、你却很少用的 server，每一轮照样花 token；工具一多，模型也更难选（Tool calling，以及怎么给 agent 设计工具）。绕开的办法是有的，我在这里只点到为止。协议自己的文档提到，连了很多 server 的 client，可以用渐进式的工具发现，而不是一开始就把所有工具都加载进来（Architecture overview）。Anthropic 的文章 Code execution with MCP 则把工具定义撑爆上下文窗口当作一个问题，并介绍了只加载所需工具，或者让 agent 通过代码来调用 server 的办法。这笔开销有多大，取决于你连了多少工具，所以数一数你自己的。

加之前要检查什么

既然 server 是一个依赖，对任何依赖该问的问题，对它也都该问。下面是四个，按我会问的顺序排。

  • 谁写的，谁在持续更新？VS Code 的建议是，在安装或启动 server 之前，先审查“发布者、命令或端点，以及它请求的访问权限”。
  • 它能碰什么？优先选只限于任务所需的 server，比如一个读 issue 的 server，就不该拿着一个能删仓库的 token。
  • 凭据放在哪？别放在对话里，也别提交进项目，VS Code 的文档也是这样提醒的。
  • 它返回的东西可信吗？如果文本来自外部，比如公开的网页、任何人都能提的工单，就当成不可信的。

用 MCP，还是一条命令就够？

在这四个问题之前，其实还有一个问题：这个工具真的需要一个 server 吗？agent 需要的很多东西，本来就以命令行程序的形式存在，比如 git、测试运行器、云平台的命令行工具。只要 agent 能用终端，不需要任何 server 就能用上它们。

选 什么时候
命令行程序 它已经有了，在本地运行，输出又短又清楚。活动部件更少
MCP server 你想在多个平台上用同一个工具，或者它需要结构化的输入、可发现的能力清单，或者要登录一个远程服务

我倾向于先用命令，因为它给你的配置加进来的代码和权限都更少。等共用插头的好处开始抵得过多出来的那个依赖，再换成 MCP 也不迟。

hook 管得住 MCP 工具吗？

你也许指望，hook 能像拦下一次糟糕的内置工具调用那样，拦下一次糟糕的 MCP 调用。这一点我没法给你打包票。我自己的 harness 没有搭任何 MCP server（这类 server 是公司按自己的环境配的，有的公司还禁止非官方的），所以 MCP 工具调用是不是像内置工具调用那样经过 hook、hook 能不能看到它们的完整参数，我没有测过。在你自己用一个无害的 server 测过之前，别指望 hook 能替你守住 MCP 工具。

怎么检查你自己的配置

已经连上的 server，也值得回头看一看。对每一个，问三个问题：

  1. 我知道它是谁写的、能碰什么吗？
  2. 命令行程序能做同样的事吗？
  3. 它的工具里，我真正用到的有几个？

第三个问题，不用安装任何东西就能回答。列出你的 agent 现在有的工具（多数编辑器在对话的工具选择器里显示，具体在哪要看编辑器，查一下它的文档），数一数，再问问自己上周用过其中哪些。其余的，就是有成本、有风险，却没有收益。

Where more plugs go wrong

The risk starts with the servers themselves. Each server is a path for outside text and outside code to reach your agent, so every plug you add widens the attack surface. That includes the one you added to try something and then forgot, because it is still there.

A famous name is no reason to skip the review. A server published by a respected company is "official", yet it is still given your credentials and still returns text from other people. Official does not mean safe for you.

Even a server you reviewed carefully can change under you. The protocol lets a server tell the client that its tools changed, so a tool that was fine when you looked at it may not be the one you have next month. A server can also change a tool's description after you approved it, and the description is text the model obeys (this kind of attack is often called a rug pull or tool poisoning, and chapter 4.6 covers the idea). Re-read the list now and then, and pin the version of a server where you can.

The last trap is assuming that a shared standard means shared behavior. Platforms differ in which parts of the protocol they support, in how they ask for approval and in where they store the settings, so check the current documentation for yours.

插頭多了，會在哪裡出問題

風險先從 server 本身說起。每個 server 都是外面的文字和外面的程式碼通向你的 agent 的一條路，所以每多接一個插頭，攻擊面就大一些。而且不只是正在用的才算，那些當初為了試試而加、後來忘掉的 server，也一直在那裡。

名氣大，也不是跳過審查的理由。受人敬重的公司發布的 server 是「官方」的，可它一樣會拿到你的憑證，也一樣會回傳別人寫的文字。官方不代表對你安全。

就算是你仔細審查過的 server，也可能在你不知道的時候變了。協定讓 server 可以通知 client，它的工具變了，所以你審查時沒問題的工具，下個月可能就不是你手上這個了。server 還可以在你批准之後改工具的描述，而描述是模型會照做的文字（這種攻擊常被叫做 rug pull 或 tool poisoning，agent 讀到的文字可能在指揮它 講了這個想法）。所以要不時重讀清單，能固定 server 的版本就固定。

最後一個陷阱，是以為標準一樣，行為也就一樣。各平台支援協定的哪些部分、怎麼要求批准、設定存在哪裡，都不同，所以請查你的平台目前的文件。

插头多了，会在哪里出问题

风险先从 server 本身说起。每个 server 都是外部文本和外部代码通向你的 agent 的一条路，所以每多接一个插头，攻击面就大一圈。而且不光是在用的才算，那些当初为了试试加上、后来忘掉的 server，也一直在那里。

名气大，也不是跳过审查的理由。一个受人尊敬的公司发布的 server 是“官方”的，可它照样会拿到你的凭据，照样会返回别人写的文本。官方不等于对你安全。

就算是你仔细审查过的 server，也可能在你不知情的时候变了。协议允许 server 告诉 client，它的工具变了，所以你审查时没问题的工具，下个月可能就不是那一个了。server 还可以在你批准之后改某个工具的描述，而描述是模型会照做的文本（这类攻击常被叫作 rug pull 或工具投毒，agent 读到的文字可能在指挥它讲了这个想法）。所以要时不时重读一遍清单，能固定 server 的版本就固定。

最后一个坑，是以为标准一样，行为也就一样。各平台支持协议的哪些部分、怎么请求审批、把设置存在哪里，都不一样，所以请查你所用平台的当前文档。

Do the protocol and VS Code see it this way? Industry practice

The protocol's own docs describe MCP as a protocol for context exchange, and say it "does not dictate how AI applications use LLMs or manage the provided context". In other words, the host decides what to load and how to ask you. (Architecture overview) VS Code, one such host, treats servers as code to review: look at the publisher and the access requested, and approve only actions you understand. (MCP servers in VS Code)

So the two agree on how the jobs are split. The protocol makes plugging in easy, and deciding what to plug in is still yours.

協定和 VS Code 也這麼看嗎？ 業界做法

協定自己的文件把 MCP 描述成交換上下文的協定，並說它「不規定 AI 應用程式怎麼使用 LLM，或怎麼管理提供的上下文」。換句話說，載入什麼、怎麼問你，由 host 決定。（Architecture overview）VS Code 正是這樣的一個 host，它把 server 當成要審查的程式碼：看發布者和要求的存取權，只批准你看得懂的動作。（MCP servers in VS Code）

所以兩者在分工上是一致的。協定讓接上去變容易，而決定接什麼，仍然是你的事。

协议和 VS Code 也这么看吗？ 业界做法

协议自己的文档把 MCP 描述为一个交换上下文的协议，并说它“不规定 AI 应用如何使用 LLM，也不规定如何管理所提供的上下文”。换句话说，加载什么、怎么问你，由 host 决定。（Architecture overview）VS Code 就是这样一个 host，它把 server 当成要审查的代码：看发布者和它请求的访问权限，只批准你理解的操作。（MCP servers in VS Code）

所以两者对分工的看法是一致的。协议让接入变容易，而决定接入什么，仍然是你的事。

When to delete a server Industry practice

Deciding what to plug in includes deciding what to unplug. Remove a server when you stop using its tools, or when a plain command does the job. The caution itself can loosen if platforms start to sandbox servers by default, so that a bad one cannot do much harm. Even then, I would check the publisher and the access before adding one.

什麼時候可以刪掉一個 server 業界做法

決定接什麼，也包括決定拔掉什麼。你不再用某個 server 的工具，或者一個普通指令就能做同樣的事，就把它移除。如果平台開始預設把 server 放進沙箱，讓壞的 server 做不了太大的壞事，這份謹慎本身也可以放鬆一些。即使這樣，我還是會在加之前，先檢查發布者和存取權。

什么时候可以删掉一个 server 业界做法

决定接入什么，也包括决定拔掉什么。不再用某个 server 的工具了，或者一条普通命令就能完成任务了，就把它移除。如果平台开始默认给 server 加沙箱，让坏的 server 干不了多大的坏事，这份谨慎本身也可以放松一点。即便如此，我还是会在添加之前检查发布者和访问权限。
