In one sentence

MCP is a standard protocol for connecting tools to an agent, and it usually doesn't give the agent any new abilities, but every server you connect brings in someone else's code, your permissions, someone else's text and a token cost, so check first whether a command would do, and once a server is connected, manage it as a dependency.

一句話

MCP 是把工具接到 agent 上的標準協定，它通常不會讓 agent 多出新能力，但每接一個 server，別人的程式碼、你的權限、別人寫的文字和一筆 token 成本都會跟著進來，所以接之前先看一條指令夠不夠，接了就當成依賴來管。

一句话

MCP 是把工具接到 agent 上的标准协议，它一般不会让 agent 多出新本事，但是每接一个 server，别人的代码、你的权限、别人写的文本和一笔 token 开销都会跟着进来，所以接之前先看一条命令够不够，接了就当成依赖来管。

For leaders

  • The decision: treat every MCP server as a dependency that needs approval, the way you'd treat a library you didn't write yourselves, and when an ordinary command can do the job, prefer the command.
  • The risk: a server brings in someone else's code, your permissions and text the model will take at face value, and it can still change after you approve it. npm has already seen a server whose first 15 versions were clean and which added a backdoor only in 1.0.16. Whether hooks can control MCP tools in Copilot isn't in the docs, and I haven't tested it.
  • The cost of doing it right: a short review of each server (who wrote it, what it can touch, where its credentials live, whether its version is pinned), and rereading the tool list every so often.
  • Ask the team: "Which servers are connected right now? For each one, who approved it, what can it touch, and is its version pinned?"

給主管

  • 要做的決定：把每個 MCP server 都當成一個要批准的依賴，就像一個不是你們寫的函式庫；一條普通指令做得到的事，優先用指令。
  • 風險：server 會帶進來別人的程式碼、你們的權限，以及模型會信以為真的文字，而且批准之後它還可能變，npm 上就出現過前 15 個版本都正常、到 1.0.16 才加後門的 server。hook 管不管得住 Copilot 裡的 MCP 工具，文件沒有寫，我也沒有測過。
  • 做對的成本：每個 server 做一次簡短的審查（誰寫的、能碰什麼、憑證放在哪、版本固定了沒有），再隔一段時間重讀一遍工具清單。
  • 可以問團隊：「現在連著哪些 server？每個是誰批准的，能碰什麼，版本固定了嗎？」

  • 风险：server 会带进来别人的代码、你们的权限，以及模型会当真的文本，而且批准之后它还可能变，npm 上就出过前 15 个版本都正常、到 1.0.16 才加后门的 server。hook 能不能管住 Copilot 里的 MCP 工具，文档没有写，我也没有测过。

Without MCP, every tool gets written once per platform

In this chapter I want to teach you three things to think through before you connect an MCP server: what it actually changes, what comes in with it, and when a single command would do.

What an agent can do depends on the tools it has, and sooner or later you'll want it to read your issue tracker, query a database or drive a browser, and somebody has to write those tools. Each platform (VS Code Copilot, Claude Code, Codex) connects tools in its own way, so without a shared standard, three platforms and three tools can mean nine connectors, and every platform or tool you add multiplies the code there is to write and maintain.

Model Context Protocol (MCP) is the standard that solves this, and Anthropic open-sourced it in November 2024. It sets the format of the messages between AI applications and tools, so a tool only has to be written once, as an MCP server, and a platform only has to implement the protocol once. After that, any server works on any platform that supports MCP, and nine connectors turn into three plus three. The official docs compare it to a USB-C port. VS Code, Claude Code, Codex, Cursor and ChatGPT all support it today. (What is the Model Context Protocol (MCP)?)

There are two more roles in the protocol you need to know. The MCP host is the AI application itself, such as VS Code or Claude Code, and for each server it connects to, the host creates an MCP client, which maintains the connection to that server. (Architecture overview)

You might expect MCP to give the agent new abilities, but usually it doesn't. It changes how tools get connected, and most of what a server can do, the agent could also do with a command or an API call. The exception is a remote server hosted by the vendor with its own sign-in, which can give you access you couldn't get any other way. So when you connect a server, don't start by asking what more it gives you. Start by asking what else came in along with the tools.

What actually comes in when you connect a server

Connecting a server adds a dependency you didn't write to your setup. It has its own code and its own release pace, it works with the permissions you give it, and it writes into the model's context.

A server can offer three things

The protocol defines three things a server can offer, and what separates them is who decides to use them. Tools are functions the model decides to call by itself, for things like working with files, calling an API or querying a database, and they're what most people mean when they say MCP. Resources are read-only data, such as file contents or a database schema, and the application decides whether they go into the context. Prompts are reusable templates that the user invokes explicitly. (Understanding MCP servers)

Once connected, the host sends a tools/list request and gets back each tool's name, description and parameters, then merges the tools from all its servers into one table for the model. When the model wants a tool, the host sends a tools/call to the right server and puts the result back into the conversation. So to the model, an MCP tool looks the same as a built-in one. It still has only the name, description and error messages to go on, and every rule from the previous chapter applies, except that someone else wrote those words now.

A local server runs on your machine, a remote server runs on someone else's

A server can run in two ways, and both use the same messages. A local server uses the stdio transport: the host starts a process on your machine and talks to it through its standard input and output, so what you put in your configuration is really just a startup command, like the Playwright example in the VS Code docs, npx -y @playwright/mcp@latest. A remote server uses the Streamable HTTP transport: it runs on someone else's machine, the host talks to it over HTTP, you usually have to sign in, and one server usually serves many users, as Sentry's official server does.

This difference decides what you're defending against. A local server is code running on your computer with your permissions, so what worries you is what it does on your machine. A remote server is someone else's service, so what worries you is the data you send it and the account access you hand it.

Four things come in with every server

  1. Someone else's code. A local server is a program running on your machine, and it's running from the moment it starts, without waiting for the model to call a tool. The VS Code docs put it plainly: "Local MCP servers can run code on your machine, and tools can access external services using your permissions." (Add MCP servers in VS Code)
  2. Your permissions. A server acts with the access you give it, such as your database account or your issue tracker token, and through the server the agent gets that access too. So however wide the token's scope is, that's roughly how much damage is possible when the agent makes a mistake or gets tricked.
  3. Someone else's text. Tool descriptions are written by someone else, and the model reads them and believes them. What tools return (the body of an issue, a web page) is written by someone else too, and this text can hide commands aimed at the model (Text the agent reads can give it orders).
  4. A fixed token cost. Tool names, descriptions and parameters all count as model input, and if the host sends all of them to the model, they go along with every request. Caching makes that cheaper, but it doesn't free up any of the context window, and the more tools there are, the more likely the model is to pick the wrong one.

The fourth one can get large. Anthropic gives an example with five servers: GitHub's 35 tools take about 26K tokens, Slack's 11 take about 21K, and with Sentry, Grafana and Splunk added, 58 tools take up about 55K tokens before the conversation starts (Introducing advanced tool use for Claude). What a host can do about it is tool search: instead of sending the tool definitions to the model, it gives the model a search tool and loads a full definition only when that tool is needed. Claude Code does this by default, loading just the tool names and server instructions at session start (Connect Claude Code to tools via MCP). VS Code has it on by default too for Claude Sonnet 4.5, Opus 4.5 and later, keeping only a small core set loaded, such as reading and writing files and running commands, and in a live experiment its team saw the median user's token usage over a whole session fall by about 18% with Claude models (Improving token efficiency for GitHub Copilot in VS Code). So how big this cost is depends on your host, your model and how many tools you've connected, and it's best to count your own.

First see whether a command will do

A lot of what an agent needs already exists as command-line programs, such as git, gh, test runners and the cloud platforms' CLIs, and as long as the agent can use a terminal, it can use them without any server. I lean toward commands first, because they add less code and fewer permissions to your setup, and you can always switch to MCP later, once sharing one tool across platforms is worth the extra dependency.

The tool vendors themselves say the same. The VS Code docs say right at the start that if your existing tools meet your needs, you don't need another server. The Claude Code docs recommend preferring CLIs like gh, aws and gcloud, because they don't add a tool listing to the context (Manage costs effectively). And the README of Microsoft's Playwright MCP tells people using coding agents that a CLI plus skills may suit them better, leaving MCP for long loops that need to keep browser state (Playwright MCP).

How many tokens you save depends on the job, though. In July 2026, Stefan Judis at Checkly ran the same browser task three times each in Claude Code: with Playwright MCP the context ended up at about 48K to 50K, and with playwright-cli at about 45K to 48K. That's a small gap, and his explanation is that tool definitions are loaded lazily now (CLIs are more token-efficient than MCP. Or are they?). So on a host with tool search, the advantage of a command is mainly fewer dependencies and permissions, not tokens.

MCP has things a command can't match, too. Each of its tools has a name and a parameter schema, so the host can approve tool by tool, whereas once an agent has a terminal it can run any command, and all a hook sees is the command's text (Hooks, the point every call passes through). So if you're building an interface to an internal system with a lot of write operations, a few narrow MCP tools may be easier to control than one command-line program that can do everything.

Choose When
A command-line program It already exists, it runs locally, its output is short and clear, and the agent can use a terminal
An MCP server You want to share one tool across platforms, you need structured input, you have to sign in to a remote service, you want to approve tool by tool, or the agent runs somewhere with no terminal

Ask five questions before you connect one

A server is a dependency, so whatever you'd ask about a dependency, you should ask about a server. Here are five questions, in the order I'd ask them.

  • Who wrote it, and who keeps it up to date? VS Code's advice is to review "the publisher, command or endpoint, and requested access" before installing or starting a server (Add MCP servers in VS Code). Being listed doesn't mean being reviewed either: the official MCP Registry only stores metadata and verifies publishers' namespaces, and it leaves security scanning to package registries like npm and to downstream marketplaces (The MCP Registry).
  • What can it touch? Prefer a server limited to what the task needs. A server that reads issues shouldn't be holding a token that can delete repositories.
  • Where do its credentials live? Not in the chat and not committed to the project, and the VS Code docs add that a personal configuration file isn't a place for secrets either (MCP configuration reference).
  • Is the version pinned? If the startup command says @latest, then as soon as the package updates, later starts may run new code, so pin a version you've looked at.
  • Can you trust what it returns? If the text comes from outside, like public web pages or tickets anyone can file, treat it as untrusted.

Whether a hook can control MCP tools depends on the platform

The Claude Code docs spell it out: MCP tools appear in events like PreToolUse and PostToolUse just as ordinary tools do, named mcp__<server>__<tool> (Hooks reference). The Copilot side doesn't say. GitHub's hook reference only says preToolUse fires "Before each tool executes", the tool names it lists are all built-in ones, and the VS Code hook docs don't mention MCP either (GitHub Copilot hooks reference). My own harness doesn't set up any MCP server, because these servers are something each company configures for its own environment, and some companies forbid unofficial ones, so I haven't tested whether MCP tools on Copilot pass through hooks or whether a hook sees the complete arguments.

If you want to rely on a hook, test it first with a harmless server: write a hook that only records its input, call an MCP tool once, and look in the record for that call and its full arguments. Even if the call does pass through the hook, all the hook sees is the arguments of this one call. It can't see what the server does after receiving them.

How to check after connecting

Servers you've already connected deserve a second look too. Ask three questions about each one:

  1. Do I know who wrote it and what it can touch?
  2. Could a command-line program do the same thing?
  3. How many of its tools do I actually use?

You can answer the third without installing anything. In VS Code, open the Tools page in Chat: Open Customizations to see how many tools are enabled in each group and how many there are in total, and in Claude Code, use /context to see what's taking up the context. Once you've counted, think about which ones you used last week. All the others carry cost and risk with no benefit, so turn those tools off or disable the whole server.

接上一個 server，到底接進來了什麼

接上一個 server，等於在你的設定裡加了一個不是你寫的依賴，它有自己的程式碼和更新節奏，用著你給的權限，還會往模型的上下文裡寫東西。

server 能提供三樣東西

協定定義了 server 可以提供的三樣東西，差別在於由誰決定用。工具（Tools）是模型自己決定呼叫的函式，例如操作檔案、呼叫 API、查資料庫，多數人說 MCP，指的就是它。資源（Resources）是唯讀的資料，例如檔案內容或資料庫 schema，由應用程式決定要不要放進上下文。提示（Prompts）是可重複使用的範本，由使用者明確呼叫。（Understanding MCP servers）

host 連上 server 以後發一個 tools/list 請求，拿回每個工具的名字、描述和參數，再把所有 server 的工具合成一張表交給模型，模型要用某個工具時，host 向對應的 server 發一個 tools/call，再把結果放回對話。所以在模型看來，MCP 工具和內建工具沒有差別，它還是只能靠名字、描述和錯誤訊息來用工具，上一章的規則全都適用，只是這些文字現在是別人寫的。

本機 server 跑在你的機器上，遠端 server 跑在別人那裡

server 有兩種執行方式，用的是同一套訊息。本機 server 走 stdio 傳輸，host 在你的機器上啟動一個處理程序，透過它的標準輸入和輸出溝通，所以設定裡寫的其實就是一條啟動指令，例如 VS Code 文件裡 Playwright 的例子是 npx -y @playwright/mcp@latest。遠端 server 走 Streamable HTTP 傳輸，執行在別人的機器上，host 透過 HTTP 和它溝通，通常要登入，同一個 server 通常服務很多使用者，例如 Sentry 官方的 server。

這個差別決定了你要防什麼。本機 server 是用你的權限、在你電腦上執行的程式碼，要防的是它在你機器上做什麼；遠端 server 是別人的服務，要防的是你傳給它的資料，和你交給它的帳號權限。

接上一個 server，有四樣東西跟著進來

  1. 別人的程式碼。本機 server 就是執行在你機器上的一支程式，一啟動就在跑，不用等模型呼叫工具。VS Code 的文件說得很直接：「本機 MCP server 可以在你的機器上執行程式碼，工具可以用你的權限存取外部服務。」（Add MCP servers in VS Code）
  2. 你的權限。server 用你給它的存取權限做事，例如你的資料庫帳號、你在問題追蹤系統裡的 token，agent 透過這個 server 也就拿到了這些權限，所以 token 的範圍有多大，agent 出錯或被騙的時候，損失就可能有多大。
  3. 別人寫的文字。工具的描述是別人寫的，模型會讀、會當真，工具回傳的內容（一個 issue 的內文、一個網頁）也是別人寫的，這些文字裡可能藏著給模型的命令（agent 讀到的文字可能在指揮它）。
  4. 一筆固定的 token 成本。工具的名字、描述和參數都算模型的輸入，如果 host 把它們全送給模型，每次請求都要帶上，快取能讓錢少花一些，但占掉的上下文視窗一點也沒少，工具一多，模型也更容易選錯。

第四樣成本可以很大。Anthropic 舉過一個五個 server 的例子，GitHub 的 35 個工具約 26K token，Slack 的 11 個約 21K，再加上 Sentry、Grafana 和 Splunk，一共 58 個工具，對話還沒開始就占了約 55K token（Introducing advanced tool use for Claude）。host 這邊的辦法是工具搜尋，先不把工具定義送給模型，只給它一個搜尋工具，用到的時候才載入完整定義。Claude Code 預設就這麼做，會話開始時只載入工具名稱和 server 的說明（Connect Claude Code to tools via MCP）。VS Code 在 Claude Sonnet 4.5、Opus 4.5 以上的模型上也預設開啟，只留讀寫檔案、執行指令這樣一小組核心工具常駐，它的團隊做過線上實驗，用 Claude 模型時，中位使用者一整個會話的 token 用量降了約 18%（Improving token efficiency for GitHub Copilot in VS Code）。所以這筆成本到底有多大，要看你用的 host、模型和連了多少工具，最好數一數你自己的。

先看一條指令夠不夠

agent 需要的很多東西本來就是命令列程式，例如 git、gh、測試執行器、雲端平台的命令列工具，只要 agent 能用終端機，不接任何 server 就能用上它們。我傾向先用指令，因為它加進你設定裡的程式碼和權限都比較少，等多個平台共用一個工具的好處抵得過多出來的那個依賴，再換成 MCP 也不遲。

工具的廠商自己也這麼建議。VS Code 的文件一開頭就說，現有的工具夠用的話，就不需要再加 server。Claude Code 的文件建議優先用 gh、aws、gcloud 這些命令列工具，因為它們不會往上下文裡加工具清單（Manage costs effectively）。微軟的 Playwright MCP 的 README 也告訴用 coding agent 的讀者，CLI 加 skill 可能更合適，MCP 留給需要保持瀏覽器狀態的長循環（Playwright MCP）。

不過省多少 token 要看具體的工作。Checkly 的 Stefan Judis 在 2026 年 7 月用 Claude Code 把同一個瀏覽器任務各跑了三遍，用 Playwright MCP 結束時的上下文約 48K 到 50K，用 playwright-cli 約 45K 到 48K，差別很小，他的解釋是工具定義現在是延遲載入的（CLIs are more token-efficient than MCP. Or are they?）。所以在有工具搜尋的 host 上，指令的好處主要是依賴和權限比較少，不在 token 上。

MCP 也有指令比不上的地方。它的每個工具都有名字和參數 schema，host 可以按工具來批准，而 agent 一旦能用終端機，就能跑任何指令，hook 讀到的也只是指令的文字（Hooks：每次呼叫都會經過的執行點）。所以替一個寫入操作很多的內部系統做介面時，幾個窄的 MCP 工具可能比一個什麼都能做的命令列程式更好管。

選 什麼時候
命令列程式 它已經有了，在本機執行，輸出又短又清楚，agent 又能用終端機
MCP server 你想在多個平台上共用同一個工具，需要結構化的輸入，要登入一個遠端服務，想按工具來批准，或者 agent 執行的地方沒有終端機

接之前問五個問題

既然 server 是依賴，對任何依賴該問的問題，對它也都該問，下面五個按我會問的順序排。

  • 誰寫的，誰在持續更新？VS Code 的建議是，在安裝或啟動之前先看「發布者、指令或端點，以及它請求的存取權限」（Add MCP servers in VS Code）。上架了也不等於審查過，MCP 官方的 Registry 只存中繼資料、驗證發布者的命名空間，安全掃描交給 npm 這樣的套件倉庫和下游的市集（The MCP Registry）。
  • 它能碰什麼？優先選只限於任務所需的 server，例如一個讀 issue 的 server，就不該拿著一個能刪倉庫的 token。
  • 憑證放在哪？別放在對話裡，也別提交進專案，VS Code 的文件還提醒，個人設定檔也不是存機密的地方（MCP configuration reference）。
  • 版本固定了嗎？啟動指令裡寫著 @latest 的話，套件一更新，之後啟動跑的就可能是新程式碼，所以要寫死一個看過的版本。
  • 它回傳的東西可信嗎？如果文字來自外部，例如公開的網頁、任何人都能開的工單，就當成不可信的。

hook 管不管得住 MCP 工具，各家不一樣

Claude Code 的文件寫明了，MCP 工具在 PreToolUse、PostToolUse 這些事件裡和一般工具一樣出現，名字是 mcp__<server>__<tool>（Hooks reference）。Copilot 這邊沒有寫，GitHub 的 hook 參考只說 preToolUse 在「每個工具執行之前」觸發，列出來的工具名稱都是內建工具，VS Code 的 hook 文件也沒有提到 MCP（GitHub Copilot hooks reference）。我自己的 harness 沒有搭任何 MCP server，這類 server 是公司依自己的環境設定的，有的公司還禁止非官方的，所以 MCP 工具在 Copilot 上是不是經過 hook、hook 能不能看到完整的參數，我沒有測過。

想靠 hook 的話，先用一個無害的 server 測一次，寫一個只記錄輸入的 hook，呼叫一次 MCP 工具，看記錄裡有沒有這次呼叫、參數全不全。就算經過了 hook，它看到的也只是這次呼叫的參數，server 收到以後做了什麼，它看不到。

接上以後怎麼查

已經連上的 server 也要回頭看，對每一個問三個問題：

  1. 我知道它是誰寫的、能碰什麼嗎？
  2. 命令列程式能做同樣的事嗎？
  3. 它的工具裡，我真正用到的有幾個？

第三個問題不用安裝任何東西就能回答。在 VS Code 裡打開 Chat: Open Customizations 的 Tools 頁，能看到每組工具啟用了幾個、一共幾個，在 Claude Code 裡用 /context 看是什麼在占上下文。數完再想想上週用過其中哪些，其餘的都是有成本、有風險，卻沒有收益的，可以把工具關掉，或者把整個 server 停用。

接上一个 server，到底接进来了什么

接上一个 server，等于给你的配置加了一个不是你写的依赖，它有自己的代码和更新节奏，用着你给的权限，还往模型的上下文里写东西。

server 能提供三样东西

协议定义了 server 可以提供的三样东西，区别在于由谁决定用。工具（Tools）是模型自己决定调用的函数，比如操作文件、调 API、查数据库，多数人说 MCP，指的就是它。资源（Resources）是只读的数据，比如文件内容或者数据库 schema，由应用决定放不放进上下文。提示（Prompts）是可复用的模板，由用户明确调用。（Understanding MCP servers）

host 连上 server 以后发一个 tools/list 请求，拿回每个工具的名字、描述和参数，再把所有 server 的工具合成一张表交给模型，模型要用某个工具时，host 向对应的 server 发一个 tools/call，再把结果放回对话。所以在模型看来，MCP 工具和内置工具没有区别，它还是只能靠名字、描述和报错来用工具，上一章的规则全都适用，只不过这些文字现在是别人写的。

本地 server 跑在你的机器上，远程 server 跑在别人那里

server 有两种运行方式，用的是同一套消息。本地 server 走 stdio 传输，host 在你的机器上启动一个进程，通过它的标准输入和输出通信，所以配置里写的其实就是一条启动命令，比如 VS Code 文档里 Playwright 的例子是 npx -y @playwright/mcp@latest。远程 server 走 Streamable HTTP 传输，运行在别人的机器上，host 通过 HTTP 和它通信，通常要登录，同一个 server 通常服务很多用户，比如 Sentry 官方的 server。

这个区别决定了你要防什么，本地 server 是用你的权限、在你电脑上运行的代码，要防的是它在你机器上做什么，远程 server 是别人的服务，要防的是你发给它的数据，和你交给它的账号权限。

接上一个 server，有四样东西跟着进来

  1. 别人的代码。本地 server 就是运行在你机器上的一个程序，一启动就在运行，不用等模型调用工具。VS Code 的文档说得很直接：“本地 MCP server 可以在你的机器上运行代码，工具可以用你的权限访问外部服务。”（Add MCP servers in VS Code）
  2. 你的权限。server 用你给它的访问权限做事，比如你的数据库账号、你在问题跟踪系统里的 token，agent 通过这个 server 也就拿到了这些权限，所以 token 的范围有多大，agent 出错或者被骗的时候，损失就可能有多大。
  3. 别人写的文本。工具的描述是别人写的，模型会读、会当真，工具返回的内容（一个 issue 的正文、一个网页）也是别人写的，这些文本里可能藏着给模型的命令（Agent 读到的网页和文件，可能在给它下命令）。
  4. 一笔固定的 token 开销。工具的名字、描述和参数都算模型的输入，如果 host 把它们全发给模型，每次请求都要带上，缓存能让钱少花一些，但是占的上下文窗口一点都不少，工具一多，模型也更容易选错。

第四样的开销可以很大。Anthropic 举过一个五个 server 的例子，GitHub 的 35 个工具约 26K token，Slack 的 11 个约 21K，再加上 Sentry、Grafana 和 Splunk，一共 58 个工具，对话还没开始就占了约 55K token（Introducing advanced tool use for Claude）。host 这边的办法是工具搜索，先不把工具定义发给模型，只给它一个搜索工具，用到的时候才加载完整定义。Claude Code 默认就这么做，会话开始时只加载工具名和 server 的说明（Connect Claude Code to tools via MCP）。VS Code 在 Claude Sonnet 4.5、Opus 4.5 以上的模型上也默认打开，只留读写文件、运行命令这样一小组核心工具常驻，它的团队做过线上实验，用 Claude 模型时，中位用户一整个会话的 token 用量降了约 18%（Improving token efficiency for GitHub Copilot in VS Code）。所以这笔开销到底有多大，要看你用的 host、模型和连了多少工具，最好数一数你自己的。

先看一条命令够不够

agent 需要的很多东西本来就是命令行程序，比如 git、gh、测试运行器、云平台的命令行工具，只要 agent 能用终端，不接任何 server 就能用上它们。我倾向于先用命令，因为它给你的配置加进来的代码和权限都更少，等多个平台共用一个工具的好处抵得过多出来的那个依赖，再换成 MCP 也不迟。

工具的厂商自己也这么建议。VS Code 的文档开头就说，现有工具够用的话就不需要再加 server。Claude Code 的文档建议优先用 gh、aws、gcloud 这些命令行工具，因为它们不会往上下文里加工具清单（Manage costs effectively）。微软的 Playwright MCP 的 README 也告诉用 coding agent 的读者，CLI 加 skill 可能更合适，MCP 留给需要保持浏览器状态的长循环（Playwright MCP）。

不过省多少 token 要看具体的活。Checkly 的 Stefan Judis 在 2026 年 7 月用 Claude Code 把同一个浏览器任务各跑了三遍，用 Playwright MCP 结束时的上下文约 48K 到 50K，用 playwright-cli 约 45K 到 48K，差别很小，他的解释是工具定义现在是延迟加载的（CLIs are more token-efficient than MCP. Or are they?）。所以在有工具搜索的 host 上，命令的好处主要是依赖和权限更少，不在 token 上。

MCP 也有命令比不了的地方。它的每个工具都有名字和参数 schema，host 可以按工具来批准，而 agent 一旦能用终端，就能跑任何命令，hook 读到的也只是命令的文本（硬性规则放在哪？用 hook）。所以给一个写操作很多的内部系统做接口时，几个窄的 MCP 工具可能比一个什么都能做的命令行更好管。

选 什么时候
命令行程序 它已经有了，在本地运行，输出又短又清楚，agent 又能用终端
MCP server 你想在多个平台上共用同一个工具，需要结构化的输入，要登录一个远程服务，想按工具来批准，或者 agent 运行的地方没有终端

接之前问五个问题

既然 server 是依赖，对任何依赖该问的问题，对它也都该问，下面五个按我会问的顺序排。

  • 谁写的，谁在持续更新？VS Code 的建议是，在安装或启动之前先看“发布者、命令或端点，以及它请求的访问权限”（Add MCP servers in VS Code）。上架了也不等于审查过，MCP 官方的 Registry 只存元数据、验证发布者的命名空间，安全扫描交给 npm 这样的包仓库和下游的市场（The MCP Registry）。
  • 它能碰什么？优先选只限于任务所需的 server，比如一个读 issue 的 server，就不该拿着一个能删仓库的 token。
  • 凭据放在哪？别放在对话里，也别提交进项目，VS Code 的文档还提醒，个人配置文件也不是存密钥的地方（MCP configuration reference）。
  • 版本固定了吗？启动命令里写着 @latest 的话，包一更新，之后启动跑的就可能是新代码，所以要写死一个看过的版本。
  • 它返回的东西可信吗？如果文本来自外部，比如公开的网页、任何人都能提的工单，就当成不可信的。

Claude Code 的文档写明了，MCP 工具在 PreToolUse、PostToolUse 这些事件里和普通工具一样出现，名字是 mcp__<server>__<tool>（Hooks reference）。Copilot 这边没有写，GitHub 的 hook 参考只说 preToolUse 在“每个工具运行之前”触发，列出来的工具名都是内置工具，VS Code 的 hook 文档也没有提 MCP（GitHub Copilot hooks reference）。我自己的 harness 没有搭任何 MCP server，这类 server 是公司按自己的环境配的，有的公司还禁止非官方的，所以 MCP 工具在 Copilot 上是不是经过 hook、hook 能不能看到完整的参数，我没有测过。

想靠 hook 的话，先用一个无害的 server 测一次，写一个只记录输入的 hook，调用一次 MCP 工具，看记录里有没有这次调用、参数全不全。就算经过了 hook，它看到的也只是这次调用的参数，server 收到以后做了什么，它看不到。

接上以后怎么查

  1. 我知道它是谁写的、能碰什么吗？
  2. 命令行程序能做同样的事吗？
  3. 它的工具里，我真正用到的有几个？

第三个问题不用安装任何东西就能回答。在 VS Code 里打开 Chat: Open Customizations 的 Tools 页，能看到每组工具启用了几个、一共几个，在 Claude Code 里用 /context 看是什么在占上下文。数完再想想上周用过其中哪些，其余的都是有成本、有风险，却没有收益的，可以把工具关掉，或者把整个 server 停用。

Official servers can go wrong too, and a server you reviewed can change

Every server is a route for outside text and outside code to reach the agent, so the more you connect, the more places there are for something to go wrong, and that doesn't only count the ones you're using. A server you added to try out and then forgot about is still there.

A big name is no reason to skip the review. In May 2025, Invariant Labs published a case where an attacker files an issue on a public repository with instructions for the agent hidden inside. The user only asks the agent to look at that repository's issues, but the agent is connected to the official GitHub MCP server and has access to the user's private repositories, and it ends up writing private repository contents into a pull request on a public repository. Invariant says this isn't a flaw in the server's code and that GitHub can't fix it by changing the server alone, and they recommend narrowing permissions, for example letting the agent touch only one repository per session (GitHub MCP Exploited). Untrusted text, private data and a way out were all present here (Text the agent reads can give it orders). "Official" only tells you who wrote the code. The server still holds your credentials and still reads text other people wrote.

Even a server you reviewed carefully can change without your knowing, in three places.

  • The tool list. The protocol lets a server update its tools and then tell the client to fetch the list again, so a server can change a tool's description after you've approved it, a move known as a rug pull. Invariant Labs showed what a description can hide, in an attack they call tool poisoning: an add tool that looks like it only does addition has a passage hidden in its description telling the model to read ~/.ssh/id_rsa and send the contents back in a parameter (Tool Poisoning Attacks).
  • The code. postmark-mcp on npm borrowed Postmark's name, its first 15 versions were clean, and 1.0.16 added a backdoor that quietly BCC'd emails to an outside server (Security Alert: Malicious 'postmark-mcp' npm Package).
  • The configuration. In VS Code, the workspace .mcp.json and .vscode/mcp.json follow Workspace Trust, so in a trusted workspace you won't be asked again when they change, and what they hold is a command that will run. So review a pull request that changes these files the way you'd review a code change (Manage and troubleshoot MCP servers).

So reread the tool list every so often, and pin versions wherever you can.

Another trap is assuming that the same standard means the same behavior. The protocol only standardizes the messages between host and server. Where the configuration lives, which parts of the protocol are supported and how approval works are all up to each vendor. VS Code alone has two configuration formats, one with the top-level key mcpServers and one with servers, and you can't copy directly between them. For where each platform keeps its configuration, see the Extension points cheat sheet. The protocol itself is still changing as well: the current version is 2026-07-28, which removed the connection handshake and sessions and marked sampling, roots and logging as deprecated, only eight months after the previous version (Key Changes). If you only use other people's servers you probably won't notice these changes, but if you write your own, leave time to keep up with the versions.

官方的 server 也會出事，審查過的 server 也會變

每個 server 都是外部文字和外部程式碼通往 agent 的一條路，接得越多，能出問題的地方就越多，而且不只在用的才算，當初為了試試加上、後來忘掉的 server 也一直在那裡。

名氣大也不是跳過審查的理由。Invariant Labs 在 2025 年 5 月公開過一個例子，攻擊者在一個公開倉庫裡開一個 issue，裡面藏著給 agent 的指示，使用者只是讓 agent 看看這個倉庫的 issue，而 agent 連著官方的 GitHub MCP server，又有權限讀使用者的私有倉庫，結果它把私有倉庫的內容寫進了公開倉庫的一個 pull request。Invariant 說這不是 server 程式碼的缺陷，GitHub 光改 server 修不好，他們的建議是收窄權限，例如一個會話只讓 agent 碰一個倉庫（GitHub MCP Exploited）。不可信的文字、私有資料和對外的出路，這三樣在這裡全湊齊了（agent 讀到的文字可能在指揮它）。「官方」只告訴你程式碼是誰寫的，它拿著你的憑證，照樣會讀到別人寫的文字。

就算是你仔細審查過的 server，也可能在你不知情的時候變了，變的地方有三處。

  • 工具清單變了。協定允許 server 更新工具，再通知 client 重新抓取清單，所以 server 可以在你批准之後改掉某個工具的描述，這種做法叫 rug pull。描述裡能藏什麼，Invariant Labs 示範過，叫工具投毒（tool poisoning），一個看起來只做加法的 add 工具，描述裡藏著一段話，要模型讀 ~/.ssh/id_rsa，再把內容放進一個參數傳回去（Tool Poisoning Attacks）。
  • 程式碼變了。npm 上的 postmark-mcp 冒用 Postmark 的名字，前 15 個版本都正常，到 1.0.16 才加上後門，把郵件偷偷用密件副本寄到外部伺服器（Security Alert: Malicious 'postmark-mcp' npm Package）。
  • 設定變了。VS Code 裡工作區的 .mcp.json 和 .vscode/mcp.json 跟著 Workspace Trust 走，在受信任的工作區裡，設定改了也不會再單獨問你，而設定裡寫的是一條會執行的指令，所以改這些檔案的 pull request 要當成改程式碼來審（Manage and troubleshoot MCP servers）。

所以要隔一段時間重讀一遍工具清單，能固定版本就固定。

另一個陷阱是以為標準一樣，行為也就一樣。協定只統一了 host 和 server 之間的訊息，設定放在哪、支援協定的哪些部分、怎麼批准，都是各家自己定的，光 VS Code 就有兩種設定格式，頂層鍵一個是 mcpServers，一個是 servers，不能直接互相複製，各家的設定放在哪，可以查擴充點速查表。協定本身也還在變，目前的版本是 2026-07-28，這一版拿掉了連線時的交握和會話，還把 sampling、roots 和 logging 標成棄用，距離上一版只有八個月（Key Changes）。只是用別人的 server，這些變化你多半感覺不到，自己寫 server 的話，就要留出跟版本的時間。

官方的 server 也会出事，审查过的 server 也会变

每个 server 都是外部文本和外部代码通向 agent 的一条路，接得越多，能出问题的地方越多，而且不光是在用的才算，当初为了试试加上、后来忘掉的 server 也一直在那里。

名气大也不是跳过审查的理由。Invariant Labs 在 2025 年 5 月公开过一个例子，攻击者在一个公开仓库里提一个 issue，里面藏着给 agent 的指令，用户只是让 agent 看看这个仓库的 issue，而 agent 连着官方的 GitHub MCP server，又有权限读用户的私有仓库，结果它把私有仓库的内容写进了公开仓库的一个 pull request。Invariant 说这不是 server 代码的缺陷，GitHub 光改 server 修不好，他们的建议是收窄权限，比如一个会话只让 agent 碰一个仓库（GitHub MCP Exploited）。不可信的文本、私有数据和对外的出路，这三样在这里全凑齐了（Agent 读到的网页和文件，可能在给它下命令）。“官方”只告诉你代码是谁写的，它拿着你的凭据，照样会读到别人写的文本。

就算是你仔细审查过的 server，也可能在你不知情的时候变了，变的地方有三处。

  • 工具清单变了。协议允许 server 更新工具，再通知 client 重新拉取清单，所以 server 可以在你批准之后改掉某个工具的描述，这种做法叫 rug pull。描述里能藏什么，Invariant Labs 演示过，叫工具投毒（tool poisoning），一个看起来只做加法的 add 工具，描述里藏着一段话，让模型读 ~/.ssh/id_rsa，再把内容放进一个参数发回去（Tool Poisoning Attacks）。
  • 代码变了。npm 上的 postmark-mcp 冒用 Postmark 的名字，前 15 个版本都正常，到 1.0.16 才加上后门，把邮件偷偷密送到外部服务器（Security Alert: Malicious 'postmark-mcp' npm Package）。
  • 配置变了。VS Code 里工作区的 .mcp.json 和 .vscode/mcp.json 跟着 Workspace Trust 走，在受信任的工作区里，配置改了也不会再单独问你，而配置里写的是一条会运行的命令，所以改这些文件的 pull request 要当成改代码来审（Manage and troubleshoot MCP servers）。

所以要隔一段时间重读一遍工具清单，能固定版本就固定。

另一个坑是以为标准一样，行为也就一样。协议只统一了 host 和 server 之间的消息，配置放在哪、支持协议的哪些部分、怎么批准，都是各家自己定的，光 VS Code 就有两种配置格式，顶层键一个是 mcpServers，一个是 servers，不能直接互相复制，各家的配置放在哪，可以查扩展点速查表。协议本身也还在变，当前版本是 2026-07-28，这一版去掉了连接时的握手和会话，还把 sampling、roots 和 logging 标成了废弃，距离上一版只有八个月（Key Changes）。只是用别人的 server，这些变化你多半感觉不到，自己写 server 的话，就要留出跟版本的工夫。

The protocol and VS Code both leave the decision to you Industry practice

The protocol's docs say MCP covers only the exchange of context and "does not dictate how AI applications use LLMs or manage the provided context" (Architecture overview). The specification requires hosts to get explicit user consent before invoking any tool, and it also admits that MCP itself can't enforce these principles at the protocol level (Specification). VS Code is one such host. It has you look at the publisher and the requested access and approve only the operations you understand, and for organizations it offers the ChatMCP policy, which can restrict servers to a registry, although the policy doesn't reach servers the Copilot runtime discovers on its own (Secure AI-assisted development in VS Code). So the two agree on who does what: the protocol makes connecting easy, and deciding what to connect is still your job.

協定和 VS Code 都把決定權留給了你 業界做法

協定的文件說，MCP 只管交換上下文，「不規定 AI 應用程式如何使用 LLM，也不規定如何管理所提供的上下文」（Architecture overview）。規格要求 host 呼叫任何工具之前都要得到使用者明確的同意，同時也承認 MCP 自己沒辦法在協定層面強制這些原則（Specification）。VS Code 就是這樣一個 host，它讓你看發布者和請求的存取權限，只批准你理解的操作，給組織的是 ChatMCP 政策，可以把 server 限制在一份 registry 裡，不過這個政策管不到 Copilot 執行環境自己發現的 server（Secure AI-assisted development in VS Code）。所以兩邊的分工是一致的，協定讓接入變容易，決定接入什麼仍然是你的事。

协议和 VS Code 都把决定权留给了你 业界做法

协议的文档说，MCP 只管交换上下文，“不规定 AI 应用如何使用 LLM，也不规定如何管理所提供的上下文”（Architecture overview）。规范要求 host 调用任何工具之前都要得到用户明确的同意，同时也承认 MCP 自己没法在协议层面强制这些原则（Specification）。VS Code 就是这样一个 host，它让你看发布者和请求的访问权限，只批准你理解的操作，给组织的是 ChatMCP 策略，可以把 server 限制在一份 registry 里，不过这个策略管不到 Copilot 运行时自己发现的 server（Secure AI-assisted development in VS Code）。所以两边的分工是一致的，协议让接入变容易，决定接入什么仍然是你的事。

When to delete a server Industry practice

When you no longer use a server's tools, or an ordinary command can do the job, remove it.

When you can relax this caution depends on the platform. If a platform put local servers in a sandbox by default, a bad server could do far less, but as I write this we're not there yet: VS Code's Copilot session sandbox is off by default, and even when it's on, it doesn't block outbound network access by default (Sandbox Copilot agent sessions). A sandbox also contains only the server's process. It can't limit the remote account you gave the server or the text the server returns to the model, so even with a sandbox I'd still check the publisher and the access before adding one.

什麼時候可以刪掉一個 server 業界做法

不再用某個 server 的工具了，或者一條普通指令就能完成任務了，就把它移除。

這份謹慎什麼時候能放鬆，要看平台。如果平台預設把本機 server 關進沙箱，壞的 server 能做的事就少很多，但是寫這一章的時候還沒到這一步，VS Code 的 Copilot 會話沙箱預設是關的，打開以後也預設不擋對外網路連線（Sandbox Copilot agent sessions）。沙箱也只管得住 server 這個處理程序，管不了你交給它的遠端帳號，也管不了它回傳給模型的文字，所以就算有了沙箱，我還是會在新增之前檢查發布者和存取權限。

什么时候可以删掉一个 server 业界做法

不再用某个 server 的工具了，或者一条普通命令就能完成任务了，就把它移除。

这份谨慎什么时候能放松，要看平台。如果平台默认把本地 server 关进沙箱，坏的 server 能做的事就少很多，但是写这一章的时候还没到这一步，VS Code 的 Copilot 会话沙箱默认是关的，打开以后也默认不拦出站网络（Sandbox Copilot agent sessions）。沙箱也只管得住 server 这个进程，管不了你交给它的远程账号，也管不了它返回给模型的文本，所以即便有了沙箱，我还是会在添加之前检查发布者和访问权限。
