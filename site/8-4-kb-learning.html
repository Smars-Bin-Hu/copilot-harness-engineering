Learning a domain in batches分批學一個領域让 Agent 学一个大系统：从底层往上，分批读

This chapter follows The audit, which left the map trusted enough to learn from. It covers steps four to six of the road set out in 8.1, and it leans on Context budget for the reason one big context is a bad place to learn a lot. Two words come back from earlier chapters. A task is one piece of work with a plan, a to-do list and its own files (5.1), and a write-back is the single copy of finished work into the base, which a person approves (5.3).

The Knowledge經驗分享经验分享

In one sentence

Learn from the bottom of the dependency tree upward, in batches small enough to read in one go. Because what an object uses is learned before it, the cards above can point down at the cards below instead of reading their code again.

一句話

從依賴樹的底部往上學，每批小到一次讀得完。一個物件用到的東西都先於它學過了，所以上面的卡片可以直接指向下面的卡片，不用再讀它們的程式碼。

一句话

从依赖树的底部往上学，每批小到一次读得完。一个对象用到的东西都先于它学过了，所以上面的卡片可以直接指向下面的卡片，不用再读一遍它们的代码。

For leaders

  • The decision: for each domain, approve the entry points, the plan and the final write-back into the base. Where a domain starts and ends is a person's choice.
  • The risk: the checks cover structure, not meaning. A note can pass every check and still misstate what a rule is for, and a wrong note low in the order spreads to the notes above it. Cited lines are only checked to fall inside the object, so a made-up citation can pass.
  • The cost of doing it right: the model reads each object's code once, and that is the real token cost of the whole base. Review time can be the slowest part. The batch size (up to 20 objects, about 1500 lines) is a number I picked, not one I measured.
  • Ask the team: "Who reviews whether each note's rule means what the cited code says, not only that the lines exist?"

給主管

  • 要做的決定：對每個領域，批准入口、計劃，和最後寫回知識庫這三處。一個領域從哪裡開始、到哪裡結束，由人來選。
  • 風險：檢查涵蓋的是結構，不是意思。一張卡片可以通過每個檢查，還是講錯了一條規則是做什麼的；排在底層的一張錯誤卡片，還會傳到它上面的卡片。引用的行只檢查是否落在物件裡面，所以編造的引用也能通過。
  • 做對的成本：模型把每個物件的程式碼讀一遍，這就是整個知識庫真正的 token 成本。審查的時間可能是最慢的部分。批次大小（最多 20 個物件、約 1500 行）是我挑的數字，不是量出來的。
  • 可以問團隊：「誰來審查每張卡片的規則，意思是不是和引用的程式碼說的一樣，而不只是那些行存在？」

写给管理者

  • 要拍板的事：对每个领域，审批入口、计划和最后写回知识库这三处。一个领域从哪里开始、到哪里结束，由人来选。
  • 风险：检查管的是结构，不是含义。一张卡片可以通过每项检查，却仍然讲错了某条规则是干什么的；顺序靠下的一张错误卡片，还会传到它上面的卡片。引用的行只检查是否落在对象之内，所以编造的引用也能通过。
  • 做对的代价：模型把每个对象的代码读一遍，这就是整个知识库真正的 token 成本。审查的时间可能是最慢的一环。批次大小（最多 20 个对象、约 1500 行）是我挑的数字，不是测出来的。
  • 可以问团队：“谁来审查每张卡片里的规则，意思是不是和引用的代码一致，而不只是那些行存在？”

Why does the order of learning matter?

Once the audit has passed, you have a trusted map and a few thousand objects, and you want a card for each. The two simplest plans both fail, but the way they fail shows what a good plan needs.

The first plan is one big prompt: "Learn the whole domain." Everything the agent reads then sits in one context. As that context fills, the agent can forget and mix things up toward the end (context budget). So I would expect the cards written last to be the worst, though that is reasoning, not a comparison I have run.

The second plan is to go object by object, in any order. Say the agent starts with a procedure that calls three others. To explain it properly it has to read those three, so it reads them too. A few objects later it meets one of the three on its own and reads it again. The same code ends up being read many times, and each card was written without the cards below it.

A good order would learn those three first. The procedure's card can then say "it calls A, B and C" and point to their cards, so the agent never reads their code again. Finding such an order for a whole domain starts with knowing where the domain begins.

學習的順序為什麼重要？

既然抽查已經通過，你手上就有一張可信的地圖、幾千個物件，想為每個物件寫一張卡片。最簡單的兩個計劃都行不通，不過看看它們怎麼失敗，就知道好的計劃需要什麼。

第一個計劃是一個大 prompt：「學完整個領域。」這樣一來，agent 讀過的所有東西都裝在一個上下文裡。上下文越裝越滿，agent 到後面可能會忘掉前面的，也會搞混（上下文預算），所以我預期最後寫的卡片是最差的，不過這只是推理，不是我做過的比較。

第二個計劃是一個物件一個物件來，順序隨意。假設 agent 從一個呼叫了其他三個的預存程序開始。要好好解釋它，就得讀那三個，於是它把那三個也讀了。過了幾個物件，它又單獨遇到那三個之一，只好再讀一遍。同樣的程式碼就這樣讀了很多次，而且每張卡片寫的時候，它下面的卡片都還沒有。

所以，好的順序應該先學那三個。這樣預存程序的卡片就可以說「它呼叫 A、B 和 C」，並指向它們的卡片，agent 也不用再讀它們的程式碼。要替整個領域排出這樣的順序，得先知道這個領域從哪裡開始。

学习的顺序为什么要紧？

既然审计已经通过，你手里就有一张可信的地图、几千个对象，想给每个对象写一张卡片。最简单的两个计划都行不通，不过看看它们怎么失败，就知道好的计划需要什么。

第一个计划是一个大 prompt：“把整个领域学完。”这样一来，agent 读过的所有东西都装在一个上下文里。上下文越装越满，agent 到后面可能会忘掉前面的，还会搞混（上下文预算），所以我预计最后写的那些卡片质量最差，不过这只是推理，不是我做过的对比。

第二个计划是一个对象一个对象地学，顺序随意。假设 agent 从一个调用了另外三个的存储过程开始。要把它讲清楚，就得读那三个，于是它把那三个也读了。过了几个对象，它又单独碰上那三个里的一个，只好再读一遍。同样的代码就这样读了很多次，而且每张卡片写的时候，它下面的卡片都还没有。

所以，好的顺序应该先学那三个。这样存储过程的卡片就可以写“它调用 A、B 和 C”，并指向它们的卡片，agent 也不用再读它们的代码。要给整个领域排出这样的顺序，得先知道这个领域从哪里开始。

Learning from the bottom up, one batch at a time

Start from the entry points

A domain (see A knowledge base: an honest index of the code) is a group of objects that serve one job. To learn one, you need to say where it begins. An entry point is an object that the outside world calls, such as a screen's controller, a public API or a scheduled job. Starting from the entry points, the map shows everything they reach.

A person chooses the entry points and the boundaries. A script and a research note can propose them, and the agent asks, but it is the person who knows which is which. Two boundaries matter:

  • Stop at code you do not own. Framework code and another team's code are cut off, so the domain does not grow into them.
  • Cut off what is shared. An object used from many entry points belongs to no single domain, so it is set aside to keep one domain from swallowing everything. (How many entry points make an object shared is a setting you can lower if one domain still swallows the rest.)

This chapter leaves open who learns the shared objects, and when. That deserves a plan of its own, because they are the ones many things depend on.

A script sets the order

With the entry points chosen, a script walks the map from them, bottom up. An object that uses nothing comes first, while any other object comes only after everything it uses. The script then cuts this order into batches.

Here is a real order, from the open-source spring-petclinic sample. The four tables come first (owners, pets, types, visits), then the entities that map them, then the repositories that read the entities, and last the controllers that sit on top. Each controller card then points at the cards below it, just as the procedure's card could point at A, B and C.

How big is a batch?

A batch holds objects of one type, because objects of one type share a card form and the same questions. It also stays small, at most 20 objects and about 1500 lines of code in all. I picked these numbers so that one batch fits in a context with room to think. The exception is an object longer than that, which becomes a batch of its own and is read in parts.

One domain, one task, one write-back

All the batches of a domain make up one task (see Manage tasks, not chats), and the task holds three things:

  • A plan, listing every batch, approved by a person once.
  • A to-do list with one step per batch.
  • The cards, kept inside the task until the whole domain is done.

Only then is the domain written into the knowledge base, in one write-back (see Two gates: where a person approves) that the person approves. So the base never holds half a domain.

Chats, meanwhile, come and go. After every two or three batches I start a new chat and say "continue", because the task, not the chat, keeps the state: the plan, what is learned, what is left. The next batch is the first one the script gives once the learned objects are left out. This is the same idea as work that survives across sessions, with memory kept in files rather than in a chat.

What the scripts check in a card

The model writes each card, and the words are its own, but two parts of every card are checked by script:

  • The relations line must equal the map. The "uses" a card lists have to be the same as the map's uses for that object, so the card cannot add or drop one.
  • Every rule cites its lines, and the check makes sure those lines fall inside that object's code. A rule that cites lines outside the object is wrong.

Here is the form of one card, from the harness's guide for writing them. In the example, a stored procedure, the relations line is the one the script checks.

A card: what it is for, relations (checked against the map), the level, the rules with their lines, what is not known, traps.
```markdown
## sp:Db.dbo.usp_load_orders

- What: loads the day's orders from staging into dbo.orders, then logs the run
- Reads: `table:Db.dbo.stg_orders`, `table:Db.dbo.calendar` · Writes: `table:Db.dbo.orders` · Called by: `job:Daily_Load` · Calls: `sp:Db.dbo.usp_log`
- Level: verified (read in repo_a at 3f1c0a9e)

In: @run_date (date, default today). Out: none; rows in dbo.orders.
```

Both checks cover structure only, and the second is a weak one. It shows that the lines exist, not that they support the rule, so a made-up citation inside the right range passes. Whether the model understood a rule correctly is something a script cannot tell at all, so that is left to a person's review or an independent reviewer (5.6). The same reviewer should spot-check whether the cited lines say what the rule says. I do not claim the checks cover meaning.

Beyond the weak check, the bottom-up order brings a risk of its own. A card that points at a lower card does not read the code again, so it inherits that card's mistakes. A wrong card low in the order can therefore spread upward (8.5).

When the code shows a use the map lacks

The check refuses a relations line that differs from the map. But what if, while reading, the agent sees a use in the code that the map does not have? It must not add the use to the card by hand. The check would refuse it, and a hand fix would mend only this card: the next object written in the same form would be missed too. Instead it notes the use. The note goes back to the toolkit as a new example to fix, after which the map is rebuilt and checked again (8.3).

Writing the architecture page last

When all batches are done, the model writes the domain's architecture page: its purpose, main flows, where to start reading, traps and limits. The flows are paths taken from the map. The model puts them into words, and the script checks them against the map the same way it checks a card's relations. That page is written last, but it is the part most readers see first.

Test your own setup

  1. Pick one small domain and one entry point.
  2. Ask a script, or an agent, to list what the entry point reaches, deepest first.
  3. Learn in that order, in one task, in two or three batches.
  4. Check that each card's "uses" equal the map's, and that every cited line is inside the object.

由下往上，一批一批地學

從入口開始

領域（見 知識庫：程式碼的誠實索引）是為同一件工作服務的一組物件。要學一個領域，你得先說清楚它從哪裡開始。入口是外部會呼叫的物件，例如畫面的 controller、公開的 API、排程工作。從入口出發，地圖會顯示它們碰得到的一切。

由人選擇入口和邊界。腳本和一份研究筆記可以提議，agent 也會問，但哪個是哪個，只有人才知道。有兩個邊界很重要：

  • 停在不歸你管的程式碼上。框架的程式碼和別的團隊的程式碼要切開，這樣領域才不會長進它們裡面。
  • 切開共用的物件。很多入口都會用到的物件，不屬於任何單一領域，所以要把它放在一邊，免得一個領域吞掉所有東西。（要有多少個入口，物件才算共用，是一個設定；如果一個領域還是吞掉了其餘的，可以把它調低。）

不過，這一章沒有決定共用的物件由誰學、什麼時候學。這件事值得單獨計劃，因為很多東西都依賴它們。

腳本定順序

入口選好之後，腳本從入口出發，由下往上走一遍地圖。什麼都不用的物件排第一，其餘的物件，都要等它用到的一切排完才輪到。然後腳本把這個順序切成批次。

這是開源範例 spring-petclinic 的真實順序。先是四張資料表（owners、pets、types、visits），然後是對應它們的 entity，再來是讀 entity 的 repository，最上面是 controller。每張 controller 的卡片都指向它下面的卡片，就像前面那個預存程序的卡片可以指向 A、B 和 C。

一批有多大？

一批只放同一種類型的物件，因為同一種類型的物件，卡片的形式一樣，要問的問題也一樣。一批還要小，總共最多 20 個物件、約 1500 行程式碼。我挑這些數字，是為了讓一批放得進一個上下文，還留有思考的空間。例外是比這更長的物件，它自己是一批，分段讀。

一個領域，一個任務，一次寫回

一個領域的所有批次合起來是一個任務（見 管任務，不管對話），這個任務裡有三樣東西：

  • 一份計劃，列出每一批，由人批准一次。
  • 一份待辦清單，每批一步。
  • 卡片，在整個領域完成之前，留在任務裡面。

等整個領域完成，才用一次寫回寫進知識庫（見 兩道門：人在哪裡批准），由人批准。所以知識庫從不會只有半個領域。

任務一直在，對話卻來來去去。每兩、三批之後我就開一個新對話，說一聲「繼續」就好，因為計劃、學了什麼、還剩什麼，都記在任務裡，不在對話裡。下一批，就是把學過的物件排除之後，腳本給的第一批。這和 跨會話的長任務 是同一個想法：記憶放在檔案裡，不放在對話裡。

腳本在卡片上檢查什麼

每張卡片都由模型寫，裡面的話是它自己的，但有兩個部分要由腳本檢查：

  • 關係行必須和地圖一致。一張卡片列的「用到」，必須和地圖上那個物件的使用一樣，卡片不能多加，也不能少掉一個。
  • 每條規則都要附上行號，檢查會確保那些行落在那個物件的程式碼裡面。引用了物件之外的行，這條規則就是錯的。

這是一張卡片的樣子，來自 harness 寫卡片的指南。例子是一個預存程序，關係行就是腳本檢查的那一行。

一張卡片：它做什麼、關係（對照地圖檢查）、層級、附行號的規則、不知道的部分、陷阱。

這兩項都只管結構，而且第二項是個弱的檢查。它只能說明那些行存在，說明不了它們支持這條規則，所以落在正確範圍內的編造引用也能通過。至於模型有沒有正確理解一條規則，腳本根本分辨不出來，要靠人的審查，或獨立的 reviewer（5.6）。引用的行說的是不是和規則一樣，也由他們來抽查。我不宣稱這些檢查涵蓋了意思。

弱檢查之外，由下往上本身也帶來一個風險。指向下層卡片的卡片不再讀程式碼，所以會繼承那張卡片的錯誤。這樣一來，排在底層的一張錯誤卡片，就可能往上傳（8.5）。

程式碼顯示了地圖沒有的使用

檢查會拒絕和地圖不一致的關係行。可是如果 agent 讀程式碼時發現一處使用，地圖卻漏了，該怎麼辦？它不能手動把這處使用加進卡片。檢查會拒絕，而且手動改只補得了這一張，之後用同樣形式寫的物件還是會漏掉。它該做的是把這處使用記下來，交回 toolkit 當成待修的新例子，再重建地圖、檢查一次（8.3）。

最後寫架構頁

所有批次完成後，模型寫這個領域的架構頁：它的用途、主要的流程、從哪裡開始讀、陷阱和限制。流程是從地圖取來的路徑。模型把它們寫成文字，腳本再像檢查卡片的關係行那樣，拿地圖來檢查它們。這一頁最後才寫，卻是多數讀者最先看到的部分。

測你自己的設定

  1. 挑一個小的領域和一個入口。
  2. 請腳本或 agent 列出這個入口碰得到的東西，最深的排最前。
  3. 照那個順序學，在一個任務裡，分兩、三批。
  4. 檢查每張卡片的「用到」等於地圖上的，而且每一行引用都在物件裡面。

自底向上，一批一批地学

从入口开始

领域（见为什么要给代码建一个知识库？）是为同一项工作服务的一组对象。要学一个领域，得先说清它从哪里开始。入口是外部会调用的对象，比如某个页面的 controller、公开的 API、定时任务。从入口出发，地图会显示它们能碰到的一切。

入口和边界由人来选。脚本和调研笔记可以提议，agent 也会来问，但哪个是哪个，只有人知道。有两条边界要紧：

  • 停在不归你管的代码上。框架代码和别的团队的代码要切开，这样领域才不会长进它们里面去。
  • 切开共用的对象。被很多入口用到的对象不属于任何一个领域，所以要把它放在一边，免得一个领域吞掉所有东西。（多少个入口用到才算共用，是一个可调的设置；如果一个领域还是吞掉了其余的，可以把它调低。）

不过，这一章没有定下共用对象由谁来学、什么时候学。这件事值得单独计划，因为很多东西都依赖它们。

脚本定顺序

入口选好之后，脚本从入口出发，自底向上走一遍地图。什么都不用的对象排第一，其余的对象，都要等它用到的所有东西排完才轮到。然后脚本把这个顺序切成批次。

这是一个真实的顺序，来自开源示例 spring-petclinic。先是四张表（owners、pets、types、visits），然后是映射这些表的实体，再然后是读取实体的仓库，最上面是 controller。每张 controller 卡片都指向它下面的卡片，就像前面那个存储过程的卡片可以指向 A、B 和 C。

一批有多大？

一批只放同一种类型的对象，因为同一类型的对象卡片格式一样，要问的问题也一样。一批还要小，最多 20 个对象、合计约 1500 行代码。我挑这些数字，是为了让一批能装进一个上下文，还留有思考的空间。例外是比这更长的对象，它自成一批，分段来读。

一个领域，一个任务，一次写回

一个领域的所有批次合起来是一个任务（见一个任务一个文件夹），这个任务里有三样东西：

  • 一份计划，列出所有批次，由人审批一次。
  • 一份待办清单，每批一步。
  • 卡片，整个领域学完之前都放在任务里。

等整个领域学完，才通过一次写回写进知识库（见哪些事必须由人来批？），由人审批。所以知识库里不会出现只有半个领域的情况。

任务一直在，对话却来来去去。每学两三批我就开一个新对话，说一声“继续”就行，因为计划、已经学了什么、还剩什么，都记在任务里，不在对话里。下一批，就是把已学的对象去掉之后，脚本给出的第一批。这和一个会话做不完的任务，怎么接着做？是同一个思路：记忆放在文件里，不放在对话里。

脚本在卡片上查什么

每张卡片都由模型来写，措辞是它自己的，但有两部分要由脚本检查：

  • 关系行必须和地图一致。卡片列出的“用到”，要和地图上这个对象的“用到”相同，卡片不能多加，也不能漏掉。
  • 每条规则都要引用行号，检查会确认这些行落在这个对象的代码之内。引用的行在对象之外，这条规则就是错的。

这是一张卡片的样子，取自 harness 里写卡片的指南。例子是一个存储过程，关系行就是脚本要检查的那一行。

一张卡片：它是干什么的、关系（对照地图检查）、层级、带行号的规则、不知道的部分、坑。
```markdown
## sp:Db.dbo.usp_load_orders

- What: loads the day's orders from staging into dbo.orders, then logs the run
- Reads: `table:Db.dbo.stg_orders`, `table:Db.dbo.calendar` · Writes: `table:Db.dbo.orders` · Called by: `job:Daily_Load` · Calls: `sp:Db.dbo.usp_log`
- Level: verified (read in repo_a at 3f1c0a9e)

In: @run_date (date, default today). Out: none; rows in dbo.orders.
Changes: MERGE into dbo.orders on id (L18-L26): new rows inserted, known rows updated; then sets flag = 1 (L28).
Twice: safe; the MERGE matches on id.
On an error: no TRY/CATCH; the error goes to the job step, nothing is logged.

Logic: only rows whose date is a working day in dbo.calendar (L12-L16). See the card of `sp:Db.dbo.usp_log` for the log.

Not known: which environments run it on holidays (req-0004).

Traps: a staging row with a NULL id is dropped by the MERGE, with no error (L19).
```

这两项都只管结构，而且第二项是个弱检查。它只能说明这些行存在，说明不了这些行支持这条规则，所以落在正确范围内的编造引用也能通过。至于模型有没有把一条规则理解对，脚本根本分不出来，要靠人审查，或者靠独立的 reviewer（5.6）。引用的行是不是真的说了规则说的话，也由他们来抽查。我不会说这些检查覆盖了含义。

弱检查之外，自底向上本身也带来一个风险。指向下层卡片的卡片不再读代码，所以会继承那张卡片的错误。这样一来，顺序靠下的一张错卡片，可能一路传到上面（8.5）。

代码里有地图没有的调用关系

检查会拒绝和地图不一致的关系行。可如果 agent 读代码时发现一处调用关系，地图却漏了，该怎么办？它不能手动把这条关系加进卡片。检查会拒绝，而且手动改只补得了这一张，之后按同样格式写的对象还是会漏掉。它要做的是把这一处记下来，这条记录作为一个待修的新例子回到 toolkit，然后重新生成地图，再检查一遍（8.3）。

最后写架构页

所有批次做完后，模型写这个领域的架构页：目的、主要流程、从哪里开始读、坑和边界。流程是从地图上取下来的路径。模型把它们写成文字，脚本再像查卡片的关系行那样，拿地图来检查它们。这一页最后才写，却是大多数读者最先看到的部分。

测一测你自己的配置

  1. 挑一个小领域和一个入口。
  2. 让脚本或 agent 列出这个入口能碰到的一切，最深的排最前。
  3. 按这个顺序学，放在一个任务里，分两三批。
  4. 检查每张卡片的“用到”和地图一致，每条引用的行都在对象之内。

What batches cost, and where they can go wrong

Where does the cost sit? The real token cost of the whole base is the model reading each object's code once, while the scripts are free. Caching may change the bill, because cached reads of repeated context cost far less than fresh ones (Anthropic's docs: about a tenth), but I have not checked how much this helps on Copilot (1.1).

Batches also take patience. A domain of a few hundred objects is many batches, all of them listed in a plan that a person has to approve. With approvals for the plan, each write-back and the entry points, review time can be the slowest part of the work.

Long objects break the pattern too: a procedure of thousands of lines is its own batch, read in parts, and its card may be longer.

The order itself helps only if the map is right. A map that misses a use gives a wrong order and a card that lacks a relation. The audit is there for this.

分批學要花什麼，又可能在哪裡出錯

錢花在哪裡？整個知識庫真正的 token 成本，是模型把每個物件的程式碼讀一遍，腳本則是免費的。快取可能改變帳單，因為重複上下文的快取讀取比全新的便宜得多（Anthropic 的文件：約十分之一），不過在 Copilot 上能省多少，我沒有確認（1.1）。

分批還需要耐心。幾百個物件的領域就有很多批，計劃要把它們全列出來，人還必須批准。加上計劃、每次寫回和入口的批准，審查的時間可能是這份工作裡最慢的部分。

還有一種例外：很長的物件會打破這個規律，幾千行的預存程序自己是一批，分段讀，它的卡片也可能比較長。

順序有用，前提是地圖對。地圖只要漏掉一處使用，排出的順序就是錯的，卡片也會少一條關係。抽查就是為此而設的。

分批学要花什么，又可能在哪里出错

钱花在哪里？整个知识库真正的 token 成本，是模型把每个对象的代码读一遍，脚本则是免费的。缓存可能会改变账单，因为重复上下文的缓存读取比新读便宜得多（Anthropic 文档：约十分之一），不过在 Copilot 上能省多少，我没查过（1.1）。

分批还要有耐心。几百个对象的领域就有很多批，计划里要全部列出来，还必须由人审批。计划、每次写回、入口都要审批，审查的时间可能是整件事里最慢的一环。

还有一种例外：特别长的对象会打破这个模式，几千行的存储过程自成一批，分段读，它的卡片也可能更长。

顺序有用，前提是地图对。地图只要漏掉一处调用关系，顺序就是错的，卡片也会缺一条关系。盲抽查就是为这个设的。

When the batches can grow, and what stays

The batch size is a guess for today's context windows and models. If a model can reliably read and write far more in one go, make the batches larger, or measure it (6.3). The bottom-up order is another matter, and it stays useful as long as cards point at other cards.

什麼時候批次可以加大，什麼要留下

批次大小是照今天的上下文視窗和模型猜的。如果模型一次能可靠地讀寫多得多的內容，就把批次加大，或者實際量一量（6.3）。由下往上的順序是另一回事，只要卡片還指向別的卡片，它就一直有用。

什么时候批次可以调大，什么要留下

批次大小是针对今天的上下文窗口和模型猜的。如果有模型一次能可靠地读和写多得多的内容，就把批次调大，或者去测一测（6.3）。自底向上的顺序是另一回事，只要卡片还指向别的卡片，它就一直有用。
