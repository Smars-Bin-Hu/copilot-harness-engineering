8.4

Learning a domain in batches分批學一個領域

This chapter follows The audit. The map is now trusted enough to learn from. This is steps four to six of the road. It leans on Context budget for why one big context is a bad place to learn a lot. Two words from earlier: a task is one piece of work with a plan, a to-do list and its own files (5.1); a write-back is the single copy of finished work into the base, which a person approves (5.3).

這一章接在 地圖對不對：盲抽查 後面。地圖現在可信到足以拿來學。這是路線的第四到第六步。它靠 上下文是一份預算 來說明，為什麼一個大的上下文不適合一次學很多。前面出現過的兩個詞：任務是一件有計劃、待辦清單和自己檔案的工作（5.1）；寫回是把做完的工作一次複製進知識庫，由人批准（5.3）。

The Knowledge經驗分享

In one sentence

Learn from the bottom of the dependency tree upward, in batches small enough to read in one go. What an object uses is learned before it, so the cards above can point down at the cards below instead of reading their code again.

一句話

從依賴樹的底部往上學，分成小到一次讀得完的批次。一個物件用到的東西，先於它被學到，所以上面的卡片可以指向下面的卡片，不用再讀它們的程式碼。

For leaders

  • The decision: approve, for each domain, the entry points, the plan, and the final write-back into the base. A person chooses where a domain starts and ends.
  • The risk: the checks cover structure, not meaning. A note can pass every check and still misstate what a rule is for, and a wrong note low in the order spreads to the notes above it. Cited lines are checked only to fall inside the object, which a made-up citation can pass.
  • The cost of doing it right: the model reads each object's code once, which is the real token cost of the whole base. Review time can be the slowest part. The batch size (up to 20 objects, about 1500 lines) is a number I picked, not a measured one.
  • Ask the team: "Who reviews whether each note's rule means what the cited code says, not only that the lines exist?"

給主管

  • 要做的決定：對每個領域，批准入口、計劃，和最後寫回知識庫。由人選擇一個領域從哪裡開始、到哪裡結束。
  • 風險：檢查涵蓋結構，不涵蓋意義。一則筆記可以通過每個檢查，還是講錯了一條規則是做什麼的，而順序低處的一則錯誤筆記，會傳到它上面的筆記。引用的行只檢查落在物件裡面，編造的引用也能通過。
  • 做對的成本：模型把每個物件的程式碼讀一遍，這是整個知識庫真正的 token 成本。審查的時間可能是最慢的部分。批次大小（最多 20 個物件、約 1500 行）是我挑的數字，不是量出來的。
  • 可以問團隊：「誰來審查每則筆記的規則，意思是不是和引用的程式碼說的一樣，而不只是那些行存在？」

The problem

You have a trusted map and a few thousand objects, and you want a card for each. Two simple plans do not work.

Plan one: one big prompt. "Learn the whole domain." One context holds everything the agent reads. As it fills, the agent can forget and mix things up toward the end (context budget), so I expect the cards written last to be the worst ones. That is reasoning; I have not compared the plans.

Plan two: object by object, in any order. Say the agent starts with a procedure that calls three others. To explain it properly, it has to read those three. So it reads them too. A few objects later it meets one of those three on its own and reads it again. The same code is read many times, and each card was written without the cards below it.

A good order would learn the three first. Then the procedure's card can say "it calls A, B and C" and point to their cards. The agent never reads their code again.

問題

你有一張可信的地圖，和幾千個物件，你想為每個物件寫一張卡片。兩個簡單的計劃都行不通。

計劃一：一個大 prompt。「學完整個領域。」一個上下文裝著 agent 讀的一切。裝滿的時候，agent 可能忘掉並在接近尾聲時搞混（上下文預算），所以我預期最後寫的卡片是最差的。這是推理；我沒有比較過這幾個計劃。

計劃二：一個物件一個物件來，順序隨意。假設 agent 從一個呼叫其他三個的預存程序開始。要好好解釋它，就得讀那三個。所以它也讀了它們。幾個物件之後，它自己遇到那三個之一，又讀了一遍。同樣的程式碼讀了很多次，而且每張卡片寫的時候，下面的卡片都還沒有。

好的順序，是先學那三個。這樣預存程序的卡片就可以說「它呼叫 A、B 和 C」，並指向它們的卡片。agent 不用再讀它們的程式碼。

How it works

Start from the entry points

A domain (see A knowledge base: an honest index of the code) is a group of objects that serve one job. To learn one, you need to say where it begins. An entry point is an object that the outside world calls: a screen's controller, a public API, a scheduled job. Starting from entry points, the map shows everything they reach.

A person chooses the entry points and the boundaries. A script and a research note can propose them, and the agent asks, but it is the person who knows which is which. Two boundaries matter:

  • Stop at code you do not own. Framework code and another team's code are cut off, so the domain does not grow into them.
  • Cut off what is shared. An object used from many entry points belongs to no single domain. It is set aside, so that one domain does not swallow everything. (How many entry points make an object shared is a setting you can lower if one domain still swallows the rest.) Who learns the shared objects, and when, is left open in this chapter; they are the ones many things depend on, so it should be planned.

A script sets the order

A script walks the map from the entry points, bottom up. An object that uses nothing comes first. An object comes only after everything it uses. Then the script cuts this order into batches.

Here is a real order, from the open-source spring-petclinic sample. Four tables first (owners, pets, types, visits). Then the entities that map them. Then the repositories that read the entities. Then the controllers that sit on top. Each controller card points at the cards below it.

How big is a batch

A batch is objects of one type, at most 20 objects and about 1500 lines of code in all. I picked these numbers so that one batch fits in a context with room to think. An object longer than that is a batch of its own and is read in parts.

One type per batch helps because objects of one type share a card form and the same questions.

One domain, one task, one write-back

All the batches of a domain are one task (see Manage tasks, not chats). The task has:

  • A plan, listing every batch, approved by a person once.
  • A to-do list with one step per batch.
  • The cards, kept inside the task until the whole domain is done.

Then the domain is written into the knowledge base in one write-back (the single copy of the finished cards into the base, see Two gates: where a person approves), which the person approves. So the base never holds half a domain.

Chats come and go. After every two or three batches I start a new chat and say "continue". The task keeps the state: the plan, what is learned, what is left. The next batch is the first one the script gives once the learned objects are left out. This is the same idea as work that survives across sessions: memory in files, not in a chat.

Checks on what the model writes

The model writes each card. Its words are its own, but two parts are checked by script:

  • The relations line must equal the map. The "uses" a card lists have to be the same as the map's uses for that object. The card cannot add or drop one.
  • Every rule cites its lines, and the check makes sure those lines fall inside that object's code. A rule that cites lines outside the object is wrong. This is a weak check: it shows the lines exist, not that they support the rule. A made-up citation inside the right range passes. A person or an independent reviewer should spot-check whether the cited lines say what the rule says.

The flows on the architecture page also come from paths on the map, and are checked in the same way.

Here is the form of one card, from the harness's guide for writing them. The example is a stored procedure; the relations line is the one the script checks.

A card: what it is for, relations (checked against the map), the level, the rules with their lines, what is not known, traps.
```markdown
## sp:Db.dbo.usp_load_orders

- What: loads the day's orders from staging into dbo.orders, then logs the run
- Reads: `table:Db.dbo.stg_orders`, `table:Db.dbo.calendar` · Writes: `table:Db.dbo.orders` · Called by: `job:Daily_Load` · Calls: `sp:Db.dbo.usp_log`
- Level: verified (read in repo_a at 3f1c0a9e)

In: @run_date (date, default today). Out: none; rows in dbo.orders.
Changes: MERGE into dbo.orders on id (L18-L26): new rows inserted, known rows updated; then sets flag = 1 (L28).
Twice: safe; the MERGE matches on id.
On an error: no TRY/CATCH; the error goes to the job step, nothing is logged.

Logic: only rows whose date is a working day in dbo.calendar (L12-L16). See the card of `sp:Db.dbo.usp_log` for the log.

Not known: which environments run it on holidays (req-0004).

Traps: a staging row with a NULL id is dropped by the MERGE, with no error (L19).
```

A card that points at a lower card inherits that card's mistakes, since it does not read the code again. A wrong card low in the order can therefore spread upward (8.5).

What remains unchecked is whether the model understood a rule correctly. A script cannot tell. That is for a person's review, or an independent reviewer (5.6). I do not claim the checks cover meaning.

When the code shows a use the map lacks

While reading, the agent may see a use in the code that the map does not have. It must not add the use to the card by hand. The check would refuse it, and the next object written in the same form would be missed too. It notes the use, and the note goes back to the toolkit as a new example to fix. Then the map is rebuilt and checked again (8.3).

The last step: the architecture page

When all batches are done, the model writes the domain's architecture page: its purpose, main flows, where to start reading, traps and limits. The flows are paths taken from the map, and the model puts them into words. That page is the part most readers see first.

Test your own setup

  1. Pick one small domain and one entry point.
  2. Ask a script, or an agent, to list what the entry point reaches, deepest first.
  3. Learn in that order, in one task, in two or three batches.
  4. Check that each card's "uses" equal the map's, and that every cited line is inside the object.

原理

從入口開始

領域（見 知識庫：程式碼的誠實索引）是為了同一件工作的一組物件。要學一個領域，你得說它從哪裡開始。入口是外面的世界呼叫的物件：畫面的 controller、公開的 API、排程工作。從入口開始，地圖顯示它們碰得到的一切。

由人選擇入口和邊界。腳本和一份研究筆記可以提議，agent 也會問，但哪個是哪個，是人才知道。有兩個邊界很重要：

  • 停在不是你的程式碼上。框架的程式碼和別的團隊的程式碼要切開，這樣領域才不會長進去。
  • 切開共用的。從很多入口被用到的物件，不屬於任何單一領域。把它放在一邊，這樣一個領域才不會吞掉所有東西。（要有多少個入口，物件才算共用，是一個設定；如果一個領域還是吞掉其餘的，可以調低它。）共用的物件由誰、什麼時候學，這一章沒有決定；它們是很多東西依賴的對象，所以應該有計劃。

腳本定順序

腳本從入口開始，由下往上走地圖。什麼都不用的物件排第一。一個物件只排在它用到的一切之後。然後腳本把這個順序切成批次。

這是開源範例 spring-petclinic 的真實順序。先是四張資料表（owners、pets、types、visits）。然後是對應它們的 entity。然後是讀 entity 的 repository。然後是最上面的 controller。每張 controller 的卡片都指向它下面的卡片。

一批有多大

一批是同一種類型的物件，總共最多 20 個物件和約 1500 行程式碼。我挑這些數字，是為了讓一批放得進一個上下文，還留有思考的空間。比這更長的物件自己是一批，分段讀。

一批只有一種類型有幫助，因為同一種類型的物件，共用卡片的形式和同樣的問題。

一個領域，一個任務，一次寫回

一個領域的所有批次是一個任務（見 管任務，不管對話）。任務有：

  • 一份計劃，列出每一批，由人批准一次。
  • 一份待辦清單，每批一步。
  • 卡片，在整個領域完成之前，留在任務裡面。

然後領域用一次寫回寫進知識庫（把做完的卡片一次複製進知識庫，見 兩道門：人在哪裡批准），由人批准。所以知識庫從不會有半個領域。

對話來來去去。每兩、三批之後，我就開一個新對話，說「繼續」。任務保留狀態：計劃、學了什麼、還剩什麼。下一批，是把學過的物件排除之後，腳本給的第一批。這和 跨會話的長任務 是同一個想法：記憶放在檔案裡，不放在對話裡。

對模型寫的東西的檢查

每張卡片由模型寫。裡面的話是它自己的，但有兩個部分由腳本檢查：

  • 關係那一行必須等於地圖。一張卡片列的「用到」，必須和地圖上那個物件的使用一樣。卡片不能多加或少掉一個。
  • 每條規則都引用它的行，檢查確保那些行落在那個物件的程式碼裡面。引用物件之外的行的規則是錯的。這是個弱的檢查：它顯示那些行存在，不顯示它們支持這條規則。落在正確範圍內的編造引用，可以通過。人或獨立的 reviewer 應該抽查，引用的行說的是不是和規則說的一樣。

架構頁上的流程，也來自地圖上的路徑，以同樣的方式檢查。

這是一張卡片的形式，來自 harness 寫卡片的指南。例子是一個預存程序；關係那一行就是腳本檢查的那一行。

一張卡片：它做什麼、關係（對照地圖檢查）、層級、附行號的規則、不知道的部分、陷阱。

指向下層卡片的卡片，會繼承那張卡片的錯誤，因為它不再讀程式碼。所以順序低處的一張錯誤卡片，會往上傳（8.5）。

剩下沒檢查的，是模型有沒有正確理解一條規則。腳本分辨不出來。這要靠人的審查，或獨立的 reviewer（5.6）。我不宣稱這些檢查涵蓋了意義。

程式碼顯示了地圖沒有的使用

讀的時候，agent 可能看到程式碼裡有地圖上沒有的使用。它不能手動把這個使用加進卡片。檢查會拒絕，而且用同樣的形式寫的下一個物件，也會漏掉。它把這個使用記下來，這則備註回到 toolkit，成為一個要修的新例子。然後地圖重建並再檢查一次（8.3）。

最後一步：架構頁

所有批次完成後，模型寫這個領域的架構頁：它的用途、主要的流程、從哪裡開始讀、陷阱和限制。流程是從地圖取來的路徑，模型把它們寫成文字。那一頁是多數讀者最先看到的部分。

測你自己的設定

  1. 挑一個小的領域和一個入口。
  2. 請腳本或 agent 列出這個入口碰得到的東西，最深的排最前。
  3. 照那個順序學，在一個任務裡，分兩、三批。
  4. 檢查每張卡片的「用到」等於地圖上的，而且每一行引用都在物件裡面。

Costs and traps

  • The model reads each object's code once. That is the real token cost of the whole base. The scripts are free.
  • Batches take patience. A domain of a few hundred objects is many batches. The plan lists them all, and a person must approve it. With approvals for the plan, each write-back and the entry points, review time can be the slowest part of the work.
  • Caching may change the bill. Cached reads of repeated context cost far less than fresh ones (Anthropic's docs: about a tenth). I have not checked how much this helps on Copilot (1.1).
  • A long object breaks the pattern. A procedure of thousands of lines is its own batch, read in parts. Its card may be longer.
  • Order helps only if the map is right. A map that misses a use gives a wrong order and a card that lacks a relation. The audit is there for this.
  • Unchecked meaning. See above. A card can pass every check and still misstate what a rule is for.

代價和陷阱

  • 模型把每個物件的程式碼讀一遍。這是整個知識庫真正的 token 成本。腳本是免費的。
  • 批次需要耐心。幾百個物件的領域有很多批。計劃把它們全列出來，人必須批准。加上計劃、每次寫回和入口的批准，審查的時間可能是這份工作裡最慢的部分。
  • 快取可能改變帳單。重複上下文的快取讀取，比全新的便宜得多（Anthropic 的文件：約十分之一）。這在 Copilot 上幫多少，我沒有確認（1.1）。
  • 很長的物件會打破這個規律。幾千行的預存程序自己是一批，分段讀。它的卡片可能比較長。
  • 順序只有在地圖對的時候才有用。漏掉一個使用的地圖，會給出錯的順序，和少一個關係的卡片。抽查就是為這個而有的。
  • 沒檢查的意義。見上面。一張卡片可以通過每個檢查，還是講錯一條規則是做什麼的。

When to delete it

The batch size is a guess for today's context windows and models. If a model can reliably read and write far more in one go, make the batches larger, or measure it (6.3). The bottom-up order stays useful as long as cards point at other cards.

什麼時候可以刪掉

批次大小是對今天的上下文視窗和模型的猜測。如果模型能可靠地一次讀和寫多得多，就把批次加大，或者去量（6.3）。只要卡片指向別的卡片，由下往上的順序就一直有用。
