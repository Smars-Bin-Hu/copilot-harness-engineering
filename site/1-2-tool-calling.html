The Knowledge經驗分享经验分享

In one sentence

The model only asks for tool calls and a program outside it runs them, and since the model can only work from a tool's name, description and error messages, how well those words are written decides how well the tool gets used.

一句話

模型只負責提出工具呼叫，真正執行工具的是它外面的程式，而模型要用工具，能依靠的只有工具的名字、描述和錯誤訊息，所以這些文字寫得好不好，決定了工具能不能被用好。

一句话

模型只提出工具调用，真正运行工具的是它外面的程序，而模型只能靠工具的名字、描述和报错信息来用工具，所以这些文字写得好不好，决定了工具能不能被用好。

For leaders

  • The decision: treat the tools you give an agent as a product, with someone responsible for the descriptions and error messages, and decide which fixed steps become commands rather than lines in a prompt.
  • The risk: the model can only guess from a tool's name and description, so a vague tool gets used wrongly or not at all. A rule in a prompt is only a request, while a step done by a command can't be skipped, as long as the work goes through that command.
  • The cost of doing it right: rewriting descriptions and error messages costs very little. Commands are code, and someone has to maintain and test them.
  • Ask the team: "If you saw only a tool's name and description, would you know when to use it? And what do its error messages say?"

給主管

  • 要做的決定：把給 agent 的工具當成產品來做，描述和錯誤訊息都要有人負責；另外也要決定，哪些固定的步驟做成指令，不寫進 prompt。
  • 風險：模型只能靠工具的名字和描述去猜，含糊的工具會被用錯，或者根本沒人用。寫在 prompt 裡的規則只是請求，而由指令完成的步驟，只要走這條路徑，就跳不過去。
  • 做對的成本：重寫描述和錯誤訊息花不了多少功夫。指令是程式碼，要有人維護和測試。
  • 可以問團隊：「如果只看每個工具的名字和描述，你知道什麼時候該用它嗎？它的錯誤訊息又是怎麼寫的？」

写给管理者

  • 要拍板的事：把给 agent 的工具当成产品来做，描述和报错信息都要有人负责；还要决定哪些固定的步骤做成命令，不写进 prompt。
  • 风险：模型只能根据工具的名字和描述去猜，含糊的工具会被用错，或者根本没人用。写在 prompt 里的规则只是请求，而由命令完成的步骤，走这条路径就跳不过去。
  • 做对的代价：重写描述和报错信息花不了多少。命令是代码，要有人维护和测试。
  • 可以问团队：“如果只看每个工具的名字和描述，你能知道什么时候该用它吗？它的报错信息又是怎么说的？”

The model can't touch your files on its own

When you watch an agent edit a file, it looks like the model did it, but the model is just a program that reads text and writes text. It can't open a file or run a command by itself. What it can do is write a structured request that amounts to "call the tool read_file with the path src/app.py", and that's a tool call. The program around the model (the first meaning of harness in What is Harness Engineering?) reads this request, goes and reads the file, and puts the contents back into the conversation as a tool result, and the model reads that and decides what to do next. Reading files, searching, editing files, running commands, fetching web pages: anything an agent can ask for this way is called a tool.

Two things follow from this. First, every action the agent takes has to go through a call, and calls are carried out outside the model, so the program can check, refuse or change them, and that's what makes it possible to enforce rules on an agent at all. Second, when the model uses a tool, all it has is the tool's name, description and parameter list. It isn't a programmer who has read the docs and can ask a colleague. It's a user guessing from those few lines, so how well they're written directly decides whether the tool gets used well.

One round trip

Take Anthropic's API as an example. When the model wants a tool, its response comes back with stop_reason set to tool_use and a tool_use block that gives the tool name and arguments. Your code runs the tool and sends the result back in a tool_result block (Tool use overview). Tools that run on your side like this are called client tools, and most of what an agent in your editor does happens this way, on your machine. There's a second kind, server tools, such as Anthropic's web_search, which run on the provider's side and return the result directly with none of your code in between, so you have no chance to step in before or after they run.

模型自己碰不到你的檔案

看 agent 改檔案，你會以為是模型改的，其實模型只是一個讀文字、寫文字的程式，自己打不開檔案，也跑不了指令。它能做的，是寫出一段結構化的請求，意思是「呼叫工具 read_file，路徑是 src/app.py」，這就是一次工具呼叫（tool call）。模型外面的程式（什麼是 Harness Engineering？裡第一種意思的 harness）讀到這個請求，才真的去讀檔案，再把內容當成工具結果放回對話，模型讀完再決定下一步。讀檔案、搜尋、改檔案、執行指令、抓取網頁，這些 agent 能要求做的動作都叫工具。

這件事有兩個後果。第一，agent 的每個動作都要經過一次呼叫，而呼叫是在模型外面執行的，所以程式可以檢查、拒絕或者修改它，你能對 agent 強制執行規則，靠的就是這一點。第二，模型用工具的時候，手上只有工具的名字、描述和參數清單，它不是看過文件、能問同事的程式設計師，而是一個靠這幾行字來猜的使用者，所以這幾行字寫得好不好，直接決定工具能不能被用好。

一次來回

拿 Anthropic 的 API 來說，模型要用工具時，回覆的 stop_reason 是 tool_use，裡面帶著寫明工具名和參數的 tool_use 區塊，你的程式碼執行這個工具，再用 tool_result 區塊把結果送回去（Tool use overview）。這種在你這邊執行的叫用戶端工具，編輯器裡的 agent 做的事，大部分都是這樣在你的機器上執行的。另外還有一類伺服器端工具，例如 Anthropic 的 web_search，它在供應商那邊執行，結果直接回傳，中間沒有你的程式碼，所以你沒辦法在它執行之前或之後插手。

模型自己碰不到你的文件

看着 agent 改文件，你会觉得是模型改的，其实模型只是一个读文本、写文本的程序，它自己打不开文件，也运行不了命令。它能做的是写出一段结构化的请求，意思是“调用工具 read_file，路径是 src/app.py”，这就是一次工具调用（tool call）。模型外面的程序（什么是 Harness Engineering？里第一种意思的 harness）读到这个请求，真的去读文件，再把读到的内容作为工具结果放回对话，模型读完再决定下一步。读文件、搜索、改文件、运行命令、抓取网页，这些 agent 能要求做的动作都叫工具。

这件事有两个后果。第一，agent 的每个动作都要经过一次调用，而调用是在模型外面执行的，所以程序可以检查、拒绝或者修改它，这是你能对 agent 强制执行规则的基础。第二，模型用工具的时候，手里只有工具的名字、描述和参数列表，它不是一个看过文档、能问同事的程序员，而是一个靠这几行字来猜的用户，所以这几行字写得好不好，直接决定工具能不能被用好。

Where you can step in, and how to write the tools

Where you can step in

With client tools the program sits between the request and the action, which gives you two places to step in. Before a tool runs, the program can allow, refuse or change the call, usually through a hook, and when it refuses, the reason goes back to the agent (Hooks, the point every call passes through). After a tool runs, the program can trim, filter or add to the result before the model reads it. Rules placed here are code that runs, whereas rules in a prompt are only requests (A rule in a prompt is a request). But a hook can only judge a call the model has already made. Whether the model makes the right call depends on what it sees before the call and what it gets back after, and you write both of those.

The model has only your words to go on

Someone using a command line can read the docs, ask a colleague and sense when something's off. The model has a tool's name, a description and a parameter list, and that's all. It uses those to decide when to call the tool and guesses the arguments from context, it knows nothing the tool doesn't tell it, it reads everything that comes back as plain text, and however big the result is, that's how much of the context window it takes. So it guesses wrong. Anthropic's docs give the example of get_weather, which needs a location: if you ask "What's the weather?" without saying where, Opus is more likely to ask you, while Sonnet might fill in New York by itself (Tool use overview).

The flip side is that changing those few lines pays off well. Anthropic says "even small refinements to tool descriptions can yield dramatic improvements", and Claude Sonnet 3.5 got the best score of its time on the SWE-bench Verified evaluation after they made precise changes to the tool descriptions (Writing tools for agents). The five rules below follow the order of a single call.

1. Write the description like handover notes for a new hire

Before the call, the description is the only place the model can learn what a tool is for, so it needs to say what the tool does, when to use it and when not to. A vague description gets the tool used wrongly or not at all. Parameter names work the same way: Anthropic's example is to call a parameter user_id and not user, because user could be a name, an email address or an ID. And if two tools look alike, each description should say how it differs from the other.

2. Write error messages for the agent to read

When a call fails, the error is the next thing the model reads. A person who sees a stack trace stops to think, but the model takes the text and carries on. If the error just says Error 400, it can only guess, and it often guesses the same wrong value again. If the error says what was wrong and what to try next, it can fix the call. The same goes for refusals, which should say what to do instead (Asking is not a limit).

3. Keep the output short, and make it pageable

When a call succeeds, the model reads the output. Everything a tool returns goes into the context window (Context is a budget) and gets read again on every later turn (Don't pick a model by token price alone), so if the agent wants one line and the tool returns a whole large file, you don't just waste tokens, you may also push useful things out of the window. The fix is to put limits on results, such as a default cap, paging, range selection or filters. Claude Code limits tool responses to 25,000 tokens by default, and wherever you set your limit, say so when you cut something off, and tell the agent how to narrow its query. Anthropic has one more idea, a response_format parameter that lets the agent choose concise or detailed. In their example the detailed response is 206 tokens and the concise one is 72, about a third (Writing tools for agents).

4. Fewer tools mean better choices

More tools have a price. Once a tool is loaded, its name, description and parameters go to the model on every call, so the more tools you have, the more tokens you spend and the more chances the model has to pick the wrong one, especially when they overlap. Claude Code and VS Code (Claude Sonnet 4.5, Opus 4.5 and later) use tool search by default, which holds some tools back until the model searches for them. That saves the tokens their definitions would take, but the model still finds them through their names and descriptions (What should you think through before connecting an MCP server?). VS Code also has a hard limit of 128 enabled tools per request, and you can turn off the ones you don't need in the tool picker (Agent tools). So prefer a small set of clearly different tools, and merge what you can. Anthropic's examples are a search_contacts tool instead of list_contacts, and a single schedule_event tool that both finds a free slot and books it. When you do have a lot of tools, giving related ones a shared name prefix also helps the agent tell them apart, though Anthropic says whether a prefix or a suffix works better varies by model, so decide with your own evals (Writing tools for agents).

5. Put fixed steps in a command, not a prompt

Of the five, this is the one I most want to stress. Some work has the same steps every time and a clear right and wrong, such as creating a folder for a new task, copying files, computing a hash, writing a record, or checking that everything's ready before writing back. You can put those steps in the instructions and ask the agent to follow them, and most of the time it will, but you can also write them once as a command, a small program the agent runs as a tool. The command does the steps itself, checks the preconditions and returns a short result. When the work goes through the command, the agent can't skip a step and can't write a wrong state, because it isn't the one writing the state.

This suits steps that take no judgment. If a step needs the agent to make a decision, leave that part to it and let the command do the fixed work around it. My harness works this way: a command-line tool creates task folders (Manage tasks, not chats), fetches files, computes diffs and tallies checks, and the model just runs the commands and reads the results. Progress is the best example. The task list reads a data file the command writes, not a Markdown note the agent wrote by hand, because hand-written progress misses checkboxes and gets things wrong.

A command's output should ideally say what to do next, so the agent doesn't have to guess. The same command gets read by people in a terminal and by scripts through a pipe, so it can print aligned text in a terminal and JSON on a pipe, with the same fields in both.

A command's weakness is that it only helps when the agent actually uses it, and it only guards what passes through it. If the agent has another way to do the same thing, such as editing the file by hand, the command is a convenience and not a limit (A rule in a prompt is a request).

How to check your own tools

For any tool you give an agent, start with three questions. Going by the name and description alone, would you know when to use it and when not to? When it fails, does the message tell the agent what to do next? How big can its output get, and if that's very big, what happens to the context?

The quickest experiment needs no setup. Have the agent call one of your tools in a way you know is wrong, look at what comes back, and ask whether that message would tell you what to do if you were the agent. If it wouldn't, that's the message to rewrite.

If you build your own tools, Anthropic's method is the same idea at a bigger scale: write tasks based on real use, run them, read the raw transcripts (the calls and results, not just the final answer), and change the descriptions and error messages wherever the agent went wrong. They also paste those transcripts into Claude Code and have it improve the tools, and most of the advice in their article came from doing that (Writing tools for agents).

能在哪裡插手，工具又該怎麼寫

你能在哪裡插手

只要是用戶端工具，程式就夾在請求和動作之間，所以有兩個地方可以插手。工具執行之前，程式可以放行、拒絕或者修改這次呼叫，常用的辦法是 hook，拒絕時給的原因會送回給 agent（Hooks：每次呼叫都會經過的執行點）。工具執行之後，程式可以在模型讀到結果之前，先把結果精簡、過濾或者補充一下。放在這裡的規則是會執行的程式碼，而寫在 prompt 裡的規則只是請求（提示裡的規則只是請求）。但是 hook 只能判斷模型已經發出的呼叫，模型能不能把呼叫發對，要看它呼叫之前看到了什麼、呼叫之後拿回了什麼，這兩樣都是你寫的文字。

模型只能靠你寫的文字來用工具

人用命令列，可以看文件、問同事，還能察覺哪裡不對勁。模型手上只有工具的名字、一段描述和參數清單，它靠這些決定什麼時候用，靠上下文去猜參數，工具沒告訴它的事它一概不知道，回傳的結果它也都當普通文字讀，結果有多大，就占掉多少上下文視窗。所以它會猜錯，Anthropic 的文件舉的例子是，get_weather 需要地點，你問「天氣怎麼樣？」卻沒說在哪，Opus 比較可能回頭問你，Sonnet 可能自己填一個 New York（Tool use overview）。

反過來說，改這幾行字的回報很高。Anthropic 說「就算只是對工具描述做很小的改進，也能帶來顯著的提升」，Claude Sonnet 3.5 在 SWE-bench Verified 評測上拿到當時最好的成績，就是在精確地修改工具描述之後（Writing tools for agents）。下面五條規則，按一次呼叫經過的順序排。

1. 描述要寫得像給新進同事的交接說明

呼叫之前，描述是模型了解工具用途的唯一地方，所以要寫清楚這個工具做什麼、什麼時候用、什麼時候不用，寫得含糊，工具就會被用錯，或者沒人用。參數的名字也一樣，Anthropic 的例子是別叫 user，要叫 user_id，因為 user 可能是名字，也可能是電子郵件或者 ID。如果兩個工具看起來很像，每個工具的描述裡都要說清楚它和另一個有什麼不同。

2. 錯誤訊息要寫給 agent 看

呼叫出了錯，模型接下來讀到的就是錯誤訊息。人看到堆疊追蹤會停下來想一想，模型則是拿到文字就接著往下走，如果錯誤訊息只有 Error 400，它就只能猜，而且往往又猜回同一個錯的值，如果訊息說明了哪裡不對、接下來該試什麼，它就能把呼叫改對。拒絕也一樣，要說明應該改做什麼（詢問不是限制）。

3. 輸出要短，還要能分頁

呼叫成功了，模型讀到的是輸出。工具回傳的所有東西都會放進上下文視窗（上下文是一份預算），而且之後每一輪都要再讀一遍（選模型，別只看 token 單價），所以如果 agent 只想要一行，工具卻把一個大檔案整個回傳，不但浪費 token，還可能把有用的東西擠出視窗。辦法是給結果設限制，例如預設的上限、分頁、範圍選擇或者過濾器。Claude Code 預設把工具的回應限制在 25,000 個 token 以內，不管上限定在哪裡，截斷的時候都要說一聲，並且告訴 agent 怎麼縮小查詢範圍。Anthropic 還有一個做法，是加一個 response_format 參數，讓 agent 自己選簡潔或詳細，他們的例子裡詳細回應是 206 個 token，簡潔回應是 72 個，只有三分之一（Writing tools for agents）。

4. 工具少，選得更準

多一個工具不是沒有壞處。工具只要載入了，它的名字、描述和參數每次呼叫都要送給模型，工具越多，花的 token 越多，選錯的機會也越多，功能重疊的時候尤其如此。Claude Code 和 VS Code（Claude Sonnet 4.5、Opus 4.5 以上）預設用工具搜尋，一部分工具先不載入，用到時才搜出來，這能省下定義占的 token，但是模型還是要靠名字和描述才搜得到它（接 MCP server 之前，要想清楚什麼？）。VS Code 還有一個硬上限，一次請求最多啟用 128 個工具，用不上的可以在工具選擇器裡關掉（Agent tools）。所以優先用一小組明顯不同的工具，能合併的就合併，Anthropic 的例子是做一個 search_contacts 而不是 list_contacts，做一個 schedule_event 把查空檔和建立行程合在一起。工具很多的時候，把相關的工具歸到同一個名字前綴下也能幫 agent 分清楚，不過前綴和後綴哪種好，Anthropic 說不同模型效果不一樣，要用自己的評測來決定（Writing tools for agents）。

5. 固定的步驟做成指令，不寫進 prompt

這是五條裡我最想強調的一條。有些工作的步驟每次都一樣，而且有對錯之分，例如替新任務建資料夾、複製檔案、算一個雜湊值、寫入紀錄、寫回之前檢查一切就緒。你可以把這些步驟寫進指令檔讓 agent 照著做，它大多數時候也會照做，但是也可以一次寫成一個指令（command），也就是 agent 當作工具來執行的一個小程式，由指令自己完成這些步驟、檢查前置條件，最後回傳一個簡短的結果。走指令這條路徑時，agent 跳不過任何一步，也寫不出錯誤的狀態，因為狀態根本不是它寫的。

這適合不需要判斷的步驟，如果某一步需要 agent 拿主意，就把那部分留給它，指令只做周圍那些固定的事。我的 harness 就是這麼做的，一個命令列工具負責建任務資料夾（管任務，不管對話）、取檔案、算 diff、統計檢查，模型只要執行指令、讀結果。進度是最好的例子，任務清單讀的是指令寫入的資料檔，不是 agent 手寫的 Markdown 筆記，因為手寫的進度會漏打勾，也會寫錯。

指令的輸出最好能說明下一步做什麼，這樣 agent 就不用猜了。同一個指令既有人在終端機裡看，也有腳本透過管線讀，所以可以在終端機裡印出對齊的文字，接到管線上時印出 JSON，兩種輸出的欄位一樣。

指令的弱點是 agent 真的去用它才有用，而且它只守得住經過它的東西，如果 agent 能用別的辦法做同樣的事，例如手動改檔案，指令就只是圖個方便，算不上限制（提示裡的規則只是請求）。

怎麼檢查你自己的工具

對你給 agent 的任何一個工具，先問三個問題。只看名字和描述，你知道什麼時候該用、什麼時候不該用嗎？它失敗的時候，訊息有沒有告訴 agent 接下來做什麼？它的輸出最大能有多大，如果很大，上下文會怎麼樣？

最快的實驗什麼都不用裝：讓 agent 用一種你明知不對的方式呼叫你的某個工具，看看回傳了什麼，假如你就是那個 agent，這條訊息能不能讓你知道該怎麼辦，如果不能，要重寫的就是這條訊息。

如果你自己做工具，Anthropic 的方法是同一個想法的放大版：根據真實的使用情境寫出任務，執行它們，讀原始紀錄（呼叫和結果，不只是最後的答案），然後在 agent 出錯的地方改描述和錯誤訊息。他們還把這些紀錄貼給 Claude Code，讓它來改工具，文章裡大部分的建議就是這麼來的（Writing tools for agents）。

能在哪里插手，工具又该怎么写

你能在哪里插手

用客户端工具的时候，程序夹在请求和动作之间，所以有两个地方可以插手。工具运行之前，程序可以放行、拒绝或者修改这次调用，常用的办法是 hook，拒绝时给出的原因会送回给 agent（硬性规则放在哪？用 hook）。工具运行之后，程序可以在模型读到结果之前，把结果精简、过滤或者补充一下。放在这里的规则是会运行的代码，而写在 prompt 里的规则只是请求（为什么 Agent 不听 prompt 里的规则？）。但是 hook 只能判断模型已经发出的调用，模型能不能把调用发对，取决于它调用之前看到了什么、调用之后拿回了什么，这两样都是你写的文字。

模型只能靠你写的文字来用工具

人用命令行，可以看文档、问同事，还能察觉到哪里不对劲。模型手里只有工具的名字、一段描述和参数列表，它靠这些决定什么时候用，靠上下文去猜参数，工具没告诉它的事它一概不知道，返回的结果它也都当普通文本读，结果有多大，就占掉多少上下文窗口。所以它会猜错，Anthropic 的文档举的例子是，get_weather 需要地点，你问“天气怎么样？”却没说在哪，Opus 更可能回头问你，Sonnet 可能自己填一个 New York（Tool use overview）。

反过来，改这几行字的回报很高。Anthropic 说“哪怕对工具描述做很小的改进，也能带来显著的提升”，Claude Sonnet 3.5 在 SWE-bench Verified 评测上拿到当时最好的成绩，就是在精确地改了工具描述之后（Writing tools for agents）。下面五条规则按一次调用经过的顺序排。

1. 描述要写得像给新员工的交接说明

调用之前，描述是模型了解一个工具用途的唯一地方，所以要写清楚这个工具做什么、什么时候用、什么时候不用，写得含糊，工具就会被用错，或者没人用。参数的名字也一样，Anthropic 的例子是别叫 user，要叫 user_id，因为 user 可能是名字，也可能是邮箱或者 ID。如果两个工具看起来很像，每个工具的描述里都要说清它和另一个有什么不同。

2. 报错信息要写给 agent 看

调用出了错，模型接下来读到的就是报错。人看到堆栈会停下来想一想，模型是拿到文本就接着往下走，如果报错是 Error 400，它就只能猜，往往又猜回同一个错的值，如果报错说明了哪里不对、接下来该试什么，它就能把调用改对。拒绝也一样，要说明应该改做什么（“先问我”为什么挡不住 Agent？）。

3. 输出要短，还要能分页

调用成功了，模型读到的是输出。工具返回的所有东西都会放进上下文窗口（为什么不能把所有规则都塞给 Agent？），而且之后每一轮都要再读一遍（选模型，别只看 token 单价），所以如果 agent 只想要一行，工具却把一个大文件整个返回，不光浪费 token，还可能把有用的东西挤出窗口。办法是给结果设限制，比如默认的上限、分页、范围选择或者过滤器。Claude Code 默认把工具的响应限制在 25,000 个 token 以内，不管上限定在哪里，截短的时候都要说一声，并告诉 agent 怎么缩小查询范围。Anthropic 还有一个做法是加一个 response_format 参数，让 agent 自己选简洁还是详细，他们的例子里详细回复是 206 个 token，简洁回复是 72 个，只有三分之一（Writing tools for agents）。

4. 工具少，选得更准

多一个工具不是没坏处。工具只要加载了，它的名字、描述和参数每次调用都要发给模型，工具越多，token 花得越多，选错的机会也越多，功能重叠的时候尤其如此。Claude Code 和 VS Code（Claude Sonnet 4.5、Opus 4.5 以上）默认用工具搜索，一部分工具先不加载，用到时才搜出来，这能省下定义占的 token，但是模型还是要靠名字和描述才搜得到它（接 MCP server 之前，要想清楚什么？）。VS Code 还有一个硬上限，一次请求最多启用 128 个工具，用不上的可以在工具选择器里关掉（Agent tools）。所以优先用一小组明显不同的工具，能合并的就合并，Anthropic 的例子是做一个 search_contacts 而不是 list_contacts，做一个 schedule_event 把查空闲和建日程合在一起。工具很多的时候，把相关的工具归到同一个名字前缀下也能帮 agent 分清楚，不过前缀和后缀哪种好，Anthropic 说不同模型效果不一样，要用自己的评测来定（Writing tools for agents）。

5. 固定的步骤做成命令，不写进 prompt

这是五条里我最想强调的一条。有些活的步骤每次都一样，而且有对错之分，比如给新任务建文件夹、复制文件、算一个哈希、写入记录、写回之前检查一切就绪。你可以把这些步骤写进指令让 agent 照着做，它大多数时候也会照做，但是也可以一次性写成一个命令，也就是 agent 当作工具来运行的一个小程序，由命令自己完成这些步骤、检查前置条件，最后返回一个简短的结果。走命令这条路径时，agent 跳不过任何一步，也写不出错误的状态，因为状态根本不是它写的。

这适合不需要判断的步骤，如果某一步需要 agent 拿主意，就把那部分留给它，命令只做周围那些固定的事。我的 harness 就是这么做的，一个命令行工具负责建任务文件夹（一个任务一个文件夹）、取文件、算 diff、统计检查，模型只要运行命令、读结果。进度是最好的例子，任务清单读的是命令写入的数据文件，不是 agent 手写的 Markdown 笔记，因为手写的进度会漏打勾，也会写错。

命令的输出最好能说明下一步做什么，这样 agent 就不用猜了。同一个命令既有人在终端里看，也有脚本通过管道读，所以可以在终端里打印对齐的文本，接到管道上时打印 JSON，两种输出的字段一样。

命令的短板是 agent 真去用它才有用，而且它只守得住经过它的东西，如果 agent 能用别的办法做同样的事，比如手动改文件，命令就只是图个方便，算不上限制（为什么 Agent 不听 prompt 里的规则？）。

怎么检查你自己的工具

对你给 agent 的任何一个工具，先问三个问题。只看名字和描述，你知道什么时候该用、什么时候不该用吗？它失败的时候，信息有没有告诉 agent 接下来做什么？它的输出最大能有多大，如果很大，上下文会怎么样？

最快的实验什么都不用装：让 agent 用一种你明知不对的方式调用你的某个工具，看看返回了什么，假如你就是那个 agent，这条信息能不能让你知道该怎么办，如果不能，要重写的就是这条信息。

如果你自己做工具，Anthropic 的方法是同一个想法的放大版：根据真实的使用场景写出任务，运行它们，读原始记录（调用和结果，不只是最终答案），然后在 agent 出错的地方改描述和报错信息。他们还把这些记录贴给 Claude Code 让它来改工具，文章里的大部分建议就是这么来的（Writing tools for agents）。

Good tools have costs, and you can't fully trust the arguments the model picks

However good a description is, it costs tokens, because once the tool is loaded it's sent on every call, so write only what the model needs to choose and use the tool, and put the long manual in a file the agent can read when it needs to. A command costs you something else. It's code to maintain, it can break when the project changes, and it breaks in ways a prompt never does, so keep each command small and write tests for it.

You also can't treat a tool call as what the user wants, because the model chose the arguments, and the text it read before choosing could have come from anywhere (Text the agent reads can give it orders). On Anthropic's API, strict: true guarantees that a call matches the tool's schema, but that only covers the format, and the values are still the model's choice (Tool use overview).

One more practical trap: tool names change between versions, so if your rules or hooks match on tool names, keep that mapping in one place and a rename touches only that place.

好工具也有代價，模型選的參數也不能全信

描述寫得再好也要花 token，因為工具只要載入了，描述每次呼叫都要送一遍，所以只寫模型選擇和使用這個工具需要的內容，長的說明放進檔案，讓 agent 需要時再讀。指令的代價不一樣，它是要維護的程式碼，專案一變就可能出錯，而且是 prompt 不會有的那種錯，所以每個指令都要保持小，並且寫測試。

工具呼叫也不能當成使用者的意願，因為參數是模型選的，而它選之前讀到的文字可能來自任何地方（agent 讀到的文字可能在指揮它）。Anthropic 的 API 上加 strict: true 能保證呼叫符合工具的 schema，但這只保證格式，值還是模型選的（Tool use overview）。

還有一個很實際的陷阱，工具名在不同版本之間會變，如果你的規則或 hook 按工具名來比對，就把這份對應關係放在同一個地方，改名時只改一處。

好工具也有代价，模型选的参数也不能全信

描述写得再好也要花 token，因为工具只要加载了，描述每次调用都要发一遍，所以只写模型选择和使用这个工具需要的内容，长的说明书放进文件里，让 agent 需要时再读。命令的代价不一样，它是要维护的代码，项目一变就可能出错，而且是 prompt 不会有的那种错，所以每个命令都要保持小，并且写测试。

工具调用也不能当成用户的意愿，因为参数是模型选的，而它选之前读到的文本可能来自任何地方（Agent 读到的网页和文件，可能在给它下命令）。Anthropic 的 API 上加 strict: true 能保证调用符合工具的 schema，但这只保证格式，值还是模型选的（Tool use overview）。

还有一个很实际的坑，工具名在不同版本之间会变，如果你的规则或 hook 按工具名来匹配，就把这份对应关系放在一个地方，改名时只改一处。

Model providers treat a tool's words as part of the interface too Industry practice

Two Anthropic sources say the same thing: a tool is an interface, and its words are part of that interface. Their article on writing tools treats tool design as part of the work, and holds that descriptions and error messages are worth testing the way you test code (Writing tools for agents). The tool use docs say client tools are run by your application, which sends the results back, and warn that the model "might guess values you didn't supply" (Tool use overview).

模型供應商也把工具的文字當介面 業界做法

Anthropic 的兩份資料說的是同一件事：工具是一個介面，它的文字也是介面的一部分。講怎麼寫工具的那篇把工具設計當成工作的一部分，認為描述和錯誤訊息值得像程式碼一樣測試（Writing tools for agents）。工具使用文件說用戶端工具由你的應用程式執行，再把結果送回去，還提醒模型「可能會猜出你沒提供的值」（Tool use overview）。

模型提供方也把工具的文字当接口 业界做法

Anthropic 的两份资料说的是同一件事：工具是一个接口，它的文字也是接口的一部分。讲怎么写工具的那篇把工具设计当成工作的一部分，认为描述和报错信息值得像代码一样测试（Writing tools for agents）。工具使用文档说客户端工具由你的应用运行，再把结果送回去，还提醒模型“可能会猜出你没提供的值”（Tool use overview）。

When to delete a command Industry practice

Commands are the part most likely to go out of date, because a command that checks preconditions is scaffolding built around a weakness of the model. If models become reliable enough at following multi-step instructions, a command may stop being better than a good prompt. Even then, I'd still use commands for anything that has to be exactly the same every time or has to leave a record. Descriptions and error messages are different, and for as long as models read text, that advice holds.

什麼時候可以刪掉指令 業界做法

最可能過時的是指令，因為檢查前置條件的指令是圍著模型的弱點搭起來的鷹架，如果模型在遵循多步驟的說明上變得夠可靠，指令也許就不再比一個好的 prompt 強。即使到了那一天，那些每次都必須完全一樣、或者需要留下紀錄的事，我還是會用指令。描述和錯誤訊息的道理不一樣，只要模型還在讀文字，它就一直成立。

什么时候可以删掉命令 业界做法

最可能过时的是命令，因为检查前置条件的命令是围着模型的弱点搭起来的脚手架，如果模型在遵循多步指令上变得足够可靠，命令也许就不再比一个好的 prompt 强。即便到了那一天，那些每次都必须完全一样、或者需要留下记录的事，我还是会用命令。描述和报错信息的道理不一样，只要模型还在读文本，它就一直成立。
