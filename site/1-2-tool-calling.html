1.2

Tool calling, and designing tools for an agentTool calling，和給 agent 設計工具

This chapter assumes you know that an AI coding agent can read files and run commands. You do not need to know how.

讀這一章，只需要知道 AI 寫程式 agent 能讀檔案、執行指令。怎麼做到的，不用知道。

The Knowledge經驗分享

In one sentence

A model only asks for a tool call; the program around it runs the tool. So a tool is an interface for an unreliable user, and its description and error messages decide whether it is used well.

一句話

模型只是要求呼叫工具；執行工具的，是它周圍的程式。所以工具是給一個不可靠的使用者用的介面，它的描述和錯誤訊息，決定它能不能被用好。

For leaders

  • The decision: treat the tools you give an agent as a product that needs a good description and good error messages, and decide which fixed steps go into a command, not a prompt.
  • The risk: the model only guesses from a tool's name and description, so a vague tool is used wrongly or never. A rule written in a prompt is a request; a step done by a command cannot be skipped on that path.
  • The cost of doing it right: rewriting descriptions and error messages is small. A command is code someone has to maintain. Anthropic suggests five real tasks are enough to start testing tools.
  • Ask the team: "If you read only the name and description of each tool, would you know when to use it? What does its error say?"

給主管

  • 要做的決定：把你給 agent 的工具當成產品，需要好的描述和好的錯誤訊息；並決定哪些固定的步驟，放進指令（command）裡，不放進 prompt 裡。
  • 風險：模型只能從工具的名字和描述去猜，所以含糊的工具會被用錯，或從來沒被用到。寫在 prompt 裡的規則是請求；由指令做的步驟，在那條路徑上沒辦法被跳過。
  • 做對的成本：重寫描述和錯誤訊息，成本很小。指令是程式碼，要有人維護。Anthropic 建議，五個真實的任務，就夠開始測試工具了。
  • 可以問團隊：「如果只讀每個工具的名字和描述，你知道什麼時候該用它嗎？它的錯誤訊息說了什麼？」

The problem

When you watch an agent edit a file, it looks as if the model did it. It did not. A language model is a program that takes in text and produces text. It cannot open a file, run a command or send a request. It has no hands.

What it can do is write a sentence that means "please call the tool read_file with the path src/app.py". That sentence is the tool call. The program around the model (the harness, in the first sense from chapter 0.1) reads the sentence, does the work, and puts the result back into the conversation as more text. The model then reads that result and decides what to do next.

This looks like a technical detail, but it changes how you should think about tools. Every action an agent takes passes through a call that the program could inspect, refuse or change. And the model is not a careful programmer calling a function: it is a reader guessing from a description. Treat it like a user who skims.

Three words first

  • A tool is one action the agent may ask for: read a file, search, edit a file, run a command, fetch a web page.
  • A tool call is the model's request to use one, with the arguments it chose.
  • A tool result is the text the program sends back after running it.

One round trip

The provider's own documentation describes the same round trip: the model answers with a stop reason of tool_use and a block that names the tool and its arguments; your code runs it and sends back a tool_result. (Tool use overview) One exception is worth knowing: some server tools, such as web search, run on the provider's side, so you never handle the call yourself. Most of what an agent in your editor does are client tools, run on your machine. The difference matters for this chapter: for a server tool, you cannot step in before or after it runs, because the program never sees the call.

問題

看 agent 改檔案的時候，好像是模型做的。其實不是。語言模型是一個吃進文字、吐出文字的程式。它不能打開檔案、執行指令或送出請求。它沒有手。

它能做的，是寫出一句話，意思是「請用路徑 src/app.py 呼叫工具 read_file」。這句話就是工具呼叫。模型周圍的程式（harness，用的是 差距在模型外面 裡的第一個意思）讀這句話，做事，再把結果當成更多文字放回對話裡。然後模型讀這個結果，決定下一步。

這看起來是個技術細節，但它改變了你該怎麼想工具。agent 做的每個動作，都經過一次呼叫，而程式可以檢查、拒絕或修改這次呼叫。而且模型不是在呼叫函式的謹慎程式設計師：它是根據描述去猜的讀者。把它當成一個只會快速瀏覽的使用者。

先講三個詞

  • 工具是 agent 可以要求的一個動作：讀檔案、搜尋、改檔案、執行指令、抓一個網頁。
  • 工具呼叫是模型要求用其中一個，附上它選的參數。
  • 工具結果是程式執行之後送回來的文字。

一次來回

供應商自己的文件也描述了同樣的來回：模型回答時帶著停止原因 tool_use，以及一個寫出工具名和參數的區塊；你的程式執行它，再送回 tool_result。（Tool use overview）有一個例外值得知道：有些 server tool（例如網頁搜尋）是在供應商那邊執行的，所以你自己永遠碰不到那次呼叫。你編輯器裡的 agent 做的大部分事，是 client tool，在你的機器上執行。這個差別對這一章很重要：對 server tool，你沒辦法在它執行之前或之後插手，因為程式從來看不到那次呼叫。

How it works

Where you can step in

Because the program sits between the request and the action, there are two places to step in:

  • Before the tool runs. The program can let the call through, refuse it, or change it. A hook (chapter 2.2) is the usual way to do that, and a refusal comes with a reason that goes back to the agent.
  • After it runs. The program can shorten, filter or add to the result before the model reads it.

That is the main reason it is possible to enforce rules on an agent at all. A rule that lives in the program is code that runs; a rule in a prompt is a request (chapter 4.1).

The rest of this chapter is about the middle of that trip: what the model sees and what it gets back. Both are text you write.

A tool is an interface for an unreliable user

A person using a command line can read documentation, ask a colleague, and notice that something looks wrong. The model has the tool's name, a short description, and the list of parameters. That is all. It can guess wrongly, and the provider's documentation says so: given a tool that needs a location and a request that does not give one, a model might make one up. (Tool use overview)

So designing a tool for an agent is designing for someone who:

  • reads only the name and description to decide when to use it,
  • fills the arguments by guessing from context,
  • does not know what the tool does not tell it,
  • reads the result as text, with whatever room it takes in the context window.

Anthropic's advice on writing tools for agents says the same in other words: "Even small refinements to tool descriptions can yield dramatic improvements." (Writing tools for agents) The five rules below follow from it.

1. Write the description like a brief for a new hire

Say what the tool does, when to use it, and when not to. Make names unambiguous: a parameter called user can mean a name, an ID or an email; user_email cannot. If two tools look alike, say in each one how it differs. The description is the only place the model learns this, so a vague one means the tool is used wrongly or never.

2. Write errors for the agent to read

A person can look at a stack trace and think. A model gets the text and goes on. If the error is Error 400, the model guesses, often the same thing again. If the error says what was wrong and what to try next, it fixes the call.

The same goes for a refusal: say what to do instead (chapter 4.2).

3. Keep the output short, and let it be paged

Everything a tool returns is put in the context window (chapter 3.1), and it is read again on every later turn (chapter 1.1). A tool that returns a whole large file when the agent wanted one line wastes tokens, and it can crowd useful things out of the window.

So give results sensible limits: a default cap, a way to ask for a range or the next page, a filter. Anthropic also describes letting the agent choose between a concise and a detailed response. And when you have many tools, grouping related ones under a common name prefix helps the agent tell them apart. (Writing tools for agents) Claude Code caps tool responses at 25,000 tokens by default (Anthropic's figure at the time of writing). When you cut the output, say so, and tell the agent how to narrow its query. (Writing tools for agents)

4. Fewer tools choose better

Every tool's name, description and parameters are sent to the model on every call. More tools cost more tokens and give more chances to pick the wrong one, especially when they overlap. Prefer a small set that is clearly different, and merge related operations into one where you can. (Writing tools for agents)

5. Do the fixed steps in a command, not in a prompt

This is the one I would stress most. Sometimes a job has steps that always go the same way and where there is a right and wrong: make the folder for a new task, copy the files, compute a hash, write the record, check that everything is ready before writing back. You can describe those steps in the instructions and ask the agent to follow them. It will, most of the time.

Or you can write them once as a command: a small program the agent runs as a tool. The command does the steps, checks the preconditions itself, and returns a short result. On the path through the command, the agent cannot skip a step and cannot write a wrong state, because it never writes it.

The fit is for steps that need no judgment. If a step needs the agent to decide something, leave that part to the agent and let the command do only what is fixed around it. This is what my harness does. A command line creates a task folder (the unit of work in Manage tasks, not chats), fetches files, works out diffs and counts checks, and the model only runs the command and reads the answer. Progress is a good example: the task list reads a data file that commands write, and not the Markdown notes an agent wrote by hand, because hand-written progress misses ticks and goes wrong. The result is the same every time, and the model does not have to get the steps right.

Two details make a command friendly to an agent:

  • A result that says what comes next. The command's output tells the agent what to do next, so it does not have to guess.
  • Text for people, JSON for scripts. The same command prints aligned text in a terminal and JSON when it is piped. The fields are the same.

A command only helps if the agent actually uses it, and it only guards what goes through it. If the agent can do the same thing another way (edit the file by hand), the command is a convenience, not a limit. Chapter 4.1 takes that further.

Test your own setup

Three questions for any tool you give an agent:

  1. If you read only its name and description, would you know when to use it and when not to?
  2. When it fails, does the message tell the agent what to do next?
  3. How big can its output be, and what happens to the context if it is large?

A zero-install experiment. Ask the agent to call one of your tools in a way that you know is wrong, and read what comes back. Is it clear enough that you would know what to do if you were the agent? If not, that is the message to rewrite.

A bigger loop, if you build tools. Anthropic's method is the same idea at scale: write tasks drawn from real use, run them, read the raw transcripts (the calls and the results, not only the final answer), and fix the descriptions and errors where the agent went wrong. Five tasks are enough to start. (Writing tools for agents)

原理

你能在哪裡插手

因為程式站在請求和動作之間，有兩個地方可以插手：

  • 工具執行之前。程式可以放行、拒絕或修改這次呼叫。通常的辦法是用 hook（Hooks：每次呼叫都會經過的執行點），而拒絕會附上一個原因，回到 agent 那裡。
  • 執行之後。程式可以在模型讀到結果之前，縮短、過濾或補充它。

這是能對 agent 執行規則的主要原因。放在程式裡的規則，是會執行的程式碼；寫在 prompt 裡的規則，是請求（提示裡的規則只是請求）。

這一章其餘的部分，講這趟來回的中間：模型看到什麼，拿回什麼。兩者都是你寫的文字。

工具是給不可靠使用者的介面

人在用命令列時，可以讀文件、問同事，也會注意到哪裡看起來不對。模型有的只是工具的名字、一段簡短的描述，和參數清單。就這樣。它可能猜錯，供應商的文件也這麼說：給它一個需要地點的工具，而請求裡沒有地點，模型可能會編一個。（Tool use overview）

所以替 agent 設計工具，是在為這樣的人設計：

  • 只讀名字和描述，來決定什麼時候用，
  • 靠從上下文猜來填參數，
  • 不知道工具沒告訴它的事，
  • 把結果當文字讀，結果占多少上下文視窗的空間，就占多少。

Anthropic 寫給 agent 的工具的建議，用別的話說了一樣的事：「就算只是把工具描述稍微改好，也能帶來很大的進步。」（Writing tools for agents）下面的五條規則由此而來。

1. 描述要寫得像給新同事的交辦單

寫清楚這個工具做什麼、什麼時候用、什麼時候不用。名字不要有歧義：叫 user 的參數，可能是名字、ID 或 email；叫 user_email 就不會。如果兩個工具看起來很像，在每一個裡都說明它哪裡不同。模型只能在描述裡學到這些，所以含糊的描述，就是工具被用錯，或從來沒被用到。

2. 錯誤訊息要寫給 agent 讀

人看到堆疊追蹤會思考。模型拿到文字就繼續。如果錯誤訊息是 Error 400，模型就會猜，常常又猜同一件事。如果錯誤訊息寫了哪裡錯、接著可以試什麼，它就會修好這次呼叫。

拒絕也一樣：寫明該改做什麼（詢問不是限制）。

3. 輸出要短，而且能分頁

工具回傳的所有東西，都會放進上下文視窗（上下文是一份預算），而且之後每一輪都會再讀一遍（選模型：算的是每次成功的成本）。agent 只想要一行，工具卻回傳整個大檔案，就浪費 token，還可能把有用的東西擠出視窗。

所以結果要有合理的限制：預設的上限、要求某個範圍或下一頁的辦法、一個過濾條件。Anthropic 也描述過，讓 agent 在簡潔和詳細的回應之間選。而且工具很多的時候，把相關的工具用共同的名字前綴分組，能幫 agent 分辨它們。（Writing tools for agents）Claude Code 預設把工具回應限制在 25,000 個 token（這是我寫作時 Anthropic 的數字）。你截掉輸出的時候，要說出來，並告訴 agent 怎麼把查詢範圍縮小。（Writing tools for agents）

4. 工具少，選得更準

每個工具的名字、描述和參數，每次呼叫都會送給模型。工具越多，花的 token 越多，選錯的機會也越多，尤其是它們功能重疊的時候。偏好一小組明顯不同的工具，能合併的相關操作就合併成一個。（Writing tools for agents）

5. 固定的步驟，放進指令裡，不放進 prompt 裡

這是我最想強調的一條。有時一件工作，有些步驟永遠是同一個走法，而且有對有錯：為新任務建資料夾、複製檔案、算雜湊值、寫紀錄、寫回去之前檢查一切就緒。你可以在指令裡描述這些步驟，請 agent 照做。它大多數時候會照做。

或者你可以把它們寫成一次的指令：一個 agent 當工具執行的小程式。指令做這些步驟，自己檢查前置條件，回傳一個簡短的結果。在經過這個指令的路徑上，agent 沒辦法跳過一步，也寫不出錯的狀態，因為它根本沒有寫。

這適合不需要判斷的步驟。如果某一步需要 agent 決定什麼，就把那部分留給 agent，讓指令只做周圍固定的部分。我的 harness 就是這樣。一條命令列指令建立任務資料夾（工作的單位，見 管任務，不管對話）、抓檔案、算 diff、數檢查的次數，而模型只執行指令、讀答案。進度是個好例子：任務清單讀的是指令寫入的資料檔，不是 agent 手寫的 Markdown 筆記，因為手寫的進度會漏打勾、會出錯。結果每次都一樣，模型也不用把步驟做對。

兩個細節讓指令對 agent 友善：

  • 結果要說明接下來是什麼。指令的輸出告訴 agent 下一步做什麼，它就不用猜。
  • 給人的是文字，給腳本的是 JSON。同一個指令，在終端機裡印出對齊的文字，透過管線接出去時印出 JSON。欄位是一樣的。

指令只有在 agent 真的用它的時候才有幫助，而且它只守得住經過它的東西。如果 agent 能用別的辦法做同一件事（手動改檔案），指令就只是方便，不是限制。提示裡的規則只是請求 把這一點講得更深。

測你自己的設定

對你給 agent 的任何工具，問三個問題：

  1. 如果只讀它的名字和描述，你知道什麼時候該用、什麼時候不該用嗎？
  2. 它失敗的時候，訊息有沒有告訴 agent 接下來做什麼？
  3. 它的輸出最大可以多大？大的時候，上下文會怎樣？

一個不用安裝任何東西的實驗。請 agent 用一個你知道是錯的方式，呼叫你的某個工具，讀回來的是什麼。如果你是 agent，這個訊息夠不夠清楚，讓你知道該做什麼？如果不夠，那就是要重寫的訊息。

更大的迴圈，如果你自己做工具。Anthropic 的方法是同一個想法放大：寫出取材自真實使用的任務，執行它們，讀原始的紀錄（呼叫和結果，不只是最後的答案），並在 agent 出錯的地方修好描述和錯誤訊息。五個任務就夠開始。（Writing tools for agents）

Costs and traps

Good descriptions cost tokens, too. A long description is sent on every call. Write what the model needs to choose and use the tool, and put the long manual in a file the agent reads when needed.

A command is code to maintain. If your project changes, the command can be wrong in a way a prompt cannot. Keep each one small, and give it a test.

A tool call is not a trusted act. The model chose the arguments, after reading text that may have come from anywhere. Do not treat a call as the user's wish. Chapter 4.6 explains why.

Tool names change between versions. If your rules or hooks match on tool names, keep the mapping in one place so a rename means one change.

代價和陷阱

好的描述也要花 token。長的描述每次呼叫都會送出去。寫模型選工具和用工具需要的就好，長的手冊放在 agent 需要時才讀的檔案裡。

指令是要維護的程式碼。專案變了，指令可能出錯，而 prompt 不會這樣。每個指令都保持小，並給它一個測試。

工具呼叫不是可信的行為。參數是模型選的，而且是讀了可能來自任何地方的文字之後選的。別把一次呼叫當成使用者的意願。agent 讀到的文字可能在指揮它 說明了原因。

工具名稱會隨版本改變。如果你的規則或 hook 靠工具名稱比對，把對應關係放在一個地方，改名時就只要改一處。

What the industry says Industry practice

  • Anthropic: tool design is part of the work, and descriptions and error messages deserve testing like code. (Writing tools for agents)
  • Tool use documentation: the application runs client tools and sends back results; the model "might guess values you didn't supply". (Tool use overview)

They agree with the argument here: the tool is an interface, and its text is part of the interface.

業界怎麼說 業界做法

  • Anthropic：工具設計是工作的一部分，描述和錯誤訊息值得像程式碼一樣測試。（Writing tools for agents）
  • Tool use 文件：應用程式執行 client tool 並送回結果；模型「可能會猜出你沒有提供的值」。（Tool use overview）

它們和這裡的論點一致：工具是介面，它的文字是介面的一部分。

When to delete it Industry practice

A command that checks preconditions is scaffolding around the model's weak spots. If models become reliable enough at following multi-step instructions, a command may no longer beat a good prompt, but I would still keep commands for anything that has to be exactly the same every time, or that needs a record. The reasoning on descriptions and errors stays as long as the model reads text.

什麼時候可以刪掉 業界做法

檢查前置條件的指令，是圍繞模型弱點搭的鷹架。如果模型在照著多步驟的指令做事上變得夠可靠，指令可能不再勝過一個好的 prompt，但凡是每次都必須完全一樣、或需要留紀錄的事，我仍然會保留指令。只要模型還是讀文字，關於描述和錯誤訊息的道理就還在。

Copilot Harness is my open-source harness for VS Code Copilot.

Repository: https://github.com/Smars-Bin-Hu/copilot-agentic-harness

Get started: clone it, open it in VS Code, and type /harness-rookie-get-me-ready in Copilot Chat. You need Python 3.9 or later and git.

Copilot Harness 是我開源的 VS Code Copilot harness。

倉庫: https://github.com/Smars-Bin-Hu/copilot-agentic-harness

開始：clone 下來，用 VS Code 打開，在 Copilot Chat 裡輸入 /harness-rookie-get-me-ready。需要 Python 3.9 以上和 git。

Explore it in the harness

My harness gives the agent a command line for the steps that must be certain, and a hook that stands at the door of every tool call. The harness can show you both from the inside, with the real files. After the setup above, type:

/harness-rookie-wondering I have read the chapter "Tool calling, and designing tools for an agent". Teach me what tools this harness gives the agent: the built-in ones, and its command line. Open the real files with me, show me a refusal and its reason, and draw how one tool call travels.

It teaches one small piece at a time, stops to ask if you are following, and opens the files with you.

在 harness 裡探索

我的 harness 給 agent 一個命令列，處理那些必須確定的步驟；還有一個 hook，站在每次工具呼叫的門口。harness 可以從裡面把兩者都展示給你看，帶著真實的檔案。照上面的說明準備好之後，輸入：

/harness-rookie-wondering 我讀完了「Tool calling，和給 agent 設計工具」這一章。請教我這個 harness 給 agent 哪些工具：內建的，和它的命令列。帶我打開真實的檔案，讓我看一次拒絕和它的原因，並畫出一次工具呼叫是怎麼走的。

它一次教一小塊，停下來確認你跟得上，然後和你一起打開檔案。
