Tool calling, and designing tools for an agentTool calling，和給 agent 設計工具Tool calling，以及怎么给 agent 设计工具

This chapter assumes you know that an AI coding agent can read files and run commands. You do not need to know how.

讀這一章，只需要知道寫程式的 AI agent 能讀檔案、執行指令。怎麼做到的，不用知道。

读这一章，只需要知道写代码的 AI agent 能读文件、跑命令。不需要知道它是怎么做到的。

The Knowledge經驗分享经验分享

In one sentence

A model only asks for a tool call, while the program around it runs the tool. So a tool is an interface for an unreliable user, and its description and error messages decide whether it is used well.

一句話

模型只是要求呼叫工具，真正執行工具的，是它周圍的程式。所以工具是給一個不可靠的使用者用的介面，它的描述和錯誤訊息，決定它能不能被用好。

一句话

模型只负责提出工具调用，真正运行工具的是它外面的程序。所以工具是给一个不可靠的用户用的接口，它的描述和报错信息，决定了它能不能被用好。

For leaders

  • The decision: treat the tools you give an agent as a product that needs a good description and good error messages, and decide which fixed steps go into a command rather than a prompt.
  • The risk: the model can only guess from a tool's name and description, so a vague tool gets used wrongly or not at all. A rule written in a prompt is a request, while a step done by a command cannot be skipped on that path.
  • The cost of doing it right: rewriting descriptions and error messages costs little. A command is code, and someone has to maintain it. Anthropic suggests five real tasks are enough to start testing tools.
  • Ask the team: "If you read only the name and description of each tool, would you know when to use it? What does its error say?"

給主管

  • 要做的決定：把你給 agent 的工具當成產品來看待，它需要好的描述和好的錯誤訊息；還要決定哪些固定的步驟交給指令（command），而不是寫進 prompt。
  • 風險：模型只能從工具的名字和描述去猜，所以含糊的工具會被用錯，或者根本沒人用。寫在 prompt 裡的規則是請求，而由指令完成的步驟，在那條路徑上是跳不過去的。
  • 做對的成本：重寫描述和錯誤訊息，花不了多少。指令是程式碼，就得有人維護。Anthropic 建議，有五個真實的任務，就夠開始測試工具了。
  • 可以問團隊：「如果只讀每個工具的名字和描述，你知道什麼時候該用它嗎？它的錯誤訊息說了什麼？」

写给管理者

  • 要拍板的事：把你给 agent 的工具当成产品来对待，它需要好的描述和好的报错信息；还要决定哪些固定的步骤交给命令，而不是写进 prompt。
  • 风险：模型只能根据工具的名字和描述去猜，所以含糊的工具会被用错，或者干脆没人用。写在 prompt 里的规则是请求，而由命令完成的步骤，在这条路径上是跳不过去的。
  • 做对的代价：重写描述和报错信息，花不了多少。命令是代码，就得有人维护。Anthropic 建议，有五个真实的任务就足够开始测试工具了。
  • 可以问团队：“如果只看每个工具的名字和描述，你能知道什么时候该用它吗？它的报错信息又是怎么说的？”

Who actually runs the tool?

When you watch an agent edit a file, it looks as if the model did it. It did not. A language model is a program that takes in text and produces text, so on its own it cannot open a file, run a command or send a request. It has no hands.

What it can do is write a sentence that means "please call the tool read_file with the path src/app.py". That sentence is a tool call: the model's request to use a tool, along with the arguments it chose. A tool here means one action the agent may ask for, such as reading a file, searching, editing a file, running a command or fetching a web page. The program around the model (the harness, in the first sense from chapter 0.1) reads the sentence and does the work, then puts what came back into the conversation as more text. The model reads that text, the tool result, to decide what to do next.

This looks like a technical detail, but it changes how you should think about tools. Every action an agent takes passes through a call that the program could inspect, refuse or change. And the model is not a careful programmer calling a function. It is a reader guessing from a description, so treat it like a user who skims.

One round trip

The provider's own documentation describes the same round trip. The model answers with a stop reason of tool_use and a block that names the tool and its arguments. Your code then runs the tool and sends back a tool_result. (Tool use overview)

There is one exception worth knowing. Some server tools, such as web search, run on the provider's side, so you never handle the call yourself. Most of what an agent in your editor does, though, goes through client tools, which run on your machine. The difference matters for this chapter, because with a server tool you cannot step in before or after it runs. The program never sees the call.

工具到底是誰在執行？

看 agent 改檔案的時候，你會覺得是模型改的。其實不是。語言模型是一個吃進文字、吐出文字的程式，光靠它自己，打不開檔案、執行不了指令，也送不出請求。它沒有手。

它能做的，是寫出一句話，意思是「請用路徑 src/app.py 呼叫工具 read_file」。這句話就是一次工具呼叫：模型要求使用某個工具，並附上它選好的參數。所謂工具，就是 agent 可以要求的一個動作，例如讀檔案、搜尋、改檔案、執行指令、抓一個網頁。模型周圍的程式（也就是差距在模型外面裡第一種意思的 harness）讀到這句話，把事情做完，再把拿回來的東西變成文字，接著放進對話裡。這段文字就是工具結果，模型讀了它，再決定下一步。

這看起來是個技術細節，卻會改變你看待工具的方式。agent 做的每個動作，都要經過一次呼叫，而程式可以檢查、拒絕或修改這次呼叫。而且模型也不是在呼叫函式的謹慎程式設計師，它是根據描述去猜的讀者，所以要把它當成一個只會快速瀏覽的使用者。

一次來回

供應商自己的文件，描述的也是這樣一個來回。模型回答時帶著停止原因 tool_use，以及一個寫出工具名和參數的區塊，你的程式執行這個工具，再送回 tool_result。（Tool use overview）

有一個例外值得知道。有些 server tool（例如網頁搜尋）是在供應商那邊執行的，所以你自己永遠碰不到那次呼叫；而你編輯器裡的 agent 做的大部分事，用的都是在你機器上執行的 client tool。這個差別對這一章很重要，因為遇到 server tool，你沒辦法在它執行之前或之後插手，程式根本看不到那次呼叫。

工具到底是谁在运行？

看着 agent 改文件，你会觉得是模型改的。其实不是。语言模型是一个读入文本、产出文本的程序，单靠它自己，打不开文件，运行不了命令，也发不出请求。它没有手。

它能做的，是写出一句话，意思是“请调用工具 read_file，路径是 src/app.py”。这句话就是一次工具调用：模型请求使用某个工具，并附上它选好的参数。所谓工具，就是 agent 可以要求做的一个动作，比如读文件、搜索、改文件、运行命令、抓取网页。模型外面的程序（也就是差距在模型外面里第一种意思的 harness）读到这句话，把事情做完，再把拿回来的东西变成文本，接着添进对话里。这段文本就是工具结果，模型读了它，再决定下一步做什么。

这看起来像个技术细节，却会改变你看待工具的方式。agent 的每个动作都要经过一次调用，而程序可以检查、拒绝或修改这次调用。而且模型也不是一个认真的程序员在调用函数，它是一个靠描述来猜的读者，所以要把它当成一个只会扫一眼的用户。

一次来回

模型提供方自己的文档，讲的也是这样一个来回。模型回复时，停止原因是 tool_use，并带着一个写明工具名和参数的块，你的代码运行这个工具，再送回一个 tool_result。（Tool use overview）

有一个例外值得知道。有些服务端工具，比如网页搜索，是在提供方那边运行的，所以你从头到尾碰不到这次调用；而你编辑器里的 agent 做的大部分事，用的都是在你机器上运行的客户端工具。这个区别对本章很要紧，因为碰上服务端工具，你没法在它运行之前或之后插手，程序根本看不到这次调用。

Where you can step in, and what to write for the model

Where you can step in

With a client tool, the program sits between the request and the action, which gives it two places to step in. Before the tool runs, it can let the call through, refuse it or change it. The usual way to do that is a hook (chapter 2.2). When a hook refuses, the reason it gives goes back to the agent. After the tool runs, the program can shorten, filter or add to the result before the model reads it.

That is the main reason it is possible to enforce rules on an agent at all. A rule that lives in the program is code that runs, whereas a rule in a prompt is a request (chapter 4.1).

But a hook can only judge a call the model has already made. Whether the model makes a good call in the first place depends on the middle of the trip, on what it sees before it calls and what it gets back afterwards, and both of those are text you write.

A tool is an interface for an unreliable user

Think about what each side has to go on. A person using a command line can read documentation, ask a colleague, and notice that something looks wrong. The model has the tool's name, a short description and the list of parameters, and nothing more. So it can guess wrongly, and the provider's documentation says as much: given a tool that needs a location and a request that does not give one, a model might make one up. (Tool use overview)

Designing a tool for an agent, then, means designing for a user who decides when to use it from the name and description alone, and who fills in the arguments by guessing from context. It does not know anything the tool does not tell it, and it reads the result as plain text, however much room that takes in the context window.

Anthropic's advice on writing tools for agents makes the same point in other words: "Even small refinements to tool descriptions can yield dramatic improvements." (Writing tools for agents) The five rules below follow from it, and they come roughly in the order a call meets them.

1. Write the description like a brief for a new hire

Before any call, the description is the only place the model learns what a tool is for, so it has to say what the tool does, when to use it, and when not to. A vague one means the tool is used wrongly or never. Names need the same care, because a parameter called user can mean a name, an ID or an email, while user_email can mean only one thing. And if two tools look alike, each description should say how it differs from the other.

2. Write errors for the agent to read

When a call goes wrong, the next thing the model reads is the error. A person can look at a stack trace and stop to think, but a model takes the text it is given and goes on. If the error is Error 400, the model guesses, often the same thing again. If the error says what was wrong and what to try next, it fixes the call.

The same goes for a refusal, which should say what to do instead (chapter 4.2).

3. Keep the output short, and let it be paged

When the call works, what the model reads is the output. Everything a tool returns goes into the context window (chapter 3.1), and it is read again on every later turn (chapter 1.1). So a tool that returns a whole large file when the agent wanted one line not only wastes tokens but can also crowd useful things out of the window.

The fix is to give results sensible limits, such as a default cap, a way to ask for a range or the next page, or a filter. Anthropic also describes letting the agent choose between a concise and a detailed response. When there are many tools, grouping related ones under a common name prefix helps the agent tell them apart. (Writing tools for agents)

For a sense of scale, Claude Code caps tool responses at 25,000 tokens by default (Anthropic's figure at the time of writing). Whatever the cap, when you cut the output, say so, and tell the agent how to narrow its query. (Writing tools for agents)

4. Fewer tools choose better

So far each rule has been about one tool, but the number of tools matters too. You might think an extra tool does no harm when it is not used. It still costs something, because every tool's name, description and parameters are sent to the model on every call. More tools mean more tokens and more chances to pick the wrong one, especially when they overlap. So prefer a small set of clearly different tools, and merge related operations into one where you can. (Writing tools for agents)

5. Do the fixed steps in a command, not in a prompt

The first four rules are about tools you already have. The last is about which work should become a tool at all, and it is the one I would stress most. Some jobs have steps that always go the same way and where there is a right and a wrong: make the folder for a new task, copy the files, compute a hash, write the record, check that everything is ready before writing back. You can describe those steps in the instructions and ask the agent to follow them, and it will, most of the time.

Or you can write them once as a command, a small program the agent runs as a tool. The command does the steps, checks the preconditions itself and returns a short result. On the path through the command, the agent cannot skip a step or write a wrong state, because it never writes the state at all.

The fit is for steps that need no judgment. If a step needs the agent to decide something, leave that part to the agent and let the command do only the fixed work around it. This is what my harness does. A command line creates a task folder (the unit of work in Manage tasks, not chats), fetches files, works out diffs and counts checks, and the model only runs the command and reads the answer. The result is the same every time, and the model never has to get the steps right. Progress is a good example of why: the task list reads a data file that commands write, not the Markdown notes an agent wrote by hand, because hand-written progress misses ticks and goes wrong.

A command is also friendlier to an agent when its output says what to do next, because then the agent does not have to guess. And since the same command is read by people in a terminal and by scripts through a pipe, it can print aligned text for the first and JSON for the second, with the same fields in both.

A command has limits of its own, though. It only helps if the agent actually uses it, and it only guards what goes through it. If the agent can do the same thing another way, say by editing the file by hand, the command is a convenience, not a limit. Chapter 4.1 takes that further.

How to check your own tools

You can start with three questions about any tool you give an agent.

  1. If you read only its name and description, would you know when to use it and when not to?
  2. When it fails, does the message tell the agent what to do next?
  3. How big can its output be, and what happens to the context if it is large?

The quickest experiment needs nothing installed. Ask the agent to call one of your tools in a way that you know is wrong, and read what comes back. If you were the agent, would it be clear enough to tell you what to do? If not, that is the message to rewrite.

If you build tools, Anthropic's method is the same idea at scale. Write tasks drawn from real use, run them, read the raw transcripts (the calls and the results, not only the final answer), and fix the descriptions and errors where the agent went wrong. Five tasks are enough to start. (Writing tools for agents)

能在哪裡插手，又該給模型寫些什麼

你能在哪裡插手

用 client tool 的時候，程式站在請求和動作之間，所以有兩個地方可以插手。工具執行之前，程式可以放行這次呼叫、拒絕它，或者修改它。通常的辦法是用 hook（見Hooks：每次呼叫都會經過的執行點），hook 拒絕時給的原因，會回到 agent 那裡。工具執行之後，程式還可以在模型讀到結果之前，把結果縮短、過濾或補充。

這就是能對 agent 強制執行規則的主要原因。放在程式裡的規則是會執行的程式碼，而寫在 prompt 裡的規則是請求（見提示裡的規則只是請求）。

不過，hook 只能判斷模型已經送出的呼叫。模型一開始能不能把呼叫送對，要看這趟來回的中間：呼叫之前它看到什麼，呼叫之後它拿回什麼。而這兩樣，恰恰都是你寫的文字。

工具是給不可靠使用者的介面

先看看兩邊各有什麼可以依靠。人在用命令列時，可以讀文件、問同事，也會注意到哪裡看起來不對。模型手上只有工具的名字、一段簡短的描述和參數清單，除此之外什麼都沒有。所以它可能猜錯，供應商的文件也這麼說：如果一個工具需要地點，而請求裡沒有給，模型可能會自己編一個。（Tool use overview）

這樣看來，替 agent 設計工具，就是在為這樣一個使用者設計。它只憑名字和描述決定什麼時候用，參數則靠上下文去猜。工具沒告訴它的事，它一概不知道；回傳的結果，它也都當成普通的文字來讀，結果有多大，就占掉多少上下文視窗。

Anthropic 談怎麼替 agent 寫工具的那篇建議，換個說法講的也是這件事：「就算只是把工具描述稍微改好，也能帶來很大的進步。」（Writing tools for agents）下面的五條規則都由此而來，大致照一次呼叫經過的順序排。

1. 描述要寫得像給新同事的交辦單

呼叫之前，描述是模型了解一個工具用途的唯一地方，所以它得寫清楚這個工具做什麼、什麼時候用、什麼時候不用。描述含糊，工具就會被用錯，或者從來沒被用到。名字也一樣要講究。例如一個叫 user 的參數，可能是名字、ID，也可能是 email，而 user_email 只可能是一種意思。還有，如果兩個工具看起來很像，每個工具的描述裡都要說清楚它和另一個哪裡不同。

2. 錯誤訊息要寫給 agent 讀

呼叫出了錯，模型接下來讀到的就是錯誤訊息。人看到堆疊追蹤，會停下來想一想，模型卻是拿到文字就繼續往下走。如果錯誤訊息是 Error 400，模型就只能猜，常常又猜回同一個錯的值。如果錯誤訊息寫了哪裡錯、接著可以試什麼，它就能把這次呼叫修好。

拒絕也一樣，要寫明該改做什麼（見詢問不是限制）。

3. 輸出要短，而且能分頁

呼叫成功了，模型讀到的是輸出。工具回傳的所有東西，都會放進上下文視窗（見上下文是一份預算），而且之後每一輪都會再讀一遍（見選模型：算的是每次成功的成本）。所以，如果 agent 只想要一行，工具卻回傳整個大檔案，不只浪費 token，還可能把有用的東西擠出視窗。

辦法是給結果合理的限制，例如預設的上限、要求某個範圍或下一頁的辦法，或者一個過濾條件。Anthropic 也描述過，讓 agent 在簡潔和詳細的回應之間選。工具很多的時候，把相關的工具歸到共同的名字前綴底下，能幫 agent 分辨它們。（Writing tools for agents）

具體到數字，Claude Code 預設把工具回應限制在 25,000 個 token（這是我寫作時 Anthropic 的數字）。不管上限訂在哪裡，你截掉輸出的時候都要說出來，並告訴 agent 怎麼把查詢範圍縮小。（Writing tools for agents）

4. 工具少，選得更準

前面幾條講的都是單一工具，但工具的數量也有講究。你也許覺得多一個工具，不用就沒壞處。其實它照樣有成本，因為每個工具的名字、描述和參數，每次呼叫都會送給模型。工具越多，花的 token 越多，選錯的機會也越多，功能重疊的時候尤其如此。所以盡量用一小組明顯不同的工具，能合併的相關操作，就合併成一個。（Writing tools for agents）

5. 固定的步驟，放進指令裡，不放進 prompt 裡

前四條講的是已有的工具，最後這一條講的是哪些工作該做成工具，也是我最想強調的一條。有些工作裡的步驟，永遠是同一個走法，而且有對有錯：為新任務建資料夾、複製檔案、算雜湊值、寫紀錄、寫回去之前檢查一切就緒。你可以把這些步驟寫成指令檔裡的指示，請 agent 照著做，它大多數時候也會照做。

你也可以不靠指示，把它們一次寫成一個指令（command），也就是 agent 當工具執行的一個小程式。指令自己完成這些步驟，自己檢查前置條件，最後回傳一個簡短的結果。在經過這個指令的路徑上，agent 沒辦法跳過任何一步，也寫不出錯的狀態，因為狀態根本不是它寫的。

這適合不需要判斷的步驟。如果某一步需要 agent 拿主意，就把那部分留給它，讓指令只做周圍那些固定的事。我的 harness 就是這樣做的。一條命令列指令負責建立任務資料夾（任務是管任務，不管對話裡講的工作單位）、抓檔案、算 diff、數檢查的次數，模型只要執行指令、讀答案就好。這樣一來，結果每次都一樣，模型也從來不用自己把步驟做對。為什麼要這樣，進度是個好例子：任務清單讀的是指令寫入的資料檔，不是 agent 手寫的 Markdown 筆記，因為手寫的進度會漏打勾，也會出錯。

指令的輸出如果能說明下一步做什麼，對 agent 就更友善，因為它不用猜。而同一個指令，既有人在終端機裡看，也有腳本透過管線讀，所以它可以在終端機裡印出對齊的文字，接到管線上時印出 JSON，兩種輸出的欄位是一樣的。

不過，指令也有自己的限度。agent 真的去用它，它才幫得上忙，而且它只守得住經過它的東西。如果 agent 能用別的辦法做同一件事，例如手動改檔案，這個指令就只是圖個方便，算不上限制。提示裡的規則只是請求會把這一點講得更深。

怎麼檢查你自己的工具

對你給 agent 的任何一個工具，都可以先問三個問題。

  1. 如果只讀它的名字和描述，你知道什麼時候該用、什麼時候不該用嗎？
  2. 它失敗的時候，訊息有沒有告訴 agent 接下來做什麼？
  3. 它的輸出最大可以多大？大的時候，上下文會怎樣？

最快的實驗什麼都不用裝。請 agent 用一個你明知不對的方式呼叫你的某個工具，看看回來的是什麼。假如你就是那個 agent，這個訊息夠不夠清楚，能讓你知道該做什麼？如果不夠，要重寫的就是這個訊息。

如果你自己做工具，Anthropic 的方法就是同一個想法放大。根據真實的使用情況寫出任務，執行它們，讀原始的紀錄（呼叫和結果，不只是最後的答案），然後在 agent 出錯的地方修好描述和錯誤訊息。五個任務就夠開始。（Writing tools for agents）

能在哪里插手，又该给模型写些什么

你能在哪里插手

用客户端工具的时候，程序夹在请求和动作之间，所以有两个地方可以插手。工具运行之前，程序可以放行这次调用、拒绝它，或者修改它。常用的办法是 hook（见Hook：每次调用都会经过的执行点），hook 拒绝时给出的原因，会送回给 agent。工具运行之后，程序还可以在模型读到结果之前，把结果精简、过滤或补充一下。

这就是能对 agent 强制执行规则的主要原因。放在程序里的规则是会运行的代码，而写在 prompt 里的规则是请求（见提示里的规则只是请求）。

不过，hook 只能对模型已经发出的调用做判断。模型一开始能不能把调用发对，取决于这趟来回的中间：调用之前它看到什么，调用之后它拿回什么。而这两样，恰恰都是你写的文本。

工具是给不可靠用户的接口

先看看两边各有什么可依靠的。人用命令行，可以看文档、问同事，还能察觉到哪里不对劲。模型手里只有工具的名字、一段简短的描述和参数列表，别的什么都没有。所以它会猜错，提供方的文档也这么说：如果一个工具需要地点，而请求里没给，模型可能会自己编一个。（Tool use overview）

这样看来，给 agent 设计工具，就是在给这样一个用户设计。它只凭名字和描述决定什么时候用，参数则靠上下文去猜。工具没告诉它的事，它一概不知道；返回的结果，它也都当成普通文本来读，结果有多大，就占掉多少上下文窗口。

Anthropic 关于给 agent 写工具的建议，换了个说法讲的也是这件事：“哪怕对工具描述做很小的改进，也能带来显著的提升。”（Writing tools for agents）下面五条规则都由此而来，大致按一次调用经过的顺序排。

1. 把描述写得像给新员工的交接说明

调用之前，描述是模型了解一个工具用途的唯一地方，所以它得说清楚这个工具做什么、什么时候用、什么时候不用。描述含糊，工具就会被用错，或者没人用。名字也一样要讲究。比如一个叫 user 的参数，可能是名字、ID，也可能是邮箱，而 user_email 只可能是一种意思。还有，如果两个工具看起来很像，每个工具的描述里都要说清它和另一个有什么不同。

2. 报错信息要写给 agent 看

调用出了错，模型接下来读到的就是报错。人看到堆栈，会停下来想一想，模型却是拿到文本就接着往下走。如果报错是 Error 400，模型就只能猜，往往又猜回同一个错的值。如果报错说明了哪里不对、接下来该试什么，它就能把调用改对。

拒绝也一样，要说明应该改做什么（见询问不是限制）。

3. 输出要短，还要能分页

调用成功了，模型读到的是输出。工具返回的所有东西都会放进上下文窗口（见上下文是一份预算），而且之后每一轮都要再读一遍（见选模型：看每次成功的成本）。所以，如果 agent 只想要一行，工具却把一个很大的文件整个返回，不光浪费 token，还可能把有用的东西挤出窗口。

办法是给结果设合理的限制，比如默认的上限、取某个范围或下一页的办法，或者一个过滤器。Anthropic 还提到，可以让 agent 在简洁回复和详细回复之间选。工具很多的时候，把相关的工具归到同一个名字前缀下，能帮 agent 把它们分清楚。（Writing tools for agents）

具体到数字，Claude Code 默认把工具的响应限制在 25,000 个 token 以内（这是我写作时 Anthropic 给出的数字）。不管上限定在哪里，截短输出时都要说一声，并告诉 agent 怎么缩小查询范围。（Writing tools for agents）

4. 工具少，选得更准

前面几条讲的都是单个工具，可工具的数量也有讲究。你也许觉得多一个工具，不用就没坏处。其实它照样有成本，因为每个工具的名字、描述和参数，每次调用都要发给模型。工具越多，token 花得越多，选错的机会也越多，功能重叠的时候尤其如此。所以优先用一小组明显不同的工具，能把相关的操作合并成一个，就合并。（Writing tools for agents）

5. 固定的步骤写进命令，不写进 prompt

前四条讲的是已有的工具，最后这一条讲的是哪些活该做成工具，也是我最想强调的一条。有些活儿里的步骤每次都一样，而且有对错之分：给新任务建文件夹、复制文件、算一个哈希、写入记录、写回之前检查一切就绪。你可以把这些步骤写进指令，让 agent 照着做，它大多数时候也会照做。

你也可以把它们一次性写成一个命令，也就是 agent 当作工具来运行的一个小程序。命令自己完成这些步骤，自己检查前置条件，最后返回一个简短的结果。走命令这条路径时，agent 跳不过任何一步，也写不出错误的状态，因为状态根本不是它写的。

这适合不需要判断的步骤。如果某一步需要 agent 拿主意，就把那部分留给它，让命令只做周围那些固定的事。我的 harness 就是这么做的。一个命令行工具负责建任务文件夹（任务是管任务，不管对话里讲的工作单元）、取文件、算 diff、统计检查，模型只要运行命令、读结果就行。这样一来，结果每次都一样，模型也从来不必自己把步骤做对。为什么要这样，进度是个好例子：任务清单读的是命令写入的数据文件，而不是 agent 手写的 Markdown 笔记，因为手写的进度会漏打勾，也会出错。

命令的输出如果能说明下一步做什么，对 agent 就更友好，因为它不用去猜。而同一个命令，既有人在终端里看，也有脚本通过管道读，所以它可以在终端里打印对齐的文本，接到管道上时打印 JSON，两种输出的字段是一样的。

不过，命令也有自己的局限。agent 真去用它，它才帮得上忙，而且它只守得住经过它的东西。如果 agent 能用别的办法做同样的事，比如手动改文件，这个命令就只是图个方便，算不上限制。提示里的规则只是请求会接着往下讲这一点。

怎么检查你自己的工具

对你给 agent 的任何一个工具，都可以先问三个问题。

  1. 只看它的名字和描述，你知道什么时候该用、什么时候不该用吗？
  2. 它失败的时候，信息有没有告诉 agent 接下来做什么？
  3. 它的输出最大能有多大？如果很大，上下文会怎么样？

最快的实验什么都不用装。让 agent 用一种你明知不对的方式调用你的某个工具，看看返回了什么。假如你就是那个 agent，这条信息够不够清楚，能让你知道该怎么办？如果不够，要重写的就是这条信息。

如果你自己做工具，Anthropic 的方法就是同一个想法的放大版。根据真实的使用场景写出任务，运行它们，读原始的记录（调用和结果，不只是最终答案），然后在 agent 出错的地方修改描述和报错信息。五个任务就够开始了。（Writing tools for agents）

What good tools cost, and where they go wrong

None of this comes free. Even a good description costs tokens, because a long one is sent on every call. So write what the model needs to choose and use the tool, and put the long manual in a file the agent reads when needed.

A command costs something different, because it is code to maintain. When your project changes, the command can be wrong in a way a prompt cannot, so keep each one small and give it a test.

Cost is not the only way tools go wrong. A tool call is not a trusted act, because the model chose the arguments after reading text that may have come from anywhere. Do not treat a call as the user's wish. Chapter 4.6 explains why.

One last, practical trap: tool names change between versions. If your rules or hooks match on tool names, keep the mapping in one place, so that a rename means one change.

好工具要付出什麼，又會在哪裡出錯

這些做法都不是免費的。描述寫得再好，也要花 token，因為長的描述每次呼叫都會送出去。所以，只寫模型選工具、用工具需要的內容就好，長的手冊放進檔案裡，讓 agent 需要時才讀。

指令的代價不一樣，因為它是要維護的程式碼。專案一變，指令就可能出錯，而且是 prompt 不會有的那種錯，所以每個指令都要保持小，並給它一個測試。

不過，工具會出問題的地方，不只是代價。工具呼叫不能當成可信的舉動，因為參數是模型選的，而它選之前讀到的文字，可能來自任何地方。別把一次呼叫當成使用者的意願，agent 讀到的文字可能在指揮它說明了原因。

最後還有一個很實際的陷阱：工具名稱會隨版本改變。如果你的規則或 hook 靠工具名稱比對，就把這份對應關係放在一個地方，這樣改名時只要改一處。

好工具要付出什么，又会在哪里出错

这些做法都不是免费的。描述写得再好，也要花 token，因为长描述每次调用都要发一遍。所以，只写模型选择和使用这个工具所需要的内容，长的说明书放进文件里，让 agent 需要时再读。

命令的代价不一样，因为它是要维护的代码。项目一变，命令就可能出错，而且是 prompt 不会有的那种错，所以每个命令都要保持小，并且给它写测试。

不过，工具会出问题的地方，不只是代价。工具调用不能当成可信的举动，因为参数是模型选的，而它选之前读到的文本，可能来自任何地方。别把一次调用当成用户的意愿，agent 读到的文字可能在指挥它解释了为什么。

最后还有一个很实际的坑：工具名在不同版本之间会变。如果你的规则或 hook 按工具名来匹配，就把这份对应关系放在一个地方，这样改名时只需改一处。

Does Anthropic see it the same way? Industry practice

The advice in this chapter rests on two sources, and both come from Anthropic. Its advice on writing tools treats tool design as part of the work, with descriptions and error messages that deserve testing like code (Writing tools for agents). Its tool use documentation says that the application runs client tools and sends back the results, and that the model "might guess values you didn't supply" (Tool use overview). Both agree with the argument here, that the tool is an interface and its text is part of the interface.

Anthropic 也這麼看嗎？ 業界做法

這一章的建議依據的是兩份資料，都出自 Anthropic。其中談怎麼寫工具的那一篇，把工具設計當成工作的一部分，認為描述和錯誤訊息值得像程式碼一樣測試（Writing tools for agents）。tool use 文件則說，client tool 由應用程式執行，再把結果送回去，還提醒說，模型「可能會猜出你沒有提供的值」（Tool use overview）。兩者都和這裡的論點一致：工具是介面，它的文字也是介面的一部分。

Anthropic 也这么看吗？ 业界做法

这一章的建议依据的是两份资料，都出自 Anthropic。其中讲怎么写工具的那篇，把工具设计当成工作的一部分，认为描述和报错信息值得像代码一样测试（Writing tools for agents）。工具使用文档则说，客户端工具由应用运行，再把结果送回去，还提醒说，模型“可能会猜出你没提供的值”（Tool use overview）。两者都和这里的论点一致：工具是一个接口，它的文本也是接口的一部分。

When to delete a command Industry practice

Of the advice above, the commands are the part most likely to age, because a command that checks preconditions is scaffolding around the model's weak spots. If models become reliable enough at following multi-step instructions, a command may no longer beat a good prompt. Even then, I would keep commands for anything that has to be exactly the same every time, or that needs a record. The reasoning about descriptions and errors is a different matter, since it holds for as long as the model reads text.

什麼時候可以刪掉指令 業界做法

上面這些建議裡，最可能過時的是指令，因為檢查前置條件的指令，是圍繞模型弱點搭起來的鷹架。如果模型在照著多步驟的指示做事上變得夠可靠，指令可能就不再勝過一個好的 prompt。就算到了那一天，凡是每次都必須完全一樣、或需要留下紀錄的事，我仍然會保留指令。描述和錯誤訊息的道理則是另一回事，只要模型還是讀文字，它就一直成立。

什么时候可以删掉命令 业界做法

上面这些建议里，最可能过时的是命令，因为检查前置条件的命令，是围着模型的弱点搭起来的脚手架。如果模型在遵循多步指令上变得足够可靠，命令也许就不再比一个好的 prompt 强。即便到了那一天，对那些每次都必须完全一样、或者需要留下记录的事，我还是会保留命令。描述和报错信息的道理则是另一回事，只要模型还在读文本，它就一直成立。
