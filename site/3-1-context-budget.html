3.1

Context is a budget上下文是一份預算为什么不能把所有规则都塞给 Agent？

This chapter assumes you have read The agent loop, or know that an agent reads text and answers with text.

讀這一章，請先讀過 agent 循環，和你能插手的地方，或至少知道 agent 讀文字、再用文字回答。

读这一章，请先读过 Agent 到底是怎么干活的？，或者至少知道 agent 读文本、再用文本回答。

The Knowledge經驗分享经验分享

In one sentence

Rules, knowledge, files and tool results all share one window, and each one crowds the others out. So manage context like a budget: fetch it when needed instead of loading it all.

一句話

規則、知識、檔案和工具結果共用同一個視窗，每一樣都會擠掉別的。所以要把上下文當預算來管：需要時再去取，不要一次全部載入。

一句话

规则、知识、文件和工具结果共用同一个窗口，每一样都在挤占其他几样的位置。所以要像管预算一样管上下文：需要时再取，不要一次全装进去。

For leaders

  • The decision: treat what the agent reads as a budget, and decide what is always loaded and what is fetched only when a task needs it.
  • The risk: everything shares one window, and having room left does not make a window perform well. A rule buried in a long, noisy context is more likely to be missed. I have no number for how much. The advice comes from the platform makers and my own design, not from a test of mine.
  • The cost of doing it right: mostly setup time, spent layering the rules, shortening tool output and keeping any index true. Loading too little has its own price, because then the agent guesses.
  • Ask the team: "What is loaded on every turn, and how much of it applies to the task in front of us?"

給主管

  • 要做的決定：把 agent 讀的東西當預算，決定什麼東西一直載入，什麼東西只在任務需要時才去取。
  • 風險：所有東西共用一個視窗，而視窗還有空位，並不代表表現就好。埋在又長又雜的上下文裡的規則，更容易被漏掉。漏掉的程度我沒有數字。這些建議來自平台廠商和我自己的設計，不是我做的測試。
  • 做對的成本：主要是設定的時間，花在把規則分層、縮短工具輸出、讓任何索引保持正確上。載入太少也有代價，因為那樣 agent 就只能用猜的。
  • 可以問團隊：「每一輪都載入了什麼？其中有多少和眼前的任務有關？」

写给管理者

  • 要拍板的事：把 agent 读到的内容当成预算，决定哪些每次都加载，哪些只在任务需要时才取。
  • 风险：所有内容共用一个窗口，而窗口还有空位，并不等于表现就好。埋在又长又杂的上下文里的规则，更容易被漏掉。漏掉多少，我没有数字。这条建议来自平台厂商和我自己的设计，不是我做过的测试。
  • 做对的代价：主要是配置的时间，花在给规则分层、缩短工具输出、让索引始终保持准确上。装得太少也有代价，因为那样 agent 就只能去猜。
  • 可以问团队：“每一轮都加载了什么？其中有多少和眼前这个任务有关？”

Why can more information make the answer worse?

When an answer comes back weak, the usual advice is "give the AI more information". So you paste the whole style guide, add every rule and let it read all the files. It feels safe, because more facts ought to mean fewer mistakes.

It often goes the other way. Think of a desk. You can lay out every document for a project on it, but then you cannot find the one you need, and there is no room left to write. The agent's version of that desk is called the context window: all the text the model can look at in one turn. The rules are on it, along with your words, the files the agent read, the results of its tool calls and its own earlier answers. The desk has a size limit. And, as I will show, it has a second limit that is not about size.

I did not run a clean experiment for this chapter, so what I can say comes from two other places. The first is the people who build these tools. Anthropic writes that context "must be treated as a finite resource with diminishing marginal returns" (Effective context engineering), and VS Code's guide says to "avoid context overload that can dilute focus" (Context engineering guide). The second is the way I built my own setup, where almost every design choice is a way to put less into the window. Cost points the same way: most of what a task costs is what the model reads (Models and cost). Before we get to the second limit, though, it helps to see what actually fills the window.

資訊給得越多，答案為什麼反而可能越差？

AI 回答得不好時，最常聽到的建議是「給它更多資訊」。於是你貼上整份風格指南，加上每一條規則，再讓它把所有檔案都讀一遍。這樣感覺很安全，畢竟事實越多，錯誤照理說就越少。

結果卻常常相反。不妨想想一張書桌。你當然可以把一個專案的所有文件都攤在上面，可是這樣一來，要用的那一份反而找不到，也沒有地方寫字了。agent 也有這麼一張書桌，叫做上下文視窗，也就是模型在一輪裡能看到的全部文字。桌上有規則，也有你說的話、agent 讀過的檔案、工具呼叫的結果，還有它自己之前的回答。這張桌子有大小的上限。而且我接下來會說，它還有第二個限制，跟大小無關。

這一章我沒有做過乾淨的實驗，所以我能說的，來自另外兩個地方。一個是做這些工具的人。Anthropic 寫道，上下文「必須被當成一種有限的資源，邊際報酬會遞減」（Effective context engineering），VS Code 的指南也說要「避免上下文過載而分散注意力」（Context engineering guide）。另一個是我自己搭設定的方式，裡面幾乎每個設計選擇，都是在想辦法讓視窗裡少放一點。從成本來看也是同一個方向：一個任務的成本，大部分花在模型讀的東西上（選模型：算的是每次成功的成本）。不過在談第二個限制之前，我們先看看視窗裡到底裝了什麼。

信息给得越多，答案为什么反而可能越差？

AI 答得不好时，最常听到的建议是“多给它点信息”。于是你把整份风格指南贴进去，把所有规则都加上，再让它把所有文件读一遍。这样做感觉很稳妥，毕竟事实越多，错误按理说就越少。

结果却往往相反。不妨想想一张书桌。你当然可以把一个项目的所有文档都摊在上面，可那样一来，要用的那一份就找不着了，也没地方写字了。agent 也有这么一张书桌，叫上下文窗口，也就是模型在一轮里能看到的全部文本。桌上放着规则，也放着你说的话、agent 读过的文件、工具调用的结果，以及它自己之前的回答。这张桌子有大小上限。而且我后面会讲到，它还有第二个上限，和大小无关。

这一章我没有做过干净的实验，所以我能说的，来自另外两个地方。一个是做这些工具的人。Anthropic 写道，上下文“必须当作一种有限的资源来对待，边际收益会递减”（Effective context engineering），VS Code 的指南也说要“避免上下文过载而分散注意力”（Context engineering guide）。另一个是我自己搭配置的方式，里面几乎每个设计选择，都是在想办法让窗口里少放一点。从成本上看也是同一个方向：一个任务的成本，大部分来自模型读的东西（选模型，别只看 token 单价）。不过在讲第二个上限之前，我们先看看窗口里到底装了什么。

What fills the window, and how to put less in it

What is in the window

Six things share the window:

  1. Rules and instructions that the platform puts in every time.
  2. The list of tools, with each tool's description. The model needs it to know what it can ask for, and with many tools, for example from several MCP servers (MCP), this list can be a large part of the window. I have not measured how large.
  3. Your messages.
  4. Files the agent read. A file goes in as whole text, however much of it matters.
  5. Tool results, such as search listings, command output and test logs. These are often the biggest part, and the part nobody looks at.
  6. The agent's own earlier answers.

Each turn of the loop adds one more result and takes nothing out, and the model reads all of it again (what that costs is in Models and cost). So the window only grows, until it is full. Then the platform has to cut or summarise the oldest parts, and details are lost. That is what Long chats get worse is about.

Two limits, not one

Then why not simply use a bigger window? Because running out of room is only the obvious limit. The second one is attention, and Anthropic describes it as an "attention budget" that the model draws on when it reads a lot of text. In practice this means that a window with room left is not the same as a window that performs well. A rule buried in a long, noisy context is more likely to be missed than the same rule in a short one.

I take this as a reason to put less in, even when it all fits, although that step is my own inference and not something Anthropic says. How big the effect is depends on the model and the task.

Load everything, load an index, or both

If less is better even when everything fits, the question becomes what to leave out. That choice sits behind most of the decisions in this part of the book.

The simplest answer is to leave nothing out, so that the agent starts with all the rules and all the notes in the window and never has to look anything up. The trouble is that the window is spent before work starts, most of it on things this task does not need.

The opposite answer is to load an index and fetch what the task needs. The agent starts with a short list of the things that exist, each with a name and a one-line description. When the task needs one of them, it opens that one. Anthropic calls this a "just in time" approach, in which the agent keeps lightweight identifiers (a file path, a name) and loads the data at run time. It works the way a library does, where nobody carries the whole library to a desk. You use the catalog, then fetch the one book.

Between those two ends, Anthropic's own suggestion is a mix. In their words, "the most effective agents might employ a hybrid strategy, retrieving some data up front for speed", and then explore further on their own. Their example is Claude Code, which drops its instruction file into the context up front and uses search tools to find the rest as it goes.

Loading everything still wins in some cases. For a small task, or a small set of rules, it is simpler and costs little. And where a missed fact is expensive, I would rather pay for it to be in the window than bet on the agent opening the right file.

Cost adds one more point in its favour. A beginning that is loaded every time and never changes can be cached, and a cache read is much cheaper than a normal read (Models and cost). So if the beginning stays stable, loading everything is cheaper than the token count suggests. I have not tested the cache on Copilot, though. And even a cache leaves the attention limit above untouched.

Whichever mix you choose, the index part only works if three things are true. First, the index entry has to say when to open the thing, because the agent decides from that one line alone. A vague line means it opens the wrong thing or never opens the right one, which is why the description of a skill matters so much (Instructions and skills). Second, the fetch has to be cheap and exact. If fetching means reading a whole folder, the index saved nothing. Third, the agent has to know that it does not know, because an index cannot help with a thing the agent does not realise is missing. That is the real risk, and I come back to it below.

Ways to read less

An index is only one way to keep the window small. Each of the ones I use below either keeps a thing out of the window or takes it out. If you want somewhere to start, the two cheapest are layering your rules and shortening tool output.

  • Rules by layers. Keep a small set of rules always loaded, and put the rest where they are read only for the files or the job they apply to. Rules that never change the next step are only noise. (How: Instructions and skills.)
  • Search first, then read. Ask the agent to find where something is, then read only that part of the file, not the whole file. Or give it a short map of the project written ahead of time, which is an index in the sense above. A map only wins if reading it beats searching, and it only stays true if someone keeps it true. I have not tested whether mine wins (A knowledge base from code).
  • Make tool output short. A command that prints 2,000 lines puts 2,000 lines in the window, so filter it, or print only the failures.
  • Remind with a few lines, not a page. In my setup, only a short piece of the rules is added to each prompt, and when there is a task (Manage tasks, not chats), it says how far the task has got. It is a reminder. The full text is read when it is needed.
  • Hand a big read to a subagent (Use subagents sparingly, Long chats get worse).
  • Write state into files, so a new chat reads one short file and not the old conversation. A new chat is an empty window. When to start one, and what to carry over, is in Long chats get worse.

Three questions and a test

How does your own setup spend its window? Three questions help answer that:

  1. What is loaded every time? Count the lines of your always-on rules, and ask how much of that applies to the task you are doing now. (In Claude Code, the /context command shows what is using the window. I have not checked what Copilot offers.)
  2. What was the biggest thing the agent read last time? Was it a file, or a log, and was all of it needed?
  3. If the agent started a new chat now, what would it have to read to carry on? Is that in a file?

There is also a test you can run today. Take a task you know the answer to and run it twice, in a new chat each time. In the first run, paste the whole file or doc into the prompt. In the second, name the file and the part, and let the agent read only that. For each run, write down four things: whether the answer was right, the time, the usage your tool shows, and anything the agent missed. To trust the difference, repeat each a few times and score both runs the same way. Then compare the answer, the time and the usage.

視窗裡裝了什麼，怎麼少裝一點

視窗裡有什麼

共用這個視窗的有六樣東西：

  1. 規則和指令，平台每次都會放進去。
  2. 工具清單，附上每個工具的描述。模型要靠它才知道自己可以請求什麼；工具一多，例如來自好幾個 MCP server（MCP server：插工具的標準接口），這份清單可能佔掉視窗的一大塊。到底有多大，我沒量過。
  3. 你的訊息。
  4. agent 讀過的檔案。檔案是整份文字放進去的，不管其中有多少是相關的。
  5. 工具結果，例如搜尋的清單、指令的輸出、測試紀錄。它們常常是最大的一塊，也是沒人看的一塊。
  6. agent 自己之前的回答。

迴圈每轉一輪，視窗裡就多一個結果，卻不會少掉任何東西。每一輪，模型還要把這六樣東西從頭重讀一遍（這筆成本在選模型：算的是每次成功的成本裡）。所以視窗只會越來越滿，直到滿了為止。到那時，平台只能裁掉或摘要最舊的部分，細節也就丟了。長對話會變差講的就是這件事。

是兩個限制，不是一個

那換一個更大的視窗不就好了？問題是，放不下只是誰都看得到的那個限制。第二個限制是注意力，Anthropic 把它描述成一份「注意力預算」，模型讀大量文字時就會消耗它。落到實際，意思是視窗還有空位，不等於表現就好。同一條規則，埋在又長又雜的上下文裡，比放在短上下文裡更容易被漏掉。

我拿這一點當理由：就算全都放得下，也要少放一點。不過這一步是我自己的推論，不是 Anthropic 說的。影響有多大，要看模型和任務。

全部載入、載入索引，或兩者都用

既然放得下也該少放，問題就變成了：該把什麼留在外面？這一部分大多數的決定，背後都是這個選擇。

最簡單的回答是什麼都不留在外面。agent 一開始，視窗裡就有所有規則和所有筆記，它什麼都不必查。麻煩在於，工作還沒開始，視窗就已經花掉了，而且大半花在這個任務用不到的東西上。

另一頭的回答，是只載入一份索引，需要什麼再去取。agent 一開始只有一份簡短的清單，列出現有每樣東西的名稱和一行描述，等任務需要其中一樣，它才打開那一樣。Anthropic 把這叫做「即時」做法：agent 只留輕量的標記（檔案路徑、名稱），到執行時才載入資料。這和圖書館是一樣的道理：沒有人會把整座圖書館搬到書桌上，我們都是先查目錄，再去取那一本。

在這兩頭之間，Anthropic 自己的建議是兩者混合。用他們的話說，「最有效的 agent 也許會採用混合策略，先取一部分資料求速度」，其餘的再讓它自己去探索。他們舉的例子是 Claude Code：它先把自己的指令檔放進上下文，其餘的在過程中用搜尋工具去找。

全部載入在有些情況下還是比較好。任務小、或規則少的時候，全部載入比較簡單，成本也低。而在漏掉一個事實代價很高的地方，我寧可花錢把它放在視窗裡，也不賭 agent 會打開對的檔案。

成本上，全部載入還多一個好處。每次都載入、又從不變的開頭，是可以快取的，而讀快取比一般的讀便宜很多（選模型：算的是每次成功的成本）。所以只要開頭保持穩定，「全部載入」其實比 token 數看起來便宜。不過，我沒有在 Copilot 上測過快取。而且就算用上快取，上面說的注意力限制也還在那裡。

不管怎麼搭配，索引這一部分要行得通，都得滿足三件事。第一，索引的條目得說明什麼時候該打開它，因為 agent 只憑那一行就做決定。寫得含糊，agent 就會打開錯的東西，或是永遠不打開對的，這就是為什麼 skill 的描述這麼重要（指令與 skill：只載入需要的）。第二，取用得便宜而且精確。如果取用要讀整個資料夾，索引就什麼也沒省。第三，agent 得知道自己不知道，因為 agent 自己沒意識到缺了的東西，索引是幫不上忙的。這才是真正的風險，下面我會再回來談。

少讀一點的辦法

索引只是讓視窗保持小的辦法之一。下面這些是我在用的，每一個要麼讓某樣東西不進視窗，要麼把它拿出來。如果想找個地方開始，最便宜的兩個是把規則分層和縮短工具輸出。

  • 規則分層。一小組規則一直載入，其餘的放在只有碰到相關檔案或工作時才讀的地方。不會改變下一步的規則，只是雜訊。（做法：指令與 skill：只載入需要的。）
  • 先搜尋，再讀。請 agent 先找出東西在哪，然後只讀檔案中那一部分，不讀整個檔案。或者給它一份事先寫好的專案簡短地圖，也就是上面說的那種索引。只有讀地圖比搜尋划算時，它才贏；也只有有人讓它保持正確，它才一直是對的。我沒有測過我的地圖是不是划算（知識庫：程式碼的誠實索引）。
  • 讓工具輸出變短。一個印出 2,000 行的指令，就會把 2,000 行放進視窗，所以要把它過濾一下，或只印失敗的部分。
  • 用幾行來提醒，不用一整頁。在我的設定裡，每個 prompt 只加上規則的一小段；有任務時（管任務，不管對話），這段提醒還會說任務做到哪了。這只是提醒，完整的內容要到需要時才讀。
  • 把大量閱讀交給子 agent（慎用子 agent、長對話會變差）。
  • 把狀態寫進檔案，這樣新的對話讀一個簡短的檔案就好，不用讀舊的對話。新的對話就是空的視窗，至於什麼時候開一個、帶什麼過去，見長對話會變差。

三個問題和一個測試

你自己的設定，視窗是怎麼花掉的？可以先問三個問題：

  1. 每次都載入了什麼？數一數你一直開著的規則有幾行，再看其中有多少和你現在做的任務有關。（在 Claude Code 裡，/context 指令會顯示什麼在佔用視窗。Copilot 有什麼，我沒查過。）
  2. agent 上一次讀的最大一樣東西是什麼？是一個檔案還是一份紀錄，全部都需要嗎？
  3. 如果 agent 現在開一個新的對話，它得讀什麼才能接著做？那些在檔案裡嗎？

還有一個今天就能跑的測試。挑一個你知道答案的任務，各開一個新對話，跑兩遍。第一遍，把整個檔案或文件貼在 prompt 裡；第二遍，只說出檔案和那一部分，讓 agent 只讀那裡。每一遍都記下四樣：答案對不對、時間、你的工具顯示的用量，以及 agent 漏掉了什麼。想讓差別可信，每種做法多跑幾次，兩邊用同樣的方式打分。最後再比較兩種做法的答案、時間和用量。

窗口里装了什么，怎么少装一点

窗口里有什么

共用这个窗口的有六样东西：

  1. 规则和指令，由平台每次都放进去。
  2. 工具列表，附带每个工具的描述。模型要靠它才知道自己能请求什么；工具一多，比如来自好几个 MCP server（接 MCP server 之前，要想清楚什么？），这份列表可能占掉窗口很大一块。到底有多大，我没量过。
  3. 你发的消息。
  4. agent 读过的文件。文件是整段文本放进去的，不管其中真正有用的有多少。
  5. 工具结果，比如搜索列表、命令输出、测试日志。它们常常是最大的一块，也是没人去看的一块。
  6. agent 自己之前的回答。

循环每转一轮，窗口里就多一条结果，却不会少掉任何东西。每一轮，模型还要把这六样东西从头再读一遍（这笔账在选模型，别只看 token 单价里）。所以窗口只会越来越满，直到装不下为止。到了那时，平台只能截掉或总结最早的部分，细节也就丢了。对话越久，Agent 越笨讲的就是这件事。

是两个上限，不是一个

那换个更大的窗口不就行了？问题是，装不下只是谁都看得见的那个上限。第二个上限是注意力，Anthropic 把它叫作“注意力预算”，模型读大量文本时要从里面扣。落到实际，意思就是窗口还有空位，不等于表现就好。同一条规则，埋在又长又杂的上下文里，比放在短上下文里更容易被漏掉。

我把这当成少放的理由，哪怕东西全都装得下。不过这一步是我自己的推断，不是 Anthropic 说的。影响有多大，要看模型和任务。

全装进去、只放索引，还是两者结合

既然装得下也该少放，问题就变成了：该把什么留在外面？这本书这一部分里的大多数决定，背后都是这个选择。

最简单的回答是什么都不留在外面。agent 一开始，窗口里就有所有规则、所有笔记，它什么都不用查。麻烦在于，工作还没开始，窗口就已经花掉了，而且大半花在这个任务用不上的东西上。

另一头的回答，是只放一份索引，需要什么再取。agent 一开始只有一份简短的列表，上面是现有各样东西的名字和一行说明，等任务需要其中某一样，它再去打开那一样。Anthropic 把这叫作“即时”（just in time）做法：agent 只保留轻量的标识（文件路径、名字），到运行时再加载数据。这和图书馆是一个道理：谁也不会把整座图书馆搬到书桌上，我们都是先查目录，再去取那一本。

在这两头之间，Anthropic 自己的建议是把两者结合起来。用他们的话说，“最有效的 agent 可能采用混合策略，先取一部分数据来保证速度”，其余的再由它自己去探索。他们举的例子是 Claude Code，它事先把指令文件放进上下文，其余的在工作中用搜索工具去找。

全装进去在有些情况下还是更合适。任务小，或者规则少，全装进去更简单，也花不了多少。而在漏掉一条事实代价很高的地方，我宁愿花钱把它放进窗口，也不愿赌 agent 会打开对的文件。

成本上，全装进去还多一条好处。每次都加载、又从不变化的开头，是可以缓存的，而读缓存比正常读便宜得多（选模型，别只看 token 单价）。所以只要开头保持稳定，“全装进去”其实比 token 数看起来要便宜。不过，我没有在 Copilot 上测过缓存。而且就算用上缓存，上面说的注意力上限也还在那里。

不管怎么搭配，索引这一部分要管用，都得满足三件事。第一，索引里的条目得说清什么时候该打开它，因为 agent 只凭那一行就做决定。说得含糊，agent 就会打开错的东西，或者永远不打开对的那个，这就是为什么 skill 的描述那么重要（规则写太多，Agent 反而记不住）。第二，取用得便宜而且准确。如果取一样东西要读整个文件夹，索引就什么也没省下。第三，agent 得知道自己不知道，因为 agent 自己没意识到缺了的东西，索引是帮不上忙的。这才是真正的风险，下面我还会回到这一点。

少读一点的办法

索引只是让窗口保持小的办法之一。下面这些是我在用的，每一种要么不让东西进窗口，要么把它拿出去。如果想找个地方下手，最省事的两个是给规则分层和缩短工具输出。

  • 规则分层。 留一小组规则始终加载，其余的放在只有处理相关文件或相关工作时才会读到的地方。不会改变下一步动作的规则，只是噪音。（做法：规则写太多，Agent 反而记不住。）
  • 先搜索，再阅读。 让 agent 先找到东西在哪，再只读文件里的那一部分，而不是整个文件。或者事先写好一份简短的项目地图给它，也就是上面说的那种索引。只有读地图比搜索划算，它才算赢；也只有有人让它保持准确，它才一直可信。我没有测过我的地图是不是划算（为什么要给代码建一个知识库？）。
  • 让工具输出变短。 一条命令打印 2,000 行，窗口里就多了 2,000 行，所以要把它过滤一下，或者只打印失败的部分。
  • 用几行提醒，不要一整页。 在我的配置里，每条 prompt 只附加规则里很短的一小段；有任务时（一个任务一个文件夹），这段提醒还会说明任务进行到了哪里。这只是提醒，完整的内容要到需要时才读。
  • 把大块的阅读交给子 agent（别跟风瞎用子 Agent、对话越久，Agent 越笨）。
  • 把状态写进文件，这样新对话读一个简短的文件就行，不用去读旧的对话。新对话就是一个空窗口，至于什么时候开新对话、带什么过去，见对话越久，Agent 越笨。

三个问题和一个测试

你自己的配置，窗口是怎么花掉的？可以先问三个问题：

  1. 每次都加载了什么？数一数你那些始终开启的规则有多少行，再看其中有多少和你现在做的任务有关。（在 Claude Code 里，/context 命令能显示什么在占用窗口。Copilot 提供什么，我没查过。）
  2. agent 上一次读的最大的一样东西是什么？是文件还是日志，全都需要吗？
  3. 如果 agent 现在开一个新对话，它要读什么才能接着干？这些东西在文件里吗？

还有一个今天就能跑的测试。找一个你知道答案的任务，各开一个新对话，跑两次。第一次，把整个文件或文档贴进 prompt；第二次，只说出文件名和相关的部分，让 agent 只读那一部分。每次运行都记下四样：答案对不对、时间、你的工具显示的用量，以及 agent 漏掉了什么。想让差异可信，每种做法都多跑几次，而且两种做法用同样的方式打分。最后再比较两种做法的答案、时间和用量。

What loading less can cost

The first cost of putting less in the window is the risk I promised to come back to: loading less can lose something the agent needed. An index is a bet that the agent will open the right thing. When it does not, the agent works from a guess. The fix is better descriptions, and then a check that the thing was opened when it should have been. To make that check, run a task you know needs a certain file, look at the tool's log of what was opened, and count how often it was not. A new chat, a rule or a skill can be lost in the same way, because each of them also depends on the agent reading the right thing at the right time.

Summaries carry a similar risk, because a subagent's report and a platform's compression both make text shorter and can both drop the one line that mattered. Use them where a short version is enough.

An index also has to be kept true. A map that is out of date costs more than it saves, because the agent trusts it. Keep it true is about that.

As I said at the start, there are no numbers behind any of this. For Copilot's models, I know of no clean measure of how much attention is lost as a window fills.

少裝要付出什麼

少往視窗裡放，第一個代價，就是前面說要回來談的那個風險：載入得少，可能丟掉 agent 需要的東西。索引其實是一場賭注，賭 agent 會打開對的東西。agent 要是沒打開，就只能憑猜測做事。補救的辦法是把描述寫得更好，再檢查該打開的時候到底有沒有打開。檢查的方法是跑一個你知道需要某個檔案的任務，看工具紀錄裡打開了哪些，數它沒打開的次數。新的對話、規則或 skill 也可能這樣丟掉，因為它們同樣要靠 agent 在對的時候讀到對的東西。

同樣的風險也出在摘要上。子 agent 的報告和平台的壓縮，都會把文字縮短，也都可能丟掉最要緊的那一行，所以只用在簡短的版本就夠的地方。

索引還得一直保持正確。過期的地圖花的比省的多，因為 agent 會相信它。讓知識庫一直是對的講的就是這個。

開頭說過，這一章背後沒有數字。對於 Copilot 的模型，視窗填滿時失去多少注意力，我不知道有任何乾淨的量法。

少装要付出什么

少往窗口里放，头一个代价，就是前面说要回过头来谈的那个风险：装得少，可能丢掉 agent 需要的东西。索引其实是一场赌注，赌 agent 会打开对的东西。agent 要是没打开，就只能凭猜测干活。补救的办法是把描述写得更好，再检查该打开的时候到底有没有打开。检查起来也不难：跑一个你知道需要某个文件的任务，看工具里记录的打开了什么，数一数有多少次没打开。新对话、规则或 skill 也可能这样丢掉，因为它们同样要靠 agent 在对的时候读到对的东西。

同样的风险也出在摘要上。子 agent 的报告和平台的压缩，都会把文本缩短，也都可能丢掉最关键的那一行，所以只在简短版本够用的地方用它们。

索引还得一直保持准确。过期的地图花的比省的多，因为 agent 会信它。代码变了，知识库怎么跟着变？讲的就是这个。

开头说过，这一章背后没有数字。对于 Copilot 的模型，窗口越满、注意力丢掉多少，我不知道有什么干净的衡量办法。

Do the platform makers agree? Industry practice

Both makers came up at the start of this chapter. Side by side, their advice reads like this. Anthropic says context is "a finite resource with diminishing marginal returns" and that agents can load data "just in time" by keeping light references (Effective context engineering). VS Code's guide says: "Start with concise context and expand only when needed." (Context engineering guide)

They agree on the direction. Neither, though, gives a number I can quote for how much to load. That leaves a practical question: how long will the manual work in this chapter be needed?

平台廠商也這麼看嗎？ 業界做法

這兩家廠商在開頭都引過，這裡把兩家的說法放在一起看。Anthropic 說，上下文是「有限的資源，邊際報酬遞減」，agent 可以靠帶著輕量的參照，「即時」地載入資料（Effective context engineering）。VS Code 的指南則說：「從簡短的上下文開始，只在需要時才擴充。」（Context engineering guide）

可見兩家在方向上是一致的。不過，該載入多少，兩家都沒有給出我能引用的數字。這就留下一個實際的問題：這一章裡的手動作業還要做多久？

平台厂商也这么看吗？ 业界做法

这两家厂商在开头都引过，这里把两家的说法放在一起看。Anthropic 说，上下文是“有限的资源，边际收益递减”，agent 可以通过保留轻量的引用来“即时”加载数据（Effective context engineering）。VS Code 的指南则说：“从简洁的上下文开始，需要时再扩充。”（Context engineering guide）

可见两家在方向上是一致的。不过，到底该加载多少，两家都没有给出我能引用的数字。这就留下一个实际的问题：这一章里的手工活还要做多久？

When the manual work can be deleted Industry practice

The reasoning itself stays as long as the window has a size and the model reads it every turn. What may go is my own effort, the manual layering of rules and the manual new chats. If the platform loads rules by relevance well and compresses without dropping what matters, I will stop doing it by hand. A very large window, however, does not remove the second limit by itself, so before relying on one I would want to see a test of that.

什麼時候可以刪掉這些手動作業 業界做法

只要視窗有大小、模型每一輪都要讀它，這套道理本身就還在。可能會消失的，是我自己花的力氣，也就是手動把規則分層、手動開新對話。如果平台能按相關性把規則載入得很好，壓縮時又不丟掉要緊的東西，我就不再手動做這些。但視窗再大，本身也不會讓第二個限制消失，所以在指望大視窗之前，我會想先看到這方面的測試。

什么时候可以删掉这些手工活 业界做法

只要窗口有大小，模型每一轮都要读它，这套道理本身就在。可能会去掉的，是我自己花的功夫，也就是手动给规则分层、手动开新对话。如果平台能按相关性把规则加载好，压缩时又不丢重要的内容，我就不再手动做了。但窗口再大，也不会自动消除第二个上限，所以在指望大窗口之前，我想先看到这方面的测试。
