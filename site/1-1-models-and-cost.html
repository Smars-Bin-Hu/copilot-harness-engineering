Choosing a model: cost per finished task選模型：算的是每次成功的成本选模型，别只看 token 单价

This chapter assumes you have used an AI coding agent and have seen a usage or billing page for it. Nothing else.

讀這一章，只需要用過寫程式的 AI agent，並且看過它的用量或帳單頁面。其他都不用。

读这一章，只需要用过写代码的 AI agent，并且看过它的用量页面或账单页面。别的都不需要。

The Knowledge經驗分享经验分享

In one sentence

Judge a model by what it costs to get one task done, not by its price per token. Most of that cost is what the model reads, so reading less and redoing less saves the most.

一句話

評斷一個模型，要看做完一個任務花多少，而不是每個 token 的單價。這筆錢大部分花在模型讀的東西上，所以少讀、少重做，省得最多。

一句话

评价一个模型，要看做完一个任务花多少钱，而不是每个 token 的单价。这笔钱大部分花在模型读的东西上，所以少读、少返工，省得最多。

For leaders

  • The decision: judge models and setups by what it costs to finish one task, not by the price per token. When a result is bad, try the cheaper fixes first (a missing rule, a missing check, a lost thread) before paying for a bigger model.
  • The risk: in a long agent task, most of the tokens go to the model re-reading the same material. In my worked example, which uses round numbers I chose, reading was over 90% of the tokens. A cache can cut the bill a lot, but only while the start of the input stays unchanged.
  • The cost of doing it right: mostly setup time and a habit of measuring. A fair comparison of models takes a few tasks, each run about three times.
  • Ask the team: "What does one finished task cost us, and when did we last check that number?"

給主管

  • 要做的決定：評斷模型和設定，看的是做完一個任務的成本，不是每個 token 的單價。結果不好的時候，先試比較便宜的修法（是不是缺了一條規則、缺了一道檢查，或是丟了線索），再考慮付錢換更大的模型。
  • 風險：在長的 agent 任務裡，大部分 token 都花在模型一再重讀同樣的材料上。在我的算例裡（數字是我挑的整數），讀的部分占了 token 的九成以上。快取（cache）可以讓帳單降很多，但前提是輸入的開頭一直不變。
  • 做對的成本：主要是設定的時間，再加上量測的習慣。想公平地比較模型，要挑幾個任務，每個跑三次左右。
  • 可以問團隊：「我們做完一個任務要花多少？上次確認這個數字是什麼時候？」

写给管理者

  • 要拍板的事：评价模型和配置，看的是做完一个任务的成本，不是每个 token 的单价。结果不好的时候，先试便宜的办法（是不是缺了一条规则、缺了一道检查，或者线索丢了），再考虑花钱换更大的模型。
  • 风险：在一个长的 agent 任务里，大部分 token 都花在模型反复重读同样的内容上。在我的算例里（数字是我挑的整数），读占了 90% 以上的 token。缓存能让账单降下来很多，但前提是输入的开头一直不变。
  • 做对的代价：主要是配置的时间，再加上一个量化的习惯。想公平地比较模型，要挑几个任务，每个跑三次左右。
  • 可以问团队：“做完一个任务，我们要花多少钱？上次核对这个数字是什么时候？”

What are you really paying for?

A model comparison usually starts with a price list, which tells you how many dollars a model charges per million tokens. A token is a small piece of text, roughly a short word or part of one, and since models read and write in tokens, bills are counted in them as well. Tokens come in two kinds. Input tokens are what the model reads in a call, and output tokens are what it writes. The two are priced differently, and output is usually the more expensive per token.

The price list is the number you can look up, so it is the number people use. But you never buy tokens for their own sake. What you buy is a finished task, a bug fixed or a report written, and what matters is the total for that.

It is a poor guide to that total, for two reasons. A cheap model that fails the task and has to be asked again may cost more than a strong one that gets it right the first time. And in an agent, the number of tokens is not what you expect, as the next part shows.

Where the tokens go in an agent

Why would the count surprise you? In a chat, you send a question and get an answer. In an agent loop (chapter 2.1), the model is called again after every tool result, and every call sends the whole conversation so far: the rules, your request, every file it read and every result. The model has no memory between calls, so this is the only way it knows what has happened. All of it has to fit in the context window, which is how much text the model can see at once. That window has a size limit of its own (chapter 3.1 is about managing it), and every call fills it again from the start.

Here is the arithmetic, with round numbers I chose to make it easy rather than numbers I measured. Say the rules and your request come to 10,000 tokens, and each tool result adds 5,000. Over 10 calls the model reads about 10,000 + 15,000 + 20,000 + ... = 325,000 tokens, but it writes perhaps a few hundred tokens per call. In this example reading is more than 90% of the tokens. The real share depends on your task, but the longer the loop runs, the more it leans toward reading.

Tokens are not the same as money, since output costs more per token. The shape holds all the same: a long agent task is mostly the model reading the same material again and again. That is why the second half of this chapter is about reading less.

I can also show one real case. In chapter 2.3 I gave the same four tasks to a team of three agents with job titles and to a single agent. Both got every task right, yet the team used about 4.5 times as much. The largest waste was re-reading, because each new agent started with an empty context and had to read the same files again. These were four small tasks, each run once, so trust the direction and not the ratio.

The prompt cache changes the sum

Because so much of every call is the same beginning, providers offer a prompt cache. It lets the provider remember a long beginning of your input, so that a later call starting with the same text can be charged less for it. On Anthropic's API, reading cached input costs a tenth of the base input price on most models, and less on some. Writing to the cache costs more than a normal read, 1.25 times for a five-minute cache and 2 times for a one-hour cache (Prompt caching).

Those prices reward a stable beginning. The cache works only on an exact match from the start of the input, so if you change something near the top, such as an edited rule or a different tool list, everything after it misses the cache. They also punish a pause. A cache lives only a short time, so a conversation you leave for an hour and return to may pay full price to rebuild it. And even a cache read is not free: the cheapest token is still the one that is not sent. Reading less is still the first thing to try.

To see how much the cache moves, take the same example with a cache that hits every time, counting input only and using the five-minute prices. The first call writes 10,000 tokens at 1.25 times, which is 12,500. In each of the next nine calls, the earlier text is read from the cache. The cached part grows from 10,000 to 50,000 tokens, 270,000 over the nine calls, and at 0.1 times the price that is 27,000. Each call also writes its 5,000 new tokens, 45,000 in all, which at 1.25 times is 56,250. The total is about 96,000 token-prices instead of 325,000, and the repeated reading is now less than a third of it.

So the cache changes where the money goes, away from re-reading and toward new material. That is why the earlier "more than 90%" is a count of tokens read, not a share of the bill, and why a team with a well-kept cache can read a lot and still pay little. Misses undo that. An edited rule near the top, or a pause long enough for the cache to expire, brings the cost back toward the 325,000.

你到底在為什麼付錢？

比較模型，通常從一張價目表開始，上面寫著每百萬個 token 多少美元。token 是一小段文字，大約是一個短的英文單字，或單字的一部分；模型用 token 讀和寫，所以帳單也用 token 算。token 又分兩種：輸入 token 是模型在一次呼叫裡讀的，輸出 token 是它寫出來的。兩者的價格不同，通常輸出每個 token 比較貴。

價目表上的數字查得到，所以大家都拿它來比。可是你買 token，從來不是為了 token 本身。你買的是一件做完的事，像是修好一個 bug、寫好一份報告，所以重要的是那件事總共花了多少。

拿價目表來估這個總花費並不可靠，原因有兩個。第一，便宜的模型如果任務失敗，還得再問一次，算下來可能比第一次就做對的強模型更貴。第二，在 agent 裡，token 的數量和你預期的不一樣，下面就來看看。

在 agent 裡，token 去哪了

token 的數量為什麼會出乎意料？在對話裡，你送出一個問題，得到一個回答，就結束了。在 agent 迴圈裡（agent 循環，和你能插手的地方），每個工具結果出來之後，模型都會被再呼叫一次，而每次呼叫都要把到目前為止的整段對話重新送出：規則、需求、它讀過的每個檔案、每個結果。模型在兩次呼叫之間沒有記憶，只有這樣，它才知道之前發生過什麼。這些內容都得放進上下文視窗，也就是模型一次能看到的文字。視窗本身有大小上限（怎麼管它，上下文是一份預算 會講），而每次呼叫都會把它從頭重新裝滿一遍。

我們用整數來算一遍。這些數字是我為了好算而挑的，不是量出來的。假設規則加你的需求一共 10,000 個 token，每個工具結果再加 5,000。呼叫 10 次下來，模型讀的大約是 10,000 + 15,000 + 20,000 + …… = 325,000 個 token，但每次呼叫寫的大概只有幾百個 token。在這個例子裡，讀的部分占了 token 的九成以上。實際的比例要看你的任務，但迴圈跑得越久，就越偏向讀。

當然，輸出每個 token 比較貴，所以 token 數不等於錢。不過大致的樣子不變：長的 agent 任務，多半是模型在一遍又一遍地讀同樣的材料。這也是為什麼這一章的後半，講的都是怎麼少讀。

我還可以舉一個真實的例子。在 慎用子 agent 裡，我把同樣的四個任務，分別交給一個有三個職位、由三個 agent 組成的團隊，和一個單獨的 agent。兩邊每個任務都答對了，團隊用掉的卻是後者的 4.5 倍左右。浪費最多的就是重讀，因為每個新的 agent 都從空的上下文開始，只好把同樣的檔案再讀一遍。那只是四個小任務，每個只跑一次，所以方向可以相信，倍數不要當真。

prompt 快取改變了算式

既然每次呼叫有這麼大一段開頭都一樣，供應商就提供了 prompt 快取：它記住你輸入裡很長的一段開頭，之後的呼叫只要開頭是同樣的文字，那一段就可以收得便宜些。在 Anthropic 的 API 上，大多數模型讀快取的輸入，只收基本輸入價的十分之一，有些模型更低。寫入快取則比一般的讀取貴，五分鐘的快取是 1.25 倍，一小時的快取是 2 倍（Prompt caching）。

這幾個價格最直接的影響是，開頭越穩定越划算。因為快取只認從輸入開頭起完全一致的內容，只要你改了靠近頂端的東西，例如改了一條規則、換了一份工具清單，它後面的所有內容就都沒辦法命中快取。反過來，停下來也可能要付錢：快取只活很短的時間，一段對話你離開一小時再回來，可能就得付全價把它重建一遍。不過，就算每次都命中，讀快取也不是免費的：最便宜的 token，仍然是沒送出去的那個。少讀仍然是第一件該試的事。

快取到底能省多少？還是用同一個例子，假設快取每次都命中，只算輸入，用五分鐘的價格。第一次呼叫寫入 10,000 個 token，乘 1.25 倍，是 12,500。接下來九次呼叫，之前的文字都從快取讀。快取的部分從 10,000 個 token 增加到 50,000 個，九次加起來是 270,000，乘 0.1 倍是 27,000。每次呼叫也都要寫入新的 5,000 個 token，共 45,000，乘 1.25 倍是 56,250。加起來大約是 96,000 個 token 的價格，而不是 325,000，重複讀取的部分現在也只占不到三分之一。

換句話說，快取改變的是錢花在哪裡：從重讀，轉到新材料上。這樣一來就能明白，前面說的「九成以上」算的是讀了多少 token，不是帳單的占比；也能明白為什麼快取維護得好的團隊，可以讀很多，卻付得很少。可是一旦沒命中，這些就都白省了：例如改了開頭的規則，或是停太久、快取過期了，成本就會被拉回 325,000 附近。

你到底在为什么付钱？

比较模型，通常从一张价目表开始，上面写着每百万 token 多少美元。token 是一小段文本，大致相当于一个短的英文单词，或者单词的一部分；模型按 token 读写，所以账单也按 token 算。token 又分两种：输入 token 是模型在一次调用里读的内容，输出 token 是它写出来的内容。两者价格不同，通常输出的单价更贵。

价目表上的数字查得到，所以大家都拿它来比。可你从来不是为了 token 本身付钱。你买的是一件做完的事，比如修好一个 bug、写完一份报告，所以要紧的是这件事一共花了多少。

拿价目表来估这个总价并不靠谱，原因有两个。一是便宜的模型如果把任务做砸了，还得再问一遍，算下来可能比一次就做对的强模型更贵。二是在 agent 里，token 的数量和你想的不一样，下面就来看看。

agent 里的 token 都去了哪

token 的数量为什么会出乎意料？在聊天里，你发一个问题，得到一个回答，就结束了。在 agent 循环里（Agent 到底是怎么干活的？），每拿到一个工具结果，模型都要被再调用一次，而每次调用都要把到目前为止的整段对话重新发过去：规则、需求、读过的每个文件、每个结果。模型在两次调用之间没有记忆，只有这样它才知道之前发生了什么。这些内容都得装进上下文窗口，也就是模型一次能看到的文本。窗口本身有大小上限（怎么管理它，为什么不能把所有规则都塞给 Agent？会讲），而每次调用都会把它从头重新装满一遍。

我们用整数来算一笔账。这些数字是我为了好算挑的，不是测出来的。假设规则加你的需求一共 10,000 个 token，每个工具结果再加 5,000 个。10 次调用下来，模型读的大约是 10,000 + 15,000 + 20,000 + ... = 325,000 个 token，每次调用写的却可能只有几百个。在这个例子里，读占了 token 的 90% 以上。实际的比例要看你的任务，但循环跑得越久，就越偏向读。

当然，输出的单价更高，所以 token 数不等于钱。不过大致的格局不变：一个长的 agent 任务，大部分时候都是模型在一遍遍地重读同样的内容。这也是为什么这一章的后半部分，讲的都是怎么少读。

我还可以举一个真实的例子。在别跟风瞎用子 Agent里，我把同样的四个任务，分别交给一个由三个按岗位分工的 agent 组成的团队，和一个单干的 agent。两边每个任务都做对了，可团队用掉的是后者的 4.5 倍左右。浪费最多的就是重读，因为每个新开的 agent 都从空白的上下文开始，只好把同样的文件再读一遍。那只是四个小任务，每个只跑了一次，所以方向可以信，倍数别当真。

prompt 缓存改变了这笔账

既然每次调用的很大一部分都是同样的开头，提供方就推出了 prompt 缓存：它记住你输入里很长的一段开头，后面的调用只要以同样的文本开头，这一段就能少收钱。在 Anthropic 的 API 上，大多数模型读缓存的输入只收基础输入价的十分之一，有些模型更低。写入缓存则比普通读取贵，五分钟的缓存是 1.25 倍，一小时的缓存是 2 倍（Prompt caching）。

这几个价格最直接的影响是，开头越稳定越划算。因为缓存只认从输入开头起一模一样的内容，只要你改了靠前的东西，比如改了一条规则、换了一份工具列表，它后面的所有内容就都命中不了缓存。反过来，停下来也可能要花钱：缓存只能活很短的时间，一个对话你放下一小时再回来，可能就得付全价把缓存重建一遍。不过，就算每次都命中，读缓存也不是免费的：最便宜的 token，仍然是没发出去的那个。少读仍然是第一个该试的办法。

缓存到底能省多少？还是用同一个例子，假设缓存每次都命中，只算输入，用五分钟缓存的价格。第一次调用写入 10,000 个 token，按 1.25 倍算是 12,500。接下来的九次调用，之前的文本都从缓存里读。缓存的部分从 10,000 个 token 涨到 50,000 个，九次加起来是 270,000 个，按 0.1 倍算是 27,000。每次调用还要写入新增的 5,000 个 token，一共 45,000 个，按 1.25 倍算是 56,250。加起来约合 96,000 个 token 的价钱，而不是 325,000，重复读取的部分也只占了不到三分之一。

换句话说，缓存改变的是钱花在哪里：从重读，转到了新内容上。这下就能明白，前面说的“90% 以上”数的是读了多少 token，不是账单的占比；也能明白为什么缓存维护得好的团队，读得很多，付得却很少。可一旦没命中，这些就都白省了：比如改了开头的规则，或者停得太久、缓存过期了，成本就会回到 325,000 附近。

Where a task's cost comes from, and where to cut it

What a task costs

With reading, writing and the cache in view, we can put together what one finished task costs. Think of it as three parts.

  1. What the model reads, across every call, discounted where the cache hits.
  2. What the model writes: the answer, the code, the thinking.
  3. Redoing, meaning a wrong answer, a lost thread or a repeated attempt. Redoing is a multiplier on parts 1 and 2.

Most savings come from the first and the third. A good rule of thumb is: do things in the cheapest way that is enough.

When a strong model is cheaper

Redoing is also where the choice of model comes in. A stronger model costs more per token, yet it can still cost less per finished task when it gets the answer in one pass and the weaker one needs three. If the task was easy, though, it can also be a waste.

Where does it flip? I have no measurement of my own, so this is an argument, not a result. The way to find the point is to test it on your own tasks: run the same few tasks on two models and compare the cost per success, not the cost per call. Chapter 6.4 says how to do that honestly.

Pick by task, and check the setting

My own rule of thumb, just as unmeasured, is to use a strong model for thinking (a plan, an approach, a hard bug) and a medium model for doing (a change whose plan is already clear). Some tools also let you set reasoning effort, a setting on some models that controls how long they think before they answer. More thinking usually means more output tokens and more time. I have not tested whether Copilot lets you set it from a harness, so check your own tool.

How you are billed in Copilot (as of late October 2026)

What you actually pay depends on your plan, and for Copilot the plans change often, so check the date against your own.

  • Monthly Copilot plans: since June 1, 2026, Copilot has been moving to usage-based billing. Premium request units were replaced by GitHub AI Credits, and usage is calculated from input, output and cached tokens at each model's listed API rates. Code completions and next edit suggestions stay included. (GitHub blog)
  • Annual Pro and Pro+ plans stay on the older premium request model until they expire. There, each prompt you send counts as a request multiplied by the model's multiplier, while the tool calls the agent makes do not count. (Copilot requests)

The two models reward different habits. Under per-request billing a long autonomous run is cheap for you, so it can pay to do a big task in a single prompt. Under token billing, a long run costs in proportion to how much it reads. Which one you are on decides how much the rest of this chapter matters, and if your plan is billed by tokens, it matters a lot.

When the result is wrong, change the model last

Back to choosing a model, then. When a result comes back wrong, the easy reaction is to switch to a bigger model. It is also the most expensive fix, and often the wrong one. Before reaching for it, look at what went wrong:

What went wrong Try first
It did not know a rule, a name or how the project does it Write it into the rules or a knowledge file. A bigger model does not know it either
It said "done" and it was not Add a check: run the tests (chapter 5.4)
It lost the thread in a long session Start a new session and carry the state in files (chapter 3.2)
It knew everything and still reasoned badly Now try a stronger model

Four ways to save, and how each can go too far

Choosing the model is only one lever. The first of the four ways below comes before any of the three parts of a task's cost: not calling the model at all. The other three follow the parts in order. Each of the four can also go too far.

  1. Use the model less. If code can do it, do not ask a model. Counting, copying files, converting a Word file into text and checking a format are jobs a script does the same way every time, using no tokens. The danger is moving judgment into code that cannot judge, and chapter 5.9 draws that line.
  2. Read less. Keep the rules short, load details only when they are needed, and ask for a diff rather than the whole file. The danger is that if it reads too little, it guesses, and the rework costs more than the reading saved.
  3. Write less. Ask for short answers, such as a one-line verdict or a short list. The danger is output so terse that the next step cannot use it.
  4. Redo less. Agree the plan before the work starts, keep state in files so a lost session can be picked up, and cap the number of retries. The danger is a cap that cuts off useful work, so set caps from what you saw, not from fear.

Also mind the standing costs, which you pay on every call before any of these choices come in. Every tool the agent has adds its name, description and parameters to the input of every call (chapter 1.2), and every rule you inject rides along on every turn.

When a bill surprises you

When a bill comes in higher than you expected, start with three questions.

  1. Which call or turn read the most? Look at the usage page of your tool, and at the biggest tasks.
  2. What was in the context that did not need to be there? Old tool results, a large file read in full, a long rules file?
  3. Did the task get redone? If so, why did the first attempt fail?

The same habit of checking helps when you are choosing between two models, and for that a small experiment is enough. Take one task whose right answer you know, run it on two models three times each, and note the usage and whether the result was right. 一個任務的錢花在哪裡，又該從哪裡省

一個任務花多少

讀、寫和快取都看過了，我們可以把做完一個任務的成本拼起來。不妨把它想成三個部分。

  1. 模型讀的，每次呼叫都算，快取命中的地方有折扣。
  2. 模型寫的：回答、程式碼、思考。
  3. 重做，也就是答錯、丟了線索、再試一次。重做是第 1、2 部分的乘數。

這三部分裡，能省的大多在第一和第三部分。一個好用的經驗法則是：在夠用的方式裡挑最便宜的。

強模型什麼時候比較便宜

選哪個模型，也正是在重做這一項上見分曉。更強的模型每個 token 更貴，但如果它一次就得到答案，弱的模型卻要三次，那麼算到每個做完的任務上，強模型的成本反而可能更低。不過，如果任務很簡單，用強模型也可能是浪費。

轉折點在哪裡？我自己沒有量過，所以這只是論證，不是結果。要找到那一點，辦法是在你自己的任務上測：拿同樣幾個任務在兩個模型上跑，比較每次成功的成本，而不是每次呼叫的成本。怎麼誠實地做這件事，一次運行證明不了什麼 會講。

依任務挑模型，再確認一下設定

我自己的經驗法則同樣沒有量過，大致是：用強模型來想，像是定計劃、找做法、處理難的 bug；用中等的模型來做，像是一處計劃已經很清楚的改動。有些工具還讓你設定推理強度，這是某些模型有的設定，控制它回答之前想多久。想得越多，通常輸出的 token 越多，時間也越長。至於 Copilot 能不能從 harness 裡調它，我還沒測過，你得查一下自己的工具。

在 Copilot 裡怎麼計費（2026 年 10 月下旬）

你實際付多少，取決於你的方案，而 Copilot 的方案常常變，請對照日期確認你自己的。

  • 年繳的 Pro 和 Pro+ 方案，在到期之前仍用舊的 premium request 模式。在這種模式下，你送出的每個 prompt 算一次請求，再乘上該模型的倍率，而 agent 做的工具呼叫不算。（Copilot requests）

這兩種模式獎勵的習慣不一樣。按請求計費時，一次長的自主執行對你來說很便宜，所以把一個大任務放進一個 prompt 裡做，可能很划算。按 token 計費時，一次長的執行花多少，和它讀了多少成正比。所以你用的是哪一種，決定了這一章其餘的部分對你有多重要。如果你的方案按 token 計費，那就非常重要。

四種省法，以及各自怎樣過頭

選模型只是其中一個槓桿。下面四種省法裡，第一種排在成本的三個部分之前：乾脆不呼叫模型。後三種依序對應那三個部分，而且四種都可能做過頭。

  1. 少用模型。程式碼能做的，就不要去問模型。計數、複製檔案、把 Word 檔轉成文字、檢查格式，這些事腳本每次都做得一樣，也不用 token。危險是把需要判斷的事搬進一段不會判斷的程式，這條線畫在哪裡，見誰來判斷：程式、便宜模型、主模型、人。
  2. 少讀。規則寫短，細節要用時才載入，要 diff 而不是整個檔案。危險是讀太少，它就會猜，而重做花的錢比省下來的讀取還多。
  3. 少寫。要簡短的回答，例如一行結論、一份短清單。危險是簡短到下一步用不上。
  4. 少重做。工作開始前先談好計劃，把狀態放在檔案裡，這樣會話丟了也能接著做，再限制重試的次數。危險是上限切斷了有用的工作，所以上限要依你看到的情況設，而不是依擔心設。

一个任务的钱花在哪，又该从哪里省

一个任务的成本

读、写和缓存都看过了，我们可以把做完一个任务的成本拼起来了。不妨把它看成三部分。

  1. 模型读的，所有调用加起来，缓存命中的部分打折。
  2. 模型写的：回答、代码、思考。
  3. 返工，也就是错误的回答、丢了的线索、重复的尝试。返工是第 1、2 部分的乘数。

这三部分里，能省的大多在第一和第三部分。一条好用的经验法则是：用够用的办法里最便宜的那个。

什么时候强模型反而便宜

选哪个模型，也正是在返工这一项上见分晓。更强的模型每个 token 更贵，可如果它一次就答对，而弱的模型要试三次，那么算到每个做完的任务上，强模型反而可能花得更少。不过，如果任务本来就简单，用强模型也可能是浪费。

转折点在哪里？我自己没有测过，所以这只是一个推理，不是结果。要找到这个点，办法是在你自己的任务上测：拿同样的几个任务，在两个模型上各跑一遍，比较每次成功的成本，而不是每次调用的成本。怎么老老实实地做这件事，同一个任务跑两次，结果不一样会讲。

按任务选模型，再看一眼设置

我自己的经验法则同样没有测过，大致是：思考用强模型，比如定计划、想思路、啃难的 bug；动手用中等的模型，比如做一处计划已经很清楚的改动。有些工具还能设置推理强度，这是部分模型上的一个设置，控制它回答之前想多久。想得越多，通常输出的 token 越多，花的时间也越长。至于 Copilot 能不能从 harness 里调它，我没测过，你得查一下自己用的工具。

Copilot 怎么计费（截至 2026 年 10 月下旬）

你实际付多少钱，取决于你的套餐，而 Copilot 的套餐经常变，请对照日期核对你自己的。

  • 按月的 Copilot 套餐：从 2026 年 6 月 1 日起，Copilot 在改成按用量计费。高级请求单位被 GitHub AI Credits 取代，用量按输入、输出和缓存的 token 计算，价格是每个模型公布的 API 费率。代码补全和下一处编辑建议仍然包含在内。（GitHub blog）
  • 年度的 Pro 和 Pro+ 套餐在到期前仍然用旧的高级请求模式。在这种模式下，你发的每个 prompt 算一次请求，再乘上该模型的倍率，而 agent 做的工具调用不算。（Copilot requests）

这两种模式鼓励的习惯不一样。按请求计费时，一次很长的自主运行对你来说很便宜，所以把一个大任务放进一个 prompt 里做，可能很划算。按 token 计费时，一次长的运行花多少钱，和它读了多少成正比。所以你用的是哪一种，决定了这一章剩下的内容对你有多要紧。如果你的套餐按 token 计费，那就非常要紧。

结果不对时，最后才换模型

说回选模型。结果不对的时候，最容易想到的就是换一个更大的模型。可这也是最贵的办法，而且常常是错的。换之前，先看看到底出了什么问题：

出了什么问题 先试什么
它不知道一条规则、一个名字，或者项目里的做法 写进规则或知识文件。更大的模型一样不知道
它说“做完了”，其实没有 加一道检查：跑测试（让 Agent 自己跑测试）
在长会话里它丢了线索 开一个新会话，把状态放在文件里带过去（对话越久，Agent 越笨）
它什么都知道，推理还是不行 这时再试更强的模型

四个省钱的办法，以及各自怎样会过头

选模型只是其中一个抓手。下面四个省钱的办法里，第一个排在成本的三部分之前：干脆不调用模型。后三个按顺序对应那三部分，而且四个办法都可能做过头。

  1. 少用模型。代码能做的，就别去问模型。计数、复制文件、把 Word 文件转成文本、检查格式，这些活脚本每次都做得一样，而且不花 token。危险在于把需要判断的事交给了不会判断的代码，这条线划在哪里，见这个判断该交给谁：代码、便宜模型、主模型，还是人？。
  2. 少读。规则写得简短，细节需要时才加载，要 diff 而不是整个文件。危险在于读得太少，它就会去猜，返工的成本比省下的读取还高。
  3. 少写。要简短的回答，比如一句话的结论、一个简短的清单。危险在于输出简略到下一步用不上。
  4. 少返工。动手前先商定计划，把状态放在文件里，会话丢了也能接着做，再给重试的次数设个上限。危险在于上限卡掉了有用的工作，所以上限要根据你见到的情况来定，而不是根据担心来定。

还有一类固定成本，不管你在任务里怎么选，每次调用都要付。agent 拥有的每个工具，都会把自己的名字、描述和参数加进每次调用的输入里（Agent 用不好工具，先看工具的描述和报错），你注入的每条规则，也会每一轮都跟着走。

  2. 上下文里有什么是不必在那里的？旧的工具结果、整个读进来的大文件、很长的规则文件？
  3. 任务有没有被重做？如果有，第一次为什么失败？

What saving costs, and what I cannot see

Everything I have said about savings is "by design", not read off a bill, because of what my tools let me see. My own harness records no token counts in its log. For how much a task really used, I read the platform's session record, which reports credits and premium requests, and I do not convert those to money.

The savings also have costs of their own. A hook that runs on tool calls adds a small delay, independent checks call the model again, and rules injected on every prompt cost tokens on every prompt. I accept those on purpose, for control, but they are still costs.

The trap that looks most like thrift is reading too little. The cheapest call is the one that guesses wrong and is thrown away. If a task keeps failing for lack of context, the answer is to give it the right context, not less of it.

Prices and plans also change. The cache multipliers and the Copilot billing above are as of the dates in the sources, and I would expect them to move. What has been moving, though, is not only the prices but what gets counted.

省錢要付出什麼，我又看不到什麼

我在這一章說的所有節省，都是「依設計」算的，不是從帳單上讀出來的，因為我手上的工具只讓我看到這麼多。我自己的 harness，日誌裡沒有記 token 數。一個任務真正用了多少，我讀的是平台的會話紀錄，它回報的是 credits 和 premium request，我也不把它們換算成錢。

而這些節省本身也有代價。在工具呼叫上執行的 hook 會加一點延遲，獨立檢查要再呼叫一次模型，每個 prompt 都注入的規則，每個 prompt 都要花 token。我是為了控制才刻意接受這些，但它們終究是成本。

最像節儉的陷阱，是讀得太少。最便宜的呼叫，恰恰是猜錯然後被丟掉的那一個。如果一個任務一直因為缺上下文而失敗，該做的是給它對的上下文，而不是給它更少。

另外，價格和方案都會變。上面的快取倍率和 Copilot 計費，是來源上那些日期的情況，我預期它們還會變。不過，變的不只是價格，還有收費時算的是什麼。

省钱要付出什么，我又看不到什么

我在这一章里说的所有节省，都是“按设计”算的，不是从账单上读出来的，因为我手上的工具只让我看到这么多。我自己的 harness 在日志里不记录 token 数。一个任务实际用了多少，我看的是平台的会话记录，它报告的是 credits 和高级请求，我也不把它们换算成钱。

而这些节省本身也有代价。在工具调用上运行的 hook 会带来一点延迟，独立检查要再调用一次模型，每个 prompt 都注入的规则，每个 prompt 都要花 token。我是为了控制而有意接受这些的，但它们终究是成本。

最像节俭的坑，是读得太少。最便宜的调用，恰恰是猜错了然后被扔掉的那一次。如果一个任务总是因为缺上下文而失败，该做的是给它正确的上下文，而不是给得更少。

另外，价格和套餐都会变。上面的缓存倍率和 Copilot 的计费方式，都是截至来源里写的日期，我预计它们还会变。不过，变的不只是价格，还有收费时数的是什么。

Is the market pricing it the same way? Industry practice

The two providers this chapter leans on point the same way. Anthropic prices cached reads at a fraction of normal input, and says tool definitions are counted as input tokens on every request (Prompt caching, Tool use). GitHub moved Copilot from counting requests to counting tokens (GitHub blog). In other words, the market now charges for what the model reads and writes, which is the argument of this chapter.

市場也是這樣算的嗎？ 業界做法

這一章依靠的兩家供應商，指向同一個方向。Anthropic 把讀取快取的價格訂成一般輸入的一小部分，並且說明工具定義在每個請求裡都算輸入 token（Prompt caching、Tool use）。GitHub 把 Copilot 從算請求改成算 token（GitHub blog）。換句話說，市場現在按模型讀和寫了多少來收費，這正是這一章的論點。

市场也是这么算的吗？ 业界做法

这一章依靠的两家提供方，指向的是同一个方向。Anthropic 把读缓存的价格定为普通输入的一小部分，并且说明工具定义在每次请求里都按输入 token 计算（Prompt caching、Tool use）。GitHub 把 Copilot 从按请求计费改成了按 token 计费（GitHub blog）。说白了，市场现在按模型读和写了多少来收费，这正是这一章的论点。

When to delete these tricks Industry practice

Much of this chapter is advice for a world where reading is expensive. If reading becomes so cheap that the extra work of trimming context costs more than it saves, drop the tricks, but keep the habit of measuring cost per finished task. I would also look again if a platform started showing per-task cost on its own, because then you would need to guess less.

什麼時候可以刪掉這些省錢技巧 業界做法

這一章有很多是為「讀取很貴」的世界寫的建議。如果有一天讀取便宜到，修剪上下文多出來的工夫比省下的還多，那就丟掉這些技巧，只留下量測每個完成任務成本的習慣。另外，如果某個平台開始自己顯示每個任務的成本，我也會重新看一遍，因為到那時，你要猜的就少了。

什么时候可以删掉这些省钱技巧 业界做法

这一章的很多内容，是写给“读取很贵”的世界的建议。如果有一天读取便宜到，精简上下文多花的功夫比省下的还多，那就把这些技巧丢掉，只留下核算每个完成任务的成本这个习惯。另外，如果哪个平台开始自己显示每个任务的成本，我也会重新考虑，因为到那时，你需要猜的就少了。

Explore it in the harness

My harness is built around reading less and redoing less. Rules are loaded in layers, state lives in files, and checks are off unless you ask for them. It also says plainly what it cannot see about cost. The harness can open the real files with you and show each of these from the inside.

Once you have set it up as described above, type:

/harness-rookie-wondering I have read the chapter "Choosing a model: cost per finished task". Teach me how this harness reads less, writes less and redoes less, and what it can and cannot tell me about the real usage of a task. Open the real files with me and draw how the pieces fit together.

It teaches one small piece at a time, stops to check that you are following, and opens the files with you.
