In one sentence

Choose a model by what it costs to finish a task, not by the price of a token, and since most of that money goes to what the model rereads, reading less and redoing less save the most.

一句話

選模型要看做完一個任務花多少錢，不是看每個 token 的單價，而這筆錢大部分花在模型反覆讀的東西上，所以少讀、少重做省得最多。

一句话

选模型要看做完一个任务花多少钱，不是看每个 token 的单价，而这笔钱大部分花在模型反复读的东西上，所以少读、少返工省得最多。

For leaders

  • The decision: judge models and setups by the cost of finishing a task, not by the price per token. When results are poor, try the cheap fixes first (a missing rule, a missing check, a lost thread), and only then pay for a bigger model.
  • The risk: on a long agent task, most of the money goes to the model rereading the same material. In my worked example (round numbers I picked), reading takes more than 95% of the money. Caching can bring the bill down to about a quarter, but only if the start of the input stays the same.
  • The cost of doing it right: mainly setup time, plus a habit of measuring. A fair comparison of models means picking a few tasks and running each about three times.
  • Ask the team: "What does it cost us to finish a task, and when did we last check that number?"

給主管

  • 要做的決定：評價模型和設定，看做完一個任務的成本，不看每個 token 的單價。結果不好的時候，先試便宜的辦法（是不是缺了一條規則、缺了一道檢查，或者線索丟了），再考慮花錢換更大的模型。
  • 風險：一個長的 agent 任務，大部分的錢都花在模型反覆重讀同樣的內容上。在我的算例裡（數字是我挑的整數），讀占了九成五以上的錢。快取能把帳單降到四分之一左右，但前提是輸入的開頭一直不變。
  • 做對的成本：主要是設定的時間，再加上一個量化的習慣。想公平地比較模型，要挑幾個任務，每個跑三次左右。
  • 可以問團隊：「做完一個任務，我們要花多少錢？上次核對這個數字是什麼時候？」

写给管理者

  • 要拍板的事：评价模型和配置，看做完一个任务的成本，不看每个 token 的单价。结果不好的时候，先试便宜的办法（是不是缺了一条规则、缺了一道检查，或者线索丢了），再考虑花钱换更大的模型。
  • 风险：一个长的 agent 任务，大部分钱都花在模型反复重读同样的内容上。在我的算例里（数字是我挑的整数），读占了九成五以上的钱。缓存能把账单降到四分之一左右，但前提是输入的开头一直不变。
  • 做对的代价：主要是配置的时间，再加上一个量化的习惯。想公平地比较模型，要挑几个任务，每个跑三次左右。
  • 可以问团队：“做完一个任务，我们要花多少钱？上次核对这个数字是什么时候？”

Where your money goes

People usually start choosing a model from the price list: Sonnet 5.5 is $2 per million input tokens and $10 per million output tokens, and Opus 5.5 is $4 and $20 (Pricing, prices as of late October 2026). A token is the unit a model reads and writes, roughly a short English word or part of a word. What the model reads is input tokens, what it writes is output tokens, and output usually costs much more. List prices are easy to look up, so everyone compares them, but you're not really buying tokens. You're buying a finished job, such as a fixed bug, so what you need to compare is what the whole job cost. That number is a long way from the unit price, for two reasons: a cheap model that botches the job has to run again, which can end up costing more than an expensive model that gets it right the first time, and an agent uses far more tokens than you'd think, most of them on reading.

Where the tokens go in an agent

In a chat, you ask a question, the model answers, and that's one call. An agent runs a loop (The agent loop, and where you can step in): the model asks to read a file, a program reads it and sends back the result, and the model decides what to do next, so every tool result means calling the model again. The model has no memory between calls, so each call sends the whole conversation so far all over again: the rules, the request, every file it has read and every tool result. All of this sits in the context window, the full text the model can see at once. The window has a size limit (Context is a budget), and you pay for what's in it every time you make a call.

Let's work it out with round numbers, which I picked to keep the arithmetic easy and did not measure. Say the rules and the request come to 10,000 tokens, each tool result adds 5,000, and a task makes 10 calls to the model, writing 300 tokens each time. The model reads 10,000 + 15,000 + ... + 55,000 = 325,000 tokens in total and writes only 3,000. In money the gap is just as wide: at Sonnet 5.5 prices, reading costs $0.65 and writing only $0.03, because although output costs 5 times as much per token, the model reads more than 100 times as much. The longer the loop runs, the further the money tilts toward reading, because every extra call rereads everything before it.

Prompt caching changes the math

The start of every call is almost the same, so model providers offer prompt caching: the provider remembers the start of your input, and if the next call begins with exactly the same text, that part is charged at a very low price. Anthropic's prices work like this. Writing to the cache costs more than normal input, 1.25 times for a 5-minute cache and 2 times for a 1-hour cache, while reading from the cache costs far less: a tenth of the input price on most models, and a twentieth on Opus 5.5 and Sonnet 5.5 (Prompt caching).

Take the same example at Sonnet 5.5 prices and assume every call hits the cache. The first call writes 10,000 tokens to the cache. Each of the next nine calls reads everything before it from the cache, 270,000 tokens across the nine, and writes its new 5,000 tokens to the cache, 45,000 across the nine. That comes to $0.1375 for writes and $0.027 for cache reads, about $0.16 in all, a quarter of the original $0.65. Most of that $0.16 is the write charge for new content, which caching can't save and only reading less can, so even with every call hitting the cache, reading less is still the first thing to try.

Caching also breaks easily, in three ways. The first is that the start changed: the cache matches only identical content, in the order tool definitions, system prompt, conversation messages, and a change at one level invalidates that level and everything after it, so editing one tool's description loses the whole cache, and a rules file shouldn't start with something that changes every time, such as the current time. The second is stopping for too long: the default cache lives 5 minutes and is renewed for free each time it's used, so if you go to a meeting, it expires. The third is a start that's too short: below the minimum length nothing is cached, and you get no error. For Sonnet 5.5 the minimum is 512 tokens, and some older models need 4,096. If you keep missing the cache, the cost goes back to around $0.65 or even higher, because a cache write costs more than normal input.

你的錢花到哪去了

選模型的時候，大家一般都從價目表開始：Sonnet 5.5 每百萬個輸入 token 2 美元、輸出 token 10 美元，Opus 5.5 是 4 美元和 20 美元（Pricing，2026 年 10 月底的價格）。token 是模型讀寫文字的單位，大致相當於一個短的英文單字或者單字的一部分，模型讀的叫輸入 token，寫的叫輸出 token，輸出通常貴得多。價目表的數字好查，所以大家都拿它來比，但是你其實不是在買 token，你買的是一件做完的事，比如修好一個 bug，所以要比的是這件事一共花了多少錢。這個數字和單價差得很遠，一是因為便宜的模型做砸了要再跑一遍，算下來可能比一次做對的貴模型還貴，二是因為 agent 用掉的 token 比你想的多得多，而且大部分花在讀上。

agent 裡的 token 都去了哪

在聊天裡，你發一個問題，模型回一段話，一次呼叫就結束了。agent 跑的是一個循環（agent 循環，和你能插手的地方）：模型說要讀一個檔案，程式讀完把結果送回去，模型再決定下一步，所以每拿到一個工具結果，模型都要被重新呼叫一次。模型在兩次呼叫之間沒有記憶，每次呼叫都要把到目前為止的整段對話重新送一遍，包括規則、需求、讀過的每個檔案和每個工具結果。這些內容都裝在上下文視窗裡，也就是模型一次能看到的全部文字，它有大小上限（上下文是一份預算），而你每呼叫一次，就要為裡面的內容付一次錢。

我們用整數算一筆帳，這些數字是我為了好算挑的，不是測出來的。假設規則加需求一共 10,000 個 token，每個工具結果再加 5,000 個，一個任務呼叫 10 次模型，每次寫 300 個 token。模型一共讀了 10,000 + 15,000 + …… + 55,000 = 325,000 個 token，寫的只有 3,000 個。換成錢差距一樣大：用 Sonnet 5.5 的價格，讀要 0.65 美元，寫只要 0.03 美元，輸出的單價雖然貴 5 倍，讀的量卻大了 100 多倍。循環跑得越久，錢就越往讀上偏，因為每多一次呼叫，前面所有的內容都要再讀一遍。

prompt 快取改變了這筆帳

每次呼叫的開頭幾乎都一樣，所以模型供應商做了 prompt 快取：它記住你輸入的開頭一段，下一次呼叫只要開頭一字不差，這一段就按很低的價格算。Anthropic 的價格是這樣的：寫入快取比一般輸入貴，5 分鐘的快取是 1.25 倍，1 小時的快取是 2 倍，讀快取便宜得多，大多數模型是輸入價的十分之一，Opus 5.5 和 Sonnet 5.5 是二十分之一（Prompt caching）。

還是上面那個例子，用 Sonnet 5.5 的價格，假設快取每次都命中。第一次呼叫把 10,000 個 token 寫入快取，後面九次呼叫，每次從快取讀之前的全部內容，九次加起來是 270,000 個 token，再把新增的 5,000 個寫入快取，九次加起來是 45,000 個。算下來寫入花 0.1375 美元，讀快取花 0.027 美元，一共約 0.16 美元，只有原來 0.65 美元的四分之一。這 0.16 美元裡大部分是新內容的寫入費，快取省不掉，只有少讀才省得掉，所以就算快取每次都命中，少讀仍然是第一個該試的辦法。

快取也很容易失效，有三種情況。第一種是開頭變了：快取只認一字不差的內容，順序是工具定義、系統提示、對話訊息，哪一層變了，這一層和它後面的全部都命中不了，所以改一個工具的描述，整個快取就沒了，規則檔開頭也別放目前時間這種每次都變的東西。第二種是停得太久：預設的快取只活 5 分鐘，每用一次會免費續期，你去開個會回來，它就過期了。第三種是開頭太短：不到最小長度就不快取，也不報錯，Sonnet 5.5 的下限是 512 個 token，有些舊模型要 4,096 個。一直命中不了的話，成本就回到 0.65 美元附近，甚至更高，因為寫入快取比一般輸入還貴。

你的钱花到哪去了

选模型的时候，大家一般都从价目表开始：Sonnet 5.5 每百万个输入 token 2 美元、输出 token 10 美元，Opus 5.5 是 4 美元和 20 美元（Pricing，2026 年 10 月底的价格）。token 是模型读写文本的单位，大致相当于一个短的英文单词或者单词的一部分，模型读的叫输入 token，写的叫输出 token，输出通常贵得多。价目表的数字好查，所以大家都拿它来比，但是你其实不是在买 token，你买的是一件做完的事，比如修好一个 bug，所以要比的是这件事一共花了多少钱。这个数和单价差得很远，一是因为便宜的模型做砸了要再跑一遍，算下来可能比一次做对的贵模型还贵，二是因为 agent 用掉的 token 比你想的多得多，而且大部分花在读上。

agent 里的 token 都去了哪

在聊天里，你发一个问题，模型回一段话，一次调用就结束了。agent 跑的是一个循环（Agent 到底是怎么干活的？）：模型说要读一个文件，程序读完把结果发回去，模型再决定下一步，所以每拿到一个工具结果，模型都要被重新调用一次。模型在两次调用之间没有记忆，每次调用都要把到目前为止的整段对话重新发一遍，包括规则、需求、读过的每个文件和每个工具结果。这些内容都装在上下文窗口里，也就是模型一次能看到的全部文本，它有大小上限（为什么不能把所有规则都塞给 Agent？），而你每调用一次，就要为里面的内容付一次钱。

我们用整数算一笔账，这些数字是我为了好算挑的，不是测出来的。假设规则加需求一共 10,000 个 token，每个工具结果再加 5,000 个，一个任务调用 10 次模型，每次写 300 个 token。模型一共读了 10,000 + 15,000 + …… + 55,000 = 325,000 个 token，写的只有 3,000 个。换成钱差距一样大：用 Sonnet 5.5 的价格，读要 0.65 美元，写只要 0.03 美元，输出的单价虽然贵 5 倍，读的量却大了 100 多倍。循环跑得越久，钱就越往读上偏，因为每多一次调用，前面所有的内容都要再读一遍。

prompt 缓存改变了这笔账

每次调用的开头几乎都一样，所以模型提供方做了 prompt 缓存：它记住你输入的开头一段，下一次调用只要开头一字不差，这一段就按很低的价格算。Anthropic 的价格是这样的：写入缓存比普通输入贵，5 分钟的缓存是 1.25 倍，1 小时的缓存是 2 倍，读缓存便宜得多，大多数模型是输入价的十分之一，Opus 5.5 和 Sonnet 5.5 是二十分之一（Prompt caching）。

还是上面那个例子，用 Sonnet 5.5 的价格，假设缓存每次都命中。第一次调用把 10,000 个 token 写入缓存，后面九次调用，每次从缓存读之前的全部内容，九次加起来是 270,000 个 token，再把新增的 5,000 个写入缓存，九次加起来是 45,000 个。算下来写入花 0.1375 美元，读缓存花 0.027 美元，一共约 0.16 美元，只有原来 0.65 美元的四分之一。这 0.16 美元里大部分是新内容的写入费，缓存省不掉，只有少读才省得掉，所以就算缓存每次都命中，少读仍然是第一个该试的办法。

缓存也很容易失效，有三种情况。第一种是开头变了：缓存只认一字不差的内容，顺序是工具定义、系统提示、对话消息，哪一层变了，这一层和它后面的全部都命中不了，所以改一个工具的描述，整个缓存就没了，规则文件开头也别放当前时间这种每次都变的东西。第二种是停得太久：默认的缓存只活 5 分钟，每用一次会免费续期，你去开个会回来，它就过期了。第三种是开头太短：不到最小长度就不缓存，也不报错，Sonnet 5.5 的下限是 512 个 token，有些旧模型要 4,096 个。一直命中不了的话，成本就回到 0.65 美元附近，甚至更高，因为写入缓存比普通输入还贵。

How to add up a task's cost, and where to save

A task's cost has three parts: what the model reads (all calls added up, with cache hits discounted), what it writes (answers, code, thinking), and rework (wrong answers, lost threads, repeated attempts). Rework isn't a separate charge. It's a multiplier on the other two, because every time you redo something, you pay for both again. Most of the savings are at the two ends, reading and rework, and a good rule of thumb is to use the cheapest approach that's good enough.

When the expensive model is cheaper

An expensive model costs more per token, but if it gets the job right the first time, it can cost less per finished task. The math is simple: the cost of finishing a task is the cost of one run divided by the success rate. Opus 5.5 costs twice as much per token as Sonnet 5.5, so if one run uses about the same tokens on both, Opus is cheaper only when Sonnet's success rate is less than half of Opus's. If Opus gets 80% of tasks right, for example, Sonnet has to be below 40%. That's only the token bill. Add the time you spend watching it and cleaning up after it, and the break-even point moves further toward the expensive model. On the other hand, if the task is simple enough that both models get it right the first time, the expensive one is money wasted.

You can only measure success rates on your own tasks: run the same few tasks several times on both models, and compare the cost per success, not the cost per call (One run proves nothing).

Choose the model by the task, then check the reasoning effort

My own rule of thumb is a strong model for thinking, such as making a plan, working out an approach or digging into a hard bug, and a mid-level model for doing, such as a change the plan has already made clear. There's also a setting called reasoning effort (thinking effort), which controls how long the model thinks before it answers. More thinking usually means more output tokens and more time. In VS Code you set it in the model picker, through the arrow next to the model name, and models that don't support it don't show the option (AI language models). The highest setting isn't always better: in the LangChain experiment in What is Harness Engineering?, running at the top level throughout actually scored lower, because many tasks timed out.

How Copilot bills (as of late October 2026)

Since June 1, 2026, Copilot's monthly plans have been on usage-based billing. GitHub AI Credits replaced premium requests, 1 credit is worth $0.01, and usage is calculated from input, output and cached tokens at each model's published API rates. Pro, for example, is $10 a month and includes $10 of credits, and code completions and Next Edit suggestions don't use credits (GitHub blog, Usage-based billing). Annual Pro and Pro+ plans stay on the old premium request model until they expire, with 300 requests a month on Pro and 1,500 on Pro+. Each prompt you send counts as one request, times the model's multiplier, and the tool calls the agent makes on its own don't count (Copilot requests).

The two models encourage different habits. When you pay per request, a long autonomous run is cheap for you, so putting a big job into one prompt can be a good deal. When you pay per token, a run costs in proportion to what it reads, and the savings in this chapter matter a lot.

When the result is wrong, change the model last

When the result is wrong, the first idea that comes to mind is to switch to a bigger model, but that's the most expensive fix and it often doesn't help, so look first at what actually went wrong:

What went wrong Try first
It doesn't know a rule, a name, or how the project does something Write it into the rules or a knowledge file. A bigger model wouldn't know it either
It says "done" and it isn't Add a check: run the tests (Let the agent check its own work)
It loses the thread in a long session Start a new session and carry the state over in a file (Long chats get worse)
It knows everything and still reasons badly Now try a stronger model

Four ways to save, and how each can go too far

The first way comes before the three parts of the cost: don't call the model at all. The other three map to reading, writing and rework, and all four can go too far.

  1. Use the model less. If code can do it, don't ask the model. Counting, copying files, converting a Word file to text and checking a format are jobs a script does the same way every time, at no token cost. Going too far means handing a judgment call to code that can't judge (Who decides: code, a cheap model, the main model, a person).
  2. Read less. Keep rules short, load details when they're needed, and ask for a diff rather than a whole file. Going too far means the agent guesses when it lacks information, and the rework costs more than the reading you saved.
  3. Write less. Ask for a one-sentence conclusion or a short list. Going too far means the output is too thin for the next step to use.
  4. Redo less. Agree on a plan before starting, keep state in files so work survives a lost session, and put a limit on retries. Going too far means the limit cuts off useful work, so set it from what you've seen, not from what you fear.

There's also a fixed cost you pay on every call, whatever you choose during the task. Each of the agent's tools adds its name, description and parameters to the input of every call (Tool calling, and designing tools for an agent), and every rule you inject comes along on every turn, so remove the tools and rules you don't use.

When the bill surprises you

If the bill is higher than you expected, ask yourself three questions. First, which call or turn read the most? Look at your tool's usage page and at your biggest tasks. Second, what's in the context that doesn't need to be there, such as old tool results, big files read in full, or a long rules file? Third, was any task redone, and if so, why did the first attempt fail?

When you're choosing between two models, a small experiment is enough: pick a task you know the right answer to, run it three times on each model, record the usage and whether the result was right, and compare the cost per success. Don't decide from one run. A four-column table will do:

怎麼算一個任務的成本，又該從哪裡省

一個任務的成本分三部分：模型讀的（所有呼叫加起來，快取命中的部分打折），模型寫的（回答、程式碼、思考），還有重做（錯誤的回答、丟了的線索、重複的嘗試）。重做不是單獨的一筆錢，它是前兩部分的乘數，重做一次，前兩部分就要再付一遍。能省的大多在讀和重做這兩頭，一條好用的經驗法則是用夠用的辦法裡最便宜的那個。

什麼時候貴模型反而便宜

貴模型每個 token 貴，但是如果它一次就做對，算到每個做完的任務上可能反而便宜。算法很簡單，做完一個任務的成本等於跑一次的成本除以成功率。Opus 5.5 的單價是 Sonnet 5.5 的 2 倍，假設兩者跑一次用的 token 差不多，那麼只有當 Sonnet 的成功率不到 Opus 的一半時，Opus 才更便宜，比如 Opus 能做對 80% 的任務，Sonnet 要低於 40%。這只是 token 的帳，如果再算上你盯著它、幫它收拾的時間，這個點還會往貴模型那邊挪。反過來，如果任務本來就簡單，兩個模型都能一次做對，用貴的就是白花錢。

成功率只能在你自己的任務上測：拿同樣的幾個任務，在兩個模型上各跑幾遍，比較每次成功的成本，而不是每次呼叫的成本（一次運行證明不了什麼）。

按任務選模型，再看一眼推理強度

我自己的經驗法則是思考用強模型，比如定計畫、想思路、啃難的 bug，動手用中等的模型，比如做一處計畫已經很清楚的改動。另外還有一個設定叫推理強度（thinking effort），它控制模型回答之前想多久，想得越多，通常輸出的 token 越多，花的時間也越長。在 VS Code 裡，點模型選擇器裡模型名字旁邊的箭頭就能選，不支援的模型不顯示這一項（AI language models）。開到最高不一定更好，什麼是 Harness Engineering？裡 LangChain 的實驗就是全程用最高檔的分數反而更低，因為很多任務逾時了。

Copilot 怎麼計費（截至 2026 年 10 月底）

Copilot 的月繳方案從 2026 年 6 月 1 日起改成了按用量計費：premium request 被 GitHub AI Credits 取代，1 個 credit 等於 0.01 美元，用量按輸入、輸出和快取的 token 計算，價格是每個模型公布的 API 費率，比如 Pro 每月 10 美元，含 10 美元的額度，程式碼補全和 Next Edit 建議不占額度（GitHub blog、Usage-based billing）。年繳的 Pro 和 Pro+ 到期之前還用舊的 premium request 模式，Pro 每月 300 次，Pro+ 每月 1,500 次，你發的每個 prompt 算一次，再乘上模型的倍率，agent 自己做的工具呼叫不算（Copilot requests）。

這兩種模式鼓勵的習慣不一樣。按請求計費時，一次很長的自主執行對你來說很便宜，所以把一個大任務放進一個 prompt 裡做可能很划算；按 token 計費時，一次執行花多少錢和它讀了多少成正比，這一章講的省錢辦法就非常要緊。

結果不對時，最後才換模型

結果不對的時候，最容易想到的就是換一個更大的模型，但這是最貴的辦法，而且常常沒用，所以換之前先看看到底出了什麼問題：

出了什麼問題 先試什麼
它不知道一條規則、一個名字，或者專案裡的做法 寫進規則或知識檔。更大的模型一樣不知道
它說「做完了」，其實沒有 加一道檢查：跑測試（讓 agent 能檢查自己的活）
在長會話裡它丟了線索 開一個新會話，把狀態放在檔案裡帶過去（長對話會變差）
它什麼都知道，推理還是不行 這時再試更強的模型

四個省錢的辦法，以及各自怎樣會過頭

第一個辦法排在成本的三部分之前，乾脆不呼叫模型，後三個分別對應讀、寫和重做，而且四個辦法都可能做過頭。

  1. 少用模型。程式能做的就別問模型，計數、複製檔案、把 Word 檔轉成文字、檢查格式，這些工作腳本每次都做得一樣，而且不花 token。做過頭是把需要判斷的事交給了不會判斷的程式（誰來判斷：程式、便宜模型、主模型、人）。
  2. 少讀。規則寫短，細節需要時才載入，要 diff 不要整個檔案。做過頭是它缺資訊就去猜，重做的錢比省下的讀取還多。
  3. 少寫。讓它給一句話的結論或者一份簡短的清單。做過頭是輸出簡略到下一步用不上。
  4. 少重做。動手前先商定計畫，把狀態放在檔案裡，會話丟了也能接著做，再給重試的次數設個上限。做過頭是上限卡掉了有用的工作，所以上限要根據你見到的情況來定，不要根據擔心來定。

還有一類固定成本，不管你在任務裡怎麼選，每次呼叫都要付。agent 的每個工具都會把名字、描述和參數加進每次呼叫的輸入裡（Tool calling，和給 agent 設計工具），你注入的每條規則也每一輪都跟著走，所以用不上的工具和規則要拿掉。

怎么算一个任务的成本，又该从哪里省

一个任务的成本分三部分：模型读的（所有调用加起来，缓存命中的部分打折），模型写的（回答、代码、思考），还有返工（错误的回答、丢了的线索、重复的尝试）。返工不是单独的一笔钱，它是前两部分的乘数，返工一次，前两部分就要再付一遍。能省的大多在读和返工这两头，一条好用的经验法则是用够用的办法里最便宜的那个。

什么时候贵模型反而便宜

成功率只能在你自己的任务上测：拿同样的几个任务，在两个模型上各跑几遍，比较每次成功的成本，而不是每次调用的成本（同一个任务跑两次，结果不一样）。

四个省钱的办法，以及各自怎样会过头

第一个办法排在成本的三部分之前，干脆不调用模型，后三个分别对应读、写和返工，而且四个办法都可能做过头。

  1. 少用模型。代码能做的就别问模型，计数、复制文件、把 Word 文件转成文本、检查格式，这些活脚本每次都做得一样，而且不花 token。做过头是把需要判断的事交给了不会判断的代码（这个判断该交给谁：代码、便宜模型、主模型，还是人？）。
  2. 少读。规则写短，细节需要时才加载，要 diff 不要整个文件。做过头是它缺信息就去猜，返工的钱比省下的读取还多。
  3. 少写。让它给一句话的结论或者一个简短的清单。做过头是输出简略到下一步用不上。
  4. 少返工。动手前先商定计划，把状态放在文件里，会话丢了也能接着做，再给重试的次数设个上限。做过头是上限卡掉了有用的工作，所以上限要根据你见到的情况来定，不要根据担心来定。

Saving has costs too, and the easiest trap is reading too little

The easiest trap to fall into is reading too little. The cheapest call may well be the one that guessed wrong and got thrown away, so if a task keeps failing for lack of context, the fix is to give it the right context, not less of it.

Controls cost money too: a hook that runs on tool calls adds a little delay, an independent check means another model call, and a rule injected into every prompt costs tokens on every prompt. I accept these on purpose in exchange for control, but they're still costs.

The prices and Copilot's billing above are as of late October 2026, and they will change. What gets counted changes too, as Copilot's move from counting requests to counting tokens showed.

省錢也有代價，最容易踩的坑是讀得太少

最容易踩的坑是讀得太少。最便宜的呼叫，恰恰可能是猜錯了然後被丟掉的那一次，如果一個任務總是因為缺上下文而失敗，該做的是給它正確的上下文，而不是給得更少。

控制手段本身也要花錢：在工具呼叫上執行的 hook 會帶來一點延遲，獨立檢查要再呼叫一次模型，每個 prompt 都注入的規則，每個 prompt 都要花 token。我是為了控制而有意接受這些的，但它們終究是成本。

另外，上面的價格和 Copilot 的計費方式都是 2026 年 10 月底的情況，它們還會變，而且變的不只是價格，還有收費時數的是什麼，Copilot 這次就從數請求改成了數 token。

省钱也有代价，最容易踩的坑是读得太少

最容易踩的坑是读得太少。最便宜的调用，恰恰可能是猜错了然后被扔掉的那一次，如果一个任务总是因为缺上下文而失败，该做的是给它正确的上下文，而不是给得更少。

控制手段本身也要花钱：在工具调用上运行的 hook 会带来一点延迟，独立检查要再调用一次模型，每个 prompt 都注入的规则，每个 prompt 都要花 token。我是为了控制而有意接受这些的，但它们终究是成本。

另外，上面的价格和 Copilot 的计费方式都是 2026 年 10 月底的情况，它们还会变，而且变的不只是价格，还有收费时数的是什么，Copilot 这次就从数请求改成了数 token。

Model providers charge this way too Industry practice

Anthropic prices cache reads at a small fraction of normal input and states that tool definitions count as input tokens on every request (Prompt caching, Tool use). GitHub moved Copilot from per-request to per-token billing (GitHub blog). The market now charges by what the model reads and writes, which is why counting cost per task is what lines up with the bill.

模型供應商也是這樣收費的 業界做法

Anthropic 把讀快取的價格定得只有一般輸入的一小部分，並且說明工具定義在每次請求裡都按輸入 token 計算（Prompt caching、Tool use）。GitHub 把 Copilot 從按請求計費改成了按 token 計費（GitHub blog）。市場現在是按模型讀和寫了多少來收費的，所以按任務算成本，這筆帳才對得上帳單。

模型提供方也是这么收费的 业界做法

Anthropic 把读缓存的价格定得只有普通输入的一小部分，并且说明工具定义在每次请求里都按输入 token 计算（Prompt caching、Tool use）。GitHub 把 Copilot 从按请求计费改成了按 token 计费（GitHub blog）。市场现在是按模型读和写了多少来收费的，所以按任务算成本，这笔账才对得上账单。

When to delete these cost-saving tricks Industry practice

Much of this chapter is advice for a world where reading is expensive. If reading ever gets so cheap that trimming context takes more effort than it saves, drop these tricks and keep only the habit of counting the cost of each finished task. And if a platform starts showing the cost of each task by itself, I'll think again, because then you'll have less to guess.

什麼時候可以刪掉這些省錢技巧 業界做法

這一章的很多內容，是寫給讀取很貴的世界的建議。如果有一天讀取便宜到，精簡上下文多花的功夫比省下的還多，那就把這些技巧丟掉，只留下核算每個完成任務的成本這個習慣。另外，如果哪個平台開始自己顯示每個任務的成本，我也會重新考慮，因為到那時，你需要猜的就少了。

上手：把仓库 clone 下来，用 VS Code 打开，在 Copilot Chat 里输入 /harness-rookie-get-me-ready。需要 Python 3.9 及以上版本和 git。

Explore it in the harness

My harness is built around reading less and redoing less. Rules are loaded in layers, state lives in files, and checks are off unless you ask for them. It also says plainly what it cannot see about cost. The harness can open the real files with you and show each of these from the inside.

Once you have set it up as described above, type:

/harness-rookie-wondering I have read the chapter "Don't pick a model by token price alone". Teach me how this harness reads less, writes less and redoes less, and what it can and cannot tell me about the real usage of a task. Open the real files with me and draw how the pieces fit together.

It teaches one small piece at a time, stops to check that you are following, and opens the files with you.

在 harness 裡探索

我的 harness 就是圍繞少讀、少重做搭起來的：規則分層載入，狀態放在檔案裡，檢查除非你要求，否則是關的。在成本上它看不到什麼，它也說得很直白。harness 可以和你一起打開真實的檔案，從裡面把這些一項項指給你看。

照上面的說明準備好之後，輸入：

/harness-rookie-wondering 我讀完了「選模型，別只看 token 單價」這一章。請教我這個 harness 怎麼少讀、少寫、少重做，以及它能和不能告訴我一個任務的真實用量。帶我打開真實的檔案，並畫出各部分怎麼接在一起。

它會一次教一小塊，停下來確認你跟上了，再和你一起打開檔案。

在 harness 里探索

我的 harness 就是围绕少读、少返工来搭的：规则分层加载，状态放在文件里，检查你不要求就不开。在成本上它看不到什么，它也说得很直白。harness 可以和你一起打开真实的文件，从内部把这些一一指给你看。

按上面的说明准备好之后，输入：

/harness-rookie-wondering 我读完了“选模型，别只看 token 单价”这一章。请教我这个 harness 是怎么少读、少写、少返工的，以及它能告诉我、不能告诉我一个任务的真实用量的哪些方面。带我打开真实的文件，并画出各部分是怎么连起来的。

它会一次只教一小块，停下来确认你跟上了，再和你一起打开文件。
