4.3

Guard the files that hold the rules保護規則本身的檔案别让 Agent 改自己的规则

This chapter assumes you have read Asking is not a limit: a limit is a refusal the agent cannot argue with.

這一章假設你讀過詢問不是限制：限制是 agent 吵不贏的拒絕。

读这一章，请先读过“先问我”为什么挡不住 Agent？：限制，就是 agent 辩不过的拒绝。

The Knowledge經驗分享经验分享

In one sentence

If the agent can edit the rules, the rules mean nothing. So keep the rule files and the hook files out of its reach, and make any human override last one session, expire, and leave a record.

一句話

agent 能改規則，規則就沒有意義。所以要把規則檔和 hook 檔放到它碰不到的地方。人給的任何 override，都只管一個會話，會過期，還要留下紀錄。

一句话

agent 如果能改规则，规则就等于没有。所以要把规则文件和 hook 文件放到它够不着的地方。人给的任何 override，都只管一个会话，会过期，还要留下记录。

For leaders

  • The decision: decide that the agent may not edit the files that hold its rules, its hooks or its evidence, and that any human override is limited to one session, expires and leaves a record.
  • The risk: a rule the agent can edit is a rule it can remove, and a "passed" record it can write is a pass it can give itself. I have no incident to report, so the case rests on the argument, not on a count.
  • The cost of doing it right: a list of protected files, kept up to date as parts are added, plus a way for a person to open the fence on purpose. My own override depends on a person remembering to switch it off. A time limit and a second reader would be better, but I do not have them.
  • Ask the team: "Can the agent edit the files that hold its own rules and records, and can you show me a refusal when it tries?"

給主管

  • 要做的決定：決定 agent 不能編輯存放它自己規則、hook 和證據的檔案；人給的任何 override，只限一個會話，會過期，並留下紀錄。
  • 風險：agent 能改的規則，它就能刪掉；它能寫的「通過」紀錄，就是它能自己給自己的通過。我沒有事故可報告，所以這裡靠的是論證，不是次數。
  • 做對的成本：一份受保護檔案的清單，每加一個新元件就跟著更新，再加上一個讓人刻意打開圍欄的辦法。我自己的 override 要靠人記得關掉。有時間限制、再有第二個人來讀會更好，可是這兩樣我都沒有。
  • 可以問團隊：「agent 能不能編輯存放它自己規則和紀錄的檔案？它試的時候，你能給我看一次被拒絕的紀錄嗎？」

写给管理者

  • 要拍板的事：决定 agent 不许编辑存放它的规则、hook 和证据的那些文件，并且人给的任何 override 都只限一个会话、会过期、会留下记录。
  • 风险：agent 能改的规则，它就能删掉；它能写的“通过”记录，就是它能自己发给自己的通过。我没有事故可以报告，所以这里靠的是论证，不是次数。
  • 做对的代价：一份受保护文件的清单，每加一个新部件就要跟着更新，再加上一个让人有意打开围栏的办法。我自己的 override 靠人记得去关。有时间限制、再有第二个人来读会更好，可这两样我都没有。
  • 可以问团队：“agent 能编辑存放它自己的规则和记录的文件吗？它试的时候，你能给我看一次被拒绝的情形吗？”

What if the agent edits the rule?

Say you have a hook that refuses dangerous commands. It works. Now ask where that hook lives. It lives in a file, and so does the configuration that tells the platform to run it. The numbers it uses are in a file too. And the agent has an edit tool.

The agent does not need bad intent to change those files. Picture one that is stuck behind a refusal and under pressure to finish its task. It sees that the rule is in the way and does the sensible-looking thing, which is to loosen the rule. A rule the agent can edit is a rule the agent can remove. I have no incident to report and did not measure how often agents try to edit rules, so the point rests on the argument alone.

Records have the same weakness. If a check leaves a "passed" file and the agent can write that file, then the agent can pass itself. So the question is not only which commands are refused. It is also who can change the things that do the refusing and the proving.

In both cases the threat is mostly a careless agent, not a hostile one. An agent led by injected text is a second case (Text the agent reads can give it orders), one that needs the same fence and more.

I call the files that must be out of the agent's reach guardrail files. Together they are a fence, in the sense that the agent works inside it and cannot move it. That raises three questions: which files belong in the fence, how it is held, and how a person gets through when the rules themselves must change.

If you only do one thing after this chapter, make the rule files and the hook files unwritable for the agent.

agent 要是改了規則呢？

假設你有一個會拒絕危險指令的 hook，它也確實管用。現在問一句：這個 hook 放在哪裡？放在一個檔案裡。告訴平台要執行它的設定，同樣是一個檔案，它用到的那些數字也在檔案裡。而 agent 手上有編輯工具。

其實 agent 去改這些檔案，並不需要什麼惡意。設想它被一條拒絕卡住，又趕著把任務做完，看到規則擋了路，就做了一件看起來很合理的事：把規則放鬆。agent 能編輯的規則，agent 就能刪掉。我沒有事故可報告，也沒有量過 agent 多常想編輯規則，所以這裡只靠這個論證。

同樣，紀錄也有這個弱點。如果檢查留下一個「通過」的檔案，而 agent 能寫這個檔案，那它就能讓自己通過。所以要問的不只是「哪些指令被拒絕」，還有「誰能改那些負責拒絕、負責證明的東西」。

不管是規則還是紀錄，威脅多半來自一個粗心的 agent，而不是懷有惡意的 agent。被注入的文字帶偏的 agent 是另一種威脅（agent 讀到的文字可能在指揮它），它需要同樣的圍欄，而且還要更多。

這些必須放在 agent 碰不到的地方的檔案，我叫它們護欄檔案。它們合起來是一道圍欄，意思是 agent 在裡面工作，卻移不動它。那麼，哪些檔案該圍進去？圍欄怎麼守住？規則本身真的要改的時候，人又怎麼進去？

讀完這一章，如果你只做一件事，那就是讓規則檔和 hook 檔對 agent 不可寫。

agent 要是改了规则呢？

假设你有一个拒绝危险命令的 hook，它也确实管用。现在问一句：这个 hook 放在哪？放在一个文件里。告诉平台去运行它的配置，同样是一个文件，它用到的那些数字也在文件里。而 agent 手里有编辑工具。

其实 agent 去改这些文件，并不需要什么恶意。设想它被一条拒绝挡住了，又急着把任务做完，它看到规则挡了路，就做了一件看上去很合理的事：把规则放松。agent 能编辑的规则，agent 就能删掉。我没有事故可以报告，也没有量过 agent 多久会尝试编辑规则，所以这里只靠这个论证。

同样，记录也有这个弱点。如果一次检查留下一个“通过”的文件，而 agent 能写这个文件，那它就能让自己通过。所以要问的不只是“哪些命令被拒绝”，还有“谁能改动那些负责拒绝和负责证明的东西”。

不管是规则还是记录，威胁多半来自一个粗心的 agent，而不是怀有恶意的 agent。被注入的文本带偏的 agent 是另一种威胁（Agent 读到的网页和文件，可能在给它下命令），它需要同样的围栏，而且还要更多。

这些必须放在 agent 够不着的地方的文件，我叫它们护栏文件。它们合起来是一道围栏，意思是 agent 在里面干活，却挪不动它。那么，哪些文件该围进去？围栏怎么守住？规则本身真要改的时候，人又怎么进去？

读完这一章，如果你只做一件事，那就是让规则文件和 hook 文件对 agent 不可写。

How the fence is built, and how a person gets through

Which files are the fence

In my setup the fence is made of these files:

  • the hook configuration, the file that tells the platform which hook to run;
  • the engine, the code of the hook itself, and the commands the agent is allowed to call;
  • the policies, the plain files that hold the numbers and patterns of the rules;
  • the runtime state, the files the hook writes while it runs: session state, approval records and logs;
  • the editor settings that could switch the hooks off;
  • the license files of the repository.

You might expect instruction files and skills on the list, but they are not. They are text for the agent to read, a request rather than a limit. Changing them does not change what the code refuses.

How the fence is held

Once the list is set, every way the agent could write to those files has to be stopped. How hard that is depends on the tool. Edit tools are the easy case, because the path is in the call and the hook can refuse the call before it runs.

The terminal is harder, because the same write can be spelled in many ways. The hook catches the common spellings, such as a redirect, rm, mv, sed -i, cp and tee. But the limits from Asking is not a limit apply here too, so an indirect spelling is not caught.

Even the path needs care, because the same file can be written with other letter case, with .., as an absolute path, or with the backslash of Windows. If the rule compared paths as they came, the fence would have gaps in the spelling, so it brings them all to one form before it compares. Two more gaps are worth checking in your own setup, although I have not tested either: a symbolic link that points into a guarded folder and a disk that ignores letter case.

One more rule governs the list itself. A company can add paths to it, but it cannot take the defaults away, because an override that removed a default would be the same hole as an agent that can edit the rule.

All of this guards against mistakes. It is not a sandbox, because an agent set on getting round it can do so with a script it writes first. For the strong version, see Least privilege.

Files only a command may write

Rules are not the only files worth guarding. Some files are evidence: the state of a task, the verdicts of the independent checks (Can a model check a model?), snapshots (copies of files taken at a point in time), the diff an approval is based on and the final report.

If the agent could write them, it could declare a check passed, or change what was approved. So the agent never writes them with its edit tools. A command writes them instead and judges the result itself. When I say "the agent recorded a result", I mean that the agent asked the command to record it and the command made the decision.

Folders that hold what the person brought follow the same rule. Documents, reference code and results from a run are for the agent to read. The person writes them, through a page or a command. Evidence that the agent could edit is not evidence.

The breaker

A fence that holds brings a new problem. When a refusal keeps coming, an agent may keep trying. A hook cannot stop it, because all a hook can do is refuse a call. So when the same refusal comes up three times in a row (three is my setting), the breaker trips and replaces the reason with a different one: stop trying this, and tell the person. That is still a request, in the form of a message, but it is all a hook can do. It also keeps the log from filling with the same refusal.

When a person must open the fence

Sometimes, though, the rules themselves have to change. When I extend the harness, I change guardrail files, so there must be a way in. The question is how to give that right to a person without giving it to the agent.

My first thought was to let one named agent edit the fence. That does not work in Copilot today, because the event a hook receives does not carry the name of the main agent (Hooks). Since the hook cannot tell which agent is calling, any agent could pass for the named one. Rights that follow a name can be claimed by anyone who uses the name.

So the right follows the session instead, set by the person. It rests on a switch in the state of the session that only the person can turn on, by typing a code in their own terminal. The agent cannot run that command: if it tries, the hook refuses it. This is the same channel as in Two gates.

Four things make the override safe:

  1. It belongs to a session, not to an agent, so it ends with that session.
  2. It is turned off when the work is done. My rule is to switch it off and then read, in git, the diff of what changed.
  3. It leaves a record. While it is on, every logged call is marked as admin.
  4. Some doors stay shut even then. In my setup even admin cannot write the runtime state, which holds the approval records, because if it could, it could forge an approval. And in the same session no task can be opened and no subagent called.

Each of these removes a way that a short exception turns into a standing hole. The second, though, is also the weak point of the design. There is no timer in my setup, so switching admin off depends on a person remembering. A time limit is a better design, and the approval of git writes already uses one. For a team, add an expiry and a second person who reads the diff.

Test your own setup

In a copy of your project, ask your agent to loosen one rule in its own hook configuration. If it succeeds, your rules are a request, so protect the file and try again.

圍欄怎麼搭，人又怎麼進去

哪些檔案是圍欄

在我的設定裡，圍欄由這些檔案組成：

  • hook 設定，告訴平台要執行哪個 hook 的檔案；
  • 引擎，也就是 hook 本身的程式碼，以及 agent 被允許呼叫的指令；
  • 政策，存放規則的數字和模式的純文字檔；
  • 執行期狀態，hook 執行時寫出的檔案：會話狀態、批准紀錄和日誌；
  • 能把 hook 關掉的編輯器設定；
  • 倉庫的授權檔案。

你也許以為指令檔和 skill 也在清單上，其實不在。它們是寫給 agent 讀的文字，是請求，不是限制。改了它們，程式拒絕的東西並不會變。

圍欄怎麼守住

清單定下來以後，agent 寫這些檔案的每一條路都得堵住，至於難不難，就要看是什麼工具了。編輯工具最好辦，因為路徑就在呼叫裡，hook 在呼叫執行之前就能拒絕。

終端機就難多了，因為同一次寫入可以有很多種寫法。hook 攔得住常見的寫法，例如重新導向、rm、mv、sed -i、cp、tee。不過詢問不是限制裡說的那些限制在這裡一樣存在，所以間接的寫法攔不到。

就連路徑本身也得小心。同一個檔案，可以換個大小寫來寫，可以帶 ..，可以寫成絕對路徑，也可以用 Windows 的反斜線。如果規則拿到路徑就直接比較，圍欄在寫法上就會有縫，所以它先把這些寫法變成同一種形式，再去比較。你自己的設定裡還有兩個縫值得檢查：指向受保護資料夾的符號連結，以及不分大小寫的磁碟。這兩個我都沒有測過。

還有一條規矩管的是清單本身。公司可以往清單裡加路徑，但不能拿掉預設的，因為一個能拿掉預設項的 override，和一個能編輯規則的 agent 是同一個漏洞。

說到底，這些只防失誤，算不上沙箱，因為一個鐵了心要繞過去的 agent，先寫好一個腳本就繞得過去。想要更強的做法，見有些東西根本不給。

只有指令能寫的檔案

值得守的檔案不只是規則。有些檔案是證據：任務的狀態、獨立檢查的裁決（模型能檢查模型嗎）、快照（在某個時間點複製下來的檔案）、批准所依據的 diff，還有最終報告。

這些檔案要是 agent 能寫，它就能宣布一次檢查通過，或者改掉已經批准的內容。所以它們從不由 agent 的編輯工具來寫，而是交給一個指令，結果也由這個指令自己判斷。我說「agent 記錄了一個結果」，意思是 agent 請指令去記錄，做決定的是指令。

人帶進來的東西，放在資料夾裡也是同樣的道理。文件、參考程式碼、一次運行的結果，都是給 agent 讀的，寫它們的則是人（透過一個頁面或一個指令）。agent 能編輯的證據，就不是證據。

斷路器

圍欄守住了，又會冒出一個新問題：拒絕一次次出現，agent 可能就一次次地試。hook 沒辦法讓它停下來，因為 hook 能做的只有拒絕一次呼叫。所以同一個拒絕連續出現三次時（三是我的設定），斷路器就會跳開，把拒絕的原因換成另一句：別再試這個了，去告訴人。這仍然只是一個請求，以訊息的形式出現，不過已經是 hook 能做的全部了。另外，它也讓日誌不會被同一個拒絕塞滿。

什麼時候要由人打開圍欄

可是有時候，規則本身就是得改。我擴充 harness 的時候，就會改護欄檔案，所以必須留一條路進去。問題是，怎麼把這個權利交給人，又不交給 agent？

我一開始想的是讓一個指定名字的 agent 去編輯圍欄。在今天的 Copilot 裡這行不通，因為 hook 收到的事件不帶主 agent 的名字（Hooks：每次呼叫都會經過的執行點）。hook 分不出是哪個 agent 在呼叫，任何 agent 都能冒充那個名字。權利跟著名字走，誰用了這個名字，誰就能拿到它。

所以權利改成跟著會話走，由人來設定。它靠的是會話狀態裡的一個開關，只有人能打開：在自己的終端機裡輸入一組驗證碼。agent 不能執行那條指令，它要是試，hook 就會拒絕。這和兩道門：人在哪裡批准用的是同一個管道。

讓這個 override 安全的有四點：

  1. 它屬於一個會話，不屬於某個 agent，所以會話結束，它也就結束了。
  2. 工作做完就關掉。我的規則是先關掉它，再用 git 讀一遍改了什麼的 diff。
  3. 它會留下紀錄。開著的時候，每一次被記錄的呼叫都會標上 admin。
  4. 即使這時，有些門也仍然關著。在我的設定裡，連 admin 也不能寫執行期狀態，那裡存著批准紀錄，要是能寫，它就能偽造批准。而且在同一個會話裡，不能打開任何任務，也不能呼叫子 agent。

每一點都堵住了一條路，免得短期的例外變成長期的漏洞。不過，第二點同時也是這個設計的弱點：我的設定裡沒有計時器，關掉 admin 要靠人記得。更好的做法是加時間限制，git 寫入的批准就已經這樣做了。如果是團隊，就要加上過期，再加一個讀 diff 的第二個人。

測一下你自己的設定

在你專案的副本裡，請你的 agent 去放鬆它自己 hook 設定裡的一條規則。要是它成功了，你的規則就是一個請求，那就把這個檔案保護起來，再試一次。

围栏怎么搭，人又怎么进去

哪些文件是围栏

在我的配置里，围栏由这些文件组成：

  • hook 配置，告诉平台去运行哪个 hook 的那个文件；
  • 引擎，也就是 hook 本身的代码，以及允许 agent 调用的命令；
  • 策略，存放规则里的数字和模式的普通文件；
  • 运行时状态，hook 运行时写下的文件：会话状态、审批记录和日志；
  • 能把 hook 关掉的编辑器设置；
  • 仓库的许可证文件。

你也许以为指令文件和 skill 也在清单上，其实不在。它们是写给 agent 读的文本，是请求，不是限制。改了它们，代码会拒绝什么并不会变。

围栏是怎么守住的

清单定下来以后，agent 写这些文件的每一条路都得堵上，至于难不难，就要看是什么工具了。编辑工具最好办，因为路径就在调用里，hook 在调用执行之前就能拒绝。

终端就难多了，因为同一次写入可以有很多种写法。hook 能拦住常见的写法，比如重定向、rm、mv、sed -i、cp、tee。不过“先问我”为什么挡不住 Agent？里说的那些局限在这里同样存在，所以间接的写法拦不住。

就连路径本身也得小心。同一个文件，可以换个大小写来写，可以带 ..，可以写成绝对路径，也可以用 Windows 的反斜杠。如果规则拿到路径就直接比较，围栏在写法上就会有缺口，所以它先把这些写法统一成一种形式，再去比较。在你自己的配置里还有两个缺口值得查一查：指向受保护文件夹的符号链接，以及不区分大小写的磁盘。这两个我都没有测过。

还有一条规矩管的是清单本身。公司可以往清单里加路径，但不能把默认的去掉，因为一个能去掉默认项的 override，和一个能编辑规则的 agent 是同一个漏洞。

说到底，这些只防失误，算不上沙箱，因为一个铁了心要绕过去的 agent，先写好一个脚本就能绕过。要更强的做法，见不要开放全部的权限或使用沙箱。

只有命令才能写的文件

值得守的文件不只是规则。有些文件是证据：任务的状态、独立检查的结论（让另一个模型来审，靠得住吗？）、快照（在某个时间点给文件做的拷贝）、一次审批所依据的 diff，还有最终报告。

这些文件要是 agent 能写，它就能宣布一次检查通过了，或者改掉已经批准的内容。所以它们从不由 agent 的编辑工具来写，而是交给一条命令，结果也由这条命令自己判断。我说“agent 记录了一个结果”，意思是 agent 请命令去记录，拍板的是命令。

人带进来的东西，放在文件夹里也是同样的道理。文档、参考代码、一次运行的结果，都是给 agent 读的。写它们的是人（通过一个页面或一条命令）。agent 能改的证据，就不算证据。

熔断器

围栏守住了，又会冒出一个新问题：拒绝一次次出现，agent 可能就一次次地试。hook 没法让它停下来，因为 hook 能做的只有拒绝一次调用。所以，当同一个拒绝连续出现三次（三是我的设置），熔断器就会跳闸，把拒绝的理由换成另一条：别再试这个了，去告诉人。这仍然只是一个请求，以消息的形式出现，不过已经是 hook 能做的全部了。另外，它也让日志不会被同一条拒绝塞满。

人必须打开围栏的时候

可有时候，规则本身就是得改。我扩展 harness 的时候，就要改护栏文件，所以必须留一条路进去。问题是，怎么把这个权利交给人，又不交给 agent？

我一开始想的是让一个指定的 agent 去编辑围栏。在今天的 Copilot 里这行不通，因为 hook 收到的事件里没有主 agent 的名字（硬性规则放在哪？用 hook）。hook 分不清是哪个 agent 在调用，任何 agent 都可以冒充那个指定的 agent。权利跟着名字走，谁用了这个名字，谁就能拿到它。

所以权利改成跟着会话走，由人来设定。它靠的是会话状态里的一个开关，只有人能打开：在自己的终端里输入一个验证码。agent 运行不了那条命令，它要是试，hook 就会拒绝。这和哪些事必须由人来批？里用的是同一个渠道。

让这个 override 安全的有四点：

  1. 它属于一个会话，不属于某个 agent，所以会话结束，它也就结束了。
  2. 工作做完就关掉。我的规则是先把它关掉，再用 git 读一遍改了什么的 diff。
  3. 它会留下记录。开着的时候，每一条记入日志的调用都会标成 admin。
  4. 即便这时，有些门也始终关着。在我的配置里，就连 admin 也不能写运行时状态，那里面存着审批记录，要是能写，它就能伪造一次审批。而且在同一个会话里，不能打开任何任务，也不能调用子 agent。

每一点都堵上了一条路，免得短暂的例外变成长期的漏洞。不过，第二点同时也是这个设计的弱点：我的配置里没有计时器，关掉 admin 要靠人记得。更好的做法是加时间限制，git 写入的审批就已经这样做了。如果是团队，就要加上过期时间，再加一个读 diff 的第二个人。

检验你自己的配置

在你项目的一份拷贝里，让你的 agent 去放松它自己 hook 配置里的一条规则。要是它成功了，你的规则就是一个请求，那就把这个文件保护起来，再试一次。

Where the fence can still fail

Does a fence that passes that test hold everywhere? Not quite, and there are three places where it can still leak. The first is its list. A guardrail file missing from the list is open, so when you add a part to the engine, add its path too.

The second is the way through the fence, which is also a gap in it. Admin is real power: it can change the engine, so what it does is not hard-limited. The control is a person reading the diff afterwards, and I do not claim more than that.

The third is spelling. Because the terminal is guarded by pattern, in theory a spelling the hook does not know could change a record that lives in a task folder (the folder that holds one piece of work; see Manage tasks, not chats). I have not tried to build one. The fix, again, is to keep what must never be touched out of reach altogether.

One more trap is not a hole but a puzzle. If the agent hits a refusal on a file it does not know is guarded, the reason must say so and say what to do. The previous chapter covers how to write that reason.

圍欄還會在哪裡失守

通過了這個測試，圍欄是不是就萬無一失？還不是，還有三個地方會漏。第一處在清單本身：圍欄只守得住清單上列出的檔案，不在清單上的護欄檔案就是開著的。所以給引擎加新元件的時候，記得把它的路徑也加進去。

第二處是穿過圍欄的那條路，它本身也是一個缺口。admin 是實實在在的權力：它能改引擎，所以它做什麼都沒有硬性限制。能管住它的，只有事後有人讀一遍 diff，除此之外，我不說它還有別的保障。

第三處在寫法上。終端機是按模式防護的，所以理論上，一種它不認識的寫法，可能改動放在任務資料夾裡的紀錄（存放一件工作的資料夾；見管任務，不管對話）。我沒有試著做出這樣一種寫法。解法還是那一個：把絕對不能碰的東西，整個放到碰不到的地方。

還有一個陷阱，算不上漏洞：圍欄要是 agent 看不見，它碰上了也不知道為什麼被擋。這時，拒絕的原因裡就得說明這個檔案受保護，並說清楚該怎麼做。這個原因怎麼寫，上一章講過。

围栏还会在哪里失守

通过了这个检验，围栏是不是就万无一失了？还不是，还有三个地方会漏。第一处在清单本身：围栏只守得住清单上列出的文件，漏掉的护栏文件就是敞开的。所以给引擎加新部件的时候，记得把它的路径也加进去。

第二处是穿过围栏的那条路，它本身也是一个缺口。admin 是实打实的权力：它能改引擎，所以它做什么都没有硬性的限制。能管住它的，只有事后有人读一遍 diff，除此之外，我不说它还有别的保障。

第三处在写法上。终端是靠模式来守的，所以理论上，一种它不认识的写法，可能改动放在任务文件夹里的记录（任务文件夹存放一项工作；见一个任务一个文件夹）。我没有试过去造这样一种写法。办法还是那一个：把绝不能碰的东西，彻底放到够不着的地方。

还有一个坑，算不上漏洞：围栏要是 agent 看不见，它撞上了也不知道为什么被拦。这时，拒绝的理由里就得说明这个文件受保护，并说清该怎么办。这个理由怎么写，上一章讲过。

Why "out of reach" and not "safe" Industry practice

How far can a fence made of hooks be trusted? VS Code's hooks page says hooks and instructions are not substitutes for enforced permissions or sandboxing, and its security page recommends sandboxing over approval rules alone (hooks, security). The trouble is that a fence made of hooks stands inside the same machine the agent runs on. So this chapter says "out of reach" and not "safe".

為什麼說「碰不到」，不說「安全」 業界做法

那麼，用 hook 做成的圍欄，能信到什麼程度？VS Code 的 hooks 頁面說，hooks 和指令不能代替強制的權限或沙箱；它的 security 頁面也建議用沙箱，不要只靠批准規則（hooks、security）。問題在於，用 hook 做的圍欄，和 agent 立在同一台機器上。所以這一章只說「碰不到」，不說「安全」。

为什么说“够不着”，而不说“安全” 业界做法

那么，用 hook 搭起来的围栏，能信到什么程度？VS Code 的 hooks 页面说，hook 和指令不能替代强制执行的权限或沙箱；它的安全页面也建议用沙箱，而不是单靠审批规则（hooks、security）。问题在于，用 hook 搭的围栏，和 agent 立在同一台机器上。所以这一章只说“够不着”，不说“安全”。

When the list of guarded paths can go Industry practice

The same point tells you when the list can go. If the agent runs in an environment where the rule files are mounted read-only, or the hook runs outside the machine the agent can touch, the list of guarded paths is not needed, because the environment is the fence. Keep the other lesson even then: any override a person grants should be bound to the session, time-limited, and recorded.

什麼時候可以刪掉受保護路徑的清單 業界做法

同一個道理，也告訴你這份清單什麼時候可以刪。如果 agent 跑在一個規則檔以唯讀方式掛載的環境，或者 hook 跑在 agent 碰不到的那台機器之外，就不需要受保護路徑的清單，因為環境本身就是圍欄。另一條教訓到那時也要留著：人給的任何 override，都應該綁在會話上、有時間限制，並留下紀錄。

什么时候可以删掉受保护路径的清单 业界做法

同一个道理，也告诉你这份清单什么时候可以删。如果 agent 运行的环境里，规则文件是只读挂载的，或者 hook 运行在 agent 碰不到的那台机器之外，受保护路径的清单就用不着了，因为环境本身就是围栏。另一条经验到那时也要留着：人给出的任何 override，都应该绑定到会话、有时间限制，并且留下记录。
