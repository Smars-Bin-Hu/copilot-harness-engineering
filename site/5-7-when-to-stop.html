5.7

Unattended: when it must stop無人值守：什麼時候必須停无人值守：什么时候必须停

This chapter picks up the unattended run from Use subagents sparingly, where a hook keeps the agent working down a to-do list while nobody watches. That chapter showed how such a run keeps going. This one is about how it ends.

這一章接著 慎用子 agent 裡的無人值守的執行往下講：一個 hook 讓 agent 在沒人看著的時候，沿著待辦清單一直做下去。那一章講的是這樣的執行怎麼跑起來，這一章講它怎麼結束。

这一章接着慎用子 agent里的无人值守的运行往下讲：一个 hook 让 agent 在没人看着的时候，沿着待办清单一直干下去。那一章讲的是这样的运行怎么跑起来，这一章讲它怎么收场。

The Knowledge經驗分享经验分享

In one sentence

An unattended agent goes only as far as its stop rules reach. Set them in advance, as a total budget and not only a step count, and guard against the agent declaring the job done too early.

一句話

無人值守的 agent，只會走到停止規則管得到的地方。所以要事先把規則設好，設成總預算，而不只是步數，同時還要防著它太早宣布「做完了」。

一句话

无人值守的 agent，只能走到它的停止规则管得到的地方。所以要提前把规则设好，用总预算，而不只是步数，同时还要防着它过早宣布“做完了”。

For leaders

  • The decision: before approving an unattended run, set its stop rules in advance, as a total budget and not only a step count, and require a stop to hand back a reason.
  • The risk: once you leave, you are no longer the stop rule. The run could loop for hours, spend a night's usage on a step that cannot succeed, or stop early and say it is finished. My setup has step and time limits but no total budget yet, and I call unattended runs beta. I have not measured whether an unattended run beats a person watching to the end.
  • The cost of doing it right: a few rules and one budget number per task. The price of tight rules is more stops, and a person on call in the morning. A vague hand-back, on the other hand, costs more time than watching would have.
  • Ask the team: "If this runs overnight and goes wrong, what stops it, and what will I find in the morning?"

給主管

  • 要做的決定：批准無人值守的執行之前，先設好它的停止規則，要設成總預算，不只是步數，並要求每次停止都交回一個原因。
  • 風險：你一離開，就不再是那條停止規則了。這次運行可能繞上好幾個小時，可能把一整晚的用量花在一個不可能成功的步驟上，也可能太早停下來，還說自己做完了。我的設定有步數和時間的上限，但還沒有總預算，我也把無人值守的執行稱為 beta。無人值守的執行是否勝過有人看到最後，我沒有量過。
  • 做對的成本：每個任務幾條規則，加上一個預算數字。規則收得緊，代價是停得更多，早上要有一個人待命。反過來，交回的東西要是含糊，花的時間比在旁邊看著還多。
  • 可以問團隊：「如果這個整晚在跑，結果出了問題，什麼會讓它停下來？早上我會看到什麼？」

写给管理者

  • 要拍板的事：批准无人值守的运行之前，先把它的停止规则设好，用总预算，而不只是步数，并要求每次停下都交回原因。
  • 风险：你一走，就不再是那条停止规则了。运行可能循环好几个小时，可能在一个注定成不了的步骤上烧掉一晚上的用量，也可能提前停下，还说自己做完了。我的配置有步数和时间的限制，但还没有总预算，我也把无人值守的运行叫作 beta。无人值守的运行是否比人盯到最后更好，我没有测过。
  • 做对的代价：每个任务几条规则，加一个预算数字。规则收得紧，代价是停得更多，早上得有人待命。反过来，交回的东西要是含糊，比盯着看还费时间。
  • 可以问团队：“如果这个任务通宵跑、中途出了问题，什么会让它停下来？我早上会看到什么？”

When you leave, who stops the run?

When you watch an agent, you are its stop rule. You see it go wrong, and you press stop. When you leave, that rule leaves with you. What remains is whatever you wrote down before going.

So the question to ask of an unattended run is not "will it work?" but "what happens when it does not?" It could loop for hours, or spend a night's worth of usage on a step that cannot succeed. It could reach a choice that only you can make and make it anyway. Or it could do the opposite and stop early, saying it is finished.

Each of these needs a different rule, set before you leave. Together they come down to three questions. When must the run stop, what does it hand back when it does, and how do we know it is really done?

你離開以後，誰來喊停？

你看著 agent 的時候，你就是它的停止規則。看到它出錯，你就按停止。可是你一離開，這條規則也跟著你走了，剩下的只有你離開前寫下來的東西。

所以對無人值守的執行，該問的不是「它會成功嗎？」，而是「它不成功的時候會怎樣？」它可能繞上好幾個小時，也可能把一整晚的用量花在一個不可能成功的步驟上。碰到只有你能做的選擇，它可能自己就做了決定。它也可能反過來，太早停下來，說自己做完了。

這幾種情況各需要一條不同的規則，而且都得在你離開之前設好。歸納起來是三個問題：它什麼時候必須停？停下來時交回什麼？我們怎麼知道它真的做完了？

你走了以后，谁来叫停？

你盯着 agent 的时候，你就是它的停止规则。看到它跑偏了，你就按停。可你一走，这条规则也跟着你走了，剩下的只有你走之前写下的东西。

所以对无人值守的运行，该问的不是“它行不行”，而是“不行的时候会怎样”。它可能循环好几个小时，也可能在一个注定成不了的步骤上烧掉一晚上的用量。碰上只有你才能做的选择，它可能自己就拍了板。它还可能反过来，提前停下，说自己做完了。

这几种情况各需要一条不同的规则，而且都得在你走之前设好。归结起来是三个问题：运行什么时候必须停？停下时交回什么？我们怎么知道它真的做完了？

When it stops, what it hands back, and when it is really done

Each stop rule catches one way to go wrong

The first question, when the run must stop, has several answers, because each stop rule catches a different way a run goes wrong. What the rules share is one principle: code judges them from facts, not the agent. An agent that is stuck is the worst judge of whether it is stuck.

Three of the rules you have already met in Use subagents sparingly: a cap on steps and time, a stop after the guardrails refuse the agent twice in a run, and a stop when no step gets ticked. (A step is one item on the to-do list. This stop rule is not the breaker of Guard the files that hold the rules, which reacts to one refusal repeating inside a session.) Their numbers are there too. Those are the numbers in my setup, and they are examples, not wisdom: I chose them, and I have not measured whether they are the right ones.

Two more can be judged from facts in the same way. One is a change of plan: the run is allowed to carry out the plan the person approved, so if the plan changes, the permission ends at once. The other is running out of checks: the independent check keeps failing until its limit is reached (Make a pass count).

The last kind is different, because some stops cannot be seen in the facts. Say two tables define a field differently and the plan does not say which to use. Only the agent can see that, so it may stop itself, but only with a reason and only for the cases that need a person, not for small choices.

A budget is a total, not a count

All the rules above count things, whether steps or refusals. But what you are afraid of is spending, which a count does not limit. Twenty small steps and twenty steps that each launch helpers are not the same bill.

What limits spending is a budget, a total over usage and time that covers the main agent and all its helpers together. A helper gets what is left rather than a new allowance of its own. As soon as either line, usage or time, is crossed, the run stops.

My own setup does not have this yet (it has the counts above and a time limit), but here is a way to build it. The person sets one task-level budget, in usage and minutes. Before each step, a hook adds up the usage of the main session and every helper session from the platform's own session record. At the line, it stops the run and writes "budget" as the reason. Whether the helpers' usage shows up in that record in time to stop on, I have not checked.

And a budget in usage is not quite a budget in money: input the provider has cached is read at about a tenth of the base price (Models and cost; how Copilot bills it, I have not checked).

Some tools already offer a simple version for non-interactive runs, though I have not tried them. Claude Code has --max-turns and --max-budget-usd, both for print mode (claude -p) only. The money cap is checked against a client-side estimate rather than your bill and can be passed. Spend from subagents counts toward it, and once it is reached no new subagent can start (CLI reference).

What the person coming back should find

Whichever rule fires, a person will come back to a run that has stopped. If it stopped without saying why, what they find is a puzzle. So a stop has to hand back three things:

  1. Why it stopped, in a word the person can act on: budget, refused, no progress, needs a decision.
  2. Where it is: the steps done, the step it was on, and the state of the work.
  3. What a person has to decide, in one sentence.

In my setup, the code writes the reason when it stops on facts, while the agent writes one sentence when it stops itself. The instruction for that sentence asks which step is stuck, why, and what you must decide. "Ran into a problem" is not enough.

The decisions the agent made along the way matter too. For anything the plan left open and the agent chose, it writes a line saying what it chose and why. That log, read when the person returns, is what makes unattended work reviewable.

When "done" comes too early

So far the worry has been a run that does not stop when it should. The opposite failure is just as real: a run that stops too soon and calls itself finished. Anthropic described it in a long-running coding agent, where "a later agent instance would look around, see that progress had been made, and declare the job done" (Effective harnesses for long-running agents).

After all, stopping is what the agent was asked to do, so it has a reason to say it is done. That is why the end of a run goes by facts that code can check, not by the agent's word:

  • Every step on the list is ticked.
  • The independent check passed, counted by code, on the version of the work as it is now.
  • The plan is the one that was approved.
  • The write-back plan is made, for a person to read (Two gates).

Only then is "done" a state, not a claim.

Even this is not airtight, because an agent can tick a step without finishing it. The checker reads the whole result at the end and the person reads the whole diff, but nothing in code proves that step 7 was really done. That is why I treat ticks as claims and the end-of-run check as the thing that counts.

什麼時候停、交回什麼、怎樣才算真的做完

每條停止規則，抓一種出錯的方式

第一個問題，什麼時候必須停，答案不只一個，因為每一條停止規則抓的是運行出錯的一種方式。這些規則有一個共同的原則：由程式根據事實來判斷，不是由 agent。卡住的 agent，最沒資格判斷自己是不是卡住了。

其中三條你已經在 慎用子 agent 裡見過，分別是步數和時間的上限、一次運行中圍欄拒絕 agent 兩次就停止、沒有任何一步被勾掉就停止，具體的數字也在那一章裡。（一步是待辦清單上的一項。這條停止規則不是 保護規則本身的檔案 裡的斷路器，斷路器處理的是一個會話裡同一個拒絕一再重複。）那些是我設定裡的數字，只是例子，不是什麼定論：是我選的，我也沒有量過它們對不對。

另外兩條，同樣可以根據事實來判斷。一條是計畫變了。人批准的是一份計畫，這次運行只被允許執行那份計畫，所以計畫一變，授權立刻失效。另一條是檢查用完了：獨立檢查一直失敗，直到碰上它的上限（讓「通過」可信）。

最後一種不一樣，因為有些停止是事實顯示不出來的。比方說兩張表對同一個欄位的定義不同，計畫又沒說該用哪個，這一點只有 agent 看得到。所以它可以自己停下來，但必須附上原因，而且只限於需要人的情況，不能為了小選擇就停。

預算是總量，不是次數

上面這些規則數的都是東西，不是步數就是拒絕次數。可是你真正擔心的是花費，而次數限制不了花費。二十個小步驟和二十個各自啟動幫手的步驟，帳單根本不是一回事。

能限制花費的是預算，也就是對用量和時間的一個總量，把主 agent 和它所有的幫手合在一起算。幫手拿到的是剩下的部分，不是自己另有一份新的額度。用量和時間，只要越過其中一條線，運行就停止。

我自己的設定還沒有這個（它有上面那些次數限制和一個時間上限），不過可以這樣建。由人設一個任務層級的預算，用量和分鐘數各一個。每一步之前，一個 hook 從平台自己的會話紀錄，把主會話和每個幫手會話的用量加起來，到了那條線就停止運行，並把「budget」寫成原因。至於幫手的用量會不會及時出現在紀錄裡、讓它來得及據以停止，我沒有檢查過。

而且，按用量算的預算，並不完全等於按錢算的預算：供應商快取過的輸入，讀取的價格大約是基本價格的十分之一（選模型：算的是每次成功的成本），只是 Copilot 怎麼計費，我沒有檢查過。

有些工具已經為非互動的執行提供了簡單的版本。Claude Code 有 --max-turns 和 --max-budget-usd（我自己沒試過），兩者都只用於 print 模式（claude -p）。金額上限是拿用戶端的估計值來比對，不是你的帳單，而且可能被超過。子 agent 的花費也算進去，一旦達到上限，就不能再啟動新的子 agent（CLI reference）。

回來的人該看到什麼

不管是哪條規則觸發的，回來的人面對的都是一次已經停下來的運行。它要是不說原因就停了，留給人的就是一個謎。所以一次停止要交回三樣東西：

  1. 為什麼停止，用一個人能據以行動的詞：budget、refused、no progress、needs a decision。
  2. 現在在哪裡：做完的步驟、它正在做的那一步，以及工作的狀態。
  3. 人要決定什麼，用一句話。

在我的設定裡，根據事實停止時，原因由程式寫，而 agent 自己停止時，則由 agent 寫一句話。那一句話的指令是：哪一步卡住、為什麼、你必須決定什麼。只寫「遇到了問題」是不夠的。

agent 一路上做過的決定也很重要。計畫沒定、由 agent 選的任何事，它都要寫一行，說明選了什麼、為什麼。這份紀錄，人回來時會讀，無人值守的工作也正是靠它才能被審查。

「做完了」說得太早

前面擔心的，都是該停的時候不停。反方向的失敗一樣真實：運行停得太早，還說自己做完了。Anthropic 在一個長時間運行的寫程式 agent 上描述過這種情況：「後來的 agent 實例會看一圈，見到已經有進展，就宣布工作完成」（Effective harnesses for long-running agents）。

說到底，停下來本來就是交給 agent 的事，所以它說「做完了」是有來由的。正因為這樣，運行能不能結束，要看程式能核對的事實，不看 agent 怎麼說：

  • 清單上的每一步都勾了。
  • 獨立檢查通過了，由程式計數，針對工作目前的版本。
  • 計畫就是被批准的那份。
  • 寫回的計畫已經做好，給人讀（兩道門：人在哪裡批准）。

到這時，「做完了」才是一個狀態，不是一個說法。

即使這樣也不是密不透風，因為 agent 可以勾掉一步卻沒做完。檢查者在最後讀整個結果，人讀整份 diff，但程式裡沒有任何東西證明第 7 步真的做了。所以我把勾當成說法，把運行結束時的檢查當成算數的東西。

什么时候停，交回什么，怎样才算真做完

每条停止规则，抓一种出错的方式

第一个问题，什么时候必须停，答案不止一个，因为每条停止规则抓的是运行出错的一种方式。这些规则有一个共同的原则：由代码根据事实来判断，不由 agent 判断。一个卡住的 agent，最没资格判断自己是不是卡住了。

其中三条你已经在慎用子 agent里见过，分别是步数和时间的上限、一次运行里护栏拒绝了 agent 两次就停、没有任何一步被勾掉就停，具体数字也在那一章里。（一步是待办清单上的一项。这条停止规则不是保护规则本身的文件里的熔断器，那个熔断器针对的是同一个会话里同一次拒绝反复出现。）那些是我配置里的数字，只是例子，算不上什么真理：是我选的，我也没有测过它们合不合适。

另外两条，同样可以根据事实来判断。一条是计划变了。人批准的是一份计划，运行只被允许执行这份计划，所以计划一变，授权立刻失效。另一条是检查次数用完了：独立检查一直不通过，直到达到它的上限（见让“通过”可信）。

最后一种不一样，因为有些停止是事实显示不出来的。比如两张表对同一个字段的定义不一样，计划里又没说用哪个，这一点只有 agent 看得到。所以它可以自己停，但必须写明原因，而且只限于需要人的情况，小事不行。

预算是总量，不是次数

上面这些规则数的都是东西，不是步数就是拒绝次数。可你真正怕的是花费，而次数限制不了花费。二十个小步骤和二十个每步都启动帮手的步骤，账单根本不是一回事。

能限制花费的是预算，也就是对用量和时间的一个总量，把主 agent 和它所有的帮手合在一起算。帮手拿到的是剩下的部分，而不是自己另有一份额度。用量和时间，只要越过其中一条线，运行就停。

我自己的配置还没有这个（它有上面那些次数限制和一个时间限制），不过可以这样搭。由人给每个任务设一个预算，用量和分钟数各一个。每一步之前，hook 根据平台自己的会话记录，把主会话和每个帮手会话的用量加起来，到了线就停下运行，把“预算”写成原因。至于帮手的用量能不能及时出现在记录里、赶得上叫停，我没有查过。

而且，按用量算的预算，并不完全等于按钱算的预算：服务商已缓存的输入，读取价格约是基础价格的十分之一（见选模型：看每次成功的成本），只是 Copilot 怎么计这部分，我没有查过。

有些工具已经为非交互的运行提供了简单的版本。Claude Code 有 --max-turns 和 --max-budget-usd（我自己没试过），都只用于 print 模式（claude -p）。金额上限对照的是客户端的估算，不是你的账单，而且可能被超过。子 agent 的花费也算在里面，一旦达到上限，就不能再启动新的子 agent（见 CLI reference）。

回来的人该看到什么

不管是哪条规则触发的，回来的人面对的都是一次已经停下的运行。它要是不说明为什么停，留给人的就是一个谜。所以停下时必须交回三样东西：

  1. 为什么停，用一个人能据此行动的词：预算、被拒绝、没有进展、需要决定。
  2. 走到哪了：做完的步骤、正在做的那一步，以及工作的状态。
  3. 人要决定什么，一句话。

在我的配置里，由事实触发的停止，原因由代码来写，而 agent 自己停的时候，则由它写一句话。这句话的指令是：哪一步卡住了，为什么，你要决定什么。光写“遇到了问题”是不够的。

agent 一路上做的决定也很重要。计划没定、由 agent 自己选的每一处，它都要写一行，说明选了什么、为什么。这份日志，人回来时会读，无人值守的工作也正是靠它才能被复核。

“做完了”说得太早

前面担心的，都是该停的时候不停。反方向的失败同样真实：运行停得太早，还说自己做完了。Anthropic 在一个长时间运行的编程 agent 上描述过这种情况：“后来的 agent 实例四下看看，发现已经有了进展，就宣布任务完成”（Effective harnesses for long-running agents）。

说到底，停下来本来就是交给 agent 的事，所以它说“做完了”是有来由的。正因为这样，运行能不能结束，得看代码能核对的事实，不看 agent 怎么说：

  • 清单上的每一步都勾掉了。
  • 独立检查通过了，由代码计数，针对的是工作现在的这个版本。
  • 计划就是当时批准的那一份。
  • 写回计划已经做好，供人阅读（见两道门：人在哪里审批）。

到这时，“做完了”才是一种状态，而不是一个声明。

即便这样也不严密，因为 agent 可以不完成就勾掉一步。检查者在最后读整个结果，人读整个 diff，但没有任何代码能证明第 7 步真的做了。所以我把勾当作声明，把运行结束时的检查当作算数的东西。

What safety costs, and what stop rules cannot do

All of this makes a run safer, but it is not free. The more rules a run has, the fewer wins it brings home. A run with tight stop rules will stop on many nights and hand back little, so the price of safe is a person on call in the morning. I have not measured whether an unattended run is better than a person watching to the end. That is why my setup still calls it beta.

And a stop is not an answer: each one leaves the work half done. The snapshots taken at the gates (Two gates) let a person look at the state the run stopped in. Even so, a vague hand-back costs the person more time than watching would have.

Some work, though, should not run unattended at all, however good the stop rules are. The three points of Two gates apply here: work that spends real money, grants power such as writing to a shared repository, or cannot be undone needs a person.

The last trap is for the agent rather than for you: taking a detour to avoid a refusal. A refusal is the system telling you that a step is out of scope, so the rule I give the agent is to change the step once as the reason says, then stop if that does not work.

安全的代價，和停止規則做不到的事

這些規則讓運行更安全，但不是免費的。規則越多，能一口氣跑完的晚上就越少：收得緊的運行，很多個晚上都會中途停下，交回的東西不多，早上得有人待命接手。安全的代價就落在這裡。無人值守的執行是否比有人看到最後更好，我沒有量過，所以它在我的設定裡還被稱為 beta。

停止也不等於有了答案：每一次停下來，留下的都是做了一半的工作。在門上拍下的快照（兩道門：人在哪裡批准），能讓人看到運行停下來時的狀態。即使如此，交回的內容要是含糊，人反而得花比在旁邊看著更多的時間。

不過，有些工作根本不該無人值守，不管停止規則多好都一樣。兩道門：人在哪裡批准 的那三個點在這裡同樣適用：花真錢的、授予權限的（例如寫入共用的倉庫）、無法復原的工作，都需要人。

還有一個陷阱是留給 agent 的，不是留給你的：為了避開拒絕而繞路。拒絕是系統在說：這一步超出了範圍。所以我給 agent 的規則是：照原因說的改一次，還是不行，就停下來。

安全的代价，和停止规则做不到的事

这些规则让运行更安全，但不是白来的。规则越多，能一口气跑完的晚上就越少：收得紧的运行，很多个晚上都会中途停下，交回的东西不多，早上得有人待命接手。安全的代价就落在这里。无人值守是否比人盯到最后更好，我没有测过，所以它在我的配置里还叫 beta。

停下也不等于有了答案：每一次停下，留下的都是做了一半的活。在关卡处拍下的快照（见两道门：人在哪里审批），能让人看到运行停下时的状态。即便如此，交回的内容要是含糊，人花的时间还是比盯着看更多。

不过，有些活根本不该无人值守，不管停止规则多好都一样。两道门：人在哪里审批里的三点在这里同样适用：花真钱的、授予权力的（比如写入共享仓库）、无法撤销的活，都需要人。

还有一个坑是留给 agent 的，不是留给你的：为了躲开拒绝而绕路。拒绝是系统在说：这一步超出了范围。所以我给 agent 定的规则是：按理由说的改一次，还不行，就停。

When to delete these rules, and what stays

The stop rules exist because the platform does not provide them. If the platform gives you a total budget over the whole run, helpers included, use it. The idea of stopping on facts stays either way: the agent's "I'm done" is not a finish line.

什麼時候刪掉這些規則，什麼會留下

這些停止規則之所以存在，是因為平台沒有提供它們。如果平台給你一個涵蓋整次運行、包括幫手的總預算，就用它。不管怎樣，根據事實停止的想法都會留下：agent 的「我做完了」不是終點線。

什么时候删掉这些规则，什么会留下

这些停止规则之所以存在，是因为平台没有提供它们。如果平台提供覆盖整个运行（包括帮手）的总预算，就用平台的。不管怎样，基于事实来停的想法都会留下：agent 说的“我做完了”不是终点线。
