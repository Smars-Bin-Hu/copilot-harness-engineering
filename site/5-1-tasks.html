5.1

Manage tasks, not chats管任務，不管對話一个任务一个文件夹

This chapter assumes you have used an AI coding agent, and that you know a hook is code the platform runs before a tool call (Hooks).

這一章假設你用過 AI 程式 agent，並且知道 hook 是平台在工具呼叫之前執行的程式碼（Hooks：每次呼叫都會經過的執行點）。

读这一章，你要用过 AI 编程 agent，还要知道 hook 是平台在工具调用之前运行的代码（见 硬性规则放在哪？用 hook）。

The Knowledge經驗分享经验分享

In one sentence

Manage tasks, not chats: one folder per task. What the work could break decides which gates it passes; its kind decides what counts as done.

一句話

管任務，不管對話：一個任務一個資料夾。這件事可能弄壞什麼，決定它要過哪些門；它的種類，決定怎樣才算做完。

一句话

管任务，不管对话：一个任务一个文件夹。工作可能弄坏什么，决定它要过哪些关卡；工作的类型，决定怎样才算做完。

For leaders

  • The decision: approve the job, not the chat, as the unit of work. That means one folder per task with a handover file, and care that follows what a mistake could break.
  • The risk: a chat gets shortened or ends, and a new one knows nothing. The other trap is process that is too heavy. My first design had a heavy level with a team of role agents, and in a small test it cost about 4.5 times the usage and 6 times the time, with no gain on tasks with a clear request (four tasks, one run each, so read the direction, not the ratio).
  • The cost of doing it right: the first step is only a folder per task with one handover file. More files are added only when the task earns them, and quick questions open nothing. In return, the agent must keep the files true, and a person has to read them when it matters.
  • Ask the team: "If the agent's chat disappeared tonight, could someone pick the job up tomorrow from files alone?"

給主管

  • 要做的決定：批准把一件事、而不是一段對話，當作工作的單位。具體來說，就是一個任務一個資料夾，附一份交接檔，謹慎的程度跟著出錯可能弄壞什麼走。
  • 風險：對話會被縮短或結束，新的對話什麼也不知道。另一個陷阱是流程太重。我的第一版設計有一個重的等級，帶一組分角色的 agent，在一個小測試裡，它花了約 4.5 倍的用量和 6 倍的時間，在需求明確的任務上卻沒有任何好處（四個任務，各跑一次，所以讀方向，不要讀倍數）。
  • 做對的成本：第一步只是每個任務一個資料夾，裡面一份交接檔。任務值得時才加更多檔案，隨口問的問題什麼都不開。相對地，agent 必須讓檔案保持真實，要緊的時候也得有人去讀。
  • 可以問團隊：「如果 agent 的對話今晚消失了，明天有人能只靠檔案接著做這件事嗎？」

写给管理者

  • 要拍板的事：批准把任务，而不是对话，当作工作的单位。具体来说，就是一个任务一个文件夹，带一份交接文件，谨慎的程度跟着“出错可能弄坏什么”走。
  • 风险：对话会被压缩，会结束，新开的对话什么都不知道。另一个陷阱是流程太重。我最初的设计里有一个重的级别，用一组按岗位分工的 agent，一次小测试下来，它多花了约 4.5 倍的用量和 6 倍的时间，在需求清楚的任务上却没有任何收益（四个任务，每个只跑了一次，所以看方向，别看倍数）。
  • 做对的代价：第一步只是每个任务一个文件夹、里面一份交接文件。任务值得的时候才加更多文件，随口一问什么都不开。相应地，agent 得让这些文件保持真实，要紧的时候也得有人去读。
  • 可以问团队：“如果今晚 agent 的对话没了，明天有人只靠文件就能把这件事接着做下去吗？”

If not the chat, what holds the work?

Say you ask an agent to change a pipeline. It reads, makes a plan and starts editing, and the chat grows as it goes. The next morning you open a new chat to ask a follow-up, but the new agent has never seen the first one. Or the tool has shortened the first chat in the meantime, and the agent no longer remembers why it chose what it chose (Long chats get worse).

Either way, the chat turns out to be the wrong thing to manage. It gets compressed, it ends, and one chat can hold three unrelated jobs. What you actually care about is the job itself: what was asked, what was decided, how far it has got and whether it was checked.

So I stopped treating the chat as the unit of work. The unit is a task, one job with one task folder. The requirement, the plan, the progress and the results are all files in that folder, so any session, today or next week, picks the task up by reading the folder.

That settles where the work lives. It is also the whole of the first step: one folder per task, with one handover file in it. Everything below is what I added on top of that, and you can add it one piece at a time.

But a second question follows, because not every job needs the same care. Fixing a typo in a note is not the same as writing to a shared repository, and the two should not get the same amount of process.

對話靠不住，工作要放在哪裡？

假設你請一個 agent 改一條 pipeline。它讀了一圈，做了規劃，開始動手編輯，對話也跟著越來越長。第二天早上，你開了一個新對話想問個後續問題，可是新的 agent 從沒見過第一個對話。又或者，第一個對話在這段時間裡已經被工具縮短了，agent 再也想不起自己當初為什麼那樣選（長對話會變差）。

說到底，這兩種情況都是管錯了對象。對話會被壓縮，會結束，而且一個對話裡可能放著三件毫不相干的工作。你真正在乎的是工作本身：被要求做什麼、決定了什麼、做到哪裡了、有沒有被檢查過。

所以我不再把對話當成工作的單位，單位改成了任務：一件事，一個任務資料夾。需求、計劃、進度和結果都是這個資料夾裡的檔案，所以不管是今天還是下週，任何會話只要讀這個資料夾，就能接手這個任務。

這樣一來，工作放在哪裡的問題就解決了，而這也就是第一步的全部：每個任務一個資料夾，裡面一份交接檔。下面的一切，都是我在這個基礎上加的，你可以一次加一塊。

可是接著就冒出第二個問題，因為不是每件事都需要同樣的謹慎。改筆記裡的一個錯字，和寫進共用的倉庫，不是同一回事，兩者也不該走一樣多的流程。

对话靠不住，工作放在哪里？

假设你让 agent 改一条 pipeline。它读了一圈，做了计划，开始动手编辑，对话也跟着越拉越长。第二天早上，你开了一个新对话想问个后续问题，可新的 agent 从没见过第一个对话。又或者，第一个对话在这期间已经被工具压缩过了，agent 已经不记得当初为什么那样选（见对话越久，Agent 越笨）。

说到底，这两种情况都是管错了东西。对话会被压缩，会结束，一个对话里还可能装着三件毫不相干的事。你真正在乎的是这件事本身：被要求做什么、决定了什么、做到了哪一步、检查过没有。

所以我不再把对话当作工作的单位，单位改成了任务：一件事，对应一个任务文件夹。需求、计划、进度和结果都是这个文件夹里的文件，所以不管是今天还是下周，任何一个会话读一读文件夹，就能接手这个任务。

这样，工作放在哪里的问题就解决了，而这也就是第一步的全部：每个任务一个文件夹，里面一份交接文件。下面的一切，都是我在这个基础上加的，你可以一块一块地往上加。

可接着就来了第二个问题，因为不是每件事都需要同样的谨慎。改笔记里的一个错别字，和往共享仓库里写东西，不是一回事，两者也不该走一样多的流程。

How much process does each job get?

My first answer was levels, and it was wrong

My first answer was three levels, from a light level 1 up to a heavy level 3 with a team of role agents (Use subagents sparingly). You picked one at the start of every job.

After some use, three things were clear. The first was that only the middle level got used, while the other two sat idle most of the time. The second was that the heavy level did not earn its weight. On tasks with a clear request it was no better than one agent, yet it cost about 4.5 times the usage and 6 times the time. The test behind that was small, four tasks with one run each, so read the direction rather than the ratio (Use subagents sparingly). The third was that having to choose first added one more step every time. Worse, with two sets of rules side by side, the agent got unsure, and gave wrong explanations of which one applied.

The deepest problem, though, was in the idea itself. How hard a job is cannot be known before you start, but a level asks you to guess it up front.

So I removed the levels. Care is now decided by two other things, neither of which asks you to guess difficulty.

Care follows what a mistake costs

The first of the two is what the action can break. Nobody has to pick it, because code makes a rough judgment of it from the paths and commands. That judgment is a heuristic, not a proof, and the section on the folder below says where it can be fooled.

What the work does Example How it is guarded
Reads only A question, a look-up in notes Nothing stops it
Changes the task folder Writing an analysis, a design, a plan Nothing stops it
Changes a real repository Code, a knowledge base (A knowledge base: an honest index of the code) It is written in the folder first. Writing it back needs a person to approve (Two gates)
Touches git history or production Commit, push, switch branch Stopped by a hook; a person approves, and some commands are always refused

This is the same idea as the grading in Asking is not a limit: the more a mistake costs, the harder the stop. A stop like that is a gate, a point the task cannot pass until a person approves (Two gates).

The kind sets the standard for done

The second thing is the kind of task, which says what counts as done, because a question and a code change are not finished in the same way.

Kind Done when
Question The answer has a source
Root-cause analysis There is a chain of evidence: what was seen, the logs, the cause, how it was verified
Design or plan There are options and a reason for the choice
Development The change matches the approved plan, and there is a record of testing it
Testing The cases and their results are on disk
Knowledge update The source is clear, and it goes through the same write-back gate (Two gates)

Without a list like this, "done" is whatever the agent feels like saying. With it, a reader and a checker both know what to look for (Counted checks).

The size sets how many files the folder has

Those two settle how carefully a task is guarded and when it is done. They do not settle how much paperwork it carries. That differs too, since a question does not need a requirement file, a plan and a to-do list, but a development task does. So each task also has a size. It is not a third measure of care, because it decides nothing except which files the folder holds.

  • Light: one handover file, saying how far the task is, what the next step is and what has been decided.
  • Medium: adds the requirement and its source documents, reference material, and a log.
  • Full: adds a to-do list, a working copy of the code, and test results.

Each kind starts at a default size, and a task that grows can be raised, with the missing files added then, but it never goes down. That keeps the cheap path cheap, while the heavy path is still there when a task earns it. You might wonder whether this is the old levels coming back under a new name. It is not, because nobody guesses the size at the start. The kind sets it, and it only moves up when the work shows it needs more.

The folder is the workspace

For a task that changes a real repository, the folder is also where the work is done. The files to change are copied in and changed there, and only after approval do they go back. Until then, the real repository is not touched.

That promise is weaker than it sounds. The folder is held by rules in the gate, not by the operating system, so a command spelled in an indirect way may get past it, because a hook sees calls, not effects (Hooks). So the rule keeps a careful agent in its place, but it does not contain a determined one. For things that must never be touched, see Least privilege.

Why files are the handover

The folder holds more than the files being changed. Whatever its size, it also keeps the state of the task, in files rather than in the conversation, and three of those files do the handing over.

  • A handover file says how far the task is and what comes next. A fresh session reads only this to pick the task up.
  • A requirement file holds what was agreed (The agent writes the requirement).
  • A state file for programs is where the list of tasks, and what each one waits for, is read from, rather than from the Markdown. Progress that an agent writes by hand in prose misses ticks and gets things wrong, while progress a program records does not.

When a written record says one thing and the files actually on disk say another, the disk wins. This is the same idea as the progress file in Anthropic's long-running agent work, where state lives in files outside the chat (Long work across sessions). What I add is the kind, the size and the gates.

A session holds one task; a task can have many sessions

Sessions and tasks are kept apart on purpose. A session holds only one task at a time, but it can switch to another without closing the first. While it holds a task, the edit tools can write only that task's folder. A task, in turn, outlives its sessions: closing it only changes its state, so the folder stays and the task can be opened again. And at the start of each prompt, a hook tells the agent how far its task is, or, if it has none, which tasks are still open.

The one cost of the separation is that a task can be left without any session, if its session moved on to another task or the session's record was lost, and then nothing notes that the agent stopped. My board of tasks (Ten things at once: parallel tasks) shows these tasks as having no session, along with how long nobody has touched them, so that a person can see them.

None of this applies to quick questions that write nothing. They open no task at all, because a task would only slow them down for nothing.

Try it without any setup

You can test the handover idea in your own tool. At the end of a long chat, ask the agent to write into one file what was asked, what was decided, how far it got and what comes next. Then open a new chat and tell it to read only that file and carry on. If the second chat goes wrong, the file was missing something, and whatever it missed is what a handover file must hold.

每件事該走多少流程？

我的第一個答案是分等級，而且是錯的

我的第一個答案是三個等級，從輕的等級 1 到重的等級 3，最重的那一級帶一組分角色的 agent（慎用子 agent）。每件事開始時，你要先選一個等級。

用了一陣子之後，有三件事很清楚。第一，只有中間那一級被用到，另外兩級大部分時間都閒著。第二，重的那一級並不划算：在需求明確的任務上，它不比一個 agent 好，卻花了約 4.5 倍的用量和 6 倍的時間。這個結論背後的測試很小，四個任務，各跑一次，所以只讀方向，不要讀倍數（慎用子 agent）。第三，先選等級本身就讓每次都多了一步。更糟的是，兩套規則並排放著，agent 會拿不準，還會錯誤地解釋哪一套適用。

不過最根本的問題，出在分等級這個想法本身。一件事有多難，開始之前是不知道的，等級卻要你事先去猜。

所以我拿掉了等級，現在謹慎的程度由另外兩件事決定，兩件都不要你猜難度。

謹慎的程度跟著出錯的代價走

第一件事是這個動作可能弄壞什麼。這一點不用人來選，因為程式會根據路徑和指令做一個粗略的判斷。這個判斷是一種啟發式，不是證明；它哪裡會被騙，下面講資料夾的那一節會說。

這件事做什麼 例子 怎麼守
只讀 一個問題、在筆記裡查東西 什麼都不攔
改任務資料夾 寫分析、設計、計劃 什麼都不攔
改真正的倉庫 程式碼、知識庫（知識庫：程式碼的誠實索引） 先寫在資料夾裡。寫回去需要人批准（兩道門：人在哪裡批准）
碰到 git 歷史或正式環境 commit、push、切換分支 由 hook 攔住；人批准，有些指令永遠拒絕

這和詢問不是限制裡的分級是同一個想法：出錯的代價越大，攔得越硬。這樣的攔截就是一道門，也就是任務在人批准之前過不去的一個點（兩道門：人在哪裡批准）。

種類決定怎樣才算做完

第二件事是任務的種類。一個問題和一次程式碼修改，做完的方式不一樣，所以要由種類來說什麼算做完。

種類 什麼時候算做完
問題 答案有來源
根因分析 有一條證據鏈：看到了什麼、日誌、原因、怎麼驗證的
設計或計劃 有幾個選項，和選擇的理由
開發 修改符合批准的計劃，並有測試過的紀錄
測試 案例和結果都在磁碟上
知識更新 來源清楚，並且過同一道寫回的門（兩道門：人在哪裡批准）

沒有這樣一張表，「做完了」就是 agent 想怎麼說就怎麼說。有了它，讀的人和檢查的人都知道要找什麼（讓「通過」可信）。

大小決定資料夾裡有幾個檔案

這兩件事管的是守得多嚴、怎樣算做完，卻不管一個任務要帶多少檔案。可是這也因任務而異：一個問題不需要需求檔、計劃和待辦清單，開發任務卻需要。所以每個任務還有一個大小。它不是第三把衡量謹慎的尺，只決定資料夾裡放哪些檔案。

  • 輕：一份交接檔，寫著做到哪裡、下一步是什麼、決定了什麼。
  • 中：加上需求和它的來源文件、參考資料，和一份日誌。
  • 完整：再加上待辦清單、程式碼的工作副本，和測試結果。

每個種類都有預設的大小。任務長大了，大小可以調高，缺的檔案到時候再補上，但不會往下調。這樣一來，便宜的路保持便宜，任務值得時，重的路也還在那裡。你也許會問：這不就是舊的等級換了個名字回來嗎？其實不是，因為沒有人在開始時去猜大小。大小由種類來定，而且只有工作顯示需要更多時，才往上走。

資料夾就是工作區

如果任務要改真正的倉庫，這個資料夾也是做事的地方。要改的檔案先複製進來，在這裡改，批准之後才送回去。在那之前，誰也不會去碰真正的倉庫。

這個保證沒有聽起來那麼牢。資料夾是由門裡的規則守著的，不是由作業系統，而 hook 看到的是呼叫，不是效果（Hooks：每次呼叫都會經過的執行點），所以用間接寫法寫的指令，可能就漏過去了。這樣一來，規則能讓一個小心的 agent 守規矩，卻擋不住一個鐵了心要繞過去的。對絕對不能碰的東西，見有些東西根本不給。

為什麼用檔案交接

資料夾裡放的不只是要改的檔案。不管大小，任務的狀態也存在這裡的檔案裡，而不是對話裡。負責交接的，主要是下面三個檔案。

  • 交接檔說任務做到哪裡、接下來是什麼。新的會話只讀這一個檔案，就能接手。
  • 需求檔存放達成的共識（需求由 agent 寫，人確認）。
  • 給程式用的狀態檔。任務清單和每個任務在等什麼，都是從這裡讀的，不是從 Markdown 讀的。agent 用文字手寫的進度會漏掉打勾、會寫錯，程式記錄的進度不會。

文字紀錄和磁碟上的實際情況對不上時，以磁碟為準。這和 Anthropic 長時間執行的 agent 工作裡的進度檔是同一個想法：狀態放在對話之外的檔案裡（跨會話的長任務）。我加上的，是種類、大小和門。

一個會話管一個任務；一個任務可以有很多會話

會話和任務是故意分開的：一個會話一次只管一個任務，但它可以切換到另一個，不用關掉第一個。管著一個任務時，編輯工具只能寫那個任務的資料夾。反過來，任務比它的會話活得久。關閉任務只改它的狀態，所以資料夾還在，任務也還可以再打開。每次 prompt 開始時，hook 也會告訴 agent 它的任務做到哪裡了；如果它手上沒有任務，就告訴它還有哪些任務開著。

這樣分開只有一個代價：任務可能落得一個會話都沒有，例如它的會話換去做別的任務，或者會話的紀錄丟了，這時就沒有任何東西記下 agent 已經停了。我的任務看板（同時管十件事：並行的是任務）會把這些任務顯示成沒有會話，並顯示沒人碰它多久了，好讓人看得到。

這一切都和不寫任何東西的隨口提問無關。這類問題根本不開任務，開了只會讓它平白變慢。

不用任何設定就能試

交接這個想法，你在自己的工具裡就能試。在一個長對話的結尾，請 agent 把被要求做什麼、決定了什麼、做到哪裡、接下來是什麼，寫進一個檔案。然後開一個新對話，叫它只讀那個檔案，接著做下去。第二個對話如果出錯，就表示那個檔案缺了東西，而缺的那些，正是交接檔必須放的。

每件事该走多少流程？

我最初的答案是分级，而且错了

我最初的答案是三个级别，从轻的级别 1 到重的级别 3，最重的那一级带一组按岗位分工的 agent（见别跟风瞎用子 Agent）。每件事开始时，你要先选一个级别。

用了一阵之后，有三件事很清楚。第一，只有中间那一级被用到，另外两级大部分时间都闲着。第二，重的那一级并不划算：在需求清楚的任务上，它并不比一个 agent 单干好，却要多花约 4.5 倍的用量和 6 倍的时间。这个结论背后的测试很小，四个任务，每个只跑一次，所以只看方向，别看倍数（见别跟风瞎用子 Agent）。第三，先选级别本身就让每次都多了一步。更糟的是，两套规则并排放着，agent 会拿不准，还会错误地解释哪一套在起作用。

不过最根本的问题，出在分级这个想法本身。一件事有多难，开始之前是没法知道的，分级却要你一开始就去猜。

所以我把级别删了，现在谨慎的程度由另外两样东西决定，这两样都不要求你去猜难度。

谨慎的程度，跟着出错的代价走

第一样是这个动作可能弄坏什么。这一点不用人来选，因为代码会根据路径和命令做一个粗略的判断。这个判断是经验性的，不是证明；它在哪里可能被骗过去，下面讲文件夹的那一节会说。

工作在做什么 例子 怎么守着
只读 一个问题，在笔记里查一下 什么都不拦
改任务文件夹 写分析、设计、计划 什么都不拦
改真实的仓库 代码、知识库（见为什么要给代码建一个知识库？） 先写在文件夹里。写回去要人审批（见哪些事必须由人来批？）
碰 git 历史或生产环境 提交、push、切换分支 由 hook 拦住；人审批，有些命令永远拒绝

这和“先问我”为什么挡不住 Agent？里的分级是同一个思路：出错的代价越大，拦得越狠。这样的拦截就是一道关卡，也就是任务在人批准之前过不去的一个点（见哪些事必须由人来批？）。

类型决定“做完”的标准

第二样是任务的类型。既然一个问题和一次代码改动做完的方式不一样，就由类型来说怎样才算做完。

类型 什么时候算做完
问题 答案有来源
根因分析 有一条证据链：看到了什么、日志、原因、怎么验证的
设计或计划 有几个方案，选择有理由
开发 改动和批准的计划一致，并且有测试它的记录
测试 用例和结果都落在磁盘上
知识更新 来源清楚，并且走同一道写回关卡（见哪些事必须由人来批？）

没有这样一张表，“做完了”就是 agent 想怎么说就怎么说。有了它，读的人和检查的人都知道该看什么（见Agent 说“测过了”，能信吗？）。

规模决定文件夹里有几个文件

这两样管的是守得多严、怎样算做完，却不管一个任务要带多少文件。可这也因任务而异：一个问题用不着需求文件、计划和待办清单，一个开发任务却需要。所以每个任务还有一个规模。它不是第三把衡量谨慎的尺子，只决定文件夹里放哪些文件。

  • 轻量：一份交接文件，写着做到哪一步、下一步是什么、决定了什么。
  • 中等：加上需求和它的来源文档、参考资料，以及一份日志。
  • 完整：再加一份待办清单、代码的工作副本和测试结果。

每种类型都有默认的规模。任务变大了，规模可以往上升，缺的文件到时候再补上，但只升不降。这样，便宜的路一直便宜，任务值得的时候，重的路也还在那里。你也许会问：这不就是旧的级别换了个名字回来了吗？其实不是，因为没人在开始时去猜规模。规模由类型来定，只有当工作表明需要更多时，才往上升。

文件夹就是工作区

如果任务要改真实的仓库，文件夹也是干活的地方。要改的文件先复制进来，在这里改，批准之后才写回去。在那之前，谁也不会去碰真实的仓库。

这个保证没有听上去那么牢。文件夹是靠关卡里的规则守住的，不是靠操作系统，而 hook 看到的是调用，不是效果（见 硬性规则放在哪？用 hook），所以一条换了间接写法的命令，可能就绕过去了。这样一来，规则能让一个小心的 agent 守本分，却管不住一个铁了心的 agent。对绝不能碰的东西，见不要开放全部的权限或使用沙箱。

为什么用文件做交接

文件夹里放的不只是要改的文件。不管规模大小，任务的状态也保存在这里的文件里，而不是对话里。负责交接的，主要是下面三个文件。

  • 交接文件说明任务做到了哪一步、接下来是什么。新的会话只读这一个文件，就能接手。
  • 需求文件记录达成一致的内容（见需求说不清？让 Agent 先写一页给你确认）。
  • 给程序读的状态文件。任务清单，以及每个任务在等什么，都是从这里读的，而不是从 Markdown 里读。agent 用文字手写的进度会漏勾、会写错，程序记录的进度不会。

书面记录和磁盘上的实际情况对不上时，以磁盘为准。这和 Anthropic 长时间运行的 agent 工作里的进度文件是同一个思路：状态放在对话之外的文件里（见一个会话做不完的任务，怎么接着做？）。我加上的，是类型、规模和关卡。

一个会话只持有一个任务；一个任务可以有多个会话

会话和任务是有意分开的：一个会话一次只持有一个任务，但它可以切到另一个任务，而不用关掉第一个。持有任务期间，编辑工具只能写那个任务的文件夹。反过来，任务比它的会话活得长。关闭任务只改变它的状态，所以文件夹还在，任务也还能重新打开。每条 prompt 开始时，hook 也会告诉 agent 它的任务做到了哪一步；如果它手上没有任务，就告诉它还有哪些任务没关。

这样分开，只有一个代价：一个任务可能落得一个会话都没有，比如它的会话转去做别的任务了，或者会话的记录丢了，这时就没有任何东西注明 agent 已经停下。我的任务看板（见怎么让 Agent 同时做十件事？）会把这些任务显示为没有会话，并标出多久没人碰过，好让人看得到。

这一切都和随口一问、不写任何东西的问题无关。这类问题根本不开任务，开了只会让它白白变慢。

不用任何配置，就能试

交接这个想法，你在自己的工具里就能试。在一个长对话的最后，让 agent 把被要求做什么、决定了什么、做到了哪一步、接下来是什么，写进一个文件。然后开一个新对话，让它只读这个文件，接着干。如果第二个对话做偏了，说明文件里缺了东西，而缺的那些，正是交接文件必须放的。

What the folder costs, and what it cannot promise

That small test also shows the first cost. A folder is useful only if its handover file is true, so the agent has to keep the files up to date. A reminder when the agent stops helps, but it does not guarantee it. When it matters, I read the files rather than taking the agent's word.

The folder also adds steps, because opening one, writing the requirement and waiting at gates is slower than just making a small change in a chat. That is why light tasks exist, and why a question opens nothing.

And although nobody guesses difficulty any more, the kind is still a guess, because a job often starts as a question and turns into a change. So the kind can change. The size can too, but only upward. I have not measured how often people pick the wrong kind.

Finally, the folder is not a sandbox in the security sense, for the reasons given above under "The folder is the workspace".

資料夾要付出什麼，又保證不了什麼

上面那個小試驗，也帶出了第一筆代價。資料夾只有在交接檔是真的時候才有用，所以 agent 必須讓檔案一直保持最新。在 agent 停下來時提醒它一下有幫助，但保證不了。要緊的時候，我讀檔案，不信 agent 的話。

任務資料夾還會多出一些步驟：開一個資料夾、寫需求、在門前等待，都比在對話裡直接做一個小修改慢。這就是為什麼有輕的任務，也是為什麼一個問題什麼都不開。

雖然現在不用再猜難度了，種類卻仍然是一種猜測，因為一件事常常一開始是問題，後來才變成修改。所以種類可以變。大小也可以變，但只能往上。人多常選錯種類，我沒有量過。

最後，這個資料夾不是安全意義上的沙箱，原因上面「資料夾就是工作區」那一節已經說過。

文件夹要付出什么，又保证不了什么

上面那个小试验，也引出了第一笔代价。只有交接文件是真实的，文件夹才有用，所以 agent 得让这些文件一直保持最新。在 agent 停下来时提醒它一下有帮助，但保证不了。要紧的时候，我读文件，不信 agent 的话。

文件夹还会多出一些步骤：开一个文件夹、写需求、在关卡处等，都比在对话里直接做一个小改动慢。这就是为什么有轻量任务，也是为什么一个问题什么都不开。

虽然现在不用再猜难度了，类型却仍然是一种猜测，因为一件事常常一开始是个问题，后来才变成一次改动。所以类型可以改。规模也可以改，但只能往上升。人们选错类型的频率有多高，我没有测过。

最后，从安全的意义上说，文件夹不是沙箱，原因上面“文件夹就是工作区”那一节已经讲过。

Which parts to delete, and what stays

Not all of this has to last. Two parts of it are scaffolding for today's platform. The first is the handover file, together with the reminder at each prompt. Both exist because chats are compressed and sessions end. If the platform keeps a memory of its own that survives both, and that a person can read, drop my files and keep the idea.

The second is the playbook each kind has, the written-out steps for doing that kind of task. As models need such steps less, you can shorten the playbooks. Keep the lists of what counts as done, though, because they say what you want, not how to get it.

What does not retire is the unit itself. Whatever the platform does, a job has a requirement, a plan and a result, and a person wants to find them.

哪些可以刪，哪些留下

這些東西裡，有兩部分是為今天的平台搭的鷹架，以後可以拆。第一部分是交接檔，連同每次 prompt 的提醒。它們之所以存在，是因為對話會被壓縮、會話會結束。如果平台有自己的記憶，能撐過這兩件事，而且人讀得到，就丟掉我的檔案，留下這個想法。

第二部分是每個種類各自的操作手冊，也就是做這類任務時寫出來的步驟。模型越來越不需要這些步驟，手冊也就可以縮短。但「什麼算做完」的清單要留著，因為它們說的是你要什麼，而不是怎麼得到。

不會退場的是單位本身。不管平台怎麼做，一件事總有需求、計劃和結果，而人想找得到它們。

哪些可以删，哪些留下

这些东西里，有两部分是为今天的平台搭的脚手架，以后可以拆。第一部分是交接文件，连同每条 prompt 处的提醒。它们之所以存在，是因为对话会被压缩、会话会结束。如果平台自己有一份能挺过这两者、而且人读得到的记忆，就把我的文件去掉，留下这个想法。

第二部分是每种类型各自的操作手册，也就是做这类任务时写明的步骤。模型越来越不需要这些步骤，手册也就可以缩短。但“怎样才算做完”的清单要留着，因为它们说的是你要什么，而不是怎么得到。

不会退役的是单位本身。不管平台怎么做，一件事总有需求、计划和结果，而人想找得到它们。
