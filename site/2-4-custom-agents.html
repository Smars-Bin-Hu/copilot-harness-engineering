Custom agentsCustom agent：固定模型和工具的角色什么时候才需要自定义 Agent？

This chapter assumes you have read Use subagents sparingly, or at least know what a subagent is.

讀這一章，請先讀過慎用子 agent，或至少知道子 agent 是什麼。

读这一章，需要你读过别跟风瞎用子 Agent，或者至少知道什么是子 agent。

The Knowledge經驗分享经验分享

In one sentence

Build a custom agent only when you must change the model or shrink the tools. If what you want to change is what it knows or how it works, a skill or an instruction file is enough.

一句話

只有在必須換模型、或縮小工具時，才建立 custom agent。如果要改的只是它知道什麼、怎麼做事，用 skill 或指令檔就夠了。

一句话

只有在必须换模型、或者缩小工具范围时，才去建自定义 agent。如果要改的只是它知道什么、怎么干活，一个 skill 或一个指令文件就够了。

For leaders

  • The decision: approve a custom agent only when it changes something that cannot be shared another way: its tools, its model, or a separate context for an independent check.
  • The risk: a role agent that changes only tone and know-how is one more file to keep in step, and the platform enforces nothing in it. Roles that run as separate agents also add usage, and Anthropic measured its multi-agent research system at about 15 times the tokens of a chat.
  • The cost of doing it right: one agent file per real limit, changed through code review like any rule. Mine keeps only a read-only helper and a checker.
  • Ask the team: "Does this agent file list tools or a model? If not, why isn't it a skill?"

給主管

  • 要做的決定：只有 custom agent 改變了別的方式共用不了的東西時才批准：它的工具、它的模型，或一個用來做獨立檢查的獨立上下文。
  • 風險：一個角色 agent 如果只改了語氣和做事的訣竅，就只是多一個要同步維護的檔案，裡面卻沒有任何一樣是平台強制執行的。角色各自作為獨立的 agent 執行時，用量也會增加，Anthropic 就量過，他們的多 agent 研究系統用的 token 約是聊天的 15 倍。
  • 做對的成本：每一種真正的限制對應一個 agent 檔，像任何規則一樣走 code review 來改。我的設定只留了一個唯讀的幫手和一個檢查者。
  • 可以問團隊：「這個 agent 檔有列出工具或模型嗎？沒有的話，為什麼不是 skill？」

写给管理者

  • 要拍板的事：自定义 agent 只在它改变了别的办法共享不了的东西时才批：它的工具、它的模型，或者一份用来做独立检查的独立上下文。
  • 风险：一个只改了语气和专业知识的角色 agent，不过是多出一个要同步维护的文件，里面却没有一样是平台强制执行的。角色各自作为独立的 agent 运行时，用量也会涨，Anthropic 就测过，他们的多 agent 研究系统用的 token 约是聊天的 15 倍。
  • 做对的代价：每一个真实的限制对应一个 agent 文件，像任何规则一样通过代码审查来改。我的配置里只留了一个只读的帮手和一个检查者。
  • 可以问团队：“这个 agent 文件里列了工具或模型吗？如果没有，为什么它不是一个 skill？”

When you want a different agent, what do you build?

Use subagents sparingly asked whether to split work between agents at all. Once you do want a different agent, many setups go on to build roles, such as a "SQL expert", a "code reviewer" and a "documentation writer", each in its own agent file. It feels like organizing. To see whether it is, start with what such a file is. A custom agent is a file that defines a role for the agent. In VS Code Copilot it is a file ending in .agent.md, with a short header (name, description, settings) above a body of instructions. The default agent, by contrast, is the plain agent you talk to when you pick nothing.

Look at what such a file holds, though, and you find that most of it could reach the default agent some other way. A role that is only a different tone and some know-how is then a costume: it adds a thing to maintain, but nothing in it is enforced by the platform. So which parts of the file are more than that?

想要另一個 agent 時，到底要做出什麼？

慎用子 agent問的是要不要把工作分給多個 agent。真的想要另一個 agent 時，很多設定接下來的做法是做角色：「SQL 專家」「程式碼 reviewer」「文件作者」，每個都是一個 agent 檔，感覺像在整理。可這到底算不算整理，得先弄清楚這種檔案是什麼。custom agent 是一個為 agent 定義角色的檔案，在 VS Code Copilot 裡就是副檔名為 .agent.md 的檔案：上面一段簡短的檔頭（名稱、描述、設定），下面一段指令正文。和它相對的是預設 agent，也就是你什麼都不選時對話的那個普通 agent。

可是再看一看這種檔案裡有什麼，你會發現大部分內容，用別的方式也能交給預設 agent。換句話說，一個角色如果只是換了語氣、加了些做事的訣竅，就是一件戲服：它多了一個要維護的東西，裡面卻沒有任何一樣是平台強制執行的。那麼，除了戲服，檔案裡還有什麼？

想要一个不一样的 agent，到底要搭什么？

别跟风瞎用子 Agent问的是，要不要把工作分给多个 agent。真想要一个不一样的 agent 时，很多配置接下来的做法是搭角色，“SQL 专家”“代码 reviewer”“文档撰写者”，每个都是一个 agent 文件，让人觉得是在整理。可这到底算不算整理，得先弄清这种文件是什么。自定义 agent 是为 agent 定义一个角色的文件，在 VS Code Copilot 里就是以 .agent.md 结尾的文件：上面一小段头部（名字、描述、设置），下面一段正文指令。和它相对的是默认 agent，也就是你什么都不选时，与你对话的那个普通 agent。

可是再看看这种文件里装的是什么，你会发现大部分内容，其实都可以用别的办法交给默认 agent。说白了，一个只是换了语气、加了点专业知识的角色，就是戏服：它多出一样要维护的东西，里面却没有一样是平台强制执行的。那么，除了戏服，文件里还有什么？

Which parts of an agent file are more than a costume?

What is in an agent file

The answer starts in the header, where the settings live. Going by the VS Code docs and my own files, only a few of them matter.

The name and the description are written for whoever calls the agent. The description tells the model when this agent is the right one to call, so say in it what the agent is for and what it needs to be told. A subagent starts with an empty context (Use subagents sparingly), and a vague call message gives it nothing to work from.

The other settings decide what the agent works with and who may call it. If the header gives a list of tools, only those tools are available to the agent. The model is optional and can be a list in order of preference, so that when the first cannot be used, the next one is tried. Who may call the agent takes two settings, and they do different things. user-invocable: false keeps the agent out of the drop-down list (the VS Code docs call it picker visibility), while a separate setting, disable-model-invocation, is for whether the model may call it as a subagent. Each of them still lets some calls through, as "Hidden is not forbidden" below explains.

Below the header, the body is text. It says what the role is for, how it works, what it must not do and what it hands back.

What only an agent file can do

Put the settings next to each other and ask of each one whether the default agent could get it some other way.

For what the agent knows and how it works, the answer is yes. Instruction files and skills reach any agent, so a SQL style guide, a review checklist or the way things are named here can go into a skill or an instruction file (Instructions and skills). The default agent then does the job, with no new agent.

The tools are another matter, because they cannot be given another way. An agent has the tools its file lists, and the platform enforces that list, so an agent without the edit tools cannot edit, however it is asked. A rule written in the body of the file, such as "do not edit files", has no such force. It is a request like any other.

The model, too, can only be set in an agent file, whether that is a cheap model for a simple job or a strong one for hard thinking. The person can switch the model in the drop-down for the default agent, but a subagent's model is set in its file.

The tools and the model are both written in the file. A separate context is different, because it is not written in the file at all. When the agent runs as a subagent, it starts with an empty context and only its report comes back, and that comes from running as a subagent, not from anything in the file. It is a reason to build one when you want an independent check, the case that Use subagents sparingly covers.

So the rule I use is short. Build a custom agent when at least one of these cannot be shared: the tools differ, the model differs, or you need a context that must not see the caller's reasoning. For everything else, use the default agent and write the know-how down.

The rule is easier to apply with a quick test. If you can say it as "when doing X, do it like this", it is a skill. If you can say it as "this job must not have tool Y" or "this job should run on model Z", it is an agent. And before I add one, I still ask two questions: which failure does it prevent, and why can the default agent not do the same?

The VS Code context engineering guide draws the same line. It offers agents for "workflows that follow a multi-turn process with specific tools", and its example planning agent fits it: the short, read-only tool list is the limit, while the instruction not to implement is a request.

An example: the reviewer

In my setup there is one custom agent I would keep above all others. It is the reviewer, a checker that sees only the request and the result, and here is the top of its file:

The header of the reviewer: the tools line is the limit, the model line is a fallback list, the description is a request to the model that calls it.
---
name: reviewer
description: The independent checker. The default agent calls it when the user switches checks on ([review]=n). It looks only at the requirement, the work and the diff, gives PASS or FAIL, and names file:line for every finding. It changes no file.
user-invocable: false
agents: []
model: ['Claude Sonnet 5.5 (copilot)', 'Claude Sonnet 5.5', 'Claude Haiku 5.5 (copilot)', 'Claude Haiku 5.5', 'Claude Haiku 4.5 (copilot)', 'Claude Haiku 4.5']
tools: ['read', 'search', 'execute']
---

The tools line gives it tools for reading, searching and running commands but none for changing files, so it cannot "just fix it". agents: [] means it cannot start other subagents, and the model is a fallback list. (The reasons for each choice are in Use subagents sparingly.) What matters here is that every line of the header that changes behavior is a tool limit, a model or a boundary of context. The description, by contrast, only asks, and the body mostly says what to look at and what to hand back.

Not everything I ran into was this tidy.

Three facts that bit me

The first is that "hidden" is not "forbidden". The setting that keeps an agent out of the drop-down list does not stop another agent from calling it as a subagent, and neither does the setting that keeps the model from using it. If "who may call whom" matters, a hook has to decide it (Hooks), not these two settings.

A hook has a blind spot of its own, because it cannot see which agent is current. The events it receives carry no name for the main agent (Hooks), so rights cannot be handed to "the admin agent": any agent could pass for it. Rights have to follow the session instead. In my setup, for example, an admin switch is turned on by the person in a terminal (Guard the files that hold the rules). I once had an admin agent, and I retired it.

The last one is that a check may be silently skipped. When a subagent's model is a class above the main model, the platform does not run it and says nothing. I have seen this only once, but because it happens without a word, "did the check happen" has to be confirmed by something that is not the model, such as a hook that saves the reviewer's answer to disk.

Test your own setup

Now go back to the rule and test your own role agents against it. Take one you have, a "SQL expert" or a "documentation writer", and look at whether its file lists tools or a model. If it lists neither, move its body into a skill (Instructions and skills), give the same task to the default agent with and without the skill, and compare. If you see no difference, the agent was a costume, though you should run each a few times before you trust what you see.

agent 檔裡，哪些東西不只是戲服？

agent 檔裡有什麼

這個答案要從檔頭找起，因為設定都放在那裡。照 VS Code 文件和我自己的檔案來看，重要的只有幾個。

名稱和描述是寫給呼叫者看的。描述告訴模型什麼時候該呼叫這個 agent，所以裡面要說明這個 agent 是做什麼的、需要被告知什麼。子 agent 從空的上下文開始（慎用子 agent），呼叫訊息一含糊，它就無從下手。

其餘的設定，決定這個 agent 用什麼做事、誰可以呼叫它。檔頭如果給了一份工具清單，這個 agent 就只能用清單裡的工具。模型是可選的，也可以是一個依偏好排序的清單，第一個用不了，就試下一個。誰可以呼叫它，由兩個設定來管，作用各不相同。user-invocable: false 讓這個 agent 不出現在下拉清單裡（VS Code 文件稱之為 picker visibility）；另一個設定 disable-model-invocation，管的是模型能不能把它當子 agent 呼叫。它們各有擋不住的呼叫，見後面的「隱藏不等於禁止」。

檔頭下面的正文就是文字，寫的是這個角色做什麼、怎麼做、不能做什麼、交回什麼。

只有 agent 檔能做的事

把這些設定放在一起，一項一項地問：這樣東西，預設 agent 能不能用別的方式拿到？

知道什麼、怎麼做事，這些預設 agent 都拿得到。指令檔和 skill 對任何 agent 都有效，所以 SQL 風格指南、review 清單、這裡的命名習慣，都可以放進 skill 或指令檔（指令與 skill：只載入需要的）。這樣預設 agent 就能做這份工作，不用新的 agent。

工具就不同了，它沒有別的方式可以給。一個 agent 有的就是它的檔案列出的工具，平台會強制執行這份清單，所以沒有編輯工具的 agent，怎麼要求都改不了檔案。而寫在檔案正文裡的規則，例如「不要編輯檔案」，就沒有這樣的效力。它和別的規則一樣，只是請求。

同樣，模型也只能在 agent 檔裡定，不管是讓簡單的工作用便宜的模型，還是讓難的思考用強的。使用者可以在下拉清單裡為預設 agent 切換模型，但子 agent 的模型是在它的檔案裡設定的。

工具和模型都寫在檔案裡。獨立的上下文不一樣，它根本不寫在檔案裡。作為子 agent 執行時，它從空的上下文開始，只有它的報告會交回來，這來自「作為子 agent 執行」這件事，而不是檔案裡寫了什麼。想要獨立檢查時，這就是做一個的理由，慎用子 agent講的就是這種情況。

所以我用的規則很短。至少有一樣共用不了時，才建立 custom agent：工具不同、模型不同，或需要一個不能看到呼叫者思路的上下文。其他情況，用預設 agent，把做事的訣竅寫下來。

有一個快速的判斷，能讓這條規則更好用。如果你能把它說成「做 X 的時候，這樣做」，它就是 skill；如果你能說成「這份工作不能有工具 Y」或「這份工作要用模型 Z」，它就是 agent。真要加一個之前，我還是會問兩個問題：它防的是哪種失敗？預設 agent 為什麼做不到同樣的事？

VS Code 的上下文工程指南也是這樣劃線的。它建議，「按多輪流程、用特定工具來走的 workflow」可以用 agent，它的範例規劃 agent 正好符合這一點：那份簡短的唯讀工具清單是限制，那句不要動手實作的指令是請求。

一個例子：reviewer

在我的設定裡，有一個 custom agent 是我最想留下的，那就是 reviewer。它是一個只看需求和結果的檢查者，下面是它檔案的開頭：

reviewer 的檔頭：tools 那一行是限制，model 那一行是備用清單，描述是對呼叫它的模型的請求。
---
name: reviewer
description: The independent checker. The default agent calls it when the user switches checks on ([review]=n). It looks only at the requirement, the work and the diff, gives PASS or FAIL, and names file:line for every finding. It changes no file.
user-invocable: false
agents: []
model: ['Claude Sonnet 5.5 (copilot)', 'Claude Sonnet 5.5', 'Claude Haiku 5.5 (copilot)', 'Claude Haiku 5.5', 'Claude Haiku 4.5 (copilot)', 'Claude Haiku 4.5']
tools: ['read', 'search', 'execute']
---

tools 那一行給了它讀取、搜尋和執行指令的工具，卻沒有改檔案的工具，所以它不能「順手修掉」。agents: [] 表示它不能再開別的子 agent，模型則是一份備用清單。（每個選擇的理由在慎用子 agent。）這裡要看的是，檔頭裡每一行會改變行為的，不是工具限制，就是模型，或是上下文的邊界。相較之下，描述只是請求，正文則大多在說看什麼、交回什麼。

不過，我碰到的事並不都這麼乾淨俐落。

三件讓我吃過虧的事

第一件是，「隱藏」不等於「禁止」。讓 agent 不出現在下拉清單的設定，擋不住另一個 agent 把它當子 agent 呼叫；不讓模型使用它的那個設定，也一樣擋不住。「誰可以呼叫誰」如果重要，就要由 hook 來決定（Hooks：每次呼叫都會經過的執行點），不能靠這兩個設定。

可是 hook 自己也有盲點：它看不到目前是哪個 agent。hook 收到的事件裡沒有主 agent 的名字（Hooks：每次呼叫都會經過的執行點），所以權限不能交給「admin agent」：任何 agent 都能冒充它。權限只能跟著會話走，例如在我的設定裡，admin 開關是由使用者在終端機裡打開的（保護規則本身的檔案）。我曾經有過一個 admin agent，後來撤掉了。

最後一件是，檢查可能被悄悄跳過：子 agent 的模型比主模型高一個等級時，平台不執行它，也不說一聲。這種情況我只見過一次，可是正因為它不說一聲，「檢查到底有沒有做」，要由不是模型的東西來確認，例如一個把 reviewer 的回答存到磁碟的 hook。

測一測你自己的設定

現在回到那條規則，拿它來測一測你自己的角色 agent。挑一個你有的，例如「SQL 專家」或「文件作者」，看它的檔案有沒有列出工具或模型。都沒有的話，把它的正文搬進 skill（指令與 skill：只載入需要的），再把同一個任務交給預設 agent，分別在有 skill 和沒有 skill 時做，然後比較。看不出差別，這個 agent 就是戲服；不過每種都多跑幾次，再相信你看到的。

agent 文件里，哪些东西不只是戏服？

agent 文件里有什么

这个答案，要从头部找起，因为设置都在那里。按 VS Code 的文档和我自己的文件来看，要紧的只有几项。

名字和描述是写给调用方看的。描述告诉模型什么时候该调用这个 agent，所以里面要说清这个 agent 是做什么的、需要被告知什么。子 agent 从空白的上下文开始（别跟风瞎用子 Agent），调用消息一含糊，它就无从下手。

其余的设置，决定这个 agent 用什么干活、谁可以调用它。头部如果给了一份工具清单，这个 agent 就只有清单上的工具。模型是可选的，也可以是一份按偏好排序的列表，第一个用不了，就试下一个。谁可以调用它，由两个设置来管，作用各不相同。user-invocable: false 让这个 agent 不出现在下拉列表里（VS Code 文档叫它选择器里的可见性）；另一个单独的设置 disable-model-invocation，管的是模型能不能把它当子 agent 调用。它们各有拦不住的调用，见后面的“隐藏不等于禁止”。

头部下面的正文就是文本，写的是这个角色是干什么的、怎么干、不能做什么、交回什么。

只有 agent 文件才能做到的

把这些设置并排放在一起，一项一项地问：这样东西，默认 agent 能不能用别的办法拿到？

知道什么、怎么干活，这些默认 agent 都能拿到。指令文件和 skill 对任何 agent 都有效，所以 SQL 风格指南、检查清单、这里的命名方式，都可以放进 skill 或指令文件（规则写太多，Agent 反而记不住）。这样默认 agent 就能干这份活，用不着新的 agent。

工具就不一样了，它没法用别的办法给。一个 agent 有的就是它的文件里列出的那些工具，平台会强制执行这份清单，所以没有编辑工具的 agent，无论你怎么要求，都编辑不了。而写在文件正文里的规则，比如“不要改文件”，就没有这样的效力。它和别的规则一样，只是请求。

同样，模型也只能在 agent 文件里定，不管是给简单的活配一个便宜的模型，还是给难的思考配一个强的。人可以在下拉列表里切换默认 agent 的模型，但子 agent 的模型是在它的文件里设的。

工具和模型都写在文件里。独立的上下文不一样，它根本不写在文件里。作为子 agent 运行时，它从空白的上下文开始，只有它的报告会回来，这来自“作为子 agent 运行”这件事，而不是文件里写了什么。想要独立检查时，这是搭一个的理由，别跟风瞎用子 Agent讲的就是这种情况。

所以我用的规则很短。这几样里至少有一样没法共享时，才建自定义 agent：工具不同、模型不同，或者你需要一份不能让它看到调用方推理过程的上下文。其他情况，都用默认 agent，把专业知识写下来。

有一个快速的检验，能让这条规则更好用。如果你能把它说成“做 X 的时候，这样做”，它就是 skill；如果你能把它说成“这份活不能有工具 Y”或者“这份活要用模型 Z 来跑”，它就是 agent。真要加一个之前，我还是会问两个问题：它防的是哪种故障？默认 agent 为什么做不到同样的事？

VS Code 的上下文工程指南也是这样划线的。它把 agent 用在“遵循多轮流程、使用特定工具的 workflow”上，它的示例规划 agent 正好符合这一点：那份简短的只读工具清单是限制，那条不要去实现的指令是请求。

一个例子：reviewer

在我的配置里，有一个自定义 agent 是我最想留下的，那就是 reviewer。它是一个只看需求和结果的检查者，下面是它文件的开头：

reviewer 的头部：tools 那一行是限制，model 那一行是备选列表，description 是对调用它的模型的请求。
---
name: reviewer
description: The independent checker. The default agent calls it when the user switches checks on ([review]=n). It looks only at the requirement, the work and the diff, gives PASS or FAIL, and names file:line for every finding. It changes no file.
user-invocable: false
agents: []
model: ['Claude Sonnet 5.5 (copilot)', 'Claude Sonnet 5.5', 'Claude Haiku 5.5 (copilot)', 'Claude Haiku 5.5', 'Claude Haiku 4.5 (copilot)', 'Claude Haiku 4.5']
tools: ['read', 'search', 'execute']
---

tools 那一行给了它读、搜索和运行命令的工具，却没有改文件的，所以它没法“顺手修一下”。agents: [] 表示它不能再启动别的子 agent，模型则是一份备选列表。（每一项选择的理由，在别跟风瞎用子 Agent里。）这里要紧的是，头部里每一行会改变行为的，要么是工具限制，要么是模型，要么是上下文的边界。相比之下，描述只是在请求，正文则主要说该看什么、该交回什么。

不过，我碰到的事并不都这么干净利落。

我踩过的三个坑

第一个坑是，“隐藏”不等于“禁止”。让一个 agent 不出现在下拉列表里的设置，拦不住另一个 agent 把它当子 agent 来调用；让模型不去使用它的那个设置，同样拦不住。如果“谁可以调用谁”很要紧，就得由 hook 来决定（硬性规则放在哪？用 hook），不能靠这两个设置。

可 hook 自己也有盲区：它看不到当前是哪个 agent。hook 收到的事件里没有主 agent 的名字（硬性规则放在哪？用 hook），所以权限不能交给“admin agent”：任何 agent 都可以冒充它。权限只能跟着会话走，比如在我的配置里，admin 开关是由人在终端里打开的（别让 Agent 改自己的规则）。我曾经有过一个 admin agent，后来撤掉了。

最后一个坑是，检查可能被悄悄跳过：子 agent 的模型比主模型高一个级别时，平台不会运行它，也不吭声。这种情况我只见过一次，可正因为它一声不吭，“检查到底有没有发生”，必须由模型之外的东西来确认，比如一个把 reviewer 的回答存到磁盘上的 hook。

测一测你自己的配置

现在回到那条规则，拿它来测一测你自己的角色 agent。挑你有的一个，比如“SQL 专家”或“文档撰写者”，看它的文件里有没有列工具或模型。都没有的话，把它的正文挪进一个 skill（规则写太多，Agent 反而记不住），再把同一个任务交给默认 agent，一次带这个 skill，一次不带，对比一下。如果看不出差别，这个 agent 就是戏服；不过每种都多跑几次，再相信你看到的。

What each agent you keep costs

The plainest cost is upkeep. Each file has a model name, a tool list and a body that can go out of date. Model names change, for one, so a name that no longer matches the drop-down breaks the agent. Because an agent file sets limits, in a team it should be changed through code review like any rule.

Switching agents may also lose the chat. The VS Code docs say a selected agent applies to your requests until you switch. They do not say what happens to the chat history on a plain switch, so keep what matters in files (Long chats get worse).

Last comes usage, and here you need fewer roles than you think. Every role that runs as its own agent does its own reading and writing, and Anthropic has measured what that adds up to in their research system: agents use about 4 times the tokens of a chat, and multi-agent systems about 15 times (How we built our multi-agent research system). In my early setup I had three job-title agents, one to coordinate, one to build and one to check, and I kept only the checker (Use subagents sparingly tells why).

多留一個 agent 要付出什麼

最直接的代價是維護。每個檔案都有模型名稱、工具清單和一段會過期的正文。就拿模型名稱來說，它會變，而名稱一旦和下拉清單對不上，這個 agent 就壞了。agent 檔設定的是限制，所以在團隊裡，也要像任何規則一樣走 code review 來改。

還有，切換 agent 可能會丟掉對話。VS Code 文件說，選定的 agent 會一直用在你的請求上，直到你切換為止；至於單純切換一次之後對話紀錄會怎樣，文件沒說，所以要緊的東西，存進檔案（長對話會變差）。

最後是用量。算下來，你需要的角色其實比你想的少。每個作為獨立 agent 執行的角色，都要自己讀、自己寫，這些加起來有多少，Anthropic 在他們的研究系統裡量過：agent 用的 token 約是聊天的 4 倍，多 agent 系統約是 15 倍（How we built our multi-agent research system）。在我早期的設定裡，有三個按職位分工的 agent，一個協調、一個實作、一個檢查，最後只留了檢查者，原因見慎用子 agent。

多留一个 agent 要付出什么

最直接的代价是维护。每个文件里都有模型名、工具清单和一段会过期的正文。就拿模型名来说，它会变，而和下拉列表对不上的名字，会让 agent 坏掉。agent 文件设定的是限制，所以在团队里，它也应该像任何规则一样通过代码审查来改。

还有，切换 agent 可能会丢掉对话。VS Code 文档说，选定的 agent 会作用于你的请求，直到你切换为止；至于单纯切换一次之后对话历史会怎么样，文档没有说，所以要紧的东西，放在文件里（对话越久，Agent 越笨）。

最后是用量。算下来，你需要的角色其实比你以为的少。每个作为独立 agent 运行的角色，都要自己读、自己写，这些加起来有多少，Anthropic 在他们的研究系统里量过：agent 用的 token 约是聊天的 4 倍，多 agent 系统约是 15 倍（How we built our multi-agent research system）。在我早期的配置里，我有三个按岗位分工的 agent，一个协调、一个开发、一个检查，最后只留下了检查者，为什么见别跟风瞎用子 Agent。

When to delete an agent file Industry practice

An agent file earns its place as long as it enforces something a skill cannot: a tool list or a model. Some platforms already let a skill carry tool settings. In Claude Code, a skill's allowed-tools only pre-approves tools and does not restrict them. Removing tools is the job of a separate setting, disallowed-tools, which takes them away while the skill is active (Skills). Whether such a setting is enforced on your platform is something you have to check. Where it is, many agent files become unnecessary. And any agent whose only content is "act like an expert in X" can be deleted today.

什麼時候可以刪掉 agent 檔 業界做法

只要 agent 檔還強制執行著 skill 做不到的東西，也就是工具清單或模型，它就值得留著。有些平台已經讓 skill 帶工具設定。在 Claude Code 裡，skill 的 allowed-tools 只是預先批准工具，並不限制工具；移除工具靠的是另一個設定 disallowed-tools，它會在 skill 啟用期間把工具拿掉（Skills）。這樣的設定在你的平台上有沒有強制執行，要自己去查，有的話，很多 agent 檔就不需要了。至於內容只有「表現得像 X 的專家」的 agent，今天就可以刪掉。

什么时候可以删掉 agent 文件 业界做法

只要 agent 文件还强制执行着 skill 做不到的东西，也就是工具清单或模型，它就值得留着。有些平台已经让 skill 带上工具设置。在 Claude Code 里，skill 的 allowed-tools 只是预先批准某些工具，并不限制它们；移除工具靠的是另一个单独的设置 disallowed-tools，它会在 skill 生效期间把工具拿掉（Skills）。这样的设置在你的平台上是不是强制执行的，要自己去查，如果是，很多 agent 文件就不再需要了。至于那些内容只是“表现得像 X 领域专家”的 agent，今天就可以删。
