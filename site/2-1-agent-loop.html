2.1

The agent loopagent 循環，和你能插手的地方Agent 到底是怎么干活的？

This chapter assumes only that you have used an AI coding agent, such as Copilot in agent mode.

讀這一章，只需要你用過寫程式的 AI agent，例如 Copilot 的 agent 模式。

读这一章，只需要你用过写代码的 AI agent，比如 Copilot 的 agent 模式。

The Knowledge經驗分享经验分享

In one sentence

An agent is a loop: ask the model, run the tool it asks for, feed the result back. You steer it at a few points in each turn.

一句話

agent 是一個迴圈：問模型，執行它要的工具，把結果餵回去。你可以在每一輪的幾個點上掌舵。

一句话

agent 是一个循环：问模型，运行它要的工具，把结果喂回去。你在每一轮的几个点上掌舵。

For leaders

  • The decision: when an agent misbehaves, ask which of four places to fix (what it reads, which tools it has, a check before a call, a check after a call) before asking for a bigger model or a longer prompt.
  • The risk: the loop itself almost never breaks, but a rule that lives only in a prompt is a request the model may not follow.
  • The cost of doing it right: mostly setup time. The cheapest lever, what the agent reads, takes only a few lines of written rules.
  • Ask the team: "For the last bad result, was the fix a better context, a tighter tool list, or a check outside the model?"

給主管

  • 要做的決定：agent 出錯時，先問該修四個地方的哪一個（它讀什麼、有哪些工具、呼叫前的檢查、呼叫後的檢查），再去要更大的模型或更長的 prompt。
  • 風險：迴圈本身幾乎不會壞，可是只寫在 prompt 裡的規則不過是請求，模型不一定照做。
  • 做對的成本：主要是設定的時間。最便宜的槓桿是 agent 讀什麼，只要寫幾行規則。
  • 可以問團隊：「上一次的壞結果，修法是更好的上下文、更緊的工具清單，還是模型外面的一道檢查？」

写给管理者

  • 要拍板的事：agent 出了问题，先问该改四个地方里的哪一个（它读什么、有哪些工具、调用前的检查、调用后的检查），再去考虑换更大的模型或写更长的 prompt。
  • 风险：循环本身几乎不会坏，可只写在 prompt 里的规则不过是请求，模型不一定照做。
  • 做对的代价：主要是配置的时间。最便宜的杠杆是 agent 读什么，只要写几行规则。
  • 可以问团队：“上一次的坏结果，修的办法是更好的上下文、更紧的工具清单，还是模型之外的一道检查？”

When an agent goes wrong, what is actually wrong?

When an agent does something wrong, it is natural to picture a mind that has made a bad choice. The trouble is that this picture sends people to the wrong fix. They write a longer prompt, add "be careful" in capital letters, or switch to a bigger model. Sometimes that helps, but often it does not, because the problem was not in the thinking.

If the problem is not in the thinking, where is it? The answer lies in the machine. It turns out to be small and plain, with a few places where you can reach into it. Every later chapter in this part, like most of the chapters after it, works on one of them.

The machine starts with the model, the AI itself. It reads text and writes text and does nothing else, yet an agent plainly does more than write, since it reads files, searches, changes files and runs commands. Each of these is a tool, one thing the agent can do in your project. What joins the two is the tool call, which is the model's request to use a tool, written as text: "read this file". How a model that can only write text ends up changing your files is what the loop explains.

agent 出錯時，到底錯在哪裡？

agent 做錯事的時候，人很自然會覺得，是背後有個頭腦做了糟糕的選擇。問題是，這個想像會把人引到錯誤的修法上：把 prompt 寫得更長、用大寫字母加上「小心點」，或者換成更大的模型。這些有時有用，但常常沒用，因為問題本來就不在思考裡。

那麼，不在思考裡，又在哪裡？答案在這台機器裡。其實它很小，也很普通，上面只有幾個地方能伸手進去。這一部分後面的每一章，和再往後的大部分章節一樣，都在處理其中一個地方。

這台機器的起點是模型，也就是 AI 本身。它讀文字、寫文字，除此之外什麼都不做。可是 agent 顯然不只會寫字，它還會讀檔案、搜尋、改檔案、執行指令。這裡的每一樣都叫一個工具，也就是 agent 在你的專案裡能做的一件事。把兩者接起來的是工具呼叫：模型想用某個工具時提出的要求，寫成文字，例如「讀這個檔案」。一個只會寫字的模型，最後怎麼會改到你的檔案？答案就在迴圈裡。

agent 出了错，到底错在哪？

agent 做错事的时候，人很自然会觉得，是背后有个头脑做了个糟糕的选择。麻烦在于，这幅图景会把人引向错误的修法：把 prompt 写得更长，用大写字母加上一句“小心”，或者换一个更大的模型。这些有时候管用，但往往不管用，因为问题本来就不出在思考上。

那么，不出在思考上，又出在哪？答案在这台机器里。其实它又小又朴素，上面只有几个地方可以伸手进去。这一部分后面的每一章，和再往后的大多数章一样，都是在其中某一个地方下功夫。

这台机器的起点是模型，也就是 AI 本身。它读文本、写文本，别的什么都不做。可 agent 显然不只会写字，它还会读文件、搜索、改文件、运行命令。这里的每一样，都叫一个工具，也就是 agent 在你的项目里能做的一件事。把两者连起来的是工具调用：模型要用某个工具时提出的请求，写成文本，比如“读这个文件”。一个只会写字的模型，最后怎么就改了你的文件？答案就在循环里。

What the machine is, and where you can reach into it

Ask, run, feed back

The model cannot touch your files, because all it can do is write text. So an agent needs a program outside the model to do the acting for it. The model writes a tool call, and a program around the model, the part that is not AI, reads that text and runs the tool for real, then pastes the result back in front of the model as more text. The model reads that result and writes the next tool call. This repeats until the model writes an answer with no tool call in it, which is the signal that it thinks it is done.

I call one trip around this loop a turn. Not everyone uses the word this way. Some people mean the whole exchange from your message to the final answer, and in one trip a model can also ask for several tools at once. Here, a turn is one round of ask, run, feed back.

Two facts follow from this picture.

The first is that every action is a tool call. The model has no other way to do anything, so there is a door that every action passes through. Whoever stands at that door can see, and stop, everything the agent does. A hook stands there: a small program of yours that the platform runs at fixed points, just before and just after each tool call. (For the built-in tools and for subagents I have seen every call pass the hook point, though I have not tested MCP tools. The next chapter, Hooks, has the details.)

The second is that the model sees only text. It does not see your screen or your disk, only what is in its context: the rules, your words, the results of earlier tool calls and its own earlier answers. That context also has a size limit, which is what The context is a budget is about.

When does it stop?

The ordinary stop is the one just described, the model answering without asking for a tool. But there are others. You can press stop, the platform can reach a limit, or something can refuse the stop.

That last one is useful. A hook can run when the agent is about to stop, look at the to-do list of the task (the steps it still has open), and say "not yet, step 4 is open", after which the loop goes on. This is how an agent is made to work through a long list without you, a case that Use subagents sparingly covers along with its stop rules. It is a first sign that the loop has places where your own code can step in.

Where you can step in

Look at the loop again. You cannot change how the model thinks. What you can change are four things around it.

  1. What it reads. The rules and instructions put in its context, and the files it is pointed at, make up the most used lever and also the cheapest. Instructions and skills is about it.
  2. Which tools exist. An agent that has no tool for changing files cannot change files. A tool's description and its error messages are also the only manual the model gets for it (When an Agent misuses a tool, check its description and errors first). To give a role a shorter list, you use a custom agent (Custom agents).
  3. A hook before a call. Code here sees the call before it runs and can refuse it. Because the platform guarantees that every call passes through this point, a rule here is code that runs, not a request. A hook is not the only rule made of code, though. A tool list, or a command the agent runs to check itself, also counts, only each covers a narrower range (chapter 4.1). Permission settings and sandboxes are another kind of lever. They do not read the call but limit what any command can do, so I leave them out of the four.
  4. A hook after a call. Code here sees the result, can keep a record, and can add a note for the model. It cannot undo what happened.

A short way to remember the four is that two of them decide what the model knows, and two decide what it is allowed to do. Words only change what it knows.

Why most mistakes are not in the loop

That split, between what the model knows and what it is allowed to do, is also how I read an agent's mistakes. The loop itself almost never breaks. The mistakes come from what is in the context, or from what is allowed. Below is the list I keep from my own use. It records what I have seen, not a statistic.

What you see Usually why
It changed what it should not It reasons about how to get the job done, not whether it is allowed.
It forgot something from earlier The context was compressed or the chat was too long.
It checked its own work and said it was fine The same model with the same reasoning has the same blind spots.
It keeps retrying a refused action It wants to finish the task.
It said "done" and it was not In my experience models lean towards reporting success.

Few of these are about the model being unintelligent. The first and the last need a check outside the model. Of the rest, the second needs a better context (Long chats get worse) and the third a second view (Use subagents sparingly). Only the fourth is close to a habit of the model itself. So the opening question has its answer: the fix usually belongs at one of the four places, not in the model's thinking.

See the loop yourself

You do not need to install anything to watch the loop go round. In your agent's chat, ask "Read the README and tell me what the project does" and watch the chat. Before the answer you will see a line such as "Read README.md". That line is one tool call, shown to you. Now ask a question that needs three files, and count the lines. Each is one turn of the loop, and each result is now in the context.

這台機器是什麼，你又能從哪裡伸手進去

問、執行、餵回去

模型碰不到你的檔案，因為它能做的只有寫文字。所以 agent 得靠模型外面的程式替它動手。模型先寫出一個工具呼叫，模型周圍的這個程式（也就是不是 AI 的那一部分）讀到這段文字，就真的去執行這個工具，再把結果當成更多文字，貼回模型面前。模型讀完結果，又寫出下一個工具呼叫。就這樣一圈一圈地轉，直到模型寫出一個不含工具呼叫的回答，這就是它認為自己做完了的訊號。

我把繞這個迴圈一圈叫做一輪。不是每個人都這樣用這個詞。有些人用它指從你的訊息到最後回答的整段來回。再說，模型在一圈裡也可以同時要求好幾個工具。所以在這裡，一輪就是問、執行、餵回去這一個回合。

這張圖引出兩個事實。

第一個事實是，每個動作都是工具呼叫。模型沒有別的辦法做任何事，所以有一扇每個動作都會經過的門。誰站在這扇門口，誰就看得到、也擋得住 agent 做的一切。hook 就站在那裡：它是你的一個小程式，平台在每次工具呼叫之前和之後的固定位置執行它。（內建工具和子 agent，我看過每次呼叫都經過 hook 的位置，不過 MCP 工具我沒有測過。細節見下一章 Hooks：每次呼叫都會經過的執行點。）

第二個事實是，模型只看得到文字。你的螢幕、你的磁碟，它都看不到，它看到的只有上下文裡的東西：規則、你說的話、之前工具呼叫的結果，還有它自己之前的回答。而上下文還有大小上限，上下文是一份預算 講的就是這件事。

什麼時候停？

一般的停止就是上面說的那種：模型沒有要求工具，直接回答。但停下來的方式不只一種。你可以按停止，平台可能到了上限，也可能有東西拒絕了這次停止。

最後這種很有用。agent 要停下來的時候，可以執行一個 hook，去看任務的待辦清單（還沒做完的步驟），然後說「還沒，第 4 步還沒做完」，迴圈就會繼續下去。讓 agent 不靠你、把一長串清單做完，靠的就是這個辦法，慎用子 agent 講了這種情況和它的停止規則。從這裡已經能看出一點端倪：迴圈上有一些地方，你自己的程式碼可以插進去。

你能在哪裡插手

再看一次這個迴圈。模型怎麼思考，你改變不了；你能改變的，是它周圍的四樣東西。

  1. 它讀什麼。放進它上下文的規則和指令，以及指給它看的檔案，是用得最多、也最便宜的槓桿。指令與 skill：只載入需要的 講的就是這個。
  2. 有哪些工具。沒有改檔案工具的 agent，就改不了檔案。工具的描述和錯誤訊息，也是模型拿到的關於這個工具的唯一手冊（Agent 用不好工具，先看工具的描述和錯誤訊息）。想給一個角色較短的工具清單，就用 custom agent（Custom agent：固定模型和工具的角色）。
  3. 呼叫前的 hook。這裡的程式碼在呼叫執行之前就看得到它，並且能拒絕它。平台保證每次呼叫都會經過這一點，所以這裡的規則是會執行的程式碼，不是請求。不過，用程式碼寫成的規則不只 hook 一種。工具清單，或 agent 用來檢查自己的指令，也算，只是各自涵蓋的範圍窄一些（提示裡的規則只是請求）。權限設定和沙箱是另一種槓桿。它們不讀呼叫，而是限制任何指令能做什麼，所以我沒把它們算進這四樣。
  4. 呼叫後的 hook。這裡的程式碼看得到結果、可以留下紀錄，還能為模型加一則備註。不過，已經發生的事，它沒辦法撤銷。

有個簡單的記法：這四樣裡，兩樣決定模型知道什麼，兩樣決定它被允許做什麼。光靠寫下來的話，你改變的只是它知道什麼。

為什麼大部分錯誤不在迴圈裡

「知道什麼」和「被允許做什麼」這條分界，也是我看 agent 錯誤的角度。迴圈本身幾乎不會壞，錯誤不是出在上下文裡有什麼，就是出在允許它做什麼。下面這張清單，是我自己用下來慢慢整理的，記的是我看到的情況，算不上統計。

你看到的 通常為什麼
它改了不該改的 它推理的是怎麼把事做完，不是被不被允許。
它忘了先前的某件事 上下文被壓縮了，或者對話太長。
它檢查了自己的工作，說沒問題 同一個模型、同樣的推理，有同樣的盲點。
它一直重試被拒絕的動作 它想把任務完成。
它說「做完了」，其實沒有 依我的經驗，模型傾向回報成功。

細看這幾條，很少是因為模型不夠聰明。第一條和最後一條，需要模型外面的一道檢查。剩下的，第二條需要更好的上下文（長對話會變差），第三條需要第二個視角（慎用子 agent）。只有第四條，接近模型自己的習慣。這樣一來，開頭的問題也有了答案：要修的，通常是這四個地方中的某一個，而不是模型的思考。

自己看看迴圈

想親眼看迴圈怎麼轉，你不用安裝任何東西。在 agent 的對話裡問一句：「讀 README，告訴我這個專案做什麼。」然後盯著對話看。回答出來之前，你會看到一行像「Read README.md」的字，那一行就是一次工具呼叫，只是顯示給你看了。接著再問一個需要讀三個檔案的問題，數一數有幾行。每一行是迴圈的一輪，而每個結果現在都留在上下文裡了。

这台机器是什么，你又能从哪里伸手进去

问、运行、喂回去

模型碰不到你的文件，因为它能做的只有写文本。所以 agent 得靠模型外面的程序替它动手。模型先写出一个工具调用，模型外面的这个程序（也就是不是 AI 的那部分）读到这段文本，就真的去运行这个工具，再把结果当作更多的文本，贴回模型面前。模型读完结果，又写出下一个工具调用。就这样一圈一圈地转，直到模型写出一个不带工具调用的回答，这就是它认为自己做完了的信号。

我把绕这个循环走一圈，叫作一轮。不是每个人都这么用这个词。有些人用它指从你发消息到最终回答的整个来回。再说，模型在一圈里也可以同时要求用好几个工具。所以在这里，一轮就是一次“问、运行、喂回去”。

这幅图引出了两个事实。

第一个事实是，每个动作都是一次工具调用。模型没有别的办法做任何事，所以有一扇门，每个动作都要从这里经过。谁站在这扇门口，谁就能看到并拦住 agent 做的一切。hook 就站在那里：它是你的一个小程序，平台在每次工具调用之前和之后、在固定的点上运行它。（对内置工具和子 agent，我见过每次调用都经过 hook 点，不过 MCP 工具我没有测过。细节见下一章硬性规则放在哪？用 hook。）

第二个事实是，模型只看得到文本。你的屏幕、你的磁盘，它都看不到，它看到的只有上下文里的内容：规则、你说的话、之前工具调用的结果，还有它自己之前的回答。而上下文还有大小上限，为什么不能把所有规则都塞给 Agent？讲的就是这件事。

它什么时候停？

通常的停止就是上面说的那种：模型不再要求工具，直接作答。但停下来的方式不止这一种。你可以按停止，平台可能到了某个上限，也可能有什么东西拒绝了这次停止。

最后这一种很有用。agent 要停的时候，可以运行一个 hook，去看任务的待办清单（它还没做完的步骤），然后说“还没完，第 4 步还没做”，循环就会接着走下去。让 agent 不用你守着、把一长串清单做完，靠的就是这个办法，别跟风瞎用子 Agent讲了这种情况和它的停止规则。从这里已经能看出一点端倪：循环上有一些地方，你自己的代码可以插进去。

你能在哪里插手

再看一遍这个循环。模型怎么思考，你改变不了；你能改的，是它周围的四样东西。

  1. 它读什么。放进它上下文的规则和指令，以及指给它看的文件，是用得最多的杠杆，也是最便宜的。规则写太多，Agent 反而记不住讲的是这个。
  2. 有哪些工具。没有改文件工具的 agent，就改不了文件。工具的描述和报错信息，也是模型拿到的关于这个工具的唯一说明书（Agent 用不好工具，先看工具的描述和报错）。想给一个角色一份更短的工具清单，就用自定义 agent（什么时候才需要自定义 Agent？）。
  3. 调用前的 hook。这里的代码在调用运行之前就能看到它，并且能拒绝它。平台保证每次调用都经过这个点，所以这里的规则是会运行的代码，不是请求。不过，用代码写成的规则不只 hook 一种。一份工具清单，或者一条让 agent 自查用的命令，也算，只是各自覆盖的范围更窄（为什么 Agent 不听 prompt 里的规则？）。权限设置和沙箱是另一类杠杆。它们不读调用本身，而是限制任何命令能做什么，所以我没把它们算进这四样里。
  4. 调用后的 hook。这里的代码能看到结果、留下记录，还能给模型加一条备注。不过，已经发生的事它撤销不了。

有个简便的记法：这四样里，两样决定模型知道什么，两样决定它被允许做什么。光靠写下来的话，你改变的只是它知道什么。

为什么大多数错误不出在循环里

“知道什么”和“被允许做什么”这条分界，也是我看 agent 犯错的角度。循环本身几乎不会坏，错误要么出在上下文里有什么，要么出在允许它做什么。下面这张清单是我在自己的使用中攒下来的，记的是我见过的情况，算不上统计数据。

你看到的 通常的原因
它改了不该改的 它推理的是怎么把活干完，不是被不被允许。
它忘了前面的某件事 上下文被压缩了，或者对话太长了。
它检查了自己的工作，说没问题 同一个模型，同样的推理，有同样的盲区。
它对一个被拒绝的操作不停重试 它想把任务做完。
它说“做完了”，其实没有 按我的经验，模型倾向于汇报成功。

细看这几条，很少是因为模型不够聪明。第一条和最后一条，需要模型之外的一道检查。剩下的，第二条需要更好的上下文（对话越久，Agent 越笨），第三条需要另一个视角（别跟风瞎用子 Agent）。只有第四条，接近模型本身的习惯。这下，开头的问题有了答案：要修的，通常是这四个地方中的某一个，而不是模型的思考。

自己看看这个循环

想亲眼看看循环怎么转，你不用安装任何东西。在 agent 的对话里问一句：“读一下 README，告诉我这个项目是做什么的。”然后盯着对话看。回答出来之前，你会看到一行类似“Read README.md”的字，这一行就是一次工具调用，只是展示给你看了。接着再问一个需要读三个文件的问题，数数有几行。每一行都是循环的一轮，而每一个结果，现在都留在了上下文里。

What the loop costs, and how it is misread

The cost of the loop starts from that last point, that every result stays in the context. Each time around, the model reads the whole context again, now with one more result in it, so a task of thirty turns is thirty reads of a growing text. What the agent reads therefore matters more than how clever the model is, and the model's price per token is the wrong number to look at alone.

The reread is not always charged at full price, though. Providers cache a repeated beginning, and on Anthropic's API a cache read costs about a tenth of the base input price (Prompt caching). So the cache lowers the bill. It does nothing for the other cost: the model still has to attend to all of that text.

And of all that text, tool results are the biggest part and the least watched. You wrote the prompt, so you know what is in it. The file the agent read, or the log a command printed, you may never have seen. It is still in the context, where the model may act on it.

An agent is not always the answer, either, because letting the model choose its own next step has a price. Such a loop costs more and is harder to predict than a fixed series of model calls, or a single call. Anthropic's advice is to find the simplest solution possible and add complexity only when needed (Building effective agents). If the steps of a job never change, a script that calls the model at fixed points may serve you better than an agent.

One more trap has nothing to do with cost. It is easy to read the loop as a plan, and it is not one. The model does not plan the whole path and then follow it. It decides one turn at a time from what it sees, so when it goes down a wrong path, it is usually because the result of an earlier turn led it there.

迴圈要花什麼，又容易被怎麼誤讀

迴圈的開銷，就是從「每個結果都留在上下文裡」這一點開始的。每繞一圈，模型都要把整個上下文重讀一遍，裡面又多了一個結果，所以三十輪的任務，就是把一份越來越長的文字讀三十次。也因此，agent 讀什麼比模型有多聰明更重要，只看每個 token 的單價，是看錯了數字。

不過，重讀不一定按全價收費。供應商會把重複的開頭快取起來，在 Anthropic 的 API 上，讀快取的價格大約是基本輸入價的十分之一（Prompt caching）。快取省下的是錢，省不下的是另一筆：模型還是得把注意力分到那麼多文字上。

而在這麼多文字裡，工具結果是最大的一塊，也是最少人盯著的一塊。prompt 是你寫的，裡面有什麼你心裡有數。可是 agent 讀的檔案、指令印出來的紀錄，你可能從來沒看過。它們照樣在上下文裡，模型也可能照著它們去做。

也不是每件事都該交給 agent，因為讓模型自己決定下一步是有代價的。這樣的迴圈比一串固定的模型呼叫、或單次呼叫花得更多，也更難預測。Anthropic 的建議是找到最簡單的解法，只在需要時才加複雜度（Building effective agents）。如果一件工作的步驟從來不變，一個在固定位置呼叫模型的腳本，可能比 agent 更適合你。

還有一個陷阱和開銷無關。人很容易把迴圈讀成一份計劃，可它不是。模型不是先規劃好整條路，再照著走下去，而是每一輪根據眼前看到的東西做決定。所以它走錯路，通常是前面某一輪的結果把它帶去的。

循环要花什么，又容易被怎么误读

循环的开销，正是从“每个结果都留在上下文里”这一点开始的。每绕一圈，模型都要把整个上下文重读一遍，而里面又多了一个结果，所以一个三十轮的任务，就是把一段越来越长的文本读三十遍。也因此，agent 读什么比模型多聪明更要紧，只盯着模型每个 token 的价格看也是不对的。

不过，重读并不总是按全价收费。提供方会缓存重复的开头，在 Anthropic 的 API 上，读缓存的价格约是基础输入价的十分之一（Prompt caching）。缓存省下的是钱，省不下的是另一笔：模型还是得把注意力分到那一大段文本上。

而在这一大段文本里，工具结果是最大的一块，也是最少有人盯着的一块。prompt 是你写的，里面有什么你心里有数。可 agent 读的文件、一条命令打印出来的日志，你可能从来没见过。它们照样在上下文里，模型也可能照着它们去行动。

也不是每件事都该交给 agent，因为让模型自己决定下一步是有代价的。这样的循环比一串固定的模型调用、或者单次调用更贵，也更难预测。Anthropic 的建议是找最简单的解决办法，只在需要时才增加复杂度（Building effective agents）。如果一件事的步骤从来不变，一个在固定位置调用模型的脚本，可能比 agent 更适合你。

还有一个坑和开销无关。人很容易把循环读成一份计划，可它不是。模型不会先规划好整条路，再照着走下去，而是每一轮根据眼前看到的东西做决定。所以它走上错路，通常是前面某一轮的结果把它带过去的。

When to delete my hooks, and what stays Industry practice

Will any of this go out of date? The reasoning about the loop does not retire while agents work by calling tools, but the practical parts may. Today I steer at four places because that is what the platform gives me. If the platform starts to offer a native way to enforce a rule, a budget or a stop condition, I will use that instead of my own hooks.

什麼時候可以刪掉我的 hook，什麼會留下來 業界做法

這一章講的這些，會不會過時？只要 agent 還是靠呼叫工具運作，關於迴圈的道理就不會退役，但實務的部分可能會。今天我在四個地方掌舵，是因為平台給我的就是這些。如果平台開始提供原生的辦法，來執行規則、預算或停止條件，我會改用那個，不再用自己的 hook。
