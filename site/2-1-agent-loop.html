How does an Agent actually work?Agent 到底是怎麼做事的？Agent 到底是怎么干活的？

This chapter assumes only that you've used an AI coding agent, such as Copilot in agent mode.

讀這一章，只需要你用過寫程式的 AI agent，例如 Copilot 的 agent 模式。

读这一章，只需要你用过写代码的 AI agent，比如 Copilot 的 agent 模式。

The Knowledge經驗分享经验分享

In one sentence

An agent is a loop in which the model decides what to do, a program outside the model does it, and the result goes back to the model so it can decide the next step. There are four places on that loop you can change, so when an agent gets something wrong, work out which of them to fix before you reach for a different model or a longer prompt.

一句話

agent 就是一個迴圈：模型決定要做什麼，外面的程式替它去做，結果再回到模型面前，讓它決定下一步。這個迴圈上有四個地方可以改，agent 出錯時，先找出該改哪一處，再考慮換模型或加 prompt。

一句话

agent 就是一个循环：模型决定要做什么，外面的程序替它做，结果回到模型面前，模型再决定下一步。这个循环上有四个地方可以改，agent 出错时先判断该改哪一处，再考虑换模型或者加 prompt。

For leaders

  • The decision: when an agent goes wrong, ask which of the four places needs fixing (what it reads, which tools it has, the check before a call, the check after a call) before you pay for a pricier model or ask for a longer prompt.
  • The risk: the loop itself rarely breaks, and what breaks is usually one of the four things around it. A rule written in a prompt is only a request the model may not follow, and the loop stops when the model no longer wants a tool, not when the work is actually finished, so an agent that says "done" shouldn't be taken at its word.
  • The cost of doing it right: mostly setup time. The cheapest fix is changing what the agent reads, which can take a few lines of rules. The checks before and after a call are code, and someone has to maintain them.
  • Ask the team: "The last time a result was bad, did we fix the context or the tool list, or did we add a check outside the model?"

給主管

  • 要做的決定：agent 出了問題，先問該改四個地方裡的哪一個（它讀什麼、有哪些工具、呼叫之前的檢查、呼叫之後的檢查），再考慮換更貴的模型或寫更長的 prompt。
  • 風險：迴圈本身很少出問題，出問題的通常是它周圍的這四樣。寫在 prompt 裡的規則只是請求，模型不一定照做，而迴圈什麼時候停，看的是模型還要不要工具，不是事情有沒有真的做完，所以 agent 說「做完了」，不能直接當真。
  • 做對的成本：主要是設定的時間。最便宜的是改 agent 讀什麼，寫幾行規則就夠了。呼叫前後的檢查是程式碼，要有人維護。
  • 可以問團隊：「上一次結果不好，我們修的是上下文、工具清單，還是加了一道模型之外的檢查？」

写给管理者

  • 要拍板的事：agent 出了问题，先问该改四个地方里的哪一个（它读什么、有哪些工具、调用之前的检查、调用之后的检查），再考虑换更贵的模型或者写更长的 prompt。
  • 风险：循环本身很少出问题，出问题的通常是它周围这四样。写在 prompt 里的规则只是请求，模型不一定照做；循环什么时候停，看的是模型还要不要工具，不看活有没有真的做完，所以 agent 说“做完了”不能直接当真。
  • 做对的代价：主要是配置的时间。最便宜的是改 agent 读什么，写几行规则就够；调用前后的检查是代码，要有人维护。
  • 可以问团队：“上一次结果不好，我们修的是上下文、工具清单，还是加了一道模型之外的检查？”

When an agent goes wrong, don't rush to blame the model

When an agent makes a mistake, people tend to assume the model behind it got something wrong, so they keep adding lines to the prompt to guard against it, like "be careful" or "don't do XX", or they switch to a smarter model, say from Sonnet to Opus with thinking effort turned all the way up. Sometimes that helps, but it doesn't touch the root cause, because what an agent ends up doing depends not only on the model but also on what the model has read, which tools it has, and whether anything checks a tool call before and after it runs, and all of that sits outside the model, where switching to another model can't reach it.

An AI agent really has two parts, the model (the LLM) and the tools (Tool Calling). You send a prompt and the model thinks, but a model on its own is a brain with no hands: it can't look up a file, change a file, run a terminal command, open a browser or drive your whole computer through Computer Use by itself, and Tool Calling is how it gets those things done. Once the model has decided what to do, it issues a call through the tool interface it has been given, and a program outside the model actually runs it (Claude Code and Copilot's agent mode are both programs like this). The result comes back as the model's next input, the model reads it and thinks again, and it decides either to call another tool or that the task is done, in which case it writes you a reply, and that reply is the answer you see.

That process is what we call the Agent Loop.

There are four places on this loop you can change: what the model reads, which tools it gets, the check before a tool call, and the check after one. In this chapter I want to teach you to read that loop, so that the next time an agent goes wrong, you first work out which of the four to fix, and only then think about switching models or adding to the prompt.

agent 出錯，先別急著怪模型

agent 犯錯的時候，大家通常會覺得是背後的大模型出了錯，於是繼續往 prompt 裡加句子來防，像是「小心」「不要做 XX」，或者換一個更聰明的模型，例如從 Sonnet 換到 Opus，再把推理強度開到最高。這些有時候有用，但碰不到根本原因，因為 agent 最後做出什麼事，不只看模型，還要看模型讀到了什麼、手上有哪些工具、呼叫工具的前後有沒有檢查，這些都在模型外面，換一個模型也改變不了。

AI agent 其實由兩部分組成：模型（LLM）和工具（Tool Calling）。你送出 prompt，模型開始思考，可是模型本身只是一顆大腦，沒有手，查檔案、改檔案、執行終端機指令、開瀏覽器，甚至用 Computer Use 從頭到尾操作你的電腦，這些它自己都做不到，要靠 Tool Calling。模型想好要做什麼，就透過提供給它的工具介面發出呼叫，由外面的程式真正去執行（Claude Code、Copilot 的 agent 模式都是這樣的程式），執行的結果再當成下一段輸入交回模型。模型拿到以後繼續思考，決定是再呼叫工具，還是任務已經完成，如果完成了，就回給你一段結果，也就是你看到的答案。

上面這個流程，就是所謂的 Agent Loop（迴圈）。

這個迴圈上有四個地方可以改：模型讀到什麼、給它哪些工具、呼叫工具之前的檢查、呼叫之後的檢查。這一章我想教你看懂這個迴圈，以後 agent 出錯時，先判斷該改哪一處，再考慮換模型或加 prompt。

agent 出错，别急着怪模型

agent 犯错的时候，人会觉得是背后的大模型出了错，于是就继续在 prompt 里加很多句子去规避这种风险，比如“小心”“不要做 XX”，或者换一个更聪明的模型，比如从 Sonnet 换到 Opus，把 thinking effort 开到最高。这些有的时候管用，但是这并不是根因，因为 agent 最后做出什么事，不光看模型，还要看模型读到了什么、手里有哪些工具、调用工具的前后有没有检查，这些都在模型外面，换一个模型也改变不了。

AI agent 其实包括两部分：模型（LLM）和工具（Tool Calling）。用户发出 prompt，模型进行思考，但是模型本身就是一个大脑，它没有手，那它怎么来触碰你的本地系统呢（比如查文件、改文件、运行一个终端命令、访问浏览器，或者直接进行 Computer Use 来全程操作你的电脑）？这就是靠 Tool Calling。模型思考以后决定要做什么操作，通过提供给它的工具接口发出调用，外面的程序（Claude Code、Copilot 的 agent 模式都是这样的程序）真正去运行，返回一个结果作为下一段输入，模型拿到以后就继续思考，决定下一步是继续调用工具，还是认为任务已经完成，然后返回给用户一段结果，这就是你看到的答案。

How the loop runs, and how to change its four places

On every turn, the model reads the prompt from scratch

This book calls one trip around the loop a turn. The program assembles the prompt and sends it to the model, the model writes back some text, possibly with one or more tool calls in it, and the program runs those tools, records the results and decides whether to go on. The VS Code team draws the same line when they describe Copilot's loop, though they call it a round, and they say the prompt is rebuilt on every round (The Coding Harness Behind GitHub Copilot in VS Code). The model remembers nothing from one turn to the next, and anything that isn't in this turn's prompt doesn't exist as far as it's concerned, so the system instructions, the rules, what you said, and every earlier tool call along with its result all have to be put back in on every turn. Watch the word when you read the docs, though: Claude Code's and Copilot's documentation usually say turn for the whole stretch from the message you send to the answer you get back, which can hold many of this book's turns.

Two things follow from this. The first is that every action the agent takes is a tool call, because the model has no other way to do anything, and since the tools are run by a program outside the model, a call can be stopped before it runs. That's where a hook sits: a small program you write that the platform runs at fixed moments, such as before and after every tool call (Hooks, the point every call passes through). The second is that the model sees nothing but the text in the prompt. It can't see your screen or your disk, so its picture of the project is whatever the context says, and the context has a size limit (Context is a budget).

Whether a hook catches every call depends on the platform. Claude Code's docs say outright that tool calls inside subagents and MCP tools fire the same hooks (Hooks reference). Copilot's docs only say that hooks fired inside a subagent get a few extra input fields, and the tool names they list are all built-in tools, with no mention of MCP (GitHub Copilot hooks reference). On Copilot I've seen calls from built-in tools and from subagents go through hooks, but I haven't tested MCP tools. Two kinds of action skip this path entirely. One is server-side tools, which run at the provider with none of your code in between (When an Agent misuses a tool, check its description and errors first). The other is a file you reference with @ in Claude Code, which by default goes straight into the context without any tool call, so a hook that guards file reads never fires.

The loop stops when the model stops asking for tools

There's only one normal way for the loop to end, and that's a turn in which the model asks for no tool. On Anthropic's API the loop keeps going as long as stop_reason is tool_use, and once the model writes its answer, stop_reason becomes end_turn and the loop exits (How tool use works). Copilot works the same way: when a turn has no tool calls, its text is the final answer. So a stopped loop only tells you that the model thinks it's done, not that the work is done, and nothing along the way has checked the result for you.

The other two ways to stop aren't the model's call. One is you pressing stop, and the VS Code docs are clear that stopping doesn't undo actions already completed, or changes already made to external services (Build with AI in VS Code). The other is a platform limit: VS Code's chat.agent.maxRequests caps how many requests the agent can make, and the default is 25 (AI settings reference).

There's also the opposite case, in which the model wants to stop and gets sent back. Copilot's agentStop and Claude Code's Stop are hooks that run when the model finishes its answer, and they can return block with a reason, which goes back to the model as a new prompt, so the loop carries on. That's a useful spot to have. When the model says it's done, the hook can check the to-do list or run the tests, and if something's missing it can answer "not done yet, step 4 is still open", which lets an agent work through a long list without you watching over it (Use subagents sparingly). The price is that the agent might never stop, and every turn costs money, so Copilot CLI and Claude Code both have a safety valve that forces the stop after 8 blocks in a row, and a hook can tell from the stop_hook_active field that the current turn is one that was already sent back (GitHub Copilot hooks reference, Hooks reference).

There are four places on the loop you can change

You can't change how the model thinks. What you can change are the four things around it.

  1. What it reads. Rules files, skills and the files you point it at are all text placed in its context, and this is the most used and the cheapest of the four, since a few lines of rules can tell it things it would never guess on its own (Instructions and skills, load only what you need). The weakness is that all this text is only a request the model may not follow, and once a conversation gets long, both VS Code and Claude Code compact its earlier part into a summary, which can lose details and instructions from the start.
  2. Which tools it has. The model can only call the tools it has been given, and a tool's description and error messages are the only way it learns what that tool does (When an Agent misuses a tool, check its description and errors first). To give a role a fixed, shorter tool list, you use a custom agent (Custom agents). The weakness is that a tool can often do more than its name says: take away the file-editing tool but leave the terminal, and the agent can still edit files with commands.
  3. The check before a call. Before a tool runs, a hook sees the tool's name and arguments, and it can let the call through or refuse it with a reason that goes back to the model. The platform runs the hook and the model can't skip it, so a rule here is code that runs, not a request. Hooks aren't the only way to enforce a rule in code, either: the tool list, and a command the agent runs to check itself, also count, they just cover narrower ground (A rule in a prompt is a request). The platform's own approval rules sit here too, such as VS Code's auto-approve rules, which match on the text of a command. The weakness is that the check sees only the text of the call and not what the command does once it's running, and the VS Code docs say plainly that hooks aren't a substitute for enforced permissions, sandboxing or enterprise controls (Security).
  4. The check after a call. After a tool runs, a hook sees the result. It can keep a record or add a note for the model, and in Copilot and Claude Code it can even rewrite the result the model reads. The weakness is that it can't undo what has already happened, as the VS Code docs also point out (Hooks), so any action you need to stop has to be stopped before the call.

Places 1 and 4 change what the model knows, and places 2 and 3 change what it can do. Anything that lives only in a rules file changes nothing but what it knows.

A sandbox is a different kind of thing. It doesn't look at calls at all but limits what a command can touch once it's running, so I haven't counted it among the four (Some things you never hand over).

When something goes wrong, first find which place to fix

The loop itself rarely goes wrong. Anthropic's docs give its standard form as a while loop on stop_reason, only a few lines of code, and nearly every problem turns up at one of the four places instead. The table below comes from my own use of agents, so it records what I've seen rather than any statistics.

What you see Usually why Fix this first
It changed something it shouldn't have It's thinking about how to get the job done, not about whether it's allowed to The check before a call, or a shorter tool list
It forgot something said earlier The context was compacted, or the conversation ran too long What it reads: put what matters in a file instead of leaving it in the chat (Long chats get worse)
It checked its own work and said it was fine The same model with the same reasoning has the same blind spots A check from another angle: a second agent, or a command (Use subagents sparingly)
It keeps retrying an action that was refused It wants to finish the task Make the refusal's reason say what to do instead (Asking is not a limit)
It said "done" and it wasn't The loop only asks whether the model wants another tool, and models lean towards reporting success A check when it stops, and letting it run the tests itself (Let the agent check its own work)

The third and the last rows aren't only my experience, because Anthropic has written about both. They found that agents grading their own work skew positive, confidently praising work that's only mediocre (Harness design for long-running application development), and that Claude tends to mark a feature as complete without testing it properly (Effective harnesses for long-running agents). Few of these come down to the model not being clever enough, so switching models belongs after you've checked all of them (Don't pick a model by token price alone).

Watch the loop go round once yourself

You don't need to install anything to see the loop in action. In your agent's chat, ask "Read the README and tell me what this project does", and before the answer appears you'll see a line like "Read README.md". That line is one tool call, and VS Code collapses its details by default, so expand it to see the input and output (Use tools with agents). Then ask a question that needs three files and you'll see three calls, which may be bunched into a single turn, and all three results are now sitting in the context. To see exactly what the model receives each time, run Developer: Show Chat Debug View in VS Code. It lists every model interaction with its system prompt, prompt, context, response and tool inputs and outputs, and paging through them one at a time shows you what each turn added (Debug chat interactions). The view contains your code and file paths, so look it over before you share it.

迴圈怎麼轉，四個地方怎麼改

每一輪，模型都要把 prompt 從頭讀一遍

繞迴圈走一圈，這本書叫一輪：程式把 prompt 組好送給模型，模型回一段文字，裡面可能帶著一個或幾個工具呼叫，程式執行這些工具、記下結果，再決定要不要繼續。VS Code 團隊介紹 Copilot 的迴圈時也是這樣切的，只是他們叫 round，而且說 prompt 每一輪都會重新組一次（The Coding Harness Behind GitHub Copilot in VS Code）。模型在兩輪之間什麼都不記得，這一輪的 prompt 裡沒有的東西，對它來說就不存在，所以系統提示、規則、你說過的話、之前每一輪的工具呼叫和結果，每一輪都得重新放進去。看文件時要留意，Claude Code 和 Copilot 的文件說 turn，通常指從你送出一則訊息到它給出回答的整段過程，中間可以有很多輪。

從這個過程可以看出兩件事。第一，agent 的每個動作都是一次工具呼叫，因為模型沒有別的辦法做事，而工具是由模型外面的程式執行的，所以在執行之前可以把呼叫攔下來。hook 就放在這個位置，它是你寫的一支小程式，平台會在固定的時機執行它，例如每次工具呼叫之前和之後（Hooks：每次呼叫都會經過的執行點）。第二，模型只看得到 prompt 裡的文字，你的螢幕、你的磁碟它都看不到，它以為專案長什麼樣子，全看上下文裡寫了什麼，而上下文有大小上限（上下文是一份預算）。

hook 能不能管到所有呼叫，要看平台。Claude Code 的文件寫明了，子 agent 裡的工具呼叫和 MCP 工具都會觸發同樣的 hook（Hooks reference）。Copilot 的文件只說，在子 agent 裡觸發的 hook，輸入會多幾個欄位，列出來的工具名稱也都是內建工具，沒有提到 MCP（GitHub Copilot hooks reference）。我在 Copilot 上看過內建工具和子 agent 的呼叫都會經過 hook，MCP 工具則沒有測過。另外有兩樣東西完全不走這條路。一樣是伺服器端工具，它們在供應商那邊執行，中間沒有你的程式碼（Agent 用不好工具，先看工具的描述和錯誤訊息）。另一樣是 Claude Code 裡用 @ 引用的檔案，預設直接放進上下文，不經過工具呼叫，所以攔讀檔的 hook 根本不會觸發。

模型不再要工具，迴圈就停了

迴圈正常結束的條件只有一個，就是模型這一輪沒有要求工具。在 Anthropic 的 API 上，只要 stop_reason 是 tool_use 就繼續轉，等模型寫完回答、stop_reason 變成 end_turn，迴圈就結束（How tool use works）。Copilot 也一樣，一輪裡沒有工具呼叫，這段文字就是最後的回答。所以迴圈停下來，只代表模型覺得做完了，不代表事情真的做完了，中間沒有任何東西替你檢查過結果。

另外兩種停法不是模型決定的。一種是你自己按停止，VS Code 的文件寫得很清楚，停止不會撤銷已經完成的動作，也不會撤銷對外部服務做過的改動（Build with AI in VS Code）。另一種是平台的上限，VS Code 的 chat.agent.maxRequests 限制 agent 能送出多少次請求，預設是 25（AI settings reference）。

還有一種情況剛好相反：模型想停，卻被擋了回去。Copilot 的 agentStop 和 Claude Code 的 Stop，是模型寫完回答時執行的 hook，它可以回傳 block 加上一個原因，這個原因會當成新的 prompt 送回模型，迴圈就繼續轉。這個位置很好用。模型說做完了，hook 可以去看待辦清單或者跑一次測試，沒通過就回一句「還沒完，第 4 步還沒做」，agent 不用你在旁邊盯著，也能把一長串清單做完（慎用子 agent）。代價是它可能一直停不下來，而每轉一輪都要花錢，所以 Copilot CLI 和 Claude Code 都設了保險，連續擋 8 次以後就強制結束，hook 自己也能從 stop_hook_active 這個欄位看出，這一輪已經是被擋回來過的（GitHub Copilot hooks reference、Hooks reference）。

迴圈上有四個地方可以改

模型怎麼思考，你改變不了，你能改的是它周圍的四樣東西。

  1. 它讀什麼。規則檔、skill、你指給它看的檔案，都是放進上下文的文字，這是用得最多、也最便宜的辦法，寫幾行規則，就能告訴它自己猜不到的事（指令與 skill：只載入需要的）。短處是這些文字只是請求，模型可能不照做，而且對話一長，VS Code 和 Claude Code 都會把前面的內容壓縮成摘要，早期的細節和指示就可能不見了。
  2. 有哪些工具。模型只能呼叫你給它的工具，工具的描述和錯誤訊息，也是它認識這個工具的唯一管道（Agent 用不好工具，先看工具的描述和錯誤訊息）。想給某個角色固定一份比較短的工具清單，就用 custom agent（Custom agent：固定模型和工具的角色）。短處是工具能做的事常常比名字大，你拿掉了改檔案的工具，只要還留著終端機，它照樣能用指令改檔案。
  3. 呼叫之前的檢查。工具執行之前，hook 看得到工具名稱和參數，可以放行，也可以拒絕並說明原因，原因會送回給模型。hook 是平台執行的，模型跳不過去，所以這裡的規則是會執行的程式碼，不是請求。用程式碼守住規則也不只 hook 一種，工具清單、讓 agent 自我檢查的指令都算，只是涵蓋的範圍比較窄（提示裡的規則只是請求）。平台內建的批准規則也在這個位置，例如 VS Code 依指令文字比對的自動批准規則。短處是它看到的只有呼叫的文字，指令執行起來實際做了什麼，它看不到，VS Code 的文件也說，hook 不能取代強制執行的權限、沙箱或企業管控（Security）。
  4. 呼叫之後的檢查。工具執行之後，hook 看得到結果，可以留一筆紀錄，可以給模型補一段話，在 Copilot 和 Claude Code 裡還能改寫模型讀到的結果。短處是已經發生的事它撤銷不了，VS Code 的文件也是這樣寫的（Hooks），所以要擋的動作，只能在呼叫之前擋。

這四處裡，第 1、4 處改變模型知道什麼，第 2、3 處改變它能做什麼。只寫在規則檔裡的東西，改變的只有它知道什麼。

沙箱是另一類，它不看呼叫，限制的是指令執行起來以後能碰到什麼，所以我沒有把它算進這四樣（有些東西根本不給）。

常見的錯，先看該改哪一處

迴圈本身很少出問題，Anthropic 的文件說，它的標準寫法就是一個依 stop_reason 判斷的 while 迴圈，沒幾行程式碼，出問題的幾乎都在上面這四處。下面這張表是我自己用 agent 時累積下來的，記的是我看過的情況，不是統計資料。

你看到的 通常的原因 先改哪裡
它改了不該改的 它想的是怎麼把事做完，不是准不准它做 呼叫之前的檢查，或者縮小工具清單
它忘了前面說過的事 上下文被壓縮了，或者對話太長 它讀什麼：重要的東西放進檔案，不要只留在對話裡（長對話會變差）
它檢查自己的成果，說沒問題 同一個模型、同樣的推理，有同樣的盲點 換個角度來查：另一個 agent，或者一條指令（慎用子 agent）
它一直重試一個被拒絕的動作 它想把任務完成 拒絕的原因要寫清楚該改做什麼（詢問不是限制）
它說「做完了」，其實沒有 迴圈只看模型還要不要工具，而模型又傾向回報成功 停下時的檢查，讓它自己跑測試（讓 agent 能檢查自己的活）

第三條和最後一條不只是我看過，Anthropic 也寫過。他們發現 agent 給自己的成果打分時總是偏高，品質普通也會很有自信地稱讚（Harness design for long-running application development），Claude 也有沒好好測試就把功能標成完成的傾向（Effective harnesses for long-running agents）。這幾條的原因很少是模型不夠聰明，所以換模型，應該排在這些都查過之後（選模型，別只看 token 單價）。

自己看一次迴圈怎麼轉

想親眼看迴圈怎麼轉，什麼都不用裝。在 agent 的對話裡問一句「讀一下 README，告訴我這個專案是做什麼的」，回答出來之前，你會看到一行類似「Read README.md」的字，這就是一次工具呼叫。VS Code 預設把細節收起來，展開就看得到它的輸入和輸出（Use tools with agents）。再問一個需要讀三個檔案的問題，你會看到三次呼叫，它們可能擠在同一輪裡，而這些結果現在都留在上下文裡了。想看模型每次到底收到了什麼，就在 VS Code 裡執行 Developer: Show Chat Debug View，它會依每一次和模型的互動，列出系統提示、prompt、上下文、回答，以及工具的輸入和輸出，一筆一筆翻過去，就能看到每一輪多了什麼（Debug chat interactions）。這個畫面裡有你的程式碼和檔案路徑，分享之前要先看過一遍。

循环怎么转，四个地方怎么改

每一轮，模型都要重新读一遍 prompt

绕循环走一圈，这本书叫一轮：程序把 prompt 拼好发给模型，模型写回一段文本，可能还带着一个或几个工具调用，程序运行这些工具、记下结果，再决定要不要继续。VS Code 团队讲 Copilot 的循环时也是这么分的，他们叫 round，并且说 prompt 在每一轮都重新构建一次（The Coding Harness Behind GitHub Copilot in VS Code）。模型在两轮之间什么都不记得，这一轮的 prompt 里没有的东西，对它来说就不存在，所以系统指令、规则、你说的话、之前每一轮的工具调用和结果，每一轮都要重新放进去。读文档的时候要注意，Claude Code 和 Copilot 的文档说 turn，一般指你发一条消息到它给出回答这一整段，里面可以有很多轮。

从这个过程能得出两件事。第一，agent 的每个动作都是一次工具调用，模型没有别的办法做事，而工具是模型外面的程序运行的，所以运行之前可以拦下来。hook 就放在这个位置，它是你写的一个小程序，平台在固定的时机运行它，比如每次工具调用之前和之后（硬性规则放在哪？用 hook）。第二，模型只看得到 prompt 里的文本，你的屏幕、你的磁盘它都看不到，它以为项目是什么样子，全看上下文里写了什么，而上下文有大小上限（为什么不能把所有规则都塞给 Agent？）。

hook 能不能管住所有调用，要看平台。Claude Code 的文档写明了，子 agent 里的工具调用和 MCP 工具都会触发同样的 hook（Hooks reference）。Copilot 的文档只说子 agent 里触发的 hook 输入会多几个字段，列出来的工具名都是内置工具，没有提 MCP（GitHub Copilot hooks reference），我在 Copilot 上见过内置工具和子 agent 的调用都经过 hook，MCP 工具没有测过。另外有两样东西不走这条路。一样是服务端工具，它们在提供方那边运行，中间没有你的代码（Agent 用不好工具，先看工具的描述和报错）。另一样是 Claude Code 里用 @ 引用的文件，默认直接放进上下文，不经过工具调用，所以拦读文件的 hook 不会触发。

模型不再要工具，循环就停了

循环正常结束的条件只有一个：模型这一轮没有要工具。在 Anthropic 的 API 上，只要 stop_reason 是 tool_use 就接着转，模型写完回答，stop_reason 变成 end_turn，循环就退出（How tool use works）。Copilot 也一样，这一轮没有工具调用，这段文本就是最后的回答。所以循环停下来，只说明模型觉得做完了，不说明活真的做完了，中间没有任何东西替你检查过结果。

另外两种停法不是模型决定的。一种是你自己按停止，VS Code 的文档说得很清楚，停止不会撤销已经做完的动作，也不会撤销对外部服务的改动（Build with AI in VS Code）。另一种是平台的上限，VS Code 的 chat.agent.maxRequests 限制 agent 能发多少次请求，默认是 25（AI settings reference）。

还有一种情况正好相反，模型想停，被挡了回去。Copilot 的 agentStop 和 Claude Code 的 Stop 是模型写完回答时运行的 hook，它可以返回 block 和一个原因，这个原因会当作新的 prompt 送回模型，循环就接着转。这个位置很有用，模型说做完了，hook 可以去看待办清单或者跑一遍测试，没通过就说“还没完，第 4 步没做”，agent 不用你守着也能把一长串清单做完（别跟风瞎用子 Agent）。代价是它可能一直停不下来，而每转一轮都要花钱，所以 Copilot CLI 和 Claude Code 都设了保险，连续挡 8 次以后强制结束，hook 自己也能从 stop_hook_active 这个字段看出，这一轮已经是被挡回来的（GitHub Copilot hooks reference、Hooks reference）。

循环上有四个地方可以改

模型怎么思考你改变不了，你能改的是它周围的四样东西。

  1. 它读什么。规则文件、skill、你指给它看的文件，都是放进上下文的文本，这是用得最多、也最便宜的办法，写几行规则就能告诉它自己猜不到的事（规则写太多，Agent 反而记不住）。短板是这些文本只是请求，模型可能不照做，而且对话长了，VS Code 和 Claude Code 都会把前面的内容压缩成摘要，早期的细节和指令可能就丢了。
  2. 有哪些工具。模型只能调用给了它的工具，工具的描述和报错也是它了解工具的唯一途径（Agent 用不好工具，先看工具的描述和报错）。想给一个角色固定一份更短的工具清单，就用自定义 agent（什么时候才需要自定义 Agent？）。短板是工具的能力常常比名字大，你拿掉了改文件的工具，只要还留着终端，它照样可以用命令改文件。
  3. 调用之前的检查。工具运行之前，hook 能看到工具名和参数，可以放行，也可以拒绝并说明原因，原因会送回给模型。hook 是平台运行的，模型跳不过去，所以这里的规则是会运行的代码，不是请求。用代码守规则也不只有 hook 这一种，工具清单、自查用的命令都算，只是覆盖的范围更窄（为什么 Agent 不听 prompt 里的规则？）。平台自带的审批规则也在这个位置，比如 VS Code 按命令文本匹配的自动批准规则。短板是它看到的只是调用的文本，命令运行起来做了什么它看不到，VS Code 的文档也说 hook 不能替代强制执行的权限、沙箱或者企业管控（Security）。
  4. 调用之后的检查。工具运行之后，hook 能看到结果，可以留一条记录，可以给模型加一段话，Copilot 和 Claude Code 还能改写模型读到的结果。短板是已经发生的事它撤销不了，VS Code 的文档也是这么写的（Hooks），所以要挡住的动作只能放在调用之前。

这四处里，第 1、4 处改变模型知道什么，第 2、3 处改变它能做什么。只写在规则文件里的东西，改变的只是它知道什么。

沙箱是另一类，它不看调用，限制的是命令运行起来以后能碰什么，所以我没把它算进这四样（不要开放全部的权限或使用沙箱）。

常见的错，先看该改哪一处

循环本身很少出问题，Anthropic 的文档说它的标准写法就是一个按 stop_reason 判断的 while 循环，没几行代码。出问题的基本都在上面这四处。下面这张表是我自己用 agent 时攒下来的，记的是我见过的情况，不是统计数据。

你看到的 通常的原因 先改哪里
它改了不该改的 它想的是怎么把活干完，不是被不被允许 调用之前的检查，或者收紧工具清单
它忘了前面说过的事 上下文被压缩了，或者对话太长了 它读什么：要紧的东西放进文件，不留在对话里（对话越久，Agent 越笨）
它检查自己的活，说没问题 同一个模型、同样的推理，有同样的盲区 换一个视角来查：另一个 agent 或者一条命令（别跟风瞎用子 Agent）
它不停重试一个被拒绝的操作 它想把任务做完 拒绝的原因写清楚该改做什么（“先问我”为什么挡不住 Agent？）
它说“做完了”，其实没有 循环只看模型还要不要工具，模型又倾向于报告成功 停止时的检查，让它自己跑测试（让 Agent 自己跑测试）

第三条和最后一条不只是我见过，Anthropic 也写过。他们发现 agent 给自己的活打分时总是偏高，质量一般也会很有信心地夸（Harness design for long-running application development），Claude 也有没好好测就把功能标成完成的倾向（Effective harnesses for long-running agents）。这几条的原因很少是模型不够聪明，所以换模型要放到这些都查过以后（选模型，别只看 token 单价）。

自己看一次循环怎么转

想亲眼看循环怎么转，什么都不用装。在 agent 的对话里问一句“读一下 README，告诉我这个项目是做什么的”，回答出来之前你会看到一行类似“Read README.md”的字，这就是一次工具调用，VS Code 默认把细节折叠起来，展开就能看到它的输入和输出（Use tools with agents）。再问一个要读三个文件的问题，你会看到三个调用，它们可能挤在同一轮里，这些结果现在都留在上下文里了。想看模型每次到底收到了什么，在 VS Code 里运行 Developer: Show Chat Debug View，它按每次模型交互列出系统提示、prompt、上下文、回答和工具的输入输出，一次一次翻过去，就能看到每一轮多了什么（Debug chat interactions）。这个视图里有你的代码和文件路径，分享之前要先看一遍。

The loop costs more with every turn, and it isn't a plan

Most of what the loop costs goes on rereading. On every turn the model reads the whole context again, now with the last turn's results added, so the amount it reads grows faster than the number of turns. Using the numbers from the worked example in Don't pick a model by token price alone, 10 turns read 325,000 tokens in total and 20 turns read 1,150,000, about 3.5 times as much. Prompt caching makes the rereading much cheaper: on Anthropic's API a cache read costs a tenth of the base input price on most models, and a twentieth on Opus 5.5 and Sonnet 5.5 (Prompt caching). But caching only saves money. The text still fills the context window and still pulls on the model's attention, and Anthropic says context "must be treated as a finite resource with diminishing marginal returns" (Effective context engineering for AI agents).

Of all that text, the part nobody watches much is the tool results. You wrote the prompt, so you know what's in it, but the files the agent read and the logs a command printed may be things you've never seen. They take up the window all the same, and the model may act on the words in them (Text the agent reads can give it orders). As for how much room they take, Anthropic has one figure: in a 100-turn web search evaluation, automatically clearing stale tool results as the context neared its limit cut token use by 84% (Managing context on the Claude Developer Platform).

Letting the model choose its own next step has a price of its own. Anthropic says agentic systems trade latency and cost for better task performance, and recommends finding the simplest solution possible and adding complexity only when it's needed (Building effective agents). If the steps of a job never change, a script that calls the model at fixed points may suit you better than an agent, because it's cheaper and easier to predict.

The other trap is reading the loop as a plan. The model doesn't work out the whole route first and then follow it. On each turn it decides the next step from that turn's prompt, and even if it wrote a plan at the start, the plan is just a piece of text in the context. So when an agent heads down the wrong path, it was usually led there by the result of some earlier turn, and that result is still in the context, read again on every turn that follows.

迴圈越轉越貴，而且它不是一份計畫

迴圈的錢主要花在重讀上。每轉一輪，模型都要把整個上下文再讀一遍，裡面還多了上一輪的結果，所以讀的量比輪數漲得快。用選模型，別只看 token 單價那個算例的數字，10 輪總共要讀 325,000 個 token，20 輪就是 1,150,000 個，大約 3.5 倍。prompt 快取能讓重讀便宜很多，Anthropic 讀快取的價格在大多數模型上是輸入價的十分之一，在 Opus 5.5 和 Sonnet 5.5 上是二十分之一（Prompt caching）。但快取省下的只是錢，這些內容照樣占著上下文視窗，照樣分走模型的注意力，Anthropic 說上下文是「邊際收益遞減的有限資源」（Effective context engineering for AI agents）。

在這些文字裡，最少人盯著的是工具結果。prompt 是你寫的，裡面有什麼你心裡有數，可是 agent 讀的檔案、指令印出來的紀錄，你可能從來沒看過，它們一樣占著視窗，模型也可能照著裡面的文字去行動（agent 讀到的文字可能在指揮它）。它們能占掉多少，Anthropic 有一個數字：在一個 100 輪的網頁搜尋評測裡，快到上限時自動清掉過期的工具結果，token 用量少了 84%（Managing context on the Claude Developer Platform）。

讓模型自己決定下一步，本身也有代價。Anthropic 說 agent 是拿延遲和成本去換更好的任務表現，建議先找最簡單的辦法，需要時才增加複雜度（Building effective agents）。如果一件事的步驟從來不變，一個在固定位置呼叫模型的腳本，可能比 agent 更適合你，它比較便宜，也比較好預測。

還有一個坑，是把迴圈當成一份計畫。模型不是先想好整條路再照著走，而是每一輪依這一輪的 prompt 決定下一步，就算它一開始寫了一份計畫，那也只是上下文裡的一段文字。所以它走上錯路，通常是前面某一輪的結果把它帶過去的，而那個結果還留在上下文裡，之後每一輪都會再讀到。

循环越转越贵，而且它不是一份计划

循环的钱主要花在重读上。每转一轮，模型都要把整个上下文再读一遍，里面还多了上一轮的结果，所以读的量比轮数涨得快，用选模型，别只看 token 单价那个算例的数字，10 轮一共读 325,000 个 token，20 轮就是 1,150,000 个，约 3.5 倍。prompt 缓存能让重读便宜很多，Anthropic 读缓存的价格在大多数模型上是输入价的十分之一，在 Opus 5.5 和 Sonnet 5.5 上是二十分之一（Prompt caching），但是缓存省的只是钱，这些内容照样占着上下文窗口，照样分走模型的注意力，Anthropic 说上下文是“边际收益递减的有限资源”（Effective context engineering for AI agents）。

这段文本里最少有人盯着的是工具结果。prompt 是你写的，里面有什么你心里有数，可是 agent 读的文件、命令打印的日志，你可能从来没见过，它们照样占着窗口，模型也可能照着里面的文字去行动（Agent 读到的网页和文件，可能在给它下命令）。它们能占多少，Anthropic 有一个数，在一个 100 轮的网页搜索评测里，快到上限时自动清掉过期的工具结果，token 用量降了 84%（Managing context on the Claude Developer Platform）。

让模型自己决定下一步，本身也有代价。Anthropic 说 agent 是拿延迟和成本去换更好的任务表现，建议先找最简单的办法，需要时才增加复杂度（Building effective agents）。如果一件事的步骤从来不变，一个在固定位置调用模型的脚本可能比 agent 更适合你，它更便宜，也更好预测。

还有一个坑是把循环当成一份计划。模型不是先想好整条路再照着走，它每一轮根据这一轮的 prompt 决定下一步，就算它一开始写了一份计划，那也只是上下文里的一段文本。所以它走上错路，通常是前面某一轮的结果把它带过去的，而那个结果还留在上下文里，后面每一轮都会再读到。

Once the platform has it built in, delete your own hooks Industry practice

As long as agents work by calling tools, the loop and its four places won't go out of date. What will is the part I wrote myself. Today I use hooks to block calls and to push the agent to keep going because those are the places the platform leaves me, and if the platform offers a native way to enforce rules, budgets or stop conditions, I'll switch to it and drop my own hooks. That has already started. VS Code's Autopilot approves every tool and keeps the agent going until the task is complete, and with chat.autopilot.advanced.enabled turned on, a separate model judges whether the request is complete (Security, AI settings reference). Claude Code's /goal is, in effect, a built-in Stop hook (Hooks reference).

平台內建了，就可以刪掉自己的 hook 業界做法

只要 agent 還是靠呼叫工具來做事，這個迴圈和這四個地方就不會過時，會過時的是我自己寫的那部分。我今天用 hook 擋呼叫、催 agent 繼續做，是因為平台留給我的就是這幾個位置，如果平台提供了原生的辦法來強制執行規則、預算或停止條件，我會改用它，不再用自己的 hook。這件事已經開始了。VS Code 的 Autopilot 會批准所有工具，推著 agent 一直做到任務完成，開啟 chat.autopilot.advanced.enabled 之後，還會由另一個模型來判斷請求有沒有完成（Security、AI settings reference），而 Claude Code 的 /goal 就是一個內建的停止 hook（Hooks reference）。
