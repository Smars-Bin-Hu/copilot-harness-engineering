6.5

When the model is upgraded, delete模型升級了，就要刪模型升级了，就要删

This chapter assumes you have used an AI coding agent and that you have written rules or steps for it. Nothing else.

讀這一章，你需要用過寫程式的 AI agent，而且替它寫過規則或步驟。不需要別的。

读这一章，你需要用过一个写代码的 AI agent，并且给它写过规则或步骤。别的都不需要。

The Knowledge經驗分享经验分享

In one sentence

When the model is upgraded, rerun your evals first. Then delete the rules, checks and steps that the new model no longer needs, because scaffolding built for an old model may slow the new one.

一句話

模型升級時，先重跑你的評測。然後刪掉新模型不再需要的規則、檢查和步驟，因為為舊模型搭的鷹架，可能會拖慢新模型。

一句话

模型升级了，先重跑你的评测。然后把新模型已经不需要的规则、检查和步骤删掉，因为为旧模型搭的脚手架，可能会拖慢新模型。

For leaders

  • The decision: after each model change, schedule a review of the setup, and decide who reruns the evals and who may delete a rule.
  • The risk: rules and steps built for an old model may slow the new one. I have not measured this on an upgrade, so it is a worry rather than a result. Hard limits against damage, the record and the evals are not on the list to cut.
  • The cost of doing it right: a rerun of your fixed tasks, more than once, plus one person's time to remove one piece at a time. That is mostly money and time, and I have no numbers for it.
  • Ask the team: "If the model changed tomorrow, which rules would we test removing first, and which evals would tell us?"

給主管

  • 要做的決定：每次換模型之後，安排檢查一次設定，並決定誰重跑評測、誰可以刪規則。
  • 風險：為舊模型搭的規則和步驟，可能會拖慢新模型。我沒有在一次升級上量過這件事，所以它只是個擔心，不是結果。防止損害的硬限制、紀錄和評測，都不在要砍的清單上。
  • 做對的成本：把你的固定任務重跑不只一次，再加上一個人的時間，一次移除一塊。花的大多是錢和時間，確切多少我沒有數字。
  • 可以問團隊：「如果模型明天換了，我們會先測試拿掉哪些規則？哪些評測能告訴我們答案？」

写给管理者

  • 要拍板的事：每次换模型之后，安排一次对配置的复查，并定下谁来重跑评测、谁有权删规则。
  • 风险：为旧模型搭的规则和步骤，可能会拖慢新模型。我没有在一次升级上测过这一点，所以它只是一种担心，不是结果。防止破坏的硬性限制、记录和评测，都不在要砍的清单上。
  • 做对的代价：把你的固定任务重跑不止一遍，再搭上一个人的时间，一次删一块。花的主要是钱和时间，具体多少我没有数字。
  • 可以问团队：“如果明天换了模型，我们会先试着删掉哪些规则？哪些评测能告诉我们结果？”

What happens to the scaffolding when the model gets better?

Think of the setup around an agent as scaffolding, the frame builders put up around a building while they work. Every rule, check and written-out step in it was put there for a reason, to cover something that the model of that day got wrong, did badly or forgot.

Then the model is upgraded. The reasons were about the old model, and with a new one some of them are gone. Nobody told your setup.

This is a real worry, though I have not measured it on an upgrade. What I do have is the history of my own harness, whose first version had levels and three job-title agents. The three agents came out after a few days of use, on the evidence in Use subagents sparingly (that chapter has the cost numbers and their limits), while the levels went for a different reason (What I cut, and what the data says). Both had seemed reasonable at the time they went in. What I take from this is a question rather than a result: might structure built when the model was weaker stop earning its cost once the model improves? If it does, it keeps costing until someone tests it and removes it.

While it stays, scaffolding that no longer earns its place costs in three ways. There is time and money, since every extra step is paid for at every task. There is room, since a long rule file uses part of the context window on every turn (Context is a budget). And there is confusion, because a rule written for an old model's habit can pull a new model the wrong way, a risk I have not measured.

So which pieces are dead, and how would you know?

模型變強了，鷹架會怎樣？

不妨把 agent 周圍的設定想成鷹架（scaffolding），也就是蓋房子時，工人在建築周圍搭起來的那層架子。裡面每一條規則、每個檢查、每一個寫出來的步驟，當初放進去都是有原因的，為的是補上當時的模型做錯、做不好或忘記的事。

可是後來模型升級了。那些原因說的都是舊模型，換了新模型，有些原因也就不在了。偏偏沒有人通知你的設定。

這是個真實的擔心，雖然我沒有在一次升級上量過。我手上有的，是自己這套 harness 的經歷：它的第一版有等級，還有三個按職務分工的 agent。那三個 agent 用了幾天就拿掉了，依據是 慎用子 agent 裡的證據（成本數字和它們的限制都在那一章）。等級被拿掉，則是另一個原因（我砍掉了什麼，數據怎麼說）。這兩樣東西剛放進去的時候，看起來都很合理。我得到的是一個問題，而不是一個結果：模型比較弱時搭起來的結構，等模型進步以後，會不會就不再值回它的成本？如果會，那麼在有人測試它、把它移除之前，它會一直花錢。

這些不再值得留的鷹架，留著的時候，花的成本有三種。一是時間和金錢，每多一步，每個任務都要為它付一次。二是空間，一份長長的規則檔，每一輪都占用上下文視窗的一部分（上下文是一份預算）。三是混亂：為舊模型的習慣寫的規則，可能把新模型拉向錯的方向，不過這個風險我沒有測過。

那麼，哪些部分已經沒用了，你又要怎麼知道？

模型变强了，脚手架会怎样？

不妨把 agent 周围的配置想成脚手架，也就是工人盖楼时在楼外搭起来的那层架子。里面的每条规则、每项检查、每一步写明的步骤，当初放进去都是有理由的，为的是补上当时那个模型做错的、做得差的或者忘掉的东西。

可后来模型升级了。那些理由说的都是旧模型，换了新模型，其中一些也就不成立了。偏偏没人通知你的配置。

这是个实实在在的担心，虽然我没有在一次升级上测过。我手里有的，是自己这套 harness 的经历：它的第一版有分级，还有三个按岗位分工的 agent。那三个 agent 用了几天就拿掉了，依据是慎用子 agent里的证据（成本数字和它们的局限都在那一章）。分级被拿掉，则是另一个原因（我砍掉了什么，数据怎么说）。这两样东西刚放进去的时候，看起来都挺合理。我从中得到的是一个问题，而不是一个结果：模型还弱的时候搭起来的结构，等模型变强以后，会不会就不再值它的成本了？如果会，那么在有人去测它、把它拿掉之前，它会一直花钱。

这些不再值得留的脚手架，留着的时候会在三个方面花钱。一是时间和钱，每多一步，每个任务都要为它付一次。二是空间，一份很长的规则文件，每一轮都占着上下文窗口的一部分（上下文是一份预算）。三是混乱：为旧模型的某个习惯写的规则，可能把新模型往错的方向拉，不过这个风险我没测过。

那么，哪些块已经没用了，你又怎么知道？

How to find out what the new model no longer needs

The rule is simple: do not delete by feeling, and do not keep by habit. Run the evals. The picture shows the order in which that happens.

1. Before you upgrade, have something to rerun

Running the evals assumes there is something to run, which is why fixed tasks come first. Without a set of fixed tasks and a script to score them, an upgrade is a change you cannot judge. So keep the set and its old results as your baseline.

2. Rerun with only the model changed

If the provider publishes notes on moving from the old model to the new one, read them before the rerun, so that you know what to watch. Then run the same tasks on the new model with the same setup, making sure the model is the only thing you changed, and compare the results with the baseline. Even so, more than quality can move: a new model can tokenize text differently, change the default amount of thinking and miss the prompt cache at first. Each of these changes cost without changing quality, so record them next to the numbers.

The rerun then tells you one of two things. Either something got worse (a rule that held with the old model may not hold with the new one), and you want to know that before you remove anything. Or the results got better or held, in which case the gap to look at is the cost: time, usage, turns. Either way, runs differ (One run proves nothing), so run each more than once, or you will read noise as a result.

3. What does not go, whatever the evals say

Before you start removing, it is better to know that some things should not be on the list at all. They start with hard limits against damage: a refusal to touch production, a guard on the rule files, a person approving what cannot be undone. None of these depends on how clever the model is, because they protect against what happens if it is wrong or fooled. A better model is not a reason to remove them (Some things you never hand over). The record stays too, because a better model still needs a log, a report and a person to read them (Record what happened). And the evals stay, because they are how you decide everything else.

The pieces you may cut do not all age at the same speed. Text (rules and steps) changes first and is the easiest to cut. Enforcement in code changes more slowly, and on the evidence of the evals. A platform change sits underneath all of it.

4. Take out one piece at a time

Now you can ask of each piece of scaffolding: does the new model still need it? You find out by removing it and running the tasks again. Take out one piece per round, because if you take out two, you will not know which one mattered.

For a piece like an independent check, the experiment is direct: run the tasks with the check on and with it off, and compare. If the evals show no difference, the check is not earning its cost for those tasks (Use subagents sparingly has the same reasoning for the second agent). But if it still catches things, keep it.

5. What I would look at first

Which pieces would I try first? The table lists the parts that I expect to be the first candidates in my own setup. They are things to test, not results, because I have not rerun them after a model upgrade.

Part Why it may change What I would do
Written-out playbooks for kinds of work A newer model may need steps spelled out less Shorten them. Keep the lists of what counts as done: they say what you want, not how to get it (Manage tasks, not chats)
Independent checks A model may check itself more reliably Compare no check and one check. Only if the evals show no difference between them does the default become no check
Reminders and workarounds They cover a habit the old model had Test with them off (Turn your way of working into skills says the same of "gotchas")
Rules moved into code because the model ignored them The new model may follow them Switch the code rule off where a breach can be undone, and count (A rule in a prompt is a request)
Which model each role uses New models come out Change the one setting, and run the tasks
Wording tuned for the old model Emphasis written to be heard by one model may be too strong for another Rewrite it plainly and run the tasks

The table is only my guess. The fuller list is already in the book. Almost every chapter ends with a section on when to delete what it describes. After an upgrade I go through those sections in order, asking of each one whether its condition now holds.

6. Write down what you deleted, and when you would put it back

When I take something out, I write one line: what, why, and what evidence would bring it back. That line is what keeps the setup from becoming a guess, because when the next model is worse at something, you know which line to look at. (The same habit runs through What I cut, and what the data says.)

Test your own setup

Three questions are worth asking about your own setup:

  1. If the model were upgraded tomorrow, what would you rerun to find out whether your setup still works?
  2. Which rule or step do you keep only because you added it once?
  3. Which one would hurt if it were removed, and how do you know?

There is also a test you can run today. Pick one rule or step in your setup that you suspect is dead weight, then choose three tasks where it should matter. Copy the rule file first, so that you can put the rule back. Then run the tasks with and without it, more than once, and compare pass and usage. If you cannot tell the two apart, you have learned something. If it does matter, you have learned what the rule is worth.

怎麼查出新模型不再需要什麼

規則很簡單：不要憑感覺刪，也不要憑習慣留。跑評測。圖裡畫出了先後順序。

1. 升級之前，先有東西可以重跑

要跑評測，先得有東西可跑，這就是 固定的任務 排在前面的原因。如果沒有一組固定任務和替它們打分的腳本，升級就是一個你沒辦法評判的改動。所以要把這組任務和它舊的結果留好，作為你的基準。

2. 只改模型，重跑

如果供應商發布了從舊模型換到新模型的說明，重跑之前先讀一讀，這樣你就知道要留意什麼。然後在新模型上，用同樣的設定跑同樣的任務，確保變的只有模型，再和基準比較。難處在於，就算只換了模型，也會順帶變掉幾樣東西：新模型可能用不同的方式把文字切成 token，可能改變預設的思考量，一開始也可能沒命中 prompt 快取。它們改變的是成本，不是品質，所以要和數字一起記下來。

這樣重跑下來，結果不外乎兩種。一種是某處變差了：舊模型下守得住的規則，在新模型下可能守不住。這一點你要在動手刪東西之前就知道。另一種是變好了，或者持平，這時要看的差距就是成本：時間、用量、輪數。不管是哪一種，各次運行的結果都不同（一次運行證明不了什麼），所以每個都要跑不只一次，不然你會把雜訊當成結果。

3. 不管評測怎麼說，都不能拿掉的

開始移除之前，最好先知道一件事：有些東西根本不該在這張清單上。頭一類是防止損害的硬限制，比如拒絕碰正式環境、守住規則檔的防護、無法復原的事由人批准。這些都不取決於模型有多聰明，因為它們保護的，是模型錯了或被騙了時會發生的事。更好的模型不是拿掉它們的理由（有些東西根本不給）。紀錄也一樣省不掉，更好的模型仍然需要日誌、報告，和讀它們的人（記下發生了什麼，不是 agent 說了什麼）。評測也要留著，因為其他一切都靠它們來決定。

可以砍的那些，過時的速度也不一樣。文字層面的規則和步驟最先變，也最容易砍。寫進程式碼的執行變得比較慢，砍不砍要看評測。平台的改變，則在這一切的底下。

4. 一次拿掉一塊

到了這裡，就可以對每一塊鷹架問一句：新模型還需要它嗎？要知道答案，就把它拿掉，再把任務跑一次。每一輪只動一塊，因為一次拿掉兩塊，你就不知道是哪一塊有影響了。

比如獨立檢查，實驗做起來就很直接：開著檢查跑一次任務，關掉再跑一次，然後比較。如果評測顯示沒有差別，這個檢查在這些任務上就沒有值回它的成本（慎用子 agent 對第二個 agent 有同樣的推理）。但如果它還是抓得到東西，就留著。

5. 我會先看什麼

在我自己的設定裡，我會先試哪幾塊？下表列的是我預期最先成為候選的部分。它們是要測試的東西，不是結果，因為模型升級之後，我還沒有重跑過它們。

部分 為什麼可能變 我會怎麼做
為各種工作寫出來的手冊 較新的模型，可能不需要把步驟寫得那麼細 縮短它們。留著「什麼才算做完」的清單：它們說的是你要什麼，不是怎麼得到（管任務，不管對話）
獨立檢查 模型可能更可靠地檢查自己 比較沒有檢查和有一次檢查。只有評測顯示兩者沒有差別，預設才變成不檢查
提醒和變通辦法 它們補的是舊模型的習慣 關掉它們來測試（把團隊的做法寫成 skill 對「陷阱」也這麼說）
因為模型不聽，而搬進程式碼的規則 新模型可能會遵守 在違反了還能復原的地方，把程式碼規則關掉，並計數（提示裡的規則只是請求）
每個角色用哪個模型 新模型會出來 改那一個設定，然後跑任務
為舊模型調過的措辭 為了讓一個模型聽見而寫的強調，對另一個可能太重 改寫得平實一點，然後跑任務

這張表只是我的猜測。更完整的清單其實書裡已經有了：這本書幾乎每一章的結尾，都有一節講什麼時候可以把這一章講的東西刪掉。升級之後，我依序把這些節走一遍，逐節問它說的條件現在成不成立。

6. 寫下你刪了什麼，以及什麼時候會放回去

我每拿掉一樣東西，都會寫一行：拿掉了什麼、為什麼，以及什麼證據會讓它回來。有了這一行，設定才不會變成猜測，因為下一個模型在某件事上比較差時，你知道該看哪一行。（我砍掉了什麼，數據怎麼說 裡貫穿的也是這個習慣。）

測你自己的設定

關於你自己的設定，有三個問題值得問一問：

  1. 如果模型明天升級，你會重跑什麼，來知道你的設定還行不行？
  2. 哪一條規則或步驟，你留著只是因為你曾經加過它？
  3. 哪一個拿掉會痛，你怎麼知道？

還有一個今天就能做的測試。挑你設定裡一條你懷疑是累贅的規則或步驟，再選三個它應該有影響的任務。先複製一份規則檔，好讓你能把規則放回去。然後有它和沒它各跑這些任務，而且不只一次，比較通過的情況和用量。如果你分不出兩者，你就學到了一點東西。如果它確實有影響，你就知道了這條規則值多少。

怎么查出新模型不再需要什么

规则很简单：不凭感觉删，也不凭习惯留。跑评测。图里画出了先后顺序。

1. 升级之前，先准备好能重跑的东西

要跑评测，先得有东西可跑，这就是固定任务排在前面的原因。如果没有一组固定任务和给它们打分的脚本，升级就是一个你没法评判的改动。所以要把这组任务和它以前的结果留好，作为你的基线。

2. 只换模型，重跑

如果提供方发布了从旧模型迁移到新模型的说明，重跑之前先读一读，这样你就知道该留意什么。然后在新模型上，用同样的配置跑同样的任务，确保变的只有模型，再和基线比较。难处在于，就算只换了模型，也会顺带变掉几样东西：新模型把文字切成 token 的方式（分词）可能不同，默认的思考量可能变了，一开始还可能命中不了 prompt 缓存。它们改变的是成本，不是质量，所以要和数字记在一起。

这样重跑下来，结果不外乎两种。一种是某个地方变差了：旧模型下管用的规则，换了新模型可能就不管用了。这一点你要在动手删东西之前就知道。另一种是变好了，或者持平，这时要看的差距就是成本：时间、用量、轮数。不管是哪种，每次运行的结果都不一样（一次运行证明不了什么），所以每个都要跑不止一次，否则你会把噪声当成结果。

3. 不管评测怎么说，都不能删的

开始删之前，最好先清楚一点：有些东西根本就不该上这张清单。头一类是防止破坏的硬性限制，比如拒绝碰生产环境、守护规则文件、不可撤销的事要由人审批。这些都不取决于模型有多聪明，因为它们防的是模型出错或者被骗时会发生的事。模型变好了，不是去掉它们的理由（有些东西根本不给）。记录也一样省不掉，更好的模型照样需要日志、报告，以及读它们的人（记下发生了什么）。评测也要留着，因为其他一切都靠它来决定。

可以砍的那些，过时的速度也不一样。文本层面的规则和步骤变得最快，也最容易砍。写进代码的强制执行变得慢一些，砍不砍要看评测。平台的变化，则在这一切的底下。

4. 一次只拿掉一块

到这里，就可以对每一块脚手架问一句：新模型还需要它吗？要知道答案，就把它拿掉，再把任务重跑一遍。每一轮只动一块，因为一次拿掉两块，你就不知道起作用的是哪一块了。

比如独立检查，实验做起来就很直接：开着检查跑一遍任务，关掉再跑一遍，然后比较。如果评测显示没有差别，这项检查在这些任务上就不值它的成本（慎用子 agent对第二个 agent 也是同样的道理）。但如果它还能抓出问题，就留着。

6. 写下你删了什么，什么时候会放回去

我每拿掉一样东西，都会写一行：拿掉了什么、为什么，以及什么证据会让它回来。有了这一行，配置才不至于变成瞎猜，因为下一个模型在某件事上更差时，你知道该看哪一行。（我砍掉了什么，数据怎么说里贯穿的也是这个习惯。）

测你自己的配置

关于你自己的配置，有三个问题值得问一问：

  1. 如果明天模型升级了，你会重跑什么，来看你的配置还管不管用？
  2. 哪条规则或哪一步，你留着只是因为曾经加过？
  3. 哪一个删了会出问题？你怎么知道？

还有一个今天就能做的测试。挑你配置里一条你怀疑是累赘的规则或步骤，再选三个它应该起作用的任务。先把规则文件复制一份，好让你能把规则放回去。然后有它和没它各跑这些任务，不止一次，比较通过情况和用量。如果分不出两者的差别，你就学到了一点东西。如果它确实有影响，你就知道了这条规则值多少。

The risks of removing, and the price of rerunning

The procedure itself has risks and a price. Removing a piece is a change like any other and can break things, which is why you remove one piece at a time and run the evals after each.

Even then, your claim stops at the edge of the evals: you can only say that a piece is not needed for the tasks you tested. If the tasks are few, say so and be careful with anything that guards against damage, because a new model can be worse than the old one at some tasks.

Each rerun also costs money, so a full rerun after every model release is not always affordable. Rerun when you change model family, when the version number changes, or when you notice a change in behaviour. The cache can skew the sum as well. On Anthropic's API, cached reads cost about a tenth of the base input price (Models and cost), but the first runs on a new model start cold. How Copilot bills any of this, I have not checked.

There is a subtler risk, too: scaffolding can hide a weak spot. A check that always caught the same mistake may be the thing that kept you from noticing it, so when you remove it, look at the failed runs.

刪的風險，重跑的代價

這套做法本身也有風險和代價。最直接的是，拿掉一塊和任何改動一樣，也可能弄壞東西，所以要一次只拿掉一塊，每拿掉一塊就跑一次評測。

但即使這樣，結論也只能停在評測的範圍裡：你能說的，只是某一塊在你測過的任務上不需要。如果任務很少，就照實說出來，並且對任何防止損害的東西都要小心，因為新模型在有些任務上可能比舊模型差。

每次重跑也都要花錢，所以每次有模型發布就完整重跑一遍，不一定負擔得起。換模型系列、版本號變了，或你注意到行為變了的時候，再重跑。快取也會讓帳算偏。在 Anthropic 的 API 上，快取讀取大約是基本輸入價格的十分之一（選模型：算的是每次成功的成本），可是新模型上最先的幾次運行是冷啟動，用不上快取。至於這一切 Copilot 怎麼計費，我沒查過。

還有一種更隱蔽的情況：鷹架會把弱點蓋住。一個檢查要是每次都抓到同一種錯誤，可能正是它讓你一直沒注意到那種錯誤，所以拿掉它的時候，要去看失敗的運行。

删的风险，重跑的代价

这套做法本身也有风险和代价。最直接的是，拿掉一块和任何改动一样，也可能把东西弄坏，所以要一次只拿掉一块，每拿掉一块就跑一次评测。

但即便这样，结论也只能停在评测的边界上：你能说的，只是某一块对你测过的那些任务不需要。如果任务很少，就照实说，并且对任何防止破坏的东西都要小心，因为新模型在有些任务上可能比旧模型更差。

每次重跑也都要花钱，所以每发布一个新模型就完整重跑一遍，不一定负担得起。换了模型系列、版本号变了，或者你注意到行为变了，再重跑。缓存也会让账算偏。在 Anthropic 的 API 上，命中缓存的读取约是基础输入价格的十分之一（选模型：看每次成功的成本），可新模型上最初几次运行是冷启动，用不上缓存。至于 Copilot 对这些怎么计费，我没有查过。

还有一种更隐蔽的情况：脚手架会把弱点盖住。一项检查要是每次都抓住同一个错误，可能正是它让你一直没注意到这个错误，所以拿掉它的时候，要去看失败的运行。

When to delete this procedure Industry practice

This chapter is itself a procedure for deleting, so what is there to delete? The step-by-step rerun. If a platform tells you, on your own tasks, what an upgrade changed, or runs your evals on each release, I would use that. What stays is the habit: nothing in the setup is permanent, and every piece has to earn its place against the model you have now.

什麼時候連這套流程也刪掉 業界做法

這一章本身就是一套刪東西的程序，那它還有什麼可刪的？就是一步一步重跑的那套做法。如果有平台能在你自己的任務上告訴你一次升級改變了什麼，或在每次發布時替你跑評測，我會改用它。留下來的是這個習慣：設定裡沒有東西是永久的，每一塊都要對照你現在有的模型，證明自己該留下。

什么时候连这套流程也删掉 业界做法

这一章本身就是一套删东西的流程，那它还有什么可删的？就是一步一步重跑的那套做法。如果有平台能在你自己的任务上告诉你一次升级改变了什么，或者每次发布都替你跑评测，我会用它。留下来的是这个习惯：配置里没有什么是永久的，每一块都得对照你现在用的这个模型，证明自己该留下。
