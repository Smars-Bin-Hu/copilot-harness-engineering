The Knowledge經驗分享经验分享

In one sentence

The three job-title agents cost the most and bought nothing I could measure. Removing them, along with levels and a separate coordinator, made the harness simpler, though only the first removal was measured.

一句話

按職位分工的三個 agent 花得最多，卻沒換來任何我量得出來的東西。把它們連同級別和獨立的協調者一起拿掉，harness 變簡單了，不過量過的只有第一刀。

一句话

三个按岗位分工的 agent 花得最多，却没换来我能量出来的任何东西。把它们连同级别和单独的协调者一起拿掉，harness 简单了，不过量过的只有第一刀。

For leaders

  • The decision: ask of every agent, rule and step what it bought and what would make it safe to remove, then set a time to review the answers.
  • The risk: setups only grow, so every part keeps costing context, upkeep and learning time. The one cut I measured was three job-title agents against one agent, and the team cost several times as much for the same number right (four tasks, run once each).
  • The cost of doing it right: an hour to list the parts and write one line for each. The harder cost is telling the people already using a part what replaces it.
  • Ask the team: "For each agent, rule and step: what did it buy, how do you know, and what would make it safe to remove?"

給主管

  • 要做的決定：對每個 agent、規則和步驟都問一遍，它換來了什麼，怎樣才能安全地拿掉它，然後定一個時間回頭檢查這些答案。
  • 風險：設定只會越長越大，每個部分都在持續花上下文、維護和學習的時間。我量過的只有一刀，三個按職位分工的 agent 對一個 agent：答對的數量一樣，團隊的花費是好幾倍（四個任務，各跑一次）。
  • 做對的成本：一個小時，把各部分列出來，每個寫一行。更難的成本，是告訴已經在用某個部分的人，用什麼取代它。
  • 可以問團隊：「每個 agent、規則和步驟：它換來了什麼，你怎麼知道，怎樣才能安全地拿掉？」

写给管理者

  • 要拍板的事：对每个 agent、规则和步骤都问一遍，它换来了什么，什么情况下可以安全地拿掉，再定一个时间复查这些答案。
  • 风险：配置只会越长越大，每个部分都在持续占用上下文、维护成本和学习时间。我量过的只有一刀，三个按岗位分工的 agent 对一个 agent：做对的数量一样，团队的成本是好几倍（一共四个任务，每个只跑了一次）。
  • 做对的代价：花一个小时把各部分列出来，每个写一句话。更难的代价是，要告诉已经在用某个部分的人，拿什么来替代它。
  • 可以问团队：“对每个 agent、规则和步骤：它换来了什么？你怎么知道？什么情况下可以安全地拿掉？”

What did each part buy, and when can it go?

Every part you add to an agent setup has a price. It takes room in the context, someone has to keep it true, and every newcomer has to learn it. Yet most setups only grow, because adding a part feels like progress and removing one feels like losing something.

So I want to ask each part a different question: what did it buy, and when can it go? If I cannot answer the first half, the part is a cost with no return. If I cannot answer the second, I will keep it forever.

Version 1.0 of my own setup turned out to be a good test of this, because it had several parts that sounded right. I shipped it and used it, and after a few days of use I took out a large share of it in version 1.1. As I go through what I cut and why, the line I most want to keep clear is for each cut, what I measured and what I only judged.

The cuts only make sense against how that version worked. At the start of each job the user chose a level: a light one for a quick answer, a middle one for a medium task, or a heavy one for several agents working together, and each level came with its own rules. A job-title agent is an agent given a role like planner, builder or reviewer, as in a team of people. The heavy level was built out of them. With several roles, someone has to hand out the work. That is the coordinator, an agent whose only job is to hand work to others (the word is used as in Use subagents sparingly), and in the heavy level it was a separate agent of its own. The team kept its plan, its handovers and its results in a request folder, a separate folder apart from the task.

Four cuts came out of that design, and they do not all stand on the same kind of evidence.

每個部分換來了什麼，什麼時候可以拿掉？

你加進 agent 設定的每個部分，都有代價：它占上下文的空間，要有人一直讓它保持正確，每個新人也都得花時間學它。可是多數設定只會越長越大，因為加東西感覺像進步，拿掉東西卻像損失。

所以我想換一個問題去問每個部分：它換來了什麼，什麼時候可以拿掉？答不出前一半，這個部分就是只有成本、沒有回報；答不出後一半，我就會永遠留著它。

我自己設定的 1.0 版，剛好是這個問題的好考題，因為它有好幾個聽起來很對的部分。我發布了它，用了幾天，就在 1.1 版裡拿掉了很大一部分。接下來講我砍了什麼、為什麼砍，一路上我最想守住的一條線是：每一刀，哪些是我量過的，哪些只是我的判斷。

要看懂這幾刀，得先知道那個版本怎麼運作。每個工作開始時，使用者要先選一個級別：輕的用來快速回答，中間的用於中等的任務，重的讓好幾個 agent 一起工作，而每個級別都有自己的規則。按職位分工的 agent，是被給了一個角色的 agent，例如計劃者、實作者或 reviewer，就像一個人的團隊那樣。重級別就是用它們搭起來的。這麼多角色，誰來分配工作？是協調者，也就是只負責把工作交給別人的 agent（用法和 慎用子 agent 一樣）。在重級別裡，它是一個獨立的 agent。這個團隊把計劃、交接和結果放在請求資料夾裡，那是和任務分開的另一個資料夾。

從這套設計裡砍下了四刀，可是每一刀背後的證據並不是同一種。

每个部分换来了什么，什么时候可以拿掉？

往 agent 配置里加的每个部分都有代价：它要占上下文的空间，要有人一直让它保持正确，每个新人还得去学它。可大多数配置只会越长越大，因为加东西感觉像在前进，拿掉东西却像是在失去什么。

所以我想换个问题去问每个部分：它换来了什么，什么时候可以拿掉？前一半答不上来，这个部分就是只花钱不回本；后一半答不上来，我就会永远留着它。

我自己配置的 1.0 版，正好拿来检验这件事，因为它有好几个听起来很对的部分。我发了版，用了几天，然后在 1.1 版里拿掉了其中很大一部分。下面讲我砍掉了什么、为什么砍，一路上我最想讲清楚的一条线是：每一刀，哪些是我量过的，哪些只是我的判断。

要看懂这几刀，得先知道那个版本是怎么运作的。每个工作开始时，用户要先选一个级别：轻的用来快速回答，中等的用于中等任务，重的让几个 agent 一起干活，而每个级别各有各的规则。按岗位分工的 agent，是被指定了计划者、开发者或 reviewer 这类角色的 agent，就像人的团队那样。重级别就是用它们搭起来的。这么多角色，谁来分活？是协调者，也就是只负责把活分给别人的 agent（这个词的用法和别跟风瞎用子 Agent里一样）。在重级别里，它是一个单独的 agent。这个团队把计划、交接和结果放在请求文件夹里，那是和任务分开的另一个文件夹。

从这套设计里砍下了四刀，可每一刀背后的证据并不是同一种。

Four cuts, and how sure I am of each

At a glance

The table puts the four cuts side by side with the evidence behind each, leaving the reasons to the sections after it.

Cut What it was meant to buy Why it went Evidence Reconsider when
Three job-title agents A division of labour like a human team Several times the cost, same result Measured: 4 tasks, one run each, direction only A comparison on a larger, messier task shows a gain
Levels Rules matched to the difficulty of a job Only one was used; hard to choose; rules clashed My experience of use, no count How hard a job is can be reliably told before it starts
Separate coordinator Someone to hand out the work The one that understands is not the one that acts; the worker learns it again Reasoned; a clue in the test records, not measured alone The platform can restore the context of a finished subagent
Request folder A separate place for a team's files Nothing needed it once the team was gone Follows from the other cuts, untested A flow comes back that needs its own workspace

The test I use for any part

Before the cuts one by one, here is the test behind them. Your setup only grows too, so the questions are as much for you as for me. Whenever I decide whether to keep a part, I ask the same few (the ones in Roll out and govern a harness). What failure does it prevent, with a real example? What does it cost? What would have to change for it to go? The cuts below are those questions answered late, after use.

In the picture of the two versions, the lit box marks the one cut I measured and the dashed boxes are the cuts I did not.

Cut 1: the three job-title agents (measured)

In 1.0, the heavy level ran a team in which a coordinator wrote the plan, a builder made the changes and a reviewer checked them. I compared it with one agent working alone on the same four tasks. That test is told in Use subagents sparingly, so instead of repeating it I will only go through what limits it.

The first limit is size. Each of the four tasks ran only once, and a second run would move the numbers. The second is that the two sides were not equal. The single agent used a top model, while the team had a knowledge base to read (A knowledge base: an honest index of the code). With limits like these, why trust the test at all? What I trust is the direction: the team cost several times more and got the same number right. The exact ratio I do not trust.

That is enough to say the team did not pay on those tasks, but not that a team never pays. Not all of the team went, though. I kept one role, the independent reviewer, because an independent check is one of the four things worth a second agent. That is reasoning rather than measurement, since I did not test the reviewer alone to the same standard as the cut I did measure.

Cut 2: levels (design history, no data)

What I have on levels is what I saw while using them over a few days. I did not log how often each was used, so it is experience, not a count. Only the middle level got used, while the light and the heavy ones sat idle most of the time. Even so, every job began with the extra step of choosing a level. And when two sets of rules sat side by side, the agent got confused and gave wrong explanations of which one applied.

The deeper reason under all of that is that how hard a job is cannot be told before it starts, yet a level asks you to guess it.

What replaced levels is the task, with care set by what a mistake would cost and by the kind of task (Manage tasks, not chats).

Cut 3: the separate coordinator (reasoned, partly from the test)

The coordinator did understand the task. That was never the trouble. The trouble was that the one that understood was not the one that acted, so the worker it handed the task to had to learn it again. That matches what I saw in the records of the three-role test, where the coordinator read the files and understood the change, after which the builder started from nothing and read them again.

What the test cannot do is single out the coordinator. It compared the whole team with one agent, not the team with and without a separate coordinator. So I have no number for the coordinator alone, and the double reading in the records is a clue, not a measurement. The rest is an argument: whoever moves a task forward has to understand it, and the agent that holds the task already does.

Cut 4: the request folder (design history, no data)

The last cut followed from the others. The heavy-level team kept its work in a request folder, separate from the task folder, so once the heavy-level flow was gone, a second place to keep a job's files had no use. The task folder is now the workspace. One place is easier to find, to back up, and for a person or a new session to read. I did not test any of this.

What the cuts took out, and what it did to the harness

In all, the 1.1 release removed the levels, the whole heavy-level flow with its commands, two agents, a skill, some numbers in the configuration and the request folder. It also shortened the rules that are injected at the top of every prompt to three or four lines and dropped the limits on the count of searches and tool calls. The agent now sees fewer rules, and fewer ways to be confused.

That is the benefit I trust most, even though it is not a measurement. A smaller harness is easier to explain, to test and to hand to a colleague (Roll out and govern a harness). What the change did to accuracy or cost, I did not measure.

Things I chose not to build

Cuts deal with things that existed. Beside them I keep a second list, of things I decided not to build, each with the condition that would make me reconsider. A few examples:

  • I did not let agents send messages to each other, because a subagent has no state and messages across sessions were not verified. I will reconsider when that is measured to be reliable.
  • I did not let several subagents change the same files at once. That would bring merge conflicts, and the code cannot be run to judge who is right, so it waits until the repository can run its tests locally.
  • Nor did I build my own sandbox, context compression or subagent scheduling. The platform keeps changing these, so I would rather wait for the platform.
  • Features on Preview or experimental settings stay unbuilt too, since they can change or vanish. That waits until they are stable.

The habit behind the list is simple. A "no" that comes with a reason and a condition can be reopened, while a "no" with neither becomes a taboo.

我對任何部分都用的測試

一刀一刀看之前，先說這幾刀背後的測試。你的設定其實也只會越長越大，所以這些問題不只是我問自己的，也是問你的。決定要不要留下一個部分時，我都會問同樣的幾個問題（就是 落地與治理 裡那些）。它防止什麼失敗，有真實的例子嗎？它花多少？要變成什麼樣，它才能拿掉？下面的每一刀，就是這些問題晚了一步才得到的答案。

在這張兩個版本的圖裡，亮著的方框是我量過的那一刀，虛線方框則是我沒量的幾刀。

第一刀：三個按職位分工的 agent（量過）

在 1.0 裡，重級別會讓一個團隊上場：協調者寫計劃，實作者改程式碼，reviewer 檢查。我拿它和一個 agent 單獨做事相比，用的是同樣的四個任務。那個測試在 慎用子 agent 裡講過，所以這裡不重複，只講它有哪些限制。

第一個限制是規模小。四個任務各只跑了一次，再跑一次，數字就會動。第二個限制是兩邊並不對等。單一 agent 用的是頂級模型，團隊卻有一個知識庫可以讀（知識庫：程式碼的誠實索引）。限制這麼多，這個測試還能信什麼？我相信的是方向，也就是團隊花了好幾倍，答對的數量卻一樣。確切的倍數，我不信。

這足以說明在那些任務上團隊不划算，卻不能說團隊永遠不划算。不過，團隊也沒有整個拿掉。我留下了一個角色，就是獨立的 reviewer，因為獨立檢查是值得多一個 agent 的四件事之一。只是這一條靠的是推理：量那一刀的標準，我從沒單獨拿來測過 reviewer。

第二刀：級別（設計歷史，沒有數據）

關於級別，我有的只是幾天裡用它們時看到的事。我沒有記錄每個級別各用了幾次，所以這是經驗，不是計數。只有中間的級別被用到，輕的和重的多半閒置。每個工作開始前，卻還是得先選一次級別。兩套規則並排放著的時候，agent 還會被搞糊塗，把「哪一套適用」解釋錯。

這些背後還有一個更深的原因：工作有多難，在開始之前是看不出來的，級別卻要你先去猜。

那用什麼取代級別？是任務：照出錯的代價和任務的種類，決定要多小心（管任務，不管對話）。

第三刀：獨立的協調者（推理出來的，部分來自測試）

協調者其實懂這個任務，問題從來不在這裡。問題在於，懂的那個不是動手的那個，所以接手做事的 agent 得把任務再學一遍。這和我在三角色測試的紀錄裡看到的一致：協調者讀了檔案，懂了這個改動，接著實作者又從零開始，把這些檔案重新讀了一遍。

可是那個測試沒辦法把協調者單獨拿出來看。它比的是整個團隊和一個 agent，而不是有、沒有獨立協調者的兩個團隊。所以單看協調者，我沒有數字。紀錄裡那次重複閱讀，只算線索，不是量測。撐著這一刀的，是一個論證：推動任務前進的，必須懂這個任務，而手上拿著任務的那個 agent 本來就懂。

第四刀：請求資料夾（設計歷史，沒有數據）

最後一刀是跟著前面幾刀來的。重級別的團隊把工作放在請求資料夾裡，和任務資料夾分開，所以重級別的流程一沒了，第二個放工作檔案的地方就沒有用了。現在任務資料夾就是工作區。只有一個地方，比較好找、好備份，人或新會話讀起來也比較容易。這些我都沒有測過。

這幾刀拿掉了什麼，對 harness 做了什麼

算起來，1.1 版拿掉了級別、整個重級別的流程和它的指令、兩個 agent、一個 skill、設定裡的一些數字，還有請求資料夾。它也把每個 prompt 開頭注入的規則縮短成三、四行，並去掉了對搜尋次數和工具呼叫次數的限制。現在 agent 看到的規則更少，能搞糊塗的地方也更少。

這是我最相信的好處，雖然它不是量出來的。小一點的 harness，比較好說明、好測試，也比較好交給同事（落地與治理）。至於對準確度或成本的影響，我沒有量過。

我選擇不做的事

前面說的都是砍，拿掉原本存在的東西。還有一類，是我一開始就決定不做的，記在第二份清單裡，每一項都附上會讓我重新考慮的條件。舉幾個例子：

  • 我沒有讓 agent 之間互相傳訊息，因為子 agent 沒有狀態，跨會話的訊息也沒有驗證過。等量出它可靠了，再重新考慮。
  • 我沒有讓好幾個子 agent 同時改同一批檔案。那樣會有合併衝突，而且程式碼跑不起來，就沒辦法判斷誰對，所以要等倉庫可以在本機跑測試了再說。
  • 我也沒有自己做沙箱、上下文壓縮或子 agent 排程。平台一直在改這些，所以我寧可等平台。
  • 建在 Preview 或實驗性設定上的功能，我也沒有做，因為它們可能改變或消失。等它們穩定了再說。

這份清單背後的習慣其實很簡單。附上理由和條件的「不」，以後可以重新打開；兩樣都沒有的「不」，會變成禁忌。

我对任何一个部分用的检验

一刀刀看之前，先说这几刀背后的检验。你的配置其实也只会越长越大，所以这些问题不只是我在问自己，也是留给你的。决定要不要留下一个部分时，我都会问同样的几个问题（就是怎么把 Agent 配置推广到整个团队？里的那几个）。它防止了什么故障，有真实的例子吗？它花多少？要变成什么样，它才能拿掉？下面这几刀，就是这些问题晚了一步才得到的答案。

在这张两个版本的图里，亮着的框是我量过的那一刀，虚线框是我没量过的几刀。

第 1 刀：三个按岗位分工的 agent（量过）

在 1.0 里，重级别会跑一个团队：协调者写计划，开发者改代码，reviewer 做检查。我拿它和一个 agent 单干做对比，用的是同样的四个任务。那个测试在别跟风瞎用子 Agent里讲过，这里不再重复，只说它有哪些局限。

头一个局限是规模小。四个任务每个只跑了一次，再跑一次，数字就会变。第二个局限是两边的条件不对等。单个 agent 用的是顶级模型，团队却有一份知识库可读（为什么要给代码建一个知识库？）。局限这么多，这个测试还能信什么？我信的是方向，也就是团队贵了好几倍，做对的数量却一样。具体的倍数，我不信。

这足以说明在那些任务上团队不划算，却不能说明团队永远不划算。不过，团队也没有整个拿掉。我留下了一个角色，就是独立的 reviewer，因为独立检查是值得多开一个 agent 的四样东西之一。只是这一条靠的是推理：量那一刀的标准，我从没单独拿来测过 reviewer。

第 2 刀：级别（设计史，没有数据）

关于级别，我手里有的只是几天里用它们时看到的情况。我没有记录每个级别各用了多少次，所以这是经验，不是计数。只有中等级别被用到，轻的和重的大多数时候都闲着。每个工作开始前，却还是得先选一次级别。两套规则放在一起时，agent 还会被弄糊涂，把“哪套适用”解释错。

这些背后还有一个更深的原因：一个工作有多难，开工之前是判断不了的，级别却要你先去猜。

那用什么替代级别？是任务，谨慎的程度由出错的代价和任务的类型来定（一个任务一个文件夹）。

第 3 刀：单独的协调者（推理出来的，部分来自测试）

协调者其实弄懂了任务，问题从来不在这里。问题在于，弄懂的那个不是动手的那个，于是接手干活的 agent 还得把任务再学一遍。这和我在三角色测试的记录里看到的一致：协调者读了文件，弄懂了要改什么，接着开发者又从零开始，把这些文件重新读了一遍。

可这个测试没法把协调者单独拎出来看。它比较的是整个团队和一个 agent，而不是有、没有单独协调者的两个团队。所以单看协调者，我没有数字。记录里那次重复阅读，只算线索，不是测量。撑着这一刀的，是一个论证：推动任务往前走的，必须理解这个任务，而手里拿着任务的那个 agent 本来就理解。

第 4 刀：请求文件夹（设计史，没有数据）

最后一刀是跟着前面几刀来的。重级别的团队把工作放在请求文件夹里，和任务文件夹分开，所以重级别的流程一没了，再留第二个放工作文件的地方就没有用了。现在任务文件夹就是工作区。只有一个地方，找起来、备份起来都更容易，人或者新会话读起来也更省事。这些我都没有测过。

这几刀拿掉了什么，对 harness 有什么影响

算下来，1.1 版拿掉了级别、整个重级别的流程（连同它的命令）、两个 agent、一个 skill、配置里的一些数字，还有请求文件夹。它还把注入在每条 prompt 最前面的规则缩短到三四行，并去掉了对搜索次数和工具调用次数的限制。现在 agent 看到的规则更少，能被弄糊涂的地方也更少。

这是我最信的好处，虽然它不是测量出来的。更小的 harness 更容易解释、更容易测试，也更容易交给同事（怎么把 Agent 配置推广到整个团队？）。至于对准确率和成本的影响，我没有量过。

我选择不做的

前面说的都是砍，拿掉原来有的东西。还有一类，是我一开始就决定不做的，记在第二份清单里，每一项都带着会让我重新考虑的条件。举几个例子：

  • 我没有让 agent 之间互相发消息，因为子 agent 没有状态，跨会话的消息也没有验证过。等测出来可靠了，再重新考虑。
  • 我没有让好几个子 agent 同时改同样的文件。那样会有合并冲突，而且代码跑不起来，没法判断谁对，所以要等仓库能在本地跑测试了再说。
  • 我也没有自己做沙箱、上下文压缩或子 agent 调度。平台一直在改这些，所以我宁可等平台。
  • 建立在 Preview 或实验性设置上的功能，我也没有做，因为它们可能变，也可能消失。等它们稳定了再说。

这份清单背后的习惯其实很简单。带着理由和条件的“不”，以后可以重新打开；两样都没有的“不”，就成了禁忌。

Where a cut can go wrong

Even the measured cut is a bet. The three-role team lost in the small comparison above, in a made-up repository. A very large, messy repository with a vague request may be different, though I have no data either way. If your tasks look like that, test before you copy my cut. The other three cuts, levels, the separate coordinator and the request folder, went on reasoning and use rather than data. They are judgments, so a reader could disagree, and I could be wrong. I have marked which cut is which so that you can judge for yourself.

It would be a misreading to take "multi-agent is bad" from any of this. I kept an independent reviewer, on reasoning that I did not test, and I use read-only helpers for broad reading (Use subagents sparingly). What I cut is splitting one piece of work by job title.

Once a thing is cut, write down why it went and when to reconsider it, in the same place as the reason you added it. Without that, someone adds it back a year later for the same reason.

Old setups need an exit. Taking out the old flow broke a request in progress, and anyone with old settings had to change them by hand, as the 1.1 notes say. Removing a part has a cost to the people already using it, so when you remove one, say what replaces it, how to move, which old settings stop working, and what happens to work in progress.

砍的時候會在哪裡出錯

就連量過的那一刀，也是一場賭注。三角色的團隊輸掉的，是上面那次小規模的比較，而且是在一個虛構的倉庫裡。換成一個很大、很亂的倉庫，再加上一個模糊的需求，結果可能不一樣，只是兩邊我都沒有數據。如果你的任務長那樣，先測，再照我的砍法。

另外三刀沒有數據。級別、獨立的協調者和請求資料夾，是靠推理和使用經驗拿掉的，只能算判斷，讀者可以不同意，我也可能錯。我把每一刀屬於哪一種寫出來，就是為了讓你能自己判斷。

要是從這裡讀出「多 agent 不好」，那就讀錯了。我留下了一個獨立的 reviewer，理由是一段我沒測過的推理；做大範圍的閱讀時，我也會用唯讀的幫手（慎用子 agent）。我砍掉的，是照職位把一件工作切開。

一樣東西砍掉以後，要把它為什麼拿掉、什麼時候重新考慮寫下來，和當初加它的理由放在同一個地方。不然一年後，有人會因為同樣的理由把它加回來。

舊的設定需要退場的路。拿掉舊流程的時候，讓一個進行中的請求壞掉了，有舊設定的人也得手動改，1.1 的說明寫了這點。拿掉一個部分，對已經在用的人是有成本的。所以拿掉之前要交代清楚：用什麼取代、怎麼搬過去、哪些舊設定不再有效，以及進行中的工作會怎樣。

砍的时候会在哪里出错

就连量过的那一刀，也是一种赌注。三角色团队输掉的，是上面那次小规模的比较，而且是在一个虚构的仓库里。换成一个非常大、非常乱的仓库，再加上一个含糊的需求，结果可能就不一样了，只是两边我都没有数据。如果你的任务是那样的，抄我的砍法之前先测一下。

另外三刀没有数据。级别、单独的协调者和请求文件夹，是凭推理和使用经验拿掉的，只能算判断，读者可以不同意，我也可能错。我把每一刀属于哪一种写清楚，就是为了让你自己判断。

要是从这里读出“多 agent 不好”，那就读错了。我留下了独立的 reviewer，依据是一段我没测过的推理；做大范围阅读时，我也会用只读的帮手（别跟风瞎用子 Agent）。我砍掉的，是把一份工作按岗位拆开。

一样东西砍掉以后，要把它为什么拿掉、什么时候重新考虑，写在当初记下加它的理由的同一个地方。不然一年以后，会有人出于同样的理由把它加回来。

旧的配置需要出路。拿掉旧流程时，弄坏了一个进行中的请求，用着旧设置的人也得手工去改，1.1 版的发布说明里写了这一点。拿掉一个部分，对已经在用它的人是有代价的。所以拿掉之前要交代清楚：拿什么替代、怎么迁移、哪些旧设置不再生效，以及进行中的工作会怎样。

When to revisit the cuts, and prune the list of what I did not build

If cuts are bets, they need a time to be checked again. The best time is after a model upgrade, because the reasons behind my cuts were facts about the models and the platform of that month. Models get better at long tasks, and the platform may one day let a finished subagent be resumed, which would remove the relearning cost behind the coordinator cut. After an upgrade, re-run the same fixed tasks and see (Fixed tasks, scored by a script).

The list of "not built, reconsider when" is itself something to prune (When the model is upgraded, delete uses the same habit for the rules you keep). When a condition has been met, build the thing or strike it out.

什麼時候重審這幾刀，什麼時候修剪不做的清單

既然砍是賭注，就得有個時候回頭再驗一次。最好的時機是模型升級之後，因為我砍的那些理由，都是那個月的模型和平台的事實。模型在長任務上會越來越好，平台有一天也可能讓已結束的子 agent 能繼續，這樣一來，協調者那一刀背後重學的成本就沒了。升級之後，重跑同樣的固定任務，看看結果（固定的任務，用腳本打分）。

「沒做，等條件到了再考慮」的清單，本身也是要修剪的東西（模型升級了，就要刪 對你留下的規則，用的是同一個習慣）。條件一到，不是做出來，就是劃掉。

什么时候重审这几刀，什么时候修剪不做的清单

既然砍是赌注，就得有个时候回头再验一次。最好的时机是模型升级之后，因为我砍的理由，都是那个月的模型和平台的事实。模型在长任务上会越来越好，平台有一天也可能让已结束的子 agent 接着干，那样一来，协调者那一刀背后重学的成本就没了。升级之后，重跑同样的固定任务，看看结果（改了配置，怎么知道是不是变好了？）。

“不做，等条件到了再考虑”的清单，本身也是要修剪的东西（换了新模型，旧规则该删了对你留下的规则，用的是同一个习惯）。条件一到，要么做出来，要么划掉。
