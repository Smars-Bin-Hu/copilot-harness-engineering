What is Harness Engineering?什麼是 Harness Engineering？什么是 Harness Engineering？

This chapter assumes only that you have typed a request into an AI chat box.

讀這一章，只需要你在 AI 對話框裡打過一段需求。

读这一章，只需要你在 AI 聊天框里提过需求。

The Knowledge經驗分享经验分享

In one sentence

Harness engineering is building the rules, checks and limits around a model so that an agent can be trusted with real work. Put the same model in a good harness and it can do far more than it can in a chat box, because most of the gap lies outside the model.

一句話

駕馭工程（harness engineering）是在模型周圍搭規則、檢查和限制，讓 agent 能放心交給真實的工作。同一個模型，放進好的 harness 裡，能做的事比在對話框裡多得多，因為差距大部分在模型外面。

一句话

驾驭工程（harness engineering）是在模型周围搭规则、检查和限制，让 agent 能放心交给真实的工作。同一个模型，放进好的 harness 里，能做的事比在聊天框里多得多，因为差距大部分在模型外面。

For leaders

  • The decision: where the team's effort goes: a better model, or the rules, checks and limits around the model.
  • The risk: if the problem sits outside the model, switching models or turning reasoning effort to the maximum leaves the results just as disappointing, and costs more.
  • The cost of doing it right: the next chapter starts from the smallest setup that is still useful; after that, the cost is mostly the time to build the setup.
  • Ask the team: "The last time an agent let us down, was it the model, or was something missing around it, such as a check, a rule, or a file it never got to see?"

給主管

  • 要做的決定：團隊的力氣花在哪裡：換更好的模型，還是把模型周圍的規則、檢查和限制做好。
  • 風險：如果問題出在模型外面，換了模型、把推理強度開到最高，結果照樣讓人失望，錢還多花了。
  • 做對的成本：下一章從最小、但有用的一組設定講起；之後主要是把設定做起來的時間。
  • 可以問團隊：「上次 agent 讓我們失望，是模型本身的問題，還是它周圍少了東西，例如少了一道檢查、一條規則，或是沒讓它看到相關的檔案？」

写给管理者

  • 要拍板的事：团队的力气往哪儿使：换更好的模型，还是把模型周围的规则、检查和限制做好。
  • 风险：如果问题出在模型外面，换了模型、把推理强度开到最高，结果照样让人失望，钱还多花了。
  • 做对的代价：下一章从最小、但有用的一套配置讲起；之后主要是搭配置的时间。
  • 可以问团队：“上次 agent 让我们失望，是模型本身的问题，还是它周围缺了东西，比如少了一道检查、一条规则，或者没让它看到相关的文件？”

Same model, and the gap is outside it

A user reports that the export button sometimes produces an empty file. You paste the report into a chat box, and the model gives you a confident explanation and a code change. But it has never seen your code and cannot run your tests, so whether the change is right is yours to find out. Put the same model in Copilot's agent mode and it searches the code, opens the relevant files and runs the tests. It reads the project's written rules before it touches anything, and when it is done, a check outside the model runs the tests again.

The model did not change, yet the results are far apart, because the difference is outside the model: what it can see, what it can do, which rules it must follow, and who checks the result. The whole set of programs and configuration around the model is called the harness.

LangChain measured how much changing only the harness can buy. They kept the model fixed at gpt-5.2-codex and went from 52.8% to 66.5% on Terminal Bench 2.0, a benchmark of 89 terminal tasks. The changes came from the traces of failed tasks. The agent wrote its code, read it over and stopped, so they reminded it to verify against the task spec before it exited. It made mistakes finding files and tools, so at the start they told it what the working directory held and which tools were available. It kept making small edits to the same broken approach, more than ten times in some traces, so after a set number of edits to one file they told it to rethink. (Improving deep agents with harness engineering)

The result on reasoning effort is the least intuitive. gpt-5.2-codex has four levels: low, medium, high and xhigh. Running at xhigh throughout scored only 53.9%, while running at high throughout scored 63.6%, because the agent thought for so long that many tasks timed out. In the end they used xhigh for planning and verification and high for writing code, though the different splits scored about the same in trial runs. How much reasoning effort to use is itself a harness setting.

This is one team's own result on one benchmark, but it points the same way as the export-button example: what widens the gap is work the model cannot do for itself, such as checking from outside, getting the environment laid out in advance, and breaking out of a loop.

模型一樣，差距在模型外面

使用者回報，匯出按鈕有時會匯出空檔案。你把描述貼進對話框，模型給了一段很有把握的解釋和一處修改，但它沒看過你的程式碼，也跑不了測試，改得對不對只能你自己去驗。把同一個模型放進 Copilot 的 agent 模式，它會自己搜尋程式碼、打開相關檔案、跑測試，動手前先讀專案裡寫好的規則，改完以後還有一道模型之外的檢查再跑一次測試。

模型沒換，結果差這麼多，原因在模型外面：它看得到什麼、能做什麼、要守什麼規則、誰來驗收。這一整套包在模型外面的程式和設定，叫 harness。

LangChain 量過只改 harness 能差多少。他們把模型固定為 gpt-5.2-codex，在 Terminal Bench 2.0（89 個終端機任務）上從 52.8% 提高到 66.5%。改動來自失敗任務的執行紀錄：agent 寫完程式碼自己讀一遍就停，於是在它結束前提醒它對照任務要求驗證；它找檔案、找工具出錯，於是一開始就把工作目錄和可用的工具告訴它；它在一個錯誤的思路上反覆小改，有時超過 10 次，於是同一個檔案改到一定次數，就提醒它換個思路。（Improving deep agents with harness engineering）

推理強度的結果最違反直覺。gpt-5.2-codex 的推理強度（reasoning effort）分 low、medium、high、xhigh 四檔。全程開到 xhigh 只有 53.9%，全程用 high 反而是 63.6%，因為想得太久，很多任務逾時了。最後他們在規劃和驗證時用 xhigh、寫程式碼時用 high，幾種分配方式之間差別不大。推理強度開多高，本身就是 harness 的一個設定。

這是一個團隊在一個基準上自己量的結果，但它和匯出按鈕的例子指向同一件事：拉開差距的，都是模型自己做不到的事，例如從外部驗證、事先給好的環境資訊、打斷鬼打牆的迴圈。

模型一样，差距在模型外面

用户反馈导出按钮有时导出空文件。你把描述贴进聊天框，模型给了一段很肯定的解释和一处修改，但它没看过你的代码，也跑不了测试，改得对不对只能你自己去验。把同一个模型放进 Copilot 的 agent 模式，它会自己搜索代码、打开相关文件、跑测试，动手前先读项目里写好的规则，改完以后还有一道模型之外的检查再跑一遍测试。

模型没换，结果差这么多，原因在模型外面：它能看到什么、能做什么、要守什么规则、谁来验收。这一整套围着模型的程序和配置，叫 harness。

LangChain 测过只改 harness 能差多少。他们把模型固定为 gpt-5.2-codex，在 Terminal Bench 2.0（89 个终端任务）上从 52.8% 提到 66.5%。改动来自失败任务的执行记录：agent 写完代码自己读一遍就停，于是在它退出前提醒它对照任务要求验证；它找文件、找工具出错，于是启动时先把工作目录和可用工具告诉它；它在一个错误思路上反复小改，有时超过 10 次，于是同一个文件改到一定次数，就提醒它换思路。（Improving deep agents with harness engineering）

推理强度的结果最反直觉。gpt-5.2-codex 的推理强度（reasoning effort）分 low、medium、high、xhigh 四档。全程开到 xhigh 只有 53.9%，全程用 high 反而是 63.6%，因为想得太久，很多任务超时了。最后他们在规划和验证时用 xhigh、写代码时用 high，几种分配方式之间差别不大。推理强度开多高，本身就是 harness 的一个设置。

这是一个团队在一个基准上自己测的结果，但它和导出按钮的例子指向同一件事：拉开差距的，都是模型自己做不到的事，比如外部验证、提前给好的环境信息、打断死循环。

Seven layers around the model

From model to agent

Start by taking an agent apart. The model (the LLM) is the agent's brain: Sonnet, Opus, GPT-5. It reads text and writes text, and on its own it can only answer questions. To act, it needs tools, its hands: reading a file, searching code, editing a file, running a terminal command are each one tool. The model uses a tool by writing a request that names the tool and its arguments ("read src/export.ts"). That request is a tool call (details in Tool calling, and designing tools for an agent).

The model can only write the request; it cannot carry it out. So a program has to connect the two. It hands the task to the model, runs the tool the model asks for, passes the result back, and asks for the next step, over and over until the model says it is done. The model, the tools and this loop together make an agent (how the loop runs is in The agent loop, and where you can step in). The program that runs the loop is the first meaning of harness.

Two meanings of "harness"

The word has two uses, and mixing them causes confusion. The first is the general harness, the program that runs the loop: Claude Code, Codex and Copilot's agent mode are all general harnesses that you download or buy and use as they are. The second is the team harness: the layer you build on top of a general harness for your own team, made of rules, skills, checks, limits and reports, plugged into the extension points the general harness leaves open.

This book is about the second kind, with every example built on VS Code Copilot. When I say harness engineering, I mean the work of building that layer.

Seven layers

A team harness has many small pieces. I sort everything around the model into seven layers, each with a question that stays the same however the tools and models change.

Layer Analogy Examples Question
Model Brain Sonnet, Opus, GPT-5; reasoning effort How deeply can it think, and what does it cost?
Tools Hands Reading and writing files, terminal commands, MCP servers What can it reach?
Runtime Nerves that connect brain and hands Copilot's agent mode, Claude Code; hooks, subagents Who runs the loop, and where does it leave me a way in?
Context Onboarding Instruction files (AGENTS.md), skills, memory What should it know, and what should it not read?
Control Computer permissions Permissions, a hook that blocks dangerous commands Why should I trust it?
Flow Project process, team rules Task lists, approvals, when to stop How is the work split, who decides, when does it stop, when does it call a person?
Evidence Work log, expense report Logs, task reports, evals What did it do, was it right, what did it cost?

The lower three layers are the agent itself: a brain, hands, and the nerves that connect them. They are mostly bought, built by model and platform vendors, and they change fast. The upper four layers are how a company manages a new hire: onboarding, computer permissions, project process, a record of the work. You can hire the person, but how you manage them is up to your company, so these four layers are yours to build, and they depend on your code, your colleagues and the risks you carry. They also last longer: a platform upgrade rarely wipes out your rules, though it may make the workarounds you built for a weaker model unnecessary.

Where hooks and skills belong

The seven layers cover most of harness engineering. The two pieces most often argued over are hooks and skills. Both are mechanisms the platform provides, yet what you build with them belongs to the upper layers. The test is what a piece is used for, not who provides it.

  • A hook is a gap the platform (Claude Code, Copilot and others) leaves at fixed events: when an event fires, it runs a command you choose. Common events are PreToolUse (before a tool call), PostToolUse (after a tool call), UserPromptSubmit (when the user sends a prompt) and Stop (when the agent is about to finish). When the event fires, the platform hands the details to your command, such as the tool's name and arguments, and the command can let the call through or block it. The hook mechanism belongs to the runtime; what you attach to it belongs where its purpose puts it. A Python script on PreToolUse that blocks any terminal command containing rm -rf is control. A script on PostToolUse that writes every call to a log is evidence. (Details in Hooks, the point every call passes through.)
  • A skill is a folder. Its main file, SKILL.md, holds a name, a description and a manual, and scripts and templates can sit beside it. The agent normally sees only each skill's name and description, and reads the full manual only when a task calls for it. The mechanism that loads skills on demand belongs to the runtime; the manual is written for the agent to read, so it is context; the scripts in the folder are run as commands, so they are tools. (Details in Instructions and skills, load only what you need.)

Three ways to fail

Control, flow and evidence are separate layers because they fail in different ways.

When control fails, the agent does damage: it deletes the wrong thing or edits a file it should not touch.

When flow fails, the work comes back: the agent takes on too much at once or says it is done too early. Anthropic saw both when Opus 4.5 built a clone of claude.ai across many sessions. "The agent tended to try to do too much at once—essentially to attempt to one-shot the app," and "a later agent instance would look around, see that progress had been made, and declare the job done." Their fixes were all outside the model. The first session wrote a list of more than 200 features, each marked as failing. Every later session worked on one feature at a time, could change only whether that feature passed, and was not allowed to remove or edit tests; when it finished, it committed to git and logged what it had done in a progress file. For testing, the agent was told to use browser automation and act as a real user would, which caught bugs that were not obvious from the code alone. (Effective harnesses for long-running agents)

When evidence fails, it looks different again: the work may be fine, but nobody can say what happened. You cannot show the result is right, you cannot find the cause of an error, and you cannot tell whether a change helped. When the bill goes up, you cannot tell which task spent it.

When something goes wrong, asking "which kind of failure is this?" usually leads to a fix faster than asking "which model should we switch to?"

模型周圍的七層

從模型到 agent

先把 agent 拆開。模型（LLM）是 agent 的大腦，例如 Sonnet、Opus、GPT-5。它讀文字、寫文字，單靠它只能回答問題。要動手，它需要工具，也就是雙手：讀檔案、搜尋程式碼、改檔案、跑終端機指令，每一樣是一個工具。模型使用工具的方式，是寫出一段請求，說明用哪個工具、參數是什麼（例如「讀 src/export.ts」），這叫一次工具呼叫（tool calling，細節見Tool calling，和給 agent 設計工具）。

模型只會寫請求，自己執行不了。所以還需要一個程式把兩者接起來：它把任務交給模型，執行模型要的工具，把結果交回模型，再問下一步，一直重複到模型說做完了。模型、工具加上這個迴圈，就是 agent（迴圈怎麼轉，見agent 循環，和你能插手的地方）。跑這個迴圈的程式，是 harness 的第一種意思。

「harness」的兩種意思

這個詞有兩種用法，混著用容易搞混。第一種是通用 harness，就是跑迴圈的那個程式：Claude Code、Codex、Copilot 的 agent 模式都是，下載或買來就能用。第二種是團隊的 harness：你在通用 harness 上為自己團隊搭的那一層，包括規則、skill、檢查、限制和報告，接在通用 harness 留下的擴充點上。

這本書講第二種，例子都搭在 VS Code Copilot 上。我說 Harness Engineering，指的就是搭這一層的工作。

七層

團隊的 harness 零碎的東西很多。我把模型周圍的一切分成七層，每層帶一個問題；工具和模型怎麼換，這些問題都不變。

層 比喻 例子 問題
模型 大腦 Sonnet、Opus、GPT-5；推理強度 它能想多深，要花多少錢？
工具 雙手 讀寫檔案、跑終端機指令、MCP server 它搆得到什麼？
執行環境 神經，把大腦和雙手接起來 Copilot 的 agent 模式、Claude Code；hook、子 agent 誰來跑這個迴圈，在哪裡給我留了插手的地方？
上下文 新人訓練 指令檔（AGENTS.md）、skill、記憶 它該知道什麼，不該讀什麼？
控制 電腦權限 權限、攔下危險指令的 hook 我憑什麼信它？
流程 專案流程、團隊規定 任務清單、批准、什麼時候停 工作怎麼拆，誰來判斷，什麼時候停，什麼時候找人？
證據 工作紀錄、操作帳單 日誌、任務報告、評測 它做了什麼，做對了沒有，花了多少？

下面三層是 agent 自己：大腦、雙手和連起它們的神經。這三層大部分是買來的：模型廠商和平台廠商在做，變得也快。上面四層是公司怎麼管一個新員工：新人訓練、電腦權限、專案流程、工作紀錄。人可以請來，怎麼管得由公司自己決定，所以這四層要你自己搭，它們取決於你的程式碼、你的同事和你要承擔的風險。上面四層也更持久：平台升級很少會抹掉你的規則，卻可能讓你當初為了繞過弱模型想出來的辦法變得多餘。

hook 和 skill 放在哪一層

七層涵蓋了 Harness Engineering 的大部分概念，放哪一層最容易有爭議的是 hook 和 skill。兩樣都是平台提供的機制，你用它們做出來的東西卻屬於上面的層。判斷的辦法是看它用來做什麼，不看它是誰提供的。

  • hook 是平台（Claude Code、Copilot 等）在固定事件上留的口子：某個事件發生時，執行你指定的一個指令。常用的事件有 PreToolUse（工具呼叫之前）、PostToolUse（工具呼叫之後）、UserPromptSubmit（使用者送出 prompt 時）和 Stop（agent 準備結束時）。事件發生時，平台把內容交給你的指令，例如要呼叫的工具名和參數；指令可以放行，也可以攔下。hook 這個機制屬於執行環境，掛在上面的東西各有歸屬：在 PreToolUse 上掛一個 Python 腳本，發現終端機指令裡有 rm -rf 就攔下，這是控制；在 PostToolUse 上把每次呼叫寫進日誌，這是證據。（細節見Hooks：每次呼叫都會經過的執行點。）
  • skill 是一個資料夾：主檔案 SKILL.md 寫著名字、描述和一份操作手冊，旁邊可以放腳本和範本。agent 平時只看得到每個 skill 的名字和描述，任務用得上時才讀整份手冊。按需載入 skill 的機制屬於執行環境；手冊是寫給 agent 看的，屬於上下文；資料夾裡的腳本，agent 會當指令去跑，屬於工具。（細節見指令與 skill：只載入需要的。）

三種失敗方式

控制、流程、證據分成三層，是因為它們出問題的樣子不一樣。

控制出問題，agent 會造成損害：刪錯東西，或者改了不該碰的檔案。

流程出問題，工作會被退回來：agent 一次做太多，或者太早說做完。Anthropic 用 Opus 4.5 跨好幾個會話做一個 claude.ai 的複製版時，兩種都遇到了：agent「傾向一次做太多，基本上想一口氣把整個應用程式做完」；後來的會話則會「四處看看，發現已經有進展，就宣布工作完成」。他們的修法都在模型外面。第一個會話先寫出 200 多項功能的清單，每項都標成未通過；之後的每個會話一次只做一項，只能改這一項有沒有通過，不准刪改測試，做完提交到 git，並在進度檔裡記下做了什麼。測試時要求 agent 用瀏覽器自動化工具，像真實使用者一樣操作，這樣能找出光看程式碼看不出來的 bug。（Effective harnesses for long-running agents）

證據出問題又是另一種樣子：工作可能做得很好，但沒人說得清發生了什麼。你證明不了結果是對的，出了錯找不到原因，也說不準某個改動有沒有用；帳單變高了，你分不清是哪個任務花的。

出了問題，先問「這是哪一類失敗」，往往比問「該換哪個模型」更快找到修法。

模型周围的七层

从模型到 agent

先把 agent 拆开。模型（LLM）是 agent 的大脑，比如 Sonnet、Opus、GPT-5。它读文本、写文本，单靠它只能回答问题。要动手，它需要工具，也就是双手：读文件、搜索代码、改文件、跑终端命令，每一样是一个工具。模型用工具的方式，是写出一段请求，说明用哪个工具、参数是什么（比如“读 src/export.ts”），这叫一次工具调用（Tool Calling，细节见Agent 用不好工具，先看工具的描述和报错）。

模型只会写请求，自己执行不了。所以还需要一个程序把两者接起来：它把任务交给模型，执行模型请求的工具，把结果交回模型，再问下一步，一直重复到模型说做完了。模型、工具加上这个循环，就是 agent（循环怎么转，见Agent 到底是怎么干活的？）。跑这个循环的程序，是 harness 的第一种意思。

“harness”的两种意思

这个词有两种用法，混着用容易糊涂。第一种是通用 harness，就是跑循环的那个程序：Claude Code、Codex、Copilot 的 agent 模式都是，下载或者买来就能用。第二种是团队的 harness：你在通用 harness 上为自己团队搭的那一层，包括规则、skill、检查、限制和报告，接在通用 harness 留出来的扩展点上。

这本书讲第二种，例子都搭在 VS Code Copilot 上。我说 Harness Engineering，指的就是搭这一层的工作。

七层

团队的 harness 零碎东西很多。我把模型周围的一切分成七层，每层带一个问题；工具和模型怎么换，这些问题都不变。

层 比方 例子 问题
模型 大脑 Sonnet、Opus、GPT-5；推理强度 它能想多深，要花多少钱？
工具 双手 读写文件、跑终端命令、MCP server 它够得着什么？
运行环境 神经，把大脑和双手接起来 Copilot 的 agent 模式、Claude Code；hook、子 agent 谁来跑这个循环，在哪里给我留了插手的口子？
上下文 岗前培训 指令文件（AGENTS.md）、skill、记忆 它该知道什么，不该读什么？
控制 电脑权限 权限、拦截危险命令的 hook 我凭什么信它？
流程 项目流程、团队规定 任务清单、审批、什么时候停 工作怎么拆，谁来判断，什么时候停，什么时候叫人？
证据 工作记录、操作账单 日志、任务报告、评测 它做了什么，做对了没有，花了多少？

下面三层是 agent 自己：大脑、双手和连起它们的神经。这三层大部分是买来的：模型厂商和平台厂商在造，变得也快。上面四层是公司怎么管一个新员工：岗前培训、电脑权限、项目流程、工作记录。人可以招来，怎么管得公司自己定，所以这四层要你自己搭，它们取决于你的代码、你的同事和你要承担的风险。上面四层也更持久：平台升级很少会抹掉你的规则，却可能让你当初为了绕开弱模型想出来的办法变得多余。

hook 和 skill 放在哪一层

七层涵盖了 Harness Engineering 的大部分概念，放哪一层最容易有争议的是 hook 和 skill。两样都是平台提供的机制，你用它们做出来的东西却属于上面的层。判断的办法是看它用来做什么，不看它是谁提供的。

  • hook 是平台（Claude Code、Copilot 等）在固定事件上留的口子：某个事件发生时，运行你指定的一个命令。常用的事件有 PreToolUse（工具调用之前）、PostToolUse（工具调用之后）、UserPromptSubmit（用户发出 prompt 时）和 Stop（agent 准备结束时）。事件发生时，平台把内容交给你的命令，比如要调用的工具名和参数；命令可以放行，也可以拦下。hook 这个机制属于运行环境，挂在上面的东西各有归属：在 PreToolUse 上挂一个 Python 脚本，发现终端命令里有 rm -rf 就拦下，这是控制；在 PostToolUse 上把每次调用写进日志，这是证据。（细节见硬性规则放在哪？用 hook。）
  • skill 是一个文件夹：主文件 SKILL.md 写着名字、描述和一份操作手册，旁边可以放脚本和模板。agent 平时只看得到每个 skill 的名字和描述，任务用得上时才读整份手册。按需加载 skill 的机制属于运行环境；手册是写给 agent 看的，属于上下文；文件夹里的脚本，agent 会当命令去跑，属于工具。（细节见规则写太多，Agent 反而记不住。）

三种失败方式

控制、流程、证据分成三层，是因为它们出问题的样子不一样。

控制出问题，agent 会造成损害：删错东西，或者改了不该碰的文件。

流程出问题，活会被打回来：agent 一次做太多，或者太早说做完。Anthropic 用 Opus 4.5 跨多个会话搭一个 claude.ai 的克隆时，两种都见到了：agent “倾向于一次做太多，基本上想一口气把整个应用做完”；后来的会话则会“四处看看，发现已经有进展，就宣布工作完成”。他们的修法都在模型外面。第一个会话先写出 200 多项功能的清单，每项都标成未通过；之后的每个会话一次只做一项，只许改这一项通没通过，不许删改测试，做完提交到 git，并在进度文件里记下做了什么。测试时要求 agent 用浏览器自动化工具，像真实用户一样操作，这样能找出光看代码看不出来的 bug。（Effective harnesses for long-running agents）

证据出问题又是另一种样子：活可能干得很好，但没人说得清发生了什么。你证明不了结果是对的，出了错找不到原因，也说不准某个改动有没有用；账单涨了，你分不清是哪个任务花的。

出了问题，先问“这是哪一类失败”，往往比问“该换哪个模型”更快找到修法。

You don't need all seven

Seven layers side by side can make it look as if a good harness needs something in each. It does not. Every layer you add is one more thing to maintain and one more place to fail, which is why the next chapter (A minimal harness in 30 minutes) starts from the smallest useful set.

A stronger model does help. But the model is bought, and for the same model, most of the difference you can influence comes from the layers around it.

七層不必都搭

七層擺在一起，容易讓人以為好的 harness 每一層都得有東西。不必。每多搭一層，就多一樣要維護的東西，也多一處可能出錯的地方。所以下一章（30 分鐘搭一個最小 harness）從最小的有用組合講起。

更強的模型當然有幫助。但模型是你買來的，同一個模型，你能左右的那部分差距，大多來自它周圍的幾層。

What LangChain and Anthropic found Industry practice

The two sources point the same way but show different things. LangChain fixed the model, changed only the harness and saw the score rise, which shows how wide a gap the harness can open. Anthropic describes where failures happen on long tasks (doing too much at once, declaring the job done too early) and the fixes it made with a feature list, a progress file and git. It does not compare against a stronger model, so it cannot say how much switching models would help.

LangChain 和 Anthropic 看到了什麼 業界做法

兩個來源指向同一個方向，說明的東西不一樣。LangChain 固定模型、只改 harness，看到了分數的提升，說明 harness 能拉開多大的差距。Anthropic 描述的是長任務裡失敗出在哪裡（一次做太多、太早宣布完成），以及靠功能清單、進度檔和 git 做的修正；它沒有拿更強的模型做比較，所以說明不了換模型能幫多少。

How to read this book

The book spends little time on the lower three layers and most of its pages on the upper four: Parts 1 and 2 cover what you need to know about the lower three, and Parts 3 to 6 each take one of the upper layers.

Every chapter has two parts. The Knowledge explains the idea and stands on its own; In my practice points to the real files in my own setup, so you can look inside.

If you have little time, read the chapters marked as core; they carry the main line of the book, and the others are there for when a problem sends you to them. If you decide where the team's time and budget go, start with 0.2, 1.1 and 7.4.

Explore it in the harness

Copilot Harness is a team harness in the second sense above. It has a part for each of the four upper layers, and it can walk you through them from the inside, with the real files.

Once you have set it up as described above, type:

/harness-rookie-wondering I have read the chapter "What is Harness Engineering?". Teach me how a coding agent works in this harness: the loop, the tools, and where the harness steps in. Open the real files with me and draw how the pieces fit together.

It teaches one small piece at a time, stops to check that you are following, and opens the files with you.
