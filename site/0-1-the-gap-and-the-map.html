The gap is outside the model差距在模型外面差距在模型外面

This chapter assumes only that you have typed a request into an AI chat box.

讀這一章，只需要你在 AI 對話框裡打過一段需求。

读这一章，只需要你在 AI 聊天框里提过需求。

The Knowledge經驗分享经验分享

In one sentence

The same model does far more inside a good harness than in a chat box, because most of the gap lies outside the model.

一句話

同一個模型，放進好的 harness 裡，能做的事比在對話框裡多得多，因為大部分差距在模型外面。

一句话

同一个模型，放进好的 harness 里，能干的事比在聊天框里多得多，因为差距大部分在模型之外。

For leaders

  • The decision: where the team's effort should go: into a better model, or into the setup around it (the rules, checks and limits that surround the model).
  • The risk: if most of the gap sits outside the model, switching models will not fix a disappointing result. One team changed only the setup of a coding agent and saw its score on a public benchmark go from 52.8% to 66.5%, though that is one team on one benchmark, measuring its own work.
  • The cost of doing it right: the next chapter starts from the smallest set that is still useful; beyond that, the cost is mostly setup time.
  • Ask the team: "The last time the agent let us down, was it the model, or something missing around it: a check, a rule, a view of the files?"

給主管

  • 要做的決定：團隊的力氣該花在哪裡：換一個更好的模型，還是把模型周圍的設定做好（也就是包住模型的規則、檢查和限制）。
  • 風險：如果大部分差距在模型外面，換了模型，結果照樣讓人失望。有一個團隊只改了寫程式 agent 的設定，它在一個公開基準上的分數就從 52.8% 升到 66.5%；不過這只是一個團隊、一個基準，而且是團隊自己量的。
  • 做對的成本：下一章從最小、但仍然有用的一組設定開始；再往後，主要是花時間把設定做起來。
  • 可以問團隊：「上次 agent 讓我們失望，是模型本身的問題，還是它周圍少了東西，例如少了一道檢查、一條規則，或是沒讓它看到檔案？」

写给管理者

  • 要拍板的事：团队的力气该往哪儿使：换一个更好的模型，还是把模型周围的配置做好（也就是围着模型的规则、检查和限制）。
  • 风险：如果差距大部分在模型之外，换了模型，结果照样让人失望。有个团队只改了编码 agent 的配置，它在一个公开基准上的分数就从 52.8% 涨到了 66.5%；不过这只是一个团队、一个基准，而且是团队自己测的。
  • 做对的代价：下一章从最小、但仍然有用的一套配置讲起；再往后，主要是花时间把配置搭起来。
  • 可以问团队：“上次 agent 让我们失望，是模型本身的问题，还是它周围缺了东西，比如少了一道检查、一条规则，或者没让它看到文件？”

If the model is the same, where does the gap come from?

Picture an ordinary afternoon. Users report that the export button sometimes produces an empty file. When you paste their description into a chat box, a strong model soon gives you a confident explanation and a code fix.

Now put the same model in a different setup, facing the same bug. This time it can open your files, search them and run your tests. Before it touches anything, it reads the rules written down for the project and shows you a plan. And when it finally says "fixed", you do not have to take its word for it, because a check outside the model has already run the tests.

Neither the model nor the bug has changed, yet the two afternoons could hardly be more different. I made the scene up as a thought experiment, to show the shape of the gap rather than to measure it. What, exactly, did the second setup give the model that the chat box did not?

What the chat box leaves out

In the chat box, the model had only what you pasted, so it could not see your files and had to guess at them. It could not run its fix either, which meant nobody knew whether the fix was right. And since it did not know the project's rules, nothing stopped it from suggesting something you forbid. None of these is a skill the model lacks. Each is something missing around it.

Is there evidence beyond a made-up afternoon?

There is some. When a team at LangChain kept the model of a coding agent fixed and changed only its harness, the agent's score on a public coding benchmark (Terminal Bench 2.0) went from 52.8% to 66.5%. Their changes were things like a step that makes the agent verify its work before it exits, a map of the working folder given at the start, and a nudge to reconsider after repeated edits to the same file. (Improving deep agents with harness engineering)

Each of these changes adds something the model does not supply for itself: a check from outside, a view of the folder, a break in a loop. This is one team's result on one benchmark, from a harness the team changed and measured itself, so it is a sign rather than a law. Still, it points the same way as the thought experiment: much of what separates a good result from a poor one is not in the model.

模型一樣，差距從哪裡來？

先想像一個再平常不過的下午。使用者回報，匯出按鈕有時會產生空檔案。你把問題描述貼進對話框，一個很強的模型馬上給了你一段信心滿滿的解釋，還附上一段修正好的程式碼。

現在把同一個模型放進另一種設定裡，面對的還是這個 bug。這一次，它能自己打開你的檔案、搜尋程式碼，也能執行你的測試。動手之前，它會先讀專案裡寫好的規則，再把打算怎麼改拿給你看。等它最後說「修好了」，你也不必只聽它一句話，因為模型以外的一道檢查已經把測試跑過了。

模型沒換，bug 也沒換，這兩個下午卻幾乎是兩回事。這個場景是我編的思想實驗，為的是讓你看清差距的樣子，而不是去量它。那麼，第二種設定到底給了模型哪些對話框給不了的東西？

對話框裡少了什麼

在對話框裡，模型只有你貼進去的東西，看不到你的檔案，只能用猜的。給出的修正它自己沒辦法執行，改得對不對，沒有人知道。專案的規則它也不知道，就算它建議了你明明禁止的做法，也沒有任何東西擋得住。這些都不是模型少了哪項能力，而是它周圍少了東西。

除了編出來的下午，還有別的證據嗎？

有一些。LangChain 的一個團隊讓寫程式 agent 的模型保持不變，只改了它的 harness，結果這個 agent 在一個公開的程式基準（Terminal Bench 2.0）上的分數從 52.8% 升到 66.5%。他們改的是這類東西：讓 agent 在結束前先驗證自己的工作，一開始就給它一張工作資料夾的地圖，還有在同一個檔案被反覆修改之後，提醒它重新想一想。（Improving deep agents with harness engineering）

這幾處改動有個共同點：補上的都是模型自己不會提供的東西，有的是外面來的檢查，有的是讓它看清楚資料夾，有的是幫它跳出迴圈。當然，這只是一個團隊在一個基準上的結果，harness 也是團隊自己改、自己量的，所以只能當作一個跡象，不能當作定律。但它和那個思想實驗指向同一個方向：好結果和差結果之間，很大一部分的差別不在模型裡。

模型一样，差距从哪来？

先设想一个再普通不过的下午。用户反馈说，导出按钮有时会导出一个空文件。你把问题描述贴进聊天框，一个很强的模型马上给了你一段言之凿凿的解释，还附上了一处代码修改。

现在把同一个模型放进另一种配置里，面对的还是这个 bug。这一次，它能自己打开你的文件、搜索代码，也能跑你的测试。动手之前，它会先读项目里写好的规则，再把打算怎么改拿给你过目。等它最后说“修好了”，你也不必只听它一句话，因为模型之外的一道检查已经把测试跑过了。

模型没换，bug 也没换，这两个下午却几乎是两回事。这个场景是我编的思想实验，为的是让你看清差距的样子，而不是去测量它。那么，第二种配置到底给了模型哪些聊天框给不了的东西？

聊天框里缺了什么

在聊天框里，模型只有你贴进去的东西，看不到你的文件，只能猜。给出的修改它自己跑不了，改得对不对，没人知道。项目的规则它也不知道，就算它建议了你明令禁止的做法，也没有什么能拦住它。这些都不是模型缺了哪项本事，而是它周围缺了东西。

除了编出来的下午，还有别的证据吗？

有一些。LangChain 的一个团队让编码 agent 的模型保持不变，只改了它的 harness，结果这个 agent 在一个公开的编码基准（Terminal Bench 2.0）上的分数从 52.8% 涨到了 66.5%。他们改的是这样一些东西：让 agent 在退出前先验证自己的工作，一开始就给它一张工作文件夹的地图，还有在同一个文件被反复修改之后，提醒它重新想一想。（Improving deep agents with harness engineering）

这几处改动有个共同点：补上的都是模型自己提供不了的东西，有的是来自外部的检查，有的是让它看清文件夹，有的是把一个循环打断。当然，这只是一个团队在一个基准上的结果，harness 也是团队自己改、自己测的，所以只能算一个迹象，算不上定律。但它和那个思想实验指向同一个方向：好结果和差结果之间的差别，很大一部分不在模型里。

A map of what surrounds the model

From a model to an agent

If the difference lies around the model, it helps to name what is there, piece by piece. Start with the model itself, the program that reads text and writes text. It is the "brain", but on its own it can only answer. To act, it needs tools, each of them one thing it can ask for, such as reading a file, searching, changing a file or running a command. These are its "hands". How the model asks for one is the subject of Tool calling.

A brain and a pair of hands still do not make a worker, though. Something has to ask the model what to do, run the tool it asks for, show it the result, and repeat until the model says it is done. Connected in that loop, the two become an agent (Chapter 2.1 walks through the loop). The loop does not write itself. Somebody has to program it, and that program is the harness, in the first of its two meanings.

The two meanings of "harness"

People use the word in two ways, and mixing them up causes a good deal of confusion. The first is the general harness, the program that runs the loop. Claude Code, Codex and Copilot's agent mode are all general harnesses, the kind you buy or download. The second is a team's harness: the layer you build on top of a general harness for your own team, made of rules, skills, checks, limits and reports. It plugs into the extension points that the general harness leaves open.

This book is about the second kind, built on VS Code Copilot. When I say "harness engineering", I mean the work of building that layer.

Seven layers

A team's harness has many pieces, so to keep them apart I sort everything around a model into seven layers. The frame is my own (more on where it can mislead you later). What makes it useful is that each layer comes with a question that stays the same when the tools and models change.

Read it from the bottom up. Each layer has an everyday picture and a question.

Layer Picture The question
Model the brain How deeply can it think, and what does that cost?
Tools the hands What can it reach?
Runtime joining brain and hands Who runs the loop, and where does the loop leave a gap for me?
Context company training What should it know, and what should it not read?
Control fences Why should I trust it?
Flow how work gets done How is the job split, who judges, when does it stop, when is a person called?
Evidence being able to explain What did it do, was it right, what did it cost?

The lower three layers are mostly bought. Model makers and platform makers build them, and they change fast. The upper four are yours to build, because they depend on your code, your colleagues and your risks. They also last longer: a platform update rarely erases your rules, but it may well make obsolete a clever trick you built to get around a weak model.

That is why this book spends little time on the lower layers and most of its pages on the upper ones. Part 1 and Part 2 cover what you need to know about the bought layers, while Parts 3 to 6 take one upper layer each.

The edges are not clean

The layers are a way of sorting, not a law of nature, so it is no surprise that some pieces sit right on a border. Take the hook, a small program the platform runs at fixed moments, such as just before a tool runs. Those moments come round in every turn of the loop, that is, in every round of asking the model, running its tools and handing back the results. The platform provides the slot, which belongs to the runtime, but what you put in the slot is control (more on hooks in Chapter 2.2).

A skill is another border case. It is a written manual the agent reads when it needs it, which makes it context. Only the scripts attached to it count as hands.

Three ways it fails

Why give control, flow and evidence a layer each? Because each of them fails in its own way.

When control fails, the agent causes damage: it deletes the wrong thing, or changes a file it should not touch. A failure of flow looks different. The work comes back to you, because the agent said "done" too early or tried to do everything in one go. Anthropic saw both patterns in long-running agents, where "the agent tended to try to do too much at once", and a later session "would look around, see that progress had been made, and declare the job done". (Effective harnesses for long-running agents) Evidence, finally, can fail even when the work is fine. Then nobody can say what happened: you cannot show that the work is right, cannot find the cause when it breaks, and cannot tell whether a change helped. If the bill goes up, say, you cannot tell which task caused it.

This is where the map earns its keep. When something goes wrong, asking "which of the three is this?" is often faster than asking "which model should I switch to?". Try it on the next failure you see.

替模型周圍的東西畫一張地圖

從模型到 agent

既然差別在模型周圍，不妨把那裡有什麼一樣一樣說清楚。先從模型本身說起：它是讀文字、寫文字的程式，就像「腦」，可是單靠它自己，只能回答問題。要動手做事，它需要工具，每個工具是它能要求做的一件事，例如讀檔案、搜尋、改檔案、執行指令。這些就是它的「手」（模型怎麼要求使用工具，見Tool calling，和給 agent 設計工具）。

可是有了腦和手，還不等於有了一個做事的人。總得有個東西去問模型下一步要做什麼，替它執行它要的工具，把結果拿給它看，然後一次次重複，直到模型說做完了。用這樣一個迴圈把兩者接起來，它們就成了 agent（這個迴圈怎麼運作，見agent 循環，和你能插手的地方）。迴圈不會自己寫出來，總得有人把它寫成程式，這個程式就是 harness 的第一種意思。

「harness」的兩種意思

這個詞有兩種用法，混在一起很容易讓人搞混。第一種是通用 harness，也就是執行迴圈的那個程式。Claude Code、Codex 和 Copilot 的 agent 模式都是，你買來或下載下來就能用。第二種是團隊的 harness：你在通用 harness 上面，為自己團隊搭的那一層，由規則、skill、檢查、限制和報告組成。它接在通用 harness 留出來的擴充點上。

這本書講的是第二種，搭在 VS Code Copilot 上。我說「harness engineering」，指的就是搭這一層的工作。

七層

團隊的 harness 有很多零散的部分，為了把它們分清楚，我把模型周圍的一切分成七層。這個框架是我自己的（它會在哪裡誤導你，後面再談）。它好用的地方在於，每一層都帶著一個問題，不管工具和模型怎麼變，這個問題都不會變。

從下往上讀。每一層都有一個日常的比方和一個問題。

層 比方 問題
模型 腦 它能想多深，要花多少錢？
工具 手 它能碰到什麼？
執行環境 把腦和手接起來 誰來跑迴圈？迴圈在哪裡留了一個讓我插手的位置？
上下文 公司的新人訓練 它該知道什麼？不該讀什麼？
控制 圍欄 我為什麼可以信它？
流程 工作怎麼完成 工作怎麼拆？誰來判斷？什麼時候停？什麼時候叫人？
證據 說得清楚 它做了什麼？對不對？花了多少？

下面三層大多是買來的。模型廠商和平台廠商在做，變化也快。上面四層要你自己搭，因為它們取決於你的程式碼、你的同事和你要承擔的風險。它們也比較持久：平台更新很少會抹掉你的規則，卻很可能讓你當初為了繞過弱模型而想出的小技巧變得多餘。

也因為這樣，這本書在下面幾層花的篇幅很少，大部分都留給上面幾層。第 1 部和第 2 部講你需要知道的、買來的那幾層，第 3 到第 6 部各講上面的一層。

邊界沒那麼分明

分層只是一種分類的方法，不是自然定律，所以有些東西剛好落在邊界上，也就不奇怪了。例如 hook，它是平台在固定時刻執行的一小段程式，像是在工具執行之前。這樣的時刻在迴圈的每一輪裡都會出現；所謂一輪，就是問一次模型、執行它要的工具、再把結果交回去。插槽是平台給的，屬於執行環境，可是你往插槽裡放什麼，屬於控制。（hook 的細節見Hooks：每次呼叫都會經過的執行點。）

skill 也是落在邊界上的例子。它是一份寫好的手冊，agent 需要的時候才去讀，所以它屬於上下文；只有附在它上面的腳本，才算是手。

三種失敗方式

控制、流程、證據為什麼要各占一層？因為它們出問題的方式各不相同。

控制出問題時，agent 會造成損害：刪了不該刪的東西，或改了不該碰的檔案。流程出問題是另一種樣子：工作會被退回來，因為 agent 太早說了「做完了」，或是想一口氣把所有事做完。Anthropic 在長時間執行的 agent 裡看過這兩種模式：「agent 傾向一次做太多」，而之後的一個會話會「看一圈，見到已經有進展，就宣布工作完成」。（Effective harnesses for long-running agents）證據則不一樣：工作做得再好，這一層也可能出問題。那時沒有人說得清楚發生了什麼：你證明不了工作是對的，壞了也找不到原因，也說不準某個改動到底有沒有用。例如帳單漲了，你卻不知道是哪個任務造成的。

這正是這張地圖派上用場的地方。出了問題，先問一句「這是三類裡的哪一類？」，往往比問「該換哪個模型？」更快。下次遇到失敗，不妨試試看。

给模型周围的东西画一张地图

从模型到 agent

既然差别在模型周围，不妨把那里有什么一样一样说清楚。先从模型本身说起：它是读文本、写文本的程序，相当于“大脑”，可单靠它自己，只能回答问题。要动手做事，它需要工具，每个工具是它能要求做的一件事，比如读文件、搜索、改文件、运行命令。这些就是它的“双手”（模型怎么要求使用工具，见Tool calling，以及怎么给 agent 设计工具）。

可是有了大脑和双手，还不等于有了一个干活的人。总得有个东西去问模型下一步做什么，替它运行它要的工具，把结果拿给它看，然后一遍遍重复，直到模型说做完了。用这样一个循环把两者接起来，它们就成了 agent（这个循环怎么转，见agent 循环，以及你能插手的地方）。循环不会自己写出来，总得有人把它写成程序，这个程序就是 harness 的第一种意思。

“harness”的两种意思

这个词有两种用法，混在一起很容易让人糊涂。第一种是通用 harness，也就是运行循环的那个程序。Claude Code、Codex 和 Copilot 的 agent 模式都是，你买来或者下载下来就能用。第二种是团队的 harness：你在通用 harness 之上，为自己团队搭的那一层，由规则、skill、检查、限制和报告组成。它接在通用 harness 留出来的扩展点上。

这本书讲的是第二种，搭在 VS Code Copilot 上。我说“harness engineering”，指的就是搭这一层的工作。

七层

团队的 harness 零零碎碎的东西很多，为了分清它们，我把模型周围的一切分成七层。这个框架是我自己的（它会在哪里误导你，后面再说）。它好用的地方在于，每一层都带着一个问题，工具和模型怎么变，这个问题都不变。

从下往上读。每一层都有一个日常的比方和一个问题。

层 比方 问题
模型 大脑 它能想多深，要花多少钱？
工具 双手 它够得着什么？
运行环境 把大脑和双手接起来 谁来跑这个循环，循环在哪里给我留了插手的口子？
上下文 公司的岗前培训 它该知道什么，不该读什么？
控制 围栏 我凭什么信它？
流程 活是怎么干成的 工作怎么拆，谁来判断，什么时候停，什么时候叫人？
证据 能讲清楚 它做了什么，做对了没有，花了多少？

下面三层大多是买来的。模型厂商和平台厂商在造，变化也快。上面四层要你自己搭，因为它们取决于你的代码、你的同事和你要承担的风险。它们也更持久：平台升级很少会抹掉你的规则，却很可能让你当初为了绕开弱模型而想出的小聪明变得多余。

正因为这样，本书在下面几层上着墨不多，大部分篇幅留给了上面几层。第 1 部分和第 2 部分讲你需要了解的、买来的那几层，第 3 到第 6 部分各讲上面的一层。

边界没那么清楚

分层只是一种归类的办法，不是自然规律，所以有些东西正好骑在边界上，也就不奇怪了。比如 hook，它是平台在固定时机运行的一小段程序，例如在工具运行之前。这样的时机在循环的每一轮里都会出现；所谓一轮，就是问一次模型、运行它要的工具、再把结果交回去。插槽是平台给的，属于运行环境，可你往插槽里放什么，属于控制。（hook 的细节见Hook：每次调用都会经过的执行点。）

skill 也是骑在边界上的例子。它是一份写好的手册，agent 需要的时候才去读，所以它属于上下文；只有附在它上面的脚本，才算双手。

三种失败方式

控制、流程、证据为什么要各占一层？因为它们出问题的方式各不相同。

控制出了问题，agent 会造成损害：删错了东西，或者改了不该碰的文件。流程出问题是另一副样子：活会被打回来，因为 agent 太早说了“做完了”，或者想一口气全做完。Anthropic 在长时间运行的 agent 里见过这两种情况：“agent 倾向于一次做太多”，而后来的一个会话会“四处看看，发现已经有进展，就宣布工作完成”。（Effective harnesses for long-running agents）证据则不同：活干得再好，这一层也可能出问题。那时没人说得清发生了什么：你证明不了活是对的，出了错找不到原因，也说不准某个改动到底有没有用。比如账单涨了，你却分不清是哪个任务造成的。

这正是这张地图派上用场的地方。出了问题，先问一句“这是三类里的哪一类？”，往往比问“该换哪个模型？”更快。下次碰到失败，不妨试试。

Where the map can mislead you

Seven layers can make it look as if a good harness needs something in every one of them. It does not. Every layer you add is something to maintain and something that can fail, which is why Chapter 0.2 starts from the smallest useful set, and why every chapter ends with a section on when to delete what it describes.

The map can also make the model look as if it hardly matters. That is not my claim either. A stronger model does help. My claim is narrower: for the same model, most of the difference you can influence comes from the layers around it. I have not measured that split, and the LangChain result is a single benchmark.

And the map can look more official than it is. The seven layers are my own frame rather than a standard, one way among others to put the pieces in order.

這張地圖會在哪裡誤導你

七層擺在那裡，容易讓人以為好的 harness 每一層都得有東西。其實不用。你每多搭一層，就多一樣要維護的東西，也多一個可能出錯的地方。所以下一章（30 分鐘搭一個最小 harness）從最小的有用組合講起，每一章的最後也都有一節，講這一章說的東西什麼時候可以刪掉。

這張地圖也可能讓人覺得模型無關緊要，這也不是我的意思。更強的模型確實有幫助。我的說法比較窄：同一個模型，你能影響的那部分差別，大多來自它周圍的幾層。這個比例我沒有量過，LangChain 的結果也只是一個基準。

還有一點，這張地圖看起來可能比實際上更有權威。七層是我自己的框架，不是什麼標準，只是把各個部分排出順序的一種方法。

这张地图会在哪里误导你

还有一点，这张地图看起来可能比它实际上更权威。七层是我自己的框架，不是什么标准，只是把各个部分理出个顺序的一种办法。

What LangChain and Anthropic found Industry practice

Both sources point the same way, though they show different things. LangChain changed only the harness and saw a large gain on one benchmark. Anthropic's write-up on long-running agents describes the failures it saw (doing too much at once, declaring the job done too early) and the fixes it made with files, checklists and structure around the agent. Since it does not compare against a stronger model, it shows where the failures were, not how much a better model would have helped. Neither source claims that the model does not matter.

LangChain 和 Anthropic 看到了什麼 業界做法

上面兩個來源指向同一個方向，只是說明的東西不一樣。LangChain 只改了 harness，就在一個基準上看到大幅提升。Anthropic 那篇談長時間執行 agent 的文章，描述了它看到的失敗（一次做太多、太早宣布完成），以及用檔案、清單和包在 agent 周圍的結構做出的修正。它沒有拿更強的模型來比較，所以它說明的是失敗出在哪裡，而不是換一個更好的模型能幫上多少忙。兩個來源都沒有說模型不重要。

LangChain 和 Anthropic 看到了什么 业界做法

上面两个来源指向同一个方向，只是说明的东西不一样。LangChain 只改了 harness，就在一个基准上看到了大幅提升。Anthropic 那篇讲长时间运行 agent 的文章，描述了它见到的失败（一次做太多、太早宣布完成），以及用文件、清单和围绕 agent 的结构做出的修复。它没有拿更强的模型来对比，所以它说明的是失败出在哪里，而不是换个更好的模型能帮上多少忙。两个来源都没有说模型不重要。

When to redraw the map, or delete it Industry practice

The seven-layer picture is a teaching tool, so treat it like one. If a layer does not help you sort a problem, redraw it. What I would keep is the idea underneath it: when an agent disappoints you, look at what surrounds the model before you blame the model.

什麼時候重畫這張地圖，或乾脆刪掉 業界做法

七層的圖是一個教學工具，就該當教學工具來用。哪一層幫不上你替問題分類，就把它重畫。我會留下的，是圖底下那個想法：agent 讓你失望的時候，先看看模型周圍有什麼，再去怪模型。

什么时候重画这张地图，或者干脆删掉 业界做法

七层的图是个教学工具，就该当教学工具来用。哪一层帮不上你给问题归类，就把它重画。我会留下的，是图底下的那个想法：agent 让你失望的时候，先看看模型周围有什么，再去怪模型。

Explore it in the harness

Copilot Harness is a team harness in the second sense above, with a part for each of the four upper layers. It can walk you through them from the inside, with the real files.

Once you have set it up as described above, type:

/harness-rookie-wondering I have read the chapter "The gap is outside the model". Teach me how a coding agent works in this harness: the loop, the tools, and where the harness steps in. Open the real files with me and draw how the pieces fit together.

It teaches one small piece at a time, stops to check that you are following, and opens the files with you.
