读这一章之前，需要先读过[慎用子 agent](2-3-subagents.html)和[管任务，不管对话](5-1-tasks.html)。

## 一句话 {#in-one-sentence}

想同时管十件事，就开十个独立的任务，每个任务一个 agent，只在关卡处叫人。按任务拆，不按文件拆。任务内部只读的活，仍然可以交给子 agent。

## 写给管理者 {#for-leaders}

- **要拍板的事**：定下是否允许大家同时跑几个任务，一开始跑几个，以及在哪些地方叫人。
- **风险**：瓶颈是人的注意力，不是 agent 的数量。一个永远不看就批准的关卡，只是摆设。我没有整体提速的证据：十个任务并行和十个任务串行，我没有对比测过。
- **做对的代价**：用量随任务数增长（十个任务，十倍用量），外加一块看板，或者一份简单的等待清单。先从两三个开始。
- **可以问团队**：“现在有哪些任务在等人、等了多久？如果其中两个改了同样的文件，会怎样？”

## 问题 {#problem}

agent 在你不在的时候能干很多活。于是下一个念头是：一个 agent 好用，为什么不同时开很多个？这个念头有两种理解，只有一种行得通。

**第一种，是一件大活配很多 agent**。你交出一个大任务，由一个协调者把它分给一队 agent，每个有自己的角色（计划、实现、检查）。看起来像公司的组织架构图。这正是[慎用子 agent](2-3-subagents.html)测过的做法：交接会丢掉理解，每个 agent 又把同样的文件读一遍。那一章并不反对一个任务的每一步都换一个新的帮手。它反对的是好几个 agent 同时改同样的文件，因为那样就得有人来合并它们的成果。

**第二种，是很多件活，每件一个 agent**。十个人提的十个需求，或者你自己的十个不同的问题。每一件都是独立的一份工作，有自己的文件夹、自己的 agent、自己的终点。它们之间什么都不共享，所以什么都不用合并。

这一章讲的是第二种。它不花哨，但一个人能同时推进十件事，靠的就是它。

稀缺的不是 agent，是你。agent 可以等人等上好几个小时，不消耗任何算力。但它等的时候带着的东西会过期：对话的缓存会失效，等你回复时仓库可能已经变了。人同样不能等十个 agent 而不丢线索。所以设计上的问题是：怎么把一个人的注意力分给十个任务？

## 原理 {#how-it-works}

### 并行在任务之间，不在任务内部

每个任务是一个文件夹，和[管任务，不管对话](5-1-tasks.html)里一样：需求、计划、待办清单和交接文件都在文件里。一个 agent 会话一次只管一个任务。十个任务就是十个文件夹、十个会话。

::: figure 7-2-ten-lanes

为什么这样拆很干净，而“一件大活”的拆法不行：

- **什么都不共享**。每个任务有自己的文件夹，所以两个 agent 不会在同一时刻改同一个文件。任务内部没有合并，因为只有一个写入者。
- **每个任务是完整的**。干活的 agent 同时也拿着计划和上下文。不存在从“理解了的 agent”到“要动手的 agent”的交接。三角色测试里的成本，就是这么来的。
- **交接靠文件，不靠消息**。任务停了一天，接手的人读文件夹就行。

这些 agent 之间不交谈。在任务之间穿梭的，只有你。

### 任务什么时候需要人

现在说关键的问题：任务什么时候需要你？如果答案是“经常，而且说不准”，十个任务会吃掉你一整天。所以设计上把所有对人的需要，都推到几个固定的点上，也就是**关卡**。关卡是 agent 停下来、等人点头的地方（细节见[两道门：人在哪里审批](5-3-two-approvals.html)）。

任务只会因为下面这些原因等你：

- 第一道关卡：需求写好了，计划也备好了，两者都在等你确认和批准；
- 第二道关卡：写回（把做完的改动复制进仓库）在等你批准；
- 一次写入中途失败；
- 它需要一次只有你能做的运行的结果；
- 它的独立检查次数用完了，由你决定下一步；
- agent 停了，或者一次无人值守的运行结束了。

在这些点之间，agent 自己干活，不需要你。这就是整个思路：**只在关卡处叫人**。一个任务“时不时有问题就来问你”，是最糟的情况，因为你没法围绕它做安排。只在明确的点上提问的任务，是可以排进日程的。

这也告诉你该建设什么。凡是让 agent 因为非关卡的原因停下来的东西，都是你注意力的漏洞：含糊的需求、缺少的权限、对无害操作弹出的确认框。每一个都值得去掉（[询问不是限制](4-2-ask-vs-refuse.html)）。

### 改同一份代码的任务

这是最常见的情况，所以放在前面。任务文件夹分开了，仓库并没有分开。两个改同样文件的任务，会在写回的时候撞上。一种设计办法：每个任务有自己的分支或工作副本（git worktree 是一种办法），写回时检查它碰过的文件在任务开始之后有没有变，变了就停下来问人。一次只写回一个任务。十个任务同时改一个仓库，我没有测过，所以说不准这个问题多久发生一次。

### 注意力才是贵的

跑十个任务，不会让你快十倍。它只是把你的时间挪到了关卡上，而关卡只有在你真的看了的时候才有价值。

- **让每个关卡都容易读**。你要批准的计划应该一页放得下，在编辑器里看，而不是在终端里翻滚动条。你要确认的需求也应该是一页（[需求由 agent 写，人确认](5-2-requirements.html)）。如果读一遍要二十分钟，你就会扫一眼了事，扫一眼就批准，又回到了“点允许”的老问题。有个值得盯的数字：你驳回或修改计划的频率。如果从来没有，你可能是在扫一眼。
- **手里的不要超过你读得过来的**。能跑多少个任务，取决于你读计划和 diff 有多快，不取决于屏幕上放得下几个会话。先从两三个开始。能稳稳拿住几个，要看任务本身，我没有测过。
- **把相似的关卡放一起**。有三份计划在等，就一口气读完。在计划、diff 和需求之间来回切换，比连读三份计划更费力。
- **成本会累加**。十个任务是十倍用量，所以每个任务都要配一条停止规则（[无人值守：什么时候必须停](5-7-when-to-stop.html)）。一个任务等你的时间如果超过了 prompt 缓存的存活时间（Anthropic 的 API 上是五分钟或一小时，见[选模型：看每次成功的成本](1-1-models-and-cost.html)），你回来时它要按全价把上下文重读一遍。Copilot 在这方面怎么处理，我没有查过。

### 一份等你的清单

开着十个会话，你怎么知道哪一个在等你？一个窗口一个窗口地翻，正是你想避免的成本。

答案是**看板**：一个页面，列出每个未结束的任务、它在等什么、等了多久。有两个设计点让它值得信任。

::: figure 7-2-board

- **状态由代码写，不由 agent 写**。agent 停下来时，一个 hook 会运行，记下“等你”。看板读的是这份给机器看的状态文件。它不读 agent 用文字写的进度笔记，因为 agent 会忘了打勾，或者勾多了。
- **等待是一个数字**。一个任务从开始等待到现在过了多久，告诉你先打开哪一个。

同一个页面上有个开关，我在一天结束时用。它会暂停每个 agent 没在干活的未结束任务，第二天早上再接回来。暂停期间的等待时间不计，所以数字保持真实。

**没有看板？用清单**。这个思路手工也行：每个任务一个终端标签页，标题写任务名，再自己记一份短清单，写哪个标签页在等、等了多久。

### 任务内部只读的帮手

“一个任务一个 agent”这条规矩，针对的是会写入的活。在一个任务内部，只读的帮手仍然可以并行，交回简短的摘要，因为没有哪个帮手会改文件（[慎用子 agent](2-3-subagents.html)）。每个任务一个写入者，读的人要多少有多少，只要读的活值得。

## 代价和坑 {#costs-and-traps}

**上下文切换的成本在你身上**。agent 不在乎切换，你在乎。十个任务分布在十个不同的领域，比十个都在同一领域更费注意力，因为每个关卡需要不同的知识。

**永远通过的关卡，就是你不会读的关卡**。如果你连着批准了十份计划，一份也没打开过，这些关卡就是摆设。补救办法是更少、更小的关卡，不是更多。

**看板的好坏取决于它的状态**。如果状态来自 agent 自己说的话，看板就会说谎。这就是状态来自 hook 和文件的原因。

**我没有拿它和别的办法比过**。我没有整体提速的证据：十个并行任务和十个串行任务，或者和一个团队，我都没对比测过。论据在结构上：什么都不共享，人的注意力是上限。标题里的“十”是个例子，不是结果。

## 什么时候可以删掉 {#when-to-delete-it}

有看板，是因为会话不会告诉你它在等。等平台在一个地方显示所有正在运行的 agent 会话和它们各自在等什么，看板就可以删。Copilot 在这方面做到哪一步了，我没有查过。

思路不会消失。即使列表由平台来做，这个划分依然成立：每个任务一个写入者，只在关卡处叫人。

## 在你自己的环境里试试 {#try-it}

不用装 harness。在你自己的仓库里打开 agent，粘贴：

::: prompt
只用只读的 git 命令，列出这个仓库里最近有提交的分支、worktree 和未合并的 pull request。对每一个，列出它相对主分支改了哪些文件。然后找出改了相同文件的几对，说明如果一起写回，哪些会冲突。对每一项工作，说明它多半在等什么（review、一个决定、一次测试运行）。不要修改任何文件。
:::

## 在 harness 里探索 {#explore}

任务文件夹、看板和“等你”这个状态，都在 Copilot Harness 里跑着。harness 可以给你看一块放着真实任务的看板。按上面的说明准备好之后，输入：

::: prompt
/harness-rookie-wondering 我读完了“同时管十件事：并行的是任务”这一章。请教我这个 harness 是怎么让一个人跑多个任务的：任务文件夹、任务可以处于哪几种等待状态，以及看板怎么知道一个任务在等。带我打开真实的文件，并让我看看看板读什么、谁来写。
:::

它一次只教一小块，停下来确认你跟上了，再和你一起打开文件。
