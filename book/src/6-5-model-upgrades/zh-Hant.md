讀這一章，你需要用過 AI 寫程式的 agent，而且替它寫過規則或步驟。不需要別的。

## 一句話 {#in-one-sentence}

模型升級時，先重跑你的評測。然後刪掉新模型不再需要的規則、檢查和步驟，因為為舊模型搭的鷹架，可能會拖慢新模型。

## 給主管 {#for-leaders}

- **要做的決定**：每次換模型之後，排一次對設定的檢視，並決定誰重跑評測、誰可以刪規則。
- **風險**：為舊模型搭的規則和步驟，可能會拖慢新模型。我沒有在一次升級上量過這件事；它是個擔心，不是結果。防止損害的硬限制、紀錄和評測，不在要砍的清單上。
- **做對的成本**：重跑你的固定任務，而且不只一次，再加上一個人的時間，一次移除一塊。大多是錢和時間；我沒有數字。
- **可以問團隊**：「如果模型明天換了，我們會先測試拿掉哪些規則？哪些評測能告訴我們答案？」

## 問題 {#problem}

把 agent 周圍的設定，想成**鷹架**（scaffolding），也就是蓋房子時，工人在建築周圍搭的架子。裡面每一條規則、每個檢查、每一個寫出來的步驟，都是有原因才放進去的。每一個，都在補當時的模型做錯、做不好或忘記的事。

然後模型升級了。那些原因是關於舊模型的。有些已經不在了。沒有人通知你的設定。

這是個真實的擔心，雖然我沒有在一次升級上量過。我自己的 harness 的第一版，有等級，還有三個有職稱的 agent。三個 agent 用了幾天就拿掉了，依據是 [慎用子 agent](2-3-subagents.html) 裡的證據，那一章有成本數字和它們的限制。等級被拿掉的原因不同（[我砍掉了什麼，數據怎麼說](7-3-what-we-cut.html)）。兩者在當時都看起來合理。我從中帶走的是一個問題，不是一個結果：模型比較弱時搭的結構，在模型進步後，可能不再值回它的成本，而且在有人測試、移除它之前，它會一直花錢。這一章其餘的部分，講怎麼測。

沒用的鷹架，花的成本有三種。

- **時間和金錢**。每多一步，每個任務都要付一次。
- **空間**。一份長的規則檔，每一輪都占用上下文視窗的一部分（[上下文是一份預算](3-1-context-budget.html)）。
- **混亂**。為舊模型的習慣寫的規則，可能把新模型拉向錯的方向。這有多常發生，我沒有測過。它是風險，不是量到的效果。

## 原理 {#how-it-works}

規則很簡單：**不要憑感覺刪，也不要憑習慣留。跑評測**。圖顯示順序。

::: figure 6-5-thinner

### 1. 升級之前，先有東西可以重跑

這就是 [固定的任務](6-3-eval-tasks.html) 排在前面的原因。如果你沒有一組固定任務和給它們打分的腳本，升級就是一個你沒辦法評判的改動。把這組任務和它舊的結果留著。它們是基準。

### 2. 只改模型，重跑

在新模型上，用同樣的設定跑同樣的任務。和基準比較。確認只有模型變了：新模型可能用不同的方式把文字切成 token、改變預設的思考量、一開始又沒命中 prompt 快取，這每一項都會改變成本，卻不改變品質。把它們和數字一起記下來。如果供應商發布了從舊模型換到新模型的說明，在重跑之前先讀，這樣你就知道要留意什麼。有兩種情況可能發生。

- **某處變差了**。舊模型下守得住的規則，在新模型下可能守不住。先知道比較好。模型升級和任何其他改動一樣，可能弄壞東西。
- **變好了，或一樣**。那麼要看的差距就是成本：時間、用量、輪數。

因為各次運行不同（[一次運行證明不了什麼](6-4-variance.html)），每個都要跑不只一次，不然你會把雜訊讀成結果。

### 3. 不管評測怎麼說，都不能拿掉的

有些東西根本不該在清單上，開始移除之前先知道比較好。

- **防止損害的硬限制**。拒絕碰正式環境、保護規則檔的防護、由人批准無法復原的事。這些不取決於模型有多聰明；它們保護的，是模型錯了或被騙了會怎樣。**更好的模型不是拿掉它們的理由**（[有些東西根本不給](4-5-least-privilege.html)）。
- **紀錄**。更好的模型仍然需要日誌、報告，和讀它們的人（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)）。
- **評測**。其他一切，都靠它們來決定。

各層的變化速度不同。文字（規則和步驟）最先變，也最容易砍。程式碼裡的執行，變得比較慢，而且要靠評測。平台的改變，在這一切底下。

### 4. 一次拿掉一塊

現在對每一塊鷹架問：新模型還需要它嗎？你要靠拿掉它、再跑一次任務才知道。一輪一塊，不然你不知道是哪一塊有影響。

對像獨立檢查這樣的一塊，實驗很直接。開著檢查跑任務，關掉檢查再跑，然後比較。如果評測顯示沒有差別，這個檢查在這些任務上就沒有值回它的成本（[慎用子 agent](2-3-subagents.html) 對第二個 agent 有同樣的推理）。如果它還是抓得到東西，就留著。

### 5. 我會先看什麼

這些是我預期，在我自己的設定裡會最先成為候選的部分。我把它們列成要測試的東西，不是結果；模型升級之後，我還沒有重跑過它們。

| 部分 | 為什麼可能變 | 我會怎麼做 |
| --- | --- | --- |
| 為各種工作寫出來的手冊 | 較新的模型，可能不需要把步驟寫得那麼細 | 縮短它們。留著「什麼才算做完」的清單：它們說的是你要什麼，不是怎麼得到（[管任務，不管對話](5-1-tasks.html)） |
| 獨立檢查 | 模型可能更可靠地檢查自己 | 比較沒有檢查和有一次檢查。只有評測顯示兩者沒有差別，預設才變成不檢查 |
| 提醒和變通辦法 | 它們補的是舊模型的習慣 | 關掉它們來測試（[把團隊的做法寫成 skill](3-4-skills-and-workflows.html) 對「gotchas」也這麼說） |
| 因為模型不聽，而搬進程式碼的規則 | 新模型可能會遵守 | 在違反了還能復原的地方，把程式碼規則關掉，並計數（[提示裡的規則只是請求](4-1-requests-and-rules.html)） |
| 每個角色用哪個模型 | 新模型會出來 | 改那一個設定，然後跑任務 |
| 為舊模型調過的措辭 | 為了讓一個模型聽見而寫的強調，對另一個可能太重 | 改寫得平實一點，然後跑任務。我沒有測過這個 |

這本書幾乎每一章，都以一節「什麼時候可以刪掉」結尾。那一節就是這一步的清單。升級之後，我依序走過這些節，對每一節問它的條件現在成不成立。

### 6. 寫下你刪了什麼，以及什麼時候會放回去

拿掉東西時，我寫一行：什麼、為什麼、什麼證據會讓它回來。這讓設定不會變成猜測。下一個模型在某件事上比較差時，你知道該看哪一行。（同樣的習慣貫穿 [我砍掉了什麼，數據怎麼說](7-3-what-we-cut.html)。）

### 測你自己的設定

**三個問題**：

1. 如果模型明天升級，你會重跑什麼，來知道你的設定還行不行？
2. 哪一條規則或步驟，你留著只是因為你曾經加過它？
3. 哪一個拿掉會痛，你怎麼知道？

**今天就能做的測試**。挑你設定裡一條你懷疑是廢物的規則或步驟。選三個它應該有影響的任務。先複製規則檔，這樣你能把規則放回去。有它和沒它各跑任務，而且不只一次，比較通過和用量。如果你分不出兩者，你就學到了東西。如果它確實有影響，你就學到了這條規則值多少。

## 代價和陷阱 {#costs-and-traps}

**拿掉東西也是改動，也可能弄壞東西**。一次拿掉一塊，每次之後都跑評測。

**評測就是極限**。你只能說，某一塊在你測過的任務上不需要。如果任務很少，就說出來，並且對任何防止損害的東西要小心。

**重跑要花錢**。每次模型發布之後都完整重跑，不一定負擔得起。換模型系列、版本號變了，或你注意到行為變了的時候再重跑。快取在這裡有影響：在 Anthropic 的 API 上，快取讀取大約是基本輸入價格的十分之一（[選模型：算的是每次成功的成本](1-1-models-and-cost.html)），但新模型上最先的幾次運行是冷啟動，而這一切 Copilot 怎麼計費，我沒查過。

**新模型可能在某件事上比較差**。升級不一定在每個任務上都更好。評測也是為了這個。

**鷹架可能藏著弱點**。一個總是抓到同一種錯誤的檢查，可能正是讓你沒注意到那種錯誤的東西。拿掉它的時候，去看失敗的運行。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

這一章本身就是一套刪東西的程序，那有什麼可刪的？一步一步重跑的做法。如果平台在你自己的任務上告訴你升級改變了什麼，或在每次發布時替你跑評測，我會用那個。習慣會留著：設定裡沒有東西是永久的，每一塊都要對照你現在有的模型，證明自己該在那裡。

Copilot Harness 有一份清單，列出它預期模型升級後最先會變的東西，另有一份清單，列出它選擇不做的東西，以及什麼時候會重新考慮。harness 可以帶你走過這兩份。照上面的說明準備好之後，輸入：

::: prompt
/harness-rookie-wondering 我讀完了「模型升級了，就要刪」這一章。請教我這個 harness 預期模型升級後哪些東西會變（主題 15），以及哪些東西它永遠不會拿掉。對每一部分，帶我打開真實的檔案，並示範我該怎麼測試它是不是還需要。
