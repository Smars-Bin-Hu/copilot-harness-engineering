讀這一章，你需要用過寫程式的 AI agent，而且替它寫過規則或步驟。不需要別的。

## 一句話 {#in-one-sentence}

模型升級時，先重跑你的評測。然後刪掉新模型不再需要的規則、檢查和步驟，因為為舊模型搭的鷹架，可能會拖慢新模型。

## 給主管 {#for-leaders}

- **要做的決定**：每次換模型之後，安排檢查一次設定，並決定誰重跑評測、誰可以刪規則。
- **風險**：為舊模型搭的規則和步驟，可能會拖慢新模型。我沒有在一次升級上量過這件事，所以它只是個擔心，不是結果。防止損害的硬限制、紀錄和評測，都不在要砍的清單上。
- **做對的成本**：把你的固定任務重跑不只一次，再加上一個人的時間，一次移除一塊。花的大多是錢和時間，確切多少我沒有數字。
- **可以問團隊**：「如果模型明天換了，我們會先測試拿掉哪些規則？哪些評測能告訴我們答案？」

## 模型變強了，鷹架會怎樣？ {#problem}

不妨把 agent 周圍的設定想成**鷹架**（scaffolding），也就是蓋房子時，工人在建築周圍搭起來的那層架子。裡面每一條規則、每個檢查、每一個寫出來的步驟，當初放進去都是有原因的，為的是補上當時的模型做錯、做不好或忘記的事。

可是後來模型升級了。那些原因說的都是舊模型，換了新模型，有些原因也就不在了。偏偏沒有人通知你的設定。

這是個真實的擔心，雖然我沒有在一次升級上量過。我手上有的，是自己這套 harness 的經歷：它的第一版有等級，還有三個按職務分工的 agent。那三個 agent 用了幾天就拿掉了，依據是 [慎用子 agent](2-3-subagents.html) 裡的證據（成本數字和它們的限制都在那一章）。等級被拿掉，則是另一個原因（[我砍掉了什麼，數據怎麼說](7-3-what-we-cut.html)）。這兩樣東西剛放進去的時候，看起來都很合理。我得到的是一個問題，而不是一個結果：模型比較弱時搭起來的結構，等模型進步以後，會不會就不再值回它的成本？如果會，那麼在有人測試它、把它移除之前，它會一直花錢。

這些不再值得留的鷹架，留著的時候，花的成本有三種。一是時間和金錢，每多一步，每個任務都要為它付一次。二是空間，一份長長的規則檔，每一輪都占用上下文視窗的一部分（[上下文是一份預算](3-1-context-budget.html)）。三是混亂：為舊模型的習慣寫的規則，可能把新模型拉向錯的方向，不過這個風險我沒有測過。

那麼，哪些部分已經沒用了，你又要怎麼知道？

## 怎麼查出新模型不再需要什麼 {#how-it-works}

規則很簡單：**不要憑感覺刪，也不要憑習慣留。跑評測**。圖裡畫出了先後順序。

::: figure 6-5-thinner

### 1. 升級之前，先有東西可以重跑

要跑評測，先得有東西可跑，這就是 [固定的任務](6-3-eval-tasks.html) 排在前面的原因。如果沒有一組固定任務和替它們打分的腳本，升級就是一個你沒辦法評判的改動。所以要把這組任務和它舊的結果留好，作為你的基準。

### 2. 只改模型，重跑

如果供應商發布了從舊模型換到新模型的說明，重跑之前先讀一讀，這樣你就知道要留意什麼。然後在新模型上，用同樣的設定跑同樣的任務，確保變的只有模型，再和基準比較。難處在於，就算只換了模型，也會順帶變掉幾樣東西：新模型可能用不同的方式把文字切成 token，可能改變預設的思考量，一開始也可能沒命中 prompt 快取。它們改變的是成本，不是品質，所以要和數字一起記下來。

這樣重跑下來，結果不外乎兩種。一種是某處變差了：舊模型下守得住的規則，在新模型下可能守不住。這一點你要在動手刪東西之前就知道。另一種是變好了，或者持平，這時要看的差距就是成本：時間、用量、輪數。不管是哪一種，各次運行的結果都不同（[一次運行證明不了什麼](6-4-variance.html)），所以每個都要跑不只一次，不然你會把雜訊當成結果。

### 3. 不管評測怎麼說，都不能拿掉的

開始移除之前，最好先知道一件事：有些東西根本不該在這張清單上。頭一類是防止損害的硬限制，比如拒絕碰正式環境、守住規則檔的防護、無法復原的事由人批准。這些都不取決於模型有多聰明，因為它們保護的，是模型錯了或被騙了時會發生的事。**更好的模型不是拿掉它們的理由**（[有些東西根本不給](4-5-least-privilege.html)）。紀錄也一樣省不掉，更好的模型仍然需要日誌、報告，和讀它們的人（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)）。評測也要留著，因為其他一切都靠它們來決定。

可以砍的那些，過時的速度也不一樣。文字層面的規則和步驟最先變，也最容易砍。寫進程式碼的執行變得比較慢，砍不砍要看評測。平台的改變，則在這一切的底下。

### 4. 一次拿掉一塊

到了這裡，就可以對每一塊鷹架問一句：新模型還需要它嗎？要知道答案，就把它拿掉，再把任務跑一次。每一輪只動一塊，因為一次拿掉兩塊，你就不知道是哪一塊有影響了。

比如獨立檢查，實驗做起來就很直接：開著檢查跑一次任務，關掉再跑一次，然後比較。如果評測顯示沒有差別，這個檢查在這些任務上就沒有值回它的成本（[慎用子 agent](2-3-subagents.html) 對第二個 agent 有同樣的推理）。但如果它還是抓得到東西，就留著。

### 5. 我會先看什麼

在我自己的設定裡，我會先試哪幾塊？下表列的是我預期最先成為候選的部分。它們是要測試的東西，不是結果，因為模型升級之後，我還沒有重跑過它們。

| 部分 | 為什麼可能變 | 我會怎麼做 |
| --- | --- | --- |
| 為各種工作寫出來的手冊 | 較新的模型，可能不需要把步驟寫得那麼細 | 縮短它們。留著「什麼才算做完」的清單：它們說的是你要什麼，不是怎麼得到（[管任務，不管對話](5-1-tasks.html)） |
| 獨立檢查 | 模型可能更可靠地檢查自己 | 比較沒有檢查和有一次檢查。只有評測顯示兩者沒有差別，預設才變成不檢查 |
| 提醒和變通辦法 | 它們補的是舊模型的習慣 | 關掉它們來測試（[把團隊的做法寫成 skill](3-4-skills-and-workflows.html) 對「陷阱」也這麼說） |
| 因為模型不聽，而搬進程式碼的規則 | 新模型可能會遵守 | 在違反了還能復原的地方，把程式碼規則關掉，並計數（[提示裡的規則只是請求](4-1-requests-and-rules.html)） |
| 每個角色用哪個模型 | 新模型會出來 | 改那一個設定，然後跑任務 |
| 為舊模型調過的措辭 | 為了讓一個模型聽見而寫的強調，對另一個可能太重 | 改寫得平實一點，然後跑任務 |

這張表只是我的猜測。更完整的清單其實書裡已經有了：這本書幾乎每一章的結尾，都有一節講什麼時候可以把這一章講的東西刪掉。升級之後，我依序把這些節走一遍，逐節問它說的條件現在成不成立。

### 6. 寫下你刪了什麼，以及什麼時候會放回去

我每拿掉一樣東西，都會寫一行：拿掉了什麼、為什麼，以及什麼證據會讓它回來。有了這一行，設定才不會變成猜測，因為下一個模型在某件事上比較差時，你知道該看哪一行。（[我砍掉了什麼，數據怎麼說](7-3-what-we-cut.html) 裡貫穿的也是這個習慣。）

### 測你自己的設定

關於你自己的設定，有三個問題值得問一問：

1. 如果模型明天升級，你會重跑什麼，來知道你的設定還行不行？
2. 哪一條規則或步驟，你留著只是因為你曾經加過它？
3. 哪一個拿掉會痛，你怎麼知道？

還有一個今天就能做的測試。挑你設定裡一條你懷疑是累贅的規則或步驟，再選三個它應該有影響的任務。先複製一份規則檔，好讓你能把規則放回去。然後有它和沒它各跑這些任務，而且不只一次，比較通過的情況和用量。如果你分不出兩者，你就學到了一點東西。如果它確實有影響，你就知道了這條規則值多少。

## 刪的風險，重跑的代價 {#costs-and-traps}

這套做法本身也有風險和代價。最直接的是，拿掉一塊和任何改動一樣，也可能弄壞東西，所以要一次只拿掉一塊，每拿掉一塊就跑一次評測。

但即使這樣，結論也只能停在評測的範圍裡：你能說的，只是某一塊在你測過的任務上不需要。如果任務很少，就照實說出來，並且對任何防止損害的東西都要小心，因為新模型在有些任務上可能比舊模型差。

每次重跑也都要花錢，所以每次有模型發布就完整重跑一遍，不一定負擔得起。換模型系列、版本號變了，或你注意到行為變了的時候，再重跑。快取也會讓帳算偏。在 Anthropic 的 API 上，快取讀取大約是基本輸入價格的十分之一（[選模型：算的是每次成功的成本](1-1-models-and-cost.html)），可是新模型上最先的幾次運行是冷啟動，用不上快取。至於這一切 Copilot 怎麼計費，我沒查過。

還有一種更隱蔽的情況：鷹架會把弱點蓋住。一個檢查要是每次都抓到同一種錯誤，可能正是它讓你一直沒注意到那種錯誤，所以拿掉它的時候，要去看失敗的運行。

## 什麼時候連這套流程也刪掉 {#when-to-delete-it}
{status: industry}

這一章本身就是一套刪東西的程序，那它還有什麼可刪的？就是一步一步重跑的那套做法。如果有平台能在你自己的任務上告訴你一次升級改變了什麼，或在每次發布時替你跑評測，我會改用它。留下來的是這個習慣：設定裡沒有東西是永久的，每一塊都要對照你現在有的模型，證明自己該留下。
