读这一章，你需要用过一个写代码的 AI agent，并且给它写过规则或步骤。别的都不需要。

## 一句话 {#in-one-sentence}

模型升级了，先重跑你的评测。然后把新模型已经不需要的规则、检查和步骤删掉，因为为旧模型搭的脚手架，可能会拖慢新模型。

## 写给管理者 {#for-leaders}

- **要拍板的事**：每次换模型之后，安排一次对配置的复查，并定下谁来重跑评测、谁有权删规则。
- **风险**：为旧模型搭的规则和步骤，可能会拖慢新模型。我没有在一次升级上测过这一点，所以它只是一种担心，不是结果。防止破坏的硬性限制、记录和评测，都不在要砍的清单上。
- **做对的代价**：把你的固定任务重跑不止一遍，再搭上一个人的时间，一次删一块。花的主要是钱和时间，具体多少我没有数字。
- **可以问团队**：“如果明天换了模型，我们会先试着删掉哪些规则？哪些评测能告诉我们结果？”

## 模型变强了，脚手架会怎样？ {#problem}

不妨把 agent 周围的配置想成**脚手架**，也就是工人盖楼时在楼外搭起来的那层架子。里面的每条规则、每项检查、每一步写明的步骤，当初放进去都是有理由的，为的是补上当时那个模型做错的、做得差的或者忘掉的东西。

可后来模型升级了。那些理由说的都是旧模型，换了新模型，其中一些也就不成立了。偏偏没人通知你的配置。

这是个实实在在的担心，虽然我没有在一次升级上测过。我手里有的，是自己这套 harness 的经历：它的第一版有分级，还有三个按岗位分工的 agent。那三个 agent 用了几天就拿掉了，依据是[别跟风瞎用子 Agent](2-3-subagents.html)里的证据（成本数字和它们的局限都在那一章）。分级被拿掉，则是另一个原因（[多 Agent 分工没换来什么：我砍掉的东西](7-3-what-we-cut.html)）。这两样东西刚放进去的时候，看起来都挺合理。我从中得到的是一个问题，而不是一个结果：模型还弱的时候搭起来的结构，等模型变强以后，会不会就不再值它的成本了？如果会，那么在有人去测它、把它拿掉之前，它会一直花钱。

这些不再值得留的脚手架，留着的时候会在三个方面花钱。一是时间和钱，每多一步，每个任务都要为它付一次。二是空间，一份很长的规则文件，每一轮都占着上下文窗口的一部分（[为什么不能把所有规则都塞给 Agent？](3-1-context-budget.html)）。三是混乱：为旧模型的某个习惯写的规则，可能把新模型往错的方向拉，不过这个风险我没测过。

那么，哪些块已经没用了，你又怎么知道？

## 怎么查出新模型不再需要什么 {#how-it-works}

规则很简单：**不凭感觉删，也不凭习惯留。跑评测**。图里画出了先后顺序。

::: figure 6-5-thinner

### 1. 升级之前，先准备好能重跑的东西

要跑评测，先得有东西可跑，这就是[固定任务](6-3-eval-tasks.html)排在前面的原因。如果没有一组固定任务和给它们打分的脚本，升级就是一个你没法评判的改动。所以要把这组任务和它以前的结果留好，作为你的基线。

### 2. 只换模型，重跑

如果提供方发布了从旧模型迁移到新模型的说明，重跑之前先读一读，这样你就知道该留意什么。然后在新模型上，用同样的配置跑同样的任务，确保变的只有模型，再和基线比较。难处在于，就算只换了模型，也会顺带变掉几样东西：新模型把文字切成 token 的方式（分词）可能不同，默认的思考量可能变了，一开始还可能命中不了 prompt 缓存。它们改变的是成本，不是质量，所以要和数字记在一起。

这样重跑下来，结果不外乎两种。一种是某个地方变差了：旧模型下管用的规则，换了新模型可能就不管用了。这一点你要在动手删东西之前就知道。另一种是变好了，或者持平，这时要看的差距就是成本：时间、用量、轮数。不管是哪种，每次运行的结果都不一样（[同一个任务跑两次，结果不一样](6-4-variance.html)），所以每个都要跑不止一次，否则你会把噪声当成结果。

### 3. 不管评测怎么说，都不能删的

开始删之前，最好先清楚一点：有些东西根本就不该上这张清单。头一类是防止破坏的硬性限制，比如拒绝碰生产环境、守护规则文件、不可撤销的事要由人审批。这些都不取决于模型有多聪明，因为它们防的是模型出错或者被骗时会发生的事。**模型变好了，不是去掉它们的理由**（[不要开放全部的权限或使用沙箱](4-5-least-privilege.html)）。记录也一样省不掉，更好的模型照样需要日志、报告，以及读它们的人（[记下发生了什么](6-1-observe.html)）。评测也要留着，因为其他一切都靠它来决定。

可以砍的那些，过时的速度也不一样。文本层面的规则和步骤变得最快，也最容易砍。写进代码的强制执行变得慢一些，砍不砍要看评测。平台的变化，则在这一切的底下。

### 4. 一次只拿掉一块

到这里，就可以对每一块脚手架问一句：新模型还需要它吗？要知道答案，就把它拿掉，再把任务重跑一遍。每一轮只动一块，因为一次拿掉两块，你就不知道起作用的是哪一块了。

比如独立检查，实验做起来就很直接：开着检查跑一遍任务，关掉再跑一遍，然后比较。如果评测显示没有差别，这项检查在这些任务上就不值它的成本（[别跟风瞎用子 Agent](2-3-subagents.html)对第二个 agent 也是同样的道理）。但如果它还能抓出问题，就留着。

### 5. 我会先看什么

在我自己的配置里，我会先试哪几块？下表列的是我预期最先被考虑的候选。它们是要测的东西，不是结果，因为模型升级之后，我还没有重跑过它们。

| 部分 | 为什么可能变 | 我会怎么做 |
| --- | --- | --- |
| 针对各类工作写明的步骤手册 | 更新的模型可能不需要把步骤写得那么细 | 把它们缩短。保留“什么算做完”的清单：它们说的是你要什么，不是怎么得到（[一个任务一个文件夹](5-1-tasks.html)） |
| 独立检查 | 模型可能更可靠地检查自己 | 比较不检查和检查一次。只有当评测显示两者没有差别，默认才变成不检查 |
| 提醒和变通办法 | 它们补的是旧模型的某个习惯 | 关掉它们再测（[怎么写一个真正好用的 skill？](3-4-skills-and-workflows.html)对“坑”也是这么说的） |
| 因为模型不听而挪进代码的规则 | 新模型可能会遵守 | 在违反了也能撤销的地方，把代码里的规则关掉，并计数（[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)） |
| 每个角色用哪个模型 | 新模型会不断出来 | 只改这一项设置，再跑任务 |
| 为旧模型调过的措辞 | 为了让某个模型听见而写的强调，对另一个模型可能太重 | 用平实的话重写，再跑任务 |

这张表只是我的猜测。更完整的清单其实书里已经有了：本书几乎每一章的结尾，都有一节讲什么时候可以把这一章讲的东西删掉。升级之后，我按顺序把这些节过一遍，逐节问它说的条件现在成不成立。

### 6. 写下你删了什么，什么时候会放回去

我每拿掉一样东西，都会写一行：拿掉了什么、为什么，以及什么证据会让它回来。有了这一行，配置才不至于变成瞎猜，因为下一个模型在某件事上更差时，你知道该看哪一行。（[多 Agent 分工没换来什么：我砍掉的东西](7-3-what-we-cut.html)里贯穿的也是这个习惯。）

### 测你自己的配置

关于你自己的配置，有三个问题值得问一问：

1. 如果明天模型升级了，你会重跑什么，来看你的配置还管不管用？
2. 哪条规则或哪一步，你留着只是因为曾经加过？
3. 哪一个删了会出问题？你怎么知道？

还有一个今天就能做的测试。挑你配置里一条你怀疑是累赘的规则或步骤，再选三个它应该起作用的任务。先把规则文件复制一份，好让你能把规则放回去。然后有它和没它各跑这些任务，不止一次，比较通过情况和用量。如果分不出两者的差别，你就学到了一点东西。如果它确实有影响，你就知道了这条规则值多少。

## 删的风险，重跑的代价 {#costs-and-traps}

这套做法本身也有风险和代价。最直接的是，拿掉一块和任何改动一样，也可能把东西弄坏，所以要一次只拿掉一块，每拿掉一块就跑一次评测。

但即便这样，结论也只能停在评测的边界上：你能说的，只是某一块对你测过的那些任务不需要。如果任务很少，就照实说，并且对任何防止破坏的东西都要小心，因为新模型在有些任务上可能比旧模型更差。

每次重跑也都要花钱，所以每发布一个新模型就完整重跑一遍，不一定负担得起。换了模型系列、版本号变了，或者你注意到行为变了，再重跑。缓存也会让账算偏。在 Anthropic 的 API 上，命中缓存的读取约是基础输入价格的十分之一（[选模型，别只看 token 单价](1-1-models-and-cost.html)），可新模型上最初几次运行是冷启动，用不上缓存。至于 Copilot 对这些怎么计费，我没有查过。

还有一种更隐蔽的情况：脚手架会把弱点盖住。一项检查要是每次都抓住同一个错误，可能正是它让你一直没注意到这个错误，所以拿掉它的时候，要去看失败的运行。

## 什么时候连这套流程也删掉 {#when-to-delete-it}
{status: industry}

这一章本身就是一套删东西的流程，那它还有什么可删的？就是一步一步重跑的那套做法。如果有平台能在你自己的任务上告诉你一次升级改变了什么，或者每次发布都替你跑评测，我会用它。留下来的是这个习惯：配置里没有什么是永久的，每一块都得对照你现在用的这个模型，证明自己该留下。

## 在你自己的环境里试试 {#try-it}

::: prompt
列出这个仓库的 agent 指令、skill 和 hook 文件里的每一条规则、步骤和检查。把每一项归入以下之一：防止破坏的硬性限制、记录或日志、针对旧模型某个习惯的变通办法、写明的步骤手册、措辞里的强调。对每个变通办法、步骤手册或强调，根据 git 历史说明它是为了什么失败而加的，或者写“没找到原因”。然后指出，模型升级后我应该先试着删哪五项，以及该重跑我的哪些任务来检查。不要修改任何文件。
