讀這一章，你需要讀過 [詢問不是限制](4-2-ask-vs-refuse.html) 和 [保護規則本身的檔案](4-3-guardrails.html)：為什麼「先問我」不是限制，以及為什麼 agent 不能改規則。

## 一句話 {#in-one-sentence}

在花錢、給權力、不能反悔的地方放一個人。讓批准從 agent 碰不到的管道進來，而且只綁定到被批准的那一份計畫。

## 給主管 {#for-leaders}

- **要做的決定**：決定人必須在哪裡批准：花錢、給權力、不能反悔的地方，其他地方都不用。批准必須走 agent 碰不到的管道，而且只屬於人讀過的那份計畫或那次改動。
- **風險**：確認框可以在整個會話裡被悄悄關掉，而 agent 能自己給的批准不是批准。累了的人還是可能不讀就批准；把批准綁到內容上，擋得住掉包，擋不住隨手按的「好」。
- **做對的成本**：每道門要人讀一次、打一個指令。門太多，人就不讀了。在我的設定裡，門上的快照預設保留 14 天。
- **可以問團隊**：「我們的流程裡，哪些批准是 agent 能自己給或自己關掉的？計畫事後改了，批准還算數嗎？」

## 問題 {#problem}

你想讓人批准重要的步驟。最直接的工具是 agent 工具跳出的確認框：「允許這個嗎？」它效果不好，原因有兩個。

第一，人會按允許。到第一百個框，就沒人在讀了（[詢問不是限制](4-2-ask-vs-refuse.html)）。第二，很多工具讓你勾「這個會話都允許」，之後框就再也不出現。你倚靠的批准不見了，也沒有任何東西告訴你。

第三個問題更微妙。假設批准是一個由人打出來的指令。如果 agent 能執行指令，它也能打出同一個指令。agent 自己能給的批准，不是批准。

所以問題是：人要放在哪裡，以及怎麼讓他的「好」成為 agent 造不出來、也沒辦法重複使用的東西。

## 原理 {#how-it-works}

### 人要放在哪裡

人的注意力是系統裡最稀少的東西。只把它花在三種地方，其他地方都不花：

- **花錢的地方**。例如，開始一次昂貴的運行。
- **給權力的地方**。讓 agent 寫入共用的倉庫。
- **不能反悔的地方**。做了就收不回來的事。

任務資料夾裡的一切，重做都很便宜，所以 agent 在那裡可以自由工作（[管任務，不管對話](5-1-tasks.html)）。一個會改動真實倉庫的任務有兩個這樣的地方。我把每一個叫做**門**：人批准之前，任務不能通過。

::: figure 5-3-two-gates

### 第一道門：批准計畫

agent 寫出需求和計畫，然後停下來。人讀計畫，讀完才批准。在這之前，agent 可以起草、可以讀；不能開始改工作檔案。

這道門是為了成本。計畫錯了，改一段文字很便宜；錯到做完才改，就很貴。在我的設定裡，計畫也建立在已確認的需求上（[需求由 agent 寫，人確認](5-2-requirements.html)），所以一次批准可以同時確認兩者。

### 第二道門：批准寫回

agent 已經在任務資料夾裡做完改動，檢查也跑過了。現在結果要送到真實的倉庫。把它複製過去叫**寫回**。人讀的是確切的 **diff**：會被改動的那些行的清單。然後批准。

寫回時，結果會進到倉庫的一個新分支，而且不提交。它絕不會直接碰主分支。寫入之前，程式先檢查：

- 工作樹是乾淨的，
- 分支名稱沒被用掉，
- 要改的檔案，自從被複製之後，在主分支上都沒有動過。

只要有一個倉庫沒通過檢查，就什麼都不寫。兩個人、或兩個任務改同一個檔案，也是在這裡被發現的：由程式在這裡發現，不是之後在審查裡。

### 為什麼批准要在終端機裡打

聊天裡的確認框，可以被「這個會話都允許」關掉。人在終端機裡打的一段碼，不行。批准指令需要真正的終端機，agent 去執行它時會被拒絕。有三點讓這件事成立：

1. **終端機不是牆**。檢查「這是終端機」不是安全邊界；有心的程式可以假裝。
2. **hook 是第二條腿**。它是一段程式碼，直接拒絕 agent 去執行批准指令，而且它在 agent 碰不到的地方，像 [保護規則本身的檔案](4-3-guardrails.html) 說的。如果這個 hook 不見了，或 agent 能編輯它，批准就只是客氣的請求。這個設計站在兩條腿上，單靠任何一條都不夠。
3. **拒絕必須撐過錯誤**。執行層在自己壞掉時會放行呼叫（[把執行層當軟體來設計](4-4-enforcement-design.html)）。所以拒絕批准指令，要放在那份「即使 hook 出錯也必須擋住」的短清單上；不然這條腿剛好在最需要的時候斷掉。

內容在別處讀。計畫和 diff 在終端機裡很難讀，所以人在編輯器裡讀，終端機只顯示檔案路徑和要打的碼。讀和批准是兩個動作，這是故意的。

### 把批准綁到讀過的內容

假設人批准了一份計畫，然後 agent 改了這份計畫。批准還有效嗎？不應該。所以人要打的碼，是從計畫的內容算出來的：一個 hash，一種指紋，改一個字就會變。批准之後計畫變了，批准就對不上，門就又關上了。

寫回也一樣：批准屬於當時顯示的那份確切的 diff。「綁定到被批准的那一份計畫」就是這個意思。沒有這一步，人批准的是一樣東西，agent 交出的卻是另一樣。

### 門上的快照

計畫被批准時、每次檢查之前、寫回的試跑之前，都會自動存一份工作的副本（快照）。哪裡壞了，那個時刻的狀態找得回來。在我的設定裡，預設保留 14 天。

寫入多個倉庫的途中失敗，不會自動回復。任務進入「寫了一部分」的狀態，由人執行恢復。我選擇不去猜一個自動的還原。

### 沒有這些機制

用手也能養成這個習慣。叫 agent 動手之前，先讀計畫。提交之前，先讀 diff。對會寫入的工具，不要勾「這個會話都允許」。上面的機制，只是確保你累了、或不在的時候，這些事也會發生。

### 多輪

寫回之後，同一個目標可能再回來：reviewer 找到缺陷，或有人要求改動。新的一輪開始。舊的工作移到一旁，寫新的計畫，兩道門都再走一次。不同的目標是新任務。

在其他環境測試，不算另一輪。agent 在那裡什麼都不能執行，要由人來。那會成為自己的一個*測試*類任務：agent 寫說明，等人給結果，再判斷結果。測試失敗，就回到開發任務，成為新的一輪。

## 代價和陷阱 {#costs-and-traps}

- **它會讓 agent 停下來，所以工作變慢**。每道門要人讀一次、打一個指令。這是代價。門放得到處都是，人就不讀了，又回到第一百個框。
- **只有拒絕的 hook 在的時候才成立**。拒絕批准指令的 hook 如果被移除、被編輯或失敗，能執行指令的 agent 就可能自己批准。照 [保護規則本身的檔案](4-3-guardrails.html) 的規則保護這個 hook，並且測試它。測試很便宜：叫 agent 去執行批准，確認它被拒絕。
- **人可能不讀就批准**。把批准綁到計畫，擋得住掉包，擋不住累了的「好」。讓 diff 短、門少，會有幫助；這裡沒有任何東西能消除這個問題。一個我還沒試過的想法，是記下每次批准花了多久、diff 有多大：大 diff 卻很快就批准，是值得看一眼的訊號。
- **終端機檢查不是鎖**。把它當成防意外的措施，不是防攻擊的（[有些東西根本不給](4-5-least-privilege.html)）。
- **跨倉庫沒有自動還原**。部分失敗需要人處理。

## 什麼時候可以刪掉 {#when-to-delete-it}

打出來的批准機制存在，是因為平台自己的確認可以在一個會話裡被關掉，也沒辦法綁到計畫的 hash。如果平台提供一種批准：agent 無法關掉、會記錄當時顯示的內容、內容一變就失效，那就用它，把我的拿掉。

想法會留下：在三種地方放一個人，而且批准只屬於他讀過的內容。

## 在你自己的環境試試 {#try-it}

不用裝 harness。在你自己的倉庫裡打開 agent，貼上：

::: prompt
走一遍在這個專案裡，工作怎麼從這個 agent 的改動走到主分支或正式環境：pull request、必要的審查、CI、部署步驟，以及 agent 工具裡的任何批准提示。對每一個花錢、給權力或不能反悔的點，說明誰批准、走什麼管道，以及 agent 能不能自己給出或跳過那個批准。也說明：批准給出之後，如果改動又被編輯，批准還算不算數。不要改任何檔案。
:::

## 在 harness 裡探索 {#explore}

兩道門、打出來的批准、計畫的 hash 和快照，都在 Copilot Harness 裡執行。照上面的說明準備好之後，輸入：

::: prompt
/harness-rookie-wondering 我讀完了「兩道門：人在哪裡批准」這一章。請教我這個 harness 怎麼做這兩道批准（主題 9，以及講權限的主題 8）：為什麼要在終端機裡打、批准綁定到什麼，以及哪個 hook 拒絕 agent。帶我看一個真實的任務怎麼走過兩道門，並且畫出來。
:::

它一次教一小塊，停下來確認你跟得上，然後和你一起打開檔案。
