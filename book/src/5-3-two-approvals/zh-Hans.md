读这一章之前，你要读过[询问不是限制](4-2-ask-vs-refuse.html)和[保护规则本身的文件](4-3-guardrails.html)：为什么“先问我”不是限制，以及为什么 agent 不能有权编辑规则。

## 一句话 {#in-one-sentence}

在花钱、授权、无法撤销的地方放一个人。让审批走 agent 够不着的渠道，并把它绑定到被批准的那份计划上，一字不差。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定哪些地方必须由人审批：花钱、授权、无法撤销的地方，别的地方都不用。审批必须走 agent 够不着的渠道，并且只属于人读过的那份计划或改动。
- **风险**：确认框可以在整个会话里被关掉，而没有人注意到；agent 自己能给的审批，不是审批。疲惫的人仍然可能不读就批；把审批绑定到内容上，能防住被调包，防不住草率地点“同意”。
- **做对的代价**：每道关卡让人读一次、敲一条命令。关卡太多，人就不读了。在我的配置里，关卡处的快照默认保留 14 天。
- **可以问团队**：“我们的流程里，哪些审批是 agent 能自己给、或者能关掉的？计划事后改了，审批还算数吗？”

## 问题 {#problem}

你想让人批准重要的步骤。最顺手的工具，是 agent 工具弹出的确认框：“允许吗？”它不太管用，有两个原因。

第一，人会点“允许”。到第一百个框的时候，他们已经不读了（见[询问不是限制](4-2-ask-vs-refuse.html)）。第二，很多工具让你勾选“本次会话都允许”，勾了之后框就再也不出现了。你依赖的审批没了，也没有任何东西告诉你。

第三个问题更微妙。假设审批是人敲的一条命令。如果 agent 能运行命令，它也能敲这条命令。agent 能自己给的审批，不是审批。

所以问题是：把人放在哪里，以及怎样让他的“同意”成为 agent 造不出来、也重复用不了的东西。

## 原理 {#how-it-works}

### 把人放在哪里

人的注意力是系统里最稀缺的东西。只把它花在三类点上，别的地方不花：

- **花钱的点**。比如启动一次昂贵的运行。
- **授权的点**。让 agent 往共享仓库里写。
- **无法撤销的点**。一旦做了就收不回来的事。

任务文件夹里的一切，重做起来都很便宜，所以 agent 在那里可以随便干（见[管任务，不管对话](5-1-tasks.html)）。改真实仓库的任务有两个这样的点。我把每一个叫一道**关卡**：人批准之前，任务过不去。

::: figure 5-3-two-gates

### 关卡 1：批准计划

agent 写出需求和计划，然后停下。人读计划，之后才批准。在此之前，agent 可以起草、可以读；不能开始改工作文件。

这道关卡的意义在成本。一份错的计划，作为一段文字改起来很便宜，作为一个做完的改动改起来很贵。在我的配置里，计划还建立在已确认的需求之上（见[需求由 agent 写，人确认](5-2-requirements.html)），所以一次审批可以同时确认两者。

### 关卡 2：批准写回

agent 已经在任务文件夹里做完了改动，检查也跑过了。现在结果要进入真实的仓库。把它复制过去，就是**写回**。人读确切的 **diff**：将要改动的那些行的清单。然后批准。

写回时，结果进入仓库的一个新分支，并且不提交。它从不直接碰主分支。而且在写之前，代码会检查：

- 工作树是干净的，
- 分支名没被占用，
- 要改的文件在复制之后，没有在主分支上变动过。

只要有一个仓库没通过检查，就什么都不写。两个人、或者两个任务改同一个文件，也是在这里发现的：由这里的程序发现，而不是以后在评审里。

### 为什么审批要在终端里敲

聊天里的确认框，可以被“本次会话都允许”关掉。人在终端里敲的一个码，关不掉。审批命令需要一个真正的终端，agent 来运行它，就会被拒绝。有三点让这一条站得住：

1. **终端不是一堵墙**。检查“这是个终端”不是安全边界；有心的程序可以假冒。
2. **hook 是第二条腿**。它是一段代码，会拒绝 agent 运行审批命令的任何尝试，而且它在 agent 够不着的地方，正如[保护规则本身的文件](4-3-guardrails.html)所讲。如果这个 hook 没了，或者 agent 能编辑它，审批就只是一个客客气气的请求。这个设计靠两条腿站着，单靠哪一条都不够。
3. **拒绝必须经得起出错**。执行层在自己出故障时会放行调用（见[把执行层当软件来设计](4-4-enforcement-design.html)）。所以对审批命令的拒绝，应该放在那份即使 hook 出错也必须拦下的短清单上；否则这条腿恰好在最需要它的时候断了。

内容在别处读。计划和 diff 在终端里不好读，所以人在编辑器里读，终端只显示文件路径和要敲的码。读和批准是有意分开的两个动作。

### 把审批绑在读过的内容上

假设人批准了一份计划，然后 agent 编辑了这份计划。批准还有效吗？不应该有效。所以人要敲的那个码，是从计划的内容算出来的：一个哈希，一个指纹，改一个字符它就变。批准之后计划变了，批准就对不上了，关卡重新关上。

写回也一样：批准属于展示过的那份确切的 diff。这就是“绑定到被批准的那份计划上，一字不差”的意思。没有它，人批准的是一样东西，agent 交付的是另一样。

### 关卡处的快照

计划被批准时、每次检查之前、写回试运行（dry run）之前，会自动保存一份工作的副本（快照）。出了问题，那一刻的状态能找回来。在我的配置里，它们默认保留 14 天。

往多个仓库写的中途失败，不会自动回滚。任务进入“部分写入”状态，由人来做恢复。我选择不去猜一个自动撤销。

### 没有这套机制也行

这个习惯用手工也行。叫 agent 动手之前，先读计划。提交之前，先读 diff。对会写东西的工具，别勾“本次会话都允许”。上面的机制只是保证，在你累了或者不在的时候，这些事也照样发生。

### 好几轮

写回之后，同一个目标可能再来：reviewer 发现了缺陷，或者有人要求改动。新的一轮开始。旧的工作挪到一边，写新的计划，两道关卡再走一遍。不同的目标，是一个新任务。

在其他环境里测试，不算另一轮。agent 在那里运行不了任何东西；由人来跑。这成为一个单独的任务，类型是*测试*：agent 写说明，等人给结果，再判断结果。测试失败，作为新的一轮回到开发任务。

## 代价和坑 {#costs-and-traps}

- **它会拦住 agent，所以会拖慢工作**。每道关卡让人读一次、敲一条命令。这就是价钱。如果到处设关卡，人就不读了，你又回到了第一百个框。
- **只有拒绝用的 hook 在，它才成立**。如果拒绝审批命令的 hook 被删了、被改了或者出故障了，能运行命令的 agent 就可能自己批准自己。按[保护规则本身的文件](4-3-guardrails.html)里的规则保护这个 hook，并测试它。测试很便宜：让 agent 运行审批，检查它被拒绝。
- **人可以不读就批**。把审批绑到计划上，能防住被调包，防不住疲惫的“同意”。让 diff 短一点、关卡少一点有帮助；这里没有任何东西能消除这个问题。有一个我没试过的想法：记录每次审批用了多久、diff 有多大：对一个大 diff 飞快地批，是值得留意的信号。
- **终端检查不是锁**。把它当作防意外的守卫，不是防攻击的（见[有些东西根本不给](4-5-least-privilege.html)）。
- **跨仓库没有自动撤销**。部分失败需要人来处理。

## 什么时候可以删掉 {#when-to-delete-it}

敲码审批的机制之所以存在，是因为平台自己的确认可以在一个会话里被关掉，也没法绑到计划的哈希上。如果平台提供这样的审批：agent 关不掉、会记录展示过什么、内容一变就失效，那就用它，把我的去掉。

想法留着：在三类点上放一个人，审批只属于他读过的那份确切内容。
