读这一章之前，你要读过[询问不是限制](4-2-ask-vs-refuse.html)和[保护规则本身的文件](4-3-guardrails.html)：为什么“先问我”不是限制，以及为什么 agent 不能有权编辑规则。

## 一句话 {#in-one-sentence}

在花钱、授权、无法撤销的地方放一个人。让审批走 agent 够不着的渠道，并把它绑定到被批准的那份计划上，一字不差。

## 写给管理者 {#for-leaders}

- **要拍板的事**：哪些地方必须由人审批。只放在花钱、授权、无法撤销的地方，别处都不放。审批必须走 agent 够不着的渠道，而且只属于人读过的那份计划或那次改动。
- **风险**：确认框可以在整个会话里被关掉，没有人会注意到；agent 自己能给的审批，也算不上审批。就算审批是真的，也有软肋，因为人累了照样可能不读就批。把审批绑定到内容上，能防住调包，防不住随手点的“同意”。
- **做对的代价**：每道关卡要人读一遍、敲一条命令，关卡一多，人就不读了。在我的配置里，关卡处的快照默认保留 14 天。
- **可以问团队**：“我们的流程里，哪些审批是 agent 能自己给、或者能关掉的？计划事后改了，审批还算数吗？”

## 确认框为什么算不上审批 {#problem}

你希望重要的步骤由人来批准，而最顺手的工具就摆在眼前：agent 工具弹出来的确认框，问你“允许吗？”可它不太管用，原因有两个。一是人会点“允许”，到了第一百个框，早就不读了（见[询问不是限制](4-2-ask-vs-refuse.html)）。二是很多工具可以勾选“本次会话都允许”，勾了之后这个框再也不会出现。你指望的审批就这样没了，也没有任何东西提醒你。

还有第三个问题，更不容易察觉。假设审批不是一个框，而是人敲的一条命令。可如果 agent 能运行命令，它也能敲这条命令。一个 agent 自己就能给出的审批，算不上审批。

那么，人该放在哪里？他的“同意”又怎样才能成为 agent 既造不出来、也没法重复使用的东西？

## 把人放在哪里，又怎样让他的“同意”算数 {#how-it-works}

### 把人放在哪里

第一个问题的答案很简单。人的注意力是整个系统里最稀缺的东西，所以只把它花在三类点上，别处一概不花。有的点要花钱，比如启动一次昂贵的运行；有的点会授权，比如让 agent 往共享仓库里写东西；还有的点无法撤销，一旦做了，就再也收不回来。

agent 的大部分工作都不属于这三类，因为任务文件夹里的一切重做起来都很便宜，agent 在那里可以放手去干（见[管任务，不管对话](5-1-tasks.html)）。但一个要改真实仓库的任务，会碰上两个这样的点。我把每一个都叫作一道**关卡**，因为人批准之前，任务过不去。

::: figure 5-3-two-gates

### 关卡 1：批准计划

第一道关卡设在任何工作文件被改动之前。agent 写出需求和计划后就停下来，在人读完计划、批准之前，它可以起草、可以读，但还不能动手改。

之所以停在这里，是为了成本。一份错的计划，还停留在一段文字的时候改起来很便宜，等它变成一个做完的改动再改就贵了。在我的配置里，计划还建立在已经确认的需求之上（见[需求由 agent 写，人确认](5-2-requirements.html)），所以一次审批可以把两者一起确认。

### 关卡 2：批准写回

到了第二道关卡，agent 已经在任务文件夹里做完改动，检查也跑过了，剩下的就是把结果复制到真实的仓库里，这一步叫**写回**。在写回之前，人要读那份确切的 **diff**，也就是将要改动的那些行的清单，然后再批准。

就算批准了，写回也不会直接进主分支。结果会进入仓库的一个新分支，并且不提交。而且在真正写之前，代码会先检查：

- 工作树是干净的，
- 分支名没被占用，
- 要改的文件在复制之后，没有在主分支上变动过。

只要有一个仓库没通过检查，就什么都不写。两个人或者两个任务改了同一个文件，也是在这里被发现的，发现它的是这里的程序，而不是后来的评审。

### 为什么审批要在终端里敲

再看第二个问题的前一半：怎样让一声“同意”成为 agent 造不出来的东西？聊天里的确认框可以被“本次会话都允许”关掉，人在终端里敲的一个码却关不掉，所以审批被做成一条需要真正终端的命令。不过，这个设计是靠两条腿站着的，终端只是其中一条。

可光靠终端，算不上一堵墙。检查“这是不是终端”并不是安全边界，因为有心的程序完全可以假冒一个终端。那要是真有程序假冒，靠什么拦住它？

靠的是第二条腿，也就是 hook。agent 只要试图运行审批命令，这段代码就会直接拒绝。它必须放在 agent 够不着的地方，正如[保护规则本身的文件](4-3-guardrails.html)所讲的那样：如果这个 hook 没了，或者 agent 能编辑它，审批就只剩一个客客气气的请求。两条腿，单靠哪一条都不够。

而 hook 本身出了错的时候，也得照样拒绝。执行层在自己出故障时会放行调用（见[把执行层当软件来设计](4-4-enforcement-design.html)），所以对审批命令的拒绝，应该列进那份即使 hook 出错也必须拦下的短清单。不然的话，这条腿恰恰会在最需要它的时候断掉。

这并不是说人要在终端里读计划。计划和 diff 在终端里很难读，所以人是在编辑器里读的，终端只显示文件路径和要敲的码。读和批准是两个有意分开的动作。

### 把审批绑在读过的内容上

剩下的是后一半：重复使用。假设人批准了一份计划，之后 agent 又改了这份计划，那这个批准还有效吗？不应该有效。正因为这样，人要敲的那个码是从计划的内容算出来的。它是一个哈希，相当于一枚指纹，哪怕只改一个字符它也会变；所以批准之后计划一变，批准就对不上了，关卡也随之重新关上。

同样，写回的批准只属于当时展示的那份确切的 diff。所谓“绑定到被批准的那份计划上，一字不差”，说的就是这个。没有这一步，人批准的是一样东西，agent 交出来的可能是另一样。

### 关卡处的快照

关卡除了决定什么能往下走，还负责把工作存下来。计划被批准时、每次检查之前、写回试运行（dry run）之前，系统都会自动保存一份工作的副本（快照），这样出了问题，就能把那一刻的状态找回来。在我的配置里，快照默认保留 14 天。

不过，能找回某个状态，不等于能自动退回去。往多个仓库写到一半失败了，并不会自动回滚，任务会进入“部分写入”的状态，由人来做恢复。自动撤销只能靠猜，我宁可不做。

### 好几轮

任务不一定在写回之后就结束。同一个目标可能再回来，比如 reviewer 发现了缺陷，或者有人要求改动，这时就开始新的一轮：旧的工作挪到一边，重新写计划，两道关卡再走一遍。如果是不同的目标，那就是一个新任务。

在其他环境里测试，看起来像是又一轮，其实不是。agent 在那里什么都运行不了，只能由人来跑，所以这件事另外开成一个*测试*类的任务：agent 写好说明，等人给出结果，再判断结果。测试失败的话，就作为新的一轮回到开发任务。

### 没有这套机制也行

关卡背后的习惯，手工也做得到：叫 agent 动手之前先读计划，提交之前先读 diff，对会写东西的工具别勾“本次会话都允许”。上面这套机制，只是保证你累了或者不在的时候，这些事也照样会发生。

## 关卡要付出什么，还会在哪里失守 {#costs-and-traps}

最直接的代价是时间。每道关卡都要让 agent 停下来，等人读一遍、敲一条命令，这是这套设计要付的价。可要是到处都设关卡，人就不读了，你又回到了第一百个框。

这套关卡也只有在负责拒绝的 hook 还在时才成立。如果拒绝审批命令的 hook 被删了、被改了，或者出了故障，能运行命令的 agent 就可能自己批准自己。所以要按[保护规则本身的文件](4-3-guardrails.html)里的规则保护好这个 hook，并且测试它。测试很便宜，让 agent 去运行审批，看它是不是被拒绝就行。

就算 hook 好好的，人也可能不读就批。把审批绑到计划上，能防住调包，却防不住一句疲惫的“同意”。让 diff 短一点、关卡少一点会有帮助，但这里没有任何东西能消除这个问题。有一个我还没试过的想法，是记下每次审批用了多久、diff 有多大，因为对一个很大的 diff 飞快地批下来，是值得留意的信号。

剩下两条限制前面已经说过：终端检查只防意外，防不了攻击（见[有些东西根本不给](4-5-least-privilege.html)）；跨仓库的部分失败，仍然要人来处理。

## 什么时候可以删掉敲码审批 {#when-to-delete-it}

整套设计里，敲码审批是跟平台绑在一起的那一部分。它之所以存在，是因为平台自己的确认可以在一个会话里被关掉，也没法绑到计划的哈希上。如果哪天平台提供的审批 agent 关不掉、会记录展示过什么、内容一变就失效，那就用平台的，把我的这套去掉。

不管怎样，想法会留下来：在三类点上放一个人，而审批只属于他读过的那份确切内容。

## 在你自己的环境里试试 {#try-it}

::: prompt
梳理一下，在这个项目里，工作是怎么从这个 agent 的改动走到主分支或生产环境的：pull request、必需的评审、CI、部署步骤，以及 agent 工具里的各种审批提示。对每一个花钱、授权或无法撤销的点，说清楚由谁批准、走什么渠道、agent 能不能自己给出或跳过这个审批。另外说一下：如果审批给出之后改动又被编辑了，这个审批还算不算数。不要修改任何文件。
:::
