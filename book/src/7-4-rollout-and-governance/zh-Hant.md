讀這一章，你需要讀過 [保護規則本身的檔案](4-3-guardrails.html)、[指令與 skill：只載入需要的](3-3-instructions-and-skills.html) 和 [記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)。

## 一句話 {#in-one-sentence}

把 agent 設定推給一個團隊，主要是問：誰擁有規則，誰審查對規則的改動。只有紀錄顯示規則撐得住的時候，才擴大範圍。

## 給主管 {#for-leaders}

- **要做的決定**：為每一層規則指定一個負責人，要求任何改動都有第二位審查者，並先講好：要符合什麼條件，設定才能交給下一個團隊。
- **風險**：沒有負責人，規則會漂成每人一份，過期的規則會留著。我沒有團隊的數據，所以給不出數字。這一章給的是我會用的設計，不是量過的結果。
- **做對的成本**：主要是人的時間：核心和每個領域的負責人，以及審查者在每次改規則時花的時間。設定本身加的很少。
- **可以問團隊**：「這條規則誰負責，上一次改它是誰審查的？如果它是錯的，紀錄會顯示什麼？」

## 問題 {#problem}

適合一個人的設定，只是碰巧有一個負責人：那個人。他寫規則，規則錯了他會發現，每一條為什麼在那裡他也知道。把同樣的檔案交給十個同事，會出三個問題，沒有一個和工具有關。

- **副本會漂移**。每個人為自己的任務，在自己的副本裡修規則。一個月後有十個版本，沒有人說得清哪一個是「規則」。
- **沒有人負責一條規則**。去年還對的規則，現在錯了，每個人都學會了不理它。規則會過期，除非有人用心力去修剪它。
- **一個改動弄壞別人的事**。為一個專案收緊一條規則，擋住了另一個團隊的正常工作。做改動的人，永遠看不到傷害。

第四個擔心是主管的：推出去之後，你怎麼知道 agent 做了什麼？這需要一份有人在看的紀錄。

我該老實說我自己的位置。我的設定是為一個人建的，我沒有帶著量測做過團隊推行。下面是我會用的設計，建在設定現在已經做到的事上（我能指出來的部分），以及我加任何東西之前問的問題上。只是提議的地方，我會說明。

## 原理 {#how-it-works}

### 誰擁有規則

「誰擁有規則」沒有單一的答案，因為規則不都一樣。我把它們分成三層，看一條規則錯了會傷到誰。

::: figure 7-4-rule-layers

- **核心**。每個任務都必須遵守的短規則，以及執行它們的檔案（[保護規則本身的檔案](4-3-guardrails.html) 裡的圍欄）。這裡錯了，影響所有人。它有一、兩位指名的負責人，其他人不改它。
- **團隊層**。領域的 skill、團隊的知識庫（程式碼的索引，見 [知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)），以及對所有人都一樣的設定，例如哪些路徑任何 agent 都不能碰。每個領域有一位負責人：懂那一塊程式碼的人。部署的 skill 屬於負責部署的人。
- **個人層**。使用者名稱、語言、你的倉庫放在你機器上的哪個資料夾。它屬於個人。它不提交，因為裡面是只存在於一台電腦的路徑。

在我的設定裡，有兩個機制讓這件事做得起來。團隊不用那個工具，也可以拿走這個想法。

**override 是放在預設旁邊的一個小設定，不是預設的副本**。它只列出你要改的。想多加一個禁止路徑的人，寫一行；他不用分叉整份規則檔。所以團隊的客製化，只是幾行誰都讀得懂的東西，核心升級時也不會和它衝突。在我的實作裡，核心的護欄不能被 override 移除：如果 override 把它們拿掉，引擎會放回去並回報錯誤。設定的健康檢查也會列出每個 override 改了什麼，審查者就有一個地方可以看。

**一條規則有一個主要來源**。同一條規則寫在三個檔案裡，就是副本漂移的起點（[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)）。指定負責人的時候，指定給來源。有兩個家的規則有兩個負責人，也就是沒有。

### 誰審查對規則的改動

規則檔不是文件。它是 agent 服從的東西，所以改它，就是改團隊的 agent 明天會做什麼。我把它當程式碼，有四個習慣。

1. **agent 不改規則**。這些檔案被圍起來。由人為一個會話打開圍欄，做改動，再關上，之後在 git 裡讀 diff（[保護規則本身的檔案](4-3-guardrails.html)）。這樣會留下一份別人可以審查的 diff。
2. **作者不是唯一的審查者**。那一層的負責人讀這個改動，另一位沒參與討論的人也讀。把規則的改動，當成攻擊者很想做的程式碼改動：一個草率或惡意的 pull request，或一個共用的 skill 或知識庫檔案，帶著 agent 會當成自己的指令讀進去的內容，都是入口（[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)）。講好誰可以批准例外，以及負責人離開時誰接手那一層。只有作者看得懂的規則，對 agent 也是差的規則：它是從零開始讀的。
3. **審查要問六個問題**。這是我在為自己的設定加任何東西之前問的問題。
   - 這防止什麼失敗？有真實的例子、紀錄或量測嗎？
   - 平台已經做了嗎？有人讀過它現在的文件嗎？
   - 它花多少，在上下文、token 和時間上？
   - 它是用文字寫的請求，還是程式碼裡的規則（[提示裡的規則只是請求](4-1-requests-and-rules.html)）？對這個傷害來說，選對了嗎？
   - 什麼時候可以刪掉？要變成什麼樣？
   - 如果我們換到別的工具，學到的東西還有用嗎？
4. **說「這有幫助」，需要同樣的任務前後各跑一次**。如果這個改動是要改善結果，審查就該要求在固定任務上的前後比較（[固定的任務，用腳本打分](6-3-eval-tasks.html)），不是一個意見。

還有一條規則對審查有幫助。**只寫模型會做錯的**。模型本來就會照做的一行，花上下文，還讓審查者多讀一行。說不出它防止哪個錯誤，就不要寫。

### 稽核：設定留下什麼

沒在場的主管，需要回答「agent 做了什麼，誰讓它做的？」這就是稽核。只有設定寫下 agent 控制不了的紀錄，它才行得通，所以下面是我的設定寫下的東西。前五項已經做了；後兩項是想法。

- **每次工具呼叫一行紀錄**。呼叫的種類、放行還是拒絕、哪條規則拒絕的，以及花了多久。沒有參數，也沒有 prompt 的文字，只有被拒絕的呼叫會保留路徑和指令（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)）。
- **拒絕，以及它的計數**。一個統計指令，加總 prompt、呼叫和拒絕，以及設定的哪個部分拒絕的。
- **批准**。每個任務的批准，存成只有人能建立的紀錄，任務的報告會顯示兩道批准的時間。
- **任務報告**。任務結束時由程式碼寫出：問了什麼、改了什麼、有多少檢查和每個檢查的結論，以及什麼被拒絕了（[一份五分鐘讀得完的報告](6-2-task-report.html)）。
- **規則的改動**。agent 不能改規則檔。由人在一個會話裡改，這個會話裡記下的每個呼叫都標成 admin，而改動是 git 裡的一份 diff。
- **想法，沒做：誰批准的**。批准的紀錄帶有時間。它們有沒有帶人名，我沒有確認，而我的設定只有一位使用者，所以我從沒需要過。團隊需要。
- **想法，沒做：紀錄放在同一個地方**。在我的設定裡，紀錄留在每台電腦上，不放進 git。我沒有做任何跨團隊收集它們的辦法。

誰來看，多久看一次？在我自己的設定裡，我在一次運行失敗和我改規則的時候讀紀錄，不是每天（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)）。對團隊，我會加一個簡短的例行，當作提議：每一層的負責人，每隔一陣子看一下拒絕的計數，並讀每次規則改動的 diff。沒有人負責的紀錄，不是稽核的軌跡。

### 分階段推行

先鋪開、之後再補審查，就是得到十份副本的辦法。所以我會分階段擴大，並為每個階段寫下：要符合什麼條件才能進入。

::: figure 7-4-rollout-stages

1. **一個團隊，只有核心**。挑一個想要這套設定、自己擁有程式碼的團隊。從第一天就把核心交給一、兩位負責人。*進入條件*：團隊要它。現在還不需要證明什麼。
2. **加上團隊層**。領域的 skill、共用設定和知識庫，在團隊用核心夠久、知道自己需要什麼之後再加。*進入條件*：核心有指名的負責人，而且負責人能靠紀錄，不是靠 agent 的摘要，說出最近一個任務發生了什麼。
3. **開放給下一個團隊**。*進入條件*：審查的習慣在第一個團隊行得通。每次規則改動都有第二位審查者，diff 有人讀，任何要改善結果的改動，都附有固定任務上的前後比較。
4. **所有人，包括沒有要求的同事**。*進入條件*：紀錄顯示規則撐得住。訊號在下一節。

這些條件是我的提議。我沒有在團隊上跑過，而門檻（多久才算「夠久」）要你自己定。

### 你怎麼知道它有效

我沒有團隊的數字，所以這是我會看的，不是我量到的：

- **人們是開任務，還是繞過設定**？開了多少任務，對比在一般對話裡做的工作。
- **規則拒絕什麼，每週都是同樣的東西嗎**？一條一直拒絕同樣正常工作的規則，是該修的規則（[詢問不是限制](4-2-ask-vs-refuse.html)）。
- **批准之後，多常需要返工**？批准後返工，表示那道門被看得太快。
- **本機的 override 有多少，它們一致嗎**？見下面的分叉陷阱。

第 4 階段要求這些都不再變動：拒絕的數量穩定，而且多半是你想要它拒絕的，返工少，override 也少。「紀錄顯示規則撐得住」，就是這個意思，沒有更大的意思。

### 這本書的證據有多強

讀這本書其餘的部分時，請記住這些限制。

- **一個平台**。一切都是在 VS Code Copilot 上建立和試的。別的工具有對應的東西，但我沒有測過。
- **一個人的 harness**。我建了它，我用它。沒有別人測過，我也不是它的中立評審。
- **沒有團隊數據，也沒有事故**。我沒有量過採用情況，也沒有團隊裡規則失敗的紀錄。我唯一量過的比較，是四個任務、各跑一次（[慎用子 agent](2-3-subagents.html)）。
- **數字都附著它的條件**。一章給出數字時，旁邊會給運行次數和設定，讓你看出該信多少。

所以請把這本書用在它的問題和設計上，不要當成證明。從裡面拿一個設計，說出你預期它做到什麼，再在你自己的任務上檢查（[固定的任務，用腳本打分](6-3-eval-tasks.html)、[一次運行證明不了什麼](6-4-variance.html)）。你的數字應該取代我的。

## 代價和陷阱 {#costs-and-traps}

**負責人變成瓶頸**。如果每次改規則都要經過兩個人，人們就不再提改動，轉而留私人副本，也就是你本來要解決的問題。核心要小，讓需要嚴格流程的改動很少，團隊層則讓它走得快。

**審查規則不風光**。沒有人會因為一條沒加的規則被感謝。把負責人的時間排進某個人的計劃，不然審查會變成蓋章。

**審查者必須能判斷這條規則**。一條關於部署路徑的規則，讓從沒部署過的人審查，只是拼字檢查。

**太多本機 override，就是分叉**。如果多數使用者都帶著同一個 override，它就屬於團隊層。時不時看一下 override，把常見的升上去。

**紀錄裡有關於人的事**。一份每個呼叫的紀錄，會說某人什麼時候工作，以及他要 agent 碰什麼。在集中收集之前，先決定誰可以讀它，以及保留多久。

**階段的門，只有紀錄那麼可靠**。紀錄裡的一個洞（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)），會讓「規則撐得住」看起來是真的，其實並不知道。

**我沒有團隊數據**。三層、審查的習慣、稽核的例行和各階段，是建在一個人使用上的設計。我沒有量過採用情況，也沒有追蹤團隊裡誰改了什麼。把它們當成要檢查的起點，不是結果。

## 什麼時候可以刪掉 {#when-to-delete-it}

三層的劃分存在，是因為平台給你檔案，卻沒有辦法擁有它們。如果你的平台讓組織集中發布規則，並附帶自己的審查、稽核和推行，核心層就用它，只留團隊層自己做。Copilot 今天在這方面提供什麼，我沒有確認，所以在自己動手之前，先看它目前的文件。

審查的問題不會退役。它們是你決定任何規則、skill 或 agent 值不值得存在的辦法。

## 在 harness 裡探索 {#explore}

override、健康檢查、被圍起來的規則檔和紀錄，都在 Copilot Harness 裡執行。harness 可以用真實的檔案帶你看。照上面的說明準備好之後，輸入：

::: prompt
/harness-rookie-wondering 我讀完了「落地與治理」這一章。請教我這個 harness 怎麼讓團隊客製化卻不用分叉（policy override，和列出它們的健康檢查），怎麼保護它自己的規則檔，以及它的紀錄和報告記下什麼。和我一起打開真實的檔案，讓我看團隊的改動該放在哪裡，不該放在哪裡。
:::

它一次教一小塊，停下來確認你跟得上，然後和你一起打開檔案。
