读这一章之前，需要先读过[保护规则本身的文件](4-3-guardrails.html)、[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)和[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)。

## 一句话 {#in-one-sentence}

把一套 agent 配置推广到团队，主要是两个问题：规则归谁管，谁来审查对规则的改动。只有日志显示规则站得住，才往外放开。

## 写给管理者 {#for-leaders}

- **要拍板的事**：给每一层规则指定负责人，要求对规则的任何改动都有第二个人审查，并约定配置推给下一个团队之前必须满足什么条件。
- **风险**：没有负责人，规则会漂移成每人一份，过期的规则也留在那里。我没有团队的数据，所以给不出数字。这一章讲的是我会采用的设计，不是量出来的结果。
- **做对的代价**：主要是人的时间：核心层和每个领域的负责人，以及审查者在每次规则改动上花的时间。配置本身增加的很少。
- **可以问团队**：“这条规则归谁管？上一次改动是谁审查的？如果它是错的，日志会显示什么？”

## 问题 {#problem}

适合一个人的配置，只有一个负责人，而且是碰巧的：就是他自己。规则他来写，规则错了他会发现，每条为什么在那里他都清楚。把同样的文件交给十个同事，会出三个问题，都和工具无关。

- **副本会漂移**。每个人都为自己的任务，在自己的副本里改规则。一个月后有十个版本，没人说得清哪一个是“规则”。
- **没人负责某条规则**。去年还对的规则，现在错了，大家都学会了无视它。除非有人专门花精力去修剪，否则规则会过期。
- **一次改动弄坏别人**。为一个项目收紧一条规则，会挡住另一个团队的正常工作。做改动的人永远看不到这些破坏。

还有第四个担心，是管理者的：推广之后，你怎么知道 agent 做了什么？这需要一份有人会去看的记录。

我要说清楚自己的位置。我的配置是为一个人搭的，我没有带着测量去做过团队落地。下面讲的，是我会采用的设计，它根据这套配置现在能做的事（我能指出来的那些部分）和我在加任何东西之前问的那些问题搭出来。只是建议的地方，我会说明。

## 原理 {#how-it-works}

### 规则归谁管

“规则归谁管”没有唯一的答案，因为规则不都一样。我按“一条规则错了，谁受伤”，把它们分成三层。

::: figure 7-4-rule-layers

- **核心层**。每个任务都必须遵守的简短规则，以及执行它们的文件（[保护规则本身的文件](4-3-guardrails.html)里的围栏）。这里出错，影响所有人。它有一两个指定的负责人，别人不改。
- **团队层**。领域 skill、团队的知识库（代码的索引，见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)），以及对所有人都一样的设置，比如哪些路径任何 agent 都不许碰。每个领域有一位负责人：最了解那部分代码的人。关于部署的 skill，归负责部署的人。
- **个人层**。用户名、语言、你的仓库在你机器上所在的文件夹。它归个人。不提交，因为里面的路径只在一台电脑上有效。

在我的配置里，有两个机制让这件事行得通，团队不用这个工具，也可以照搬思路。

**override 是放在默认配置旁边的一小份配置，不是默认配置的副本**。它只列出你改的东西。想多禁止一个路径的人，写一行就行，不用把整个规则文件 fork 出去。这样，团队的定制就只有几行，谁都读得懂，核心层升级时也不会和它冲突。在我的实现里，核心层的护栏不能被 override 删掉：如果 override 把它们去掉了，引擎会把它们放回去，并报告一个错误。配置的健康检查还会列出每个 override 改了什么，这样审查者有一个地方可看。

**一条规则只有一个主来源**。同一条规则写在三个文件里，副本就是这么漂移起来的（[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)）。分派负责人时，要分派给来源。一条规则有两个家，就有两个负责人，也就等于没有。

### 谁来审查对规则的改动

规则文件不是文档。它是 agent 要服从的东西，所以改它，就是改团队的 agent 明天会做什么。我像对待代码那样对待它，有四个习惯。

1. **agent 不改规则**。这些文件被围起来了。由人为一次会话打开围栏，做完改动，再关上，之后在 git 里读 diff（[保护规则本身的文件](4-3-guardrails.html)）。这样留下一份别人可以审查的 diff。
2. **作者不是唯一的审查者**。这一层的负责人要读这个改动，另一个没参与讨论的人也要读。把规则改动当作攻击者很想做的代码改动来对待：一个草率或怀有恶意的 pull request，或者一个共享的 skill 或知识库文件里带着 agent 会当成自己的指令来读的话，都是入口（[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)）。要约定谁可以批准例外，负责人离开时谁接手这一层。只有作者自己看得懂的规则，对 agent 来说也是差的规则：它是从零开始读的。
3. **审查要问六个问题**。这是我往自己的配置里加任何东西之前问的那些。
   - 它防止什么故障？有真实的例子、日志或测量吗？
   - 平台已经做了吗？有人读过它现在的文档吗？
   - 它花多少，在上下文、token 和时间上？
   - 它是文字里的请求，还是代码里的规则（[提示里的规则只是请求](4-1-requests-and-rules.html)）？对这个危害，选这个对吗？
   - 什么时候可以删？要变成什么样？
   - 如果我们换了别的工具，学到的东西还有用吗？
4. **说“这有帮助”，要用同样的任务做前后对比**。如果这个改动是要改善结果，审查应该要一份在固定任务上的前后对比（[固定的任务，用脚本打分](6-3-eval-tasks.html)），不是一个意见。

还有一条规矩对审查有帮助。**只写模型会弄错的东西**。模型本来就会照做的一行，占上下文，还让审查者多读一行。说不出它防止了什么错误，就别写。

### 审计：配置留下了什么

没在场的管理者，需要能回答“agent 做了什么，是谁让它们做的”。这就是审计。只有配置写下的记录不归 agent 控制，它才行得通，下面是我的配置写了什么。前五项做了，后两项只是想法。

- **每次工具调用一行日志**。调用的类型、是放行还是拒绝、哪条规则拒绝的、花了多长时间。不记参数，也不记 prompt 文本，只有被拒绝的调用会保留它的路径和命令（[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)）。
- **拒绝，以及拒绝的次数**。一条统计命令会汇总 prompt、调用和拒绝的数量，以及是配置的哪个部分拒绝的。
- **审批**。每个任务的审批，都保存成只有人才能创建的记录，任务报告会显示两道审批的时间。
- **任务报告**。任务关闭时由代码写：要求是什么，改了什么，做了多少次检查、每次的结论，以及拒绝了什么（[一份五分钟读得完的报告](6-2-task-report.html)）。
- **对规则的改动**。agent 不能改规则文件。由人在一次会话里改，这次会话里每个记录下来的调用都标成 admin，改动就是 git 里的一份 diff。
- **想法，没做：是谁批准的**。审批记录带有时间。它们带不带人名，我没查过，而我的配置只有一个用户，所以从来不需要。团队需要。
- **想法，没做：日志集中放一处**。在我的配置里，日志留在每台电脑上，不放进 git。我没有做过把它们在团队范围内收集起来的办法。

谁来看，多久看一次？在我自己的配置里，我在一次运行失败时，以及改规则时读日志，不是每天读（[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)）。对团队，我会加一个简短的例行动作，作为建议：每一层的负责人时不时看看拒绝的次数，并读每一次规则改动的 diff。没人负责的日志，不是审计线索。

### 分阶段落地

先铺开、后补审查，就会得到十个副本。所以我会分阶段放开，并且为每个阶段写下进入它之前必须满足什么。

::: figure 7-4-rollout-stages

1. **一个团队，只用核心层**。挑一个想要这套配置、并且拥有自己代码的团队。从第一天起，把核心层交给一两个负责人。*进入条件：*这个团队来要。现在还不需要证明什么。
2. **加上团队层**。领域 skill、共享设置和知识库，在这个团队用核心层用得足够久、知道自己需要什么之后再加。*进入条件：*核心层有了指定的负责人，而且负责人能根据记录，而不是 agent 的摘要，说出最近一个任务里发生了什么。
3. **放给下一个团队**。*进入条件：*审查的习惯在第一个团队里行得通。每次规则改动都有第二个审查者，diff 被读过，凡是要改善结果的改动，都附了固定任务上的前后对比。
4. **所有人，包括没要求过的那位同事**。*进入条件：*日志显示规则站得住。信号在下一节。

这些条件是我的建议。我没有在团队里跑过它们，阈值（多久才算“足够久”）由你来定。

### 怎么知道它在起作用

我没有来自团队的数字，所以这是我会盯的东西，不是我量过的东西：

- **大家是在开任务，还是绕开这套配置**？开了多少任务，对比在普通对话里完成的活。
- **规则拒绝了什么？每周都是同样的东西吗**？一条总是拒绝同样的正常工作的规则，是要修的规则（[询问不是限制](4-2-ask-vs-refuse.html)）。
- **批准之后有多少活被打回来**？点头之后又返工，说明关卡被读得太快。
- **本地 override 有多少，它们一样吗**？见下面的 fork 陷阱。

第 4 阶段要求这些都不再变动：拒绝的次数稳定，而且多半是你想拒绝的那些，返工很少，override 很少。“日志显示规则站得住”指的就是这个，没有更大的含义。

### 这本书里的证据有多强

读这本书的其余部分，请记住这些局限。

- **一个平台**。所有东西都是在 VS Code Copilot 上搭建和试验的。别的工具有对应的东西，但我没有测过。
- **一个人的 harness**。我搭的，我在用。没有别人测过，我也不是它的中立评判者。
- **没有团队数据，也没有事故**。我没有测过采用情况，也没有规则在团队里失效的记录。我唯一量过的对比是四个任务，各跑一次（[慎用子 agent](2-3-subagents.html)）。
- **数字带着它的条件**。章节里给出数字的地方，都在旁边写了运行次数和配置，好让你看出该信到什么程度。

所以，请把这本书当作问题和设计来用，不要当作证明。从中取一个设计，说明你预期它做什么，再在你自己的任务上检验（[固定的任务，用脚本打分](6-3-eval-tasks.html)、[一次运行证明不了什么](6-4-variance.html)）。你的数字应该取代我的。

## 代价和坑 {#costs-and-traps}

**负责人会变成瓶颈**。如果每次规则改动都要经过两个人，大家就不再提改动，转而留私人副本，这正是你要解决的问题。让核心层保持小，这样走严格流程的改动就少，团队层则让它改得快。

**审查规则没什么光彩**。没人会因为一条没加的规则而被感谢。把负责人的时间排进某个人的计划里，否则审查会变成走过场。

**审查者得有能力判断这条规则**。一条关于部署路径的规则，让一个从没部署过的人审查，只是一次拼写检查。

**太多本地 override，就是 fork**。如果大多数用户带着同样的 override，它就该放进团队层。时不时看看 override，把常见的提升上去。

**日志里有关于人的东西**。一份记录每次调用的日志，会显示某人什么时候工作、让 agent 去碰什么。在集中收集之前，先定谁可以读它，保存多久。

**阶段关卡的好坏取决于记录**。日志里的漏洞（[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)），会让“规则站得住”看起来是真的，实际上并不知道。

**我没有团队数据**。三层划分、审查习惯、审计例行动作和各个阶段，是根据一个人的使用设计出来的。我没有测过团队里的采用情况，也没有跟踪过谁改了什么。把它们当作要验证的起点，不要当结果。

## 什么时候可以删掉 {#when-to-delete-it}

三层划分之所以存在，是因为平台给你文件，却没有给你管理这些文件的办法。如果你的平台允许组织集中发布规则，并自带审查、审计和推广，核心层就用它的，自己只留团队层。Copilot 现在在这方面提供什么，我没查过，所以自己动手建之前，先看它当前的文档。

审查的那些问题不会退役。你就是用它们来决定，任何规则、skill 或 agent 值不值得存在。

## 在 harness 里探索 {#explore}

override、健康检查、被围起来的规则文件和日志，都在 Copilot Harness 里跑着。harness 可以带着真实的文件把它们展示给你。按上面的说明准备好之后，输入：

::: prompt
/harness-rookie-wondering 我读完了“落地与治理”这一章。请教我这个 harness 是怎么让团队定制它而不用 fork 的（策略 override，以及列出它们的健康检查），它怎么守住自己的规则文件，以及它的日志和报告记录了什么。带我打开真实的文件，让我看看团队的改动该放在哪里、不该放在哪里。
:::

它一次只教一小块，停下来确认你跟上了，再和你一起打开文件。
