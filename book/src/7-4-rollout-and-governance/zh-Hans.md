读这一章之前，需要先读过[别让 Agent 改自己的规则](4-3-guardrails.html)、[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)和[别信 Agent 的总结，看日志](6-1-observe.html)。

## 一句话 {#in-one-sentence}

把一套 agent 配置推广到团队，主要是两个问题：规则归谁管，谁来审查对规则的改动。等日志显示规则站得住了，再往外放开。

## 写给管理者 {#for-leaders}

- **要拍板的事**：给每一层规则指定负责人，对规则的任何改动都要有第二个人审查，并事先约定好配置推给下一个团队之前必须满足什么条件。
- **风险**：没有负责人，规则会漂移成每人一份，过期的规则也一直留着。我没有团队的数据，给不出数字，所以这一章讲的是我会采用的设计，不是量出来的结果。
- **做对的代价**：主要是人的时间，既有核心层和各个领域负责人的时间，也有审查者在每次规则改动上花的时间。配置本身增加的很少。
- **可以问团队**：“这条规则归谁管？上一次改动是谁审查的？如果它是错的，日志会显示什么？”

## 一个人的配置交给整个团队，会出什么问题？ {#problem}

适合一个人的配置，碰巧只有一个负责人，就是这个人自己。规则是他写的，哪条错了他会发现，每条为什么在那里他也清楚。可一旦把同样的文件交给十个同事，就会出三个问题，而且都和工具无关。

第一个问题是副本会漂移。每个人都为自己的任务，在自己的副本里改规则，一个月后就有了十个版本，谁也说不清哪一个才是“规则”。第二个问题是没有哪条规则有人负责。去年还对的规则，现在已经错了，可大家只是学会了无视它。除非有人专门花精力去修剪，规则就是这样过期的。第三个是，为一处做的改动会弄坏另一处。为一个项目收紧一条规则，会挡住另一个团队的正常工作，而做改动的人永远看不到这些破坏。

还有第四个担心，是管理者的：推广之后，你怎么知道 agent 做了什么？要回答这个问题，得有一份有人会去看的记录。

我得先说清楚自己的位置。我的配置是为一个人搭的，也没有带着测量去做过团队落地。下面讲的是我会采用的设计，依据是这套配置现在已经能做的事（我能指出来的那些部分），以及我在加任何东西之前都会问的那些问题。只是建议的地方，我会说明。

## 负责人、审查、记录，再分阶段落地 {#how-it-works}

### 规则归谁管

副本漂移也好，规则没人负责也好，最后都会回到同一个问题：规则归谁管？这个问题没有唯一的答案，因为规则不都一样。我按“一条规则错了，谁会受伤”，把它们分成三层。

::: figure 7-4-rule-layers

**核心层**是每个任务都必须遵守的那几条简短规则，加上执行它们的文件（[别让 Agent 改自己的规则](4-3-guardrails.html)里的围栏）。这里出错，影响的是所有人。它有一两个指定的负责人，别人不去改它。

往下是**团队层**，包括领域 skill、团队的知识库（代码的索引，见[为什么要给代码建一个知识库？](8-1-why-a-knowledge-base.html)），以及对所有人都一样的设置，比如哪些路径任何 agent 都不许碰。这一层每个领域有一位负责人，就是最了解那部分代码的人。比如关于部署的 skill，就归负责部署的人。

最后是**个人层**，比如用户名、语言、你的仓库在你机器上所在的文件夹。它归个人，也不提交，因为里面的路径只在一台电脑上有效。

这套分法要行得通，在我的配置里靠的是两个机制，不过团队就算不用这个工具，也可以照搬思路。

一个是 **override**。它是放在默认配置旁边的一小份配置，而不是默认配置的副本，只列出你改动的东西。想多禁止一个路径的人，写一行就行，用不着把整个规则文件 fork 出去。这样一来，团队的定制始终只有几行，谁都读得懂，核心层升级时也不会和它冲突。在我的实现里，override 删不掉核心层的护栏：哪个 override 要是把它们去掉了，引擎会把它们放回去，并报告一个错误。配置的健康检查还会列出每个 override 改了什么，这样审查者就有了一个集中查看的地方。

另一个是一条规则只有一个主来源。同一条规则写在三个文件里，副本就是这么漂移起来的（[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)），所以分派负责人时，要分派给来源。一条规则有两个家，就有两个负责人，实际上等于没有。

### 谁来审查对规则的改动

每一层有了负责人，接下来的问题是：对它的改动由谁来把关？这要从规则文件是什么说起。它不是文档，而是 agent 要服从的东西，所以改它，就是改团队的 agent 明天会做什么。我像对待代码那样对待它，具体有四个习惯。

第一个习惯是 agent 不改规则。这些文件被围栏围着，要改，得由人为一次会话打开围栏，改完再关上，之后在 git 里读 diff（[别让 Agent 改自己的规则](4-3-guardrails.html)）。这样留下来的，就是一份别人可以审查的 diff。

第二个习惯是，作者不是唯一的审查者。这一层的负责人要读这个改动，另一个没参与讨论的人也要读。对待规则改动，要像对待攻击者很想做的代码改动那样，因为一个草率或怀有恶意的 pull request 是入口，一个共享的 skill 或知识库文件也是入口，只要里面带着 agent 会当成自己的指令来读的话（[Agent 读到的网页和文件，可能在给它下命令](4-6-untrusted-input.html)）。

两个人读过，管得了这一次改动，管不了以后的。以后的事，要约定好谁可以批准例外、负责人离开时谁接手这一层。写规则的人还要记得，agent 是从零开始读的，所以只有作者看得懂的规则，对它来说就是差的规则。

第三个习惯是一组固定的问题。审查要问六个，也就是我往自己的配置里加任何东西之前会问的那些。

- 它防止什么故障？有真实的例子、日志或测量吗？
- 平台已经做了吗？有人读过它现在的文档吗？
- 它花多少，在上下文、token 和时间上？
- 它是文字里的请求，还是代码里的规则（[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)）？对这个危害，选这个对吗？
- 什么时候可以删？要变成什么样？
- 如果我们换了别的工具，学到的东西还有用吗？

还有一条规矩能帮上审查：**只写模型会弄错的东西**。模型本来就会照做的一行，既占上下文，又让审查者多读一行。说不出它防止了什么错误，就别写。

最后一个习惯，是不接受空口的“这有帮助”。如果一个改动是为了改善结果，审查就该要一份在同样的固定任务上做的前后对比（[改了配置，怎么知道是不是变好了？](6-3-eval-tasks.html)），而不是一个意见。

### 审计：配置留下了什么

审查发生在改动生效之前，可事后，没在场的管理者还要能回答“agent 做了什么，是谁让它们做的”。回答这个问题，就是审计。审计要行得通，前提是记录不归 agent 控制。那我的配置到底写下了什么？已经做了的有五类。

- 每次工具调用记一行日志：调用的类型、是放行还是拒绝、哪条规则拒绝的、花了多长时间。这一行不记参数，也不记 prompt 文本，只有被拒绝的调用会保留它的路径和命令（[别信 Agent 的总结，看日志](6-1-observe.html)）。
- 拒绝还会被计数。一条统计命令会汇总 prompt、调用和拒绝的数量，以及是配置的哪个部分拒绝的。
- 每个任务的审批，都保存成只有人才能创建的记录，任务报告会显示两道审批的时间。
- 任务报告在任务关闭时由代码写出，写的是要求是什么，改了什么，做了多少次检查、每次的结论，以及拒绝了什么（[Agent 干完活，你该看什么？](6-2-task-report.html)）。
- 对规则的改动也有自己的痕迹。agent 不能改规则文件，所以由人来改，而且是在一次会话里改，这次会话里每个记录下来的调用都标成 admin，改动本身就是 git 里的一份 diff。

还有两类只是想法，没有做。审批记录带有时间，但带不带人名，我没查过。我的配置只有一个用户，所以从来不需要，团队却需要。日志也没有集中放在一处：在我的配置里，它们留在每台电脑上，不放进 git，我也没有做过在团队范围内把它们收集起来的办法。

这些记录还得有人读。那么，谁来看，多久看一次？在我自己的配置里，我在一次运行失败时和改规则时读日志，不是每天读（[别信 Agent 的总结，看日志](6-1-observe.html)）。对团队，我会建议加一个简短的例行动作，由每一层的负责人时不时看看拒绝的次数，并读每一次规则改动的 diff。没人负责的日志，算不上审计线索。

### 分阶段落地

还有一件事，是按什么顺序推开。先铺开、后补审查，得到的就是这一章开头那十个副本。所以我会分阶段放开，并为每个阶段写下进入之前必须满足什么。

::: figure 7-4-rollout-stages

1. 一个团队，只用核心层。挑一个想要这套配置、并且拥有自己代码的团队，从第一天起就把核心层交给一两个负责人。*进入条件：*这个团队来要。现在还不需要证明什么。
2. 加上团队层。领域 skill、共享设置和知识库，要等这个团队用核心层用得足够久、知道自己需要什么之后再加。*进入条件：*核心层有了指定的负责人，而且负责人能根据记录，而不是 agent 的摘要，说出最近一个任务里发生了什么。
3. 放给下一个团队。*进入条件：*审查的习惯在第一个团队里行得通，也就是每次规则改动都有第二个审查者，diff 被读过，凡是要改善结果的改动，都附了固定任务上的前后对比。
4. 所有人，包括没要求过的那位同事。*进入条件：*日志显示规则站得住。这句话具体指什么，见下一节。

和这套设计的其他部分一样，这些条件没有在团队里跑过，阈值（多久才算“足够久”）也由你来定。

### 怎么知道它在起作用

第 4 阶段靠的是“日志显示规则站得住”这句话，所以它得指向看得见的东西。没有团队的数字，我只能说会盯什么，说不出量到了什么。

- 大家是在开任务，还是绕开这套配置？数一数开了多少任务，对比在普通对话里完成的活。
- 规则拒绝了什么？每周都是同样的东西吗？一条总是拒绝同样的正常工作的规则，是要修的规则（[“先问我”为什么挡不住 Agent？](4-2-ask-vs-refuse.html)）。
- 批准之后有多少活被打回来？点头之后又返工，说明审批时看得太快。
- 本地 override 有多少，它们一样吗？见后面关于 override 的那个坑。

第 4 阶段要求这些都不再变动：拒绝的次数稳定，而且多半是你想拒绝的那些，返工很少，override 也很少。“日志显示规则站得住”指的就是这个，没有更大的含义。

### 这本书里的证据有多强

这一章靠的是设计而不是数据，整本书在一定程度上也是这样。读其余部分时，这些局限值得记在心里。所有东西都是在一个平台上搭建和试验的，就是 VS Code Copilot。别的工具也有对应的东西，但我没有测过。而且这是一个人的 harness：是我搭的，我在用。没有别人测过，而我作为搭建者，也不是它的中立评判者。我也没有团队数据或事故可以依据：我没测过采用情况，也没有规则在团队里失效的记录。我唯一量过的对比，是四个任务、各跑一次（[别跟风瞎用子 Agent](2-3-subagents.html)）。章节里给出数字的地方，都会在旁边写明运行次数和配置，好让你看出该信到什么程度。

所以，请把这本书当作问题和设计来用，不要当作证明。从中取一个设计，说清你预期它做什么，再在你自己的任务上检验（[改了配置，怎么知道是不是变好了？](6-3-eval-tasks.html)、[同一个任务跑两次，结果不一样](6-4-variance.html)）。你的数字应该取代我的。

## 治理本身会在哪里出问题 {#costs-and-traps}

治理本身也有代价，多半落在人身上。首先，负责人可能变成瓶颈。如果每次规则改动都要经过两个人，大家就不再提改动，转而留私人副本，而这正是你要解决的问题。让核心层保持小，这样走严格流程的改动就少，团队层则让它改得快。

审查规则也没什么光彩，没人会因为一条没加的规则而被感谢。要把负责人的时间排进某个人的计划里，否则审查就会变成走过场。而且审查者得有能力判断这条规则。一条关于部署路径的规则，让一个从没部署过的人来审，就只剩一次拼写检查。

override 也要盯着，因为本地 override 太多，就等于 fork。如果大多数用户都带着同样的 override，它就该放进团队层，所以要时不时看看 override，把常见的提升上去。

日志带来的则是另一种代价，因为里面有关于人的东西。一份记录每次调用的日志，会显示某人什么时候工作、让 agent 去碰了什么。在集中收集之前，先定好谁可以读，保存多久。

日志还有一层作用：它是阶段关卡的证据，而关卡的好坏，取决于背后的记录。日志里的漏洞（[别信 Agent 的总结，看日志](6-1-observe.html)）会让“规则站得住”看起来是真的，实际上却无从知道。

这一切都建立在我开头承认的那个局限上。三层划分、审查习惯、审计例行动作和各个阶段，都是根据一个人的使用设计出来的。我没有测过团队里的采用情况，也没有跟踪过谁改了什么，所以请把它们当作要验证的起点，不要当成结果。

## 什么时候可以删掉这三层，什么会留下来 {#when-to-delete-it}

三层划分之所以存在，是因为平台给了你文件，却没给你管理这些文件的办法。如果你的平台允许组织集中发布规则，并自带审查、审计和推广，核心层就用它的，自己只留团队层。Copilot 现在在这方面提供什么，我没查过，所以自己动手建之前，先看看它当前的文档。

不过，审查的那些问题不会退役。任何规则、skill 或 agent 值不值得存在，你都要靠它们来决定。
