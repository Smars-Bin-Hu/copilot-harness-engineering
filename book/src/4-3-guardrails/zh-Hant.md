這一章假設你讀過[詢問不是限制](4-2-ask-vs-refuse.html)：限制是 agent 吵不贏的拒絕。

## 一句話 {#in-one-sentence}

agent 能改規則，規則就沒有意義。把規則檔和 hook 檔放在它碰不到的地方；人給的任何 override，都只管一個會話，會過期，並留下紀錄。

## 給主管 {#for-leaders}

- **要做的決定**：決定 agent 不能編輯存放它自己規則、hook 和證據的檔案；人給的任何 override，只限一個會話，會過期，並留下紀錄。
- **風險**：agent 能改的規則，agent 就能刪掉；它能寫的「通過」紀錄，就是它能自己給自己的通過。我沒有事故可報告。重點是這個論證，不是次數。
- **做對的成本**：一份受保護檔案的清單，加了新部件就更新；還有一個讓人刻意打開圍欄的辦法。我的 override 要靠人記得關掉；有時間限制和第二個人來讀會更好，我沒有做。
- **可以問團隊**：「agent 能不能編輯存放它自己規則和紀錄的檔案？它試的時候，你能給我看一次被拒絕的紀錄嗎？」

## 問題 {#problem}

這裡的威脅是誰？多半是個粗心的 agent，不是惡意的：它趕著完成任務，就把擋路的規則放鬆了。被注入的文字帶偏的 agent 是第二種情況（[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)）；它需要同樣的圍欄，而且更多。

你有一個 hook，會拒絕危險的指令，它管用。現在問：這個 hook 放在哪裡？在一個檔案裡。告訴平台要執行它的設定，是一個檔案。它用到的數字，是一個檔案。而 agent 有編輯工具。

一個被拒絕卡住的 agent，不需要惡意就會去改那個檔案。它只是想完成任務，看到規則擋路，就做了看起來合理的事：放鬆規則。我沒有事故可報告。重點是這個論證：agent 能編輯的規則，agent 就能刪掉。

紀錄也一樣。檢查通過後留下一個「通過」的檔案，如果 agent 能寫這個檔案，它就能讓自己通過。所以問題不只是「哪些指令被拒絕」，而是「誰能改那些負責拒絕和證明的東西」。

我把必須放在碰不到的地方的檔案叫作**護欄檔案**：一道圍欄，agent 在裡面工作，但移不動它。

這一章只做一件事的話：讓規則檔和 hook 檔對 agent 不可寫。

## 原理 {#how-it-works}

### 哪些檔案是圍欄

::: figure 4-3-fence

在我的設定裡是這些：

- **hook 設定**，告訴平台要執行哪個 hook 的檔案；
- **引擎**，也就是 hook 本身的程式碼，以及 agent 被允許呼叫的指令；
- **政策**，存放規則的數字和模式的純文字檔；
- **執行期狀態**，hook 執行時寫出的檔案：會話狀態、批准紀錄和日誌；
- 能把 hook 關掉的編輯器設定；
- 倉庫的授權檔案。

指令檔和 skill 不在清單上。它們是文字，是請求，而且本來就是要給 agent 讀的。改了它們，程式拒絕的東西並不會變。

### 圍欄怎麼守住

- **編輯工具：呼叫之前就拒絕**。這是容易的一種。路徑就在呼叫裡。
- **終端機：攔常見的寫法**。重新導向、`rm`、`mv`、`sed -i`、`cp`、`tee` 等等。[詢問不是限制](4-2-ask-vs-refuse.html)裡的限制在這裡也適用：間接的寫法攔不到。
- **比較之前先把路徑變成同一種形式**。同一個檔案可以用不同的大小寫、`..`、絕對路徑，或 Windows 的反斜線來寫。規則先把它們都變成同一種形式。不然圍欄在寫法上就會有縫。你自己的設定裡，還有兩個縫值得檢查：指向受保護資料夾的符號連結，以及不分大小寫的磁碟。這兩個我都沒有測過。
- **公司可以加路徑，不能拿掉預設的**。替團隊做設定的人可以保護更多檔案。一個能拿掉預設項的 override，就和能編輯規則的 agent 是同一個洞。

這是防失誤的，不是沙箱，我也不叫它沙箱。一個鐵了心要繞過去的 agent，先寫一個腳本再執行，就繞得過去。想要強的版本，見[有些東西根本不給](4-5-least-privilege.html)。

### 只有指令能寫的檔案

有些檔案不是規則，而是證據：任務的狀態、獨立檢查的裁決（[模型能檢查模型嗎](5-6-model-checks-model.html)）、快照（在某個時間點複製下來的檔案）、批准所依據的 diff、最終報告。

agent 如果能寫它們，就能宣布一次檢查通過，或者改掉被批准的內容。所以 agent 從不用編輯工具寫它們。由一個指令來寫，並且由這個指令自己判斷結果。「agent 記錄了一個結果」的意思是：agent 請指令去記錄，而指令做了決定。

人帶來的東西所在的資料夾也一樣：文件、參考程式碼、一次運行的結果。agent 讀它們。人（透過一個頁面或一個指令）來寫。agent 能編輯的證據，就不是證據。

### 斷路器

拒絕不斷出現時，agent 可能一直試。hook 只能拒絕一次呼叫，它停不了 agent。所以同一個拒絕連續出現三次（三是我的設定），**斷路器**就跳開，把原因換成另一句：別再試這個了，告訴人。這是以訊息形式出現的請求，但這是 hook 唯一能做的。它也讓日誌不會被同一個拒絕塞滿。

### 什麼時候要由人打開圍欄

有時規則本身要改。我擴充 harness 的時候，就會改護欄檔案。所以必須有一條路進去。怎麼把這個權利給出去，又不給 agent？

**不能按 agent**。我一開始想過讓一個指定名字的 agent 編輯圍欄。但在今天的 Copilot 裡，hook 收到的事件不帶主 agent 的名字（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)），所以 hook 分不出是哪個 agent 在呼叫。任何 agent 都能冒充那個名字。跟著名字走的權利，誰用了這個名字誰就能拿到。

**按會話，由人設定**。依據是會話狀態裡的一個開關。只有人能打開它，方法是在自己的終端機裡打一個代碼。agent 不能執行那條指令，它試的話 hook 會拒絕。這和[兩道門：人在哪裡批准](5-3-two-approvals.html)是同一個管道。

::: figure 4-3-admin

讓 override 安全的是這幾點：

1. **它屬於一個會話，不屬於某個 agent**。會話結束，它就結束。
2. **工作做完就關掉**。我的規則是關掉它，然後用 git 讀一遍改了什麼的 diff。我靠這一點；我的設定裡沒有計時器。這是設計的弱點：它要靠人記得。時間限制是更好的設計，git 寫入的批准已經在用。團隊的話，加上過期，以及第二個人來讀 diff。
3. **它會留下紀錄**。開著的時候，每一次被記錄的呼叫都標上 admin。
4. **有些門仍然關著**。在我的設定裡，連 admin 也不能寫執行期狀態，那裡存著批准紀錄。能寫的話，它就能偽造批准。而且同一個會話裡不能打開任何任務，也不能呼叫子 agent。

每一條都是在去掉一個讓短期例外變成長期漏洞的路。

### 測一下你自己的設定

在你專案的副本裡，請你的 agent 放鬆它自己 hook 設定裡的一條規則。成功了嗎？成功的話，你的規則就只是請求。那就保護這個檔案，再試一次。

## 代價和陷阱 {#costs-and-traps}

**圍欄只和它的清單一樣好**。不在清單上的護欄檔案是開著的。給引擎加了新部件，就把它的路徑加進去。

**admin 是真正的權力**。它能改引擎，所以它做的事沒有被硬性限制。控制手段是人事後讀 diff。我不聲稱比這更多。

**寫法上的縫還在**。因為終端機是按模式防護的，理論上有一種它不認識的寫法，可以改動放在任務資料夾裡的紀錄（存放一件工作的資料夾；見[管任務，不管對話](5-1-tasks.html)）。我沒有試著做出來。解法還是一樣：把絕對不能碰的東西整個放到碰不到的地方。

**看不見的圍欄是個謎題**。agent 碰到一個它不知道受保護的檔案而被拒絕時，原因必須說明這一點，以及該怎麼做。見上一章。

**我沒有量過 agent 多常想編輯規則**。我寫這道圍欄，是因為論證很簡單，不是因為我看到了某次具體的事故。

## 業界怎麼說 {#industry}
{status: industry}

VS Code 的 hooks 頁面說，hooks 和指令不能代替強制的權限或沙箱；它的 security 頁面建議用沙箱，不要只靠批准規則（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)、[security](https://code.visualstudio.com/docs/copilot/security)）。用 hook 做的圍欄，是在 agent 所在的同一台機器裡面的圍欄。所以這一章說「碰不到」，不說「安全」。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

如果 agent 跑在一個規則檔以唯讀方式掛載的環境，或者 hook 跑在 agent 碰不到的機器之外，就不需要受保護路徑的清單；環境本身就是圍欄。另一條教訓要留著：人給的任何 override，都應該綁在會話上、有時間限制、並留下紀錄。

不用裝 harness。在你自己的倉庫裡打開 agent，貼上：

::: prompt
找出這個專案裡每一個定義了 agent 能做什麼、不能做什麼的檔案：指令檔、hook 腳本和它們的設定、權限設定、編輯器設定，以及任何記錄檢查或批准的檔案。對每一個，根據你看得到的規則和權限，告訴我 agent 自己的編輯工具和終端機今天能不能改它。輸出一份清單，按「這個檔案被改了會有多糟」排序。不要改任何檔案，也不要為了確認而去試著編輯它們。
:::
