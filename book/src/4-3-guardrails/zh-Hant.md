這一章假設你讀過[詢問不是限制](4-2-ask-vs-refuse.html)：限制是 agent 吵不贏的拒絕。

## 一句話 {#in-one-sentence}

agent 能改規則，規則就沒有意義。所以要把規則檔和 hook 檔放到它碰不到的地方。人給的任何 override，都只管一個會話，會過期，還要留下紀錄。

## 給主管 {#for-leaders}

- **要做的決定**：決定 agent 不能編輯存放它自己規則、hook 和證據的檔案；人給的任何 override，只限一個會話，會過期，並留下紀錄。
- **風險**：agent 能改的規則，它就能刪掉；它能寫的「通過」紀錄，就是它能自己給自己的通過。我沒有事故可報告，所以這裡靠的是論證，不是次數。
- **做對的成本**：一份受保護檔案的清單，每加一個新元件就跟著更新，再加上一個讓人刻意打開圍欄的辦法。我自己的 override 要靠人記得關掉。有時間限制、再有第二個人來讀會更好，可是這兩樣我都沒有。
- **可以問團隊**：「agent 能不能編輯存放它自己規則和紀錄的檔案？它試的時候，你能給我看一次被拒絕的紀錄嗎？」

## agent 要是改了規則呢？ {#problem}

假設你有一個會拒絕危險指令的 hook，它也確實管用。現在問一句：這個 hook 放在哪裡？放在一個檔案裡。告訴平台要執行它的設定，同樣是一個檔案，它用到的那些數字也在檔案裡。而 agent 手上有編輯工具。

其實 agent 去改這些檔案，並不需要什麼惡意。設想它被一條拒絕卡住，又趕著把任務做完，看到規則擋了路，就做了一件看起來很合理的事：把規則放鬆。agent 能編輯的規則，agent 就能刪掉。我沒有事故可報告，也沒有量過 agent 多常想編輯規則，所以這裡只靠這個論證。

同樣，紀錄也有這個弱點。如果檢查留下一個「通過」的檔案，而 agent 能寫這個檔案，那它就能讓自己通過。所以要問的不只是「哪些指令被拒絕」，還有「誰能改那些負責拒絕、負責證明的東西」。

不管是規則還是紀錄，威脅多半來自一個粗心的 agent，而不是懷有惡意的 agent。被注入的文字帶偏的 agent 是另一種威脅（[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)），它需要同樣的圍欄，而且還要更多。

這些必須放在 agent 碰不到的地方的檔案，我叫它們**護欄檔案**。它們合起來是一道圍欄，意思是 agent 在裡面工作，卻移不動它。那麼，哪些檔案該圍進去？圍欄怎麼守住？規則本身真的要改的時候，人又怎麼進去？

讀完這一章，如果你只做一件事，那就是讓規則檔和 hook 檔對 agent 不可寫。

## 圍欄怎麼搭，人又怎麼進去 {#how-it-works}

### 哪些檔案是圍欄

::: figure 4-3-fence

在我的設定裡，圍欄由這些檔案組成：

- **hook 設定**，告訴平台要執行哪個 hook 的檔案；
- **引擎**，也就是 hook 本身的程式碼，以及 agent 被允許呼叫的指令；
- **政策**，存放規則的數字和模式的純文字檔；
- **執行期狀態**，hook 執行時寫出的檔案：會話狀態、批准紀錄和日誌；
- 能把 hook 關掉的編輯器設定；
- 倉庫的授權檔案。

你也許以為指令檔和 skill 也在清單上，其實不在。它們是寫給 agent 讀的文字，是請求，不是限制。改了它們，程式拒絕的東西並不會變。

### 圍欄怎麼守住

清單定下來以後，agent 寫這些檔案的每一條路都得堵住，至於難不難，就要看是什麼工具了。編輯工具最好辦，因為路徑就在呼叫裡，hook 在呼叫執行之前就能拒絕。

終端機就難多了，因為同一次寫入可以有很多種寫法。hook 攔得住常見的寫法，例如重新導向、`rm`、`mv`、`sed -i`、`cp`、`tee`。不過[詢問不是限制](4-2-ask-vs-refuse.html)裡說的那些限制在這裡一樣存在，所以間接的寫法攔不到。

就連路徑本身也得小心。同一個檔案，可以換個大小寫來寫，可以帶 `..`，可以寫成絕對路徑，也可以用 Windows 的反斜線。如果規則拿到路徑就直接比較，圍欄在寫法上就會有縫，所以它先把這些寫法變成同一種形式，再去比較。你自己的設定裡還有兩個縫值得檢查：指向受保護資料夾的符號連結，以及不分大小寫的磁碟。這兩個我都沒有測過。

還有一條規矩管的是清單本身。公司可以往清單裡加路徑，但不能拿掉預設的，因為一個能拿掉預設項的 override，和一個能編輯規則的 agent 是同一個漏洞。

說到底，這些只防失誤，算不上沙箱，因為一個鐵了心要繞過去的 agent，先寫好一個腳本就繞得過去。想要更強的做法，見[有些東西根本不給](4-5-least-privilege.html)。

### 只有指令能寫的檔案

值得守的檔案不只是規則。有些檔案是證據：任務的狀態、獨立檢查的裁決（[模型能檢查模型嗎](5-6-model-checks-model.html)）、快照（在某個時間點複製下來的檔案）、批准所依據的 diff，還有最終報告。

這些檔案要是 agent 能寫，它就能宣布一次檢查通過，或者改掉已經批准的內容。所以它們從不由 agent 的編輯工具來寫，而是交給一個指令，結果也由這個指令自己判斷。我說「agent 記錄了一個結果」，意思是 agent 請指令去記錄，做決定的是指令。

人帶進來的東西，放在資料夾裡也是同樣的道理。文件、參考程式碼、一次運行的結果，都是給 agent 讀的，寫它們的則是人（透過一個頁面或一個指令）。agent 能編輯的證據，就不是證據。

### 斷路器

圍欄守住了，又會冒出一個新問題：拒絕一次次出現，agent 可能就一次次地試。hook 沒辦法讓它停下來，因為 hook 能做的只有拒絕一次呼叫。所以同一個拒絕連續出現三次時（三是我的設定），**斷路器**就會跳開，把拒絕的原因換成另一句：別再試這個了，去告訴人。這仍然只是一個請求，以訊息的形式出現，不過已經是 hook 能做的全部了。另外，它也讓日誌不會被同一個拒絕塞滿。

### 什麼時候要由人打開圍欄

可是有時候，規則本身就是得改。我擴充 harness 的時候，就會改護欄檔案，所以必須留一條路進去。問題是，怎麼把這個權利交給人，又不交給 agent？

我一開始想的是讓一個指定名字的 agent 去編輯圍欄。在今天的 Copilot 裡這行不通，因為 hook 收到的事件不帶主 agent 的名字（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）。hook 分不出是哪個 agent 在呼叫，任何 agent 都能冒充那個名字。權利跟著名字走，誰用了這個名字，誰就能拿到它。

所以權利改成跟著會話走，由人來設定。它靠的是會話狀態裡的一個開關，只有人能打開：在自己的終端機裡輸入一組驗證碼。agent 不能執行那條指令，它要是試，hook 就會拒絕。這和[兩道門：人在哪裡批准](5-3-two-approvals.html)用的是同一個管道。

::: figure 4-3-admin

讓這個 override 安全的有四點：

1. 它屬於一個會話，不屬於某個 agent，所以會話結束，它也就結束了。
2. 工作做完就關掉。我的規則是先關掉它，再用 git 讀一遍改了什麼的 diff。
3. 它會留下紀錄。開著的時候，每一次被記錄的呼叫都會標上 admin。
4. 即使這時，有些門也仍然關著。在我的設定裡，連 admin 也不能寫執行期狀態，那裡存著批准紀錄，要是能寫，它就能偽造批准。而且在同一個會話裡，不能打開任何任務，也不能呼叫子 agent。

每一點都堵住了一條路，免得短期的例外變成長期的漏洞。不過，第二點同時也是這個設計的弱點：我的設定裡沒有計時器，關掉 admin 要靠人記得。更好的做法是加時間限制，git 寫入的批准就已經這樣做了。如果是團隊，就要加上過期，再加一個讀 diff 的第二個人。

### 測一下你自己的設定

在你專案的副本裡，請你的 agent 去放鬆它自己 hook 設定裡的一條規則。要是它成功了，你的規則就是一個請求，那就把這個檔案保護起來，再試一次。

## 圍欄還會在哪裡失守 {#costs-and-traps}

通過了這個測試，圍欄是不是就萬無一失？還不是，還有三個地方會漏。第一處在清單本身：圍欄只守得住清單上列出的檔案，不在清單上的護欄檔案就是開著的。所以給引擎加新元件的時候，記得把它的路徑也加進去。

第二處是穿過圍欄的那條路，它本身也是一個缺口。admin 是實實在在的權力：它能改引擎，所以它做什麼都沒有硬性限制。能管住它的，只有事後有人讀一遍 diff，除此之外，我不說它還有別的保障。

第三處在寫法上。終端機是按模式防護的，所以理論上，一種它不認識的寫法，可能改動放在任務資料夾裡的紀錄（存放一件工作的資料夾；見[管任務，不管對話](5-1-tasks.html)）。我沒有試著做出這樣一種寫法。解法還是那一個：把絕對不能碰的東西，整個放到碰不到的地方。

還有一個陷阱，算不上漏洞：圍欄要是 agent 看不見，它碰上了也不知道為什麼被擋。這時，拒絕的原因裡就得說明這個檔案受保護，並說清楚該怎麼做。這個原因怎麼寫，上一章講過。

## 為什麼說「碰不到」，不說「安全」 {#industry}
{status: industry}

那麼，用 hook 做成的圍欄，能信到什麼程度？VS Code 的 hooks 頁面說，hooks 和指令不能代替強制的權限或沙箱；它的 security 頁面也建議用沙箱，不要只靠批准規則（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)、[security](https://code.visualstudio.com/docs/copilot/security)）。問題在於，用 hook 做的圍欄，和 agent 立在同一台機器上。所以這一章只說「碰不到」，不說「安全」。

## 什麼時候可以刪掉受保護路徑的清單 {#when-to-delete-it}
{status: industry}

同一個道理，也告訴你這份清單什麼時候可以刪。如果 agent 跑在一個規則檔以唯讀方式掛載的環境，或者 hook 跑在 agent 碰不到的那台機器之外，就不需要受保護路徑的清單，因為環境本身就是圍欄。另一條教訓到那時也要留著：人給的任何 override，都應該綁在會話上、有時間限制，並留下紀錄。
