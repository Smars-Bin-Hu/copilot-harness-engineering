读这一章，请先读过[询问不是限制](4-2-ask-vs-refuse.html)：限制，就是 agent 辩不过的拒绝。

## 一句话 {#in-one-sentence}

agent 如果能改规则，规则就等于没有。要让规则文件和 hook 文件它碰不到，人的任何 override 都只管一个会话、会过期，并且留下记录。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定 agent 不许编辑存放它的规则、hook 和证据的那些文件，并且人的任何 override 都只限一个会话、会过期、并留下记录。
- **风险**：agent 能编辑的规则，agent 就能删掉；agent 能写的“通过”记录，就是它能给自己的通过。我没有事故可以报告。重点是这个论证，不是次数。
- **做对的代价**：一份受保护文件的清单，增加新部件时要随之更新，再加一个让人有意打开围栏的办法。我的 override 靠人记得去关；时间限制加上第二个读的人更好，但我还没有。
- **可以问团队**：“agent 能编辑存放它自己的规则和记录的文件吗？它试的时候，你能给我看一次被拒绝的情形吗？”

## 问题 {#problem}

威胁是谁？多数时候是一个粗心的 agent，而不是怀有恶意的：一个急着完成任务的 agent，把挡路的规则放松了。被注入的文本引着走的 agent 是第二种情况（[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)）；它需要同样的围栏，而且要更多。

你有一个 hook，会拒绝危险的命令。它起作用。现在问：这个 hook 放在哪？在文件里。告诉平台去运行它的配置，是一个文件。它用到的数字，是一个文件。而 agent 有编辑工具。

一个被拒绝挡住的 agent，不需要有恶意才去改那个文件。它只要想完成任务，看到规则挡了路，然后做看上去合理的事：把规则放松。我没有事故可以报告。重点是这个论证：agent 能编辑的规则，agent 就能删掉。

记录也一样。如果一次检查留下一个“通过”的文件，而 agent 能写这个文件，agent 就能让自己通过。所以问题不只是“哪些命令被拒绝”，而是“谁能改动那些负责拒绝和证明的东西”。

我把必须放在它碰不到的地方的这些文件，叫作**护栏文件**：一道围栏，意思是 agent 在里面干活，却挪不动它。

这一章里如果你只做一件事：让规则文件和 hook 文件对 agent 不可写。

## 原理 {#how-it-works}

### 哪些文件是围栏

::: figure 4-3-fence

在我的配置里，这些是：

- **hook 配置**，告诉平台去运行哪个 hook 的那个文件；
- **引擎**，也就是 hook 本身的代码，以及允许 agent 调用的命令；
- **策略**，存放规则里的数字和模式的普通文件；
- **运行时状态**，hook 运行时写下的文件：会话状态、审批记录和日志；
- 能把 hook 关掉的编辑器设置；
- 仓库的许可证文件。

指令文件和 skill 不在这份清单里。它们是文本，是请求，本来就是给 agent 读的。改了它们，并不会改变代码会拒绝什么。

### 围栏是怎么守的

- **编辑工具：在调用之前就拒绝。** 这是容易的一种。路径就在调用里。
- **终端：常见的写法。** 重定向、`rm`、`mv`、`sed -i`、`cp`、`tee` 等等。[询问不是限制](4-2-ask-vs-refuse.html)里的限度在这里同样适用：间接的写法抓不到。
- **比较之前，先把路径统一成一种形式。** 同一个文件可以用不同的大小写、用 `..`、用绝对路径，或者用 Windows 的反斜杠来写。规则先把它们都统一成一种形式。否则围栏在写法上就会有缺口。在你自己的配置里还值得查两个缺口：指向受保护文件夹的符号链接，以及不区分大小写的磁盘。这两个我都没有测过。
- **公司可以增加路径，但不能去掉默认的。** 任何搭建团队配置的人，都可以保护更多文件。去掉默认值的 override，就和 agent 能编辑规则是同一个漏洞。

这是防失误的措施。它不是沙箱，我也不叫它沙箱。一个铁了心要绕过它的 agent，先写好一个脚本，就能绕过。要更强的版本，见[有些东西根本不给](4-5-least-privilege.html)。

### 只有命令才能写的文件

有些文件不是规则，而是证据：任务的状态、独立检查的结论（[模型能检查模型吗](5-6-model-checks-model.html)）、快照（在某个时间点对文件做的拷贝）、一次审批所依据的 diff、最终报告。

如果 agent 能写它们，它就能宣布一次检查通过了，或者改掉获批的内容。所以 agent 永远不用它的编辑工具去写这些文件。由命令来写，而命令自己判断结果。“agent 记录了一个结果”的意思是，agent 请命令去记录，而命令做了判断。

存放人带来的东西的文件夹也是一样：文档、参考代码、一次运行的结果。agent 读它们。人（通过一个页面或一条命令）写它们。agent 能编辑的证据，不算证据。

### 熔断器

拒绝不断出现时，agent 可能会一直试。hook 只能拒绝一次调用；它没法让 agent 停下。所以当同一个拒绝连续出现三次时（三是我的设置），**熔断器**就会跳闸，并把理由换成另一条：别再试这个了，去告诉人。它是以消息形式出现的请求，但这是 hook 唯一能做的。它也避免日志里塞满同一条拒绝。

### 人必须打开围栏的时候

有时规则本身必须改。我扩展 harness 的时候，就要改护栏文件。所以必须有一条路进去。怎么把这个权利给出去，又不给 agent？

**不靠 agent。** 我一开始想让一个指定的 agent 去编辑围栏。但在 Copilot 目前的情况下，hook 收到的事件里没有主 agent 的名字（[Hook：每次调用都会经过的执行点](2-2-hooks.html)），所以 hook 分不清是哪个 agent 在调用。任何 agent 都可以冒充那个指定的 agent。跟着名字走的权利，谁用了这个名字谁就能主张。

**按会话，由人来设定。** 依据是会话状态里的一个开关。只有人能打开它，办法是在自己的终端里输入一个验证码。agent 运行不了那条命令，它要是试，hook 会拒绝。这和[两道门：人在哪里审批](5-3-two-approvals.html)里是同一个渠道。

::: figure 4-3-admin

让这个 override 安全的有这几点：

1. **它属于一个会话，不属于某个 agent。** 会话结束，它就结束。
2. **工作做完，就关掉。** 我的规则是把它关掉，然后用 git 读一遍改了什么的 diff。我靠的是这个习惯；我的配置里没有计时器。这是这个设计的弱点：它依赖人记得去做。时间限制是更好的设计，而 git 写入的审批已经在用了。对团队来说，要加上过期时间，再加第二个读 diff 的人。
3. **它会留下记录。** 开着的时候，每条记入日志的调用都标成 admin。
4. **有些门始终关着。** 在我的配置里，即便是 admin 也不能写运行时状态，那里面存着审批记录。如果能写，它就能伪造一次审批。而且同一个会话里不能打开任何任务，也不能调用子 agent。

这几点，每一点都去掉了一种让短暂的例外变成长期漏洞的办法。

### 检验你自己的配置

在你项目的一份拷贝里，让你的 agent 放松它自己 hook 配置里的一条规则。它成功了吗？如果成功了，你的规则就只是请求。然后保护这个文件，再试一次。

## 代价和坑 {#costs-and-traps}

**围栏的好坏，取决于它的清单。** 清单里漏掉的护栏文件，就是敞开的。给引擎增加新部件时，要把它的路径加进去。

**admin 是真正的权力。** 它可以改引擎，所以它做的事没有硬性的限制。控制手段是事后有人读 diff。我不声称更多。

**写法上的缺口依然存在。** 因为终端是靠模式来守的，理论上，一种它不认识的写法，可能改动放在任务文件夹里的记录（任务文件夹存放一项工作；见[管任务，不管对话](5-1-tasks.html)）。我没有试过去造一个。办法还是那个：把绝不能碰的东西，彻底放在够不着的地方。

**看不见的围栏是个谜。** 如果 agent 对一个它不知道受保护的文件，撞上了拒绝，理由里必须说明这一点，以及该怎么办。见上一章。

**agent 多久会尝试编辑规则，我没量过。** 我写这道围栏，是因为这个论证很简单，不是因为我亲眼看到过某次具体的事故。

## 业界怎么说 {#industry}
{status: industry}

VS Code 的 hooks 页面说，hook 和指令不能替代强制执行的权限或沙箱，它的安全页面建议用沙箱，而不是单靠审批规则（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)、[security](https://code.visualstudio.com/docs/copilot/security)）。用 hook 做成的围栏，是在 agent 所运行的同一台机器里面的围栏。这就是这一章说“够不着”而不是“安全”的原因。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

如果 agent 运行的环境里，规则文件是以只读方式挂载的，或者 hook 运行在 agent 碰不到的机器之外，那么受保护路径的清单就不需要了；环境本身就是围栏。另一条经验要保留：人给出的任何 override，都应该绑定到会话，有时间限制，并留下记录。
