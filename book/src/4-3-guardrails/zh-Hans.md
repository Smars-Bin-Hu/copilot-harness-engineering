读这一章，请先读过[询问不是限制](4-2-ask-vs-refuse.html)：限制，就是 agent 辩不过的拒绝。

## 一句话 {#in-one-sentence}

agent 如果能改规则，规则就等于没有。所以要把规则文件和 hook 文件放到它够不着的地方。人给的任何 override，都只管一个会话，会过期，还要留下记录。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定 agent 不许编辑存放它的规则、hook 和证据的那些文件，并且人给的任何 override 都只限一个会话、会过期、会留下记录。
- **风险**：agent 能改的规则，它就能删掉；它能写的“通过”记录，就是它能自己发给自己的通过。我没有事故可以报告，所以这里靠的是论证，不是次数。
- **做对的代价**：一份受保护文件的清单，每加一个新部件就要跟着更新，再加上一个让人有意打开围栏的办法。我自己的 override 靠人记得去关。有时间限制、再有第二个人来读会更好，可这两样我都没有。
- **可以问团队**：“agent 能编辑存放它自己的规则和记录的文件吗？它试的时候，你能给我看一次被拒绝的情形吗？”

## agent 要是改了规则呢？ {#problem}

假设你有一个拒绝危险命令的 hook，它也确实管用。现在问一句：这个 hook 放在哪？放在一个文件里。告诉平台去运行它的配置，同样是一个文件，它用到的那些数字也在文件里。而 agent 手里有编辑工具。

其实 agent 去改这些文件，并不需要什么恶意。设想它被一条拒绝挡住了，又急着把任务做完，它看到规则挡了路，就做了一件看上去很合理的事：把规则放松。agent 能编辑的规则，agent 就能删掉。我没有事故可以报告，也没有量过 agent 多久会尝试编辑规则，所以这里只靠这个论证。

同样，记录也有这个弱点。如果一次检查留下一个“通过”的文件，而 agent 能写这个文件，那它就能让自己通过。所以要问的不只是“哪些命令被拒绝”，还有“谁能改动那些负责拒绝和负责证明的东西”。

不管是规则还是记录，威胁多半来自一个粗心的 agent，而不是怀有恶意的 agent。被注入的文本带偏的 agent 是另一种威胁（[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)），它需要同样的围栏，而且还要更多。

这些必须放在 agent 够不着的地方的文件，我叫它们**护栏文件**。它们合起来是一道围栏，意思是 agent 在里面干活，却挪不动它。那么，哪些文件该围进去？围栏怎么守住？规则本身真要改的时候，人又怎么进去？

读完这一章，如果你只做一件事，那就是让规则文件和 hook 文件对 agent 不可写。

## 围栏怎么搭，人又怎么进去 {#how-it-works}

### 哪些文件是围栏

::: figure 4-3-fence

在我的配置里，围栏由这些文件组成：

- **hook 配置**，告诉平台去运行哪个 hook 的那个文件；
- **引擎**，也就是 hook 本身的代码，以及允许 agent 调用的命令；
- **策略**，存放规则里的数字和模式的普通文件；
- **运行时状态**，hook 运行时写下的文件：会话状态、审批记录和日志；
- 能把 hook 关掉的编辑器设置；
- 仓库的许可证文件。

你也许以为指令文件和 skill 也在清单上，其实不在。它们是写给 agent 读的文本，是请求，不是限制。改了它们，代码会拒绝什么并不会变。

### 围栏是怎么守住的

清单定下来以后，agent 写这些文件的每一条路都得堵上，至于难不难，就要看是什么工具了。编辑工具最好办，因为路径就在调用里，hook 在调用执行之前就能拒绝。

终端就难多了，因为同一次写入可以有很多种写法。hook 能拦住常见的写法，比如重定向、`rm`、`mv`、`sed -i`、`cp`、`tee`。不过[询问不是限制](4-2-ask-vs-refuse.html)里说的那些局限在这里同样存在，所以间接的写法拦不住。

就连路径本身也得小心。同一个文件，可以换个大小写来写，可以带 `..`，可以写成绝对路径，也可以用 Windows 的反斜杠。如果规则拿到路径就直接比较，围栏在写法上就会有缺口，所以它先把这些写法统一成一种形式，再去比较。在你自己的配置里还有两个缺口值得查一查：指向受保护文件夹的符号链接，以及不区分大小写的磁盘。这两个我都没有测过。

还有一条规矩管的是清单本身。公司可以往清单里加路径，但不能把默认的去掉，因为一个能去掉默认项的 override，和一个能编辑规则的 agent 是同一个漏洞。

说到底，这些只防失误，算不上沙箱，因为一个铁了心要绕过去的 agent，先写好一个脚本就能绕过。要更强的做法，见[有些东西根本不给](4-5-least-privilege.html)。

### 只有命令才能写的文件

值得守的文件不只是规则。有些文件是证据：任务的状态、独立检查的结论（[模型能检查模型吗](5-6-model-checks-model.html)）、快照（在某个时间点给文件做的拷贝）、一次审批所依据的 diff，还有最终报告。

这些文件要是 agent 能写，它就能宣布一次检查通过了，或者改掉已经批准的内容。所以它们从不由 agent 的编辑工具来写，而是交给一条命令，结果也由这条命令自己判断。我说“agent 记录了一个结果”，意思是 agent 请命令去记录，拍板的是命令。

人带进来的东西，放在文件夹里也是同样的道理。文档、参考代码、一次运行的结果，都是给 agent 读的。写它们的是人（通过一个页面或一条命令）。agent 能改的证据，就不算证据。

### 熔断器

围栏守住了，又会冒出一个新问题：拒绝一次次出现，agent 可能就一次次地试。hook 没法让它停下来，因为 hook 能做的只有拒绝一次调用。所以，当同一个拒绝连续出现三次（三是我的设置），**熔断器**就会跳闸，把拒绝的理由换成另一条：别再试这个了，去告诉人。这仍然只是一个请求，以消息的形式出现，不过已经是 hook 能做的全部了。另外，它也让日志不会被同一条拒绝塞满。

### 人必须打开围栏的时候

可有时候，规则本身就是得改。我扩展 harness 的时候，就要改护栏文件，所以必须留一条路进去。问题是，怎么把这个权利交给人，又不交给 agent？

我一开始想的是让一个指定的 agent 去编辑围栏。在今天的 Copilot 里这行不通，因为 hook 收到的事件里没有主 agent 的名字（[Hook：每次调用都会经过的执行点](2-2-hooks.html)）。hook 分不清是哪个 agent 在调用，任何 agent 都可以冒充那个指定的 agent。权利跟着名字走，谁用了这个名字，谁就能拿到它。

所以权利改成跟着会话走，由人来设定。它靠的是会话状态里的一个开关，只有人能打开：在自己的终端里输入一个验证码。agent 运行不了那条命令，它要是试，hook 就会拒绝。这和[两道门：人在哪里审批](5-3-two-approvals.html)里用的是同一个渠道。

::: figure 4-3-admin

让这个 override 安全的有四点：

1. 它属于一个会话，不属于某个 agent，所以会话结束，它也就结束了。
2. 工作做完就关掉。我的规则是先把它关掉，再用 git 读一遍改了什么的 diff。
3. 它会留下记录。开着的时候，每一条记入日志的调用都会标成 admin。
4. 即便这时，有些门也始终关着。在我的配置里，就连 admin 也不能写运行时状态，那里面存着审批记录，要是能写，它就能伪造一次审批。而且在同一个会话里，不能打开任何任务，也不能调用子 agent。

每一点都堵上了一条路，免得短暂的例外变成长期的漏洞。不过，第二点同时也是这个设计的弱点：我的配置里没有计时器，关掉 admin 要靠人记得。更好的做法是加时间限制，git 写入的审批就已经这样做了。如果是团队，就要加上过期时间，再加一个读 diff 的第二个人。

### 检验你自己的配置

在你项目的一份拷贝里，让你的 agent 去放松它自己 hook 配置里的一条规则。要是它成功了，你的规则就是一个请求，那就把这个文件保护起来，再试一次。

## 围栏还会在哪里失守 {#costs-and-traps}

通过了这个检验，围栏是不是就万无一失了？还不是，还有三个地方会漏。第一处在清单本身：围栏只守得住清单上列出的文件，漏掉的护栏文件就是敞开的。所以给引擎加新部件的时候，记得把它的路径也加进去。

第二处是穿过围栏的那条路，它本身也是一个缺口。admin 是实打实的权力：它能改引擎，所以它做什么都没有硬性的限制。能管住它的，只有事后有人读一遍 diff，除此之外，我不说它还有别的保障。

第三处在写法上。终端是靠模式来守的，所以理论上，一种它不认识的写法，可能改动放在任务文件夹里的记录（任务文件夹存放一项工作；见[管任务，不管对话](5-1-tasks.html)）。我没有试过去造这样一种写法。办法还是那一个：把绝不能碰的东西，彻底放到够不着的地方。

还有一个坑，算不上漏洞：围栏要是 agent 看不见，它撞上了也不知道为什么被拦。这时，拒绝的理由里就得说明这个文件受保护，并说清该怎么办。这个理由怎么写，上一章讲过。

## 为什么说“够不着”，而不说“安全” {#industry}
{status: industry}

那么，用 hook 搭起来的围栏，能信到什么程度？VS Code 的 hooks 页面说，hook 和指令不能替代强制执行的权限或沙箱；它的安全页面也建议用沙箱，而不是单靠审批规则（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)、[security](https://code.visualstudio.com/docs/copilot/security)）。问题在于，用 hook 搭的围栏，和 agent 立在同一台机器上。所以这一章只说“够不着”，不说“安全”。

## 什么时候可以删掉受保护路径的清单 {#when-to-delete-it}
{status: industry}

同一个道理，也告诉你这份清单什么时候可以删。如果 agent 运行的环境里，规则文件是只读挂载的，或者 hook 运行在 agent 碰不到的那台机器之外，受保护路径的清单就用不着了，因为环境本身就是围栏。另一条经验到那时也要留着：人给出的任何 override，都应该绑定到会话、有时间限制，并且留下记录。

## 在你自己的环境里试试 {#try-it}

::: prompt
找出这个项目里，定义了 agent 可以做什么、不可以做什么的每一个文件：指令文件、hook 脚本及其配置、权限设置、编辑器设置，以及任何记录一次检查或一次审批的文件。对每一个，根据你能看到的规则和权限，告诉我 agent 自己的编辑工具和终端今天能不能改动它。输出一份清单，按“这个文件被改了有多糟”来排序。不要修改任何文件，也不要为了确认而去尝试编辑它们。
:::
