讀這一章，你需要讀過 [agent 循環，和你能插手的地方](2-1-agent-loop.html)，或者知道 agent 是靠要求工具呼叫來運作的。

## 一句話 {#in-one-sentence}

hook 是平台在每一輪的固定位置執行的程式碼，子 agent 裡面也一樣。硬規則就放在這裡，不過它看到的是呼叫，不是指令執行起來會做什麼。

## 給主管 {#for-leaders}

- **要做的決定**：決定哪些規則必須每次都成立，把它們放進 hook（平台在每次工具呼叫時執行的程式碼），而不是寫在 prompt 裡。
- **風險**：hook 看到的是呼叫的文字，不是指令執行起來會做什麼，它也可能悄悄失效。依我 2026 年 10 月看到的 Copilot，逾時的 hook 算通過，啟動不了的 hook 則會擋掉所有工具。在一台機器上的一小批樣本裡，大約三分之一的 prompt 到達模型時，沒有帶著 hook 本來要加上的規則。這個數字讀成「很多」就好，不要當成比率。
- **做對的成本**：一個小程式和一個設定檔，放在程式碼審查之下。我的通常在幾十毫秒內執行完。
- **可以問團隊**：「hook 很慢或壞掉的時候，我們的規則會怎樣？我們怎麼知道模型真的收到了它們？」

## 怎樣讓一條規則每次都成立？ {#problem}

你寫了一條規則：「絕不要改設定資料夾裡的檔案」。agent 遵守了九次。到了第十次，它正埋頭做一個任務，上下文已經很長，那條規則離得很遠，於是它改了那個檔案。會這樣，是因為規則只是一句話，模型可以把它和其他句子放在一起權衡。這一次，它把這句話看得比較輕。

所以你需要的，是一樣不靠模型的記憶、也不看模型心情的東西：一段每次工具呼叫都必須經過、而且會說「可以」或「不行」的程式碼。這就是 **hook**。

hook 是你寫的小程式，由平台在固定的時刻替你執行。每到一個時刻，平台就交給它一段 JSON（一種表示資料的純文字格式），說明正在發生什麼事，例如「agent 想執行這個指令」。hook 也用 JSON 回答，平台再依照這個答案行動。執行 hook 的是平台，不是模型，所以模型沒辦法跳過它。

不過，我在 hook 上學到的第一課，正好來自一個沒有作用的 hook。我用它在每個 prompt 開頭，把 harness 的規則放到模型面前。表面上看它好好的，每次都執行了，輸出看起來也對。可是等我去看模型實際收到什麼，2026 年 10 月在一台機器上的一小批 prompt 裡，大約三分之一根本沒有規則（確切的數字我沒有留，所以「三分之一」讀成「很多」就好，不要當成比率）。hook 回傳的答案沒錯，卻什麼也沒發生。後來查清楚，問題出在 VS Code 自己：它會在 prompt 裡加上自己的提醒，這些提醒占掉了 hook 用的那個位置。我的修法，是在文字送給模型之前的最後一關，再檢查一次。那裡看得到整段文字，規則如果不在，就把它們補回去。

這一課適用於每個 hook：**要檢查模型真正收到什麼，而不是 hook 回傳什麼**。既然一個每次都執行的 hook 也會這樣失效，就值得弄清楚 hook 到底能做什麼、還會怎樣失效，以及有哪些東西它根本看不到。

## hook 能做什麼，做不到什麼？ {#how-it-works}

### hook 在什麼時候執行

::: figure 2-2-hook-points

hook 只在平台提供的時刻執行。下面是我用的那幾個，名字是 VS Code 在它的文件裡給的。

| 時刻 | 發生什麼 | 我拿它做什麼 |
| --- | --- | --- |
| 會話開始 | 新的對話開始 | 把這個會話的基本事實給模型 |
| 送出 prompt | 你按了 Enter | 加上規則；記下這是哪個任務 |
| **工具呼叫之前** | 模型提出了要求；什麼都還沒執行 | **拒絕一次呼叫**。每條硬規則都在這裡 |
| 工具呼叫之後 | 工具已經執行了 | 留下紀錄；加一則備註 |
| 子 agent 開始或結束 | 幫手 agent 開始或結束 | 把它要的那一包材料交給它；記下結束 |
| agent 快要停下來 | 模型寫出了回答 | 還有工作沒做完，就說一次「還沒」 |

這些時刻裡，只有工具呼叫之前這一個能拒絕某個具體的動作。一條規則需要的，是一個已經存在、卻還沒發生的呼叫，只有這個時刻才有。其他時刻能看、能記錄，也能加一些文字。（停止的時刻也可以說「還沒」，下面會講，但那不是在拒絕一個動作。）想親眼看到這些時刻，可以做這一節結尾的那個小測試。

### 什麼進去，什麼出來

那麼在這樣一個時刻，hook 實際拿到的是什麼？是一段 JSON，寫著這是哪個事件、哪個會話；如果是工具呼叫，還有工具名稱和它的參數。下面是從 VS Code 記錄下來的真實樣本，是一個指令執行完之後，hook 收到的東西：

::: code harness .harness/eval/fixtures/hooks/copilot-sdk/payloads/PostToolUse.Bash.json L1-L15 "hook 在終端機指令之後收到的東西：事件、工具名稱、參數和結果。"

hook 也用 JSON 回答。真正有用的答案其實只有三種：

- 放行。空的答案算沒意見，平台正常的權限檢查照樣適用。
- 拒絕，附上原因。這次呼叫不會執行，原因會顯示給模型，也顯示給你看。
- 加幾句話給模型讀，例如一則提醒、一行狀態。

到了停止的時刻，還有第四種：擋下這次停止，附上一個原因，這個原因會像新的 prompt 一樣餵回給模型。我每次停止只允許這樣做一次，因為每次停止都擋的 hook，會讓 agent 永遠跑下去，每一輪還都要你付錢。

**原因是設計的一部分**。拒絕的時候要寫清楚為什麼不行、該改做什麼，不然 agent 會再試同一件事，甚至做出更糟的事（[詢問不是限制](4-2-ask-vs-refuse.html)）。

### hook 出錯的三種方式

上面說的這些，前提都是 hook 本身沒問題。可是 hook 也是軟體，總會出錯。出錯的時候平台怎麼處理，決定了你的規則是圍欄，還是裝飾。

| 發生什麼 | Copilot 怎麼做（我在 2026 年 10 月觀察到的，也是 VS Code 文件說的） |
| --- | --- |
| hook 執行了並拒絕 | 呼叫被擋下，原因顯示出來。在預設模式，以及跳過權限提示的模式下都有效。 |
| hook 啟動不了（例如寫它用的語言沒裝） | 當成拒絕：沒有任何工具能執行，畫面上也只說「hook 出錯」之類的話。 |
| hook 花太久 | 當成通過，而且沒有任何通知。VS Code 文件說，它會退回到正常的權限檢查。 |

所以同一種失敗，可能把你鎖在外面，也可能讓門開著，就看它是怎麼失敗的。你寧可要哪一種，是設計上的選擇。這個選擇該怎麼做，[把執行層當軟體來設計](4-4-enforcement-design.html) 裡有講。那裡也寫了我的選擇：放行這次呼叫並記錄錯誤，最近最慢的一次呼叫接近時間上限時發出警告。

### 在子 agent 裡面

子 agent 是為了一部分工作而啟動的第二個 agent（[慎用子 agent](2-3-subagents.html)）。它在自己的會話裡執行，你也許會以為 hook 就管不到它了。其實在今天的 Copilot 裡，它的工具呼叫一樣會經過 hook，事件裡還帶著父會話的 id。所以為主 agent 設的規則，對它啟動的幫手也成立。別的平台我還沒測過，所以換了平台，我不會這樣假設。

### hook 看不到什麼

hook 看不到什麼，是這一章裡我最希望你記住的部分。

::: figure 2-2-blind-spot

**它看到的是呼叫，不是效果**。對終端機指令，hook 讀的是指令的文字，看得到「寫入這個路徑」。可是它看不到用變數拼出來的路徑，也看不到一分鐘前才寫好、現在才執行的腳本。指令一旦被放行，hook 就不在畫面裡了。因此終端機指令上的 hook，擋得住常見的寫法，卻擋不住一個一心要繞過它的 agent。VS Code 文件也這麼說：hook 是可執行的程式碼，不能代替強制的權限或沙箱。那些絕不能被碰的東西，就不要只靠 hook（[有些東西根本不給](4-5-least-privilege.html)）。

就算是它看得到的呼叫，hook 也不知道是哪個 agent 發出的。在今天的 Copilot 裡，事件不帶主 agent 的名字，所以「這個 agent 被允許」不能成為規則，因為任何 agent 都可以冒充它。如果權限必須有所不同，就得來自 agent 自己設不了的東西，例如由人在終端機裡打開的開關。

還有一些呼叫，hook 根本看不到，因為它並不是到處都會執行。在我的測量裡，用 Copilot 的命令列模式（沒有視窗）時，倉庫的 hook 沒有執行；一個看起來像關閉開關的設定，在較新的會話裡也沒能擋住它們。公司的政策也可以為一個工作區關掉 hook，就連改了 hook 檔，也要重新載入才會生效，因為這個檔案是在視窗啟動時讀的。這些是我 2026 年 10 月找到的事實，它們會變，所以請看平台目前的文件。

最後，就算 hook 執行了、也給了回答，它的訊息還是可能丟掉。這就是開頭那個故事：hook 的輸出可能永遠到不了模型。所以要測的是訊息有沒有送達，而不只是 hook 本身。

### 迴圈裡其他站著的東西

那麼，站在模型和外面世界之間的，只有 hook 嗎？並不是。**包裝器**（你呼叫來代替原始指令的小程式）、**MCP server**（[MCP server：插工具的標準接口](1-3-mcp.html)），以及平台和模型之間的**代理**，也都站在那裡。但它們每一個都只看得到經過自己的東西，agent 可以繞過它們。hook 的不同在於，平台保證會呼叫它。內建工具和子 agent，我看過每次呼叫都經過它，不過 MCP 工具我沒有測過。

### 三個問題和一個小測試

想把這些用在你自己的設定上，可以對任何一條你在乎的規則問三個問題。

1. 它是寫在 prompt 裡，還是 hook 裡？如果在 prompt 裡，它就是請求。
2. 規則被破壞時，hook 看到什麼？呼叫的文字，還是效果？
3. hook 自己壞掉或很慢的時候，會怎樣？

另外還有一個今天就能跑的測試。寫出你的平台允許的最小 hook，它只做一件事，把事件名稱和工具名稱附加到一個檔案裡。然後用你的 agent 做一件小任務，再去讀這個檔案。你會依序看到上面表格裡的每個時刻，也數得出一共有幾個，這是理解迴圈最快的辦法。檔案格式請照 [VS Code hooks 文件](https://code.visualstudio.com/docs/copilot/customization/hooks)。

## hook 要付出什麼，要提防什麼 {#costs-and-traps}

上面三種失敗裡，對團隊最重要的是逾時，因為逾時就是無聲的通過。規則沒有被執行，卻沒有人被告知。所以要留意你的 hook 花多少時間；在決定失敗時怎麼辦之前，也請先讀 [把執行層當軟體來設計](4-4-enforcement-design.html)。

時間重要，還有另一個原因。hook 每次呼叫都會執行，它慢，一切都慢。我的通常幾十毫秒。要讓它便宜，並且限制它能做的事。

hook 也是你必須信任的程式碼。它在你的機器上執行，agent 送來什麼它都讀，所以絕不要在 hook 裡把 agent 的文字直接放進 shell 指令。在團隊裡，hook 檔要像任何其他守著東西的程式碼一樣對待，改動都要經過審查。另外，hook 在 VS Code 裡還是 Preview，平台一變，它的行為也可能跟著變。失敗表裡寫的只是我看到的，每次更新後都該再確認一次。

最後一個陷阱在原因本身：它也可能寫得太好。一個把怎麼繞過規則說得清清楚楚的拒絕，等於在教模型去那樣做。要說該改做什麼，而不是說怎麼閃躲。

## 平台文件怎麼說？ {#industry}
{status: industry}

VS Code 列出了我用的那些時刻（會話開始、送出 prompt、工具前後、子 agent 開始和結束、agent 停止），並說明 `preToolUse` hook 可以回傳一個附原因的拒絕。它也指出逾時會退回到正常的權限檢查，這個功能也還在 Preview。（[Agent hooks in VS Code](https://code.visualstudio.com/docs/copilot/customization/hooks)）

我在這裡沒有詳細比較其他平台的 hook，那些平台的事件名稱不同，涵蓋的範圍也不同。

## 哪些可以刪，什麼時候刪 {#when-to-delete-it}
{status: industry}

只要平台還允許 prompt 裡的規則被忽略，規則用的 hook 就會留著，因為背後的道理不會退役。我最先會刪的，是各種繞路的做法。等平台能可靠地送達 hook 的輸出，那道把遺失的規則補回去的檢查就可以拿掉；等逾時改成會被回報，不再無聲通過，計時的監看也可以拿掉。如果有一天平台提供原生的、強制執行的政策（一個它自己檢查的規則檔），我會把硬規則搬到那裡，hook 留給紀錄和提醒。
