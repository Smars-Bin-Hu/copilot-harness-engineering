读这一章，需要你读过[Agent 到底是怎么干活的？](2-1-agent-loop.html)，或者知道 agent 是靠发出工具调用来工作的。

## 一句话 {#in-one-sentence}

hook 是平台在每一轮的固定位置运行的代码，子 agent 里也一样。硬性规则就放在这里，不过它看得到的是调用，看不到命令运行起来之后做了什么。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定哪些规则必须每次都成立，把它们放进 hook（平台在每次工具调用时运行的代码），而不是写在 prompt 里。
- **风险**：hook 只看得到调用的文本，它也可能悄悄失效。按我在 2026 年 10 月看到的 Copilot，超时的 hook 算通过，启动不了的 hook 则会挡住所有工具。在一台机器上的一小批 prompt 里，约三分之一送到模型时没有带上 hook 本该加进去的规则。
- **做对的代价**：一个小程序，加一个配置文件，放在代码审查之下。
- **可以问团队**：“hook 慢了或者坏了，我们的规则会怎么样？我们怎么知道模型真的收到了它们？”

## 怎样让一条规则每次都成立？ {#problem}

你写了一条规则：“永远不要改配置文件夹里的文件”。agent 遵守了九次。到了第十次，它正埋头在一个任务里，上下文已经很长，那条规则离得很远，于是它改了那个文件。之所以会这样，是因为规则只是一句话，模型会把它和别的话放在一起掂量。这一次，它掂量得轻了。

所以你需要的，是一样不靠模型记性、也不看模型心情的东西：一段每次工具调用都必须经过、并且会说行或不行的代码。这就是 **hook**。

hook 是你写的一个小程序，由平台在固定的时机替你运行。每到一个时机，平台交给它一段 JSON（一种表示数据的纯文本格式），说明正在发生什么，比如“agent 想运行这条命令”。hook 同样用 JSON 回答，平台再按这个回答行事。运行 hook 的是平台，不是模型，所以模型跳不过它。

不过，我在 hook 上学到的第一课，恰恰来自一个没起作用的 hook。我用它在每个 prompt 开头把 harness 的规则放到模型面前。表面上看它好好的，每次都运行了，输出看着也对。可是等我去看模型实际收到了什么，2026 年 10 月在一台机器上的一小批 prompt 里，约有三分之一根本没有规则（“三分之一”理解为“不少”就好，别当成比率）。后来查明，问题出在 VS Code 自己：它会往 prompt 里加自己的提醒，这些提醒占掉了 hook 用的那个位置。我的修法是在文本送到模型之前的最后一道关口，再检查一次。那里能看到全部文本，规则要是不在，就把它们补回去。

这个教训对每个 hook 都适用：**要检查模型收到了什么，而不是 hook 返回了什么**。可是，一个每次都运行的 hook 尚且会这样失效，它还会怎样失效？又有哪些东西它根本看不到？

## hook 能做什么，做不到什么？ {#how-it-works}

### hook 在什么时候运行

::: figure 2-2-hook-points

hook 只在平台提供的时机运行。下面是我用到的几个，名字是 VS Code 在它文档里起的。

| 时机 | 发生了什么 | 我拿它做什么 |
| --- | --- | --- |
| 会话开始 | 一个新对话开始 | 把这次会话的基本情况告诉模型 |
| 发出 prompt | 你按下回车 | 加上规则；记下这是哪个任务 |
| **工具调用之前** | 模型提出了请求；还没有运行任何东西 | **拒绝一次调用**。所有硬性规则都在这里 |
| 工具调用之后 | 工具已经运行 | 留一份记录；加一条备注 |
| 子 agent 启动或停止 | 一个帮手 agent 开始或结束 | 把它的材料交给它；记下结束 |
| agent 即将停止 | 模型写完了一个回答 | 如果还有活没干完，说一次“还没完” |

这些时机里，只有工具调用之前这一个能拒绝某个具体的动作。一条规则需要的，是一个已经存在、却还没有发生的调用，而只有这个时机才有。其他时机能观察、能记录，也能添几句话。（停止的时机也能说“还没完”，下面会讲，但那不是在拒绝某个动作。）想亲眼看看这些时机，可以做这一节末尾的那个测试。

### 进去什么，出来什么

那么在这样一个时机，hook 实际拿到的是什么？是一段 JSON，里面写着这是什么事件、哪个会话；如果是工具调用，还有工具名和它的参数。下面是从 VS Code 录下来的一个真实样本，是一条命令运行完之后 hook 收到的内容：

::: code harness .harness/eval/fixtures/hooks/copilot-sdk/payloads/PostToolUse.Bash.json L1-L15 "hook 在一条终端命令运行完之后收到的内容：事件、工具名、参数和结果。"

hook 也用 JSON 回答，有用的回答只有三种：

- 放行。空的回答算没有意见，平台正常的权限检查照样生效。
- 拒绝，并附上原因。这次调用不会运行，原因会显示给模型，也显示给你。
- 加几句话给模型读，比如一条提醒、一行状态。

到了停止的时机，还有第四种：挡住这次停止，并附上一个原因，这个原因会像一个新的 prompt 一样喂回给模型。我每次停止只允许挡一次，因为每次停止都挡的 hook 会让 agent 永远跑下去，每一轮还都得你付钱。

**原因是设计的一部分**。拒绝的时候要说清楚为什么不行、应该改做什么，否则 agent 会再试同样的事，甚至做出更糟的事（[“先问我”为什么挡不住 Agent？](4-2-ask-vs-refuse.html)）。

### hook 出问题的三种方式

上面说的这些，前提都是 hook 本身好好的。可 hook 也是软件，它总会出问题。出问题时平台怎么处理，决定了你的规则是围栏，还是摆设。

| 发生了什么 | Copilot 怎么处理（我在 2026 年 10 月观察到的，也是 VS Code 文档里说的） |
| --- | --- |
| hook 运行了，并且拒绝 | 调用被拦住，原因会显示出来。这在默认模式下有效，在跳过权限提示的模式下也有效。 |
| hook 启动不了（比如它所用的语言没有安装） | 当作拒绝：没有任何工具能运行，屏幕上除了“hook 出错”，几乎没有别的说明。 |
| hook 花的时间太长 | 当作通过，不吭声。 |

所以，hook 坏了的时候，是该把你锁在门外，还是让大门敞开，这是一个设计选择。这个选择该怎么做，[hook 自己出故障了怎么办？](4-4-enforcement-design.html)里有讲。那里也写了我的选择：放行这次调用并记下错误，最近最慢的一次调用接近时间上限时发出警告。

### 在子 agent 里

子 agent 是为了某一部分工作而开的第二个 agent（[别跟风瞎用子 Agent](2-3-subagents.html)）。它在自己的会话里运行，你也许会以为 hook 就管不到它了。其实在今天的 Copilot 里，它的工具调用同样会经过 hook，事件里还带着父会话的 id。所以给主 agent 定的规则，对它开的帮手也成立。

### hook 看不到什么

这一章所有内容里，这一部分是我最想让你记住的。

::: figure 2-2-blind-spot

**它看到的是调用，不是效果**。对终端命令，hook 读的是命令的文本，它能看到“写入这个路径”。可它看不到用变量拼出来的路径，也看不到一个一分钟前才写好、现在才运行的脚本。命令一旦被放行，hook 就出局了。所以针对终端命令的 hook，拦得住常见的写法，却拦不住铁了心要绕过它的 agent。VS Code 文档说的也是这一点：hook 是可执行的代码，不能替代强制执行的权限或沙箱。那些绝对不能碰的东西，就别只靠 hook（[不要开放全部的权限或使用沙箱](4-5-least-privilege.html)）。

就算是它看得到的调用，hook 也不知道是哪个 agent 发出的。在今天的 Copilot 里，事件里没有主 agent 的名字，所以“这个 agent 被允许”做不成规则，因为任何 agent 都可以冒充它。如果权限必须有所不同，就得来自 agent 自己设置不了的东西，比如由人在终端里打开的开关。

还有一些调用，hook 根本看不到，因为它并不是到处都会运行。2026 年 10 月我测的时候，在 Copilot 的命令行模式（没有窗口）下，仓库里的 hook 没有运行；有一个看起来像关闭开关的设置，在较新的会话里也并没有让它们停下来。公司策略也可以为某个工作区关掉 hook，就连改了 hook 文件，也得重新加载才生效，因为这个文件是在窗口启动时读的。

最后，就算 hook 运行了、也给出了回答，它的消息还是可能在送往模型的路上丢掉，就像这一章开头那个故事。

### 循环里其他站岗的东西

那么，站在模型和外部世界之间的，只有 hook 吗？并不是。**包装器**（一个你调用它、而不是调用原始命令的小程序）、**MCP server**（[接 MCP server 之前，要想清楚什么？](1-3-mcp.html)），以及平台和模型之间的**代理**，也都站在那里。但它们每一个都只看得到经过自己的东西，agent 可以绕开它们。hook 的不同之处在于，平台承诺会调用它。对内置工具和子 agent，我见过每次调用都经过它，不过 MCP 工具我没有测过。

### 一个今天就能做的测试

写一个你的平台允许的最小的 hook，它只做一件事，把事件名和工具名追加到一个文件里。然后用你的 agent 做一个小任务，再去读那个文件。你会按顺序看到上面表格里的每个时机，也能数出一共有多少个，这是理解循环最快的办法。文件格式请看 [VS Code hooks 文档](https://code.visualstudio.com/docs/copilot/customization/hooks)。

## hook 要付出什么，要提防什么 {#costs-and-traps}

上面三种故障里，在团队里最要紧的是超时，因为超时就是悄悄放行。所以要盯着你的 hook 花多长时间。

时间要紧，还有另一个原因。hook 在每次调用上都运行，它要是慢，一切都慢。我的通常几十毫秒。让它保持廉价，并且限制它能做的事。

hook 还是你必须信任的代码。它在你的机器上运行，agent 发来什么它都读，所以永远不要把 agent 的文本直接放进 hook 里的 shell 命令。在团队里，hook 文件要像任何其他守着东西的代码一样对待，改动都要经过审查。另外，hook 在 VS Code 里还是 Preview，平台一变，它的行为也可能跟着变。这一章讲的 Copilot 行为，都只是我看到的，每次更新之后都该再查一遍。

最后一个坑在原因本身：它可能写得太好。一个把怎么绕过规则解释得清清楚楚的拒绝，等于在教模型这么做。要说该改做什么，而不是说怎么躲。

## 平台文档怎么说？ {#industry}
{status: industry}

VS Code 列出了我用到的那些时机（会话开始、提交 prompt、工具前后、子 agent 的启动和停止、agent 停止），并说明 `preToolUse` hook 可以返回带原因的拒绝。它还指出，超时会回落到正常的权限检查，这个功能也还是 Preview。（[Agent hooks in VS Code](https://code.visualstudio.com/docs/copilot/customization/hooks)）

## 哪些可以删，什么时候删 {#when-to-delete-it}
{status: industry}

只要平台还允许 prompt 里的规则被忽略，针对规则的 hook 就要留着。我最先会删的，是那些绕弯的补丁。等平台能可靠地送达 hook 的输出，那道把丢掉的规则补回去的检查就可以去掉；等超时会被报告出来，而不是悄悄放行，对耗时的监控也可以去掉。如果哪天平台提供了原生的、强制执行的策略（一个它自己会检查的规则文件），我会把硬性规则搬到那里，hook 留给记录和提醒。
