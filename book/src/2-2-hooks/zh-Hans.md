读这一章，需要你读过[agent 循环，以及你能插手的地方](2-1-agent-loop.html)，或者知道 agent 是靠发出工具调用来工作的。

## 一句话 {#in-one-sentence}

hook 是平台在每一轮的固定位置运行的代码，子 agent 里也一样。硬性规则就放在这里。它看得到调用，看不到命令运行起来之后做了什么。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定哪些规则必须每次都成立，把它们放进 hook（平台在每次工具调用时运行的代码），而不是放在 prompt 里。
- **风险**：hook 看到的是调用的文本，看不到命令运行起来之后做了什么。它也可能悄悄失效。按我在 2026 年 10 月看到的 Copilot，超时的 hook 算通过，启动不了的 hook 会挡住所有工具。在一台机器上的一小批 prompt 里，约三分之一送到模型时，没有 hook 本该加上的规则；把它理解为“不少”，不要当成比率。
- **做对的代价**：一个小程序，加一个配置文件，放在代码审查之下。我的通常几十毫秒就跑完。
- **可以问团队**：“hook 慢了或者坏了，我们的规则会怎么样？我们怎么知道模型真的收到了它们？”

## 问题 {#problem}

你写了一条规则：“永远不要改配置文件夹里的文件”。agent 遵守了九次。第十次，它正深陷一个任务，上下文很长，规则离得很远。它改了那个文件。规则只是一句话，模型可以把它和别的话放在一起掂量，而这一次，它掂量得轻了。

你需要的是不依赖模型记性或心情的东西：一段每次工具调用都必须经过的代码，说行或者不行。这就是 **hook**。

hook 是你写的一个小程序，平台在固定时机替你运行它。平台交给它一段 JSON（一种表示数据的纯文本格式），说明正在发生什么，比如“agent 想运行这条命令”。hook 同样用 JSON 回答。然后平台按这个回答行事。模型不会运行 hook，也跳不过它。

我的第一个教训，来自一个没起作用的 hook。我用一个 hook，在每个 prompt 开头，把 harness 的规则放到模型面前。它每次都运行，输出看着也对。但是我去看模型实际收到了什么时，在 2026 年 10 月一台机器上的一小批 prompt 里，约有三分之一里没有规则。确切的数我没有记下来，所以把“三分之一”理解为“不少”，不要当成比率。VS Code 会往 prompt 里加它自己的提醒，这些提醒占掉了 hook 用的那个位置。hook 返回了正确的答案，却什么也没发生。我的修法是，在文本送到模型之前的最后一个点上再加第二道检查，那里能看到全部文本，如果规则不在，就把它们补回去。

这个教训适用于每个 hook：**检查模型实际收到了什么，而不是 hook 返回了什么。** 这一章其余的部分，讲 hook 能做什么、怎么失效、看不到什么。

## 原理 {#how-it-works}

### 那些时机

::: figure 2-2-hook-points

平台提供一张时机的清单。下面是我用到的几个，名字是 VS Code 在它文档里起的。

| 时机 | 发生了什么 | 我拿它做什么 |
| --- | --- | --- |
| 会话开始 | 一个新对话开始 | 把这次会话的基本情况告诉模型 |
| 发出 prompt | 你按下回车 | 加上规则；记下这是哪个任务 |
| **工具调用之前** | 模型提出了请求；还没有运行任何东西 | **拒绝一次调用**。所有硬性规则都在这里 |
| 工具调用之后 | 工具已经运行 | 留一份记录；加一条备注 |
| 子 agent 启动或停止 | 一个帮手 agent 开始或结束 | 把它的材料交给它；记下结束 |
| agent 即将停止 | 模型写完了一个回答 | 如果还有活没干完，说一次“还没完” |

只有工具调用之前这个时机，能拒绝某一个具体的动作。规则需要的东西它都有：调用已经存在，但还没有发生。其他时机可以观察、记录、添几句话。（停止的时机也能说“还没完”，下面会讲，但那不是对某个动作的拒绝。）你可以用本章末尾的小测试，亲眼看看这些时机。

### 进去什么，出来什么

hook 收到的是 JSON：这是什么事件、哪个会话，如果是工具调用，还有工具名和它的参数。下面是从 VS Code 录下来的一个真实样本，是一条命令运行完之后，hook 收到的内容：

::: code harness .harness/eval/fixtures/hooks/copilot-sdk/payloads/PostToolUse.Bash.json L1-L15 "hook 在一条终端命令运行完之后收到的内容：事件、工具名、参数和结果。"

hook 用 JSON 回答。真正有用的回答其实只有三种：

- **放行**。（空的回答算没有意见。平台正常的权限检查仍然适用。）
- **拒绝，并附上原因**。这次调用不会运行。原因会显示给模型，也显示给你。
- **加几句话**给模型读：一条提醒，一行状态。

在停止的时机，还有第四种：挡住这次停止，并附上一个原因，这个原因会像一个新 prompt 一样喂回给模型。我每次停止只允许挡一次。每次停止都挡的 hook，会让 agent 永远运行下去，而每一轮你都得付钱。

**原因是设计的一部分**。要说明为什么拒绝、应该改做什么，否则 agent 会再试同样的事，或者更糟的事（[询问不是限制](4-2-ask-vs-refuse.html)）。

### hook 出问题的三种方式

hook 是软件，它会出问题。出问题时平台怎么处理，决定了你的规则是围栏，还是摆设。

| 发生了什么 | Copilot 怎么处理（我在 2026 年 10 月观察到的，也是 VS Code 文档里说的） |
| --- | --- |
| hook 运行了，并且拒绝 | 调用被拦住，原因会显示出来。这在默认模式下有效，在跳过权限提示的模式下也有效。 |
| hook 启动不了（比如它所用的语言没有安装） | 当作拒绝：没有任何工具能运行，屏幕上除了“hook 出错”，几乎没有别的说明。 |
| hook 花的时间太长 | 当作通过，不吭声。VS Code 文档的说法是，回落到正常的权限检查。 |

所以同一种故障，可能把你锁在门外，也可能让大门敞开，取决于它是怎么失败的。你想要哪一种，是一个设计选择。该怎么选，以及我选了什么（放行这次调用并记下错误，最近最慢的一次调用接近时间上限时发出警告），是[把执行层当软件来设计](4-4-enforcement-design.html)的主题。

### 在子 agent 里

子 agent 是为了某一部分工作而开的第二个 agent（[慎用子 agent](2-3-subagents.html)）。它在自己的会话里运行。在今天的 Copilot 里，它的工具调用也会经过 hook，事件里还带着父会话的 id。所以给主 agent 定的规则，对它开的帮手也成立。换一个平台，我不会不经测试就这样假设。我没有测过。

### hook 看不到什么

这是我最想让你记住的部分。

::: figure 2-2-blind-spot

**它看到的是调用，不是效果**。对终端命令，hook 读的是命令的文本。它能看到“写入这个路径”。它看不到用变量拼出来的路径，也看不到一个一分钟前才写好、现在才运行的脚本。命令一旦被放行，hook 就出局了。所以，针对终端命令的 hook，能拦住常见的写法。拦不住铁了心要绕过它的 agent。VS Code 文档说的也是这一点：hook 是可执行的代码，不能替代强制执行的权限或沙箱。对那些绝对不能碰的东西，不要只靠 hook（[有些东西根本不给](4-5-least-privilege.html)）。

**它不知道是哪个 agent 在调用**。在今天的 Copilot 里，事件里没有主 agent 的名字。所以“这个 agent 被允许”做不成规则：任何 agent 都可以冒充它。如果权限必须不同，就得来自 agent 设置不了的东西，比如由人在终端里打开的开关。

**它不是到处都会运行**。在我的测量里，我用 Copilot 的命令行模式（没有窗口）时，仓库里的 hook 没有运行。有一个看起来像关闭开关的设置，在较新的会话里并没有让它们停下来。公司策略可以为某个工作区关掉 hook。而且 hook 文件是在窗口启动时读的，所以改了之后要重新加载。这些是我在 2026 年 10 月发现的情况；它们会变。请看平台当前的文档，文档里也说 hook 现在还是 Preview。

**它可能丢掉自己的消息**。开头那个故事：hook 的输出可能根本没到达模型。要测消息有没有送到，不只是测 hook。

### 循环里其他站岗的东西

hook 不是模型和外部世界之间唯一的东西。**包装器**（一个你调用它而不是调用原始命令的小程序）、**MCP server**（[MCP server：接工具的标准接口](1-3-mcp.html)），以及平台和模型之间的**代理**，每个都只看得到经过它们的东西，而 agent 可以绕过它们。区别在于：平台承诺会调用 hook。对内置工具和子 agent，我见过每次调用都经过它；MCP 工具我没有测过。

### 测一测你自己的配置

对任何你在乎的规则，问**三个问题**：

1. 它是写在 prompt 里，还是写在 hook 里？如果在 prompt 里，它就是请求。
2. 规则被违反时，hook 看到的是什么？调用的文本，还是效果？
3. hook 自己坏了或者慢了，会怎么样？

**一个今天就能做的测试**。写出你的平台允许的最小的 hook。它只把事件名和工具名追加到一个文件里。用你的 agent 做一个小任务，然后读那个文件。你会按顺序看到上面表格里的每个时机，以及一共有多少个。这是理解循环最快的办法。文件格式请看 [VS Code hooks 文档](https://code.visualstudio.com/docs/copilot/customization/hooks)。

## 代价和坑 {#costs-and-traps}

**超时就是悄悄放行**。上面三种故障里，这一种在团队里最要紧：规则没有强制执行，却没人知道。盯着你的 hook 花多长时间，并在选择失败时怎么处理之前，先读[把执行层当软件来设计](4-4-enforcement-design.html)。

**hook 在每次调用上都运行**。它如果慢，一切都慢。我的通常几十毫秒。让它保持廉价，并限制它能做什么。

**hook 是你必须信任的代码**。它在你的机器上运行，读 agent 发来的任何东西。永远不要把 agent 的文本直接放进 hook 里的 shell 命令。在团队里，把 hook 文件当作任何其他守着什么东西的代码：通过审查来改。

**hook 是一个仍在变化的平台上的功能**。VS Code 把它标为 Preview。我在故障表里写的是我看到的；每次更新之后都再查一遍。

**原因可能写得太好**。一个把怎么绕过规则解释得清清楚楚的拒绝，等于教模型这么做。说该做什么，不要说怎么躲。

## 业界怎么说 {#industry}
{status: industry}

VS Code 列出了我用到的那些时机（会话开始、提交 prompt、工具前后、子 agent 的启动和停止、agent 停止），并说明 `preToolUse` hook 可以返回带原因的拒绝。它还指出，超时会回落到正常的权限检查，而且这个功能还是 Preview。（[Agent hooks in VS Code](https://code.visualstudio.com/docs/copilot/customization/hooks)）

我在这里没有把它和其他平台的 hook 做详细比较。它们的事件名和覆盖的范围都不一样。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

只要平台还允许 prompt 里的规则被忽略，针对规则的 hook 就要留着。背后的道理不会退役。我最先删的，是那些绕弯的补丁：等平台能可靠地送达 hook 的输出，为丢失注入而加的第二道检查就可以去掉；等超时会被报告，而不是悄悄放行，对耗时的盯防就可以去掉。如果哪天平台提供原生的、强制执行的策略（一个它自己会检查的规则文件），我会把硬性规则搬到那里，hook 留给记录和提醒。
