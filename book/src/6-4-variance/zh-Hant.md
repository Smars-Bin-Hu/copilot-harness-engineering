讀這一章，你需要用過一個會寫程式的 AI agent，而且看過你把同一件事要求兩次，它做得有點不一樣。不需要別的。

## 一句話 {#in-one-sentence}

agent 從不會把同一件事做得一模一樣兩次，所以一次運行證明不了什麼。把任務跑好幾次，看看分布範圍有多大，報告數字時連同條件一起寫上。

## 給主管 {#for-leaders}

- **要做的決定**：凡是說「某種設定比較好」，都要寫明兩邊各跑了幾次、在什麼條件下跑的。無人值守的工作，要看「每次都成功」，而不是平均值。
- **風險**：只跑幾次，範圍會很寬。以這一章的教科書例子來說，5 次運行通過 4 次，真實通過率落在大約 38% 到 96% 之間的任何地方都說得通；要可靠地分辨 50% 和 70%，每一邊大約得跑九十次。
- **做對的成本**：要付的是任務數乘以設定數乘以次數，大多是錢和時間。
- **可以問團隊**：「兩邊各跑了幾次？範圍有沒有重疊？除了被測的東西，其他一切都相同嗎？」

## 新的設定真的比較好嗎？ {#problem}

假設你改了設定裡的某樣東西，例如換了一份指令檔，或換了一個模型。舊的設定跑了一次，新的設定跑了一次，新的分數比較高。那新的真的比較好嗎？還是說，再跑一次，分數比較高的就換成了舊的？

這不只是新手才會碰到的問題。Anthropic 談 agent 評測的文章提醒過：「一個任務這次評測通過了，下次可能就失敗。」它每個任務都跑好幾次，也是出於這個原因：「因為模型的輸出每次執行都不一樣，我們會做多次試驗，讓結果更穩定。」（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

要回答這個問題，得先給兩樣東西取個名字。agent 對一個任務從頭到尾嘗試一次，叫做一次**運行**（run）；同一種設定在同一個任務上跑好幾次，各次結果之間差多少，叫做**分布範圍**（spread）。不過在問它有多大之前，還有一個更早的問題：為什麼會有分布範圍？

## 看見分布範圍，再說清它代表什麼 {#how-it-works}

### 為什麼各次運行不同

請一個人把同一件工作做兩次，你會得到兩個稍微不同的結果，agent 也一樣，原因都很平常。

第一個原因在模型選字上，它帶有一點隨機性，不是每次都走最可能的那一步，所以兩次運行就算從同樣的要求開始，第一步也可能走得不一樣。這些小差異接著會越長越大，因為 agent 是在一個循環裡工作的（[Agent 到底是怎麼做事的？](2-1-agent-loop.html)）。如果運行 A 先讀了檔案 X，運行 B 先讀了檔案 Y，之後的一切就都建立在不同的理解上，早期的一個選擇，最後可能走到不同的答案。

還有 agent 周圍的世界，它也在變。工具回傳的，是它在那一刻回傳的東西，所以同一個指令可能花的時間不同、逾時，或被速率限制拖慢，一次搜尋列出結果的順序也會不一樣。連模型本身都可能改變。如果平台可以不通知你就換掉一個名字背後的模型，相隔一週的兩次運行用的可能就不是同一個模型，所以每次運行旁邊都要記下模型和日期。

不管哪個原因影響最大，應對的辦法都一樣：做任何決定之前，先看到分布範圍。

### 要跑幾次？

沒有一個數字對每種情況都對，因為次數取決於你想看出多大的差距。大的差距，幾次運行就看得出來；小的差距，就需要很多次。

要感受為什麼，先看一種 5 次運行通過了 4 次的設定。對這個結果，通常的 95% 區間（Wilson 區間）大約是 38% 到 96%。就算 5 次全過，區間也還是大約 57% 到 100%。所以五次運行分不出一個通過率 40% 的設定，和一個通過率 95% 的設定。比較兩種設定，需要的就更多了，照標準的樣本數公式，要可靠地看出 50% 對 70%，每一邊大約要跑九十次。這些是通過或失敗型任務的粗略教科書數字，不是對任何 agent 的測量。

實際做的時候，我從小處開始：先用已經有的設定在一個任務上跑幾次，看看結果自己會差多少。如果結果差很多，幾次運行就看不出小的效果，那就繼續加，直到再多跑一次範圍也動得不多，這時才算大致摸清了分布範圍。

到了比較的時候，每邊五次只是起點，不是結論。比較時要成對地比：兩種設定在相同的任務上都跑，再逐個任務看差異。這樣一來，對兩邊都難的任務就不會再給比較增加雜訊，比起比較兩個平均值，需要的運行次數更少。Evan Miller 談評測誤差範圍的論文，比較兩個模型時也建議這樣做，還說成對分析降低雜訊是「免費的」，因為一道題對一個模型難，對另一個模型往往也難（[Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640)）。

這些運行都要花錢，而且帳會很快變大，因為它是任務數乘以設定數乘以次數。這筆帳也是把任務集保持小而精的一個理由（[固定的任務，用腳本打分](6-3-eval-tasks.html)）。不是每件事都需要跑這麼多次，多出來的次數，我留給自己在乎的改動。

### 「k 次都成功」和「k 次裡至少一次成功」

把一個任務跑了 k 次，你可以對結果問兩個問題，答案差很多。第一個問題是 k 次裡有沒有至少一次成功，人可以試好幾次再挑最好的時候，該問的就是它。它叫 **pass@k**，Anthropic 的定義是「agent 在 k 次嘗試中，至少得到一個正確解的可能性」。k 越大，它越高。

第二個問題是 k 次是不是全部成功，agent 獨自執行、沒人看著、又必須每次都成功的時候，該問的是它（[無人值守：什麼時候必須停](5-7-when-to-stop.html)）。它叫 **pass^k**，k 越大，它越低，因為「要求更多次試驗都一致，是更難跨過的門檻」。（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

tau-bench 論文就是為了這個原因提出 pass^k。它報告說，2024 年它測的 agent「相當不一致（零售領域的 pass^8 <25%）」，這裡的 pass^8，指的是同一個任務的八次嘗試全部成功（[tau-bench](https://arxiv.org/abs/2406.12045)）。這個數字屬於他們的零售任務和那些模型，但這個問題本身值得借鏡。如果 agent 是無人值守地執行，平均通過率 80% 並不是你需要的數字，評判試辦也一樣，要看的是它每次都成功的機率有多高。

### 方向可以信，比例不行

那麼，只跑幾次的結果就毫無價值嗎？也不是。如果一種設定幾乎每次都通過，另一種很少通過，幾次運行也看得出結果指向哪個方向，因為光靠運氣，很難把這麼大的差距翻過來。幾次運行給不了的，是差距有多大。每個結果周圍的區間都很寬（上面 5 次通過 4 次的例子，是 38% 到 96%），再跑幾次，差距就可能移動很遠。所以從很少的運行，只能說結果指向哪個方向，說不了差了多少。[慎用子 agent](2-3-subagents.html) 裡那個每個任務只跑一次的比較，就是這種情況。

### 常見的誤讀

除了各跑一次（開頭說的就是這種情況），讀錯比較結果還有別的方式。

- 把幾次運行的平均當成一個數字報告。這會把各次之間的差距藏起來，而平均相同的兩種設定，行為可能差很多：一個總是落在中間，另一個在很好和很差之間擺盪。
- 只算成功的運行。如果你為了「得到乾淨的數字」而丟掉失敗的，你量到的就是別的東西了。
- 結果看起來不錯就停。如果你一直跑到新設定贏了才停，那是你自己選了答案，因為連續三次好的運行，可能來自一個只有一半時間會通過的設定。開始之前就要決定運行的次數。
- 比較不對等的兩邊，像是頂級模型對小一點的模型、有沒有知識庫（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）、規則不同。這時的差距是好幾個差異加在一起，所以除了你測試的東西，其他都要保持一樣。
- 漏掉隱藏的成本。如果你報告的用量不含子 agent，用了子 agent 的設定就會看起來很便宜（[慎用子 agent](2-3-subagents.html)）。

### 數字旁邊要寫什麼

一個孤零零的數字，既沒辦法檢查，也沒辦法重複，所以我會在旁邊寫上這些：

1. 跑了幾次，涵蓋幾個任務。
2. 兩邊各用哪個模型和設定。
3. 怎麼打分，由誰或什麼來打。
4. 用量算了什麼（只有主對話，還是也含子 agent）。
5. 分布範圍是多少，或者只跑一次時，就寫明只跑了一次。

### 測你自己的設定

拿一個你知道正確答案的任務，用同樣的要求交給你的 agent 五次，每次都開新的對話。新的對話很重要，因為舊的對話帶著它學到的東西，後面的運行就不公平了。做一張小表，每次運行一列，記下通過或失敗、花了幾分鐘、用量多少。五列並排來看，就是你自己的設定在那個任務上的分布範圍，它通常比大家預期的大。

## 多跑幾次要花什麼，又說明不了什麼 {#costs-and-traps}

要是分布範圍比你預想的大，自然會想多跑幾次。預算要是不夠跑足夠的次數，就說出來，並改用比較弱的措辭，像是「指向」、「我跑了兩次」。

就算負擔得起，分布範圍本身也不是要消除的缺點。設定更嚴謹一些，可以把它降低，但總有一部分會留下來，所以要事先為它做計畫，靠檢查、在每道門前安排人把關、給重試設上限來應對（[讓「通過」可信](5-5-counted-checks.html)）。

而且不管跑了多少次，統計都不能取代閱讀。五次運行能告訴你範圍有多大，卻不能告訴你其中一次為什麼失敗，那得去讀失敗的運行（[固定的任務，用腳本打分](6-3-eval-tasks.html)）。

## 什麼時候可以刪掉手動重跑的習慣 {#when-to-delete-it}
{status: industry}

手動把任務一次又一次重跑，這個習慣之所以存在，只是因為手邊的設定沒有工具能做這件事並報告分布範圍。如果平台能把同一個任務跑好幾次並顯示結果的範圍，就用那個。如果模型變得很穩，在你的任務上範圍很小，也可以少跑幾次，但這得靠測量，不能靠假設。

只要 agent 選下一步時還帶有一點隨機性，這背後的道理就不會變：一次運行，說不出一種設定有多好。
