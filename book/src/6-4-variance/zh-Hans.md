读这一章，你需要用过一个写代码的 AI agent，并且见过你两次提同样的要求，它做出来的东西略有不同。别的都不需要。

## 一句话 {#in-one-sentence}

agent 从来不会把同一件事做得一模一样，所以一次运行什么也证明不了。把任务多跑几次，看看波动有多大，报告数字时要连同条件一起写。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求凡是说“某套配置更好”，都必须写明两边各跑了多少次、在什么条件下跑的。对无人值守的工作，要看“每次都行”，不要看平均值。
- **风险**：每边只跑一次，什么也证明不了。本章的教科书例子里，5 次运行通过 4 次，和真实通过率在约 38% 到 96% 之间的任何值都吻合。要可靠地分清 50% 和 70%，每边大约要跑九十次。这些是针对通过/失败类任务的粗略数字，不是对任何 agent 的实测。
- **做对的代价**：运行次数会相乘：任务数乘配置数乘运行次数。主要是钱和时间。
- **可以问团队**：“每一边各跑了多少次？范围有没有重叠？除了被测的那一样，其他是不是都一样？”

## 问题 {#problem}

[慎用子 agent](2-3-subagents.html)里的每个数字，都来自每个任务跑一次。团队的用量约是单个 agent 的 4.5 倍，时间约 6 倍。这两个倍数是那一章里引用最多的数字，也是最站不稳的数字。如果我把同样四个任务再跑一遍，这两个倍数会变。我不知道会变多少。

这就是本章要讲的问题。旧配置你跑了一次，新配置你跑了一次，新的得分更高。新的更好吗？还是说，下一次旧的会得分更高？

先交代两个词。

- **一次运行**（run），是 agent 对一个任务从头到尾做一次。
- **波动**（spread），是同一套配置在同一个任务上，多次运行的结果之间相差多少。

## 原理 {#how-it-works}

### 为什么每次运行都不一样

让一个人把同一件活干两遍，得到的结果会略有不同。agent 也一样，原因很平常。

- **模型选词带有一定的随机性**。它不总是选最可能的那一步。两次运行从同一个需求开始，第一步可能就不同。
- **小差别会越滚越大**。agent 在一个循环里干活（[agent 循环，以及你能插手的地方](2-1-agent-loop.html)）。如果运行 A 先读文件 X，运行 B 先读文件 Y，之后的一切就建立在不同的认识上。早期的一个选择，可能导向不同的答案。
- **周围的环境会变**。工具返回的是那一刻它返回的东西。一条命令的耗时不一样，或者超时，或者被速率限制拖慢。一次搜索列出结果的顺序也可能不同。
- **模型本身也可能变**。如果平台能在不告诉你的情况下，换掉某个名字背后的模型，那么相隔一周的两次运行，可能就不是同一个模型。每次运行旁边，都记下模型和日期。

这几个因素各占多少波动，我没有测过。对本章来说这不要紧。要紧的是波动是存在的，在你做任何决定之前，必须先看到它。

### 一次运行和多次运行

看这张图。每边只跑一次时，配置 B 看起来比配置 A 好。每边多跑几次，你就会看到两边有重叠。让 B 看起来更好的那一次运行，两种配置都可能跑出来。这是示意图，不是数据：它显示的是问题的形状，不是你的 agent 上这个问题有多大。

### 要跑几次？

没有一个数字对所有情况都对。取决于你想看出多大的差别。差距大，几次运行就能看出来。差距小，就需要很多次。

想体会为什么，先数一套配置。假设它 5 次运行通过了 4 次。对这个结果，常用的 95% 区间（Wilson 区间，我是手算的）大约是从 38% 到 96%。就算 5 次全过，也只能说大约是 57% 到 100%。五次运行分不清一套通过率 40% 的配置和一套通过率 95% 的配置。两套配置对比，需要更多：标准的样本量公式说，要可靠地看出 50% 对 70%，每边大约要跑九十次。这些是针对通过/失败类任务的粗略的教科书数字，不是对任何 agent 的实测。

我的做法：

- **先对你已有的配置，在一个任务上跑几次**。每边五次是起点，不是结论。看看结果自己会相差多少。如果相差很大，几次运行就看不出小的效果。
- **一直加运行，直到图不再变**。如果再多跑一次，范围没怎么动，你就大致知道波动有多大了。
- **成对比较**。两套配置在同样的任务上都跑，逐个任务看差值。对两边都很难的任务，不会再给比较增加噪声，所以比起比较两个平均值，需要的运行次数更少。
- **对你在意的改动多跑几次**。不必每件事都跑很多次。

这要花钱，而且涨得很快：任务数乘配置数乘运行次数。这是让任务集保持小而精的理由（[固定的任务，用脚本打分](6-3-eval-tasks.html)），也是在你付不起更多次数时要老实说明的理由。

### “k 次全部成功”和“k 次里至少成功一次”

一个任务跑 k 次，有两个问题，答案差别很大。

- **k 次运行里至少成功一次**。如果人可以多试几次，挑最好的，要看的就是这个。它叫 **pass@k**（Anthropic 的定义：“agent 在 k 次尝试中至少得到一个正确解的可能性”）。k 越大，它越高。
- **k 次运行全部成功**。如果 agent 独自运行，没人看着，而且必须每次都行，要看的就是这个。它叫 **pass^k**。k 越大，它越低：“要求在更多次试验里都保持一致，门槛更高。”（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

tau-bench 的论文正是为此提出了 pass^k。它报告说，它在 2024 年测的那些 agent “相当不稳定（零售任务上 pass^8 低于 25%）”。这里的 pass^8，是指同一个任务试 8 次全部成功。这个数字只针对他们的零售任务和那些模型，不是对你的任务的论断。（[tau-bench](https://arxiv.org/abs/2406.12045)）能迁移过来的是这个问题。如果 agent 无人值守地运行，平均通过率 80% 不是你要的数字。你要知道的是它有多大概率每次都行。试点也一样：按这个来评判，不要按平均通过率。

挑和你用 agent 的方式相符的那个问题。有人盯着的 agent，问的是第一个。通宵运行的 agent，问的是第二个（[无人值守：什么时候必须停](5-7-when-to-stop.html)）。

### 方向可以信，倍数别当真

我在[慎用子 agent](2-3-subagents.html)里的结果，只有有限的说服力。四到六倍的差距很大，所以我相信方向：同样的结果，团队贵得多。我不信“4.5”或者“6”。每个任务只跑了一次，而且两边的配置也不一样。这就是靠很少几次运行做出的诚实结论该有的样子：说它指向哪边，不说差多远。

### 常见的误读

- **每边只跑一次**。上面讲过的情况。
- **几次运行的平均值，只报一个数**。它把波动藏起来了。两套平均值相同的配置，行为可能差别很大：一套总落在中间，另一套在很好和很差之间摆动。
- **只算成功的那几次**。如果你为了“数字好看”把失败的去掉，你量的就是另一样东西了。
- **结果看起来好就停**。如果你一直跑到新配置赢了才停，那就是你选了答案。连续三次好结果，可能来自一套只有一半时间能通过的配置。开跑之前就定好运行次数。
- **比较不对等的两边**。顶级模型对小模型，有知识库对没有（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)），规则也不一样。这时差距是好几处差别的总和。除了被测的那一样，其他都保持一致。
- **漏掉隐藏的成本**。如果你报告的用量不含子 agent，用了子 agent 的配置就显得便宜（[慎用子 agent](2-3-subagents.html)）。

### 怎么写出一句诚实的话

把条件放在数字旁边。没有条件的数字，没法检查，也没法重复。我会写下的条件：

1. **跑了多少次，多少个任务**。
2. **每一边用的模型和配置**。
3. **怎么打分的**，由谁或什么打的。
4. **用量算了哪些**（只算主对话，还是连子 agent 一起算）。
5. **波动有多大**，如果只跑了一次，就写“我只跑了一次”。

这是按这个写法写出来的我自己的结果：“四个任务，各跑一次；一个用顶级模型的 agent，对一个带知识库的三角色团队；由同一个脚本打分；用量是平台给的 AI credits。两边四个都做对了。团队的用量约是 4.5 倍，时间约是 6 倍。每边只跑了一次，所以我信方向，不信倍数。”

这句话看起来比“团队贵 4.5 倍”差。但它才是真的。

### 测你自己的配置

对任何“某样东西更好”的说法，问**三个问题**：

1. 每一边各跑了几次？
2. 范围有没有重叠？
3. 除了被测的那一样，其他是不是都一样？

**今天就能跑的一个测试**。挑一个你知道正确答案的任务。用同样的需求，让你的 agent 做五次，每次开一个新对话。新对话很重要：旧对话带着它学到的东西，后面几次运行就不公平了。做一张小表，每次运行一行：通过还是失败、几分钟、用量。把五个结果放在一起看。这就是你自己的配置在那个任务上的波动，通常比人预想的大。

## 代价和坑 {#costs-and-traps}

**多跑要花真金白银**。如果预算不够跑足次数，就直说，并用弱一点的措辞：“倾向于”“我跑了两次”。

**波动不是要消除的故障**。配置收紧可以让它小一些，但总有一部分留着。要把它考虑进去：检查、关卡处有人、对重试设上限（[让“通过”可信](5-5-counted-checks.html)）。

**统计不能代替阅读**。五次运行告诉你波动。它不告诉你其中一次为什么失败。要去读失败的运行（[固定的任务，用脚本打分](6-3-eval-tasks.html)）。

**我自己的结果没有置信区间**。每边只跑一次，没有东西可以拿来算区间；只跑几次，区间也会非常宽，上面的例子就是这样。所以我给出每次运行，再说它们指向哪边。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

把任务一遍遍重跑的这个手工习惯之所以存在，是因为我没有工具能做这件事并报告波动。如果哪个平台能把同一个任务跑几次并显示波动，就用它的。如果模型变得足够稳定，在我的任务上波动很小，我可以少跑几次。但这得靠测，不能靠假设。

只要 agent 选下一步时还带着一定的随机性，这背后的道理就不变：一次运行说不清一套配置有多好。
