读这一章，你需要用过一个写代码的 AI agent，并且见过你两次提同样的要求，它做出来的东西略有不同。别的都不需要。

## 一句话 {#in-one-sentence}

agent 从来不会把同一件事做得一模一样，所以一次运行什么也证明不了。把任务多跑几次，看看波动有多大，报告数字时连同条件一起写上。

## 写给管理者 {#for-leaders}

- **要拍板的事**：凡是说“某套配置更好”，都要写明两边各跑了多少次、在什么条件下跑的。无人值守的工作，要看“每次都行”，而不是平均值。
- **风险**：只跑几次，范围会很宽。拿本章的教科书例子来说，5 次运行通过 4 次，真实通过率落在约 38% 到 96% 之间的任何地方都说得通；要可靠地分清 50% 和 70%，每边大约得跑九十次。
- **做对的代价**：要付的是任务数乘配置数乘运行次数，主要是钱和时间。
- **可以问团队**：“每一边各跑了多少次？范围有没有重叠？除了被测的那一样，其他是不是都一样？”

## 新配置真的更好吗？ {#problem}

假设你改了配置里的某样东西，比如换了一份指令文件，或者换了个模型。旧配置跑了一次，新配置跑了一次，新的得分更高。那新的真的更好吗？还是说，再跑一次，得分更高的就成了旧的？

这不只是新手才会碰到的问题。Anthropic 讲 agent 评测的文章提醒过：“一个任务这次评测通过了，下次可能就失败。”它每个任务都跑好几次，也是出于这个原因：“因为模型的输出每次运行都不一样，我们会做多次试验，让结果更稳定。”（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

要回答这个问题，得先给两样东西起个名字。agent 把一个任务从头到尾做一遍，叫一次**运行**（run）；同一套配置在同一个任务上跑多次，结果之间相差多少，叫**波动**（spread）。不过在问波动有多大之前，还有个更早的问题：为什么会有波动？

## 看见波动，再说清它意味着什么 {#how-it-works}

### 为什么每次运行都不一样

让一个人把同一件活干两遍，得到的结果会略有不同，agent 也一样，原因都很平常。

头一个原因在模型选词上，它带着一定的随机性，并不总是挑最可能的那一步，所以两次运行哪怕从同一个需求出发，第一步就可能走得不一样。这些小差别接着会越滚越大，因为 agent 是在一个循环里干活的（[agent 循环，以及你能插手的地方](2-1-agent-loop.html)）。如果运行 A 先读了文件 X，运行 B 先读了文件 Y，之后的一切就都建立在不同的认识上，早期的一个选择，最后可能导向不同的答案。

还有 agent 周围的环境，它也在变。工具返回的，是它那一刻返回的东西，所以同一条命令可能耗时不同、超时，或者被速率限制拖慢，一次搜索列出结果的顺序也会不一样。连模型本身都可能变。要是平台能不打招呼就换掉某个名字背后的模型，相隔一周的两次运行用的可能就不是同一个模型，所以每次运行旁边都要记下模型和日期。

不管哪个因素影响最大，应对的办法都一样：做任何决定之前，先看到波动。

### 要跑几次？

没有哪个数字对所有情况都对，因为次数取决于你想看出多大的差别。差距大，几次运行就能看出来；差距小，就得跑很多次。

想体会为什么，先看一套 5 次运行通过了 4 次的配置。对这个结果，常用的 95% 区间（Wilson 区间）大约是 38% 到 96%。就算 5 次全过，区间也还是大约 57% 到 100%。所以五次运行分不清一套通过率 40% 的配置和一套通过率 95% 的配置。比较两套配置，要的就更多了，按标准的样本量公式，想可靠地看出 50% 对 70%，每边大约要跑九十次。这些是针对通过/失败类任务的粗略的教科书数字，不是对任何 agent 的实测。

实际做的时候，我从小处起步：先拿已有的配置在一个任务上跑几次，看看结果自己会相差多少。如果结果相差很大，几次运行就看不出小的效果，那就继续加，直到再多跑一次范围也没怎么动，这时才算大致摸清了波动。

到了比较的时候，每边五次只是起点，不是结论。比较时要成对地比：两套配置在同样的任务上都跑，再逐个任务看差值。这样一来，对两边都难的任务就不会再给比较添噪声，比起比较两个平均值，需要的运行次数更少。Evan Miller 讲评测误差棒的论文，比较两个模型时也建议这么做，还说成对分析降低噪声是“白送的”，因为一道题对一个模型难，对另一个模型往往也难（[Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640)）。

这些运行都要花钱，而且账涨得很快，因为它是任务数乘配置数乘运行次数。这笔账也是让任务集保持小而精的一个理由（[固定的任务，用脚本打分](6-3-eval-tasks.html)）。不是每件事都需要跑这么多次，多出来的次数，我留给自己在意的改动。

### “k 次全部成功”和“k 次里至少成功一次”

一个任务跑了 k 次，你可以对结果问两个问题，答案差别很大。第一个问题是 k 次里有没有至少一次成功，人可以多试几次、挑最好的那次时，该问的就是它。它叫 **pass@k**，Anthropic 的定义是“agent 在 k 次尝试中至少得到一个正确解的可能性”。k 越大，它越高。

第二个问题是 k 次是不是全部成功，agent 独自运行、没人看着、又必须每次都行时，该问的是它（[无人值守：什么时候必须停](5-7-when-to-stop.html)）。它叫 **pass^k**，k 越大，它越低，因为“要求在更多次试验里都保持一致，门槛更高”。（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

tau-bench 的论文正是为此提出了 pass^k。它报告说，它在 2024 年测的那些 agent “相当不稳定（零售任务上 pass^8 低于 25%）”，这里的 pass^8，是指同一个任务试 8 次全部成功（[tau-bench](https://arxiv.org/abs/2406.12045)）。这个数字属于他们的零售任务和那些模型，但这个问题本身能迁移过来。如果 agent 无人值守地运行，平均通过率 80% 并不是你要的数字，评判试点也一样，要看的是它有多大概率每次都行。

### 方向可以信，倍数别当真

那么，只跑几次的结果就一文不值吗？也不是。如果一套配置几乎每次都过，另一套很少过，几次运行也能看出结果指向哪边，因为光靠运气，很难把这么大的差距翻过来。几次运行给不了的，是差距有多大。每个结果周围的区间都很宽（上面 5 次过 4 次的例子，是 38% 到 96%），再跑几次，差距就可能挪出很远。所以靠很少几次运行，只能说结果指向哪边，说不了差多远。[慎用子 agent](2-3-subagents.html)里那个每个任务只跑一次的比较，就是这种情况。

### 常见的误读

除了每边只跑一次（开头说的就是这种情况），读错比较结果还有别的方式。

- 把几次运行的平均值当成一个数来报。这会把波动藏起来，而两套平均值相同的配置，表现可能差别很大：一套总落在中间，另一套在很好和很差之间来回摆。
- 只算成功的那几次。如果你为了“数字好看”把失败的去掉，你量的就是另一样东西了。
- 结果看起来不错就停。如果你一直跑到新配置赢了才停，那是你自己选了答案，因为连续三次好结果，可能来自一套只有一半时候能通过的配置。开跑之前就要定好运行次数。
- 比较不对等的两边，比如顶级模型对小模型，有知识库对没有知识库（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)），规则也不一样。这时的差距是好几处差别加在一起，所以除了被测的那一样，其他都要保持一致。
- 漏掉隐藏的成本。如果你报告的用量不含子 agent，用了子 agent 的配置就显得便宜（[慎用子 agent](2-3-subagents.html)）。

### 数字旁边要写什么

光秃秃的一个数字，既没法检查，也没法重复，所以我会在旁边写上这些：

1. 跑了多少次，多少个任务。
2. 每一边用的模型和配置。
3. 怎么打分的，由谁或什么打的。
4. 用量算了哪些（只算主对话，还是连子 agent 一起算）。
5. 波动有多大，如果只跑了一次，就写明只跑了一次。

### 测你自己的配置

挑一个你知道正确答案的任务，用同样的需求让 agent 做五次，每次都开一个新对话。新对话很重要，因为旧对话带着它学到的东西，后面几次运行就不公平了。做一张小表，每次运行一行，记下通过还是失败、用了几分钟、用量多少。五行放在一起，就是你的配置在这个任务上的波动，它通常比人预想的大。

## 多跑几次要花什么，又说明不了什么 {#costs-and-traps}

要是波动比你预想的大，自然会想多跑几次。预算要是不够跑足次数，就直说，并换用弱一点的措辞，比如“倾向于”“我跑了两次”。

就算付得起，波动本身也不是要消除的故障。配置收紧一些，可以让它小一点，但总有一部分会留着，所以要事先把它考虑进去，靠检查、关卡处有人、给重试设上限来兜住（[让“通过”可信](5-5-counted-checks.html)）。

而且不管跑了多少次，统计都代替不了阅读。五次运行能告诉你波动有多大，却不能告诉你其中一次为什么失败，那得去读失败的运行（[固定的任务，用脚本打分](6-3-eval-tasks.html)）。

## 什么时候可以删掉手工重跑的习惯 {#when-to-delete-it}
{status: industry}

把任务一遍遍手工重跑，这个习惯之所以存在，只是因为手头的配置里没有工具能做这件事并报告波动。如果哪个平台能把同一个任务跑几次并显示波动，就用它的。如果模型变得足够稳定，在你的任务上波动很小，也可以少跑几次，但这得靠测出来，不能靠假设。

只要 agent 选下一步时还带着一定的随机性，这背后的道理就不会变：一次运行，说不清一套配置有多好。
