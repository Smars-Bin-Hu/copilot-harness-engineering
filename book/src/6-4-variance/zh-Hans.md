读这一章，你需要用过一个写代码的 AI agent，并且见过你两次提同样的要求，它做出来的东西略有不同。别的都不需要。

## 一句话 {#in-one-sentence}

agent 从来不会把同一件事做得一模一样，所以一次运行什么也证明不了。把任务多跑几次，看看波动有多大，报告数字时连同条件一起写上。

## 写给管理者 {#for-leaders}

- **要拍板的事**：凡是说“某套配置更好”，都要写明两边各跑了多少次、在什么条件下跑的。无人值守的工作，要看“每次都行”，而不是平均值。
- **风险**：每边只跑一次，什么也证明不了。拿本章的教科书例子来说，5 次运行通过 4 次，真实通过率落在约 38% 到 96% 之间的任何地方都说得通；要可靠地分清 50% 和 70%，每边大约得跑九十次。这些是针对通过/失败类任务的粗略数字，不是对任何 agent 的实测。
- **做对的代价**：运行次数是相乘的，要付的是任务数乘配置数乘运行次数，主要花在钱和时间上。
- **可以问团队**：“每一边各跑了多少次？范围有没有重叠？除了被测的那一样，其他是不是都一样？”

## 新配置真的更好吗？ {#problem}

[慎用子 agent](2-3-subagents.html)里的每个数字，都来自每个任务跑一次，那一章被引用最多的两个数字也不例外：团队的用量约是单个 agent 的 4.5 倍，时间约 6 倍。而这两个倍数，也是那一章里最站不稳的数字。要是把同样四个任务再跑一遍，这两个倍数会变，至于变多少，我不知道。

这不只是那一章的事。每次比较两套配置，你都会碰上同一个问题。旧配置跑了一次，新配置跑了一次，新的得分更高。那新的真的更好吗？还是说，再跑一次，得分更高的就成了旧的？

要回答它，得先给两样东西起个名字。agent 把一个任务从头到尾做一遍，叫一次**运行**（run）；同一套配置在同一个任务上跑多次，结果之间相差多少，叫**波动**（spread）。在问波动有多大之前，不妨先问一句：为什么会有波动？

## 看见波动，再说清它意味着什么 {#how-it-works}

### 为什么每次运行都不一样

让一个人把同一件活干两遍，得到的结果会略有不同，agent 也一样，原因都很平常。

头一个原因在模型选词上，它带着一定的随机性，并不总是挑最可能的那一步，所以两次运行哪怕从同一个需求出发，第一步就可能走得不一样。这些小差别接着会越滚越大，因为 agent 是在一个循环里干活的（[agent 循环，以及你能插手的地方](2-1-agent-loop.html)）。如果运行 A 先读了文件 X，运行 B 先读了文件 Y，之后的一切就都建立在不同的认识上，早期的一个选择，最后可能导向不同的答案。

还有 agent 周围的环境，它也在变。工具返回的，是它那一刻返回的东西，所以同一条命令可能耗时不同、超时，或者被速率限制拖慢，一次搜索列出结果的顺序也会不一样。连模型本身都可能变。要是平台能不打招呼就换掉某个名字背后的模型，相隔一周的两次运行用的可能就不是同一个模型，所以每次运行旁边都要记下模型和日期。

这几个因素各占多少波动，我没有测过，不过对这一章来说这不要紧。要紧的是波动确实存在，而且在你做任何决定之前，得先看到它。

### 要跑几次？

没有哪个数字对所有情况都对，因为次数取决于你想看出多大的差别。差距大，几次运行就能看出来；差距小，就得跑很多次。

想体会为什么，先看一套 5 次运行通过了 4 次的配置。对这个结果，常用的 95% 区间（Wilson 区间，我是手算的）大约是 38% 到 96%。就算 5 次全过，区间也还是大约 57% 到 100%。换句话说，五次运行分不清一套通过率 40% 的配置和一套通过率 95% 的配置。比较两套配置，要的就更多了，按标准的样本量公式，想可靠地看出 50% 对 70%，每边大约要跑九十次。这些是针对通过/失败类任务的粗略的教科书数字，不是对任何 agent 的实测。

实际做的时候，我从小处起步：先拿已有的配置在一个任务上跑几次，看看结果自己会相差多少。如果结果相差很大，几次运行就看不出小的效果，那就继续加，直到再多跑一次范围也没怎么动，这时才算大致摸清了波动。

到了比较的时候，每边五次只是起点，不是结论。我成对地比：两套配置在同样的任务上都跑，再逐个任务看差值。这样一来，对两边都难的任务就不会再给比较添噪声，比起比较两个平均值，需要的运行次数更少。

这些运行都要花钱，而且账涨得很快，因为它是任务数乘配置数乘运行次数。这笔账也是让任务集保持小而精的一个理由（[固定的任务，用脚本打分](6-3-eval-tasks.html)），也是付不起更多次数时要老实说明的理由。不是每件事都需要跑这么多次，多出来的次数，我留给自己在意的改动。

### “k 次全部成功”和“k 次里至少成功一次”

一个任务跑了 k 次，你可以对结果问两个问题，答案差别很大。第一个问题是：k 次里有没有至少一次成功？如果人可以多试几次、挑最好的那次，要看的就是它。它叫 **pass@k**，Anthropic 的定义是“agent 在 k 次尝试中至少得到一个正确解的可能性”。k 越大，它越高。

第二个问题是：k 次是不是全部成功？如果 agent 独自运行、没人看着，而且必须每次都行，要看的就是它。它叫 **pass^k**，k 越大，它越低，因为“要求在更多次试验里都保持一致，门槛更高”。（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

tau-bench 的论文正是为此提出了 pass^k。它报告说，它在 2024 年测的那些 agent “相当不稳定（零售任务上 pass^8 低于 25%）”，这里的 pass^8，是指同一个任务试 8 次全部成功。这个数字只针对他们的零售任务和那些模型，不是对你的任务的论断（[tau-bench](https://arxiv.org/abs/2406.12045)）。能迁移过来的，是这个问题本身。如果 agent 无人值守地运行，平均通过率 80% 并不是你要的数字，你要知道的是它有多大概率每次都行。评判试点也该看这个数。

所以，挑和你用 agent 的方式相符的那个问题。有人盯着的 agent，问的是第一个；通宵运行的 agent，问的是第二个（[无人值守：什么时候必须停](5-7-when-to-stop.html)）。

### 方向可以信，倍数别当真

这下就能回到这一章开头那两个倍数了。我在[慎用子 agent](2-3-subagents.html)里的结果，说服力是有限的。四到六倍的差距很大，正因为大，我相信它的方向：同样的结果，团队贵得多。但我不信“4.5”或者“6”，因为每个任务只跑了一次，两边的配置也不一样。靠很少几次运行做出的诚实结论，就该是这个样子：说它指向哪边，不说差多远。

### 常见的误读

除了每边只跑一次（这一章开头就是这种情况），读错比较结果还有别的方式。

- 把几次运行的平均值当成一个数来报。这会把波动藏起来，而两套平均值相同的配置，表现可能差别很大：一套总落在中间，另一套在很好和很差之间来回摆。
- 只算成功的那几次。如果你为了“数字好看”把失败的去掉，你量的就是另一样东西了。
- 结果看起来不错就停。如果你一直跑到新配置赢了才停，那是你自己选了答案，因为连续三次好结果，可能来自一套只有一半时候能通过的配置。开跑之前就要定好运行次数。
- 比较不对等的两边，比如顶级模型对小模型，有知识库对没有知识库（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)），规则也不一样。这时的差距是好几处差别加在一起，所以除了被测的那一样，其他都要保持一致。
- 漏掉隐藏的成本。如果你报告的用量不含子 agent，用了子 agent 的配置就显得便宜（[慎用子 agent](2-3-subagents.html)）。

### 怎么写出一句诚实的话

一句诚实的话，要把条件写在数字旁边。没有条件的数字，既没法检查，也没法重复。我会写下这些条件：

1. 跑了多少次，多少个任务。
2. 每一边用的模型和配置。
3. 怎么打分的，由谁或什么打的。
4. 用量算了哪些（只算主对话，还是连子 agent 一起算）。
5. 波动有多大，如果只跑了一次，就写“我只跑了一次”。

按这个写法，我自己的结果是这样的：“四个任务，各跑一次；一个用顶级模型的 agent，对一个带知识库的三角色团队；由同一个脚本打分；用量是平台给的 AI credits。两边四个都做对了。团队的用量约是 4.5 倍，时间约是 6 倍。每边只跑了一次，所以我信方向，不信倍数。”

这句话看起来比“团队贵 4.5 倍”难看，但只有它是真的。

### 测你自己的配置

对任何“某样东西更好”的说法，问三个问题：

1. 每一边各跑了几次？
2. 范围有没有重叠？
3. 除了被测的那一样，其他是不是都一样？

你自己配置的波动，今天就能看到。挑一个你知道正确答案的任务，用同样的需求让 agent 做五次，每次都开一个新对话。新对话很重要，因为旧对话带着它学到的东西，后面几次运行就不公平了。做一张小表，每次运行一行，记下通过还是失败、用了几分钟、用量多少，再把五个结果放在一起看。这就是你的配置在这个任务上的波动，它通常比人预想的大。

## 多跑几次要花什么，又说明不了什么 {#costs-and-traps}

要是波动比你预想的大，自然会想多跑几次，可多跑几次，花的是真金白银。预算要是不够跑足次数，就直说，并换用弱一点的措辞，比如“倾向于”“我跑了两次”。

就算付得起，波动本身也不是要消除的故障。配置收紧一些，可以让它小一点，但总有一部分会留着，所以要事先把它考虑进去，靠检查、关卡处有人、给重试设上限来兜住（[让“通过”可信](5-5-counted-checks.html)）。

而且不管跑了多少次，统计都代替不了阅读。五次运行能告诉你波动有多大，却不能告诉你其中一次为什么失败，那得去读失败的运行（[固定的任务，用脚本打分](6-3-eval-tasks.html)）。

回到我自己的结果：它们没有置信区间。每边只跑一次，就没有东西可以拿来算区间。就算跑上几次，区间也会非常宽，上面的例子就是这样。所以我把每次运行都摆出来，说明它们指向哪边。

## 什么时候可以删掉手工重跑的习惯 {#when-to-delete-it}
{status: industry}

把任务一遍遍手工重跑，这个习惯之所以存在，只是因为我没有工具能做这件事并报告波动。如果哪个平台能把同一个任务跑几次并显示波动，就用它的。如果模型变得足够稳定，在我的任务上波动很小，我也可以少跑几次，但这得靠测出来，不能靠假设。

只要 agent 选下一步时还带着一定的随机性，这背后的道理就不会变：一次运行，说不清一套配置有多好。
