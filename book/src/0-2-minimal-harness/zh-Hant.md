讀這一章，你需要在自己的專案裡用過 Copilot 的 agent 模式，並且讀過[差距在模型外面](0-1-the-gap-and-the-map.html)，或至少知道「harness」這個詞。

## 一句話 {#in-one-sentence}

先從一頁規則、一個 skill 和一個擋危險指令的 hook 開始。其他東西，等真的有痛點了再加。

## 給主管 {#for-leaders}

- **要做的決定**：從最小的組合開始（一頁規則、一個 skill、一個會擋指令的 hook），之後每加一部分，都讓真的痛點來批准，而不是讓計劃來批准。
- **風險**：一次搭出來的大 harness，維護起來很貴，而且你分不出哪一部分有用。就算是最小的組合，規則也只是請求。hook 是模型沒辦法跟它爭的規則，但它只擋得住它認得的指令。
- **做對的成本**：我估計一個已經打開專案的人，大約要半小時。團隊還要像審程式碼那樣，審規則檔和 hook 檔。
- **可以問團隊**：「我們的設定裡，哪一部分來自真的失敗，哪一部分來自範本？」

## 為什麼不一口氣全搭起來？ {#problem}

很多人一聽到「harness」，想到的就是一個大系統，有[兩道門：人在哪裡批准](5-3-two-approvals.html)、[同時管十件事：並行的是任務](7-2-many-tasks.html)、知識庫，還有報告。面對這樣的想像，他們不是乾脆放棄，就是一口氣全搭起來。這兩條路都走錯了。

一口氣全搭的問題在於，大 harness 是有代價的。每一部分都要你去寫、去保持正確，出錯時還得除錯。而且既然是一次全加進去的，到底是哪一部分有用，你也分不出來。這一點我是從自己的 harness 上知道的：它並不是一開始就這麼大，而是一個痛點一個痛點長出來的，後來我也拿掉了一些沒換到任何東西的部分（見[我砍掉了什麼，數據怎麼說](7-3-what-we-cut.html)）。

所以不如從另一頭開始：先搭值得擁有的最小組合，照我會搭的順序一樣一樣來。如果你已經在 VS Code 裡打開了專案，我估計大約要半小時。

### 為什麼先規則，再 skill，最後 hook

這三部分約束 agent 的力度不一樣，一樣比一樣緊。這就帶出一個問題：hook 約束得最緊，為什麼反而放到最後才搭？

先說規則。它只要寫幾分鐘，不用寫程式，卻能告訴 agent 那些它自己猜不到的事，例如你的專案怎麼建、哪些東西不要碰。規則只是請求，模型可能不理，但依我的經驗，它大多數時候會照寫的做。

不過規則那一頁也有放不下的東西，因為有些知識太長了。如果每個流程都放在那裡，agent 每次對話都得背著全部（為什麼這樣很貴，見[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)）。**skill** 就是為這個準備的，它是為某一類工作寫的一份簡短手冊。agent 一開始只看到它的名字和一行描述，等需求對上了，才去讀全文。

可是規則和 skill 終究都是請求，模型可以不理。**hook** 才是第一條你真正靠得住的規則。它是平台在固定時刻（例如 agent 執行工具之前）執行的小程式。它說不的時候，模型沒辦法跟它爭。它之所以還是放在最後，是因為它是你得寫、得維護的程式碼，這份力氣應該留給少數絕對不能發生的事。

### 第 1 步：一頁規則（約 10 分鐘）

先在專案根目錄建一個指令檔。VS Code 和 Copilot 會讀 `AGENTS.md` 或 `.github/copilot-instructions.md` 這樣的檔案，並在每次對話都交給 agent（它接受哪些確切的檔名，請查目前的 VS Code 文件）。

檔案裡只寫模型會弄錯或漏掉的東西，也就是你專案自己的指令、限制和陷阱。它本來就知道的就別寫了，例如在你的語言裡怎麼寫迴圈。越短越好，因為規則檔一長，模型就很容易不理它。規則頁雖然要短，有一行卻值得早點加上：改完之後要執行的指令（測試、linter），再加一句「通過之前，不要說做完了」。這是最便宜的檢查（[讓 agent 能檢查自己的活](5-4-self-checks.html)）。

好的第一頁有五到十行。我的設定裡，真正的檔案比這長，但它的核心限制長這樣：

::: code harness AGENTS.md L44-L45 "隨附的規則頁裡的兩條核心限制：動手前先看，並保留使用者自己的改動。"

要確認這個檔案有用，可以打開新的對話，問一個只有你的規則才答得出的問題，例如「這個專案怎麼執行測試？」如果它是照你的規則回答，檔案就載入了；如果它在猜，就檢查一下檔名和位置。

### 第 2 步：一個 skill（約 10 分鐘）

skill 要寫什麼？挑一件你對 agent 解釋過不只一次的工作就好。skill 是一個資料夾，裡面有一個 `SKILL.md` 檔，檔案開頭寫著名字和**描述**。最重要的是描述，因為 agent 找不找得到這個 skill，就看它。好的描述會說清楚這個 skill 做什麼、什麼時候用，以及使用者可能會說哪些詞。

::: code harness .github/skills/generic-code-standards/SKILL.md L1-L6 "真實 skill 的開頭：agent 最先看到的是名字和描述。"

開頭下面寫步驟，步驟後面再列一份簡短的陷阱清單，也就是 agent 通常會出錯的地方。每看到它失敗一次，就加一條陷阱。就我所知，這是寫 skill 最有用的習慣（[把團隊的做法寫成 skill](3-4-skills-and-workflows.html)）。

要確認 skill 有用，可以在對話裡輸入 `/`，看看有沒有它的名字。然後說一個符合描述、但沒點名這個 skill 的需求，看 agent 會不會用上它。agent 如果從來不選某個 skill，問題通常出在描述上。

### 第 3 步：一個擋危險指令的 hook（約 10 分鐘）

終端機是 agent 最強的工具，所以 hook 就從這裡開始。挑那些損害無法復原的指令，例如遞迴刪除一個資料夾，或者下載一個腳本並在同一行執行。

這要分成兩部分：一是設定檔，告訴平台在哪些時刻呼叫你的程式；二是程式本身。在我的設定裡只有一個設定檔，每個時刻都指向同一個程式：

::: code harness .github/hooks/harness.json L40-L51 "工具執行前那個時刻的設定：只是寫出要呼叫哪個程式。"

程式拿到的，是 agent 將要發出的那次工具呼叫，也就是要用哪個工具、輸入是什麼。如果指令對上了你擋掉的樣式，它就回一個拒絕和一個原因。原因很重要，因為 agent 看得到它，所以要寫該改做什麼，不然 agent 還會再試同一件事（[詢問不是限制](4-2-ask-vs-refuse.html)）。這是我的其中一條樣式，它寫得很長，因為同一個指令有很多種寫法：

::: code harness .harness/policies/gate.json L59-L62 "一條真實的拒絕規則：對根目錄、家目錄或目前資料夾做遞迴強制刪除，並附上 agent 讀得懂的原因。"

這是一個真實的檔案，比你第一天需要的大得多。先從三、四條樣式開始就好。

確認 hook 有用要小心一點，因為不能拿真的危險的指令來測。先加一條無害的測試規則，例如拒絕指令 `echo hook-test`，再請 agent 執行它。你應該會看到帶著你寫的原因的拒絕。測完，把這條測試規則移除。

我自己的 hook 踩過三個坑：

- hook 程式如果啟動不了（例如找不到直譯器），平台會當成拒絕，agent 一個工具也用不了。可是畫面上只會說 hook 出錯，所以依賴它之前，先測一次。
- hook 執行如果超過時間限制（在我的設定裡是 30 秒），平台會放行這次呼叫，而且不會通知。換句話說，hook 是失效時放行的：它一慢，指令就像沒有 hook 一樣照常執行。所以程式一定要跑得快。
- 設定是在視窗啟動時讀的，所以改完之後，要重新載入 VS Code 視窗。

hook 做不到的事，同樣重要。它看到的是一次呼叫，看不到指令執行起來會做什麼（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）。所以樣式清單擋得住危險指令的常見寫法，卻擋不住每一種寫法。它是安全帶，不是沙箱。

### 你需要多少 harness？

這三部分夠不夠，要看 agent 出錯時誰會受影響。

| 你是 | 大概夠了 | 為什麼 |
| --- | --- | --- |
| 一個人，做自己的專案 | 上面三部分 | 每個改動你都看得到，錯了只有你付代價 |
| 小團隊，共用一個倉庫 | 三部分，規則檔和 hook 檔像程式碼一樣審，再加一個記錄 agent 做了什麼的地方 | 別人會承接 agent 的錯，而「誰改了規則」成了問題（[落地與治理](7-4-rollout-and-governance.html)） |
| 大團隊，或有合規責任的程式碼 | 上面這些，再依你的風險加上[兩道門：人在哪裡批准](5-3-two-approvals.html)、[讓「通過」可信](5-5-counted-checks.html)和報告 | 錯了要別人付代價，而你必須拿得出發生了什麼 |

我猜大多數讀者在第一列。開頭那幅圖裡的兩道批准的門和任務看板，都不是起點。

### 怎麼知道有沒有變好？

每加一部分，你都會想知道它有沒有用，可是感覺靠不住。比較好的做法是挑幾個你知道正確答案的任務，每次改動前後各跑一遍，用同樣的方式打分。[慎用子 agent](2-3-subagents.html)展示了一個這樣的比較，[第 6 部](6-3-eval-tasks.html)講方法。就算是粗糙的版本，五個任務加一份「怎樣算對」的清單，也比猜強。只是這份清單要在跑之前寫好。每個任務也要跑幾次，因為一次可能只是運氣（[一次運行證明不了什麼](6-4-variance.html)）。

## 這組入門設定會在哪裡出問題 {#costs-and-traps}

這組入門設定雖然小，也有自己出問題的地方。最先出問題的是規則頁，它會越長越舊。大家每出一次事故，就加一行，所以過一陣子它變長了，有的互相矛盾，模型也就不理它了。要不時刪減，讓每條規則只放在一個地方。

hook 出問題的方式比較隱蔽，它會給人虛假的安心。它只擋它認得的，所以不要把它說成「agent 不能刪東西」，要說成「agent 不能執行這幾個特定的指令」。

最後還要交代一句：VS Code 的設定，我沒有每一項都測過。檔名、hook 的支援和設定，不同版本之間會變，所以上面的步驟雖然在我的設定裡行得通，你的還是請查目前的文件。

## 什麼時候可以把每一部分刪掉 {#when-to-delete-it}
{status: industry}

除了盯緊它們，你還要知道什麼時候可以拿掉它們，因為這組入門的每一部分，都是平台正在慢慢內建的東西。等平台自己的權限系統開箱就拒絕同樣的危險指令，就丟掉你的 hook。等它自己學會你專案的指令，就把你的規則頁縮短。還有，每次大的模型升級之後，都要重讀你的規則（[模型升級了，就要刪](6-5-model-upgrades.html)），因為為舊模型寫的行，可能已經是累贅。

::: prompt
用一個最小設定的三部分來檢查這個倉庫：一頁簡短的規則、一個 skill、一個會擋指令的 hook。每一部分都說明有沒有、在哪裡、能不能用。規則的部分，列出太長、過期或互相矛盾的行，並說明缺了哪些模型猜不到的指令和限制。hook 的部分，列出哪些不可逆的指令（例如遞迴刪除）沒有任何東西擋住。不要改任何檔案。
