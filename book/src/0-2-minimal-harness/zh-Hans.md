读这一章，需要你在自己的项目里用过 Copilot 的 agent 模式，并且读过[第一章](0-1-the-gap-and-the-map.html)，或者知道“harness”这个词。

## 一句话 {#in-one-sentence}

先从一页规则、一个 skill、一个拦截危险命令的 hook 开始。真遇到痛点了，再往上加。

## 写给管理者 {#for-leaders}

- **要拍板的事**：从最小的一套开始（一页规则、一个 skill、一个拦截的 hook），后面每加一样，都由真实的痛点来批，不由计划来批。
- **风险**：一口气搭一个大 harness，维护成本高，你也说不清哪一部分起了作用。规则只是请求；hook 是模型争不过的规则，但它只拦得住它认得的命令。
- **做对的代价**：据我估计，对一个已经打开了项目的人，大约半小时。团队还要像审代码一样，审规则文件和 hook 文件。
- **可以问团队**：“我们的配置里，哪些部分来自真实的失败，哪些来自模板？”

## 问题 {#problem}

很多人一听到“harness”，脑子里就是一个庞大的系统：[两道审批关卡](5-3-two-approvals.html)、[任务看板](7-2-many-tasks.html)、知识库、报告。然后他们要么放弃，要么一口气全搭出来。这两样都是错的。

大 harness 是有代价的。每个部分都要写，要保持准确，出了毛病还要排查。而且你分不清哪一部分起了作用，因为是一次全加上的。我的 harness 不是一开始就大的。它是一个痛点一个痛点长出来的，后来我还删掉了一些没换来任何东西的部分（[我砍掉了什么，数据怎么说](7-3-what-we-cut.html)）。

所以这一章讲的是值得拥有的最小一套，按我会搭的顺序来讲。据我估计，如果你已经在 VS Code 里打开了项目，大约要半小时。

## 原理 {#how-it-works}

### 为什么是这个顺序

这三样东西，对 agent 的约束力度不同。

1. **规则排第一**。它只要几分钟，不用写代码。它告诉 agent 那些它猜不到的事：你的项目是怎么搭的，什么不能碰。规则是请求，模型可能不理，但按我的经验，写下来的东西它大多数时候都会照做。
2. **skill 排第二**。**skill** 是针对某一类工作的一份简短手册。agent 一开始只看到它的名字和一行描述，需求对得上时才去读全文。你需要它，是因为有些知识太长，放不进规则页：每个步骤都堆在那里，agent 每次对话都得背着全部内容（[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)讲了为什么这很贵）。
3. **hook 排最后**。**hook** 是平台在固定时机运行的一个小程序，比如 agent 运行工具之前。它能说不，模型争不过它。规则和 skill 都是请求。hook 是第一样你能靠得住的规则。它排第三，是因为它是你要写、要维护的代码，所以应该留给那几件绝对不能发生的事。

### 第 1 步：一页规则（约 10 分钟）

在项目根目录建一个指令文件。VS Code 和 Copilot 会读 `AGENTS.md` 或 `.github/copilot-instructions.md` 这样的文件，并在每次对话里交给 agent。它具体认哪些文件名，请查当前的 VS Code 文档。

只写模型会搞错或者会漏掉的东西：你项目自己的命令、限制和坑。别写它本来就懂的，比如在你用的语言里怎么写循环。越短越好，因为太长的规则文件，模型很容易忽略。有一行值得早点加：改完之后要运行的命令（测试、lint），再加上“通过之前不许说做完了”。这是最便宜的检查（[让 agent 能检查自己的活](5-4-self-checks.html)）。

好的第一页有五到十行。我配置里的真实文件更长，但它的核心限制是这样的：

::: code harness AGENTS.md L44-L45 "自带规则页里的两条核心限制：动手之前先看，保留用户自己的改动。"

**怎么确认它生效了**。开一个新对话，问一个只有你的规则才答得出的问题，比如“这个项目里怎么跑测试？”如果它按你的规则回答，说明文件加载了。如果它在猜，检查文件名和位置。

### 第 2 步：一个 skill（约 10 分钟）

挑一件你给 agent 解释过不止一次的活。skill 是一个文件夹，里面有一个 `SKILL.md` 文件。文件开头有名字和**描述**，最重要的是描述。agent 能不能找到这个 skill，全看它。好的描述会说明这个 skill 做什么、什么时候用，以及用户可能会说哪些词。

::: code harness .github/skills/generic-code-standards/SKILL.md L1-L6 "一个真实 skill 的开头：agent 最先看到的，是名字和描述。"

描述下面写步骤，再写一小段坑的清单：agent 通常会在哪些地方出错。每次看到它失败就加一条坑，是我知道的写 skill 最有用的习惯（[把团队的做法写成 skill](3-4-skills-and-workflows.html)）。

**怎么确认它生效了**。在对话里输入 `/`，看有没有这个 skill 的名字。然后说一个符合描述、但不点名这个 skill 的需求，看 agent 会不会用它。agent 一直不选的 skill，通常是描述的问题。

### 第 3 步：一个拦截危险命令的 hook（约 10 分钟）

终端是 agent 手里最厉害的工具，所以从这里下手。挑那些造成的损害无法撤销的命令，比如递归删除一个文件夹，或者下载一个脚本、一行命令就运行。

这要分两部分。一个配置文件告诉平台，在哪些时机调用你的程序。在我的配置里只有一个文件，每个时机都指向同一个程序：

::: code harness .github/hooks/harness.json L40-L51 "工具运行之前那个时机的配置：它只是写明了要调用哪个程序。"

你的程序读取收到的调用。如果命令符合你拦截的某个模式，它就回复一个拒绝，并附上原因。原因很重要：agent 看得到它，所以要写明应该改做什么，否则 agent 会再试同样的事（[询问不是限制](4-2-ask-vs-refuse.html)）。下面是我的一个模式。它很长，因为同一条命令有很多种写法：

::: code harness .harness/policies/gate.json L59-L62 "一条真实的拒绝规则：对根目录、主目录或当前文件夹做递归强制删除，附上 agent 看得懂的原因。"

这是个真实的文件，比你第一天需要的大得多。先写三四个模式就够了。

**怎么确认它生效了**。别拿真正危险的命令来测。先加一条无害的测试规则，比如拒绝命令 `echo hook-test`，然后让 agent 运行它。你应该看到一个带着你写的原因的拒绝。测完把这条测试规则删掉。

我自己的 hook 踩过三个坑：

- **hook 程序启动不了**（比如找不到解释器），平台会把它当作拒绝，agent 一个工具也用不了。屏幕上只写着 hook 出错。在你依赖它之前，先测一次。
- **hook 运行超过时间限制**，平台会放行这次调用，而且不提醒。在我的配置里，限制是 30 秒。这是故障放行：慢的 hook 就是个漏洞，所以让程序保持快。
- **配置是在窗口启动时读的**。改完配置，要重新加载 VS Code 窗口。

hook 做不到什么，同样重要。它看到的是一次调用，看不到命令运行起来之后做了什么（[Hook：每次调用都会经过的执行点](2-2-hooks.html)）。一份模式清单拦得住危险命令的常见写法，拦不住所有写法。它是安全带，不是沙箱。

### 你需要多大的 harness？

这取决于 agent 出错时，谁会受影响。

| 你是 | 大概够用的 | 原因 |
| --- | --- | --- |
| 在自己的项目上单干的一个人 | 上面这三样 | 每处改动你都看得到，出错的代价只有你自己担 |
| 在共享仓库上的小团队 | 这三样，规则文件和 hook 文件像代码一样审，再加一个记录 agent 做了什么的地方 | 别人会承接 agent 的错误，而“谁改了规则”会成为一个问题（[落地与治理](7-4-rollout-and-governance.html)） |
| 大团队，或者有合规义务的代码 | 以上这些，再按你的风险需要加[审批点](5-3-two-approvals.html)、[可计数的检查](5-5-counted-checks.html)和报告 | 出错的代价由别人承担，而且你得拿得出发生了什么 |

我猜大多数读者属于第一行。两道审批关卡和一个任务看板，不是起点。

### 变好了吗？

别信感觉。挑几个你知道正确答案的任务，每次改动前后各跑一遍，用同样的方式打分。[慎用子 agent](2-3-subagents.html)给出了这样的一个对比，[第 6 部分](6-3-eval-tasks.html)讲方法。哪怕是粗糙的版本，五个任务加一张“什么算对”的清单，也比猜强。“什么算对”的清单要在运行之前写好，每个任务要跑几次，因为一次运行可能只是运气（[一次运行证明不了什么](6-4-variance.html)）。

## 代价和坑 {#costs-and-traps}

**规则的第一页会越写越长，也会过期**。每出一次事故，人们就加一行。过一阵它就很长了，有的互相矛盾，模型也就不理它了。时常删减一下，让每条规则只在一个地方。

**hook 会带来虚假的安心**。它只拦它认得的东西。别说“agent 删不了东西”，要说“agent 不能运行这几条具体的命令”。

**我没有测过 VS Code 的每一项设置**。文件名、hook 的支持情况和设置，在不同版本之间会变。上面的步骤在我的配置里能用；你的请查当前的文档。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

这套入门配置里的每一样，都在平台正在吸收的清单上。等平台自己的权限系统开箱就能拒绝同样的危险命令，就把你的 hook 删掉。等它自己学会了你项目的命令，就把你的规则页缩短。每次大的模型升级之后，都重读一遍你的规则（[模型升级了，就要删](6-5-model-upgrades.html)）；为旧模型写的那些行，可能已经成了累赘。
