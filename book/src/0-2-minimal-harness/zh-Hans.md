读这一章，需要你在自己的项目里用过 Copilot 的 agent 模式，并且读过[第一章](0-1-the-gap-and-the-map.html)，或者知道“harness”这个词。

## 一句话 {#in-one-sentence}

先从一页规则、一个 skill、一个拦截危险命令的 hook 开始。别的东西，等真遇到痛点了再加。

## 写给管理者 {#for-leaders}

- **要拍板的事**：从最小的一套开始（一页规则、一个 skill、一个拦截的 hook），以后每加一样，都让真实的痛点来批，而不是让计划来批。
- **风险**：一口气搭出来的大 harness，维护成本高，你也说不清哪一部分起了作用。就算是最小的一套，规则也只是请求。hook 是模型争不过的规则，但它只拦得住它认得的命令。
- **做对的代价**：据我估计，一个已经打开了项目的人，大约要半小时。团队还要像审代码一样，审规则文件和 hook 文件。
- **可以问团队**：“我们的配置里，哪些部分来自真实的失败，哪些来自模板？”

## 为什么不一口气全搭起来？ {#problem}

很多人一听到“harness”，脑子里浮现的就是一个庞大的系统，有[两道审批关卡](5-3-two-approvals.html)、[任务看板](7-2-many-tasks.html)、知识库，还有报告。面对这样一幅图，他们要么干脆放弃，要么一口气全搭出来。这两条路都走错了。

一口气全搭的麻烦在于，大 harness 是有代价的。每个部分都要你去写、去保持准确，出了毛病还得排查。而且既然是一次全加上的，到底是哪一部分起了作用，你也分不清。这一点我是从自己的 harness 上知道的：它并不是一开始就这么大，而是一个痛点一个痛点长出来的，后来我还删掉了一些没换来任何东西的部分（[多 Agent 分工没换来什么：我砍掉的东西](7-3-what-we-cut.html)）。

所以不如从另一头开始：先搭值得拥有的最小一套，按我会搭的顺序一样一样来。如果你已经在 VS Code 里打开了项目，据我估计大约要半小时。

### 为什么先规则，再 skill，最后 hook

这三样东西约束 agent 的力度不同，一样比一样紧。这就引出一个问题：hook 约束得最紧，为什么反而放到最后才搭？

先说规则。它只要写几分钟，不用写代码，却能告诉 agent 那些它自己猜不到的事，比如你的项目是怎么搭的、什么东西不能碰。规则只是请求，模型可能不理，但按我的经验，写下来的东西它大多数时候都会照做。

不过规则页也有装不下的东西，因为有些知识太长了。要是每个步骤都堆在那里，agent 每次对话都得背着全部内容（为什么这很贵，见[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)）。**skill** 就是为这个准备的，它是针对某一类工作的一份简短手册。agent 一开始只看到它的名字和一行描述，等需求对得上了，才去读全文。

可规则和 skill 终归都是请求，模型可以不理。**hook** 才是第一样你真正靠得住的规则。它是平台在固定时机（比如 agent 运行工具之前）运行的一个小程序。它说不的时候，模型争不过它。它之所以还是放在最后，是因为它是你要写、要维护的代码，这份力气应该留给那几件绝对不能发生的事。

### 第 1 步：一页规则（约 10 分钟）

先在项目根目录建一个指令文件。VS Code 和 Copilot 会读 `AGENTS.md` 或 `.github/copilot-instructions.md` 这样的文件，并在每次对话里交给 agent（它具体认哪些文件名，请查当前的 VS Code 文档）。

文件里只写模型会搞错或者会漏掉的东西，也就是你项目自己的命令、限制和坑。它本来就懂的就别写了，比如在你用的语言里怎么写循环。越短越好，因为规则文件一长，模型就很容易忽略它。规则页虽然要短，有一行却值得早点加上：改完之后要运行的命令（测试、lint），再加一句“通过之前不许说做完了”。这是最便宜的检查（[让 Agent 自己跑测试](5-4-self-checks.html)）。

好的第一页有五到十行。我配置里的真实文件要长一些，但它的核心限制是这样的：

::: code harness AGENTS.md L44-L45 "自带规则页里的两条核心限制：动手之前先看，保留用户自己的改动。"

要确认这个文件生效了，可以开一个新对话，问一个只有你的规则才答得出的问题，比如“这个项目里怎么跑测试？”如果它是照着你的规则回答的，说明文件加载了；如果它在猜，就检查一下文件名和位置。

### 第 2 步：一个 skill（约 10 分钟）

skill 写什么？挑一件你给 agent 解释过不止一次的活就行。skill 是一个文件夹，里面有一个 `SKILL.md` 文件，文件开头写着名字和**描述**。最要紧的是描述，因为 agent 能不能找到这个 skill，全看它。好的描述会说清这个 skill 做什么、什么时候用，以及用户可能会说哪些词。

::: code harness .github/skills/generic-code-standards/SKILL.md L1-L6 "一个真实 skill 的开头：agent 最先看到的，是名字和描述。"

开头下面写步骤，步骤后面再列一小段坑的清单，也就是 agent 通常会出错的地方。每看到它失败一次就加一条坑，这是我知道的写 skill 最有用的习惯（[怎么写一个真正好用的 skill？](3-4-skills-and-workflows.html)）。

要确认 skill 生效了，可以在对话里输入 `/`，看看有没有它的名字。然后提一个符合描述、但不点名这个 skill 的需求，看 agent 会不会用上它。agent 要是一直不选某个 skill，问题通常出在描述上。

### 第 3 步：一个拦截危险命令的 hook（约 10 分钟）

终端是 agent 手里最厉害的工具，所以 hook 就从这里下手。挑那些造成的损害无法撤销的命令，比如递归删除一个文件夹，或者下载一个脚本、一行命令就直接运行。

这要分两部分：一是配置文件，告诉平台在哪些时机调用你的程序；二是程序本身。在我的配置里只有一个配置文件，每个时机都指向同一个程序：

::: code harness .github/hooks/harness.json L40-L51 "工具运行之前那个时机的配置：它只是写明了要调用哪个程序。"

程序拿到的，是 agent 将要发出的那次工具调用，也就是要用哪个工具、输入是什么。如果命令符合你拦截的某个模式，它就回复一个拒绝，并附上原因。原因很重要，因为 agent 看得到它，所以要写明应该改做什么，否则 agent 还会再试同样的事（[“先问我”为什么挡不住 Agent？](4-2-ask-vs-refuse.html)）。下面是我的一个模式，它写得很长，因为同一条命令有很多种写法：

::: code harness .harness/policies/gate.json L59-L62 "一条真实的拒绝规则：对根目录、主目录或当前文件夹做递归强制删除，附上 agent 看得懂的原因。"

这是个真实的文件，比你第一天需要的大得多。先写三四个模式就够了。

确认 hook 生效要小心一点，因为不能拿真正危险的命令来测。先加一条无害的测试规则，比如拒绝命令 `echo hook-test`，再让 agent 去运行它。你应该会看到一个带着你写的原因的拒绝。测完，把这条测试规则删掉。

我自己的 hook 踩过三个坑：

- hook 程序要是启动不了（比如找不到解释器），平台会把它当作拒绝，agent 一个工具也用不了。可屏幕上只写着 hook 出错，所以在你依赖它之前，先测一次。
- hook 运行超过时间限制（在我的配置里是 30 秒），平台会放行这次调用，而且不提醒。换句话说，hook 是故障放行的：它一慢，命令就像没有 hook 一样照常运行。所以要让程序保持快。
- 配置是在窗口启动时读的，所以改完配置，要重新加载 VS Code 窗口。

hook 做不到什么，同样重要。它看到的是一次调用，看不到命令运行起来之后做了什么（[硬性规则放在哪？用 hook](2-2-hooks.html)）。所以一份模式清单拦得住危险命令的常见写法，却拦不住所有写法。它是安全带，不是沙箱。

### 你需要多大的 harness？

这三样够不够，取决于 agent 出错时谁会受影响。

| 你是 | 大概够用的 | 原因 |
| --- | --- | --- |
| 在自己的项目上单干的一个人 | 上面这三样 | 每处改动你都看得到，出错的代价只有你自己担 |
| 在共享仓库上的小团队 | 这三样，规则文件和 hook 文件像代码一样审，再加一个记录 agent 做了什么的地方 | 别人会承接 agent 的错误，而“谁改了规则”会成为一个问题（[怎么把 Agent 配置推广到整个团队？](7-4-rollout-and-governance.html)） |
| 大团队，或者有合规义务的代码 | 以上这些，再按你的风险需要加[审批点](5-3-two-approvals.html)、[可计数的检查](5-5-counted-checks.html)和报告 | 出错的代价由别人承担，而且你得拿得出发生了什么 |

我猜大多数读者属于第一行。开头那幅图里的两道审批关卡和任务看板，不是起点。

### 怎么知道变好了没有？

每加一样东西，你都会想知道它有没有用，可感觉是靠不住的。更好的办法是挑几个你知道正确答案的任务，每次改动前后各跑一遍，用同样的方式打分。[别跟风瞎用子 Agent](2-3-subagents.html)给出了这样的一个对比，[第 6 部分](6-3-eval-tasks.html)讲方法。哪怕是粗糙的版本，五个任务加一张“什么算对”的清单，也比猜强。只是这张清单要在运行之前写好。每个任务也要跑几次，因为一次运行可能只是运气（[同一个任务跑两次，结果不一样](6-4-variance.html)）。

## 这套入门配置会在哪里出问题 {#costs-and-traps}

这套入门配置虽小，也有自己出问题的地方。最先出问题的是规则页，它会越写越长，也会过期。每出一次事故，人们就加一行，所以过一阵它就很长了，有些条目互相矛盾，模型也就不理它了。要时常删减一下，让每条规则只在一个地方。

hook 出问题的方式更隐蔽，它会带来虚假的安心。它只拦它认得的东西，所以别说“agent 删不了东西”，要说“agent 不能运行这几条具体的命令”。

最后还要交代一句：我没有测过 VS Code 的每一项设置。文件名、hook 的支持情况和设置在不同版本之间会变，所以上面的步骤虽然在我的配置里能用，你的还是请查当前的文档。

## 什么时候可以把每一样删掉 {#when-to-delete-it}
{status: industry}

除了盯紧它们，你还要知道什么时候可以拿掉它们，因为这套入门配置里的每一样，都是平台正在慢慢自带的东西。等平台自己的权限系统开箱就能拒绝同样的危险命令，就把你的 hook 删掉。等它自己学会了你项目的命令，就把你的规则页缩短。还有，每次大的模型升级之后，都重读一遍你的规则（[换了新模型，旧规则该删了](6-5-model-upgrades.html)），因为为旧模型写的那些行，可能已经成了累赘。

## 在你自己的环境里试试 {#try-it}

::: prompt
对照一套三部分的最小配置，检查这个仓库：一页简短的规则、一个 skill、一个拦截的 hook。每一部分，说明它在不在、在哪、有没有用。对规则，列出又长、又过期或者互相矛盾的行，并指出缺了哪些模型猜不到的命令和限制。对 hook，列出哪些不可逆的命令（比如递归删除）没有任何东西拦着。不要修改任何文件。
