读这一章，需要你用过 AI 编程 agent 开过很长的对话，并且读过[上下文是一份预算](3-1-context-budget.html)（窗口有大小上限，里面的东西互相争地方）。

## 一句话 {#in-one-sentence}

对话越长，表现越差。别指望模型自己记住：把重要的写进文件，清掉旧的工具结果，或者开一个新对话。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求重要的东西都放在文件里，而不是只留在对话中，并且约定好什么时候开新对话。
- **风险**：对话变长会变差，而平台对对话做的摘要会丢细节，比如你的原话和做某个选择的原因。在我自己的配置里，质量下降得多快，我没量过，所以不给速率。
- **做对的代价**：每项工作一个简短的笔记文件，每做完一步就更新一次。如果交接内容半页纸写不下，说明这件事还没想清楚。
- **可以问团队**：“如果这个对话现在没了，我们会丢什么？”

## 问题 {#problem}

你和 agent 已经合作了两个小时。一开始它很利落。现在它却来问你开头就定下的事，重复犯一个已经修掉的错，或者改错了文件。什么都没坏。只是对话变长了。

先说三个词。前两个在[上下文是一份预算](3-1-context-budget.html)里定义过，这里简单提一下。

- **上下文窗口**是模型一次能看到的文本。它有大小上限。
- **工具结果**是 agent 用工具后返回的内容。它们通常是窗口里最大的几项。
- **压缩**是平台在窗口快满时做的事：让模型把到目前为止的对话总结一下，然后从摘要接着往下走。

在我自己的配置里，质量下降得多快，我没量过，所以不会给你一个数字。问题的形状已经足够清楚，可以据此行动，做模型的人也是这么描述的（见[业界怎么说](#industry)）。

### 长对话为什么会变差

看图最容易懂：同一个对话的三个时刻。

::: figure 3-2-context-rot

四件事同时发生。

1. **有用的部分不会变大，其余的会。** 任务眼下需要的（需求、你给的规则、正在改的文件）大小基本不变。其余的都堆在它周围：一小时前读的文件，一份又长又已经无关的测试输出，三次错误的尝试。
2. **模型每次都要把所有内容读一遍。** 它没有文件柜。每一轮，整个窗口都要重新读一遍。旧文本越多，那一行要紧的内容要争的对手就越多。（缓存能让重复读取省钱，见[选模型：看每次成功的成本](1-1-models-and-cost.html)，但不会让窗口变得不那么挤。）这种现象叫**上下文腐化**：窗口越满，模型对里面内容的回忆就越不可靠。
3. **早先的内容离用到它的地方很远。** 第一条消息里的规则，现在已经在几千行之前。它还在，但离用到它的那一步很远。这一条是我自己对所见现象的理解，没有出处。
4. **压缩会丢细节。** 摘要留下的，是写摘要的一方认为重要的。你的原话、做某个选择的原因、那条古怪的约束，都是摘要最先丢掉的，而且你没法知道它丢了哪些。

这些都不是某个产品的 bug。它来自窗口本身的工作方式，所以对每个 agent 都适用。

## 原理 {#how-it-works}

答案不是“更大的窗口”，也不是“更聪明的摘要”。而是别再把对话当成放重要东西的地方。一共有四招。第一招是要一直保持的习惯。另外三招在对话变长时用，从最轻到最重。

::: figure 3-2-four-moves

### 1. 把要紧的写进文件

问自己：如果这个对话现在没了，我会丢什么？不管答案是什么，那些东西都不该只存在于对话里。

- **定了什么**，以及为什么。
- **做完了什么，下一步是什么。**
- **东西在哪**（哪些文件，哪些命令）。

这些写进 agent 能重新读到的文件：任务文件夹里的一份简短笔记，或者它的待办清单（两者都在[管任务，不管对话](5-1-tasks.html)里讲）。文件不会被压缩，新对话一秒钟就能读完。重新读到时，它的文本在窗口的靠后位置，离用到它的地方很近。

在我的配置里，每项工作都有一个文件夹，里面有一份**交接文件**：做到哪了、下一步、定了什么。新对话先读这份文件，然后接着干。因此丢一个对话，我损失的是几分钟，不是整份工作。

**笔记怎么写。** 要短。写现在是什么情况，不要讲怎么走到这一步的故事。下一步放在最上面。一页比十页好，因为新对话得读它，而它也占地方。

**让 agent 来做。** 让它每做完一步就更新笔记，不要等到最后。到最后你已经累了，对话也最长。一句话就能说清：“每做完一步，更新笔记文件：定了什么、做完了什么、下一步。”

Anthropic 为长时间运行的 agent 描述过同样的习惯：一份进度文件加上 git 历史，新会话开始时 agent 先读它们（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。下面是我配置里交接文件的模板：

::: code harness .harness/contracts/templates/task/en/TASK.md L1-L23 "交接文件模板：状态、现在在做什么、下一步、要读的文件、已经定下的事，以及待解决的问题。"

### 2. 清掉旧的工具结果

窗口里的大部分，通常是旧的工具输出。agent 为了找一个函数读了整个文件，整个文件还留在那里。一次测试跑出了好几页输出，真正有用的只有失败的那一行。

扔掉这些，是最轻的一种压缩，也最安全：决定和结论留下，只去掉原始材料。agent 如果还要用那个文件，可以再读一遍。在 Anthropic 的 API 上，这是一个叫上下文编辑（context editing）的功能：名为 `clear_tool_uses` 的策略，会在输入超过你设定的大小之后，把最旧的工具结果清掉。它还在 beta 阶段，而且清除会让缓存的开头失效，所以是有代价的（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）。你的工具有没有类似的功能、什么时候触发，需要去查，不能想当然。Copilot 今天怎么做，我没测过（见[代价和坑](#costs-and-traps)）。

你也可以手动做到同样的效果。一段长时间的阅读结束后，让 agent 只写下它的发现，然后在一个新对话里接着干，新对话里有发现，没有阅读的过程。

### 3. 把大块的阅读交给子 agent

如果下一步要读很多东西，别在主对话里读。**子 agent** 是第二个 agent，它从空窗口开始，只把一份简短的报告送回来。阅读的内容留在它的窗口里，你的主对话只拿到结论。这就是[慎用子 agent](2-3-subagents.html)里的“并行阅读”那种情况，限制也一样：只有一份简短的报告就够用时才行，而且总共花得更多。

有的平台把它做成了设置。在 VS Code 里，skill 可以在头部声明 `context: fork`，这样它就在自己的子 agent 里运行，而不是在你的对话里（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)；文档标明它是实验性的）。读得多、报告得少的 skill 很适合。我没试过，所以不知道它怎么计用量，也不知道 hook 怎么看待它。

### 4. 开一个新对话

有时候正确的做法是停下来。该停的信号：

- agent 重复你已经定下的事。
- 它撤销了一小时前的修复。
- 你发现自己在重新解释。
- 任务变了（新任务就开新对话）。

新对话从空窗口加规则开始。只给它继续干活所需的东西：让它去读笔记文件。按我的经验，它常常比旧对话到最后时做得更好，因为它读到的是一张干净的纸。这一点我没量过。

比一比成本。重新开始让人觉得进度丢了。但进度在文件里、在代码里；对话里只留着对进度的记忆，而这份记忆早就磨损了。

**有计划地重新开始。** 对我拆成多步的长任务，我不会等对话变差。比如学一个大代码库，是分批做的，每两三批我就开一个新对话。状态在任务里，不在对话里，所以交界处什么也不会丢。

### 交接什么

换对话时，新对话需要一小套固定的内容：

1. 需求，几行就行。
2. 哪些定了，哪些没定。
3. 做完了什么，下一步是什么。
4. 文件在哪。

这四样如果半页纸写不下，那才是真正的发现：这件事还没想清楚，没法交给任何人，包括明天的你自己。

### 检验你自己的配置

一个便宜的测试，不需要额外配置，一个人一小时就能做完。挑一条你在长对话早期给的规则，要有两三个部分。工作一小时后，让 agent 不回头看，直接复述这条规则。然后开一个新对话，只给它你的笔记文件，再问同样的问题。按每个回答答对了几个部分来打分。如果第二个更准确，说明你的对话还不如你的文件靠谱。

还要查一下你的指令放在哪。只在对话里给的规则，对话被压缩时就丢了；放在平台会重新读取的文件里的规则就不会。Claude Code 的文档对它的项目指令文件，说的就是这一点。想让一条规则留下来，就把它放进文件。

## 代价和坑 {#costs-and-traps}

**别掩盖坏习惯。** 如果对话变长是因为任务太大，办法是把任务拆小，而不是更好地记笔记。

**笔记可能是错的。** 如果 agent 在笔记里写“测试通过”，而实际没有，下一个对话就是从一个假的事实出发。笔记是 agent 的报告；重要的要核对。[agent 该记住什么](3-5-memory.html)详细讲的就是这个问题。

**笔记也占地方。** 一份不断变长又不修剪的笔记文件，会变成填满窗口的那个东西。保持简短，把已经做完的删掉。另外，笔记文件里可能有你不想共享的内容，放进共享仓库之前要想一想。

**新对话会丢掉“默契”。** 旧对话知道你怎么措辞，也知道你说的“老办法”是什么意思。如果这很重要，就写下来；它多半就是一条规则。

**我没测的。** 我没量过我用的平台是怎么压缩的：留下什么，丢掉什么，会不会自己清理旧的工具结果。在你为自己的工具查过之前，把压缩当作有损的。

## 业界怎么说 {#industry}
{status: industry}

Anthropic 的工程团队描述过这个问题和同样的办法。他们用的术语是上下文腐化（context rot）：窗口越满，“模型准确回忆那段上下文里信息的能力就越下降”。他们提出了压缩（“把一段接近上下文窗口上限的对话，总结其内容”），称清除工具结果是“最安全、最轻量的压缩方式之一”，还描述了记笔记，即“agent 定期写下笔记，保存在上下文窗口之外的内存里”。（[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）

Claude Code 的文档补充了一个实用细节：根目录的项目指令文件在压缩之后会从磁盘重新读取，而只在对话里给的指令就没了。（[How Claude remembers your project](https://code.claude.com/docs/en/memory)）

对需要很多个会话才能完成的长任务，Anthropic 描述了一份进度文件加 git 历史，每个新会话先读它们。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）在 API 上，清除工具结果以上下文编辑的形式提供，处于 beta 阶段。（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）

它们彼此一致，也和这一章一致。没有一家给出对话多长算太长的规则，我也没有；凭上面的信号来判断。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

这里有一部分是平台的活，平台会做得更好：清掉旧的工具结果、压缩、把关键事实带到下一轮。等你的工具把这些做好了，而且你查过它留下什么，就不用再手动做了。

核心不变：如果这项工作重要，它的状态就该放在你能读到的文件里，而不是对话里。窗口更大、压缩更好，能让对话撑得更久。但它们不会让摘要和原文一样好，也不会让新对话拥有你最近两个小时的经历。如果有平台能证明，它压缩后的对话没有丢掉我在意的任何东西，并且是在我自己的任务上量出来的，我会重新考虑。
