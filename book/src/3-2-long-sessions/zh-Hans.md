读这一章，需要你用 AI 编程 agent 开过很长的对话，并且读过[上下文是一份预算](3-1-context-budget.html)（窗口有大小上限，里面的东西互相争地方）。

## 一句话 {#in-one-sentence}

对话越长，表现越差。别指望模型自己记住：把重要的写进文件，清掉旧的工具结果，或者开一个新对话。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求凡是重要的东西都放在文件里，不能只留在对话中，并且约定好什么时候开新对话。
- **风险**：对话变长会变差；平台给对话做摘要时，还会丢掉细节，比如你的原话、做某个选择的原因。在我自己的配置里，质量掉得多快我没量过，所以不给速率。
- **做对的代价**：每项工作一个简短的笔记文件，每做完一步就更新一次。如果交接内容半页纸写不下，说明这件事还没想清楚。
- **可以问团队**：“如果这个对话现在没了，我们会丢什么？”

## 对话越长，agent 为什么越差？ {#problem}

你和 agent 已经一起干了两个小时。一开始它很利落，可现在它会来问你开头就定下的事，会重犯一个已经修掉的错，或者干脆改错了文件。什么都没坏，只是对话变长了。

那么，光是对话变长，为什么就会出问题？因为 agent 手上的一切，都放在它的**上下文窗口**里，也就是模型一次能看到的全部文本，而这个窗口有大小上限。窗口里最大的几项，通常是**工具结果**，也就是 agent 每次用工具后返回的内容（这两个词在[上下文是一份预算](3-1-context-budget.html)里都定义过）。窗口快满的时候，平台还会做一件事，叫**压缩**：让一个模型把到目前为止的对话总结一遍，再从这份摘要接着往下走。

在我自己的配置里，质量下降得有多快，我没量过，所以不会给你一个数字。但问题的样子已经清楚到可以据此行动了，做模型的人也是这么描述的（详见[做模型的人也这么看吗？](#industry)）。

### 对话变长时，窗口里发生了什么

看图最容易明白：下面是同一个对话的三个时刻。

::: figure 3-2-context-rot

这几个时刻里，有四件事在同时发生。头一件是，有用的部分不会变大，其余的却越来越多。任务眼下需要的东西（需求、你给的规则、正在改的文件）大小基本不变，围着它堆起来的，却是一小时前读过的文件、一份又长又早已无关的测试输出，还有三次失败的尝试。

要是模型能把旧东西收进文件柜，这还不算太要紧，可它没有文件柜：每一轮，它都要把整个窗口从头再读一遍。旧文本越多，真正要紧的那一行要争的对手就越多。（缓存能让重复读取少花点钱，见[选模型：看每次成功的成本](1-1-models-and-cost.html)，可窗口并不会因此变得不挤。）这种现象叫**上下文腐化**：窗口越满，模型对里面内容的回忆就越靠不住。

还有，早先说过的话，会离用到它的地方越来越远。你在第一条消息里给的规则还在，只是和它该起作用的那一步之间，已经隔了几千行。这一条是我自己对所见现象的理解，没有出处。

等到窗口快满，压缩又会丢掉细节。摘要留下的，是写摘要的一方认为重要的东西。你的原话、做某个选择的原因、那条古怪的约束，都是摘要最先丢掉的，而丢了哪些，你根本没法知道。

这些都不是某个产品的 bug。它们来自窗口本身的工作方式，所以对每个 agent 都一样。既然如此，我们能做些什么？

## 把要紧的东西放到对话外面 {#how-it-works}

答案不是“更大的窗口”，也不是“更聪明的摘要”，而是别再把对话当成存放重要东西的地方。为此有四招。第一招是要一直保持的习惯；另外三招在对话变长时才用，从最轻到最重。

::: figure 3-2-four-moves

### 1. 把要紧的写进文件

先问自己一个问题：如果这个对话现在没了，我会丢什么？不管答案是什么，那些东西都不该只存在于对话里。具体说，就是定了什么、为什么这么定，做完了什么、下一步做什么，以及东西在哪（哪些文件，哪些命令）。

这些都要写进 agent 能重新读到的文件里，比如任务文件夹里的一份简短笔记，或者它的待办清单（两者都在[管任务，不管对话](5-1-tasks.html)里讲）。文件不会被压缩，新对话一秒钟就能读完。而且重新读进来时，它的文本落在窗口的靠后位置，正好离用到它的地方很近。

在我的配置里，每项工作都有一个文件夹，里面放着一份**交接文件**，记着做到哪了、下一步是什么、定了什么。新对话先读这份文件，再接着往下干。所以就算丢了一个对话，我损失的也只是几分钟，而不是整份工作。

笔记要写得短。一页比十页好，因为新对话得把它读一遍，它本身也占地方。写现在是什么情况，不讲是怎么走到这一步的，下一步放在最上面。

这件事交给 agent。让它每做完一步就更新笔记，别等到最后，因为到了最后你已经累了，对话也最长。设置起来一句话就够：“每做完一步，更新笔记文件：定了什么、做完了什么、下一步。”

Anthropic 为长时间运行的 agent 描述过同样的习惯，靠的是一份进度文件加上 git 历史，新会话一开始，agent 先读它们（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。下面是我配置里交接文件的模板：

::: code harness .harness/contracts/templates/task/en/TASK.md L1-L23 "交接文件模板：状态、现在在做什么、下一步、要读的文件、已经定下的事，以及待解决的问题。"

### 2. 清掉旧的工具结果

窗口里的大部分，通常是旧的工具输出。agent 为了找一个函数读了一个文件，可整个文件都还留在那里；一次测试跑出好几页输出，真正有用的只有失败的那一行。

把这些扔掉，是最轻的一种压缩，也是最安全的一种，因为决定和结论都留着，去掉的只是原始材料。agent 要是还需要那个文件，再读一遍就是了。在 Anthropic 的 API 上，这是一个叫上下文编辑（context editing）的功能：名为 `clear_tool_uses` 的策略，会在输入超过你设定的大小之后，把最旧的工具结果清掉。不过这个功能还在 beta，清除也不是没有代价，因为它会让缓存的开头失效（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）。你自己的工具有没有类似的功能、什么时候触发，得去查，不能想当然。至于 Copilot 现在怎么做，我没测过（见[这几招在哪里会出问题](#costs-and-traps)）。

你也可以手动做到同样的效果。一段长长的阅读结束后，让 agent 只写下它发现了什么，然后换一个新对话接着干。新对话里有那份发现，却没有读的过程。

### 3. 把大块的阅读交给子 agent

如果下一步要读很多东西，就别在主对话里读，交给一个**子 agent**。它是第二个 agent，从空窗口开始，最后只送回一份简短的报告。读过的内容都留在它的窗口里，你的主对话拿到的是结论。这就是[慎用子 agent](2-3-subagents.html)里说的“并行阅读”，两条限制也一样：只有一份简短的报告就够用时才行得通，而且总的花费会更多。

有的平台把这件事做成了一个设置。在 VS Code 里，skill 可以在头部声明 `context: fork`，这样它就在自己的子 agent 里运行，而不是在你的对话里（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)；文档标明它是实验性的）。读得多、报告得少的 skill 正适合这么做。不过我没试过，所以不知道它怎么计用量，也不知道 hook 怎么看到它。

### 4. 开一个新对话

有时候，正确的做法是停下来。出现下面这些信号，就该停了：

- agent 重复你已经定下的事。
- 它撤销了一小时前的修复。
- 你发现自己在重新解释。
- 任务变了（新任务就开新对话）。

新对话从一个空窗口加上规则开始。只给它继续干活所需的东西就行，也就是让它去读笔记文件。按我的经验（这一点我没量过），它常常比旧对话到最后时做得更好，因为它读的是一张干净的纸。

重新开始，难免让人觉得进度丢了，所以值得算一算到底丢了什么。进度其实在文件里、在代码里，对话里留着的只是对进度的记忆，而这份记忆早就磨损了。

对我拆成多步的长任务，我不会等对话变差，而是在事先定好的节点重新开始。比如学一个大代码库是分批做的，每两三批我就开一个新对话。状态在任务里，不在对话里，所以在交界处什么也不会丢。

### 交接什么

既然要开新对话，接下来的问题就是给它什么。它需要一小套固定的内容：

1. 需求，几行就行。
2. 哪些定了，哪些没定。
3. 做完了什么，下一步是什么。
4. 文件在哪。

这四样要是半页纸写不下，那才是真正的发现：这件事还没想清楚，没法交给任何人，包括明天的你自己。

### 用一小时检验你自己的配置

那么，怎么知道你的对话是不是已经不如你的文件了？有一个便宜的测试，不需要额外配置，一个人一小时就能做完。挑一条你在长对话早期给的、包含两三个部分的规则。干了一小时之后，让 agent 不回头看，直接复述这条规则。然后开一个新对话，只给它你的笔记文件，再问同样的问题。按每个回答答对了几个部分来打分。如果第二个更准，就说明你的对话还不如你的文件。

顺便也查一下你的指令放在哪。只在对话里给的规则，对话一压缩就丢了；放在平台会重新读取的文件里的规则则不会。Claude Code 的文档说到它的项目指令文件时，讲的正是这一点。所以，想让一条规则留下来，就把它放进文件。

## 这几招在哪里会出问题 {#costs-and-traps}

用这几招之前，先想想对话为什么会变长。如果是因为任务太大，办法是把任务拆小。笔记记得再好，也只是掩盖了坏习惯。

就算任务大小合适，笔记本身也可能是错的。agent 在笔记里写了“测试通过”，实际却没通过，下一个对话就是从一个假的事实出发的。笔记是 agent 的报告，重要的那些要核对。[agent 该记住什么](3-5-memory.html)详细讲的就是这个问题。

写对了的笔记也有自己的代价：它占地方。一份不断变长、又没人修剪的笔记文件，最后会变成填满窗口的那个东西，所以要保持简短，把已经做完的删掉。另外，笔记文件里可能有你不想共享的内容，放进共享仓库之前要想一想。

笔记记得再好，新对话也还是会丢掉旧对话的那份“默契”。旧对话知道你习惯怎么措辞，也知道你说的“老办法”是什么意思。如果这很重要，就把它写下来，因为它多半就是一条规则。

最后是我没测过的部分。我没量过我用的平台是怎么压缩的：留下什么，丢掉什么，会不会自己清理旧的工具结果。在你为自己的工具查清楚之前，就把压缩当作有损的。

## 做模型的人也这么看吗？ {#industry}
{status: industry}

Anthropic 的工程团队描述过这个问题，也给过同样的办法。他们用的术语是上下文腐化（context rot），意思是窗口越满，“模型准确回忆那段上下文里信息的能力就越下降”。他们提出了压缩（“把一段接近上下文窗口上限的对话，总结其内容”），称清除工具结果是“最安全、最轻量的压缩方式之一”，还描述了记笔记，即“agent 定期写下笔记，保存在上下文窗口之外的内存里”。（[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）

Claude Code 的文档补充了一个实用的细节，前面查指令放在哪，依据的就是它：根目录的项目指令文件在压缩之后会从磁盘重新读取，而只在对话里给的指令就没了。（[How Claude remembers your project](https://code.claude.com/docs/en/memory)）

对需要很多个会话才能完成的长任务，Anthropic 描述了一份进度文件加 git 历史，每个新会话先读它们。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）而在 API 上，清除工具结果以上下文编辑的形式提供，处于 beta 阶段。（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）

这些说法彼此一致，也和这一章一致。对话多长算太长，没有一家给出规则，我也不给，还是凭上面那些信号来判断。

## 哪些可以删掉，哪些要留下 {#when-to-delete-it}
{status: industry}

上面这几招里，有一部分本来就是平台的活，平台也会做得更好：清掉旧的工具结果、压缩、把关键事实带过去。等你的工具把这些做好了，而且你查过它留下了什么，就不用再手动做了。

不过核心不变：如果这项工作重要，它的状态就该放在你能读到的文件里，而不是对话里。窗口更大、压缩更好，能让对话撑得更久，但它们不会让摘要和原文一样好，也不会让新对话拥有你最近这两个小时。如果有平台能证明，它压缩后的对话没有丢掉我在意的任何东西，而且是在我自己的任务上量出来的，我会重新考虑。

## 在你自己的环境里试试 {#try-it}

::: prompt
假设这个对话丢了，要由一个新的 agent 接着干。根据你在这个仓库里能看到的东西（最近的提交、未提交的改动、任何笔记或任务文件、指令文件），写出那个 agent 需要的交接内容：几行说清需求、哪些已经定了、做完了什么和下一步、文件在哪。然后列出你从仓库里看不出来的东西，作为必须由人来补上的空缺。只打印出来，不要修改任何文件。
:::
