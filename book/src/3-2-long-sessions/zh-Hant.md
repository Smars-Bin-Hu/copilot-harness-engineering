讀這一章，需要你已經和寫程式的 AI agent 開過很長的對話，也讀過[上下文是一份預算](3-1-context-budget.html)（視窗有大小上限，裡面所有東西都在搶位子）。

## 一句話 {#in-one-sentence}

長對話會變差。別指望模型記得：把要緊的寫進檔案、清掉舊的工具結果，或開一個新的對話。

## 給主管 {#for-leaders}

- **要做的決定**：要求凡是要緊的東西都放在檔案裡，不能只留在對話裡，並且約好什麼時候開新的對話。
- **風險**：長對話會變差；平台替對話做摘要時，還會丟掉細節，例如你原話的措辭、做某個選擇的理由。在我自己的設定裡，品質掉得多快我沒量過，所以不給比率。
- **做對的成本**：每件工作一份簡短的筆記檔，每做完一步就更新一次。如果交接寫不進半頁，說明這件工作還不夠清楚。
- **可以問團隊**：「如果這個對話現在消失了，我們會丟掉什麼？」

## 對話越長，agent 為什麼越差？ {#problem}

你和 agent 已經一起工作了兩小時。一開始它很敏銳，現在卻會問起你一開始就定好的事，會重犯一個已經修掉的錯誤，或是乾脆改錯檔案。什麼都沒壞，只是對話變長了。

那麼，光是對話變長，為什麼就會出問題？因為 agent 手上的一切，都放在它的**上下文視窗**裡，也就是模型一次能看到的全部文字，而這個視窗有大小上限。視窗裡最大的項目，通常是**工具結果**，也就是 agent 每次使用工具後回來的內容（這兩個詞在[上下文是一份預算](3-1-context-budget.html)裡都定義過）。視窗快滿的時候，平台還會做一件事，叫**壓縮**（compaction）：請一個模型把到目前為止的對話摘要一遍，再從這份摘要繼續下去。

在我自己的設定裡，品質掉得多快，我沒量過，所以不會給你一個數字。但問題的樣子已經清楚到可以據此行動，做模型的人也是這樣描述的（詳見[做模型的人也這麼看嗎？](#industry)）。

### 對話變長時，視窗裡發生了什麼

用一張圖最容易看懂：下面是同一個對話的三個時刻。

::: figure 3-2-context-rot

這幾個時刻裡，有四件事同時在發生。頭一件是，有用的部分不會變大，其餘的卻越來越多。任務眼下需要的東西（需求、你給的規則、正在編輯的檔案）大小差不多不變，圍著它堆起來的，卻是一小時前讀過的檔案、一份很長而現在早已無關的測試輸出，還有三次錯誤的嘗試。

要是模型能把舊東西收進檔案櫃，這還不算太要緊，可它沒有檔案櫃：每一輪，它都要把整個視窗從頭重讀一遍。舊的文字越多，真正要緊的那一行要競爭的對手就越多。（快取可以讓重讀少花一點錢，見[選模型，別只看 token 單價](1-1-models-and-cost.html)，但視窗並不會因此變得不擠。）這個現象叫**上下文腐化**：視窗越滿，模型對裡面內容的回想就越不可靠。

還有，早先說過的話，會離用到它的地方越來越遠。你在第一則訊息裡給的規則還在，只是和它該適用的那一步之間，已經隔了幾千行。這一點是我自己對所見的解讀，沒有來源。

等到視窗快滿，壓縮又會丟掉細節。摘要留下的，是寫摘要的那一方認為重要的東西。你原話的措辭、做某個選擇的理由、那一條古怪的限制，都是摘要最先丟掉的，而丟了哪些，你根本無從知道。

這些都不是某一個產品的 bug。它們來自視窗的運作方式，所以每一個 agent 都一樣。既然如此，我們能做些什麼？

## 把要緊的東西放到對話外面 {#how-it-works}

答案不是「更大的視窗」，也不是「更聰明的摘要」，而是不再把對話當成存放要緊東西的地方。為此有四個動作。第一個是要一直保持的習慣；另外三個，等對話變長再用，由輕到重。

::: figure 3-2-four-moves

### 1. 把要緊的寫進檔案

先問自己一個問題：如果這個對話現在消失了，我會丟掉什麼？不管答案是什麼，那些東西都不該只存在於對話裡。具體來說，就是決定了什麼、為什麼這樣決定，做完了什麼、接下來做什麼，以及東西在哪裡（哪些檔案、哪些指令）。

這些都要寫進 agent 能再讀的檔案，例如任務資料夾裡一份簡短的筆記檔，或是它的待辦清單（兩者都在[管任務，不管對話](5-1-tasks.html)裡說明）。檔案不會被壓縮，新的對話一秒鐘就能讀完。而且再讀進來的時候，它的文字會落在視窗的末端，正好靠近用到它的地方。

在我的設定裡，每件工作都有一個資料夾，裡面放著一份**交接檔**，記著做到哪了、下一步是什麼、已經決定了什麼。新的對話先讀這份檔案，再接著做下去。所以就算丟掉一個對話，我也只損失幾分鐘，而不是整件工作。

筆記要寫得短。一頁比十頁好，因為新的對話得把它讀一遍，它本身也佔位子。寫現在是什麼樣子，不寫是怎麼走到這一步的，下一步放在最上面。

這件事交給 agent。請它每做完一步就更新筆記，不要等到最後，因為最後正是你累了、對話也最長的時候。設定起來一句話就夠：「每做完一步，就更新筆記檔：已決定的事、已完成的事、下一步。」

Anthropic 為長時間運行的 agent 描述了同樣的習慣，靠的是一份進度檔加上 git 歷史，新的會話一開始，agent 先讀這些（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。下面是我的設定裡交接檔的範本：

::: code harness .harness/contracts/templates/task/en/TASK.md L1-L23 "交接檔的範本：狀態、現在在做什麼、下一步、要讀的檔案、已決定的事，和未解決的問題。"

### 2. 清掉舊的工具結果

視窗的大部分，通常是舊的工具輸出。agent 為了找一個函式讀了一個檔案，整個檔案卻還留在那裡；一次測試跑出好幾頁輸出，要緊的只有失敗的那一行。

把這些丟掉，是最輕的一種壓縮，也是最安全的一種，因為決定和結論都留著，拿掉的只是原始材料。agent 如果又需要那個檔案，再讀一次就好。在 Anthropic 的 API 上，這是一個叫 context editing 的功能：一個叫 `clear_tool_uses` 的策略，會在輸入超過你設定的大小之後，移除最舊的工具結果。不過這個功能還在 beta，清除也不是沒有代價，因為它會讓被快取的開頭失效（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）。你自己的工具有沒有做類似的事、什麼時候做，要去查，不要假設。至於 Copilot 現在怎麼做，我沒有測過（見[這幾招在哪裡會出問題](#costs-and-traps)）。

你也可以手動得到同樣的效果。一次很長的閱讀做完後，請 agent 只寫下它發現了什麼，然後換一個新的對話繼續。新的對話有這份發現，卻沒有那些閱讀。

### 3. 把大量閱讀交給子 agent

如果下一步要讀很多東西，就別在主對話裡讀，交給一個**子 agent**。它是第二個 agent，從空的視窗開始，最後只交回一份簡短的報告。讀過的內容都留在它的視窗裡，你的主對話拿到的是結論。這就是[慎用子 agent](2-3-subagents.html)裡說的「並行閱讀」，兩個限制也一樣：只有一份簡短的報告就夠的時候才行得通，而且總共花得更多。

有些平台把這件事做成了一個設定。在 VS Code 裡，skill 可以在檔頭寫 `context: fork`，它就會在自己的子 agent 裡執行，而不是在你的對話裡（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)；文件標明是實驗性的）。讀得多、回報得少的 skill，正適合這樣做。不過我沒試過，所以不知道它的用量怎麼算，hook 又怎麼看到它。

### 4. 開一個新的對話

有時候，對的做法是停下來。出現下面這些跡象，就該停了：

- agent 重複你已經定好的事。
- 它推翻一小時前的一個修正。
- 你發現自己在重新解釋。
- 任務變了（新的任務就是新的對話）。

新的對話從空的視窗加上規則開始。只給它繼續所需要的東西就好，也就是讓它去讀筆記檔。依我的經驗（這一點我沒有量過），它常常比舊的對話在結尾時做得更好，因為它讀的是一張乾淨的紙。

重新開始，難免讓人覺得進度丟了，所以值得算一算到底丟了什麼。進度其實在檔案裡、在程式碼裡，對話裡留著的，只是對進度的記憶，而這份記憶早就磨損了。

對於我拆成幾步的長工作，我不會等對話變差，而是在事先排好的時間點重新開始。例如學習一個大的程式碼庫是分批做的，每兩三批我就開一個新的對話。狀態在任務裡，不在對話裡，所以在交界處什麼都不會丟。

### 交接什麼

既然要開新的對話，接下來的問題就是給它什麼。它需要一小組固定的東西：

1. 需求，幾行就好。
2. 決定了什麼，沒決定什麼。
3. 做完了什麼，和下一步。
4. 檔案在哪裡。

這四樣如果半頁寫不下，那才是真正的發現：這件工作還不夠清楚，沒法交給任何人，包括明天的你自己。

### 用一小時測一測你自己的設定

那麼，怎麼知道你的對話是不是已經不如你的檔案了？有一個便宜的測試，不用額外設定，一個人一小時就能做完。挑一條你在長對話早期給的、有兩三個部分的規則。工作一小時之後，請 agent 不回頭看，把它說出來。然後開一個新的對話，只給它你的筆記檔，問同樣的問題。每個答案按它答對了幾個部分打分。如果第二個更準，就表示你的對話還不如你的檔案。

順便也檢查一下你的指令放在哪裡。只在對話裡給的規則，對話一被壓縮就丟了；放在平台會再讀的檔案裡的規則，則不會。Claude Code 的文件談到它的專案指令檔時，說的正是這一點。所以，要讓一條規則留下來，就把它放進檔案。

## 這幾招在哪裡會出問題 {#costs-and-traps}

用這幾招之前，先想想對話為什麼會變長。如果是因為任務太大，該做的是把任務拆小。筆記做得再好，也只是掩蓋了壞習慣。

就算任務大小合適，筆記本身也可能是錯的。agent 在筆記裡寫了「測試通過」，實際卻沒有通過，下一個對話就會從一個錯誤的事實開始。筆記是 agent 的報告，要緊的那些要檢查。[agent 該記住什麼](3-5-memory.html)用較長的篇幅談這個問題。

寫對了的筆記也有自己的代價：它佔位子。一份一直長大、又沒人修剪的筆記檔，最後會變成填滿視窗的那個東西，所以要保持簡短，把做完的剪掉。另外，筆記檔裡可能有你不想分享的東西，放進共用的倉庫之前要想一想。

筆記寫得再好，新的對話也還是會失去舊對話的那份手感。舊的對話知道你怎麼說話，也知道你說「照平常的做法」是什麼意思。如果這很重要，就把它寫下來，因為這很可能就是一條規則。

最後是我沒測過的部分。我沒有量過我的平台怎麼壓縮：留下什麼、丟掉什麼，以及它會不會自己清掉舊的工具結果。在你為自己的工具查清楚之前，就把壓縮當成有損的。

## 做模型的人也這麼看嗎？ {#industry}
{status: industry}

Anthropic 的工程團隊描述過這個問題，也給過同樣的補救。他們用上下文腐化這個詞，意思是視窗越滿，「模型準確回想那段上下文中資訊的能力就越低」。他們談到壓縮，也就是「拿一段接近上下文視窗上限的對話，把它的內容摘要出來」，把清除工具結果稱為「最安全、最輕的壓縮方式之一」，也描述了做筆記，即「agent 定期把筆記寫到上下文視窗之外、持久保存的記憶裡」。（[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）

Claude Code 的文件補充了一個實用的細節，前面檢查指令放在哪裡，根據的就是它：根目錄的專案指令檔在壓縮後會從磁碟重新讀取，而只在對話裡給的指令就沒了。（[How Claude remembers your project](https://code.claude.com/docs/en/memory)）

對於需要很多個會話的長任務，Anthropic 描述了一份進度檔加上 git 歷史，每個新的會話先讀它們。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）而在 API 上，清除工具結果以 context editing 的形式提供，還在 beta。（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）

這些說法彼此一致，也和這一章一致。對話多長才算太長，沒有一家給出規則，我也不給，還是看上面那些跡象來判斷。

## 哪些可以刪掉，哪些要留下 {#when-to-delete-it}
{status: industry}

上面這幾招裡，有一部分本來就是平台的工作，平台也會做得更好：清掉舊的工具結果、壓縮，以及把關鍵事實帶過去。等你的工具把這些做好了，而且你查過它留下了什麼，就不用再手動做。

不過核心不變：工作如果要緊，它的狀態就屬於一個你能讀的檔案，而不屬於對話。更大的視窗和更好的壓縮，能讓對話撐得更久，但它們不會讓摘要和原文一樣好，也不會讓新的對話擁有你最後那兩小時。如果有平台能證明，它壓縮過的對話不會丟掉我在乎的東西，而且是在我自己的任務上量的，我會再看一次。
