讀這一章，請先在長對話裡用過寫程式的 AI agent，並讀過[上下文是一份預算](3-1-context-budget.html)（視窗有大小上限，裡面所有東西都在搶位子）。

## 一句話 {#in-one-sentence}

長對話會變差。別指望模型記得：把要緊的寫進檔案、清掉舊的工具結果，或開一個新的對話。

## 給主管 {#for-leaders}

- **要做的決定**：要求凡是要緊的東西都放在檔案裡，不能只在對話裡；並且約好什麼時候開新的對話。
- **風險**：長對話會變差，而平台對對話做的摘要會丟細節，例如你原話的措辭和做某個選擇的理由。在我自己的設定裡，品質掉得多快我沒量過，所以不給比率。
- **做對的成本**：每件工作一個簡短的筆記檔，每做完一步就更新。如果交接寫不滿半頁，說明這件工作還不夠清楚。
- **可以問團隊**：「如果這個對話現在消失了，我們會丟掉什麼？」

## 問題 {#problem}

你和 agent 已經工作了兩小時。一開始它很敏銳。現在它問起你一開始就定好的事，重複一個已經修掉的錯誤，或是改錯檔案。什麼都沒壞。只是對話變長了。

先說三個詞。前兩個在[上下文是一份預算](3-1-context-budget.html)裡定義過，這裡簡單講一下。

- **上下文視窗**是模型一次能看到的文字。它有大小上限。
- **工具結果**是 agent 使用工具後回來的東西。它們通常是視窗裡最大的項目。
- **壓縮**（compaction）是視窗快滿時平台做的事。它請模型把到目前為止的對話摘要一遍，然後從摘要繼續。

在我自己的設定裡，品質掉得多快我沒量過，所以我不會給你一個數字。問題的形狀已經清楚到可以行動，做模型的人也用同樣的方式描述它（見[業界怎麼說](#industry)）。

### 為什麼長對話會變差

用一張圖最容易看懂：同一個對話的三個時刻。

::: figure 3-2-context-rot

有四件事同時發生。

1. **有用的部分不增長，其餘的一直長**。任務現在需要的東西（需求、你給的規則、正在編輯的檔案）大小差不多不變。其他的都堆在它周圍：一小時前讀的檔案、一份很長、現在已經無關的測試輸出、三次錯誤的嘗試。
2. **模型每次都把全部讀一遍**。它沒有檔案櫃。每一輪，整個視窗都會被重讀。舊的文字越多，那一行要緊的就越要和它們競爭。（快取可以讓重讀在花費上便宜一點，見[選模型：算的是每次成功的成本](1-1-models-and-cost.html)，但不會讓視窗不那麼擠。）這個現象的名字叫**上下文腐化**：視窗越滿，模型對裡面內容的回想越不可靠。
3. **早期的東西離用到它的地方很遠**。第一則訊息裡的規則，現在落在幾千行之後。它還在，但離適用它的那一步很遠。這一點是我自己對所見的解讀，我沒有來源。
4. **壓縮會丟細節**。摘要留下的是寫摘要的那方認為重要的東西。你原話的措辭、做某個選擇的理由、那一條古怪的限制，是摘要最先丟掉的，而你無從知道它丟了哪些。

這些都不是某一個產品的 bug。它來自視窗的運作方式，所以適用於每一個 agent。

## 原理 {#how-it-works}

答案不是「更大的視窗」，也不是「更聰明的摘要」。是不再把對話當成要緊東西存放的地方。有四個動作。第一個是要一直保持的習慣。另外三個，隨著對話變長再用，由輕到重。

::: figure 3-2-four-moves

### 1. 把要緊的寫進檔案

問自己：如果這個對話現在消失了，我會丟掉什麼？不管答案是什麼，它都不該只存在於對話裡。

- **決定了什麼**，和為什麼。
- **做完了什麼、接下來是什麼**。
- **東西在哪裡**（哪些檔案、哪些指令）。

這些放在 agent 能再讀的檔案裡：任務資料夾裡一份簡短的筆記檔，或是它的待辦清單（兩者都在[管任務，不管對話](5-1-tasks.html)裡說明）。檔案不會被壓縮，新的對話一秒鐘就能讀完。再讀的時候，它的文字會落在視窗的末端，靠近用到它的地方。

在我的設定裡，每件工作都有一個資料夾，裡面有一份**交接檔**：做到哪了、下一步、已經決定的事。新的對話先讀這個檔案，然後接著做。因為這樣，丟掉一個對話只花我幾分鐘，不會丟掉工作。

**怎麼寫筆記**。要短。寫現在是什麼樣，不寫是怎麼走到這一步的。把下一步放在最上面。一頁比十頁好，因為新的對話要讀它，它也佔位子。

**讓 agent 去做**。請它每做完一步就更新筆記，不要等到最後。最後是你累了、對話最長的時候。一句話就能說完：「每做完一步，就更新筆記檔：已決定的事、已完成的事、下一步。」

Anthropic 為長時間運行的 agent 描述了同樣的習慣：一份進度檔加上 git 歷史，新的會話一開始，agent 先讀這些（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。下面是我的設定裡交接檔的範本：

::: code harness .harness/contracts/templates/task/en/TASK.md L1-L23 "交接檔的範本：狀態、現在在做什麼、下一步、要讀的檔案、已決定的事，和未解決的問題。"

### 2. 清掉舊的工具結果

視窗的大部分通常是舊的工具輸出。agent 為了找一個函式讀了一個檔案；整個檔案還留在那裡。一次測試跑出幾頁輸出；要緊的只有失敗的那一行。

丟掉這些，是最輕的壓縮，也是最安全的：決定和結論留著，只有原始材料走掉。如果 agent 又需要那個檔案，它可以再讀一次。在 Anthropic 的 API 上，這是一個叫 context editing 的功能：一個叫 `clear_tool_uses` 的策略，會在輸入超過你設定的大小之後，移除最舊的工具結果。它還在 beta，而清除會讓被快取的開頭失效，所以有代價（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）。你的工具有沒有做類似的事、什麼時候做，要去查，不要假設。我沒有測過 Copilot 今天怎麼做（見[代價和陷阱](#costs-and-traps)）。

你也可以手動得到同樣的效果。一次很長的閱讀做完後，請 agent 只寫下它發現了什麼，然後在新的對話裡繼續，新的對話有這個發現，但沒有那些閱讀。

### 3. 把大量閱讀交給子 agent

如果下一步要讀很多東西，別在主對話裡讀。**子 agent** 是第二個 agent，它從空的視窗開始，只交回一份簡短的報告。閱讀留在它的視窗裡，你的主對話拿到結論。這就是[慎用子 agent](2-3-subagents.html)裡的「並行閱讀」，限制也一樣：只有一份簡短的報告就夠的時候才行得通，而且總共花得更多。

### 4. 開一個新的對話

有時候對的做法是停下來。該停的跡象：

- agent 重複你已經定好的事。
- 它推翻一小時前的一個修正。
- 你發現自己在重新解釋。
- 任務變了（新的任務就是新的對話）。

新的對話從空的視窗和規則開始。只給它繼續所需要的：指向筆記檔就行。依我的經驗，它常常比舊的對話在結尾時做得更好，因為它讀的是一張乾淨的紙。我沒有量過這一點。

比較一下成本。重新開始感覺像丟掉進度。但進度在檔案裡和程式碼裡；對話只是記著這些進度，而那份記憶已經磨損了。

**有計劃地重新開始**。對於我拆成幾步的長工作，我不等對話變差。例如學習一個大的程式碼庫，是分批做的，每兩三批我就開一個新的對話。狀態在任務裡，不在對話裡，所以在交界處什麼都不會丟。

### 交接什麼

換對話時，新的對話需要一小組固定的東西：

1. 需求，幾行就好。
2. 決定了什麼，沒決定什麼。
3. 做完了什麼，和下一步。
4. 檔案在哪裡。

如果這四樣你寫不滿半頁，這才是真正的發現：這件工作還不夠清楚，沒法交給任何人，包括明天的你自己。

### 測一測你自己的設定

一個便宜的測試，不用額外設定，一個人一小時就能做。挑一條你在長對話早期給的規則，有兩三個部分的。工作一小時後，請 agent 不回頭看，把它說出來。然後開一個新的對話，只給它你的筆記檔，問同樣的問題。每個答案按它答對了幾個部分打分。如果第二個更準，你的對話就比你的檔案做得差。

也檢查一下你的指令放在哪裡。只在對話裡給的規則，對話被壓縮時就丟了；放在平台會再讀的檔案裡的規則，不會。Claude Code 的文件對它的專案指令檔說的就是這個。要讓一條規則留下來，就把它放進檔案。

## 代價和陷阱 {#costs-and-traps}

**不要掩蓋壞習慣**。如果對話變長是因為任務太大，補救是更小的任務，不是更好的筆記。

**筆記可能是錯的**。如果 agent 在筆記裡寫「測試通過」而實際沒有，下一個對話就從一個錯誤的事實開始。筆記是 agent 的報告；要緊的，要檢查。[agent 該記住什麼](3-5-memory.html)用較長的篇幅談這個問題。

**筆記也佔位子**。一個不修剪、一直長大的筆記檔，會變成填滿視窗的東西。保持簡短，把做完的剪掉。而且筆記檔裡可能有你不想分享的東西，放進共用的倉庫之前要想一想。

**新的對話會失去手感**。舊的對話知道你怎麼說話，也知道你說「照平常的做法」是什麼意思。如果這很重要，就寫下來；這很可能就是一條規則。

**我沒測的**。我沒有量過我的平台怎麼壓縮：留下什麼、丟掉什麼，以及它會不會自己清掉舊的工具結果。在你為自己的工具查清楚之前，把壓縮當成有損的。

## 業界怎麼說 {#industry}
{status: industry}

Anthropic 的工程團隊描述了這個問題和同樣的補救。他們用上下文腐化這個詞：視窗越滿，「模型準確回想那段上下文中資訊的能力就越低」。他們談到壓縮，也就是「把一段接近上下文視窗上限的對話，把內容摘要」，把清除工具結果稱為「最安全、最輕的壓縮方式之一」，也描述了做筆記，即「agent 定期把筆記寫到上下文視窗之外、持久保存的記憶裡」。（[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）

Claude Code 的文件補充了一個實用的細節：根目錄的專案指令檔在壓縮後會從磁碟重新讀取，而只在對話裡給的指令就沒了。（[How Claude remembers your project](https://code.claude.com/docs/en/memory)）

對於需要很多個會話的長任務，Anthropic 描述了一份進度檔加上 git 歷史，每個新的會話先讀它們。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）在 API 上，清除工具結果以 context editing 的形式提供，還在 beta。（[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）

它們彼此一致，也和這一章一致。沒有一家給出對話多長才算太長的規則，我也不給；請看上面的跡象來判斷。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

其中一部分是平台的工作，平台會做得更好：清掉舊的工具結果、壓縮，以及把關鍵事實帶過去。你的工具把這些做得好，而且你查過它留下了什麼，就不用再手動做。

核心不變：工作如果要緊，它的狀態就屬於一個你能讀的檔案，不屬於對話。更大的視窗和更好的壓縮，讓對話撐得更久。它們不會讓摘要和原文一樣好，也不會讓新的對話擁有你最後那兩小時。如果有平台能證明，它壓縮過的對話不會丟掉我在乎的東西，而且是在我自己的任務上量的，我會再看一次。

## 在你自己的環境試試 {#try-it}

不用裝 harness。在你自己的倉庫裡打開 agent，貼上：

::: prompt
想像這個對話丟了，必須由一個新的 agent 接手。根據你在這個倉庫裡看得到的（最近的 commit、未提交的改動、任何筆記或任務檔、指令檔），寫出那個 agent 需要的交接：幾行的需求、已決定的事、已完成的事和下一步，以及檔案在哪裡。然後列出你從倉庫裡看不出來的部分，作為需要人來補的缺口。只印出來，不要改任何檔案。
