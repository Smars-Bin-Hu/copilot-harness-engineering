读这一章，只需要你用过写代码的 AI agent，比如 Copilot 的 agent 模式。

## 一句话 {#in-one-sentence}

agent 是一个循环：问模型，运行它要的工具，把结果喂回去。你在每一轮的几个点上掌舵。

## 写给管理者 {#for-leaders}

- **要拍板的事**：agent 出了问题，先问该改四个地方里的哪一个（它读什么、有哪些工具、调用前的检查、调用后的检查），再去考虑换更大的模型或写更长的 prompt。
- **风险**：循环本身几乎不会坏，可只写在 prompt 里的规则不过是请求，模型不一定照做。
- **做对的代价**：主要是配置的时间。最便宜的杠杆是 agent 读什么，只要写几行规则。
- **可以问团队**：“上一次的坏结果，修的办法是更好的上下文、更紧的工具清单，还是模型之外的一道检查？”

## agent 出了错，到底错在哪？ {#problem}

agent 做错事的时候，人很自然会觉得，是背后有个头脑做了个糟糕的选择。麻烦在于，这幅图景会把人引向错误的修法：把 prompt 写得更长，用大写字母加上一句“小心”，或者换一个更大的模型。这些有时候管用，但往往不管用，因为问题本来就不出在思考上。

那么，不出在思考上，又出在哪？答案在这台机器里。其实它又小又朴素，上面只有几个地方可以伸手进去。这一部分后面的每一章，和再往后的大多数章一样，都是在其中某一个地方下功夫。

这台机器的起点是**模型**，也就是 AI 本身。它读文本、写文本，别的什么都不做。可 agent 显然不只会写字，它还会读文件、搜索、改文件、运行命令。这里的每一样，都叫一个**工具**，也就是 agent 在你的项目里能做的一件事。把两者连起来的是**工具调用**：模型要用某个工具时提出的请求，写成文本，比如“读这个文件”。一个只会写字的模型，最后怎么就改了你的文件？答案就在循环里。

## 这台机器是什么，你又能从哪里伸手进去 {#how-it-works}

### 问、运行、喂回去

模型碰不到你的文件，因为它能做的只有写文本。所以 agent 得靠模型外面的程序替它动手。模型先写出一个工具调用，模型外面的这个程序（也就是不是 AI 的那部分）读到这段文本，就真的去运行这个工具，再把结果当作更多的文本，贴回模型面前。模型读完结果，又写出下一个工具调用。就这样一圈一圈地转，直到模型写出一个不带工具调用的回答，这就是它认为自己做完了的信号。

我把绕这个循环走一圈，叫作一**轮**。不是每个人都这么用这个词。有些人用它指从你发消息到最终回答的整个来回。再说，模型在一圈里也可以同时要求用好几个工具。所以在这里，一轮就是一次“问、运行、喂回去”。

::: figure 2-1-loop

这幅图引出了两个事实。

第一个事实是，每个动作都是一次工具调用。模型没有别的办法做任何事，所以有一扇门，每个动作都要从这里经过。谁站在这扇门口，谁就能看到并拦住 agent 做的一切。**hook** 就站在那里：它是你的一个小程序，平台在每次工具调用之前和之后、在固定的点上运行它。（对内置工具和子 agent，我见过每次调用都经过 hook 点，不过 MCP 工具我没有测过。细节见下一章[Hook：每次调用都会经过的执行点](2-2-hooks.html)。）

第二个事实是，模型只看得到文本。你的屏幕、你的磁盘，它都看不到，它看到的只有上下文里的内容：规则、你说的话、之前工具调用的结果，还有它自己之前的回答。而上下文还有大小上限，[上下文是一份预算](3-1-context-budget.html)讲的就是这件事。

### 它什么时候停？

通常的停止就是上面说的那种：模型不再要求工具，直接作答。但停下来的方式不止这一种。你可以按停止，平台可能到了某个上限，也可能有什么东西拒绝了这次停止。

最后这一种很有用。agent 要停的时候，可以运行一个 hook，去看任务的待办清单（它还没做完的步骤），然后说“还没完，第 4 步还没做”，循环就会接着走下去。让 agent 不用你守着、把一长串清单做完，靠的就是这个办法，[慎用子 agent](2-3-subagents.html)讲了这种情况和它的停止规则。从这里已经能看出一点端倪：循环上有一些地方，你自己的代码可以插进去。

### 你能在哪里插手

再看一遍这个循环。模型怎么思考，你改变不了；你能改的，是它周围的四样东西。

1. **它读什么**。放进它上下文的规则和指令，以及指给它看的文件，是用得最多的杠杆，也是最便宜的。[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)讲的是这个。
2. **有哪些工具**。没有改文件工具的 agent，就改不了文件。工具的描述和报错信息，也是模型拿到的关于这个工具的唯一说明书（[Tool calling，以及怎么给 agent 设计工具](1-2-tool-calling.html)）。想给一个角色一份更短的工具清单，就用自定义 agent（[自定义 agent：固定模型和工具的角色](2-4-custom-agents.html)）。
3. **调用前的 hook**。这里的代码在调用运行之前就能看到它，并且能拒绝它。平台保证每次调用都经过这个点，所以这里的规则是会运行的代码，不是请求。不过，用代码写成的规则不只 hook 一种。一份工具清单，或者一条让 agent 自查用的命令，也算，只是各自覆盖的范围更窄（[提示里的规则只是请求](4-1-requests-and-rules.html)）。权限设置和沙箱是另一类杠杆。它们不读调用本身，而是限制任何命令能做什么，所以我没把它们算进这四样里。
4. **调用后的 hook**。这里的代码能看到结果、留下记录，还能给模型加一条备注。不过，已经发生的事它撤销不了。

有个简便的记法：这四样里，两样决定模型知道什么，两样决定它被允许做什么。光靠写下来的话，你改变的只是它知道什么。

### 为什么大多数错误不出在循环里

“知道什么”和“被允许做什么”这条分界，也是我看 agent 犯错的角度。循环本身几乎不会坏，错误要么出在上下文里有什么，要么出在允许它做什么。下面这张清单是我在自己的使用中攒下来的，记的是我见过的情况，算不上统计数据。

| 你看到的 | 通常的原因 |
| --- | --- |
| 它改了不该改的 | 它推理的是怎么把活干完，不是被不被允许。 |
| 它忘了前面的某件事 | 上下文被压缩了，或者对话太长了。 |
| 它检查了自己的工作，说没问题 | 同一个模型，同样的推理，有同样的盲区。 |
| 它对一个被拒绝的操作不停重试 | 它想把任务做完。 |
| 它说“做完了”，其实没有 | 按我的经验，模型倾向于汇报成功。 |

细看这几条，很少是因为模型不够聪明。第一条和最后一条，需要模型之外的一道检查。剩下的，第二条需要更好的上下文（[长对话会变差](3-2-long-sessions.html)），第三条需要另一个视角（[慎用子 agent](2-3-subagents.html)）。只有第四条，接近模型本身的习惯。这下，开头的问题有了答案：要修的，通常是这四个地方中的某一个，而不是模型的思考。

### 自己看看这个循环

想亲眼看看循环怎么转，你不用安装任何东西。在 agent 的对话里问一句：“读一下 README，告诉我这个项目是做什么的。”然后盯着对话看。回答出来之前，你会看到一行类似“Read README.md”的字，这一行就是一次工具调用，只是展示给你看了。接着再问一个需要读三个文件的问题，数数有几行。每一行都是循环的一轮，而每一个结果，现在都留在了上下文里。

## 循环要花什么，又容易被怎么误读 {#costs-and-traps}

循环的开销，正是从“每个结果都留在上下文里”这一点开始的。每绕一圈，模型都要把整个上下文重读一遍，而里面又多了一个结果，所以一个三十轮的任务，就是把一段越来越长的文本读三十遍。也因此，agent 读什么比模型多聪明更要紧，只盯着[模型每个 token 的价格](1-1-models-and-cost.html)看也是不对的。

不过，重读并不总是按全价收费。提供方会缓存重复的开头，在 Anthropic 的 API 上，读缓存的价格约是基础输入价的十分之一（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。缓存省下的是钱，省不下的是另一笔：模型还是得把注意力分到那一大段文本上。

而在这一大段文本里，工具结果是最大的一块，也是最少有人盯着的一块。prompt 是你写的，里面有什么你心里有数。可 agent 读的文件、一条命令打印出来的日志，你可能从来没见过。它们照样在上下文里，模型也可能照着它们去行动。

也不是每件事都该交给 agent，因为让模型自己决定下一步是有代价的。这样的循环比一串固定的模型调用、或者单次调用更贵，也更难预测。Anthropic 的建议是找最简单的解决办法，只在需要时才增加复杂度（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)）。如果一件事的步骤从来不变，一个在固定位置调用模型的脚本，可能比 agent 更适合你。

还有一个坑和开销无关。人很容易把循环读成一份计划，可它不是。模型不会先规划好整条路，再照着走下去，而是每一轮根据眼前看到的东西做决定。所以它走上错路，通常是前面某一轮的结果把它带过去的。

## 什么时候可以删掉我的 hook，什么会留下 {#when-to-delete-it}
{status: industry}

这一章讲的这些，会不会过时？只要 agent 还是靠调用工具来工作，关于循环的道理就不会退役，但实际操作的那部分也许会。我今天在四个地方掌舵，是因为平台给我的就是这些。如果平台开始提供原生的办法，来强制执行规则、预算或停止条件，我会改用它，而不再用自己的 hook。

## 在你自己的环境里试试 {#try-it}

::: prompt
读这个项目的指令文件和设置。你找到的每条规则或限制，告诉我它在四个地方里的哪一个起作用：agent 读什么、有哪些工具、工具调用前的检查、工具调用后的检查。把只是写下来的请求、没有模型之外的东西来强制执行的规则，每一条都标出来。列出五条一旦被破坏影响最大的规则。不要修改任何文件。
:::
