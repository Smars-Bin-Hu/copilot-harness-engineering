讀這一章，只需要你用過寫程式的 AI agent，例如 Copilot 的 agent 模式。

## 一句話 {#in-one-sentence}

agent 是一個迴圈：問模型，執行它要的工具，把結果餵回去。你可以在每一輪的幾個點上掌舵。

## 給主管 {#for-leaders}

- **要做的決定**：agent 出錯時，先問該修四個地方的哪一個（它讀什麼、有哪些工具、呼叫前的檢查、呼叫後的檢查），再去要更大的模型或更長的 prompt。
- **風險**：迴圈本身幾乎不會壞。依我的看法，錯誤不是出在上下文裡有什麼，就是出在允許 agent 做什麼，而寫在 prompt 裡的規則只是請求。每一種發生得多頻繁，我沒有計數。
- **做對的成本**：主要是設定的時間。最便宜的槓桿是 agent 讀什麼，只要寫幾行規則。
- **可以問團隊**：「上一次的壞結果，修法是更好的上下文、更緊的工具清單，還是模型外面的一道檢查？」

## agent 出錯時，到底錯在哪裡？ {#problem}

agent 做錯事的時候，人很自然會覺得，是背後有個頭腦做了糟糕的選擇。問題是，這個想像會把人引到錯誤的修法上：把 prompt 寫得更長、用大寫字母加上「小心點」，或者換成更大的模型。這些有時有用，但常常沒用，因為問題本來就不在思考裡。

那麼，不在思考裡，又在哪裡？要回答這個問題，得先知道這台機器到底是什麼。其實它很小，也很普通。看清楚它之後，你也就看得到有哪幾個地方能伸手進去，所以我們先把它畫出來，再把這幾個地方標上。這一部分後面的每一章，和再往後的大部分章節一樣，都在處理其中一個地方。

這台機器的起點是**模型**，也就是 AI 本身。它讀文字、寫文字，除此之外什麼都不做。可是 agent 顯然不只會寫字，它還會讀檔案、搜尋、改檔案、執行指令。這裡的每一樣都叫一個**工具**，也就是 agent 在你的專案裡能做的一件事。把兩者接起來的是**工具呼叫**：模型想用某個工具時提出的要求，寫成文字，例如「讀這個檔案」。一個只會寫字的模型，最後怎麼會改到你的檔案？答案就在迴圈裡。

## 這台機器是什麼，你又能從哪裡伸手進去 {#how-it-works}

### 問、執行、餵回去

模型碰不到你的檔案，因為它能做的只有寫文字。所以 agent 得靠模型外面的程式替它動手。模型先寫出一個工具呼叫，模型周圍的這個程式（也就是不是 AI 的那一部分）讀到這段文字，就真的去執行這個工具，再把結果當成更多文字，貼回模型面前。模型讀完結果，又寫出下一個工具呼叫。就這樣一圈一圈地轉，直到模型寫出一個不含工具呼叫的回答，這就是它認為自己做完了的訊號。

我把繞這個迴圈一圈叫做**一輪**。不是每個人都這樣用這個詞。有些人用它指從你的訊息到最後回答的整段來回。再說，模型在一圈裡也可以同時要求好幾個工具。所以在這裡，一輪就是問、執行、餵回去這一個回合。

::: figure 2-1-loop

這張圖引出兩個事實，之後都會用到。

第一個事實是，每個動作都是工具呼叫。模型沒有別的辦法做任何事，所以有一扇每個動作都會經過的門。誰站在這扇門口，誰就看得到、也擋得住 agent 做的一切。**hook** 就站在那裡：它是你的一個小程式，平台在每次工具呼叫之前和之後的固定位置執行它。（內建工具和子 agent，我看過每次呼叫都經過 hook 的位置，不過 MCP 工具我沒有測過。細節見下一章 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)。）

第二個事實是，模型只看得到文字。你的螢幕、你的磁碟，它都看不到，它看到的只有上下文裡的東西：規則、你說的話、之前工具呼叫的結果，還有它自己之前的回答。上下文就是它的整個世界。這個世界還有大小上限，[上下文是一份預算](3-1-context-budget.html) 講的就是這件事。

### 什麼時候停？

一般的停止就是上面說的那種：模型沒有要求工具，直接回答。但停下來的方式不只一種。你可以按停止，平台可能到了上限（Copilot 預設把輪數限制在多少，我沒有查過，所以這裡不給數字），也可能有東西拒絕了這次停止。

最後這種很有用。agent 要停下來的時候，可以執行一個 hook，去看任務的待辦清單（還沒做完的步驟），然後說「還沒，第 4 步還沒做完」，迴圈就會繼續下去。讓 agent 不靠你、把一長串清單做完，靠的就是這個辦法，[慎用子 agent](2-3-subagents.html) 講了這種情況和它的停止規則。從這裡已經能看出一點端倪：迴圈上有一些地方，你自己的程式碼可以插進去。

### 你能在哪裡插手

再看一次這個迴圈。模型怎麼思考，你改變不了；你能改變的，是它周圍的四樣東西。

1. **它讀什麼**。放進它上下文的規則和指令，以及指給它看的檔案，是用得最多、也最便宜的槓桿。[指令與 skill：只載入需要的](3-3-instructions-and-skills.html) 講的就是這個。
2. **有哪些工具**。沒有改檔案工具的 agent，就改不了檔案。工具的描述和錯誤訊息，也是模型拿到的關於這個工具的唯一手冊（[Tool calling，和給 agent 設計工具](1-2-tool-calling.html)）。想給一個角色較短的工具清單，就用 custom agent（[Custom agent：固定模型和工具的角色](2-4-custom-agents.html)）。
3. **呼叫前的 hook**。這裡的程式碼在呼叫執行之前就看得到它，並且能拒絕它。平台保證每次呼叫都會經過這一點，所以這裡的規則是會執行的程式碼，不是請求。不過，用程式碼寫成的規則不只 hook 一種。工具清單，或 agent 用來檢查自己的指令，也算，只是各自涵蓋的範圍窄一些（[提示裡的規則只是請求](4-1-requests-and-rules.html)）。權限設定和沙箱是另一種槓桿，因為它們不讀呼叫，而是限制任何指令能做什麼。我沒有在 Copilot 上一項項測過，所以沒把它們算進這四樣。
4. **呼叫後的 hook**。這裡的程式碼看得到結果、可以留下紀錄，還能為模型加一則備註。不過，已經發生的事，它沒辦法撤銷。

有個簡單的記法：這四樣裡，兩樣決定模型知道什麼，兩樣決定它被允許做什麼。光靠寫下來的話，你改變的只是它知道什麼。

### 為什麼大部分錯誤不在迴圈裡

「知道什麼」和「被允許做什麼」這條分界，也是我看 agent 錯誤的角度。迴圈本身幾乎不會壞，錯誤不是出在上下文裡有什麼，就是出在允許它做什麼。下面這張清單，是我自己用下來慢慢整理的，記的是我看到的情況，算不上統計，因為每一種發生得多頻繁，我沒有計數。

| 你看到的 | 通常為什麼 |
| --- | --- |
| 它改了不該改的 | 它推理的是怎麼把事做完，不是被不被允許。prompt 裡的規則只是請求。 |
| 它忘了先前的某件事 | 上下文被壓縮了，或者對話太長。 |
| 它檢查了自己的工作，說沒問題 | 同一個模型、同樣的推理，有同樣的盲點。 |
| 它一直重試被拒絕的動作 | 它想把任務完成。 |
| 它說「做完了」，其實沒有 | 依我的經驗，模型傾向回報成功。 |

細看這幾條，很少是因為模型不夠聰明。第一條和最後一條，需要模型外面的一道檢查。剩下的，第二條需要更好的上下文（[長對話會變差](3-2-long-sessions.html)），第三條需要第二個視角（[慎用子 agent](2-3-subagents.html)）。只有第四條，接近模型自己的習慣。這樣一來，開頭的問題也有了答案：要修的，通常是這四個地方中的某一個，而不是模型的思考。

### 自己看看迴圈

想親眼看迴圈怎麼轉，你不用安裝任何東西。在 agent 的對話裡問一句：「讀 README，告訴我這個專案做什麼。」然後盯著對話看。回答出來之前，你會看到一行像「Read README.md」的字，那一行就是一次工具呼叫，只是顯示給你看了。接著再問一個需要讀三個檔案的問題，數一數有幾行。每一行是迴圈的一輪，而每個結果現在都留在上下文裡了。

## 迴圈要花什麼，又容易被怎麼誤讀 {#costs-and-traps}

迴圈的開銷，就是從「每個結果都留在上下文裡」這一點開始的。每繞一圈，模型都要把整個上下文重讀一遍，裡面又多了一個結果，所以三十輪的任務，就是把一份越來越長的文字讀三十次。這就是為什麼 agent 讀什麼，比模型有多聰明更重要，也是為什麼只看[每個 token 的單價](1-1-models-and-cost.html)，是看錯了數字。

不過這裡要補一句：重讀不一定按全價收費。供應商會把重複的開頭快取起來，在 Anthropic 的 API 上，讀快取的價格大約是基本輸入價的十分之一（[選模型：算的是每次成功的成本](1-1-models-and-cost.html) 有算式）。Copilot 怎麼計費，我沒有查過。快取省下的是錢，省不下的是另一筆：模型還是得把注意力分到那麼多文字上。

而在這麼多文字裡，工具結果是最大的一塊，也是最少人盯著的一塊。prompt 是你寫的，裡面有什麼你心裡有數。可是 agent 讀的檔案、指令印出來的紀錄，你可能從來沒看過。它們照樣在上下文裡，模型也可能照著它們去做。

也不是每件事都該交給 agent，因為讓模型自己決定下一步是有代價的。這樣的迴圈比一串固定的模型呼叫、或單次呼叫花得更多，也更難預測。有時候，這個代價並不值得付。Anthropic 的建議是找到最簡單的解法，只在需要時才加複雜度（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)）。如果一件工作的步驟從來不變，一個在固定位置呼叫模型的腳本，可能比 agent 更適合你。

還有一個陷阱和開銷無關。人很容易把迴圈讀成一份計劃，可它不是。模型不是先規劃好整條路，再照著走下去，而是每一輪根據眼前看到的東西做決定。所以它走錯路，通常是前面某一輪的結果把它帶去的。

## 什麼時候可以刪掉我的 hook，什麼會留下來 {#when-to-delete-it}
{status: industry}

這一章講的這些，會不會過時？只要 agent 還是靠呼叫工具運作，關於迴圈的道理就不會退役，但實務的部分可能會。今天我在四個地方掌舵，是因為平台給我的就是這些。如果平台開始提供原生的辦法，來執行規則、預算或停止條件，我會改用那個，不再用自己的 hook。到那時我丟掉的是 hook，不是這張圖。
