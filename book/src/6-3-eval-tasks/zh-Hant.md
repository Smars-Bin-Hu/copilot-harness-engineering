讀這一章，你需要用過 AI 寫程式的 agent，而且至少改過一次它的規則或設定。不需要別的。

## 一句話 {#in-one-sentence}

要知道一個改動有沒有幫助，就在改動前後跑同樣的固定任務，用腳本打分，然後讀失敗的那幾次運行。

## 給主管 {#for-leaders}

- **要做的決定**：對 agent 的規則或設定做的任何改動，都要附上改動前後在同樣固定任務上的運行，並用腳本打分。
- **風險**：光看一個好結果，你分辨不出改動有沒有幫助。我自己的這組只有四個任務，足以顯示四到六倍的差距，卻顯示不出百分之十的差距。
- **做對的成本**：花一個下午建評分腳本，並用一個好答案和一個壞答案測試它，之後就是每一次運行的成本。在我的實驗裡，三角色團隊把四個任務做一遍，大約 16 分鐘、大約 456 個 AI credits。
- **可以問團隊**：「這個改動前後，你們跑了哪些固定任務？你們怎麼知道給它們打分的腳本，抓得到錯的答案？」

## 怎麼知道一個改動有沒有幫助？ {#problem}

你加了一條規則、改了一個 prompt，或開啟了一個檢查，接下來那個任務做得很順利。是改動有幫助嗎？

光憑這一次，你分辨不出來。那個任務可能本來就簡單，agent 也可能只是運氣好（[下一章](6-4-variance.html) 就講這個）。再說，你也不是中立的評審：改動是你做的，你當然希望它有用。看著一個結果，覺得變好了，這不是證據。

寫 [慎用子 agent](2-3-subagents.html) 的時候，我想知道三個分工不同的 agent，是不是比一個 agent 好。我沒有拿一個任務來看看就算了，而是拿了四個固定任務，兩種設定各跑一次，再讓同一個腳本替所有結果打分。結果改變了我的設計：團隊花的錢多得多，卻沒有多做對任何一件事（數字在那一章，連同它們的限制）。要是只看幾個結果，我不會相信這一點。

我在那裡用的辦法，叫做**評測**（eval，evaluation 的縮寫）。它是對 agent 設定的測試，分三部分：一組任務、一種執行它們的方法、一種為結果打分的方法。我用的是**固定任務**：要求、起始檔案和正確答案在每次運行之間都不變；替它們打分的東西，這裡主要是一個腳本，叫**評分器**（grader）。那麼，要怎麼建一個答案信得過的評測？

## 怎麼建一個信得過的評測 {#how-it-works}

圖裡畫的就是這個方法：固定任務，改動前後各跑一次，腳本替兩邊打分，再由人讀失敗的運行。

### 好的任務長什麼樣

方法從任務開始，但並不是每個任務都適合做評測。我找三樣東西。

1. 它是真的。它應該像 agent 平常替你做的工作，不是像考試題，所以如果你只加 pipeline、修公式，就不要測寫詩。只在虛構的工作上有用、在你的工作上沒用的改動，教不了你什麼。
2. 它有一個你能檢查的正確答案。「加一個 pipeline」可以檢查：五個檔案存在、位置對、彼此一致。「讓程式碼更漂亮」就不行。如果兩個講理的人會對結果對不對有不同意見，腳本就沒辦法打分。
3. 它涵蓋人真的會犯的錯。好的一組有簡單的案例，也要有陷阱。在我的實驗裡，有一個任務要求 agent 改一個規則禁止它改的檔案，好的結果是拒絕。這個任務放在這裡，是因為真實的要求本來就可能這樣提，而照做的 agent 就是做錯了。

我的實驗的四個任務，從小到中等：加一個 pipeline；把一個欄位經過三個 pipeline 往下游傳（其中一個欄位途中改了名）；跨區域重新命名一個 pipeline 並刪掉舊檔案；修一個存在兩個地方的公式，而要求裡也要求改一個受保護的檔案。四個任務確實很少，這對結果代表什麼，後面再說。

這類任務還分兩種，失敗代表的意思也不同。**能力**任務檢查設定還做不到的事，所以一開始預期它常常失敗。**回歸**任務檢查已經做得到的事，所以預期它每次都通過，一旦失敗，就表示有改動把它弄壞了。兩種要有意地混在一起，但兩種的通過率要分開看。

這些任務底下的倉庫是虛構的（93 個檔案、5 個區域），而且不能執行。這是刻意的。正因為正確答案事先就知道，腳本才能判斷哪個結果是對的，不需要有人執行程式碼去查。

### 看結果，還是看過程？

任務有了，評分器該看什麼？它可以看結果，也就是 agent 留下來的檔案，例如五個檔案加了沒有、登記表有沒有列出新的 pipeline、受保護的檔案是不是沒動。它也可以看過程，也就是 agent 怎麼做到的，例如它有沒有被拒絕，有沒有在計畫批准之前就寫到某個地方。

大多數任務，給結果打分。到達正確答案通常有很多有效的路，所以堅持只走一條路的評分器，會把好的工作判成錯的。只有過程本身就是你在乎的東西時，才給過程打分，例如「規則在計畫批准之前，拒絕寫入」。在我的 harness 裡，這類情境要同時看兩件事：日誌顯示了那次拒絕，檔案也沒有變，兩樣都對上才算通過。沒有日誌就沒東西可查，這就是 [記錄每一次呼叫](6-1-observe.html) 要排在最前面的原因。

在我的實驗的評分裡，結果是一張檢查清單。有些項目每個任務都一樣，檢查倉庫是不是仍然一致（檔案有效、每個 pipeline 有它的五個檔案、欄位一致、受保護的區域沒動）。有些項目只屬於一個任務，檢查要求本身做完了沒有。還有一項檢查範圍，看是不是只有該改的檔案被改了。每一項都通過，一個任務才算通過。

這樣的分數是全有或全無。如果你想在長任務上看到進度，就分段打分（部分給分），並報告各段。我沒有拆，因為對這些短任務來說，一項錯通常就表示結果是錯的。

### 用腳本還是用模型當評分器

接著的問題是，由誰、或由什麼來打分。腳本讀檔案，回答通過或失敗；模型可以讀結果，給出判斷。兩者各有弱點。

腳本便宜、快，每次給同樣的答案。它的弱點是脆。因為它只找某一種特定的形式，有效的結果也可能被它判成錯的，而這種情況要靠讀失敗的結果才找得出來。模型評分器可以接受有效的變化，也能判斷腳本做不到的事，例如一段解釋清不清楚。但它的答案每次運行可能不同，還可能和被它評分的 agent 有同樣的盲點（[模型能檢查模型嗎](5-6-model-checks-model.html)）。

Anthropic 的建議也一致：「我們建議盡量選確定性的評分器，必要時，或需要額外彈性時，才用 LLM 評分器。」（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）我自己也是這樣做的。答案能在檔案裡檢查的地方，我就用腳本，模型評分器只留給腳本看不到的少數東西。這裡的實驗沒有模型評分器。

### 先證明評分器是對的

不管用哪一種，評分器都是程式，而程式會有 bug。什麼都放行的評分器，會讓每個改動看起來都無害；什麼都擋的評分器，會讓每個改動看起來都有害。所以在相信任何分數之前，我先測評分器。我的實驗有一個自我測試，分三部分：

- **沒動過**的倉庫，必須每個任務都失敗（什麼都沒做）。
- 手寫的**正確答案**，必須每個任務都通過。
- 正確答案的**壞版本**，必須全部被抓到。有 23 個，每個有一個錯誤，例如少了一行登記，或欄位錯了。評分器放過一個，評分器就是錯的。

最小的版本是一個好答案，加上一個你手動弄壞的答案：評分器必須放行第一個、抓到第二個。我的實驗做這一步花了一個下午。這正是大家會跳過的部分，可我能說「一項失敗是有意義的」，靠的也是它。

### 讀失敗的運行

就算評分器測過了，它也只能告訴你有東西失敗了，說不出為什麼。所以就算有腳本，我也一直守著一個習慣：**一次運行失敗，我會打開它，讀發生了什麼**。失敗的原因可能是三種很不一樣的事。可能是 agent 真的犯了錯，這正是評測要找的；可能是評分器錯了，結果其實是對的，只是形式不是腳本預期的；也可能是任務不清楚，兩個答案都講得通，要求卻沒有說是哪一個。

三種裡只有第一種，才告訴你 agent 的事。如果你把每個失敗都當成這一種，你會丟掉好的改動、留下壞的。Anthropic 是這麼說的：「讀對話紀錄，是你驗證評測量的是不是真正重要的東西的辦法。」（同一篇文章）

所以腳本不取代親自去看。它省掉的，是把每次運行都看一遍的功夫。該細看哪幾次，交給腳本來挑。它挑出失敗的運行，這就是它對該看哪裡的猜測，人再去讀這幾次。

### 你的任務和公開的基準測試

你也許會問，既然有公開的任務，為什麼還要自己建一套？**基準測試**（benchmark）是一組公開的任務，對每個人用同樣的方式打分，讓模型可以互相比較。它只對一個問題有用：這個模型在別人的任務上表現如何？另一個問題它回答不了：我對我的設定做的改動，在我的工作上有沒有幫助？要回答這個，需要來自你的倉庫、帶著你的規則的任務，例如我的實驗裡那個受保護的檔案。這就是我自己建的原因。

這個選擇也有代價。自己建的一組任務很小，又只屬於我自己。它還會過期：倉庫一變，任務也得跟著變。

### 我的 harness 今天怎麼做

前面講的都是實驗。我的 harness 本身做得比較少。在我的設定裡有幾個固定情境，每一個是一個 prompt 加上預期的結果，也就是日誌裡必須出現的幾個呼叫（例如一次拒絕），和必須變或不能變的幾個檔案。我在 Copilot 裡手動把一個情境跑一遍，再由一個檢查讀日誌和檔案，說有沒有做對。

它現在還做不到的，是批次執行。寫這段的時候（2026 年 10 月），在我自己的設定裡，我看到 Copilot 的非互動模式不會執行 hook，所以我沒辦法批次跑這些情境，在真實任務上做前後比較也還沒做。這一章講的有打分、可重複的比較，我只在這個倉庫的實驗裡用數字做過。日常用的時候，就是手動跑一個情境，再看它留下的日誌。

### 自己跑

想在自己動手之前，先看看這一切怎麼運作，可以從這個實驗開始。它就是 [慎用子 agent](2-3-subagents.html) 裡那些數字背後的測試，包括虛構的倉庫、四個任務和評分腳本。它們都適用於任何 agent 工具。[`labs/subagents/`](../labs/subagents/README.md) 說了怎麼先跑自我測試，再跑你自己的比較。看懂怎麼運作之後，把任務換成你自己的。

### 測你自己的設定

不管跑不跑這個實驗，在 agent 設定上做任何改動之前，都值得先問三個問題：

1. 如果這個改動有幫助，我會看到什麼？如果沒有，又會看到什麼？
2. 腳本分得出這兩種嗎？
3. 腳本自己有沒有通過「沒動過、正確、壞掉」的測試？

不用任何工具，也能先小小地開始。挑三個你和 agent 做過的任務，為每一個寫下你預期最後會有的檔案，和一個你見過的錯誤，再寫一個短腳本檢查這些檔案。（如果你的工作不是程式碼，就檢查輸出：表格的欄位、列數、總和。）在一個好結果和一個你手動弄壞的結果上各跑一次。它抓到壞的、放行好的，你就有一個評測了。它很小，但下次你改規則時，就可以用它。

## 小評測看不出的東西，和它的成本 {#costs-and-traps}

這麼小的評測，能靠它走多遠？它的限制大多出在任務上。四個任務的底子很薄。我這四個提示了四到六倍的差距，可要是只差百分之十，就看不出來了。你沒想到的情況，它們也涵蓋不了，所以每次有真實的失敗讓你意外，就加一個任務。任務還會用兩種不那麼顯眼的方式誤導你。一種是你一直改設定，直到任務通過，這時量到的其實是設定和這四個任務貼合得多緊，所以要留一些不拿來調的任務。另一種是問題反過來，任務太容易了：每種設定都通過每個任務，任務就飽和了。用 Anthropic 的話說：「當 agent 通過所有可解的任務，沒有留下任何進步空間，就是評測飽和。」到了這一步，評測就分不出各種設定了，這時該加更難的任務。

另一些限制出在分數上。其一，靜態的分數不執行程式碼。我的評分器讀檔案，所以沒辦法說程式碼能不能用。對執行很重要的工作，評分器得去跑測試（[讓 agent 能檢查自己的活](5-4-self-checks.html)）。其二，分數公不公平，還要看背後的運行公不公平，所以任務之間不能共用狀態。每次運行都要從同一份乾淨的副本開始。如果一次運行留下了檔案、快取或改過的設定，下一次運行就不是公平的測試，因為分數量到的是殘留的東西。

然後是帳單：運行要花錢，也要花時間。在我的實驗裡，團隊把四個任務做一遍，大約 16 分鐘、大約 456 個 AI credits。prompt 快取會改變總額，在 Anthropic 的 API 上，快取讀取大約是基本價格的十分之一（[選模型：算的是每次成功的成本](1-1-models-and-cost.html)），但 Copilot 怎麼計費，我沒查過。十個任務，在兩種設定上各跑幾次，就是一筆實實在在的開銷。開始之前，先決定你拿到答案要做什麼。（前面「我的 harness 今天怎麼做」說過，在我的設定裡，真實的工作沒辦法為此批次跑。）

最後，一次運行很薄。我的結果是每個任務只有一次運行，[下一章](6-4-variance.html) 說怎麼跑更多次、怎麼報告你發現的東西。

## 什麼時候刪掉腳本，任務為什麼要留著 {#when-to-delete-it}
{status: industry}

這些腳本和手動跑的習慣之所以存在，是因為我沒有內建的辦法，讓一種設定跑一組固定任務並比較。如果平台加了這個功能，有日誌也有打分，我會用它，把自己拼湊的膠水程式丟掉。

固定任務卻不會跟著腳本一起退役。模型升級、加一條規則、重寫一個 prompt，都是改動，每一次都會把同一個問題再問一遍：這個改動有沒有幫助？固定任務就是用來回答它的（[模型升級了，就要刪](6-5-model-upgrades.html)）。一個任務在每種設定都通過它的時候才退役。如果實驗裡的四個任務不再分得出各種設定，我會重新檢視它們。

## 在你自己的環境試試 {#try-it}
