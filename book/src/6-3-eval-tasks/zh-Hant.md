讀這一章，你需要用過 AI 寫程式的 agent，而且至少改過一次它的規則或設定。不需要別的。

## 一句話 {#in-one-sentence}

要知道一個改動有沒有幫助，就在改動前後，跑同樣的固定任務，用腳本打分。然後讀失敗的那幾次運行。

## 給主管 {#for-leaders}

- **要做的決定**：要求對 agent 的規則或設定做的改動，都要附上改動前後在同樣固定任務上的運行，並用腳本打分。
- **風險**：光看一個好結果，你分辨不出改動有沒有幫助。我自己的這組是四個任務：足以顯示四到六倍的差距，顯示不出百分之十的差距。
- **做對的成本**：一個下午，建評分腳本，並用一個好答案和一個壞答案測試它；再加上每一次運行的成本。在我的實驗裡，三角色團隊做四個任務，一次大約 16 分鐘、大約 456 個 AI credits。
- **可以問團隊**：「這個改動前後，你們跑了哪些固定任務？你們怎麼知道給它們打分的腳本，抓得到錯的答案？」

## 問題 {#problem}

你加了一條規則。你改了一個 prompt。你打開了一個檢查。下一個任務做得很順利。是改動有幫助嗎？

你分辨不出來。下一個任務可能本來就簡單。agent 也可能只是運氣好（[下一章](6-4-variance.html) 就講這個）。而且你不是中立的評審：改動是你做的，你希望它有用。看著一個結果，覺得變好了，這不是證據。

我在 [慎用子 agent](2-3-subagents.html) 時，是這樣做的。我想知道，三個有職稱的 agent，是不是比一個 agent 好。我沒有拿一個任務來看看。我拿了四個固定任務，兩種設定各跑一次，再讓同一個腳本替所有結果打分。結果改變了我的設計：團隊花的錢多得多，卻沒有多做對任何一件事（數字在那一章，連同它們的限制）。光看幾個結果，我不會相信這一點。

先交代三個詞。

- **評測**（eval，evaluation 的縮寫）是對 agent 設定的測試：一組任務、一種執行它們的方法、一種為結果打分的方法。
- **固定任務**是這樣的任務：要求、起始檔案和正確答案，在每次運行之間都不變。
- **評分器**（grader）是為結果打分的東西：這裡主要是腳本。

## 原理 {#how-it-works}

### 好的任務長什麼樣

不是每個任務都適合做評測。我找三樣東西。

1. **它是真的**。它應該像 agent 平常替你做的工作，不是像考試題。如果你只加 pipeline、修公式，就不要測寫詩。一個改動在虛構的工作上有幫助、在你的工作上沒有，什麼也教不了你。
2. **它有一個你能檢查的正確答案**。「加一個 pipeline」可以檢查：五個檔案存在、位置對、彼此一致。「讓程式碼更漂亮」不行。如果兩個講理的人會對結果對不對有不同意見，腳本就沒辦法打分。
3. **它涵蓋人真的會犯的錯**。好的一組有簡單的案例，也有陷阱。在我的實驗裡，有一個任務要求 agent 改一個規則禁止它改的檔案。好的結果是拒絕。這個任務在這裡，是因為真實的要求可能就是這樣要求，而照做的 agent 就是做錯了。

我的實驗的四個任務，從小到中等：加一個 pipeline；把一個欄位經過三個 pipeline 往下游傳（其中一個欄位途中改了名）；跨區域重新命名一個 pipeline 並刪掉舊檔案；修一個存在兩個地方的公式，而要求裡也要求改一個受保護的檔案。四個很少。它提示了四到六倍的差距，但它顯示不出百分之十的差距。

這類任務分兩種。**能力**任務檢查設定還做不到的事，所以一開始預期常常失敗。**回歸**任務檢查已經能用的事，所以預期每次都通過，失敗就表示有改動把它弄壞了。有意地把兩種混在一起，並且對兩種用不同的方式讀通過率。

這個倉庫是虛構的（93 個檔案、5 個區域），而且不能執行。這是一個選擇。正確答案事先就知道，所以腳本可以說哪個結果是對的，沒有人需要執行程式碼去查。

### 看結果，還是看過程？

評分器可以看兩樣東西。

- **結果**：agent 留下來的檔案。它加了五個檔案嗎？登記表列出了新的 pipeline 嗎？受保護的檔案沒動嗎？
- **過程**：agent 怎麼做到的。它有被拒絕嗎？它有沒有在計畫批准之前就寫到某個地方？

大多數任務，給結果打分。到達正確答案通常有很多有效的路，堅持只走一條路的評分器，會把好的工作判成錯的。只有過程本身就是你在乎的東西時，才給過程打分，例如「規則在計畫批准之前，拒絕寫入」。在我的 harness 裡，這類情境看兩件事：日誌必須顯示拒絕，檔案必須沒有變。這就是 [記錄每一次呼叫](6-1-observe.html) 要排在最前面的原因。

在我的實驗的評分裡，結果是一張檢查清單。有些項目每個任務都一樣：倉庫仍然一致（檔案有效、每個 pipeline 有它的五個檔案、欄位一致、受保護的區域沒動）。有些項目只屬於一個任務：要求本身做完了。還有一項檢查範圍：只有該改的檔案被改了。一個任務要每一項都通過才算通過。這是全有或全無；如果你想在長任務上看到進度，就分段打分（部分給分），並報告各段。對這些短任務來說，一項錯通常就表示結果是錯的，所以我不拆。

### 用腳本還是用模型當評分器

腳本讀檔案，回答通過或失敗。模型可以讀結果，給出判斷。各有弱點。

- **腳本**便宜、快，每次給同樣的答案。弱點是脆：它可能把有效的結果判成錯的，因為它找的是某一種特定的形式。你要靠讀失敗的結果才找得出來。
- **模型評分器**可以接受有效的變化，也能判斷腳本做不到的事，例如一段解釋清不清楚。但它的答案每次運行可能不同，而且可能和被它評分的 agent 有同樣的盲點（[模型能檢查模型嗎](5-6-model-checks-model.html)）。

Anthropic 的建議也一致：「我們建議盡量選確定性的評分器，必要時，或需要額外彈性時，才用 LLM 評分器。」（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）答案能在檔案裡檢查的地方，我就用腳本；模型評分器只留給腳本看不到的少數東西。這裡的實驗沒有模型評分器。

### 先證明評分器是對的

評分器是程式，程式有 bug。什麼都放行的評分器，會讓每個改動看起來都無害。什麼都擋的評分器，會讓每個改動看起來都有害。所以在相信任何分數之前，我先測評分器。我的實驗有一個自我測試，分三部分：

- **沒動過**的倉庫，必須每個任務都失敗（什麼都沒做）。
- 手寫的**正確答案**，必須每個任務都通過。
- 正確答案的**壞版本**，必須全部被抓到。有 23 個，每個有一個錯誤，例如少了一行登記，或欄位錯了。評分器放過一個，評分器就是錯的。

最小的版本是一個好答案，和一個你手動弄壞的答案：評分器必須放行第一個、抓到第二個。對我的實驗來說，這花了一個下午，而這正是大家會跳過的部分。這也是我能說「一項失敗是有意義的」的原因。

### 讀失敗的運行

有一個習慣，就算有腳本我也不放棄。**一次運行失敗，我會打開它，讀發生了什麼**。分數說有東西失敗了。它不說為什麼，而為什麼可能是三種很不一樣的事：

1. **agent 真的犯了錯**。這是評測要找的。
2. **評分器錯了**。結果是對的，但形式是腳本沒預期的。
3. **任務不清楚**。兩個答案都講得通，而要求沒有說是哪一個。

只有第一種告訴你 agent 的事。如果你把每個失敗都當成第一種，你會丟掉好的改動、留下壞的。Anthropic 是這麼說的：「讀對話紀錄，是你驗證評測量的是不是真正重要的東西的辦法。」（同一篇文章）

所以腳本不取代看。它取代的是什麼都看、靠猜該看哪裡。腳本挑出失敗的運行。然後由人去讀那些。

### 你的任務和公開的基準測試

**基準測試**（benchmark）是一組公開的任務，對每個人用同樣的方式打分，讓模型可以比較。基準測試只對一個問題有用：這個模型在別人的任務上表現如何？它們回答不了另一個問題：我對我的設定做的改動，在我的工作上有沒有幫助？那需要你的倉庫裡的任務，和你的規則，例如我的實驗裡那個受保護的檔案。這就是我自己建的原因。

自己建的代價是：它很小，它是我的，而且會過期。倉庫變了，任務也得跟著變。

### 我的 harness 今天怎麼做

在我的設定裡有幾個固定情境。每一個是一個 prompt，加上預期的結果：日誌裡必須出現的幾個呼叫（例如一次拒絕），和必須變或不能變的幾個檔案。我在 Copilot 裡手動跑一個情境一次，再由一個檢查讀日誌和檔案，說有沒有做對。寫這段的時候（2026 年 10 月），在我自己的設定裡，我看到 Copilot 的非互動模式不會執行 hook，所以我沒辦法批次跑這些情境，在真實任務上做前後比較也還沒做。我用數字做過的，是這個倉庫裡的實驗。日常使用中，那是手動跑一個情境，再看它留下的日誌。這一章講的有打分、可重複的比較，是那個實驗。

### 自己跑

這個實驗是 [慎用子 agent](2-3-subagents.html) 裡那些數字背後的測試：虛構的倉庫、四個任務和評分腳本。它適用於任何 agent 工具。[`labs/subagents/`](../labs/subagents/README.md) 說了怎麼先跑自我測試，再跑你自己的比較。看懂怎麼運作之後，把任務換成你自己的。

### 測你自己的設定

對你即將在 agent 設定上做的任何改動，**問三個問題**：

1. 如果這個改動有幫助，我會看到什麼？如果沒有，又會看到什麼？
2. 腳本分得出這兩種嗎？
3. 腳本自己有沒有通過「沒動過、正確、壞掉」的測試？

**一個不用工具的小開始**。挑三個你和 agent 做過的任務。對每一個，寫下你預期最後會有的檔案，和一個你見過的錯誤。寫一個短腳本檢查這些檔案。（如果你的工作不是程式碼，就檢查輸出：表格的欄位、列數、總和。）在一個好結果和一個你手動弄壞的結果上各跑一次。它抓到壞的、放行好的，你就有一個評測了。它很小。下次你改規則時就用它。

## 代價和陷阱 {#costs-and-traps}

**四個任務是很薄的基礎**。它們能顯示大的差距。顯示不出小的，也涵蓋不了你沒想到的。每次有真實的失敗讓你意外，就加一個任務。

**你可能把設定調成配合測試**。如果你一直改設定，直到任務通過，你量到的是你配合這四個任務配合得多好。留一些不拿來調的任務。

**靜態的分數不執行程式碼**。我的評分器讀檔案。它沒辦法說程式碼能不能用。對執行很重要的工作，評分器得去跑測試（[讓 agent 能檢查自己的活](5-4-self-checks.html)）。

**任務會飽和**。Anthropic 的說法是「當 agent 通過所有可解的任務，沒有留下任何進步空間，就是評測飽和。」當每種設定都通過每個任務，評測就再也分不出它們。加更難的任務。

**任務之間不能共用狀態**。每次運行都從同一份乾淨的副本開始。如果一次運行留下了檔案、快取或改過的設定，下一次運行就不是公平的測試，分數量到的是殘留的東西。

**運行要花錢和時間**。在我的實驗裡，團隊做四個任務，一次大約 16 分鐘、大約 456 個 AI credits。prompt 快取會改變總額：在 Anthropic 的 API 上，快取讀取大約是基本價格的十分之一（[選模型：算的是每次成功的成本](1-1-models-and-cost.html)），但 Copilot 怎麼計費，我沒查過。十個任務，在兩種設定上各跑幾次，是一筆真的帳單。開始之前先決定，你拿到答案要做什麼。而且在我的設定裡，Copilot 的非互動模式不會執行 hook，所以真實的工作沒辦法為此批次跑（見「我的 harness 今天怎麼做」）。

**一次運行很薄**。我的結果是每個任務一次運行。[下一章](6-4-variance.html) 說怎麼跑更多次、怎麼報告你發現的東西。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

這些腳本和手動跑的習慣存在，是因為我沒有內建的辦法，讓一種設定跑一組固定任務並比較。如果平台加了這個功能，有日誌也有打分，我會用它，把我自己黏起來的東西丟掉。

固定任務不會退役。模型升級了、加了一條規則、重寫了一個 prompt：每一個都是改動，每一個都需要對同一個問題給同一種答案（[模型升級了，就要刪](6-5-model-upgrades.html)）。一個任務在每種設定都通過它的時候退役。如果實驗裡的四個任務不再分得出各種設定，我會重新檢視它們。
