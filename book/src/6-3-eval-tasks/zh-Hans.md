读这一章，你需要用过一个写代码的 AI agent，并且至少改过一次它的规则或配置。别的都不需要。

## 一句话 {#in-one-sentence}

想知道一个改动有没有用，就在改动前后，对同样的固定任务各跑一遍，用脚本打分，然后去读失败的那几次运行。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对 agent 规则或配置的任何改动，都要附上在同一组固定任务上改动前后各跑一遍的结果，由脚本打分。
- **风险**：光凭一次好结果，分不出改动有没有用。我自己这套只有四个任务，够看出四到六倍的差距，却看不出一成的差距。
- **做对的代价**：花一个下午写打分脚本，并用一个好答案和一个故意弄坏的答案测它，之后就是每次运行的开销。在我的实验里，三角色团队把四个任务做一遍，约 16 分钟、约 456 AI credits。
- **可以问团队**：“这个改动前后，你们跑了哪些固定任务？你们怎么知道给它们打分的脚本能抓出错误答案？”

## 怎么知道一个改动有没有用？ {#problem}

你加了一条规则，改了一个 prompt，或者打开了一项检查，接下来的那个任务做得挺顺。是改动起了作用吗？

光凭这一次，你分不出来。那个任务也许本来就简单，agent 也许只是运气好（[下一章](6-4-variance.html)讲的就是这个）。再说，你也不是中立的裁判：改动是你做的，你自然希望它有用。看着一个结果，觉得它变好了，这算不上证据。

写[慎用子 agent](2-3-subagents.html)的时候，我想知道三个岗位的 agent 是不是比一个 agent 强。我没有拿一个任务看一眼就下结论，而是拿了四个固定任务，每个任务两种配置各跑一次，所有结果交给同一个脚本打分。结果改变了我的设计：团队贵了好多，做对的却一个也没多（数字和它们的局限在那一章里）。要是只看几个结果，我是不会信的。

我在那里用的办法，叫**评测**（eval，evaluation 的简称）。它是对 agent 配置的测试，分三部分：一组任务、一种运行它们的方式、一种给结果打分的方式。我用的是**固定任务**：需求、起始文件和正确答案在多次运行之间都不变；给它们打分的东西，这里主要是一个脚本，叫**打分器**（grader）。那么，怎样才能搭出一个结论信得过的评测？

### 好任务长什么样

方法从任务开始，但并不是每个任务都适合做评测。我看三点。

1. 它是真的。它该像 agent 平时替你干的活，而不是考试题，所以如果你只加 pipeline、修公式，就别去测写诗。一个改动只在编出来的活上有用，在你的活上没用，什么也教不了你。
2. 它有一个能检查的正确答案。“加一条 pipeline”可以检查：五个文件存在，位置对，彼此一致。“把代码写得更好看”就不行。如果两个讲道理的人对结果对不对会有分歧，脚本就没法打分。
3. 它覆盖人真正会犯的错。好的一组任务里有简单的，也得有陷阱。在我的实验里，有一个任务要 agent 去改一个规则禁止它改的文件，好结果是拒绝。放这个任务，是因为真实的需求就可能这么要求，而听话照做的 agent 就是做错了。

我实验里的四个任务从小到中等：加一条 pipeline；把一个字段沿三条 pipeline 往下游传（其中一个字段中途改了名）；跨领域给一条 pipeline 改名并删掉旧文件；修一个在两处都有的公式，而需求同时要求改一个受保护的文件。四个任务确实很少，这对结果意味着什么，后面再说。

这类任务还分两种，失败的含义也不一样。**能力**任务检查配置还做不到的事，所以一开始你预期它常常失败。**回归**任务检查已经能做的事，所以你预期它每次都通过，一旦失败，就说明某个改动把它弄坏了。两种要有意混在一起，但通过率得分开解读。

这些任务底下的仓库是编出来的（93 个文件，5 个领域），也跑不起来。这是有意的选择。正因为正确答案事先就知道，脚本才能判断哪个结果对，用不着谁去运行代码来确认。

### 看结果，还是看过程？

任务有了，打分器该看什么？它可以看结果，也就是 agent 留下的文件，比如那五个文件加了没有、注册表里有没有新的 pipeline、受保护的文件是不是没动。它也可以看过程，也就是 agent 是怎么做到的，比如它有没有被拒绝过，计划还没审批时它有没有往某个地方写过东西。

大多数任务，给结果打分。通向正确答案的有效路径通常有很多条，所以死咬一条路径的打分器，会把好的活判成错的。只有当过程本身就是你在意的东西时，才给过程打分，比如“计划审批之前，规则会拒绝写入”。在我的 harness 里，这类场景要同时看两样东西：日志里有那次拒绝，文件也没变，两样都对上才算通过。没有日志就无从检查，这就是为什么要先[记录每一次调用](6-1-observe.html)。

在我实验的打分里，结果是一张清单。有些项对每个任务都一样，检查仓库是不是仍然自洽（文件有效、每条 pipeline 都有它的五个文件、字段一致、受保护的区域没动）。有些项只属于某一个任务，检查需求本身做完了没有。还有一项检查范围，看是不是只有该改的文件被改了。每一项都通过，任务才算通过。

这样打出来的分是全有或全无。如果你想在长任务里看到进展，就分部分打分（给部分分），并分别报告各部分。我没有拆，因为对这样的短任务来说，错一项通常就意味着结果是错的。

### 用脚本还是用模型打分

还有一个问题：由谁、或者由什么来打分？脚本读文件，回答通过或不通过；模型可以读结果，给出判断。两者各有弱点。

脚本便宜、快，每次答案都一样。它的弱点是脆。因为它只认一种特定的写法，有效的结果也可能被它判错，而这类情况只有读失败的运行才能发现。模型打分器能接受有效的变体，也能判断脚本判断不了的东西，比如一段解释清不清楚。但它的答案可能每次运行都不一样，还可能和被它打分的 agent 有同样的盲点（[模型能检查模型吗](5-6-model-checks-model.html)）。

Anthropic 的建议也是这样：“能用确定性的打分器就用，必要时，或者为了更灵活，再用 LLM 打分器。”（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）我自己也是这么做的。凡是答案能在文件里查出来的，我就用脚本，模型打分器只留给脚本看不到的少数事情。这里的实验没有用模型打分器。

### 先证明打分器靠谱

不管用哪一种，打分器都是程序，而程序会有 bug。什么都放过的打分器，会让每个改动看起来都无害；什么都判失败的打分器，会让每个改动看起来都有害。所以在信任任何分数之前，我先测打分器。我的实验有一个自测，分三部分：

- **没动过的**仓库，必须每个任务都不通过（什么都没做）。
- 手写的**正确答案**，必须每个任务都通过。
- 正确答案的**破坏版本**，必须全部被抓出来。一共 23 个，每个带一处错误，比如少了一行注册表，或者字段写错了。只要打分器放过一个，打分器就是错的。

最小的版本是一个好答案，加一个你亲手弄坏的答案：打分器必须放过前者、抓住后者。我的实验做这一步花了一个下午。这是人最爱跳过的一步，可我能说“失败的一项是有意义的”，靠的也正是它。

### 去读失败的运行

就算打分器测过了，它也只能告诉你有东西失败了，说不出为什么。所以哪怕有了脚本，我也一直守着一个习惯：**一次运行失败了，我就打开它，读发生了什么**。失败的原因，可能是三种很不一样的情况。可能是 agent 真的犯了错，评测本来就是为这个设的；可能是打分器错了，结果其实是对的，只是形式不是脚本预期的；也可能是任务不清楚，两种答案都说得通，需求却没说要哪一种。

三种里只有第一种，才能告诉你 agent 的情况。如果你把每次失败都当成这一种，就会丢掉好的改动、留下坏的改动。Anthropic 是这么说的：“读 transcript，才能确认你的评测衡量的是真正重要的东西。”（同一篇文章）

所以脚本并不能取代亲自去看。它省掉的，是把每次运行都看一遍的功夫。该细看哪几次，交给脚本来挑。它挑出失败的运行，这就是它对该看哪里的猜测，人再去读这几次。

### 你自己的任务和公开的基准

你也许会问，既然有公开的任务，为什么还要自己搭一套？**基准**（benchmark）是一组公开的任务，对所有人用同样的方式打分，好让模型之间可以比较。它只适合回答一个问题：这个模型在别人的任务上表现如何？另一个问题它回答不了：我对自己配置做的改动，在我的活上有没有用？要回答这个，你需要来自你仓库的任务，里面带着你自己的规则，比如我实验里那个受保护的文件。这就是我自己搭一套的原因。

这个选择也有代价。自己搭的一套任务很小，又只属于我自己。它还会过期：仓库一变，任务也得跟着变。

### 我的 harness 现在做到哪一步

前面说的都是实验。我的 harness 本身做得要少一些。在我的配置里，有几个固定的场景。每个场景是一个 prompt 加上预期结果，也就是日志里必须出现的几次调用（比如一次拒绝），和必须改或不能改的几个文件。我在 Copilot 里手动跑一次场景，再由一个检查读日志和文件，告诉我做得对不对。

它现在还做不到的，是批量运行。写作时（2026 年 10 月），我在自己的配置里看到，Copilot 的非交互模式不运行 hook，所以我没法批量跑这些场景，在真实任务上做改动前后的对比也还没做。本章讲的这种带打分、可重复的对比，我只在这个仓库的实验里用数字做过。日常用的时候，就是手动跑一个场景，再看它留下的日志。

### 自己跑一遍

想在自己动手之前先看看这一切怎么运转，可以从这个实验开始。它就是[慎用子 agent](2-3-subagents.html)里那些数字背后的测试，包括编出来的仓库、四个任务和打分脚本。它们都适用于任何 agent 工具。[`labs/subagents/`](../labs/subagents/README.md)讲了怎么先跑自测，再跑你自己的对比。看明白怎么用之后，把任务换成你自己的任务。

### 测你自己的配置

不管跑不跑这个实验，对 agent 配置做任何改动之前，都值得先问三个问题：

1. 如果这个改动有用，我会看到什么？如果没用，又会看到什么？
2. 脚本能把这两种情况区分开吗？
3. 脚本本身通过了“没动过的、正确的、被弄坏的”这三项测试吗？

不用任何工具，也能先小小地起个步。挑三个你用 agent 做过的任务，给每一个写下你预期最后会有的文件，和一个你见过的错误，再写一个短脚本检查这些文件。（如果你的工作不是代码，就检查输出：表的列、行数、合计。）用它跑一个好结果，再跑一个你手动弄坏的结果。如果它抓住了坏的、放过了好的，你就有了一个评测。它很小，但下次改规则的时候，就可以用上它。

## 小评测看不出的东西，和它的开销 {#costs-and-traps}

这么小的评测，能靠它走多远？它的局限大多出在任务上。四个任务的底子很薄。我这四个提示了四到六倍的差距，可要是只差一成，就看不出来了。你没想到的情况，它们也覆盖不了，所以每次遇到出乎意料的真实失败，就加一个任务。任务还会用两种不那么显眼的方式误导你。一种是你不停改配置，直到任务通过，这时量到的其实是配置对这四个任务拟合得有多好，所以要留一些不拿来调优的任务。另一种是问题反过来，任务太容易了：每种配置都通过每个任务，任务就饱和了。用 Anthropic 的话说：“评测饱和，是指 agent 通过了所有可解的任务，再没有改进的余地。”到了这一步，评测就分不出各种配置了，这时该加更难的任务。

另一些局限出在分数上。其一，静态打分不运行代码。我的打分器读文件，所以没法说代码能不能跑。对运行结果要紧的活，打分器得去跑测试（[让 agent 能检查自己的活](5-4-self-checks.html)）。其二，分数公不公平，还要看背后的运行公不公平，所以任务之间不能共享状态。每次运行都要从同一份干净的副本开始。如果某次运行留下了文件、缓存或改过的设置，下一次运行就不是公平的测试，因为分数量到的是残留物。

然后是账单：运行要花钱，也要花时间。在我的实验里，团队把四个任务做一遍，约 16 分钟、约 456 AI credits。prompt 缓存会改变这笔账，在 Anthropic 的 API 上，命中缓存的读取约是基础价格的十分之一（[选模型：看每次成功的成本](1-1-models-and-cost.html)），但我没有查过 Copilot 怎么计费。十个任务，在两种配置上各跑好几次，就是一笔实在的账单。动手之前，先想好答案出来后你打算拿它做什么。（前面“我的 harness 现在做到哪一步”说过，在我的配置里，真实的工作没法为此批量运行。）

最后，一次运行很单薄。我的结果是每个任务只跑了一次，[下一章](6-4-variance.html)讲怎么多跑几次，以及怎么汇报你发现的东西。

## 什么时候删掉脚本，任务为什么要留着 {#when-to-delete-it}
{status: industry}

这些脚本和手动运行的习惯之所以存在，是因为我没有内置的办法，把一套配置放到一组固定任务上跑一遍再比较。如果哪个平台加了这个功能，带日志和打分，我会用它，把自己的胶水代码丢掉。

固定任务却不会跟着脚本一起退休。模型升级、加一条规则、重写一个 prompt，都是改动，每一次都会把同一个问题再提一遍：这个改动有没有用？固定任务就是用来回答它的（[模型升级了，就要删](6-5-model-upgrades.html)）。一个任务只有在每种配置都能通过时才退休。如果实验里这四个任务不再能区分各种配置，我会重新审视它们。

## 在你自己的环境里试试 {#try-it}

::: prompt
看这个仓库里最近十次改过指令、skill、agent 或 hook 文件的提交。对每一次，说明当时有没有给出证据（如果有）证明这个改动有用。然后从这个仓库的真实历史里，提出三个固定任务：每个给出需求、起始提交，以及一个脚本只看文件就能检查的结束状态。其中包含一个正确结果是拒绝的任务。不要创建或修改任何文件。
