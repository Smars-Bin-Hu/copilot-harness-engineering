這一章是個案研究的第一章。讀它，你需要讀過 [上下文是一份預算](3-1-context-budget.html) 和 [agent 該記住什麼](3-5-memory.html)，它們講的是一般的想法。它適合有一大份老程式碼的團隊。如果你的程式碼很小，讀它是為了判斷你不需要。最有用的部分，是 [測你自己的設定](#test) 裡那個小實驗：你在建任何東西之前，就可以先跑。

## 一句話 {#in-one-sentence}

程式碼才是真相。知識庫只是它的索引和摘要，讀起來應該比較便宜。它不求第一天就完整，它求誠實：每張卡片說明它讀的是哪個版本的原始檔案，每個缺口都寫在下一個讀者會看到的地方。

## 給主管 {#for-leaders}

- **要做的決定**：要不要出錢做知識庫（一個資料夾，裡面是寫給 agent 的程式碼短筆記），以及誰負責。先測一下，只搜尋程式碼是不是已經夠了。
- **風險**：程式碼庫很大、同樣的探索在每個會話都要再付一次、或者答錯很貴的時候，搜尋就開始吃力。我沒有拿知識庫和單純搜尋比較過，所以這是一場賭注，不是證明過的勝利。沒有人更新的知識庫，會變成很有自信地答錯。
- **做對的成本**：模型把每個物件的程式碼讀一遍；對大的領域，這是真金白銀，我沒有算過價。要有人負責更新，筆記也需要和程式碼一樣的存取規則。
- **可以問團隊**：「十個我們知道答案的問題，只用單純搜尋的 agent 答對幾個？」

## 問題 {#problem}

假設一個團隊擁有一份有幾千個物件的程式碼庫。**物件**是程式碼裡一個有名字、被別的東西使用的東西：預存程序、排程工作、類別、資料表。你請 agent 改其中一個。要改得安全，agent 得知道這個物件做什麼、誰在用它、改了會壞掉什麼。

新的 agent 會話開始時，這些一概不知道。第一個問題是顯而易見的。

### 為什麼不乾脆讓 agent 搜尋程式碼？

agent 會搜尋。它能執行 `grep`（找出每一行含有某個詞的地方）、開檔案、順著名字追。對很多工作，這就是正確的答案，而且不用任何設定。我想說清楚它什麼時候就夠了。搜尋也不必是單純的 `grep`：語言伺服器（回答「這個在哪裡定義、誰在用」的編輯器服務）或程式碼搜尋服務都可以幫忙，一頁簡短而好的規則也有幫助。知識庫要贏的是這一整套，不是單純的 `grep`。

**搜尋就夠的時候**：

- 程式碼庫很小，或者你要的那一塊放得進一個上下文。
- 你知道要找的東西的名字。
- 任務只做一次，所以沒有人為同樣的探索付兩次。

**開始吃力的時候**：

- **agent 靠剛讀到的東西，決定下一步讀什麼**。它可能漏掉一個物件，追到一個名字相同、意思不同的東西，太早停下來。它說不出自己漏了多少。問它兩次，可能得到兩個不同的答案。
- **同樣的探索，每個會話都要付一次**。每個新會話都從空的上下文開始（[上下文預算](3-1-context-budget.html)），所以 agent 又找到同樣的東西。
- **有些事不在程式碼裡**。哪個環境執行一個工作、一條規則為什麼存在、去年什麼壞了。搜尋找不到，因為那裡沒有寫。
- **答錯很貴**。如果物件碰到共用的資料，靠不完整的搜尋猜出來的答案，是不夠的。

**知識庫**是一個資料夾，裡面是關於程式碼的純文字檔案，寫給 agent 讀。想法是：探索只付一次錢，把結果留下來，並先讀結果，因為它應該比讀程式碼便宜。這一點我沒有量過。

**我沒有拿它和搜尋比較過**。我沒有把同樣的問題，一次用單純搜尋、一次用知識庫跑過，所以我不知道第二個贏多少，甚至贏不贏。我有的，是上面的推理，以及一個讓你在自己的程式碼上測試的辦法（見 [測你自己的設定](#test)）。把知識庫看成一場賭注：在上面那些條件下才會有回報，不是證明過的勝利。

## 原理 {#how-it-works}

### 知識庫的形狀

讀者只往下走到任務需要的深度。

::: figure 8-1-kb-layers

- **總覽**列出**領域**，並有一份詞彙表。領域是為了同一件工作的一組物件，例如「訂單」或「薪資」。
- 一個領域的**架構頁**說明這個領域是做什麼的、主要的流程、從哪裡開始讀、它的陷阱和它的限制。
- **卡片**是關於一個物件的短條目：它做什麼、它的規則、它用誰、它的陷阱。每條規則都註明它來自哪幾行程式碼。一個檔案放同一種類型的卡片。agent 往下走來找到卡片：總覽，然後是領域的頁面，再用 id 找到卡片。
- **程式碼**在最底下。它是真相的來源。卡片和程式碼不一致時，程式碼贏。

所以卡片是一份附日期的承諾，不是程式碼的替代品。需要更多的 agent，去讀程式碼。

### 腳本做結構，模型做意義

寫一張卡片有兩種工作，它們不一樣。

- **結構**有一個正確答案：有哪些物件、誰用誰（合起來是程式碼的**地圖**）、照什麼順序學它們、一張卡片列的關係對不對。腳本能算出來。每次答案都一樣，也不花 token。要模型去做，它是憑判斷在程式碼裡走，可能漏掉東西。
- **意義**沒有單一答案：一個物件是做什麼的、它的規則是什麼、哪個陷阱會絆住人。只有讀了程式碼的模型能寫。

這一部其餘的內容，都從這個分工來。[Toolkit](8-2-kb-toolkit.html) 是腳本怎麼畫出地圖。[盲抽查](8-3-kb-audit.html) 量這張地圖。[分批學](8-4-kb-learning.html) 是模型寫下意義的地方，腳本能檢查的就檢查。[讓它一直是對的](8-5-kb-keep-true.html) 是程式碼改了之後的事。

### 誠實，不求完整

我的猜測是，知識庫的大部分可以從程式碼來。這是猜測，不是量測。其餘的不行：什麼在哪個環境執行、什麼壞了和為什麼、有人做了什麼決定。這一部分隨時間而來，來自做完的任務、根因報告、人們匯出的東西。所以知識庫第一天不會完成，假裝完成只會讓它更糟，因為看起來完整的知識庫，會被人相信。

兩個習慣讓它誠實：

1. **每張卡片說明它讀的是它的原始檔案的哪個版本**。它記下一個 commit（程式碼的一個存下來的版本，用一個叫 sha 的短 id 命名）。腳本也維護一份**物件索引**：每個物件的清單、它所在的原始檔案，以及該檔案的 sha。這樣你之後才能列出程式碼已經走過去的卡片。[第 8.5 章](8-5-kb-keep-true.html) 說明怎麼做。
2. **每個缺口都寫下來**。程式碼說不出的，進入一份**請求清單**：每一列是一件必須由人提供的事，附上它是哪一種，以及一個唯讀的取得辦法。agent 在下一個停下來的地方問這些，從不在工作到一半時問。[第 8.5 章](8-5-kb-keep-true.html) 有細節。

### 每一步都是一個由人批准的任務

建知識庫不是一個大 prompt。每一步都是一個任務（見 [管任務，不管對話](5-1-tasks.html)），有一份人批准的計劃，和一次人批准的寫回（寫回是把做完的工作複製進知識庫；見 [兩道門：人在哪裡批准](5-3-two-approvals.html)）。腳本檢查能檢查的：檔案的格式、關係、被引用的行。而且我不讓 agent 連上正在執行的環境。只有環境才說得出的事，由人執行並交過來。

### 路線

1. 建一個 toolkit，每個程式碼庫一次（8.2）。
2. 計算地圖，每次使用之前（8.2）。
3. 抽查地圖（8.3）。
4. 把程式碼分成領域，一次（8.4）。
5. 分批學每個領域（8.4）。
6. 寫架構頁（8.4）。
7. 讓它一直是對的：更新、擷取、請求（8.5）。

### 測你自己的設定 {#test}

在你建任何東西之前，先弄清楚你需不需要它。

1. 寫 10 個關於你程式碼的問題，正確答案是你知道的。混合幾種：「什麼呼叫 X？」、「Y 改了會怎樣？」、「為什麼 Z 跳過這個情況？」
2. 在全新的對話裡，只用單純搜尋，把每個問題問 agent。照你知道的，每個答案判對或錯。
3. 為一個小領域寫卡片，自己寫或讓 agent 寫。在全新的對話裡，有卡片可用的情況下，再問同樣的問題。
4. 比較：答對的數量、用量（你的工具為一次運行顯示的 token 數字）、時間。

兩個提醒。問題的形式要讓人無法只靠一個檔案回答，例如「Y 改了會壞掉什麼？」，並讓沒讀過卡片的人來選。十個問題只看得出很大的差別。

每個條件都做好幾次，不要只做一次，因為 agent 不會做兩次同樣的事（見 [一次運行證明不了什麼](6-4-variance.html)）。如果單靠搜尋得分差不多，就不要建知識庫。

## 代價和陷阱 {#costs-and-traps}

- **它需要維護**。沒有人更新的知識庫，會變成很有自信地答錯。如果你的程式碼每天都在變，又沒有人負責更新，搜尋是比較好的選擇。
- **卡片可能是錯的**。它是模型對程式碼的解讀。檢查抓得到結構，抓不到一條規則是不是理解對了。這要靠人的審查，或獨立的 reviewer（[模型能檢查模型嗎](5-6-model-checks-model.html)）來涵蓋。
- **卡片可能讓 agent 被錨定**。先讀卡片的 agent，可能看比較少的程式碼，並保留錯誤卡片的看法。對答錯很貴的工作，讓它重讀卡片引用的那幾行。
- **讀卡片也花 token**。太長的知識庫只是把成本搬到別處。卡片要短，agent 只在需要時才打開下面的層。
- **建它是有價錢的**。模型把每個物件的程式碼讀一遍。對大的領域，這是真金白銀。這是賭讀過的東西會被重複使用。粗略的大小：每個物件讀一遍，加上每個月會變的檔案。我沒有算過價。prompt 快取（Anthropic 的文件說，快取讀取大約是基本價格的十分之一；我沒有在 Copilot 上確認過；見 [選模型：算的是每次成功的成本](1-1-models-and-cost.html)）可能同時降低建和讀的成本，所以測的時候要開著它，像你真正執行時那樣。
- **必須有人負責，而且卡片需要和程式碼一樣的存取規則**。卡片是內部程式碼的摘要。決定誰更新它、誰可以讀它，像你對程式碼做的那樣。

## 什麼時候可以刪掉 {#when-to-delete-it}

如果你自己的測試顯示，單靠搜尋，用同樣的成本給出同樣的答案，就把卡片刪掉，只留請求清單，因為那是搜尋永遠給不了的部分。還有，如果有一天平台建立並更新一份程式碼索引，而且你量得出它是準確的，就用它，不要自己維護。
