從這一章起是一個個案研究。一般的想法，前面的[上下文是一份預算](3-1-context-budget.html)和[agent 該記住什麼](3-5-memory.html)已經講過，這裡就不重複了。它寫給手上有一大份老程式碼的團隊。程式碼庫很小的話，讀它是為了確認自己用不著這些。不管是哪一種，最有用的都是[先弄清楚你需不需要它](#test)裡那個小實驗，因為什麼都還沒建，你就可以先跑一遍。

## 一句話 {#in-one-sentence}

程式碼才是真相，知識庫只是它的索引和摘要，讀起來應該比程式碼便宜。它不求第一天就完整，只求誠實：每張卡片都寫明它讀的是哪個版本的原始檔案，每個缺口都寫在下一個讀者看得到的地方。

## 給主管 {#for-leaders}

- **要做的決定**：要不要出錢做知識庫（一個資料夾，裡面是寫給 agent 看的程式碼短筆記），以及由誰負責。決定之前，先測一下只搜尋程式碼是不是已經夠用。
- **風險**：程式碼庫很大、同樣的探索每個會話都要再付一次，或者答錯的代價很高，這些時候搜尋就開始吃力了。我沒有拿知識庫和單純的搜尋比較過，所以這是一場賭注，不是已經證實的好處。而沒有人更新的知識庫，會很有把握地答錯。
- **做對的成本**：模型要把每個物件的程式碼讀一遍。對大的領域來說，這是真金白銀，我也沒有算過要花多少。另外得有人負責更新，筆記也需要和程式碼一樣的存取規則。
- **可以問團隊**：「十個我們知道答案的問題，只用單純搜尋的 agent 答對幾個？」

## agent 改一個物件之前，得先知道什麼？ {#problem}

假設一個團隊管著一份有幾千個物件的程式碼庫。這裡說的**物件**，是程式碼裡有名字、被別的東西用到的東西：預存程序、排程工作、類別、資料表。你請 agent 改其中一個。要改得安全，它得知道這個物件是做什麼的、誰在用它、改了會壞掉什麼，可是新開的 agent 會話對這些一無所知。要補上這個缺口，最直接的辦法就是讓它自己去搜。

### 為什麼不乾脆讓 agent 搜尋程式碼？

agent 當然會搜尋。它能執行 `grep`（找出每一行含有某個詞的地方）、打開檔案、順著名字往下追。很多工作這樣做就是對的，而且不用任何設定。正因為這樣，我想先說清楚它什麼時候就夠了。再說，搜尋也不一定是光禿禿的 `grep`：語言伺服器（回答「這個在哪裡定義、誰在用」的編輯器服務）或程式碼搜尋服務都幫得上忙，一頁簡短而好的規則也有幫助。知識庫要贏的是這一整套，不是單純的 `grep`。

如果程式碼庫很小，或者你要的那一塊放得進一個上下文；如果你知道要找的東西叫什麼；又或者任務只做一次，沒有人會為同樣的探索付兩次錢，那搜尋就夠了。

在這些情況之外，搜尋就開始吃力了，頭一個原因出在 agent 搜尋的方式上。它根據剛讀到的東西決定下一步讀什麼，所以可能漏掉一個物件，追到一個名字相同、意思不同的東西，或者太早停下來。漏了多少，它自己說不出來。同一個問題問它兩次，可能得到兩個不同的答案。

這樣的搜尋就算很順利，下次也得重來。每個新會話都從空的上下文開始（[上下文是一份預算](3-1-context-budget.html)），agent 只好把同樣的東西再找一遍，同樣的探索每個會話都要付一次錢。

還有些事，搜尋再順利也幫不上忙，因為它們根本不在程式碼裡，例如哪個環境執行某個工作、某條規則為什麼存在、去年出過什麼問題。程式碼裡沒有寫，自然搜不到。

最後一種情況和代價有關：有些答案錯不起。如果物件碰到共用的資料，靠不完整的搜尋猜出來的答案就不夠用。

而**知識庫**走的是反過來的路。它是一個資料夾，裡面是關於程式碼的純文字檔案，寫給 agent 讀。想法是探索只付一次錢，把結果留下來，之後先讀結果，因為它應該比讀程式碼便宜。

我說「應該」，是因為我沒有把同樣的問題一次用單純搜尋、一次用知識庫跑過，所以不知道後者能贏多少，甚至贏不贏。我手上有的，是上面這番推理，再加上一個讓你在自己的程式碼上測試的辦法（見[先弄清楚你需不需要它](#test)）。所以請把知識庫看成一場賭注：滿足上面那些條件才會有回報，而不是已經證實的好處。

## 一個誠實的知識庫是怎麼建起來的 {#how-it-works}

### 知識庫的形狀

如果你決定下這個注，要建的究竟是什麼？知識庫分好幾層，讀的人只往下走到任務需要的那一層。

::: figure 8-1-kb-layers

最上面是**總覽**，列出所有**領域**，還附一份詞彙表。領域是為了同一件工作而存在的一組物件，例如「訂單」或「薪資」。每個領域有一份**架構頁**，說明這個領域是做什麼的、有哪些主要流程、從哪裡開始讀、有哪些陷阱、有哪些限制。

再往下一層是**卡片**，一張卡片是關於一個物件的短條目：它做什麼、它的規則、它用到誰、它的陷阱。每條規則都註明它來自哪幾行程式碼。卡片按類型分組，一種類型放一個檔案。要找一張卡片，agent 就一層層往下走：先看總覽，再到領域的頁面，最後用 id 找到卡片。

最底下是**程式碼**，它是真相的來源，所以卡片和程式碼不一致時，以程式碼為準。這樣看來，卡片是一份附日期的承諾，而不是程式碼的替代品。agent 需要更多資訊時，就去讀程式碼。

### 腳本管結構，模型管意義

那卡片由誰來寫？寫一張卡片其實要做兩種不一樣的工作。

**結構**只有一個正確答案：有哪些物件、誰用誰（合起來就是程式碼的**地圖**）、照什麼順序去學、一張卡片列出的關係對不對。這些腳本算得出來，每次給出同樣的答案，也不花 token。換成模型來做，它會憑判斷在程式碼裡走，可能漏掉東西。

**意義**正好相反。它沒有單一的答案：一個物件是做什麼的、它的規則是什麼、哪個陷阱會絆住人。這只有讀了程式碼的模型才寫得出來。

這一部分後面的內容，都是從這個分工推出來的。[Toolkit：用腳本畫出程式碼的地圖](8-2-kb-toolkit.html)講腳本怎麼畫地圖，[地圖對不對：盲抽查](8-3-kb-audit.html)再來量一量它畫得對不對。[分批學一個領域](8-4-kb-learning.html)是模型寫下意義的地方，腳本在旁邊檢查它能檢查的部分。[讓知識庫一直是對的](8-5-kb-keep-true.html)講的是程式碼改了之後怎麼辦。

### 求誠實，不求完整

知識庫有多少內容能從程式碼裡得到？我猜是大部分，不過這只是猜測，不是量測。剩下的得不到：什麼在哪個環境執行、出過什麼問題、原因是什麼、誰做了什麼決定。這一部分要靠時間慢慢累積，來自做完的任務、根因報告和人們匯出的東西。所以知識庫第一天不可能完成；假裝它已經完成只會更糟，因為一個看起來完整的知識庫會被人相信。

讓它保持誠實的，是兩個習慣。一個是每張卡片都寫明它讀的是哪個版本的原始檔案。卡片會記下一個 commit（程式碼的一個存下來的版本，用一個叫 sha 的短 id 來命名）。為了之後能核對，腳本還維護一份**物件索引**，列出每個物件、它所在的原始檔案，以及那個檔案的 sha。靠著這些，你才能列出程式碼已經改過、卡片卻還沒跟上的那些卡片。

另一個習慣是每個缺口都寫下來。程式碼說不清楚的事，記進一份**請求清單**：每件必須由人提供的東西占一列，寫明它屬於哪一類，以及一個唯讀的取得辦法。agent 會在下一個停下來的地方提出這些請求，絕不在工作做到一半時提。這兩個習慣的細節，都在[第 8.5 章](8-5-kb-keep-true.html)。

### 每一步都是一個由人批准的任務

建知識庫不是靠一個大 prompt。每一步都是一個任務（見[管任務，不管對話](5-1-tasks.html)），計劃要人批准，寫回也要人批准；寫回，就是把做完的工作複製進知識庫（見[兩道門：人在哪裡批准](5-3-two-approvals.html)）。能檢查的部分交給腳本：檔案的格式、關係、被引用的程式碼行。

還有一條限制，每一步都適用：agent 從不連上正在執行的環境。只有環境才說得出的事，由人去執行，再把結果交過來。

### 路線

照先後排起來，這些步驟就是一條路線：

1. 建一個 toolkit，每個程式碼庫一次（8.2）。
2. 計算地圖，每次使用之前（8.2）。
3. 盲抽查地圖（8.3）。
4. 把程式碼分成領域，一次（8.4）。
5. 分批學每個領域（8.4）。
6. 寫架構頁（8.4）。
7. 讓它一直是對的：更新、擷取、請求（8.5）。

### 先弄清楚你需不需要它 {#test}

走這條路之前，一個小測試就能告訴你需不需要它。

1. 寫 10 個關於你程式碼的問題，正確答案是你知道的。種類要混著來：「什麼呼叫了 X？」「Y 改了會怎樣？」「為什麼 Z 跳過這個情況？」
2. 每個問題都在全新的對話裡問 agent，只用單純搜尋。照你知道的答案，每個回答判對或錯。
3. 自己寫或讓 agent 幫忙，為一個小領域寫卡片。然後在全新的對話裡再問同樣的問題，這次有卡片可用。
4. 比較答對的數量、用量（你的工具為一次運行顯示的 token 數）和時間。

這個測試要靠得住，有幾點得注意。問題的形式要讓人無法只靠一個檔案回答，例如「Y 改了會壞掉什麼？」，而且要讓沒讀過卡片的人來選題。agent 不會把同一件事做得兩次一樣，所以每種條件都要做好幾次，而不是只做一次（見[一次運行證明不了什麼](6-4-variance.html)）。再說，十個問題本來就只看得出很大的差別。如果單靠搜尋得分也差不多，就不要建知識庫。

## 要付出什麼，又會在哪裡出錯 {#costs-and-traps}

就算測試說值得建，知識庫也不會自己一直保持正確。它需要維護，因為沒有人更新的知識庫會很有把握地答錯。如果你的程式碼每天都在變，又沒有人願意負責更新，搜尋是比較好的選擇。

就算卡片是最新的，它也可能是錯的，畢竟它是模型對程式碼的解讀。檢查抓得到結構，抓不到一條規則是不是理解對了，這部分要靠人的審查，或獨立的 reviewer（[模型能檢查模型嗎](5-6-model-checks-model.html)）。而且 agent 是先讀卡片的，所以卡片可能讓它被錨定：它可能少看一些程式碼，沿用一張錯誤卡片的看法。對出錯代價高的工作，讓它重讀卡片引用的那幾行。

agent 每讀一張卡片都要花 token，所以太長的知識庫只是把成本搬到別處。卡片要短，agent 只在需要時才往下打開更低的層。

前面說的都是維護和使用的成本，建的那一次還要另算：模型要把每個物件的程式碼讀一遍，所以對大的領域來說，建一次就是真金白銀，賭的是這些讀過的東西會被重複使用。粗略的規模是每個物件讀一遍，再加上每個月會變的檔案，不過我沒有算過價。prompt 快取也許能同時降低建和讀的成本。Anthropic 的文件說，快取讀取大約是基本價格的十分之一（見[選模型：算的是每次成功的成本](1-1-models-and-cost.html)），不過我沒有在 Copilot 上確認過。所以測的時候要把它開著，就像你真正執行時那樣。

最後要定的是誰來負責。知識庫得有人管。卡片又是內部程式碼的摘要，所以也需要和程式碼一樣的存取規則。誰來更新、誰可以讀，要決定下來。

## 什麼時候刪掉卡片，留下什麼 {#when-to-delete-it}

如果你自己的測試顯示，單靠搜尋就能用同樣的成本給出同樣的答案，那就把卡片刪掉，只留下請求清單，因為那是搜尋永遠給不了的部分。如果有一天平台能建立並更新一份程式碼索引，而且你量得出它是準確的，就改用它，不要再自己維護一份。

## 在你自己的環境試試 {#try-it}

::: prompt
判斷這個倉庫是否會從一份寫下來的程式碼知識庫得到好處，還是搜尋就夠了。估計它有多少物件（模組、工作、資料表、服務），以及程式碼庫有多大。指出完全不在程式碼裡的那幾類事實，例如哪個環境執行一個工作，或一條規則為什麼存在。說明程式碼多久變一次。然後給出結論：搜尋就夠，或值得測一個知識庫，並附上理由。不要改任何檔案。
:::
