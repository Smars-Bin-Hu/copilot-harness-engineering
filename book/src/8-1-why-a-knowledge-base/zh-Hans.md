从这一章起是一个案例研究。一般的思路，前面的[上下文是一份预算](3-1-context-budget.html)和[agent 该记住什么](3-5-memory.html)已经讲过，这里就不重复了。它写给手里有一大份老代码的团队。代码库很小的话，读它是为了确认自己用不着这些。不管是哪种情况，最有用的都是[先弄清楚你需不需要它](#test)里那个小实验，因为什么都还没建，你就可以先跑一遍。

## 一句话 {#in-one-sentence}

代码才是真相，知识库只是它的索引和摘要，读起来应该比代码便宜。它不求第一天就完整，只求诚实：每张卡片都写明它读的是源文件的哪个版本，每个缺口都写在下一个读者看得到的地方。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要不要出钱做知识库（一个文件夹，里面是写给 agent 看的代码短笔记），以及由谁负责。拍板之前，先测一下只搜索代码是不是已经够用。
- **风险**：代码库很大、同样的探索每个会话都要再付一次，或者答错的代价很高，这些时候搜索就开始吃力了。我没有拿知识库和单纯的搜索比过，所以这是一次押注，不是已经证明的收益。而没人更新的知识库，会变得自信满满地答错。
- **做对的代价**：模型要把每个对象的代码读一遍。对大的领域来说，这是真金白银，我也没有算过要花多少。另外得有人负责更新，笔记也需要和代码一样的访问规则。
- **可以问团队**：“十个我们知道答案的问题，只用单纯搜索的 agent 能答对几个？”

## agent 改一个对象之前，得先知道什么？ {#problem}

假设一个团队管着一份有几千个对象的代码库。这里说的**对象**，是代码里有名字、被别的东西用到的东西：存储过程、定时任务、类、表。你让 agent 改其中一个。要改得安全，它得知道这个对象是干什么的、谁在用它、改了会弄坏什么，可新开的 agent 会话对这些一概不知。要补上这个缺口，最直接的办法就是让它自己去搜。

### 为什么不直接让 agent 搜索代码？

agent 当然会搜索。它能运行 `grep`（找出每一行含有某个词的地方）、打开文件、顺着名字往下追。很多活这样做就是对的，而且不用任何配置。正因为这样，我想先说清楚它什么时候就够了。再说，搜索也不一定是光秃秃的 `grep`：语言服务器（回答“这个在哪里定义、谁在用”的编辑器服务）或者代码搜索服务都能帮上忙，一页简短而好的规则也有用。知识库要赢的是这一整套，不是单纯的 `grep`。

如果代码库很小，或者你要的那一块装得进一个上下文；如果你知道要找的东西叫什么；又或者任务只做一次，没人会为同样的探索付两次钱，那搜索就够了。

在这些情况之外，搜索就开始吃力了，头一个原因出在 agent 搜索的方式上。它根据刚读到的东西决定下一步读什么，所以可能漏掉一个对象，追到一个重名但意思不同的东西，或者太早停下来。漏了多少，它自己说不出来。同一个问题问它两次，可能得到两个不同的答案。

这样的搜索就算很顺利，下次也得重来。每个新会话都从空的上下文开始（[上下文是一份预算](3-1-context-budget.html)），agent 只好把同样的东西再找一遍，同样的探索每个会话都要付一次钱。

还有些事，搜索再顺利也帮不上忙，因为它们根本不在代码里，比如哪个环境运行某个任务、某条规则为什么存在、去年出过什么故障。代码里没写，自然搜不到。

最后一种情况和代价有关：有些答案错不起。如果对象碰到共用的数据，靠不完整的搜索猜出来的答案就不够用。

而**知识库**走的是反过来的路子。它是一个文件夹，里面是关于代码的纯文本文件，写给 agent 读。思路是探索只付一次钱，把结果留下来，以后先读结果，因为它应该比读代码便宜。

我说“应该”，是因为我没有把同样的问题一次用单纯搜索、一次用知识库跑过，所以不知道后者能赢多少，甚至赢不赢。我手里有的，是上面这番推理，外加一个让你在自己的代码上测试的办法（见[先弄清楚你需不需要它](#test)）。所以请把知识库看成一次押注：满足上面那些条件才会有回报，而不是已经证明的收益。

## 一个诚实的知识库是怎么搭起来的 {#how-it-works}

### 知识库的形状

如果你决定押这一注，要搭的究竟是个什么东西？知识库分好几层，读的人只往下走到任务需要的那一层。

::: figure 8-1-kb-layers

最上面是**总览**，列出所有**领域**，还附一份词汇表。领域是为同一项工作服务的一组对象，比如“订单”或者“薪资”。每个领域有一份**架构页**，写明这个领域是干什么的、有哪些主要流程、从哪里开始读、有哪些坑、有哪些限制。

再往下一层是**卡片**，一张卡片是关于一个对象的简短条目：它的用途、它的规则、它用到谁、它的坑。每条规则都引用它所依据的代码行。卡片按类型分组，一种类型放一个文件。要找一张卡片，agent 就一层层往下走：先看总览，再到领域的页面，最后按 id 找到卡片。

最底下是**代码**，它是真相的来源，所以卡片和代码对不上时，以代码为准。这样看，卡片是一份带日期的承诺，而不是代码的替代品。agent 需要更多信息时，就去读代码。

### 脚本管结构，模型管含义

那卡片由谁来写？写一张卡片其实要干两种不一样的活。

**结构**只有一个正确答案：有哪些对象、谁用谁（合起来就是代码的**地图**）、按什么顺序去学、一张卡片列出的关系对不对。这些脚本算得出来，每次给出同样的答案，也不花 token。换成模型来做，它会凭判断在代码里走，可能漏掉东西。

**含义**正好相反。它没有唯一的答案：一个对象是干什么的、它的规则是什么、哪个坑会绊倒人。这只有模型读了代码才写得出来。

这一部分后面的内容，都是从这个分工推出来的。[Toolkit：用脚本画出代码的地图](8-2-kb-toolkit.html)讲脚本怎么画地图，[地图对不对：盲抽查](8-3-kb-audit.html)再来量一量它画得对不对。[分批学一个领域](8-4-kb-learning.html)是模型写下含义的地方，脚本在旁边检查它能检查的部分。[让知识库一直是对的](8-5-kb-keep-true.html)讲的是代码改了以后怎么办。

### 求诚实，不求完整

知识库有多少内容能从代码里得到？我猜是大部分，不过这只是猜测，不是测量。剩下的得不到：什么在哪个环境里运行、出过什么故障、原因是什么、谁做了什么决定。这部分要靠时间慢慢积累，来自做完的任务、根因报告和人导出的东西。所以知识库第一天不可能完成；假装它已经完成只会更糟，因为一个看起来完整的知识库会被人相信。

让它保持诚实的，是两个习惯。一个是每张卡片都写明它读的是源文件的哪个版本。卡片会记下一个 commit（代码的一个已保存版本，用一个叫 sha 的短 id 来命名）。为了以后能核对，脚本还维护一份**对象索引**，列出每个对象、它所在的源文件，以及那个文件的 sha。靠着这些，你才能列出代码已经改过、卡片却还没跟上的那些卡片。

另一个习惯是每个缺口都写下来。代码说不清的事，记进一张**请求清单**：每件需要人提供的东西占一行，写明它属于哪一类，以及一种只读的获取办法。agent 会在下一个停靠点提出这些请求，绝不在干活干到一半时提。这两个习惯的细节，都在[第 8.5 章](8-5-kb-keep-true.html)。

### 每一步都是一个由人审批的任务

建知识库不是靠一个大 prompt。每一步都是一个任务（见[管任务，不管对话](5-1-tasks.html)），计划要人审批，写回也要人审批；写回，就是把做完的工作复制进知识库（见[两道门：人在哪里审批](5-3-two-approvals.html)）。能检查的部分交给脚本：文件的格式、关系、引用的代码行。

还有一条限制，每一步都适用：agent 从不连接线上环境。只有环境才知道的事，由人去运行，再把结果交给它。

### 路线

按先后排起来，这些步骤就是一条路线：

1. 搭一个 toolkit，每个代码库一次（8.2）。
2. 计算地图，每次使用之前（8.2）。
3. 盲抽查地图（8.3）。
4. 把代码切成领域，一次（8.4）。
5. 分批学每个领域（8.4）。
6. 写架构页（8.4）。
7. 让它一直是对的：更新、捕获、请求（8.5）。

### 先弄清楚你需不需要它 {#test}

走这条路之前，一个小测试就能告诉你需不需要它。

1. 写 10 个关于你的代码的问题，正确答案你是知道的。种类要混着来：“什么调用了 X？”“如果 Y 改了会怎样？”“为什么 Z 跳过了这种情况？”
2. 每个问题都在新对话里问 agent，只用单纯搜索。对照你已知的答案，每个回答判对或错。
3. 手工或者让 agent 帮忙，给一个小领域写卡片。然后在新对话里再问同样的问题，这次卡片可以用。
4. 比较答对的个数、用量（你的工具为一次运行显示的 token 数）和时间。

这个测试要靠得住，有几点得注意。提问的形式要让一个文件回答不了，比如“如果 Y 改了，什么会坏？”，而且要让没读过卡片的人来选题。agent 不会把同一件事做得两次一样，所以每种条件都要做几次，而不是只做一次（见[一次运行证明不了什么](6-4-variance.html)）。再说，十个问题本来就只能显示出很大的差别。如果只靠搜索得分也差不多，就不要建知识库。

## 要花什么，又会在哪里出错 {#costs-and-traps}

就算测试说值得建，知识库也不会自己一直保持正确。它需要维护，因为没人更新的知识库会变得自信满满地答错。如果你的代码天天在变，又没人愿意负责更新，搜索是更好的选择。

就算卡片是最新的，它也可能是错的，毕竟它是模型对代码的理解。检查只能抓住结构，抓不住一条规则理解得对不对，这部分要靠人审查，或者靠独立的 reviewer（[模型能检查模型吗](5-6-model-checks-model.html)）。而且 agent 是先读卡片的，所以卡片可能把它锚住：它可能少看一些代码，沿用一张错卡片的看法。对出错代价高的工作，让它重读卡片引用的那几行。

agent 每读一张卡片都要花 token，所以太长的知识库只是把成本挪了个地方。卡片要短，agent 只在需要时才往下打开更低的层。

前面说的都是维护和使用的成本，建的那一次还要另算：模型要把每个对象的代码读一遍，所以对大的领域来说，建一次就是真金白银，押的是这些读过的东西会被反复用到。粗略的规模是每个对象读一遍，再加上每月变动的文件，不过我没有算过价。prompt 缓存也许能同时降低建库和读取的成本。Anthropic 的文档说缓存读取约为基础价格的十分之一（见[选模型：看每次成功的成本](1-1-models-and-cost.html)），不过我没有在 Copilot 上核实过。所以测试时要把它打开，就像你真正运行时那样。

最后要定的是谁来负责。知识库得有人管。卡片又是对内部代码的摘要，所以也需要和代码一样的访问规则。谁来更新、谁能读，要定下来。

## 什么时候删掉卡片，留下什么 {#when-to-delete-it}

如果你自己的测试表明，只靠搜索就能以同样的成本给出同样的答案，那就把卡片删掉，只留下请求清单，因为这是搜索永远给不了的部分。如果哪天平台能构建并更新一份代码索引，而且你测得出它是准确的，就改用它，别再自己维护一份。

## 在你自己的环境里试试 {#try-it}

::: prompt
判断这个仓库是否能从一份写下来的代码知识库中受益，还是搜索就够了。估算它有多少个对象（模块、任务、表、服务），代码库有多大。指出哪些种类的事实根本不在代码里，比如哪个环境运行某个任务、某条规则为什么存在。说明代码多久变动一次。然后给出结论：搜索就够，或者值得测试一份知识库，并给出理由。不要修改任何文件。
:::
