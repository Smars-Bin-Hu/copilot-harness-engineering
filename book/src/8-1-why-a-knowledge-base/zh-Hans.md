这一章是案例研究的第一章。读它之前，你需要读过[上下文是一份预算](3-1-context-budget.html)和[agent 该记住什么](3-5-memory.html)，它们讲的是一般的思路。它适合有一大份老代码的团队。如果你的代码很小，读它是为了判断自己不需要。最有用的部分，是[在你自己的环境里测一测](#test)里那个小实验：什么都还没建，你就可以先跑。

## 一句话 {#in-one-sentence}

代码才是真相。知识库只是它的索引和摘要，读起来应该更便宜。它不求第一天就完整，只求诚实：每张卡片都写明它读的是源文件的哪个版本，每个缺口都写在下一个读者看得到的地方。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要不要出钱做知识库（一个文件夹，里面是写给 agent 看的代码短笔记），以及由谁负责。先测一下，只搜索代码是不是已经够用。
- **风险**：代码库很大、同样的探索每个会话都要再付一次、或者答错代价很高的时候，搜索就开始吃力。我没有拿知识库和单纯搜索比过，所以这是一次押注，不是已经证明的收益。没人更新的知识库，会变得自信满满地答错。
- **做对的代价**：模型要把每个对象的代码读一遍；对大的领域，这是真金白银，我没有算过价。要有人负责更新，笔记也需要和代码一样的访问规则。
- **可以问团队**：“十个我们知道答案的问题，只用单纯搜索的 agent 能答对几个？”

## 问题 {#problem}

假设一个团队有一份几千个对象的代码库。**对象**是代码里有名字、被别的东西使用的东西：存储过程、定时任务、类、表。你让 agent 改其中一个。要改得安全，agent 得知道这个对象是干什么的、谁在用它、改了会弄坏什么。

新开的 agent 会话，这些一概不知道。第一个问题显而易见。

### 为什么不直接让 agent 搜索代码？

agent 会搜索。它能运行 `grep`（找出每一行含有某个词的地方）、打开文件、顺着名字追。很多活这就是正确答案，而且不用任何配置。我想先说清楚它什么时候就够了。搜索也不必是单纯的 `grep`：语言服务器（回答“这个在哪里定义、谁在用”的编辑器服务）或代码搜索服务都能帮忙，一页简短而好的规则也有用。知识库要赢的是这一整套，不是单纯的 `grep`。

**搜索就够的时候**：

- 代码库很小，或者你要的那一块装得进一个上下文。
- 你知道要找的东西叫什么。
- 任务只做一次，没人会为同样的探索付两次钱。

**开始吃力的时候**：

- **agent 根据刚读到的东西，决定下一步读什么**。它可能漏掉一个对象，追到一个重名但意思不同的东西，太早停下来。它说不出自己漏了多少。问它两次，可能得到两个不同的答案。
- **同样的探索，每个会话都要付一次**。每个新会话都从空的上下文开始（[上下文是一份预算](3-1-context-budget.html)），所以 agent 又会把同样的东西找一遍。
- **有些事不在代码里**。哪个环境运行某个任务、某条规则为什么存在、去年出了什么故障。搜索找不到，因为那里没写。
- **答错代价很高**。如果对象碰到共用的数据，靠不完整的搜索猜出来的答案是不够的。

**知识库**是一个文件夹，里面是关于代码的纯文本文件，写给 agent 读。思路是：探索只付一次钱，把结果留下来，并且先读结果，因为它应该比读代码便宜。这一点我没有量过。

**我没有拿它和搜索比较过**。我没有把同样的问题，一次用单纯搜索、一次用知识库跑过，所以我不知道第二种赢多少，甚至赢不赢。我有的，是上面的推理，以及一个让你在自己的代码上测试的办法（见[在你自己的环境里测一测](#test)）。把知识库看成一次押注：满足上面那些条件才会有回报，不是已经证明的收益。

## 原理 {#how-it-works}

### 知识库的形状

读者只往下走到任务需要的深度。

::: figure 8-1-kb-layers

- **总览**列出**领域**，并有一份词汇表。领域是为同一项工作服务的一组对象，例如“订单”或“薪资”。
- 一个领域的**架构页**写明这个领域是干什么的、主要的流程、从哪里开始读、它的坑和它的限制。
- **卡片**是关于一个对象的简短条目：它的用途、它的规则、它用到谁、它的坑。每条规则都引用它所依据的代码行。一个文件放一种类型的卡片。agent 顺着往下走来找卡片：总览，再到领域的页面，再按 id 找到卡片。
- **代码**在最底下。它是真相的来源。卡片和代码不一致时，以代码为准。

所以卡片是一份带日期的承诺，不是代码的替代品。agent 需要更多时，就去读代码。

### 脚本管结构，模型管含义

写一张卡片有两种活，它们不一样。

- **结构**只有一个正确答案：有哪些对象、谁用谁（合起来就是代码的**地图**）、按什么顺序去学、一张卡片列出的关系对不对。脚本能算出来。它每次给同样的答案，也不花 token。让模型来做，它会凭判断在代码里走，可能漏东西。
- **含义**没有唯一的答案：一个对象是干什么的、它的规则是什么、哪个坑会绊倒人。只有模型读了代码才写得出来。

这一部分后面的内容都由这个分工推出来。[toolkit](8-2-kb-toolkit.html)讲脚本怎么画地图。[审计](8-3-kb-audit.html)衡量这张地图。[分批学一个领域](8-4-kb-learning.html)是模型写下含义的地方，脚本检查它能检查的部分。[让知识库一直是对的](8-5-kb-keep-true.html)讲代码改了以后怎么办。

### 求诚实，不求完整

我的猜测是，知识库的大部分内容可以从代码里得到。这是猜测，不是测量。其余的得不到：什么在哪个环境里运行、出过什么故障、原因是什么、谁做了什么决定。这部分要靠时间积累，来自做完的任务、根因报告、人导出的东西。所以知识库第一天不可能完成；假装它完成了只会更糟，因为一个看起来完整的知识库会被人相信。

两个习惯让它保持诚实：

1. **每张卡片都写明它读的是源文件的哪个版本**。它记录一个 commit（代码的一个已保存版本，用一个叫 sha 的短 id 命名）。脚本还维护一份**对象索引**：每个对象一行，写明它在哪个源文件里，以及那个文件的 sha。这样你以后就能列出代码已经改过、卡片还没跟上的那些卡片。[第 8.5 章](8-5-kb-keep-true.html)讲怎么做。
2. **每个缺口都写下来**。代码说不清的事，进入一张**请求清单**：每件需要人提供的东西一行，写明它是哪一类，以及一种只读的获取办法。agent 在下一个停靠点提出这些请求，绝不在干活到一半时提。[第 8.5 章](8-5-kb-keep-true.html)有细节。

### 每一步都是一个由人审批的任务

建知识库不是一个大 prompt。每一步都是一个任务（见[管任务，不管对话](5-1-tasks.html)），计划由人审批，写回也由人审批（写回是把做完的工作复制进知识库；见[两道门：人在哪里审批](5-3-two-approvals.html)）。脚本检查能检查的部分：文件的格式、关系、引用的行。我也不让 agent 连接线上环境。只有环境才知道的事，由人去运行、再交给它。

### 路线

1. 搭一个 toolkit，每个代码库一次（8.2）。
2. 计算地图，每次使用之前（8.2）。
3. 审计地图（8.3）。
4. 把代码切成领域，一次（8.4）。
5. 分批学每个领域（8.4）。
6. 写架构页（8.4）。
7. 让它一直是对的：更新、捕获、请求（8.5）。

### 在你自己的环境里测一测 {#test}

在建任何东西之前，先弄清楚你需不需要它。

1. 写 10 个关于你的代码的问题，正确答案你是知道的。种类要混着来：“什么调用了 X？”“如果 Y 改了会怎样？”“为什么 Z 跳过了这种情况？”
2. 每个问题在新对话里问 agent，只用单纯搜索。对照你已知的答案，每个回答判对或错。
3. 手工或让 agent 帮忙，给一个小领域写卡片。有了卡片，在新对话里再问同样的问题。
4. 比较：答对的个数、用量（你的工具为一次运行显示的 token 数）、时间。

两点提醒。提问的形式要让一个文件回答不了，比如“如果 Y 改了，什么会坏？”，而且让没读过卡片的人来选题。十个问题只能显示出很大的差别。

每种条件都要做几次，不要只做一次，因为 agent 不会把同一件事做两次一样（见[一次运行证明不了什么](6-4-variance.html)）。如果只靠搜索得分差不多，就不要建知识库。

## 代价和坑 {#costs-and-traps}

- **它需要维护**。没人更新的知识库，会变得自信满满地答错。如果你的代码天天在变、又没人负责更新，搜索是更好的选择。
- **卡片可能是错的**。它是模型对代码的理解。检查只能抓住结构，抓不住一条规则理解得对不对。这部分要靠人审查，或者靠独立的 reviewer（[模型能检查模型吗](5-6-model-checks-model.html)）。
- **卡片可能把 agent 锚住**。先读卡片的 agent，可能少看一些代码，还沿用一张错卡片的看法。对出错代价高的工作，让它重读卡片引用的那几行。
- **读卡片也要花 token**。太长的知识库只是把成本挪了个地方。卡片要短，agent 只在需要时才往下打开更低的层。
- **建知识库有成本**。模型要把每个对象的代码读一遍。对大的领域，这是真金白银。这是押注读的结果会被反复用到。粗略的规模：每个对象读一遍，加上每月变动的文件。我没有算过价。prompt 缓存（Anthropic 的文档说缓存读取约为基础价格的十分之一；我没有在 Copilot 上核实过；见[选模型：看每次成功的成本](1-1-models-and-cost.html)）也许能同时降低建库和读取的成本，所以测试时要打开它，就像你真正运行时那样。
- **要有人负责，卡片需要和代码一样的访问规则**。卡片是对内部代码的摘要。像对代码一样，决定谁来更新、谁能读。

## 什么时候可以删掉 {#when-to-delete-it}

如果你自己的测试表明，只靠搜索就能以同样的成本给出同样的答案，就把卡片删掉，只留下请求清单，因为这是搜索永远给不了的部分。如果哪天平台能构建并更新一份代码索引，而且你测得出它是准确的，就用它，别再自己维护一份。
