這一章假設你用過 AI 寫程式的 agent，也讀過[上下文是一份預算](3-1-context-budget.html)（agent 讀的所有東西共用一個大小有限的視窗）。

## 一句話 {#in-one-sentence}

預設只載入最少的規則，其餘的等需要時才讀。skill 是一本按需要才讀的手冊，和任何寫下來的規則一樣，它不會被強制執行。

## 給主管 {#for-leaders}

- **要做的決定**：讓一直載入的規則保持很少，並決定誰負責規則檔、誰去剪掉不再需要的內容。
- **風險**：長的規則檔比短的更不容易被遵守，兩個檔案說法不一致時，模型會挑其中一個。就算寫進了檔案，規則也只是一個請求，模型可能不照做，所以一定要成立的事，要放進程式碼。我手上沒有可以引用的、規則被無視的實測案例。
- **做對的成本**：一個負責人，加上定期修剪規則檔。剪掉 agent 本來就會做對的那些行，成本很低；在我自己的檔案裡，這樣剪過之後通常沒看到什麼變差，不過我沒有系統地測過。
- **可以問團隊**：「我們一直載入的檔案裡，哪幾行是 agent 沒有它們就會做錯的？誰負責那個檔案？」

## 規則檔為什麼越長越不管用？ {#problem}

想讓 agent 認識你的專案，最自然的辦法是把一切都寫進一個檔案，規則、慣例、警告，還有每種工作的做法。agent 每犯一次錯，你就加一行。幾個星期下來，檔案已經很長了，agent 卻反而不如檔案還短的時候守得好。

規則多了，怎麼反倒守得更差？檔案變長以後，有兩件事會出問題，而只有第二件和「守不守」有關。

第一，檔案裡的所有東西，每一輪都要付錢。這個檔案一直待在視窗裡，不管手上這份工作用不用得到，所以你在改一個錯字的時候，一條講資料庫遷移的規則也照樣佔著位子。它佔的就是[上下文是一份預算](3-1-context-budget.html)講的那份預算，至於每一輪要花多少，在[選模型：算的是每次成功的成本](1-1-models-and-cost.html)。

第二，規則越多，每一條被遵守的程度就越低。在一個長檔案裡，規則會互相競爭，兩行之間可能互相矛盾，要緊的一行也可能淹沒在一堆小事裡。平台自己的文件也是這個意思。Claude Code 和 VS Code 的文件都建議讓指令檔保持簡短，Claude Code 的文件還提醒，兩條指令互相矛盾時，模型可能隨意挑一條。

那麼出路在哪裡？就是別把所有東西一下子都擺到 agent 面前，先給它看一點，等它需要更多時再讓它去讀。這個想法叫**漸進式揭露**（progressive disclosure），就像一家店把菜單放在門口，完整的食譜留在廚房裡。Anthropic 稱它是「讓 Agent Skills 靈活、可擴展的核心設計原則」（[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）。

把這個想法落實的，是兩種檔案。**指令**是寫給 agent 讀的規則檔，有些在每個對話裡都載入，有些只在 agent 處理特定檔案時才載入。**skill** 是一個資料夾，裡面放著某一類工作的手冊，agent 要等這份工作真的來了才去讀，不會事先讀。

有了這兩種檔案，對每條規則要做的第一個選擇，就是把它放在哪裡。（下面給的是推理和檢查的辦法，因為我手上沒有可以引用的、規則被無視的實測案例。）

## 每條規則該放在哪裡，為什麼還是會被無視 {#how-it-works}

### 1. 規則的三個位置

規則放在哪裡，決定了它什麼時候佔位子，也決定了 agent 什麼時候看得到它。

::: figure 3-3-places

第一個位置上的規則一直載入。它們寫在倉庫根目錄一個簡短的檔案裡，每個對話都會讀，所以只有每份工作都需要的規則才放這裡，例如安全限制、怎麼開始、被拒絕時該怎麼辦。在我的設定裡，這個檔案只有短短一頁。如果一條規則十份工作裡只有一份需要，它就不該放在這裡。

只適用於某一類檔案的規則，放在第二個位置，依檔案載入。在 VS Code 裡，指令檔有一行檔頭 `applyTo`，寫著像「這個資料夾底下所有檔案」這樣的模式。只有 agent 打開了符合的檔案，這些規則才會載入。例如怎麼寫 skill 的規則，要等 agent 打開 skill 檔案時才載入，它去編輯 pipeline 時，這些規則一點位子也不佔。下面是這樣一個檔案的開頭：

::: code harness .github/instructions/skills.instructions.md L1-L4 "只在處理 skill 檔案時載入的指令檔：applyTo 那一行就是模式。"

其餘的一切都按需要才讀，包括很長的做法說明和很少用到的細節。skill 和參考筆記就放在這裡，工作需要時，agent 才去讀。

還有第四種方式。**hook**（平台在固定時刻執行的小程式，見 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）可以在你送出的每則訊息最前面加上幾行，讓一條規則在用得到它的地方附近再出現一次。不過只能放幾行，不然你又把那個長檔案蓋回來了。

有了這幾個位置，對每一條規則要問的就是同一個問題：**這條多常需要？agent 漏掉了會怎樣**？每次都需要、漏掉代價又高的，一直載入；只有某一類檔案需要的，依檔案載入；只有某一份工作需要的，放進 skill。

最後這個位置值得多看幾眼，因為 skill 並不是一次讀完的。

### 2. skill 分三層載入

skill 是一個資料夾，主檔案 `SKILL.md` 有一段檔頭（名稱和描述）和一段正文（手冊），旁邊還可以放更長的筆記、腳本和範本。

::: figure 3-3-three-layers

agent 不會一次看到全部。

1. 每個 skill 的名稱和描述，它一直都看得到。這就是菜單。菜單很小，但每一輪都要付錢，你裝了多少個 skill，就要付多少份。
2. 請求符合某個描述時，它才讀整本手冊。這是 agent 自己決定的，或者由你直接輸入 skill 的名稱。
3. 只有手冊指向時，它才去讀額外的檔案，所以很長的參考資料或腳本，要等到需要它的那一步才讀。

這樣一來，你可以裝很多 skill，而不會塞滿視窗。

這也表示，在第 1 層，agent 手上只有描述可以依據，所以**描述決定了 skill 到底找不找得到**。含糊的描述（例如「幫助提升程式碼品質」）永遠對不上任何東西。好的描述要說清三件事：這個 skill 做什麼、什麼時候用（「use when……」），以及人真的需要它時會用的那些說法。長度也要留意，平台對它有限制，而囉嗦的描述還會佔掉其他每個 skill 的位子。

不過，就算描述寫得很好，也不保證 skill 會被用上。VS Code 的文件說得很明白，發現機制只是讓 skill 可以被用到，並不保證模型會用某一個，所以值得測一測（測試的辦法在這一節最後）。

還有一點，菜單本身也可能變得太長。有了幾十個 skill，菜單就成了一筆實實在在的成本，而其中很多 skill 從來不會被選到。一個辦法是，任務還沒碰到某個業務領域時，先別把這個領域的 skill 放進菜單。

### 3. 一條規則，一個來源

規則一旦分散到幾個地方，同一條規則就很容易寫進三個檔案。這樣一來，改的時候總會漏掉一個，agent 讀到的就是三個慢慢分歧的版本。所以一條規則只寫在一個地方，其他地方只放一個連結和一句話。要是發現一條規則得到處重述，那就說明結構錯了。規則檔也是共用的程式碼，所以要給它們一個負責人，由他剪掉不再需要的行。

### 4. 寫下來的規則為什麼會被無視

規則明明載入了，agent 為什麼還是不理它？載入了不等於就會被遵守，常見的原因有五種。前四種出在文字本身和它放的位置上：

1. 檔案太長。對每一行都問一句，沒有它，agent 會做錯嗎？不會，就刪掉這一行。
2. 規則互相衝突。兩個檔案說的不同，模型會挑一個，而且不一定是你要的那個。VS Code 的文件說，指令的來源是疊加的，不要靠檔案的順序來解決衝突，所以消除衝突是你自己的工作。把它們搜尋出來，改好措辭，直到只留下一個版本。
3. 規則離適用的地方很遠。它在第一則訊息裡，現在已經是幾千行以前的事了。依檔案載入的規則，或者 hook 的提醒，可以讓它離得近一點。
4. 它沒有理由。「絕對不要做 X」很容易被找個理由繞過去，「絕對不要做 X，因為 Y 會壞掉」，卻能讓模型把這個想法用在你沒列出來的情況上。

第五種原因最根本，改文字、換位置都解決不了：規則只是請求。你寫在檔案裡的任何東西，都只是給模型讀的，而模型可以不照做。Claude Code 的文件說得很直白，memory 檔是「上下文，不是強制執行的設定」，不管模型怎麼決定，想擋掉某個動作，文件給的辦法是 hook。skill 的文字也一樣，它能讓工作進行得順利，卻不能讓錯事無從發生。

所以一條必須成立的規則，要放進程式碼。怎麼做這個選擇，是[提示裡的規則只是請求](4-1-requests-and-rules.html)的主題。有了程式碼，文字只需要解釋為什麼，免得 agent 再試著繞過那個拒絕。在我的設定裡，要緊的規則有兩層，文字負責教，程式碼負責擋。

那 skill 的檔頭能不能改變這一點？有些平台允許檔頭帶上更強的設定，這時要去查清楚它們到底做什麼。例如在 Claude Code 裡，`allowed-tools` 只是預先批准工具，並不限制工具。skill 還可以註冊 hook，而 hook 是程式碼（[Skills](https://code.claude.com/docs/en/skills)）。

### 5. 還有一個選擇：語言

「一個來源」的道理，也能回答一個只有在你用不止一種語言工作時才會遇到的問題。我的做法是只留一份規則和 skill，用英文寫，再告訴模型用哪種語言回答，因為第二份文字會慢慢和第一份對不上。這是我自己的選擇，原則只有一條：只留一份。

### 三個問題，三個測試

加一條規則之前，先問它三個問題：

1. 這條多常需要？很少的話，就不放進一直載入的檔案。
2. 別處已經寫過了嗎？有的話，連過去。
3. agent 無視它會怎樣？答案如果是「很糟、而且無法挽回的事」，那就不是靠文字能解決的事。

有一個測試今天就能做，不用額外設定。把你一直載入的檔案從頭看一遍，每一行都問，沒有它，agent 會做錯嗎？把不通過的行都剪掉，再跑一次和之前一樣的任務，看有沒有什麼變差。我從自己的規則檔剪掉一些行時，通常沒看到什麼變差，不過我沒有系統地測過。

要測 skill 找不找得到，先把請求寫好。請求要用人平常會說的話，而不是描述裡的用語：三種要求這份工作的說法，再加兩個相鄰、不該觸發它的請求。

寫好以後，每一個請求都開一個新的對話，因為舊的對話可能已經載入了這個 skill，也不要輸入 skill 的名稱。然後看哪些 skill 被載入了。平台有紀錄的話就看紀錄，因為 agent 自己說的不算證據。沒載入，說明描述裡缺少使用者的用語；不該載入時卻載入了，說明描述太寬。

skill 有沒有改變什麼，是另一個測試。同一個任務在新的對話裡跑兩次，有 skill 和沒有 skill 各一次。看不出差別的話，就剪掉那些沒有差別的行。agent 本來就知道它們。

## 少載入要付出什麼 {#costs-and-traps}

把規則拆開能省位子，那要付出什麼？skill 裡的規則，只有 skill 被找到時才會被讀，所以一條要緊的規則，要是放進了一個描述很弱的 skill，可能永遠不會被讀到。這就是省位子的代價。所以，漏掉一條規則的代價要是很高，它就該留在會載入的地方。

而且找不找得到，也不是一次就定下來的。skill 不是一項設定，而是模型每次都要重新做的選擇，所以同一個請求，這次可能載入它，下次就未必。skill 越多，在它們之間挑就越難，因為就算描述寫得好，也可能和相鄰的 skill 搞混。所以每一個 skill 的範圍都要窄，並寫明它不是做什麼的。

用 hook 往訊息裡注入文字，也就是第四種方式，同樣有自己的陷阱：這些行會越積越多，因為每一行都會在每則訊息裡重複一次。一直載入的那個檔案也有類似的上限：Claude Code 的文件建議它低於約 200 行，不過那只是經驗法則，不是量出來的限制，你得量量自己的。

## 平台也這麼看嗎？ {#industry}
{status: industry}

VS Code 對 skill 也是三層載入。它先讀名稱和描述，「skill 相關時」才載入正文，其他檔案「只有在被引用時」才讀。它還說，發現機制「不保證每個相關的 prompt 都會呼叫某個 skill」。對於指令檔，它建議「讓你的指令簡短而獨立」「附上規則背後的理由」，並說來源是「疊加的」。（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)、[Custom instructions](https://code.visualstudio.com/docs/copilot/customization/custom-instructions)）

Anthropic 為 Agent Skills 描述的也是這三層，先是名稱和描述，skill 適用時載入正文，連結的檔案只在需要時才載入（[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）。Claude Code 建議每個 memory 檔保持在 200 行以下，把屬於程式碼某一部分的規則移到只在路徑符合時才載入的檔案，並移除矛盾。它把這些檔案當成「上下文，不是強制執行的設定」（[How Claude remembers your project](https://code.claude.com/docs/en/memory)）。

可見兩個平台用的是同一種結構，一直載入的檔案、依路徑載入的規則、按需要才讀的 skill。既然各個工具的想法都一樣，你在這裡做的東西也就可以帶著走。

## 哪些手動的部分可以刪，哪些會留下 {#when-to-delete-it}
{status: industry}

這一章裡有兩件事是靠手動做的：只列出目前領域的 skill，以及剪短過長的菜單。這兩件都是平台以後可能接手的工作。如果平台學會更好地按相關性載入 skill，按領域篩選的辦法就可以不用了。

不過這套道理不會過時。視窗變大，並不會讓長的規則檔變好，它只是讓你在問題出現之前能多放一些。何況沒有任何載入方式，能讓寫下來的規則變成強制執行。如果有平台能在我自己的任務上證明，長的規則檔和短的守得一樣好，我會重新檢視一次。
