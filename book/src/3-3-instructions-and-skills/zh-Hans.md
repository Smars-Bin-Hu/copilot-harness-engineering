读这一章，需要你用过 AI 编程 agent，并且读过[上下文是一份预算](3-1-context-budget.html)（agent 读到的所有东西共用一个大小有限的窗口）。

## 一句话 {#in-one-sentence}

默认只加载最少的规则，其余的需要时再读。skill 是按需阅读的手册，和任何写下来的规则一样，它不是强制执行的。

## 写给管理者 {#for-leaders}

- **要拍板的事**：始终加载的规则要少，并决定谁负责规则文件、谁来删掉不再需要的内容。
- **风险**：长的规则文件，agent 遵守得不如短的好；两个文件说法不一致，模型会挑其中一个。写在文件里的规则仍然只是请求：模型可以不照做。必须成立的事要写进代码。我没有实测过的“规则被无视”的案例可以引用。
- **做对的代价**：一个负责人，加上定期精简规则文件。删掉 agent 本来就会做对的那些行，代价很小；在我自己的文件里，我一般没看到有什么变差，但我没有系统地测过。
- **可以问团队**：“我们始终加载的文件里，哪些行是去掉之后 agent 就会做错的？这个文件归谁管？”

## 问题 {#problem}

教 agent 了解你的项目，最自然的办法是把所有东西写进一个文件：规则、约定、警告，以及每种工作的做法。agent 每犯一次错，你就加一行。几周之后文件变得很长，agent 遵守它的程度反而不如以前文件短的时候。

出了两个问题。它们是这一章的主题。

- **每一轮都要为所有内容付费。** 这个文件一直放在窗口里，不管这项工作需不需要它。你在改一个错别字，一条关于数据库迁移的规则也在占着地方。这个地方就是[上下文是一份预算](3-1-context-budget.html)讲的那份预算；每一轮要花多少，在[选模型：看每次成功的成本](1-1-models-and-cost.html)里。
- **规则越多，每条规则被遵守得越差。** 长文件会让规则互相竞争。两行可能互相矛盾；重要的一行淹没在细小的几行里。Claude Code 和 VS Code 的文档都建议把指令文件写短，Claude Code 的文档还警告说，两条指令互相矛盾时，模型可能会随便挑一条。

先说三个词。

- **指令**是写给 agent 读的规则文件。有的在每次对话里都加载。有的只在 agent 处理某些文件时才加载。
- **skill** 是一个文件夹，里面有针对某一类工作的手册。agent 在这项工作出现时才读手册，不会提前读。
- **渐进式披露**是这两者背后的思路：先给 agent 看一点，需要更多时再让它去读。就像一家店，门口放菜单，完整的菜谱在厨房里。Anthropic 称它是“让 Agent Skills 灵活、可扩展的核心设计原则”（[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）。

我没有实测过的“规则被无视”的案例可以引用，所以这一章讲的是推理和检查的办法。

## 原理 {#how-it-works}

### 1. 规则的三个存放位置

规则放在哪里，决定了它什么时候占地方，以及 agent 什么时候看得到它。

::: figure 3-3-places

- **始终加载。** 仓库根目录里的一个简短文件，每次对话都会读。只有每项工作都需要的规则才放这里：安全底线、怎么开始、被拒绝时该怎么办。在我的配置里，这只有短短一页。如果一条规则十项工作里只有一项要用，它就不属于这里。
- **按文件加载。** 只适用于某一类文件的规则。在 VS Code 里，指令文件的头部有一行 `applyTo`，写一个模式，比如“这个文件夹下的所有文件”。只有 agent 打开匹配的文件时，这些规则才会加载。怎么写 skill 的规则，在它打开 skill 文件时加载；它改 pipeline 时，一点代价也没有。下面是这样一个文件的开头：

::: code harness .github/instructions/skills.instructions.md L1-L4 "一个只对 skill 文件加载的指令文件：applyTo 那一行就是匹配模式。"
- **按需阅读。** 其余的一切：长的操作指南、很少用到的细节。skill 和参考笔记就放在这里。工作需要时，agent 才去读。

还有第四种办法：**hook**（平台在固定时刻运行的小程序，见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)）可以在你发的每条消息的开头加上几行，在用到规则的地方附近重复一下它。只加几行，不然又变回了那个长文件。

对每条规则，要问的问题是：**这条规则多久用一次？agent 漏掉它会怎样？** 每次都要用、漏掉代价大：始终加载。只有某一类文件要用：按文件加载。只有某项工作要用：放进 skill。

### 2. skill 分三级加载

skill 是一个文件夹。主文件 `SKILL.md` 有头部（名字和描述）和正文（手册）。旁边可以放更长的笔记、脚本和模板。

::: figure 3-3-three-layers

agent 不会一次看到全部内容。

1. **始终在的，是每个 skill 的名字和描述。** 这是菜单。它不大，但每一轮都要付费，你装了多少个 skill 就付多少份。
2. **需求对得上某个描述时，才读整份手册。** 这由 agent 自己决定，或者你直接输入 skill 的名字。
3. **只有手册指到时，才读额外的文件。** 长的参考资料或脚本，要等到用得上它的那一步才读。

所以你可以装很多 skill，而不会把窗口填满。

**描述决定这个 skill 能不能被找到。** 在第 1 级，agent 手上只有描述。含糊的描述（“帮助提升代码质量”）什么也匹配不上。好的描述要说三件事：这个 skill 做什么，什么时候用（“在……时使用”），以及人真正需要它时会说的那些话。平台对长度有限制，啰嗦的描述还会占掉其他所有 skill 的地方。

即使描述写得好，也不保证会被用上。VS Code 的文档明说，发现机制只是让 skill 可用，并不保证模型会用。所以要测一下（见下面）。

**菜单也会太长。** 有几十个 skill 时，菜单就是一笔实实在在的开销，而且很多 skill 永远不会被选中。一种办法是：任务不涉及某个业务领域时，不把这个领域的 skill 放进菜单。

### 3. 一条规则，一个来源

同一条规则如果写在三个文件里，改的时候总会漏掉一个，agent 读到的是三个慢慢变得不一样的版本。一条规则只写在一个地方。别处只放一个链接和一句话。一条规则如果得到处重复，说明结构不对。规则文件是共用的代码，所以要有人负责，把不再需要的行删掉。

### 4. 写下来的规则为什么会被无视

规则可能已经加载了，却没被遵守。常见的原因：

1. **文件太长。** 对每一行问：没有它，agent 会做错吗？不会，就删掉这一行。
2. **规则冲突。** 两个文件说的不一样。模型挑一个，而且不一定是你想要的那个。VS Code 的文档说，各个指令来源是叠加的，不要靠文件顺序来解决冲突。所以消除冲突是你的活：去搜，改措辞，让只剩一个版本。
3. **规则离用到它的地方太远。** 它在第一条消息里，现在已经在几千行之前。按文件加载的规则，或者 hook 的提醒，能让它离得近一点。
4. **没写理由。** “绝对不要做 X”很容易被绕过去。“绝对不要做 X，因为 Y 会坏掉”，则能让模型把这个道理用到你没列出的情况上。
5. **它是请求。** 这是最根本的原因。你写在文件里的任何东西，都是模型去读的，而模型可以不照做。Claude Code 的文档说得很直白：记忆文件是“上下文，不是强制执行的配置”，想不管模型怎么决定都拦住某个动作，就用 hook。skill 的正文也一样。它让工作顺畅，但不会让错事无法发生。在有的平台上，skill 的头部可以带更强的设置，要查一下它们到底做什么。比如在 Claude Code 里，`allowed-tools` 只是预先批准工具，并不限制工具，而且 skill 可以注册 hook，那是代码（[Skills](https://code.claude.com/docs/en/skills)）。

对第 5 条，办法不是把措辞写得更好。必须成立的规则要写进代码。这个选择是[提示里的规则只是请求](4-1-requests-and-rules.html)的主题。到那时，文本只需要解释为什么，这样 agent 就不会再想办法绕过拒绝。在我的配置里，重要的规则两层都有：文本负责教，代码负责拦。

### 5. 再说一个选择：语言

如果你用不止一种语言工作，我的做法是规则和 skill 只留一份，用英文写，再告诉模型用哪种语言回答。散文的第二份副本会慢慢和第一份对不上。这是我的选择；原则只是只留一份。

### 检验你自己的配置

**对你添加的任何规则，问三个问题：**

1. 这条多久用一次？如果很少，它就不放进始终加载的文件。
2. 别处已经写过了吗？如果写过，就链接过去。
3. 如果 agent 无视它，会怎样？如果答案是“发生了无法撤销的坏事”，那就不是文本能解决的事。

**今天就能做的测试，不需要额外配置。** 看你那份始终加载的文件。对每一行，问：没有它，agent 会做错吗？把不满足的行都删掉。然后跑和之前一样的任务，看有没有变差。我从自己的规则文件里删过行，一般没看到有什么变差。我没有系统地测过。

**测试 skill 能不能被找到。** 先把请求写好，用人真正会说的话，而不是描述里的话：三种提出这项工作的说法，再加两个相邻的、不该触发它的请求。每个请求开一个新对话（旧对话里可能已经带着这个 skill），并且不要输入 skill 的名字。然后看加载了哪些 skill。如果平台有日志，就用日志，因为 agent 自己怎么说不算证据。如果没加载，说明描述里缺用户会说的词。如果不该加载时加载了，说明描述太宽。

**测试 skill 有没有改变什么。** 同一个任务，在新对话里各跑一次，一次带 skill，一次不带。如果看不出区别，就把没起作用的行删掉。agent 本来就知道它们。

## 代价和坑 {#costs-and-traps}

**拆分是有代价的。** skill 里的规则，只有 skill 被找到才会被读到。一条重要的规则，如果放在描述很弱的 skill 里，可能永远不会被读到。这就是省地方的代价。如果漏掉的代价很高，就放在会加载的地方。

**skill 不是设置。** 它依赖模型选中它。同一个请求，这次可能加载它，下次就不加载了。

**skill 越多，选择越难。** 即使描述写得好，也可能和相邻的 skill 混淆。每个都要写得窄，并说清它不是干什么的。

**注入文本的 hook 会累积。** 每一行在每条消息里都会重复。Claude Code 的文档建议一个项目文件不超过 200 行左右；这是经验法则，不是量出来的上限。要量你自己的。

## 业界怎么说 {#industry}
{status: industry}

- **VS Code** 对 skill 有三级加载：先读名字和描述，“一旦这个 skill 相关”才加载正文，其他文件“只有被引用时”才读。它还说，发现机制“不保证对每个相关的 prompt 都调用 skill”。对于指令文件，它建议“让你的指令保持简短、自成一体”，“写明规则背后的理由”，并说各个来源是“叠加”的。（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)、[Custom instructions](https://code.visualstudio.com/docs/copilot/customization/custom-instructions)）
- **Anthropic** 对 Agent Skills 描述了同样的三级：先是名字和描述，skill 适用时再读正文，链接的文件只在需要时才读。（[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）
- **Claude Code** 建议每个记忆文件控制在 200 行以内，把只关系到部分代码的规则移到只对匹配路径加载的文件里，并去掉互相矛盾的地方。它把这些文件视为“上下文，不是强制执行的配置”。（[How Claude remembers your project](https://code.claude.com/docs/en/memory)）

两个平台用的是同一种结构：始终开启的文件、按路径划分的规则、按需的 skill。各个工具的思路是一样的，所以你在这里搭的东西可以带着走。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

平台可能接手的手动部分：只列出当前领域的 skill，以及削减过长的菜单。如果平台学会了更好地按相关性加载 skill，按领域取舍的办法就可以去掉。

这套道理不会过时。窗口更大，也不会让长的规则文件变好；它只是让你在问题冒出来之前能装更多。而且没有哪种加载方案能让写下来的规则变成强制执行的。如果有平台能在我自己的任务上证明，长的规则文件和短的一样被遵守，我会重新考虑。
