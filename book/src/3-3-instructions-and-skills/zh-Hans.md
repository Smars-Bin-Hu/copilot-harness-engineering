这一章假定你用过 AI 编程 agent，也读过[为什么不能把所有规则都塞给 Agent？](3-1-context-budget.html)（agent 读到的所有东西共用一个大小有限的窗口）。

## 一句话 {#in-one-sentence}

默认只加载最少的规则，其余的等需要时再读。skill 是一本按需阅读的手册，和任何写下来的规则一样，它不是强制执行的。

## 写给管理者 {#for-leaders}

- **要拍板的事**：始终加载的规则要少，并且定下谁负责规则文件、谁来删掉不再需要的内容。
- **风险**：长的规则文件不如短的被遵守得好，两个文件说法不一致时，模型会挑其中一个。就算写进了文件，规则也只是一个请求，模型可能不照做，所以必须成立的事要写进代码。我手上没有实测过的“规则被无视”的案例可以引用。
- **做对的代价**：一个负责人，加上定期精简规则文件。删掉 agent 本来就会做对的那些行，花不了多少；在我自己的文件里，这样删过之后一般没看到什么变差，不过我没有系统地测过。
- **可以问团队**：“我们始终加载的文件里，哪些行是去掉之后 agent 就会做错的？这个文件归谁管？”

## 规则文件为什么越长越不好使？ {#problem}

想让 agent 了解你的项目，最自然的办法是把所有东西都写进一个文件，规则、约定、警告，还有每种活儿的做法。agent 每犯一次错，你就加上一行。几周下来，文件已经很长了，agent 却反而不如文件短的时候守得好。

规则多了，怎么反倒守得更差？文件变长以后，有两件事会出问题，而只有第二件和“守不守”有关。

第一，文件里的所有内容，每一轮都要付费。这个文件一直待在窗口里，不管手头这项工作用不用得上，所以你在改一个错别字的时候，一条讲数据库迁移的规则也照样占着地方。它占的就是[为什么不能把所有规则都塞给 Agent？](3-1-context-budget.html)讲的那份预算，至于每一轮要花多少，在[选模型，别只看 token 单价](1-1-models-and-cost.html)里。

第二，规则越多，每一条被遵守得就越差。在一个长文件里，规则会互相竞争，两行之间可能说法矛盾，重要的一行也可能淹没在一堆细枝末节里。平台自己的文档也是这个意思。Claude Code 和 VS Code 的文档都建议把指令文件写短，Claude Code 的文档还提醒，两条指令互相矛盾时，模型可能随便挑一条。

那么出路在哪？就是别把所有东西一下子都摆到 agent 面前，先给它看一点，等它需要更多时再让它去读。这个思路叫**渐进式披露**，就像一家店把菜单放在门口，完整的菜谱留在厨房里。Anthropic 称它是“让 Agent Skills 灵活、可扩展的核心设计原则”（[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）。

把这个思路落到实处的，是两种文件。**指令**是写给 agent 读的规则文件，有的在每次对话里都加载，有的只在 agent 处理某些文件时才加载。**skill** 是一个文件夹，里面放着针对某一类工作的手册，agent 要等这项工作真的来了才去读，不会提前读。

有了这两种文件，对每条规则要做的第一个选择，就是把它放在哪里。（下面讲的是推理和检查的办法，因为我手上没有实测过的“规则被无视”的案例可以引用。）

## 每条规则该放在哪里，为什么还是会被无视 {#how-it-works}

### 1. 规则的三个存放位置

规则放在哪里，决定了它什么时候占地方，也决定了 agent 什么时候看得到它。

::: figure 3-3-places

第一个位置上的规则始终加载。它们写在仓库根目录的一个简短文件里，每次对话都会读，所以只有每项工作都需要的规则才放这里，比如安全底线、怎么开始、被拒绝时该怎么办。在我的配置里，这个文件只有短短一页。如果一条规则十项工作里只有一项要用，它就不该放在这里。

只适用于某一类文件的规则，放在第二个位置，按文件加载。在 VS Code 里，指令文件的头部有一行 `applyTo`，写着一个匹配模式，比如“这个文件夹下的所有文件”。只有 agent 打开了匹配的文件，这些规则才会加载。比如怎么写 skill 的规则，要等 agent 打开 skill 文件时才加载，它去改 pipeline 时，这些规则一点地方也不占。下面是这样一个文件的开头：

::: code harness .github/instructions/skills.instructions.md L1-L4 "一个只对 skill 文件加载的指令文件：applyTo 那一行就是匹配模式。"

其余的一切都按需阅读，包括长篇的操作指南和很少用到的细节。skill 和参考笔记就放在这里，工作需要时，agent 才去读。

还有第四种办法。**hook**（平台在固定时刻运行的小程序，见 [硬性规则放在哪？用 hook](2-2-hooks.html)）可以在你发的每条消息开头加上几行，让一条规则在用得着它的地方附近再出现一次。不过只能加几行，不然你又把那个长文件搭回来了。

有了这几个位置，对每条规则要问的就是同一个问题：**这条规则多久用一次？agent 漏掉它会怎样？** 每次都要用、漏掉代价又大的，始终加载；只有某一类文件要用的，按文件加载；只有某项工作要用的，放进 skill。

最后这个位置值得多看几眼，因为 skill 并不是一次读完的。

### 2. skill 分三级加载

skill 是一个文件夹，主文件 `SKILL.md` 有头部（名字和描述）和正文（手册），旁边还可以放更长的笔记、脚本和模板。

::: figure 3-3-three-layers

agent 不会一次看到全部内容。

1. 每个 skill 的名字和描述，它始终都看得到。这就是菜单。菜单不大，但每一轮都要付费，你装了多少个 skill，就付多少份。
2. 需求对得上某个描述时，它才读整份手册。这由 agent 自己决定，或者由你直接输入 skill 的名字。
3. 只有手册指到时，它才去读额外的文件，所以长的参考资料或脚本，要等到用得上的那一步才读。

这样一来，你可以装很多 skill，而不会把窗口填满。

这也意味着，在第 1 级，agent 手上只有描述可以依据，所以**描述决定了这个 skill 能不能被找到**。含糊的描述（比如“帮助提升代码质量”）什么也匹配不上。好的描述要说清三件事：这个 skill 做什么，什么时候用（“use when……”），以及人真正需要它时会说的那些话。长度也要留意，平台对它有限制，而啰嗦的描述还会占掉其他所有 skill 的地方。

不过，即使描述写得好，也不保证 skill 会被用上。VS Code 的文档说得很明白，发现机制只是让 skill 可用，并不保证模型会用，所以值得测一测（测试办法在这一节最后）。

还有一点，菜单本身也会变得太长。有了几十个 skill，菜单就成了一笔实实在在的开销，而其中很多 skill 从来不会被选中。一种办法是，任务不涉及某个业务领域时，就不把这个领域的 skill 放进菜单。

### 3. 一条规则，一个来源

规则一旦分散到几个地方，同一条规则就很容易写进三个文件。这样一来，改的时候总会漏掉一个，agent 读到的就是三个慢慢走样的版本。所以一条规则只写在一个地方，别处只放一个链接和一句话。要是发现一条规则得到处重复，那说明结构出了问题。规则文件也是共用的代码，所以要有人负责，把不再需要的行删掉。

### 4. 写下来的规则为什么会被无视

规则明明加载了，agent 为什么还是不理它？加载了不等于就会被遵守，常见的原因有五种。前四种出在文本本身和它放的位置上：

1. 文件太长。对每一行都问一句，没有它，agent 会做错吗？不会，就删掉这一行。
2. 规则冲突。两个文件说法不一样，模型会挑一个，而且不一定是你想要的那个。VS Code 的文档说，各个指令来源是叠加的，不要指望靠文件顺序来解决冲突，所以消除冲突是你自己的活儿。去把它们搜出来，改好措辞，直到只剩一个版本。
3. 规则离用到它的地方太远。它在第一条消息里，现在已经在几千行之前了。按文件加载的规则，或者 hook 的提醒，能让它离得近一点。
4. 没写理由。“绝对不要做 X”很容易被找个理由绕过去，“绝对不要做 X，因为 Y 会坏掉”，却能让模型把这个道理用到你没列出的情况上。

第五种原因最根本，改文本、挪位置都解决不了：规则只是请求。你写在文件里的任何东西，都只是给模型读的，而模型可以不照做。Claude Code 的文档说得很直白，记忆文件是“上下文，不是强制执行的配置”，想不管模型怎么决定都拦住某个动作，文档给的办法是 hook。skill 的正文也一样，它能让工作进行得顺畅，却不能让错事无法发生。

所以必须成立的规则，要写进代码。怎么做这个选择，是[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)的主题。有了代码，文本只需要解释为什么，这样 agent 就不会再想办法绕过拒绝。在我的配置里，重要的规则两层都有，文本负责教，代码负责拦。

那 skill 的头部能不能改变这一点？有的平台允许头部带上更强的设置，这时要查清楚它们到底做什么。比如在 Claude Code 里，`allowed-tools` 只是预先批准工具，并不限制工具。skill 还可以注册 hook，而 hook 是代码（[Skills](https://code.claude.com/docs/en/skills)）。

### 5. 再说一个选择：语言

“一个来源”的道理，也能回答一个只有在你用不止一种语言工作时才会碰到的问题。我的做法是，规则和 skill 只留一份，用英文写，再告诉模型用哪种语言回答，因为散文的第二份副本会慢慢和第一份对不上。这是我自己的选择，原则只有一条：只留一份。

### 三个问题，三个测试

添加一条规则之前，先问它三个问题：

1. 这条多久用一次？如果很少，它就不放进始终加载的文件。
2. 别处已经写过了吗？如果写过，就链接过去。
3. 如果 agent 无视它，会怎样？如果答案是“发生了无法撤销的坏事”，那就不是文本能解决的事。

有一个测试今天就能做，不需要额外配置。把你那份始终加载的文件过一遍，对每一行都问，没有它，agent 会做错吗？把通不过的行都删掉，再跑一遍和之前一样的任务，看有没有什么变差。我从自己的规则文件里删过行，一般没看到什么变差，不过我没有系统地测过。

要测 skill 能不能被找到，先把请求写好。请求要用人真正会说的话，而不是描述里的话：三种提出这项工作的说法，再加两个相邻的、不该触发它的请求。

写好以后，每个请求都开一个新对话，因为旧对话里可能已经带着这个 skill，也不要输入 skill 的名字。然后看加载了哪些 skill。平台有日志的话就看日志，因为 agent 自己怎么说不算证据。没加载，说明描述里缺了用户会说的词；不该加载时却加载了，说明描述太宽。

skill 有没有改变什么，是另一个测试。同一个任务在新对话里跑两次，一次带 skill，一次不带。如果看不出区别，就把那些不起作用的行删掉。agent 本来就知道它们。

## 少加载要付出什么 {#costs-and-traps}

把规则拆开能省地方，那要付出什么？skill 里的规则，只有 skill 被找到才会被读到，所以一条重要的规则，要是放进了一个描述很弱的 skill，可能永远都不会被读到。这就是省地方的代价。所以，漏掉一条规则的代价要是很高，它就该放在会加载的地方。

而且能不能被找到，也不是一次就定下来的。skill 不是一项设置，而是模型每次都要重新做的选择，所以同一个请求，这次可能加载它，下次就未必。skill 越多，在它们之间挑就越难，因为即使描述写得好，也可能和相邻的 skill 混淆。所以每个 skill 都要写得窄一点，并说清它不是干什么的。

第四种办法，也就是往消息里注入文本的 hook，也有自己的坑。这些行会越积越多，因为每一行在每条消息里都会重复一次。始终加载的那个文件也有类似的上限：Claude Code 的文档建议它不超过 200 行左右，不过这只是经验法则，不是量出来的上限，你得量量自己的。

## 平台也这么看吗？ {#industry}
{status: industry}

VS Code 对 skill 也是三级加载。它先读名字和描述，“一旦这个 skill 相关”才加载正文，其他文件“只有被引用时”才读。它还说，发现机制“不保证对每个相关的 prompt 都调用 skill”。对指令文件，它建议“让你的指令保持简短、自成一体”，“写明规则背后的理由”，并说各个来源是“叠加”的。（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)、[Custom instructions](https://code.visualstudio.com/docs/copilot/customization/custom-instructions)）

Anthropic 对 Agent Skills 描述的也是这三级，先是名字和描述，skill 适用时再读正文，链接的文件只在需要时才读（[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)）。Claude Code 建议每个记忆文件控制在 200 行以内，把只关系到部分代码的规则移到只对匹配路径加载的文件里，并去掉互相矛盾的地方。它把这些文件视为“上下文，不是强制执行的配置”（[How Claude remembers your project](https://code.claude.com/docs/en/memory)）。

可见两个平台用的是同一种结构，始终开启的文件、按路径划分的规则、按需的 skill。既然各个工具的思路都一样，你在这里搭的东西也就可以带着走。

## 哪些手工活可以删，哪些会留下 {#when-to-delete-it}
{status: industry}

这一章里有两件事是靠手工做的：只列出当前领域的 skill，以及削减过长的菜单。这两件都是平台以后可能接手的活儿。如果平台学会了更好地按相关性加载 skill，按领域取舍的办法就可以去掉。

不过这套道理不会过时。窗口变大，并不会让长的规则文件变好，它只是让你在问题冒出来之前能多装一些。何况没有哪种加载方案能让写下来的规则变成强制执行的。如果有平台能在我自己的任务上证明，长的规则文件和短的一样被遵守，我会重新考虑。

审查这个仓库里的指令文件和 skill。列出：始终加载的文件里，你不用交代也会做对的那些行；写在不止一个地方的规则；互相矛盾的规则对；没有写理由的规则；以及描述太含糊而找不到、或太宽泛的 skill，并为每个给出更好的描述。标出那些一旦出错代价高、又无法挽回的规则，因为它们需要代码，而不是文本。不要修改任何文件。
