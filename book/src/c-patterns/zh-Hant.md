這個附錄像一個架子，上面擺著一些小模式，每個都照同樣的格式寫：一行問題、幾行做法、一份可以照著抄的、來自我的 harness 的真實檔案，還有解釋原因的那一章。大多數模式最後還有一行**限制**，取自它連結的那一章。這些檔案是釘住的 tag 上的真實版本，比你的第一版該有的樣子更長、更具體，所以它們是讓你改寫的例子，不是讓你整份貼上的。抄過去之後，每一個都還要在你自己的環境裡檢查一遍。如果不知道從哪裡開始，先看安全的模式（拒絕一個指令、把批准留給人），再看省上下文的，最後看給長任務用的，這和下面的排列順序不一樣。

## 把核心限制放在一頁上 {#core-limits}

**問題**。agent 亂猜路徑和指令，或者把你改過的檔案「整理」掉。

**做法**。保留一頁永遠載入的簡短規則。裡面只放沒有它模型就會做錯的東西，而且放在最前面。剛開始，有兩條限制就夠了。

::: code harness AGENTS.md L44-L45 "出貨的規則頁裡的兩條核心限制：動手前先看，並保留使用者自己的改動。"

**限制**。頁面一長就不會有人讀了，所以每一行都得有它存在的理由。

更多內容見 [指令與 skill：只載入需要的](3-3-instructions-and-skills.html) 和 [30 分鐘搭一個最小 harness](0-2-minimal-harness.html)。

## 只為適用的檔案載入規則 {#rules-by-file}

**問題**。一條只對某一種檔案重要的規則，卻在每個對話裡都占著空間。

**做法**。把規則放進帶 `applyTo` 樣式的指令檔。這樣一來，只有 agent 處理符合的檔案時它才載入，其他時候一點空間都不占。

::: code harness .github/instructions/skills.instructions.md L1-L4 "依檔案載入的指令的標頭：一段描述和一個 applyTo 樣式。"

**限制**。這是對模型的請求，不是平台強制的規則。

更多內容見 [指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。

## 每個時刻共用一個 hook 入口 {#one-hook-entry}

**問題**。好幾個 hook 腳本各有自己的逾時和 shell，很難保持一致。

**做法**。設定檔只說要在哪些時刻呼叫，每個時刻都指向同一個程式，到時候要做什麼由這個程式決定。還要注意兩件事：給這個入口設定時間上限，並且記得這個檔案是在視窗啟動時讀的。

::: code harness .github/hooks/harness.json L40-L51 "工具執行之前那個時刻的入口：它只指名程式和它的時間上限。"

**限制**。逾時的 hook 會被當成通過，所以要讓它跑得快。

更多內容見 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html) 和 [把執行層當軟體來設計](4-4-enforcement-design.html)。

## 拒絕危險的指令，並附上原因 {#refuse-with-reason}

**問題**。有些指令造成的傷害無法復原，例如遞迴刪除根目錄或家目錄，這種指令絕不該執行。

**做法**。每一條指令寫一個樣式，旁邊配一句 `why`。agent 會讀這個原因，所以要說清楚這個指令會做什麼。樣式也要窄，因為每誤擋一次，就有一個任務卡住。

::: code harness .harness/policies/gate.json L59-L62 "一條真實的拒絕規則：遞迴強制刪除根目錄、家目錄或目前的資料夾，附上 agent 讀得懂的原因。"

**限制**。這是減速丘，不是邊界，因為它只擋得住指令的常見寫法，擋不住每一種寫法。所以，絕不能被碰的東西，乾脆就不要交出去（[有些東西根本不給](4-5-least-privilege.html)）。

更多內容見 [詢問不是限制](4-2-ask-vs-refuse.html) 和 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)。

## 把批准留給人的終端機 {#person-only-commands}

**問題**。如果 agent 自己就能執行批准的指令，批准就沒有意義了。

**做法**。在同一個 hook 裡拒絕每一個授予權限的指令，並在原因裡告訴 agent，請人在他自己的終端機裡執行。要測試它，就請 agent 執行其中一個。

::: code harness .harness/policies/gate.json L83-L86 "對只有人才能執行的指令的拒絕：批准、豁免、開啟無人值守模式。"

**限制**。只有在 hook 執行、它的檔案也受到保護時，這一招才行得通。

更多內容見 [兩道門：人在哪裡批准](5-3-two-approvals.html) 和 [保護規則本身的檔案](4-3-guardrails.html)。

## 標記一個只有人能啟動的 skill {#user-only-skill}

**問題**。一個會花錢或交出權限的 skill，不該因為模型覺得合適就啟動。

**做法**。設定 `disable-model-invocation: true`，並在描述裡說明 agent 不可以呼叫它。

::: code harness .github/skills/harness-autorun/SKILL.md L1-L8 "一個只有使用者能啟動的 skill 的開頭：標頭裡的旗標，和描述裡的那句話。"

**限制**。它限制的是誰來啟動 skill，不限制 skill 啟動之後做什麼。

更多內容見 [指令與 skill：只載入需要的](3-3-instructions-and-skills.html) 和 [無人值守：什麼時候必須停](5-7-when-to-stop.html)。

## 一個唯讀的幫手 {#read-only-helper}

**問題**。你想讓 agent 讀很多東西，又不讓它改任何東西。

**做法**。建立一個 custom agent，它的 `tools` 清單只有讀和搜尋，而且不能呼叫別的 agent。工具清單才是限制，內文裡那些「不要」只是請求。內文的用處，是說明這個幫手必須交回什麼。

::: code harness .github/agents/mapper.agent.md L1-L8 "一個唯讀的幫手：工具清單只有讀和搜尋，而且它不呼叫其他 agent。"

**限制**。每個幫手都從空的上下文開始，所以好幾個幫手的花費就是一個 agent 的好幾倍。

更多內容見 [Custom agent：固定模型和工具的角色](2-4-custom-agents.html) 和 [慎用子 agent](2-3-subagents.html)。

## 給幫手一份它能單獨使用的任務說明 {#helper-brief}

**問題**。幫手看不到你的對話，所以呼叫時說得含糊，得到的答案也含糊。

**做法**。寫下問題、要讀的範圍和要交回的項目，再加上長度限制，並要求每個結論都附上來源。

::: code harness .github/skills/generic-mapreduce/templates/brief.md L5-L18 "給唯讀幫手的簡報：問題、範圍、要交什麼、長度和來源。"

更多內容見 [慎用子 agent](2-3-subagents.html)。

## 回答 PASS 或 FAIL 的檢查者 {#pass-fail-checker}

**問題**。寫長篇大論的檢查者，交出來的東西人沒辦法數，腳本也沒辦法讀。

**做法**。把第一行固定為 PASS 或 FAIL，每個發現都要指出檔案、行號，以及它違反的規則。篇幅控制在上限以內，不給建議，也不給修法。這樣一來，腳本就能數出通過了幾次，並丟掉沒有指向任何地方的發現。

::: code harness .github/agents/reviewer.agent.md L58-L76 "獨立檢查者的固定輸出：一行結論、附檔案和行號的發現、長度上限。"

**限制**。模型當檢查者還是會犯錯，一次錯誤的 FAIL 就會讓作者去追一個不存在的問題。

更多內容見 [讓「通過」可信](5-5-counted-checks.html) 和 [模型能檢查模型嗎](5-6-model-checks-model.html)。

## 把需求寫在一頁上，並讓人確認 {#requirement-page}

**問題**。請求含糊又會變，事後沒有人說得出當初同意了什麼。

**做法**。由 agent 寫一頁，說明要做什麼、不要做什麼、什麼時候算做完，再附一份誠實的「還不清楚」清單。最上面有一行，記下人有沒有確認過。

::: code harness .harness/contracts/templates/task/en/REQ.md L1-L42 "需求頁：要做什麼、不要做什麼、做完的條件、還不清楚的，和誰確認的。"

更多內容見 [需求由 agent 寫，人確認](5-2-requirements.html)。

## 給下一個會話的交接檔 {#handover-file}

**問題**。新的對話對舊對話裡做過的工作一無所知。

**做法**。保留一個短檔案讓新會話最先讀，裡面寫著狀態、正在做什麼、下一步、要讀什麼，以及人做了什麼決定。每次停下來之前都更新它。

::: code harness .harness/contracts/templates/task/en/TASK.md L1-L23 "任務的交接檔：狀態、現在在做什麼、下一步、要讀的檔案、決定、未解決的問題。"

**限制**。它是 agent 寫的，所以可能是錯的。重要的地方要對照來源檢查，而不是直接相信它。

更多內容見 [管任務，不管對話](5-1-tasks.html) 和 [跨會話的長任務](5-8-long-work.html)。

## 寫下人知道的那些使用 {#known-uses}

**問題**。模型或腳本產生的程式碼地圖看起來沒問題，可是它後來要是弄丟了東西，你沒有辦法知道。

**做法**。在抽取器出現之前，由人寫下幾個他確定存在的使用，一行一個。從那之後，地圖的每一次執行都必須把它們全部找到。

::: code harness .harness/examples/kb-toolkits/spring/facts.jsonl L4-L8 "Spring 範例的五個已知使用：一個物件、使用的種類、另一個物件。"

**限制**。一份短清單只能說明地圖找得到使用，不能說明它全都找得到。

更多內容見 [Toolkit：用腳本畫出程式碼的地圖](8-2-kb-toolkit.html)。

## 每次都用同樣的方式報告抽查 {#audit-report}

**問題**。對模型輸出的檢查，最後變成一段文字，所以兩次抽查沒辦法比較。

**做法**。用一份固定的報告：通過或失敗、每種類型的分數、每一處差異和它的檔案與行號、規律，以及被修正的解讀。

::: code harness .github/skills/generic-kb-toolkit-audit/templates/audit.md L1-L36 "抽查報告的範本：結果、每種類型的分數、漏掉的、假的使用、規律、被修正的解讀。"

**限制**。小樣本只看得出大的差距。

更多內容見 [地圖對不對：盲抽查](8-3-kb-audit.html)。

## 讓一次停止自己說明原因 {#stop-reason}

**問題**。無人值守的執行停下來時只說一句「遇到問題」，人只好自己去弄清楚發生了什麼。

**做法**。告訴 agent 什麼時候該停、什麼時候不該停，以及原因裡必須寫什麼：哪一步卡住了、為什麼卡住、人必須決定什麼。不過這些話並不取代 hook，凡是從事實就看得出該停的，還是交給 hook 判斷。

::: code harness .github/skills/harness-autorun/references/when-to-stop.md L11-L36 "什麼時候自己停、什麼時候不停，以及怎麼為回來的人寫下原因。"

更多內容見 [無人值守：什麼時候必須停](5-7-when-to-stop.html)。
