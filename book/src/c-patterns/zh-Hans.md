这个附录像一个书架，上面摆着一些小模式，每个都按同样的格式写：一行问题，几行做法，一份可以照着抄的、来自我的 harness 的真实文件，还有讲清道理的那一章。大多数模式最后还有一行**局限**，取自它链接的那一章。这些文件是钉住的 tag 上的真实版本，比你的第一版该有的样子更长、更具体，所以它们是拿来改的例子，不是拿来直接粘贴的。抄过去以后，每一个都还要在你自己的环境里检查一遍。如果不知道从哪里下手，先看安全类的模式（拒绝一条命令、把审批留给人），再看省上下文的，最后看长任务用的，这和下面的排列顺序不一样。

## 把核心限制放在一页上 {#core-limits}

**问题**。agent 乱猜路径和命令，或者把你改过的文件“整理”掉。

**做法**。保留一页始终加载的简短规则。里面只放模型没有它就会做错的内容，并且放在最前面。一开始，有两条限制就够了。

::: code harness AGENTS.md L44-L45 "随 harness 发布的规则页里的两条核心限制：先看再动手，保留用户自己的改动。"

**局限**。页面一长就没人读了，所以每一行都得有它存在的理由。

更多内容见[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)和[30 分钟搭一个最小 harness](0-2-minimal-harness.html)。

## 规则只为它适用的文件加载 {#rules-by-file}

**问题**。一条只对某一类文件要紧的规则，却在每个对话里都占着地方。

**做法**。把规则放进带 `applyTo` 匹配模式的指令文件。这样一来，只有 agent 处理匹配的文件时它才加载，其余时候一点空间都不占。

::: code harness .github/instructions/skills.instructions.md L1-L4 "按文件加载的指令的头部：一段描述和一个 applyTo 匹配模式。"

**局限**。这是对模型的请求，不是平台强制执行的规则。

更多内容见[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)。

## 所有时机只用一个 hook 入口 {#one-hook-entry}

**问题**。好几个 hook 脚本各有各的超时和 shell，很难保持一致。

**做法**。配置文件只说明在哪些时机调用，每个时机都指向同一个程序，到时候做什么由这个程序决定。还要注意两件事：给这个入口设一个时间限制，并且记住这个文件是在窗口启动时读取的。

::: code harness .github/hooks/harness.json L40-L51 "工具运行之前那个时机的入口：它只写出程序的名字和时间限制。"

**局限**。超时的 hook 会被当作通过，所以要让它跑得快。

更多内容见[硬性规则放在哪？用 hook](2-2-hooks.html)和[hook 自己出故障了怎么办？](4-4-enforcement-design.html)。

## 拒绝危险命令，并给出理由 {#refuse-with-reason}

**问题**。有些命令造成的损害无法挽回，比如递归删除根目录或主目录，这类命令永远不该运行。

**做法**。为每条命令写一个匹配模式，旁边配一句 `why`。agent 会读这个理由，所以要写清这条命令会做什么。匹配模式也要窄，因为每误拒一次，就有一个任务卡住。

::: code harness .harness/policies/gate.json L59-L62 "一条真实的拒绝规则：对根目录、主目录或当前文件夹做递归强制删除，附上 agent 读得懂的理由。"

**局限**。这是减速带，不是边界，因为它只拦得住命令的常见写法，拦不住所有写法。所以，绝不能碰的东西，干脆就不要交出去（[不要开放全部的权限或使用沙箱](4-5-least-privilege.html)）。

更多内容见[“先问我”为什么挡不住 Agent？](4-2-ask-vs-refuse.html)和[硬性规则放在哪？用 hook](2-2-hooks.html)。

## 审批留在人的终端里 {#person-only-commands}

**问题**。如果 agent 自己就能运行审批命令，审批就没有意义了。

**做法**。在同一个 hook 里拒绝所有授予权限的命令，并在理由里告诉 agent，请人到自己的终端里去运行。要测试它，就让 agent 运行其中一条。

::: code harness .harness/policies/gate.json L83-L86 "对只有人才能运行的命令的拒绝：审批、豁免、打开无人值守模式。"

**局限**。只有 hook 在运行、它的文件也受到保护时，这一招才有效。

更多内容见[哪些事必须由人来批？](5-3-two-approvals.html)和[别让 Agent 改自己的规则](4-3-guardrails.html)。

## 标出只有人才能启动的 skill {#user-only-skill}

**问题**。一个会花钱或者会交出权限的 skill，不该因为模型觉得合适就启动。

**做法**。设置 `disable-model-invocation: true`，并在描述里写明 agent 不得调用它。

::: code harness .github/skills/harness-autorun/SKILL.md L1-L8 "只有用户才能启动的 skill 的开头：头部的标志，和描述里的那句话。"

**局限**。它限制的是谁来启动这个 skill，不限制 skill 启动之后做什么。

更多内容见[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)和[让 Agent 自己跑一晚上，怎么让它该停就停？](5-7-when-to-stop.html)。

## 只读的帮手 {#read-only-helper}

**问题**。你想让一个 agent 大量阅读，又不让它改任何东西。

**做法**。建一个自定义 agent，它的 `tools` 列表里只有读和搜索，也不能调用别的 agent。工具列表才是限制，正文里那些“不要……”只是请求。正文的用处，是写明这个帮手必须交回什么。

::: code harness .github/agents/mapper.agent.md L1-L8 "一个只读的帮手：工具列表只有读和搜索，也不调用别的 agent。"

**局限**。每个帮手都从空白的上下文开始，所以几个帮手的成本就是单个 agent 的好几倍。

更多内容见[什么时候才需要自定义 Agent？](2-4-custom-agents.html)和[别跟风瞎用子 Agent](2-3-subagents.html)。

## 给帮手一份它能独立使用的任务说明 {#helper-brief}

**问题**。帮手看不到你的对话，所以调用时说得含糊，换来的回答也含糊。

**做法**。写明问题、要读的范围和要交回的条目，再加上长度限制，并要求每个结论都给出来源。

::: code harness .github/skills/generic-mapreduce/templates/brief.md L5-L18 "给只读帮手的任务说明：问题、范围、要交回什么、长度和来源。"

更多内容见[别跟风瞎用子 Agent](2-3-subagents.html)。

## 只回答 PASS 或 FAIL 的检查者 {#pass-fail-checker}

**问题**。一个写长篇大论的检查者，交出来的东西人没法数，脚本也没法读。

**做法**。把第一行固定为 PASS 或 FAIL，每条发现都要写明文件、行号和它违反的规则。篇幅控制在上限以内，不提建议，也不给修法。这样一来，脚本就能数出通过了几次，并丢掉哪里都没指向的发现。

::: code harness .github/agents/reviewer.agent.md L58-L76 "独立检查者的固定输出：一行结论、带文件和行号的发现、长度上限。"

**局限**。模型当检查者照样会出错，一次误报的 FAIL 就会让作者去追一个不存在的问题。

更多内容见[Agent 说“测过了”，能信吗？](5-5-counted-checks.html)和[让另一个模型来审，靠得住吗？](5-6-model-checks-model.html)。

## 把需求写在一页上，并让人确认 {#requirement-page}

**问题**。请求含糊，还会变来变去，事后没人说得清当初约定了什么。

**做法**。由 agent 写一页，写明要做什么、不做什么、做到什么算完成，再附一份诚实的“还不清楚”清单。页面顶上有一行，记录人有没有确认过。

::: code harness .harness/contracts/templates/task/en/REQ.md L1-L42 "需求页：要做什么、不做什么、做到什么算完成、还不清楚的事，以及是谁确认的。"

更多内容见[需求说不清？让 Agent 先写一页给你确认](5-2-requirements.html)。

## 给下一个会话的交接文件 {#handover-file}

**问题**。新对话对旧对话里做过的工作一无所知。

**做法**。留一个简短的文件让新会话先读，里面写着状态、正在做什么、下一步、该读什么，以及人做过的决定。每次停下之前都更新它。

::: code harness .harness/contracts/templates/task/en/TASK.md L1-L23 "任务的交接文件：状态、正在做、下一步、要读的文件、决定、未解决的问题。"

**局限**。它是 agent 写的，所以可能有错。要紧的内容要对照源头检查，而不是直接相信它。

更多内容见[一个任务一个文件夹](5-1-tasks.html)和[一个会话做不完的任务，怎么接着做？](5-8-long-work.html)。

## 把人知道的调用关系写下来 {#known-uses}

**问题**。模型或脚本生成的代码地图看起来没问题，可它后来要是丢了东西，你没办法知道。

**做法**。在抽取器还不存在的时候，由人写下几条他确知存在的调用关系，一行一条。从那以后，每次生成地图都必须把它们全部找出来。

::: code harness .harness/examples/kb-toolkits/spring/facts.jsonl L4-L8 "Spring 示例里五条已知的调用关系：一个对象、调用的类型、另一个对象。"

**局限**。一份短清单只能说明地图找得到调用关系，不能说明它全都找得到。

更多内容见[代码里谁调用谁，交给脚本来算](8-2-kb-toolkit.html)。

## 每次都用同样的格式汇报一次抽查 {#audit-report}

**问题**。对模型输出的检查，最后写成了一段文字，所以两次抽查没法比较。

**做法**。用一份固定的报告：通过还是失败，每种类型一个分数，每处差异附上文件和行号，出现的规律，以及被纠正过的读法。

::: code harness .github/skills/generic-kb-toolkit-audit/templates/audit.md L1-L36 "抽查报告模板：结果、每种类型的分数、漏掉的、误报的调用关系、规律、被纠正的读法。"

**局限**。样本小，只看得出大的缺口。

更多内容见[知识库写得对不对？抽查一遍](8-3-kb-audit.html)。

## 让每次停下都自己说明原因 {#stop-reason}

**问题**。无人值守的运行停下来时只说一句“遇到了问题”，人只好自己去弄清发生了什么。

**做法**。告诉 agent 什么时候该停、什么时候不该停，以及理由里必须写什么：哪一步卡住了、为什么卡住、人要决定什么。不过这些话并不取代 hook，凡是从事实就看得出该停的，还是交给 hook 判断。

::: code harness .github/skills/harness-autorun/references/when-to-stop.md L11-L36 "什么时候该自己停、什么时候不该停，以及怎么给回来的人写理由。"

更多内容见[让 Agent 自己跑一晚上，怎么让它该停就停？](5-7-when-to-stop.html)。
