读这一章之前，你要读过[慎用子 agent](2-3-subagents.html)，它讲了为什么上下文独立的检查者值得有。这里的问题是另一个：你怎么知道一次检查真的发生了，而且真的通过了？

## 一句话 {#in-one-sentence}

一次检查要算数，就由代码来数通过的次数。不要接受 agent 说“我检查过了”。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定“检查过”指的是一条由代码计数的记录，不是 agent 的一句话。连续要通过多少次，由人来定，也只有人可以豁免这条规则。
- **风险**：“我让人检查过了，通过了”这句话没法验证。agent 可能跳过了检查，可能检查的是旧版本，也可能把 FAIL 看成了通过。豁免也可能变成习惯，那样上限就成了摆设。
- **做对的代价**：额外的检查每次都要花用量，而计数器需要一个把对的东西都包括进去的工作指纹。在我的配置里，上限是 n 次检查再加两次，这只是个例子，不是调优过的值。没有任何机制的话，就让 agent 给出命令和它的结果。
- **可以问团队**：“拿最近上线的那次改动来说，给我看那个确切版本上做过检查的记录。”

## 问题 {#problem}

假设你想让每份工作在写回仓库之前，都通过一次独立检查（写回：把做完的工作复制进真实的仓库，见[两道门：人在哪里审批](5-3-two-approvals.html)）。你把它写进规则里。agent 做完了，说：“我让人检查过了，通过了。”

这句话你能拿它做什么？什么也做不了。它可能是真的。agent 也可能跳过了检查，或者检查的是工作的旧版本，或者因为想早点结束，把 FAIL 看成了通过。聊天里的一句话，是 agent 产出的最廉价的东西。它也是你唯一没法测试的东西。

这一章讲的是：检查有没有发生，是不是对着这个版本，结论是什么。它保证的是过程，不是工作的质量。解法和[提示里的规则只是请求](4-1-requests-and-rules.html)是同一个思路：不要问 agent 它有没有做那件事。让那件事留下代码读得懂的痕迹，让代码来判断。

## 原理 {#how-it-works}

### 检查者的回答由代码保存，不由 agent 保存

检查者回答时，它的回答由 hook 原样写进一个文件。agent 改不了这个文件。回答的第一行是固定的：PASS 或 FAIL（见[慎用子 agent](2-3-subagents.html)）。这样，“检查发生了没有，结论是什么？”就成了关于文件的问题，一个小程序就能回答。

### 对确切的那份工作，数连续通过的次数

只通过一次，证明力很弱。检查者是个模型，它可能走运，也可能错。连续通过几次，能降低一次走运的结论的可能性。它消除不了每次运行共有的盲区，因为检查者是同一类模型（见[模型能检查模型吗](5-6-model-checks-model.html)）。所以由人来说需要通过几次：**连续通过 n 次**。在我的配置里，人把它写在 prompt 里，比如“连续通过两次”。agent 不能替自己写。

计数由代码来做，做法是：从最近一次检查开始往回走。数连续的 PASS。碰到第一个 FAIL 就停。FAIL 之后通常会有一次编辑，而编辑改变了工作，所以更早的通过不再算数：这 n 次通过必须全都对着同一个版本。并且，只有当它检查的版本**恰好就是工作现在的样子**时，才把这次 PASS 算进去。

::: figure 5-5-pass-counter

“恰好”需要一个定义。代码会给工作取一个**指纹**：对结果文件、需求和计划做的哈希（内容一变就会变的一小段码）。一次检查会记下它看到的指纹。如果现在的指纹不同，那次检查说的是更早的工作，所以不算数。

有两个细节让它保持诚实：

- **指纹里只放会改变结果的东西**。进度笔记、日志和检查者自己的记录不放进去。否则勾掉一个待办项就会抵销一次通过，计数器白白归零。
- **需求或计划的改动，也会让计数归零**。对着旧计划的通过，对新计划说明不了什么。

这个计数接着管住下一步。把工作写回仓库的那一步，在通过次数达到 n 之前会被拒绝。agent 绕不过去：提高计数的唯一办法，是让工作再被检查一次。

### 检查次数的上限

检查者可能一直发现点什么。如果每一轮都有新的发现，循环就永远结束不了。所以有一个**上限**：n 次检查，再加一小点余量（在我的配置里是多两次；是个例子，不是调优过的值）。用完了还没有足够的通过次数，agent 就停下来，告诉人最后的发现在哪里。

然后人在终端里，用敲码的方式选择：允许更多次检查，或者对这个版本豁免这条规则。

### 豁免

**豁免**让当前版本不够通过次数也能放行。人需要它：有时最后的发现只是措辞问题，或者检查者错了，而人已经读过这份工作，也满意了。三条规则让豁免是安全的：

- **只有人能给**，走 agent 够不着的渠道（怎么走，见[两道门：人在哪里审批](5-3-two-approvals.html)）。
- **只管一个版本**。工作再变，豁免就失效，计数从头开始。
- **留下记录**。以后你能看出，这个版本是靠人的决定过去的，不是靠通过次数。

还有第二个工具，用于相反的情形。如果人判断某一次检查是错的，可以把它搁置。它不再算数，既不算用掉的一次检查，也不算一个 FAIL。

### 没有这套机制时

如果你没有检查者 agent，也保留这个想法：不接受“我检查过了”。让 agent 贴出它运行的命令和结果，自己读结论。之后只要有编辑，就再问一遍。

### 检查开着，却什么都没检查

最隐蔽的失败是沉默：检查是开着的，agent 就是从来不调用检查者。因为什么都没运行，一个 FAIL 也不会被记下。prompt 里的规则抓不住这种情况，因为忘记的恰恰是 agent。

所以要把检查放在 agent 非经过不可的地方：它想停下的那一刻。那一刻的 hook（见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)）把状态和事实对一对。如果检查是开着的，却没有检查，或者最后一次检查之后工作又变了，它就拦一次，让 agent 补上。无论如何，写回的关卡（见[两道门：人在哪里审批](5-3-two-approvals.html)）仍然是关着的，因为计数还没到 n。

### 检查者交上来的东西

计数只和被数的东西一样好，所以检查者的回答有固定的形状，和[慎用子 agent](2-3-subagents.html)里一样。回答之后，由脚本检查这个形状。它会丢掉文件或行号不存在的发现。一个丢完之后什么都不剩的 FAIL 是**无效**的：这次检查会退回去，这样含糊的检查者就不会白吃预算。

脚本检查的是形状，不是判断。检查者对不对，仍然是一个模型的意见。[模型能检查模型吗](5-6-model-checks-model.html)会讲这个问题。

## 代价和坑 {#costs-and-traps}

**指纹得取对**。包括得太多，每个小编辑都会抵销通过，你得再付一次检查的钱。包括得太少，改动就会从一次通过旁边溜过去。我没找到完美的清单；我靠问“这个文件会不会改变工作是什么”来决定。

**计数的通过，只和检查者一样可靠**。计数器证明的是：这个确切的版本上发生过一次检查。它不证明检查者是对的。两个检查者对同一份工作可能给出不同的结论（见[模型能检查模型吗](5-6-model-checks-model.html)）；这就是对重要的改动，允许要求连续通过不止一次的一个理由。检查者有多常出错，我没有测过。

**它不能代替运行东西**。一个只读的检查者给出的通过，是关于“读”的通过。对 agent 能运行的检查（测试、linter），见[让 agent 能检查自己的活](5-4-self-checks.html)。那里的警告同样适用：一个“通过了”的测试，除非你能看到命令和它的输出，否则意义不大。Anthropic 的指南说得很直接：“'All tests pass' on its own tells you very little”（[Best practices](https://code.claude.com/docs/en/best-practices)）。

**豁免可能变成习惯**。如果每次碰到上限，人都选择豁免，上限就是摆设。你靠豁免的记录来发现这一点。

## 什么时候可以删掉 {#when-to-delete-it}

这样的计数器之所以存在，是因为平台没有内置“这份工作在这个版本上被独立检查了 n 次”这个概念。如果平台加上了，并且记录是 agent 改不了的，就用它，把计数器去掉。想法不会退役：由人，而不是 agent，来决定什么算检查过。
