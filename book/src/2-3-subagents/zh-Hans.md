读这一章，只需要用过一个写代码的 AI agent，比如 Copilot 的 agent 模式。

## 一句话 {#in-one-sentence}

分工本身不值钱。多加一个 agent，只有在它换来下面四样之一时才划算：独立检查、并行干活、无人值守，或者对工具的硬性限制。

## 写给管理者 {#for-leaders}

- **要拍板的事**：多加一个 agent，只在它换来上面四样之一时才批。
- **风险**：按岗位分工的一组 agent，可能多花好几倍的用量和时间，结果却没差别。在我用四个任务做的测试里，用量约是 4.5 倍，时间约是 6 倍。
- **做对的代价**：一般是每个任务多一个 agent，也就是负责检查的 reviewer。
- **可以问团队**：“这个 agent 换来的是四样里的哪一样？同一个任务，不用它试过吗？”

## 按岗位分工的 agent 团队，换来了什么？ {#problem}

我曾经给一个 AI 安排了三个岗位。同样四个任务，这个三 agent 团队的用量约是一个 agent 单干的 4.5 倍，时间约是 6 倍，做对的却一个也没多。现在我的做法是，一个 agent 干活，另一个只负责检查。

整个故事的关键，在于每个 agent 看得到什么。**agent** 是在一个循环里干活的 AI 模型：它读文件、跑命令、改代码，自己决定下一步做什么。它在一次对话里看过的所有东西，从你的需求到它读过的文件、它试过的办法，合起来就是它的**上下文**，相当于 agent 的工作记忆，容量是有上限的。**子 agent** 则是第一个 agent 为了某一部分工作而开的第二个 agent，它和第一个 agent 并不共用这份记忆，而是从空白的上下文开始。

### 看起来很对的做法

最自然的想法，是给 AI 分岗位：做计划的、写代码的、做检查的，各由一个 agent 担任。人的团队就是这么分工的，很多工具点几下就能搭起来。

我早期的 Copilot 配置就是这么搭的。**协调者**读需求、写计划，**开发者**改代码，**reviewer** 做检查。然后，我拿它和一个 agent 单干做了对比。

### 我是怎么测的

仓库是虚构的，一个有 5 个领域、93 个文件的数据工程项目。用虚构的仓库，是为了事先就知道有哪些任务、正确答案是什么。任务一共四个，从小到中等：一个是加一条 pipeline，一个是跨几个领域加一个字段，一个是给一条 pipeline 改名并删掉旧文件。最后一个是修一个公式，可需求里同时要求改一个不许动的文件。

每个任务都用两种做法各做一次。一次交给三角色团队，团队还有一份知识库可以读（写给 agent 看的仓库说明）；另一次交给一个用顶级模型的 agent，不加额外配置，规则直接写在需求里。每个结果都由同一个脚本读文件来检查，不靠人眼判断。每次运行我记下三件事：是不是一次就通过，用了多少用量（AI credits，也就是平台向你收的钱），花了多长时间。

::: figure agents-vs-roles

两种做法四个任务全做对了，所以团队多花的钱，在正确性上什么也没换来。不过每个任务只跑了一次，再跑一次，数字就会变。两边条件也不对等：单个 agent 用的是顶级模型，没加额外配置，团队却多了一份知识库可读，每个差异都可能把数字往任意一边推。所以我信的是方向，也就是结果一样、团队贵好几倍，而不是具体的倍数。四到六倍的差距大到值得认真对待，可要确定到底差多少，得多跑几次。

### 多花的钱去哪了

我把每次运行的记录都看了一遍，发现最大的浪费在交接上。协调者把任务研究得很透，读了需求和文件，弄清楚了要改什么，然后写了一份简短的计划交出去。开发者却是从空白的上下文开始的，读完计划，只好把同样的文件再研究一遍。

::: figure handoff-relearn

### 岗位为什么对 AI 没用

这张图说的不只是这一次，任何交接都是这样：理解要压缩成摘要才能交出去，可下一个 agent 要动手，光有摘要是不够的。

那人的团队为什么还要分工？因为人有局限。没人能精通所有专业，一天只有 8 小时，一个人也不能同时出现在两个地方。模型没有这些局限，它真正的局限是上下文的容量，下一节的四种情况说的都是这一点。

岗位本身也不带知识。“你是设计师”只会改变语气，不会改变 agent 知道什么。真正管用的是为这份工作配好的东西，说白了就是两样：写在文件里、任何 agent 都能读的领域知识，以及一套适合这份工作的工具。前者根本不需要第二个 agent，后者倒可以是多开一个的理由（见下面第 4 种情况）。

团队还把一些本不必由模型做的决定交给了模型。“下一步谁来做”“做完没有”这类问题，往往有固定答案，一个小程序每次都能答对，模型却只是大多数时候答对。所以固定规则能决定的事，就别交给模型。一旦要返工，也得从头来：在我的配置里，每一轮检查都会开一个新的 reviewer，从头再读一遍。

这些都不是说第二个 agent 永远没用，而是说它得证明自己值得开。那么，什么时候才值得？

## 什么时候值得多开一个 agent？ {#how-it-works}

### 子 agent 能做什么、不能做什么

不妨把子 agent 想成一个外包，你只给他寄了一份书面说明。它只看得到这份说明，看不到你们之前的对话，也看不到你的笔记。它也没法回头问你，说明里缺了什么，它只能猜，或者停下来。等它做完，交回来的是一份报告，而不是它的理解，因为它读过的东西都留在它自己那里。

所以拆出任何一块工作之前，先问一个问题：**一份简短的报告，够不够主 agent 接着干**？

够，就可以拆。如果主 agent 要接着干，却需要帮手的全部理解，那就别拆。设计师把活交给开发者，就过不了这一关，因为开发者要的不只是一份摘要。

不过，过了这一关还不够。拆分还必须换来一个 agent 自己拿不到的东西，而这样的东西有四种。

### 1. 独立检查

自己校对自己的文章时，你读到的是你想写的，而不是你实际写出来的。agent 检查自己的工作也一样，它的上下文里全是自己的思路，这些思路会带着它绕过自己犯的错。

一个从没见过这些思路的检查者，只读需求和结果，两者对不上，它就能看出来。这个检查者就是 **reviewer**。三个岗位里，最后只有它留了下来，原因后面会讲。它必须是另一个 agent，因为它需要另一份上下文。

::: figure independent-check

另一份上下文是必要条件，但不是充分条件。reviewer 往往是同一个模型，有同样的盲区，它也会误判，要么把好的判成不通过，要么把坏的放过去。换句话说，独立检查能降低风险，但消除不了风险。

一个好用的 reviewer，取决于下面几个设计：

- **给它一个检查包，别给对话**。包里有需求、改过的文件和 diff（到底改了哪几行）。作者的笔记故意不给。
- **拿掉它改文件的工具**。就算它想“顺手修一下”，也做不到。
- **只让它指出问题，不让它修**。它要是写了修法，下一轮检查就成了检查它自己的方案。
- **每个问题都要指到文件和行号**。指不出来的不算问题，这样能挡掉那些含糊的担心。
- **第一行固定写 PASS 或 FAIL**。这样一个小程序就能读出结论，不用再找另一个 AI 来解读“reviewer 这是什么意思”。
- **限制轮数**。每个任务检查几次之后，就交给人决定。从第二轮开始只报影响正确性的问题，不然检查会在措辞上没完没了。

### 2. 并行阅读

有些问题需要读很多东西，比如“这五个领域各管什么？各有什么规则？”一个 agent 只能一个领域接一个领域地读，这很慢，而且读到最后，它的上下文里塞满了已经用不上的原始材料。

换个办法，可以像处理大数据那样拆：把每一份 **map**（分发）给一个帮手，它读完写一份简短的摘要；再把这些摘要 **reduce**（汇总）成一个答案。这个方法叫 **map-reduce**，每个帮手叫 **mapper**。几份材料同时读，就不再慢了；主 agent 从头到尾只看到摘要，原始材料也就进不了它的上下文。

::: figure parallel-read

**这正是多 agent 明显占优的地方**。Anthropic 用这个模式做了一个研究系统，由一个主 agent 负责规划，几个子 agent 同时朝不同方向搜索。在他们内部的研究评测上，它比单个 agent（Claude Opus 4）好 90.2%，尤其擅长那种能拆成几个独立方向的大范围问题。代价是这类系统消耗的 token 约是普通聊天的 15 倍。Anthropic 也提到，大多数编程任务里能并行的部分比研究少。（[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)）

所以判断起来只有两个问题：这份工作能不能拆成互不依赖的几块？答案值不值好几倍的成本？

即便两个问题都答“是”，这也只适用于读。几个帮手要是同时改同一批文件，就得有人合并它们的改动，而冲突会藏在合并里。

并行阅读要用得好，也得靠几个设计：

- **由人来开，不让 agent 开**。它贵好几倍，该你来拍板。一个小程序负责计数（比如一小时内最多四个），agent 开不了更多。只有人输入的命令才算数，agent 不能替自己输入。
- **每个 mapper 只能读和搜索，别的都不行**。
- **每份说明都包含三部分**：问题、范围（读哪些文件或文件夹，只读这些）、要交回什么。Anthropic 见过说明写得含糊的后果：帮手之间重复干活、漏查该查的、理解错任务。早期版本甚至为一个简单的问题开了 50 个子 agent。
- **每份摘要格式固定**：结论，每条注明出自哪个文件、哪一行；没找到的；不确定的。

### 3. 无人值守

平时 agent 做完一步就停下来等你。可有时候，你想把整张待办清单交出去，等它做完再回来看。

最简单的做法要用到 **hook**，也就是工具在固定时机会运行的一个小程序（Copilot 和 Claude Code 都有）。这里的时机是“agent 停下来了”。hook 看一眼待办清单，如果还有没做完的步骤，就让 agent 继续。这只有人能开启，而且一次只针对一个任务。

一个不停往前推的 hook，还得知道什么时候该停。每条停止规则防的是一种不同的故障：

- **步数和时间有上限**（比如 20 步或 2 小时）：失控的运行不会跑一整夜。
- **被拒绝几次就停**（比如两次）：agent 一直在尝试不许做的事，说明哪里出了问题，该让人来看看。
- **没有进展就停**（比如连推三次都没完成任何一步）：agent 陷在循环里了。

在这个最简单的做法里，所有步骤都由一个 agent 来做，清单短的话没问题。可清单一长，它的上下文就会塞满前面每一步留下的东西：第 2 步读过的文件、第 5 步跑过的命令、一个先失败后修好的测试。到第 15 步时，它背着前十四步的残留，上下文这么满，就会忘事、搞混。

更好的做法，像工地上的项目经理。项目经理不亲自砌砖，而是拿着图纸和清单，把每份活写在任务单上交给工人，工人回报后他就打个勾。他的脑子之所以一直清醒，是因为每份活的细节都留在了干活的工人那里。

::: figure autorun-manager

1. **你把整张待办清单交出去**。主 agent 替你盯着。
2. **每一步，主 agent 写一份说明**（做什么、涉及哪些文件、怎样算做完、怎么测），开一个新的子 agent：一个 worker。
3. **worker 完成这一步和对应的测试**，记下自己做了什么，用几行字回报：做完没有、测试过没过、改了哪些文件。
4. **主 agent 给这一步打勾**，为下一步开一个新的 worker。它自己的上下文里始终只有计划、清单和简短的回报。
5. **全部做完后，由 reviewer 检查整体结果**。不通过，主 agent 就开一个 worker 去修 reviewer 找出的问题。

三角色团队行不通，为什么这样拆就行？团队是把同一件事按阶段拆，一个 agent 负责弄懂，另一个要接着这份理解去干。这里是按块拆。每个 worker 拿到的是一件完整的小事，干活和测试都包在里面，所以主 agent 只要知道“做完了，测试通过”就能往下走，这就过了摘要那一关。

这样拆也有代价，大多来自两件事。一是每个 worker 都从零开始，手里只有那份说明。它没法回头问，所以说明必须写全，它需要的都得写下来；它还要重新读自己那部分文件，所以很多小步骤加起来，比一个 agent 一路做到底更贵。二是主 agent 只看得到回报，而回报不等于证明。worker 说“测试通过”也可能是错的，主 agent 却分辨不出来。所以最后的独立检查很重要，主 agent 也该时不时打开某一步的文件看一眼。

步骤之间要是互相依赖细节，就根本不适合这样拆。如果第 4 步需要确切知道第 3 步是怎么做的，那就把它写下来交给下一个 worker，或者干脆两步都交给一个 agent。

所以它适合那种很长、每一步都能独立完成的清单。清单短，一个 agent 还是更便宜。如果你人就在旁边，把长任务拆成几个小任务，也能拿到大部分好处。

### 4. 工具的硬性限制

每个 agent 都有一份能用的工具清单，比如读文件、搜索、跑命令、改文件。在 Copilot 里，这是 agent 文件里的 `tools` 列表（Claude Code 的子 agent 也有）。和写在指令里的话不同，这份清单由平台强制执行，所以一个没有“改文件”工具的 agent，你怎么让它改，它都改不了。

主 agent 通常什么工具都有。所以某项工作绝对不能改任何东西时，跟主 agent 说“请不要改文件”只是一个请求；把这项工作交给一个没有这个工具的子 agent，它才成了规则。

::: figure tool-limit

### 让它成为规则，而不是请求

那怎么保证不会有别的子 agent 跑起来？这里碰到的，还是请求和规则的区别。在指令里写“不要开其他子 agent”只是请求，模型大多数时候会照做。

hook 能把它变成规则。一个在任何子 agent 启动前运行的 hook，可以读出子 agent 的名字，决定放行还是拒绝。它每次都会运行，模型也说服不了它。好的拒绝还会说明应该改做什么，免得 agent 再去试同一件事。

### 靠文件交接

agent 一多，工作就要在它们之间传递，但它们不该靠互相发消息来传。更好的办法是给每件工作建一个自己的**任务文件夹**，里面放需求、计划、待办清单和每次检查的结果，agent 通过往这里写文件来交接。

为什么用文件，而不是发消息？因为你能打开同样的文件，看到发生了什么。中断一天，下一个会话能从文件接着做。事后，这个文件夹就是一份记录，谁做了什么、检查结论是什么，都在里面。

::: figure subagent-map

### 用它检验你自己的配置

有一个今天就能做、不需要任何额外配置的测试。挑一个你知道正确答案的任务，在你自己的工具里做两遍。第一遍让 agent 检查自己的工作；第二遍新开一个对话，只给它需求和结果，让它来检查。然后对比一下，两边各找出了什么。

想公平地对比两种配置，有几个习惯很要紧：

- 每种跑几次，不要只跑一次，因为 agent 不会两次做得一模一样。
- 两边用同一种方式打分，最好用脚本。
- 记下三个数：对不对、用了多少、花了多久。

想复现我的测试，虚构的仓库、四个任务和打分脚本都在 [`labs/subagents/`](../labs/subagents/README.md)，任何 agent 工具都能用。

## 多花的钱换来了什么，拆分还有哪些代价 {#costs-and-traps}

其实就在我的测试里，多花的钱也不是全打了水漂。有一次，开发者漏改了两处跨领域的引用，reviewer 发现了，把活打回去重做，全程没人插手。所以团队里的其他角色都撤了，我留下了 reviewer。

除此之外，拆分还有两笔账容易算漏。先说并行阅读，它并不免费，因为每个 mapper 都从空白的上下文开始，从头读自己那一份。只有要读的东西一份上下文装不下时才用它，别为了几个文件省点时间就上。

另一笔容易漏的是子 agent 的用量：工具往往只显示主对话的用量，你得看看自己的工具有没有把子 agent 也算进去。就算看得到了，限制能开几个帮手，也并不能限制它们一共花多少。更好的设计是让主 agent 和所有子 agent 共用一份预算，子 agent 拿到的是剩下的部分，而不是自己另起一份。

## 平台厂商也这么看吗？ {#industry}
{status: industry}

平台厂商在方向上是一致的：agent 越多，token 多得越多。前面讲并行阅读时说到的 Anthropic 研究系统就是一例（[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)）。Claude Code 有 *agent teams*，也就是几个 agent 组成团队、互相发消息。它的文档说，“当 teammates 在 plan mode 下运行时，token 用量约是普通会话的 7 倍”（plan mode：每个成员先规划再动手）。这和我的测试配置不一样，数字不能直接比；而且 agent teams 还是实验功能，默认关闭（[Manage costs](https://code.claude.com/docs/en/costs)）。VS Code 的指南则说：“让 agent 链尽量浅，每个 agent 只给它真正需要的工具。”（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）

没有哪一家说一个 agent 永远更好。把它们和我的测试放在一起看，结论是：需求清楚的单个任务，别搞编排；能拆成几块独立工作的大范围任务，多 agent 可能值这个成本。

## 什么时候删掉这些 hook，什么时候重新考虑拆分 {#when-to-delete-it}
{status: industry}

这一章里的 hook（只放行指定的子 agent、给帮手计数、推动无人值守的运行）之所以存在，是因为平台还不做这些事。等 Copilot 自己能只放行指定的子 agent，并且能给整个任务设一份用量预算，就把这些 hook 删掉。

hook 可以删，背后的道理却还在。真正会让我重新考虑拆分本身的，是另外两件事。第一件，是平台能让一个做完的子 agent 接着干。那样返工就不用从头开始，在一个任务里放一个很轻的协调者也许就划算了。第二件，要是哪天有对比表明，自我检查能抓到独立检查能抓到的所有问题，那连 reviewer 也可以撤了。
