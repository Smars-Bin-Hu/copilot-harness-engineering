读这一章，只需要用过一个写代码的 AI agent，比如 Copilot 的 agent 模式。别的都不需要。

## 一句话 {#in-one-sentence}

分工本身不值钱。多加一个 agent，只有在它换来下面四样之一时才划算：独立检查、并行干活、无人值守，或者对工具的硬性限制。

## 写给管理者 {#for-leaders}

- **要拍板的事**：多加一个 agent，只在它换来四样之一时才批：独立检查、并行、无人值守、工具的硬性限制。
- **风险**：按岗位分工的一组 agent，可能多花好几倍的用量和时间，结果却没差别。在我的测试里，用量约 4.5 倍，时间约 6 倍；一共四个任务，每个只跑了一次。
- **做对的代价**：一般是每个任务多一个 agent，也就是负责检查的那个。
- **可以问团队**：“这个 agent 换来的是四样里的哪一样？同一个任务，不用它试过吗？”

## 问题 {#problem}

我曾经给 AI 安排了三个岗位。同样四个任务，用量约是原来的 4.5 倍，时间约是 6 倍，做对的一个也没多。现在我的做法是：一个 agent 干活，另一个只负责检查。

先交代这一章反复会用到的三个词。

- **agent**：在一个循环里干活的 AI 模型。它读文件、跑命令、改代码，自己决定下一步做什么。
- **上下文**：它在一次对话里看过的所有东西：你的需求、它读过的文件、它试过的办法。这是 agent 的工作记忆，容量有上限。
- **子 agent**：第一个 agent 为了某一部分工作而开的第二个 agent。它从空白的上下文开始。

### 看起来很对的做法

给 AI 分岗位：做计划的、写代码的、做检查的，各一个 agent。人的团队就是这么分工的，很多工具点几下就能搭起来。

我早期的 Copilot 配置就是这么搭的。**协调者**读需求、写计划，**开发者**改代码，**reviewer** 做检查。然后我拿它和一个 agent 单干做了对比。

### 我是怎么测的

- **仓库**：一个虚构的数据工程项目，5 个领域，93 个文件。用虚构的，是为了事先就知道有哪些任务、正确答案是什么。
- **四个任务，从小到中等**：加一条 pipeline；跨几个领域加一个字段；给一条 pipeline 改名并删掉旧文件；修一个公式，而需求同时要求改一个不许动的文件。
- **两种做法**：每个任务让三角色团队做一次，团队还有一份知识库可以读（写给 agent 看的仓库说明）；再让一个用顶级模型的 agent 做一次，不加额外配置，规则写在需求里。
- **怎么打分**：同一个脚本读文件，检查每个结果，不靠人眼判断。
- **统计什么**：是不是一次就通过、用了多少用量（AI credits，也就是平台向你收的钱）、花了多长时间。

::: figure agents-vs-roles

两种做法四个任务全做对了。也就是说，团队在正确性上什么也没多换来，却多付了约 4.5 倍的用量、约 6 倍的时间。

引用这两个数字之前要知道：只有四个任务，每个只跑一次，而且两边的配置不一样。方向可以信（结果一样，团队贵好几倍），具体倍数别当真。[代价和坑](#costs-and-traps)里有更多说明。

### 多花的钱去哪了

我把每次运行的记录都看了一遍。最大的浪费在交接上。协调者把任务研究得很透：读了需求和文件，弄清楚了要改什么。然后它写了一份简短的计划交出去。开发者从空白的上下文开始，读完计划，只好把同样的文件再研究一遍。同一份理解，付了两次钱。

::: figure handoff-relearn

### 岗位为什么对 AI 没用

1. **人要分工，是因为人有局限**。没人能精通所有专业，一天只有 8 小时，一个人也不能同时在两个地方。模型没有这些局限。它真正的局限是上下文的容量，下一节的四种情况都和这一点有关。
2. **岗位本身不带知识，合适的配置才有用**。“你是设计师”只会改变语气，不会改变 agent 知道什么。真正管用的是两样：写在文件里、任何 agent 都能读的领域知识，以及一套适合这份工作的工具。前者不需要第二个 agent，后者可以是多开一个的理由（见下面第 4 种情况）。
3. **交接会丢掉理解**。就是上面那张图。理解要压缩成摘要才能交出去，而下一个 agent 要动手，光有摘要是不够的。
4. **固定规则能决定的事，别交给模型**。“下一步谁来做”“做完没有”往往有固定答案。一个小程序每次都能答对，模型只是大多数时候答对。
5. **返工要从头来**。在我的配置里，每一轮检查都会开一个新的 reviewer，从头再读一遍。

## 原理 {#how-it-works}

### 子 agent 能做什么、不能做什么

把子 agent 想成一个外包，你只给他寄了一份书面说明：

- **它只看得到这份说明**。你们之前的对话、你的笔记，它都看不到。
- **它没法回头问你**。说明里缺了什么，它只能猜，或者停下来。
- **它交回来的是报告，不是理解**。它读过的东西都留在它自己那里。

所以拆出任何一块工作之前，先问一个问题：**一份简短的报告，够不够主 agent 接着干**？

够，就可以拆。如果主 agent 要接着干，却需要帮手的全部理解，那就别拆。设计师把活交给开发者，就过不了这一关：开发者要的是设计师的全部理解，不是一份摘要。

过了这一关还不够。拆分还必须换来一个 agent 自己拿不到的东西。这样的东西有四种。

### 1. 独立检查

自己校对自己的文章时，你读到的是你想写的，而不是你实际写出来的。agent 检查自己的工作也一样：它的上下文里全是自己的思路，这些思路会带着它绕过自己犯的错。

一个从没见过这些思路的检查者，只读需求和结果。两者对不上，它就能看出来。这个检查者就是 **reviewer**。它必须是另一个 agent，因为它需要另一份上下文。

::: figure independent-check

另一份上下文是必要条件，但不是充分条件。reviewer 往往是同一个模型，有同样的盲区，它也会误判：把好的判成不通过，把坏的放过去。所以独立检查能降低风险，但消除不了风险。

**怎么搭一个好用的**：

- **给它一个检查包，别给对话**。包里有需求、改过的文件和 diff（到底改了哪几行）。作者的笔记故意不给。
- **拿掉它改文件的工具**。就算它想“顺手修一下”，也做不到。
- **只让它指出问题，不让它修**。它要是写了修法，下一轮检查就成了检查它自己的方案。
- **每个问题都要指到文件和行号**。指不出来的不算问题。这样能挡掉那些含糊的担心。
- **第一行固定写 PASS 或 FAIL**。这样一个小程序就能读出结论，不用再找另一个 AI 来解读“reviewer 这是什么意思”。
- **限制轮数**。每个任务检查几次就够了，之后交给人决定。从第二轮开始只报影响正确性的问题，不然检查会在措辞上没完没了。

### 2. 并行阅读

有些问题需要读很多东西。“这五个领域各管什么？各有什么规则？”一个 agent 只能一个领域接一个领域地读。这很慢，而且读到最后，它的上下文里塞满了已经用不上的原始材料。

换个办法，像处理大数据那样拆：把每一份 **map**（分发）给一个帮手，它读完写一份简短的摘要；再把这些摘要 **reduce**（汇总）成一个答案。这个方法叫 **map-reduce**，每个帮手叫 **mapper**。几份同时读，主 agent 从头到尾只看到摘要。

::: figure parallel-read

**这正是多 agent 明显占优的地方**。Anthropic 用这个模式做了一个研究系统：一个主 agent 负责规划，几个子 agent 同时朝不同方向搜索。在他们内部的研究评测上，它比单个 agent（Claude Opus 4）好 90.2%，尤其擅长那种能拆成几个独立方向的大范围问题。代价是：这类系统消耗的 token 约是普通聊天的 15 倍。他们也说，大多数编程任务里真正能并行的部分比研究少。（[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)）

所以判断起来只有两个问题：这份工作能不能拆成互不依赖的几块？答案值不值好几倍的成本？

这只适用于读。几个帮手同时改同一批文件，就得有人合并它们的改动，冲突会藏在合并里。

**怎么搭**：

- **由人来开，不让 agent 开**。它贵好几倍，该你来拍板。一个小程序负责计数（比如一小时内最多四个），agent 开不了更多。只有人输入的命令才算数，agent 不能替自己输入。
- **每个 mapper 只能读和搜索，别的都不行**。
- **每份说明都包含三部分**：问题、范围（读哪些文件或文件夹，只读这些）、要交回什么。Anthropic 见过说明写得含糊的后果：帮手之间重复干活、漏查该查的、理解错任务。早期版本甚至为一个简单的问题开了 50 个子 agent。
- **每份摘要格式固定**：结论，每条注明出自哪个文件、哪一行；没找到的；不确定的。

### 3. 无人值守

平时 agent 做完一步就停下来等你。有时候你想把整张待办清单交出去，等它做完再回来看。

**最简单的做法**要用到 **hook**：工具在固定时机会运行的一个小程序。Copilot 和 Claude Code 都有。这里的时机是“agent 停下来了”。hook 看一眼待办清单，还有没做完的步骤，就让 agent 继续。只有人能开启，一次只针对一个任务。

它还得知道什么时候别再推了。每条停止规则防的是一种不同的故障：

- **步数和时间有上限**（比如 20 步或 2 小时）：失控的运行不会跑一整夜。
- **被拒绝几次就停**（比如两次）：agent 一直在尝试不许做的事，说明哪里出了问题，该让人来看看。
- **没有进展就停**（比如连推三次都没完成任何一步）：agent 陷在循环里了。

在这个最简单的做法里，所有步骤都由一个 agent 来做。清单短，没问题。清单一长，它的上下文就会塞满前面每一步留下的东西：第 2 步读过的文件、第 5 步跑过的命令、一个先失败后修好的测试。到第 15 步时，它背着前 14 步的残留，上下文太满，就会忘事、搞混。

**更好的做法**像工地上的项目经理。项目经理不亲自砌砖。他手里拿着图纸和清单，把每份活写在任务单上交给工人，工人回报后他就打个勾。项目经理的脑子一直是清醒的，因为每份活的细节都留在干活的工人那里。

::: figure autorun-manager

1. **你把整张待办清单交出去**。主 agent 替你盯着。
2. **每一步，主 agent 写一份说明**（做什么、涉及哪些文件、怎样算做完、怎么测），开一个新的子 agent：一个 worker。
3. **worker 完成这一步和对应的测试**，记下自己做了什么，用几行字回报：做完没有、测试过没过、改了哪些文件。
4. **主 agent 给这一步打勾**，为下一步开一个新的 worker。它自己的上下文里始终只有计划、清单和简短的回报。
5. **全部做完后，由 reviewer 检查整体结果**。不通过，主 agent 就开一个 worker 去修 reviewer 找出的问题。

三角色团队行不通，为什么这样拆就行？团队是把同一件事按阶段拆：一个 agent 负责弄懂，另一个要接着这份理解去干。这里是按块拆：每个 worker 拿到的是一件完整的小事，干活和测试都包在里面，主 agent 只要知道“做完了，测试通过”就能往下走。这能过摘要那一关。

代价：

- **每份说明都得写全**。worker 没法回头问，它需要的都得写下来。
- **每个 worker 都从零开始**。它要重新读自己那部分文件，所以很多小步骤加起来，比一个 agent 一路做到底更贵。
- **回报不等于证明**。worker 说“测试通过”也可能是错的，只看回报的主 agent 分辨不出来。所以最后的独立检查很重要，主 agent 也该时不时打开某一步的文件看一眼。
- **步骤之间互相依赖细节的，不合适**。第 4 步需要确切知道第 3 步是怎么做的，那就把它写下来交给下一个 worker，或者干脆两步都交给一个 agent。

所以它适合那种很长、每一步都能独立完成的清单。清单短，一个 agent 还是更便宜。如果你人就在旁边，把长任务拆成几个小任务，也能拿到大部分好处。

### 4. 工具的硬性限制

每个 agent 都有一份能用的工具清单：读文件、搜索、跑命令、改文件。在 Copilot 里，这是 agent 文件里的 `tools` 列表；Claude Code 的子 agent 也有。平台会强制执行这份清单。一个没有“改文件”工具的 agent，你怎么让它改，它都改不了。

主 agent 通常什么工具都有。某项工作绝对不能改任何东西时，跟主 agent 说“请不要改文件”只是一个请求。把这项工作交给一个没有这个工具的子 agent，它才成了规则。

::: figure tool-limit

### 让它成为规则，而不是请求

怎么保证不会有别的子 agent 跑起来？在指令里写“不要开其他子 agent”只是请求：模型大多数时候会照做。

hook 能把它变成规则。一个在任何子 agent 启动前运行的 hook，可以读出子 agent 的名字，决定放行还是拒绝。它每次都会运行，模型也说服不了它。好的拒绝还会说明应该改做什么，免得 agent 再去试同一件事。

### 靠文件交接

agent 之间不该互相发消息。给每件工作建一个自己的**任务文件夹**，里面放需求、计划、待办清单和每次检查的结果。agent 通过往这里写文件来交接。

这一招换来三样东西。你能打开同样的文件，看到发生了什么。中断一天，下一个会话能从文件接着做。事后，这个文件夹就是一份记录：谁做了什么，检查结论是什么。

::: figure subagent-map

### 用它检验你自己的配置

**三个问题**，拿去问你自己配置里的、或者别人找你审批的任何一个额外 agent：

1. 它换来的是四种里的哪一种？
2. 一份简短的报告，够不够主 agent 接着干？
3. 同一个任务，你试过不用它吗？

**今天就能做、不需要任何额外配置的测试**。挑一个你知道正确答案的任务，在你自己的工具里做两遍。一遍让 agent 检查自己的工作。另一遍新开一个对话，只给它需求和结果，让它来检查。对比一下两边各找出了什么。

**公平地对比两种配置**：

- 每种跑几次，不要只跑一次。agent 不会两次做得一模一样。
- 两边用同一种方式打分，最好用脚本。
- 记下三个数：对不对、用了多少、花了多久。
- 别凭一次结果下结论。

**想复现我的测试**：虚构的仓库、四个任务和打分脚本都在 [`labs/subagents/`](../labs/subagents/README.md)，任何 agent 工具都能用。

## 代价和坑 {#costs-and-traps}

**我有多大把握**。方向有把握，具体倍数没把握。原因有两个：

- **每个任务只跑了一次**。再跑一次，数字就会变。
- **两边条件不对等**。单个 agent 用的是顶级模型，没加额外配置；团队多了一份知识库可读。每个差异都可能把数字往任意一边推。

四到六倍的差距，大到值得认真对待。要坐实它，得多跑几次。

**我没测的**。一个含糊的需求，加上一个又大又乱的仓库。拆分在那种场景下也许划算。两边我都没有数据。

**多花的钱确实换来了一点东西**。有一次，开发者漏改了两处跨领域的引用。reviewer 发现了，把活打回去重做，全程没人插手。所以团队里的其他角色都撤了，我留下了 reviewer。

**并行阅读不是免费的**。每个 mapper 都从空白的上下文开始，从头读自己那一份。四个 mapper 的成本是一个 agent 的好几倍。只有要读的东西一份上下文装不下时才用它，别为了几个文件省点时间就上。

**子 agent 的用量很容易被漏掉**。工具往往只显示主对话的用量。看看你的工具有没有把子 agent 也算进去。

**限制个数不等于限制预算**。限制能开几个帮手，不等于限制它们一共花多少。更好的设计是让主 agent 和所有子 agent 共用一份预算，子 agent 拿到的是剩下的部分，而不是自己另起一份。

## 业界怎么说 {#industry}
{status: industry}

平台厂商在方向上是一致的：agent 越多，token 多得越多。

- **Anthropic 的研究系统**（见上文）：token 约是普通聊天的 15 倍，用来做大范围的研究值得，用在大多数编程任务上就没那么值。（[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)）
- **Claude Code** 有 *agent teams*：几个 agent 组成团队、互相发消息。它的文档说，“当 teammates 在 plan mode 下运行时，token 用量约是普通会话的 7 倍”（plan mode：每个成员先规划再动手）。这和我的测试配置不一样，数字不能直接比。agent teams 是实验功能，默认关闭。（[Manage costs](https://code.claude.com/docs/en/costs)）
- **VS Code**：“让 agent 链尽量浅，每个 agent 只给它真正需要的工具。”（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）

没有哪一家说一个 agent 永远更好。再加上我的测试：需求清楚的单个任务，别搞编排；能拆成几块独立工作的大范围任务，多 agent 可能值这个成本。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

这一章里的 hook（只放行指定的子 agent、给帮手计数、推动无人值守的运行）之所以存在，是因为平台还不做这些事。等 Copilot 自己能只放行指定的子 agent，并且能给主 agent 和所有子 agent 的用量设一个总上限，就把这些 hook 删掉。

背后的道理不会跟着退役。有两件事会让我重新考虑拆分本身：

- **平台能让一个做完的子 agent 接着干**。返工就不用从头开始，在一个任务里放一个很轻的协调者也许就划算了。Copilot 现在能不能做到，我还没测过。
- **一次对比表明，自我检查能抓到独立检查能抓到的所有问题**。那就连 reviewer 也可以撤了。

不用装 harness。在你自己的仓库里打开 agent，粘贴：
