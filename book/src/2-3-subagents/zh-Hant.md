讀這一章，只需要用過一個寫程式的 AI agent，例如 Copilot 的 agent 模式。

## 一句話 {#in-one-sentence}

分工本身沒有價值。多一個 agent，只有在它換來下面四樣之一時才值得：獨立檢查、並行工作、無人值守，或對工具的硬性限制。

## 給主管 {#for-leaders}

- **要做的決定**：多開一個 agent，只在它換來上面四樣之一時才批。
- **風險**：按職位分工的一組 agent，可能花幾倍的用量和時間，結果卻一樣。在我用四個任務做的測試裡，用量約是 4.5 倍，時間約是 6 倍。
- **做對的成本**：通常是每個任務多一個 agent，也就是負責檢查的 reviewer。
- **可以問團隊**：「這個 agent 換來的是四樣裡的哪一樣？同一個任務，試過不用它嗎？」

## 按職位分工的 agent 團隊，換來了什麼？ {#problem}

我曾經給一個 AI 安排了三個職位。同樣四個任務，這個三 agent 團隊的用量約是一個 agent 單獨做的 4.5 倍，時間約是 6 倍，答對的卻一個也沒多。現在我的做法是，一個 agent 做事，另一個只負責檢查。

整個故事的關鍵，在於每個 agent 看得到什麼。**agent** 是在迴圈裡工作的 AI 模型：它讀檔案、執行指令、改程式碼，自己決定下一步。它在一次對話裡看過的全部東西，從你的需求到它讀過的檔案、它試過的做法，合起來就是它的**上下文**，等於 agent 的工作記憶，大小是有上限的。**子 agent** 則是第一個 agent 為了一部分工作而開的第二個 agent，它和第一個 agent 並不共用這份記憶，而是從空的上下文開始。

### 感覺很對的做法

最自然的想法，是給 AI 安排職位：計劃的、開發的、檢查的，各由一個 agent 擔任。人的團隊就是這樣分工的，很多工具點幾下就能搭好。

我在自己早期的 Copilot 設定裡就是這樣搭的。**協調者**讀需求、寫計劃，**實作者**改程式碼，**reviewer** 做檢查。然後，我拿它和一個 agent 單獨做事來比。

### 我怎麼測的

倉庫是虛構的，一個有 5 個領域、93 個檔案的資料工程專案。用虛構的倉庫，是為了事先就知道任務和正確答案。任務一共四個，從小到中等：一個是加一條 pipeline，一個是跨幾個領域加一個欄位，一個是改一條 pipeline 的名字並刪掉舊檔案。最後一個是修一個公式，可是需求同時要求改一個不准動的檔案。

每個任務都用兩種做法各做一次。一次交給三角色團隊，團隊還有一份知識庫可讀（為 agent 寫的倉庫說明）；另一次交給一個用頂級模型的 agent，沒有額外設定，規則直接寫在需求裡。每個結果都由同一個腳本讀檔案來檢查，沒有人憑眼睛判斷。每次執行我記下三件事：第一次就通過了沒有、用了多少用量（AI credits，也就是平台向你收的錢）、花了多久。

::: figure agents-vs-roles

兩種做法四個任務都答對了，所以團隊多花的錢，在正確性上什麼也沒換到。不過每個任務只跑了一次，再跑一次，數字就會變。兩邊也不對等：單個 agent 用的是頂級模型，沒有額外設定，團隊卻多了一份知識庫可讀，每個差別都可能把數字往任一邊推。所以我信的是方向，也就是同樣的結果、團隊貴了好幾倍，而不是確切的倍數。四到六倍的差距大到值得認真對待，可是要確定到底差多少，得多跑幾次。

### 多出來的錢花在哪

我讀了每一次執行的紀錄，發現最大的浪費在交接。協調者很認真地研究了任務，讀了需求和檔案，搞懂了要改什麼，然後寫了一份簡短的計劃交出去。實作者卻是從空的上下文開始的，讀了計劃，只好把同樣的檔案再研究一遍。

::: figure handoff-relearn

### 為什麼職位對 AI 沒用

這張圖說的不只是這一次，任何交接都是這樣：理解要壓成摘要才能交出去，可是下一個 agent 要動手，光有摘要不夠。

那人的團隊為什麼還要分工？因為人有限制。沒有人學得會所有專業，一天只有 8 小時，一個人也不能同時在兩個地方。模型沒有這些限制，它真正的限制是上下文的大小，下一節的四種情況講的都是這一點。

職位本身也不帶知識。「你是設計師」只改變語氣，不改變 agent 知道什麼。真正有用的是為這份工作配好的東西，換句話說就是兩樣：寫在檔案裡、任何 agent 都能讀的領域知識，以及一組適合這份工作的工具。前者根本不需要第二個 agent，後者倒可以是多開一個的理由（下面第 4 種情況）。

團隊還把一些本來不必由模型做的決定交給了模型。「誰做下一步」「做完了沒」這類問題，常常有固定的答案，一個小程式每次都答對，模型卻只是大多數時候答對。所以固定規則能決定的事，就別交給模型。一旦要返工，也得從零開始：在我的設定裡，每一輪檢查都開一個新的 reviewer，從頭再讀一遍。

這些都不是說第二個 agent 永遠沒用，而是說它得證明自己值得開。那麼，什麼時候才值得？

## 什麼時候值得多開一個 agent？ {#how-it-works}

### 子 agent 能做什麼、不能做什麼

不妨把子 agent 想成一個外包，你只寄了一份書面說明給他。它只看得到這份說明，看不到你們的對話，也看不到你的筆記。它也不能回頭問你，說明裡少了什麼，它只能猜，或者停下來。等它做完，交回來的是一份報告，而不是它的理解，因為它讀過的東西都留在它那裡。

所以在拆出任何工作之前，先問一個問題：**一份簡短的報告，夠不夠主 agent 接著做**？

夠，就可以拆。主 agent 要接著做，卻需要幫手的全部理解，就不要拆。設計師把工作交給開發者就過不了這一關，因為開發者需要的不只是一份摘要。

不過，過了這一關還不夠。拆分還得換來一個 agent 自己得不到的東西，而這樣的東西有四種。

### 1. 獨立檢查

校對自己的文章時，你讀到的是你想寫的，不是你寫出來的。agent 檢查自己的工作也一樣，它的上下文裡全是它自己的思路，這些思路會帶著它繞過自己的錯。

一個從沒看過那些思路的檢查者，只讀需求和結果，結果對不上，它就看得出來。這個檢查者就是 **reviewer**。三個職位裡，最後只有它留了下來，原因後面會講。它必須是另一個 agent，因為它需要另一個上下文。

::: figure independent-check

另一個上下文是必要的，但不夠。reviewer 常常是同一個模型，有同樣的盲點，它也會判錯，可能把好的判成不通過，也可能把壞的放過去。換句話說，獨立檢查能降低風險，但不能消除風險。

一個好的 reviewer，取決於下面幾個設計：

- **給它一個檢查包，不給對話**。包裡有需求、改過的檔案和 diff（到底改了哪幾行）。作者的筆記故意不給。
- **拿掉它改檔案的工具**。就算它想「順手修掉」，也做不到。
- **只讓它指出問題，不讓它修**。它寫了修法，下一輪檢查就是在檢查它自己的方案。
- **每個問題都要指到檔案和行號**。指不出來的就不算問題，這樣可以擋掉含糊的擔心。
- **第一行固定寫 PASS 或 FAIL**。這樣一個小程式就能讀出結論，不用再問另一個 AI「reviewer 是什麼意思」。
- **限制輪數**。每個任務檢查幾次之後，就由人決定。從第二輪起只報影響正確性的問題，不然檢查會為了措辭沒完沒了。

### 2. 並行閱讀

有些問題要讀很多東西，例如「這五個領域各自負責什麼？各有什麼規則？」一個 agent 只能一個領域接一個領域地讀，這很慢，而且讀到最後，它的上下文塞滿了已經用不著的原始材料。

換個做法，可以像處理大數據那樣拆：把每一份 **map**（分派）給一個幫手，它讀完寫一份簡短的摘要；再把這些摘要 **reduce**（合併）成一個答案。這個方法叫 **map-reduce**，每個幫手叫 **mapper**。幾份材料同時讀，就不再慢了；主 agent 自始至終只看到摘要，原始材料也就進不了它的上下文。

::: figure parallel-read

**這正是多個 agent 明顯佔優的地方**。Anthropic 用這個模式做了一個研究系統，由一個主 agent 做規劃，幾個子 agent 同時往不同方向搜尋。在他們內部的研究評測上，它比單個 agent（Claude Opus 4）好 90.2%，尤其擅長能拆成幾個獨立方向的廣泛問題。代價是這類系統用的 token 約是聊天的 15 倍。Anthropic 也提到，大多數寫程式的任務，能並行的部分比研究少。（[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)）

所以判斷只有兩個問題：這份工作能不能拆成互不依賴的幾塊？答案值不值得好幾倍的成本？

就算兩個問題都答「是」，這也只適用於讀。幾個幫手要是同時改同樣的檔案，就得有人合併它們的改動，而衝突會藏在合併裡。

並行閱讀要用得好，也得靠幾個設計：

- **由人來開，不由 agent 開**。它貴好幾倍，該由你決定。一個小程式負責計數（例如一小時內最多四個），agent 開不了更多。只有人輸入的指令才算，agent 不能替自己輸入。
- **每個 mapper 只能讀和搜尋，別的都不行**。
- **每份說明都有三部分**：問題、範圍（讀哪些檔案或資料夾，只讀這些）、要交回什麼。Anthropic 看到過說明含糊的後果：幫手重複工作、漏掉該查的、誤解任務。早期版本甚至為一個簡單問題開了 50 個子 agent。
- **每份摘要格式固定**：結論，每條附上出自哪個檔案、哪一行；找不到的；不確定的。

### 3. 無人值守

平常 agent 做完一步就停下來等你。可是有時候，你想把整份待辦清單交出去，做完再回來看。

最簡單的做法要用到 **hook**，也就是工具在固定時刻會執行的一個小程式（Copilot 和 Claude Code 都有）。這裡的時刻是「agent 停下來了」。hook 看一眼待辦清單，要是還有沒做完的步驟，就叫 agent 繼續。這只有人能開，而且一次只對一個任務。

一個不停往前推的 hook，還得知道什麼時候該停。每條停止規則防的是一種不同的出錯：

- **步數和時間有上限**（例如 20 步或 2 小時）：失控的執行不會跑一整夜。
- **被拒絕幾次就停**（例如兩次）：agent 一直在試不准做的事，說明哪裡不對了，該由人來看。
- **沒有進展就停**（例如連推三次都沒有完成任何一步）：agent 卡在迴圈裡了。

在這個最簡單的做法裡，所有步驟都由一個 agent 做，清單短的話沒問題。可是清單一長，它的上下文就會塞滿前面每一步留下的東西：第 2 步讀過的檔案、第 5 步跑過的指令、一個失敗後又修好的測試。到第 15 步，它背著前十四步的殘留，上下文這麼滿，就會忘事、搞混。

更好的做法，像工地主任。工地主任不砌磚，而是拿著計劃和清單，把每份活寫在工作卡上交給工人，工人回報後就打勾。他的腦子之所以一直清楚，是因為每份活的細節都留在做工的工人那裡。

::: figure autorun-manager

1. **你把整份待辦清單交出去**。主 agent 代替你負責。
2. **每一步，主 agent 寫一份說明**（做什麼、哪些檔案、怎樣算做完、怎麼測），開一個新的子 agent：一個 worker。
3. **worker 做這一步和它的測試**，記下自己做了什麼，用幾行字回報：做完沒有、測試過沒過、改了哪些檔案。
4. **主 agent 把這一步打勾**，為下一步開一個新的 worker。它自己的上下文裡永遠只有計劃、清單和簡短的回報。
5. **全部做完後，reviewer 檢查整體結果**。不通過，主 agent 就開一個 worker 去修 reviewer 找到的問題。

三角色團隊不行，為什麼這樣拆就行？團隊是把同一件事按階段拆，一個 agent 搞懂，另一個要接著那份理解去做。這裡是按塊拆。每個 worker 拿到的是一整件小事，做和測都包含在內，所以主 agent 只需要知道「做完了、測試通過」就能往下走，這就過得了摘要那一關。

這樣拆也有代價，大多來自兩件事。一是每個 worker 都從零開始，手上只有那份說明。它不能回頭問，所以說明一定要寫全，它需要的都得寫下來；它還要重讀自己的檔案，所以很多小步驟加起來，比一個 agent 一路做下來貴。二是主 agent 只看得到回報，而回報不是證明。worker 說「測試通過」也可能是錯的，主 agent 卻分辨不出來。所以最後的獨立檢查很重要，主 agent 也該不時打開某一步的檔案看看。

步驟之間要是彼此依賴細節，就根本不適合這樣拆。要是第 4 步得確切知道第 3 步是怎麼做的，就把它寫下來交給下一個 worker，或者乾脆兩步都由一個 agent 做。

所以它適合很長、每一步都能獨立完成的清單。清單短，一個 agent 還是更便宜。要是你人在旁邊，把長任務拆成幾個小任務，也能拿到大部分好處。

### 4. 工具的硬性限制

每個 agent 都有一份能用的工具清單，例如讀檔案、搜尋、執行指令、改檔案。在 Copilot 裡，這是 agent 檔案裡的 `tools` 清單（Claude Code 的子 agent 也有）。和寫在指示裡的話不同，這份清單由平台強制執行，所以沒有「改檔案」這個工具的 agent，怎麼叫它都改不了檔案。

主 agent 通常什麼工具都有。所以一份工作絕不能改任何東西時，跟主 agent 說「請不要改檔案」只是請求；把這份工作交給一個沒有這個工具的子 agent，它才變成規則。

::: figure tool-limit

### 讓它成為規則，而不是請求

那怎麼確保不會有別的子 agent 跑起來？這裡碰到的，還是請求和規則的差別。在指示裡寫「不要開別的子 agent」只是請求，模型大多數時候會照做。

hook 能把它變成規則。一個在任何子 agent 啟動前執行的 hook，可以讀出子 agent 的名字，決定准或不准。它每次都會執行，模型也說服不了它。好的拒絕還會說明該改做什麼，免得 agent 再試同一件事。

### 靠檔案交接

agent 一多，工作就要在它們之間傳遞，但它們不該靠互相傳訊息來傳。比較好的做法是給每件工作一個自己的**任務資料夾**，裡面放需求、計劃、待辦清單和每次檢查的結果，agent 把檔案寫進這裡來交接。

為什麼用檔案，而不是傳訊息？因為你能打開同樣的檔案，看到發生了什麼。中斷一天，下一個會話能從檔案接著做。事後，這個資料夾就是一份紀錄，誰做了什麼、檢查怎麼說，都在裡面。

::: figure subagent-map

### 測一測你自己的設定

有一個今天就能做、不用任何額外設定的測試。挑一個你知道正確答案的任務，在你自己的工具裡做兩遍。第一遍讓 agent 檢查自己的工作；第二遍開一個新對話，只給它需求和結果，請它檢查。然後比一比，兩邊各找到了什麼。

想公平地比較兩種設定，有幾個習慣很要緊：

- 每種跑幾次，不是一次，因為 agent 不會兩次做出一樣的事。
- 兩邊用同一種方式評分，最好用腳本。
- 記下三個數：對不對、用量多少、花多久。

想重做我的測試，虛構的倉庫、四個任務和評分腳本都在 [`labs/subagents/`](../labs/subagents/README.md)，任何 agent 工具都能用。

## 多花的錢換到了什麼，拆分還有哪些代價 {#costs-and-traps}

其實就在我的測試裡，多花的錢也不是全白花。有一次，實作者漏改了兩處跨領域的引用，reviewer 抓到了，把工作退回去，全程沒有人插手。所以團隊的其他角色都撤了，我留下了 reviewer。

除此之外，拆分還有兩筆帳容易算漏。先說並行閱讀，它並不免費，因為每個 mapper 都從空的上下文開始，從零讀自己那一份。要讀的東西一個上下文裝不下時才用它，別為了幾個檔案省時間。

另一筆容易漏看的是子 agent 的用量：工具常常只顯示主對話的用量，你得看看自己的工具有沒有把子 agent 也算進去。就算看得到了，限制開幾個幫手，也不能限制它們一共花多少。更好的設計是讓主 agent 和所有子 agent 共用一個預算，子 agent 拿到的是剩下的部分，而不是自己另起一份。

## 平台廠商也這麼看嗎？ {#industry}
{status: industry}

平台廠商在方向上是一致的：agent 越多，token 多得越多。前面講並行閱讀時提到的 Anthropic 研究系統就是一例（[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)）。Claude Code 有 *agent teams*，也就是幾個 agent 組成團隊、互相傳訊息。它的文件說，「teammates 在 plan mode 下執行時，token 用量約是一般會話的 7 倍」（plan mode：每個成員先規劃再動手）。這和我的測試設定不同，數字不能直接比；而且 agent teams 還是實驗功能，預設關閉（[Manage costs](https://code.claude.com/docs/en/costs)）。VS Code 的指南則說：「讓 agent 鏈盡量淺，每個 agent 只給它真正需要的工具。」（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）

沒有一家說一個 agent 永遠比較好。把它們和我的測試放在一起看，結論是：需求清楚的單一任務，不要編排；能拆成獨立幾部分的廣泛工作，多個 agent 可能值得它的成本。

## 什麼時候刪掉這些 hook，什麼時候重新考慮拆分 {#when-to-delete-it}
{status: industry}

這一章裡的 hook（只准指定的子 agent、替幫手計數、推動無人值守的執行）之所以存在，是因為平台還不做這些事。等 Copilot 自己能只准指定的子 agent，並且能給整個任務設一份用量預算，就刪掉這些 hook。

hook 可以刪，背後的道理卻還在。真正會讓我重新考慮拆分本身的，是另外兩件事。第一件，是平台能接著用一個做完的子 agent。這樣一來，返工就不用從零開始，一個任務裡放一個很輕的協調者也許就划算了。第二件，要是哪天有比較顯示，自我檢查能抓到獨立檢查抓到的一切，那連 reviewer 都可以撤掉。
