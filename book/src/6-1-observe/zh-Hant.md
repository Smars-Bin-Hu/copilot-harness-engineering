讀這一章，只需要用過寫程式的 AI agent，例如 agent 模式的 Copilot。

## 一句話 {#in-one-sentence}

agent 寫的總結可能是錯的，日誌卻可以查證。所以每一次呼叫都記一行（不記參數），每一次拒絕也記下來；出了問題，就去讀軌跡。

## 給主管 {#for-leaders}

- **要做的決定**：要求每個 agent 任務都留下一份由程式寫的紀錄，並決定誰在什麼時候讀它。
- **風險**：沒有這份紀錄，agent 自己的總結就是唯一的說法，而總結可能是錯的。在我仔細讀過的那一次運行裡（只有一次，不是通則），agent 自己的說法完全沒提到花得最多的那次交接。
- **做對的成本**：一個小程式，每次工具呼叫寫一行，再加上運行失敗時有人花時間讀紀錄。大部分是設定的時間。
- **可以問團隊**：「上一個重要的任務，請你用紀錄，不是用 agent 的總結，告訴我它做了什麼。」

## agent 說的不對，你怎麼知道？ {#problem}

任務結束時，agent 會寫類似這樣的話：「我改了三個檔案，跑了測試，都通過。」這是做事的那一方自己講的經過。多半時候它是對的，可是錯了的話，光看這段話，你是分辨不出來的。

所以你需要一份不是 agent 寫的說法。最樸素的一種是**日誌**（log）：在事情發生的當下把它記下來，每件事一行，累積成一份清單。把一次運行的日誌從第一次呼叫讀到最後一次，看到的就是**軌跡**（trace），也就是 agent 依什麼順序做了什麼。這兩樣都算是**紀錄**。這一章說的紀錄，是任何寫下來、以後可以回頭查的事實，前提是它不是 agent 寫的。

這裡的道理其實很簡單：事情真正重要的時候，就從程式寫的紀錄去查，不要聽 agent 自己怎麼說。我第一次靠它，是在 [慎用子 agent](2-3-subagents.html) 那一章，當時我讀了那些運行的紀錄，想弄清楚三角色團隊多花的錢花到哪裡去了。在我仔細讀過的那一次運行裡（只有一次，不是通則），agent 自己的說法完全沒提到花得最多的那次交接。後面的 [讓「通過」可信](5-5-counted-checks.html) 也建立在同一個道理上：在那裡，檢查者的答案由程式存下來，不是由 agent 存。

既然 agent 的話靠不住，我們就得自己留一份紀錄。可是這份紀錄該記什麼、由誰來寫，運行出錯時又該怎麼讀？

## 記什麼、誰來寫、怎麼讀 {#how-it-works}

### 日誌由 agent 控制不了的程式來寫

先說誰來寫，因為只有不是 agent 寫的，才稱得上紀錄。適合的寫手是 **hook**，也就是工具在固定時刻執行的小程式，例如每次工具呼叫之前和之後。在呼叫之前執行的那一個，甚至可以把指令直接拒絕掉。（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html) 講它怎麼運作、哪裡有缺口。）

這件事交給 hook 很合適，原因有兩個。它每次呼叫都會執行，所以不用靠 agent 記得寫下什麼。而且日誌由 hook 來寫，agent 自己的工具根本不需要碰這些檔案，所以可以像其他受保護的檔案一樣，把它們放到 agent 碰不到的地方（[保護規則本身的檔案](4-3-guardrails.html)）。不過這兩點都有前提，就是 hook 看得到這次呼叫，而且圍住這些檔案的圍欄守得住。守不住的地方，後面「日誌的代價，和它回答不了的事」會講。

每一行放什麼，是一個選擇。在我的設定裡，每次 hook 呼叫記一行，一行裡有五樣東西：

- 事件：呼叫之前、呼叫之後、一個 prompt，或 agent 停下來；
- 工具的種類：讀、改、執行指令，或啟動子 agent；
- 結果：放行還是拒絕，以及是哪條規則拒絕的；
- 花了多久；
- 用了哪些 skill。這一項不用額外做就會出現，因為用 skill 本身就是一次工具呼叫。

你也許覺得，日誌記得越完整越好。其實**日誌不記什麼，和它記什麼一樣，都是刻意的**。它不記呼叫的參數，也不記 prompt 的文字，因為那些可能含有程式碼或機密。例外是被拒絕、或需要人確認的呼叫，這種呼叫會記下路徑和指令，並截成固定長度。理由很簡單，有東西被拒絕時，你最想知道的就是 agent 想做什麼。日誌留在電腦上，不放進 git，舊的可以刪掉。

在「只記一行」和「什麼都記」之間，還有一條折衷的路，我還沒做。做法是每次呼叫照樣只記簡短的一行，只在呼叫被拒絕、你正在除錯某個任務，或打開了某個開關的時候，才記下完整的內容，連參數都記。這樣預設不會留下機密，真正需要時又有東西可以重播。即使如此，日誌也不是拿來重播的好材料。一次運行的完整對話紀錄好得多，因為它顯示 agent 在兩次呼叫之間看到了什麼、說了什麼。日誌的用處，是告訴你該打開哪一份對話紀錄。

### 讀一次出錯的運行

整章的價值，就在這一段。假設一次運行失敗了，或是跑得怪怪的，你手上有它的軌跡，接下來要怎麼用？

1. 從症狀開始，不要從日誌的開頭開始。結果哪裡不對，是哪個檔案、哪一輪？
2. 找出第一次拒絕或失敗的呼叫。一條規則拒絕了什麼，是一條線索；一個工具失敗後又重試，是另一條。很多出錯的運行，起點都是一次小小的拒絕，agent 繞了過去，繞的方式卻沒有人想要。
3. 把 agent 的說法和紀錄擺在一起看。它說跑了測試，那有沒有一次呼叫真的跑了測試？它說某個檔案沒動，那有沒有改過那個檔案的紀錄？兩邊對不上的地方，相信紀錄。
4. 看時間和用量在哪裡跳高。如果某一個 prompt 花的時間比其他的長很多，或某一輪又把同樣的檔案讀了一遍，運行就是在那裡走偏的。
5. 判斷這是哪一種問題。是少了一條規則，還是有一條 agent 看不懂的規則？是拒絕訊息沒說該改做什麼，還是這一步模型本來就不擅長？怎麼修，取決於答案；有了軌跡，你才是在找答案，而不是在猜。

舉個例子，agent 的最後一則訊息說「測試通過」，日誌裡卻沒有任何一次呼叫執行過測試指令。第 3 步一分鐘就能抓到，可是那則訊息你讀再多遍也看不出來。

Anthropic 對評測也說過同樣的話：「你不讀很多次試驗的對話紀錄和評分，就不會知道你的評分器有沒有在好好工作。」（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

### 八個問題

有了日誌，其他紀錄就可以圍著它長出來。在我的設定裡一共有八種。要看清每一種為什麼存在，最清楚的方法是看它回答哪個問題，所以圖裡就是按問題列的。不過如果你只做一件事，就做 hook 日誌，並且把拒絕記進去。

::: figure 6-1-eight-questions

這八種不是我事先計畫好的。每一種，都是因為我一直想問同一個問題，卻沒有辦法回答，才加上去的。日誌以外的七種裡，有兩種值得在這裡多說幾句，第三種一句話就夠，另外四種看圖就行。

**讀取紀錄**回答的是「agent 讀了哪些知識庫檔案，又有哪些從來沒人讀？」（知識庫見 [知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。沒人讀的檔案，就是可以刪的候選。照規矩，放行的呼叫不記它碰了什麼，讀取紀錄是唯一的例外。它只記檔名，而且可以關掉。

**健康檢查**的方向正好反過來，它看的是設定本身，不是 agent。它查的是這些事：檔案都在不在、規則檔是否有效、hook 能不能執行（它會真的執行一次）、上次被呼叫是什麼時候、最近最慢的一次呼叫是不是太接近時間上限。它的輸出分三級：正常、警告（不擋）和錯誤（必須修）。它能在事後發現問題，卻沒辦法預防。

**固定情境**回答的是另一類問題：我改了東西之後，行為有沒有變？那是 [後面幾章](6-3-eval-tasks.html) 的內容。

### token 和時間

八個問題裡有一個是「時間和用量花在哪」，光靠 hook 回答不了。hook 看到的是呼叫，看不到模型讀了多少 token。在我的設定裡，hook 日誌不記 token，這是刻意的，因為平台自己有一份時間和用量的紀錄，再多留一份，早晚會對不上。所以，我用一個分析頁來顯示一個任務的時間和用量花在哪裡，它讀的是平台的紀錄，讀不到的時候，才退回去用 hook 日誌裡的時間。不管你從哪裡讀用量，都要先弄清楚它算的是什麼，因為主對話的數字可能不含子 agent 的（[慎用子 agent](2-3-subagents.html) 也有同樣的提醒）。

### 記錄器壞掉的時候

hook 是軟體，就一定會壞。在我的設定裡，hook 自己失敗時會放行這次呼叫，把錯誤寫進另一個檔案，健康檢查會提醒我去看。這是刻意的選擇，[把執行層當軟體來設計](4-4-enforcement-design.html) 說了為什麼它適合寫程式的 harness，以及不適合時該怎麼辦。對記錄器來說，這個選擇很容易接受，因為少一行日誌，只是證據裡的一個缺口，算不上事故。

但它帶來的後果，你得心裡有數。某段時間日誌一行也沒有，可能表示「什麼都沒發生」，也可能表示「記錄器停了」；要分辨這兩種情況，就得看那個錯誤檔。

### 三個問題，和一個今天就能跑的測試

我的設定就是這樣。想知道你自己的做到哪一步，可以先問三個問題。

1. 上一個重要的 agent 任務，你能不能用紀錄，而不是它的總結，說出它做了什麼？
2. 如果它做了你不想要的事，你會發現嗎？什麼時候發現？
3. 你的紀錄有沒有記被拒絕的，還是只記成功的？

還有一個今天就能跑的測試，不用額外設定。請你的 agent 做一件小任務，並在最後說出它執行了哪些指令，然後去看你的工具自己的工具呼叫歷史（顯示在哪裡，每個工具都不同，我沒有一一確認過），把兩份清單比對一下。如果一致，你就知道在這類任務上，總結可以信到什麼程度；如果不一致，你也就知道為什麼需要紀錄了。

## 日誌的代價，和它回答不了的事 {#costs-and-traps}

紀錄不是免費的，有一部分代價來自對平台的依賴。用量來自一個不是公開格式的檔案，平台一次更新，就可能在你不知道的時候把它改掉。真到那時，分析頁就只能顯示時間。更新之後我的會怎樣，我還沒有測過。

就算平台一切照常，日誌光留著不讀，也只是成本，換不來任何好處。所以要決定誰讀、什麼時候讀。我的做法是運行失敗的時候讀，改規則的時候讀，不是每天讀。如果團隊要留日誌，還得決定留多久、誰可以讀、能不能含個人資料。日誌要有人負責，才算得上稽核軌跡。

再來是日誌能告訴你的東西有哪些限度。hook 只看得到平台給它看的，有些動作發生在 hook 看得到的工具呼叫之外。那時日誌就有一個洞，而光看日誌，你看不到這個洞。（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html) 說了 Copilot 今天涵蓋什麼。）

還有一個洞，是我們自己刻意留下的：日誌不記參數。這保護了日誌裡的程式碼和機密，代價是光靠日誌，你沒辦法重播一次運行。要重播，就需要平台自己的紀錄，而那份紀錄你不能指望它一直留著。

日誌也不會告訴你，發生的事對不對。一份乾淨的軌跡，最後仍然可能以錯的程式碼收場。要抓住這種問題，靠的是 [讓 agent 能檢查自己的活](5-4-self-checks.html) 和 [固定的任務，用腳本打分](6-3-eval-tasks.html) 裡的檢查。

## 什麼時候可以刪掉這個 hook，什麼會留下來 {#when-to-delete-it}
{status: industry}

寫我這份日誌的 hook 之所以存在，是因為我想要一種自己擁有、自己讀得懂的紀錄格式。如果平台能提供每次工具呼叫的軌跡，可以匯出、agent 又改不了，那就用平台的，把 hook 拿掉。用量那一頁也一樣，如果平台已經顯示每個任務的用量，就把讀它會話檔的那部分拿掉。

但背後的道理不會退役。事情真正重要的時候，它應該來自程式寫的紀錄，而不是來自被評判的那一方。如果我發現八種紀錄裡有一種我從來沒打開過，我也會把這八種重新檢視一遍。
