读这一章，只需要用过一个写代码的 AI agent，比如 Copilot 的 agent 模式。

## 一句话 {#in-one-sentence}

agent 写的总结可能是错的，日志却可以核对。所以要记下每一次调用（每次一行，不含参数）和每一次拒绝；出了问题，就去读轨迹。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求每个 agent 任务都留下一份由代码写的记录，并定下谁来读、什么时候读。
- **风险**：没有这份记录，agent 自己的总结就成了关于发生过什么的唯一说法，而总结可能是错的。在我仔细读过的那一次运行里（只是一次，不是规律），agent 自己的说法对花得最多的那次交接只字未提。
- **做对的代价**：一个小程序，每次工具调用写一行，再加上运行失败时有人花时间去读记录。大部分是搭建的时间。
- **可以问团队**：“拿最近一个重要的任务，给我看 agent 做了什么，要从记录里看，不要看它的总结。”

## agent 说的不对，你怎么知道？ {#problem}

任务结束时，agent 会写类似这样的话：“我改了三个文件，跑了测试，通过了。”这是干活的人自己讲的经过。多数时候它是对的，可要是错了，光看这段话，你是看不出来的。

所以你需要一份不是 agent 写的说法。最朴素的一种是**日志**：在事情发生的当下把它写下来，一件事一行，攒成一份清单。把一次运行的日志从第一次调用读到最后一次，看到的就是**轨迹**，也就是 agent 按什么顺序做了什么。这两样都属于**记录**。这一章说的记录，是任何写下来、之后能回头查的事实，前提是它不是 agent 写的。

这里的道理其实很简单：事实真正要紧的时候，就从代码写的记录里拿，不要拿 agent 自己的话。我第一次靠它，是在[慎用子 agent](2-3-subagents.html)那一章，当时我读了那些运行的记录，想弄清三个角色的团队多花的钱去了哪里。在我仔细读过的那一次运行里（只是一次，不是规律），agent 自己的说法对花得最多的那次交接只字未提。后面的[让“通过”可信](5-5-counted-checks.html)也建立在同一个道理上：在那里，检查者的回答由代码保存，而不是由 agent 保存。

既然 agent 的话靠不住，我们就得自己留一份记录。可这份记录该记什么、由谁来写，运行出了错又该怎么读？

## 记什么，谁来写，怎么读 {#how-it-works}

### 日志由 agent 控制不了的代码来写

先说谁来写，因为只有不是 agent 写的，才算得上记录。合适的写手是 **hook**，也就是工具在固定时刻运行的一个小程序，比如每次工具调用之前和之后。在调用之前运行的那个，甚至可以把命令直接拒绝掉。（hook 怎么工作、哪里有缺口，见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)。）

这件事交给 hook 合适，原因有两个。它在每次调用时都会运行，所以不用指望 agent 记得写点什么。而且日志由 hook 来写，agent 自己的工具根本用不着碰这些文件，所以可以像其他受保护的文件一样，把它们放到 agent 够不着的地方（见[保护规则本身的文件](4-3-guardrails.html)）。不过这两条都有前提，就是 hook 看得到这次调用，而且围住这些文件的围栏守得住。守不住的地方，后面“日志的代价，和它回答不了的事”里会讲。

每一行装什么，是个取舍。在我的配置里，每次 hook 调用记一行，一行里有五样东西：

- 事件：调用前、调用后、一个 prompt，或者 agent 停下；
- 工具的种类：读、改、运行命令，或者启动子 agent；
- 结果：放行还是拒绝，以及是哪条规则拒绝的；
- 花了多长时间；
- 用到了哪些 skill。这一项不用额外做什么，因为用 skill 本身就是一次工具调用。

你也许觉得，日志记得越全越好。其实**日志不记什么，和它记什么一样，都是有意为之**。它不记调用的参数，也不记 prompt 的文字，因为那里面可能有代码或密钥。例外是被拒绝、或者需要人确认的调用，这种调用会记下路径和命令，截成固定长度。理由很简单，出现拒绝的时候，你最想知道的就是 agent 试图做什么。日志留在本机，不放进 git，旧的可以删掉。

在“只记一行”和“什么都记”之间，还有一条折中的路，我还没搭。做法是每次调用照样只记那简短的一行，只在调用被拒绝、你在调试某一个任务，或者打开了某个开关的时候，才记完整的内容，参数也一并记下。这样默认不会留下密钥，真需要的时候又有东西可以回放。即便如此，日志也不是拿来回放的好材料。一次运行的完整对话记录要好得多，因为它能显示两次调用之间 agent 看到了什么、说了什么。日志的用处，是告诉你该打开哪一份对话记录。

### 怎么读一次糟糕的运行

整章的价值，就在这一部分。假设一次运行失败了，或者跑得很奇怪，你手上有它的轨迹，接下来怎么用？

1. 从症状开始，不要从日志开头开始。结果哪里不对，是哪个文件、哪一轮？
2. 找到第一次拒绝或失败的调用。一条规则拒绝了什么，是一条线索；一个工具失败后又重试，是另一条。很多糟糕的运行，都是从一次小小的拒绝开始的，agent 绕了过去，绕的方式却谁也不想要。
3. 把 agent 的说法和记录摆在一起。它说跑了测试，那有没有一次调用真的跑了测试？它说某个文件没动，那有没有对这个文件的修改？两边对不上的地方，相信记录。
4. 看时间和用量在哪里陡增。如果某一个 prompt 比其他的久得多，或者某一轮又把同样的文件读了一遍，运行就是在那里跑偏的。
5. 判断是哪一种问题。是缺了一条规则，还是有一条 agent 看不懂的规则？是拒绝信息没说该改做什么，还是这一步模型本来就不擅长？怎么修取决于答案，而有了轨迹，你才是在找答案，而不是在瞎猜。

举个例子，agent 最后一条消息说“测试通过了”，日志里却没有任何一次调用运行过测试命令。第 3 步一分钟就能抓出来，可那条消息你读上多少遍也看不出来。

Anthropic 在评测上也说过同样的话：“除非你读了很多次试验的对话记录和评分，否则你不会知道你的评分器工作得好不好。”（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

### 八个问题

有了日志，别的记录就可以围着它长出来。我的配置里一共有八种。要看清每一种为什么存在，最好的办法是看它回答什么问题，所以图里就是按问题列的。不过如果你只做一样，就做 hook 日志，并且把拒绝记在里面。

::: figure 6-1-eight-questions

这八种不是我事先规划好的。每一种，都是因为我一再想问同一个问题，又没有办法回答，才加上的。日志之外的七种里，有两种值得在这里说几句，第三种一句话就够，另外四种看图就行。

**读取记录**回答的是“agent 读了知识库里的哪些文件，又有哪些从来没人读？”（知识库见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）。没人读的文件，就是可以删的候选。按规矩，放行的调用不记它碰了什么，读取记录是唯一的例外。它只记文件名，而且可以关掉。

**健康检查**的方向正好反过来，它看的是配置本身，不是 agent。它查的是这些事：文件都在不在，规则文件是否有效，hook 能不能运行（它会真的运行一次），上一次被调用是什么时候，最近最慢的那次调用是不是离时间限制太近。它的输出分三级：正常、警告（不拦截）和错误（必须修）。它能在事后发现问题，却预防不了。

**固定场景**回答的是另一类问题：我改了什么之后，行为有没有变？那是[后面几章](6-3-eval-tasks.html)的内容。

### token 和时间

八个问题里有一个是“时间和用量花在哪”，光靠 hook 回答不了。hook 看到的是调用，看不到模型读了多少 token。在我的配置里，hook 日志不记 token，这是有意的，因为平台自己有一份时间和用量的记录，再多记一份，迟早会对不上。所以，我用一个分析页来显示一个任务的时间和用量花在哪里，它读的是平台那份记录，读不到的时候，才退回去用 hook 日志里的时间。不管你从哪里读用量，都要先弄清它数的是什么，因为主对话的数字可能不含子 agent 的（[慎用子 agent](2-3-subagents.html)里也有同样的提醒）。

### 记录器出故障时

hook 是软件，就一定会出故障。在我的配置里，hook 本身出错时，会放行这次调用，把错误写进一个单独的文件，健康检查会提醒我去看。这是有意的选择，[把执行层当软件来设计](4-4-enforcement-design.html)讲了它为什么适合编程用的 harness，以及不适合的地方该怎么办。对记录器来说，这个选择很容易接受，因为漏了一行日志，只是证据里的一个缺口，算不上事故。

但它带来的后果你得心里有数。某段时间里日志一行也没有，可能是“什么都没发生”，也可能是“记录器挂了”，要分清这两种情况，就得看那个错误文件。

### 三个问题，和一个今天就能做的测试

我的配置就是这样。想知道你自己的做到了哪一步，可以先问三个问题。

1. 对最近一个重要的 agent 任务，你能根据记录，而不是根据它的总结，说出它做了什么吗？
2. 如果它做了你不想要的事，你会发现吗？什么时候发现？
3. 你的记录写了什么被拒绝了，还是只写了什么成功了？

还有一个今天就能做的测试，不用额外配置。让 agent 做一个小任务，并在最后说出它运行了哪些命令，然后去看你的工具自己记下的工具调用历史（在哪里看，每个工具不一样，我没有逐个查过），把两份清单对一对。如果一致，你就知道了在这类任务上，总结能信到什么程度；如果不一致，你也就明白为什么需要一份记录了。

## 日志的代价，和它回答不了的事 {#costs-and-traps}

记录不是免费的，有一部分代价来自对平台的依赖。用量来自一个不是公开格式的文件，平台一次更新，就可能在你不知道的时候把它改掉。真到那时，分析页就只能显示时间。更新之后我的会怎样，我还没有测过。

就算平台一切照常，日志光留着不读，也只是成本，换不来任何收益。所以要定下谁来读、什么时候读。我的做法是在运行失败的时候读，在改规则的时候读，不是每天都读。如果团队要留日志，还得定下留多久、谁可以读、能不能含有个人数据。日志只有在有人负责的时候，才算得上审计的依据。

再来看日志能告诉你的东西有哪些限度。hook 只看得到平台给它看的东西，有些操作发生在 hook 看得到的工具调用之外。这时日志里就有一个洞，而光看日志，你发现不了这个洞。（Copilot 现在覆盖到哪里，见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)。）

还有一个洞，是我们自己有意留下的：日志不记参数。这保护了日志里的代码和密钥，代价是光靠日志，你没法回放一次运行。要回放，就得用平台自己的记录，而那份记录你没法指望它一直留着。

日志也不会告诉你，发生的事对不对。一份干净的轨迹，最后照样可能得到错误的代码。要抓住这种问题，靠的是[让 agent 能检查自己的活](5-4-self-checks.html)和[固定的任务，用脚本打分](6-3-eval-tasks.html)里的检查。

## 什么时候可以删掉这个 hook，什么会留下来 {#when-to-delete-it}
{status: industry}

写我这份日志的 hook 之所以存在，是因为我想要一种自己拥有、自己读得懂的记录格式。如果平台能给你一份每次工具调用的轨迹，可以导出，agent 又改不了，那就用平台的，把 hook 去掉。用量页面也一样，如果平台已经按任务显示用量，就去掉读它会话文件的那一部分。

但背后的道理不会退役。事实真正要紧的时候，它应该来自代码写的记录，而不是来自被评判的那一方。如果我发现八种记录里有哪一种我从来不打开，我也会把这八种重新审视一遍。

## 在你自己的环境里试试 {#try-it}

::: prompt
找出这个项目里和这台机器上，有哪些关于 AI agent 所做之事的记录：工具自己的日志或对话记录、任何 hook 或审计设置，以及任何报告。对每一种记录，告诉我它在哪里，一条记录里有什么，agent 自己能不能编辑或删除它，它可能含有密钥或个人数据吗，谁可以读。然后说，下面这些问题里，哪些我只靠记录就能回答、不用看 agent 的总结：它运行了什么，它改了什么，什么被拒绝了。不要修改任何文件。
