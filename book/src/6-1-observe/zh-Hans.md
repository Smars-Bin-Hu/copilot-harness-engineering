读这一章，只需要用过一个写代码的 AI agent，比如 Copilot 的 agent 模式。别的都不需要。

## 一句话 {#in-one-sentence}

agent 自己写的总结可能是错的，日志却可以核对。记下每一次调用（每次一行，不含参数）和每一次拒绝；出了问题，就去读轨迹。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求每个 agent 任务都留下一份由代码写的记录，并决定谁来读、什么时候读。
- **风险**：否则 agent 自己的总结就成了对发生过什么的唯一说法，而总结可能是错的。在我仔细读过的那一次运行里（只是一次，不是规律），agent 自己的说法对花得最多的那次交接只字未提。
- **做对的代价**：一个小程序，每次工具调用写一行；再加上运行失败时有人花时间去读记录。主要是搭建的时间。
- **可以问团队**：“拿最近一个重要的任务，给我看 agent 做了什么，要从记录里看，不要看它的总结。”

## 问题 {#problem}

任务结束时，agent 会写类似这样的话：“我改了三个文件，跑了测试，通过了。”这是干活的人讲的、关于发生了什么的一个故事。多数时候它是对的。它错了的时候，光看这个故事，你看不出来。

先说三个词。

- **日志**，是发生了什么的清单，在事情发生的当下写下，一件事一行。
- **轨迹**，是一次运行的日志，从第一次调用读到最后一次：agent 按顺序做了什么。
- **记录**，是任何这样写下来、之后可以回头看的事实。在这一章里，“记录”指的是不是 agent 写的东西。

想法很简单。一个事实要紧的时候，就从代码写的记录里拿，不要拿 agent 自己的话。我最早用这个想法，是在[慎用子 agent](2-3-subagents.html)里。我读了那些运行的记录，看三个角色的团队多花的钱去了哪里。在我仔细读过的那一次运行里（所以这是一次运行，不是规律），agent 自己的说法对花得最多的那次交接只字未提。后面的一章，[让“通过”可信](5-5-counted-checks.html)，也建立在同一件事上：检查者的回答由代码保存，不由 agent 保存。

所以问题是：记什么，谁来写，运行出错时怎么读。

## 原理 {#how-it-works}

### 日志由 agent 控制不了的代码来写

**hook** 是工具在固定时刻运行的一个小程序，比如在每次工具调用之前（它可以在命令运行之前拒绝它），以及之后。（hook 怎么工作、哪里有缺口，见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)。）hook 是写日志的好地方，有两个原因。它在每次调用时都运行，所以不用指望 agent 记得写点什么。而且 agent 的工具不写日志，是 hook 写；存放日志的文件，可以像其他受保护的文件一样放到 agent 够不着的地方（见[保护规则本身的文件](4-3-guardrails.html)）。这只在 hook 看得到这次调用、围栏也守得住的时候成立。缺口见下面的“代价”。

每一行装什么，是个取舍。在我的配置里，每次 hook 调用一行：

- **事件**：调用前、调用后、一个 prompt、agent 停下。
- **工具的种类**：读、改、运行命令、启动子 agent。
- **结果**：放行，还是拒绝，以及是哪条规则拒绝的。
- **花的时间。**
- **用到的 skill**。用 skill 本身就是一次工具调用，所以不用额外做什么就能看到。

**日志不记什么，和它记什么一样是有意为之**。它不记调用的参数，也不记 prompt 的文字，因为那些里面可能有代码或密钥。例外是被拒绝、或需要人确认的调用：这种调用会记下路径和命令，截成固定长度。理由很简单。出现拒绝的时候，你唯一想知道的就是 agent 试了什么。日志留在本机，不放进 git。旧的可以删。

有一条折中的路我还没搭：对每次调用保留那一行简短的，只在被拒绝的调用、你正在调试的某一个任务、或者开关打开的时候，才打开完整的记录（参数等全都记）。这样默认不留密钥，真需要时又有东西可以回放。这件事上，运行的完整对话记录比任何日志都好，因为它显示了调用之间 agent 看到了什么、说了什么；日志告诉你该打开哪一份对话记录。

### 怎么读一次糟糕的运行

整章的价值就在这一部分。一次运行失败了，或者跑得很奇怪。你手上有轨迹。怎么用它？

1. **从症状开始，不要从日志开头开始**。结果哪里不对？哪个文件，哪一轮？
2. **找到第一次拒绝或失败的调用**。拒绝了什么的规则是一条线索。失败后又重试的工具是另一条。很多糟糕的运行，都是从一次小小的拒绝开始，agent 绕了过去，绕的方式没有人想要。
3. **把 agent 的说法放在记录旁边**。它说跑了测试？有没有一次调用真的跑了测试？它说某个文件没动？有没有对那个文件的修改？两者不一致的地方，相信记录。
4. **看时间和用量在哪里陡增**。某一个 prompt 比其他的久得多，或者某一轮又把同样的文件读了一遍，就告诉你运行是在哪里偏离的。
5. **判断是哪一种问题**。缺了一条规则？一条 agent 看不懂的规则？一条没说该改做什么的拒绝信息？还是模型本来就不擅长的一步？怎么修取决于答案，而轨迹让你得到答案，而不是瞎猜。

比如，agent 最后一条消息说“测试通过了”，日志里却没有一次调用运行过测试命令。第 3 步一分钟就能抓出来，把那条消息读上多少遍也看不出来。

Anthropic 在评测上也说了同样的话：“除非你读了很多次试验的对话记录和评分，否则你不会知道你的评分器工作得好不好。”（[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)）

### 八个问题

有了日志，别的记录就可以围着它长出来。我的配置里有八种，看清为什么，最好的办法是列出每一种回答的问题。如果你只做一样，就做 hook 日志，把拒绝记在里面。

::: figure 6-1-eight-questions

八种不是我规划出来的。每一种，都是因为我一再问同一个问题，又没有办法回答，才加上的。其中两种值得说一句，第三种一行就够。

- **读取记录**（针对知识库，见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）回答“agent 读了知识库里的哪些文件，没人读的是哪些？”它是“放行的调用不记它碰了什么”这条规矩的唯一例外：它只记文件名，而且可以关掉。没人读的文件，是可以删的候选。
- **健康检查**比较特别。它不看 agent，它看配置本身：文件都在吗，规则文件有效吗，hook 能运行吗（它真的运行一次），上次被调用是什么时候，最近最慢的一次调用是不是离它的时间限制太近了？它的输出分三级：正常、警告（不拦截）、错误（必须修）。它事后发现问题，预防不了。
- **固定场景**回答“我改了什么之后，行为变了吗？”那是[后面几章](6-3-eval-tasks.html)的内容。另外四种记录在图里列出了。

### token 和时间

hook 看到的是调用，看不到模型读了多少 token。在我的配置里，hook 日志有意不记 token：平台自己有一份时间和用量的记录，再多一份会对不上。显示一个任务的时间和用量花在哪里的页面，读的是平台那份记录；读不到时，就退回到 hook 日志里的时间。不管你从哪里读用量，都要弄清它数的是什么：主对话的数字可能不含子 agent 的（[慎用子 agent](2-3-subagents.html)里有同样的提醒）。

### 记录器出故障时

hook 是软件，会出故障。在我的配置里，hook 本身出错时，会放行这次调用，并把错误写进单独的文件；健康检查会提醒我去看。这是有意的选择，[把执行层当软件来设计](4-4-enforcement-design.html)讲了为什么它适合编程用的 harness，以及不适合的地方该怎么办。对记录器来说，它很容易接受：漏了一行日志，是证据里的一个缺口，不是事故。但要知道这一点：某段时间里日志一行也没有，可能是“什么都没发生”，也可能是“记录器挂了”。错误文件就是用来区分这两种情况的。

### 测一测你自己的配置

**三个问题：**

1. 对最近一个重要的 agent 任务，你能根据记录，而不是根据它的总结，说出它做了什么吗？
2. 如果它做了你不想要的事，你会发现吗？什么时候发现？
3. 你的记录写了什么被拒绝了，还是只写了什么成功了？

**今天就能做的测试，不用额外的配置**。让 agent 做一个小任务，并在最后说出它运行了哪些命令。然后看你的工具自己有关工具调用的历史（在哪里看，每个工具不一样，我没有逐个查过）。把两份清单对一对。如果一致，你就知道了在这类任务上总结能信到什么程度。如果不一致，你就明白了为什么需要一份记录。

## 代价和坑 {#costs-and-traps}

**用量来自一个不是公开格式的文件**。它可能在你不知道的时候改掉，那时页面就只显示时间了。这是对平台的依赖：一次更新就可能让你的用量数字失效，更新之后我的会怎样，我没有测过。

**没人读的日志，是有成本、没收益**。决定谁来读，什么时候读。我的做法是：运行失败的时候，和我改规则的时候。不是每天。如果团队要留日志，还要决定留多久，谁可以读，能不能含有个人数据。日志只有在有人负责的时候，才是审计的依据。

**hook 只看得到平台给它看的东西**。有些操作发生在 hook 看不到的工具调用之外。这时日志里有个洞，而你从日志里看不出来。（Copilot 现在覆盖到哪里，见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)。）

**不记参数是一种取舍**。它保护日志里的代码和密钥。代价是，光靠日志，你没法回放一次运行。要回放，得用平台自己的记录，而你没法指望它一直保留。

**日志显示发生了什么，不显示对不对**。一份干净的轨迹，最后仍可能得到错误的代码。[让 agent 能检查自己的活](5-4-self-checks.html)和[固定的任务，用脚本打分](6-3-eval-tasks.html)里的检查，就是管这个的。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

写我这份日志的 hook 之所以存在，是因为我想要一种我自己拥有、自己能读的记录格式。如果平台提供一份每次工具调用的轨迹，可以导出，agent 又改不了，就用那个，把 hook 去掉。用量页面也一样：如果平台按任务显示用量，就去掉读它会话文件的那一部分。

背后的道理不会退役。一个事实要紧的时候，它应该来自代码写的记录，而不是来自被评判的那一方。如果我发现八种记录里有哪一种我从来不打开，我会重新审视这八种。
