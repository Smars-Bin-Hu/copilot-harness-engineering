读这一章之前，你要读过[Hook：每次调用都会经过的执行点](2-2-hooks.html)和[把执行层当软件来设计](4-4-enforcement-design.html)，或者至少知道：hook 能拒绝一次工具调用，但它自己也会出故障。

## 一句话 {#in-one-sentence}

hook 只能拦下它看得见的东西。对绝不能碰的东西（生产环境、凭证、别人的仓库），最好的防御是压根不交给 agent。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对生产系统、凭证和其他团队的仓库，决定根本不给 agent 访问权限，而不是给了权限再用 hook 守着。
- **风险**：hook 看到的是一次调用的文本，看不到它的效果，而且它自己也会出故障。“大多数时候守得住”的守卫，拿来管撤销不了、或者不属于你的东西，是选错了工具。防住了多少起事故，我没有统计过。
- **做对的代价**：人的时间。由人来跑查询、再把答案贴回来，比直接连接慢。真正的沙箱是更大的一步，我还没有搭过。所以只在危害大或者无法撤销的地方这样做，不必到处都用。
- **可以问团队**：“把这个 agent 能打开、能运行、能连接的东西列一张清单。其中哪些是绝不能碰的？为什么 agent 够得着它们？”

## 为什么有些东西压根不该靠守 {#problem}

门口的守卫再好，也只是个守卫。他可能被骗，可能打瞌睡，也可能拿到一份错的名单。一堵没有门的墙，就没有这些问题。

可到目前为止，这一部分讲的都是守卫。hook 读的是一次调用的文本，却看不到这次调用会做什么（见[Hook：每次调用都会经过的执行点](2-2-hooks.html)）。而且 hook 本身也是会出故障的软件（见[把执行层当软件来设计](4-4-enforcement-design.html)）。VS Code 的文档也说，hook 和指令“不能替代强制执行的权限、沙箱或企业管控”。

话说回来，对 agent 做的大部分事，不完美的守卫也够用了。比如在代码项目里，hook 漏拦了一次文件编辑，改动会出现在 diff 里，撤销就是了。可有些事撤销不了，有些东西也不是你的。生产系统算一个，因为在那里一条错的命令就会改动真实数据。凭证也是一个：泄露一次就收不回来。至于别的团队的仓库，你根本没有资格在那里犯错。

而对这些东西，“大多数时候守得住”的守卫是选错了工具。它们需要的是一个比 agent 还老的想法，叫**最小权限**：只给程序完成工作所需要的，别的一概不给。讲 prompt 注入的安全指南，也把同一个想法列为防御措施的第一条，“落实权限控制和最小权限访问”（[OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)）。agent 够不着的东西，谁也没法说服它、骗它或者把它搞糊涂，让它去碰，自然也用不着 hook 去拦。

所以对高风险的工作，最小权限是首选，前面几章讲的 hook 排第二。这就留下一个实际的问题：活还得让 agent 干，怎么才能把东西拿走，又不把活一起拿走？

## 把东西挪出 agent 够得着的范围 {#how-it-works}

::: figure 4-5-reach

办法是对每样危险的东西都问一次：**我能不能把工作安排成 agent 根本用不着它**？很多时候是可以的，做法有四种。

### 1. 给它要改的文件的副本，不给整个工作区

假设 agent 要改的代码放在一个很大的共享仓库里。省事的做法是打开这个仓库，让 agent 随便逛，可这样一来，每个文件都在它够得着的范围里，既有它该改的，也有上千个它不该碰的。

另一种做法是先想好这项工作会碰到什么，只把这些交出去。在我的配置里，如果工作落在一个目标仓库上，agent 会照一份计划干活，计划里写明了要改哪些文件。只有这些文件会被取出来，作为副本放进任务自己的文件夹（见[管任务，不管对话](5-1-tasks.html)），agent 改的就是这些副本。你的工作树、当前分支和已有的提交，都不会被改动。

写回真实仓库是单独的一步，要由人审批（见[两道门：人在哪里审批](5-3-two-approvals.html)里的第二道门）。这一步把文件写到一个**新分支**上，而且不提交，所以哪里不对，把分支删掉就行。这样一来，agent 犯的错就被限制在一个只为这个任务存在的文件夹里。这个文件夹仍然有 hook 守着，但就算 hook 出了故障，最坏也不过是一份坏的副本，而不是一个坏的仓库。

命令也照这个思路处理。推送、开 pull request、硬重置（reset hard）、清理（clean）这类命令，agent 从不运行，只由人来运行。守卫要是在推送上判断错了，泄露就收不回来。而一条用不了的命令，不可能出错。

### 2. 从不连接环境，让人去跑查询

agent 到底要从生产环境得到什么？通常不是一个连接，而是一条事实：“这张表里有什么”“部署的是哪个版本”“这个作业存不存在”。而事实，是可以由人去取的。

我的配置不给 agent 凭证，也不给它连接任何环境的工具。这是使用上的规则，不是沙箱的保证，两者的差别后面还会讲到。agent 需要只有环境才能告诉它的信息时，会把问题写在一个固定的位置。问题后面附着一条只读的命令或查询，人拿来就能原样运行。人跑完，把答案贴回来。agent 会等到下一次停下来时再问，不会在干活干到一半时问。

::: figure 4-5-ask-a-person

这要花时间，我不假装不是：人就是比连接慢。换来的是三件事。agent 没有通往生产环境的路，所以注入的文本、一次错误的猜测、一个出故障的 hook，都够不着生产环境。每一条来自环境的事实都记了下来，连同是谁跑的。而且查询运行之前，人就已经看过它了，这正是你本来就想要的审查。（不过，人贴回来的答案本身也是不可信的文本，见[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)。）

### 3. 凭证和密钥不进上下文

连接拿掉了，密钥本身却还在。问题是，agent 上下文里的任何东西都可能被送到别处，比如写进文件、放进命令、在摘要里复述一遍。所以 agent 见过的秘密，就是可能泄露的秘密，哪怕 agent 并没有恶意。一个模型在调试时把 token 抄进一行日志，损害就已经造成了。

下面四条习惯就是由此来的。它们是一种设计，效果我没有量过。

- 不要把秘密放进 agent 会读的文件。规则、笔记和知识库文件里不放值，只写值存在哪里、归谁管。
- 让需要秘密的程序在用的那一刻，自己从专门存放它的地方去拿，而不是经过 agent 转手。agent 写“运行部署脚本”，密钥由脚本持有。
- agent 自己用的访问权限，配一把受限的密钥：只读、只限一个项目、很快过期。这样就算泄露了，影响也不大。
- 管住 agent 可能不经意读到的地方，比如它所在 shell 的环境变量、home 目录里的配置文件。这些很容易忘。

### 4. 堵上出路

让秘密不被看见只是一部分。另一部分是出路：一个秘密要是送不出去，危险就小得多。如果 agent 的命令能连到互联网上的任何地址，它能读到的任何东西就都能被送出去。如果它只能连一份简短的清单里的地址，损害就有限。这是[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)里的第三个圆，我在那一章细讲。这里只想说一点：网络访问也是一种权限，和别的权限一样，agent 需要什么就给什么。

### 什么时候该上真正的沙箱

前面这些办法都是让 agent 少拿一些。可我在第二种做法里说过，这只是使用上的规则，不是保证。**沙箱**或**容器**不一样，它是操作系统设下的一道边界，围住 agent 运行的一切。在边界里面，agent 想怎么干都行，就算命令写得再巧妙，围墙也不会倒。hook 做不到这一点，因为它只读文本。

我的 harness 没有沙箱。终端命令能写用户能写的任何路径，而 hook 只拦得住常见的写法。harness 自己的设计笔记里说得很明白，要强隔离，就得用操作系统或者容器。如果你遇到下面任何一种情况，就该比我更早去看看沙箱：

- agent 在没人盯着的情况下运行命令（见[慎用子 agent](2-3-subagents.html)和后面讲无人值守的各章）；
- 项目涉及生产环境、凭证或者别的团队的仓库；
- agent 能运行来路你控制不了的代码。

Anthropic 那篇讲给 Claude Code 做沙箱的文章，有一点值得照抄：有效的沙箱需要文件系统隔离和网络隔离同时具备。没有网络隔离，被劫持的 agent 能把你的文件送出去；没有文件系统隔离，它能逃出沙箱连上网络（[Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)）。只有一样是不够的。落到实际做法上，就是一个有自己网络规则的容器或虚拟机，而不只是一个文件夹。

不过，沙箱也不是魔法。VS Code 文档说自己的沙箱是“额外的一层”，“不是虚拟机或用户账户的边界”，所以要读清楚你用的那个管什么、不管什么。VS Code 的沙箱我没有测过。

### 测试你自己的配置

对每样绝不能碰的东西，都值得问三个问题。

1. 它到底在不在 agent 够得着的范围内？列出 agent 能打开、能运行、能连接的东西，把用不着的划掉。
2. 如果今天你的 hook 和指令都失灵了，agent 拿它能做的最坏的事是什么？
3. 有没有一个由人来做的步骤，可以代替一个连接或一把密钥？

还有一个今天就能做、一分钟就够的测试。按你的 agent 打开终端的方式打开一个终端，运行 `env`，看看变量的名字。再列出你 home 目录里存着密钥或 token 的文件，问问自己 agent 能不能读到它们。如果你不喜欢这个答案，这就是你要修的第一件事，而且用不着 hook。

## 少给要付出什么，又在哪里不够 {#costs-and-traps}

少给是有代价的。一部分代价落在工作上，因为 agent 够不着它需要的东西，就会停下来，或者做得更差。这会让多少任务失败，我没有数字，所以撤掉权限时要留意。另一部分落在人身上，因为让人去问比直接连接慢。这对生产环境来说值得，对读一个公开文件来说就不值得了。这个办法用在危害大或者无法撤销的地方就好，不必到处都用。

副本还带来一个自己的坑。agent 改的是文件的副本，如果工作进行期间真实仓库动了，写回时就得应付这种变化。任务要尽量短，写回之前先检查 diff。

最小权限也只和你的清单一样好。要是你忘了某个配置文件里还有一把密钥，agent 就拿到了它。上面那个测试，就是用来找出这类东西的。

这些都不等于 hook 不重要。对绝不能碰的东西，不给是最好的防御，但对其他一切，hook 是便宜的、一直开着的检查，是次好的防御。我两样都用。这一章的主张说的是顺序：先拿掉，再守卫。

这些我都没有测量过，也没有统计过它防住了多少起事故。我能说的是，这样的设计更容易推理：不存在的东西，没法被滥用。

## OWASP 和 VS Code 也这么看吗？ {#industry}
{status: industry}

这两个来源前面都出现过，放在一起看，指的是同一个方向。OWASP 的 prompt 注入防御清单里有“落实权限控制和最小权限访问”和“高风险操作要求人工审批”（[OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)）。VS Code 文档说 hook 和指令“不能替代强制执行的权限、沙箱或企业管控”，并把自己的沙箱描述为“额外的一层”，而不是“虚拟机或用户账户的边界”（[Hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)、[Security](https://code.visualstudio.com/docs/copilot/security)）。两边都没说 hook 没用，只是说光靠它不够。

## 什么时候可以删掉“让人去问”这一步 {#when-to-delete-it}
{status: industry}

让人去跑查询这一步之所以存在，是因为我不信任一个拿着实时连接的 agent。如果有一天平台提供了这样一种连接：强制只读、限定在一张表、有日志、agent 改不了，那么对那份数据，让人去问这一步就可以去掉。另一部分，也就是不交出用不着的东西，不会退役。它是原则，不是权宜之计。

## 在你自己的环境里试试 {#try-it}

::: prompt
列出这个 agent 在这个项目里按现在的运行方式能够到的一切：它能读或写的文件夹和文件、能运行的 shell 命令、连接的工具和 server、在环境或配置文件里看得到的账号或凭证，以及它能调用的网络地址。通过读配置和项目文件来做，不要连接任何东西。把每一项标成工作需要或者不需要，并把生产环境、凭证、别的团队的仓库标出来。不要修改任何文件，也不要打印秘密的值，只说它们放在哪里。
