读这一章之前，你要读过[Hook：每次调用都会经过的执行点](2-2-hooks.html)和[把执行层当软件来设计](4-4-enforcement-design.html)，或者至少知道：hook 能拒绝一次工具调用，但它自己也会出故障。

## 一句话 {#in-one-sentence}

hook 只能拦下它看得见的东西。对绝不能碰的东西（生产环境、凭证、别人的仓库），最好的防御是压根不交给 agent。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对生产系统、凭证和其他团队的仓库，决定根本不给 agent 访问权限，而不是用 hook 去守着这份访问权限。
- **风险**：hook 看到的是一次调用的文本，看不到它的效果，而且它会出故障。“大多数时候守得住”的守卫，用来管无法撤销、或者不属于你的东西，是选错了工具。我没有统计过防住了多少起事故。
- **做对的代价**：人的时间。由人来跑查询、把答案贴回来，比直接连接慢。真正的沙箱是更大的一步，我还没有搭过。用在危害大或者无法撤销的地方，不是到处都用。
- **可以问团队**：“把这个 agent 能打开、能运行、能连接的东西列一张清单。其中哪些是绝不能碰的？为什么 agent 够得着它们？”

## 问题 {#problem}

门口再好的守卫，也还是守卫。他可能被骗，可能睡着，也可能拿到一份错的名单。一堵没有门的墙，就没有这些问题。

这一部分到目前为止讲的都是守卫。hook 读的是一次调用的文本，看不到它的效果（见[Hook：每次调用都会经过的执行点](2-2-hooks.html)），而 hook 本身也是会出故障的软件（见[把执行层当软件来设计](4-4-enforcement-design.html)）。用 VS Code 文档的话说，hook 和指令“不能替代强制执行的权限、沙箱或企业管控”。

agent 做的大部分事，这样就够了。在代码项目里，编辑文件时漏掉的一次拦截，能在 diff 里看到，也能撤销。但有些东西撤销不了，有些东西不是你的：

- 生产系统，一条错的命令就会改动真实数据；
- 凭证，一次泄露就收不回来；
- 别的团队的仓库，你没有资格在那里犯错。

对这些，“大多数时候守得住”的守卫是选错了工具。这一章的想法比 agent 还老：**最小权限**。只给程序完成工作所需要的，别的一概不给。关于 prompt 注入的安全指南，把同一个想法列在防御措施的第一条：“Enforce privilege control and least privilege access”（[OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)）。agent 够不着的东西，就没法被说服、被骗、被搞糊涂去碰它，也不需要 hook 去拦什么。对高风险的工作，这是首选，前面各章讲的 hook 排第二。（本章末尾有一个一分钟就能做的测试。）

## 原理 {#how-it-works}

::: figure 4-5-reach

方法是对每样危险的东西问一次：**我能不能安排好工作，让 agent 根本用不着它**？常常是可以的。有四种办法。

### 1. 给它要改的文件的副本，不给整个工作区

假设 agent 要改的代码放在一个很大的共享仓库里。省事的做法是打开那个仓库，让 agent 随便逛。这样每个文件都够得着：它该改的，和它不该碰的上千个。

另一种做法是先决定这项工作会碰哪些文件，只把那些交出去。在我的配置里，对一个目标仓库，agent 照一份计划干活，计划里写明了要改的文件。只有这些文件被取出来，作为副本放进任务自己的文件夹（见[管任务，不管对话](5-1-tasks.html)）。agent 改的是副本。你的工作树、你当前的分支和已有的提交都不会被改动。

写回真实仓库是单独的一步，由人审批（见[两道门：人在哪里审批](5-3-two-approvals.html)里的第二道门）。它把文件写到一个**新分支**上，而且不提交。如果哪里不对，把分支删掉就行。所以 agent 的错误，被限制在一个只为这个任务存在的文件夹里。这个文件夹仍然有 hook 守着，但就算 hook 出了故障，最坏也不过是一份坏的副本，而不是一个坏的仓库。

另外：推送、开 pull request、硬重置（reset hard）、清理（clean）这类命令，agent 从不运行，由人来运行。一个对推送判断错了的守卫，造成的是收不回来的泄露。一条根本用不了的命令，就不会出错。

### 2. 从不连接环境，让人去跑查询

agent 要从生产环境得到什么？通常不是一个连接，而是一条事实：“这张表里有什么”“部署的是哪个版本”“这个作业存不存在”。事实可以由人去取。

我的配置不给 agent 凭证，也不给它连接任何环境的工具。这是使用上的规则，不是沙箱的保证（见最后一节）。当它需要只有环境才能告诉它的信息时，就把问题写在一个固定的位置。每个问题都附一条只读的命令或查询，人可以原样运行。人跑完，把答案贴回来。agent 在下一次停下来时提问，不会在干活干到一半时问。

::: figure 4-5-ask-a-person

这要花时间，我不假装不是：人比连接慢。作为交换，有三件事成了真的。agent 没有通往生产环境的路，所以注入的文本、一次错误的猜测、一个出故障的 hook，都够不着生产环境。（人贴回来的答案本身也是不可信的文本，见[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)。）每一条来自环境的事实都被记了下来，连同是谁跑的。而且人在查询运行之前就看到了它，这正是你本来就想做的审查。

### 3. 凭证和密钥不进上下文

agent 上下文里的任何东西，都可能被送到别处：写进文件、放进命令、在摘要里重复一遍。所以 agent 见过的秘密，就是可能泄露的秘密，而 agent 不必有恶意。一个模型在调试时把 token 抄进一行日志，损害就已经造成了。

下面是一种设计，不是我测量过的东西：

- **不要把秘密放进 agent 会读的文件**。规则、笔记和知识库文件里不放值，只写值存在哪里、归谁管。
- **让需要秘密的程序自己去拿**，在使用的那一刻、从专门存放它的地方拿，而不是经过 agent 转手。agent 写“运行部署脚本”，密钥由脚本持有。
- **给 agent 自己用的访问，用受限的密钥**：只读、限定一个项目、很快过期。这样泄露了也影响不大。
- **管住 agent 可能不经意读到的地方**：它所在 shell 的环境变量、home 文件夹里的配置文件。这些很容易忘。

### 4. 堵上出路

读不是唯一的危险。一个送不到任何地方的秘密，危险小得多。如果 agent 的命令能连到互联网上的任何地址，那么它能读到的任何东西都能被送出去。如果它只能连一份简短的清单，损害就有限。这是[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)里的第三个圆，我在那里讲。这里要说的是：网络访问和别的权限一样，是一种权限：问问 agent 需要什么，就给什么。

### 什么时候该上真正的沙箱

上面的措施，都是给 agent 更少。**沙箱**或**容器**不一样：它是由操作系统设定的边界，围住 agent 运行的一切。在里面，agent 想怎么干都行，而且就算命令写得再巧妙，围墙也不倒。hook 做不到，因为它只读文本。

我的 harness 没有沙箱。终端命令能写用户能写的任何路径，hook 只拦常见的写法。设计笔记明说了：要强隔离，就用操作系统或者容器。有下面这些情况时，比我更早去看看沙箱：

- agent 在没人盯着的情况下运行命令（见[慎用子 agent](2-3-subagents.html)和后面讲无人值守的各章）；
- 项目涉及上面三份清单里提到的任何东西；
- agent 能运行来路你控制不了的代码。

Anthropic 那篇讲给 Claude Code 做沙箱的文章，有一点值得照抄：有效的沙箱需要文件系统隔离和网络隔离两者兼备。没有网络隔离，被劫持的 agent 能把你的文件送出去；没有文件系统隔离，它能逃出沙箱连上网络（[Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)）。只有一样不够。实际做起来，就是一个有自己网络规则的容器或虚拟机，而不只是一个文件夹。

注意 VS Code 文档对沙箱的说法：它是“an added layer”，“不是虚拟机或用户账户的边界”。沙箱也不是魔法。读一读你用的那个管什么、不管什么。我没有测过 VS Code 的沙箱。

### 测试你自己的配置

对每样绝不能碰的东西，问**三个问题**：

1. 它在 agent 够得着的范围内吗？列出 agent 能打开、能运行、能连接的东西，把用不着的划掉。
2. 如果今天你的 hook 和指令都失灵了，agent 拿它能做的最坏的事是什么？
3. 有没有一个由人来做的步骤，可以代替一个连接或一把密钥？

**今天就能做的一个测试**。在一个用你的 agent 打开终端的方式打开的终端里，运行 `env`，看变量的名字。再列出你的 home 文件夹里存着密钥或 token 的文件。问一句：agent 能读到这些吗？如果你不喜欢答案，这就是你要修的第一件事，而且不需要 hook。

## 代价和坑 {#costs-and-traps}

**权限少了，也可能意味着任务失败**。agent 够不着它需要的东西，就会停下来，或者做得更差。这会让多少任务失败，我没有数字；撤掉权限时要留意。

**权限少了，人要多干活**。让人去问，比连接慢。对生产环境，这值得。对读一个公开文件，这不值得。用在危害大或者无法撤销的地方，不是到处都用。

**副本可能和原件漂开**。agent 改的是文件的副本。如果工作进行时真实仓库动了，写回时就得应付这种情况。让任务保持简短，写回之前检查 diff。

**最小权限只和你的清单一样好**。如果你忘了某个配置文件里的一把密钥，agent 就拿到了它。上面的测试就是用来找出这类东西的。

**hook 仍然重要**。不给，是对绝不能碰的东西的最好防御。对其他一切，hook 是便宜的、一直开着的检查，是次好的防御。我两个都用。这一章的主张是关于顺序的：先拿掉，再守卫。

**这些我都没有测量过**。我没有防住多少起事故的统计。我知道的是，这样的设计更容易推理：不存在的东西没法被滥用。

## 业界怎么说 {#industry}
{status: industry}

OWASP 的 prompt 注入防御清单里有“Enforce privilege control and least privilege access”和“Require human approval for high-risk actions”。（[OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)）VS Code 文档说 hook 和指令“不能替代强制执行的权限、沙箱或企业管控”，并把它们的沙箱描述为“an added layer”，不是“虚拟机或用户账户的边界”。（[Hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)、[Security](https://code.visualstudio.com/docs/copilot/security)）两边都没有说 hook 没用；都说的是光靠它不够。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

让人去跑查询这一步，之所以存在，是因为我不信任一个拿着实时连接的 agent。如果有一天平台提供了这样的连接：强制只读、限定在一张表、有日志、agent 改不了，那么对那份数据，让人去问这一步就可以去掉。另一部分，不交出用不着的东西，不会退役。它是原则，不是权宜之计。
