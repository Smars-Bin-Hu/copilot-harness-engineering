這一章假設你讀過[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)和[把執行層當軟體來設計](4-4-enforcement-design.html)，或者知道 hook 能拒絕工具呼叫，但它自己也會出錯。

## 一句話 {#in-one-sentence}

hook 只擋得住它看得到的東西。對絕對不能碰的東西（正式環境、憑證、別人的倉庫），最好的防禦是根本不交給 agent。

## 給主管 {#for-leaders}

- **要做的決定**：對正式環境、憑證和其他團隊的倉庫，決定完全不給 agent 存取權，而不是給了存取權再用 hook 守著。
- **風險**：hook 看到的是一次呼叫的文字，看不到它的效果，而且它自己也會出錯。「大多數時候守得住」的守衛，拿來管無法撤銷、或不屬於你的東西，是用錯了工具。擋掉了幾次事故，我沒有數字。
- **做對的成本**：人的時間。由人去執行查詢、再把答案貼回來，比直接連線慢。真正的沙箱是更大的一步，我還沒有做。所以只在傷害大、或無法撤銷的地方這樣做，不必到處都用。
- **可以問團隊**：「列出這個 agent 能打開、能執行、能連上的所有東西。其中哪些絕對不能碰，為什麼 agent 碰得到它們？」

## 為什麼有些東西根本不該靠守 {#problem}

門口的守衛再好，也只是個守衛。他會被騙，會打瞌睡，也可能拿到一份錯的名單。一堵沒有門的牆，就沒有這些問題。

可到目前為止，這一部分講的都是守衛。hook 讀的是一次呼叫的文字，卻看不到這次呼叫會做什麼（見[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）。而且 hook 本身也是會出錯的軟體（見[把執行層當軟體來設計](4-4-enforcement-design.html)）。VS Code 的文件也說，hooks 和指令「不能代替強制的權限、沙箱或企業管控」。

話說回來，對 agent 做的大部分事，不完美的守衛也夠用了。比如在程式碼專案裡，hook 漏攔了一次檔案編輯，改動會出現在 diff 裡，撤回來就好。可是有些事無法撤銷，有些東西也不是你的。正式環境算一個，因為在那裡一個錯的指令就會改到真實的資料。憑證也是一個：洩漏一次就收不回來。至於另一個團隊的倉庫，你根本沒有權利在那裡犯錯。

而對這些東西，「大多數時候守得住」的守衛是用錯了工具。它們需要的是一個比 agent 還老的想法，叫**最小權限**：只給程式做這份工作所需要的，別的都不給。關於 prompt injection 的安全指引，也把同一個想法列為防禦的第一條，「落實權限控制和最小權限存取」（[OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)）。agent 碰不到的東西，誰也沒辦法說服它、騙它或把它搞糊塗，讓它去碰，自然也不需要 hook 去攔。

所以對高風險的工作，最小權限是第一選擇，前面幾章的 hook 排第二。這就留下一個實際的問題：工作還是得讓 agent 做，怎麼才能把東西拿走，又不把工作一起拿走？

## 把東西移出 agent 碰得到的範圍 {#how-it-works}

::: figure 4-5-reach

辦法是對每一樣危險的東西都問一次：**我能不能把工作安排成 agent 根本不需要它**？很多時候是可以的，辦法有四種。

### 1. 給它要改的檔案的副本，不給整個工作區

假設 agent 要改的程式碼放在一個很大的共用倉庫裡。最省事的辦法是打開那個倉庫，讓 agent 隨便逛，可是這樣一來，每個檔案都在它碰得到的範圍裡，有它該改的，也有上千個它不該碰的。

另一種辦法是先想好這份工作會碰到什麼，只把那些交出去。在我的設定裡，如果工作是在一個目標倉庫上，agent 會照一份計劃工作，計劃裡點名了要改哪些檔案。只有那些檔案會被取出來，作為副本放進任務自己的資料夾（見[管任務，不管對話](5-1-tasks.html)），agent 編輯的就是這些副本。你的工作樹、目前的分支和已有的提交，都不會被改動。

寫回真正的倉庫是另一個步驟，要由人批准（見[兩道門：人在哪裡批准](5-3-two-approvals.html)的第二道門）。這一步把檔案寫在一個**新分支**上，而且不提交，所以有哪裡不對，刪掉那個分支就好。這樣一來，agent 犯的錯就只限於一個只為這個任務存在的資料夾。hook 仍然守著那個資料夾，但就算 hook 失靈，最壞也只是一份壞掉的副本，而不是一個壞掉的倉庫。

指令也照這個思路處理。push、開 pull request、reset --hard、clean 這類指令，agent 永遠不執行，只由人來執行。守衛要是在 push 上判斷錯了，洩漏就收不回來。而一個用不了的指令，不可能出錯。

### 2. 絕不連到環境；請人去跑查詢

agent 到底要從正式環境得到什麼？通常不是一條連線，而是一個事實：「這張表裡有什麼」、「部署的是哪個版本」、「這個作業存不存在」。而事實，是可以由人去取的。

我的設定不給 agent 憑證，也不給它連到環境的工具。這是使用上的規則，不是沙箱的保證，兩者的差別後面還會講到。agent 需要只有環境才答得出來的東西時，會把問題寫在一個固定的地方。問題後面附著一條唯讀的指令或查詢，人拿來就能原樣執行。人執行完，把答案貼回來。agent 會等到下一次停下來時才提問，不會在工作做到一半時問。

::: figure 4-5-ask-a-person

這要花時間，我不假裝沒有：人就是比連線慢。換來的是三件事。agent 沒有通往正式環境的路，所以被注入的文字、錯誤的猜測、失靈的 hook，都碰不到正式環境。每一個來自環境的事實都寫了下來，連同是誰執行的。而且查詢執行之前，人就已經看過它了，這本來就是你想要的審查。（不過，人貼回來的答案本身也是不可信的文字，見[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)。）

### 3. 讓憑證和金鑰不進上下文

連線拿掉了，金鑰本身卻還在。問題是，agent 上下文裡的任何東西都可能被送到別的地方，像是寫進檔案、放進指令、在摘要裡重複一遍。所以 agent 看過的祕密，就是可能洩漏的祕密，就算 agent 沒有惡意也一樣。模型在除錯時把一個 token 複製進一行日誌，傷害就已經造成了。

下面四個習慣就是由此來的。它們是一種設計，效果我沒有量過。

- 不要把祕密放在 agent 會讀的檔案裡。規則、筆記和知識檔裡不放值，只寫值放在哪裡、誰負責。
- 讓需要祕密的程式在用的那一刻，自己從專門放它的地方去拿，而不是經過 agent 傳遞。agent 寫「執行部署腳本」，金鑰在腳本手上。
- agent 自己的存取，用一把受限的金鑰：唯讀、只限一個專案、很快過期。這樣就算洩漏，影響也很小。
- 管住 agent 可能意外讀到的地方，例如它所在的 shell 的環境變數、家目錄裡的設定檔。這些很容易忘。

### 4. 把出路關上

讓祕密不被看見只是一部分。另一部分是出路：一個祕密要是送不出去，危險就小得多。如果 agent 的指令能連到網路上的任何位址，它讀得到的任何東西就都能送出去。如果它只能連一張短清單上的位址，傷害就有限。這是[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)裡的第三個圈，我在那一章再詳細處理。這裡只想說一點：網路存取也是一種權限，和其他權限一樣，agent 需要什麼就給什麼。

### 什麼時候該用真正的沙箱

前面這些辦法都是讓 agent 少拿一點。可我在第二種辦法裡說過，這只是使用上的規則，不是保證。**沙箱**或**容器**不一樣，它是作業系統設下的一道邊界，圍住 agent 執行的一切。在邊界裡面，agent 想做什麼都行，而且即使指令寫得再巧妙，牆還是守得住。hook 做不到這一點，因為它只讀文字。

我的 harness 沒有沙箱。終端機指令可以寫使用者能寫的任何路徑，而 hook 只攔得住常見的寫法。harness 自己的設計筆記說得很直接，要強的隔離，就用作業系統或容器。如果你遇到下面任何一種情況，就該比我更早考慮沙箱：

- agent 在沒有人看著時執行指令（見[慎用子 agent](2-3-subagents.html)，以及後面講無人值守工作的幾章）；
- 專案涉及正式環境、憑證或另一個團隊的倉庫；
- agent 能執行來源你控制不了的程式碼。

Anthropic 那篇講 Claude Code 沙箱的文章，有一點值得照抄：有效的沙箱需要同時有檔案系統和網路的隔離。沒有網路隔離，被劫持的 agent 能把你的檔案送出去；沒有檔案系統隔離，它能逃出沙箱連到網路（[Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)）。只有一邊是不夠的。實際做起來，就是一個有自己網路規則的容器或虛擬機器，而不只是一個資料夾。

不過，沙箱也不是魔法。VS Code 文件說自己的沙箱是「額外的一層」，而且「不是虛擬機器或使用者帳號的邊界」，所以要讀清楚你的沙箱涵蓋什麼、不涵蓋什麼。VS Code 的沙箱我沒有測過。

### 測一下你自己的設定

對每一樣絕對不能碰的東西，都值得問三個問題。

1. 它到底在不在 agent 碰得到的範圍內？列出 agent 能打開、能執行、能連上的東西，把它不需要的劃掉。
2. 如果你的 hook 和你的指令今天都失靈，agent 拿它最糟能做什麼？
3. 有沒有一個由人執行的步驟，可以取代一條連線或一把金鑰？

還有一個今天就能跑、一分鐘就夠的測試。用你的 agent 打開終端機的方式打開一個終端機，執行 `env`，看看變數的名稱。再列出你家目錄裡存放金鑰或 token 的檔案，問問自己 agent 讀不讀得到它們。如果你不喜歡這個答案，那就是你要做的第一個修正，而且不需要 hook。

## 少給要付出什麼，又在哪裡不夠 {#costs-and-traps}

少給是有代價的。一部分代價落在工作上，因為碰不到所需東西的 agent，會停下來，或做得更差。這樣會讓多少任務失敗，我沒有數字，所以去掉存取時要留意。另一部分落在人身上，因為請人去問比連線慢。這對正式環境來說值得，對讀一個公開檔案來說就不值得了。這個辦法用在傷害大、或無法撤銷的地方就好，不必到處都用。

副本還帶來一個自己的陷阱。agent 在檔案的副本上工作，如果工作進行時真正的倉庫動了，寫回時就得應付這個變化。任務要盡量短，寫回之前先檢查 diff。

最小權限也只和你的清單一樣好。你要是忘了某個設定檔裡還有一把金鑰，agent 就拿到了。上面那個測試，就是用來找這種東西的。

這些都不代表 hook 不重要。對絕對不能碰的東西，不給是最好的防禦，但對其他所有東西，hook 是便宜的、一直開著的檢查，是次好的防禦。我兩個都用。這一章的主張說的是順序：先拿掉，再守著。

這些我都沒有量過，也沒有統計過它擋掉了幾次事故。我能說的是，這樣的設計比較好推理：不在那裡的東西，不可能被誤用。

## OWASP 和 VS Code 也這麼看嗎？ {#industry}
{status: industry}

這兩個來源前面都出現過，放在一起看，指的是同一個方向。OWASP 對 prompt injection 的防禦清單包括「落實權限控制和最小權限存取」和「高風險動作要求人批准」（[OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)）。VS Code 文件說 hooks 和指令「不能代替強制的權限、沙箱或企業管控」，並把自己的沙箱描述成「額外的一層」，而不是「虛擬機器或使用者帳號的邊界」（[Hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)、[Security](https://code.visualstudio.com/docs/copilot/security)）。兩邊都沒有說 hook 沒用，只是說只靠它不夠。

## 什麼時候可以刪掉「請人去問」這一步 {#when-to-delete-it}
{status: industry}

由人執行查詢的這個步驟之所以存在，是因為我不信任讓 agent 拿著即時的連線。如果有一天平台提供這樣一種連線：強制唯讀、限定在一張表、有紀錄、agent 又改不了它，那麼這份資料的「請人去問」就可以去掉。另一部分，也就是不交出不需要的東西，不會退場。它是原則，不是繞路的辦法。

## 在你自己的環境試試 {#try-it}

::: prompt
列出這個 agent 在這個專案裡以它目前的執行方式能碰到的一切：它能讀或寫的資料夾和檔案、它能執行的 shell 指令、它連著的工具和 server、在它的環境或設定檔裡看得到的帳號或憑證，以及它能呼叫的網路位址。靠讀設定檔和專案檔來做，不要連到任何東西。把每一項標成工作需要或不需要，並把任何屬於正式環境、憑證或其他團隊倉庫的標出來。不要改任何檔案，也不要印出祕密的值，只說它們放在哪裡。
:::
