读这一章，请先读过[提示里的规则只是请求](4-1-requests-and-rules.html)：必须成立的规则要写成代码，不能只靠文字。

## 一句话 {#in-one-sentence}

“先问我”不是限制，因为到第一百次，人就会点“允许”。真正的限制是 agent 辩不过的拒绝，并且按动作可能弄坏多少来分级。

## 写给管理者 {#for-leaders}

- **要拍板的事**：认定“先问我”不是安全限制。不许发生的动作要拒绝，并按出错的代价分级。向人提问，留给少数需要判断的情况。
- **风险**：人到第一百次就会点“允许”，而且平台还提供了把弹窗彻底去掉的办法。VS Code 说全局自动审批“绕过所有用户审批，可能导致破坏性操作”。人们不看就点的频率有多高，我没量过。
- **做对的代价**：一小组拒绝规则，每条都附一条 agent 能据以行动的理由，再加一个人去读日志，找出触发得太频繁的规则。在沙箱里隔离，能减少弹窗的数量：Anthropic 报告说，在它自己的内部使用中，权限提示少了 84%，这是它对自己工具的数字。
- **可以问团队**：“我们的 agent 有哪些动作，可以在没人把关的情况下执行？其中有没有无法撤销的？”

## 问题 {#problem}

让 agent 安全，最显而易见的办法是让它询问。在它运行一条命令之前，弹出一个框：允许或拒绝。由你说了算，你不点，什么都不会发生。

第一天，这行得通。第一条命令，你会读。第十条，你扫一眼。到第一百条，框还没画完你就点了“允许”，因为前面九十九条都没问题。这不是懒。当几乎每个问题的正确答案都一样时，人就是这么做的。这个框已经成了拖延，不是检查。（这是我和很多人看到的情况，也是平台文档警告过的。我没量过它的频率；见末尾。）

然后平台给你一些去掉这种拖延的办法，你用了，因为拖延很烦人：

- **全部允许。** 一个设置，从此不再弹框。动作直接运行。
- **本次会话内允许。** 在某一个框上点一下，同一类动作在这个对话里就不再问了。
- **Autopilot。** agent 在没人守在键盘前的情况下继续工作。也许会弹出框，但没人去读。

VS Code 说得很直白：全局自动审批“绕过所有用户审批，可能导致破坏性操作”，而且它对命令的解析是“尽力而为”（[security](https://code.visualstudio.com/docs/copilot/security)）。它的 hooks 页面还补充说，`ask` “需要交互式的审批流程”，所以别以为它能让一个无人值守的会话停下来（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)）。

在我试过的三种模式（默认、全部允许、Autopilot）里，有一样东西始终有效：hook 做出的**拒绝**。弹框可以被关掉。拒绝没法在弹窗里一点就没了。（人仍然可以改规则本身，怎么安全地改，[保护规则本身的文件](4-3-guardrails.html)会讲。）

## 原理 {#how-it-works}

### 询问和拒绝

先把两个词说清楚。**询问**是停下来，等人说“是”。**拒绝**是不等，直接说“不”，而且每次都用同样的方式说。agent 可以说服人答应（或者人自己说服自己）。但只要程序在运行，agent 没法把程序说服得不再说“不”。

::: figure 4-2-ask-vs-refuse

所以这两者各管不同的事。

- **拒绝**不许发生的事。你绝不会批准的事，或者无法撤销的事。不该让谁对这些事一百次地说“不”；程序说一次，永远这么说。
- **询问**取决于人的判断的、而且很少出现的事。只有弹框少到有人读的时候，询问才管用。把它花在值得人关注的地方。

要紧的询问还需要一样东西：它必须经过一个 agent 自己按不到的渠道，送到人面前。对话里的弹框，可以被“本次会话内允许”关掉。我在[两道门：人在哪里审批](5-3-two-approvals.html)里再讲这一点。

### 终端是最难的情况

编辑工具很容易守。路径是调用里的一个字段，规则就是“拒绝这个路径”。

终端不是。它是 agent 最强的工具，因为你能运行的东西它都能运行。它也是最难守的，因为同一个效果可以有很多种写法：重定向、`rm`、`sed -i`、一个运行另一个脚本的脚本。hook 读的是命令的文本。它能抓到常见的写法，抓不到用变量拼出来的路径，或者先写好、之后再运行的脚本（[Hook：每次调用都会经过的执行点](2-2-hooks.html)）。所以终端上的规则永远不会“完整”。这不是跳过它们的理由。这是要老实说明它们是什么的理由：它防的是失误，不是铁了心要绕过的 agent。

### 按后果分级

如果没法拦住一切，就按出错的代价来拦。不要按任务有多难来分。难的任务可能无害，而简单的命令也可能毁掉一天。代码可以根据路径和命令判断后果，所以你不用手动为每个任务选一个级别。注意这个限度：代码看到的是命令的字面，不是它的效果。分级是根据文本做的猜测（见下面的坑）。

::: figure 4-2-grades

| 后果 | 例子 | 我怎么做 |
| --- | --- | --- |
| 只读 | 查东西、读文件 | 不拦 |
| 可以撤销的写入 | 在工作文件夹里编辑、写一份计划 | 允许，只限在划定的区域内 |
| 写进真正的仓库 | 别人会用到的代码 | agent 先在工作区里写。由人审批后，才写回去（[两道门：人在哪里审批](5-3-two-approvals.html)） |
| 无法撤销 | push、删除分支、hard reset | 拒绝。agent 永远得不到“是”。由人来做 |

规律是：出错的代价越大，agent 能自己决定的就越少。到最上面，就根本不问了。

### 以 git 为例

git 两端都有，所以是个好例子。在我的配置里，连着一个仓库时：

- **读的放行。** `status`、`diff`、`log` 之类永远不拦。
- **写的拒绝，但指一条路。** `add`、`commit`、切换分支。拒绝消息里有完整的命令和一个代码。人读完之后，在自己的终端里输入一条命令来批准，并有时间限制。批准的是那一条命令，不是笼统的 git。
- **有些动作 agent 永远批不到。** `push`、开 pull request、`reset --hard`、`clean`，以及各种强制选项。这些由人自己来运行。

为什么不全部询问？因为这三组值得不同的对待。读是免费的。写是正常的，但必须被看到。push 或 hard reset 这类事，第一百次点击就会放过去。

### 把理由写给 agent 看

一条拒绝有两个读者：你，和 agent。agent 更重要。它读这条消息，决定下一步怎么办。

只说“拒绝”的消息，会有两种结果之一：agent 再试一遍同样的事，或者试更糟的办法。好的消息做两件事：

1. **为什么**被拒绝，一句话。
2. **改做什么。**

比如，agent 在计划获批之前往代码文件夹写东西，好的理由会说：计划还没获批（计划审批是[两道门：人在哪里审批](5-3-two-approvals.html)里的第一道关卡）；先写计划，然后停下来，请人在自己的终端里审批。agent 现在知道下一步了，所以它会走这条路，而不是去找旁门。

我写每一条拒绝，都当它是 agent 能得到的唯一帮助。这和上一章的划分一样：代码负责拦，文字负责教。

## 代价和坑 {#costs-and-traps}

**拒绝不是免费的。** 太宽的拒绝会挡住正常的工作，而 agent 没法通过争辩绕过去。模式要写窄，要留一条让人批准那些不该被拒绝的事的路，还要读日志，看是哪条规则触发的。

**弹框仍然有用。** 我保留了一些“需要人”的步骤作为提醒。但我从不把它们算作保护。如果某件事必须成立，就用拒绝。

**模式总是落在后面。** 对终端来说，新的写法总能漏过去。对绝不能碰的东西，根本不要依赖模式。不要把那个东西交给 agent（[有些东西根本不给](4-5-least-privilege.html)）。

**分级是根据文本做的猜测。** 代码按字面判断一条命令，而不是看它实际做什么。一条看起来无害的命令，放行之后可能造成伤害。

**审批疲劳我没有数字。** 人们不看就点“允许”这个说法，是我和很多人看到的，也是平台文档警告过的。我没量过它的频率。

## 业界怎么说 {#industry}
{status: industry}

VS Code 的安全页面建议用沙箱，而不是单靠审批规则，并建议把自动审批限制在会话范围，而不是工作区或用户范围。它称模型辅助的权限“不是安全边界”（[security](https://code.visualstudio.com/docs/copilot/security)）。这和本章吻合：询问是图方便，拒绝才是规则，而隔离比两者都强。

隔离也从根上解决审批疲劳。在沙箱里，可以允许 agent 不经询问做得多得多，所以要点的弹框就少了。Anthropic 报告说，在它内部使用 Claude Code 时，沙箱“安全地把权限提示减少了 84%”，并且需要文件系统和网络两方面的隔离才能起作用（[Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)）。那是 Anthropic 对它自己工具的数字；VS Code 提供的沙箱，我没有测过。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

我为终端写的拒绝模式，之所以存在，是因为我没有真正的沙箱。如果你的 agent 运行在容器或者锁得很死的环境里，只能碰到你选定的东西，那这些模式大多可以去掉；边界已经在起作用了。按后果分级的做法会保留，因为它是一种思路，不是一项功能。

如果平台允许你在它自己的权限设置里写拒绝规则，使它在每种模式下都有效，就把你 hook 里的规则挪到那里去，并保留那些理由。
