这一章默认你已经读过[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)：必须成立的规则要写成代码，不能只靠文字。

## 一句话 {#in-one-sentence}

“先问我”不是限制，因为问到第一百次，人就会直接点“允许”。真正的限制是 agent 辩不过的拒绝，并且按这个动作可能弄坏多少来分级。

## 写给管理者 {#for-leaders}

- **要拍板的事**：认定“先问我”不算安全限制。不许发生的动作要拒绝，并按出错的代价分级。向人提问，只留给少数需要判断的情况。
- **风险**：问到第一百次，人就会直接点“允许”，平台甚至还提供了把弹框彻底去掉的办法。VS Code 说，全局自动审批会“绕过所有用户审批，可能导致破坏性操作”。我没量过人们有多常不看就点。
- **做对的代价**：一小组拒绝规则，每条都附一句 agent 能照着做的理由，再加一个人去读日志，找出触发得太频繁的规则。把 agent 放进沙箱隔离，弹框的数量也会减少：Anthropic 报告说，它自己内部使用时权限提示少了 84%，不过这是它对自己工具的数字。
- **可以问团队**：“我们的 agent 有哪些动作，可以在没人把关的情况下执行？其中有没有无法撤销的？”

## 询问为什么会慢慢失效？ {#problem}

要让 agent 安全，最顺手的办法就是让它先问。它每次运行命令之前，都会弹出一个框，让你选“允许”还是“拒绝”。由你说了算，你不点，什么都不会发生。

头一天，这招确实管用。第一条命令你会认真读，到第十条就只扫一眼了。等到第一百条，框还没画完你就点了“允许”，因为前面九十九条都没出过问题（这是我和很多人都见过的情况，平台文档也警告过，只是有多频繁，我没量过）。这不是懒。几乎每个问题的正确答案都一样的时候，谁都会这么做。到了这一步，这个框只是在拖时间，已经起不到检查的作用了。

拖时间总是烦人的，所以平台一给出去掉它的办法，你就会用，而且这些办法一个比一个彻底。“本次会话内允许”只要在某一个框上点一下，同一类动作在这个对话里就不会再问。“全部允许”干脆把框整个去掉。它是一项设置，打开以后，动作就直接运行。Autopilot 走得更远：agent 在没人守着键盘的时候也照样干活，就算框弹了出来，也没有人去读。

平台自己也把后果说得很直白。VS Code 警告说，全局自动审批会“绕过所有用户审批，可能导致破坏性操作”。它也承认，自己对命令的解析只是“尽力而为”（[security](https://code.visualstudio.com/docs/copilot/security)）。它的 hooks 页面还补充说，`ask` “需要交互式的审批流程”，所以别以为它能让一个无人值守的会话停下来（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)）。

那么，框没了以后，还有什么守得住？在我试过的三种模式（默认、全部允许、Autopilot）里，始终有效的只有一样东西，就是 hook 做出的**拒绝**。弹框可以被关掉，拒绝却没法在弹框里一点就过去。人仍然可以改规则本身，怎么安全地改，是[别让 Agent 改自己的规则](4-3-guardrails.html)要讲的。不过在决定拒绝什么之前，得先把拒绝和询问到底差在哪里说清楚。

## 该拒绝什么，怎么拒绝 {#how-it-works}

### 询问和拒绝

**询问**是停下来，等人说“行”。**拒绝**是不等任何人，直接说“不行”，而且每次都用同样的方式说。两者的差别在于能不能被说动。agent 可以说服一个人点头（人也可能自己说服自己），可只要程序还在运行，agent 就没法说服它收回那个“不”。

::: figure 4-2-ask-vs-refuse

正因为这样，两者各管不同的事。拒绝管的是不许发生的事，也就是你绝不会批准、或者无法撤销的那些。这类事不该让人一百次地说“不”，程序说一次，以后每次都这么说就行了。询问管的是要靠人判断、而且很少出现的事，因为弹框只有少到有人肯读，才管用。所以要把它花在值得人去关注的地方。

真正要紧的询问，还得经过一个 agent 自己按不到的渠道送到人面前，因为对话里的弹框可以被“本次会话内允许”关掉。这一点我在[哪些事必须由人来批？](5-3-two-approvals.html)里再讲。

### 终端最难守

一条拒绝好不好写，要看是什么工具。编辑工具很容易守，因为路径就是调用里的一个字段，规则写成“拒绝这个路径”就行。

终端就是另一回事了。它是 agent 手里最强的工具，因为你能运行的东西它都能运行。它也是最难守的，因为同一个效果可以有很多种写法，比如重定向、`rm`、`sed -i`，或者一个运行另一个脚本的脚本。hook 难道不能直接读命令吗？能，读文本就能抓到常见的写法。它漏掉的，是用变量拼出来的路径，或者先写好、之后再运行的脚本（[硬性规则放在哪？用 hook](2-2-hooks.html)）。这样一来，终端上的规则永远到不了“完整”。但这不等于可以不写，只是得老实承认它们能做什么：防的是失误，防不住一个铁了心要绕过去的 agent。

### 按后果分级

既然没法拦住一切，就按出错的代价来拦，而不是按任务有多难。难的任务可能毫无害处，简单的命令却可能毁掉一整天。按后果分级还有一个好处：代码可以根据路径和命令判断后果，所以你不用手动给每个任务选一个级别。问题是，代码看到的是命令的字面，不是它的效果。分级其实是根据文本做的猜测，后面讲代价的时候我还会回到这一点。

::: figure 4-2-grades

| 后果 | 例子 | 我怎么做 |
| --- | --- | --- |
| 只读 | 查东西、读文件 | 不拦 |
| 可以撤销的写入 | 在工作文件夹里编辑、写一份计划 | 允许，只限在划定的区域内 |
| 写进真正的仓库 | 别人会用到的代码 | agent 先在工作区里写。由人审批后，才写回去（[哪些事必须由人来批？](5-3-two-approvals.html)） |
| 无法撤销 | push、删除分支、hard reset | 拒绝。agent 永远得不到“是”。由人来做 |

把这张表从上往下读，规律就出来了。出错的代价越大，agent 能自己决定的就越少，到了最高一级，就根本不问了。

### 以 git 为例

git 的命令在这张表的两头都有，所以是个好例子。在我的配置里，连着一个仓库的时候，git 命令分成三组。

- 读的放行。`status`、`diff`、`log` 之类永远不拦。
- `add`、`commit`、切换分支这类写操作会被拒绝，但拒绝时会指一条路。拒绝消息里有完整的命令和一个代码，人读完之后，可以在自己的终端里输入一条命令来批准，有时间限制。批准的只是那一条命令，不是笼统的 git。
- 有些命令 agent 永远批不到，包括 `push`、开 pull request、`reset --hard`、`clean`，以及各种强制选项。这些由人自己来运行。

为什么不干脆全都询问？因为这三组值得不同的对待。读是免费的，写是正常的，但必须被人看到。可 push 或 hard reset 这类事，正是第一百次点击会放过去的，所以对它们只能拒绝。

### 把理由写给 agent 看

一条拒绝有两个读者：你，和 agent。其中更要紧的是 agent，因为读这条消息、决定下一步怎么办的是它。

如果消息只说“拒绝”，结果无非两种：agent 再试一遍同样的事，或者换一个更糟的办法。好的消息能避免这种情况：它会用一句话说清为什么被拒绝，再告诉 agent 该改做什么。

比如，agent 在计划还没获批的时候就往代码文件夹里写东西。好的理由会告诉它，计划还没获批（计划审批是[哪些事必须由人来批？](5-3-two-approvals.html)里的第一道关卡），它应该先写计划，然后停下来，请人在自己的终端里审批。这下 agent 知道下一步该做什么了，就会照着走，而不是去找旁门。

我写每一条拒绝，都当它是 agent 能得到的唯一帮助。这和上一章是同一个划分：代码负责拦，文字负责教。

## 拒绝要付出什么，又在哪里不够 {#costs-and-traps}

拒绝本身也有代价。拒绝得太宽，就会挡住正常的工作，而 agent 没法靠争辩绕过去。所以拒绝规则要写窄，要留一条路，让人能批准那些本不该被拒绝的事，还要读日志，看是哪条规则触发了。

那弹框是不是就一点用都没有了？也不是。我保留了一些“需要人”的步骤，当作提醒，但从不把它们算作保护，因为凡是必须成立的事，都用拒绝来守。

还有一个限度出在字面上。终端上的拒绝规则按字面判断一条命令，而不是看它实际做了什么，这就意味着它们总是落在后面：新的写法总能漏过去。前面说要回来讲的分级，也有同样的弱点，所以一条看起来无害的命令，分级放行之后照样可能造成伤害。对那些绝不能碰的东西，就根本不要依赖拒绝规则，干脆别把它交给 agent（[不要开放全部的权限或使用沙箱](4-5-least-privilege.html)）。

还有一个限度在我自己的证据上。审批疲劳我没有数字，只有我和很多人见过的情况，以及平台文档的警告。

## 文档为什么指向沙箱 {#industry}
{status: industry}

既然询问会慢慢失效，拒绝规则又总落在后面，还能靠什么？VS Code 的安全页面给出的答案是沙箱，并且建议优先用它，而不是单靠审批规则。对审批本身，它也一样谨慎，建议把自动审批限制在会话范围，而不是工作区或用户范围，并且说模型辅助的权限“不是安全边界”（[security](https://code.visualstudio.com/docs/copilot/security)）。这和本章的划分是吻合的：询问是图方便，拒绝才是规则，而隔离比两者都强。

隔离还能从根上解决审批疲劳。在沙箱里，可以允许 agent 不经询问做得多得多，要点的弹框自然就少了。Anthropic 报告说，在它内部使用 Claude Code 时，沙箱“安全地把权限提示减少了 84%”，而且需要文件系统和网络两方面的隔离才能起作用（[Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)）。这是 Anthropic 对它自己工具的数字。VS Code 提供的沙箱，我没有测过。

## 这些拒绝规则什么时候可以删掉 {#when-to-delete-it}
{status: industry}

我自己的这些拒绝规则什么时候能删，也要看沙箱。我为终端写的拒绝规则之所以存在，是因为我没有真正的沙箱。如果你的 agent 运行在容器或者锁得很死的环境里，只能碰到你选定的东西，那这些规则大多可以去掉，因为边界已经在起作用了。按后果分级则无论如何都会留下，因为它是一种思路，不是一项功能。

另一条出路在平台那边。如果平台允许你在它自己的权限设置里写拒绝规则，让它在每种模式下都有效，就把你 hook 里的规则挪过去，并保留那些理由。

## 在你自己的环境里试试 {#try-it}

::: prompt
检查这个项目的 agent 是怎么处理权限的：编辑器和 agent 的设置、允许列表和拒绝列表、自动批准选项，以及任何会拒绝的 hook。列出什么不经询问就运行，什么会询问人，什么会被拒绝。标出任何很难撤销的动作（push、删除、reset、部署），并说明它在这三组中的哪一组。还要说明有没有哪个设置能让弹框在整个会话中、或永久地被关掉。不要修改任何文件。
:::
