這一章假設你讀過[提示裡的規則只是請求](4-1-requests-and-rules.html)：一定要守住的規則，必須是程式碼，不能只是文字。

## 一句話 {#in-one-sentence}

「先問我」不是限制，因為問到第一百次，人就會直接點允許。真正的限制是 agent 吵不贏的拒絕，並且按這個動作可能弄壞多少來分級。

## 給主管 {#for-leaders}

- **要做的決定**：決定「先問我」不算安全限制。一定不能發生的動作，要用拒絕，並按出錯的代價分級。問人，只留給少見的、需要判斷的情況。
- **風險**：問到第一百次，人就會直接點允許，平台甚至還提供了把詢問框整個拿掉的辦法。VS Code 說，全域自動批准會「繞過所有使用者批准，可能導致破壞性的動作」。我沒有量過人有多常不看就點。
- **做對的成本**：一小組拒絕規則，每條都附一句 agent 能照著做的原因，再加一個人去看日誌，找出觸發太頻繁的規則。把 agent 關進沙箱隔離，詢問框的數量也會減少：Anthropic 說它自己內部使用時，權限提示少了 84%，不過這是它對自己工具的數字。
- **可以問團隊**：「我們的 agent 有哪些動作，不用任何人在場就能做？其中有沒有無法撤銷的？」

## 詢問為什麼會慢慢失效？ {#problem}

要讓 agent 保持安全，最直覺的辦法就是讓它先問。它每次執行指令之前，都會彈出一個框，讓你選允許還是拒絕。你說了算，沒有你點頭，什麼都不會發生。

頭一天，這招確實有用。第一個指令你會認真讀，到第十個就只掃一眼了。等到第一百個，框還沒畫完你就點了允許，因為前面九十九個都沒出過事（這是我和很多人都看過的情況，平台文件也提醒過，只是有多頻繁，我沒有量過）。這不是偷懶。幾乎每個問題的正確答案都一樣的時候，誰都會這樣做。到了這一步，這個框只是在拖時間，已經起不了檢查的作用。

拖時間總是很煩，所以平台一給出拿掉它的辦法，你就會用，而且這些辦法一個比一個徹底。「這個會話內允許」只要在某一個框上點一下，同一類動作在這次對話裡就不會再問。「全部允許」乾脆把框整個拿掉。它是一項設定，打開之後，動作就直接執行。Autopilot 走得更遠：agent 在沒人守著鍵盤的時候也照樣工作，就算框彈了出來，也沒有人看。

平台自己也把後果說得很直接。VS Code 提醒，全域自動批准會「繞過所有使用者批准，可能導致破壞性的動作」。它也承認，自己對指令的解析只是「盡力而為」（[security](https://code.visualstudio.com/docs/copilot/security)）。它的 hooks 頁面還補了一句：`ask`「需要互動式的批准流程」，所以別以為它能讓無人值守的會話停下來（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)）。

那麼，框沒了以後，還有什麼守得住？我試了三種模式（預設、全部允許、Autopilot），每一種都守住的只有一樣東西，就是 hook 發出的**拒絕**。詢問框可以被關掉，拒絕卻不能像詢問框那樣一點就過去。人仍然可以改規則本身，怎麼安全地改，是[保護規則本身的檔案](4-3-guardrails.html)要講的。不過在決定拒絕什麼之前，得先把拒絕和詢問到底差在哪裡說清楚。

## 該拒絕什麼，怎麼拒絕 {#how-it-works}

### 詢問和拒絕

**詢問**是停下來，等人說好。**拒絕**是不等任何人，直接說不，而且每次都用同樣的方式說。兩者的差別在於能不能被說動。agent 可以說服一個人點頭（人也可能自己說服自己），可是只要程式還在跑，agent 就說服不了它收回那個不。

::: figure 4-2-ask-vs-refuse

正因為這樣，兩者各管不同的事。拒絕管的是不能發生的事，也就是你永遠不會批准、或者無法撤銷的那些。這類事不該讓人說一百次不，程式說一次，以後每次都這樣說就好。詢問管的是要靠人判斷、而且很少出現的事，因為詢問框只有少到有人肯讀，才會管用。所以要把它用在值得人花注意力的地方。

真正重要的詢問，還得經過一個 agent 自己按不到的管道傳到人那裡，因為對話裡的框可以被「這個會話內允許」關掉。這一點我會在[兩道門：人在哪裡批准](5-3-two-approvals.html)再講。

### 終端機最難管

一條拒絕好不好寫，要看是什麼工具。編輯工具很好管，因為路徑就是呼叫裡的一個欄位，規則寫成「拒絕這個路徑」就行。

終端機就是另一回事了。它是 agent 手上最強的工具，因為你能執行的它都能執行。它也是最難管的，因為同一個效果有很多種寫法，比如重新導向、`rm`、`sed -i`，或者一個執行另一個腳本的腳本。hook 難道不能直接讀指令嗎？能，讀文字就攔得住常見的寫法。它漏掉的，是用變數拼出來的路徑，或者先寫好、之後再執行的腳本（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）。這樣一來，終端機上的規則永遠不會「完整」。但這不等於可以不寫，只是得老實承認它們能做什麼：防的是失誤，防不了一個鐵了心要繞過去的 agent。

### 按後果分級

既然攔不住所有的事，就按出錯的代價來攔，而不是按任務難不難。難的任務可能完全無害，簡單的指令卻可能毀掉一整天。按後果分級還有一個好處：程式可以從路徑和指令判斷後果，所以你不必替每個任務手動選等級。問題是，程式看到的是指令的文字，不是它的效果。等級其實是從文字猜出來的，後面講代價的時候我會再回到這一點。

::: figure 4-2-grades

| 後果 | 例子 | 我怎麼做 |
| --- | --- | --- |
| 只讀 | 查東西、讀檔案 | 不攔 |
| 可以撤銷的寫入 | 在工作資料夾裡編輯、寫計劃 | 允許，只限在劃定的範圍內 |
| 寫進真正的倉庫 | 別人會用到的程式碼 | agent 先寫在工作區。寫回去之前由人批准（[兩道門：人在哪裡批准](5-3-two-approvals.html)） |
| 無法撤銷 | push、刪分支、reset --hard | 拒絕。agent 永遠得不到答應。由人自己做 |

把這張表從上往下讀，規律就出來了。出錯的代價越大，agent 能自己決定的就越少，到了最高一級，就完全不問了。

### 以 git 為例

git 的指令在這張表的兩頭都有，所以是個好例子。在我的設定裡，連上倉庫之後，git 指令分成三組。

- 讀的放行。`status`、`diff`、`log` 這類永遠不攔。
- `add`、`commit`、切換分支這類寫入會被拒絕，但拒絕時會附一條出路。拒絕訊息裡有完整的指令和一個代碼，人讀完之後，可以在自己的終端機裡打一條指令來批准，有時間限制。批准只針對那一條指令，不是針對整個 git。
- 有些指令 agent 永遠批不到，包括 `push`、開 pull request、`reset --hard`、`clean`，還有強制選項。這些由人自己執行。

為什麼不乾脆全都用詢問？因為這三組值得不同的對待。讀是免費的，寫是正常的，但必須被人看到。可是 push 或 hard reset 這種事，正是第一百次點擊會放過去的，所以對它們只能拒絕。

### 把原因寫給 agent 看

一條拒絕有兩個讀者：你，和 agent。其中更要緊的是 agent，因為讀這則訊息、決定下一步怎麼做的是它。

如果訊息只寫「已拒絕」，結果不外乎兩種：agent 再試一次同樣的事，或者換一個更糟的辦法。好的訊息能避開這種情況：它會用一句話說清楚為什麼被拒絕，再告訴 agent 該改做什麼。

舉例來說，agent 在計劃還沒批准時就去寫程式碼資料夾。好的原因會告訴它，計劃還沒批准（計劃批准是[兩道門：人在哪裡批准](5-3-two-approvals.html)的第一道門），它應該先寫計劃，然後停下來，請人在自己的終端機批准。這樣一來，agent 知道下一步該做什麼，就會照著走，不去找旁門。

我把每一條拒絕都當成 agent 唯一能得到的幫助來寫。這和上一章是同一個分工：程式負責擋，文字負責教。

## 拒絕要付出什麼，又在哪裡不夠 {#costs-and-traps}

拒絕本身也有代價。拒絕得太寬，連正常的工作也會擋下來，而 agent 吵不贏它。所以規則要寫窄，要留一條路，讓人能批准那些本來不該拒絕的事，還要看日誌，知道是哪條規則在觸發。

那詢問框是不是就完全沒用了？也不是。有些「需要人」的步驟我留著當提醒，但從不把它們算作保護，因為一定要守住的事，都用拒絕來守。

還有一個限度出在字面上。終端機上的拒絕規則按指令的字面判斷，不是按它實際做了什麼，這就表示它們永遠慢一步：新的寫法總會漏過去。前面說要回來講的分級，也有同樣的弱點，所以一個看起來無害的指令，分級放行之後照樣可能造成傷害。對那些絕對不能碰的東西，就完全不要靠規則，乾脆別把它交給 agent（[有些東西根本不給](4-5-least-privilege.html)）。

還有一個限度在我自己的證據上。批准疲勞我沒有數字，只有我和很多人看過的情況，以及平台文件的提醒。

## 文件為什麼指向沙箱 {#industry}
{status: industry}

既然詢問會慢慢失效，拒絕的規則又永遠慢一步，還能靠什麼？VS Code 的 security 頁面給出的答案是沙箱，並且建議優先用它，不要只靠批准規則。對批准本身，它也一樣謹慎，建議把自動批准限定在會話範圍，不要開到工作區或使用者層級，並且說模型輔助的權限「不是安全邊界」（[security](https://code.visualstudio.com/docs/copilot/security)）。這和本章的分工是一致的：詢問是方便，拒絕才是規則，而隔離比兩者都強。

隔離還能從根上解決批准疲勞。在沙箱裡，agent 可以不問就被允許做更多事，要點的詢問框自然就少了。Anthropic 說，它內部使用 Claude Code 時，沙箱「安全地減少了 84% 的權限提示」，而且要同時有檔案系統和網路的隔離才行（[Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)）。這是 Anthropic 對自己工具的數字。VS Code 提供的沙箱，我沒有測過。

## 這些拒絕規則什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

我自己的這些規則什麼時候能刪，也要看沙箱。我在終端機上寫的拒絕規則之所以存在，是因為我沒有真正的沙箱。如果你的 agent 跑在容器或鎖死的環境裡，只能碰到你選好的東西，大部分規則就可以刪，因為邊界已經在做這份工作了。按後果分級則無論如何都會留著，因為它是一種想法，不是一個功能。

另一條出路在平台那邊。如果平台讓你在它自己的權限設定裡寫拒絕，使它在每種模式下都有效，就把你的 hook 規則搬過去，原因保留。

## 在你自己的環境試試 {#try-it}

::: prompt
檢查這個專案的 agent 怎麼處理權限：編輯器和 agent 的設定、允許和拒絕清單、自動批准的選項，以及任何會拒絕的 hook。列出哪些不用問就執行、哪些要問人、哪些被拒絕。把很難撤銷的動作（push、刪除、reset、部署）標出來，並說它屬於三組中的哪一組。另外說明有沒有任何設定，能讓詢問框在整個會話或永久被關掉。不要改任何檔案。
:::
