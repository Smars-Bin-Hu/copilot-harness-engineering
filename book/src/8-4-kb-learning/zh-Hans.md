这一章接在[地图对不对：盲抽查](8-3-kb-audit.html)后面。审计过了，地图已经可信到可以拿来学，这一章讲的是 8.1 那条路线的第四到第六步。为什么在一个大上下文里学很多东西不合适，要靠[上下文是一份预算](3-1-context-budget.html)来理解。另外有两个词是前面出现过的：**任务**是一件有计划、待办清单和自己文件的工作（[5.1](5-1-tasks.html)）；**写回**是把做完的工作一次性复制进知识库，由人审批（[5.3](5-3-two-approvals.html)）。

## 一句话 {#in-one-sentence}

从依赖树的底部往上学，每批小到一次读得完。一个对象用到的东西都先于它学过了，所以上面的卡片可以直接指向下面的卡片，不用再读一遍它们的代码。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对每个领域，审批入口、计划和最后写回知识库这三处。一个领域从哪里开始、到哪里结束，由人来选。
- **风险**：检查管的是结构，不是含义。一张卡片可以通过每项检查，却仍然讲错了某条规则是干什么的；顺序靠下的一张错误卡片，还会传到它上面的卡片。引用的行只检查是否落在对象之内，所以编造的引用也能通过。
- **做对的代价**：模型把每个对象的代码读一遍，这就是整个知识库真正的 token 成本。审查的时间可能是最慢的一环。批次大小（最多 20 个对象、约 1500 行）是我挑的数字，不是测出来的。
- **可以问团队**：“谁来审查每张卡片里的规则，意思是不是和引用的代码一致，而不只是那些行存在？”

## 学习的顺序为什么要紧？ {#problem}

既然审计已经通过，你手里就有一张可信的地图、几千个对象，想给每个对象写一张卡片。最简单的两个计划都行不通，不过看看它们怎么失败，就知道好的计划需要什么。

第一个计划是一个大 prompt：“把整个领域学完。”这样一来，agent 读过的所有东西都装在一个上下文里。上下文越装越满，agent 到后面可能会忘掉前面的，还会搞混（[上下文预算](3-1-context-budget.html)），所以我预计最后写的那些卡片质量最差，不过这只是推理，不是我做过的对比。

第二个计划是一个对象一个对象地学，顺序随意。假设 agent 从一个调用了另外三个的存储过程开始。要把它讲清楚，就得读那三个，于是它把那三个也读了。过了几个对象，它又单独碰上那三个里的一个，只好再读一遍。同样的代码就这样读了很多次，而且每张卡片写的时候，它下面的卡片都还没有。

所以，好的顺序应该先学那三个。这样存储过程的卡片就可以写“它调用 A、B 和 C”，并指向它们的卡片，agent 也不用再读它们的代码。要给整个领域排出这样的顺序，得先知道这个领域从哪里开始。

## 自底向上，一批一批地学 {#how-it-works}

### 从入口开始

**领域**（见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）是为同一项工作服务的一组对象。要学一个领域，得先说清它从哪里开始。**入口**是外部会调用的对象，比如某个页面的 controller、公开的 API、定时任务。从入口出发，地图会显示它们能碰到的一切。

**入口和边界由人来选**。脚本和调研笔记可以提议，agent 也会来问，但哪个是哪个，只有人知道。有两条边界要紧：

- **停在不归你管的代码上**。框架代码和别的团队的代码要切开，这样领域才不会长进它们里面去。
- **切开共用的对象**。被很多入口用到的对象不属于任何一个领域，所以要把它放在一边，免得一个领域吞掉所有东西。（多少个入口用到才算共用，是一个可调的设置；如果一个领域还是吞掉了其余的，可以把它调低。）

不过，这一章没有定下共用对象由谁来学、什么时候学。这件事值得单独计划，因为很多东西都依赖它们。

### 脚本定顺序

入口选好之后，脚本从入口出发，自底向上走一遍地图。什么都不用的对象排第一，其余的对象，都要等它用到的所有东西排完才轮到。然后脚本把这个顺序切成**批次**。

::: figure 8-4-bottom-up

这是一个真实的顺序，来自开源示例 spring-petclinic。先是四张表（owners、pets、types、visits），然后是映射这些表的实体，再然后是读取实体的仓库，最上面是 controller。每张 controller 卡片都指向它下面的卡片，就像前面那个存储过程的卡片可以指向 A、B 和 C。

### 一批有多大？

一批只放同一种类型的对象，因为同一类型的对象卡片格式一样，要问的问题也一样。一批还要小，最多 20 个对象、合计约 1500 行代码。我挑这些数字，是为了让一批能装进一个上下文，还留有思考的空间。例外是比这更长的对象，它自成一批，分段来读。

### 一个领域，一个任务，一次写回

一个领域的所有批次合起来是一个任务（见[管任务，不管对话](5-1-tasks.html)），这个任务里有三样东西：

- **一份计划**，列出所有批次，由人审批一次。
- **一份待办清单**，每批一步。
- **卡片**，整个领域学完之前都放在任务里。

等整个领域学完，才通过一次写回写进知识库（见[两道门：人在哪里审批](5-3-two-approvals.html)），由人审批。所以知识库里不会出现只有半个领域的情况。

任务一直在，对话却来来去去。每学两三批我就开一个新对话，说一声“继续”就行，因为计划、已经学了什么、还剩什么，都记在任务里，不在对话里。下一批，就是把已学的对象去掉之后，脚本给出的第一批。这和[跨会话的长任务](5-8-long-work.html)是同一个思路：记忆放在文件里，不放在对话里。

### 脚本在卡片上查什么

每张卡片都由模型来写，措辞是它自己的，但有两部分要由脚本检查：

- **关系行必须和地图一致**。卡片列出的“用到”，要和地图上这个对象的“用到”相同，卡片不能多加，也不能漏掉。
- **每条规则都要引用行号**，检查会确认这些行落在这个对象的代码之内。引用的行在对象之外，这条规则就是错的。

这是一张卡片的样子，取自 harness 里写卡片的指南。例子是一个存储过程，关系行就是脚本要检查的那一行。

::: code harness .github/skills/generic-kb-learn-batch/references/card.md L5-L22 "一张卡片：它是干什么的、关系（对照地图检查）、层级、带行号的规则、不知道的部分、坑。"

这两项都只管结构，而且第二项是个弱检查。它只能说明这些行存在，说明不了这些行支持这条规则，所以落在正确范围内的编造引用也能通过。至于模型有没有把一条规则*理解*对，脚本根本分不出来，要靠人审查，或者靠独立的 reviewer（[5.6](5-6-model-checks-model.html)）。引用的行是不是真的说了规则说的话，也由他们来抽查。我不会说这些检查覆盖了含义。

弱检查之外，自底向上本身也带来一个风险。指向下层卡片的卡片不再读代码，所以会继承那张卡片的错误。这样一来，顺序靠下的一张错卡片，可能一路传到上面（[8.5](8-5-kb-keep-true.html)）。

### 代码里有地图没有的调用关系

检查会拒绝和地图不一致的关系行。可如果 agent 读代码时发现一处调用关系，地图却漏了，该怎么办？它不能手动把这条关系加进卡片。检查会拒绝，而且手动改只补得了这一张，之后按同样格式写的对象还是会漏掉。它要做的是把这一处记下来，这条记录作为一个待修的新例子回到 toolkit，然后重新生成地图，再检查一遍（[8.3](8-3-kb-audit.html)）。

### 最后写架构页

所有批次做完后，模型写这个领域的架构页：目的、主要流程、从哪里开始读、坑和边界。流程是从地图上取下来的路径。模型把它们写成文字，脚本再像查卡片的关系行那样，拿地图来检查它们。这一页最后才写，却是大多数读者最先看到的部分。

### 测一测你自己的配置

1. 挑一个小领域和一个入口。
2. 让脚本或 agent 列出这个入口能碰到的一切，最深的排最前。
3. 按这个顺序学，放在一个任务里，分两三批。
4. 检查每张卡片的“用到”和地图一致，每条引用的行都在对象之内。

## 分批学要花什么，又可能在哪里出错 {#costs-and-traps}

钱花在哪里？整个知识库真正的 token 成本，是模型把每个对象的代码读一遍，脚本则是免费的。缓存可能会改变账单，因为重复上下文的缓存读取比新读便宜得多（Anthropic 文档：约十分之一），不过在 Copilot 上能省多少，我没查过（[1.1](1-1-models-and-cost.html)）。

分批还要有耐心。几百个对象的领域就有很多批，计划里要全部列出来，还必须由人审批。计划、每次写回、入口都要审批，审查的时间可能是整件事里最慢的一环。

还有一种例外：特别长的对象会打破这个模式，几千行的存储过程自成一批，分段读，它的卡片也可能更长。

顺序有用，前提是地图对。地图只要漏掉一处调用关系，顺序就是错的，卡片也会缺一条关系。盲抽查就是为这个设的。

## 什么时候批次可以调大，什么要留下 {#when-to-delete-it}

批次大小是针对今天的上下文窗口和模型猜的。如果有模型一次能可靠地读和写多得多的内容，就把批次调大，或者去测一测（[6.3](6-3-eval-tasks.html)）。自底向上的顺序是另一回事，只要卡片还指向别的卡片，它就一直有用。
