这一章接在[地图对不对：盲抽查](8-3-kb-audit.html)后面。地图现在可信了，可以拿来学。这是路线的第四到第六步。为什么在一个大上下文里学很多东西不合适，要靠[上下文是一份预算](3-1-context-budget.html)来理解。先回顾前面出现过的两个词：**任务**是一件有计划、待办清单和自己文件的工作（[5.1](5-1-tasks.html)）；**写回**是把做完的工作一次性复制进知识库，由人审批（[5.3](5-3-two-approvals.html)）。

## 一句话 {#in-one-sentence}

从依赖树的底部往上学，分成小到一次读得完的批次。一个对象用到的东西，先于它被学到，这样上面的卡片可以指向下面的卡片，不用再读一遍它们的代码。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对每个领域，审批入口、计划和最后写回知识库这三处。一个领域从哪里开始、到哪里结束，由人来选。
- **风险**：检查覆盖的是结构，不是含义。一条笔记可以通过每项检查，却仍然讲错了某条规则是干什么的；顺序靠下的一条错误笔记，还会传到它上面的笔记。引用的行只检查是否落在对象之内，编造的引用也能通过。
- **做对的代价**：模型把每个对象的代码读一遍，这是整个知识库真正的 token 成本。审查的时间可能是最慢的一环。批次大小（最多 20 个对象、约 1500 行）是我挑的数字，不是测出来的。
- **可以问团队**：“谁来审查每条笔记里的规则，意思是不是和引用的代码一致，而不只是那些行存在？”

## 问题 {#problem}

你有一张可信的地图，有几千个对象，想给每个对象写一张卡片。两个简单的计划都行不通。

**计划一：一个大 prompt**。“把整个领域学完。”一个上下文装着 agent 读过的所有东西。装满之后，agent 可能忘掉前面的，到后面还会搞混（[上下文预算](3-1-context-budget.html)），所以我预计最后写的卡片质量最差。这是推理；这几个计划我没有对比过。

**计划二：一个对象一个对象地学，顺序随意**。假设 agent 从一个调用另外三个的存储过程开始。要讲清楚它，就得读那三个，于是它也读了。几个对象之后，它自己撞上那三个之一，又读了一遍。同样的代码读了很多次，而且每张卡片写的时候，下面的卡片都还没有。

好的顺序是先学那三个。这样存储过程的卡片就可以写“它调用 A、B 和 C”，并指向它们的卡片。agent 不用再读它们的代码。

## 原理 {#how-it-works}

### 从入口开始

**领域**（见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）是为同一项工作服务的一组对象。要学一个领域，得先说清它从哪里开始。**入口**是外部会调用的对象：某个页面的 controller、公开的 API、定时任务。从入口出发，地图会显示它们能碰到的一切。

**入口和边界由人来选**。脚本和调研笔记可以提议，agent 也会来问，但哪个是哪个，只有人知道。有两条边界要紧：

- **停在不归你管的代码上**。框架代码和别的团队的代码要切开，这样领域才不会长进它们里面去。
- **切开共用的对象**。被很多入口用到的对象不属于任何一个领域。把它放在一边，一个领域才不会吞掉所有东西。（多少个入口用到才算共用，是一个可调的设置；如果一个领域还是吞掉了其余的，可以调低。）共用对象由谁来学、什么时候学，这一章没有定下来；很多东西依赖它们，所以应该有计划。

### 脚本定顺序

脚本从入口出发，自底向上走一遍地图。什么都不用的对象排第一。一个对象，要等它用到的所有东西都排完才轮到。然后脚本把这个顺序切成**批次**。

::: figure 8-4-bottom-up

下面是一个真实的顺序，来自开源示例 spring-petclinic。先是四张表（owners、pets、types、visits）。然后是映射它们的实体。再然后是读取实体的仓库。最上面是 controller。每张 controller 卡片都指向它下面的卡片。

### 一批有多大

一批是**同一种类型**的对象，最多 **20 个对象**、合计约 **1500 行**代码。我挑这些数字，是为了让一批能装进一个上下文，还留有思考的空间。比这更长的对象自成一批，分段来读。

一批只放一种类型有好处：同一类型的对象，卡片格式一样，要问的问题也一样。

### 一个领域，一个任务，一次写回

一个领域的所有批次是一个**任务**（见[管任务，不管对话](5-1-tasks.html)）。这个任务有：

- **一份计划**，列出所有批次，由人审批一次。
- **一份待办清单**，每批一步。
- **卡片**，整个领域学完之前都放在任务里。

之后，整个领域通过**一次写回**写进知识库（把写好的卡片一次性复制进知识库，见[两道门：人在哪里审批](5-3-two-approvals.html)），由人审批。所以知识库里不会出现只有半个领域的情况。

对话会来来去去。每学两三批，我就开一个新对话，说“继续”。状态由任务保存：计划、已经学了什么、还剩什么。下一批，就是把已学的对象去掉之后，脚本给出的第一批。这和[跨会话的长任务](5-8-long-work.html)是同一个思路：记忆放在文件里，不放在对话里。

### 检查模型写的东西

每张卡片由模型来写。措辞由它自己定，但有两部分由脚本检查：

- **关系行必须和地图一致**。卡片列出的“用到”，要和地图上这个对象的“用到”相同。卡片不能多加，也不能漏掉。
- **每条规则都要引用行号**，检查会确认这些行落在这个对象的代码之内。引用的行在对象之外，这条规则就是错的。这是个弱检查：它只能说明这些行存在，不能说明这些行支持这条规则。落在正确范围内的编造引用也能通过。引用的行是不是真的说了规则说的话，要由人或独立的 reviewer 抽查。

架构页上的流程同样来自地图上的路径，用同样的办法检查。

下面是一张卡片的样子，取自 harness 里写卡片的指南。例子是一个存储过程；关系行就是脚本要检查的那一行。

::: code harness .github/skills/generic-kb-learn-batch/references/card.md L5-L22 "一张卡片：它是干什么的、关系（对照地图检查）、层级、带行号的规则、不知道的部分、坑。"

指向下层卡片的卡片，会继承那张卡片的错误，因为它不再读代码。所以顺序靠下的一张错卡片，可能一路传到上面（[8.5](8-5-kb-keep-true.html)）。

没有检查的是：模型有没有把一条规则*理解*对。脚本分不出来。这要靠人审查，或者靠独立的 reviewer（[5.6](5-6-model-checks-model.html)）。我不会说这些检查覆盖了含义。

### 代码里有地图没有的调用关系

读的时候，agent 可能看到代码里有一处调用关系，地图上没有。它不能手动把这条关系加进卡片。检查会拒绝，而且之后按同样格式写的对象也会漏掉它。它要把这一处记下来，这条记录作为一个待修的新例子回到 toolkit。然后重新生成地图，再检查一遍（[8.3](8-3-kb-audit.html)）。

### 最后一步：架构页

所有批次做完后，模型写这个领域的架构页：目的、主要流程、从哪里开始读、坑和边界。流程是从地图上取下来的路径，模型把它们写成文字。这一页是大多数读者最先看到的部分。

### 测一测你自己的配置

1. 挑一个小领域和一个入口。
2. 让脚本或 agent 列出这个入口能碰到的一切，最深的排最前。
3. 按这个顺序学，放在一个任务里，分两三批。
4. 检查每张卡片的“用到”和地图一致，每条引用的行都在对象之内。

## 代价和坑 {#costs-and-traps}

- **模型把每个对象的代码读一遍**。这是整个知识库真正的 token 成本。脚本是免费的。
- **分批要有耐心**。几百个对象的领域有很多批。计划里全部列出，必须由人审批。计划、每次写回、入口都要审批，审查的时间可能是整件事里最慢的一环。
- **缓存可能改变账单**。重复上下文的缓存读取比新读便宜得多（Anthropic 文档：约十分之一）。在 Copilot 上能省多少，我没查过（[1.1](1-1-models-and-cost.html)）。
- **特别长的对象会打破这个模式**。几千行的存储过程自成一批，分段读。它的卡片可能更长。
- **顺序有用的前提是地图对**。地图漏了一处调用关系，顺序就是错的，卡片也会缺一条关系。盲抽查就是为这个设的。
- **含义没有检查**。见上文。一张卡片可以通过每项检查，却仍然讲错了某条规则是干什么的。

## 什么时候可以删掉 {#when-to-delete-it}

批次大小是针对今天的上下文窗口和模型猜的。如果有模型一次能可靠地读和写多得多的内容，就把批次调大，或者去测一测（[6.3](6-3-eval-tasks.html)）。只要卡片还指向别的卡片，自底向上的顺序就一直有用。
