這一章接在 [地圖對不對：盲抽查](8-3-kb-audit.html) 後面。抽查過了，地圖已經可信到足以拿來學，這一章講的是 8.1 那條路線的第四到第六步。為什麼把很多東西塞進一個上下文裡學並不合適，要靠 [上下文是一份預算](3-1-context-budget.html) 來說明。另外有兩個詞是前面出現過的：**任務**是一件有計劃、待辦清單和自己檔案的工作（[5.1](5-1-tasks.html)）；**寫回**是把做完的工作一次複製進知識庫，由人批准（[5.3](5-3-two-approvals.html)）。

## 一句話 {#in-one-sentence}

從依賴樹的底部往上學，每批小到一次讀得完。一個物件用到的東西都先於它學過了，所以上面的卡片可以直接指向下面的卡片，不用再讀它們的程式碼。

## 給主管 {#for-leaders}

- **要做的決定**：對每個領域，批准入口、計劃，和最後寫回知識庫這三處。一個領域從哪裡開始、到哪裡結束，由人來選。
- **風險**：檢查涵蓋的是結構，不是意思。一張卡片可以通過每個檢查，還是講錯了一條規則是做什麼的；排在底層的一張錯誤卡片，還會傳到它上面的卡片。引用的行只檢查是否落在物件裡面，所以編造的引用也能通過。
- **做對的成本**：模型把每個物件的程式碼讀一遍，這就是整個知識庫真正的 token 成本。審查的時間可能是最慢的部分。批次大小（最多 20 個物件、約 1500 行）是我挑的數字，不是量出來的。
- **可以問團隊**：「誰來審查每張卡片的規則，意思是不是和引用的程式碼說的一樣，而不只是那些行存在？」

## 學習的順序為什麼重要？ {#problem}

既然抽查已經通過，你手上就有一張可信的地圖、幾千個物件，想為每個物件寫一張卡片。最簡單的兩個計劃都行不通，不過看看它們怎麼失敗，就知道好的計劃需要什麼。

第一個計劃是一個大 prompt：「學完整個領域。」這樣一來，agent 讀過的所有東西都裝在一個上下文裡。上下文越裝越滿，agent 到後面可能會忘掉前面的，也會搞混（[上下文預算](3-1-context-budget.html)），所以我預期最後寫的卡片是最差的，不過這只是推理，不是我做過的比較。

第二個計劃是一個物件一個物件來，順序隨意。假設 agent 從一個呼叫了其他三個的預存程序開始。要好好解釋它，就得讀那三個，於是它把那三個也讀了。過了幾個物件，它又單獨遇到那三個之一，只好再讀一遍。同樣的程式碼就這樣讀了很多次，而且每張卡片寫的時候，它下面的卡片都還沒有。

所以，好的順序應該先學那三個。這樣預存程序的卡片就可以說「它呼叫 A、B 和 C」，並指向它們的卡片，agent 也不用再讀它們的程式碼。要替整個領域排出這樣的順序，得先知道這個領域從哪裡開始。

## 由下往上，一批一批地學 {#how-it-works}

### 從入口開始

**領域**（見 [知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）是為同一件工作服務的一組物件。要學一個領域，你得先說清楚它從哪裡開始。**入口**是外部會呼叫的物件，例如畫面的 controller、公開的 API、排程工作。從入口出發，地圖會顯示它們碰得到的一切。

**由人選擇入口和邊界**。腳本和一份研究筆記可以提議，agent 也會問，但哪個是哪個，只有人才知道。有兩個邊界很重要：

- **停在不歸你管的程式碼上**。框架的程式碼和別的團隊的程式碼要切開，這樣領域才不會長進它們裡面。
- **切開共用的物件**。很多入口都會用到的物件，不屬於任何單一領域，所以要把它放在一邊，免得一個領域吞掉所有東西。（要有多少個入口，物件才算共用，是一個設定；如果一個領域還是吞掉了其餘的，可以把它調低。）

不過，這一章沒有決定共用的物件由誰學、什麼時候學。這件事值得單獨計劃，因為很多東西都依賴它們。

### 腳本定順序

入口選好之後，腳本從入口出發，由下往上走一遍地圖。什麼都不用的物件排第一，其餘的物件，都要等它用到的一切排完才輪到。然後腳本把這個順序切成**批次**。

::: figure 8-4-bottom-up

這是開源範例 spring-petclinic 的真實順序。先是四張資料表（owners、pets、types、visits），然後是對應它們的 entity，再來是讀 entity 的 repository，最上面是 controller。每張 controller 的卡片都指向它下面的卡片，就像前面那個預存程序的卡片可以指向 A、B 和 C。

### 一批有多大？

一批只放同一種類型的物件，因為同一種類型的物件，卡片的形式一樣，要問的問題也一樣。一批還要小，總共最多 20 個物件、約 1500 行程式碼。我挑這些數字，是為了讓一批放得進一個上下文，還留有思考的空間。例外是比這更長的物件，它自己是一批，分段讀。

### 一個領域，一個任務，一次寫回

一個領域的所有批次合起來是一個任務（見 [管任務，不管對話](5-1-tasks.html)），這個任務裡有三樣東西：

- **一份計劃**，列出每一批，由人批准一次。
- **一份待辦清單**，每批一步。
- **卡片**，在整個領域完成之前，留在任務裡面。

等整個領域完成，才用一次寫回寫進知識庫（見 [兩道門：人在哪裡批准](5-3-two-approvals.html)），由人批准。所以知識庫從不會只有半個領域。

任務一直在，對話卻來來去去。每兩、三批之後我就開一個新對話，說一聲「繼續」就好，因為計劃、學了什麼、還剩什麼，都記在任務裡，不在對話裡。下一批，就是把學過的物件排除之後，腳本給的第一批。這和 [跨會話的長任務](5-8-long-work.html) 是同一個想法：記憶放在檔案裡，不放在對話裡。

### 腳本在卡片上檢查什麼

每張卡片都由模型寫，裡面的話是它自己的，但有兩個部分要由腳本檢查：

- **關係行必須和地圖一致**。一張卡片列的「用到」，必須和地圖上那個物件的使用一樣，卡片不能多加，也不能少掉一個。
- **每條規則都要附上行號**，檢查會確保那些行落在那個物件的程式碼裡面。引用了物件之外的行，這條規則就是錯的。

這是一張卡片的樣子，來自 harness 寫卡片的指南。例子是一個預存程序，關係行就是腳本檢查的那一行。

::: code harness .github/skills/generic-kb-learn-batch/references/card.md L5-L22 "一張卡片：它做什麼、關係（對照地圖檢查）、層級、附行號的規則、不知道的部分、陷阱。"

這兩項都只管結構，而且第二項是個弱的檢查。它只能說明那些行存在，說明不了它們支持這條規則，所以落在正確範圍內的編造引用也能通過。至於模型有沒有*正確理解*一條規則，腳本根本分辨不出來，要靠人的審查，或獨立的 reviewer（[5.6](5-6-model-checks-model.html)）。引用的行說的是不是和規則一樣，也由他們來抽查。我不宣稱這些檢查涵蓋了意思。

弱檢查之外，由下往上本身也帶來一個風險。指向下層卡片的卡片不再讀程式碼，所以會繼承那張卡片的錯誤。這樣一來，排在底層的一張錯誤卡片，就可能往上傳（[8.5](8-5-kb-keep-true.html)）。

### 程式碼顯示了地圖沒有的使用

檢查會拒絕和地圖不一致的關係行。可是如果 agent 讀程式碼時發現一處使用，地圖卻漏了，該怎麼辦？它不能手動把這處使用加進卡片。檢查會拒絕，而且手動改只補得了這一張，之後用同樣形式寫的物件還是會漏掉。它該做的是把這處使用記下來，交回 toolkit 當成待修的新例子，再重建地圖、檢查一次（[8.3](8-3-kb-audit.html)）。

### 最後寫架構頁

所有批次完成後，模型寫這個領域的架構頁：它的用途、主要的流程、從哪裡開始讀、陷阱和限制。流程是從地圖取來的路徑。模型把它們寫成文字，腳本再像檢查卡片的關係行那樣，拿地圖來檢查它們。這一頁最後才寫，卻是多數讀者最先看到的部分。

### 測你自己的設定

1. 挑一個小的領域和一個入口。
2. 請腳本或 agent 列出這個入口碰得到的東西，最深的排最前。
3. 照那個順序學，在一個任務裡，分兩、三批。
4. 檢查每張卡片的「用到」等於地圖上的，而且每一行引用都在物件裡面。

## 分批學要花什麼，又可能在哪裡出錯 {#costs-and-traps}

錢花在哪裡？整個知識庫真正的 token 成本，是模型把每個物件的程式碼讀一遍，腳本則是免費的。快取可能改變帳單，因為重複上下文的快取讀取比全新的便宜得多（Anthropic 的文件：約十分之一），不過在 Copilot 上能省多少，我沒有確認（[1.1](1-1-models-and-cost.html)）。

分批還需要耐心。幾百個物件的領域就有很多批，計劃要把它們全列出來，人還必須批准。加上計劃、每次寫回和入口的批准，審查的時間可能是這份工作裡最慢的部分。

還有一種例外：很長的物件會打破這個規律，幾千行的預存程序自己是一批，分段讀，它的卡片也可能比較長。

順序有用，前提是地圖對。地圖只要漏掉一處使用，排出的順序就是錯的，卡片也會少一條關係。抽查就是為此而設的。

## 什麼時候批次可以加大，什麼要留下 {#when-to-delete-it}

批次大小是照今天的上下文視窗和模型猜的。如果模型一次能可靠地讀寫多得多的內容，就把批次加大，或者實際量一量（[6.3](6-3-eval-tasks.html)）。由下往上的順序是另一回事，只要卡片還指向別的卡片，它就一直有用。
