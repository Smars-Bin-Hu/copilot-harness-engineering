這一章假設你用過 AI 程式 agent，並且知道 hook 是平台在工具呼叫之前執行的程式碼（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）。

## 一句話 {#in-one-sentence}

管任務，不管對話：一個任務一個資料夾。這份工作可能弄壞什麼，決定它要過哪些門；它的種類，決定怎樣才算做完。

## 給主管 {#for-leaders}

- **要做的決定**：批准以工作、而不是對話，作為工作的單位：一個任務一個資料夾，附一份交接檔，照顧的程度跟著出錯可能弄壞什麼走。
- **風險**：對話會被縮短或結束，新的對話什麼也不知道。另一個陷阱是流程太重：我的第一版設計有一個重的等級，帶一組分角色的 agent，在一個小測試裡花了約 4.5 倍的用量和 6 倍的時間，在需求明確的任務上沒有任何好處（四個任務，各跑一次，所以讀方向，不要讀倍數）。
- **做對的成本**：第一步只是每個任務一個資料夾，裡面一份交接檔。任務值得時才加更多檔案，隨口問的問題什麼都不開。agent 必須讓檔案保持真實，要緊的時候人得去讀它們。
- **可以問團隊**：「如果 agent 的對話今晚消失了，明天有人能只靠檔案接手這份工作嗎？」

## 問題 {#problem}

你請一個 agent 改一條 pipeline。它讀、規劃、編輯，對話越來越長。第二天早上你開了一個新對話，問一個後續問題。新的 agent 從沒見過第一個對話。或者第一個對話被工具縮短了，它忘了自己為什麼做了那些選擇（[長對話會變差](3-2-long-sessions.html)）。

對話是錯的管理對象。它會被壓縮，會結束，而且一個對話裡可能放著三件毫不相干的工作。你真正在乎的是工作：被要求做什麼、決定了什麼、做到哪裡了、有沒有被檢查過。

所以我不再把對話當成工作的單位。單位是**任務**：一份工作，一個**任務資料夾**。需求、計劃、進度和結果，都是這個資料夾裡的檔案。任何會話，今天或下週，讀這個資料夾就能接手這個任務。

這解決了工作放在哪裡的問題。接著出現第二個問題：不是每份工作都需要同樣的照顧。改筆記裡的一個錯字，和寫進共用的倉庫，是不同的事。你怎麼決定每一份工作要有多少流程？

你可以只從第一步開始：每個任務一個資料夾，裡面一份交接檔。下面的一切，都是我在這個基礎上加的，你可以一次加一塊。

## 原理 {#how-it-works}

### 我的第一個答案是分等級，而且是錯的

我的第一版設計有三個**等級**。等級 1 輕，等級 3 重，帶一組分角色的 agent（[慎用子 agent](2-3-subagents.html)）。每份工作開始時你要選一個等級。

用了一陣子，有三件事很清楚：

- 只有中間那一級被用到。另外兩級大部分時間閒著。
- 在需求明確的任務上，重的那一級不比一個 agent 好，卻花了約 4.5 倍的用量和 6 倍的時間。那個測試很小（四個任務，各跑一次），所以只讀方向，不要讀倍數（[慎用子 agent](2-3-subagents.html)）。
- 先選等級，每次都多一步。更糟的是，兩套規則並排放著，agent 會拿不準，還會錯誤地解釋哪一套適用。

還有一個更深的問題。一份工作有多難，開始之前是不知道的。等級卻要你事先猜。

所以我拿掉了等級。現在照顧的程度由另外兩件事決定，兩件都不要你猜難度。

### 照顧的程度跟著出錯的代價走

第一件事是**這個動作可能弄壞什麼**。程式根據路徑和指令做一個粗略的判斷，所以沒有人去選。這是一種啟發式，不是證明；下面講資料夾的那一節會說它哪裡會被騙。

| 這份工作做什麼 | 例子 | 怎麼守 |
| --- | --- | --- |
| 只讀 | 一個問題、在筆記裡查東西 | 什麼都不攔 |
| 改任務資料夾 | 寫分析、設計、計劃 | 什麼都不攔 |
| 改真正的倉庫 | 程式碼、知識庫（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)） | 先寫在資料夾裡。寫回去需要人批准（[兩道門：人在哪裡批准](5-3-two-approvals.html)） |
| 碰到 git 歷史或正式環境 | commit、push、切換分支 | 由 hook 攔住；人批准，有些指令永遠拒絕 |

這和[詢問不是限制](4-2-ask-vs-refuse.html)裡的分級是同一個想法：出錯的代價越大，攔得越硬。這樣的攔截是一道**門**：任務在人批准之前過不去的一個點（[兩道門：人在哪裡批准](5-3-two-approvals.html)）。

### 種類決定怎樣才算做完

第二件事是任務的**種類**。一個問題和一次程式碼修改，做完的方式不一樣，所以由種類來說什麼算做完。

| 種類 | 什麼時候算做完 |
| --- | --- |
| 問題 | 答案有來源 |
| 根因分析 | 有一條證據鏈：看到了什麼、日誌、原因、怎麼驗證的 |
| 設計或計劃 | 有幾個選項，和選擇的理由 |
| 開發 | 修改符合批准的計劃，並有測試過的紀錄 |
| 測試 | 案例和結果都在磁碟上 |
| 知識更新 | 來源清楚，並且過同一道寫回的門（[兩道門：人在哪裡批准](5-3-two-approvals.html)） |

沒有這張表，「做完了」就是 agent 想怎麼說就怎麼說。有了它，讀的人和檢查的人就知道要找什麼（[讓「通過」可信](5-5-counted-checks.html)）。

### 大小決定資料夾裡有幾個檔案

一個問題不需要需求檔、計劃和待辦清單。開發任務需要。所以每個任務還有一個**大小**，它只決定資料夾裡放哪些檔案。

- **輕**：一份交接檔：做到哪裡、下一步、決定了什麼。
- **中**：加上需求和它的來源文件、參考資料，和一份日誌。
- **完整**：再加上待辦清單、程式碼的工作副本，和測試結果。

每種類都有預設的大小。長大的任務可以調高，缺的檔案補上。它不會往下調。所以便宜的路保持便宜，任務值得時重的路就在那裡。這不是舊的等級回來了：沒有人在開始時猜大小，由種類來定，而且只有工作顯示需要更多時才往上走。

### 資料夾就是工作區

對改真正倉庫的任務，這個資料夾也是做事的地方。要改的檔案複製進來，在這裡改，批准之後才送回去。在那之前，真正的倉庫不會被碰。

::: figure 5-1-lifecycle

我想誠實說明這有多強。資料夾是由門裡的規則守著的，不是由作業系統。用間接寫法寫的指令可能漏過去，就像[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)解釋的：hook 看到的是呼叫，不是效果。它把謹慎的 agent 留在原位。它關不住一個鐵了心的。對絕對不能碰的東西，見[有些東西根本不給](4-5-least-privilege.html)。

### 為什麼用檔案交接

任務的狀態存在檔案裡，不存在對話裡：

- **交接檔**說任務做到哪裡、接下來是什麼。新的會話只讀它就能接手。
- **需求檔**存放達成的共識（[需求由 agent 寫，人確認](5-2-requirements.html)）。
- **給程式用的狀態檔**。任務清單和每個任務在等什麼，是從這裡讀的，不是從 Markdown 讀的。agent 用文字手寫的進度會漏掉打勾、會寫錯；程式記錄的進度不會。

文字紀錄和磁碟不一致時，以磁碟為準。這和 Anthropic 長時間運行的 agent 工作裡的進度檔是同一個想法：狀態放在對話之外的檔案裡（[跨會話的長任務](5-8-long-work.html)）。我加的是種類、大小和門。

### 一個會話管一個任務；一個任務可以有很多會話

這兩者是故意分開的。

- 一個會話一次管一個任務。它可以切換到另一個，不用關掉第一個。管著一個任務時，編輯工具只能寫那個任務的資料夾。
- 任務比它的會話活得久。關閉一個任務只改它的狀態；資料夾還在，可以再打開。
- 每次 prompt 開始時，hook 會告訴 agent 它的任務做到哪裡了；如果它沒有任務，就告訴它還有哪些任務開著。

有一個代價：任務可能沒有任何會話，如果會話換去做別的任務，或它的紀錄丟了。那時沒有任何東西記下 agent 停了。我的任務看板（[同時管十件事：並行的是任務](7-2-many-tasks.html)）把這些顯示成沒有會話，並顯示沒人碰它多久了，這樣人看得到。

不是每個對話都需要一個任務。不寫任何東西的隨口提問不開任務；那只會平白拖慢它們。

### 不用任何設定就能試

在一個長對話的結尾，請 agent 把被要求做什麼、決定了什麼、做到哪裡、接下來是什麼，寫進一個檔案。開一個新對話，叫它只讀那個檔案然後接著做。第二個對話如果出錯，就是那個檔案缺了東西；這告訴你交接檔必須放什麼。

## 代價和陷阱 {#costs-and-traps}

- **agent 必須讓檔案保持最新**。資料夾只有在交接檔是真的時才有用。agent 停下來時的提醒有幫助；不保證。要緊的時候，我讀檔案，不信 agent 的話。
- **任務資料夾會多出一些步驟**。開一個、寫需求、在門前等待，比在對話裡直接做一個小修改慢。所以才有輕的任務，也所以一個問題什麼都不開。
- **種類也是一種猜測**。一份工作常常一開始是問題，後來變成修改。種類可以變，大小只能往上。人多常選錯種類，我沒有量過。
- **這個資料夾不是安全意義上的沙箱**。見上面。

## 什麼時候可以刪掉 {#when-to-delete-it}

這裡有兩部分是為今天的平台搭的鷹架。

- **交接檔和每次 prompt 的提醒**。它們存在，是因為對話會被壓縮、會話會結束。如果平台有自己的記憶，能撐過這兩件事，而且人讀得到，就丟掉我的檔案，留下這個想法。
- **各種類專屬的操作手冊**。模型越來越不需要寫出來的步驟時，就把它們縮短。「什麼算做完」的清單要留著：它們說的是你要什麼，不是怎麼得到。

不會退場的是單位本身。不管平台怎麼做，一份工作都有需求、計劃和結果，而人想找得到它們。
