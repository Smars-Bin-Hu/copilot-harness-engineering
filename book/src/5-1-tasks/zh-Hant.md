這一章假設你用過 AI 程式 agent，並且知道 hook 是平台在工具呼叫之前執行的程式碼（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）。

## 一句話 {#in-one-sentence}

管任務，不管對話：一個任務一個資料夾。這件事可能弄壞什麼，決定它要過哪些門；它的種類，決定怎樣才算做完。

## 給主管 {#for-leaders}

- **要做的決定**：批准把一件事、而不是一段對話，當作工作的單位。具體來說，就是一個任務一個資料夾，附一份交接檔，謹慎的程度跟著出錯可能弄壞什麼走。
- **風險**：對話會被縮短或結束，新的對話什麼也不知道。另一個陷阱是流程太重。我的第一版設計有一個重的等級，帶一組分角色的 agent，在一個小測試裡，它花了約 4.5 倍的用量和 6 倍的時間，在需求明確的任務上卻沒有任何好處（四個任務，各跑一次，所以讀方向，不要讀倍數）。
- **做對的成本**：第一步只是每個任務一個資料夾，裡面一份交接檔。任務值得時才加更多檔案，隨口問的問題什麼都不開。相對地，agent 必須讓檔案保持真實，要緊的時候也得有人去讀。
- **可以問團隊**：「如果 agent 的對話今晚消失了，明天有人能只靠檔案接著做這件事嗎？」

## 對話靠不住，工作要放在哪裡？ {#problem}

假設你請一個 agent 改一條 pipeline。它讀了一圈，做了規劃，開始動手編輯，對話也跟著越來越長。第二天早上，你開了一個新對話想問個後續問題，可是新的 agent 從沒見過第一個對話。又或者，第一個對話在這段時間裡已經被工具縮短了，agent 再也想不起自己當初為什麼那樣選（[長對話會變差](3-2-long-sessions.html)）。

說到底，這兩種情況都是管錯了對象。對話會被壓縮，會結束，而且一個對話裡可能放著三件毫不相干的工作。你真正在乎的是工作本身：被要求做什麼、決定了什麼、做到哪裡了、有沒有被檢查過。

所以我不再把對話當成工作的單位，單位改成了**任務**：一件事，一個**任務資料夾**。需求、計劃、進度和結果都是這個資料夾裡的檔案，所以不管是今天還是下週，任何會話只要讀這個資料夾，就能接手這個任務。

這樣一來，工作放在哪裡的問題就解決了，而這也就是第一步的全部：每個任務一個資料夾，裡面一份交接檔。下面的一切，都是我在這個基礎上加的，你可以一次加一塊。

可是接著就冒出第二個問題，因為不是每件事都需要同樣的謹慎。改筆記裡的一個錯字，和寫進共用的倉庫，不是同一回事，兩者也不該走一樣多的流程。

## 每件事該走多少流程？ {#how-it-works}

### 我的第一個答案是分等級，而且是錯的

我的第一個答案是三個**等級**，從輕的等級 1 到重的等級 3，最重的那一級帶一組分角色的 agent（[慎用子 agent](2-3-subagents.html)）。每件事開始時，你要先選一個等級。

用了一陣子之後，有三件事很清楚。第一，只有中間那一級被用到，另外兩級大部分時間都閒著。第二，重的那一級並不划算：在需求明確的任務上，它不比一個 agent 好，卻花了約 4.5 倍的用量和 6 倍的時間。這個結論背後的測試很小，四個任務，各跑一次，所以只讀方向，不要讀倍數（[慎用子 agent](2-3-subagents.html)）。第三，先選等級本身就讓每次都多了一步。更糟的是，兩套規則並排放著，agent 會拿不準，還會錯誤地解釋哪一套適用。

不過最根本的問題，出在分等級這個想法本身。一件事有多難，開始之前是不知道的，等級卻要你事先去猜。

所以我拿掉了等級，現在謹慎的程度由另外兩件事決定，兩件都不要你猜難度。

### 謹慎的程度跟著出錯的代價走

第一件事是**這個動作可能弄壞什麼**。這一點不用人來選，因為程式會根據路徑和指令做一個粗略的判斷。這個判斷是一種啟發式，不是證明；它哪裡會被騙，下面講資料夾的那一節會說。

| 這件事做什麼 | 例子 | 怎麼守 |
| --- | --- | --- |
| 只讀 | 一個問題、在筆記裡查東西 | 什麼都不攔 |
| 改任務資料夾 | 寫分析、設計、計劃 | 什麼都不攔 |
| 改真正的倉庫 | 程式碼、知識庫（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)） | 先寫在資料夾裡。寫回去需要人批准（[兩道門：人在哪裡批准](5-3-two-approvals.html)） |
| 碰到 git 歷史或正式環境 | commit、push、切換分支 | 由 hook 攔住；人批准，有些指令永遠拒絕 |

這和[詢問不是限制](4-2-ask-vs-refuse.html)裡的分級是同一個想法：出錯的代價越大，攔得越硬。這樣的攔截就是一道**門**，也就是任務在人批准之前過不去的一個點（[兩道門：人在哪裡批准](5-3-two-approvals.html)）。

### 種類決定怎樣才算做完

第二件事是任務的**種類**。一個問題和一次程式碼修改，做完的方式不一樣，所以要由種類來說什麼算做完。

| 種類 | 什麼時候算做完 |
| --- | --- |
| 問題 | 答案有來源 |
| 根因分析 | 有一條證據鏈：看到了什麼、日誌、原因、怎麼驗證的 |
| 設計或計劃 | 有幾個選項，和選擇的理由 |
| 開發 | 修改符合批准的計劃，並有測試過的紀錄 |
| 測試 | 案例和結果都在磁碟上 |
| 知識更新 | 來源清楚，並且過同一道寫回的門（[兩道門：人在哪裡批准](5-3-two-approvals.html)） |

沒有這樣一張表，「做完了」就是 agent 想怎麼說就怎麼說。有了它，讀的人和檢查的人都知道要找什麼（[讓「通過」可信](5-5-counted-checks.html)）。

### 大小決定資料夾裡有幾個檔案

這兩件事管的是守得多嚴、怎樣算做完，卻不管一個任務要帶多少檔案。可是這也因任務而異：一個問題不需要需求檔、計劃和待辦清單，開發任務卻需要。所以每個任務還有一個**大小**。它不是第三把衡量謹慎的尺，只決定資料夾裡放哪些檔案。

- **輕**：一份交接檔，寫著做到哪裡、下一步是什麼、決定了什麼。
- **中**：加上需求和它的來源文件、參考資料，和一份日誌。
- **完整**：再加上待辦清單、程式碼的工作副本，和測試結果。

每個種類都有預設的大小。任務長大了，大小可以調高，缺的檔案到時候再補上，但不會往下調。這樣一來，便宜的路保持便宜，任務值得時，重的路也還在那裡。你也許會問：這不就是舊的等級換了個名字回來嗎？其實不是，因為沒有人在開始時去猜大小。大小由種類來定，而且只有工作顯示需要更多時，才往上走。

### 資料夾就是工作區

如果任務要改真正的倉庫，這個資料夾也是做事的地方。要改的檔案先複製進來，在這裡改，批准之後才送回去。在那之前，誰也不會去碰真正的倉庫。

這個保證沒有聽起來那麼牢。資料夾是由門裡的規則守著的，不是由作業系統，而 hook 看到的是呼叫，不是效果（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)），所以用間接寫法寫的指令，可能就漏過去了。這樣一來，規則能讓一個小心的 agent 守規矩，卻擋不住一個鐵了心要繞過去的。對絕對不能碰的東西，見[有些東西根本不給](4-5-least-privilege.html)。

### 為什麼用檔案交接

資料夾裡放的不只是要改的檔案。不管大小，任務的狀態也存在這裡的檔案裡，而不是對話裡。負責交接的，主要是下面三個檔案。

- **交接檔**說任務做到哪裡、接下來是什麼。新的會話只讀這一個檔案，就能接手。
- **需求檔**存放達成的共識（[需求由 agent 寫，人確認](5-2-requirements.html)）。
- **給程式用的狀態檔**。任務清單和每個任務在等什麼，都是從這裡讀的，不是從 Markdown 讀的。agent 用文字手寫的進度會漏掉打勾、會寫錯，程式記錄的進度不會。

文字紀錄和磁碟上的實際情況對不上時，以磁碟為準。這和 Anthropic 長時間執行的 agent 工作裡的進度檔是同一個想法：狀態放在對話之外的檔案裡（[跨會話的長任務](5-8-long-work.html)）。我加上的，是種類、大小和門。

### 一個會話管一個任務；一個任務可以有很多會話

會話和任務是故意分開的：一個會話一次只管一個任務，但它可以切換到另一個，不用關掉第一個。管著一個任務時，編輯工具只能寫那個任務的資料夾。反過來，任務比它的會話活得久。關閉任務只改它的狀態，所以資料夾還在，任務也還可以再打開。每次 prompt 開始時，hook 也會告訴 agent 它的任務做到哪裡了；如果它手上沒有任務，就告訴它還有哪些任務開著。

這樣分開只有一個代價：任務可能落得一個會話都沒有，例如它的會話換去做別的任務，或者會話的紀錄丟了，這時就沒有任何東西記下 agent 已經停了。我的任務看板（[同時管十件事：並行的是任務](7-2-many-tasks.html)）會把這些任務顯示成沒有會話，並顯示沒人碰它多久了，好讓人看得到。

這一切都和不寫任何東西的隨口提問無關。這類問題根本不開任務，開了只會讓它平白變慢。

### 不用任何設定就能試

交接這個想法，你在自己的工具裡就能試。在一個長對話的結尾，請 agent 把被要求做什麼、決定了什麼、做到哪裡、接下來是什麼，寫進一個檔案。然後開一個新對話，叫它只讀那個檔案，接著做下去。第二個對話如果出錯，就表示那個檔案缺了東西，而缺的那些，正是交接檔必須放的。

## 資料夾要付出什麼，又保證不了什麼 {#costs-and-traps}

上面那個小試驗，也帶出了第一筆代價。資料夾只有在交接檔是真的時候才有用，所以 agent 必須讓檔案一直保持最新。在 agent 停下來時提醒它一下有幫助，但保證不了。要緊的時候，我讀檔案，不信 agent 的話。

任務資料夾還會多出一些步驟：開一個資料夾、寫需求、在門前等待，都比在對話裡直接做一個小修改慢。這就是為什麼有輕的任務，也是為什麼一個問題什麼都不開。

雖然現在不用再猜難度了，種類卻仍然是一種猜測，因為一件事常常一開始是問題，後來才變成修改。所以種類可以變。大小也可以變，但只能往上。人多常選錯種類，我沒有量過。

最後，這個資料夾不是安全意義上的沙箱，原因上面「資料夾就是工作區」那一節已經說過。

## 哪些可以刪，哪些留下 {#when-to-delete-it}

這些東西裡，有兩部分是為今天的平台搭的鷹架，以後可以拆。第一部分是交接檔，連同每次 prompt 的提醒。它們之所以存在，是因為對話會被壓縮、會話會結束。如果平台有自己的記憶，能撐過這兩件事，而且人讀得到，就丟掉我的檔案，留下這個想法。

第二部分是每個種類各自的操作手冊，也就是做這類任務時寫出來的步驟。模型越來越不需要這些步驟，手冊也就可以縮短。但「什麼算做完」的清單要留著，因為它們說的是你要什麼，而不是怎麼得到。

不會退場的是單位本身。不管平台怎麼做，一件事總有需求、計劃和結果，而人想找得到它們。
