读这一章，你要用过 AI 编程 agent，还要知道 hook 是平台在工具调用之前运行的代码（见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)）。

## 一句话 {#in-one-sentence}

管任务，不管对话：一个任务一个文件夹。工作可能弄坏什么，决定它要过哪些关卡；工作的类型，决定怎样才算做完。

## 写给管理者 {#for-leaders}

- **要拍板的事**：批准把任务，而不是对话，当作工作的单位：一个任务一个文件夹，带一份交接文件，谨慎的程度跟着“出错可能弄坏什么”走。
- **风险**：对话会被压缩，会结束，新开的对话什么都不知道。另一个陷阱是流程太重：我最初的设计里有一个重的级别，用一组按岗位分工的 agent，在一次小测试里多花了约 4.5 倍的用量和 6 倍的时间，而在需求清楚的任务上没有任何收益（四个任务，每个只跑了一次，所以看方向，别看倍数）。
- **做对的代价**：第一步只是每个任务一个文件夹、里面一份交接文件。任务值得的时候才加更多文件，随口一问不开任何东西。agent 必须让这些文件保持真实，要紧的时候人得去读它们。
- **可以问团队**：“如果今晚 agent 的对话没了，明天有人只靠文件就能把这件事接着做下去吗？”

## 问题 {#problem}

你让 agent 改一条 pipeline。它读、计划、编辑，对话越来越长。第二天早上，你开一个新对话问个后续问题。新的 agent 从没见过第一个对话。或者第一个对话被工具压缩了，它已经忘了当初为什么那样选（见[长对话会变差](3-2-long-sessions.html)）。

对话是管错了的东西。它会被压缩，会结束，一个对话里还可能装着三件毫不相干的事。你真正在乎的是这件事：被要求做什么、决定了什么、做到了哪一步、检查过没有。

所以我不再把对话当作工作的单位。单位是**任务**：一件事，对应一个**任务文件夹**。需求、计划、进度和结果，都是这个文件夹里的文件。任何一个会话，不管是今天的还是下周的，读一读文件夹就能接手这个任务。

这解决了工作放在哪里的问题。接着有第二个问题：不是每件事都需要同样的谨慎。改笔记里的一个错别字，和往共享仓库里写东西，是两回事。怎么决定每件事该走多少流程？

你可以只从第一步开始：每个任务一个文件夹，里面一份交接文件。下面的一切，都是我在这个基础上加的，你可以一块一块地加。

## 原理 {#how-it-works}

### 我最初的答案是分级，而且错了

我最初的设计有三个**级别**。级别 1 轻，级别 3 重，带一组按岗位分工的 agent（见[慎用子 agent](2-3-subagents.html)）。每件事开始时，你要选一个级别。

用了一阵之后，三件事很清楚：

- 只有中间那一级被用到。另外两级大部分时间闲着。
- 重的那一级，在需求清楚的任务上并不比一个 agent 单干好，却要多花约 4.5 倍的用量和 6 倍的时间。那个测试很小（四个任务，每个只跑一次），所以只看方向，别看倍数（见[慎用子 agent](2-3-subagents.html)）。
- 先选级别，每次都多一步。更糟的是，两套规则并排放着，agent 会拿不准，还会错误地解释哪一套在起作用。

还有一个更深的问题。一件事有多难，开始之前是没法知道的。分级要你一开始就去猜。

所以我把级别删了。现在谨慎的程度由另外两样东西决定，这两样都不要求你去猜难度。

### 谨慎的程度，跟着出错的代价走

第一样是**这个动作可能弄坏什么**。代码根据路径和命令做一个粗略的判断，所以没人要去选。这是个经验性的判断，不是证明；下面讲文件夹的那一节会说它在哪里可能被骗过去。

| 工作在做什么 | 例子 | 怎么守着 |
| --- | --- | --- |
| 只读 | 一个问题，在笔记里查一下 | 什么都不拦 |
| 改任务文件夹 | 写分析、设计、计划 | 什么都不拦 |
| 改真实的仓库 | 代码、知识库（见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)） | 先写在文件夹里。写回去要人审批（见[两道门：人在哪里审批](5-3-two-approvals.html)） |
| 碰 git 历史或生产环境 | 提交、push、切换分支 | 由 hook 拦住；人审批，有些命令永远拒绝 |

这和[询问不是限制](4-2-ask-vs-refuse.html)里的分级是同一个思路：出错的代价越大，拦得越狠。这样的拦截就是一道**关卡**：任务在人批准之前过不去的一个点（见[两道门：人在哪里审批](5-3-two-approvals.html)）。

### 类型决定“做完”的标准

第二样是任务的**类型**。一个问题和一次代码改动，做完的方式不一样，所以由类型来说怎样才算做完。

| 类型 | 什么时候算做完 |
| --- | --- |
| 问题 | 答案有来源 |
| 根因分析 | 有一条证据链：看到了什么、日志、原因、怎么验证的 |
| 设计或计划 | 有几个方案，选择有理由 |
| 开发 | 改动和批准的计划一致，并且有测试它的记录 |
| 测试 | 用例和结果都落在磁盘上 |
| 知识更新 | 来源清楚，并且走同一道写回关卡（见[两道门：人在哪里审批](5-3-two-approvals.html)） |

没有这个，“做完了”就是 agent 想怎么说就怎么说。有了它，读的人和检查的人知道该看什么（见[让“通过”可信](5-5-counted-checks.html)）。

### 规模决定文件夹里有几个文件

一个问题用不着需求文件、计划和待办清单。一个开发任务就需要。所以每个任务还有一个**规模**，它只决定文件夹里放哪些文件。

- **轻量**：一份交接文件：做到哪一步、下一步是什么、决定了什么。
- **中等**：加上需求和它的来源文档、参考资料，以及一份日志。
- **完整**：再加一份待办清单、代码的工作副本和测试结果。

每种类型有默认的规模。任务变大了，可以升上去，缺的文件补上。只升不降。这样，便宜的路径一直便宜，任务值得的时候，重的路径也在那里。这不是旧的级别又回来了：没人在开始时去猜规模，由类型来定，只有当工作表明需要更多时才往上升。

### 文件夹就是工作区

对于要改真实仓库的任务，文件夹也是干活的地方。要改的文件复制进来，改动在这里做，批准之后才写回去。在那之前，真实的仓库不会被碰。

::: figure 5-1-lifecycle

我想老实说一下这有多牢靠。文件夹是靠关卡里的规则守住的，不是靠操作系统。一条换了间接写法的命令，可能绕过去，正如 [Hook：每次调用都会经过的执行点](2-2-hooks.html)所讲：hook 看到的是调用，不是效果。它能让一个小心的 agent 守本分，管不住一个铁了心的 agent。对绝不能碰的东西，见[有些东西根本不给](4-5-least-privilege.html)。

### 为什么用文件做交接

任务的状态保存在文件里，不在对话里：

- **交接文件**说明任务做到了哪一步、接下来是什么。新的会话只读这个就能接手。
- **需求文件**记录达成一致的内容（见[需求由 agent 写，人确认](5-2-requirements.html)）。
- **给程序读的状态文件**。任务清单，以及每个任务在等什么，是从这里读的，不是从 Markdown 里读。agent 手写在文字里的进度，会漏勾、会写错；程序记录的进度不会。

书面记录和磁盘上的实际情况对不上时，以磁盘为准。这和 Anthropic 长时间运行的 agent 工作里的进度文件是同一个思路：状态放在对话之外的文件里（见[跨会话的长任务](5-8-long-work.html)）。我加的是类型、规模和关卡。

### 一个会话只持有一个任务；一个任务可以有多个会话

这两者是有意分开的。

- 一个会话一次持有一个任务。它可以切换到另一个，不用关掉第一个。持有任务期间，编辑工具只能写那个任务的文件夹。
- 任务比它的会话活得长。关闭任务只改变它的状态；文件夹还在，还可以重新打开。
- 每条 prompt 开始时，hook 会告诉 agent 它的任务做到了哪一步；如果它没有任务，就告诉它还有哪些任务没关。

有一个代价：一个任务可能没有任何会话，比如会话转去做另一个任务了，或者它的记录丢了。这时没有任何东西注明 agent 停下了。我的任务看板（见[同时管十件事：并行的是任务](7-2-many-tasks.html)）把这些显示为没有会话，并标出多久没人碰了，这样人看得到。

不是每个对话都需要任务。随口一问、不写任何东西的，不开任务；开了只会白白拖慢它们。

### 不用任何配置，就能试

在一个长对话的最后，让 agent 把被要求做什么、决定了什么、做到了哪一步、接下来是什么，写进一个文件。开一个新对话，让它只读这个文件，接着干。如果第二个对话做偏了，就说明文件里缺了什么；这就告诉你交接文件必须放什么。

## 代价和坑 {#costs-and-traps}

- **agent 必须让这些文件保持最新**。只有交接文件是真实的，文件夹才有用。agent 停下来时给它一个提醒有帮助，但不能保证。要紧的时候，我读文件，不信 agent 的话。
- **任务文件夹会多出一些步骤**。开一个、写需求、在关卡处等，比在对话里直接做一个小改动慢。这就是为什么有轻量任务，也是为什么一个问题不开任何东西。
- **类型也是一种猜测**。一件事常常一开始是个问题，后来变成一次改动。类型可以改，规模只能往上升。人们选错类型的频率有多高，我没有测过。
- **从安全的意义上说，文件夹不是沙箱**。见上文。

## 什么时候可以删掉 {#when-to-delete-it}

这里有两部分是为今天的平台搭的脚手架。

- **交接文件和每条 prompt 处的提醒**。它们存在，是因为对话会被压缩、会话会结束。如果平台自己有能挺过这两者、而且人能读的记忆，就把我的文件去掉，保留这个想法。
- **按类型写的操作手册**。模型越来越不需要写明的步骤时，就把它们缩短。保留“怎样才算做完”的清单：它们说的是你要什么，不是怎么得到。

不会退役的是单位本身。不管平台怎么做，一件事都有需求、计划和结果，而人想找得到它们。
