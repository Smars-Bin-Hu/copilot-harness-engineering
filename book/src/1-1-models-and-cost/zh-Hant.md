讀這一章，只需要用過 AI 寫程式 agent，並且看過它的用量或帳單頁面。其他都不用。

## 一句話 {#in-one-sentence}

評斷模型，看的是做完一個任務要花多少，不是每個 token 的單價。大部分的成本是模型在讀的東西，所以少讀、少重做，省得最多。

## 給主管 {#for-leaders}

- **要做的決定**：評斷模型和設定，看做完一個任務的成本，不看每個 token 的單價。結果不好的時候，先試比較便宜的修法（缺一條規則、缺一道檢查、丟了線索），再考慮付錢換更大的模型。
- **風險**：長的 agent 任務裡，大部分 token 是模型在重讀同樣的材料。在我的例子裡，數字是我挑的整數，讀的部分占了 token 的九成以上。快取（cache）可以大幅降低帳單，但只在輸入的開頭保持不變時才有用。
- **做對的成本**：主要是設定的時間，加上量測的習慣。公平的模型比較，是幾個任務，每個跑大約三次。
- **可以問團隊**：「我們做完一個任務要花多少？上次確認這個數字是什麼時候？」

## 問題 {#problem}

比較模型，通常從價目表開始：每百萬個 token 多少美元。這是查得到的數字，所以大家用它。但你買 token，從來不是為了 token 本身。你買的是做完的任務：修好一個 bug、寫好一份報告。重要的是那件事的總花費。

價目表是個差勁的指引，有兩個原因。一個便宜的模型，任務失敗又得再問一次，可能比一個第一次就做對的強模型還貴。而且在 agent 裡，token 的數量和你預期的不一樣，下一節會說明。

### 先講五個詞

- **token** 是一小段文字，大約是一個短字或字的一部分。模型用 token 讀和寫，帳單也用 token 算。
- **輸入** token 是模型在一次呼叫裡讀的。**輸出** token 是它寫的。兩者的價格不同，通常輸出每個 token 比較貴。
- **上下文視窗**是模型一次能看到多少文字：你的需求、規則、它讀過的檔案、之前工具的結果。它有大小上限。[上下文是一份預算](3-1-context-budget.html) 講怎麼管它。
- **推理強度**是某些模型有的設定，控制它回答前想多久。想得多，通常輸出的 token 更多，時間也更長。
- **prompt 快取**讓供應商記住你輸入的一大段開頭，這樣之後的呼叫，只要開頭是同樣的文字，那一段就可以收得便宜些。

### 在 agent 裡，token 去哪了

在對話裡，你送一個問題，得到一個回答。在 agent 迴圈裡（[agent 循環，和你能插手的地方](2-1-agent-loop.html)），每個工具結果出來之後，模型都會被再呼叫一次。而且每次呼叫，都要送出到目前為止的整段對話：規則、需求、它讀過的每個檔案、每個結果。模型在兩次呼叫之間沒有記憶，所以這是它知道發生過什麼的唯一辦法。

::: figure 1-1-token-flow

下面用整數算一遍。這些數字是我為了好算而挑的，不是量出來的。假設規則加你的需求是 10,000 個 token，每個工具結果再加 5,000。呼叫 10 次，模型讀的大約是 10,000 + 15,000 + 20,000 + …… = 325,000 個 token，但每次呼叫大概只寫幾百個 token。在這個例子裡，讀的部分占了 token 的九成以上。實際的比例看你的任務，但迴圈越長，越偏向讀。

輸出每個 token 比較貴，所以 token 不等於錢。但形狀不變：長的 agent 任務，大多是模型一遍又一遍讀同樣的材料。這就是為什麼這一章的後半，講的是怎麼少讀。

我可以給一個真實的例子。在 [慎用子 agent](2-3-subagents.html) 裡，我把同樣的四個任務，交給有三個職位的三個 agent 組成的團隊，也交給單個 agent。兩邊每個任務都答對。團隊用掉的大約是 4.5 倍。最大的浪費是重讀：每個新的 agent 都從空的上下文開始，得把同樣的檔案再讀一遍。那是四個小任務，每個只跑一次，所以相信方向，不要相信倍數。

### prompt 快取改變了算式

每次呼叫有這麼大一段開頭都一樣，所以供應商提供 **prompt 快取**。在 Anthropic 的 API 上，大多數模型讀快取的輸入，只收基本輸入價的十分之一，有些更低。寫入快取比一般的讀貴：五分鐘的快取是 1.25 倍，一小時的快取是 2 倍。（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）

由此得到三件事，它們改變了你省錢的方式：

- **穩定的開頭有回報**。快取要求從輸入的開頭起完全一致。如果你改了靠近頂端的東西（改了一條規則、換了工具清單），後面的全都會沒命中。
- **停一下可能要付錢**。快取只活很短的時間。一段對話你離開一小時再回來，可能要付全價重建。
- **最便宜的 token，是沒送出去的那個**。就算是讀快取，也不是免費的。少讀，仍然是第一件該試的事。

下面是同一個例子，假設快取每次都命中，只算輸入，用五分鐘的價格。第一次呼叫寫入 10,000 個 token，乘 1.25 倍，是 12,500。接下來九次呼叫，每次從快取讀之前的文字（從 10,000 到 50,000 個 token，共 270,000，乘 0.1 倍，是 27,000），再寫入新的 5,000 個 token（共 45,000，乘 1.25 倍，是 56,250）。總共大約 96,000 個 token 的價格，而不是 325,000，重複讀取的部分現在不到三分之一。所以快取改變的是錢花在哪裡：從重讀變成新材料。這就是為什麼前面說的「九成以上」，算的是讀了多少 token，不是帳單的占比，也是為什麼快取維護得好的團隊，可以讀很多卻付得很少。沒命中（前兩點說的情況）會把成本拉回 325,000 附近。

## 原理 {#how-it-works}

### 一個任務花多少

把一個任務的成本，想成三個部分。

::: figure 1-1-cost-parts

細看：

1. **模型讀的**，每次呼叫都算，快取命中的地方有折扣。
2. **模型寫的**：回答、程式碼、思考。
3. **重做**：答錯、丟了線索、再試一次。重做是第 1 和第 2 部的乘數。

大部分省下來的錢，來自第一和第三部分。一個好用的經驗法則是：**用夠用的最便宜的方式做事**。

### 強模型什麼時候比較便宜

更強的模型，每個 token 更貴。但它只要一次就得到答案，弱的要三次，這時它做完一個任務的成本仍然可能更低。如果任務很簡單，它也可能是浪費。

這個轉折點在哪裡，我自己沒有量過。這是論證，不是結果，找到那一點的辦法，是在你自己的任務上測：同樣幾個任務跑在兩個模型上，比較每次成功的成本，不是每次呼叫的成本。[一次運行證明不了什麼](6-4-variance.html) 說了怎麼誠實地做。

### 依任務挑，並確認設定

我的經驗法則（沒有量過）：用強模型來想（計劃、做法、難的 bug），用中等的模型來做（計劃已經清楚的改動）。有些工具也讓你設推理強度。Copilot 能不能從 harness 裡設定，我還沒測過，所以請查你自己的工具。

### 在 Copilot 裡怎麼計費（2026 年 10 月下旬）

這一段常常變，請確認日期和你自己的方案。

- **按月的 Copilot 方案**：從 2026 年 6 月 1 日起，Copilot 一直在轉向按用量計費。premium request unit 換成了 GitHub AI Credits，用量依輸入、輸出和快取的 token 算，按每個模型公開的 API 費率。程式碼補全和 next edit suggestions 仍包含在內。（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）
- **年繳的 Pro 和 Pro+ 方案**，在到期之前仍用舊的 premium request 模式。在那裡，你送出的每個 prompt 算一次請求，再乘上該模型的倍率，agent 做的工具呼叫不算。（[Copilot requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)）

兩種模式獎勵的習慣不同。按請求計費時，一次長的自主執行對你很便宜，所以把大任務放進一個 prompt 做可能划算。按 token 計費時，長的執行花多少，和它讀了多少成比例。你用哪一種，決定了這一章其餘的部分有多重要。如果你的方案按 token 計費，它就很重要。

### 結果不對時，最後才換模型

結果不好時，最容易的反應是換成更大的模型。這是最貴的修法，而且常常是錯的。先看哪裡出了問題：

| 出了什麼問題 | 先試 |
| --- | --- |
| 它不知道一條規則、一個名字，或專案怎麼做這件事 | 把它寫進規則或知識檔。更大的模型也不知道 |
| 它說「做完了」，其實沒有 | 加一道檢查：執行測試（[讓 agent 能檢查自己的活](5-4-self-checks.html)） |
| 在長會話裡丟了線索 | 開一個新會話，把狀態放在檔案裡帶過去（[長對話會變差](3-2-long-sessions.html)） |
| 它什麼都知道，推理還是不好 | 這時再試更強的模型 |

### 四種省法，以及各自怎樣過頭

1. **少用模型**。程式碼能做的，就不要問模型。計數、複製檔案、把 Word 檔轉成文字、檢查格式：腳本每次都做得一樣，也不用 token。危險是把判斷搬進一段不會判斷的程式。[誰來判斷：程式、便宜模型、主模型、人](5-9-who-decides.html) 畫了那條線。
2. **少讀**。規則寫短，細節要用時才載入，要 diff 而不是整個檔案。危險：讀太少，它就會猜，而重做花的錢比省下來的讀取還多。
3. **少寫**。要簡短的回答、一行結論、一份短清單。危險：簡短到下一步用不上。
4. **少重做**。工作開始前先談好計劃，把狀態放在檔案裡，這樣丟掉的會話可以接著做，再限制重試的次數。危險：上限切斷了有用的工作。上限要依你看到的情況設，不要依恐懼設。

還要留意固定的成本。agent 有的每個工具，都會把它的名字、描述和參數，加進每次呼叫的輸入裡（[Tool calling，和給 agent 設計工具](1-2-tool-calling.html)），而你注入的每條規則，每一輪都跟著走。

### 測你自己的設定

帳單讓你吃驚的時候，**問三個問題**：

1. 哪一次呼叫或哪一輪讀得最多？看你工具的用量頁面，和最大的幾個任務。
2. 上下文裡有什麼是不必要在那裡的？舊的工具結果、整份讀進來的大檔案、很長的規則檔？
3. 任務有沒有被重做？如果有，第一次為什麼失敗？

**一個小實驗**。挑一個你知道正確答案的任務。在兩個模型上各跑三次，記下用量和對不對。然後比較每次成功的成本。不要憑一次運行下決定。一個四欄的表就夠了：

## 代價和陷阱 {#costs-and-traps}

**我看得到的和看不到的**。我自己的 harness，日誌裡沒有記 token 數。一個任務真正用了多少，我讀的是平台的會話紀錄，它回報 credits 和 premium request，我不把它們換算成錢。所以我說的所有節省，都是「依設計」，不是帳單。

**省下來的東西不是免費的**。在工具呼叫上執行的 [hook](2-2-hooks.html)，會加一點小延遲。獨立檢查要再呼叫模型。每個 prompt 都注入的規則，每個 prompt 都花 token。我是為了控制才刻意接受這些，但它們是成本。

**讀太少，是看起來像節儉的陷阱**。最便宜的呼叫，是猜錯然後被丟掉的那一個。如果一個任務一直因為缺上下文而失敗，答案是給它對的上下文，不是給它更少。

**價格和方案會變**。上面的快取倍率和 Copilot 計費，是來源上那些日期的情況，我預期它們會變。

## 業界怎麼說 {#industry}
{status: industry}

- **Anthropic** 把讀取快取的價格，訂成一般輸入的一小部分，並說工具定義在每個請求裡都算輸入 token。（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）
- **GitHub** 把 Copilot 從算請求，改成算 token。（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）

方向一致：市場現在按模型讀和寫的東西收費，這正是這一章的論點。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

這一章有很多是為「讀取很貴」的世界寫的建議。如果讀取便宜到，修剪上下文多出來的工夫，比省下的還貴，就丟掉這些技巧，只留下量測每個完成任務成本的習慣。如果某個平台開始自己顯示每個任務的成本，我也會重新看一遍，因為那時你要猜的就少了。
