讀這一章，只需要用過寫程式的 AI agent，並且看過它的用量頁面或帳單頁面。

## 一句話 {#in-one-sentence}

選模型要看做完一個任務花多少錢，不是看每個 token 的單價，而這筆錢大部分花在模型反覆讀的東西上，所以少讀、少重做省得最多。

## 給主管 {#for-leaders}

- **要做的決定**：評價模型和設定，看做完一個任務的成本，不看每個 token 的單價。結果不好的時候，先試便宜的辦法（是不是缺了一條規則、缺了一道檢查，或者線索丟了），再考慮花錢換更大的模型。
- **風險**：一個長的 agent 任務，大部分的錢都花在模型反覆重讀同樣的內容上。在我的算例裡（數字是我挑的整數），讀占了九成五以上的錢。快取能把帳單降到四分之一左右，但前提是輸入的開頭一直不變。
- **做對的成本**：主要是設定的時間，再加上一個量化的習慣。想公平地比較模型，要挑幾個任務，每個跑三次左右。
- **可以問團隊**：「做完一個任務，我們要花多少錢？上次核對這個數字是什麼時候？」

## 你的錢花到哪去了 {#problem}

選模型的時候，大家一般都從價目表開始：Sonnet 5.5 每百萬個輸入 token 2 美元、輸出 token 10 美元，Opus 5.5 是 4 美元和 20 美元（[Pricing](https://platform.claude.com/docs/en/about-claude/pricing)，2026 年 10 月底的價格）。token 是模型讀寫文字的單位，大致相當於一個短的英文單字或者單字的一部分，模型讀的叫輸入 token，寫的叫輸出 token，輸出通常貴得多。價目表的數字好查，所以大家都拿它來比，但是你其實不是在買 token，你買的是一件做完的事，比如修好一個 bug，所以要比的是這件事一共花了多少錢。這個數字和單價差得很遠，一是因為便宜的模型做砸了要再跑一遍，算下來可能比一次做對的貴模型還貴，二是因為 agent 用掉的 token 比你想的多得多，而且大部分花在讀上。

### agent 裡的 token 都去了哪

在聊天裡，你發一個問題，模型回一段話，一次呼叫就結束了。agent 跑的是一個循環（[agent 循環，和你能插手的地方](2-1-agent-loop.html)）：模型說要讀一個檔案，程式讀完把結果送回去，模型再決定下一步，所以每拿到一個工具結果，模型都要被重新呼叫一次。模型在兩次呼叫之間沒有記憶，每次呼叫都要把到目前為止的整段對話重新送一遍，包括規則、需求、讀過的每個檔案和每個工具結果。這些內容都裝在**上下文視窗**裡，也就是模型一次能看到的全部文字，它有大小上限（[上下文是一份預算](3-1-context-budget.html)），而你每呼叫一次，就要為裡面的內容付一次錢。

::: figure 1-1-token-flow

我們用整數算一筆帳，這些數字是我為了好算挑的，不是測出來的。假設規則加需求一共 10,000 個 token，每個工具結果再加 5,000 個，一個任務呼叫 10 次模型，每次寫 300 個 token。模型一共讀了 10,000 + 15,000 + …… + 55,000 = 325,000 個 token，寫的只有 3,000 個。換成錢差距一樣大：用 Sonnet 5.5 的價格，讀要 0.65 美元，寫只要 0.03 美元，輸出的單價雖然貴 5 倍，讀的量卻大了 100 多倍。循環跑得越久，錢就越往讀上偏，因為每多一次呼叫，前面所有的內容都要再讀一遍。

### prompt 快取改變了這筆帳

每次呼叫的開頭幾乎都一樣，所以模型供應商做了 **prompt 快取**：它記住你輸入的開頭一段，下一次呼叫只要開頭一字不差，這一段就按很低的價格算。Anthropic 的價格是這樣的：寫入快取比一般輸入貴，5 分鐘的快取是 1.25 倍，1 小時的快取是 2 倍，讀快取便宜得多，大多數模型是輸入價的十分之一，Opus 5.5 和 Sonnet 5.5 是二十分之一（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。

還是上面那個例子，用 Sonnet 5.5 的價格，假設快取每次都命中。第一次呼叫把 10,000 個 token 寫入快取，後面九次呼叫，每次從快取讀之前的全部內容，九次加起來是 270,000 個 token，再把新增的 5,000 個寫入快取，九次加起來是 45,000 個。算下來寫入花 0.1375 美元，讀快取花 0.027 美元，一共約 0.16 美元，只有原來 0.65 美元的四分之一。這 0.16 美元裡大部分是新內容的寫入費，快取省不掉，只有少讀才省得掉，所以就算快取每次都命中，少讀仍然是第一個該試的辦法。

快取也很容易失效，有三種情況。第一種是開頭變了：快取只認一字不差的內容，順序是工具定義、系統提示、對話訊息，哪一層變了，這一層和它後面的全部都命中不了，所以改一個工具的描述，整個快取就沒了，規則檔開頭也別放目前時間這種每次都變的東西。第二種是停得太久：預設的快取只活 5 分鐘，每用一次會免費續期，你去開個會回來，它就過期了。第三種是開頭太短：不到最小長度就不快取，也不報錯，Sonnet 5.5 的下限是 512 個 token，有些舊模型要 4,096 個。一直命中不了的話，成本就回到 0.65 美元附近，甚至更高，因為寫入快取比一般輸入還貴。

## 怎麼算一個任務的成本，又該從哪裡省 {#how-it-works}

::: figure 1-1-cost-parts

一個任務的成本分三部分：模型讀的（所有呼叫加起來，快取命中的部分打折），模型寫的（回答、程式碼、思考），還有重做（錯誤的回答、丟了的線索、重複的嘗試）。重做不是單獨的一筆錢，它是前兩部分的乘數，重做一次，前兩部分就要再付一遍。能省的大多在讀和重做這兩頭，一條好用的經驗法則是用夠用的辦法裡最便宜的那個。

### 什麼時候貴模型反而便宜

貴模型每個 token 貴，但是如果它一次就做對，算到每個做完的任務上可能反而便宜。算法很簡單，做完一個任務的成本等於跑一次的成本除以成功率。Opus 5.5 的單價是 Sonnet 5.5 的 2 倍，假設兩者跑一次用的 token 差不多，那麼只有當 Sonnet 的成功率不到 Opus 的一半時，Opus 才更便宜，比如 Opus 能做對 80% 的任務，Sonnet 要低於 40%。這只是 token 的帳，如果再算上你盯著它、幫它收拾的時間，這個點還會往貴模型那邊挪。反過來，如果任務本來就簡單，兩個模型都能一次做對，用貴的就是白花錢。

成功率只能在你自己的任務上測：拿同樣的幾個任務，在兩個模型上各跑幾遍，比較每次成功的成本，而不是每次呼叫的成本（[一次運行證明不了什麼](6-4-variance.html)）。

### 按任務選模型，再看一眼推理強度

我自己的經驗法則是思考用強模型，比如定計畫、想思路、啃難的 bug，動手用中等的模型，比如做一處計畫已經很清楚的改動。另外還有一個設定叫**推理強度**（thinking effort），它控制模型回答之前想多久，想得越多，通常輸出的 token 越多，花的時間也越長。在 VS Code 裡，點模型選擇器裡模型名字旁邊的箭頭就能選，不支援的模型不顯示這一項（[AI language models](https://code.visualstudio.com/docs/copilot/customization/language-models)）。開到最高不一定更好，[什麼是 Harness Engineering？](0-1-the-gap-and-the-map.html)裡 LangChain 的實驗就是全程用最高檔的分數反而更低，因為很多任務逾時了。

### Copilot 怎麼計費（截至 2026 年 10 月底）

Copilot 的月繳方案從 2026 年 6 月 1 日起改成了按用量計費：premium request 被 GitHub AI Credits 取代，1 個 credit 等於 0.01 美元，用量按輸入、輸出和快取的 token 計算，價格是每個模型公布的 API 費率，比如 Pro 每月 10 美元，含 10 美元的額度，程式碼補全和 Next Edit 建議不占額度（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)、[Usage-based billing](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals)）。年繳的 Pro 和 Pro+ 到期之前還用舊的 premium request 模式，Pro 每月 300 次，Pro+ 每月 1,500 次，你發的每個 prompt 算一次，再乘上模型的倍率，agent 自己做的工具呼叫不算（[Copilot requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)）。

這兩種模式鼓勵的習慣不一樣。按請求計費時，一次很長的自主執行對你來說很便宜，所以把一個大任務放進一個 prompt 裡做可能很划算；按 token 計費時，一次執行花多少錢和它讀了多少成正比，這一章講的省錢辦法就非常要緊。

### 結果不對時，最後才換模型

結果不對的時候，最容易想到的就是換一個更大的模型，但這是最貴的辦法，而且常常沒用，所以換之前先看看到底出了什麼問題：

| 出了什麼問題 | 先試什麼 |
| --- | --- |
| 它不知道一條規則、一個名字，或者專案裡的做法 | 寫進規則或知識檔。更大的模型一樣不知道 |
| 它說「做完了」，其實沒有 | 加一道檢查：跑測試（[讓 agent 能檢查自己的活](5-4-self-checks.html)） |
| 在長會話裡它丟了線索 | 開一個新會話，把狀態放在檔案裡帶過去（[長對話會變差](3-2-long-sessions.html)） |
| 它什麼都知道，推理還是不行 | 這時再試更強的模型 |

### 四個省錢的辦法，以及各自怎樣會過頭

第一個辦法排在成本的三部分之前，乾脆不呼叫模型，後三個分別對應讀、寫和重做，而且四個辦法都可能做過頭。

1. **少用模型**。程式能做的就別問模型，計數、複製檔案、把 Word 檔轉成文字、檢查格式，這些工作腳本每次都做得一樣，而且不花 token。做過頭是把需要判斷的事交給了不會判斷的程式（[誰來判斷：程式、便宜模型、主模型、人](5-9-who-decides.html)）。
2. **少讀**。規則寫短，細節需要時才載入，要 diff 不要整個檔案。做過頭是它缺資訊就去猜，重做的錢比省下的讀取還多。
3. **少寫**。讓它給一句話的結論或者一份簡短的清單。做過頭是輸出簡略到下一步用不上。
4. **少重做**。動手前先商定計畫，把狀態放在檔案裡，會話丟了也能接著做，再給重試的次數設個上限。做過頭是上限卡掉了有用的工作，所以上限要根據你見到的情況來定，不要根據擔心來定。

還有一類固定成本，不管你在任務裡怎麼選，每次呼叫都要付。只要一個工具載入了上下文，它的名字、描述和參數就算在每次呼叫的輸入裡（[Agent 用不好工具，先看工具的描述和錯誤訊息](1-2-tool-calling.html)），你注入的每條規則也每一輪都跟著走，所以用不上的工具和規則要拿掉。不過工具不一定全部載入，Claude Code 和 VS Code（Claude Sonnet 4.5、Opus 4.5 以上）預設用工具搜尋，一部分工具先不載入，用到時才搜出來載入完整定義（[接 MCP server 之前，要想清楚什麼？](1-3-mcp.html)）。

### 帳單讓你意外的時候

如果帳單比你預想的高，先問自己三個問題。第一，哪次呼叫或哪一輪讀得最多，看看工具的用量頁面，再看看最大的那幾個任務。第二，上下文裡有什麼是不必在那裡的，比如舊的工具結果、整個讀進來的大檔案、很長的規則檔。第三，任務有沒有被重做，如果有，第一次為什麼失敗。

在兩個模型之間做選擇時，做一個小實驗就夠了：挑一個你知道正確答案的任務，在兩個模型上各跑三次，記下用量和結果對不對，然後比較每次成功的成本，別憑一次執行就下結論。一張四欄的表就行：

| 第幾次 | 模型 | 用量（來自你的用量頁面） | 對嗎？ |
| --- | --- | --- | --- |
| 1 | A | | |
| 2 | A | | |
| 3 | A | | |
| 1 | B | | |
| 2 | B | | |
| 3 | B | | |

## 省錢也有代價，最容易踩的坑是讀得太少 {#costs-and-traps}

最容易踩的坑是讀得太少。最便宜的呼叫，恰恰可能是猜錯了然後被丟掉的那一次，如果一個任務總是因為缺上下文而失敗，該做的是給它正確的上下文，而不是給得更少。

控制手段本身也要花錢：在工具呼叫上執行的 [hook](2-2-hooks.html) 會帶來一點延遲，獨立檢查要再呼叫一次模型，每個 prompt 都注入的規則，每個 prompt 都要花 token。我是為了控制而有意接受這些的，但它們終究是成本。

另外，上面的價格和 Copilot 的計費方式都是 2026 年 10 月底的情況，它們還會變，而且變的不只是價格，還有收費時數的是什麼，Copilot 這次就從數請求改成了數 token。

## 模型供應商也是這樣收費的 {#industry}
{status: industry}

Anthropic 把讀快取的價格定得只有一般輸入的一小部分，並且說明工具定義也按輸入 token 計算（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）。GitHub 把 Copilot 從按請求計費改成了按 token 計費（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）。市場現在是按模型讀和寫了多少來收費的，所以按任務算成本，這筆帳才對得上帳單。

## 什麼時候可以刪掉這些省錢技巧 {#when-to-delete-it}
{status: industry}

這一章的很多內容，是寫給讀取很貴的世界的建議。如果有一天讀取便宜到，精簡上下文多花的功夫比省下的還多，那就把這些技巧丟掉，只留下核算每個完成任務的成本這個習慣。另外，如果哪個平台開始自己顯示每個任務的成本，我也會重新考慮，因為到那時，你需要猜的就少了。
