讀這一章，只需要用過寫程式的 AI agent，並且看過它的用量或帳單頁面。其他都不用。

## 一句話 {#in-one-sentence}

評斷一個模型，要看做完一個任務花多少，而不是每個 token 的單價。這筆錢大部分花在模型讀的東西上，所以少讀、少重做，省得最多。

## 給主管 {#for-leaders}

- **要做的決定**：評斷模型和設定，看的是做完一個任務的成本，不是每個 token 的單價。結果不好的時候，先試比較便宜的修法（是不是缺了一條規則、缺了一道檢查，或是丟了線索），再考慮付錢換更大的模型。
- **風險**：在長的 agent 任務裡，大部分 token 都花在模型一再重讀同樣的材料上。在我的算例裡（數字是我挑的整數），讀的部分占了 token 的九成以上。快取（cache）可以讓帳單降很多，但前提是輸入的開頭一直不變。
- **做對的成本**：主要是設定的時間，再加上量測的習慣。想公平地比較模型，要挑幾個任務，每個跑三次左右。
- **可以問團隊**：「我們做完一個任務要花多少？上次確認這個數字是什麼時候？」

## 你到底在為什麼付錢？ {#problem}

比較模型，通常從一張價目表開始，上面寫著每百萬個 token 多少美元。**token** 是一小段文字，大約是一個短的英文單字，或單字的一部分；模型用 token 讀和寫，所以帳單也用 token 算。token 又分兩種：**輸入** token 是模型在一次呼叫裡讀的，**輸出** token 是它寫出來的。兩者的價格不同，通常輸出每個 token 比較貴。

價目表上的數字查得到，所以大家都拿它來比。可是你買 token，從來不是為了 token 本身。你買的是一件做完的事，像是修好一個 bug、寫好一份報告，所以重要的是那件事總共花了多少。

拿價目表來估這個總花費並不可靠，原因有兩個。第一，便宜的模型如果任務失敗，還得再問一次，算下來可能比第一次就做對的強模型更貴。第二，在 agent 裡，token 的數量和你預期的不一樣，下面就來看看。

### 在 agent 裡，token 去哪了

token 的數量為什麼會出乎意料？在對話裡，你送出一個問題，得到一個回答，就結束了。在 agent 迴圈裡（[agent 循環，和你能插手的地方](2-1-agent-loop.html)），每個工具結果出來之後，模型都會被再呼叫一次，而每次呼叫都要把到目前為止的整段對話重新送出：規則、需求、它讀過的每個檔案、每個結果。模型在兩次呼叫之間沒有記憶，只有這樣，它才知道之前發生過什麼。這些內容都得放進**上下文視窗**，也就是模型一次能看到的文字。視窗本身有大小上限（怎麼管它，[上下文是一份預算](3-1-context-budget.html) 會講），而每次呼叫都會把它從頭重新裝滿一遍。

::: figure 1-1-token-flow

我們用整數來算一遍。這些數字是我為了好算而挑的，不是量出來的。假設規則加你的需求一共 10,000 個 token，每個工具結果再加 5,000。呼叫 10 次下來，模型讀的大約是 10,000 + 15,000 + 20,000 + …… = 325,000 個 token，但每次呼叫寫的大概只有幾百個 token。在這個例子裡，讀的部分占了 token 的九成以上。實際的比例要看你的任務，但迴圈跑得越久，就越偏向讀。

當然，輸出每個 token 比較貴，所以 token 數不等於錢。不過大致的樣子不變：長的 agent 任務，多半是模型在一遍又一遍地讀同樣的材料。這也是為什麼這一章的後半，講的都是怎麼少讀。

我還可以舉一個真實的例子。在 [慎用子 agent](2-3-subagents.html) 裡，我把同樣的四個任務，分別交給一個有三個職位、由三個 agent 組成的團隊，和一個單獨的 agent。兩邊每個任務都答對了，團隊用掉的卻是後者的 4.5 倍左右。浪費最多的就是重讀，因為每個新的 agent 都從空的上下文開始，只好把同樣的檔案再讀一遍。那只是四個小任務，每個只跑一次，所以方向可以相信，倍數不要當真。

### prompt 快取改變了算式

既然每次呼叫有這麼大一段開頭都一樣，供應商就提供了 **prompt 快取**：它記住你輸入裡很長的一段開頭，之後的呼叫只要開頭是同樣的文字，那一段就可以收得便宜些。在 Anthropic 的 API 上，大多數模型讀快取的輸入，只收基本輸入價的十分之一，有些模型更低。寫入快取則比一般的讀取貴，五分鐘的快取是 1.25 倍，一小時的快取是 2 倍（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。

這幾個價格最直接的影響是，開頭越穩定越划算。因為快取只認從輸入開頭起完全一致的內容，只要你改了靠近頂端的東西，例如改了一條規則、換了一份工具清單，它後面的所有內容就都沒辦法命中快取。反過來，停下來也可能要付錢：快取只活很短的時間，一段對話你離開一小時再回來，可能就得付全價把它重建一遍。不過，就算每次都命中，讀快取也不是免費的：**最便宜的 token，仍然是沒送出去的那個**。少讀仍然是第一件該試的事。

快取到底能省多少？還是用同一個例子，假設快取每次都命中，只算輸入，用五分鐘的價格。第一次呼叫寫入 10,000 個 token，乘 1.25 倍，是 12,500。接下來九次呼叫，之前的文字都從快取讀。快取的部分從 10,000 個 token 增加到 50,000 個，九次加起來是 270,000，乘 0.1 倍是 27,000。每次呼叫也都要寫入新的 5,000 個 token，共 45,000，乘 1.25 倍是 56,250。加起來大約是 96,000 個 token 的價格，而不是 325,000，重複讀取的部分現在也只占不到三分之一。

換句話說，快取改變的是錢花在哪裡：從重讀，轉到新材料上。這樣一來就能明白，前面說的「九成以上」算的是讀了多少 token，不是帳單的占比；也能明白為什麼快取維護得好的團隊，可以讀很多，卻付得很少。可是一旦沒命中，這些就都白省了：例如改了開頭的規則，或是停太久、快取過期了，成本就會被拉回 325,000 附近。

## 一個任務的錢花在哪裡，又該從哪裡省 {#how-it-works}

### 一個任務花多少

讀、寫和快取都看過了，我們可以把做完一個任務的成本拼起來。不妨把它想成三個部分。

::: figure 1-1-cost-parts

1. **模型讀的**，每次呼叫都算，快取命中的地方有折扣。
2. **模型寫的**：回答、程式碼、思考。
3. **重做**，也就是答錯、丟了線索、再試一次。重做是第 1、2 部分的乘數。

這三部分裡，能省的大多在第一和第三部分。一個好用的經驗法則是：**在夠用的方式裡挑最便宜的**。

### 強模型什麼時候比較便宜

選哪個模型，也正是在重做這一項上見分曉。更強的模型每個 token 更貴，但如果它一次就得到答案，弱的模型卻要三次，那麼算到每個做完的任務上，強模型的成本反而可能更低。不過，如果任務很簡單，用強模型也可能是浪費。

轉折點在哪裡？我自己沒有量過，所以這只是論證，不是結果。要找到那一點，辦法是在你自己的任務上測：拿同樣幾個任務在兩個模型上跑，比較每次成功的成本，而不是每次呼叫的成本。怎麼誠實地做這件事，[一次運行證明不了什麼](6-4-variance.html) 會講。

### 依任務挑模型，再確認一下設定

我自己的經驗法則同樣沒有量過，大致是：用強模型來想，像是定計劃、找做法、處理難的 bug；用中等的模型來做，像是一處計劃已經很清楚的改動。有些工具還讓你設定**推理強度**，這是某些模型有的設定，控制它回答之前想多久。想得越多，通常輸出的 token 越多，時間也越長。至於 Copilot 能不能從 harness 裡調它，我還沒測過，你得查一下自己的工具。

### 在 Copilot 裡怎麼計費（2026 年 10 月下旬）

你實際付多少，取決於你的方案，而 Copilot 的方案常常變，請對照日期確認你自己的。

- **按月的 Copilot 方案**：從 2026 年 6 月 1 日起，Copilot 一直在轉向按用量計費。premium request unit 換成了 GitHub AI Credits，用量依輸入、輸出和快取的 token 算，按每個模型公開的 API 費率。程式碼補全和 next edit suggestions 仍包含在內。（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）
- **年繳的 Pro 和 Pro+ 方案**，在到期之前仍用舊的 premium request 模式。在這種模式下，你送出的每個 prompt 算一次請求，再乘上該模型的倍率，而 agent 做的工具呼叫不算。（[Copilot requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)）

這兩種模式獎勵的習慣不一樣。按請求計費時，一次長的自主執行對你來說很便宜，所以把一個大任務放進一個 prompt 裡做，可能很划算。按 token 計費時，一次長的執行花多少，和它讀了多少成正比。所以你用的是哪一種，決定了這一章其餘的部分對你有多重要。如果你的方案按 token 計費，那就非常重要。

### 結果不對時，最後才換模型

說回選模型。結果不對的時候，最容易的反應是換成更大的模型。可是這也是最貴的修法，而且常常是錯的。換之前，先看看哪裡出了問題：

| 出了什麼問題 | 先試 |
| --- | --- |
| 它不知道一條規則、一個名字，或專案怎麼做這件事 | 把它寫進規則或知識檔。更大的模型也不知道 |
| 它說「做完了」，其實沒有 | 加一道檢查：執行測試（[讓 agent 能檢查自己的活](5-4-self-checks.html)） |
| 在長會話裡丟了線索 | 開一個新會話，把狀態放在檔案裡帶過去（[長對話會變差](3-2-long-sessions.html)） |
| 它什麼都知道，推理還是不好 | 這時再試更強的模型 |

### 四種省法，以及各自怎樣過頭

選模型只是其中一個槓桿。下面四種省法裡，第一種排在成本的三個部分之前：乾脆不呼叫模型。後三種依序對應那三個部分，而且四種都可能做過頭。

1. **少用模型**。程式碼能做的，就不要去問模型。計數、複製檔案、把 Word 檔轉成文字、檢查格式，這些事腳本每次都做得一樣，也不用 token。危險是把需要判斷的事搬進一段不會判斷的程式，這條線畫在哪裡，見[誰來判斷：程式、便宜模型、主模型、人](5-9-who-decides.html)。
2. **少讀**。規則寫短，細節要用時才載入，要 diff 而不是整個檔案。危險是讀太少，它就會猜，而重做花的錢比省下來的讀取還多。
3. **少寫**。要簡短的回答，例如一行結論、一份短清單。危險是簡短到下一步用不上。
4. **少重做**。工作開始前先談好計劃，把狀態放在檔案裡，這樣會話丟了也能接著做，再限制重試的次數。危險是上限切斷了有用的工作，所以上限要依你看到的情況設，而不是依擔心設。

還有一類固定的成本，不管你在任務裡怎麼選，每次呼叫都要付。agent 有的每個工具，都會把它的名字、描述和參數加進每次呼叫的輸入裡（[Tool calling，和給 agent 設計工具](1-2-tool-calling.html)），而你注入的每條規則，也每一輪都跟著走。

### 帳單讓你吃驚的時候

如果帳單比你預期的高，先問自己三個問題。

1. 哪一次呼叫或哪一輪讀得最多？看看你工具的用量頁面，再看看最大的幾個任務。
2. 上下文裡有什麼其實不必放在那裡？舊的工具結果、整份讀進來的大檔案、很長的規則檔？
3. 任務有沒有被重做？如果有，第一次為什麼失敗？

在兩個模型之間做選擇時，同樣的檢查習慣也用得上，做一個小實驗就夠了。挑一個你知道正確答案的任務，在兩個模型上各跑三次，記下用量和對不對，然後比較每次成功的成本。不要憑一次執行就下決定。一個四欄的表就行：

| 執行 | 模型 | 用量（從你的用量頁面） | 對嗎？ |
| --- | --- | --- | --- |
| 1 | A | | |
| 2 | A | | |
| 3 | A | | |
| 1 | B | | |
| 2 | B | | |
| 3 | B | | |

## 省錢要付出什麼，我又看不到什麼 {#costs-and-traps}

我在這一章說的所有節省，都是「依設計」算的，不是從帳單上讀出來的，因為我手上的工具只讓我看到這麼多。我自己的 harness，日誌裡沒有記 token 數。一個任務真正用了多少，我讀的是平台的會話紀錄，它回報的是 credits 和 premium request，我也不把它們換算成錢。

而這些節省本身也有代價。在工具呼叫上執行的 [hook](2-2-hooks.html) 會加一點延遲，獨立檢查要再呼叫一次模型，每個 prompt 都注入的規則，每個 prompt 都要花 token。我是為了控制才刻意接受這些，但它們終究是成本。

最像節儉的陷阱，是讀得太少。最便宜的呼叫，恰恰是猜錯然後被丟掉的那一個。如果一個任務一直因為缺上下文而失敗，該做的是給它對的上下文，而不是給它更少。

另外，價格和方案都會變。上面的快取倍率和 Copilot 計費，是來源上那些日期的情況，我預期它們還會變。不過，變的不只是價格，還有收費時算的是什麼。

## 市場也是這樣算的嗎？ {#industry}
{status: industry}

這一章依靠的兩家供應商，指向同一個方向。Anthropic 把讀取快取的價格訂成一般輸入的一小部分，並且說明工具定義在每個請求裡都算輸入 token（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）。GitHub 把 Copilot 從算請求改成算 token（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）。換句話說，市場現在按模型讀和寫了多少來收費，這正是這一章的論點。

## 什麼時候可以刪掉這些省錢技巧 {#when-to-delete-it}
{status: industry}

這一章有很多是為「讀取很貴」的世界寫的建議。如果有一天讀取便宜到，修剪上下文多出來的工夫比省下的還多，那就丟掉這些技巧，只留下量測每個完成任務成本的習慣。另外，如果某個平台開始自己顯示每個任務的成本，我也會重新看一遍，因為到那時，你要猜的就少了。
