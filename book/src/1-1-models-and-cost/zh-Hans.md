读这一章，只需要用过写代码的 AI agent，并且看过它的用量页面或账单页面。

## 一句话 {#in-one-sentence}

选模型要看做完一个任务花多少钱，不是看每个 token 的单价，而这笔钱大部分花在模型反复读的东西上，所以少读、少返工省得最多。

## 写给管理者 {#for-leaders}

- **要拍板的事**：评价模型和配置，看做完一个任务的成本，不看每个 token 的单价。结果不好的时候，先试便宜的办法（是不是缺了一条规则、缺了一道检查，或者线索丢了），再考虑花钱换更大的模型。
- **风险**：一个长的 agent 任务，大部分钱都花在模型反复重读同样的内容上。在我的算例里（数字是我挑的整数），读占了九成五以上的钱。缓存能把账单降到四分之一左右，但前提是输入的开头一直不变。
- **做对的代价**：主要是配置的时间，再加上一个量化的习惯。想公平地比较模型，要挑几个任务，每个跑三次左右。
- **可以问团队**：“做完一个任务，我们要花多少钱？上次核对这个数字是什么时候？”

## 你的钱花到哪去了 {#problem}

选模型的时候，大家一般都从价目表开始：Sonnet 5.5 每百万个输入 token 2 美元、输出 token 10 美元，Opus 5.5 是 4 美元和 20 美元（[Pricing](https://platform.claude.com/docs/en/about-claude/pricing)，2026 年 10 月底的价格）。token 是模型读写文本的单位，大致相当于一个短的英文单词或者单词的一部分，模型读的叫输入 token，写的叫输出 token，输出通常贵得多。价目表的数字好查，所以大家都拿它来比，但是你其实不是在买 token，你买的是一件做完的事，比如修好一个 bug，所以要比的是这件事一共花了多少钱。这个数和单价差得很远，一是因为便宜的模型做砸了要再跑一遍，算下来可能比一次做对的贵模型还贵，二是因为 agent 用掉的 token 比你想的多得多，而且大部分花在读上。

### agent 里的 token 都去了哪

在聊天里，你发一个问题，模型回一段话，一次调用就结束了。agent 跑的是一个循环（[Agent 到底是怎么干活的？](2-1-agent-loop.html)）：模型说要读一个文件，程序读完把结果发回去，模型再决定下一步，所以每拿到一个工具结果，模型都要被重新调用一次。模型在两次调用之间没有记忆，每次调用都要把到目前为止的整段对话重新发一遍，包括规则、需求、读过的每个文件和每个工具结果。这些内容都装在**上下文窗口**里，也就是模型一次能看到的全部文本，它有大小上限（[为什么不能把所有规则都塞给 Agent？](3-1-context-budget.html)），而你每调用一次，就要为里面的内容付一次钱。

::: figure 1-1-token-flow

我们用整数算一笔账，这些数字是我为了好算挑的，不是测出来的。假设规则加需求一共 10,000 个 token，每个工具结果再加 5,000 个，一个任务调用 10 次模型，每次写 300 个 token。模型一共读了 10,000 + 15,000 + …… + 55,000 = 325,000 个 token，写的只有 3,000 个。换成钱差距一样大：用 Sonnet 5.5 的价格，读要 0.65 美元，写只要 0.03 美元，输出的单价虽然贵 5 倍，读的量却大了 100 多倍。循环跑得越久，钱就越往读上偏，因为每多一次调用，前面所有的内容都要再读一遍。

### prompt 缓存改变了这笔账

每次调用的开头几乎都一样，所以模型提供方做了 **prompt 缓存**：它记住你输入的开头一段，下一次调用只要开头一字不差，这一段就按很低的价格算。Anthropic 的价格是这样的：写入缓存比普通输入贵，5 分钟的缓存是 1.25 倍，1 小时的缓存是 2 倍，读缓存便宜得多，大多数模型是输入价的十分之一，Opus 5.5 和 Sonnet 5.5 是二十分之一（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。

还是上面那个例子，用 Sonnet 5.5 的价格，假设缓存每次都命中。第一次调用把 10,000 个 token 写入缓存，后面九次调用，每次从缓存读之前的全部内容，九次加起来是 270,000 个 token，再把新增的 5,000 个写入缓存，九次加起来是 45,000 个。算下来写入花 0.1375 美元，读缓存花 0.027 美元，一共约 0.16 美元，只有原来 0.65 美元的四分之一。这 0.16 美元里大部分是新内容的写入费，缓存省不掉，只有少读才省得掉，所以就算缓存每次都命中，少读仍然是第一个该试的办法。

缓存也很容易失效，有三种情况。第一种是开头变了：缓存只认一字不差的内容，顺序是工具定义、系统提示、对话消息，哪一层变了，这一层和它后面的全部都命中不了，所以改一个工具的描述，整个缓存就没了，规则文件开头也别放当前时间这种每次都变的东西。第二种是停得太久：默认的缓存只活 5 分钟，每用一次会免费续期，你去开个会回来，它就过期了。第三种是开头太短：不到最小长度就不缓存，也不报错，Sonnet 5.5 的下限是 512 个 token，有些旧模型要 4,096 个。一直命中不了的话，成本就回到 0.65 美元附近，甚至更高，因为写入缓存比普通输入还贵。

## 怎么算一个任务的成本，又该从哪里省 {#how-it-works}

::: figure 1-1-cost-parts

一个任务的成本分三部分：模型读的（所有调用加起来，缓存命中的部分打折），模型写的（回答、代码、思考），还有返工（错误的回答、丢了的线索、重复的尝试）。返工不是单独的一笔钱，它是前两部分的乘数，返工一次，前两部分就要再付一遍。能省的大多在读和返工这两头，一条好用的经验法则是用够用的办法里最便宜的那个。

### 什么时候贵模型反而便宜

贵模型每个 token 贵，但是如果它一次就做对，算到每个做完的任务上可能反而便宜。算法很简单，做完一个任务的成本等于跑一次的成本除以成功率。Opus 5.5 的单价是 Sonnet 5.5 的 2 倍，假设两者跑一次用的 token 差不多，那么只有当 Sonnet 的成功率不到 Opus 的一半时，Opus 才更便宜，比如 Opus 能做对 80% 的任务，Sonnet 要低于 40%。这只是 token 的账，如果再算上你盯着它、帮它收拾的时间，这个点还会往贵模型那边挪。反过来，如果任务本来就简单，两个模型都能一次做对，用贵的就是白花钱。

成功率只能在你自己的任务上测：拿同样的几个任务，在两个模型上各跑几遍，比较每次成功的成本，而不是每次调用的成本（[同一个任务跑两次，结果不一样](6-4-variance.html)）。

### 按任务选模型，再看一眼推理强度

我自己的经验法则是思考用强模型，比如定计划、想思路、啃难的 bug，动手用中等的模型，比如做一处计划已经很清楚的改动。另外还有一个设置叫**推理强度**（thinking effort），它控制模型回答之前想多久，想得越多，通常输出的 token 越多，花的时间也越长。在 VS Code 里，点模型选择器里模型名字旁边的箭头就能选，不支持的模型不显示这一项（[AI language models](https://code.visualstudio.com/docs/copilot/customization/language-models)）。开到最高不一定更好，[什么是 Harness Engineering？](0-1-the-gap-and-the-map.html)里 LangChain 的实验就是全程用最高档的分数反而更低，因为很多任务超时了。

### Copilot 怎么计费（截至 2026 年 10 月底）

Copilot 的月付套餐从 2026 年 6 月 1 日起改成了按用量计费：高级请求被 GitHub AI Credits 取代，1 个 credit 等于 0.01 美元，用量按输入、输出和缓存的 token 计算，价格是每个模型公布的 API 费率，比如 Pro 每月 10 美元，含 10 美元的额度，代码补全和下一处编辑建议不占额度（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)、[Usage-based billing](https://docs.github.com/en/copilot/concepts/billing/usage-based-billing-for-individuals)）。年付的 Pro 和 Pro+ 到期之前还用旧的高级请求模式，Pro 每月 300 次，Pro+ 每月 1,500 次，你发的每个 prompt 算一次，再乘上模型的倍率，agent 自己做的工具调用不算（[Copilot requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)）。

这两种模式鼓励的习惯不一样。按请求计费时，一次很长的自主运行对你来说很便宜，所以把一个大任务放进一个 prompt 里做可能很划算；按 token 计费时，一次运行花多少钱和它读了多少成正比，这一章讲的省钱办法就非常要紧。

### 结果不对时，最后才换模型

结果不对的时候，最容易想到的就是换一个更大的模型，但这是最贵的办法，而且常常没用，所以换之前先看看到底出了什么问题：

| 出了什么问题 | 先试什么 |
| --- | --- |
| 它不知道一条规则、一个名字，或者项目里的做法 | 写进规则或知识文件。更大的模型一样不知道 |
| 它说“做完了”，其实没有 | 加一道检查：跑测试（[让 Agent 自己跑测试](5-4-self-checks.html)） |
| 在长会话里它丢了线索 | 开一个新会话，把状态放在文件里带过去（[对话越久，Agent 越笨](3-2-long-sessions.html)） |
| 它什么都知道，推理还是不行 | 这时再试更强的模型 |

### 四个省钱的办法，以及各自怎样会过头

第一个办法排在成本的三部分之前，干脆不调用模型，后三个分别对应读、写和返工，而且四个办法都可能做过头。

1. **少用模型**。代码能做的就别问模型，计数、复制文件、把 Word 文件转成文本、检查格式，这些活脚本每次都做得一样，而且不花 token。做过头是把需要判断的事交给了不会判断的代码（[这个判断该交给谁：代码、便宜模型、主模型，还是人？](5-9-who-decides.html)）。
2. **少读**。规则写短，细节需要时才加载，要 diff 不要整个文件。做过头是它缺信息就去猜，返工的钱比省下的读取还多。
3. **少写**。让它给一句话的结论或者一个简短的清单。做过头是输出简略到下一步用不上。
4. **少返工**。动手前先商定计划，把状态放在文件里，会话丢了也能接着做，再给重试的次数设个上限。做过头是上限卡掉了有用的工作，所以上限要根据你见到的情况来定，不要根据担心来定。

还有一类固定成本，不管你在任务里怎么选，每次调用都要付。agent 的每个工具都会把名字、描述和参数加进每次调用的输入里（[Agent 用不好工具，先看工具的描述和报错](1-2-tool-calling.html)），你注入的每条规则也每一轮都跟着走，所以用不上的工具和规则要拿掉。

### 账单让你意外的时候

如果账单比你预想的高，先问自己三个问题。第一，哪次调用或哪一轮读得最多，看看工具的用量页面，再看看最大的那几个任务。第二，上下文里有什么是不必在那里的，比如旧的工具结果、整个读进来的大文件、很长的规则文件。第三，任务有没有被重做，如果有，第一次为什么失败。

在两个模型之间做选择时，做一个小实验就够了：挑一个你知道正确答案的任务，在两个模型上各跑三次，记下用量和结果对不对，然后比较每次成功的成本，别凭一次运行就下结论。一张四列的表就行：

| 第几次 | 模型 | 用量（来自你的用量页面） | 对吗？ |

## 省钱也有代价，最容易踩的坑是读得太少 {#costs-and-traps}

最容易踩的坑是读得太少。最便宜的调用，恰恰可能是猜错了然后被扔掉的那一次，如果一个任务总是因为缺上下文而失败，该做的是给它正确的上下文，而不是给得更少。

控制手段本身也要花钱：在工具调用上运行的 [hook](2-2-hooks.html) 会带来一点延迟，独立检查要再调用一次模型，每个 prompt 都注入的规则，每个 prompt 都要花 token。我是为了控制而有意接受这些的，但它们终究是成本。

另外，上面的价格和 Copilot 的计费方式都是 2026 年 10 月底的情况，它们还会变，而且变的不只是价格，还有收费时数的是什么，Copilot 这次就从数请求改成了数 token。

## 模型提供方也是这么收费的 {#industry}
{status: industry}

Anthropic 把读缓存的价格定得只有普通输入的一小部分，并且说明工具定义在每次请求里都按输入 token 计算（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）。GitHub 把 Copilot 从按请求计费改成了按 token 计费（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）。市场现在是按模型读和写了多少来收费的，所以按任务算成本，这笔账才对得上账单。

## 什么时候可以删掉这些省钱技巧 {#when-to-delete-it}
{status: industry}

这一章的很多内容，是写给读取很贵的世界的建议。如果有一天读取便宜到，精简上下文多花的功夫比省下的还多，那就把这些技巧丢掉，只留下核算每个完成任务的成本这个习惯。另外，如果哪个平台开始自己显示每个任务的成本，我也会重新考虑，因为到那时，你需要猜的就少了。
