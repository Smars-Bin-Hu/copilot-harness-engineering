读这一章，只需要用过写代码的 AI agent，并且看过它的用量页面或账单页面。别的都不需要。

## 一句话 {#in-one-sentence}

评价一个模型，看的是做完一个任务要花多少钱，不是每个 token 的单价。大部分成本是模型在读的东西，所以少读、少返工，省得最多。

## 写给管理者 {#for-leaders}

- **要拍板的事**：评价模型和配置，看做完一个任务的成本，不看每个 token 的单价。结果不好的时候，先试便宜的办法（缺一条规则、缺一道检查、线索丢了），再考虑花钱换更大的模型。
- **风险**：在一个长的 agent 任务里，大部分 token 是模型在反复重读同样的内容。在我的算例里（数字是我选的整数），读占了 90% 以上的 token。缓存能大幅降低账单，但只有输入的开头保持不变时才有用。
- **做对的代价**：主要是配置的时间，加上量化的习惯。公平地比较模型，是几个任务，每个跑大约三次。
- **可以问团队**：“做完一个任务，我们要花多少钱？上次核对这个数字是什么时候？”

## 问题 {#problem}

比较模型，通常从一张价目表开始：每百万 token 多少美元。这是查得到的数字，所以大家就用它。但你从来不是为 token 本身付钱。你买的是做完一件事：修好一个 bug，写完一份报告。要紧的是这件事的总价。

价目表不太靠谱，有两个原因。一个便宜的模型，任务失败了还得再问一遍，可能比一个一次就做对的强模型更贵。而且在 agent 里，token 的数量并不是你想的那样，下一节会讲。

### 先说五个词

- **token** 是一小段文本，大致是一个短词或半个词。模型按 token 读写，账单也按 token 算。
- **输入** token 是模型在一次调用里读的内容。**输出** token 是它写的内容。两者价格不同，输出的单价通常更贵。
- **上下文窗口**是模型一次能看到多少文本：你的需求、规则、它读过的文件、之前工具的结果。它有大小上限。[上下文是一份预算](3-1-context-budget.html)讲怎么管理它。
- **推理强度**是部分模型上的一个设置，控制它回答前想多久。想得多，通常意味着更多的输出 token 和更长的时间。
- **prompt 缓存**让提供方记住你输入里很长的一段开头，这样后面的调用如果以同样的文本开头，这部分就能少收钱。

### agent 里的 token 去了哪

在聊天里，你发一个问题，得到一个回答。在 agent 循环里（[agent 循环，以及你能插手的地方](2-1-agent-loop.html)），每拿到一个工具结果，模型就会被再调用一次。而每次调用都要把到目前为止的整个对话发过去：规则、需求、读过的每个文件、每个结果。模型在两次调用之间没有记忆，这是它知道发生了什么的唯一办法。

::: figure 1-1-token-flow

下面用整数来算，是我为了好算而选的，不是测出来的。假设规则加你的需求是 10,000 个 token，每个工具结果再加 5,000 个。10 次调用下来，模型读的大约是 10,000 + 15,000 + 20,000 + ... = 325,000 个 token，而每次调用写的可能只有几百个 token。在这个例子里，读占了 token 的 90% 以上。实际的比例取决于你的任务，但循环越长，越偏向读。

输出的单价更高，所以 token 数不等于钱。但这个形状是成立的：一个长的 agent 任务，大部分是模型在一遍遍地重读同样的内容。所以这一章的后半部分，讲的都是怎么少读。

我可以给一个真实的例子。在[慎用子 agent](2-3-subagents.html)里，我把同样的四个任务，分别交给了三个按岗位分工的 agent 组成的团队，和一个单干的 agent。两边每个任务都做对了。团队用掉的约是后者的 4.5 倍。最大的浪费就是重读：每个新开的 agent 都从空白的上下文开始，只好把同样的文件再读一遍。那是四个小任务，每个只跑了一次，所以方向可以信，倍数别当真。

### prompt 缓存改变了这笔账

每次调用的很大一部分都是同样的开头，所以提供方推出了 **prompt 缓存**。在 Anthropic 的 API 上，大多数模型读缓存的输入，价格是基础输入价的十分之一，有些更低。写入缓存比普通读取贵：五分钟的缓存是 1.25 倍，一小时的缓存是 2 倍。（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）

由此可以得出三点，它们会改变你省钱的办法：

- **稳定的开头划算**。缓存要求从输入的开头起完全一致才能命中。如果你改了靠前的东西（改了一条规则、换了工具列表），它后面的所有内容都没法命中缓存。
- **停一下可能要花钱**。缓存只活很短的时间。一个你放下一小时再回来的对话，可能要付全价来重建。
- **最便宜的 token 是没发出去的那个**。哪怕是读缓存也不是免费的。少读，仍然是第一个该试的办法。

下面是同一个例子，假设缓存每次都命中，只算输入，用五分钟缓存的价格。第一次调用写入 10,000 个 token，按 1.25 倍算，是 12,500。接下来九次调用，每次从缓存读之前的文本（从 10,000 个到 50,000 个 token，一共 270,000 个，按 0.1 倍算，是 27,000），再写入新增的 5,000 个 token（一共 45,000 个，按 1.25 倍算，是 56,250）。总共约合 96,000 个 token 的价钱，而不是 325,000，这时重复读取的部分已经不到三分之一。所以缓存改变的是钱花在哪：从重读，转到新内容。这也是为什么前面说的“90% 以上”，数的是读了多少 token，不是账单的占比；也是为什么缓存维护得好的团队，读很多也付得很少。缓存没命中的情况，就是前两条说的那些，会让成本回到 325,000 附近。

## 原理 {#how-it-works}

### 一个任务的成本

把一个任务的成本看成三部分。

::: figure 1-1-cost-parts

展开说：

1. **模型读的**，所有调用加起来，缓存命中的部分打折。
2. **模型写的**：回答、代码、思考。
3. **返工**：错误的回答、丢了的线索、重复的尝试。返工是第 1、2 部分的乘数。

大部分节省来自第一和第三部分。一条好用的经验法则是：**用够用的办法里最便宜的那个**。

### 什么时候强模型反而便宜

更强的模型，每个 token 更贵。但一次就答对，而弱的模型要试三次，那么做完一个任务，强模型花得可能更少。如果任务本来就简单，它也可能是浪费。

这个转折点在哪里，我没有自己的测量。这是一个推理，不是结果，找到这个点的办法，是在你自己的任务上测：同样的几个任务在两个模型上各跑一遍，比较每次成功的成本，而不是每次调用的成本。[一次运行证明不了什么](6-4-variance.html)讲了怎么老老实实地做这件事。

### 按任务选，并检查设置

我的经验法则（没有测过）：思考用强模型（计划、思路、难的 bug），动手用中等的模型（计划已经清楚的一处改动）。有些工具也能设置推理强度。Copilot 能不能从 harness 里设置，我没测过，请查你自己的工具。

### Copilot 怎么计费（截至 2026 年 10 月下旬）

这部分经常变，请核对日期和你自己的套餐。

- **按月的 Copilot 套餐**：从 2026 年 6 月 1 日起，Copilot 在改成按用量计费。高级请求单位被 GitHub AI Credits 取代，用量按输入、输出和缓存的 token 计算，价格是每个模型公布的 API 费率。代码补全和下一处编辑建议仍然包含在内。（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）
- **年度的 Pro 和 Pro+ 套餐**在到期前仍然用旧的高级请求模式。在这种模式里，你发的每个 prompt 算一次请求，再乘上该模型的倍率，agent 做的工具调用不算。（[Copilot requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)）

两种模式鼓励的习惯不同。按请求计费时，一次很长的自主运行对你来说很便宜，所以把大任务放在一个 prompt 里做，可能划算。按 token 计费时，一次长的运行，成本和它读了多少成正比。你用的是哪一种，决定了这一章其余部分对你有多要紧。如果你的套餐按 token 计费，那就非常要紧。

### 结果不对时，最后才换模型

结果不好，最容易想到的反应是换更大的模型。这是最贵的办法，也常常是错的。先看出了什么问题：

| 出了什么问题 | 先试什么 |
| --- | --- |
| 它不知道一条规则、一个名字，或者项目里的做法 | 写进规则或知识文件。更大的模型一样不知道 |
| 它说“做完了”，其实没有 | 加一道检查：跑测试（[让 agent 能检查自己的活](5-4-self-checks.html)） |
| 在长会话里它丢了线索 | 开一个新会话，把状态放在文件里带过去（[长对话会变差](3-2-long-sessions.html)） |
| 它什么都知道，推理还是不行 | 这时再试更强的模型 |

### 四个省钱的办法，以及各自怎样会过头

1. **少用模型**。代码能做的，就别问模型。计数、复制文件、把 Word 文件转成文本、检查格式：脚本每次都做得一样，而且不用 token。危险在于把判断交给了判断不了的代码。[谁来判断：代码、便宜模型、主模型、人](5-9-who-decides.html)划出了这条线。
2. **少读**。规则保持简短，细节需要时才加载，要 diff 而不是整个文件。危险：读得太少，它就会猜，返工的成本比省下的读取更高。
3. **少写**。要求简短的回答、一句话的结论、一个简短的清单。危险：输出太简略，下一步用不上。
4. **少返工**。动手前先商定计划，把状态放在文件里，丢了的会话才能接着做，并且给重试的次数设上限。危险：上限卡掉了有用的工作。上限要根据你见到的情况来定，不要根据恐惧来定。

还要留意固定成本。agent 拥有的每个工具，都会把名字、描述和参数加进每次调用的输入里（[Tool calling，以及怎么给 agent 设计工具](1-2-tool-calling.html)），你注入的每条规则，每一轮都会带着走。

### 测一测你自己的配置

账单让你意外的时候，问**三个问题**：

1. 哪次调用或哪一轮读得最多？看你工具的用量页面，和最大的那几个任务。
2. 上下文里有什么是不必在那里的？旧的工具结果、整个读进来的大文件、很长的规则文件？
3. 任务有没有被重做？如果有，第一次为什么失败？

**一个小实验**。挑一个你知道正确答案的任务。在两个模型上各跑三次，记下用量和对不对。然后比较每次成功的成本。别凭一次运行下结论。一张四列的表就够了：

## 代价和坑 {#costs-and-traps}

**我看得到什么，看不到什么**。我自己的 harness 在日志里不记录 token 数。一个任务实际用了多少，我看的是平台的会话记录，它报告的是 credits 和高级请求，我不把它们换算成钱。所以我说的所有节省，都是“按设计”的，不是账单上的数字。

**节省不是免费的**。在工具调用上运行的 [hook](2-2-hooks.html) 会带来一点延迟。独立检查要再调用一次模型。每个 prompt 都注入的规则，每个 prompt 都要花 token。我是为了控制，有意接受这些，但它们是成本。

**读得太少，是看起来像节俭的坑**。最便宜的调用，是猜错然后被扔掉的那一次。如果一个任务总是因为缺上下文而失败，答案是给它正确的上下文，不是给得更少。

**价格和套餐会变**。上面的缓存倍率和 Copilot 的计费，都是截至来源里写的日期，我预计它们会变。

## 业界怎么说 {#industry}
{status: industry}

- **Anthropic** 把读缓存的价格定为普通输入的一小部分，并说工具定义在每次请求里都按输入 token 计算。（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）
- **GitHub** 把 Copilot 从按请求计费改成了按 token 计费。（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）

方向是一致的：市场现在按模型读和写的量收费，这正是这一章的论点。
