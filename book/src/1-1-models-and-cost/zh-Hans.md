读这一章，只需要用过写代码的 AI agent，并且看过它的用量页面或账单页面。别的都不需要。

## 一句话 {#in-one-sentence}

评价一个模型，要看做完一个任务花多少钱，而不是每个 token 的单价。这笔钱大部分花在模型读的东西上，所以少读、少返工，省得最多。

## 写给管理者 {#for-leaders}

- **要拍板的事**：评价模型和配置，看的是做完一个任务的成本，不是每个 token 的单价。结果不好的时候，先试便宜的办法（是不是缺了一条规则、缺了一道检查，或者线索丢了），再考虑花钱换更大的模型。
- **风险**：在一个长的 agent 任务里，大部分 token 都花在模型反复重读同样的内容上。在我的算例里（数字是我挑的整数），读占了 90% 以上的 token。缓存能让账单降下来很多，但前提是输入的开头一直不变。
- **做对的代价**：主要是配置的时间，再加上一个量化的习惯。想公平地比较模型，要挑几个任务，每个跑三次左右。
- **可以问团队**：“做完一个任务，我们要花多少钱？上次核对这个数字是什么时候？”

## 你到底在为什么付钱？ {#problem}

比较模型，通常从一张价目表开始，上面写着每百万 token 多少美元。**token** 是一小段文本，大致相当于一个短的英文单词，或者单词的一部分；模型按 token 读写，所以账单也按 token 算。token 又分两种：**输入** token 是模型在一次调用里读的内容，**输出** token 是它写出来的内容。两者价格不同，通常输出的单价更贵。

价目表上的数字查得到，所以大家都拿它来比。可你从来不是为了 token 本身付钱。你买的是一件做完的事，比如修好一个 bug、写完一份报告，所以要紧的是这件事一共花了多少。

拿价目表来估这个总价并不靠谱，原因有两个。一是便宜的模型如果把任务做砸了，还得再问一遍，算下来可能比一次就做对的强模型更贵。二是在 agent 里，token 的数量和你想的不一样，下面就来看看。

### agent 里的 token 都去了哪

token 的数量为什么会出乎意料？在聊天里，你发一个问题，得到一个回答，就结束了。在 agent 循环里（[agent 循环，以及你能插手的地方](2-1-agent-loop.html)），每拿到一个工具结果，模型都要被再调用一次，而每次调用都要把到目前为止的整段对话重新发过去：规则、需求、读过的每个文件、每个结果。模型在两次调用之间没有记忆，只有这样它才知道之前发生了什么。这些内容都得装进**上下文窗口**，也就是模型一次能看到的文本。窗口本身有大小上限（怎么管理它，[上下文是一份预算](3-1-context-budget.html)会讲），而每次调用都会把它从头重新装满一遍。

::: figure 1-1-token-flow

我们用整数来算一笔账。这些数字是我为了好算挑的，不是测出来的。假设规则加你的需求一共 10,000 个 token，每个工具结果再加 5,000 个。10 次调用下来，模型读的大约是 10,000 + 15,000 + 20,000 + ... = 325,000 个 token，每次调用写的却可能只有几百个。在这个例子里，读占了 token 的 90% 以上。实际的比例要看你的任务，但循环跑得越久，就越偏向读。

当然，输出的单价更高，所以 token 数不等于钱。不过大致的格局不变：一个长的 agent 任务，大部分时候都是模型在一遍遍地重读同样的内容。这也是为什么这一章的后半部分，讲的都是怎么少读。

我还可以举一个真实的例子。在[慎用子 agent](2-3-subagents.html)里，我把同样的四个任务，分别交给一个由三个按岗位分工的 agent 组成的团队，和一个单干的 agent。两边每个任务都做对了，可团队用掉的是后者的 4.5 倍左右。浪费最多的就是重读，因为每个新开的 agent 都从空白的上下文开始，只好把同样的文件再读一遍。那只是四个小任务，每个只跑了一次，所以方向可以信，倍数别当真。

### prompt 缓存改变了这笔账

既然每次调用的很大一部分都是同样的开头，提供方就推出了 **prompt 缓存**：它记住你输入里很长的一段开头，后面的调用只要以同样的文本开头，这一段就能少收钱。在 Anthropic 的 API 上，大多数模型读缓存的输入只收基础输入价的十分之一，有些模型更低。写入缓存则比普通读取贵，五分钟的缓存是 1.25 倍，一小时的缓存是 2 倍（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)）。

这几个价格最直接的影响是，开头越稳定越划算。因为缓存只认从输入开头起一模一样的内容，只要你改了靠前的东西，比如改了一条规则、换了一份工具列表，它后面的所有内容就都命中不了缓存。反过来，停下来也可能要花钱：缓存只能活很短的时间，一个对话你放下一小时再回来，可能就得付全价把缓存重建一遍。不过，就算每次都命中，读缓存也不是免费的：**最便宜的 token，仍然是没发出去的那个**。少读仍然是第一个该试的办法。

缓存到底能省多少？还是用同一个例子，假设缓存每次都命中，只算输入，用五分钟缓存的价格。第一次调用写入 10,000 个 token，按 1.25 倍算是 12,500。接下来的九次调用，之前的文本都从缓存里读。缓存的部分从 10,000 个 token 涨到 50,000 个，九次加起来是 270,000 个，按 0.1 倍算是 27,000。每次调用还要写入新增的 5,000 个 token，一共 45,000 个，按 1.25 倍算是 56,250。加起来约合 96,000 个 token 的价钱，而不是 325,000，重复读取的部分也只占了不到三分之一。

换句话说，缓存改变的是钱花在哪里：从重读，转到了新内容上。这下就能明白，前面说的“90% 以上”数的是读了多少 token，不是账单的占比；也能明白为什么缓存维护得好的团队，读得很多，付得却很少。可一旦没命中，这些就都白省了：比如改了开头的规则，或者停得太久、缓存过期了，成本就会回到 325,000 附近。

## 一个任务的钱花在哪，又该从哪里省 {#how-it-works}

### 一个任务的成本

读、写和缓存都看过了，我们可以把做完一个任务的成本拼起来了。不妨把它看成三部分。

::: figure 1-1-cost-parts

1. **模型读的**，所有调用加起来，缓存命中的部分打折。
2. **模型写的**：回答、代码、思考。
3. **返工**，也就是错误的回答、丢了的线索、重复的尝试。返工是第 1、2 部分的乘数。

这三部分里，能省的大多在第一和第三部分。一条好用的经验法则是：**用够用的办法里最便宜的那个**。

### 什么时候强模型反而便宜

选哪个模型，也正是在返工这一项上见分晓。更强的模型每个 token 更贵，可如果它一次就答对，而弱的模型要试三次，那么算到每个做完的任务上，强模型反而可能花得更少。不过，如果任务本来就简单，用强模型也可能是浪费。

转折点在哪里？我自己没有测过，所以这只是一个推理，不是结果。要找到这个点，办法是在你自己的任务上测：拿同样的几个任务，在两个模型上各跑一遍，比较每次成功的成本，而不是每次调用的成本。怎么老老实实地做这件事，[一次运行证明不了什么](6-4-variance.html)会讲。

### 按任务选模型，再看一眼设置

我自己的经验法则同样没有测过，大致是：思考用强模型，比如定计划、想思路、啃难的 bug；动手用中等的模型，比如做一处计划已经很清楚的改动。有些工具还能设置**推理强度**，这是部分模型上的一个设置，控制它回答之前想多久。想得越多，通常输出的 token 越多，花的时间也越长。至于 Copilot 能不能从 harness 里调它，我没测过，你得查一下自己用的工具。

### Copilot 怎么计费（截至 2026 年 10 月下旬）

你实际付多少钱，取决于你的套餐，而 Copilot 的套餐经常变，请对照日期核对你自己的。

- **按月的 Copilot 套餐**：从 2026 年 6 月 1 日起，Copilot 在改成按用量计费。高级请求单位被 GitHub AI Credits 取代，用量按输入、输出和缓存的 token 计算，价格是每个模型公布的 API 费率。代码补全和下一处编辑建议仍然包含在内。（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）
- **年度的 Pro 和 Pro+ 套餐**在到期前仍然用旧的高级请求模式。在这种模式下，你发的每个 prompt 算一次请求，再乘上该模型的倍率，而 agent 做的工具调用不算。（[Copilot requests](https://docs.github.com/en/copilot/concepts/billing/copilot-requests)）

这两种模式鼓励的习惯不一样。按请求计费时，一次很长的自主运行对你来说很便宜，所以把一个大任务放进一个 prompt 里做，可能很划算。按 token 计费时，一次长的运行花多少钱，和它读了多少成正比。所以你用的是哪一种，决定了这一章剩下的内容对你有多要紧。如果你的套餐按 token 计费，那就非常要紧。

### 结果不对时，最后才换模型

说回选模型。结果不对的时候，最容易想到的就是换一个更大的模型。可这也是最贵的办法，而且常常是错的。换之前，先看看到底出了什么问题：

| 出了什么问题 | 先试什么 |
| --- | --- |
| 它不知道一条规则、一个名字，或者项目里的做法 | 写进规则或知识文件。更大的模型一样不知道 |
| 它说“做完了”，其实没有 | 加一道检查：跑测试（[让 agent 能检查自己的活](5-4-self-checks.html)） |
| 在长会话里它丢了线索 | 开一个新会话，把状态放在文件里带过去（[长对话会变差](3-2-long-sessions.html)） |
| 它什么都知道，推理还是不行 | 这时再试更强的模型 |

### 四个省钱的办法，以及各自怎样会过头

选模型只是其中一个抓手。下面四个省钱的办法里，第一个排在成本的三部分之前：干脆不调用模型。后三个按顺序对应那三部分，而且四个办法都可能做过头。

1. **少用模型**。代码能做的，就别去问模型。计数、复制文件、把 Word 文件转成文本、检查格式，这些活脚本每次都做得一样，而且不花 token。危险在于把需要判断的事交给了不会判断的代码，这条线划在哪里，见[谁来判断：代码、便宜模型、主模型、人](5-9-who-decides.html)。
2. **少读**。规则写得简短，细节需要时才加载，要 diff 而不是整个文件。危险在于读得太少，它就会去猜，返工的成本比省下的读取还高。
3. **少写**。要简短的回答，比如一句话的结论、一个简短的清单。危险在于输出简略到下一步用不上。
4. **少返工**。动手前先商定计划，把状态放在文件里，会话丢了也能接着做，再给重试的次数设个上限。危险在于上限卡掉了有用的工作，所以上限要根据你见到的情况来定，而不是根据担心来定。

还有一类固定成本，不管你在任务里怎么选，每次调用都要付。agent 拥有的每个工具，都会把自己的名字、描述和参数加进每次调用的输入里（[Tool calling，以及怎么给 agent 设计工具](1-2-tool-calling.html)），你注入的每条规则，也会每一轮都跟着走。

### 账单让你意外的时候

如果账单比你预想的高，先问自己三个问题。

1. 哪次调用或哪一轮读得最多？看看你工具的用量页面，再看看最大的那几个任务。
2. 上下文里有什么是不必在那里的？旧的工具结果、整个读进来的大文件、很长的规则文件？
3. 任务有没有被重做？如果有，第一次为什么失败？

在两个模型之间做选择时，同样的核查习惯也用得上，做一个小实验就够了。挑一个你知道正确答案的任务，在两个模型上各跑三次，记下用量和结果对不对，然后比较每次成功的成本。别凭一次运行就下结论。一张四列的表就行：

## 省钱要付出什么，我又看不到什么 {#costs-and-traps}

我在这一章里说的所有节省，都是“按设计”算的，不是从账单上读出来的，因为我手上的工具只让我看到这么多。我自己的 harness 在日志里不记录 token 数。一个任务实际用了多少，我看的是平台的会话记录，它报告的是 credits 和高级请求，我也不把它们换算成钱。

而这些节省本身也有代价。在工具调用上运行的 [hook](2-2-hooks.html) 会带来一点延迟，独立检查要再调用一次模型，每个 prompt 都注入的规则，每个 prompt 都要花 token。我是为了控制而有意接受这些的，但它们终究是成本。

最像节俭的坑，是读得太少。最便宜的调用，恰恰是猜错了然后被扔掉的那一次。如果一个任务总是因为缺上下文而失败，该做的是给它正确的上下文，而不是给得更少。

另外，价格和套餐都会变。上面的缓存倍率和 Copilot 的计费方式，都是截至来源里写的日期，我预计它们还会变。不过，变的不只是价格，还有收费时数的是什么。

## 市场也是这么算的吗？ {#industry}
{status: industry}

这一章依靠的两家提供方，指向的是同一个方向。Anthropic 把读缓存的价格定为普通输入的一小部分，并且说明工具定义在每次请求里都按输入 token 计算（[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[Tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）。GitHub 把 Copilot 从按请求计费改成了按 token 计费（[GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)）。说白了，市场现在按模型读和写了多少来收费，这正是这一章的论点。

## 什么时候可以删掉这些省钱技巧 {#when-to-delete-it}
{status: industry}

这一章的很多内容，是写给“读取很贵”的世界的建议。如果有一天读取便宜到，精简上下文多花的功夫比省下的还多，那就把这些技巧丢掉，只留下核算每个完成任务的成本这个习惯。另外，如果哪个平台开始自己显示每个任务的成本，我也会重新考虑，因为到那时，你需要猜的就少了。

## 在你自己的环境里试试 {#try-it}
