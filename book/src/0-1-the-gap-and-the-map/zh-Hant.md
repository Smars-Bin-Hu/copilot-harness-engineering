讀這一章，只需要你在 AI 對話框裡打過一段需求。

## 一句話 {#in-one-sentence}

同一個模型，放進好的 harness 裡，能做的事比在對話框裡多得多，因為大部分差距在模型外面。

## 給主管 {#for-leaders}

- **要做的決定**：團隊的力氣該花在哪裡：換一個更好的模型，還是把模型周圍的設定做好（也就是包住模型的規則、檢查和限制）。
- **風險**：如果大部分差距在模型外面，換了模型，結果照樣讓人失望。有一個團隊只改了寫程式 agent 的設定，它在一個公開基準上的分數就從 52.8% 升到 66.5%；不過這只是一個團隊、一個基準，而且是團隊自己量的。
- **做對的成本**：下一章從最小、但仍然有用的一組設定開始；再往後，主要是花時間把設定做起來。
- **可以問團隊**：「上次 agent 讓我們失望，是模型本身的問題，還是它周圍少了東西，例如少了一道檢查、一條規則，或是沒讓它看到檔案？」

## 模型一樣，差距從哪裡來？ {#problem}

先想像一個再平常不過的下午。使用者回報，匯出按鈕有時會產生空檔案。你把問題描述貼進對話框，一個很強的模型馬上給了你一段信心滿滿的解釋，還附上一段修正好的程式碼。

現在把同一個模型放進另一種設定裡，面對的還是這個 bug。這一次，它能自己打開你的檔案、搜尋程式碼，也能執行你的測試。動手之前，它會先讀專案裡寫好的規則，再把打算怎麼改拿給你看。等它最後說「修好了」，你也不必只聽它一句話，因為模型以外的一道檢查已經把測試跑過了。

模型沒換，bug 也沒換，這兩個下午卻幾乎是兩回事。這個場景是我編的思想實驗，為的是讓你看清差距的樣子，而不是去量它。那麼，第二種設定到底給了模型哪些對話框給不了的東西？

### 對話框裡少了什麼

在對話框裡，模型只有你貼進去的東西，看不到你的檔案，只能用猜的。給出的修正它自己沒辦法執行，改得對不對，沒有人知道。專案的規則它也不知道，就算它建議了你明明禁止的做法，也沒有任何東西擋得住。這些都不是模型少了哪項能力，而是它周圍少了東西。

### 除了編出來的下午，還有別的證據嗎？

有一些。LangChain 的一個團隊讓寫程式 agent 的模型保持不變，只改了它的 harness，結果這個 agent 在一個公開的程式基準（Terminal Bench 2.0）上的分數從 52.8% 升到 66.5%。他們改的是這類東西：讓 agent 在結束前先驗證自己的工作，一開始就給它一張工作資料夾的地圖，還有在同一個檔案被反覆修改之後，提醒它重新想一想。（[Improving deep agents with harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）

這幾處改動有個共同點：補上的都是模型自己不會提供的東西，有的是外面來的檢查，有的是讓它看清楚資料夾，有的是幫它跳出迴圈。當然，這只是一個團隊在一個基準上的結果，harness 也是團隊自己改、自己量的，所以只能當作一個跡象，不能當作定律。但它和那個思想實驗指向同一個方向：好結果和差結果之間，很大一部分的差別不在模型裡。

## 替模型周圍的東西畫一張地圖 {#how-it-works}

### 從模型到 agent

既然差別在模型周圍，不妨把那裡有什麼一樣一樣說清楚。先從**模型**本身說起：它是讀文字、寫文字的程式，就像「腦」，可是單靠它自己，只能回答問題。要動手做事，它需要**工具**，每個工具是它能要求做的一件事，例如讀檔案、搜尋、改檔案、執行指令。這些就是它的「手」（模型怎麼要求使用工具，見[Tool calling，和給 agent 設計工具](1-2-tool-calling.html)）。

可是有了腦和手，還不等於有了一個做事的人。總得有個東西去問模型下一步要做什麼，替它執行它要的工具，把結果拿給它看，然後一次次重複，直到模型說做完了。用這樣一個迴圈把兩者接起來，它們就成了 **agent**（這個迴圈怎麼運作，見[agent 循環，和你能插手的地方](2-1-agent-loop.html)）。迴圈不會自己寫出來，總得有人把它寫成程式，這個程式就是 **harness** 的第一種意思。

### 「harness」的兩種意思

這個詞有兩種用法，混在一起很容易讓人搞混。第一種是**通用 harness**，也就是執行迴圈的那個程式。Claude Code、Codex 和 Copilot 的 agent 模式都是，你買來或下載下來就能用。第二種是**團隊的 harness**：你在通用 harness 上面，為自己團隊搭的那一層，由規則、skill、檢查、限制和報告組成。它接在通用 harness 留出來的擴充點上。

這本書講的是第二種，搭在 VS Code Copilot 上。我說「harness engineering」，指的就是搭這一層的工作。

### 七層

團隊的 harness 有很多零散的部分，為了把它們分清楚，我把模型周圍的一切分成七層。這個框架是我自己的（它會在哪裡誤導你，[後面](#costs-and-traps)再談）。它好用的地方在於，每一層都帶著一個問題，不管工具和模型怎麼變，這個問題都不會變。

::: figure 0-1-seven-layers

從下往上讀。每一層都有一個日常的比方和一個問題。

| 層 | 比方 | 問題 |
| --- | --- | --- |
| 模型 | 腦 | 它能想多深，要花多少錢？ |
| 工具 | 手 | 它能碰到什麼？ |
| 執行環境 | 把腦和手接起來 | 誰來跑迴圈？迴圈在哪裡留了一個讓我插手的位置？ |
| 上下文 | 公司的新人訓練 | 它該知道什麼？不該讀什麼？ |
| 控制 | 圍欄 | 我為什麼可以信它？ |
| 流程 | 工作怎麼完成 | 工作怎麼拆？誰來判斷？什麼時候停？什麼時候叫人？ |
| 證據 | 說得清楚 | 它做了什麼？對不對？花了多少？ |

下面三層大多是買來的。模型廠商和平台廠商在做，變化也快。上面四層要你自己搭，因為它們取決於你的程式碼、你的同事和你要承擔的風險。它們也比較持久：平台更新很少會抹掉你的規則，卻很可能讓你當初為了繞過弱模型而想出的小技巧變得多餘。

也因為這樣，這本書在下面幾層花的篇幅很少，大部分都留給上面幾層。第 1 部和第 2 部講你需要知道的、買來的那幾層，第 3 到第 6 部各講上面的一層。

### 邊界沒那麼分明

分層只是一種分類的方法，不是自然定律，所以有些東西剛好落在邊界上，也就不奇怪了。例如 **hook**，它是平台在固定時刻執行的一小段程式，像是在工具執行之前。這樣的時刻在迴圈的每一[輪](2-1-agent-loop.html)裡都會出現；所謂一輪，就是問一次模型、執行它要的工具、再把結果交回去。插槽是平台給的，屬於執行環境，可是你往插槽裡放什麼，屬於控制。（hook 的細節見[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)。）

skill 也是落在邊界上的例子。它是一份寫好的手冊，agent 需要的時候才去讀，所以它屬於上下文；只有附在它上面的腳本，才算是手。

### 三種失敗方式

控制、流程、證據為什麼要各占一層？因為它們出問題的方式各不相同。

控制出問題時，agent 會造成損害：刪了不該刪的東西，或改了不該碰的檔案。流程出問題是另一種樣子：工作會被退回來，因為 agent 太早說了「做完了」，或是想一口氣把所有事做完。Anthropic 在長時間執行的 agent 裡看過這兩種模式：「agent 傾向一次做太多」，而之後的一個會話會「看一圈，見到已經有進展，就宣布工作完成」。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）證據則不一樣：工作做得再好，這一層也可能出問題。那時沒有人說得清楚發生了什麼：你證明不了工作是對的，壞了也找不到原因，也說不準某個改動到底有沒有用。例如帳單漲了，你卻不知道是哪個任務造成的。

這正是這張地圖派上用場的地方。出了問題，先問一句「這是三類裡的哪一類？」，往往比問「該換哪個模型？」更快。下次遇到失敗，不妨試試看。

## 這張地圖會在哪裡誤導你 {#costs-and-traps}

七層擺在那裡，容易讓人以為好的 harness 每一層都得有東西。其實不用。你每多搭一層，就多一樣要維護的東西，也多一個可能出錯的地方。所以下一章（[30 分鐘搭一個最小 harness](0-2-minimal-harness.html)）從最小的有用組合講起，每一章的最後也都有一節，講這一章說的東西什麼時候可以刪掉。

這張地圖也可能讓人覺得模型無關緊要，這也不是我的意思。更強的模型確實有幫助。我的說法比較窄：同一個模型，你能影響的那部分差別，大多來自它周圍的幾層。這個比例我沒有量過，LangChain 的結果也只是一個基準。

還有一點，這張地圖看起來可能比實際上更有權威。七層是我自己的框架，不是什麼標準，只是把各個部分排出順序的一種方法。

## LangChain 和 Anthropic 看到了什麼 {#industry}
{status: industry}

上面兩個來源指向同一個方向，只是說明的東西不一樣。LangChain 只改了 harness，就在一個基準上看到大幅提升。Anthropic 那篇談長時間執行 agent 的文章，描述了它看到的失敗（一次做太多、太早宣布完成），以及用檔案、清單和包在 agent 周圍的結構做出的修正。它沒有拿更強的模型來比較，所以它說明的是失敗出在哪裡，而不是換一個更好的模型能幫上多少忙。兩個來源都沒有說模型不重要。

## 什麼時候重畫這張地圖，或乾脆刪掉 {#when-to-delete-it}
{status: industry}

七層的圖是一個教學工具，就該當教學工具來用。哪一層幫不上你替問題分類，就把它重畫。我會留下的，是圖底下那個想法：agent 讓你失望的時候，先看看模型周圍有什麼，再去怪模型。

## 怎麼讀這本書 {#how-to-read}

每一章都分成兩個部分。**經驗分享**把想法講清楚，單獨讀也成立；**實作**指向我自己設定裡的真實檔案，讓你能進去看看。

時間不多的話，就讀標了核心的那幾章。它們串起全書的主線，不讀其他章也跟得上；其他章就等遇到問題時，再回來查。如果你要決定團隊的時間和預算花在哪裡，建議先讀 [0.2](0-2-minimal-harness.html)、[1.1](1-1-models-and-cost.html) 和 [7.4](7-4-rollout-and-governance.html) 這三章。
