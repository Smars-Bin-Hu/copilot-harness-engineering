讀這一章，只需要你在 AI 對話框裡打過一段需求。

## 一句話 {#in-one-sentence}

**駕馭工程**（harness engineering）是在模型周圍搭規則、檢查和限制，讓 agent 能放心交給真實的工作。同一個模型，放進好的 harness 裡，能做的事比在對話框裡多得多，因為差距大部分在模型外面。

## 給主管 {#for-leaders}

- **要做的決定**：團隊的力氣花在哪裡：換更好的模型，還是把模型周圍的規則、檢查和限制做好。
- **風險**：如果問題出在模型外面，換了模型、把推理強度開到最高，結果照樣讓人失望，錢還多花了。
- **做對的成本**：下一章從最小、但有用的一組設定講起；之後主要是把設定做起來的時間。
- **可以問團隊**：「上次 agent 讓我們失望，是模型本身的問題，還是它周圍少了東西，例如少了一道檢查、一條規則，或是沒讓它看到相關的檔案？」

## 模型一樣，差距在模型外面 {#problem}

使用者回報，匯出按鈕有時會匯出空檔案。你把描述貼進對話框，模型給了一段很有把握的解釋和一處修改，但它沒看過你的程式碼，也跑不了測試，改得對不對只能你自己去驗。把同一個模型放進 Copilot 的 agent 模式，它會自己搜尋程式碼、打開相關檔案、跑測試，動手前先讀專案裡寫好的規則，改完以後還有一道模型之外的檢查再跑一次測試。

模型沒換，結果差這麼多，原因在模型外面：它看得到什麼、能做什麼、要守什麼規則、誰來驗收。這一整套包在模型外面的程式和設定，叫 **harness**。

LangChain 量過只改 harness 能差多少。他們把模型固定為 gpt-5.2-codex，在 Terminal Bench 2.0（89 個終端機任務）上從 52.8% 提高到 66.5%。改動來自失敗任務的執行紀錄：agent 寫完程式碼自己讀一遍就停，於是在它結束前提醒它對照任務要求驗證；它找檔案、找工具出錯，於是一開始就把工作目錄和可用的工具告訴它；它在一個錯誤的思路上反覆小改，有時超過 10 次，於是同一個檔案改到一定次數，就提醒它換個思路。（[Improving deep agents with harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）

推理強度的結果最違反直覺。gpt-5.2-codex 的推理強度（reasoning effort）分 low、medium、high、xhigh 四檔。全程開到 xhigh 只有 53.9%，全程用 high 反而是 63.6%，因為想得太久，很多任務逾時了。最後他們在規劃和驗證時用 xhigh、寫程式碼時用 high，幾種分配方式之間差別不大。推理強度開多高，本身就是 harness 的一個設定。

這是一個團隊在一個基準上自己量的結果，但它和匯出按鈕的例子指向同一件事：拉開差距的，都是模型自己做不到的事，例如從外部驗證、事先給好的環境資訊、打斷鬼打牆的迴圈。

## 模型周圍的七層 {#how-it-works}

### 從模型到 agent

先把 agent 拆開。**模型**（LLM）是 agent 的大腦，例如 Sonnet、Opus、GPT-5。它讀文字、寫文字，單靠它只能回答問題。要動手，它需要**工具**，也就是雙手：讀檔案、搜尋程式碼、改檔案、跑終端機指令，每一樣是一個工具。模型使用工具的方式，是寫出一段請求，說明用哪個工具、參數是什麼（例如「讀 src/export.ts」），這叫一次**工具呼叫**（tool calling，細節見[Agent 用不好工具，先看工具的描述和錯誤訊息](1-2-tool-calling.html)）。

模型只會寫請求，自己執行不了。所以還需要一個程式把兩者接起來：它把任務交給模型，執行模型要的工具，把結果交回模型，再問下一步，一直重複到模型說做完了。模型、工具加上這個迴圈，就是 **agent**（迴圈怎麼轉，見[agent 循環，和你能插手的地方](2-1-agent-loop.html)）。跑這個迴圈的程式，是 harness 的第一種意思。

### 「harness」的兩種意思

這個詞有兩種用法，混著用容易搞混。第一種是**通用 harness**，就是跑迴圈的那個程式：Claude Code、Codex、Copilot 的 agent 模式都是，下載或買來就能用。第二種是**團隊的 harness**：你在通用 harness 上為自己團隊搭的那一層，包括規則、skill、檢查、限制和報告，接在通用 harness 留下的擴充點上。

這本書講第二種，例子都搭在 VS Code Copilot 上。我說 Harness Engineering，指的就是搭這一層的工作。

### 七層

團隊的 harness 零碎的東西很多。我把模型周圍的一切分成七層，每層帶一個問題；工具和模型怎麼換，這些問題都不變。

::: figure 0-1-seven-layers

| 層 | 比喻 | 例子 | 問題 |
| --- | --- | --- | --- |
| 模型 | 大腦 | Sonnet、Opus、GPT-5；推理強度 | 它能想多深，要花多少錢？ |
| 工具 | 雙手 | 讀寫檔案、跑終端機指令、MCP server | 它搆得到什麼？ |
| 執行環境 | 神經，把大腦和雙手接起來 | Copilot 的 agent 模式、Claude Code；hook、子 agent | 誰來跑這個迴圈，在哪裡給我留了插手的地方？ |
| 上下文 | 新人訓練 | 指令檔（AGENTS.md）、skill、記憶 | 它該知道什麼，不該讀什麼？ |
| 控制 | 電腦權限 | 權限、攔下危險指令的 hook | 我憑什麼信它？ |
| 流程 | 專案流程、團隊規定 | 任務清單、批准、什麼時候停 | 工作怎麼拆，誰來判斷，什麼時候停，什麼時候找人？ |
| 證據 | 工作紀錄、操作帳單 | 日誌、任務報告、評測 | 它做了什麼，做對了沒有，花了多少？ |

下面三層是 agent 自己：大腦、雙手和連起它們的神經。這三層大部分是買來的：模型廠商和平台廠商在做，變得也快。上面四層是公司怎麼管一個新員工：新人訓練、電腦權限、專案流程、工作紀錄。人可以請來，怎麼管得由公司自己決定，所以這四層要你自己搭，它們取決於你的程式碼、你的同事和你要承擔的風險。上面四層也更持久：平台升級很少會抹掉你的規則，卻可能讓你當初為了繞過弱模型想出來的辦法變得多餘。

### hook 和 skill 放在哪一層

七層涵蓋了 Harness Engineering 的大部分概念，放哪一層最容易有爭議的是 hook 和 skill。兩樣都是平台提供的機制，你用它們做出來的東西卻屬於上面的層。判斷的辦法是看它用來做什麼，不看它是誰提供的。

- **hook** 是平台（Claude Code、Copilot 等）在固定事件上留的口子：某個事件發生時，執行你指定的一個指令。常用的事件有 PreToolUse（工具呼叫之前）、PostToolUse（工具呼叫之後）、UserPromptSubmit（使用者送出 prompt 時）和 Stop（agent 準備結束時）。事件發生時，平台把內容交給你的指令，例如要呼叫的工具名和參數；指令可以放行，也可以攔下。hook 這個機制屬於執行環境，掛在上面的東西各有歸屬：在 PreToolUse 上掛一個 Python 腳本，發現終端機指令裡有 `rm -rf` 就攔下，這是控制；在 PostToolUse 上把每次呼叫寫進日誌，這是證據。（細節見[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)。）
- **skill** 是一個資料夾：主檔案 `SKILL.md` 寫著名字、描述和一份操作手冊，旁邊可以放腳本和範本。agent 平時只看得到每個 skill 的名字和描述，任務用得上時才讀整份手冊。按需載入 skill 的機制屬於執行環境；手冊是寫給 agent 看的，屬於上下文；資料夾裡的腳本，agent 會當指令去跑，屬於工具。（細節見[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。）

### 三種失敗方式

控制、流程、證據分成三層，是因為它們出問題的樣子不一樣。

控制出問題，agent 會造成損害：刪錯東西，或者改了不該碰的檔案。

流程出問題，工作會被退回來：agent 一次做太多，或者太早說做完。Anthropic 用 Opus 4.5 跨好幾個會話做一個 claude.ai 的複製版時，兩種都遇到了：agent「傾向一次做太多，基本上想一口氣把整個應用程式做完」；後來的會話則會「四處看看，發現已經有進展，就宣布工作完成」。他們的修法都在模型外面。第一個會話先寫出 200 多項功能的清單，每項都標成未通過；之後的每個會話一次只做一項，只能改這一項有沒有通過，不准刪改測試，做完提交到 git，並在進度檔裡記下做了什麼。測試時要求 agent 用瀏覽器自動化工具，像真實使用者一樣操作，這樣能找出光看程式碼看不出來的 bug。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）

證據出問題又是另一種樣子：工作可能做得很好，但沒人說得清發生了什麼。你證明不了結果是對的，出了錯找不到原因，也說不準某個改動有沒有用；帳單變高了，你分不清是哪個任務花的。

出了問題，先問「這是哪一類失敗」，往往比問「該換哪個模型」更快找到修法。

## 七層不必都搭 {#costs-and-traps}

七層擺在一起，容易讓人以為好的 harness 每一層都得有東西。不必。每多搭一層，就多一樣要維護的東西，也多一處可能出錯的地方。所以下一章（[30 分鐘搭一個最小 harness](0-2-minimal-harness.html)）從最小的有用組合講起。

更強的模型當然有幫助。但模型是你買來的，同一個模型，你能左右的那部分差距，大多來自它周圍的幾層。

## LangChain 和 Anthropic 看到了什麼 {#industry}
{status: industry}

兩個來源指向同一個方向，說明的東西不一樣。LangChain 固定模型、只改 harness，看到了分數的提升，說明 harness 能拉開多大的差距。Anthropic 描述的是長任務裡失敗出在哪裡（一次做太多、太早宣布完成），以及靠功能清單、進度檔和 git 做的修正；它沒有拿更強的模型做比較，所以說明不了換模型能幫多少。

## 怎麼讀這本書 {#how-to-read}

本書在下面三層寫得少，大部分篇幅給上面四層：第 1、2 部講下面三層裡你需要知道的，第 3 到第 6 部各講上面的一層。

每一章分成兩個部分。**經驗分享**講想法，單獨讀就成立；**實作**指向我自己設定裡的真實檔案，讓你進去看。

時間不多，就讀標了「核心」的章，它們串起全書的主線；其他章遇到問題再回來查。要決定團隊的時間和預算花在哪裡，先讀 [0.2](0-2-minimal-harness.html)、[1.1](1-1-models-and-cost.html) 和 [7.4](7-4-rollout-and-governance.html)。
