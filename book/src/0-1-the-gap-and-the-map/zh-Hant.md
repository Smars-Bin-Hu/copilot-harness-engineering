讀這一章，只需要在 AI 對話框裡打過一段需求。其他都不用。

## 一句話 {#in-one-sentence}

同一個模型，在好的 harness 裡做的事，比在對話框裡多得多，因為大部分差距在模型外面。

## 給主管 {#for-leaders}

- **要做的決定**：決定團隊的力氣放在哪裡：換更好的模型，還是改模型周圍的設定（包住模型的規則、檢查和限制）。
- **風險**：如果大部分差距在模型外面，換模型解決不了讓人失望的結果。有一個團隊只改了寫程式 agent 的設定，在一個公開基準上的分數從 52.8% 升到 66.5%。這是一個團隊、一個基準，還是團隊自己量的。
- **做對的成本**：下一章從最小的有用組合開始。除此之外，主要是花在設定上的時間。
- **可以問團隊**：「上次 agent 讓我們失望，是模型的問題，還是它周圍少了什麼：一道檢查、一條規則、一個看檔案的視角？」

## 問題 {#problem}

想像你的專案裡有個 bug。使用者說，匯出按鈕有時會產生空檔案。你把描述貼進對話框，一個強的模型給了你一段很有把握的解釋，還有一個程式碼修正。

現在想像同一個模型、同一個 bug，換一種設定。它能打開你的檔案、搜尋檔案。它能執行你的測試。它先讀專案寫下來的規則。改任何東西之前，它先給你看計劃。它說「修好了」的時候，執行測試的是別的東西，不是它自己的一句話。

同一個模型，下午的感受差很多。這是想像出來的例子，不是量出來的數據：我編它，是為了讓你看到差距的樣子。這一章其餘的部分，講差距從哪裡來。

### 對話框少了什麼

在對話框裡，模型只有你貼進去的東西。它看不到你的檔案，所以只能猜。它不能執行修正，所以沒有人知道修正有沒有用。它不知道專案的規則，也沒有東西攔住它建議你禁止的做法。這每一項，都是模型周圍缺了東西，不是模型缺了本事。

### 這本書以外的一些證據

LangChain 的一個團隊只改了寫程式 agent 的 harness，模型不動。在一個公開的寫程式基準（Terminal Bench 2.0）上，分數從 52.8% 升到 66.5%。他們改的有這些：一個讓 agent 結束前先驗證自己工作的步驟、一開始就給的工作資料夾地圖，以及在同一個檔案改了好幾次之後，提醒它重新想一想。（[Improving deep agents with harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）

看看這些改動的共同點。每一項加的，都是模型自己不會提供的東西：外面來的檢查、資料夾的視野、跳出迴圈的一個機會。這是一個基準、一個團隊，而且是團隊改自己的 harness、自己量的，所以只當作一個跡象，不當作定律。但它和上面那個想像的例子指向同一個方向：好結果和差結果之間，很多差別不在模型裡。

## 原理 {#how-it-works}

### 先講三個詞

- **模型**是讀文字、寫文字的程式。它是「腦」。單獨一個，它只能回答。
- **工具**是模型能要求做的一件事：讀檔案、搜尋、改檔案、執行指令。工具是「手」。[Tool calling，和給 agent 設計工具](1-2-tool-calling.html) 會說明模型怎麼要求一個工具。
- **agent** 是把這兩樣接在一個迴圈裡的程式：問模型該做什麼，執行它要的工具，把結果給模型看，重複，直到模型說做完了。[agent 循環，和你能插手的地方](2-1-agent-loop.html) 會帶你走一遍這個迴圈。

模型加上工具，還不是 agent。得有人寫那個迴圈。這個程式就是 **harness** 的第一個意思。

### 「harness」的兩個意思

大家用這個詞有兩種意思，混在一起會搞糊塗。

1. **通用的 harness**：執行迴圈的程式。Claude Code、Codex 和 Copilot 的 agent 模式都是通用 harness。你買來或下載。
2. **團隊的 harness**：你在通用 harness 上面，為自己團隊搭的一層：規則、skill、檢查、限制、報告。它用的是通用 harness 留出來的擴充點。

這本書講的是第二種，搭在 VS Code Copilot 上。我說「harness engineering」，指的就是搭這一層的工作。

### 七層

我發現把模型周圍的一切分成七層，很好用。這個框架是我自己的，不是標準（「代價和陷阱」裡會再說）。每一層都有一個問題，不管工具和模型怎麼變，這個問題都不變。

::: figure 0-1-seven-layers

從下往上讀。每一層有一個日常的比方和一個問題。

| 層 | 比方 | 問題 |
| --- | --- | --- |
| 模型 | 腦 | 它能想多深，要花多少錢？ |
| 工具 | 手 | 它能碰到什麼？ |
| 執行環境 | 把腦和手接起來 | 誰來跑迴圈？迴圈在哪裡留了一個讓我插手的位置？ |
| 上下文 | 公司的訓練 | 它該知道什麼？不該讀什麼？ |
| 控制 | 圍欄 | 我為什麼可以信它？ |
| 流程 | 工作怎麼完成 | 工作怎麼拆？誰來判斷？什麼時候停？什麼時候叫人？ |
| 證據 | 說得清楚 | 它做了什麼？對不對？花了多少？ |

下面三層大多是買來的。模型廠商和平台廠商做它們，而且變得很快。上面四層要你自己搭，因為它們取決於你的程式碼、你的同事和你的風險。它們也更耐久：平台更新很少抹掉你的規則，卻很可能取代某個為了繞開弱模型而用的小聰明。

這就是為什麼這本書在下面幾層花的篇幅少，大部分頁數給上面幾層。第 1 部和第 2 部，講買來的那幾層你需要知道的事。第 3 到第 6 部，每一部分講上面的一層。

### 邊界並不乾淨

別把這幾層當成自然定律。**hook** 就剛好在邊界上。hook 是平台在固定時刻執行的小程式，這些時刻在迴圈的每一[輪](2-1-agent-loop.html)（問模型一次、執行它要的工具、把結果交回去，算一輪）裡，例如工具執行之前。位置（執行環境）是平台給的，但你放進去的東西屬於控制。[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html) 會說明 hook。

skill 是另一個例子。它是 agent 需要時才讀的一份書面手冊。手冊屬於上下文，不是手。只有附在手冊上的腳本才是手。

### 三種失敗方式

為什麼把上面幾層分成三塊？因為它們有三種不同的壞法。

- **控制失敗：agent 造成損害**。它刪了不該刪的，或改了不該碰的檔案。
- **流程失敗：工作被退回來**。agent 太早說「做完了」，或一口氣什麼都試。Anthropic 在長時間執行的 agent 裡看到這兩種模式：「agent 傾向一次做太多」，而之後的一個會話「看一圈，見到已經有進展，就宣布工作完成」。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）
- **證據失敗：沒有人說得清發生了什麼**。工作可能沒問題，但你拿不出證明，壞了也找不到原因，也分不出一個改動有沒有用。例如帳單漲了，你卻不知道是哪個任務造成的。

出事的時候，問「這是三種裡的哪一種？」，常常比問「我該換哪個模型？」快。下次看到失敗時試試。

## 代價和陷阱 {#costs-and-traps}

**層多不一定好**。你搭的每一層，都要維護，也都可能壞。[30 分鐘搭一個最小 harness](0-2-minimal-harness.html) 從最小的有用組合開始，而每一章的結尾，都有一節講這一章說的東西什麼時候可以刪。

**差距不全在模型外面**。更強的模型確實有幫助。我的說法比較窄：同一個模型，你能影響的差別，大部分來自它周圍的層。這個比例我沒有量過，而 LangChain 的結果只是一個基準。

**七層是我自己的框架**。它不是標準。它是把這些東西排出順序的一種方法，你可以把界線畫在別的地方。

## 業界怎麼說 {#industry}
{status: industry}

上面兩個來源指向同一個方向。LangChain 只改了 harness，在一個基準上拿到很大的進步。Anthropic 講長時間執行 agent 的文章，說了它在長時間執行的 agent 裡看到的失敗（一次做太多、太早宣布完成），以及用檔案、檢查清單和 agent 周圍的結構做的修正。它沒有拿更強的模型來比，所以只能顯示失敗出在哪裡，看不出更好的模型能幫上多少。兩個來源都沒有說模型不重要。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

七層圖是教學的工具。如果你發現其中一層幫不上你分類問題，就重畫。底下的想法才是我會留下的：agent 讓人失望時，先看模型周圍有什麼，再去怪模型。

## 怎麼讀這本書 {#how-to-read}

每一章分兩個部分。**The Knowledge** 講想法，可以單獨讀。**In my practice** 指向我自己設定裡的真實檔案，讓你看到裡面。

時間不多，就讀標了核心的章：它們是書的主線，不讀別的也跟得上。其他章是在遇到問題時，再回頭查的。如果你要決定團隊的時間和預算怎麼花，從 [30 分鐘搭一個最小 harness](0-2-minimal-harness.html)、[選模型：算的是每次成功的成本](1-1-models-and-cost.html) 和 [落地與治理](7-4-rollout-and-governance.html) 開始。
