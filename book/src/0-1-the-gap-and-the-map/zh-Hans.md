读这一章，只需要你在 AI 聊天框里提过需求。

## 一句话 {#in-one-sentence}

**驾驭工程**（harness engineering）是在模型周围搭规则、检查和限制，让 agent 能放心交给真实的工作。同一个模型，放进好的 harness 里，能做的事比在聊天框里多得多，因为差距大部分在模型外面。

## 写给管理者 {#for-leaders}

- **要拍板的事**：团队的力气往哪儿使：换更好的模型，还是把模型周围的规则、检查和限制做好。
- **风险**：如果问题出在模型外面，换了模型、把推理强度开到最高，结果照样让人失望，钱还多花了。
- **做对的代价**：下一章从最小、但有用的一套配置讲起；之后主要是搭配置的时间。
- **可以问团队**：“上次 agent 让我们失望，是模型本身的问题，还是它周围缺了东西，比如少了一道检查、一条规则，或者没让它看到相关的文件？”

## 模型一样，差距在模型外面 {#problem}

用户反馈导出按钮有时导出空文件。你把描述贴进聊天框，模型给了一段很肯定的解释和一处修改，但它没看过你的代码，也跑不了测试，改得对不对只能你自己去验。把同一个模型放进 Copilot 的 agent 模式，它会自己搜索代码、打开相关文件、跑测试，动手前先读项目里写好的规则，改完以后还有一道模型之外的检查再跑一遍测试。

模型没换，结果差这么多，原因在模型外面：它能看到什么、能做什么、要守什么规则、谁来验收。这一整套围着模型的程序和配置，叫 **harness**。

LangChain 测过只改 harness 能差多少。他们把模型固定为 gpt-5.2-codex，在 Terminal Bench 2.0（89 个终端任务）上从 52.8% 提到 66.5%。改动来自失败任务的执行记录：agent 写完代码自己读一遍就停，于是在它退出前提醒它对照任务要求验证；它找文件、找工具出错，于是启动时先把工作目录和可用工具告诉它；它在一个错误思路上反复小改，有时超过 10 次，于是同一个文件改到一定次数，就提醒它换思路。（[Improving deep agents with harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）

推理强度的结果最反直觉。gpt-5.2-codex 的推理强度（reasoning effort）分 low、medium、high、xhigh 四档。全程开到 xhigh 只有 53.9%，全程用 high 反而是 63.6%，因为想得太久，很多任务超时了。最后他们在规划和验证时用 xhigh、写代码时用 high，几种分配方式之间差别不大。推理强度开多高，本身就是 harness 的一个设置。

这是一个团队在一个基准上自己测的结果，但它和导出按钮的例子指向同一件事：拉开差距的，都是模型自己做不到的事，比如外部验证、提前给好的环境信息、打断死循环。

## 模型周围的七层 {#how-it-works}

### 从模型到 agent

先把 agent 拆开。**模型**（LLM）是 agent 的大脑，比如 Sonnet、Opus、GPT-5。它读文本、写文本，单靠它只能回答问题。要动手，它需要**工具**，也就是双手：读文件、搜索代码、改文件、跑终端命令，每一样是一个工具。模型用工具的方式，是写出一段请求，说明用哪个工具、参数是什么（比如“读 src/export.ts”），这叫一次**工具调用**（Tool Calling，细节见[Agent 用不好工具，先看工具的描述和报错](1-2-tool-calling.html)）。

模型只会写请求，自己执行不了。所以还需要一个程序把两者接起来：它把任务交给模型，执行模型请求的工具，把结果交回模型，再问下一步，一直重复到模型说做完了。模型、工具加上这个循环，就是 **agent**（循环怎么转，见[Agent 到底是怎么干活的？](2-1-agent-loop.html)）。跑这个循环的程序，是 harness 的第一种意思。

### “harness”的两种意思

这个词有两种用法，混着用容易糊涂。第一种是**通用 harness**，就是跑循环的那个程序：Claude Code、Codex、Copilot 的 agent 模式都是，下载或者买来就能用。第二种是**团队的 harness**：你在通用 harness 上为自己团队搭的那一层，包括规则、skill、检查、限制和报告，接在通用 harness 留出来的扩展点上。

这本书讲第二种，例子都搭在 VS Code Copilot 上。我说 Harness Engineering，指的就是搭这一层的工作。

### 七层

团队的 harness 零碎东西很多。我把模型周围的一切分成七层，每层带一个问题；工具和模型怎么换，这些问题都不变。

::: figure 0-1-seven-layers

| 层 | 比方 | 例子 | 问题 |
| --- | --- | --- | --- |
| 模型 | 大脑 | Sonnet、Opus、GPT-5；推理强度 | 它能想多深，要花多少钱？ |
| 工具 | 双手 | 读写文件、跑终端命令、MCP server | 它够得着什么？ |
| 运行环境 | 神经，把大脑和双手接起来 | Copilot 的 agent 模式、Claude Code；hook、子 agent | 谁来跑这个循环，在哪里给我留了插手的口子？ |
| 上下文 | 岗前培训 | 指令文件（AGENTS.md）、skill、记忆 | 它该知道什么，不该读什么？ |
| 控制 | 电脑权限 | 权限、拦截危险命令的 hook | 我凭什么信它？ |
| 流程 | 项目流程、团队规定 | 任务清单、审批、什么时候停 | 工作怎么拆，谁来判断，什么时候停，什么时候叫人？ |
| 证据 | 工作记录、操作账单 | 日志、任务报告、评测 | 它做了什么，做对了没有，花了多少？ |

下面三层是 agent 自己：大脑、双手和连起它们的神经。这三层大部分是买来的：模型厂商和平台厂商在造，变得也快。上面四层是公司怎么管一个新员工：岗前培训、电脑权限、项目流程、工作记录。人可以招来，怎么管得公司自己定，所以这四层要你自己搭，它们取决于你的代码、你的同事和你要承担的风险。上面四层也更持久：平台升级很少会抹掉你的规则，却可能让你当初为了绕开弱模型想出来的办法变得多余。

### hook 和 skill 放在哪一层

七层涵盖了 Harness Engineering 的大部分概念，放哪一层最容易有争议的是 hook 和 skill。两样都是平台提供的机制，你用它们做出来的东西却属于上面的层。判断的办法是看它用来做什么，不看它是谁提供的。

- **hook** 是平台（Claude Code、Copilot 等）在固定事件上留的口子：某个事件发生时，运行你指定的一个命令。常用的事件有 PreToolUse（工具调用之前）、PostToolUse（工具调用之后）、UserPromptSubmit（用户发出 prompt 时）和 Stop（agent 准备结束时）。事件发生时，平台把内容交给你的命令，比如要调用的工具名和参数；命令可以放行，也可以拦下。hook 这个机制属于运行环境，挂在上面的东西各有归属：在 PreToolUse 上挂一个 Python 脚本，发现终端命令里有 `rm -rf` 就拦下，这是控制；在 PostToolUse 上把每次调用写进日志，这是证据。（细节见[硬性规则放在哪？用 hook](2-2-hooks.html)。）
- **skill** 是一个文件夹：主文件 `SKILL.md` 写着名字、描述和一份操作手册，旁边可以放脚本和模板。agent 平时只看得到每个 skill 的名字和描述，任务用得上时才读整份手册。按需加载 skill 的机制属于运行环境；手册是写给 agent 看的，属于上下文；文件夹里的脚本，agent 会当命令去跑，属于工具。（细节见[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)。）

### 三种失败方式

控制、流程、证据分成三层，是因为它们出问题的样子不一样。

控制出问题，agent 会造成损害：删错东西，或者改了不该碰的文件。

流程出问题，活会被打回来：agent 一次做太多，或者太早说做完。Anthropic 用 Opus 4.5 跨多个会话搭一个 claude.ai 的克隆时，两种都见到了：agent “倾向于一次做太多，基本上想一口气把整个应用做完”；后来的会话则会“四处看看，发现已经有进展，就宣布工作完成”。他们的修法都在模型外面。第一个会话先写出 200 多项功能的清单，每项都标成未通过；之后的每个会话一次只做一项，只许改这一项通没通过，不许删改测试，做完提交到 git，并在进度文件里记下做了什么。测试时要求 agent 用浏览器自动化工具，像真实用户一样操作，这样能找出光看代码看不出来的 bug。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）

证据出问题又是另一种样子：活可能干得很好，但没人说得清发生了什么。你证明不了结果是对的，出了错找不到原因，也说不准某个改动有没有用；账单涨了，你分不清是哪个任务花的。

出了问题，先问“这是哪一类失败”，往往比问“该换哪个模型”更快找到修法。

## 七层不必都搭 {#costs-and-traps}

七层摆在一起，容易让人以为好的 harness 每一层都得有东西。不必。每多搭一层，就多一样要维护的东西，也多一处可能出错的地方。所以下一章（[30 分钟搭一个最小 harness](0-2-minimal-harness.html)）从最小的有用组合讲起。

更强的模型当然有帮助。但模型是你买来的，同一个模型，你能左右的那部分差距，大多来自它周围的几层。

## LangChain 和 Anthropic 看到了什么 {#industry}
{status: industry}

两个来源指向同一个方向，说明的东西不一样。LangChain 固定模型、只改 harness，看到了分数的提升，说明 harness 能拉开多大的差距。Anthropic 描述的是长任务里失败出在哪（一次做太多、太早宣布完成），以及靠功能清单、进度文件和 git 做的修复；它没有拿更强的模型做对比，所以说明不了换模型能帮多少。

## 怎么读这本书 {#how-to-read}

本书在下面三层写得少，大部分篇幅给上面四层：第 1、2 部分讲下面三层里你需要知道的，第 3 到第 6 部分各讲上面的一层。

每一章分两个板块。**经验分享**讲思路，单独读就成立；**实战**指向我自己配置里的真实文件，让你进去看。

时间不多，就读标了“核心”的章，它们串起全书的主线；其余各章遇到问题再回来查。要决定团队的时间和预算往哪花，先读 [0.2](0-2-minimal-harness.html)、[1.1](1-1-models-and-cost.html) 和 [7.4](7-4-rollout-and-governance.html)。
