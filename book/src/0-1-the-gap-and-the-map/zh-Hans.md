读这一章，只需要你在 AI 聊天框里提过需求。

## 一句话 {#in-one-sentence}

同一个模型，放进好的 harness 里，能干的事比在聊天框里多得多，因为差距大部分在模型之外。

## 写给管理者 {#for-leaders}

- **要拍板的事**：团队的力气该往哪儿使：换一个更好的模型，还是把模型周围的配置做好（也就是围着模型的规则、检查和限制）。
- **风险**：如果差距大部分在模型之外，换了模型，结果照样让人失望。有个团队只改了编码 agent 的配置，它在一个公开基准上的分数就从 52.8% 涨到了 66.5%；不过这只是一个团队、一个基准，而且是团队自己测的。
- **做对的代价**：下一章从最小、但仍然有用的一套配置讲起；再往后，主要是花时间把配置搭起来。
- **可以问团队**：“上次 agent 让我们失望，是模型本身的问题，还是它周围缺了东西，比如少了一道检查、一条规则，或者没让它看到文件？”

## 模型一样，差距从哪来？ {#problem}

先设想一个再普通不过的下午。用户反馈说，导出按钮有时会导出一个空文件。你把问题描述贴进聊天框，一个很强的模型马上给了你一段言之凿凿的解释，还附上了一处代码修改。

现在把同一个模型放进另一种配置里，面对的还是这个 bug。这一次，它能自己打开你的文件、搜索代码，也能跑你的测试。动手之前，它会先读项目里写好的规则，再把打算怎么改拿给你过目。等它最后说“修好了”，你也不必只听它一句话，因为模型之外的一道检查已经把测试跑过了。

模型没换，bug 也没换，这两个下午却几乎是两回事。这个场景是我编的思想实验，为的是让你看清差距的样子，而不是去测量它。那么，第二种配置到底给了模型哪些聊天框给不了的东西？

### 聊天框里缺了什么

在聊天框里，模型只有你贴进去的东西，看不到你的文件，只能猜。给出的修改它自己跑不了，改得对不对，没人知道。项目的规则它也不知道，就算它建议了你明令禁止的做法，也没有什么能拦住它。这些都不是模型缺了哪项本事，而是它周围缺了东西。

### 除了编出来的下午，还有别的证据吗？

有一些。LangChain 的一个团队让编码 agent 的模型保持不变，只改了它的 harness，结果这个 agent 在一个公开的编码基准（Terminal Bench 2.0）上的分数从 52.8% 涨到了 66.5%。他们改的是这样一些东西：让 agent 在退出前先验证自己的工作，一开始就给它一张工作文件夹的地图，还有在同一个文件被反复修改之后，提醒它重新想一想。（[Improving deep agents with harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）

这几处改动有个共同点：补上的都是模型自己提供不了的东西，有的是来自外部的检查，有的是让它看清文件夹，有的是把一个循环打断。当然，这只是一个团队在一个基准上的结果，harness 也是团队自己改、自己测的，所以只能算一个迹象，算不上定律。但它和那个思想实验指向同一个方向：好结果和差结果之间的差别，很大一部分不在模型里。

## 给模型周围的东西画一张地图 {#how-it-works}

### 从模型到 agent

既然差别在模型周围，不妨把那里有什么一样一样说清楚。先从**模型**本身说起：它是读文本、写文本的程序，相当于“大脑”，可单靠它自己，只能回答问题。要动手做事，它需要**工具**，每个工具是它能要求做的一件事，比如读文件、搜索、改文件、运行命令。这些就是它的“双手”（模型怎么要求使用工具，见[Tool calling，以及怎么给 agent 设计工具](1-2-tool-calling.html)）。

可是有了大脑和双手，还不等于有了一个干活的人。总得有个东西去问模型下一步做什么，替它运行它要的工具，把结果拿给它看，然后一遍遍重复，直到模型说做完了。用这样一个循环把两者接起来，它们就成了 **agent**（这个循环怎么转，见[agent 循环，以及你能插手的地方](2-1-agent-loop.html)）。循环不会自己写出来，总得有人把它写成程序，这个程序就是 **harness** 的第一种意思。

### “harness”的两种意思

这个词有两种用法，混在一起很容易让人糊涂。第一种是**通用 harness**，也就是运行循环的那个程序。Claude Code、Codex 和 Copilot 的 agent 模式都是，你买来或者下载下来就能用。第二种是**团队的 harness**：你在通用 harness 之上，为自己团队搭的那一层，由规则、skill、检查、限制和报告组成。它接在通用 harness 留出来的扩展点上。

这本书讲的是第二种，搭在 VS Code Copilot 上。我说“harness engineering”，指的就是搭这一层的工作。

### 七层

团队的 harness 零零碎碎的东西很多，为了分清它们，我把模型周围的一切分成七层。这个框架是我自己的（它会在哪里误导你，[后面](#costs-and-traps)再说）。它好用的地方在于，每一层都带着一个问题，工具和模型怎么变，这个问题都不变。

::: figure 0-1-seven-layers

从下往上读。每一层都有一个日常的比方和一个问题。

| 层 | 比方 | 问题 |
| --- | --- | --- |
| 模型 | 大脑 | 它能想多深，要花多少钱？ |
| 工具 | 双手 | 它够得着什么？ |
| 运行环境 | 把大脑和双手接起来 | 谁来跑这个循环，循环在哪里给我留了插手的口子？ |
| 上下文 | 公司的岗前培训 | 它该知道什么，不该读什么？ |
| 控制 | 围栏 | 我凭什么信它？ |
| 流程 | 活是怎么干成的 | 工作怎么拆，谁来判断，什么时候停，什么时候叫人？ |
| 证据 | 能讲清楚 | 它做了什么，做对了没有，花了多少？ |

下面三层大多是买来的。模型厂商和平台厂商在造，变化也快。上面四层要你自己搭，因为它们取决于你的代码、你的同事和你要承担的风险。它们也更持久：平台升级很少会抹掉你的规则，却很可能让你当初为了绕开弱模型而想出的小聪明变得多余。

正因为这样，本书在下面几层上着墨不多，大部分篇幅留给了上面几层。第 1 部分和第 2 部分讲你需要了解的、买来的那几层，第 3 到第 6 部分各讲上面的一层。

### 边界没那么清楚

分层只是一种归类的办法，不是自然规律，所以有些东西正好骑在边界上，也就不奇怪了。比如 **hook**，它是平台在固定时机运行的一小段程序，例如在工具运行之前。这样的时机在循环的每一[轮](2-1-agent-loop.html)里都会出现；所谓一轮，就是问一次模型、运行它要的工具、再把结果交回去。插槽是平台给的，属于运行环境，可你往插槽里放什么，属于控制。（hook 的细节见[Hook：每次调用都会经过的执行点](2-2-hooks.html)。）

skill 也是骑在边界上的例子。它是一份写好的手册，agent 需要的时候才去读，所以它属于上下文；只有附在它上面的脚本，才算双手。

### 三种失败方式

控制、流程、证据为什么要各占一层？因为它们出问题的方式各不相同。

控制出了问题，agent 会造成损害：删错了东西，或者改了不该碰的文件。流程出问题是另一副样子：活会被打回来，因为 agent 太早说了“做完了”，或者想一口气全做完。Anthropic 在长时间运行的 agent 里见过这两种情况：“agent 倾向于一次做太多”，而后来的一个会话会“四处看看，发现已经有进展，就宣布工作完成”。（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）证据则不同：活干得再好，这一层也可能出问题。那时没人说得清发生了什么：你证明不了活是对的，出了错找不到原因，也说不准某个改动到底有没有用。比如账单涨了，你却分不清是哪个任务造成的。

这正是这张地图派上用场的地方。出了问题，先问一句“这是三类里的哪一类？”，往往比问“该换哪个模型？”更快。下次碰到失败，不妨试试。

## 这张地图会在哪里误导你 {#costs-and-traps}

七层摆在那里，容易让人以为好的 harness 每一层都得有东西。其实不必。你每多搭一层，就多一样要维护的东西，也多一处可能出错的地方。所以下一章（[30 分钟搭一个最小 harness](0-2-minimal-harness.html)）从最小的有用组合讲起，每一章的结尾也都有一节，讲这一章说的东西什么时候可以删。

这张地图还可能让人觉得模型无关紧要，这也不是我的意思。更强的模型确实有帮助。我的说法要窄一些：同一个模型，你能左右的那部分差别，大多来自它周围的几层。这个比例我没有测过，LangChain 的结果也只是一个基准。

还有一点，这张地图看起来可能比它实际上更权威。七层是我自己的框架，不是什么标准，只是把各个部分理出个顺序的一种办法。

## LangChain 和 Anthropic 看到了什么 {#industry}
{status: industry}

上面两个来源指向同一个方向，只是说明的东西不一样。LangChain 只改了 harness，就在一个基准上看到了大幅提升。Anthropic 那篇讲长时间运行 agent 的文章，描述了它见到的失败（一次做太多、太早宣布完成），以及用文件、清单和围绕 agent 的结构做出的修复。它没有拿更强的模型来对比，所以它说明的是失败出在哪里，而不是换个更好的模型能帮上多少忙。两个来源都没有说模型不重要。

## 什么时候重画这张地图，或者干脆删掉 {#when-to-delete-it}
{status: industry}

七层的图是个教学工具，就该当教学工具来用。哪一层帮不上你给问题归类，就把它重画。我会留下的，是图底下的那个想法：agent 让你失望的时候，先看看模型周围有什么，再去怪模型。

## 怎么读这本书 {#how-to-read}

每一章都分两个部分。**经验分享**把思路讲清楚，单独读也成立；**实战**指向我自己配置里的真实文件，让你能进去看看。

时间不多的话，就读标了核心的那几章。它们串起了全书的主线，不读别的也跟得上；其余各章，等遇到问题时再回来查。如果你要决定团队的时间和预算往哪里花，建议先读 [0.2](0-2-minimal-harness.html)、[1.1](1-1-models-and-cost.html) 和 [7.4](7-4-rollout-and-governance.html) 这三章。
