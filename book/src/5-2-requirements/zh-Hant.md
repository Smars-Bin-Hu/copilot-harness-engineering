這一章假設你用過 AI 程式 agent。它建立在[管任務，不管對話](5-1-tasks.html)上：任務是一份工作，配一個放檔案的資料夾。

## 一句話 {#in-one-sentence}

人的請求含糊，而且會變。讓 agent 把需求寫成一頁，由人確認這一頁；之後大家都照它做。

## 給主管 {#for-leaders}

- **要做的決定**：比小修改大的事，都要求一頁需求，由 agent 寫，由提出需求的人在開工前確認。
- **風險**：請求含糊、會漏東西、會隨時間改變。agent 從第一則訊息開始做的話，每個猜測都會被做進結果，到最後你才發現。這有多常發生，我沒有數字。
- **做對的成本**：每個任務請提出需求的人花幾分鐘讀。一行的修改就太多了，所以小任務可以跳過。問題太多也會讓人累，多少算太多，我沒有量過。
- **可以問團隊**：「提出需求的人確認過的那一頁在哪裡？它的『還不清楚』清單寫了什麼？」

## 問題 {#problem}

你寫：「在每日報表加上客戶的地區。」agent 做了。這不是你的意思。你指的是收貨地址的地區；它用了帳單地址的。你們誰也沒有搞錯字面。字面不夠用。

這是常態，不是特例。對 agent 的請求有三個弱點：

- **它會漏東西**。你知道背景，所以就略過了。agent 不知道，它用猜測填補空缺。
- **它可以有不止一種讀法**。「地區」可以指好幾種東西。
- **它會變**。幾輪之內，你加一個條件、拿掉另一個、改變主意。哪一版才是請求？

陷阱在這裡。讓 agent 從第一則訊息就開工，每個猜測都會被做進結果，到最後你才發現。

所以問題是：整份工作要以什麼為準。誘人的答案是：人說的原話，原封不動地留著。我試著設計過，放棄了。

## 原理 {#how-it-works}

### 為什麼我不留人的原話

我的第一個想法是記錄每個 prompt，讓「人要求了什麼」永遠在磁碟上。它因為上面的理由行不通。原話會漏東西，也不清楚。需求在幾輪之間會變，所以第一個 prompt 不是它，只看最後一個 prompt 也不是。全部留著，還會用閒聊塞滿上下文（[上下文是一份預算](3-1-context-budget.html)），而 agent 還得再整理一遍。

所以原話不是需求。需求是人*想表達*的意思，寫下來，讓他能檢查。

### agent 寫，人確認

agent 根據對話把需求寫成**一頁**。人讀這一頁並確認。這就是**需求檔**，之後每一步都以這一個檔案為準。

::: figure 5-2-one-page

為什麼是這個順序，不是「人來寫」？因為人不喜歡寫規格，而這一頁檢查起來比寫容易得多。讀到「你會用收貨地址」，回答「對」或「不，用帳單的」，成本很低。從零產出整頁就不是了。這個順序用上了 agent 擅長的（把一團亂變成結構）和人擅長的（知道自己的意思）。

它也讓確認有了清楚的意義。人確認的不是「我懂你了」。他確認的是「這一頁就是我要的」。

### 這一頁寫什麼

只寫後面幾步需要的：

- **目標**：做完時什麼應該成立。
- **要做什麼、不做什麼**：範圍和它的邊界。
- **做完的條件**：顯示它做完了的檢查，每一項都是人或程式能驗證的。
- **每一點的來源**：來源資料裡的檔案和位置，或人的回答。
- **還不清楚**：未解決的問題。這是一張誠實的清單，不是藏起來的猜測。

「做完的條件」最重要。獨立檢查（[慎用子 agent](2-3-subagents.html)）只看這一頁，[讓 agent 能檢查自己的活](5-4-self-checks.html)裡的自我檢查也是。

### agent 怎麼問

問太多的 agent 和亂猜的一樣糟。我給它的規則來自我自己的使用；我沒有拿它們和別的問法比較過：

1. **開工之前先停**。還不清楚的時候它只讀，什麼也不改。
2. **查得到的先查**。專案用哪個測試框架，在倉庫裡看得到。問這個是浪費人的時間。
3. **只問查不到的**：意圖、偏好、取捨、什麼算做完。
4. **給選項，也給建議**。「A、B 或 C；我建議 B，因為……」比「你要什麼？」好回答。建議只是建議；人確認之前不算數。
5. **不把聳肩當成同意**。「隨便」不是確認。反問一次：「我打算做 X。可以嗎？」並寫下人同意交給 agent 決定。
6. **按相依關係分批問**。上游的問題先問，一次幾個。

方法很平淡，重點是第一條：**agent 不可以用自己的猜測，填補人沒說的東西**。看起來理所當然的預設，是猜測最容易出錯的地方。

### 需求是一堆文件的時候

這一部分只在請求以業務文件的形式送來時才重要。

有時請求是一份業務文件、一張對應表的試算表和幾封信。原樣交給 agent，既花上下文，也容易出錯：Word 檔帶著封面、修訂歷史和註解；試算表有隱藏的工作表，還有帶意義的顏色。二進位檔案根本不是文字。

所以先由程式，不是模型，把它們轉成純文字。Word 變成 Markdown；每張工作表變成文字檔裡的一個表。原件原封不動地保留，並由一份簡短的報告列出程式漏掉的東西，例如隱藏的工作表或圖片。這不花 token，而且不該改動任何數字，不過它可能丟掉藏在版面或顏色裡的意義（見代價）。人修剪這份文字，加一小段說明這份工作是什麼。然後 agent 讀它，寫出那一頁。

有兩條規則讓 agent 在這裡保持誠實。看起來不對的數字要引用出來、提出來問，絕不修正。兩份互相矛盾的來源是要回報的發現，不是自己去裁決的事。這和[誰來判斷：程式、便宜模型、主模型、人](5-9-who-decides.html)是同一種分工：固定的轉換交給程式，閱讀交給模型。

### 需求的審查

這一頁一旦存在，就可以在任何工作開始之前被檢查。在我的設定裡，agent 拿它和已知的系統資訊對照，例如知識庫（為 agent 保存的一份程式碼索引，[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)；沒有的話跳過這一步），並把每個問題寫進「還不清楚」清單：問題、為什麼重要，和來源。它向人問最卡住的幾個問題，把每個答案放進這一頁，一直重複，直到清單空了、人確認為止。

有兩件事防止糟糕的審查。agent 只在文件互相矛盾、有錯、或和系統對不上的地方問。文件寫得清楚的，它不請人確認。而且確認那一行留給人：只有人才能填。

### 請求改變的時候

它一定會變。規則是：**先改這一頁**。agent 編輯需求，在變更紀錄裡加一行，然後才碰工作。如果人最新的指示和這一頁衝突，hook 會提醒 agent 先把兩者對齊，再做任何事。

計劃建立在已確認的需求上。在我的設定裡，需求還沒確認、或確認後又改了的時候，批准計劃會被拒絕（[兩道門：人在哪裡批准](5-3-two-approvals.html)）。開工之後需求才改的話，人要重新確認，重新批准計劃，已經做完的工作要重新檢查，不是丟掉。

### 測一下你自己的設定

給 agent 一個簡短的請求，裡面有兩句互相矛盾的話，例如一句說報表是每天的，一句說是每週的。看它寫的那一頁，是把衝突列在「還不清楚」下面，還是悄悄選了一個。選了一個的話，這一頁就是對一個猜測說得很有把握。

## 代價和陷阱 {#costs-and-traps}

- **它花提出需求的人幾分鐘讀**。一行的修改，這太多了。小任務可以跳過這一頁；見[管任務，不管對話](5-1-tasks.html)裡的大小。
- **確認不是證明**。人會確認只掃過一眼的頁面。這一頁可能是錯的，卻被確認了。它只是讓誤解更早被看見，僅此而已。
- **agent 可以寫出聽起來很有把握的一頁**。好的一頁有一張誠實的「還不清楚」清單。複雜的請求，這張清單卻是空的，是警訊，不是好事。
- **問題可能變成苦差事**。太多，或者問的是查得到的事，人就開始回答「隨便」。多少個問題算太多，我沒有量過。
- **轉換會丟東西**。顏色、註解和圖片都留不下來。報告會說漏掉了什麼；去讀它。

## 什麼時候可以刪掉 {#when-to-delete-it}

- **提問的方法**。隨著模型自己會問出更好的問題，就把提問的規則縮短。一頁和確認要留著：它們是為了人，不是為了模型。
- **轉換程式**。如果 agent 能可靠地讀 Word 和 Excel，把雜訊去掉，這個程式就可以丟。我沒有測過。

## 在你自己的環境試試 {#try-it}

不用裝 harness。在你自己的倉庫裡打開 agent，貼上：

::: prompt
看這個倉庫最近一個合併的 pull request，或最新的幾個 commit，連同它們連結的任何 issue 或工單文字。把請求重建成一頁需求：目標、範圍內和範圍外的是什麼、「做完」會是什麼意思，以及每一點的來源。然後列出這個請求漏掉了什麼、留下什麼沒說，以及修改裡有哪些地方顯示有人在猜。不要改任何檔案。
:::
