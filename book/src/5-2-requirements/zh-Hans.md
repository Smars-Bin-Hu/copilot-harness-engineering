读这一章，你要用过 AI 编程 agent。它建立在[管任务，不管对话](5-1-tasks.html)之上：一个任务就是一件事，加一个放文件的文件夹。

## 一句话 {#in-one-sentence}

人提的需求含糊，还会变。让 agent 把需求写成一页，由人来确认这一页；之后大家都照它干活。

## 写给管理者 {#for-leaders}

- **要拍板的事**：凡是比小改动大的事，都要求先有一页需求，由 agent 来写，提需求的人在开工之前确认。
- **风险**：需求含糊，会漏东西，还会随时间变。如果 agent 从第一条消息就开工，每一个猜测都会做进结果里，你到最后才发现。这种事有多常发生，我没有数字。
- **做对的代价**：每个任务让提需求的人花几分钟读一读。对一行的改动来说太多了，所以小任务可以跳过。问题太多也会让人厌烦，多少算太多，我没有测过。
- **可以问团队**：“提需求的人确认过的那一页在哪里？它的‘还不清楚’清单上写了什么？”

## 问题 {#problem}

你写：“在日报里加上客户所在地区。”agent 做了。但不是你的意思。你指的是收货地址的地区，它用的是账单地址的。你们俩对字面的理解都没错。光有字面不够。

这是常态，不是个别情况。给 agent 的一条需求有三个弱点：

- **它会漏东西**。你熟悉背景，所以略过了。agent 不熟悉，它用猜测把缺口补上。
- **它可以有不止一种读法**。“地区”可以指好几样东西。
- **它会变**。几轮之间，你加一个条件、去掉一个、改了主意。到底哪一版才是需求？

陷阱在这里。如果让 agent 从第一条消息就开工，每一个猜测都会做进结果里，你到最后才发现。

所以问题是：整件事该以什么为准。诱人的答案是：人说的原话，原样保留。我试着设计过，后来放弃了。

## 原理 {#how-it-works}

### 为什么我不保留人的原话

我最初的想法是记录每一条 prompt，这样“人要求了什么”始终在磁盘上。它因为上面那些原因行不通。原话会漏东西，也不清楚。需求在几轮之间会变，所以第一条 prompt 不是需求，只看最后一条 prompt 也不是。全部留着，还会用一堆闲聊填满上下文（见[上下文是一份预算](3-1-context-budget.html)），agent 之后又得重新把它们理清。

所以原话不是需求。需求是人*想表达的意思*，写下来，让他能检查。

### agent 来写，人来确认

agent 根据对话把需求写成**一页**。人读这一页，并确认它。这就是**需求文件**，之后每一步都以这一个文件为准。

::: figure 5-2-one-page

为什么是这个顺序，而不是“人来写”？因为人不喜欢写规格说明，而且这一页检查起来比写起来容易得多。读到“你会用收货地址”，回答“对”或者“不对，用账单地址”，成本很低。从零写出整页，成本就不低了。这个顺序用到了 agent 擅长的（把一团乱整理成结构）和人擅长的（知道自己是什么意思）。

它还让确认有了清楚的含义。人确认的不是“我听懂你了”，而是“这一页就是我要的”。

### 这一页上放什么

只放后面几步需要的：

- **目标**：做完之后，什么应该成立。
- **要做什么，不做什么**：范围和它的边界。
- **做完的标准**：表明已经做完的检查，每一条都是人或程序可以验证的。
- **每一点的来源**：来源文档里的文件和位置，或者人的回答。
- **还不清楚**：悬而未决的问题。这是一份诚实的清单，不是一个藏起来的猜测。

“做完的标准”最要紧。独立检查（见[慎用子 agent](2-3-subagents.html)）只以这一页为准，[让 agent 能检查自己的活](5-4-self-checks.html)里的自查也是。

### agent 怎么提问

问得太多的 agent，和乱猜的 agent 一样糟。我给它定的规则来自我自己的使用；我没有拿它们和别的提问方式比较过：

1. **开工之前先停**。还不清楚的时候，它只读，什么都不改。
2. **能查到的先查**。项目用哪个测试框架，仓库里就有。去问这个是浪费人的时间。
3. **只问查不到的**：意图、偏好、取舍、怎样才算做完。
4. **给出选项和推荐**。“A、B 或 C；我建议 B，因为……”比“你想要什么？”好回答。推荐只是建议；人确认之前不算数。
5. **不把耸肩当成同意**。“随便”不是确认。回问一次：“我打算做 X，可以吗？”并写下人同意交给 agent 决定。
6. **按依赖关系分批问**。上游的问题先问，一次问几个。

方法很朴素，要点在第一条：**agent 不能用自己的猜测，去填人没有说的东西**。看起来理所当然的默认值，正是猜测最容易出错的地方。

### 需求是一堆文档的时候

这一部分只在需求以业务文档的形式出现时才要紧。

有时候需求是一份业务文件、一张映射表格，加上几封邮件。把这些原样交给 agent，既费上下文，又容易出错：Word 文件带着封面、修订历史和批注；表格里有隐藏的工作表，还有带含义的颜色。二进制文件根本就不是文本。

所以先由程序，而不是模型，把它们转成纯文本。Word 变成 Markdown；每张工作表变成文本文件里的一张表。原件原样保留，一份简短的报告列出程序丢掉了什么，比如隐藏的工作表或图片。这不花 token，而且不该改变任何数字，不过它可能丢掉藏在排版或颜色里的含义（见“代价和坑”）。由人修剪文本，再加一段简短的说明，讲这件事是什么。然后 agent 读这些，写出那一页。

有两条规则让 agent 老实。看起来不对的数字，要引用并提问，绝不擅自更正。两个来源互相矛盾，是要报告的发现，不是自己去裁决的事。这和[谁来判断：代码、便宜模型、主模型、人](5-9-who-decides.html)是同样的分工：固定的转换交给程序，阅读交给模型。

### 需求的审查

这一页写出来之后，在开工之前就可以检查。在我的配置里，agent 把它和系统里已知的东西对照，比如知识库（为 agent 维护的一份代码索引，见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)；没有的话跳过这一步），把每个问题写进“还不清楚”清单：问题是什么、为什么要紧、来源在哪。它向人问最卡住进度的几个问题，把每个答案写进那一页，一直重复，直到清单为空、人确认为止。

有两件事防着一次糟糕的审查。agent 只在文档互相矛盾、有错、或者和系统对不上的地方才提问。文档说得清楚的东西，它不让人再确认一遍。而且确认那一行留给人：只有人才能填。

### 需求变了的时候

它会变。规则是**先改那一页**。agent 先编辑需求，在变更记录里加一行，然后才去动工作。如果人最新的指示和这一页冲突，hook 会提醒 agent 先把两者对齐，再做别的。

计划建立在已确认的需求之上。在我的配置里，需求还没确认，或者确认之后又变了，批准计划就会被拒绝（见[两道门：人在哪里审批](5-3-two-approvals.html)）。如果开工之后需求变了，人要重新确认，重新批准计划，而已经做完的工作要重新检查，不是扔掉。

### 测试你自己的配置

给 agent 一段简短的需求，里面有两句互相矛盾的话，比如一句说报告是每天的，一句说是每周的。看它写的那一页，是把这个冲突列在“还不清楚”下面，还是悄悄选了一个。如果它选了一个，这一页就是对着一个猜测说得很笃定。

## 代价和坑 {#costs-and-traps}

- **要花提需求的人几分钟来读**。对一行的改动，这太多了。小任务可以跳过这一页；见[管任务，不管对话](5-1-tasks.html)里的规模。
- **确认不是证明**。人会确认自己只扫了一眼的页面。这一页可能是错的，却被确认了。它只是让误解更早地显现出来，仅此而已。
- **agent 可以写出一页听起来很笃定的东西**。好的一页有一份诚实的“还不清楚”清单。复杂的需求配一份空清单，是警示信号，不是好兆头。
- **提问可能变成负担**。问得太多，或者问的是能查到的东西，人就开始回答“随便”了。多少个问题算太多，我没有测过。
- **转换会丢东西**。颜色、批注和图片留不下来。报告会说丢掉了什么；要读。

## 什么时候可以删掉 {#when-to-delete-it}

- **提问的方法**。模型自己越来越会提好问题时，就缩短提问的规则。保留那一页和确认：它们关乎的是人，不是模型。
- **转换程序**。如果 agent 能可靠地读 Word 和 Excel，并且把噪音去掉，这个程序就可以去掉。我没有测过。
