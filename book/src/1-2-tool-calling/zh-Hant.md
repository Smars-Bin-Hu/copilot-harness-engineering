讀這一章，只需要知道寫程式的 AI agent 能讀檔案、執行指令。怎麼做到的，不用知道。

## 一句話 {#in-one-sentence}

模型只是要求呼叫工具，真正執行工具的，是它周圍的程式。所以工具是給一個不可靠的使用者用的介面，它的描述和錯誤訊息，決定它能不能被用好。

## 給主管 {#for-leaders}

- **要做的決定**：把你給 agent 的工具當成產品來看待，它需要好的描述和好的錯誤訊息；還要決定哪些固定的步驟交給指令（command），而不是寫進 prompt。
- **風險**：模型只能從工具的名字和描述去猜，所以含糊的工具會被用錯，或者根本沒人用。寫在 prompt 裡的規則是請求，而由指令完成的步驟，在那條路徑上是跳不過去的。
- **做對的成本**：重寫描述和錯誤訊息，花不了多少。指令是程式碼，就得有人維護。Anthropic 建議，有五個真實的任務，就夠開始測試工具了。
- **可以問團隊**：「如果只讀每個工具的名字和描述，你知道什麼時候該用它嗎？它的錯誤訊息說了什麼？」

## 工具到底是誰在執行？ {#problem}

看 agent 改檔案的時候，你會覺得是模型改的。其實不是。語言模型是一個吃進文字、吐出文字的程式，光靠它自己，打不開檔案、執行不了指令，也送不出請求。它沒有手。

它能做的，是寫出一句話，意思是「請用路徑 `src/app.py` 呼叫工具 `read_file`」。這句話就是一次**工具呼叫**：模型要求使用某個**工具**，並附上它選好的參數。所謂工具，就是 agent 可以要求的一個動作，例如讀檔案、搜尋、改檔案、執行指令、抓一個網頁。模型周圍的程式（也就是[什麼是 Harness Engineering？](0-1-the-gap-and-the-map.html)裡第一種意思的 harness）讀到這句話，把事情做完，再把拿回來的東西變成文字，接著放進對話裡。這段文字就是**工具結果**，模型讀了它，再決定下一步。

這看起來是個技術細節，卻會改變你看待工具的方式。agent 做的每個動作，都要經過一次呼叫，而程式可以檢查、拒絕或修改這次呼叫。而且模型也不是在呼叫函式的謹慎程式設計師，它是根據描述去猜的讀者，所以要把它當成一個只會快速瀏覽的使用者。

### 一次來回

::: figure 1-2-tool-call

供應商自己的文件，描述的也是這樣一個來回。模型回答時帶著停止原因 `tool_use`，以及一個寫出工具名和參數的區塊，你的程式執行這個工具，再送回 `tool_result`。（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）

有一個例外值得知道。有些 **server tool**（例如網頁搜尋）是在供應商那邊執行的，所以你自己永遠碰不到那次呼叫；而你編輯器裡的 agent 做的大部分事，用的都是在你機器上執行的 client tool。這個差別對這一章很重要，因為遇到 server tool，你沒辦法在它執行之前或之後插手，程式根本看不到那次呼叫。

## 能在哪裡插手，又該給模型寫些什麼 {#how-it-works}

### 你能在哪裡插手

用 client tool 的時候，程式站在請求和動作之間，所以有兩個地方可以插手。工具執行之前，程式可以放行這次呼叫、拒絕它，或者修改它。通常的辦法是用 hook（見[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)），hook 拒絕時給的原因，會回到 agent 那裡。工具執行之後，程式還可以在模型讀到結果之前，把結果縮短、過濾或補充。

這就是能對 agent 強制執行規則的主要原因。放在程式裡的規則是會執行的程式碼，而寫在 prompt 裡的規則是請求（見[提示裡的規則只是請求](4-1-requests-and-rules.html)）。

不過，hook 只能判斷模型已經送出的呼叫。模型一開始能不能把呼叫送對，要看這趟來回的中間：呼叫之前它看到什麼，呼叫之後它拿回什麼。而這兩樣，恰恰都是你寫的文字。

### 工具是給不可靠使用者的介面

先看看兩邊各有什麼可以依靠。人在用命令列時，可以讀文件、問同事，也會注意到哪裡看起來不對。模型手上只有工具的名字、一段簡短的描述和參數清單，除此之外什麼都沒有。所以它可能猜錯，供應商的文件也這麼說：如果一個工具需要地點，而請求裡沒有給，模型可能會自己編一個。（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）

這樣看來，替 agent 設計工具，就是在為這樣一個使用者設計。它只憑名字和描述決定什麼時候用，參數則靠上下文去猜。工具沒告訴它的事，它一概不知道；回傳的結果，它也都當成普通的文字來讀，結果有多大，就占掉多少上下文視窗。

Anthropic 談怎麼替 agent 寫工具的那篇建議，換個說法講的也是這件事：「就算只是把工具描述稍微改好，也能帶來很大的進步。」（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）下面的五條規則都由此而來，大致照一次呼叫經過的順序排。

### 1. 描述要寫得像給新同事的交辦單

呼叫之前，描述是模型了解一個工具用途的唯一地方，所以它得寫清楚這個工具做什麼、什麼時候用、什麼時候不用。描述含糊，工具就會被用錯，或者從來沒被用到。名字也一樣要講究。例如一個叫 `user` 的參數，可能是名字、ID，也可能是 email，而 `user_email` 只可能是一種意思。還有，如果兩個工具看起來很像，每個工具的描述裡都要說清楚它和另一個哪裡不同。

### 2. 錯誤訊息要寫給 agent 讀

呼叫出了錯，模型接下來讀到的就是錯誤訊息。人看到堆疊追蹤，會停下來想一想，模型卻是拿到文字就繼續往下走。如果錯誤訊息是 `Error 400`，模型就只能猜，常常又猜回同一個錯的值。如果錯誤訊息寫了哪裡錯、接著可以試什麼，它就能把這次呼叫修好。

拒絕也一樣，要寫明該改做什麼（見[詢問不是限制](4-2-ask-vs-refuse.html)）。

### 3. 輸出要短，而且能分頁

呼叫成功了，模型讀到的是輸出。工具回傳的所有東西，都會放進上下文視窗（見[上下文是一份預算](3-1-context-budget.html)），而且之後每一輪都會再讀一遍（見[選模型，別只看 token 單價](1-1-models-and-cost.html)）。所以，如果 agent 只想要一行，工具卻回傳整個大檔案，不只浪費 token，還可能把有用的東西擠出視窗。

辦法是給結果合理的限制，例如預設的上限、要求某個範圍或下一頁的辦法，或者一個過濾條件。Anthropic 也描述過，讓 agent 在簡潔和詳細的回應之間選。工具很多的時候，把相關的工具歸到共同的名字前綴底下，能幫 agent 分辨它們。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

具體到數字，Claude Code 預設把工具回應限制在 25,000 個 token（這是我寫作時 Anthropic 的數字）。不管上限訂在哪裡，你截掉輸出的時候都要說出來，並告訴 agent 怎麼把查詢範圍縮小。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

### 4. 工具少，選得更準

前面幾條講的都是單一工具，但工具的數量也有講究。你也許覺得多一個工具，不用就沒壞處。其實它照樣有成本，因為每個工具的名字、描述和參數，每次呼叫都會送給模型。工具越多，花的 token 越多，選錯的機會也越多，功能重疊的時候尤其如此。所以盡量用一小組明顯不同的工具，能合併的相關操作，就合併成一個。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

### 5. 固定的步驟，放進指令裡，不放進 prompt 裡

前四條講的是已有的工具，最後這一條講的是哪些工作該做成工具，也是我最想強調的一條。有些工作裡的步驟，永遠是同一個走法，而且有對有錯：為新任務建資料夾、複製檔案、算雜湊值、寫紀錄、寫回去之前檢查一切就緒。你可以把這些步驟寫成指令檔裡的指示，請 agent 照著做，它大多數時候也會照做。

你也可以不靠指示，把它們一次寫成一個**指令**（command），也就是 agent 當工具執行的一個小程式。指令自己完成這些步驟，自己檢查前置條件，最後回傳一個簡短的結果。在經過這個指令的路徑上，agent 沒辦法跳過任何一步，也寫不出錯的狀態，因為狀態根本不是它寫的。

::: figure 1-2-prompt-vs-command

這適合不需要判斷的步驟。如果某一步需要 agent 拿主意，就把那部分留給它，讓指令只做周圍那些固定的事。我的 harness 就是這樣做的。一條命令列指令負責建立任務資料夾（任務是[管任務，不管對話](5-1-tasks.html)裡講的工作單位）、抓檔案、算 diff、數檢查的次數，模型只要執行指令、讀答案就好。這樣一來，結果每次都一樣，模型也從來不用自己把步驟做對。為什麼要這樣，進度是個好例子：任務清單讀的是指令寫入的資料檔，不是 agent 手寫的 Markdown 筆記，因為手寫的進度會漏打勾，也會出錯。

指令的輸出如果能說明下一步做什麼，對 agent 就更友善，因為它不用猜。而同一個指令，既有人在終端機裡看，也有腳本透過管線讀，所以它可以在終端機裡印出對齊的文字，接到管線上時印出 JSON，兩種輸出的欄位是一樣的。

不過，指令也有自己的限度。agent 真的去用它，它才幫得上忙，而且它只守得住經過它的東西。如果 agent 能用別的辦法做同一件事，例如手動改檔案，這個指令就只是圖個方便，算不上限制。[提示裡的規則只是請求](4-1-requests-and-rules.html)會把這一點講得更深。

### 怎麼檢查你自己的工具

對你給 agent 的任何一個工具，都可以先問三個問題。

1. 如果只讀它的名字和描述，你知道什麼時候該用、什麼時候不該用嗎？
2. 它失敗的時候，訊息有沒有告訴 agent 接下來做什麼？
3. 它的輸出最大可以多大？大的時候，上下文會怎樣？

最快的實驗什麼都不用裝。請 agent 用一個你明知不對的方式呼叫你的某個工具，看看回來的是什麼。假如你就是那個 agent，這個訊息夠不夠清楚，能讓你知道該做什麼？如果不夠，要重寫的就是這個訊息。

如果你自己做工具，Anthropic 的方法就是同一個想法放大。根據真實的使用情況寫出任務，執行它們，讀原始的紀錄（呼叫和結果，不只是最後的答案），然後在 agent 出錯的地方修好描述和錯誤訊息。五個任務就夠開始。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

## 好工具要付出什麼，又會在哪裡出錯 {#costs-and-traps}

這些做法都不是免費的。描述寫得再好，也要花 token，因為長的描述每次呼叫都會送出去。所以，只寫模型選工具、用工具需要的內容就好，長的手冊放進檔案裡，讓 agent 需要時才讀。

指令的代價不一樣，因為它是要維護的程式碼。專案一變，指令就可能出錯，而且是 prompt 不會有的那種錯，所以每個指令都要保持小，並給它一個測試。

不過，工具會出問題的地方，不只是代價。工具呼叫不能當成可信的舉動，因為參數是模型選的，而它選之前讀到的文字，可能來自任何地方。別把一次呼叫當成使用者的意願，[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)說明了原因。

最後還有一個很實際的陷阱：工具名稱會隨版本改變。如果你的規則或 hook 靠工具名稱比對，就把這份對應關係放在一個地方，這樣改名時只要改一處。

## Anthropic 也這麼看嗎？ {#industry}
{status: industry}

這一章的建議依據的是兩份資料，都出自 Anthropic。其中談怎麼寫工具的那一篇，把工具設計當成工作的一部分，認為描述和錯誤訊息值得像程式碼一樣測試（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）。tool use 文件則說，client tool 由應用程式執行，再把結果送回去，還提醒說，模型「可能會猜出你沒有提供的值」（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）。兩者都和這裡的論點一致：工具是介面，它的文字也是介面的一部分。

## 什麼時候可以刪掉指令 {#when-to-delete-it}
{status: industry}

上面這些建議裡，最可能過時的是指令，因為檢查前置條件的指令，是圍繞模型弱點搭起來的鷹架。如果模型在照著多步驟的指示做事上變得夠可靠，指令可能就不再勝過一個好的 prompt。就算到了那一天，凡是每次都必須完全一樣、或需要留下紀錄的事，我仍然會保留指令。描述和錯誤訊息的道理則是另一回事，只要模型還是讀文字，它就一直成立。
