读这一章，只需要知道写代码的 AI agent 能读文件、跑命令。不需要知道它是怎么做到的。

## 一句话 {#in-one-sentence}

模型只负责提出工具调用，运行工具的是它外面的程序。所以工具是给一个不可靠的用户用的接口，它的描述和报错信息，决定了它能不能被用好。

## 写给管理者 {#for-leaders}

- **要拍板的事**：把你给 agent 的工具当成一个产品来对待，它需要好的描述和好的报错信息；并且决定哪些固定的步骤写进命令，而不是写进 prompt。
- **风险**：模型只能根据工具的名字和描述去猜，所以含糊的工具会被用错，或者根本没人用。写在 prompt 里的规则是请求；由命令完成的步骤，在这条路径上跳不过去。
- **做对的代价**：重写描述和报错信息，花费很小。命令是代码，得有人维护。Anthropic 建议，五个真实的任务就足够开始测试工具了。
- **可以问团队**：“如果只看每个工具的名字和描述，你能知道什么时候该用它吗？它的报错信息又是怎么说的？”

## 问题 {#problem}

看着 agent 改文件，会觉得是模型干的。其实不是。语言模型是一个读入文本、产出文本的程序。它打不开文件，运行不了命令，也发不出请求。它没有手。

它能做的，是写一句话，意思是“请调用工具 `read_file`，路径是 `src/app.py`”。这句话就是**工具调用**。模型外面的程序（[差距在模型外面](0-1-the-gap-and-the-map.html)里第一种意思的 harness）读到这句话，把事情做完，再把结果作为更多文本放回对话里。然后模型读这个结果，决定下一步做什么。

这看起来像个技术细节，却改变了你该怎么看待工具。agent 的每个动作，都要经过一次调用，而程序可以检查、拒绝或修改这次调用。而且模型也不是一个认真的程序员在调用函数：它是一个靠描述来猜的读者。把它当成一个只会扫一眼的用户。

### 先说三个词

- **工具**是 agent 可以要求做的一个动作：读文件、搜索、改文件、运行命令、抓取网页。
- **工具调用**是模型请求使用一个工具，带着它选的参数。
- **工具结果**是程序运行完工具之后送回来的文本。

### 一次来回

::: figure 1-2-tool-call

模型提供方自己的文档讲的是同一个来回：模型回复时，停止原因是 `tool_use`，并带着一个写明工具名和参数的块；你的代码运行它，再送回一个 `tool_result`。（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）有一个例外值得知道：有些**服务端工具**，比如网页搜索，是在提供方那边运行的，所以你从头到尾碰不到这次调用。你编辑器里的 agent 做的大部分事，是客户端工具，在你的机器上运行。这个区别对本章很要紧：对服务端工具，你没法在它运行之前或之后插手，因为程序根本看不到这次调用。

## 原理 {#how-it-works}

### 你能在哪里插手

程序夹在请求和动作之间，所以有两个地方可以插手：

- **工具运行之前**。程序可以放行这次调用，拒绝它，或者修改它。常用的办法是 hook（[Hook：每次调用都会经过的执行点](2-2-hooks.html)），拒绝时会带上一个原因，送回给 agent。
- **运行之后**。程序可以在模型读到结果之前，对结果做精简、过滤或补充。

这是能对 agent 强制执行规则的主要原因。放在程序里的规则是会运行的代码；放在 prompt 里的规则是请求（[提示里的规则只是请求](4-1-requests-and-rules.html)）。

这一章其余的部分，讲的是这趟来回的中间：模型看到什么，又拿回什么。这两样都是你写的文本。

### 工具是给不可靠用户的接口

人用命令行，可以看文档，可以问同事，还能注意到哪里看着不对。模型有的只是工具的名字、一段简短的描述和参数列表。仅此而已。它可能猜错，提供方的文档也这么说：给一个需要位置的工具，而请求里没给位置，模型可能会编一个。（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）

所以给 agent 设计工具，是在给这样的人设计：

- 只看名字和描述，来决定什么时候用，
- 靠上下文猜着填参数，
- 不知道工具没告诉它的事，
- 把结果当文本来读，结果占多少上下文窗口，就占多少。

Anthropic 关于给 agent 写工具的建议，换了个说法讲的是同一件事：“哪怕对工具描述做很小的改进，也能带来显著的提升。”（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）下面的五条规则都由此而来。

### 1. 把描述写得像给新员工的交接说明

说清楚这个工具做什么、什么时候用、什么时候不用。名字要无歧义：叫 `user` 的参数，可能是名字、ID 或邮箱；`user_email` 就不会。如果两个工具看起来很像，就在各自的描述里说明它们哪里不同。描述是模型了解这些的唯一地方，所以含糊的描述，意味着工具会被用错，或者没人用。

### 2. 报错信息要写给 agent 看

人看到堆栈，会停下来想。模型拿到的是文本，然后继续往下走。如果报错是 `Error 400`，模型就会猜，往往又猜出同样的东西。如果报错说明了哪里不对、接下来该试什么，它就会把调用改对。

拒绝也一样：要说明应该改做什么（[询问不是限制](4-2-ask-vs-refuse.html)）。

### 3. 输出要短，还要能分页

工具返回的所有东西，都会放进上下文窗口（[上下文是一份预算](3-1-context-budget.html)），而且之后每一轮都要再读一遍（[选模型：看每次成功的成本](1-1-models-and-cost.html)）。agent 只想要一行，工具却把一个很大的文件整个返回，既浪费 token，还可能把有用的东西挤出窗口。

所以要给结果设合理的限制：默认的上限、取某个范围或下一页的办法、过滤器。Anthropic 还提到，可以让 agent 在简洁回复和详细回复之间选。工具很多的时候，把相关的工具用同一个名字前缀归在一起，有助于 agent 区分它们。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）Claude Code 默认把工具的响应限制在 25,000 个 token 以内（这是 Anthropic 写这篇文章时给出的数字）。你截短输出时，要说明这一点，并告诉 agent 怎么缩小查询范围。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

### 4. 工具少，选得更准

每个工具的名字、描述和参数，每次调用都要发给模型。工具越多，花的 token 越多，选错的机会也越多，尤其是功能重叠的时候。优先用一小组明显不同的工具，能把相关的操作合并成一个就合并。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

### 5. 固定的步骤写进命令，不写进 prompt

这一条是我最想强调的。有时候，一件事里有些步骤每次都一样，而且有对错之分：给新任务建文件夹、复制文件、算一个哈希、写入记录、写回之前检查一切就绪。你可以在指令里描述这些步骤，让 agent 照着做。它大多数时候会照做。

或者，你可以把它们一次性写成一个**命令**：一个 agent 当作工具来运行的小程序。命令自己完成这些步骤，自己检查前置条件，返回一个简短的结果。走命令这条路径时，agent 跳不过任何一步，也写不出错误的状态，因为状态不是它写的。

::: figure 1-2-prompt-vs-command

这适合不需要判断的步骤。如果某一步需要 agent 做决定，就把那部分留给 agent，让命令只做它周围固定的部分。我的 harness 就是这么做的。一个命令行工具建任务文件夹（任务是[管任务，不管对话](5-1-tasks.html)里的工作单元）、取文件、算 diff、统计检查，模型只要运行命令、读结果。进度是个好例子：任务清单读的是命令写入的数据文件，而不是 agent 手写的 Markdown 笔记，因为手写的进度会漏打勾，也会出错。结果每次都一样，模型也不必保证每一步都做对。

有两个细节，让命令对 agent 更友好：

- **结果里说明下一步**。命令的输出告诉 agent 接下来做什么，它不用去猜。
- **给人看文本，给脚本用 JSON**。同一个命令，在终端里打印对齐的文本，通过管道输出时打印 JSON。字段是一样的。

命令只有 agent 真去用才有帮助，而且它只守得住经过它的东西。如果 agent 能用另一种办法做同样的事（手动改文件），这个命令就只是个方便，不是限制。[提示里的规则只是请求](4-1-requests-and-rules.html)会往下讲这一点。

### 测一测你自己的配置

给 agent 的任何工具，都问**三个问题**：

1. 只看它的名字和描述，你知道什么时候该用、什么时候不该用吗？
2. 它失败的时候，信息有没有告诉 agent 接下来做什么？
3. 它的输出最大能有多大？如果很大，上下文会怎么样？

**一个不用安装任何东西的实验**。让 agent 用一种你知道是错的方式调用你的某个工具，然后看返回了什么。它够不够清楚，让你如果是 agent 也知道该怎么办？如果不够，就是这条信息该重写。

**更大的循环，如果你在做工具**。Anthropic 的方法是同一个想法的放大版：根据真实使用写出任务，运行它们，读原始的记录（调用和结果，不只是最终答案），然后在 agent 出错的地方修描述和报错信息。五个任务就够开始了。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

## 代价和坑 {#costs-and-traps}

**好的描述也要花 token**。长描述每次调用都要发一遍。只写模型选择和使用这个工具所需要的内容，长的说明书放在文件里，让 agent 需要时再读。

**命令是要维护的代码**。项目变了，命令可能出错，而且是 prompt 不会有的那种错。每个命令都保持小，并且给它写测试。

**一次工具调用不是一个可信的行为**。参数是模型选的，而它读到的文本可能来自任何地方。别把一次调用当成用户的意愿。[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)解释了为什么。

**工具名在不同版本之间会变**。如果你的规则或 hook 按工具名来匹配，就把这个映射放在一个地方，这样改名只需改一处。

## 业界怎么说 {#industry}
{status: industry}

- **Anthropic**：工具设计是工作的一部分，描述和报错信息值得像代码一样测试。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）
- **工具使用文档**：客户端工具由应用运行，并把结果送回去；模型“可能会猜出你没提供的值”。（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）

它们和这里的论点一致：工具是一个接口，它的文本是接口的一部分。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

检查前置条件的命令，是围着模型弱点搭的脚手架。如果模型在遵循多步指令上变得足够可靠，命令也许就不再比好的 prompt 强，但对那些每次都必须完全一样、或者需要留记录的事，我还是会保留命令。关于描述和报错信息的道理，只要模型还在读文本，就一直成立。
