读这一章，只需要知道写代码的 AI agent 能读文件、跑命令。不需要知道它是怎么做到的。

## 一句话 {#in-one-sentence}

模型只负责提出工具调用，真正运行工具的是它外面的程序。所以工具是给一个不可靠的用户用的接口，它的描述和报错信息，决定了它能不能被用好。

## 写给管理者 {#for-leaders}

- **要拍板的事**：把你给 agent 的工具当成产品来对待，它需要好的描述和好的报错信息；还要决定哪些固定的步骤交给命令，而不是写进 prompt。
- **风险**：模型只能根据工具的名字和描述去猜，所以含糊的工具会被用错，或者干脆没人用。写在 prompt 里的规则是请求，而由命令完成的步骤，在这条路径上是跳不过去的。
- **做对的代价**：重写描述和报错信息，花不了多少。命令是代码，就得有人维护。Anthropic 建议，有五个真实的任务就足够开始测试工具了。
- **可以问团队**：“如果只看每个工具的名字和描述，你能知道什么时候该用它吗？它的报错信息又是怎么说的？”

## 工具到底是谁在运行？ {#problem}

看着 agent 改文件，你会觉得是模型改的。其实不是。语言模型是一个读入文本、产出文本的程序，单靠它自己，打不开文件，运行不了命令，也发不出请求。它没有手。

它能做的，是写出一句话，意思是“请调用工具 `read_file`，路径是 `src/app.py`”。这句话就是一次**工具调用**：模型请求使用某个**工具**，并附上它选好的参数。所谓工具，就是 agent 可以要求做的一个动作，比如读文件、搜索、改文件、运行命令、抓取网页。模型外面的程序（也就是[什么是 Harness Engineering？](0-1-the-gap-and-the-map.html)里第一种意思的 harness）读到这句话，把事情做完，再把拿回来的东西变成文本，接着添进对话里。这段文本就是**工具结果**，模型读了它，再决定下一步做什么。

这看起来像个技术细节，却会改变你看待工具的方式。agent 的每个动作都要经过一次调用，而程序可以检查、拒绝或修改这次调用。而且模型也不是一个认真的程序员在调用函数，它是一个靠描述来猜的读者，所以要把它当成一个只会扫一眼的用户。

### 一次来回

::: figure 1-2-tool-call

模型提供方自己的文档，讲的也是这样一个来回。模型回复时，停止原因是 `tool_use`，并带着一个写明工具名和参数的块，你的代码运行这个工具，再送回一个 `tool_result`。（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）

有一个例外值得知道。有些**服务端工具**，比如网页搜索，是在提供方那边运行的，所以你从头到尾碰不到这次调用；而你编辑器里的 agent 做的大部分事，用的都是在你机器上运行的客户端工具。这个区别对本章很要紧，因为碰上服务端工具，你没法在它运行之前或之后插手，程序根本看不到这次调用。

## 能在哪里插手，又该给模型写些什么 {#how-it-works}

### 你能在哪里插手

用客户端工具的时候，程序夹在请求和动作之间，所以有两个地方可以插手。工具运行之前，程序可以放行这次调用、拒绝它，或者修改它。常用的办法是 hook（见[硬性规则放在哪？用 hook](2-2-hooks.html)），hook 拒绝时给出的原因，会送回给 agent。工具运行之后，程序还可以在模型读到结果之前，把结果精简、过滤或补充一下。

这就是能对 agent 强制执行规则的主要原因。放在程序里的规则是会运行的代码，而写在 prompt 里的规则是请求（见[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)）。

不过，hook 只能对模型已经发出的调用做判断。模型一开始能不能把调用发对，取决于这趟来回的中间：调用之前它看到什么，调用之后它拿回什么。而这两样，恰恰都是你写的文本。

### 工具是给不可靠用户的接口

先看看两边各有什么可依靠的。人用命令行，可以看文档、问同事，还能察觉到哪里不对劲。模型手里只有工具的名字、一段简短的描述和参数列表，别的什么都没有。所以它会猜错，提供方的文档也这么说：如果一个工具需要地点，而请求里没给，模型可能会自己编一个。（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）

这样看来，给 agent 设计工具，就是在给这样一个用户设计。它只凭名字和描述决定什么时候用，参数则靠上下文去猜。工具没告诉它的事，它一概不知道；返回的结果，它也都当成普通文本来读，结果有多大，就占掉多少上下文窗口。

Anthropic 关于给 agent 写工具的建议，换了个说法讲的也是这件事：“哪怕对工具描述做很小的改进，也能带来显著的提升。”（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）下面五条规则都由此而来，大致按一次调用经过的顺序排。

### 1. 把描述写得像给新员工的交接说明

调用之前，描述是模型了解一个工具用途的唯一地方，所以它得说清楚这个工具做什么、什么时候用、什么时候不用。描述含糊，工具就会被用错，或者没人用。名字也一样要讲究。比如一个叫 `user` 的参数，可能是名字、ID，也可能是邮箱，而 `user_email` 只可能是一种意思。还有，如果两个工具看起来很像，每个工具的描述里都要说清它和另一个有什么不同。

### 2. 报错信息要写给 agent 看

调用出了错，模型接下来读到的就是报错。人看到堆栈，会停下来想一想，模型却是拿到文本就接着往下走。如果报错是 `Error 400`，模型就只能猜，往往又猜回同一个错的值。如果报错说明了哪里不对、接下来该试什么，它就能把调用改对。

拒绝也一样，要说明应该改做什么（见[“先问我”为什么挡不住 Agent？](4-2-ask-vs-refuse.html)）。

### 3. 输出要短，还要能分页

调用成功了，模型读到的是输出。工具返回的所有东西都会放进上下文窗口（见[为什么不能把所有规则都塞给 Agent？](3-1-context-budget.html)），而且之后每一轮都要再读一遍（见[选模型，别只看 token 单价](1-1-models-and-cost.html)）。所以，如果 agent 只想要一行，工具却把一个很大的文件整个返回，不光浪费 token，还可能把有用的东西挤出窗口。

办法是给结果设合理的限制，比如默认的上限、取某个范围或下一页的办法，或者一个过滤器。Anthropic 还提到，可以让 agent 在简洁回复和详细回复之间选。工具很多的时候，把相关的工具归到同一个名字前缀下，能帮 agent 把它们分清楚。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

具体到数字，Claude Code 默认把工具的响应限制在 25,000 个 token 以内（这是我写作时 Anthropic 给出的数字）。不管上限定在哪里，截短输出时都要说一声，并告诉 agent 怎么缩小查询范围。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

### 4. 工具少，选得更准

前面几条讲的都是单个工具，可工具的数量也有讲究。你也许觉得多一个工具，不用就没坏处。其实它照样有成本，因为每个工具的名字、描述和参数，每次调用都要发给模型。工具越多，token 花得越多，选错的机会也越多，功能重叠的时候尤其如此。所以优先用一小组明显不同的工具，能把相关的操作合并成一个，就合并。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

### 5. 固定的步骤写进命令，不写进 prompt

前四条讲的是已有的工具，最后这一条讲的是哪些活该做成工具，也是我最想强调的一条。有些活儿里的步骤每次都一样，而且有对错之分：给新任务建文件夹、复制文件、算一个哈希、写入记录、写回之前检查一切就绪。你可以把这些步骤写进指令，让 agent 照着做，它大多数时候也会照做。

你也可以把它们一次性写成一个**命令**，也就是 agent 当作工具来运行的一个小程序。命令自己完成这些步骤，自己检查前置条件，最后返回一个简短的结果。走命令这条路径时，agent 跳不过任何一步，也写不出错误的状态，因为状态根本不是它写的。

::: figure 1-2-prompt-vs-command

这适合不需要判断的步骤。如果某一步需要 agent 拿主意，就把那部分留给它，让命令只做周围那些固定的事。我的 harness 就是这么做的。一个命令行工具负责建任务文件夹（任务是[一个任务一个文件夹](5-1-tasks.html)里讲的工作单元）、取文件、算 diff、统计检查，模型只要运行命令、读结果就行。这样一来，结果每次都一样，模型也从来不必自己把步骤做对。为什么要这样，进度是个好例子：任务清单读的是命令写入的数据文件，而不是 agent 手写的 Markdown 笔记，因为手写的进度会漏打勾，也会出错。

命令的输出如果能说明下一步做什么，对 agent 就更友好，因为它不用去猜。而同一个命令，既有人在终端里看，也有脚本通过管道读，所以它可以在终端里打印对齐的文本，接到管道上时打印 JSON，两种输出的字段是一样的。

不过，命令也有自己的局限。agent 真去用它，它才帮得上忙，而且它只守得住经过它的东西。如果 agent 能用别的办法做同样的事，比如手动改文件，这个命令就只是图个方便，算不上限制。[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)会接着往下讲这一点。

### 怎么检查你自己的工具

对你给 agent 的任何一个工具，都可以先问三个问题。

1. 只看它的名字和描述，你知道什么时候该用、什么时候不该用吗？
2. 它失败的时候，信息有没有告诉 agent 接下来做什么？
3. 它的输出最大能有多大？如果很大，上下文会怎么样？

最快的实验什么都不用装。让 agent 用一种你明知不对的方式调用你的某个工具，看看返回了什么。假如你就是那个 agent，这条信息够不够清楚，能让你知道该怎么办？如果不够，要重写的就是这条信息。

如果你自己做工具，Anthropic 的方法就是同一个想法的放大版。根据真实的使用场景写出任务，运行它们，读原始的记录（调用和结果，不只是最终答案），然后在 agent 出错的地方修改描述和报错信息。五个任务就够开始了。（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）

## 好工具要付出什么，又会在哪里出错 {#costs-and-traps}

这些做法都不是免费的。描述写得再好，也要花 token，因为长描述每次调用都要发一遍。所以，只写模型选择和使用这个工具所需要的内容，长的说明书放进文件里，让 agent 需要时再读。

命令的代价不一样，因为它是要维护的代码。项目一变，命令就可能出错，而且是 prompt 不会有的那种错，所以每个命令都要保持小，并且给它写测试。

不过，工具会出问题的地方，不只是代价。工具调用不能当成可信的举动，因为参数是模型选的，而它选之前读到的文本，可能来自任何地方。别把一次调用当成用户的意愿，[Agent 读到的网页和文件，可能在给它下命令](4-6-untrusted-input.html)解释了为什么。

最后还有一个很实际的坑：工具名在不同版本之间会变。如果你的规则或 hook 按工具名来匹配，就把这份对应关系放在一个地方，这样改名时只需改一处。

## Anthropic 也这么看吗？ {#industry}
{status: industry}

这一章的建议依据的是两份资料，都出自 Anthropic。其中讲怎么写工具的那篇，把工具设计当成工作的一部分，认为描述和报错信息值得像代码一样测试（[Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)）。工具使用文档则说，客户端工具由应用运行，再把结果送回去，还提醒说，模型“可能会猜出你没提供的值”（[Tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)）。两者都和这里的论点一致：工具是一个接口，它的文本也是接口的一部分。

## 什么时候可以删掉命令 {#when-to-delete-it}
{status: industry}

上面这些建议里，最可能过时的是命令，因为检查前置条件的命令，是围着模型的弱点搭起来的脚手架。如果模型在遵循多步指令上变得足够可靠，命令也许就不再比一个好的 prompt 强。即便到了那一天，对那些每次都必须完全一样、或者需要留下记录的事，我还是会保留命令。描述和报错信息的道理则是另一回事，只要模型还在读文本，它就一直成立。
