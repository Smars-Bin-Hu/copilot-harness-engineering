读这一章，你需要知道[管任务，不管对话](5-1-tasks.html)里的任务文件夹，也需要知道一段对话会被压短或者结束（见[长对话会变差](3-2-long-sessions.html)）。

## 一句话 {#in-one-sentence}

长任务要跨会话延续，记忆就得放在文件里：需求、计划、待办清单、交接文件。把大任务拆成一个个小任务，小到可以逐个验收。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对要跨好几天的工作，定下它的记忆放在文件里，并且大任务要拆成能逐个验收的小任务。
- **风险**：新会话什么都不知道，除非有文件告诉它。一个大任务一股脑交出去，会被一下子全开工，然后半途而废；后来的会话看到有进展，可能过早宣布任务完成。在我的配置里，人对某一步说的“通过”只是一段文字，代码里没有任何东西支撑它。这是最薄弱的一环。
- **做对的代价**：文件要花功夫：每一步写一点，新会话读一点。对一个会话就能做完的任务，这是浪费。一个 goal 比重新开个对话能省多少，我没有测过。
- **可以问团队**：“我们跑得最久的那个任务，哪个文件告诉新会话现在做到哪一步了？到目前为止的各步，是谁验收的？”

## 问题 {#problem}

一个要三天的任务，一次对话装不下。第一个会话结束了。或者工具为了腾地方把它压短，细节就丢了。新会话什么都不知道，除非有东西告诉它。

什么能告诉它？不是 agent 的记忆：它在会话之间没有记忆。也不是你的记忆：如果每天早上都得把背景再讲一遍，每次讲得还不太一样。每天早上唯一一模一样的东西，是文件。

还有第二个问题，来自任务的大小。一个大任务一股脑交给 agent，它往往想一下子全开工，做到一半空间用完，留下一堆做了一半的东西。Anthropic 在一个长期的编程项目上也看到了同样的情况：“agent 倾向于一次想做太多”（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。同一篇文章还描述了相反的失败，也就是后来的实例过早“宣布任务完成”；那个问题是[无人值守：什么时候必须停](5-7-when-to-stop.html)的主题。

## 原理 {#how-it-works}

### 一段对话会丢掉什么

一段对话里装着后来的会话需要的四样东西：要求是什么，定了什么、为什么这么定，工作做到哪了，接下来是什么。对话被压短或者结束时，这四样都有风险，而且 agent 不知道自己丢了哪几样。

### 文件夹里放什么

把这四样放到压不短的地方。

::: figure 5-8-shared-folder

- **需求**：要求是什么，写成人确认过的样子（见[需求由 agent 写，人确认](5-2-requirements.html)）。
- **计划**：工作打算怎么做，什么不在范围内。
- **待办清单**：一步步的事项，每一步都小，每一步都有状态，也有判断它做完了没有的办法。
- **交接**：一份简短的**交接文件**（就是[管任务，不管对话](5-1-tasks.html)里的那份，那里也讲了为什么以磁盘为准；Anthropic 把自己的版本叫 progress file），写明现在做到哪一步、接下来是什么。它得保持简短，不超过一屏，否则新会话的空间都花在读它上面。

还有第五样会有帮助：变更日志，每完成一步记一条，写清楚改了什么。有人问“为什么是这样”时，答案就在那里。

### 新会话读什么

新会话先读简短的交接文件，再读待办清单，最后才读当前这一步需要的东西。它不读整个文件夹。然后它拿文件对照磁盘：文件真的存在吗，这一步真的发生了吗？**记录和磁盘对不上时，以磁盘为准**。交接文件写着“第 4 步做完了”，并不会让第 4 步做完。

Anthropic 的团队做了三件事，我的做法与之不同。他们让 agent 每做完一步就提交到 git，这样每一步都留下一个干净的状态可以退回。他们让每个新会话在开始新工作之前，先跑一遍基本的端到端测试，这是对旧状态的检查，而不只是读文件。他们还把功能清单放在 JSON 里，因为模型误改 JSON 文件的可能性比改 Markdown 文件小。我的文件是 Markdown，两者我没有比较过。

### 先搭框架，再一步一步来

别一上来就干活。先搭框架：

1. 定下核心想法：目标是什么，范围里有什么、没有什么，整体怎么验收。
2. 拆成小步骤。
3. 让人把两样都读一遍并确认。
4. 然后做一步：做完，检查，交给人。
5. 人说“通过”，这一步才算完成。然后写日志，更新交接文件，进入下一步。

人说的“通过”是一道关卡（见[两道门：人在哪里审批](5-3-two-approvals.html)）。在我的配置里，它是文字，不是代码：代码里没有任何东西能阻止 agent 自己给自己写“通过”。我靠的是 agent 照着指令办，以及人去读。这是我知道的一个缺口。

### 多大算太大，怎么拆

大多数任务就是一个任务，goal 是留给其余的。一件事不适合只当作一个任务，是指下面任何一条成立（这三条是我的经验法则，没有测过）：

- 一个会话做不完，而且没人说得清它做到了哪里。
- 你说不出怎么一次性验收它的整体。
- 随着你了解得越来越多，计划总在变。

办法是用一个 **goal**：把这件大事放进一套文件里，下面挂几个**任务**。一个任务就是一次交付，和[管任务，不管对话](5-1-tasks.html)里一样：一个文件夹，有自己的检查，有自己的验收。goal 放想法和清单，每个任务做其中一块。

::: figure 5-8-goal-tasks

一个好的任务，小到你能用一句话说出怎么验收它。你在做任务 2 的时候，goal 不需要知道任务 3 的细节。这正是意义所在：计划可以一个任务一个任务地改，不用把已经验收的重做一遍。已经验收的步骤不改写；要重做，就是新的一步。

### 常见的坑

- **一下子全开工**。agent 想在一个会话里完成整个 goal。办法是用清单：同一时间只有一步是活动的。
- **过早说做完了**。新会话看到有进展，就认定已经完成了。办法和无人值守的活一样（见[无人值守：什么时候必须停](5-7-when-to-stop.html)）：做完是由文件和人确认的一种状态，不是 agent 嘴里说的一件事。
- **交接文件太长**。指针一旦超过一屏，就没人读了。把细节移到日志里。
- **小任务也建 goal**。大多数任务只要一个任务。goal 是留给跨会话、而且形状会变的工作。

## 代价和坑 {#costs-and-traps}

**文件要花功夫**。每一步写一点，新会话读一点。对一个会话就能做完的任务，这是浪费。

**人的“通过”只是文字**。[两道门：人在哪里审批](5-3-two-approvals.html)把一次审批绑定到确切的那份计划上，由代码来检查。这里一步的“通过”没有绑定任何东西；代码里没有什么能阻止 agent 写下它。这是本章最薄弱的一环。

**文件可能说谎**。文件是 agent 写的，所以可能写错，也可能过期。这就是为什么以磁盘为准，也是为什么人要一步一步验收。

**谁来启动很重要**。在我的配置里，只有人才能启动一个 goal。任务看起来很长时，agent 可以建议，但不能自己开一个。否则每个任务都会变成一个项目。

**我没有测过的**。一个 goal 比起直接开个新对话再解释一遍，能省多少。我认为在任务形状会变的时候省得最多，但我没有数字。

## 什么时候可以删掉 {#when-to-delete-it}

如果平台能在跨会话时对长任务保有可靠的记忆，新会话不读文件就能接着干，交接文件就可以去掉。需求和计划我还是会留成文件：人也能读，验收工作靠的就是这个。
