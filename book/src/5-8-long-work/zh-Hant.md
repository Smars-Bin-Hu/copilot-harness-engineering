讀這一章，你需要知道 [管任務，不管對話](5-1-tasks.html) 裡的任務資料夾，也要知道對話會被縮短或結束（[長對話會變差](3-2-long-sessions.html)）。

## 一句話 {#in-one-sentence}

長時間的工作要能跨會話撐下去，它的記憶就必須放在檔案裡：需求、計畫、待辦清單、交接檔。把大工作拆成小到能一個一個驗收的任務。

## 給主管 {#for-leaders}

- **要做的決定**：對跨好幾天的工作，決定它的記憶放在檔案裡，並把大工作拆成小到能一個一個驗收的任務。
- **風險**：新的會話什麼都不知道，除非有檔案告訴它。一次交出去的大工作，會被一次全部開工、做到一半就丟著，之後的會話也可能看到有進展，就太早說工作做完了。在我的設定裡，人對一步說的「通過」只是文字，程式裡沒有任何東西撐著。這是最弱的一環。
- **做對的成本**：檔案要花力氣：每一步寫一點，新的會話讀一點。對一個一次會話就做得完的工作，這是浪費。一個目標比起開新對話省多少，我沒有量過。
- **可以問團隊**：「對我們跑得最久的那項工作，哪個檔案告訴新的會話它在哪一步？到目前為止的步驟，是誰驗收的？」

## 問題 {#problem}

要花三天的工作，一次對話裝不下。第一個會話結束了。或者工具為了騰出空間把它縮短，細節就沒了。新的會話什麼都不知道，除非有東西告訴它。

什麼能告訴它？不是 agent 的記憶：它在會話之間沒有記憶。也不是你的記憶，如果你每天早上都得重新解釋一次背景，而且每次說得都有點不一樣。每天早上唯一一樣的東西，是一個檔案。

還有第二個問題，來自工作的大小。一次拿到大工作的 agent，傾向於一次全部開工，做到一半空間用完，留下一堆做到一半的東西。Anthropic 在一個長時間的寫程式專案上看到同樣的事：「agent 傾向一次做太多」（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。同一篇文章也描述了相反的失敗：後來的實例太早「宣布工作完成」；那個是 [無人值守：什麼時候必須停](5-7-when-to-stop.html) 的主題。

## 原理 {#how-it-works}

### 對話會丟掉什麼

一段對話裝著後來的會話需要的四樣東西：被要求做什麼、決定了什麼和為什麼、工作做到哪裡、接下來是什麼。對話被縮短或結束時，這四樣都有風險，而 agent 不知道自己丟了哪些。

### 資料夾裡放什麼

把這四樣東西放在不會被縮短的地方。

::: figure 5-8-shared-folder

- **需求**：被要求做什麼，以人確認過的形式（[需求由 agent 寫，人確認](5-2-requirements.html)）。
- **計畫**：工作要怎麼做，以及什麼不在範圍內。
- **待辦清單**：一步一步，每步都小，每步都有狀態，也有辦法判斷它做完了沒。
- **交接**：一份簡短的**交接檔**（就是 [管任務，不管對話](5-1-tasks.html) 裡的那個，那裡也解釋了為什麼以磁碟為準；Anthropic 把它的版本叫做 progress file），說明目前在哪一步、接下來是什麼。它必須保持簡短，一個畫面以內，不然新的會話會把空間花在讀它上面。

第五樣東西也有幫助：變更紀錄，每完成一步寫一條，說明改了什麼。有人問「為什麼是這樣？」，答案就在那裡。

### 新的會話讀什麼

新的會話先讀簡短的交接檔，再讀待辦清單，然後才讀目前這一步需要的東西。它不讀整個資料夾。接著它拿檔案對照磁碟：檔案真的存在嗎？這一步真的發生過嗎？**紀錄和磁碟不一致時，以磁碟為準**。寫著「第 4 步完成」的交接檔，不會讓第 4 步完成。

Anthropic 的團隊做了三件事，我的做法不一樣。他們讓 agent 每做完一步就 commit 到 git，所以每一步都留下一個乾淨、可以回去的狀態。他們讓每個新的會話，在開始新工作之前先跑一個基本的端到端測試，這是對舊狀態的檢查，不只是讀檔案。而且他們把功能清單放在 JSON 裡，因為模型誤改 JSON 檔案的機會，比誤改 Markdown 小。我的檔案是 Markdown，兩者我沒有比較過。

### 先搭框架，再一步一步來

不要從工作開始。從框架開始：

1. 定下核心想法：目標、範圍內有什麼、沒有什麼、整體怎麼驗收。
2. 拆成小步驟。
3. 讓人讀這兩樣並確認。
4. 然後做一步：做、檢查、交給人。
5. 一步要等人說通過才算做完。然後寫變更紀錄、更新交接檔，再進入下一步。

人的「通過」是一道門（[兩道門：人在哪裡批准](5-3-two-approvals.html)）。在我的設定裡，那是文字，不是程式：程式裡沒有任何東西阻止 agent 替自己寫下「通過」。我靠的是 agent 遵守指令，以及人去讀。這是我知道的一個缺口。

### 什麼算太大，怎麼拆

大多數工作是一個任務，目標是留給其餘的。一個工作在以下任一種情況為真時，對一個任務來說就太大了（這三條是我的經驗法則，沒有測過）：

- 一次會話做不完，而且沒人說得出做到多少了。
- 你說不出要怎麼一次驗收整件事。
- 隨著你學到更多，計畫一直在變。

解法是一個**目標**：把大事情做成一組檔案，底下有幾個**任務**。一個任務是一次交付，就像 [管任務，不管對話](5-1-tasks.html) 裡那樣：一個資料夾、自己的檢查、自己的驗收。目標放想法和清單；每個任務做一塊。

::: figure 5-8-goal-tasks

好的任務小到你能用一句話說出怎麼驗收它。你在做任務 2 的時候，目標不需要知道任務 3 的細節。重點就在這裡：計畫可以一次改一個任務，不必重做已驗收的東西。已經驗收的步驟不會被改寫；重做是新的一步。

### 常見的陷阱

- **一次全部開工**。agent 想在一次會話裡完成整個目標。解法是清單：同一時間只有一步在進行。
- **太早說做完了**。新的會話看到進展，就判定做完了。解法和無人值守的工作一樣（[什麼時候停](5-7-when-to-stop.html)）：做完是檔案和人確認的一個狀態，不是 agent 說的一句話。
- **交接檔太長**。如果指標長過一個畫面，就沒人讀了。把細節移到變更紀錄。
- **為小工作建立目標**。大多數工作只需要一個任務。目標是留給跨會話、而且會改變形狀的工作。

## 代價和陷阱 {#costs-and-traps}

**檔案要花力氣**。每一步寫一點，新的會話讀一點。對一個一次會話就做得完的工作，這是浪費。

**人的「通過」只是文字**。[兩道門：人在哪裡批准](5-3-two-approvals.html) 把批准綁到確切的計畫，由程式檢查。這裡一步的「通過」沒有綁定到任何東西；程式裡沒有任何東西阻止 agent 寫下它。這是這一章最弱的一環。

**檔案會說謊**。檔案是 agent 寫的，所以可能是錯的或過期的。這就是為什麼以磁碟為準，也是為什麼人要一步一步驗收。

**誰來開始很重要**。在我的設定裡，只有人能開始一個目標。agent 看到工作很長時可以建議，但不能自己開始。不然每個工作都會變成專案。

**我沒量過的**。一個目標比起直接開新對話再重新解釋，省了多少。我認為當工作改變形狀時，省得最多，但我沒有數字。

## 什麼時候可以刪掉 {#when-to-delete-it}

如果平台能跨會話，為長工作保有可信的記憶，讓新的會話不必讀檔案就能接著做，交接檔就可以拿掉。需求和計畫我還是會留成檔案：人也讀得了它們，而驗收工作靠的就是這個。

::: prompt
/harness-rookie-wondering 我讀完了「跨會話的長任務」這一章。請教我這個 harness 怎麼把長工作放在檔案裡（主題 9）：任務資料夾、新的會話讀的交接檔，以及把幾個任務組在一起的目標。帶我打開真實的檔案，並畫出這些部分怎麼組合在一起。
:::

它一次教一小塊，停下來確認你跟得上，然後和你一起打開檔案。
