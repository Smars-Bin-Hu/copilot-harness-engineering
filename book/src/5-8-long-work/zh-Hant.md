讀這一章，你需要知道[管任務，不管對話](5-1-tasks.html)裡的任務資料夾，也要知道對話會被縮短或結束（[長對話會變差](3-2-long-sessions.html)）。

## 一句話 {#in-one-sentence}

長時間的工作要能跨會話撐下去，它的記憶就必須放在檔案裡：需求、計畫、待辦清單、交接檔。大工作要拆成小到能一個一個驗收的任務。

## 給主管 {#for-leaders}

- **要做的決定**：對跨好幾天的工作，決定它的記憶放在檔案裡，並把大工作拆成小到能一個一個驗收的任務。
- **風險**：除非有檔案告訴它，新的會話什麼都不知道。大工作一次交出去，agent 往往會一口氣全部開工，做到一半就丟著；之後的會話看到有進展，還可能太早說工作做完了。在我的設定裡，人對一步說的「通過」只是文字，程式裡沒有任何東西撐著。這是最弱的一環。
- **做對的成本**：檔案要花力氣，因為每一步都要寫一點，每個新的會話都要讀一點。如果一次會話就做得完，這就是浪費。一個目標比起開新對話能省多少，我沒有量過。
- **可以問團隊**：「對我們跑得最久的那項工作，哪個檔案告訴新的會話它在哪一步？到目前為止的步驟，是誰驗收的？」

## 新的會話怎麼知道工作做到哪裡？ {#problem}

要花三天的工作，一次對話是裝不下的。總有一刻，第一個會話結束了，或者工具為了騰出空間把它縮短，細節也就跟著沒了。接手的下一個會話什麼都不知道，除非有東西告訴它。

那什麼能告訴它？不是 agent 的記憶，因為它在會話之間根本沒有記憶。也不能靠你記著，那樣的話，你每天早上都得把背景重新解釋一次，而且每次說得都不太一樣。每天早上唯一一樣的東西，是檔案。

還有第二個問題，它出在工作的大小上。一次拿到大工作的 agent，往往想一口氣全部開工，做到一半空間用完，留下一堆做到一半的東西。Anthropic 在一個長時間的寫程式專案上也看到同樣的事：「agent 傾向一次做太多」（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。同一篇文章也描述了相反的失敗，也就是後來的實例太早「宣布工作完成」，那是[無人值守：什麼時候必須停](5-7-when-to-stop.html)的主題。

這樣看來，檔案要做的不只是把記憶從一個會話帶到下一個會話，還得把大工作切成一塊一塊，每塊小到能做完、能驗收。

## 記憶放進檔案，工作拆成小步 {#how-it-works}

### 對話會丟掉什麼

既然只有檔案每天都一樣，那就得先弄清楚它要裝下什麼。一段對話裝著後來的會話需要的四樣東西：被要求做什麼、決定了什麼和為什麼、工作做到哪裡、接下來是什麼。對話一旦被縮短或結束，這四樣都有風險，而且 agent 並不知道自己丟了哪些。

### 資料夾裡放什麼

這四樣東西應該放在不會被縮短的地方。

::: figure 5-8-shared-folder

- 需求記下被要求做什麼，而且是人確認過的形式（[需求由 agent 寫，人確認](5-2-requirements.html)）。
- 計畫裡寫工作要怎麼做，以及什麼不在範圍內。
- 待辦清單把工作拆成一步一步，每步都小，每步都有狀態，也有辦法判斷它做完了沒。
- 交接靠一份簡短的**交接檔**，說明目前在哪一步、接下來是什麼。它和講任務那一章說的是同一份（Anthropic 把它的版本叫做 progress file）。它必須保持簡短，一個畫面以內，不然新的會話會把空間都花在讀它上面。

還有第五樣東西也有幫助：變更紀錄，每完成一步寫一條，說明改了什麼。以後有人問「為什麼是這樣？」，答案就在那裡。

### 新的會話讀什麼

那新的會話一來，先讀什麼？不是整個資料夾。它先讀簡短的交接檔，再讀待辦清單，然後才讀目前這一步需要的東西。讀完之後，它要拿檔案裡寫的去對照磁碟：檔案真的存在嗎？這一步真的發生過嗎？**紀錄和磁碟不一致時，以磁碟為準**（為什麼，見[管任務，不管對話](5-1-tasks.html)）。寫著「第 4 步完成」的交接檔，不會讓第 4 步真的完成。

同樣是新的會話接手，Anthropic 的團隊有三件事做得和我不一樣。他們的 agent 每做完一步就 commit 到 git，所以每一步都留下一個乾淨、可以回去的狀態。每個新的會話在開始新工作之前，會先跑一個基本的端到端測試，這樣舊狀態是真的檢查過，而不只是在檔案裡讀到。功能清單他們放在 JSON 裡，因為比起 Markdown，模型誤改 JSON 檔案的機會比較小。我的檔案用的是 Markdown，兩者我也沒有比較過。

### 先搭框架，再一步一步來

記憶的問題有了著落。另一個問題是一口氣全部開工，這得在動手之前就防住：先搭框架，不先動手。然後再一步一步往下做：

1. 定下核心想法：要達成什麼、範圍內有什麼、沒有什麼、整體怎麼驗收。
2. 拆成小步驟。
3. 讓人讀這兩樣並確認。
4. 然後做一步：做、檢查、交給人。
5. 一步要等人說通過才算做完。然後寫變更紀錄、更新交接檔，再進入下一步。

這裡人的「通過」是一道門（[兩道門：人在哪裡批准](5-3-two-approvals.html)）。這道門有多可靠，後面講代價時再說。

### 什麼算太大，怎麼拆

大多數工作一個任務就裝得下。一件工作只要符合下面任何一條，對一個任務來說就太大了（這三條是我的經驗法則，沒有測過）：

- 一次會話做不完，而且沒人說得出做到多少了。
- 你說不出要怎麼一次驗收整件事。
- 隨著你學到更多，計畫一直在變。

**目標**就是為這種工作準備的：它把大事情做成一組檔案，底下有幾個**任務**。一個任務是一次交付，就像[管任務，不管對話](5-1-tasks.html)裡那樣：一個資料夾、自己的檢查、自己的驗收。目標放想法和清單，每個任務各做其中一塊。

::: figure 5-8-goal-tasks

好的任務小到你能用一句話說出怎麼驗收它。你在做任務 2 的時候，目標不需要知道任務 3 的細節。拆開的重點就在這裡：計畫可以一次改一個任務，不必重做已經驗收的東西。已經驗收的步驟不會被改寫，要重做，就算新的一步。

### 常見的陷阱

這裡面有兩個陷阱，就是這一章開頭說的那兩種失敗。第一個是 agent 想在一次會話裡完成整個目標，對付它靠清單：同一時間只有一步在進行。第二個是新的會話看到進展，就判定做完了。對付它的辦法和無人值守的工作一樣（[什麼時候停](5-7-when-to-stop.html)）：做完是檔案和人確認的一個狀態，不是 agent 說的一句話。

另外兩個陷阱都和大小有關。一個是交接檔寫得太長。它本來只是用來指路的，一旦長過一個畫面就沒人讀了，所以細節要移到變更紀錄，交接檔保持簡短。另一個是為小工作建立目標，可是大多數工作一個任務就夠了，目標是留給跨會話、而且會改變形狀的工作。

這些都不是免費的，其中還有一環很弱。

## 檔案要付出什麼，弱在哪裡 {#costs-and-traps}

最直接的代價是力氣：每一步都要寫一點，每個新的會話都要讀一點，對一次會話就做得完的工作來說，這些檔案就是浪費。

人的「通過」是這一章最弱的一環。[兩道門：人在哪裡批准](5-3-two-approvals.html)把批准綁到確切的計畫，由程式檢查。這裡一步的「通過」卻沒有綁定到任何東西。在我的設定裡，那只是文字而不是程式，程式裡沒有任何東西阻止 agent 替自己寫下「通過」。這是我知道的一個缺口，我靠的是 agent 遵守指令，再靠人去讀。

而且檔案會說謊。檔案是 agent 寫的，所以可能是錯的，也可能過期了。正因為這樣，才要以磁碟為準，也才要人一步一步驗收。

還有一個風險是目標開得太多。為了防住它，在我的設定裡只有人能開目標。agent 看到工作很長時可以建議開一個，可是如果它自己就能開，每個工作都會變成專案。

我沒量過的，是一個目標比起直接開新對話再重新解釋，到底能省多少。我認為當工作會改變形狀時省得最多，但我沒有數字。

## 什麼時候可以刪掉交接檔，什麼會留下 {#when-to-delete-it}

如果平台能跨會話，為長工作保有可信的記憶，讓新的會話不必讀檔案就能接著做，交接檔就可以拿掉。不過需求和計畫我還是會留成檔案，因為人也讀得了它們，而驗收工作靠的就是這個。
