读这一章，请先读过 [agent 循环，以及你能插手的地方](2-1-agent-loop.html)，或者至少知道 agent 读文本、再用文本回答。

## 一句话 {#in-one-sentence}

规则、知识、文件和工具结果共用同一个窗口，每一样都在挤占其他几样的位置。所以要像管预算一样管上下文：需要时再取，不要一次全装进去。

## 写给管理者 {#for-leaders}

- **要拍板的事**：把 agent 读到的内容当成预算，决定哪些每次都加载，哪些只在任务需要时才取。
- **风险**：所有内容共用一个窗口，而窗口还有空位，并不等于表现就好。埋在又长又杂的上下文里的规则，更容易被漏掉。漏掉多少，我没有数字。这条建议来自平台厂商和我自己的设计，不是我做过的测试。
- **做对的代价**：主要是配置的时间，花在给规则分层、缩短工具输出、让索引始终保持准确上。装得太少也有代价，因为那样 agent 就只能去猜。
- **可以问团队**：“每一轮都加载了什么？其中有多少和眼前这个任务有关？”

## 信息给得越多，答案为什么反而可能越差？ {#problem}

AI 答得不好时，最常听到的建议是“多给它点信息”。于是你把整份风格指南贴进去，把所有规则都加上，再让它把所有文件读一遍。这样做感觉很稳妥，毕竟事实越多，错误按理说就越少。

结果却往往相反。不妨想想一张书桌。你当然可以把一个项目的所有文档都摊在上面，可那样一来，要用的那一份就找不着了，也没地方写字了。agent 也有这么一张书桌，叫**上下文窗口**，也就是模型在一轮里能看到的全部文本。桌上放着规则，也放着你说的话、agent 读过的文件、工具调用的结果，以及它自己之前的回答。这张桌子有大小上限。而且我后面会讲到，它还有第二个上限，和大小无关。

这一章我没有做过干净的实验，所以我能说的，来自另外两个地方。一个是做这些工具的人。Anthropic 写道，上下文“必须当作一种有限的资源来对待，边际收益会递减”（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)），VS Code 的指南也说要“避免上下文过载而分散注意力”（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）。另一个是我自己搭配置的方式，里面几乎每个设计选择，都是在想办法让窗口里少放一点。从成本上看也是同一个方向：一个任务的成本，大部分来自模型读的东西（[选模型：看每次成功的成本](1-1-models-and-cost.html)）。不过在讲第二个上限之前，我们先看看窗口里到底装了什么。

## 窗口里装了什么，怎么少装一点 {#how-it-works}

### 窗口里有什么

::: figure 3-1-window

共用这个窗口的有六样东西：

1. 规则和指令，由平台每次都放进去。
2. 工具列表，附带每个工具的描述。模型要靠它才知道自己能请求什么；工具一多，比如来自好几个 MCP server（[MCP server：接工具的标准接口](1-3-mcp.html)），这份列表可能占掉窗口很大一块。到底有多大，我没量过。
3. 你发的消息。
4. agent 读过的文件。文件是整段文本放进去的，不管其中真正有用的有多少。
5. 工具结果，比如搜索列表、命令输出、测试日志。它们常常是最大的一块，也是没人去看的一块。
6. agent 自己之前的回答。

循环每转一轮，窗口里就多一条结果，却不会少掉任何东西。每一轮，模型还要把这六样东西从头再读一遍（这笔账在[选模型：看每次成功的成本](1-1-models-and-cost.html)里）。所以窗口只会越来越满，直到装不下为止。到了那时，平台只能截掉或总结最早的部分，细节也就丢了。[长对话会变差](3-2-long-sessions.html)讲的就是这件事。

### 是两个上限，不是一个

那换个更大的窗口不就行了？问题是，装不下只是谁都看得见的那个上限。第二个上限是注意力，Anthropic 把它叫作“注意力预算”，模型读大量文本时要从里面扣。落到实际，意思就是窗口还有空位，不等于表现就好。同一条规则，埋在又长又杂的上下文里，比放在短上下文里更容易被漏掉。

我把这当成少放的理由，哪怕东西全都装得下。不过这一步是我自己的推断，不是 Anthropic 说的。影响有多大，要看模型和任务。

### 全装进去、只放索引，还是两者结合

既然装得下也该少放，问题就变成了：该把什么留在外面？这本书这一部分里的大多数决定，背后都是这个选择。

最简单的回答是什么都不留在外面。agent 一开始，窗口里就有所有规则、所有笔记，它什么都不用查。麻烦在于，工作还没开始，窗口就已经花掉了，而且大半花在这个任务用不上的东西上。

另一头的回答，是只放一份索引，需要什么再取。agent 一开始只有一份简短的列表，上面是现有各样东西的名字和一行说明，等任务需要其中某一样，它再去打开那一样。Anthropic 把这叫作“即时”（just in time）做法：agent 只保留轻量的标识（文件路径、名字），到运行时再加载数据。这和图书馆是一个道理：谁也不会把整座图书馆搬到书桌上，我们都是先查目录，再去取那一本。

在这两头之间，Anthropic 自己的建议是把两者结合起来。用他们的话说，“最有效的 agent 可能采用混合策略，先取一部分数据来保证速度”，其余的再由它自己去探索。他们举的例子是 Claude Code，它事先把指令文件放进上下文，其余的在工作中用搜索工具去找。

全装进去在有些情况下还是更合适。任务小，或者规则少，全装进去更简单，也花不了多少。而在漏掉一条事实代价很高的地方，我宁愿花钱把它放进窗口，也不愿赌 agent 会打开对的文件。

成本上，全装进去还多一条好处。每次都加载、又从不变化的开头，是可以缓存的，而读缓存比正常读便宜得多（[选模型：看每次成功的成本](1-1-models-and-cost.html)）。所以只要开头保持稳定，“全装进去”其实比 token 数看起来要便宜。不过，我没有在 Copilot 上测过缓存。而且就算用上缓存，上面说的注意力上限也还在那里。

::: figure 3-1-load-when

不管怎么搭配，索引这一部分要管用，都得满足三件事。第一，索引里的条目得说清什么时候该打开它，因为 agent 只凭那一行就做决定。说得含糊，agent 就会打开错的东西，或者永远不打开对的那个，这就是为什么 skill 的描述那么重要（[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)）。第二，取用得便宜而且准确。如果取一样东西要读整个文件夹，索引就什么也没省下。第三，agent 得知道自己不知道，因为 agent 自己没意识到缺了的东西，索引是帮不上忙的。这才是真正的风险，下面我还会回到这一点。

### 少读一点的办法

索引只是让窗口保持小的办法之一。下面这些是我在用的，每一种要么不让东西进窗口，要么把它拿出去。如果想找个地方下手，最省事的两个是给规则分层和缩短工具输出。

- **规则分层。** 留一小组规则始终加载，其余的放在只有处理相关文件或相关工作时才会读到的地方。不会改变下一步动作的规则，只是噪音。（做法：[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)。）
- **先搜索，再阅读。** 让 agent 先找到东西在哪，再只读文件里的那一部分，而不是整个文件。或者事先写好一份简短的项目地图给它，也就是上面说的那种索引。只有读地图比搜索划算，它才算赢；也只有有人让它保持准确，它才一直可信。我没有测过我的地图是不是划算（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）。
- **让工具输出变短。** 一条命令打印 2,000 行，窗口里就多了 2,000 行，所以要把它过滤一下，或者只打印失败的部分。
- **用几行提醒，不要一整页。** 在我的配置里，每条 prompt 只附加规则里很短的一小段；有任务时（[管任务，不管对话](5-1-tasks.html)），这段提醒还会说明任务进行到了哪里。这只是提醒，完整的内容要到需要时才读。
- **把大块的阅读交给子 agent**（[慎用子 agent](2-3-subagents.html)、[长对话会变差](3-2-long-sessions.html)）。
- **把状态写进文件**，这样新对话读一个简短的文件就行，不用去读旧的对话。新对话就是一个空窗口，至于什么时候开新对话、带什么过去，见[长对话会变差](3-2-long-sessions.html)。

### 三个问题和一个测试

你自己的配置，窗口是怎么花掉的？可以先问三个问题：

1. 每次都加载了什么？数一数你那些始终开启的规则有多少行，再看其中有多少和你现在做的任务有关。（在 Claude Code 里，`/context` 命令能显示什么在占用窗口。Copilot 提供什么，我没查过。）
2. agent 上一次读的最大的一样东西是什么？是文件还是日志，全都需要吗？
3. 如果 agent 现在开一个新对话，它要读什么才能接着干？这些东西在文件里吗？

还有一个今天就能跑的测试。找一个你知道答案的任务，各开一个新对话，跑两次。第一次，把整个文件或文档贴进 prompt；第二次，只说出文件名和相关的部分，让 agent 只读那一部分。每次运行都记下四样：答案对不对、时间、你的工具显示的用量，以及 agent 漏掉了什么。想让差异可信，每种做法都多跑几次，而且两种做法用同样的方式打分。最后再比较两种做法的答案、时间和用量。

## 少装要付出什么 {#costs-and-traps}

少往窗口里放，头一个代价，就是前面说要回过头来谈的那个风险：装得少，可能丢掉 agent 需要的东西。索引其实是一场赌注，赌 agent 会打开对的东西。agent 要是没打开，就只能凭猜测干活。补救的办法是把描述写得更好，再检查该打开的时候到底有没有打开。检查起来也不难：跑一个你知道需要某个文件的任务，看工具里记录的打开了什么，数一数有多少次没打开。新对话、规则或 skill 也可能这样丢掉，因为它们同样要靠 agent 在对的时候读到对的东西。

同样的风险也出在摘要上。子 agent 的报告和平台的压缩，都会把文本缩短，也都可能丢掉最关键的那一行，所以只在简短版本够用的地方用它们。

索引还得一直保持准确。过期的地图花的比省的多，因为 agent 会信它。[让知识库一直是对的](8-5-kb-keep-true.html)讲的就是这个。

开头说过，这一章背后没有数字。对于 Copilot 的模型，窗口越满、注意力丢掉多少，我不知道有什么干净的衡量办法。

## 平台厂商也这么看吗？ {#industry}
{status: industry}

这两家厂商在开头都引过，这里把两家的说法放在一起看。Anthropic 说，上下文是“有限的资源，边际收益递减”，agent 可以通过保留轻量的引用来“即时”加载数据（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。VS Code 的指南则说：“从简洁的上下文开始，需要时再扩充。”（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）

可见两家在方向上是一致的。不过，到底该加载多少，两家都没有给出我能引用的数字。这就留下一个实际的问题：这一章里的手工活还要做多久？

## 什么时候可以删掉这些手工活 {#when-to-delete-it}
{status: industry}

只要窗口有大小，模型每一轮都要读它，这套道理本身就在。可能会去掉的，是我自己花的功夫，也就是手动给规则分层、手动开新对话。如果平台能按相关性把规则加载好，压缩时又不丢重要的内容，我就不再手动做了。但窗口再大，也不会自动消除第二个上限，所以在指望大窗口之前，我想先看到这方面的测试。

## 在你自己的环境里试试 {#try-it}

::: prompt
看看这个项目用来测试、lint、构建和搜索的命令。逐个告诉我，它成功时和失败时大约会输出多少文本，如果你运行它，这些输出会不会把你的上下文窗口塞满。为每个命令提出一种更安静的运行方式，比如只打印失败项或摘要。把最吵的三个排个序。不要修改任何文件，也不要运行任何会改变状态的东西。
