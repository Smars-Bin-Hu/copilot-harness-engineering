读这一章，请先读过 [agent 循环，以及你能插手的地方](2-1-agent-loop.html)，或者至少知道 agent 读文本、再用文本回答。

## 一句话 {#in-one-sentence}

规则、知识、文件和工具结果共用同一个窗口，每一样都在挤占其他几样的位置。所以要像管预算一样管上下文：需要时再取，不要一次全装进去。

## 写给管理者 {#for-leaders}

- **要拍板的事**：把 agent 读到的内容当成预算。决定哪些每次都加载，哪些只在任务需要时才取。
- **风险**：所有内容共用一个窗口，窗口还有空位不等于表现就好，所以埋在又长又杂的上下文里的规则，更容易被漏掉。漏掉多少，我没有数字；这条建议来自平台厂商和我自己的设计，不是我做过的测试。
- **做对的代价**：主要是配置的时间：给规则分层、缩短工具输出、让索引始终保持准确。装得太少也有代价：agent 会去猜。
- **可以问团队**：“每一轮都加载了什么？其中有多少和眼前这个任务有关？”

## 问题 {#problem}

AI 答得不好，常见的建议是“多给它点信息”。把整份风格指南贴进去，把所有规则都加上，让它读完所有文件。这样做感觉很稳：事实越多，错误越少。

结果往往相反。想想一张书桌。你可以把一个项目的所有文档都摊开，然后就找不到要用的那一份，也没地方写字了。agent 也有这样一张书桌，叫**上下文窗口**：模型在一轮里能看到的全部文本。里面有规则、你说的话、agent 读过的文件、工具调用的结果，以及它自己之前的回答。它有大小上限。而且，我后面会讲到，它还有第二个上限，和大小无关。

我能说的，来自两个地方。第一个是做这些工具的人。Anthropic 写道，上下文“必须当作一种有限的资源来对待，边际收益会递减”（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。VS Code 的指南说要“避免上下文过载而分散注意力”（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）。第二个是我自己搭配置的方式：里面几乎每个设计选择，都是想办法让窗口里少放一点。同一个想法在成本上的一面，在[选模型：看每次成功的成本](1-1-models-and-cost.html)里：一个任务的成本，大部分来自模型读的东西。这一章我没有做过干净的实验。

## 原理 {#how-it-works}

### 窗口里有什么

::: figure 3-1-window

有六样东西共用它：

1. **规则和指令**，由平台每次都放进去。
2. **工具列表**，附上每个工具的描述。模型靠它知道自己能请求什么。工具很多时，比如来自好几个 MCP server（[MCP server：接工具的标准接口](1-3-mcp.html)），这份列表可能占窗口很大一块。有多大，我没量过。
3. **你发的消息。**
4. **agent 读过的文件。** 文件是整段文本放进去的，不管其中真正有用的有多少。
5. **工具结果**：搜索列表、命令输出、测试日志。它们常常是最大的一块，也是没人去看的一块。
6. **agent 自己之前的回答。**

循环每转一轮，模型都要把这些内容重新读一遍，再加上新增的一条结果（这笔账在[选模型：看每次成功的成本](1-1-models-and-cost.html)里）。所以窗口只会越来越满，直到装不下。到那时，平台只能截掉或总结最早的部分，细节就丢了。[长对话会变差](3-2-long-sessions.html)讲的就是这件事。

### 是两个上限，不是一个

大小是显而易见的上限。第二个是注意力。Anthropic 把它叫作“注意力预算”，模型读很多文本时要从里面扣。实际的意思是：窗口还有空位，不等于表现就好。一条规则埋在又长又杂的上下文里，比同一条规则放在短上下文里，更容易被漏掉。我把这当成少放的理由，哪怕东西全都装得下。这一步是我自己的推断，不是 Anthropic 说的。影响有多大，取决于模型和任务，我没量过。

### 全装进去、只放索引，还是两者结合

这一部分里大多数决定，背后都是这个选择。

**先全装进去。** agent 一开始，窗口里就有所有规则、所有笔记。它不用查任何东西。但是工作还没开始，窗口就已经花掉了，而且大部分花在这个任务用不上的东西上。

**只放索引，需要什么再取。** agent 一开始只有一份简短的列表：现有各样东西的名字和一行说明。任务需要其中某一样时，它再打开那一样。Anthropic 把这叫作“即时”（just in time）做法：agent 只保留轻量的标识（文件路径、名字），在运行时再加载数据。

**两者结合。** Anthropic 自己的建议是混合：“最有效的 agent 可能采用混合策略，先取一部分数据来保证速度”，再自己继续探索。他们举的例子是 Claude Code：它事先把指令文件放进上下文，其余的在工作中用搜索工具去找。

另一边在有些情况下更合适。任务小，或者规则少，全装进去更简单，花不了多少。而在漏掉一条事实代价很高的地方，我宁愿花钱把它放进窗口，也不愿赌 agent 会打开对的文件。

再说一点成本。每次加载、又从不变化的开头，可以缓存，而读缓存比正常读便宜得多（[选模型：看每次成功的成本](1-1-models-and-cost.html)）。所以只要开头保持稳定，“全装进去”比 token 数看起来的要便宜。但缓存解决不了上面说的注意力上限。我没有在 Copilot 上测过缓存。

::: figure 3-1-load-when

这和图书馆一样。你不会把整座图书馆搬到书桌上。你先查目录，再去取那一本书。

要让这个办法管用，有三件事必须成立。

- **索引里的条目必须说清什么时候该打开它。** agent 只凭那一行就做决定。说得含糊，它就会打开错的东西，或者永远不打开对的那个。这就是 skill 的描述为什么那么重要（[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)）。
- **取用必须便宜而且准确。** 如果取一样东西要读整个文件夹，索引就什么也没省下。
- **agent 必须知道自己不知道。** 索引帮不了 agent 没意识到缺了的东西。这才是真正的风险，下面我再回到这一点。

### 少读一点的办法

下面是我在用的办法。每一种，要么不让东西进窗口，要么把它拿出来。最容易上手的两个是：给规则分层，缩短工具输出。

- **规则分层。** 留一小组规则始终加载。其余的放在只有处理相关文件或相关工作时才会读到的地方。不会改变下一步动作的规则，只是噪音。（做法：[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)。）
- **先搜索，再阅读。** 让 agent 先找到东西在哪，再只读文件的那一部分，而不是整个文件。或者事先写好一份简短的项目地图给它：就是上面说的那种索引。只有读地图比搜索划算，它才算赢；也只有有人让它保持准确，它才一直可信。我没有测过我的地图是不是划算（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）。
- **让工具输出变短。** 一条命令打印 2,000 行，窗口里就多了 2,000 行。把它过滤一下，或者只打印失败的部分。
- **用几行提醒，不要一整页。** 在我的配置里，每条 prompt 只附加规则里很短的一小段。有任务时（[管任务，不管对话](5-1-tasks.html)），它说明任务进行到了哪里。这只是提醒，需要时才会读完整的内容。
- **把大块的阅读交给子 agent**（[慎用子 agent](2-3-subagents.html)、[长对话会变差](3-2-long-sessions.html)）。
- **把状态写进文件**，这样新对话读一个简短的文件就行，不用读旧的对话。新对话就是一个空窗口；什么时候开新对话、带什么过去，见[长对话会变差](3-2-long-sessions.html)。

### 检验你自己的配置

**三个问题：**

1. 每次都加载了什么？数一数你那些始终开启的规则有多少行。其中有多少和你现在做的任务有关？（在 Claude Code 里，`/context` 命令能显示什么在占用窗口。Copilot 提供什么，我没查过。）
2. agent 上一次读的最大的一样东西是什么？是文件？日志？全都需要吗？
3. 如果 agent 现在开一个新对话，它要读什么才能接着干？这些东西在文件里吗？

**今天就能跑的一个测试。** 找一个你知道答案的任务。各开一个新对话，跑两次。第一次，把整个文件或文档贴在 prompt 里。第二次，只说出文件名和相关的部分，让 agent 只读那一部分。比较答案、时间和用量。想让差异可信，每种多跑几次，而且两种做法用同样的方式打分。每次运行记下四样：答案对不对、时间、你的工具显示的用量，以及 agent 漏掉了什么。

## 代价和坑 {#costs-and-traps}

**装得少，可能丢掉 agent 需要的东西。** 索引是一场赌注：赌 agent 会打开对的东西。它没打开时，就只能凭猜测干活。补救办法是把描述写得更好，再检查该打开的时候有没有打开。检查的方法：跑一个你知道需要某个文件的任务，看工具里记录的打开了什么，数一数有多少次没打开。新对话、规则或 skill 也是同样的道理，也会这样丢掉。

**摘要会丢细节。** 子 agent 的报告和平台的压缩，都会把文本缩短，也都可能丢掉最关键的那一行。只在简短版本够用的地方用它们。

**索引必须保持准确。** 过期的地图，花的比省的多，因为 agent 会信它。[让知识库一直是对的](8-5-kb-keep-true.html)讲的就是这个。

**这里没有数字。** 对于 Copilot 的模型，窗口越满、注意力丢掉多少，我不知道有什么干净的衡量办法。这一章的建议来自平台厂商和我自己的设计，不是我做过的测试。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

只要窗口有大小，模型每一轮都要读它，这套道理就在。可能会去掉的，是我自己的功夫：手动给规则分层，手动开新对话。如果平台能按相关性把规则加载好，压缩时又不丢重要的内容，我就不再手动做了。窗口再大，也不会自动消除第二个上限。我要先看到这方面的测试。
