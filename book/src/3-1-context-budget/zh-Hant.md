讀這一章，請先讀過 [agent 循環，和你能插手的地方](2-1-agent-loop.html)，或至少知道 agent 讀文字、再用文字回答。

## 一句話 {#in-one-sentence}

規則、知識、檔案和工具結果共用同一個視窗，每一樣都會擠掉別的。所以要把上下文當預算來管：需要時再去取，不要一次全部載入。

## 給主管 {#for-leaders}

- **要做的決定**：把 agent 讀的東西當預算，決定什麼東西一直載入，什麼東西只在任務需要時才去取。
- **風險**：所有東西共用一個視窗，而視窗還有空位，並不代表表現就好。埋在又長又雜的上下文裡的規則，更容易被漏掉。漏掉的程度我沒有數字。這些建議來自平台廠商和我自己的設計，不是我做的測試。
- **做對的成本**：主要是設定的時間，花在把規則分層、縮短工具輸出、讓任何索引保持正確上。載入太少也有代價，因為那樣 agent 就只能用猜的。
- **可以問團隊**：「每一輪都載入了什麼？其中有多少和眼前的任務有關？」

## 資訊給得越多，答案為什麼反而可能越差？ {#problem}

AI 回答得不好時，最常聽到的建議是「給它更多資訊」。於是你貼上整份風格指南，加上每一條規則，再讓它把所有檔案都讀一遍。這樣感覺很安全，畢竟事實越多，錯誤照理說就越少。

結果卻常常相反。不妨想想一張書桌。你當然可以把一個專案的所有文件都攤在上面，可是這樣一來，要用的那一份反而找不到，也沒有地方寫字了。agent 也有這麼一張書桌，叫做**上下文視窗**，也就是模型在一輪裡能看到的全部文字。桌上有規則，也有你說的話、agent 讀過的檔案、工具呼叫的結果，還有它自己之前的回答。這張桌子有大小的上限。而且我接下來會說，它還有第二個限制，跟大小無關。

這一章我沒有做過乾淨的實驗，所以我能說的，來自另外兩個地方。一個是做這些工具的人。Anthropic 寫道，上下文「必須被當成一種有限的資源，邊際報酬會遞減」（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)），VS Code 的指南也說要「避免上下文過載而分散注意力」（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）。另一個是我自己搭設定的方式，裡面幾乎每個設計選擇，都是在想辦法讓視窗裡少放一點。從成本來看也是同一個方向：一個任務的成本，大部分花在模型讀的東西上（[選模型，別只看 token 單價](1-1-models-and-cost.html)）。不過在談第二個限制之前，我們先看看視窗裡到底裝了什麼。

## 視窗裡裝了什麼，怎麼少裝一點 {#how-it-works}

### 視窗裡有什麼

::: figure 3-1-window

共用這個視窗的有六樣東西：

1. 規則和指令，平台每次都會放進去。
2. 工具清單，附上每個工具的描述。模型要靠它才知道自己可以請求什麼；工具一多，例如來自好幾個 MCP server，這份清單可能佔掉視窗的一大塊，Anthropic 舉的例子是 58 個工具約 55K token。Claude Code 和 VS Code（Claude Sonnet 4.5、Opus 4.5 以上）的工具搜尋，只在用到時才載入完整定義（[接 MCP server 之前，要想清楚什麼？](1-3-mcp.html)）。
3. 你的訊息。
4. agent 讀過的檔案。檔案是整份文字放進去的，不管其中有多少是相關的。
5. 工具結果，例如搜尋的清單、指令的輸出、測試紀錄。它們常常是最大的一塊，也是沒人看的一塊。
6. agent 自己之前的回答。

迴圈每轉一輪，視窗裡就多一個結果，卻不會少掉任何東西。每一輪，模型還要把這六樣東西從頭重讀一遍（這筆成本在[選模型，別只看 token 單價](1-1-models-and-cost.html)裡）。所以視窗只會越來越滿，直到滿了為止。到那時，平台只能裁掉或摘要最舊的部分，細節也就丟了。[長對話會變差](3-2-long-sessions.html)講的就是這件事。

### 是兩個限制，不是一個

那換一個更大的視窗不就好了？問題是，放不下只是誰都看得到的那個限制。第二個限制是注意力，Anthropic 把它描述成一份「注意力預算」，模型讀大量文字時就會消耗它。落到實際，意思是視窗還有空位，不等於表現就好。同一條規則，埋在又長又雜的上下文裡，比放在短上下文裡更容易被漏掉。

我拿這一點當理由：就算全都放得下，也要少放一點。不過這一步是我自己的推論，不是 Anthropic 說的。影響有多大，要看模型和任務。

### 全部載入、載入索引，或兩者都用

既然放得下也該少放，問題就變成了：該把什麼留在外面？這一部分大多數的決定，背後都是這個選擇。

最簡單的回答是什麼都不留在外面。agent 一開始，視窗裡就有所有規則和所有筆記，它什麼都不必查。麻煩在於，工作還沒開始，視窗就已經花掉了，而且大半花在這個任務用不到的東西上。

另一頭的回答，是只載入一份索引，需要什麼再去取。agent 一開始只有一份簡短的清單，列出現有每樣東西的名稱和一行描述，等任務需要其中一樣，它才打開那一樣。Anthropic 把這叫做「即時」做法：agent 只留輕量的標記（檔案路徑、名稱），到執行時才載入資料。這和圖書館是一樣的道理：沒有人會把整座圖書館搬到書桌上，我們都是先查目錄，再去取那一本。

在這兩頭之間，Anthropic 自己的建議是兩者混合。用他們的話說，「最有效的 agent 也許會採用混合策略，先取一部分資料求速度」，其餘的再讓它自己去探索。他們舉的例子是 Claude Code：它先把自己的指令檔放進上下文，其餘的在過程中用搜尋工具去找。

全部載入在有些情況下還是比較好。任務小、或規則少的時候，全部載入比較簡單，成本也低。而在漏掉一個事實代價很高的地方，我寧可花錢把它放在視窗裡，也不賭 agent 會打開對的檔案。

成本上，全部載入還多一個好處。每次都載入、又從不變的開頭，是可以快取的，而讀快取比一般的讀便宜很多（[選模型，別只看 token 單價](1-1-models-and-cost.html)）。所以只要開頭保持穩定，「全部載入」其實比 token 數看起來便宜。不過，我沒有在 Copilot 上測過快取。而且就算用上快取，上面說的注意力限制也還在那裡。

::: figure 3-1-load-when

不管怎麼搭配，索引這一部分要行得通，都得滿足三件事。第一，索引的條目得說明什麼時候該打開它，因為 agent 只憑那一行就做決定。寫得含糊，agent 就會打開錯的東西，或是永遠不打開對的，這就是為什麼 skill 的描述這麼重要（[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)）。第二，取用得便宜而且精確。如果取用要讀整個資料夾，索引就什麼也沒省。第三，agent 得知道自己不知道，因為 agent 自己沒意識到缺了的東西，索引是幫不上忙的。這才是真正的風險，下面我會再回來談。

### 少讀一點的辦法

索引只是讓視窗保持小的辦法之一。下面這些是我在用的，每一個要麼讓某樣東西不進視窗，要麼把它拿出來。如果想找個地方開始，最便宜的兩個是把規則分層和縮短工具輸出。

- **規則分層**。一小組規則一直載入，其餘的放在只有碰到相關檔案或工作時才讀的地方。不會改變下一步的規則，只是雜訊。（做法：[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。）
- **先搜尋，再讀**。請 agent 先找出東西在哪，然後只讀檔案中那一部分，不讀整個檔案。或者給它一份事先寫好的專案簡短地圖，也就是上面說的那種索引。只有讀地圖比搜尋划算時，它才贏；也只有有人讓它保持正確，它才一直是對的。我沒有測過我的地圖是不是划算（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。
- **讓工具輸出變短**。一個印出 2,000 行的指令，就會把 2,000 行放進視窗，所以要把它過濾一下，或只印失敗的部分。
- **用幾行來提醒，不用一整頁**。在我的設定裡，每個 prompt 只加上規則的一小段；有任務時（[管任務，不管對話](5-1-tasks.html)），這段提醒還會說任務做到哪了。這只是提醒，完整的內容要到需要時才讀。
- **把大量閱讀交給子 agent**（[慎用子 agent](2-3-subagents.html)、[長對話會變差](3-2-long-sessions.html)）。
- **把狀態寫進檔案**，這樣新的對話讀一個簡短的檔案就好，不用讀舊的對話。新的對話就是空的視窗，至於什麼時候開一個、帶什麼過去，見[長對話會變差](3-2-long-sessions.html)。

### 三個問題和一個測試

你自己的設定，視窗是怎麼花掉的？可以先問三個問題：

1. 每次都載入了什麼？數一數你一直開著的規則有幾行，再看其中有多少和你現在做的任務有關。（在 Claude Code 裡，`/context` 指令會顯示什麼在佔用視窗。Copilot 有什麼，我沒查過。）
2. agent 上一次讀的最大一樣東西是什麼？是一個檔案還是一份紀錄，全部都需要嗎？
3. 如果 agent 現在開一個新的對話，它得讀什麼才能接著做？那些在檔案裡嗎？

還有一個今天就能跑的測試。挑一個你知道答案的任務，各開一個新對話，跑兩遍。第一遍，把整個檔案或文件貼在 prompt 裡；第二遍，只說出檔案和那一部分，讓 agent 只讀那裡。每一遍都記下四樣：答案對不對、時間、你的工具顯示的用量，以及 agent 漏掉了什麼。想讓差別可信，每種做法多跑幾次，兩邊用同樣的方式打分。最後再比較兩種做法的答案、時間和用量。

## 少裝要付出什麼 {#costs-and-traps}

少往視窗裡放，第一個代價，就是前面說要回來談的那個風險：載入得少，可能丟掉 agent 需要的東西。索引其實是一場賭注，賭 agent 會打開對的東西。agent 要是沒打開，就只能憑猜測做事。補救的辦法是把描述寫得更好，再檢查該打開的時候到底有沒有打開。檢查的方法是跑一個你知道需要某個檔案的任務，看工具紀錄裡打開了哪些，數它沒打開的次數。新的對話、規則或 skill 也可能這樣丟掉，因為它們同樣要靠 agent 在對的時候讀到對的東西。

同樣的風險也出在摘要上。子 agent 的報告和平台的壓縮，都會把文字縮短，也都可能丟掉最要緊的那一行，所以只用在簡短的版本就夠的地方。

索引還得一直保持正確。過期的地圖花的比省的多，因為 agent 會相信它。[讓知識庫一直是對的](8-5-kb-keep-true.html)講的就是這個。

開頭說過，這一章背後沒有數字。對於 Copilot 的模型，視窗填滿時失去多少注意力，我不知道有任何乾淨的量法。

## 平台廠商也這麼看嗎？ {#industry}
{status: industry}

這兩家廠商在開頭都引過，這裡把兩家的說法放在一起看。Anthropic 說，上下文是「有限的資源，邊際報酬遞減」，agent 可以靠帶著輕量的參照，「即時」地載入資料（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。VS Code 的指南則說：「從簡短的上下文開始，只在需要時才擴充。」（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）

可見兩家在方向上是一致的。不過，該載入多少，兩家都沒有給出我能引用的數字。這就留下一個實際的問題：這一章裡的手動作業還要做多久？

## 什麼時候可以刪掉這些手動作業 {#when-to-delete-it}
{status: industry}

只要視窗有大小、模型每一輪都要讀它，這套道理本身就還在。可能會消失的，是我自己花的力氣，也就是手動把規則分層、手動開新對話。如果平台能按相關性把規則載入得很好，壓縮時又不丟掉要緊的東西，我就不再手動做這些。但視窗再大，本身也不會讓第二個限制消失，所以在指望大視窗之前，我會想先看到這方面的測試。

## 在你自己的環境試試 {#try-it}

::: prompt
看一下這個專案用來測試、lint、建置和搜尋的指令。每一個，告訴我它成功時和失敗時大約印出多少文字，以及你執行它時，輸出會不會灌爆你的上下文視窗。為每一個提出比較安靜的跑法，例如只印失敗的部分或一份摘要。把最吵的三個排出來。不要改任何檔案，也不要執行任何會改變狀態的東西。
