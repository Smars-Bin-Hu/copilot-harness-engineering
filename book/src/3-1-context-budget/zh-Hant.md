讀這一章，請先讀過 [agent 循環，和你能插手的地方](2-1-agent-loop.html)，或至少知道 agent 讀文字、再用文字回答。

## 一句話 {#in-one-sentence}

規則、知識、檔案和工具結果共用同一個視窗，每一樣都會擠掉別的。所以要把上下文當預算來管：需要時再去取，不要一次全部載入。

## 給主管 {#for-leaders}

- **要做的決定**：把 agent 讀的東西當預算。決定什麼東西一直載入，什麼東西只在任務需要時才去取。
- **風險**：所有東西共用一個視窗，而且還有空位的視窗不等於表現好的視窗，所以埋在又長又雜的上下文裡的規則，更容易被漏掉。漏掉的程度我沒有數字；這些建議來自平台廠商和我自己的設計，不是我做的測試。
- **做對的成本**：主要是設定的時間：把規則分層、縮短工具輸出、讓任何索引保持正確。載入太少也有代價：agent 會猜。
- **可以問團隊**：「每一輪都載入了什麼？其中有多少和眼前的任務有關？」

## 問題 {#problem}

回答不好時，常見的建議是「給 AI 更多資訊」。貼上整份風格指南。加上每一條規則。讓它讀所有檔案。這感覺很安全：事實越多，錯誤越少。

結果常常相反。想想一張書桌。你可以把一個專案的所有文件都攤開，然後你找不到要的那一份，也沒有地方寫字。agent 就有這樣一張書桌。它叫**上下文視窗**：模型在一輪裡能看到的全部文字。裡面有規則、你說的話、agent 讀過的檔案、工具呼叫的結果，還有它自己之前的回答。它有大小的上限。而且，我接下來會說，它還有第二個限制，跟大小無關。

我能說的，來自兩個地方。第一個是做這些工具的人。Anthropic 寫道，上下文「必須被當成一種有限的資源，邊際報酬會遞減」（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。VS Code 的指南說要「避免上下文過載而分散注意力」（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）。第二個是我自己搭設定的方式：裡面幾乎每個設計選擇，都是一種讓視窗裡少放一點的辦法。同一個想法在成本上的一面，在[選模型：算的是每次成功的成本](1-1-models-and-cost.html)：一個任務的成本，大部分是模型讀的東西。我沒有為這一章做過乾淨的實驗。

## 原理 {#how-it-works}

### 視窗裡有什麼

::: figure 3-1-window

有六樣東西共用它：

1. **規則和指令**，平台每次都會放進去。
2. **工具清單**，附上每個工具的描述。模型要靠它知道自己可以請求什麼。工具很多時，例如來自好幾個 MCP server（[MCP server：插工具的標準接口](1-3-mcp.html)），這份清單可能佔視窗的一大塊。有多大，我沒量過。
3. **你的訊息**。
4. **agent 讀過的檔案**。檔案是整份文字放進去的，不管其中有多少是相關的。
5. **工具結果**：搜尋的清單、指令的輸出、測試紀錄。它們常常是最大的一塊，也是沒人看的一塊。
6. **agent 自己之前的回答**。

迴圈每一輪，模型都會把這一切重讀一遍，再加上多出來的一個結果（這的成本在[選模型：算的是每次成功的成本](1-1-models-and-cost.html)）。所以視窗只會越來越大，直到滿了。然後平台只能裁掉或摘要最舊的部分，細節就丟了。[長對話會變差](3-2-long-sessions.html)講的就是這個。

### 是兩個限制，不是一個

大小是明顯的限制。第二個是注意力。Anthropic 把它描述成模型在讀大量文字時消耗的一份「注意力預算」。實際的意思是：還有空位的視窗，不等於表現好的視窗。埋在又長又雜的上下文裡的規則，比在短上下文裡的同一條規則，更容易被漏掉。我拿這個當理由：就算全都放得下，也要少放一點。這一步是我自己的推論，不是 Anthropic 說的。影響有多大，取決於模型和任務，我沒有量過。

### 全部載入、載入索引，或兩者都用

這是這一部分大多數決定背後的選擇。

**先全部載入**。agent 一開始，視窗裡就有所有規則和所有筆記。它不需要查任何東西。但是工作還沒開始，視窗就花掉了，而且大部分花在這個任務用不到的東西上。

**載入索引，需要什麼再去取**。agent 一開始只有一份簡短的清單：現有的每樣東西的名稱和一行描述。任務需要其中一樣時，它才打開那一樣。Anthropic 把這叫做「即時」做法：agent 帶著輕量的識別（檔案路徑、名稱），到執行時才載入資料。

**兩者都用**。Anthropic 自己的建議是混合：「最有效的 agent 也許會採用混合策略，先取一部分資料求速度」，然後讓它自己繼續探索。他們的例子是 Claude Code：先把它的指令檔放進上下文，其餘的在過程中用搜尋工具去找。

有些情況是另一邊贏。任務小、或規則少時，全部載入比較簡單，成本也低。而漏掉一個事實代價很高的地方，我寧可花錢把它放在視窗裡，也不賭 agent 會打開對的檔案。

再說一點成本。每次都載入、又從不變的開頭，可以被快取，而讀快取比一般的讀便宜很多（[選模型：算的是每次成功的成本](1-1-models-and-cost.html)）。所以只要開頭保持穩定，「全部載入」會比 token 數看起來便宜。上面說的注意力限制，不會因為快取而消失。我沒有在 Copilot 上測過快取。

::: figure 3-1-load-when

這和圖書館一樣。你不會把整座圖書館搬到書桌上。你用目錄，然後取那一本書。

要讓這個做法行得通，三件事必須成立。

- **索引的條目必須說明什麼時候該打開它**。agent 只憑那一行就做決定。含糊的一行，會讓它打開錯的東西，或是永遠不打開對的。這就是 skill 的描述為什麼這麼重要（[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)）。
- **取用必須便宜而且精確**。取用如果要讀整個資料夾，索引就什麼也沒省。
- **agent 必須知道自己不知道**。對於 agent 沒意識到缺了的東西，索引幫不上忙。這才是真正的風險，下面再談。

### 少讀一點的辦法

這些是我在用的。每一個都是讓某樣東西不進視窗，或把它拿出來的辦法。最便宜、最適合先做的兩個，是把規則分層，和縮短工具輸出。

- **規則分層**。一小組規則一直載入。其餘的放在只有讀到對應的檔案或工作時才會讀的地方。不會改變下一步的規則，只是雜訊。（做法：[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。）
- **先搜尋，再讀**。請 agent 先找出東西在哪，然後只讀檔案中那一部分，不讀整個檔案。或者給它一份事先寫好的專案簡短地圖：就是上面說的那種索引。只有讀地圖比搜尋划算時，它才贏；也只有有人讓它保持正確，它才一直是對的。我沒有測過我的地圖是不是划算（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。
- **讓工具輸出變短**。印出 2,000 行的指令，就把 2,000 行放進視窗。把它過濾掉，或只印失敗的部分。
- **用幾行來提醒，不用一整頁**。在我的設定裡，每個 prompt 只加上規則的一小段。有任務時（[管任務，不管對話](5-1-tasks.html)），它說的是任務做到哪了。這只是提醒，完整的內容在需要時才讀。
- **把大量閱讀交給子 agent**（[慎用子 agent](2-3-subagents.html)、[長對話會變差](3-2-long-sessions.html)）。
- **把狀態寫進檔案**，這樣新的對話讀一個簡短的檔案就好，不用讀舊的對話。新的對話就是空的視窗；什麼時候開一個、帶什麼過去，在[長對話會變差](3-2-long-sessions.html)。

### 測一測你自己的設定

**三個問題**：

1. 每次都載入了什麼？數一數你一直開著的規則有幾行。其中有多少和你現在做的任務有關？（在 Claude Code 裡，`/context` 指令會顯示什麼在佔用視窗。Copilot 有什麼，我沒查過。）
2. agent 上一次讀的最大一樣東西是什麼？一個檔案？一份紀錄？全部都需要嗎？
3. 如果 agent 現在開一個新的對話，它得讀什麼才能接著做？那些在檔案裡嗎？

**今天就能跑的測試**。挑一個你知道答案的任務。各開一個新對話，跑兩遍。第一遍，把整個檔案或文件貼在 prompt 裡。第二遍，只說出檔案和那一部分，讓 agent 只讀那裡。比較答案、時間和用量。要相信這個差別，就各重複幾次，兩邊用同樣的方式打分。每次記下四樣：答案對不對、時間、你的工具顯示的用量，以及 agent 漏掉了什麼。

## 代價和陷阱 {#costs-and-traps}

**載入得少，可能丟掉 agent 需要的東西**。索引是一場賭注：賭 agent 會打開對的東西。它沒打開，就只能憑猜測做事。補救是更好的描述，以及一個確認該打開時有沒有打開的檢查。要檢查，就跑一個你知道需要某個檔案的任務，看工具紀錄裡打開了哪些，數它沒打開的次數。新的對話、規則或 skill，丟失的方式也一樣。

**摘要會丟細節**。子 agent 的報告和平台的壓縮，都會把文字縮短，也都可能丟掉最要緊的那一行。用在簡短的版本就夠的地方。

**索引必須保持正確**。過期的地圖，花的比省的多，因為 agent 會相信它。[讓知識庫一直是對的](8-5-kb-keep-true.html)講的就是這個。

**這裡沒有數字**。對於 Copilot 的模型，視窗填滿時失去多少注意力，我不知道有任何乾淨的量法。這一章的建議來自平台廠商和我自己的設計，不是我做的測試。

## 業界怎麼說 {#industry}
{status: industry}

- **Anthropic**：上下文是「有限的資源，邊際報酬遞減」，agent 可以靠帶著輕量的參照，「即時」地載入資料。（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）
- **VS Code**：「從簡短的上下文開始，只在需要時才擴充。」（[Context engineering guide](https://code.visualstudio.com/docs/copilot/guides/context-engineering-guide)）

兩家在方向上一致。兩家都沒有給我能引用的數字，說明該載入多少。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

只要視窗有大小、模型每一輪都要讀它，這套道理就還在。可能會消失的，是我自己花的力氣：手動把規則分層、手動開新對話。如果平台能按相關性把規則載入得很好，壓縮時又不丟掉要緊的東西，我就不再手動做這些。很大的視窗本身，不會讓第二個限制消失。我會想先看到這方面的測試。
