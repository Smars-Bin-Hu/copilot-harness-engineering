这个附录是给出问题那天用的。先找到你的症状，做第一项检查，再去读它指向的那一章。这里的内容都来自各章和 harness 的文档，所以每条建议我都能指出出处，但这份附录不是一份完整的原因清单。

## 怎么用 {#how-to-use}

有两条规则，几乎每个症状都用得上。

- **看实际发生了什么，不要看 agent 说了什么**。agent 讲自己做了什么，可能讲错，日志却是可以核对的（[别信 Agent 的总结，看日志](6-1-observe.html)）。
- **一次只改一样，然后把同一个任务再跑一遍**。不然你分不清是哪个改动起了作用（[改了配置，怎么知道是不是变好了？](6-3-eval-tasks.html)）。

按你看到的现象找症状：

- 规则没被遵守：[被无视](#rule-ignored)、[长对话里被丢掉](#rule-drift)。
- skill 没被用上：[从来没用过](#skill-not-loaded)。
- hook 不吭声，或者太严：[没触发](#hook-silent)、[拒绝了正常的工作](#false-refusal)。
- agent 停不下来，或者停得不对：[原地打转](#agent-loops)、[太早说做完了](#done-too-early)。
- 账单太高：[账单](#bill)。
- 你分不清发生了什么：[没有记录](#cannot-tell)。

## 规则和指令 {#rules}

### agent 无视一条规则 {#rule-ignored}

**先查什么**。这条规则真的加载了吗？要弄清楚，就开一个新对话，问一个只有你的规则才答得出的问题（[30 分钟搭一个最小 harness](0-2-minimal-harness.html)）。如果加载了，就按顺序把常见原因过一遍：文件太长，两条规则冲突，规则离它适用的地方太远，没有给理由，或者它只是个请求。这条规则要是必须成立，就把它挪进代码里。

**章节**。[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)，“4. 写下来的规则为什么会被无视”一节，然后是[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)。

### 规则文件很长，而且越来越差 {#rules-rot}

**先查什么**。对每一行都问一句：没有它，agent 会不会做错？通不过的行删掉，再跑同一个任务，看有没有变差。另外，每条规则只放在一个地方。

**章节**。[30 分钟搭一个最小 harness](0-2-minimal-harness.html)的“这套入门配置会在哪里出问题”，以及[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)。

### 规则在短对话里遵守，在长对话里被丢掉 {#rule-drift}

**先查什么**。看看这条规则现在离手头的活有多远。写在第一条消息里的规则，干了几个小时之后就离得很远了，所以要让它离得近一些：按文件加载，或者让 hook 重复其中几行。还有个便宜的测试：干了一个小时以后，让 agent 把这条规则复述一遍。

**章节**。[对话越久，Agent 越笨](3-2-long-sessions.html)和[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)。

## Skill {#skills}

### skill 从来没被用上 {#skill-not-loaded}

**先查什么**。开一个新对话，因为旧对话里可能已经装着这个 skill，然后用一个人平常会说的话去问，不要输入 skill 的名字。接着看加载了哪些 skill，平台有日志的话就看日志。没加载，说明描述里缺了用户的说法。如果你的 skill 很多，也可能是旁边的某一个抢走了请求，所以每个 skill 都要保持狭窄，并写明它不管什么。

**章节**。[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)的“三个问题，三个测试”，以及[30 分钟搭一个最小 harness](0-2-minimal-harness.html)（第 2 步）。

### skill 不该加载的时候加载了 {#skill-too-wide}

**先查什么**。描述太宽了。把它收窄，再把那些不该触发它的相邻请求写成测试用例。

**章节**。[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)。

### skill 加载了，但什么都没变 {#skill-no-effect}

**先查什么**。在新对话里把同一个任务跑两遍，一遍带 skill，一遍不带。看不出差别的话，就删掉那些没起作用的行，因为 agent 本来就知道它们。然后再看看这个 skill 是不是已经过时了。

**章节**。[规则写太多，Agent 反而记不住](3-3-instructions-and-skills.html)和[怎么写一个真正好用的 skill？](3-4-skills-and-workflows.html)。

## Hook 和拒绝 {#hooks}

### hook 没触发 {#hook-silent}

**先查什么**。有四件事会让 hook 不吭声，都是我在 2026 年 10 月发现的，以后会变。

- hook 文件在窗口启动时读取，所以改完之后要重新加载窗口。
- 我用 Copilot 的命令行模式时，hook 没有运行。
- 组织的策略可以对某个工作区关闭 hook。
- 一个看起来像关闭开关的设置，在较新的会话里可能拦不住它们。

这几点排除之后，再用你的平台允许的最小的 hook 来测，比如只把事件名追加到一个文件里的那种。

**章节**。[硬性规则放在哪？用 hook](2-2-hooks.html)的“hook 看不到什么”和“三个问题和一个小测试”。

### hook 触发了，但模型没收到消息 {#hook-lost-message}

**先查什么**。要看模型实际收到了什么，而不是 hook 返回了什么。我就遇到过：有些 prompt 到达时没带上规则，因为平台自己的提醒占了 hook 用的那个位置（数字在下面那一章里）。

**章节**。[硬性规则放在哪？用 hook](2-2-hooks.html)，开头的那个故事。

### 我改了 hook 之后，所有工具都被拒绝 {#hook-wont-start}

**先查什么**。hook 程序要是启动不了（比如找不到解释器），Copilot 会把它当作拒绝，于是任何工具都跑不了。屏幕上只会说 hook 出错了。想看到真正的错误，就在终端里手动运行一遍 hook 的命令。

**章节**。[30 分钟搭一个最小 harness](0-2-minimal-harness.html)和[硬性规则放在哪？用 hook](2-2-hooks.html)的“hook 出问题的三种方式”。

### 本该拦住一次调用的 hook，悄悄放它过去了 {#hook-timeout}

**先查什么**。看 hook 跑了多久。超出时限的 hook 会被当作通过，而且没有任何提示。量一量你的 hook 要跑多久，让它保持轻量。

**章节**。[硬性规则放在哪？用 hook](2-2-hooks.html)和[hook 自己出故障了怎么办？](4-4-enforcement-design.html)，后者讲的是事先决定一次失败是拦截还是放行。

### agent 一直重试同一件被拒绝的事 {#refusal-loop}

**先查什么**。读一读拒绝的理由。理由里只写“已拒绝”，agent 就会重试，或者去试更糟的办法，所以要把理由改成说明为什么、该改做什么。但不要解释怎么绕开这条规则。

**章节**。[硬性规则放在哪？用 hook](2-2-hooks.html)（理由是设计的一部分）和[“先问我”为什么挡不住 Agent？](4-2-ask-vs-refuse.html)。

### 一次拒绝挡住了正常的工作 {#false-refusal}

**先查什么**。匹配模式太宽了。agent 没法和拒绝争辩，所以一次误拒就是一个卡住的任务。把匹配模式收窄，留一条路让人批准那些不该拒绝的事，再读日志，看是哪条规则触发的。

**章节**。[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)和[“先问我”为什么挡不住 Agent？](4-2-ask-vs-refuse.html)。

### agent 绕过了一条规则，或者改了规则文件 {#rule-bypassed}

**先查什么**。这条规则是在 prompt 里，还是在 hook 里？如果在 hook 里，hook 看到的是调用的文字，还是调用的效果？hook 拦得住常见的写法，拦不住一心要绕开它的 agent。还要检查存放规则的文件和 hook 是否在受保护的名单上。至于那些绝不能碰的东西，干脆不要交给 agent。

**章节**。[别让 Agent 改自己的规则](4-3-guardrails.html)和[不要开放全部的权限或使用沙箱](4-5-least-privilege.html)。

### agent 替自己批准了某件事 {#self-approval}

**先查什么**。测一下：让 agent 去运行审批命令，确认它会被拒绝。拒绝这条命令的 hook 一旦被删、被改或者出错，一个能运行命令的 agent 就可能替自己批准。

**章节**。[哪些事必须由人来批？](5-3-two-approvals.html)。

## 循环、停止和成本 {#loops}

### agent 原地打转 {#agent-loops}

**先查什么**。agent 之外，有没有东西在判断它是不是卡住了？应该有，因为卡住的 agent 自己恰恰最不适合做这个判断。把停止规则放进代码，让它根据事实来判断：轮数和时间的上限，拒绝次数的上限，几轮下来没有进展，计划变了，检查次数用完。还要看看它是不是一直在试护栏拦着的事。

**章节**。[让 Agent 自己跑一晚上，怎么让它该停就停？](5-7-when-to-stop.html)。

### 运行停下了，人却不知道为什么 {#stop-vague}

**先查什么**。停下的时候，有没有用一句话交回为什么停、停在哪、人要决定什么？光说一句“遇到了问题”是不够的。

**章节**。[让 Agent 自己跑一晚上，怎么让它该停就停？](5-7-when-to-stop.html)的“回来的人该看到什么”。

### agent 说“做完了”，测试却失败 {#done-too-early}

**先查什么**。它跑过检查吗，给出命令和输出了吗？一句“所有测试都通过”，本身说明不了什么。所以要让它能在自己的循环里运行检查，并让这次运行以事实结束（步骤打了勾，一次计数的检查通过了），而不是以 agent 的话结束。

**章节**。[让 Agent 自己跑测试](5-4-self-checks.html)和[让 Agent 自己跑一晚上，怎么让它该停就停？](5-7-when-to-stop.html)的“‘做完了’说得太早”。

### 子 agent 的用量对不上 {#subagent-usage}

**先查什么**。工具往往只显示主对话的用量。看看你的工具有没有把子 agent 也算进去。还要记住，每个子 agent 都从空白的上下文开始、从零读起，所以几个子 agent 的成本就是单个的好几倍。也正因为这样，光限制能开几个，并不等于有了预算。

**章节**。[别跟风瞎用子 Agent](2-3-subagents.html)的“多花的钱换来了什么，拆分还有哪些代价”，以及[让 Agent 自己跑一晚上，怎么让它该停就停？](5-7-when-to-stop.html)的“预算是总量，不是次数”一节。

### 账单比预想的高 {#bill}

**先查什么**。先看 agent 读了什么。每一轮都会把整个上下文重读一遍，所以读了什么，比模型多聪明更要紧。先看工具返回的结果和加载的规则，再看任务被重做的频率。削减的时候要停在任务开始失败、被整个扔掉之前。看用量要看一整次运行，不要只看一条消息。缓存的上下文按较低的价格计费（Anthropic 文档：约为基础价格的十分之一），不过这一点我没有在 Copilot 上验证过，所以请看你自己的套餐显示什么。

**章节**。[选模型，别只看 token 单价](1-1-models-and-cost.html)、[Agent 到底是怎么干活的？](2-1-agent-loop.html)和[为什么不能把所有规则都塞给 Agent？](3-1-context-budget.html)。

## 检查 {#checks}

### 检查一直通不过 {#checks-never-pass}

**先查什么**。读一读发现的问题，可能是下面几种情况。一种是每一轮都冒出新问题，说明这个循环没有尽头，这时要设一个上限，让人来决定延长还是豁免。也可能发现的问题没有指向真实的文件和行号，那就是噪音。还可能结论本身是错的，一次误报的 FAIL 会让作者去修一个不存在的问题。最后，如果改动不断抵消之前的通过，可能是这份工作的指纹包含的东西太多，比如进度笔记。

**章节**。[Agent 说“测过了”，能信吗？](5-5-counted-checks.html)和[让另一个模型来审，靠得住吗？](5-6-model-checks-model.html)。

### 检查开着，却什么都没检查 {#checks-silent}

**先查什么**。agent 可能压根没调用过检查者，那样就永远不会记下 FAIL。prompt 里的规则抓不住这种情况。要把检查放在 agent 必须经过的地方，比如它想停下的那一刻。

**章节**。[Agent 说“测过了”，能信吗？](5-5-counted-checks.html)的“检查开着，却什么都没检查”。

### 一个测试有时过、有时不过 {#flaky}

**先查什么**。随机失败的测试，会让 agent 去找一个不存在的 bug，或者教会它反复重跑，直到变绿为止。要么修好它，要么去掉它。如果完整的测试集太慢，就给 agent 一个能经常跑的快速子集。

**章节**。[让 Agent 自己跑测试](5-4-self-checks.html)。

### 同一个任务跑两次，结果不同 {#variance}

**先查什么**。这很正常。把任务多跑几次，看看波动有多大，再读那些失败的运行。一次运行证明不了什么。不正常的，是波动大到没有哪个结果可信。遇到这种情况，说明任务太松，或者检查太弱，应该先把这个修好。

**章节**。[同一个任务跑两次，结果不一样](6-4-variance.html)。

## 上下文和记忆 {#context}

### 长对话变差了 {#long-chat}

**先查什么**。别指望模型记得住。把要紧的写进文件，再从这个文件开一个新对话。想知道写够了没有，就问问自己：如果这个对话现在消失，会丢掉什么？如果对话变长是因为任务太大，解法是把任务变小。

**章节**。[对话越久，Agent 越笨](3-2-long-sessions.html)。

### 笔记或记忆文件里写了不实的内容 {#notes-wrong}

**先查什么**。把笔记当作 agent 的报告，要紧的几条对照源头核对一遍。笔记要短，做完的就删掉，因为不断变长的笔记文件会把窗口填满。agent 写的记忆应当带上来源和日期，并由人来审查。

**章节**。[对话越久，Agent 越笨](3-2-long-sessions.html)和[让 Agent 记住经验，怎么防它记错？](3-5-memory.html)。

### agent 听从了它在文件或网页里读到的文字 {#injection}

**先查什么**。数一数风险的那三个圈，也就是下面三个问题：它能读私有数据吗？它读不可信的文本吗？它能把数据发出去吗？三个里去掉任意一个。要记住，不可信文本的摘要也是不可信的。每加一个工具，都要重新检查一遍。

**章节**。[Agent 读到的网页和文件，可能在给它下命令](4-6-untrusted-input.html)和[接 MCP server 之前，要想清楚什么？](1-3-mcp.html)。

## 看清发生了什么 {#seeing}

### 我分不清 agent 做了什么 {#cannot-tell}

**先查什么**。有没有一份由代码写下的记录，涵盖每次调用和每次拒绝？有的话，就去读失败那次运行的轨迹，不要读 agent 的总结。即便如此，hook 也只能看到平台给它看的东西，所以干净的日志里仍然可能有个洞。

**章节**。[别信 Agent 的总结，看日志](6-1-observe.html)和[Agent 干完活，你该看什么？](6-2-task-report.html)。

### 换了新模型，反而更糟 {#model-upgrade}

**先查什么**。升级并不是在每个任务上都更好，所以先把你的固定任务重跑一遍。然后一次删一条旧规则或旧步骤，每删一次都跑一遍评测。

**章节**。[换了新模型，旧规则该删了](6-5-model-upgrades.html)。
