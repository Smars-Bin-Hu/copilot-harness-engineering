这个附录是给出问题那天用的。先找到你的症状，做第一项检查，再去读对应的章节。这里的一切都来自各章和 harness 的文档。这是我能指出出处的建议，不是完整的原因清单。

## 怎么用 {#how-to-use}

两条规则，几乎适用于每个症状。

- **看实际发生了什么，不要看 agent 说了什么。** agent 对自己工作的讲述可能是错的；日志是可以核对的（[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)）。
- **一次只改一样，然后把同一个任务再跑一遍。** 否则你分不清是哪个改动起了作用（[固定的任务，用脚本打分](6-3-eval-tasks.html)）。

按你看到的现象找症状：

- 规则没被遵守：[被无视](#rule-ignored)、[长对话里被丢掉](#rule-drift)。
- skill 没被用上：[从来没用过](#skill-not-loaded)。
- hook 不吭声，或者太严：[没触发](#hook-silent)、[拒绝了正常的工作](#false-refusal)。
- agent 停不下来，或者停得不对：[原地打转](#agent-loops)、[太早说做完了](#done-too-early)。
- 账单太高：[账单](#bill)。
- 你分不清发生了什么：[没有记录](#cannot-tell)。

## 规则和指令 {#rules}

### agent 无视一条规则 {#rule-ignored}

**先查什么。** 这条规则真的加载了吗？开一个新对话，问一个只有你的规则才答得出的问题（[30 分钟搭一个最小 harness](0-2-minimal-harness.html)）。如果加载了，就按顺序过一遍常见原因：文件太长，两条规则冲突，规则离它适用的地方太远，没有给理由，或者它只是个请求。如果这条规则必须成立，就把它挪进代码里。

**章节。** [指令与 skill：只加载需要的](3-3-instructions-and-skills.html)，“4. 写下来的规则为什么会被无视”一节，然后是[提示里的规则只是请求](4-1-requests-and-rules.html)。

### 规则文件很长，而且越来越差 {#rules-rot}

**先查什么。** 对每一行都问一句：没有它，agent 会不会做错？删掉通不过的行，然后跑同一个任务，看有没有变差。每条规则只放一个地方。

**章节。** [30 分钟搭一个最小 harness](0-2-minimal-harness.html)（代价和坑）和[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)。

### 规则在短对话里遵守，在长对话里被丢掉 {#rule-drift}

**先查什么。** 距离。写在第一条消息里的规则，干了几个小时之后就离得很远了。让它离得更近：按文件加载，或者让 hook 重复几行。还可以做个便宜的测试：干了一个小时之后，让 agent 把这条规则复述出来。

**章节。** [长对话会变差](3-2-long-sessions.html)和[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)。

## Skill {#skills}

### skill 从来没被用上 {#skill-not-loaded}

**先查什么。** 开一个新对话（旧对话里可能已经装着这个 skill），不要输入 skill 的名字，用一个人平常会说的话去问。然后看加载了哪些 skill，平台有日志的话就用日志。如果没加载，说明描述里缺用户的说法。如果你有很多 skill，可能是旁边的某个抢走了请求：让每个 skill 保持狭窄，并写明它不管什么。

**章节。** [指令与 skill：只加载需要的](3-3-instructions-and-skills.html)，“测试 skill 能不能被找到”；[30 分钟搭一个最小 harness](0-2-minimal-harness.html)（第 2 步）。

### skill 不该加载的时候加载了 {#skill-too-wide}

**先查什么。** 描述太宽。收窄它，并把那些不该触发它的相邻请求写成测试用例。

**章节。** [指令与 skill：只加载需要的](3-3-instructions-and-skills.html)。

### skill 加载了，但什么都没变 {#skill-no-effect}

**先查什么。** 在新对话里把同一个任务跑两遍，一遍带 skill，一遍不带。如果看不出差别，就删掉那些没起作用的行；agent 本来就知道它们。然后检查这个 skill 是否已经过时。

**章节。** [指令与 skill：只加载需要的](3-3-instructions-and-skills.html)和[把团队的做法写成 skill](3-4-skills-and-workflows.html)。

## Hook 和拒绝 {#hooks}

### hook 没触发 {#hook-silent}

**先查什么。** 四件事，来自我在 2026 年 10 月的发现（它们会变）：hook 文件在窗口启动时读取，所以改完之后要重新加载窗口；我用 Copilot 的命令行模式时，hook 没有运行；组织的策略可以对某个工作区关闭 hook；还有，一个看起来像关闭开关的设置，在较新的会话里可能拦不住它们。然后用你的平台允许的最小的 hook 来测：只把事件名追加到一个文件里的那种。

**章节。** [Hook：每次调用都会经过的执行点](2-2-hooks.html)，“hook 看不到什么”和“测一测你自己的配置”。

### hook 触发了，但模型没收到消息 {#hook-lost-message}

**先查什么。** 查模型实际收到了什么，不要查 hook 返回了什么。在我的情况里，有些 prompt 到达时没带规则，因为平台自己的提醒占了 hook 用的那个位置（数字在下面那一章里）。

**章节。** [Hook：每次调用都会经过的执行点](2-2-hooks.html)，开头的那个故事。

### 我改了 hook 之后，所有工具都被拒绝 {#hook-wont-start}

**先查什么。** 如果 hook 程序启动不了（比如找不到解释器），Copilot 会把它当作拒绝，任何工具都跑不了。屏幕上只说 hook 出错了。在终端里手动运行 hook 的命令，就能看到真正的错误。

**章节。** [30 分钟搭一个最小 harness](0-2-minimal-harness.html)和[Hook：每次调用都会经过的执行点](2-2-hooks.html)，“hook 出问题的三种方式”。

### 本该拦住一次调用的 hook，悄悄放它过去了 {#hook-timeout}

**先查什么。** 时间。超出时限的 hook 会被当作通过，而且不会有任何提示。量一量你的 hook 要跑多久，让它保持轻量。

**章节。** [Hook：每次调用都会经过的执行点](2-2-hooks.html)和[把执行层当软件来设计](4-4-enforcement-design.html)，后者讲的是事先决定一次失败是拦截还是放行。

### agent 一直重试同一件被拒绝的事 {#refusal-loop}

**先查什么。** 读一读拒绝的理由。只写“已拒绝”的理由，会让 agent 重试，或者去试更糟的办法。把它改成说明为什么，以及改做什么。但不要解释怎么绕开这条规则。

**章节。** [Hook：每次调用都会经过的执行点](2-2-hooks.html)（理由是设计的一部分）和[询问不是限制](4-2-ask-vs-refuse.html)。

### 一次拒绝挡住了正常的工作 {#false-refusal}

**先查什么。** 匹配模式太宽。agent 没法和拒绝争辩，所以一次误拒就是一个卡住的任务。收窄匹配模式，留一条让人批准那些不该拒绝的事的路，再读日志看是哪条规则触发的。

**章节。** [提示里的规则只是请求](4-1-requests-and-rules.html)和[询问不是限制](4-2-ask-vs-refuse.html)。

### agent 绕过了一条规则，或者改了规则文件 {#rule-bypassed}

**先查什么。** 这条规则是在 prompt 里，还是在 hook 里？hook 看到的是什么：调用的文字，还是调用的效果？hook 拦得住常见的写法，拦不住一心要绕开它的 agent。还要检查，存放规则的文件和 hook 是否在受保护的名单上。对那些绝不能碰的东西，干脆不要交给 agent。

**章节。** [保护规则本身的文件](4-3-guardrails.html)和[有些东西根本不给](4-5-least-privilege.html)。

### agent 替自己批准了某件事 {#self-approval}

**先查什么。** 测一下：让 agent 运行审批命令，确认它被拒绝。如果拒绝这条命令的 hook 被删了、被改了或者出错了，一个能运行命令的 agent 就可能替自己批准。

**章节。** [两道门：人在哪里审批](5-3-two-approvals.html)。

## 循环、停止和成本 {#loops}

### agent 原地打转 {#agent-loops}

**先查什么。** agent 之外有没有东西在判断它卡住了？卡住的 agent 恰恰是最不适合做这个判断的。把停止规则放进代码，根据事实来判断：轮数和时间的上限，拒绝次数的上限，几轮下来没有进展，计划变了，检查次数用完。还要看它是不是一直在试护栏拦着的事。

**章节。** [无人值守：什么时候必须停](5-7-when-to-stop.html)。

### 一次停下的运行，给人留下一个谜 {#stop-vague}

**先查什么。** 停下的时候，有没有用一句话交回：为什么停、停在哪、人要决定什么？“遇到了问题”是不够的。

**章节。** [无人值守：什么时候必须停](5-7-when-to-stop.html)，“3. 停下时交回什么”。

### agent 说“做完了”，测试却失败 {#done-too-early}

**先查什么。** 它跑过检查，并给出命令和输出了吗？一句“所有测试都通过”，本身说明不了什么。让它能在自己的循环里运行检查，并让这次运行以事实结束（步骤打了勾，一次计数的检查通过了），不以 agent 的话结束。

**章节。** [让 agent 能检查自己的活](5-4-self-checks.html)和[无人值守：什么时候必须停](5-7-when-to-stop.html)，“4. 防止过早说‘做完了’”。

### 子 agent 的用量对不上 {#subagent-usage}

**先查什么。** 工具往往只显示主对话的用量。看看你的工具有没有把子 agent 也算进去。还要记住，每个子 agent 都从空白的上下文开始，从零读起，所以几个子 agent 的成本是单个 agent 的好几倍。限制能开几个，不是预算。

**章节。** [慎用子 agent](2-3-subagents.html)（代价和坑）和[无人值守：什么时候必须停](5-7-when-to-stop.html)，“2. 预算是总量，不是次数”一节。

### 账单比预想的高 {#bill}

**先查什么。** agent 读了什么。每一轮都会把整个上下文重读一遍，所以读了什么，比模型多聪明更要紧。先看工具返回的结果和加载的规则，再看任务被重做的频率。不要削得太狠，以至于任务失败被扔掉。看一整次运行的用量数字，不要看一条消息的。缓存的上下文按较低的价格计费（Anthropic 文档：约为基础价格的十分之一）；我没有在 Copilot 上验证过，所以看你自己的套餐显示什么。

**章节。** [选模型：看每次成功的成本](1-1-models-and-cost.html)、[agent 循环，以及你能插手的地方](2-1-agent-loop.html)和[上下文是一份预算](3-1-context-budget.html)。

## 检查 {#checks}

### 检查一直通不过 {#checks-never-pass}

**先查什么。** 读一读发现的问题。如果每一轮都有新问题，这个循环就是没有尽头的：设一个上限，让人来延长或豁免。如果发现的问题没有指向真实的文件和行号，那就是噪音。如果结论是错的，一次误报的 FAIL 会让作者去修一个不存在的问题。如果改动不断抵消之前的通过，可能是这份工作的指纹包含的东西太多，比如进度笔记。

**章节。** [让“通过”可信](5-5-counted-checks.html)和[模型能检查模型吗](5-6-model-checks-model.html)。

### 检查开着，却什么都没检查 {#checks-silent}

**先查什么。** agent 可能压根没调用过检查者，于是从来没有记下过 FAIL。prompt 里的规则抓不住这种情况。把检查放在 agent 必须经过的点上，比如它想要停下的那一刻。

**章节。** [让“通过”可信](5-5-counted-checks.html)，“检查开着，却什么都没检查”。

### 一个测试有时过、有时不过 {#flaky}

**先查什么。** 随机失败的测试，会让 agent 去找一个不存在的 bug，或者教会它反复重跑直到变绿。修好它，或者去掉它。如果完整的测试集太慢，就给 agent 一个能经常跑的快速子集。

**章节。** [让 agent 能检查自己的活](5-4-self-checks.html)。

### 同一个任务跑两次，结果不同 {#variance}

**先查什么。** 这是正常的。把任务多跑几次，看波动范围，再读那些失败的运行。一次运行证明不了什么。如果波动大到没有哪个结果可信，那就不正常了；这时是任务太松，或者检查太弱，应当先把它们修好。

**章节。** [一次运行证明不了什么](6-4-variance.html)。

## 上下文和记忆 {#context}

### 长对话变差了 {#long-chat}

**先查什么。** 不要指望模型记得住。把要紧的写进文件，从这个文件开一个新对话。试一试：问问自己，如果这个对话现在消失，会丢掉什么。如果对话变长是因为任务太大，解法是把任务变小。

**章节。** [长对话会变差](3-2-long-sessions.html)。

### 笔记或记忆文件里写了不实的内容 {#notes-wrong}

**先查什么。** 把笔记当作 agent 的报告：要紧的，对照源头核对。笔记保持简短，做完的就删掉，因为不断变长的笔记文件会把窗口填满。agent 写的记忆应当带来源和日期，并由人审查。

**章节。** [长对话会变差](3-2-long-sessions.html)和[agent 该记住什么](3-5-memory.html)。

### agent 听从了它在文件或网页里读到的文字 {#injection}

**先查什么。** 数一数三个圈：它能读私有数据吗，它读不可信的文本吗，它能把数据发出去吗？去掉任何一个。不可信文本的摘要也是不可信的。每次加工具，都要重新检查。

**章节。** [agent 读到的文字可能在指挥它](4-6-untrusted-input.html)和[MCP server：接工具的标准接口](1-3-mcp.html)。

## 看清发生了什么 {#seeing}

### 我分不清 agent 做了什么 {#cannot-tell}

**先查什么。** 有没有一份由代码写下的记录，涵盖每次调用和每次拒绝？读失败那次运行的轨迹，不要读 agent 的总结。hook 只能看到平台给它看的东西，所以干净的日志里仍然可能有个洞。

**章节。** [记下发生了什么，而不是 agent 说了什么](6-1-observe.html)和[一份五分钟读得完的报告](6-2-task-report.html)。

### 换了新模型，反而更糟 {#model-upgrade}

**先查什么。** 升级并不是在每个任务上都更好。把你的固定任务重跑一遍，然后一次删一条旧规则或旧步骤，每次都跑评测。

**章节。** [模型升级了，就要删](6-5-model-upgrades.html)。
