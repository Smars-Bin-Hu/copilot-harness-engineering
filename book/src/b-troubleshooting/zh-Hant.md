這個附錄是給出事的那一天用的。先找到你的症狀，做第一個檢查，再去讀它指向的那一章。這裡的內容都來自各章和 harness 的文件，所以每條建議我都指得出出處，但這份附錄不是一份完整的原因清單。

## 怎麼用 {#how-to-use}

有兩條規則，幾乎每個症狀都用得上。

- **看發生了什麼，不要看 agent 說了什麼**。agent 對自己工作的說法可能是錯的，紀錄卻可以檢查（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)）。
- **一次只改一樣，然後再跑同一個任務**。不然你分不出是哪個改動有幫助（[固定的任務，用腳本打分](6-3-eval-tasks.html)）。

照你看到的現象找症狀：

- 規則沒被遵守：[被無視](#rule-ignored)、[在長對話裡被丟掉](#rule-drift)。
- skill 沒被用到：[從沒用到](#skill-not-loaded)。
- hook 沒有反應或太嚴：[沒有觸發](#hook-silent)、[拒絕了真正的工作](#false-refusal)。
- agent 停不下來，或停得很糟：[一直繞圈](#agent-loops)、[太早說做完了](#done-too-early)。
- 帳單很高：[帳單](#bill)。
- 你說不出發生了什麼：[沒有紀錄](#cannot-tell)。

## 規則和指令 {#rules}

### agent 無視一條規則 {#rule-ignored}

**先檢查**。這條規則真的載入了嗎？要弄清楚，就打開新的對話，問一個只有你的規則才答得出的問題（[30 分鐘搭一個最小 harness](0-2-minimal-harness.html)）。如果載入了，就依序把常見的原因過一遍：檔案太長、兩條規則衝突、規則離它適用的地方太遠、沒有給理由，或者它只是一個請求。這條規則要是必須成立，就把它搬進程式碼。

**章節**。[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)，「寫下來的規則為什麼會被無視」一節，然後是 [提示裡的規則只是請求](4-1-requests-and-rules.html)。

### 規則檔很長，而且越來越糟 {#rules-rot}

**先檢查**。對每一行都問一句：沒有它，agent 會做錯嗎？答案是『不會』的那幾行就刪掉，然後跑同一個任務，看有沒有變差。另外，每條規則只放在一個地方。

**章節**。[30 分鐘搭一個最小 harness](0-2-minimal-harness.html) 的「這組入門設定會在哪裡出問題」，以及 [指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。

### 規則在短對話裡被遵守，在長對話裡被丟掉 {#rule-drift}

**先檢查**。看看這條規則現在離手上的工作有多遠。寫在第一則訊息裡的規則，工作好幾個小時之後就離得很遠了，所以要把它放近一點：依檔案載入，或者讓 hook 重複其中幾行。還有一個便宜的測試：過了一個小時，請 agent 說出這條規則。

**章節**。[長對話會變差](3-2-long-sessions.html) 和 [指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。

## Skills {#skills}

### 一個 skill 從沒被用到 {#skill-not-loaded}

**先檢查**。打開新的對話，因為舊的對話可能已經載入了這個 skill，然後用一般人會說的話來問，不要輸入 skill 的名稱。接著看載入了哪些 skill，平台有紀錄的話就看紀錄。沒載入，表示描述裡缺了使用者的說法。如果你的 skill 很多，也可能是鄰近的某一個搶走了請求，所以每個 skill 都要保持窄，並寫明它不是做什麼的。

**章節**。[指令與 skill：只載入需要的](3-3-instructions-and-skills.html) 的「三個問題，三個測試」，以及 [30 分鐘搭一個最小 harness](0-2-minimal-harness.html)（第 2 步）。

### 一個 skill 不該載入時載入了 {#skill-too-wide}

**先檢查**。描述太寬了。把它收窄，再把鄰近、不該觸發它的請求寫成測試案例。

**章節**。[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。

### 一個 skill 載入了，卻什麼都沒變 {#skill-no-effect}

**先檢查**。在新的對話裡，把同一個任務跑兩次，一次有 skill，一次沒有。如果看不出差別，就刪掉沒有差別的那幾行，因為 agent 本來就知道。之後再檢查這個 skill 有沒有過時。

**章節**。[指令與 skill：只載入需要的](3-3-instructions-and-skills.html) 和 [把團隊的做法寫成 skill](3-4-skills-and-workflows.html)。

## Hook 和拒絕 {#hooks}

### hook 沒有觸發 {#hook-silent}

**先檢查**。有四件事會讓 hook 沒有反應，都是我 2026 年 10 月的發現，以後會變。

- hook 檔是在視窗啟動時讀的，所以改了之後要重新載入視窗。
- 我用 Copilot 的命令列模式時，hook 沒有執行。
- 組織的政策可以為一個工作區關掉 hook。
- 一個看起來像關閉開關的設定，在較新的會話裡可能擋不住它們。

這幾點排除之後，再用你的平台允許的最小 hook 測試，例如只把事件名稱附加到一個檔案的那種。

**章節**。[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html) 的「hook 看不到什麼」和「三個問題和一個小測試」。

### hook 觸發了，但模型沒收到訊息 {#hook-lost-message}

**先檢查**。要看模型真正收到了什麼，而不是 hook 回傳了什麼。我就碰過：有些 prompt 到達時沒有規則，因為平台自己的提醒占掉了 hook 用的位置（數字在下面那一章）。

**章節**。[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)，開頭的故事。

### 我改了 hook 之後，每個工具都被拒絕 {#hook-wont-start}

**先檢查**。hook 程式要是啟動不了（例如找不到直譯器），Copilot 會當成拒絕，所以沒有任何工具能執行。畫面上只會說 hook 出錯了。想看到真正的錯誤，就在終端機裡手動執行一次 hook 的指令。

**章節**。[30 分鐘搭一個最小 harness](0-2-minimal-harness.html) 和 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html) 的「hook 出錯的三種方式」。

### 一個本來該擋下呼叫的 hook 放行了，而且沒有任何通知 {#hook-timeout}

**先檢查**。看 hook 跑了多久。執行超過時限的 hook，會被當成通過，而且不會有任何提示。量一量你的 hook 花多久，讓它保持輕量。

**章節**。[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html) 和 [把執行層當軟體來設計](4-4-enforcement-design.html)，後者講的是事先決定失敗時是擋下還是放行。

### agent 一直試同一件被拒絕的事 {#refusal-loop}

**先檢查**。讀拒絕的原因。原因裡只寫「denied」，agent 就會重試，或去試更糟的事，所以要改寫成說明為什麼，以及該改做什麼。但不要解釋怎麼閃躲這條規則。

**章節**。[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)（原因是設計的一部分）和 [詢問不是限制](4-2-ask-vs-refuse.html)。

### 拒絕擋住了真正的工作 {#false-refusal}

**先檢查**。樣式太寬了。agent 沒辦法跟拒絕爭辯，所以一次錯誤的拒絕就是一個卡住的任務。把樣式收窄，保留一個讓人批准那些不該被拒絕的事的辦法，再讀紀錄，看是哪條規則觸發的。

**章節**。[提示裡的規則只是請求](4-1-requests-and-rules.html) 和 [詢問不是限制](4-2-ask-vs-refuse.html)。

### agent 繞過了一條規則，或改了規則檔 {#rule-bypassed}

**先檢查**。這條規則在 prompt 裡，還是在 hook 裡？如果在 hook 裡，hook 看到的是呼叫的文字，還是它的效果？hook 擋得住常見的寫法，擋不住一心要繞過它的 agent。也要檢查放規則的檔案和 hook 是不是在受保護的清單上。至於絕不能被碰的東西，根本不要給 agent。

**章節**。[保護規則本身的檔案](4-3-guardrails.html) 和 [有些東西根本不給](4-5-least-privilege.html)。

### agent 自己批准了某件事 {#self-approval}

**先檢查**。測試一下：請 agent 執行批准的指令，確認它會被拒絕。拒絕它的 hook 一旦被移除、被編輯或失敗了，能執行指令的 agent 就可能為自己批准。

**章節**。[兩道門：人在哪裡批准](5-3-two-approvals.html)。

## 循環、停止和成本 {#loops}

### agent 一直繞圈 {#agent-loops}

**先檢查**。在 agent 之外，有沒有東西在判斷它是不是卡住了？應該要有，因為卡住的 agent 恰恰最不適合自己下這個判斷。把停止規則放進程式碼，讓它從事實來判斷：輪數和時間的上限、拒絕次數的上限、好幾輪都沒有進展、計劃改了、檢查次數用完。也看看它是不是一直在試護欄擋住的事。

**章節**。[無人值守：什麼時候必須停](5-7-when-to-stop.html)。

### 執行停下來了，人卻不知道為什麼 {#stop-vague}

**先檢查**。這次停止有沒有用一句話交回為什麼停、停在哪裡，以及人要決定什麼？只說一句「遇到問題」是不夠的。

**章節**。[無人值守：什麼時候必須停](5-7-when-to-stop.html) 的「回來的人該看到什麼」。

### agent 說「做完了」，測試卻失敗 {#done-too-early}

**先檢查**。它有沒有執行檢查，並給出指令和輸出？一句「所有測試都通過」，本身說明不了什麼。所以要給它一個在自己循環裡執行檢查的辦法，並讓運行以事實收尾（步驟打勾、算數的檢查通過），而不是以 agent 的一句話收尾。

**章節**。[讓 agent 能檢查自己的活](5-4-self-checks.html) 和 [無人值守：什麼時候必須停](5-7-when-to-stop.html) 的「『做完了』說得太早」。

### 子 agent 的用量加不起來 {#subagent-usage}

**先檢查**。工具通常只顯示主對話的用量。確認一下你的工具有沒有把子 agent 也算進去。也要記得，每個子 agent 都從空的上下文開始、從零讀起，所以好幾個子 agent 的花費就是一個的好幾倍。也正因為這樣，光限制能啟動幾個，並不等於有了預算。

**章節**。[慎用子 agent](2-3-subagents.html) 的「多花的錢換到了什麼，拆分還有哪些代價」，以及 [無人值守：什麼時候必須停](5-7-when-to-stop.html) 的「預算是總量，不是次數」一節。

### 帳單比預期高 {#bill}

**先檢查**。先看 agent 讀了什麼。每一輪都會重讀整個上下文，所以讀了什麼，比模型多聰明更重要。先看工具結果和載入的規則，再看任務被重做的頻率。砍的時候要停在任務開始失敗、被整個丟掉之前。看用量要看一整次運行，不是一則訊息。快取的上下文用較低的費率計費（Anthropic 的文件：約基本價格的十分之一），不過這一點我沒有在 Copilot 上驗證過，所以請看你自己的方案顯示什麼。

**章節**。[選模型，別只看 token 單價](1-1-models-and-cost.html)、[Agent 到底是怎麼做事的？](2-1-agent-loop.html) 和 [上下文是一份預算](3-1-context-budget.html)。

## 檢查 {#checks}

### 檢查一直過不了 {#checks-never-pass}

**先檢查**。讀一讀發現的問題，可能是下面幾種情況。一種是每一輪都帶來新的發現，表示這個循環沒有終點，這時要設一個上限，讓人決定延長還是豁免。也可能發現沒有指向真實的檔案和行號，那就是雜訊。還可能結論本身是錯的，錯誤的 FAIL 會讓作者去修一個不存在的問題。最後，如果編輯一直抵銷先前的通過，可能是這份工作的指紋包含了太多東西，例如進度筆記。

**章節**。[讓「通過」可信](5-5-counted-checks.html) 和 [模型能檢查模型嗎](5-6-model-checks-model.html)。

### 檢查開著，卻什麼都沒檢查 {#checks-silent}

**先檢查**。agent 可能根本從沒呼叫過檢查者，那就永遠不會有 FAIL 被記下。prompt 裡的規則抓不到這個。要把檢查放在 agent 必須經過的地方，例如它想停下來的那一刻。

**章節**。[讓「通過」可信](5-5-counted-checks.html) 的「檢查開著，卻什麼都沒檢查」。

### 一個測試有時通過、有時失敗 {#flaky}

**先檢查**。隨機失敗的測試，會讓 agent 去找一個不存在的 bug，或教會它一直重跑到變綠為止。要嘛修好它，要嘛丟掉它。如果完整的測試很慢，就給 agent 一個快的子集，讓它常常執行。

**章節**。[讓 agent 能檢查自己的活](5-4-self-checks.html)。

### 同一個任務跑兩次，結果不同 {#variance}

**先檢查**。這是正常的。把任務跑好幾次，看看結果差了多少，再讀失敗的那幾次運行。一次運行證明不了什麼。不正常的，是差距大到沒有哪個結果可以信。遇到這種情況，就表示任務太鬆，或檢查太弱，應該先修這個。

**章節**。[一次運行證明不了什麼](6-4-variance.html)。

## 上下文和記憶 {#context}

### 長對話變差了 {#long-chat}

**先檢查**。不要靠模型記住。把重要的寫進檔案，再從那個檔案開一個新的對話。想知道寫夠了沒有，就問自己：如果這個對話現在消失，你會失去什麼？如果對話變長是因為任務太大，解法是更小的任務。

**章節**。[長對話會變差](3-2-long-sessions.html)。

### 筆記或記憶檔說了假的東西 {#notes-wrong}

**先檢查**。把筆記當成 agent 的報告，重要的幾條對照來源檢查一遍。筆記要短，做完的就刪掉，因為越長越大的筆記檔會塞滿視窗。agent 寫的記憶，應該帶有來源和日期，並由人審查。

**章節**。[長對話會變差](3-2-long-sessions.html) 和 [agent 該記住什麼](3-5-memory.html)。

### agent 服從了它在檔案或網頁裡讀到的文字 {#injection}

**先檢查**。數一數風險的那三個圈，也就是下面三個問題：它能不能讀私人資料？它有沒有讀不可信的文字？它能不能把資料送出去？三個裡去掉任何一個。要記得，不可信文字的摘要也是不可信的。每加一個工具，就要重新檢查一遍。

**章節**。[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html) 和 [接 MCP server 之前，要想清楚什麼？](1-3-mcp.html)。

## 看見發生了什麼 {#seeing}

### 我說不出 agent 做了什麼 {#cannot-tell}

**先檢查**。有沒有一份由程式碼寫的紀錄，記下每個呼叫和每個拒絕？有的話，就讀失敗那次運行的軌跡，不要讀 agent 的摘要。即使這樣，hook 也只看得到平台給它看的東西，所以乾淨的紀錄仍然可能有洞。

**章節**。[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html) 和 [一份五分鐘讀得完的報告](6-2-task-report.html)。

### 新模型讓事情變糟 {#model-upgrade}

**先檢查**。升級不是在每個任務上都更好，所以先重跑你的固定任務。然後一次刪掉一條舊的規則或步驟，每刪一次都執行一次評測。

**章節**。[模型升級了，就要刪](6-5-model-upgrades.html)。
