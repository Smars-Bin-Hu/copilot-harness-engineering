## 一句话 {#in-one-sentence}

有哪些对象、谁用谁，这个问题只有一个正确答案，所以交给脚本来算：每次都按同样的方式算，也不花 token。这些脚本叫 toolkit，是团队自己拥有的代码，针对你自己的技术栈来写。

## 写给管理者 {#for-leaders}

- **要拍板的事**：让团队拥有一小组脚本，列出有哪些对象、谁用谁，而不是每次都让模型去推算。
- **风险**：让模型出地图，它是凭判断在读，可能漏掉对象，问两次还会给出两张不同的地图。脚本每次给的都是同一张地图，还会说明哪些地方它没读懂。在一个小的开源项目上，我的样例在 35 个文件里找到了 58 个对象，已知的 6 处使用也全部找到；这只说明它能跑，不说明它在你的代码上管用。
- **做对的代价**：脚本由模型来写，设计由人审批，之后脚本就不花 token 了。不过它们终归是代码，技术栈一变就得跟着维护。我没有在非常大的代码库上测过。
- **可以问团队**：“谁负责给我们的代码画地图的那些脚本？我们已经知道哪些使用是它必须找到的？”

## 为什么不让模型来画地图？ {#problem}

agent 要给一个对象写卡片，得先有人回答两个朴素的问题：有哪些对象？每个对象又用到了什么？这里的**对象**，是代码里有名字、别的东西可以使用的东西（见[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）。对象之间的关系叫**使用**：一个对象依赖另一个对象，比如一个存储过程调用另一个存储过程，一个类读一张表，一个任务运行一个包。把所有的对象和所有的使用合在一起，就是代码的**地图**，这是上一章起的名字。如果你听说过依赖图，它们是一回事。

最顺手的办法，是让模型去读代码，把地图交出来，它也会做出一份像样的东西。问题是，它根据刚读到的内容决定下一步读什么，一路读下去，可能漏掉一个对象，可能顺着一个有两种意思的名字追下去，也可能太早停下来。它自己也说不出漏了多少。再问它一次，两张地图还会不一样。

而一个逐个解析文件的脚本，没有这些毛病。它每次给出同样的地图，不花 token，还能说出哪些东西它没读懂。用脚本的理由，说到底就是这几条。可脚本本身又从哪里来呢？

## 脚本怎么画出地图 {#how-it-works}

### toolkit 是什么

脚本从哪里来，要看你用的是什么技术栈。一个存储过程、一个任务或者一个类在文件里长什么样，每种栈都不一样。同样是一次调用，在一种栈里写作 `CALL name`，在另一种栈里是注入对象上的一个方法。写法这么多，没有哪个现成的解析器能覆盖你代码里的所有写法。如果语言服务器或代码搜索服务已经能给你对象和使用，就先用它们（见[什么时候可以删掉自己的抽取器](#when-to-delete-it)）。它们覆盖不到的部分，才需要你自己写脚本。

这些要你来写的东西，就是 **toolkit**：一小组程序加一个配置文件，都放在知识库里。每个程序是一个**抽取器**，读一种文件，打印出这种文件定义的对象和它找到的使用。**配置文件**写明在你的代码里什么算对象、哪几种使用算数，还写明哪几类对象是**入口**（外部调用进来的地方，比如一个页面、一个 API、一个定时任务），哪些文件夹已经停用，以及名字里要忽略哪些词。

一个运行器把抽取器用到每个仓库的主分支上，把地图存进缓存。这样一来，下一次运行时，只需要重新读上次以来改过的文件。

### 谁来写：模型设计，人审批，脚本运行

你可能以为抽取器得自己写。在我的配置里是模型来写，一共分四步。第一步是调研：一个脚本统计每个仓库里各种文件的数量，模型每种读几个样本。样本读过以后，模型写出一份设计，说明在这个技术栈里对象和使用长什么样，并附上代码里的例子。人来读这份设计并审批，这时正好可以抓出“那不是使用，那是注释”这类问题。接着，模型写抽取器。最后一步留给下一节讲：反复运行，直到已知的使用都找到为止。

模型擅长把一个解析器写一次，但它不该每次都亲自充当解析器。构建完成之后，碰代码的就只有脚本了。

### 一个一直留着的测试：人知道的那些使用

地图刚做出来时，你怎么知道它不是在胡说？办法是由人写下 5 到 10 处他们知道确实存在的使用，比如“存储过程 A 调用存储过程 B”，放进 toolkit 里的一个文件。这些最好在抽取器出现之前就写好，模型写抽取器时也别给它看，免得抽取器只是为这几处调出来的。之后每次运行都必须找到全部这些使用，所以哪天改抽取器时丢了一处，那次运行就会失败。

这份已知使用的清单，就是一个回归测试，也就是保护已经管用的东西的测试。它很小，我也不假装它衡量了整张地图。它能做的是慢慢长大：每当你发现地图漏掉了一处使用，就把它加进去。地图到底有多完整，要到[第 8.3 章](8-3-kb-audit.html)再去衡量。

不过，已知的使用并不是唯一的检查。运行器每次还会报告两类可疑情况。一类是文件出了问题：要么读不了，要么读了什么都没找到。另一类是被用到、却哪里都没定义的名字。这些名字可能指向别的系统，可能是已经删除的代码，也可能是抽取器读错的写法，值得挑几个看看。

### 两个样例，只当例子

harness 自己不带 toolkit（为什么不带，看完样例再说），只带两个样例，让你看看它长什么样。一个是 SQL Server 的，覆盖存储过程、定时的 agent 任务和集成包；另一个是 Spring 的，针对一个 Spring Boot 服务，里面有 controller、repository、实体和表。

Spring 样例是我在开源项目 spring-petclinic 上做的。在那份代码上，它在 35 个文件里找到了 58 个对象，已知的 6 处使用也全部找到，没有文件读失败，也没有文件读出来是空的。这算一次冒烟测试：它说明 toolkit 能在一个小而整洁的项目上跑起来，不说明它在你的项目上也管用。难的情况（运行时拼出来的 SQL、由配置驱动的调用）不在那个项目里。你的技术栈、你的约定、你那些古怪的情况，要你自己来写。

### 为什么通用的 harness 不带 toolkit

我没有为常见的技术栈提供解析器。差不多对的解析器会悄悄出错，而且每个团队写代码的方式都略有不同。团队自己拥有、自己审计的 toolkit（[下一章](8-3-kb-audit.html)）就不一样了，漏了能修。它又放在知识库里，所以升级 harness 永远不会把它覆盖掉。

### 动手给一个仓库画地图并验证

1. 挑一个仓库，写下 5 到 10 处你知道确实存在的使用，每处带文件和行号。
2. 让 agent 起草在你的技术栈里对象和使用长什么样，附上你代码里的例子。读一遍，把不对的地方改过来。
3. 让 agent 写抽取器。运行它们，检查你所有已知的使用都出现了。
4. 运行两次。两次的输出必须完全一样。

## 自己拥有 toolkit 要付出什么，它又看不到什么 {#costs-and-traps}

如果脚本每次给同一张地图，又不花 token，那代价在哪？最直接的一笔是，toolkit 是要维护的代码。你的技术栈变了，它也得跟着变。

维护能让 toolkit 跟上技术栈，却不能保证它把每种写法都读对。假如一次调用有四种写法，抽取器只认得三种，已知的使用照样一处不少，看不出有什么问题。这个缺口，正是审计要管的（[8.3](8-3-kb-audit.html)）。

还有些东西，抽取器认得再多写法也看不到。运行时拼成字符串的查询，或者由配置表驱动的调用，对任何解析器都不可见。这些会被标出来，不去猜（[8.3](8-3-kb-audit.html)）。这些都来自一个小项目，我没有在非常大的代码库上测过 toolkit。

## 什么时候可以删掉自己的抽取器 {#when-to-delete-it}

自己写的抽取器，只是得到地图的一种办法。如果你信任的某个工具，比如你的语言服务器或代码搜索服务，已经能给出对象和使用，而且准确度测量过，就把它的输出喂给地图，丢掉你自己的抽取器。路线上的其余部分不关心地图是从哪来的。
