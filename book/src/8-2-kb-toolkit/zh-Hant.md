## 一句話 {#in-one-sentence}

有哪些物件、誰用誰，這個問題只有一個正確答案，所以交給腳本來算：每次都用同樣的方式算，也不花 token。這些腳本叫 toolkit，是團隊自己擁有的程式碼，為你自己的技術堆疊而寫。

## 給主管 {#for-leaders}

- **要做的決定**：讓團隊擁有一小組腳本，列出有哪些物件、誰用誰，不要每次都請模型去推算。
- **風險**：請模型畫地圖，它是憑判斷在讀，可能漏掉一個物件，問兩次還會給出兩張不同的地圖。腳本每次給的都是同一張地圖，也會說出自己讀不到的部分。在一個小的開源專案上，我的範例在 35 個檔案裡找到 58 個物件，6 處已知的使用也全都找到了；這只證明它跑得起來，不證明它在你的程式碼上行得通。
- **做對的成本**：模型寫腳本，人批准設計，之後腳本就不花 token 了。不過它們終究是程式碼，堆疊一改變就得跟著維護。我沒有測過很大的程式碼庫。
- **可以問團隊**：「畫我們程式碼地圖的腳本誰負責？我們已經知道它們必須找到的使用有哪些？」

## 為什麼不讓模型來畫地圖？ {#problem}

在 agent 能為一個物件寫卡片之前，得有人回答兩個簡單的問題：有哪些物件？每一個物件又用了什麼？這裡的**物件**，是程式碼裡一個有名字、別的東西可以使用的東西（見 [知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。物件之間的關係叫**使用**：一個物件依賴另一個物件，例如一個預存程序呼叫另一個預存程序，一個類別讀一張資料表，一個工作執行一個套件。所有物件加上所有使用，合起來就是程式碼的**地圖**，這是上一章取的名字。如果你聽過依賴圖這個詞，它們是同一回事。

最直接的做法，是請模型讀程式碼、把地圖畫出來，它也會做出合理的東西。問題是，它靠剛讀到的內容決定下一步讀什麼，一路讀下去，可能漏掉一個物件，可能順著一個有兩種意思的名字追下去，也可能太早停下來。它自己也說不出漏了多少。再問它一次，兩張地圖還會不一樣。

而解析每個檔案的腳本，沒有這些問題。它每次給同一張地圖，不花 token，還能說出自己讀不到的部分。用腳本的理由，說到底就是這幾條。可是腳本本身又從哪裡來呢？

## 腳本怎麼畫出地圖 {#how-it-works}

### toolkit 是什麼

腳本從哪裡來，要看你用的是什麼技術堆疊。一個預存程序、一個工作或一個類別在檔案裡長什麼樣，每種堆疊都不一樣。同樣是呼叫，在一種堆疊裡寫成 `CALL name`，在另一種堆疊裡是注入物件上的一個方法。寫法這麼多，沒有哪個現成的解析器能涵蓋你程式碼的每一種慣例。如果語言伺服器或程式碼搜尋服務已經給得出物件和使用，就先用它們（見 [什麼時候可以刪掉自己的抽取器](#when-to-delete-it)）。它們沒涵蓋的部分，才需要你自己寫腳本。

這些要你來寫的東西，就是 **toolkit**：一小組程式加上一個設定檔，全都放在知識庫裡面。每支程式是一個**抽取器**，讀一種檔案，印出這種檔案定義的物件和它找到的使用。**設定檔**說明在你的程式碼裡什麼是物件、哪些種類的使用算數，也說明哪些類型的物件是**入口**（從外部呼叫進來的地方，例如畫面、API、排程工作）、哪些資料夾已經退役，以及名字裡哪些詞要忽略。

執行器把抽取器用在每個倉庫的主分支上，並把地圖存進快取。這樣一來，下一次執行時，只要重讀上次之後改過的檔案。

### 誰寫：模型設計，人批准，腳本執行

你可能以為抽取器得自己寫。在我的設定裡，是模型來寫，一共分四步。第一步是調查：一個腳本數出每個倉庫裡各種檔案的數量，模型每一種讀幾個樣本。樣本讀過之後，模型寫出一份設計，說明在這個堆疊裡物件和使用長什麼樣，並附上程式碼裡的例子。人讀這份設計並批准它，這時正好可以抓出「那不是使用，那是註解」這類問題。接著，模型寫抽取器。最後一步留給下一節講：反覆執行，直到已知的使用都找到為止。

模型擅長把解析器寫一次，但它不該每一次都親自當解析器。建好之後，碰程式碼的就只有腳本了。

### 一個一直留著的測試：人知道的那些使用

地圖第一次做出來時，你怎麼知道它不是胡說？辦法是由人寫下 5 到 10 處自己確定存在的使用，例如「預存程序 A 呼叫預存程序 B」，放進 toolkit 裡的一個檔案。這些最好在抽取器出現之前就寫好，模型寫的時候也別給它看，免得抽取器只是對著這幾處調校出來的。之後每次執行都必須找到所有這些使用，所以哪天改抽取器時弄丟了一處，那次執行就會失敗。

這份已知使用的清單，就是一個迴歸測試，也就是確保原本好的東西不會壞掉的測試。它很小，我也不假裝它量得出整張地圖。它能做的是慢慢長大：每次你遇到地圖漏掉的使用，就把它加進去。地圖到底有多完整，要到 [第 8.3 章](8-3-kb-audit.html) 再去量。

不過，已知的使用並不是唯一的檢查。執行器每次還會回報兩類可疑的情況。一類是檔案出了問題：要麼讀不了，要麼讀了什麼都沒找到。另一類是被使用、卻沒在任何地方定義的名字。這些名字可能是別的系統，可能是被刪掉的程式碼，也可能是抽取器讀錯的寫法，值得挑幾個看看。

### 兩個範例，只當例子

harness 沒有附帶自己的 toolkit（為什麼不附，看完範例再說），只有兩個範例，讓你看看它長什麼樣。一個是 SQL Server 的，涵蓋預存程序、排程的 agent 工作和整合套件；另一個是 Spring 的，針對一個 Spring Boot 服務，裡面有 controller、repository、entity 和資料表。

Spring 範例是我在開源專案 spring-petclinic 上建的。在那份程式碼上，它在 35 個檔案裡找到 58 個物件，6 處已知的使用也全都找到了，沒有檔案讀取失敗，也沒有檔案是空的。這算是冒煙測試：它證明 toolkit 在一個小而整齊的專案上跑得起來，不證明在你的專案上也行得通。難的情況（執行時才組出來的 SQL、由設定驅動的呼叫）不在那個專案裡。你的堆疊、你的慣例和你那些奇怪的情況，要由你來寫。

### 為什麼通用的 harness 不附 toolkit

我沒有為常見的堆疊附上解析器。差不多對的解析器會悄悄出錯，而且每個團隊寫程式碼的方式都有點不同。團隊自己擁有、自己抽查的 toolkit（[下一章](8-3-kb-audit.html)）就不一樣，漏掉東西時可以修。它又放在知識庫裡，所以升級 harness 不會覆蓋它。

### 動手幫一個倉庫畫地圖並驗證

1. 挑一個倉庫，寫下 5 到 10 處你知道存在的使用，每處附上檔案和行號。
2. 請 agent 草擬在你的堆疊裡物件和使用長什麼樣，附上你程式碼裡的例子。讀一遍，把不對的地方改過來。
3. 讓 agent 寫抽取器。執行它們，檢查你所有已知的使用都出現了。
4. 執行兩次。兩次的輸出必須完全一樣。

## 自己擁有 toolkit 要付出什麼，它又看不到什麼 {#costs-and-traps}

如果腳本每次給同一張地圖，又不花 token，那代價在哪？最直接的一筆是，toolkit 是要維護的程式碼。你的堆疊改變，它也得跟著改。

維護能讓 toolkit 跟上堆疊，卻不能保證它把每種寫法都讀對。假如一次呼叫有四種寫法，抽取器只認得三種，已知的使用照樣一處不少，看不出有什麼問題。這個缺口，正是抽查要管的（[8.3](8-3-kb-audit.html)）。

還有些東西，抽取器認得再多寫法也看不到。執行時組成字串的查詢，或由設定表驅動的呼叫，任何解析器都看不見。這些要標出來，不要猜（[8.3](8-3-kb-audit.html)）。這些都來自一個小專案，我沒有在很大的程式碼庫上測過 toolkit。

## 什麼時候可以刪掉自己的抽取器 {#when-to-delete-it}

自己寫的抽取器，只是得到地圖的一種辦法。如果一個你信任的工具，例如你的語言伺服器或程式碼搜尋服務，已經給得出物件和使用，準確度也量過，就把它的輸出餵進地圖，丟掉自己的抽取器。路線的其餘部分不在乎地圖從哪裡來。
