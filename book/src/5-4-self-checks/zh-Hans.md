读这一章，你要用过 AI 编程 agent。它建立在 [Agent 到底是怎么干活的？](2-1-agent-loop.html)之上：agent 问模型、运行一个工具、把结果送回去。

## 一句话 {#in-one-sentence}

给 agent 一个检查自己活儿的办法，比如跑测试、跑 linter、跑程序。agent 自己能运行、能读懂的检查，在循环里就给了它反馈；reviewer 却只能等事后才发现问题。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求每个任务都带一个 agent 自己能运行、能读懂的检查，比如测试、构建或 linter，并决定其中哪些检查 agent 不许改。
- **风险**：agent 在活儿看起来做完时就会停下，而在我自己的使用中，模型常常倾向于报告成功，只是我没有记录过多久发生一次。Anthropic 描述过，后来的 agent 看到已经有进展，就会“宣布工作完成”。agent 还可能靠削弱测试来通过。这样的案例我没有记录过，所以要把它当作一个在设计里防着的风险。
- **做对的代价**：往往只是指令文件里的一行，也就是运行项目检查的那条命令。测试套件慢的话，需要一个能经常跑的快速子集。自查能把结果提高多少，我没有测过。
- **可以问团队**：“agent 能运行什么来知道它的活儿做完了？它能改这个检查吗？”

## “看起来做完了”为什么不算做完 {#problem}

agent 在活儿*看起来*做完时就会停下。可“看起来做完了”只是模型对自己代码的一种感觉，背后并没有运行过任何东西。于是它说“我做了这个改动”，你一读，发现了 bug。

如果 agent 手里没有什么可以运行、能告诉它活儿做完没有，那么你就是那个测试套件。每个错误都得等你发现，这既慢，又得有人守在屏幕前。

在我自己的使用中，常常看到模型倾向于报告成功，不过我没有记录过多久发生一次。Anthropic 在长时间运行里也描述过同样的倾向：后来的 agent 实例看到已经有了进展，就会“宣布工作完成”（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。你也许会想，那让 agent 回头把自己的活儿再读一遍呢？这也不管用。自己读自己的活儿，盲区还是原来那些，因为写出错误的那套思路，现在又在读这个错误（[别跟风瞎用子 Agent](2-3-subagents.html)）。

所以出路不在于换一个更聪明的 agent，而在于一个不依赖 agent 感觉的检查。有了这样的检查，会有什么不同？

## 放进循环里的检查，和它够不着的地方 {#how-it-works}

### 你能加的最有用的东西之一

要看出有什么不同，最直观的办法，是把同一个任务的两次运行放在一起看。第一次，agent 改完代码就说“做完了”。你去跑测试，两个失败了，于是你告诉 agent。它修好一个，你再跑一遍。

第二次，agent 改完代码，自己去跑测试。看到两个失败，它读了输出，把两个都修好，再跑一遍测试。这回通过了，它才说“做完了”，并附上输出。

这两次用的是同一个模型。差别在于，第二次里检查的结果在 agent 收工之前，就**在循环里**回来了。[Agent 到底是怎么干活的？](2-1-agent-loop.html)里的那个循环本来就留着这个位置，因为工具的结果会送回模型，由模型决定下一步。跑一次测试，说到底就是一个结果直截了当地说“通过”或“失败”的工具。

::: figure 5-4-check-loop

这一点，Anthropic 的 Claude Code 指南用自己的话说过：给 agent 一个能运行、结果是通过或失败的东西，它就能自己接着干下去，你也就不用盯着（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）。在能加给 agent 的各种东西里，我把自查放在靠前的位置。reviewer 当然也有价值，但它只能在事后看做完的工作，而自查改变的是 agent 干活时做的事。

### 能运行什么

那 agent 能跑什么？几乎什么都行，只要它给出的结果 agent 读得懂：

- **测试**：项目自己的测试，或者为这次改动新写的测试。
- **构建或类型检查**：光看退出码，就知道行不行。
- **linter 或格式化工具**：快，能抓住一类错误。
- **把输出和已知正确的文件做对比的脚本**：适合数据工作，因为那里正确答案就是一张表。
- **运行程序**：对 pipeline，用一小份输入跑一遍，看输出。
- **截图和设计稿并排放**：用于用户界面。

如果仓库里已经有其中一样，那么 agent 的指令文件里最有用的一行，就是运行它的那条命令。项目信任的是哪条命令，agent 自己猜不出来。

不过，知道了跑什么，还剩一个问题：要它跑，要求得有多硬？这里从软到硬分几级，用的还是[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)里那架梯子：

1. 最软的，是在 prompt 里写一句，比如“之后运行测试，直到通过为止”。什么时候算满意，由 agent 自己决定。
2. 硬一点的，是把它当作停止条件。agent 想停下的那一刻，会有一个 hook（[硬性规则放在哪？用 hook](2-2-hooks.html)）运行；检查要是失败，hook 就把 agent 送回去接着干。因为这是平台强制执行的，agent 没法带着一个失败的检查结束这一轮。Claude Code 的文档用 Stop hook 描述了这个做法（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)），不过写这一章时，我没有在 Copilot 里测过同样的做法。
3. 最硬的，是让程序来数通过的次数，这个数就不再由 agent 报告（[Agent 说“测过了”，能信吗？](5-5-counted-checks.html)）。

### 让结果简短、可读

不管检查是什么，agent 都要读它的输出，而这些输出会进入它的上下文（[为什么不能把所有规则都塞给 Agent？](3-1-context-budget.html)）。这里可能出两种问题，一种是说得太多，一种是说得太少。一次测试运行打印几千行，会把上下文塞满，agent 需要的那一个失败就淹没在里面。所以只打印失败的项，每一项带上文件和行号，再加一个计数；通过的那些噪音，藏起来就好。另一头，光一个“Error”，agent 根本无从下手。好的失败信息要说清楚期望什么、实际发生了什么、出在哪里。

这和[Agent 用不好工具，先看工具的描述和报错](1-2-tool-calling.html)里关于工具消息的建议是一回事：agent 是个不可靠的用户，它读到什么，就决定了它下一步做什么。一个输出便宜又清楚的检查，比一个全面却没人读得懂的检查更有价值。

输出还有一个用处：它是证据。“所有测试都通过了”只是一个说法，运行过的那条命令和它的输出才是证据，所以要向 agent 索取。你没在旁边看着的时候，它们就是你手里唯一的证据。

### 自查抓不住什么

不过，就算检查又短又清楚，而且通过了，它说明的东西也比看上去少。它说的是“这个做到了检查所测的东西”，而不是“这就是你想要的”，两者之间有两个要紧的缺口。

一个缺口在需求上。如果 agent 依据的那一页不是人的本意（[需求说不清？让 Agent 先写一页给你确认](5-2-requirements.html)），那么通过每一个测试的完美代码，也只是为错的东西写的完美代码。agent 照着错的需求写出来的测试，哪一个都发现不了这一点，只有人去读需求才能发现。

另一个缺口在测试本身：它可能检查得太少，带着 bug 也能通过。agent 在同一个会话里写的测试，和代码出自同一份理解，所以有同样的盲区。要是 agent 把规则理解错了，它的代码和它的测试会彼此一致，而且都是错的。

还有一个限制，既不是需求的缺口，也不是测试的缺口：有些错误只有在真实环境里、用真实数据运行程序时才会显现，而 agent 在那里运行不了。这类错误要靠人来检查，或者靠测试环境。

前面这些，是检查本来就够不着的地方。下一个问题不一样，它是检查本身带来的。

### 当 agent 转而削弱测试

给了 agent 一个检查，它也就多了一种失败的方式。agent 想让循环以通过收尾，而拿到通过最容易的办法，是改检查，不是改代码。它可以把断言放松到能通过为止，可以删掉或跳过失败的测试，可以把期望值改成代码现在给出的值，也可以捕获一个错误再把它吞掉。

这些都不需要什么恶意，agent 只是在做循环奖励的事：以通过收尾。我自己的运行里没有记录过这样的案例，所以我把它写成一个要在设计里防着的风险，而不是我测量过的东西。

那该怎么防？办法有好几种，从最便宜到最硬。最便宜的，是用话说清楚：“修代码，不要修测试。如果测试看起来不对，说出来，然后停下。”这有帮助，但它是一个请求（[为什么 Agent 不听 prompt 里的规则？](4-1-requests-and-rules.html)）。

光靠请求不够的时候，就让测试待在 agent 够不着的地方。如果测试属于不许编辑的东西，hook 会拒绝这个改动。[别让 Agent 改自己的规则](4-3-guardrails.html)讲了为什么检查 agent 的文件应该放在 agent 能写的范围之外。不过，要是新增测试本身就是工作的一部分，这个办法就不合适；那种情况下，保护已有的测试，让 agent 新增测试。

最硬的办法，是不再信报告，改成去数。看测试的 diff（改动行的清单），一个本来失败的测试要是在里面被改过，就是个信号。更好的是让代码而不是 agent 来数通过的次数，同时留下检查运行过的记录（[Agent 说“测过了”，能信吗？](5-5-counted-checks.html)）。

### 它和独立检查怎么分工

既然自查漏掉的东西这么多，独立的 reviewer 是不是更好用？其实两者不是对手，因为它们抓的东西不同。

| | 自查 | 独立 reviewer |
| --- | --- | --- |
| 什么时候 | agent 干活的时候 | 它做完之后 |
| 抓什么 | 程序能判断的东西：能运行、能通过、和某个文件一致 | 程序没法判断的东西：符不符合需求、逻辑站不站得住 |
| 漏什么 | 错的需求、弱的测试 | reviewer 和作者共有的盲区 |
| 成本 | 便宜，可以反复运行 | 多一个 agent，用量是好几倍（[别跟风瞎用子 Agent](2-3-subagents.html)） |

所以自查放在前面。把它放进循环里，能多就多，能便宜就便宜。然后在值得花这笔成本的地方，再对结果做一次独立检查。reviewer 看到测试已经全绿，就可以把注意力花在测试回答不了的那个问题上：这是对的东西吗？

## 自查的代价，和它会怎样误导你 {#costs-and-traps}

自查便宜，但它不是白送的，用错了还会误导你。最糟的情况，是一个可能错误地通过的检查。它比没有检查还糟，因为它给人虚假的安慰。一个永远不会失败的测试是最极端的例子：它每次都通过，却什么也没告诉你。

别的代价，来自检查在循环里的表现。速度是其中之一。检查太慢，agent 就不爱跑：整个套件要是得跑二十分钟，它就很少去跑，循环也跟着慢下来。所以给它一个能经常跑的快速子集，最后再跑整个套件。不稳定的检查造成的是另一种伤害：它会把 agent 教坏。一个随机失败的测试，会让 agent 去找一个根本不存在的 bug，或者教会它一直重跑，跑到变绿为止。

另外两个限制，前面已经碰到过。一个是输出会把上下文塞满，讲结果要简短、可读时说过；另一个是，有些代码 agent 根本运行不了。真实数据、真实环境或者权限它拿不到的地方，自查只能覆盖一部分，所以要说清楚是哪一部分，其余的留给人。

### 一个便宜的办法，测测你自己的检查

自查到底能把结果提高多少？我在自己的配置里没有测过。从厂商的指南和循环本身来看，方向是清楚的，但效果有多大，我不知道。能便宜地量出来的，是你自己的检查覆盖了多少。

故意往能正常运行的代码里放一个 bug，然后运行 agent 会运行的那些检查。如果它们还是绿的，那么不管 agent 怎么报告，这个检查都没有覆盖代码的这一部分。用这个便宜的办法，就能看出一次通过的检查值多少。

## Anthropic 的指南怎么说 {#industry}
{status: industry}

Anthropic 的 Claude Code 指南，把“给它一个可以运行的检查”和告诉 agent 它看不到的东西放在一起，举的例子有测试文件、构建的退出码、linter、把输出和预先备好的样例文件（fixture）对比的脚本，还有浏览器截图。它还说，要索取证据，而不只是一句“所有测试都通过了”，并提到一条构建并运行应用的命令，用来抓住测试和类型检查漏掉的东西（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）。

## 什么时候可以删掉那些提醒和 hook {#when-to-delete-it}

这些东西都得一直留着吗？检查本身是要留的，只要还有代码要检查。可以退役的，是我围绕 agent 使用这些检查而搭的脚手架，也就是反复提醒它运行测试的话，以及把它送回去的那个 hook。等到平台在 agent 收工之前，就把项目的检查当作正常的一步来运行，而且 agent 也不会去削弱它们，这些就可以去掉了。这样的平台我还没见过。

## 在你自己的环境里试试 {#try-it}

::: prompt
查一下，在这个仓库里，编程 agent 可以运行什么来检查自己的活儿：测试、构建、类型检查、linter、格式化工具、示例运行。对每一个，给出确切的命令、能看出来的话再给出耗时，并说明它的输出是不是足够简短清楚、让你能据此采取行动。说明指令文件有没有把这些命令告诉 agent。然后指出，代码里最大的一块，是这些检查里没有任何一个能在其中抓到 bug 的。不要修改任何文件，也不要运行任何超过一分钟的东西。
:::
