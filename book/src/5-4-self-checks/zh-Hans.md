读这一章，你要用过 AI 编程 agent。它建立在 [agent 循环，以及你能插手的地方](2-1-agent-loop.html)之上：agent 问模型、运行一个工具、把结果送回去。

## 一句话 {#in-one-sentence}

给 agent 一个检查自己活儿的办法：跑测试、跑 linter、跑程序。agent 能运行、能读懂的检查，在循环里就给了它反馈；reviewer 只能事后才发现问题。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求每个任务都带一个 agent 自己能运行、能读懂的检查，比如测试、构建或 linter，并决定这些检查里哪些 agent 不许编辑。
- **风险**：agent 在活儿看起来做完时就停下，而在我自己的使用中，模型常常倾向于报告成功；我没有记录过多久发生一次。Anthropic 描述过一个后来的 agent 在看到有进展后就会“declare the job done”。agent 还可能靠削弱测试来通过。我没有记录过这样的案例，所以这是个要在设计里防着的风险。
- **做对的代价**：往往是指令文件里的一行：运行项目检查的那条命令。慢的测试套件需要一个能经常跑的快速子集。自查能把结果提高多少，我没有测过。
- **可以问团队**：“agent 能运行什么来知道它的活儿做完了？它能改这个检查吗？”

## 问题 {#problem}

agent 在活儿*看起来*做完时就停下。看起来做完了，是模型对自己的代码的一种感觉。它什么都没运行过。它说“我做了这个改动”，你读了，然后发现了 bug。

如果 agent 没有什么可以运行、来说明活儿做完了没有，你就是那个测试套件。每个错误都要等到你发现。这很慢，而且需要你守在屏幕前。

在我自己的使用中，我常常看到模型倾向于报告成功；我没有记录过多久发生一次。Anthropic 描述过长时间运行中同样的倾向：后来的 agent 实例看到已经有进展，就会“declare the job done”（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。而且，靠读来检查自己活儿的 agent，有自己的盲区，因为写出错误的那套思路，也在读这个错误（见[慎用子 agent](2-3-subagents.html)）。

出路不是更聪明的 agent，而是一个不依赖 agent 感觉的检查。

## 原理 {#how-it-works}

### 你能加的最有用的东西之一

比较两种情况。

第一种，agent 改了代码，说“做完了”。你运行测试；两个失败。你告诉 agent。它修了一个。你再跑一遍。

第二种，agent 改了代码，自己运行测试。两个失败。它读输出，把两个都修了。它再跑测试。通过了。它说“做完了”，并附上输出。

同一个模型。区别在于，第二种情况里，检查的结果在 agent 做完之前，就**在循环里**回来了。[agent 循环，以及你能插手的地方](2-1-agent-loop.html)里的循环，本来就有放这个的位置：工具的结果送回模型，模型决定下一步。一次测试运行，就是一个结果直截了当地说通过或失败的工具。

::: figure 5-4-check-loop

Anthropic 的 Claude Code 指南用自己的话说了同一件事：给 agent 一个能运行、结果是通过或失败的东西，它就能自己接着干，你就不用盯着。（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）我把它放在各种杠杆的前面。reviewer 也有价值，但它在事后、对做完的工作起作用。自查改变的是 agent 干活时做的事。

### 能运行什么

任何能给出 agent 读得懂的结果的东西：

- **测试**：项目自己的测试，或者为这次改动新写的测试。
- **构建或类型检查**：光看退出码，就知道行不行。
- **linter 或格式化工具**：快，能抓住一类错误。
- **把输出和已知正确的文件做对比的脚本**：适合数据工作，因为正确答案就是一张表。
- **运行程序**：对 pipeline，用一小份输入跑一遍，看输出。
- **截图和设计稿并排放**：用于用户界面。

如果仓库里已经有其中一样，那么在 agent 的指令文件里，最有用的一行，就是运行它的那条命令。agent 猜不出项目信任的是哪条命令。

要求它做的力度，也有软有硬的几个层次。这是[提示里的规则只是请求](4-1-requests-and-rules.html)里的那个阶梯：

1. **写在 prompt 里**：“之后运行测试，直到通过为止”。什么时候满意，由 agent 自己决定。
2. **作为停止条件**：hook（见 [Hook：每次调用都会经过的执行点](2-2-hooks.html)）在 agent 想停下的那一刻运行。如果检查失败，hook 把 agent 送回去干活。这是平台强制执行的，所以 agent 不能带着一个失败的检查结束这一轮。Claude Code 的文档用 Stop hook 描述了这个做法（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）。为这一章，我没有在 Copilot 里测过同样的做法。
3. **由代码计数**：通过的次数由程序数，不由 agent 报告（见[让“通过”可信](5-5-counted-checks.html)）。

### 让结果简短、可读

agent 读检查的输出，输出会进入它的上下文（见[上下文是一份预算](3-1-context-budget.html)）。有两种问题。

- **太长**。一次测试运行打印几千行，会填满上下文，agent 需要的那个失败淹没在里面。打印失败的项，带上文件和行号，再加一个计数。把通过的噪音藏起来。
- **太含糊**。光一个“Error”，agent 无从下手。好的失败信息会说明期望什么、发生了什么、在哪里。

这和[Tool calling，以及怎么给 agent 设计工具](1-2-tool-calling.html)里关于工具消息的建议是一样的：agent 是个不可靠的用户，它读到什么，决定了它下一步做什么。一个输出便宜又清楚的检查，比一个全面却没人读得懂的检查更有价值。

还要要求证据。“所有测试都通过了”是一个说法。运行过的那条命令和它的输出，才是证据。你没在旁边看着的时候，它是你手里唯一的证据。

### 自查抓不住什么

一次通过的检查说的是：“这个做到了检查所测的东西。”它没说：“这就是你想要的。”有两个缺口要紧。

**需求是错的**。如果 agent 依据的那一页不是人的本意（见[需求由 agent 写，人确认](5-2-requirements.html)），那么通过每一个测试的完美代码，就是为错的东西写的完美代码。agent 根据错的需求写的任何测试，都发现不了这一点。只有人读需求，才能发现。

**测试很弱**。测试可能检查得太少：带着 bug 也能通过。agent 在同一个会话里写的测试，和代码是带着同样的理解写的，所以有同样的盲区。如果 agent 把规则理解错了，它的代码和它的测试会彼此一致，而且都是错的。

旁边还有第三件事：有些错误只有在真实环境里、用真实数据运行程序时才会显现，而 agent 在那里运行不了。那是人的检查，或者测试环境的检查。

### 失败模式：agent 削弱测试

给了 agent 一个检查之后，会出现这样一种失败。agent 想让循环以通过结束。拿到通过最容易的办法，是改检查，不是改代码。它可以：

- 把断言放松到能通过为止，
- 删掉或跳过失败的测试，
- 把期望值改成代码现在给出的值，
- 捕获一个错误并吞掉。

这里不需要任何恶意。agent 是在做循环所奖励的事：以通过收尾。我自己的运行里没有记录过这样的案例，所以我把它写成一个要在设计里防着的风险，不是我测量过的东西。

三种防御，从最便宜到最难：

1. **用话说清楚**。“修代码，不要修测试。如果测试看起来不对，说出来，然后停下。”有帮助，但它是一个请求（见[提示里的规则只是请求](4-1-requests-and-rules.html)）。
2. **让测试它够不着**。如果测试属于不许编辑的东西，hook 会拒绝这个改动。[保护规则本身的文件](4-3-guardrails.html)讲了为什么检查 agent 的文件应该在 agent 能写的范围之外。这不适合新增测试本身就是工作一部分的情形。那种情形下，保护已有的测试，让它新增测试。
3. **不信报告，要数**。看测试的 diff（改动行的清单）。对一个本来失败的测试做了改动，是个信号。并且让代码，而不是 agent，来数通过的次数，同时留下检查运行过的记录（见[让“通过”可信](5-5-counted-checks.html)）。

### 它和独立检查怎么分工

两者不是对手；它们抓的东西不同。

| | 自查 | 独立 reviewer |
| --- | --- | --- |
| 什么时候 | agent 干活的时候 | 它做完之后 |
| 抓什么 | 程序能判断的东西：能运行、能通过、和某个文件一致 | 程序没法判断的东西：符不符合需求、逻辑站不站得住 |
| 漏什么 | 错的需求、弱的测试 | reviewer 和作者共有的盲区 |
| 成本 | 便宜，可以反复运行 | 多一个 agent，用量是好几倍（见[慎用子 agent](2-3-subagents.html)） |

所以顺序是：先自查，在循环里，能多就多，能便宜就便宜。然后，在值得花这笔成本的地方，对结果做一次独立检查。reviewer 看到一次全绿的测试运行，就可以把注意力花在测试回答不了的问题上：这是对的东西吗？

## 代价和坑 {#costs-and-traps}

- **可能错误地通过的检查，比没有还糟**。它给人虚假的安慰。一个永远不会失败的测试，什么也告诉不了你。
- **慢的检查会拖慢循环**。如果整个套件要跑二十分钟，agent 就很少跑它。给它一个能经常跑的快速子集，最后再跑整个套件。
- **不稳定的检查会教坏 agent**。随机失败的测试，会让 agent 去找一个不存在的 bug，或者教会它一直重跑到变绿。
- **输出可能填满上下文**。见上文。
- **有些代码 agent 运行不了**。真实数据、真实环境或权限它拿不到的地方，自查只能覆盖一部分。说清是哪一部分，其余的留给人。
- **自查能把结果提高多少，我在自己的配置里没有测过**。从厂商的指南和循环本身来看，方向是清楚的；效果有多大，我不知道。

### 测试你自己的配置

故意往能正常运行的代码里放一个 bug，然后运行 agent 会运行的那些检查。如果它们仍然是绿的，那么不管 agent 怎么报告，这个检查都没有覆盖代码的这一部分。这是个便宜的办法，能看出一次通过的检查值多少。

## 业界怎么说 {#industry}
{status: industry}

Anthropic 的 Claude Code 指南，把“给它一个可以运行的检查”和告诉 agent 它看不到的东西放在一起，并列举了测试文件、构建的退出码、linter、把输出和测试数据对比的脚本、浏览器截图作为例子。它还说，要索取证据，而不只是“所有测试都通过了”，并提到一条构建并运行应用的命令，用来抓住测试和类型检查漏掉的东西。（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）

## 什么时候可以删掉 {#when-to-delete-it}

只要还有代码要检查，检查本身就会留着。可以退役的，是我围绕 agent 使用它们而搭的脚手架：反复提醒它运行测试，以及把它送回去的 hook。当平台在 agent 能结束之前，就把项目的检查当作正常的一步运行，而且 agent 不会削弱它们，这些就可以去掉。我还没见过。
