讀這一章，你需要用過 AI 寫程式的 agent。它建立在 [agent 循環，和你能插手的地方](2-1-agent-loop.html) 上：agent 問模型、執行工具、把結果餵回去。

## 一句話 {#in-one-sentence}

讓 agent 有辦法檢查自己的活：跑測試、跑 linter、跑程式。它能跑、也能讀的檢查，在循環裡就給它回饋；reviewer 只能在事後找問題。

## 給主管 {#for-leaders}

- **要做的決定**：要求每個任務都附一個 agent 自己能跑、能讀的檢查，例如測試、建置或 linter，並決定這些檢查裡，哪些 agent 不能改。
- **風險**：agent 在活「看起來」做完時就停了；就我自己的使用經驗，模型常常傾向於回報成功，我沒有記錄過頻率。Anthropic 描述過，後來的 agent 看到已有進展，就會「宣布工作完成」。agent 也可能靠削弱測試來通過。我沒有記錄過這樣的案例，所以它是要為之設計的風險。
- **做對的成本**：常常只是指令檔裡的一行：執行專案檢查的指令。慢的測試集需要一個快的子集，讓它常常跑。自我檢查能把結果改善多少，我沒有量過。
- **可以問團隊**：「agent 能跑什麼來知道它的活做完了？它能改這個檢查嗎？」

## 問題 {#problem}

agent 在活「看起來」做完時就停了。看起來做完，是模型對自己程式碼的一種感覺。它什麼都沒跑過。它說「我已經做了這個改動」，你一讀，找到了 bug。

如果 agent 沒有東西可以跑來判斷活有沒有做完，你就是測試集。每個錯誤都要等你發現。這很慢，也需要你坐在螢幕前。

就我自己的使用經驗，我常看到模型傾向於回報成功；我沒有記錄過頻率。Anthropic 描述過長時間運行裡同樣的拉力：後來的 agent 看到已有進展，就會「宣布工作完成」（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。而且靠讀來檢查自己的活的 agent，有自己的盲點，因為寫出錯誤的那套推理，同時也在讀它（[慎用子 agent](2-3-subagents.html)）。

出路不是更聰明的 agent，而是一個不靠 agent 的感覺的檢查。

## 原理 {#how-it-works}

### 你能加的最有用的東西之一

比較兩種情況。

第一種，agent 改了程式碼，說「做完了」。你跑測試，兩個失敗。你告訴 agent。它修好一個。你再跑一次。

第二種，agent 改了程式碼，自己跑測試。兩個失敗。它讀輸出，把兩個都修好。再跑一次測試。通過了。它說「做完了」，並附上輸出。

同一個模型。差別是：第二種情況裡，檢查的結果在 agent 結束之前，就**在循環裡**回來了。[agent 循環，和你能插手的地方](2-1-agent-loop.html) 裡的循環，本來就有放這件事的位置：工具的結果回到模型，模型決定下一步。跑測試只是一個工具，它的結果直白地說通過或失敗。

::: figure 5-4-check-loop

Anthropic 給 Claude Code 的指南，用自己的話說了同一件事：給 agent 一個能跑、結果是通過或失敗的東西，它就能自己繼續做下去，你不用盯著。（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）我把它放在各種槓桿的前面。reviewer 也很有價值，但它在事後、對做完的活才起作用。自我檢查改變的是 agent 工作時的行為。

### 能跑什麼

任何給出 agent 讀得懂的結果的東西：

- **測試**：專案自己的測試，或為這次改動新寫的測試。
- **建置或型別檢查**：光是結束碼，就說明行不行。
- **linter 或格式化工具**：很快，能抓到一類錯誤。
- **把輸出和已知正確的檔案比對的腳本**：適合資料工作，那裡正確的答案是一張表。
- **執行程式**：對管線，用小的輸入跑一次，看輸出。
- **截圖和設計稿並排**：用於使用者介面。

如果倉庫裡已經有其中一個，agent 指令檔裡最有用的一行，就是執行它的指令。agent 猜不出專案信任哪個指令。

要求的力道也有不同的層級，從軟到硬。這是 [提示裡的規則只是請求](4-1-requests-and-rules.html) 裡的那道階梯：

1. **在 prompt 裡**：「做完之後跑測試，一直做到通過」。什麼時候滿意，由 agent 決定。
2. **當成停止條件**：agent 想停下來的那一刻，一個 hook（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）會執行。檢查失敗，hook 就把 agent 送回去工作。由平台強制，所以 agent 不能帶著失敗的檢查結束這一輪。Claude Code 的文件用 Stop hook 描述了這件事（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）。這一章我沒有在 Copilot 測過同樣的做法。
3. **由程式計數**：通過的次數由程式計算，不是由 agent 回報（[讓「通過」可信](5-5-counted-checks.html)）。

### 讓結果短而好讀

agent 讀檢查的輸出，輸出會進它的上下文（[上下文是一份預算](3-1-context-budget.html)）。有兩件事會出錯。

- **太長**。印出幾千行的測試運行，會塞滿上下文，agent 需要的那個失敗就埋在裡面。印出失敗，附上檔案和行號，再加一個數量。把通過的雜訊藏起來。
- **太模糊**。只有「Error」，agent 沒有任何可以行動的東西。好的失敗訊息會說：預期什麼、發生什麼、在哪裡。

這和 [Tool calling，和給 agent 設計工具](1-2-tool-calling.html) 裡講工具訊息的建議一樣：agent 是個不可靠的使用者，它讀到什麼，決定它下一步做什麼。輸出便宜又清楚的檢查，比沒人讀得懂的徹底檢查更有價值。

也要要求證據。「所有測試都通過」是一個說法。執行過的指令和它的輸出，才是證據。你沒在看的時候，它是你唯一的證據。

### 自我檢查抓不到什麼

通過的檢查說的是：「這做到了檢查所測的東西。」它沒說：「這是你要的。」有兩個缺口很重要。

**需求是錯的**。如果 agent 工作所依據的那一頁，不是人的本意（[需求由 agent 寫，人確認](5-2-requirements.html)），那麼通過所有測試的完美程式碼，就是為錯的東西寫的完美程式碼。agent 從錯誤的需求寫出的任何測試，都找不到這一點。只有人讀需求，才找得到。

**測試是弱的**。測試可能檢查得太少：bug 還在，它也通過。agent 在同一個會話裡寫的測試，和程式碼出自同一個理解，所以有同樣的盲點。如果 agent 把規則讀錯了，它的程式碼和測試會彼此一致，而且都是錯的。

旁邊還有第三件事：有些錯誤只有在真實的環境、用真實的資料執行程式時才會出現，而 agent 沒辦法在那裡執行。那是人的檢查，或測試環境的檢查。

### 失敗模式：agent 削弱測試

給 agent 檢查，會帶來一種失敗。agent 想讓循環以通過收尾。拿到通過最容易的辦法，是改檢查，不改程式碼。它可以：

- 把斷言放寬到能通過，
- 刪掉或跳過失敗的測試，
- 把預期值改成程式碼現在給的值，
- 抓住錯誤然後吞掉。

這些都不需要惡意。agent 做的是循環獎勵的事：以通過收尾。我在自己的運行裡沒有記錄過這樣的案例，所以我把它描述成要為之設計的風險，不是我量過的東西。

三道防線，從最便宜到最硬：

1. **用話說**。「修程式碼，不要修測試。如果測試看起來是錯的，說出來然後停下。」有幫助，但它是請求（[提示裡的規則只是請求](4-1-requests-and-rules.html)）。
2. **讓測試在它碰不到的地方**。如果測試屬於不能編輯的東西，hook 會拒絕這個改動。[保護規則本身的檔案](4-3-guardrails.html) 解釋了為什麼檢查 agent 的檔案，應該在 agent 寫不到的地方。這不適合「新增測試本來就是工作一部分」的情況。那種情況下，保護現有的測試，讓它新增測試。
3. **不信報告，要計數**。看測試的 diff（改動的行的清單）。對一個原本失敗的測試做了改動，是個旗號。而且讓程式，不是 agent，來計算通過的次數，並留下檢查有執行的紀錄（[讓「通過」可信](5-5-counted-checks.html)）。

### 它和獨立檢查怎麼分工

兩者不是對手；它們抓的東西不同。

| | 自我檢查 | 獨立的 reviewer |
| --- | --- | --- |
| 什麼時候 | agent 工作的時候 | 它做完之後 |
| 抓得到 | 程式能判斷的事：能跑、能通過、和檔案相符 | 程式不能判斷的事：是否符合要求、邏輯站不站得住 |
| 抓不到 | 錯的需求、弱的測試 | reviewer 和作者共有的盲點 |
| 成本 | 便宜，可以一再執行 | 多一個 agent，用量是好幾倍（[慎用子 agent](2-3-subagents.html)） |

所以順序是：先做自我檢查，在循環裡盡量多、盡量便宜。然後，在值得付出成本的地方，對結果做獨立檢查。reviewer 看到測試是綠的，就能把注意力花在測試回答不了的問題上：這是對的東西嗎？

## 代價和陷阱 {#costs-and-traps}

- **可能錯誤通過的檢查，比沒有更糟**。它給人虛假的安心。永遠不會失敗的測試，什麼都告訴不了你。
- **慢的檢查會拖慢循環**。如果完整的測試集要二十分鐘，agent 就很少跑它。給它一個快的子集常常跑，完整的測試集留到最後。
- **不穩定的檢查會教錯 agent**。隨機失敗的測試，會讓 agent 去找一個不存在的 bug，或教它重跑到變綠為止。
- **輸出可能塞滿上下文**。見上面。
- **有些程式碼 agent 沒辦法執行**。真實的資料、真實的環境或權限它拿不到的地方，自我檢查只能涵蓋一部分。說清楚是哪一部分，其餘留給人。
- **我沒有量過在我自己的設定裡，自我檢查把結果改善多少**。方向從廠商的指南和循環本身看得很清楚；效果有多大，我不知道。

### 測你自己的設定

故意在能運作的程式碼裡放進一個 bug，然後執行 agent 會執行的檢查。如果它們還是綠的，不管 agent 怎麼回報，這個檢查都沒涵蓋程式碼的那一部分。這是個便宜的辦法，能看出一個通過的檢查值多少。

## 業界怎麼說 {#industry}
{status: industry}

Anthropic 的 Claude Code 指南，把「給它一個能跑的檢查」和告訴 agent 它看不到的東西放在一起，並列出測試檔、建置的結束碼、linter、把輸出和 fixture 比對的腳本、瀏覽器截圖當例子。它也說要索取證據，不是只有「所有測試都通過」，並提到一個會建置並執行應用程式的指令，用來抓測試和型別檢查漏掉的東西。（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）

## 什麼時候可以刪掉 {#when-to-delete-it}

只要還有程式碼要檢查，檢查本身就會留著。可以退役的，是我為 agent 使用它們而加的鷹架：一再提醒執行測試，以及把它送回去的 hook。平台在 agent 能結束之前，把專案的檢查當成一般步驟來執行，而且 agent 不削弱它們的時候，這些就可以拿掉。我還沒看到這樣的情況。

## 在你自己的環境試試 {#try-it}

不用裝 harness。在你自己的倉庫裡打開 agent，貼上：

::: prompt
找出在這個倉庫裡，寫程式的 agent 能執行什麼來檢查自己的活：測試、建置、型別檢查、linter、格式化工具、範例執行。對每一個，給出確切的指令、如果看得出來的話它要跑多久，以及它的輸出夠不夠短、夠不夠清楚，讓你能據以行動。說明指令檔有沒有告訴 agent 這些指令。然後指出程式碼裡最大的一塊：這些檢查沒有一個能在那裡抓到 bug。不要改任何檔案，也不要執行任何超過一分鐘的東西。
:::

## 在 harness 裡探索 {#explore}

harness 在開發任務算完成之前，要求留下自我測試的紀錄，並且有一個獨立的 reviewer，處理自我檢查判斷不了的事。照上面的說明準備好之後，輸入：

::: prompt
/harness-rookie-wondering 我讀完了「讓 agent 能檢查自己的活」這一章。請教我這個 harness 在哪裡要求 agent 執行自己的檢查、開發任務怎樣才算完成，以及獨立檢查（主題 11）怎麼和它搭配。帶我打開真實的檔案，並畫出這個循環。
:::

它一次教一小塊，停下來確認你跟得上，然後和你一起打開檔案。
