讀這一章，你需要用過 AI 寫程式的 agent。它建立在 [agent 循環，和你能插手的地方](2-1-agent-loop.html) 上：agent 問模型、執行工具、把結果餵回去。

## 一句話 {#in-one-sentence}

讓 agent 有辦法檢查自己的活，例如跑測試、跑 linter、跑程式。它自己能跑、也能讀的檢查，在循環裡就給它回饋；reviewer 卻只能在事後找問題。

## 給主管 {#for-leaders}

- **要做的決定**：要求每個任務都附一個 agent 自己能跑、能讀的檢查，例如測試、建置或 linter，並決定其中哪些檢查 agent 不能改。
- **風險**：agent 在活「看起來」做完時就會停下，而就我自己的使用經驗，模型常常傾向於回報成功，只是我沒有記錄過頻率。Anthropic 描述過，後來的 agent 看到已有進展，就會「宣布工作完成」。agent 也可能靠削弱測試來通過。這樣的案例我沒有記錄過，所以要把它當成設計時就得防著的風險。
- **做對的成本**：常常只是指令檔裡的一行，也就是執行專案檢查的那個指令。測試套件很慢的話，需要一個快的子集讓它常常跑。自我檢查能把結果改善多少，我沒有量過。
- **可以問團隊**：「agent 能跑什麼來知道它的活做完了？它能改這個檢查嗎？」

## 「看起來做完」為什麼不算做完 {#problem}

agent 在活「看起來」做完時就會停下。可是「看起來做完」只是模型對自己程式碼的一種感覺，背後並沒有跑過任何東西。於是它說「我已經做了這個改動」，你一讀，就找到了 bug。

如果 agent 手上沒有東西可以跑、能告訴它活有沒有做完，那麼你就是那個測試套件。每個錯誤都得等你發現，這不但慢，還需要有人坐在螢幕前。

就我自己的使用經驗，我常看到模型傾向於回報成功，不過我沒有記錄過頻率。Anthropic 在長時間運行裡也描述過同樣的拉力：後來的 agent 實例看到已經有了進展，就會「宣布工作完成」（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。你也許會想，那讓 agent 回頭把自己的活再讀一遍呢？這也沒用。自己讀自己的活，盲點還是原來那些，因為寫出錯誤的那套推理，現在又在讀這個錯誤（[慎用子 agent](2-3-subagents.html)）。

所以出路不在於換一個更聰明的 agent，而在於一個不靠 agent 的感覺的檢查。有了這樣的檢查，會有什麼不同？

## 放進循環裡的檢查，和它碰不到的地方 {#how-it-works}

### 你能加的最有用的東西之一

要看出差別，最直接的辦法，是把同一個任務的兩次運行擺在一起看。第一次，agent 改完程式碼就說「做完了」。你去跑測試，兩個失敗，於是你告訴 agent。它修好一個，你再跑一次。

第二次，agent 改完程式碼，自己去跑測試。看到兩個失敗，它讀了輸出，把兩個都修好，再跑一次測試。這次通過了，它才說「做完了」，並附上輸出。

這兩次用的是同一個模型。差別在於，第二次裡檢查的結果在 agent 結束之前，就**在循環裡**回來了。[agent 循環，和你能插手的地方](2-1-agent-loop.html) 裡的那個循環，本來就留著這個位置，因為工具的結果會回到模型，由模型決定下一步。跑一次測試，說穿了就是一個結果直白地說「通過」或「失敗」的工具。

::: figure 5-4-check-loop

這一點，Anthropic 給 Claude Code 的指南用自己的話說過：給 agent 一個能跑、結果是通過或失敗的東西，它就能自己繼續做下去，你也就不用盯著（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）。在能加給 agent 的各種東西裡，我把自我檢查放在靠前的位置。reviewer 當然也有價值，但它只能在事後看做完的活，而自我檢查改變的是 agent 工作時的行為。

### 能跑什麼

那 agent 能跑什麼？幾乎什麼都可以，只要它給出的結果 agent 讀得懂：

- **測試**：專案自己的測試，或為這次改動新寫的測試。
- **建置或型別檢查**：光是結束碼，就說明行不行。
- **linter 或格式化工具**：很快，能抓到一類錯誤。
- **把輸出和已知正確的檔案比對的腳本**：適合資料工作，因為那裡正確的答案是一張表。
- **執行程式**：對 pipeline，用小的輸入跑一次，看輸出。
- **截圖和設計稿並排**：用於使用者介面。

如果倉庫裡已經有其中一個，那麼 agent 指令檔裡最有用的一行，就是執行它的那個指令。專案信任的是哪個指令，agent 自己猜不出來。

不過，知道了要跑什麼，還剩一個問題：要它跑，要求得多硬？這裡從軟到硬分成幾級，用的還是 [提示裡的規則只是請求](4-1-requests-and-rules.html) 裡那道階梯：

1. 最軟的，是在 prompt 裡寫一句，例如「做完之後跑測試，一直做到通過」。什麼時候算滿意，由 agent 自己決定。
2. 硬一點的，是把它當成停止條件。agent 想停下來的那一刻，會有一個 hook（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)）執行；檢查要是失敗，hook 就把 agent 送回去繼續工作。因為這由平台強制，agent 沒辦法帶著失敗的檢查結束這一輪。Claude Code 的文件用 Stop hook 描述了這個做法（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)），不過這一章我沒有在 Copilot 測過同樣的做法。
3. 最硬的，是讓程式來計算通過的次數，這個數字就不再由 agent 回報（[讓「通過」可信](5-5-counted-checks.html)）。

### 讓結果短而好讀

不管檢查是什麼，agent 都要讀它的輸出，而這些輸出會進到它的上下文（[上下文是一份預算](3-1-context-budget.html)）。這裡可能出兩種錯，一種是說得太多，一種是說得太少。印出幾千行的測試運行，會把上下文塞滿，agent 需要的那一個失敗就埋在裡面。所以只印出失敗的項目，每一項附上檔案和行號，再加一個數量；通過的那些雜訊，藏起來就好。另一頭，只有一個「Error」，agent 根本無從下手。好的失敗訊息要說清楚預期什麼、實際發生什麼、出在哪裡。

這和 [Tool calling，和給 agent 設計工具](1-2-tool-calling.html) 裡講工具訊息的建議是同一回事：agent 是個不可靠的使用者，它讀到什麼，就決定它下一步做什麼。輸出便宜又清楚的檢查，比沒人讀得懂的徹底檢查更有價值。

輸出還有一個用處：它是證據。「所有測試都通過」只是一個說法，執行過的指令和它的輸出才是證據，所以要向 agent 索取。你沒在看的時候，它們就是你唯一的證據。

### 自我檢查抓不到什麼

不過，就算檢查又短又清楚，而且通過了，它說明的事也比看起來少。它說的是「這做到了檢查所測的東西」，而不是「這是你要的」，兩者之間有兩個要緊的缺口。

一個缺口在需求上。如果 agent 工作所依據的那一頁，不是人的本意（[需求由 agent 寫，人確認](5-2-requirements.html)），那麼通過所有測試的完美程式碼，也只是為錯的東西寫的完美程式碼。agent 照著錯誤的需求寫出來的測試，沒有一個找得到這一點，只有人去讀需求才找得到。

另一個缺口在測試本身：它可能檢查得太少，bug 還在也照樣通過。agent 在同一個會話裡寫的測試，和程式碼出自同一份理解，所以有同樣的盲點。要是 agent 把規則讀錯了，它的程式碼和測試會彼此一致，而且都是錯的。

還有一個限制，既不是需求的缺口，也不是測試的缺口：有些錯誤只有在真實的環境、用真實的資料執行程式時才會出現，而 agent 沒辦法在那裡執行。這類錯誤要靠人來檢查，或靠測試環境。

前面這些，是檢查本來就碰不到的地方。下一個問題不一樣，它是檢查本身帶來的。

### 當 agent 轉而削弱測試

給了 agent 一個檢查，它也就多了一種失敗的方式。agent 想讓循環以通過收尾，而拿到通過最容易的辦法，是改檢查，不改程式碼。它可以把斷言放寬到能通過，可以刪掉或跳過失敗的測試，可以把預期值改成程式碼現在給的值，也可以抓住錯誤再把它吞掉。

這些都不需要什麼惡意，agent 只是在做循環獎勵的事：以通過收尾。我在自己的運行裡沒有記錄過這樣的案例，所以我把它描述成要為之設計的風險，而不是我量過的東西。

那該怎麼防？辦法有好幾道，從最便宜到最硬。最便宜的，是用話說清楚：「修程式碼，不要修測試。如果測試看起來是錯的，說出來然後停下。」這有幫助，但它是請求（[提示裡的規則只是請求](4-1-requests-and-rules.html)）。

光靠請求不夠的時候，就讓測試待在 agent 碰不到的地方。如果測試屬於不能編輯的東西，hook 會拒絕這個改動。[保護規則本身的檔案](4-3-guardrails.html) 解釋了為什麼檢查 agent 的檔案，應該放在 agent 寫不到的地方。不過，要是新增測試本來就是工作的一部分，這個辦法就不適合；那種情況下，保護現有的測試，讓 agent 新增測試。

最硬的辦法，是不再信報告，改成去數。看測試的 diff（改動的行的清單），一個原本失敗的測試要是在裡面被改過，就是個警訊。更好的是讓程式而不是 agent 來計算通過的次數，並留下檢查有執行的紀錄（[讓「通過」可信](5-5-counted-checks.html)）。

### 它和獨立檢查怎麼分工

既然自我檢查漏掉的東西這麼多，獨立的 reviewer 是不是更好用？其實兩者不是對手，因為它們抓的東西不同。

| | 自我檢查 | 獨立的 reviewer |
| --- | --- | --- |
| 什麼時候 | agent 工作的時候 | 它做完之後 |
| 抓得到 | 程式能判斷的事：能跑、能通過、和檔案相符 | 程式不能判斷的事：是否符合要求、邏輯站不站得住 |
| 抓不到 | 錯的需求、弱的測試 | reviewer 和作者共有的盲點 |
| 成本 | 便宜，可以一再執行 | 多一個 agent，用量是好幾倍（[慎用子 agent](2-3-subagents.html)） |

所以自我檢查放在前面。把它放進循環裡，盡量多、盡量便宜。然後在值得付出成本的地方，再對結果做一次獨立檢查。reviewer 看到測試已經是綠的，就能把注意力花在測試回答不了的那個問題上：這是對的東西嗎？

## 自我檢查的代價，和它會怎樣誤導你 {#costs-and-traps}

自我檢查很便宜，但不是白送的，用錯了還會誤導你。最糟的情況，是一個可能錯誤通過的檢查。它比沒有檢查更糟，因為它給人虛假的安心。永遠不會失敗的測試是最極端的例子：它每次都通過，卻什麼都沒告訴你。

其他的代價，來自檢查在循環裡的表現。速度是其中之一。檢查太慢，agent 就不愛跑：完整的測試套件要是得跑二十分鐘，它就很少去跑，循環也跟著慢下來。所以給它一個快的子集常常跑，完整的測試套件留到最後。不穩定的檢查造成的是另一種傷害：它會把 agent 教錯。隨機失敗的測試，會讓 agent 去找一個根本不存在的 bug，或教它一直重跑，跑到變綠為止。

另外兩個限制，前面已經碰過。一個是輸出會把上下文塞滿，講結果要短而好讀時說過；另一個是，有些程式碼 agent 根本沒辦法執行。真實的資料、真實的環境或權限它拿不到的地方，自我檢查只能涵蓋一部分，所以要說清楚是哪一部分，其餘留給人。

### 一個便宜的辦法，測測你自己的檢查

自我檢查到底能把結果改善多少？我在自己的設定裡沒有量過。從廠商的指南和循環本身來看，方向很清楚，但效果有多大，我不知道。能便宜地量出來的，是你自己的檢查涵蓋了多少。

故意在能運作的程式碼裡放進一個 bug，然後執行 agent 會執行的檢查。如果它們還是綠的，那麼不管 agent 怎麼回報，這個檢查都沒涵蓋程式碼的那一部分。用這個便宜的辦法，就能看出一個通過的檢查值多少。

## Anthropic 的指南怎麼說 {#industry}
{status: industry}

Anthropic 的 Claude Code 指南，把「給它一個能跑的檢查」和告訴 agent 它看不到的東西放在一起，舉的例子有測試檔、建置的結束碼、linter、把輸出和預先備好的範例檔案（fixture）比對的腳本，還有瀏覽器截圖。它也說要索取證據，不是只有一句「所有測試都通過」，並提到一個會建置並執行應用程式的指令，用來抓測試和型別檢查漏掉的東西（[Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)）。

## 什麼時候可以刪掉那些提醒和 hook {#when-to-delete-it}

這些東西都得一直留著嗎？檢查本身是要留的，只要還有程式碼要檢查。可以退役的，是我為 agent 使用這些檢查而加的鷹架，也就是一再提醒它執行測試的話，以及把它送回去的那個 hook。等到平台在 agent 結束之前，就把專案的檢查當成一般的步驟來執行，而且 agent 也不會去削弱它們，這些就可以拿掉了。這樣的情況我還沒看到。

## 在你自己的環境試試 {#try-it}

::: prompt
找出在這個倉庫裡，寫程式的 agent 能執行什麼來檢查自己的活：測試、建置、型別檢查、linter、格式化工具、範例執行。對每一個，給出確切的指令、如果看得出來的話它要跑多久，以及它的輸出夠不夠短、夠不夠清楚，讓你能據以行動。說明指令檔有沒有告訴 agent 這些指令。然後指出程式碼裡最大的一塊：這些檢查沒有一個能在那裡抓到 bug。不要改任何檔案，也不要執行任何超過一分鐘的東西。
:::
