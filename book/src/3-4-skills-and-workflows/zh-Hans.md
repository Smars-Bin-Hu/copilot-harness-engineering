读这一章，请先读过[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)：skill 是 agent 在某项工作出现时去读的手册。

## 一句话 {#in-one-sentence}

好的 skill 讲的是这项工作在这里怎么做、容易错在哪里，而不是教科书上怎么说。一件有好几步的工作，如果已经手工按同样的做法做过大约三次，就把它变成 workflow：写明各个步骤、每一步的检查，以及哪一步需要人来定。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定团队里哪些例行工作一直在手工重复、已经可以写下来，并定下每个 skill 或 workflow 写好以后归谁管。
- **风险**：一个 skill 如果只是重复 agent 本来就知道的东西，就是白占地方，什么也没加。写好的 workflow 每次都按同一种方式运行，哪怕这种方式是错的；而这里的做法一变，它就过期了。skill 的前后对比，我没有量过。
- **做对的代价**：我的经验法则是，一件事手工做到第三次就把它写下来，这个数字是我自己定的，没有测过。真正的代价是设计和测试 workflow，然后让它一直保持最新。
- **可以问团队**：“哪件多步骤的工作我们已经手工做过三次？上一次 agent 错在哪？”

## skill 里值得写什么？ {#problem}

大多数人写的第一个 skill 是教程，比如“怎么写 SQL 查询”“怎么做代码评审”。可 agent 在训练时早就读过上千篇这样的教程，这种 skill 没有给它加任何新东西，每次加载却照样要占窗口里的地方。

而 agent 真正不知道的，是你这里的情况：哪张表是真正在用的、哪张是遗留下来的，哪一步大家容易忘，哪个文件看起来没人用，其实另一个团队在读。这些你知道，它不知道，也正是最值得放进 skill 的东西。

照[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)里的说法，**skill** 是针对某一类工作的手册。不过你知道的东西，有些不属于某一项工作，而是关于几项工作怎么一项接一项地做。这就要用到 **workflow**，它是比 skill 高一级的想法：几项工作按固定顺序排好，每一项后面有检查，并注明哪里必须由人来定。可以把它想成餐厅厨房里的菜谱卡，而不是烹饪教科书。这个词用的时候要小心，因为 Anthropic 用它指另一种东西，即由代码固定路径、在固定的点调用模型的系统（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)）。这里的 workflow 是 agent 照着做的、写下来的例行流程。

关于 skill，我拿不出量过的前后对比，只有自己遵循的推理，以及下一节末尾那些你可以自己跑的测试。那么，一个只装着你这里特有的东西的 skill，该是什么样子？

### 1. 只写 agent 会做错的

skill 草稿里的每一行，都要过一个问题：如果我删掉它，agent 会不会做错什么或漏掉什么？不会，就删掉。

这样过一遍，留下来的大致是四类。两类是团队的习惯：你的约定，比如命名、分层、新东西在哪里注册，以及不明显的默认做法，也就是团队里人人不假思索就会做的事。另外两类是陷阱，那些看着对、其实不对的东西，还有你的工具，也就是确切的命令和那个关键参数。

而该去掉的，是语言怎么工作、某个库是干什么的，以及文档第一页上就有的任何东西。Anthropic 自己的 skill 写作指南举过一个小例子：用一段话解释 PDF 是什么、读它需要一个库，是在教模型它已经知道的东西；而一行“用 pdfplumber 提取文本”，告诉它的是这里做了什么选择。他们的经验法则是“默认假设：Claude 已经非常聪明。只补充 Claude 还没有的上下文。”（[Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)）

这样删下来，skill 会很短。这没关系，因为短的 skill 会被整个读完，也会被遵守。剩下的这些，又该怎么排？

### 2. 一个起步的骨架

skill 是一个文件夹，但要紧的只是其中一个文件，它有头部和正文。这个文件的骨架大致是这样：

- 头部：一个名字，和一段描述，说明它做什么、什么时候用，以及人会说的那些话。
- 什么时候用，以及什么时候不用。
- 需要先具备什么，比如一个打开的任务，或者装好的某个工具。
- 步骤，如果这项工作是固定流程。对开放式的工作，给出评判的标准，而不是固定的步骤，因为死板的菜谱碰到稍有不同的情况就会失灵。
- 坑。

这几部分里，**坑是最有价值的**。它们是提前写好的警告，一行一条，规则加粗，后面跟理由。把它们当作一份持续更新的清单：agent 每做错一次这项工作，就加一行。这是改进 skill 最便宜的办法，也是越用越好的部分。

坑长什么样？看几条“影响分析”skill 里的。这个 skill 在写计划之前，找出一次改动牵涉到的所有地方：

- 只用一个光秃秃的列名去搜，什么都能匹配上。要把表名和列名一起搜。
- 运行时才拼出来的名字，任何文本搜索都找不到。要在结果里写明这一点，不要报告“没有影响”。
- 没搜到不等于没人用：你看不到的仓库之外的读取方是搜不出来的。把这一点写出来，并问还有谁在读它。

这些在教科书里都找不到，可每一条都是一个称职的 agent 第一次会做错的。第三条还体现了一个值得教给它的习惯：**skill 要告诉 agent 把它没看到的东西说出来**。

坑守的是工作里需要判断的部分。另一些部分根本用不着判断，因为它们只有一个正确答案，比如找出所有提到某个名字的文件、数一数用了几次。这些就写成脚本，让 skill 告诉 agent 去运行。脚本每次都给同样的答案，还不用花读取的成本，模型则去做需要判断的那一部分。影响分析这个 skill 就是这样：先用一条命令取代一连串搜索，再由模型对搜到的结果分类。

最后要留意的是长度。skill 超过大约 200 行时，把细节挪到单独的文件里，主文件只留流程和链接，这样细节只在用到它的那一步才加载。

### 3. 从真实的工作里来，不要凭想象

这些都有个前提：你得知道 agent 会在哪里做错。最好的来源，是你刚做完并纠正过的一项工作。动笔之前，打开最近一次这类真实的任务，问自己：

- agent 在哪里做错了？每一处都是一个坑。
- 你在哪里纠正了它？每一处都是一条约定。
- 你不得不去查的东西，有哪些本可以直接告诉它？

就从这些答案写 skill，而不是从你觉得一份好手册该说什么来写。我有一个 skill 只做这件事：任务结束时，它起草后来的 agent 会做错什么，附上任务里的证据，再交给人决定留下哪些。为什么由人来定，[agent 该记住什么](3-5-memory.html)里有讲。

### 4. 从 skill 到 workflow

如果你只写单个 skill，可以直接跳到“怎么检验 skill 和 workflow”。后面讲的是多步骤的例行工作。

一项工作是 skill，几项工作串起来的例行流程就是 workflow，比如“每次我们加一条 pipeline，都做这八步”。如果你是手工做的，而且每次都得告诉 agent，这就是该写成 workflow 的信号。

那什么时候该把它写下来？我的经验法则是：**同样的多步骤的事做到第三次，就停下来写下来**。一次是意外，两次可能是巧合，三次就是例行工作了。三是我自己选的，没有任何测试表明它是对的数字。workflow 划不划算，要两头比：一头是例行工作经常回来、漏一步代价又高，另一头是设计它、测试它和让它保持最新的成本。

而且 workflow 也不用凭空发明，可以从已经做完的工作里得来：

1. 拿两三个已经做完的例子，要真实的、人已经做完的。
2. 把它们并排放在一起，把每个例子里的名字换成占位符。每个例子里看起来都一样的部分，是骨架。随名字变化的部分是参数，除了名字之外还有差异的部分，就是判断所在的地方。
3. 把每一步归入四类之一，按这个顺序问，第一个回答“是”就停：

   | 问 | 如果是，它就是 | 怎么办 |
   | --- | --- | --- |
   | 它需要权限吗（审批、生产环境的运行、受保护的文件）？ | **人** | 留给人。 |
   | 几个例子里，相同的输入得到了相同的结果吗？ | **固定** | 可以用脚本做，加上测试。 |
   | 它是对结果的检查吗？ | **检查** | 能用命令检查的，就用脚本；否则给模型一份检查清单，再加上独立的 reviewer（[慎用子 agent](2-3-subagents.html)）。 |
   | 它需要理解需求吗？ | **判断** | 是模型的活，配上检查清单、指向你的文档的指引，以及常见的错误。 |
4. 不要只凭描述来设计。人说他们怎么做，和例子里实际有的东西是有差别的，而这个差别是最有用的发现。如果你没有例子，就说明这个设计是猜的。
5. 先把设计写下来请人审批，再动手做任何东西。workflow 会牵涉很多文件，所以要先由人批准设计。

拿不准一步是固定的还是需要判断的，就选判断。判断以后可以改成代码，可要是代码对一个判断做错了，就更难找出来。

### 5. 每一步带什么

workflow 是一条链，所以每个环节都要说清三件事：

- **入**：这一步之前必须成立什么。
- **出**：这一步之后有什么，要写成下一步能读的形式。
- **检查**：怎么知道它是对的。能用命令就用命令。

入、出、检查之外，等人的步骤也要明说。步骤写好以后，还有两处可能出错。一是跳过你的配置里已有的审批，workflow 不能这样做。二是不留余地。要写默认做法和条件（“……时跳过”），不写死脚本，并说明一个都不符合时怎么办。

如果一个 workflow 超过大约十几步，或者有两种不同的结果，就拆开。

### 6. 两个例子

用两个例子看看这些部分怎么拼在一起。第一个就是前面见过的影响分析，一个带脚本的 skill。在写计划之前，它的脚本在所有仓库里搜要改的名字，skill 再让模型把搜到的结果分成必须改、必须核对、没有影响三类，并要求列出搜索看不到的东西。[子 agent 那一章](2-3-subagents.html)讲过一个案例：做改动的那个 agent 漏掉了跨领域的两处引用，直到独立检查才发现。那只是一个案例，不是比率，但先做这一搜的 skill，会把这个发现提前。

第二个是测试指南，一个以人为终点的 workflow 步骤。改动写回真正的仓库之后，agent 不能在测试环境里运行任何东西，得由人来跑。所以 skill 写出每个环境里该跑什么、预期结果是什么、要把什么带回来；人带着结果回来时，skill 再按事先写好的标准来判断。这个设计的关键在于它在哪里停下来：停在人这里，附一份清楚的清单，说明要做什么、要带回什么。

### 怎么检验 skill 和 workflow

这些做法管不管用，是可以测的。单个 skill 有两个测试，一是能不能被找到，二是有没有改变什么，都在[指令与 skill：只加载需要的](3-3-instructions-and-skills.html)里。Anthropic 的指南还加了一个习惯：先做测试用例，再多写东西。测试用例取自没有这个 skill 时 agent 做错的任务，然后只写刚好够修正它们的内容。

而 workflow 还要多一个测试，就是它站不站得住。拿一个不属于你那几个例子的情况去跑，失败的地方，要么是缺了一种变体，要么是你把某一步归错了类。

## 写下来的做法要付出什么，会怎样出错 {#costs-and-traps}

不过，过了这些测试的 skill，照样会过期。它写的是这里的做法，而这里会变。一个让你用已经不存在的命令的 skill，比没有还糟，所以它描述的东西一变，就去看一眼，并给每个 skill 指定负责人。

坑本身也可能错，错的坑会把 agent 教错。比如从单个案例写出来的坑，到了下一个案例可能就误导人。所以要把理由和规则放在一起，读的人才能判断它是否仍然适用。

固定的步骤也有代价：灵活性。严格的菜谱适合固定流程，不适合开放式的工作。如果 agent 照着你的步骤走进了它们不适用的情况，说明步骤写得太死。

workflow 还可能错得没人发现，因为它每次都按同样的方式运行，错的方式也一样。检查就是为此而设的，所以每一步都要有一个。

最后，像开头说的，我没有在很多次运行中比较过有没有某个 skill 的 agent，所以上面的 skill 测试只是初步的，不是测量（[一次运行证明不了什么](6-4-variance.html)说了怎么量）。

## 官方指南也这么说吗？ {#industry}
{status: industry}

Anthropic 的 skill 写作指南在最要紧的一点上和我一样：假设模型已经非常聪明，只补充它没有的东西，并用“这一段值得它花的 token 吗？”来质疑每一段。（[Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)）它还建议先做测试用例，并把 skill 控制在大约 500 行以内。我自己的上限大约是 200 行，更严格，但那是一种习惯，不是量出来的值。至于 VS Code 的 skill 文档，它描述了同样的格式和三阶段加载，要求指令写得“清楚”“具体”，需要时给出分步的做法。它也明说，发现机制并不保证 skill 会被用上。（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)）

## 什么时候删掉一条坑、一个步骤或整个 workflow {#when-to-delete-it}
{status: industry}

模型不再犯那个错，或者代码让它不可能再犯时，这条坑就可以删掉。所以换模型时要检查一遍：有的可能已经成了累赘，而失效的坑只会占地方。平台替你做了的固定步骤，就可以删掉。整个 workflow，在很久没有运行过，或者例行工作本身已经没有了的时候，也可以删掉。

留下的是这个习惯：做完一项真实的任务，看看 agent 做错了什么，把它写在会被读到的地方。

## 在你自己的环境里试试 {#try-it}
