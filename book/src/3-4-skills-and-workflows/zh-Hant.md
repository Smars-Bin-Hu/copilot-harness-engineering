讀這一章，請先讀過[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)：skill 是一本手冊，工作出現時 agent 才去讀。

## 一句話 {#in-one-sentence}

好的 skill 說的是這份工作在這裡怎麼做、哪裡容易出錯，不是教科書怎麼說。一份有好幾步的工作，如果用同樣的方式手動做過大約三次，就把它變成 workflow：每一步、每一步的檢查，以及哪一步需要人。

## 給主管 {#for-leaders}

- **要做的決定**：決定團隊有哪些例行工作是手動重複做的、而且已經準備好寫下來，以及誰負責每一份寫好的 skill 或 workflow。
- **風險**：重複 agent 本來就知道的內容的 skill，佔位子，什麼也沒加。寫好的 workflow 每次都用同樣的方式跑，包括錯的方式；而且這裡做事的方式一變，它就過期。我沒有 skill 的前後實測數字。
- **做對的成本**：我的經驗法則是，一個例行工作第三次手動做的時候，就把它寫下來（這個數字是我選的，沒測過）。設計和測試 workflow，並讓它保持最新，才是真正的價錢。
- **可以問團隊**：「哪一份多步驟的工作，我們手動做過三次？上一次 agent 在哪裡做錯了？」

## 問題 {#problem}

大多數人寫的第一個 skill 是教學。「怎麼寫 SQL 查詢。」「怎麼做 code review。」agent 在訓練時讀過上千份這樣的教學。你的 skill 沒有加進任何它不知道的東西，而每次載入，還要佔視窗裡的位子。

agent 不知道的，是你這個地方。哪張表是真的、哪張是遺留的。哪一步人們會忘。哪個檔案看起來沒人用，其實另一個團隊在讀。這些是你知道、它不知道的，也是最值得放進 skill 的。

先說兩個詞。

- **skill** 是某一類工作的手冊（見[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)）。
- **workflow** 是比 skill 再高一層的想法：幾份工作的固定順序，每一份後面有檢查，並標明哪裡必須由人決定。想想餐廳廚房裡的食譜卡，而不是烹飪教科書。要小心：Anthropic 用同一個詞指別的東西，一種由程式碼固定路徑、在固定的點呼叫模型的系統（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)）。這裡的 workflow 是寫下來、讓 agent 照著做的例行流程。

關於 skill，我沒有可以給你的前後實測。下面的推理是我遵循的，最後的測試讓你自己去量。

### 1. 只寫 agent 會做錯的

草稿 skill 裡的每一行，都問：如果我刪掉它，agent 會做錯或漏掉什麼嗎？不會，就刪掉。

留下的：

- **你的慣例**。命名、分層、新東西在哪裡登記。
- **不明顯的預設**。團隊裡每個人都不假思索在做的事。
- **陷阱**。看起來對、其實不對的東西。
- **你的工具**。確切的指令，附上要緊的那個參數。

刪掉的：語言怎麼運作、函式庫做什麼，以及文件第一頁上的任何東西。Anthropic 自己的 skill 寫作指南給了一個小例子：一段解釋 PDF 是什麼、要讀它需要函式庫的文字，教的是模型已經知道的；而一行「用 pdfplumber 抽取文字」，說的是已經做好的選擇。他們的經驗法則是「預設假設：Claude 已經非常聰明。只加 Claude 還沒有的上下文。」（[Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)）

沒有這種行的 skill 很短。沒關係。短的 skill 會被整個讀完、也會被遵守。

### 2. 起步用的骨架

skill 是一個資料夾。要緊的部分是一個檔案，有檔頭和正文：

- **檔頭**：名稱，和一段描述，說明它做什麼、什麼時候用，以及人會說的字。
- **什麼時候用**（和什麼時候不用）。
- **先要有什麼**。例如一個打開的任務，或一個裝好的工具。
- **步驟**，如果這份工作是固定流程的話。開放式的工作，就給判斷用的標準，不給固定的步驟：死板的食譜遇到稍有不同的情況就壞了。
- **陷阱**（gotchas）。

**陷阱是最有價值的部分**。它們是事先寫好的警告，一行一條：規則用粗體，然後是理由。把它們當成活的清單：每次 agent 把這份工作做錯，就加一行。這是改進 skill 最便宜的辦法，也是用得越多進步越多的部分。

形狀的例子，來自一個「影響分析」skill，它在寫計劃之前，找出一項改動碰到的所有東西：

- 只用光禿禿的欄位名稱，會對上所有東西。要把表和欄位一起搜尋。
- 在執行時才組出來的名稱，任何文字搜尋都找不到。要在結果裡說明這一點，不要回報「沒有影響」。
- 沒有命中不等於沒人用：你看不到的倉庫之外的讀取者是看不見的。把這寫下來，並問還有誰在讀。

這些都不在教科書裡。每一條都是能幹的 agent 第一次會做錯的事。第三條還顯示了一個值得教的習慣：**skill 要 agent 說出它看不到什麼**。

**腳本**。如果工作的一部分只有一個正確答案（找出所有提到某個名稱的檔案、數有幾處用到），就放進腳本，由 skill 告訴 agent 去執行。腳本每次給出同樣的答案，不花任何閱讀的成本；模型做需要判斷的那部分。那個 skill 就是這樣做的：一條指令取代一連串的搜尋，然後模型把命中的結果分類。

**長度**。skill 長到超過約 200 行時，把細節移到另外的檔案，主檔案只留流程和連結。這樣細節就只在需要它的那一步才載入。

### 3. 從真實的工作取材，不要憑想像

skill 最好的來源，是你剛做完並修正過的一份工作。動筆之前，打開最近一次這類真實的任務，問：

- agent 在哪裡做錯了？每一處都是一條陷阱。
- 你在哪裡糾正了它？每一處都是一條慣例。
- 你得去查的什麼東西，本來可以直接告訴它？

從這些寫 skill，不要從你覺得好手冊該說什麼來寫。我有一個 skill 只做這件事：在任務結束時，它起草後來的 agent 會做錯什麼，附上任務裡的證據，由人決定留下什麼。為什麼由人決定，見[agent 該記住什麼](3-5-memory.html)。

### 4. 從 skill 到 workflow

如果你只寫單一的 skill，可以跳到「測一測你自己的設定」。其餘是給多步驟的例行工作的。

一份工作是 skill。幾份工作組成的例行流程是 workflow。「每次我們加一條 pipeline，就做這八步。」如果你手動做，而且每次都得告訴 agent，這就是跡象。

我的經驗法則：**同樣的多步驟事情，做第三次時，停下來寫下來**。一次是意外。兩次可能是巧合。三次就是例行工作。三次是我自己選的；我沒有測試顯示這是對的數字。當例行工作常常回來、漏掉一步代價又高時，workflow 才划算。和這相對的，是設計它、測試它、讓它保持最新的成本。

怎麼得到 workflow 而不用憑空發明：

1. **拿兩三個做完的範例**。真的，已經由人做完的。
2. **把它們並排放**，把每個範例的名稱換成佔位符。在每個範例裡看起來一樣的部分，是骨架。隨名稱變的部分，是參數。除了名稱之外還有不同的部分，是判斷所在的地方。
3. **把每一步歸入四種之一**，按這個順序問，第一個「是」就停：

   | 問 | 如果是，它是 | 怎麼辦 |
   | --- | --- | --- |
   | 它需要權限嗎（批准、正式環境的執行、受保護的檔案）？ | **人** | 留給人。 |
   | 範例裡同樣的輸入給出同樣的結果嗎？ | **固定** | 腳本可以做，附上測試。 |
   | 它是對結果的檢查嗎？ | **檢查** | 指令能檢查的，用腳本；否則給模型一份檢查清單，和一個獨立的 reviewer（[慎用子 agent](2-3-subagents.html)）。 |
   | 它需要理解需求嗎？ | **判斷** | 這是模型的工作，附上檢查清單、指向你的文件，和常見的錯誤。 |
4. **不要只憑描述來設計**。人們說自己怎麼做，和範例裡實際有的，是不同的。這個差異是最有用的發現。如果你沒有範例，就說明這份設計是猜的。
5. **在建造任何東西之前，先寫下來請人批准**。workflow 會碰到很多檔案。先由人批准設計。

不確定一步是固定還是判斷時，選判斷。判斷以後可以變成程式碼；對判斷做錯了的程式碼，更難找出來。

### 5. 每一步帶什麼

workflow 是一條鏈，所以每個環節說三件事：

- **進**：這一步之前必須成立的。
- **出**：這一步之後存在的東西，形式要讓下一步讀得懂。
- **檢查**：怎麼知道它是對的。可能的話用一條指令。

等人的那些步驟要明說。有兩件事要提防。workflow 不能跳過你的設定裡已有的批准。而且它應該留有餘地：寫預設和條件（「……時跳過」），不要寫固定的腳本，並說明遇到都不符合的情況該怎麼辦。

workflow 如果超過約十幾步，或有兩種不同的結果，就拆開。

### 6. 兩個例子

**影響分析**（帶腳本的 skill）。計劃之前，找出一項改動碰到什麼。腳本在每個倉庫裡搜尋要改的名稱。skill 讓模型把命中的結果分成必須改、必須檢查、沒有影響，並要求列出搜尋看不到的東西。這就是[慎用子 agent](2-3-subagents.html)那一章提到的情況：有一次，在一個案例裡，實作者漏掉了跨領域的兩處引用，只有獨立檢查找到了它們。這是一個案例，不是比率。先做這個搜尋的 skill，會把這個發現提前。

**測試指南**（一個終點是人的 workflow 步驟）。改動寫回去之後，agent 在測試環境裡無法執行任何東西；是由人來執行的。所以 skill 寫出在每個環境裡要跑什麼，附上預期的結果和要送回什麼。人帶著結果回來時，skill 按之前寫好的標準來判斷。這個設計的重點是它停在哪裡：停在人那裡，附上一份清楚的要做什麼、帶回什麼的清單。

### 測一測你自己的設定

**找得到嗎？有改變什麼嗎**？單一 skill 的兩個測試在[指令與 skill：只載入需要的](3-3-instructions-and-skills.html)。Anthropic 的指南加了一個習慣：寫很多之前先建立測試案例，取自 agent 沒有這個 skill 時做錯的任務，然後只寫剛好能修好它們的部分。

**workflow 站得住嗎**？用一個不是你範例的案例去跑。失敗的地方，是缺少的變體，或是你歸錯類的步驟。

## 代價和陷阱 {#costs-and-traps}

**skill 會過期**。它說的是這裡的做事方式，而這裡會變。一個說要用已經不存在的指令的 skill，比沒有還糟。它描述的東西一變，就去看一看每一個，並給每一個負責人。

**錯的陷阱會教錯**。根據單一案例寫的陷阱，在下一個案例可能誤導人。把理由和規則放在一起，讀的人才能判斷它是否仍然適用。

**固定的步驟要付出彈性的代價**。緊的食譜適合固定的流程，不適合開放的工作。如果 agent 照著你的步驟走進了它們不適用的情況，說明它們太緊了。

**workflow 可能錯得沒人看得見**。它每次都用同樣的方式跑，包括錯的方式。檢查就是為此而設的；每一步都給一個。

**我沒量的**。我沒有在很多次運行中，比較過有沒有某個 skill 的 agent。上面的 skill 測試是第一輪，不是量測（[一次運行證明不了什麼](6-4-variance.html)說了怎麼量）。

## 業界怎麼說 {#industry}
{status: industry}

VS Code 的 skill 文件描述了同樣的格式和三階段載入，並說要把指令寫得「清楚」、「具體」，在適用的地方附上一步步的程序。它也明確說，發現機制不保證 skill 一定會被使用。（[Agent skills](https://code.visualstudio.com/docs/copilot/customization/agent-skills)）Anthropic 的 skill 寫作指南給的建議和我遵循的一樣：假設模型已經很聰明，只加它沒有的，並用「這一段值得它花的 token 嗎？」來質疑每一段。（[Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)）它還建議先建立測試案例，並讓 skill 低於約 500 行；我自己約 200 行的上限更嚴，那是習慣，不是量出來的值。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

模型不再犯那個錯，或程式碼讓它不可能發生時，陷阱就可以去掉。換模型時檢查它們：有些可能已經是死重，而死掉的陷阱只佔位子。平台替你做了的固定步驟，就可以去掉。整個 workflow，在很久沒跑過、或例行工作本身消失時，可以去掉。

留下來的是習慣：做完一個真實的任務後，看 agent 做錯了什麼，把它寫在會被讀到的地方。
