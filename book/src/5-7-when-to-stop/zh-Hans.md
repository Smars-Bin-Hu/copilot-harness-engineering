这一章接着[慎用子 agent](2-3-subagents.html)里的无人值守的运行往下讲：一个 hook 让 agent 在没人看着的时候，沿着待办清单一直干下去。那一章讲的是这样的运行怎么跑起来，这一章讲它怎么收场。

## 一句话 {#in-one-sentence}

无人值守的 agent，只能走到它的停止规则管得到的地方。所以要提前把规则设好，用总预算，而不只是步数，同时还要防着它过早宣布“做完了”。

## 写给管理者 {#for-leaders}

- **要拍板的事**：批准无人值守的运行之前，先把它的停止规则设好，用总预算，而不只是步数，并要求每次停下都交回原因。
- **风险**：你一走，就不再是那条停止规则了。运行可能循环好几个小时，可能在一个注定成不了的步骤上烧掉一晚上的用量，也可能提前停下，还说自己做完了。我的配置有步数和时间的限制，但还没有总预算，我也把无人值守的运行叫作 beta。无人值守的运行是否比人盯到最后更好，我没有测过。
- **做对的代价**：每个任务几条规则，加一个预算数字。规则收得紧，代价是停得更多，早上得有人待命。反过来，交回的东西要是含糊，比盯着看还费时间。
- **可以问团队**：“如果这个任务通宵跑、中途出了问题，什么会让它停下来？我早上会看到什么？”

## 你走了以后，谁来叫停？ {#problem}

你盯着 agent 的时候，你就是它的停止规则。看到它跑偏了，你就按停。可你一走，这条规则也跟着你走了，剩下的只有你走之前写下的东西。

所以对无人值守的运行，该问的不是“它行不行”，而是“不行的时候会怎样”。它可能循环好几个小时，也可能在一个注定成不了的步骤上烧掉一晚上的用量。碰上只有你才能做的选择，它可能自己就拍了板。它还可能反过来，提前停下，说自己做完了。

这几种情况各需要一条不同的规则，而且都得在你走之前设好。归结起来是三个问题：运行什么时候必须停？停下时交回什么？我们怎么知道它真的做完了？

## 什么时候停，交回什么，怎样才算真做完 {#how-it-works}

::: figure 5-7-stop-points

### 每条停止规则，抓一种出错的方式

第一个问题，什么时候必须停，答案不止一个，因为每条停止规则抓的是运行出错的一种方式。这些规则有一个共同的原则：**由代码根据事实来判断，不由 agent 判断**。一个卡住的 agent，最没资格判断自己是不是卡住了。

其中三条你已经在[慎用子 agent](2-3-subagents.html)里见过，分别是步数和时间的上限、一次运行里护栏拒绝了 agent 两次就停、没有任何一步被勾掉就停，具体数字也在那一章里。（**一步**是待办清单上的一项。这条停止规则不是[保护规则本身的文件](4-3-guardrails.html)里的熔断器，那个熔断器针对的是同一个会话里同一次拒绝反复出现。）那些是我配置里的数字，只是例子，算不上什么真理：是我选的，我也没有测过它们合不合适。

另外两条，同样可以根据事实来判断。一条是计划变了。人批准的是一份计划，运行只被允许执行这份计划，所以计划一变，授权立刻失效。另一条是检查次数用完了：独立检查一直不通过，直到达到它的上限（见[让“通过”可信](5-5-counted-checks.html)）。

最后一种不一样，因为有些停止是事实显示不出来的。比如两张表对同一个字段的定义不一样，计划里又没说用哪个，这一点只有 agent 看得到。所以它可以自己停，但必须写明原因，而且只限于需要人的情况，小事不行。

### 预算是总量，不是次数

上面这些规则数的都是东西，不是步数就是拒绝次数。可你真正怕的是**花费**，而次数限制不了花费。二十个小步骤和二十个每步都启动帮手的步骤，账单根本不是一回事。

能限制花费的是**预算**，也就是对用量和时间的一个总量，把主 agent 和它所有的帮手合在一起算。帮手拿到的是剩下的部分，而不是自己另有一份额度。用量和时间，只要越过其中一条线，运行就停。

我自己的配置还没有这个（它有上面那些次数限制和一个时间限制），不过可以这样搭。由人给每个任务设一个预算，用量和分钟数各一个。每一步之前，hook 根据平台自己的会话记录，把主会话和每个帮手会话的用量加起来，到了线就停下运行，把“预算”写成原因。至于帮手的用量能不能及时出现在记录里、赶得上叫停，我没有查过。

而且，按用量算的预算，并不完全等于按钱算的预算：服务商已缓存的输入，读取价格约是基础价格的十分之一（见[选模型：看每次成功的成本](1-1-models-and-cost.html)），只是 Copilot 怎么计这部分，我没有查过。

有些工具已经为非交互的运行提供了简单的版本。Claude Code 有 `--max-turns` 和 `--max-budget-usd`（我自己没试过），都只用于 print 模式（`claude -p`）。金额上限对照的是客户端的估算，不是你的账单，而且可能被超过。子 agent 的花费也算在里面，一旦达到上限，就不能再启动新的子 agent（见 [CLI reference](https://code.claude.com/docs/en/cli-reference)）。

### 回来的人该看到什么

不管是哪条规则触发的，回来的人面对的都是一次已经停下的运行。它要是不说明为什么停，留给人的就是一个谜。所以停下时必须交回三样东西：

1. **为什么停**，用一个人能据此行动的词：预算、被拒绝、没有进展、需要决定。
2. **走到哪了**：做完的步骤、正在做的那一步，以及工作的状态。
3. **人要决定什么**，一句话。

在我的配置里，由事实触发的停止，原因由代码来写，而 agent 自己停的时候，则由它写一句话。这句话的指令是：哪一步卡住了，为什么，你要决定什么。光写“遇到了问题”是不够的。

agent 一路上做的决定也很重要。计划没定、由 agent 自己选的每一处，它都要写一行，说明选了什么、为什么。这份日志，人回来时会读，无人值守的工作也正是靠它才能被复核。

### “做完了”说得太早

前面担心的，都是该停的时候不停。反方向的失败同样真实：运行停得太早，还说自己做完了。Anthropic 在一个长时间运行的编程 agent 上描述过这种情况：“后来的 agent 实例四下看看，发现已经有了进展，就宣布任务完成”（[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）。

说到底，停下来本来就是交给 agent 的事，所以它说“做完了”是有来由的。正因为这样，运行能不能结束，得看代码能核对的事实，不看 agent 怎么说：

- **清单上的每一步都勾掉了。**
- **独立检查通过了**，由代码计数，针对的是工作现在的这个版本。
- **计划就是当时批准的那一份。**
- **写回计划已经做好**，供人阅读（见[两道门：人在哪里审批](5-3-two-approvals.html)）。

到这时，“做完了”才是一种状态，而不是一个声明。

即便这样也不严密，因为 agent 可以不完成就勾掉一步。检查者在最后读整个结果，人读整个 diff，但没有任何代码能证明第 7 步真的做了。所以我把勾当作声明，把运行结束时的检查当作算数的东西。

## 安全的代价，和停止规则做不到的事 {#costs-and-traps}

这些规则让运行更安全，但不是白来的。规则越多，能一口气跑完的晚上就越少：收得紧的运行，很多个晚上都会中途停下，交回的东西不多，早上得有人待命接手。安全的代价就落在这里。无人值守是否比人盯到最后更好，我没有测过，所以它在我的配置里还叫 beta。

停下也不等于有了答案：每一次停下，留下的都是做了一半的活。在关卡处拍下的快照（见[两道门：人在哪里审批](5-3-two-approvals.html)），能让人看到运行停下时的状态。即便如此，交回的内容要是含糊，人花的时间还是比盯着看更多。

不过，有些活根本不该无人值守，不管停止规则多好都一样。[两道门：人在哪里审批](5-3-two-approvals.html)里的三点在这里同样适用：花真钱的、授予权力的（比如写入共享仓库）、无法撤销的活，都需要人。

还有一个坑是留给 agent 的，不是留给你的：为了躲开拒绝而绕路。拒绝是系统在说：这一步超出了范围。所以我给 agent 定的规则是：按理由说的改一次，还不行，就停。

## 什么时候删掉这些规则，什么会留下 {#when-to-delete-it}

这些停止规则之所以存在，是因为平台没有提供它们。如果平台提供覆盖整个运行（包括帮手）的总预算，就用平台的。不管怎样，基于事实来停的想法都会留下：agent 说的“我做完了”不是终点线。
