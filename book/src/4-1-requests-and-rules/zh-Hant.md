讀這一章，請先讀過 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)：hook 是工具呼叫都要經過的程式碼，它可以拒絕這次呼叫。

## 一句話 {#in-one-sentence}

寫在提示裡的規則只是請求；寫在程式碼裡的規則才是規則。先從文字開始，當一條規則一直被違反、或傷害無法挽回時，再把它搬進程式碼。

這一章談的是一條規則守得多牢（安全）。它不談哪個最便宜的東西能做出判斷；那是[誰來判斷：程式、便宜模型、主模型、人](5-9-who-decides.html)。

## 給主管 {#for-leaders}

- **要做的決定**：決定哪些規則可以只留作寫下來的文字，哪些必須由程式碼強制執行。一條規則在一直被違反、傷害無法挽回、或其他步驟依賴它時，就搬進程式碼。
- **風險**：寫在提示裡的規則只是請求。在我自己的設定裡，有個 hook 把我的規則放在每個 prompt 的開頭，它每次都執行了，但還是有很多 prompt 到達時沒有帶著規則。那是一個設定、2026 年 10 月的一批資料，不是一般的比率，而寫下來的規則多常被違反，我沒有數字。
- **做對的成本**：程式碼有價錢：要寫、要測、平台變動時要維護。大多數規則不需要它，所以是少數幾條規則，不是全部。
- **可以問團隊**：「我們的規則裡，哪些如果 agent 違反一次就會造成無法挽回的傷害？其中每一條是由程式碼守著，還是只寫在提示裡？」

## 問題 {#problem}

你在指令檔裡寫了一條規則：「絕對不要碰產生出來的檔案」。agent 遵守了一個星期。然後它沒有。你再讀一遍規則。它還在，也很清楚。檔案裡什麼都沒變。變的是，agent 有別的事要想。

**prompt** 是模型讀的文字：你的請求、指令檔、它載入的 skill。寫在那裡的規則，和別的句子一樣是一句話。模型把它和其他句子放在一起權衡，有時其他句子贏。對話越長，其他句子越多（[長對話會變差](3-2-long-sessions.html)）。

就連把這句話送到模型面前，也不是確定的。在 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)裡，我數了我自己設定在 2026 年 10 月的一批 prompt：有個 hook 把我的規則放在每個 prompt 的開頭，它每次都執行了，但還是有很多 prompt 到達時沒有帶著規則。那是一個設定、一批資料，不是一般的比率。傳達規則都可能失敗，遵守規則更可能失敗。

所以規則有兩種，而且很容易搞混：

- **請求**。你請模型照這樣做。它通常會。沒有人能保證它永遠會。
- **規則**。有程式碼擋在路上。只要程式碼在執行、看得到這次呼叫，不管模型怎麼想，它都會被拒絕。

任何一定要成立的東西，必須是第二種。但程式碼不是免費的，大多數規則也不需要它。這一章的問題是：哪條規則放在哪裡？

## 原理 {#how-it-works}

### 四個牢固程度

一條規則可以守在四個程度。每一個保證的東西不同，每一個也都有限制。

::: figure 4-1-ladder

| 程度 | 它是什麼 | 它保證什麼 | 它的限制 |
| --- | --- | --- | --- |
| **文字** | 規則寫在指令檔、skill 或 agent 的正文裡 | agent 知道這條規則和它存在的理由 | 它可能不遵守 |
| **自己檢查的指令** | agent 透過你的一個小程式來做這個操作，程式在動手之前先檢查條件 | 在任何平台上，每次都是同樣的結果 | 它只守經過它的東西。agent 如果手動編輯檔案，這個指令根本不會被呼叫 |
| **會拒絕的 hook** | 平台在工具呼叫之前執行的程式碼，可以說不 | 在我試過的模式裡，呼叫會被擋下，即使沒有人看著 | 它依賴平台，而且它看到的是呼叫，不是效果（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)） |
| **事後發現** | 健康檢查（一個測試設定是否健全的指令）、跑一次測試、讀紀錄 | 違反可以被發現、被計數 | 它什麼也預防不了。它是偵測，不是預防 |

最後一個程度的種類不同。它不守規則；它告訴你其他的有沒有守住。每一個程度你都需要它，因為你看不到它被違反的規則，是你在猜的規則。

中間兩個需要解釋一下。這裡的**指令**，是你在 agent 內建工具旁邊給它的一個程式。agent 不再「建資料夾、複製檔案、寫狀態」，而是執行一個指令，三件事一次做完，如果前提條件不成立，就拒絕開始。規則在指令裡面。**hook** 則相反：agent 想做什麼就做什麼，hook 在每次呼叫執行前先看一眼。

### 規則該放哪裡

每條規則都從最底層開始，用文字。一句話寫起來便宜、改起來也便宜，而且對大多數規則，模型會照做。三件事有一件成立時，再往上搬。

1. **它一直被違反**。你看到它發生不止一次，而更好的句子沒有解決。對一條因為離得太遠而被無視的規則，重新措辭是錯的答案；程式碼才是對的。
2. **傷害無法挽回**。一個被刪掉的分支、一個推上去的 commit、一個沒人備份就被覆寫的檔案。違反一次就太多了，所以不要等第二次。
3. **其他部分依賴它**。如果後面的步驟相信前面的規則守住了（一筆「檢查通過」的紀錄、一個批准），那麼規則一破，後面的步驟也跟著破。

然後選夠用的最低程度。如果指令能守住這條規則，就不要做 hook。hook 要寫、要測、要在平台變動中一直維持（[把執行層當軟體來設計](4-4-enforcement-design.html)）。agent 有很多方式可以接觸到那樣東西、而你無法把它們全部導到你的指令時，才用 hook。

### 用程式碼擋，用文字教

把一條規則搬進程式碼時，不要刪掉那句話。留一句。它們做不同的事。

- **程式碼負責擋**。它不依賴模型記得什麼。
- **文字負責教**。它在 agent 撞上牆之前，告訴它這條規則為什麼存在、該改做什麼。

沒有文字，agent 一次又一次撞上拒絕，並試別的方式繞過去。沒有程式碼，文字又變回請求。拒絕的訊息是橋樑：它是帶著一句話的程式碼。好的訊息說明為什麼被拒絕、接下來做什麼（怎麼寫這些，見[詢問不是限制](4-2-ask-vs-refuse.html)）。

同一種拆分的另一面：只有判斷才能決定的事，不要放進程式碼。「這是對的需求嗎？」「這個改動好不好？」沒有可以比對的模式。這些仍然是文字，你從外面去檢查，用獨立的 reviewer（[慎用子 agent](2-3-subagents.html)）。

### 一個往上搬的例子

假設你的規則是：「產生出來的檔案絕不手動編輯」。步驟看起來是這樣。

1. **文字**。指令裡一行，附上理由：它們會被重新建置，手動編輯會丟掉。
2. **它發生了兩次**。你加一個 hook 層級的檢查：對那些路徑呼叫編輯工具，會被拒絕，附上理由和重新產生它們的指令。
3. **出現新的缺口**。agent 現在用終端機去寫那個檔案。你把這個做法常見的寫法加進 hook。你也知道它抓不到先寫好一支腳本、之後再執行的情況，所以你留著那一句文字，再加一個測試，事後找出被改過的產生檔案。

這是一個編出來顯示步驟的案例。每一步都加上了一個程度，沒有拿掉任何一個。

### 測一測你自己的設定

**一個三分鐘的練習**。寫下你今天給 agent 的三條規則。每一條回答：它是文字、指令、hook，還是事後檢查？違反一次能挽回嗎？它被違反過兩次嗎？第一個問題答「不是」、第二個答「不能挽回」、第三個答「是」的規則，就是最先要往上搬的。

## 代價和陷阱 {#costs-and-traps}

**程式碼有價錢**。它要寫、要測，平台改工具名稱或事件時要更新。你搬進程式碼的規則越多，要背的就越多。

**程式碼也會擋錯東西**。太寬的模式會擋掉真正的工作。agent 沒辦法跟拒絕爭辯，所以一次誤拒絕，就是一個卡住的任務。每條程式碼規則，訊息裡都需要一個理由，還要有辦法看出是哪條規則觸發了。

**hook 只看得到呼叫**。hook 裡的規則，對它認得的寫法有效。對一個一心想繞過它的 agent，它守不住。對於絕不能碰的東西，見[有些東西根本不給](4-5-least-privilege.html)。

**程式碼也會失敗**。hook 是軟體。它壞了，平台可能拒絕每一次呼叫，也可能放行每一次呼叫，看它是怎麼壞的（[把執行層當軟體來設計](4-4-enforcement-design.html)）。

**只有 agent 自己守著的規則，不算紀錄**。別讓 agent 成為它遵守了規則的唯一見證。凡是之後你要依賴的，都讓程式碼來寫紀錄（[讓「通過」可信](5-5-counted-checks.html)）。

**我沒有數每個程度多常失敗**。這個階梯來自對一個 harness 的經驗和文件。光靠文字多常被違反，我沒有數字，而任何人如果給你一個數字、卻不說是什麼模型和什麼任務，我不會相信。

## 業界怎麼說 {#industry}
{status: industry}

平台文件在這種拆分上是一致的，只是各有各的說法。VS Code 的 hooks 頁面說，hook 和指令不能替代強制執行的權限、沙箱或企業控制（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)）。兩個方向都要這樣讀：指令是最弱的程度，而 hook 也不是最強的程度。接下來的幾章，就是沿著這個階梯往上走。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

有兩件事會讓這個階梯隨時間縮短。

- **模型越來越會遵守文字**。有些你因為模型無視而搬進程式碼的規則，現在可能已經被遵守了。找出來的辦法，是把程式碼規則關掉，跑同樣的任務並計數（[模型升級了，就要刪](6-5-model-upgrades.html)）。選過去曾經觸發這條規則的任務，每個跑幾次，數違反的次數。跑幾次只能看出很大的變化。我沒有跑過。只在違反可以挽回的地方才關掉。
- **平台接手**。當平台自己能在每種模式下拒絕一個路徑或指令時，你自己為它做的 hook 就可以去掉。留著那一句文字。

不會消失的是這個問題：哪條規則守得多牢，為什麼。

## 在你自己的環境試試 {#try-it}

不用裝 harness。在你自己的倉庫裡打開 agent，貼上：

::: prompt
讀這個專案給 agent 的每一條規則：指令檔、skill、agent 檔、hook 和權限設定。每一條規則，說明它由哪個程度守著：只有文字、自己檢查的指令、會拒絕的 hook 或權限設定，還是事後執行的檢查。然後列出只有文字、但違反會造成無法挽回的傷害、或其他步驟依賴它的規則。輸出一張表，包含規則、它的程度，以及你建議保留還是往上搬。不要改任何檔案。
:::

::: prompt
/harness-rookie-wondering 我讀完了「提示裡的規則只是請求」這一章。請教我這個 harness 怎麼決定每條規則放在哪裡：執行的階梯（主題 14）和背後的設計選擇（主題 15）。挑三條規則，告訴我每一條在哪個程度、什麼情況會讓你把它往上搬，並帶我打開真實的檔案。
