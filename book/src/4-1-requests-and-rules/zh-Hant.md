這一章假設你已經讀過 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)，知道 hook 是工具呼叫都要經過的程式碼，可以拒絕這次呼叫。

## 一句話 {#in-one-sentence}

寫在提示裡的規則只是請求；寫在程式碼裡的規則才是規則。先從文字開始，等一條規則一直被違反，或違反的後果無法挽回，再把它搬進程式碼。

這裡關心的是規則守得多牢，說到底是安全的問題。至於一個判斷交給誰、交給什麼來做最便宜，那是另一個問題，[誰來判斷：程式、便宜模型、主模型、人](5-9-who-decides.html)會談。

## 給主管 {#for-leaders}

- **要做的決定**：哪些規則可以只留在文字裡，哪些必須由程式碼強制執行。一條規則一直被違反、一旦違反就會造成無法挽回的傷害，或其他步驟依賴它時，就該搬進程式碼。
- **風險**：寫在提示裡的規則只是請求，甚至可能根本送不到模型面前。2026 年 10 月，我數過自己設定裡的一批 prompt：有個 hook 會把我的規則放在每個 prompt 的開頭，它每次都執行了，但還是有很多 prompt 到達時沒有帶著規則。這只是我這一套設定、一批資料，不是一般的比率。寫下來的規則多常被違反，我也沒有數字。
- **做對的成本**：程式碼有成本，因為它要寫、要測，平台變動時還要跟著維護。大多數規則不需要它，所以這筆成本只花在少數幾條規則上，不是全部。
- **可以問團隊**：「我們的規則裡，哪些只要 agent 違反一次，就會造成無法挽回的傷害？其中每一條，是由程式碼守著，還是只寫在提示裡？」

## 寫清楚的規則，為什麼還是會被違反？ {#problem}

你在指令檔裡寫了一條規則，要 agent「絕對不要碰產生出來的檔案」。頭一個星期，agent 都乖乖照做，後來有一天，它還是碰了。你回頭去看那條規則，它還在原處，和當初一樣清楚，因為檔案裡一個字也沒改。不是規則變了，而是 agent 那一刻有別的事要考慮。

這是怎麼發生的？得先從模型的角度看這條規則。模型讀到的所有文字，從你的需求到指令檔，再到它載入的 skill，合起來叫做 **prompt**。在 prompt 裡，你的規則只是眾多句子中的一句，模型會把它和其他所有句子放在一起權衡。有時候其他句子的分量更重，規則就輸了。而對話拖得越長，跟它搶分量的句子就越多（[長對話會變差](3-2-long-sessions.html)）。

這一切都還假設規則送得到模型面前，而這一點其實也說不準。在 [Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)裡，我數過 2026 年 10 月自己設定裡的一批 prompt。有個 hook 會把我的規則放在每個 prompt 的開頭，它也每次都執行了，結果還是有很多 prompt 到達時沒有帶著規則。這只是我這一套設定、一批資料，稱不上一般的比率，但既然連傳達規則都可能失敗，遵守規則就更可能失敗。

所以我們平常說的「規則」，其實是兩種很容易搞混的東西。第一種是**請求**：你請模型照規矩來，它通常會照做，但沒有人能保證它永遠照做。第二種才是嚴格意義上的**規則**，靠的是擋在路上的程式碼。只要這段程式碼在執行、看得到這次呼叫，不管模型怎麼想，呼叫都會被拒絕。

任何一定要成立的事，都必須是第二種。可是程式碼不是免費的，大多數規則也用不著它。那麼，哪條規則該放在哪裡？

## 哪條規則該放在哪裡？ {#how-it-works}

### 牢固程度分四級

簡單地說，每條規則都放在對它來說夠用的最低一級。一條規則可以守在四個層級上，其中三級越往上守得越牢，所以合起來像一道階梯。每一級保證的東西不同，也各有各的限制。

::: figure 4-1-ladder

| 層級 | 它是什麼 | 它保證什麼 | 它的限制 |
| --- | --- | --- | --- |
| **文字** | 規則寫在指令檔、skill 或 agent 的正文裡 | agent 知道這條規則，也知道它存在的理由 | 它可能不遵守 |
| **自己檢查的指令** | agent 透過你寫的一個小程式來做這個操作，程式動手之前先檢查條件 | 在任何平台上，每次都是同樣的結果 | 它只守經過它的東西。agent 如果手動編輯檔案，這個指令根本不會被呼叫 |
| **會拒絕的 hook** | 平台在工具呼叫之前執行的程式碼，可以說不 | 呼叫會被擋下；在我試過的模式裡，即使沒有人看著也一樣 | 它依賴平台，而且它看到的是呼叫，不是效果（[Hooks：每次呼叫都會經過的執行點](2-2-hooks.html)） |
| **事後發現** | 健康檢查（一個測試設定是否健全的指令）、跑一次測試、讀一遍紀錄 | 違反可以被發現、被計數 | 它什麼也預防不了。它是偵測，不是預防 |

最後一級的性質不一樣，它根本不守規則，只告訴你前面幾級有沒有守住。不管一條規則放在哪一級，你都需要它，因為規則有沒有被違反，你要是看不到，就只能用猜的。

中間兩級的運作方式正好相反。這裡說的**指令**，是你在 agent 內建工具之外另外給它的一個程式。agent 不必一步步地建資料夾、複製檔案、寫狀態，而是執行一個指令，三件事一次做完。只要有一個前提條件不成立，這個指令就拒絕開始。規則就藏在指令裡面。**hook** 則反過來：agent 想做什麼就做什麼，hook 在每次呼叫執行之前先看一眼。

### 什麼時候往上搬，搬到哪一級

每條新規則都從最底層的文字開始，因為一句話寫起來便宜、改起來也便宜，而且對大多數規則，模型都會照做。以下三種情況只要有一種成立，就該把它往上搬。

1. 它一直被違反。你不只一次看到它被違反，換一句更好的寫法也沒有解決。如果一條規則被無視，是因為它在長對話裡離得太遠，那重新措辭沒有用，得靠程式碼。
2. 傷害無法挽回，例如被刪掉的分支、推上去的 commit、沒人備份就被覆寫的檔案。這時候違反一次就已經太多，不要等第二次。
3. 其他部分依賴它。如果後面的步驟相信這條規則守住了（例如一筆「檢查通過」的紀錄、一個批准），那麼規則一破，後面那一步也跟著破。

確定要搬了，就選夠用的最低一級：指令能守住的規則，就不要做 hook。除了要寫、要測，hook 還得跟著平台的變化一直維護下去（[把執行層當軟體來設計](4-4-enforcement-design.html)）。只有當 agent 有很多方式可以碰到那樣東西，而你又無法把它們全部導到你的指令上時，才輪到 hook。

### 用程式碼擋，用文字教

規則搬進程式碼以後，你也許會覺得那句文字已經完成任務，可以刪了。其實應該留一句，因為兩者做的是不同的事。程式碼負責擋，而且不依賴模型記得什麼。文字負責教，在 agent 撞牆之前，就告訴它這條規則為什麼存在、該改做什麼。沒有文字，agent 會一次又一次撞上拒絕，還會試著繞過去；沒有程式碼，文字又變回請求。

這兩者之間的橋樑，是拒絕時給的訊息。它本身是程式碼，卻帶著一句話。好的拒絕訊息會說明為什麼被拒絕、接下來該做什麼（怎麼寫這類訊息，見[詢問不是限制](4-2-ask-vs-refuse.html)）。

反過來，有些事也不該放進程式碼：只有判斷才能決定的問題，例如這是不是對的需求、這個改動好不好，沒有可以比對的模式。它們仍然留在文字裡，再由獨立的 reviewer 從外面檢查（[慎用子 agent](2-3-subagents.html)）。

### 一條規則是怎麼一級級往上搬的

往上搬一條規則是什麼樣子？拿一條和本章開頭那條同類的規則來看，假設它是「產生出來的檔案絕不手動編輯」（例子是我編的）。一開始，它只是指令檔裡的一行文字，後面附著理由：這些檔案會被重新產生，手動改的內容會丟掉。

後來這條規則被違反了兩次，你就把它往上搬，在 hook 這一級加一個檢查。從此對這些路徑呼叫編輯工具就會被拒絕，拒絕時附上理由，以及重新產生這些檔案的指令。這樣守了一陣子，直到 agent 找到新的缺口，改用終端機去寫那個檔案，於是你把用終端機寫檔案的幾種常見寫法也加進 hook。你也知道，hook 還是抓不到先寫好一支腳本、之後再執行的情況，所以你留著那一句文字，再加一個測試，事後找出被改過的產生檔案。

回頭看，這條規則一路往上，只多了層級，沒有拿掉哪一層。

### 三分鐘的小練習

往下讀之前，先拿你自己的規則試試看。寫下你今天給 agent 的三條規則，每一條問三個問題。它是文字、指令、hook，還是事後檢查？違反一次，還能挽回嗎？它被違反過兩次了嗎？最該先往上搬的，是那條只靠文字守著、一旦違反就無法挽回、而且已經被違反過兩次的規則。

## 程式碼要付出什麼，還可能在哪裡出錯 {#costs-and-traps}

不管你搬的是哪條規則，守著它的程式碼都有成本。程式碼也是軟體：要寫、要測，平台改了工具名稱或事件時還要更新，所以你搬進程式碼的規則越多，要背的就越多。軟體也會壞。hook 一壞，平台可能拒絕每一次呼叫，也可能放行每一次呼叫，看它是怎麼壞的（[把執行層當軟體來設計](4-4-enforcement-design.html)）。

就算沒壞，程式碼規則也會從兩個相反的方向出錯。一個方向是模式寫得太寬，連正常的工作也擋下來。因為 agent 沒辦法跟拒絕爭辯，誤拒一次，任務就卡住了。這就是為什麼每條程式碼規則的訊息裡都要寫明理由，還要有辦法看出是哪條規則觸發的。另一個方向是放過東西。hook 只看得到呼叫，所以只擋得住它認得的那幾種寫法，其餘的都會漏掉。一個一心想繞過它的 agent，它是擋不住的。絕不能碰的東西該怎麼辦，見[有些東西根本不給](4-5-least-privilege.html)。

還有一個陷阱和拒絕無關。規則守沒守，要是只有 agent 自己知道，就沒有紀錄可言，所以別讓它當唯一的證人。凡是之後你要依賴的，都讓程式碼來寫紀錄（[讓「通過」可信](5-5-counted-checks.html)）。

最後一個限制在階梯本身。它來自我對一個 harness 的經驗和文件，每一級多常失敗，我並沒有數過。光靠文字的規則多常被違反，我也沒有數字。誰要是給你一個數字，卻不說是什麼模型、什麼任務，我是不會信的。

## 平台也這麼看嗎？ {#industry}
{status: industry}

平台文件在這種劃分上是一致的，只是各有各的說法。VS Code 的 hooks 頁面說，hook 和寫在指令檔裡的指示，都不能取代強制執行的權限、沙箱或企業管控（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)）。這句話值得正反兩面讀：指令檔裡的文字是最弱的一級，但 hook 也不是最強的一級，它上面還有更牢的。接下來的幾章，就沿著這道階梯往上走。

## 什麼時候可以刪掉程式碼規則 {#when-to-delete-it}
{status: industry}

隨著時間過去，有兩件事會讓這道階梯變短，第一件是模型越來越能照著文字做事。有些規則，你當初是因為模型不理會才搬進程式碼的，現在它可能已經會照做了。這可以驗證，雖然這個測試我自己還沒跑過：選過去曾經觸發這條規則的任務，只在違反了也能挽回的地方關掉程式碼規則，每個任務跑幾次，數一數違反的次數（[模型升級了，就要刪](6-5-model-upgrades.html)）。跑這麼幾次，也只看得出很大的變化。

第二件是平台接手。當平台自己就能在每種模式下拒絕某個路徑或指令時，你為它做的 hook 就可以刪掉，那一句文字則留著。

不會消失的，是這個問題本身：哪條規則該守得多牢，為什麼。
