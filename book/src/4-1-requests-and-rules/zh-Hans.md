这一章默认你已经读过 [Hook：每次调用都会经过的执行点](2-2-hooks.html)，知道 hook 是工具调用必经的一段代码，可以拒绝这次调用。

## 一句话 {#in-one-sentence}

写在 prompt 里的规则只是请求；写在代码里的规则才是规则。先从文字开始，等一条规则老被违反，或者违反的后果无法挽回，再把它挪进代码。

这里关心的是规则守得有多牢，说到底是安全问题。至于一个判断交给谁、交给什么来做最便宜，那是另一个问题，[谁来判断：代码、便宜模型、主模型、人](5-9-who-decides.html)会讲。

## 写给管理者 {#for-leaders}

- **要拍板的事**：哪些规则可以只用文字写着，哪些必须由代码强制执行。一条规则老被违反、一旦违反就会造成无法挽回的伤害，或者有别的步骤依赖它，就该挪进代码。
- **风险**：写在 prompt 里的规则只是请求，甚至可能根本到不了模型面前。2026 年 10 月，我数过自己配置里的一批 prompt：有个 hook 会把我的规则放到每条 prompt 的开头，它每次都运行了，可还是有很多 prompt 到达时没带上这些规则。这只是一套配置、一批数据，不是普遍的比率。写下来的规则多久被违反一次，我也没有数字。
- **做对的代价**：代码是有成本的，因为它要写、要测，平台一变还得跟着维护。大多数规则用不着它，所以这笔成本只花在少数几条规则上，不是全部。
- **可以问团队**：“我们的规则里，哪些只要 agent 违反一次，就会造成无法挽回的损害？这些规则每一条，是由代码守着，还是只写在 prompt 里？”

## 写清楚的规则，为什么还是会被违反？ {#problem}

你在指令文件里写了一条规则，要 agent “绝不要碰生成的文件”。头一个星期，agent 守得好好的，可后来有一天，它还是碰了。你回头去翻那条规则，它还在原处，和当初一样清楚，因为文件里一个字都没变。不是规则变了，而是 agent 那一刻有别的事要考虑。

这是怎么发生的？得先从模型的角度看这条规则。模型读到的全部文本，从你的需求到指令文件，再到它加载的 skill，合起来叫 **prompt**。在 prompt 里，你的规则只是众多句子中的一句，模型会把它和其他所有句子放在一起掂量。有时候别的句子分量更重，规则就输了。而对话拖得越长，跟它抢分量的句子就越多（[长对话会变差](3-2-long-sessions.html)）。

这一切还都假设规则能送到模型面前，可这一点同样没准。在 [Hook：每次调用都会经过的执行点](2-2-hooks.html)里，我数过 2026 年 10 月自己配置里的一批 prompt。有个 hook 会把我的规则放到每条 prompt 的开头，它也确实每次都运行了，可还是有很多 prompt 到达时没带上这些规则。这只是一套配置、一批数据，算不上普遍的比率，但既然连送达都可能失败，遵守就更可能失败。

所以我们平时说的“规则”，其实是两种容易混为一谈的东西。第一种是**请求**：你请模型守规矩，它多半会守，但谁也不能保证它永远守。第二种才是严格意义上的**规则**，靠的是挡在路上的代码。只要这段代码在运行、看得到这次调用，不管模型怎么想，调用都会被拒绝。

凡是必须成立的事，都得是第二种。可代码不是免费的，大多数规则也用不着它。那么，哪条规则该放在哪里？

## 哪条规则该放在哪里？ {#how-it-works}

### 牢固程度分四级

简单地说，每条规则都放在对它来说够用的最低一级。一条规则可以守在四个级别上，其中三级越往上守得越牢，所以合起来像一架梯子。每一级承诺的东西不同，也各有各的限度。

::: figure 4-1-ladder

| 级别 | 它是什么 | 它承诺什么 | 它的限度 |
| --- | --- | --- | --- |
| **文字** | 规则写在指令文件、skill，或者 agent 的正文里 | agent 知道这条规则，也知道它为什么存在 | 它可能不遵守 |
| **自带检查的命令** | agent 通过你写的一个小程序来做这个操作，程序动手之前先检查条件 | 在任何平台上，每次结果都一样 | 它只守经过它的东西。如果 agent 手动改文件，这个命令根本不会被调用 |
| **会拒绝的 hook** | 平台在工具调用之前运行的代码，可以说不 | 调用会被拦下；在我试过的模式里，即使没人盯着也是如此 | 它依赖平台，而且它看到的是调用，不是效果（[Hook：每次调用都会经过的执行点](2-2-hooks.html)） |
| **事后发现** | 健康检查（一条用来测试配置是否健全的命令）、一次测试运行、翻一遍日志 | 违规可以被发现、被计数 | 它什么也阻止不了。这是检测，不是预防 |

最后一级的性质不一样，它根本不守规则，只告诉你前面几级守住了没有。不管一条规则放在哪一级，都离不开它，因为规则有没有被违反，你要是看不见，就只能靠猜。

中间两级的路数正好相反。这里说的**命令**，是你在 agent 的内置工具之外另给它的一个程序。agent 不用一步步地创建文件夹、复制文件、写入状态，而是运行一条命令，把三件事一次做完。只要有一个前提不成立，命令就拒绝开始。规则就藏在命令里面。**hook** 则反过来：agent 想做什么就做什么，hook 在每次调用运行之前先看一眼。

### 什么时候往上挪，挪到哪一级

每条新规则都从最底下的文字开始，因为一句话写起来成本低，改起来也容易，而且对大多数规则来说，模型都会遵守。下面三种情况只要有一种成立，就该把它往上挪。

1. 它老被违反。你不止一次看到它被违反，换一句更好的写法也没解决。如果一条规则被无视，是因为它在长对话里离得太远，那改措辞没用，得靠代码。
2. 伤害无法挽回，比如删掉的分支、推送出去的提交、没人备份就被覆盖的文件。这种时候违反一次就已经太多，别等第二次。
3. 别的部分依赖它。如果后面的某一步相信这条规则守住了（比如一条“检查通过”的记录、一次审批），那规则一破，后面那一步也跟着破。

确定要挪了，就选刚好够用的最低一级：一条命令就能守住的规则，就别去造 hook。除了要写、要测，hook 还得跟着平台的变化一直维护下去（[把执行层当软件来设计](4-4-enforcement-design.html)）。只有当 agent 能从很多条路碰到那个东西，你又没法把这些路都引到你的命令上时，才轮到 hook。

### 用代码拦，用文字教

规则挪进代码以后，你也许会觉得那句文字已经完成了任务，可以删掉了。其实应该留一句，因为两者干的是不同的活。代码负责拦，而且不依赖模型记得什么。文字负责教，在 agent 撞墙之前，就告诉它这条规则为什么存在、该改做什么。没有文字，agent 会一次又一次撞上拒绝，还会试着绕过去；没有代码，文字又变回了请求。

这两者之间的桥，是拒绝时给出的消息。它本身是代码，却带着一句话。好的拒绝消息会说明为什么被拒绝、接下来该做什么（[询问不是限制](4-2-ask-vs-refuse.html)讲的就是怎么写这类消息）。

反过来，有些事也不该放进代码：只能靠判断来决定的问题，比如这是不是对的需求、这个改动好不好，没有可以匹配的模式。它们还是留在文字里，再由独立的 reviewer 从外面检查（[慎用子 agent](2-3-subagents.html)）。

### 一条规则是怎么一级级往上挪的

往上挪一条规则是什么样子？拿一条和本章开头那条同类的规则来看，假设它是“生成的文件绝不手动编辑”（例子是我编的）。一开始，它只是指令里的一行文字，后面附着理由：这些文件会被重新生成，手动改的内容会丢。

后来这条规则被违反了两次，你就把它往上挪，在 hook 这一级加一条检查。从此对这些路径调用编辑工具就会被拒绝，拒绝时附上理由，以及重新生成这些文件的命令。这样守了一阵子，直到 agent 找到一个新缺口，改用终端去写这个文件，于是你把用终端写文件的几种常见写法也加进 hook。你也知道，hook 还是拦不住先写好一个脚本、之后再运行的做法，所以你留着那一句文字，再加一个测试，事后找出被改动过的生成文件。

回头看，这条规则一路往上，只添了层级，没有去掉哪一层。

### 三分钟的小练习

往下读之前，先拿你自己的规则试一试。写下你今天给 agent 的三条规则，每一条问三个问题。它是文字、命令、hook，还是事后检查？违反一次，还能挽回吗？它被违反过两次了吗？最该先往上挪的，是那条只靠文字守着、一旦违反就无法挽回、而且已经被违反过两次的规则。

## 代码要付出什么，还可能在哪里出错 {#costs-and-traps}

不管你挪的是哪条规则，守着它的代码都有成本。代码也是软件：要写、要测，平台改了工具名或事件，还得跟着更新，所以挪进代码的规则越多，你要扛的就越多。软件也会坏。hook 一坏，平台可能拒绝每一次调用，也可能放过每一次调用，取决于它是怎么坏的（[把执行层当软件来设计](4-4-enforcement-design.html)）。

就算不坏，代码规则也会从两个相反的方向出错。一个方向是模式写得太宽，挡住了正常的工作。因为 agent 没法跟拒绝争辩，误拒一次，任务就卡住了。这就是为什么每条代码规则的消息里都要写明理由，还要有办法看出是哪条规则触发的。另一个方向是放过东西。hook 只看得到调用，所以只拦得住它认识的那几种写法，其余的都会漏掉。一个铁了心要绕过它的 agent，它是挡不住的。绝不能碰的东西该怎么办，见[有些东西根本不给](4-5-least-privilege.html)。

还有一个坑和拒绝无关。规则守没守，要是只有 agent 自己知道，就没有记录可言，所以别让它当唯一的证人。凡是你以后要依赖的东西，都让代码来写记录（[让“通过”可信](5-5-counted-checks.html)）。

最后一个限制在梯子本身。它来自我对一个 harness 的经验和文档，每一级多久失败一次，我并没有数过。光靠文字的规则多久会被违反一次，我也没有数字。要是有人给你一个数字，却不说是什么模型、什么任务，我不会信。

## 平台也这么看吗？ {#industry}
{status: industry}

平台文档在这个划分上是一致的，只是各用各的说法。VS Code 的 hooks 页面说，hook 和指令都不能替代强制执行的权限、沙箱或企业级管控（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)）。这句话值得正反两面读：指令是最弱的一级，但 hook 也不是最强的一级，它上面还有更牢的。接下来的几章，就沿着这架梯子往上走。

## 什么时候可以删掉代码规则 {#when-to-delete-it}
{status: industry}

随着时间推移，有两件事会让这架梯子变短，第一件是模型越来越能照着文字做事。有些规则，你当初是因为模型不理会才挪进代码的，现在它可能已经会照做了。这可以验证，虽然这个测试我自己还没跑过：挑那些过去会触发这条规则的任务，只在违反了也能挽回的地方关掉代码规则，每个任务跑几次，数一数违反了几次（[模型升级了，就要删](6-5-model-upgrades.html)）。跑这么几次，也只看得出很大的变化。

第二件是平台接管。当平台自己就能在每种模式下拒绝某个路径或命令时，你为它写的 hook 就可以删掉，那一句文字则留着。

不会消失的，是这个问题本身：哪条规则该守得多牢，为什么。
