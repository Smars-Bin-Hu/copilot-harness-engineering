读这一章，请先读过 [Hook：每次调用都会经过的执行点](2-2-hooks.html)：hook 是工具调用必经的一段代码，它可以拒绝这次调用。

## 一句话 {#in-one-sentence}

写在 prompt 里的规则只是请求；写在代码里的规则才是规则。先从文字开始，等一条规则老被违反，或者造成的伤害无法挽回，再把它挪进代码。

这一章讲的是规则守得有多牢（安全）。至于由谁来做判断最划算，那是[谁来判断：代码、便宜模型、主模型、人](5-9-who-decides.html)的话题。

## 写给管理者 {#for-leaders}

- **要拍板的事**：决定哪些规则可以只用文字写着，哪些必须由代码强制执行。一条规则老被违反、伤害无法挽回，或者别的步骤依赖它时，就该挪进代码。
- **风险**：写在 prompt 里的规则只是请求。在我自己的配置里，有个 hook 会把我的规则放到每条 prompt 的开头，它每次都运行了，可还是有很多 prompt 到达时没有带上这些规则。那只是一套配置、2026 年 10 月的一批数据，不是普遍的比率，写下来的规则多久被违反一次，我没有数字。
- **做对的代价**：代码是有成本的：要写、要测，平台一变还要维护。大多数规则用不着，所以是少数几条，不是全部。
- **可以问团队**：“我们的规则里，哪些一旦 agent 违反一次就会造成无法挽回的损害？这些规则每一条，是由代码守着，还是只写在 prompt 里？”

## 问题 {#problem}

你在指令文件里写了一条规则：“绝不碰生成的文件”。agent 遵守了一周。然后它不守了。你再读这条规则。它还在那里，写得很清楚。文件里什么也没变。变的是，agent 当时有别的事要考虑。

**prompt** 是模型读到的文本：你的需求、指令文件、它加载的 skill。写在那里的规则，和别的句子一样，只是一句话。模型会把它和别的句子放在一起权衡，有时别的句子胜出。对话越长，别的句子就越多（[长对话会变差](3-2-long-sessions.html)）。

连能不能把这句话送到模型面前，都不确定。在 [Hook：每次调用都会经过的执行点](2-2-hooks.html)里，我数过自己配置里 2026 年 10 月的一批 prompt：有个 hook 会把我的规则放到每条 prompt 的开头，它每次都运行了，可还是有很多 prompt 到达时没有带上这些规则。这是一套配置、一批数据，不是普遍的比率。如果送达一条规则都可能失败，那遵守它失败的可能还要更大。

所以规则有两种，而且很容易混淆：

- **请求。** 你请模型守规矩。它通常会守。没人能保证它永远会守。
- **规则。** 有代码挡在路上。只要代码在运行、看得到这次调用，不管模型怎么想，调用都会被拒绝。

凡是必须成立的事，都要是第二种。但代码不是免费的，大多数规则用不着。这一章要回答的问题是：哪条规则放在哪里？

## 原理 {#how-it-works}

### 四级牢固程度

一条规则可以在四个级别上守着。每一级承诺的东西不同，每一级也有它的限度。

::: figure 4-1-ladder

| 级别 | 它是什么 | 它承诺什么 | 它的限度 |
| --- | --- | --- | --- |
| **文字** | 规则写在指令文件、skill，或者 agent 的正文里 | agent 知道这条规则，也知道它为什么存在 | 它可能不遵守 |
| **自带检查的命令** | agent 通过你写的一个小程序来做这个操作，程序在动手之前先检查条件 | 在任何平台上，每次结果都一样 | 它只守经过它的东西。如果 agent 手动去改文件，这个命令根本不会被调用 |
| **会拒绝的 hook** | 平台在工具调用之前运行的代码，可以说不 | 调用会被拦下，在我试过的模式里，即使没人盯着也是如此 | 它依赖平台，而且它看到的是调用，不是效果（[Hook：每次调用都会经过的执行点](2-2-hooks.html)） |
| **事后发现** | 健康检查（一条用来测试配置是否健全的命令）、一次测试运行、翻一遍日志 | 违规可以被发现并计数 | 它什么也阻止不了。这是检测，不是预防 |

最后一级在性质上不同。它不守规则；它告诉你其他几级守住了没有。每一级都需要它，因为一条你看不到有没有被违反的规则，是一条你只能猜的规则。

中间两级要多解释一句。这里的**命令**，是你在 agent 的内置工具之外给它的一个程序。不是“创建文件夹、复制文件、写入状态”，而是 agent 运行一条命令，把这三件事都做了，并且在某个前提不成立时拒绝开始。规则就在命令里面。**hook** 则相反：agent 想做什么就做什么，hook 在每次调用运行之前先看一眼。

### 规则该放在哪

每条规则都从最底下的文字开始。写一句话成本低，改起来也容易，对大多数规则来说，模型会遵守。下面三种情况有一种成立时，再往上挪。

1. **老被违反。** 你看到它发生过不止一次，换一句更好的话也没有解决。规则因为离得太远而被无视，改措辞是错的答案；代码才是对的答案。
2. **伤害无法挽回。** 删掉的分支、推送出去的提交、没人备份过的被覆盖的文件。一次违反就太多了，所以别等第二次。
3. **别的部分依赖它。** 如果后面的某一步信任前面的规则守住了（“检查通过”的记录、一次审批），那么规则一破，后面的那一步也跟着破。

然后选刚好够用的最低一级。如果一条命令就能守住规则，就别造 hook。hook 要写、要测，还要在平台变化时让它继续有效（[把执行层当软件来设计](4-4-enforcement-design.html)）。agent 能通过很多条路碰到那个东西、你又没法把它们全都引到你的命令上时，才用 hook。

### 用代码拦，用文字教

把一条规则挪进代码时，别把那句话删了。留一句。它们做的是不同的事。

- **代码负责拦。** 它不依赖模型记得什么。
- **文字负责教。** 它在 agent 撞上墙之前，就告诉它这条规则为什么存在，以及该怎么做。

没有文字，agent 就会一次又一次撞上拒绝，并试别的办法绕过去。没有代码，文字又变回了请求。拒绝的消息是两者之间的桥：它是带着一句话的代码。好的拒绝消息会说明为什么被拒绝、接下来该做什么（[询问不是限制](4-2-ask-vs-refuse.html)讲的就是怎么写这类消息）。

同一个划分的另一面：只能靠判断来决定的事，不要放进代码。“这是对的需求吗？”“这个改动好不好？”没有可以匹配的模式。这些仍然用文字，从外面来检查，用独立的 reviewer（[慎用子 agent](2-3-subagents.html)）。

### 往上挪的一个例子

假设你的规则是：“生成的文件绝不手动编辑”。步骤大致如下。

1. **文字。** 指令里写一行，附上理由：它们会被重新生成，手动编辑的内容会丢。
2. **发生了两次。** 你在 hook 这一级加一条检查：对这些路径调用编辑工具，会被拒绝，并附上理由和重新生成它们的命令。
3. **又出现一个缺口。** agent 现在改用终端来写这个文件。你把这种做法的常见写法加到 hook 里。你也知道它拦不住先写好一个脚本、之后再运行的做法，所以保留那一句文字，再加一个测试，事后找出被改动过的生成文件。

这是一个编出来的例子，用来演示这些步骤。每一步都是加了一级，没有哪一级被去掉。

### 检验你自己的配置

**一个三分钟的练习。** 写下你今天给 agent 的三条规则。对每一条回答：它是文字、命令、hook，还是事后检查？违反一次，能挽回吗？它被违反过两次吗？对第一个问题回答“不是”、第二个回答“无法挽回”、第三个回答“是”的规则，就是最先要往上挪的。

## 代价和坑 {#costs-and-traps}

**代码是有成本的。** 平台改了工具名或事件，代码就得更新，还要写、要测。挪进代码的规则越多，你要扛的就越多。

**代码也会拦错东西。** 太宽的模式会挡住正常的工作。agent 没法跟拒绝争辩，所以一次误拒就是一个卡住的任务。每条代码规则的消息里都要有理由，还要有办法看到是哪条规则触发的。

**hook 只看得到调用。** hook 里的规则，对它认识的那些写法有效。它挡不住一个铁了心要绕过它的 agent。对于绝不能碰的东西，见[有些东西根本不给](4-5-least-privilege.html)。

**代码也会出故障。** hook 是软件。它坏了，平台可能拒绝每一次调用，也可能放过每一次调用，取决于它是怎么坏的（[把执行层当软件来设计](4-4-enforcement-design.html)）。

**只有 agent 自己守的规则，不算记录。** 不要让 agent 成为它守了规则的唯一见证人。凡是你以后要依赖的东西，都让代码来写记录（[让“通过”可信](5-5-counted-checks.html)）。

**我没数过每一级多久失败一次。** 这个梯子来自我对一个 harness 的经验和文档。光靠文字，多久会被违反一次，我没有数字，而且如果有人给你一个数字却不说是什么模型、什么任务，我也不会信。

## 业界怎么说 {#industry}
{status: industry}

平台文档在这个划分上是一致的，只是各用各的话。VS Code 的 hooks 页面说，hook 和指令不能替代强制执行的权限、沙箱或企业级管控（[hooks](https://code.visualstudio.com/docs/copilot/customization/hooks)）。这句话要两头读：指令是最弱的一级，而 hook 也不是最强的一级。接下来的几章就沿着这个梯子往上走。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

有两件事会让这个梯子随时间缩短。

- **模型更善于遵守文字。** 你当初因为模型无视而挪进代码的有些规则，现在可能已经被遵守了。要知道，就把代码规则关掉，跑同样的任务并计数（[模型升级了，就要删](6-5-model-upgrades.html)）。挑过去会触发这条规则的任务，每个跑几次，数一数违反了几次。跑几次只能看出很大的变化。我还没有跑过。只在违反了可以挽回的地方才关。
- **平台接管了。** 平台自己能在每种模式下拒绝某个路径或命令时，你自己为它写的 hook 就可以去掉。那一句文字保留。

不会消失的，是这个问题：哪条规则守得多牢，为什么。
