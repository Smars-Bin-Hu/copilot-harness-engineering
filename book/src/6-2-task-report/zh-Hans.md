读这一章，你需要用过一个写代码的 AI agent。先读过[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)会有帮助，不读也跟得上。

## 一句话 {#in-one-sentence}

每个完成的任务，都需要一份人五分钟读得完的报告。同时跑很多任务时，看板告诉你该打开哪一个。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求每个完成的任务都有一页由代码写的报告，并定下这一页必须显示什么。
- **风险**：日志不是报告。几千行没人会读，所以同事或管理者最后读到的，只有 agent 自己的总结，而日志存在的目的，正是检查这份总结。报告再诚实，也诚实不过它的来源：日志有漏洞，报告就有漏洞。
- **做对的代价**：一个读任务文件夹和日志的程序。真正的代价，是顶住大家“再加一个数字”的要求，守住五分钟这条线。
- **可以问团队**：“给我看上一个完成任务的报告。我能在五分钟内读完吗？它有没有写是谁审批的、什么被拒绝了？”

## 谁需要知道一个任务做了什么？ {#problem}

读完[上一章](6-1-observe.html)，你手里可能已经有一份几千行的日志。可日志不是报告，没人会为了回答“这个任务做了什么”去读几千行。agent 自己的总结倒是短到读得完，问题是，日志存在的目的，恰恰就是检查这份总结。

那么，谁需要这个答案，他们又肯花多久去找？需要它的有三个人，在三个不同的时间点。一个是第二天早上的你：活是昨天干的，改了哪些文件、为什么某个检查做了两次，你已经记不清了。另一个是没在旁边看的同事或管理者，他们想知道做了什么、有没有人检查过，愿意为此花上几分钟。最后一个还是你，在以后出了问题的时候：有人问“这个改动是谁审批的”“检查过吗”，到那时你想从文档里找到答案，而不是靠记忆。

报告要是得读一个小时，这三个人谁都不会读。这样一来，报告就成了一个设计问题：一页上放什么，什么留给日志？

## 每个任务一页，很多任务一块看板 {#how-it-works}

### 每个任务一页，由代码写

先说这一页由谁来写。这里的**任务**，指有自己文件夹的一件工作，需求、计划、检查和改动都放在里面（[管任务，不管对话](5-1-tasks.html)）。任务结束时，一个程序去读这个文件夹和那些记录，写出一份报告。写报告的不是 agent。

这个选择，整套做法都靠它。为什么不干脆让 agent 自己写？因为 agent 写的报告会是一份总结，而总结本来就是你一开始信不过的东西。由程序从文件夹和日志拼出来的报告，每次都有同样的事实，放在同样的位置，读的人慢慢就知道该看哪里。

::: figure 6-2-report-page

### 这一页放什么

一页上放什么，要从三种读者会问的问题出发，给每个问题留一个位置。在我的配置里，报告包含五样东西：

1. 要求了什么、做了什么：人确认过的需求，和计划。
2. 谁审批的、什么时候：两次审批的时间（[两道门：人在哪里审批](5-3-two-approvals.html)）。
3. 改了什么：哪些文件、加了多少行、删了多少行，以及读过哪些知识库文件（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）。
4. 检查：跑了几次独立检查，每一次的结论是什么（[让“通过”可信](5-5-counted-checks.html)）。
5. 什么被拒绝了：规则拦下的调用，和拦下的原因。这一块常让人意外，也常能解释为什么任务比预期花的时间长。

放到页面上，这五样东西是这个样子（这是模板，不是真的报告）：

- 要求：*确认过的需求，一段*
- 审批：*计划，于（时间）；写回，于（时间）*
- 改动：*（n）个文件，+（a）/-（b）行；读过的知识库文件：（清单）*
- 检查：*（n）次独立检查；每一次的结论*
- 拒绝：*每一次被拒绝的调用，和拒绝它的规则*

这一页没放进去的，是日志本身：报告只指向这些事实，不会把它们全部重复一遍。这条线划在哪里，就用五分钟来检验。读的人在这段时间里读不完这一页，就说明上面有东西该挪回日志。

### 时间和用量花在哪里

报告回答的是“发生了什么”。时间和用量花在了哪里，是另一个问题。回答它的是分析页，也就是报告旁边的第二页。它把每个 prompt 拆成模型思考、工具运行、子 agent 和**等人**几块，再按**阶段**加总。阶段指的是需求、计划、开发、写回、完成，独立检查自己单算一个阶段。

这些数字里，我原本没想到等待的时间会这么要紧。假设一个任务“花了三天”，这一页却显示 agent 干了四十分钟，其余时间都在等人（数字只是举例，不是结果）。那么这个任务的代价出在等待上，不在 agent。这和 agent 慢是两回事，解法也不一样：少设几道关卡，或者让关卡更便宜，或者找人来回答它们（[同时管十件事：并行的是任务](7-2-many-tasks.html)）。

和报告一样，这些数字也不靠 agent 的一面之词，而是来自 hook 日志和平台自己的会话记录（用量从哪里来，记录读不到时会怎样，见[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)）。打开这一页不花 token。只有你专门让 agent 来讲解，它才会去读。

### 看板：一眼看完很多任务

只有一个任务的时候，用不着看板。可一旦有十个，问题就从“这个任务做了什么”变成了“哪个任务现在需要我”，回答这个问题的就是**看板**。它是一页纸，列出每个未完成的任务、它在等什么、等了多久。因为看板和报告用的是同一批任务文件夹和记录，两者不会互相矛盾。设计见[同时管十件事：并行的是任务](7-2-many-tasks.html)。

### 手动试一次

在写任何程序之前，你就可以先手动试试报告这个想法。下次 agent 做完一个任务，你就根据 diff 和工具调用历史写五行：要求了什么、改了什么、跑了什么、什么被拒绝或失败了、谁点了头。写完问问自己，明天你还会不会读这一页，同事又用不用得上。如果写起来要超过几分钟，这本身就告诉你，程序得去收集些什么。

### 人在哪里介入

等这些页面有了，报告和看板就是人和这套系统见面的地方，只是两者的用法不一样。看板用来掌舵：你从它打开一个任务、审批一份计划，或者暂停一个任务，只是审批本身仍然走 agent 够不着的渠道。报告则是事后读的，它在任务结束时写成，展示的也就是那一刻的样子。

还有些读者，比如管理者，根本没有权限访问你的看板。给他们的办法，是把任务页存成一个能离线打开的单文件。它是你保存那一刻的副本，没有按钮。发出去之前先读一遍；在它离开负责这个任务的小组之前，先把内部名称和路径去掉。

这些页面会显示 agent 写的内容，但只按纯文本显示，所以任务文件没法让页面运行任何东西（[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)）。

## 报告说不出的事，和守住篇幅的代价 {#costs-and-traps}

报告是从日志和任务文件夹拼出来的，再诚实，也诚实不过这些来源。日志里有漏洞（[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)），报告里就有同样的漏洞，而且不会说出来。

来源之外，报告还有一件事说不出来：**报告说的是发生了什么，不是做得好不好**。它能显示任务走过了两次审批、检查都通过了，却没法显示这份活比上周的更好，因为没有东西能跨任务给质量打分（我也没有这样的分数）。想得到这样的分数，一个办法是在改动前后各跑一遍固定任务（[后面几章](6-3-eval-tasks.html)），只是这些不是真正的工作；另一个办法是让人抽样读一些完成的任务。

报告也不是签字，它只是记录。它算不算批准一项改动的证据、保存多久、谁能编辑它，这些是团队要定的事（[落地与治理](7-4-rollout-and-governance.html)）。报告本身只在结束时由代码写一次。

让报告保持简短，也有代价。守住五分钟要花力气：每个人都想在页面上再加一个数字，你只能一次次把它挪到日志或分析页去。

最后，没人要的报告，也就没人读。如果从来没人打开这些报告，先问问为什么，再去改进它们。

## 什么时候可以删掉这些页面，什么会留下来 {#when-to-delete-it}
{status: industry}

我的报告和看板之所以存在，是因为平台显示的是对话，不是任务。如果平台给你的是任务，每个任务有自己的历史、审批和用量，那就用平台的，把你自己搭的那一页丢掉。如果它还能给管理者一个只读视图，展示同样的事实，保存的副本也可以丢掉。

不过，背后的道理会留下来。没在旁边看的人，仍然需要在几分钟内知道做了什么、谁审批的、检查了什么、花了多少。至于看板，如果我发现自己从来不会同时跑两个以上的任务，我会重新考虑它。

## 在你自己的环境里试试 {#try-it}

::: prompt
取这个仓库最近合并的三个改动。对每一个，只根据 git 历史和关联的 review 或任务笔记，写一份五行的报告：要求了什么、改了什么（文件、行数）、跑了或检查了什么、什么被拒绝或失败了、谁点了头。仓库里找不到的事实，写“未记录”。然后告诉我，这五项事实里哪几项最常缺。不要改任何文件。
:::
