读这一章，你需要用过一个写代码的 AI agent。先读过[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)会有帮助，不读也跟得上。

## 一句话 {#in-one-sentence}

每个完成的任务，都需要一份人五分钟读得完的报告。同时跑很多任务时，看板是告诉你该打开哪一个的那一页。

## 写给管理者 {#for-leaders}

- **要拍板的事**：要求每个完成的任务都有一页由代码写的报告，并决定这一页必须显示什么。
- **风险**：日志不是报告。没人会读几千行，所以同事或管理者唯一会读的，是 agent 自己的总结，而日志存在的目的，恰恰是检查这份总结。报告也只和它的来源一样诚实：日志有漏洞，报告就有漏洞。
- **做对的代价**：一个读任务文件夹和日志的程序。真正的代价，是顶住大家“再加一个数字”的要求，守住五分钟这条线。
- **可以问团队**：“给我看上一个完成任务的报告。我能在五分钟内读完吗？它有没有写是谁审批的、什么被拒绝了？”

## 问题 {#problem}

日志不是报告。读完[上一章](6-1-observe.html)之后，你可能有一份几千行的日志。没人会读它来回答“这个任务做了什么”。而 agent 自己的总结，短到读得完，却正是日志要检查的东西。

谁需要这个答案？三个人，在三个时间点。

- **你，第二天早上**。活是昨天干的。你不记得改了哪些文件，也不记得为什么某个检查做了两次。
- **没在旁边看的同事或管理者**。他们想知道做了什么、有没有人检查过，而且愿意花几分钟。
- **你，以后出了问题的时候**。有人问“这个改动是谁审批的”“检查过吗”。你想从文档里找到答案，而不是靠记忆。

报告要是得读一个小时，这些人就不会读。所以报告是个设计问题：一页上放什么，什么留给日志。

## 原理 {#how-it-works}

### 每个任务一页，由代码写

这里的**任务**，是有自己文件夹的一件工作：需求、计划、检查和改动（[管任务，不管对话](5-1-tasks.html)）。任务结束时，一个程序读文件夹和记录，写出一份报告。不是 agent 写的。

这个选择承担了大部分分量。agent 写的报告是一份总结，而总结本来就是你一开始不能信的东西。由程序从文件夹和日志拼出来的报告，每次都有同样的事实，放在同样的位置，读的人就知道该看哪里。

### 这一页放什么

从三种读者会问的问题出发，每个问题给一个位置。在我的配置里，报告包含：

1. **要求了什么、做了什么**。人确认过的需求，和计划。
2. **谁审批、什么时候**。两次审批的时间（[两道门：人在哪里审批](5-3-two-approvals.html)）。
3. **改了什么**。哪些文件、加了多少行、删了多少行，以及读过哪些知识库文件（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）。
4. **检查**。有几次独立检查，每一次的结论（[让“通过”可信](5-5-counted-checks.html)）。
5. **什么被拒绝**。规则拦下的调用，和原因。这一块常让人意外，也常能解释为什么任务比预期花的时间长。

版面是这样的，这是模板，不是真的报告：

- 要求：*确认过的需求，一段*
- 审批：*计划，于（时间）；写回，于（时间）*
- 改动：*（n）个文件，+（a）/-（b）行；读过的知识库文件：（清单）*
- 检查：*（n）次独立检查；每一次的结论*
- 拒绝：*每一次被拒绝的调用，和拒绝它的规则*

没放进去的是日志本身。报告指向这些事实，不会全部重复一遍。一个好用的测试就是五分钟：读的人在这段时间内读不完这一页，就说明上面有东西该放回日志。

### 时间和用量花在哪里

报告旁边有第二页，回答另一个问题：不是“发生了什么”，而是“时间和用量花在哪里”。它把每个 prompt 拆成模型思考、工具运行、子 agent，和**等人**。然后按**阶段**加总（需求、计划、开发、写回、完成；独立检查自己算一个阶段）。

等待的时间，是我没想到会这么重要的数字。假设一个任务“花了三天”，那一页显示 agent 干了四十分钟，其余时间都在等人（数字只是举例，不是结果）。那么代价出在等待上，不在 agent。这和 agent 慢是不同的问题，解法也不同：少设几道关卡，或者让关卡更便宜，或者找人来回答它们（[同时管十件事：并行的是任务](7-2-many-tasks.html)）。

这些数字来自 hook 日志和平台自己的会话记录，不是 agent 的一面之词（用量从哪里来，记录读不到时会怎样，见[记下发生了什么，而不是 agent 说了什么](6-1-observe.html)）。打开这一页不花 token。如果你想让 agent 给你讲解，要专门提出来，那时它才会去读这一页。

### 看板：一眼看完很多任务

只有一个任务时，不需要看板。有十个时，问题就从“这个任务做了什么”变成“哪个任务现在需要我”。**看板**是一页纸，列出每个未完成的任务、它在等什么、等了多久。它用的任务文件夹和记录，和报告是同一份，所以两者不会互相矛盾。设计见[同时管十件事：并行的是任务](7-2-many-tasks.html)。

### 手动试一次

不用写程序，也能看出这个想法行不行。下次 agent 做完一个任务后，根据 diff 和工具调用历史写五行：要求了什么、改了什么、跑了什么、什么被拒绝或失败了、谁点了头。然后问问自己，明天你会不会读这一页，同事用不用得上。如果写起来要好几分钟以上，这就告诉你程序要去收集什么。

### 人在哪里介入

报告和看板，是人和这套系统见面的地方。有三点要紧。

- **看板用来掌舵**。你从它打开一个任务、审批一份计划，或者暂停一个任务。审批仍然走 agent 够不着的渠道。
- **报告用来事后阅读**。它在任务结束时写成，所以展示的是任务结束时的样子。
- **保存的副本给没有权限的人**。任务页可以存成一个能离线打开的单文件，给没有权限访问你看板的管理者。它是你保存那一刻的副本，没有按钮。发出去之前先读一遍，并且在它离开负责这个任务的小组之前，去掉内部名称和路径。

agent 写的内容在这些页面上都按纯文本显示，所以任务文件没法让页面运行任何东西（[agent 读到的文字可能在指挥它](4-6-untrusted-input.html)）。

## 代价和坑 {#costs-and-traps}

**报告只和它的来源一样诚实**。它是从日志和文件夹拼出来的。日志里有漏洞（[记下发生了什么](6-1-observe.html)），报告里就有同样的漏洞，而且不会说出来。

**五分钟是一条要靠你去守的线**。每个人都想在页面上再加一个数字。把它移到日志或分析页，让报告保持简短。

**报告说的是发生了什么，不是做得好不好**。它能显示任务走过了两次审批、检查都通过了。它没法显示这份活比上周的更好，因为没有东西能跨任务给质量打分；我没有这样的分数。要得到这样的分数，你得在改动前后各跑一遍固定任务（[后面几章](6-3-eval-tasks.html)），这些不是真正的工作；或者让人抽样读一些完成的任务。

**报告是记录，不是签字**。它算不算批准一项改动的证据、保存多久、谁能编辑它，这些是团队要定的事（[落地与治理](7-4-rollout-and-governance.html)）。报告本身只在结束时由代码写一次。

**没人要的报告，就没人读**。如果从来没人打开这些报告，先问为什么，再去改进它们。

## 什么时候可以删掉 {#when-to-delete-it}
{status: industry}

我的报告和看板之所以存在，是因为平台显示的是对话，不是任务。如果平台给你的是任务，每个任务有自己的历史、审批和用量，就用它的，把你自己搭的那一页丢掉。如果它能给管理者一个只读视图，展示同样的事实，保存的副本也可以丢掉。

背后的道理不变。没在旁边看的人，需要在几分钟内知道做了什么、谁审批的、检查了什么、花了多少。如果我发现自己同时从来不会跑超过两个任务，我会重新考虑看板。
