讀這一章，你需要用過 AI 寫程式的 agent。先讀過 [記下發生了什麼，不是 agent 說了什麼](6-1-observe.html) 會有幫助，不讀也跟得上。

## 一句話 {#in-one-sentence}

每個完成的任務，都需要一份人五分鐘讀得完的報告。同時跑很多任務時，看板是告訴你該打開哪一個的那一頁。

## 給主管 {#for-leaders}

- **要做的決定**：要求每個完成的任務都有一頁由程式寫的報告，並決定這一頁必須顯示什麼。
- **風險**：日誌不是報告。沒有人會讀幾千行，所以同事或主管唯一會讀的，是 agent 自己的總結，而日誌存在的目的，就是檢查這份總結。報告的誠實程度，也只和它的來源一樣：日誌有洞，報告就有洞。
- **做對的成本**：一個讀任務資料夾和日誌的程式。真正的成本，是擋住大家「再加一個數字」的要求，守住五分鐘這條線。
- **可以問團隊**：「給我看上一個完成任務的報告。我能在五分鐘內讀完嗎？它有沒有說是誰批准的、什麼被拒絕了？」

## 問題 {#problem}

日誌不是報告。讀完 [上一章](6-1-observe.html) 之後，你可能有一份幾千行的日誌。沒有人會讀它來回答「這個任務做了什麼？」。而 agent 自己的總結，短到讀得完，卻正是日誌存在要檢查的東西。

誰需要這個答案？三個人，在三個時間點。

- **你，隔天早上**。工作是昨天做的。你不記得改了哪些檔案，也不記得為什麼某個檢查做了兩次。
- **沒在旁邊看的同事或主管**。他們想知道做了什麼、有沒有人檢查過，而且願意花幾分鐘。
- **你，以後出了問題的時候**。有人問「這個改動是誰批准的？」「有檢查過嗎？」。你想從文件裡找到答案，不是靠記憶。

報告要是要讀一個小時，這些人就不會讀。所以報告是個設計問題：一頁上放什麼，什麼留給日誌。

## 原理 {#how-it-works}

### 每個任務一頁，由程式寫

這裡的**任務**，是有自己資料夾的一件工作：需求、計畫、檢查和改動（[管任務，不管對話](5-1-tasks.html)）。任務結束時，一個程式讀資料夾和紀錄，寫出一份報告。不是 agent 寫的。

這個選擇承擔了大部分的分量。agent 寫的報告是一份總結，而總結本來就是你一開始不能信的東西。由程式從資料夾和日誌拼出來的報告，每次都有同樣的事實、放在同樣的位置，讀的人就學會該看哪裡。

::: figure 6-2-report-page

### 這一頁放什麼

從三種讀者會問的問題出發，每個問題給一個位置。在我的設定裡，報告包含：

1. **要求了什麼、做了什麼**。人確認過的需求，和計畫。
2. **誰批准、什麼時候**。兩次批准的時間（[兩道門：人在哪裡批准](5-3-two-approvals.html)）。
3. **改了什麼**。哪些檔案、加了多少行、刪了多少行，以及讀了哪些知識庫檔案（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。
4. **檢查**。有幾次獨立檢查，每一次的結論（[讓「通過」可信](5-5-counted-checks.html)）。
5. **什麼被拒絕**。規則擋下的呼叫，和原因。這一塊常讓人意外，也常能解釋為什麼任務比預期花得久。

版面是這樣，這是範本，不是真的報告：

- 要求：*確認過的需求，一段*
- 批准：*計畫，於（時間）；寫回，於（時間）*
- 改動：*（n）個檔案，+（a）／-（b）行；讀過的知識庫檔案：（清單）*
- 檢查：*（n）次獨立檢查；每一次的結論*
- 拒絕：*每一次被拒絕的呼叫，和拒絕它的規則*

沒放進去的是日誌本身。報告指向這些事實，不會全部重複一遍。一個好用的測試就是五分鐘：讀的人在這段時間內讀不完這一頁，就是上面有東西該放回日誌。

### 時間和用量花在哪裡

報告旁邊有第二頁，回答另一個問題：不是「發生了什麼？」，而是「時間和用量花在哪裡？」。它把每個 prompt 拆成模型思考、工具執行、子 agent，和**等人**。然後依**階段**加總（需求、計畫、開發、寫回、完成；獨立檢查自己算一個階段）。

等待的時間，是我沒想到會這麼重要的數字。假設一個任務「花了三天」，那一頁顯示 agent 工作了四十分鐘，其餘時間都在等人（數字只是舉例，不是結果）。那麼成本是在等待，不是 agent。這和 agent 慢是不同的問題，修法也不同：少一點門，或讓門便宜一點，或找人來回答它們（[同時管十件事：並行的是任務](7-2-many-tasks.html)）。

數字來自 hook 日誌和平台自己的會話紀錄，不是 agent 的一面之詞（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html) 說了用量從哪裡來，以及讀不到那份紀錄時會怎樣）。打開這一頁不花 token。如果你要 agent 解釋給你聽，你得特地要求，那時它才會去讀這一頁。

### 看板：一眼看完很多任務

只有一個任務時，你不需要看板。有十個時，問題從「這個任務做了什麼？」變成「現在哪個任務需要我？」。**看板**是一頁，列出每個還開著的任務、它在等什麼、等了多久。它用和報告相同的任務資料夾和紀錄建成，所以兩者不會不一致。設計見 [同時管十件事：並行的是任務](7-2-many-tasks.html)。

### 手動試試

不用程式，也能看這個想法行不行。下一個 agent 任務之後，從 diff 和工具呼叫的歷史寫五行：要求了什麼、改了什麼、執行了什麼、什麼被拒絕或失敗、誰說了好。然後問自己，明天你會不會讀這一頁，同事能不能用。如果你寫它要花超過幾分鐘，那就告訴你，程式要去收集什麼。

### 人在哪裡插手

報告和看板，是人和系統碰面的地方。有三點要緊。

- **看板用來掌舵**。你從它打開一個任務、批准計畫，或暫停一個任務。批准仍然走 agent 碰不到的管道。
- **報告用來事後閱讀**。它在任務結束時寫成，所以顯示的是任務結束時的樣子。
- **存下來的副本，給沒有權限的人**。任務頁可以存成一個離線也能打開的單一檔案，給沒有權限進你的看板的主管。它是你存下那一刻的副本，沒有按鈕。送出之前先讀過；要送到擁有這個任務的團體之外時，先拿掉內部名稱和路徑。

agent 寫的東西，在這些頁面上是以純文字畫出來的，所以任務檔案沒辦法讓頁面去執行任何東西（[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)）。

## 代價和陷阱 {#costs-and-traps}

**報告的誠實程度，只和它的來源一樣**。它由日誌和資料夾建成。日誌有洞（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)），報告就有一樣的洞，而且不會說出來。

**五分鐘是一條要守的線**。每個人都想在頁面上多加一個數字。把它移到日誌或分析頁，讓報告保持簡短。

**報告說的是發生了什麼，不是做得好不好**。它能顯示任務經過了兩道批准、檢查都通過。它不能顯示這次的工作比上週好，因為沒有東西在跨任務為品質打分；我沒有這樣的分數。要有的話，你得在改動前後跑固定的任務（[固定的任務，用腳本打分](6-3-eval-tasks.html)），那不是真實的工作，或者讓人讀一批完成任務的樣本。

**報告是紀錄，不是簽名**。它算不算批准一項改動的證據、保留多久、誰可以編輯，是團隊要決定的事（[落地與治理](7-4-rollout-and-governance.html)）。報告本身只在結束時，由程式寫一次。

**沒人要的報告，沒人會讀**。如果從來沒有人打開報告，先問為什麼，再去改進它們。

## 什麼時候可以刪掉 {#when-to-delete-it}
{status: industry}

我的報告和看板存在，是因為平台顯示的是對話，不是任務。如果平台提供任務，並且有各自的歷史、批准和每個任務的用量，就用那個，把你建的頁面丟掉。如果它能給主管一個唯讀的檢視、事實相同，存下來的副本也可以丟掉。

道理會留著。沒在旁邊看的人，需要知道做了什麼、誰批准、檢查了什麼、花了多少，而且形式要是幾分鐘就讀完。如果我發現自己從來不會同時跑超過兩個任務，我會重新檢視看板。

不用裝 harness。在你自己的倉庫裡打開 agent，貼上：

::: prompt
拿這個倉庫最近三個合併的改動。對每一個，只用 git 歷史和任何連結的審查或任務筆記，寫一份五行的報告：要求了什麼、改了什麼（檔案、行數）、執行或檢查了什麼、什麼被拒絕或失敗、誰說了好。倉庫裡找不到的事實，寫「沒有記錄」。然後告訴我，這五件事裡，哪幾件最常缺。不要改任何檔案。
