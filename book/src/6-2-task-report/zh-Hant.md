讀這一章，你需要用過寫程式的 AI agent。先讀過 [記下發生了什麼，不是 agent 說了什麼](6-1-observe.html) 會有幫助，不讀也跟得上。

## 一句話 {#in-one-sentence}

每個完成的任務，都需要一份人五分鐘讀得完的報告。同時跑很多任務時，看板告訴你該打開哪一個。

## 給主管 {#for-leaders}

- **要做的決定**：要求每個完成的任務都有一頁由程式寫的報告，並決定這一頁必須顯示什麼。
- **風險**：日誌不是報告。幾千行沒有人會讀，所以同事或主管最後讀到的，只有 agent 自己的總結，而日誌存在的目的，正是檢查這份總結。報告再誠實，也誠實不過它的來源：日誌有洞，報告就有洞。
- **做對的成本**：一個讀任務資料夾和日誌的程式。真正的成本，是擋住大家「再加一個數字」的要求，守住五分鐘這條線。
- **可以問團隊**：「給我看上一個完成任務的報告。我能在五分鐘內讀完嗎？它有沒有說是誰批准的、什麼被拒絕了？」

## 誰需要知道一個任務做了什麼？ {#problem}

讀完 [上一章](6-1-observe.html)，你手上可能已經有一份幾千行的日誌。可是日誌不是報告，沒有人會為了回答「這個任務做了什麼」去讀幾千行。agent 自己的總結倒是短到讀得完，問題是，日誌存在的目的，正是要檢查這份總結。

那麼，誰需要這個答案，他們又願意花多久去找？需要它的有三個人，在三個不同的時間點。一個是隔天早上的你：工作是昨天做的，改了哪些檔案、為什麼某個檢查做了兩次，你已經記不得了。另一個是沒在旁邊看的同事或主管，他們想知道做了什麼、有沒有人檢查過，願意為此花上幾分鐘。最後一個還是你，在以後出了問題的時候：有人問「這個改動是誰批准的」「有檢查過嗎」，到那時你想從文件裡找到答案，不是靠記憶。

報告要是得讀一個小時，這三個人誰都不會讀。這樣一來，報告就成了一個設計問題：一頁上放什麼，什麼留給日誌？

## 每個任務一頁，很多任務一塊看板 {#how-it-works}

### 每個任務一頁，由程式寫

先說這一頁由誰來寫。這裡的**任務**，指有自己資料夾的一件工作，需求、計畫、檢查和改動都放在裡面（[管任務，不管對話](5-1-tasks.html)）。任務結束時，一個程式去讀這個資料夾和那些紀錄，寫出一份報告。寫報告的不是 agent。

這個選擇，整套做法都靠它。為什麼不乾脆讓 agent 自己寫？因為 agent 寫的報告會是一份總結，而總結本來就是你一開始信不過的東西。由程式從資料夾和日誌拼出來的報告，每次都有同樣的事實、放在同樣的位置，讀的人就會學到該看哪裡。

::: figure 6-2-report-page

### 這一頁放什麼

一頁上放什麼，要從三種讀者會問的問題出發，替每個問題留一個位置。在我的設定裡，報告包含五樣東西：

1. 要求了什麼、做了什麼：人確認過的需求，和計畫。
2. 誰批准、什麼時候：兩次批准的時間（[兩道門：人在哪裡批准](5-3-two-approvals.html)）。
3. 改了什麼：哪些檔案、加了多少行、刪了多少行，以及讀了哪些知識庫檔案（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。
4. 檢查：跑了幾次獨立檢查，每一次的結論是什麼（[讓「通過」可信](5-5-counted-checks.html)）。
5. 什麼被拒絕了：規則擋下的呼叫，和擋下的原因。這一塊常讓人意外，也常能解釋為什麼任務比預期花得久。

放到頁面上，這五樣東西是這個樣子（這是範本，不是真的報告）：

- 要求：*確認過的需求，一段*
- 批准：*計畫，於（時間）；寫回，於（時間）*
- 改動：*（n）個檔案，+（a）／-（b）行；讀過的知識庫檔案：（清單）*
- 檢查：*（n）次獨立檢查；每一次的結論*
- 拒絕：*每一次被拒絕的呼叫，和拒絕它的規則*

這一頁沒放進去的，是日誌本身：報告只指向這些事實，不會把它們全部重複一遍。這條線畫在哪裡，就用五分鐘來檢驗。讀的人在這段時間內讀不完這一頁，就表示上面有東西該搬回日誌。

### 時間和用量花在哪裡

報告回答的是「發生了什麼」。時間和用量花在哪裡，是另一個問題。回答它的是分析頁，也就是報告旁邊的第二頁。它把每個 prompt 拆成模型思考、工具執行、子 agent 和**等人**幾塊，再依**階段**加總。階段指的是需求、計畫、開發、寫回、完成，獨立檢查自己單獨算一個階段。

這些數字裡，我原本沒想到等待的時間會這麼重要。假設一個任務「花了三天」，這一頁卻顯示 agent 工作了四十分鐘，其餘時間都在等人（數字只是舉例，不是結果）。那麼這個任務的成本是在等待，不是 agent。這和 agent 慢是兩回事，修法也不一樣：少設幾道門，或讓門便宜一點，或找人來回答它們（[同時管十件事：並行的是任務](7-2-many-tasks.html)）。

和報告一樣，這些數字也不靠 agent 的一面之詞，而是來自 hook 日誌和平台自己的會話紀錄（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html) 說了用量從哪裡來，以及讀不到那份紀錄時會怎樣）。打開這一頁不花 token。只有你特地要 agent 解釋給你聽，它才會去讀。

### 看板：一眼看完很多任務

只有一個任務的時候，用不著看板。可是一旦有十個，問題就從「這個任務做了什麼」變成「現在哪個任務需要我」，回答這個問題的就是**看板**。它是一頁，列出每個還開著的任務、它在等什麼、等了多久。因為看板和報告用的是同一批任務資料夾和紀錄，兩者不會不一致。設計見 [同時管十件事：並行的是任務](7-2-many-tasks.html)。

### 手動試試

在寫任何程式之前，你就可以先手動試試報告這個想法。下一個 agent 任務結束後，你就從 diff 和工具呼叫的歷史寫五行：要求了什麼、改了什麼、執行了什麼、什麼被拒絕或失敗、誰點了頭。寫完問問自己，明天你還會不會讀這一頁，同事又能不能用。如果寫它要花超過幾分鐘，這本身就告訴你，程式得去收集些什麼。

### 人在哪裡插手

等這些頁面有了，報告和看板就是人和系統碰面的地方，只是兩者的用法不一樣。看板用來掌舵：你從它打開一個任務、批准計畫，或暫停一個任務，只是批准本身仍然走 agent 碰不到的管道。報告則是事後讀的，它在任務結束時寫成，顯示的也就是那一刻的樣子。

還有些讀者，例如主管，根本沒有權限進你的看板。給他們的辦法，是把任務頁存成一個離線也能打開的單一檔案。它是你存下那一刻的副本，沒有按鈕。送出之前先讀過；要送到負責這個任務的團隊之外時，先拿掉內部名稱和路徑。

這些頁面會顯示 agent 寫的東西，但只以純文字顯示，所以任務檔案沒辦法讓頁面去執行任何東西（[agent 讀到的文字可能在指揮它](4-6-untrusted-input.html)）。

## 報告說不出的事，和守住篇幅的成本 {#costs-and-traps}

報告是由日誌和任務資料夾建成的，再誠實，也誠實不過這些來源。日誌有洞（[記下發生了什麼，不是 agent 說了什麼](6-1-observe.html)），報告就有一樣的洞，而且不會說出來。

來源之外，報告還有一件事說不出來：**報告說的是發生了什麼，不是做得好不好**。它能顯示任務經過了兩道批准、檢查都通過，卻不能顯示這次的工作比上週好，因為沒有什麼能跨任務替品質打分（我也沒有這樣的分數）。想要有這樣的分數，一個辦法是在改動前後跑固定的任務（[後面幾章](6-3-eval-tasks.html)），只是那不是真實的工作；另一個辦法是讓人讀一批完成任務的樣本。

報告也不是簽名，它只是紀錄。它算不算批准一項改動的證據、保留多久、誰可以編輯，是團隊要決定的事（[落地與治理](7-4-rollout-and-governance.html)）。報告本身只在結束時，由程式寫一次。

讓報告保持簡短，也有成本。守住五分鐘要花力氣：每個人都想在頁面上多加一個數字，你只能一次次把它移到日誌或分析頁去。

最後，沒人要的報告，也就沒人會讀。如果從來沒有人打開報告，先問為什麼，再去改進它們。

## 什麼時候可以刪掉這些頁面，什麼會留下來 {#when-to-delete-it}
{status: industry}

我的報告和看板之所以存在，是因為平台顯示的是對話，不是任務。如果平台提供任務，每個任務有各自的歷史、批准和用量，就用平台的，把你自己建的頁面丟掉。如果它還能給主管一個唯讀的檢視、事實相同，存下來的副本也可以丟掉。

不過，背後的道理會留下來。沒在旁邊看的人，仍然需要知道做了什麼、誰批准、檢查了什麼、花了多少，而且要能在幾分鐘內讀完。至於看板，如果我發現自己從來不會同時跑超過兩個任務，我會重新檢視它。

## 在你自己的環境試試 {#try-it}

::: prompt
拿這個倉庫最近三個合併的改動。對每一個，只用 git 歷史和任何連結的審查或任務筆記，寫一份五行的報告：要求了什麼、改了什麼（檔案、行數）、執行或檢查了什麼、什麼被拒絕或失敗、誰說了好。倉庫裡找不到的事實，寫「沒有記錄」。然後告訴我，這五件事裡，哪幾件最常缺。不要改任何檔案。
