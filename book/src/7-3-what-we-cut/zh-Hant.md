讀這一章，你需要讀過 [慎用子 agent](2-3-subagents.html) 和 [管任務，不管對話](5-1-tasks.html)。

## 一句話 {#in-one-sentence}

按職位分工的三個 agent 花得最多，卻沒換來任何我量得出來的東西。把它們連同級別和獨立的協調者一起拿掉，harness 變簡單了，不過量過的只有第一刀。

## 給主管 {#for-leaders}

- **要做的決定**：對每個 agent、規則和步驟都問一遍，它換來了什麼，怎樣才能安全地拿掉它，然後定一個時間回頭檢查這些答案。
- **風險**：設定只會越長越大，每個部分都在持續花上下文、維護和學習的時間。我量過的只有一刀，三個按職位分工的 agent 對一個 agent：答對的數量一樣，團隊的花費是好幾倍（四個任務，各跑一次）。
- **做對的成本**：一個小時，把各部分列出來，每個寫一行。更難的成本，是告訴已經在用某個部分的人，用什麼取代它。
- **可以問團隊**：「每個 agent、規則和步驟：它換來了什麼，你怎麼知道，怎樣才能安全地拿掉？」

## 每個部分換來了什麼，什麼時候可以拿掉？ {#problem}

你加進 agent 設定的每個部分，都有代價：它占上下文的空間，要有人一直讓它保持正確，每個新人也都得花時間學它。可是多數設定只會越長越大，因為加東西感覺像進步，拿掉東西卻像損失。

所以我想換一個問題去問每個部分：**它換來了什麼，什麼時候可以拿掉**？答不出前一半，這個部分就是只有成本、沒有回報；答不出後一半，我就會永遠留著它。

我自己設定的 1.0 版，剛好是這個問題的好考題，因為它有好幾個聽起來很對的部分。我發布了它，用了幾天，就在 1.1 版裡拿掉了很大一部分。接下來講我砍了什麼、為什麼砍，一路上我最想守住的一條線是：**每一刀，哪些是我量過的，哪些只是我的判斷**。

要看懂這幾刀，得先知道那個版本怎麼運作。每個工作開始時，使用者要先選一個**級別**：輕的用來快速回答，中間的用於中等的任務，重的讓好幾個 agent 一起工作，而每個級別都有自己的規則。**按職位分工的 agent**，是被給了一個角色的 agent，例如計劃者、實作者或 reviewer，就像一個人的團隊那樣。重級別就是用它們搭起來的。這麼多角色，誰來分配工作？是**協調者**，也就是只負責把工作交給別人的 agent（用法和 [慎用子 agent](2-3-subagents.html) 一樣）。在重級別裡，它是一個獨立的 agent。這個團隊把計劃、交接和結果放在**請求資料夾**裡，那是和任務分開的另一個資料夾。

從這套設計裡砍下了四刀，可是每一刀背後的證據並不是同一種。

## 四刀，每一刀有多少把握 {#how-it-works}

### 一眼看完

下面這張表把四刀並排放在一起，每一刀背後有什麼證據也寫在裡面，原因則留給後面的小節。

| 砍掉的 | 本來想換來什麼 | 為什麼拿掉 | 證據 | 什麼時候重新考慮 |
| --- | --- | --- | --- | --- |
| 三個按職位分工的 agent | 像人的團隊那樣分工 | 花費好幾倍，結果一樣 | 量過：4 個任務，各跑一次，只看方向 | 在更大、更亂的任務上比較，顯示有好處 |
| 級別 | 規則配合工作的難度 | 只用到一個；難選；規則互相打架 | 我的使用經驗，沒有計數 | 開始之前，就能可靠地知道一個工作有多難 |
| 獨立的協調者 | 有人負責分配工作 | 懂的那個不是動手的那個；做事的要重學一遍 | 推理出來的；測試紀錄裡有線索，沒有單獨量過 | 平台可以還原一個已結束的子 agent 的上下文 |
| 請求資料夾 | 團隊檔案的獨立位置 | 團隊沒了以後，沒有東西需要它 | 從其他幾刀推出來的，沒有測 | 需要自己工作區的流程回來了 |

### 我對任何部分都用的測試

一刀一刀看之前，先說這幾刀背後的測試。你的設定其實也只會越長越大，所以這些問題不只是我問自己的，也是問你的。決定要不要留下一個部分時，我都會問同樣的幾個問題（就是 [落地與治理](7-4-rollout-and-governance.html) 裡那些）。它防止什麼失敗，有真實的例子嗎？它花多少？要變成什麼樣，它才能拿掉？下面的每一刀，就是這些問題晚了一步才得到的答案。

::: figure 7-3-before-after

### 第一刀：三個按職位分工的 agent（量過）

在 1.0 裡，重級別會讓一個團隊上場：協調者寫計劃，實作者改程式碼，reviewer 檢查。我拿它和一個 agent 單獨做事相比，用的是同樣的四個任務。那個測試在 [慎用子 agent](2-3-subagents.html) 裡講過，所以這裡不重複，只講它有哪些限制。

第一個限制是規模小。四個任務各只跑了一次，再跑一次，數字就會動。第二個限制是兩邊並不對等。單一 agent 用的是頂級模型，團隊卻有一個知識庫可以讀（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。限制這麼多，這個測試還能信什麼？我相信的是方向，也就是團隊花了好幾倍，答對的數量卻一樣。確切的倍數，我不信。

這足以說明在那些任務上團隊不划算，卻不能說團隊永遠不划算。不過，團隊也沒有整個拿掉。我留下了一個角色，就是獨立的 reviewer，因為獨立檢查是值得多一個 agent 的四件事之一。只是這一條靠的是推理：量那一刀的標準，我從沒單獨拿來測過 reviewer。

### 第二刀：級別（設計歷史，沒有數據）

關於級別，我有的只是幾天裡用它們時看到的事。我沒有記錄每個級別各用了幾次，所以這是經驗，不是計數。只有中間的級別被用到，輕的和重的多半閒置。每個工作開始前，卻還是得先選一次級別。兩套規則並排放著的時候，agent 還會被搞糊塗，把「哪一套適用」解釋錯。

這些背後還有一個更深的原因：工作有多難，在開始之前是看不出來的，級別卻要你先去猜。

那用什麼取代級別？是任務：照出錯的代價和任務的種類，決定要多小心（[管任務，不管對話](5-1-tasks.html)）。

### 第三刀：獨立的協調者（推理出來的，部分來自測試）

協調者其實懂這個任務，問題從來不在這裡。問題在於，懂的那個不是動手的那個，所以接手做事的 agent 得把任務再學一遍。這和我在三角色測試的紀錄裡看到的一致：協調者讀了檔案，懂了這個改動，接著實作者又從零開始，把這些檔案重新讀了一遍。

可是那個測試沒辦法把協調者單獨拿出來看。它比的是整個團隊和一個 agent，而不是有、沒有獨立協調者的兩個團隊。所以單看協調者，我沒有數字。紀錄裡那次重複閱讀，只算線索，不是量測。撐著這一刀的，是一個論證：推動任務前進的，必須懂這個任務，而手上拿著任務的那個 agent 本來就懂。

### 第四刀：請求資料夾（設計歷史，沒有數據）

最後一刀是跟著前面幾刀來的。重級別的團隊把工作放在請求資料夾裡，和任務資料夾分開，所以重級別的流程一沒了，第二個放工作檔案的地方就沒有用了。現在任務資料夾就是工作區。只有一個地方，比較好找、好備份，人或新會話讀起來也比較容易。這些我都沒有測過。

### 這幾刀拿掉了什麼，對 harness 做了什麼

算起來，1.1 版拿掉了級別、整個重級別的流程和它的指令、兩個 agent、一個 skill、設定裡的一些數字，還有請求資料夾。它也把每個 prompt 開頭注入的規則縮短成三、四行，並去掉了對搜尋次數和工具呼叫次數的限制。現在 agent 看到的規則更少，能搞糊塗的地方也更少。

這是我最相信的好處，雖然它不是量出來的。小一點的 harness，比較好說明、好測試，也比較好交給同事（[落地與治理](7-4-rollout-and-governance.html)）。至於對準確度或成本的影響，我沒有量過。

### 我選擇不做的事

前面說的都是砍，拿掉原本存在的東西。還有一類，是我一開始就決定不做的，記在第二份清單裡，每一項都附上會讓我重新考慮的條件。舉幾個例子：

- 我沒有讓 agent 之間互相傳訊息，因為子 agent 沒有狀態，跨會話的訊息也沒有驗證過。等量出它可靠了，再重新考慮。
- 我沒有讓好幾個子 agent 同時改同一批檔案。那樣會有合併衝突，而且程式碼跑不起來，就沒辦法判斷誰對，所以要等倉庫可以在本機跑測試了再說。
- 我也沒有自己做沙箱、上下文壓縮或子 agent 排程。平台一直在改這些，所以我寧可等平台。
- 建在 Preview 或實驗性設定上的功能，我也沒有做，因為它們可能改變或消失。等它們穩定了再說。

這份清單背後的習慣其實很簡單。附上理由和條件的「不」，以後可以重新打開；兩樣都沒有的「不」，會變成禁忌。

## 砍的時候會在哪裡出錯 {#costs-and-traps}

就連量過的那一刀，也是一場賭注。三角色的團隊輸掉的，是上面那次小規模的比較，而且是在一個虛構的倉庫裡。換成一個很大、很亂的倉庫，再加上一個模糊的需求，結果可能不一樣，只是兩邊我都沒有數據。如果你的任務長那樣，先測，再照我的砍法。

另外三刀沒有數據。級別、獨立的協調者和請求資料夾，是靠推理和使用經驗拿掉的，只能算判斷，讀者可以不同意，我也可能錯。我把每一刀屬於哪一種寫出來，就是為了讓你能自己判斷。

要是從這裡讀出「多 agent 不好」，那就讀錯了。我留下了一個獨立的 reviewer，理由是一段我沒測過的推理；做大範圍的閱讀時，我也會用唯讀的幫手（[慎用子 agent](2-3-subagents.html)）。我砍掉的，是照職位把一件工作切開。

一樣東西砍掉以後，要把它為什麼拿掉、什麼時候重新考慮寫下來，和當初加它的理由放在同一個地方。不然一年後，有人會因為同樣的理由把它加回來。

舊的設定需要退場的路。拿掉舊流程的時候，讓一個進行中的請求壞掉了，有舊設定的人也得手動改，1.1 的說明寫了這點。拿掉一個部分，對已經在用的人是有成本的。所以拿掉之前要交代清楚：用什麼取代、怎麼搬過去、哪些舊設定不再有效，以及進行中的工作會怎樣。

## 什麼時候重審這幾刀，什麼時候修剪不做的清單 {#when-to-delete-it}

既然砍是賭注，就得有個時候回頭再驗一次。最好的時機是模型升級之後，因為我砍的那些理由，都是那個月的模型和平台的事實。模型在長任務上會越來越好，平台有一天也可能讓已結束的子 agent 能繼續，這樣一來，協調者那一刀背後重學的成本就沒了。升級之後，重跑同樣的固定任務，看看結果（[固定的任務，用腳本打分](6-3-eval-tasks.html)）。

「沒做，等條件到了再考慮」的清單，本身也是要修剪的東西（[模型升級了，就要刪](6-5-model-upgrades.html) 對你留下的規則，用的是同一個習慣）。條件一到，不是做出來，就是劃掉。
