讀這一章，你需要讀過 [慎用子 agent](2-3-subagents.html) 和 [管任務，不管對話](5-1-tasks.html)。

## 一句話 {#in-one-sentence}

按職位分工的三個 agent 花得最多，卻沒買到任何我量得出來的東西。把它們拿掉，連同級別和獨立的協調者一起拿掉，harness 變簡單了。只有第一項砍掉的東西是量過的。

## 給主管 {#for-leaders}

- **要做的決定**：對每個 agent、規則和步驟都問：它買到了什麼，怎樣才能安全地拿掉它。然後定一個時間，回頭檢查答案。
- **風險**：設定只會越長越大，所以每個部分都在持續花上下文、維護和學習的時間。我量過的那一刀，是三個按職位分工的 agent 對一個 agent：答對的數量一樣，花費是好幾倍。四個任務，各跑一次。
- **做對的成本**：一個小時，把各部分列出來，每個寫一行。更難的成本，是告訴已經在用某個部分的人，用什麼取代它。
- **可以問團隊**：「每個 agent、規則和步驟：它買到了什麼，你怎麼知道，怎樣才能安全地拿掉？」

## 問題 {#problem}

你加進 agent 設定的每個部分，都有代價。它占上下文的空間，要有人讓它保持正確，新人要花時間學它。多數設定只會越長越大，因為加東西像是進步，拿東西像是損失。

我想對每個部分問另一個問題：**它買到了什麼，什麼時候可以拿掉**？答不出第一個，這個部分就是只有成本、沒有回報。答不出第二個，我就會永遠留著它。

我自己設定的 1.0 版，是這個問題的好考題。它有好幾個聽起來很對的部分。我發布了它，用了它，用了幾天之後，在 1.1 版裡拿掉了很大一部分。這一章列出我砍了什麼、為什麼砍。整章只守一條線：**每一刀，哪些是我量過的，哪些只是我的判斷**。

先說幾個詞。

- **級別**是使用者在每個工作開始時做的選擇：輕的級別用來快速回答，中間的用於中等的任務，重的讓好幾個 agent 一起工作。不同級別有不同的規則。
- **協調者**是只負責把工作交給別人的 agent（用法和 [慎用子 agent](2-3-subagents.html) 一樣）。在我舊的重級別裡，它是一個獨立的 agent。
- **請求資料夾**是和任務分開的另一個資料夾。重級別的團隊把計劃、交接和結果放在這裡。
- **按職位分工的 agent**是被給了一個角色的 agent，例如計劃者、實作者或 reviewer，就像一個人的團隊那樣。

## 原理 {#how-it-works}

### 一眼看完

四刀，各有多少證據。後面的小節說明原因。

| 砍掉的 | 本來想買到什麼 | 為什麼拿掉 | 證據 | 什麼時候重新考慮 |
| --- | --- | --- | --- | --- |
| 三個按職位分工的 agent | 像人的團隊那樣分工 | 花費好幾倍，結果一樣 | 量過：4 個任務，各跑一次，只看方向 | 在更大、更亂的任務上比較，顯示有好處 |
| 級別 | 規則配合工作的難度 | 只用到一個；難選；規則互相打架 | 我的使用經驗，沒有計數 | 開始之前，就能可靠地知道一個工作有多難 |
| 獨立的協調者 | 有人負責分配工作 | 懂的那個不是動手的那個；做事的要重學一遍 | 推理出來的；測試紀錄裡有線索，沒有單獨量過 | 平台可以還原一個已結束的子 agent 的上下文 |
| 請求資料夾 | 團隊檔案的獨立位置 | 團隊沒了以後，沒有東西需要它 | 從其他幾刀推出來的，沒有測 | 需要自己工作區的流程回來了 |

### 我對任何部分都用的測試

你的設定也只會越長越大，所以這些問題是問你的。留下一個部分之前，我問同樣的幾個問題（就是 [落地與治理](7-4-rollout-and-governance.html) 裡那些）：它防止什麼失敗，有真實的例子嗎？它花多少？要變成什麼樣，它才能拿掉？下面的每一刀，就是這些問題，在用過之後才遲遲回答出來。

::: figure 7-3-before-after

圖裡是兩個版本。亮著的方框是我量過的那一刀。虛線方框是我沒量的幾刀。

### 第一刀：三個按職位分工的 agent（量過）

在 1.0 裡，重模式執行一個團隊：協調者寫計劃，實作者改程式碼，reviewer 檢查。我拿它和一個 agent 單獨做同樣的四個任務比。那個測試在 [慎用子 agent](2-3-subagents.html) 裡，所以我不重複。這裡只講它的限制。

- **四個任務，各跑一次**。再跑一次，數字會動。
- **兩邊並不對等**。單一 agent 用的是頂級模型；團隊有一個知識庫可以讀（[知識庫：程式碼的誠實索引](8-1-why-a-knowledge-base.html)）。
- **我相信的是方向**。團隊花了好幾倍，答對的數量一樣。確切的倍數，我不信。

所以這一刀有數據，但數據很薄。它足以說：在那些任務上，團隊不划算。它不能說團隊永遠不划算。我留下了一個角色，獨立的 reviewer，因為獨立檢查是值得多一個 agent 的四件事之一。這是推理，不是量出來的：我沒有用量那一刀的同樣標準，單獨測 reviewer。

### 第二刀：級別（設計歷史，沒有數據）

我沒有量過級別。我有的，是用它們時看到的事。

- 只有中間的級別被用到。輕的和重的，多半閒置。
- 先選級別，是每次多一步。
- 兩套規則並排放著，讓 agent 糊塗了。它會給出錯的解釋，說哪一套適用。
- 更深的原因：工作有多難，在開始之前是看不出來的。級別要你去猜。

這是我幾天裡自己的經驗，不是計數。我沒有記錄每個級別被用了幾次。取代級別的是任務：照出錯的代價和任務的種類，決定要多小心（[管任務，不管對話](5-1-tasks.html)）。

### 第三刀：獨立的協調者（推理出來的，部分來自測試）

問題不是協調者懂不懂任務。它懂。問題是，懂的那個不是動手的那個，所以它交辦的做事者，得把任務再學一遍。這和我在三角色測試的紀錄裡看到的一致：協調者讀了檔案，懂了這個改動；實作者從零開始，又把它們讀了一遍。

那個測試比的是整個團隊和一個 agent，不是有獨立協調者和沒有的團隊，所以協調者單獨的數字我沒有。紀錄裡讀了兩次，是線索，不是量測。其餘是論證：推動任務前進的人，必須懂這個任務，而持有任務的 agent 已經懂了。

### 第四刀：請求資料夾（設計歷史，沒有數據）

重級別的團隊，把工作放在請求資料夾裡，和任務資料夾分開。重級別的流程沒了以後，第二個放工作檔案的地方就沒有用了。任務資料夾就是工作區。一個地方比較好找、好備份，人或新會話也比較好讀。我沒有測這個。它是從其他幾刀推出來的：沒有東西再需要它了。

### 這幾刀拿掉了什麼，對 harness 做了什麼

1.1 版拿掉了級別、整個重級別的流程和它的指令、兩個 agent、一個 skill、設定裡的一些數字和請求資料夾。它也把每個 prompt 開頭注入的規則縮短成三、四行，並去掉了對搜尋次數和工具呼叫次數的限制。現在 agent 看到的規則更少，能搞糊塗的地方也更少。

這是我最相信的好處，而它不是量出來的。小一點的 harness，比較好說明、好測試，也比較好交給同事（[落地與治理](7-4-rollout-and-governance.html)）。我沒有量對準確度或成本的影響。

### 我選擇不做的事

砍掉的，是原本存在的東西。還有第二份清單：我決定不做的事，每一項都附上讓我重新考慮的條件。幾個例子：

- **agent 之間互相傳訊息**。子 agent 沒有狀態，跨會話的訊息也沒有驗證過。等量出它可靠了，再重新考慮。
- **好幾個子 agent 同時改同一批檔案**。會有合併衝突，而且程式碼跑不起來，就沒辦法判斷誰對。等倉庫可以在本機跑測試了，再重新考慮。
- **我自己的沙箱、上下文壓縮或子 agent 排程**。平台一直在改這些，我寧可等平台。
- **建在 Preview 或實驗性設定上的功能**。它們可能改變或消失。等它們穩定了，再重新考慮。

這份清單背後的習慣：附上理由和條件的「不」，可以重新打開。兩樣都沒有的「不」，會變成禁忌。

## 代價和陷阱 {#costs-and-traps}

**砍掉也是一場賭注**。三角色的團隊輸了，是在四個任務、各跑一次、一個虛構的倉庫裡。一個很大、很亂、需求又模糊的倉庫，可能不一樣，兩邊我都沒有數據。如果你的任務長那樣，先測，再照我的砍法。

**不要從這裡讀出「多 agent 不好**」。我留下了一個獨立的 reviewer，理由是我沒測過的推理。我用唯讀的幫手去做大範圍的閱讀（[慎用子 agent](2-3-subagents.html)）。我砍掉的，是照職位把一件工作切開。

**沒量過的砍法，是一個判斷**。級別、獨立的協調者和請求資料夾，是靠推理和使用經驗拿掉的。讀者可以不同意，我也可能錯。我把哪個是哪個寫出來，讓你能自己判斷。

**不要砍了就忘**。把一樣東西為什麼拿掉、什麼時候重新考慮，寫下來，和當初加它的理由放在同一個地方。不然一年後，有人會因為同樣的理由把它加回來。

**舊的設定需要退場的路**。拿掉舊流程，讓一個進行中的請求壞掉了，有舊設定的人也得手動改。1.1 的說明寫了這點。拿掉一個部分，對已經在用的人是有成本的。拿掉的時候，要說明用什麼取代、怎麼搬過去、哪些舊設定不再有效，以及進行中的工作會怎樣。

## 什麼時候可以刪掉 {#when-to-delete-it}

回頭檢查一刀的最好時機，是模型升級之後。我砍的那些理由，是那個月的模型和平台的事實。模型在長任務上會越來越好，平台有一天也可能讓已結束的子 agent 能繼續，那就會去掉協調者那一刀背後重學的成本。重跑同樣的固定任務，看看結果（[固定的任務，用腳本打分](6-3-eval-tasks.html)）。

「沒做，等條件到了再考慮」的清單，本身也是要修剪的東西（[模型升級了，就要刪](6-5-model-upgrades.html) 對你留下的規則，用的是同一個習慣）。條件到了，就做出來，或者劃掉。

## 在 harness 裡探索 {#explore}

1.0 的設計已經不在現在的 harness 裡，但它的發布說明和設計筆記還在，理由也都在。harness 可以帶你走一遍。照上面的說明準備好之後，輸入：

::: prompt
/harness-rookie-wondering 我讀完了「我砍掉了什麼，數據怎麼說」這一章。請教我主題 15，設計上的選擇：為什麼沒有級別，以及 harness 刻意不做的事的清單，和各項什麼時候會重新考慮。和我一起打開 1.1.0 版的發布說明，讓我看拿掉了什麼。
:::

它一次教一小塊，停下來確認你跟得上，然後和你一起打開檔案。
