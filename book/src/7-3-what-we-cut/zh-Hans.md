读这一章之前，需要先读过[慎用子 agent](2-3-subagents.html)和[管任务，不管对话](5-1-tasks.html)。

## 一句话 {#in-one-sentence}

三个按岗位分工的 agent 花得最多，却没换来我能量出来的任何东西。把它们连同级别和单独的协调者一起拿掉，harness 简单了。只有第一刀是量过的。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对每个 agent、规则和步骤都问一遍：它换来了什么，什么情况下可以安全地拿掉。并定一个时间来复查这些答案。
- **风险**：配置只会越长越大，所以每个部分都在持续占用上下文、维护成本和学习时间。我量过的只有一刀：三个按岗位分工的 agent 对一个 agent，做对的数量一样，成本是好几倍；一共四个任务，每个只跑了一次。
- **做对的代价**：花一个小时把各部分列出来，每个写一句话。更难的代价是，要告诉已经在用某个部分的人，拿什么来替代它。
- **可以问团队**：“对每个 agent、规则和步骤：它换来了什么？你怎么知道？什么情况下可以安全地拿掉？”

## 问题 {#problem}

给 agent 配置加的每个部分都有代价。它占上下文的空间，要一直保持正确，新人还得去学它。大多数配置只会越长越大，因为加东西像是在前进，拿东西则像是在失去什么。

我想对每个部分问另一个问题：**它换来了什么，什么时候可以拿掉**？第一个答不上来，这个部分就是只花钱不回本。第二个答不上来，我就会永远留着它。

我自己配置的 1.0 版，正好拿来检验这件事。它有好几个听起来很对的部分。我发了版，用了几天，在 1.1 版里拿掉了其中很大一部分。这一章列出我砍掉了什么、为什么。通篇保持一条清楚的线：**每一刀，哪些是我量过的，哪些只是我的判断**。

先交代几个词。

- **级别**，是用户在每个工作开始时做的一个选择：轻的用来快速回答，中等的用于中等任务，重的用于几个 agent 一起干活。不同的级别规则不同。
- **协调者**，是只负责把活分给别人的 agent（这个词的用法和[慎用子 agent](2-3-subagents.html)里一样）。在我以前的重级别里，它是一个单独的 agent。
- **请求文件夹**，是和任务分开的另一个文件夹，重级别的团队把计划、交接和结果放在里面。
- **按岗位分工的 agent**，是被指定了计划者、开发者或 reviewer 这类角色的 agent，就像人的团队那样。

## 原理 {#how-it-works}

### 一览

四刀，以及每一刀有多少证据。理由在下面各节。

| 砍掉的 | 本来想换来什么 | 为什么拿掉 | 证据 | 什么时候重新考虑 |
| --- | --- | --- | --- | --- |
| 三个按岗位分工的 agent | 像人的团队那样分工 | 成本好几倍，结果一样 | 量过：4 个任务，各跑一次，只看方向 | 在更大、更乱的任务上做对比，显示有好处 |
| 级别 | 规则配合工作的难度 | 只用到一个；难选；规则互相打架 | 我的使用经验，没有计数 | 开工之前就能可靠地判断一个工作有多难 |
| 单独的协调者 | 有人负责分配工作 | 懂的那个不是动手的那个；干活的要重学一遍 | 推理出来的；测试记录里有线索，没有单独量过 | 平台能恢复一个已结束的子 agent 的上下文 |
| 请求文件夹 | 团队文件的独立位置 | 团队没了以后，没有东西需要它 | 从其他几刀推出来的，没有测 | 需要自己工作区的流程回来了 |

### 我对任何一个部分用的检验

你的配置也只会越长越大，所以这些问题是留给你的。在留下一个部分之前，我都问同样的几个问题（就是[落地与治理](7-4-rollout-and-governance.html)里的那几个）：它防止了什么故障，有真实的例子吗？它花多少？要变成什么样，它才能拿掉？下面的几刀，就是这些问题在用过之后才答出来的结果。

这张图画的是两个版本。亮着的框是我量过的那一刀。虚线框是我没量过的几刀。

### 第 1 刀：三个按岗位分工的 agent（量过）

在 1.0 里，重模式跑一个团队：协调者写计划，开发者改代码，reviewer 做检查。我拿它和一个 agent 单干，在同样的四个任务上做了对比。那个测试在[慎用子 agent](2-3-subagents.html)里，这里不再重复。这里只关心它的局限。

- **四个任务，每个只跑一次**。再跑一次，数字就会变。
- **两边条件不对等**。单个 agent 用的是顶级模型；团队有一份知识库可读（[知识库：代码的诚实索引](8-1-why-a-knowledge-base.html)）。
- **我信的是方向**。团队贵好几倍，做对的数量一样。具体倍数我不信。

所以这一刀有数据，但数据很薄。足以说明在那些任务上，团队不划算。它不能说明团队永远不划算。我留下了一个角色，也就是独立的 reviewer，因为独立检查是值得多一个 agent 的四样东西之一。这是推理，不是测量：我没有用量过的那一刀同样的标准，单独测过 reviewer。

### 第 2 刀：级别（设计史，没有数据）

我没有量过级别。我手里有的，是用它们时看到的情况。

- 只有中等级别被用到。轻的和重的大多数时候闲着。
- 先选级别，每次都多一步。
- 两套规则放在一起，会把 agent 弄糊涂。它会就“哪套适用”给出错误的解释。
- 更深的原因是：一个工作有多难，开工之前是判断不了的。级别要你去猜。

这是我几天里的亲身经验，不是计数。我没有记录每个级别被用了多少次。替代级别的是任务，谨慎的程度由出错的代价和任务的类型来定（[管任务，不管对话](5-1-tasks.html)）。

### 第 3 刀：单独的协调者（推理出来的，部分来自测试）

问题不在协调者有没有弄懂任务。它弄懂了。问题在于：弄懂的那个不是动手的那个，所以它把任务交给的干活的，还得再学一遍。这和我在三角色测试的记录里看到的一致：协调者读了文件，弄懂了要改什么，而开发者从零开始，又把它们读了一遍。

测试比较的是整个团队和一个 agent，不是有单独协调者和没有单独协调者的团队，所以单独的协调者我没有数字。记录里的重复阅读，是线索，不是测量。其余是一个论证：推动任务往前走的人必须理解它，而拿着这个任务的 agent 本来就理解。

### 第 4 刀：请求文件夹（设计史，没有数据）

重级别的团队把工作放在请求文件夹里，和任务文件夹分开。重级别的流程没了之后，再留一个放工作文件的地方就没有用了。任务文件夹就是工作区。一个地方更容易找，更容易备份，人或者新会话读起来也更容易。我没有测过这一点。它是从其他几刀推出来的：不再有东西需要它了。

### 这几刀拿掉了什么，对 harness 有什么影响

1.1 版拿掉了级别、整个重级别的流程（连同它的命令）、两个 agent、一个 skill、配置里的一些数字，还有请求文件夹。它还把注入在每条 prompt 最前面的规则缩短到三四行，并去掉了对搜索次数和工具调用次数的限制。现在 agent 看到的规则更少，能被弄糊涂的地方也更少。

这是我最信的好处，而且它不是测量出来的。更小的 harness 更容易解释，更容易测试，也更容易交给同事（[落地与治理](7-4-rollout-and-governance.html)）。对准确率和成本的影响，我没有量过。

### 我选择不做的

砍，是拿掉原来有的东西。还有第二份清单：我决定不做的东西，每一项都带着会让我重新考虑的条件。几个例子：

- **agent 之间互相发消息**。子 agent 没有状态，跨会话的消息也没有验证过。等测出来可靠了再考虑。
- **好几个子 agent 同时改同样的文件**。会有合并冲突，而且代码跑不起来，没法判断谁对。等仓库能在本地跑测试了再考虑。
- **我自己做沙箱、上下文压缩或子 agent 调度**。平台一直在改这些，我宁可等平台。
- **建立在 Preview 或实验性设置上的功能**。它们可能变，也可能消失。等稳定了再考虑。

这份清单背后的习惯是：带着理由和条件的“不”，可以重新打开。两样都没有的“不”，就成了禁忌。

## 代价和坑 {#costs-and-traps}

**砍也是一种赌注**。三角色团队是在一个虚构的仓库里、四个任务各跑一次的情况下输的。一个非常大、非常乱的仓库，加上一个含糊的需求，结果可能不同，两边我都没有数据。如果你的任务像那样，抄我的砍法之前先测一下。

**别从这里得出“多 agent 不好”**。我留下了独立的 reviewer，依据是我没测过的推理。我用只读的帮手做大范围阅读（[慎用子 agent](2-3-subagents.html)）。我砍掉的，是把一份工作按岗位拆开。

**没量过的一刀，只是判断**。级别、单独的协调者和请求文件夹，是凭推理和使用经验拿掉的。读者可以不同意，我也可能错。我写明了哪些是哪种，好让你自己判断。

**砍了就忘，不行**。把一样东西为什么拿掉、什么时候重新考虑，写在你当初记下加它的理由的同一个地方。不然一年后有人出于同样的理由把它加回来。

**旧的配置需要出路**。拿掉旧流程，弄坏了一个进行中的请求，用着旧设置的人得手工改。1.1 版的发布说明里写了这一点。拿掉一个部分，对已经在用它的人是有代价的。你拿掉一个东西时，要说明拿什么来替代，怎么迁移，哪些旧设置不再生效，进行中的工作会怎样。

## 什么时候可以删掉 {#when-to-delete-it}

复查这几刀的最好时机，是模型升级之后。我砍的理由，是那个月的模型和平台的事实。模型在长任务上会越来越好，平台有一天也可能让已结束的子 agent 能接着干，那就会去掉协调者那一刀背后重学的成本。重跑同样的固定任务，看看结果（[固定的任务，用脚本打分](6-3-eval-tasks.html)）。

“不做，等条件到了再考虑”的清单，本身也是要修剪的东西（[模型升级了，就要删](6-5-model-upgrades.html)对你留下的规则，用的是同一个习惯）。条件到了，就做出来，或者划掉。
