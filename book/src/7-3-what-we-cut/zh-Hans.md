读这一章之前，需要先读过[别跟风瞎用子 Agent](2-3-subagents.html)和[一个任务一个文件夹](5-1-tasks.html)。

## 一句话 {#in-one-sentence}

三个按岗位分工的 agent 花得最多，却没换来我能量出来的任何东西。把它们连同级别和单独的协调者一起拿掉，harness 简单了，不过量过的只有第一刀。

## 写给管理者 {#for-leaders}

- **要拍板的事**：对每个 agent、规则和步骤都问一遍，它换来了什么，什么情况下可以安全地拿掉，再定一个时间复查这些答案。
- **风险**：配置只会越长越大，每个部分都在持续占用上下文、维护成本和学习时间。我量过的只有一刀，三个按岗位分工的 agent 对一个 agent：做对的数量一样，团队的成本是好几倍（一共四个任务，每个只跑了一次）。
- **做对的代价**：花一个小时把各部分列出来，每个写一句话。更难的代价是，要告诉已经在用某个部分的人，拿什么来替代它。
- **可以问团队**：“对每个 agent、规则和步骤：它换来了什么？你怎么知道？什么情况下可以安全地拿掉？”

## 每个部分换来了什么，什么时候可以拿掉？ {#problem}

往 agent 配置里加的每个部分都有代价：它要占上下文的空间，要有人一直让它保持正确，每个新人还得去学它。可大多数配置只会越长越大，因为加东西感觉像在前进，拿掉东西却像是在失去什么。

所以我想换个问题去问每个部分：**它换来了什么，什么时候可以拿掉**？前一半答不上来，这个部分就是只花钱不回本；后一半答不上来，我就会永远留着它。

我自己配置的 1.0 版，正好拿来检验这件事，因为它有好几个听起来很对的部分。我发了版，用了几天，然后在 1.1 版里拿掉了其中很大一部分。下面讲我砍掉了什么、为什么砍，一路上我最想讲清楚的一条线是：**每一刀，哪些是我量过的，哪些只是我的判断**。

要看懂这几刀，得先知道那个版本是怎么运作的。每个工作开始时，用户要先选一个**级别**：轻的用来快速回答，中等的用于中等任务，重的让几个 agent 一起干活，而每个级别各有各的规则。**按岗位分工的 agent**，是被指定了计划者、开发者或 reviewer 这类角色的 agent，就像人的团队那样。重级别就是用它们搭起来的。这么多角色，谁来分活？是**协调者**，也就是只负责把活分给别人的 agent（这个词的用法和[别跟风瞎用子 Agent](2-3-subagents.html)里一样）。在重级别里，它是一个单独的 agent。这个团队把计划、交接和结果放在**请求文件夹**里，那是和任务分开的另一个文件夹。

从这套设计里砍下了四刀，可每一刀背后的证据并不是同一种。

## 四刀，每一刀有多少把握 {#how-it-works}

### 一览

下面这张表把四刀并排放在一起，每一刀背后有什么证据也写在里面，理由则放在后面几节。

| 砍掉的 | 本来想换来什么 | 为什么拿掉 | 证据 | 什么时候重新考虑 |
| --- | --- | --- | --- | --- |
| 三个按岗位分工的 agent | 像人的团队那样分工 | 成本好几倍，结果一样 | 量过：4 个任务，各跑一次，只看方向 | 在更大、更乱的任务上做对比，显示有好处 |
| 级别 | 规则配合工作的难度 | 只用到一个；难选；规则互相打架 | 我的使用经验，没有计数 | 开工之前就能可靠地判断一个工作有多难 |
| 单独的协调者 | 有人负责分配工作 | 懂的那个不是动手的那个；干活的要重学一遍 | 推理出来的；测试记录里有线索，没有单独量过 | 平台能恢复一个已结束的子 agent 的上下文 |
| 请求文件夹 | 团队文件的独立位置 | 团队没了以后，没有东西需要它 | 从其他几刀推出来的，没有测 | 需要自己工作区的流程回来了 |

### 我对任何一个部分用的检验

一刀刀看之前，先说这几刀背后的检验。你的配置其实也只会越长越大，所以这些问题不只是我在问自己，也是留给你的。决定要不要留下一个部分时，我都会问同样的几个问题（就是[怎么把 Agent 配置推广到整个团队？](7-4-rollout-and-governance.html)里的那几个）。它防止了什么故障，有真实的例子吗？它花多少？要变成什么样，它才能拿掉？下面这几刀，就是这些问题晚了一步才得到的答案。

### 第 1 刀：三个按岗位分工的 agent（量过）

在 1.0 里，重级别会跑一个团队：协调者写计划，开发者改代码，reviewer 做检查。我拿它和一个 agent 单干做对比，用的是同样的四个任务。那个测试在[别跟风瞎用子 Agent](2-3-subagents.html)里讲过，这里不再重复，只说它有哪些局限。

头一个局限是规模小。四个任务每个只跑了一次，再跑一次，数字就会变。第二个局限是两边的条件不对等。单个 agent 用的是顶级模型，团队却有一份知识库可读（[为什么要给代码建一个知识库？](8-1-why-a-knowledge-base.html)）。局限这么多，这个测试还能信什么？我信的是方向，也就是团队贵了好几倍，做对的数量却一样。具体的倍数，我不信。

这足以说明在那些任务上团队不划算，却不能说明团队永远不划算。不过，团队也没有整个拿掉。我留下了一个角色，就是独立的 reviewer，因为独立检查是值得多开一个 agent 的四样东西之一。只是这一条靠的是推理：量那一刀的标准，我从没单独拿来测过 reviewer。

### 第 2 刀：级别（设计史，没有数据）

关于级别，我手里有的只是几天里用它们时看到的情况。我没有记录每个级别各用了多少次，所以这是经验，不是计数。只有中等级别被用到，轻的和重的大多数时候都闲着。每个工作开始前，却还是得先选一次级别。两套规则放在一起时，agent 还会被弄糊涂，把“哪套适用”解释错。

这些背后还有一个更深的原因：一个工作有多难，开工之前是判断不了的，级别却要你先去猜。

那用什么替代级别？是任务，谨慎的程度由出错的代价和任务的类型来定（[一个任务一个文件夹](5-1-tasks.html)）。

### 第 3 刀：单独的协调者（推理出来的，部分来自测试）

协调者其实弄懂了任务，问题从来不在这里。问题在于，弄懂的那个不是动手的那个，于是接手干活的 agent 还得把任务再学一遍。这和我在三角色测试的记录里看到的一致：协调者读了文件，弄懂了要改什么，接着开发者又从零开始，把这些文件重新读了一遍。

可这个测试没法把协调者单独拎出来看。它比较的是整个团队和一个 agent，而不是有、没有单独协调者的两个团队。所以单看协调者，我没有数字。记录里那次重复阅读，只算线索，不是测量。撑着这一刀的，是一个论证：推动任务往前走的，必须理解这个任务，而手里拿着任务的那个 agent 本来就理解。

### 第 4 刀：请求文件夹（设计史，没有数据）

最后一刀是跟着前面几刀来的。重级别的团队把工作放在请求文件夹里，和任务文件夹分开，所以重级别的流程一没了，再留第二个放工作文件的地方就没有用了。现在任务文件夹就是工作区。只有一个地方，找起来、备份起来都更容易，人或者新会话读起来也更省事。这些我都没有测过。

### 这几刀拿掉了什么，对 harness 有什么影响

算下来，1.1 版拿掉了级别、整个重级别的流程（连同它的命令）、两个 agent、一个 skill、配置里的一些数字，还有请求文件夹。它还把注入在每条 prompt 最前面的规则缩短到三四行，并去掉了对搜索次数和工具调用次数的限制。现在 agent 看到的规则更少，能被弄糊涂的地方也更少。

这是我最信的好处，虽然它不是测量出来的。更小的 harness 更容易解释、更容易测试，也更容易交给同事（[怎么把 Agent 配置推广到整个团队？](7-4-rollout-and-governance.html)）。至于对准确率和成本的影响，我没有量过。

### 我选择不做的

前面说的都是砍，拿掉原来有的东西。还有一类，是我一开始就决定不做的，记在第二份清单里，每一项都带着会让我重新考虑的条件。举几个例子：

- 我没有让 agent 之间互相发消息，因为子 agent 没有状态，跨会话的消息也没有验证过。等测出来可靠了，再重新考虑。
- 我没有让好几个子 agent 同时改同样的文件。那样会有合并冲突，而且代码跑不起来，没法判断谁对，所以要等仓库能在本地跑测试了再说。
- 我也没有自己做沙箱、上下文压缩或子 agent 调度。平台一直在改这些，所以我宁可等平台。
- 建立在 Preview 或实验性设置上的功能，我也没有做，因为它们可能变，也可能消失。等它们稳定了再说。

这份清单背后的习惯其实很简单。带着理由和条件的“不”，以后可以重新打开；两样都没有的“不”，就成了禁忌。

## 砍的时候会在哪里出错 {#costs-and-traps}

就连量过的那一刀，也是一种赌注。三角色团队输掉的，是上面那次小规模的比较，而且是在一个虚构的仓库里。换成一个非常大、非常乱的仓库，再加上一个含糊的需求，结果可能就不一样了，只是两边我都没有数据。如果你的任务是那样的，抄我的砍法之前先测一下。

另外三刀没有数据。级别、单独的协调者和请求文件夹，是凭推理和使用经验拿掉的，只能算判断，读者可以不同意，我也可能错。我把每一刀属于哪一种写清楚，就是为了让你自己判断。

要是从这里读出“多 agent 不好”，那就读错了。我留下了独立的 reviewer，依据是一段我没测过的推理；做大范围阅读时，我也会用只读的帮手（[别跟风瞎用子 Agent](2-3-subagents.html)）。我砍掉的，是把一份工作按岗位拆开。

一样东西砍掉以后，要把它为什么拿掉、什么时候重新考虑，写在当初记下加它的理由的同一个地方。不然一年以后，会有人出于同样的理由把它加回来。

旧的配置需要出路。拿掉旧流程时，弄坏了一个进行中的请求，用着旧设置的人也得手工去改，1.1 版的发布说明里写了这一点。拿掉一个部分，对已经在用它的人是有代价的。所以拿掉之前要交代清楚：拿什么替代、怎么迁移、哪些旧设置不再生效，以及进行中的工作会怎样。

## 什么时候重审这几刀，什么时候修剪不做的清单 {#when-to-delete-it}

既然砍是赌注，就得有个时候回头再验一次。最好的时机是模型升级之后，因为我砍的理由，都是那个月的模型和平台的事实。模型在长任务上会越来越好，平台有一天也可能让已结束的子 agent 接着干，那样一来，协调者那一刀背后重学的成本就没了。升级之后，重跑同样的固定任务，看看结果（[改了配置，怎么知道是不是变好了？](6-3-eval-tasks.html)）。

“不做，等条件到了再考虑”的清单，本身也是要修剪的东西（[换了新模型，旧规则该删了](6-5-model-upgrades.html)对你留下的规则，用的是同一个习惯）。条件一到，要么做出来，要么划掉。
